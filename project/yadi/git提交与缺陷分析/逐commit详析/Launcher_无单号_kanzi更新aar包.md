## 为什么能修复
上游 aar 内部修复，应用侧零改动。值得注意的隐患：**aar 体积从约 235MB 涨到 513MB**，直接翻倍，会显著增大 APK/系统镜像体积并可能拖慢启动加载，建议向上游确认是否为调试符号/多余 ABI 混入；同时 aar 无版本号区分（同名 kanzi-release.aar），仅靠提交历史追溯版本，建议引入版本化命名或依赖仓库。

## 复盘经验
- 二进制依赖修复必须留痕：提交消息应写明上游版本号/修复点/关联缺陷单，否则事后无法回答"这个 aar 修了什么"。
- 大体积 aar 更新要盯住体积变化曲线，翻倍级增长往往是打包配置回归（debug 符号、重复 so），需在合入前拦截。
- 同名覆盖式依赖（libs/*.aar）不利于审计，中大型车机项目应走私有 maven + 版本锁定。
