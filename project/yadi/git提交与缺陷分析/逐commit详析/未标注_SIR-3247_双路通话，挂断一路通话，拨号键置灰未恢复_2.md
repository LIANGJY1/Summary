# SIR-3247 · 双路通话挂断一路后拨号键置灰不恢复
- **提交**：`b4d433cb` | 2026-07-31 | liujinfeng | BTPhone | bugfix
- **缺陷库**：等级 B · 频次 必现-80%~100% · 状态 关闭 · 域 蓝牙电话

## 问题
双路通话中挂断一路后，拨号盘拨打键仍置灰，无法再次用拨号盘发起新通话。

## 根因分析
拨号键可用性由 `InCallServiceImpl.updateDialPadButtonState()` 决定：它读取 `UiCallManager.get().getCalls().size()`，按 `isShouldDisableCallBtn(2)`（通话数≥2 置灰）通过 RxBus 发 `DIAL_PAD_ENABLE_STATE_CHANGED` 给界面。问题在刷新时机链有洞：`onCallAdded` 里原来把 `updateDialPadButtonState()` 放在回调分发**之前**（HFP 校验、`callback.onTelecomCallAdded` 执行前），第二路进入时统计的还是 1 路，按钮被误判；而挂断/异常号码呼叫失败走的是**通话状态变更**路径，该路径上完全没有刷新调用——通话对象已减少但按钮状态事件从未补发，置灰保持。缺陷库结论一致："异常号码的场景判断有问题，补充刷新逻辑覆盖异常号码场景"。注意：提交消息写"修改通话数量计算"，但 diff 并未改动数量计算本身（仍是 `getCalls().size()`），实为**补刷新时机**，以 diff 为准。

## 关键代码修改
改动文件：`application/BTPhone/src/main/java/com/yadea/btphone/telecom/InCallServiceImpl.java`
```diff
--- application/BTPhone/.../telecom/InCallServiceImpl.java (onCallAdded)
-        // 【新增】更新拨号盘按钮状态
-        updateDialPadButtonState();
-
         // 【新增】在注册回调前，先验证蓝牙HFP状态
         boolean isHfpConnected = UiBluetoothMonitor.get().isHfpConnected();
         ...
         for (Callback callback : mCallbacks) {
             callback.onTelecomCallAdded(telecomCall);
         }
+        // 【新增】更新拨号盘按钮状态
+        updateDialPadButtonState();
--- (通话状态变更处理处，状态转换/通知中间件之后)
             }
             LogUtils.e(TAG, "==================================================");
         }
+        updateDialPadButtonState();
         // 将系统通话状态转换为对外通知的状态并发送给中间件
         Constants.setCallState(state);
```
（同提交另在 `setFavDownloadState` 增加下载失败/不支持时 post `FAVORITES_SYNC_FAIL` 事件，与拨号键无关，属搭车修复。）

## 为什么能修复
两处时机补齐：状态变更路径（挂断、呼叫失败、异常号码结束）现在必发一次按钮状态事件，`getCalls().size()` 已回落到实际值，按钮恢复可用；`onCallAdded` 的刷新移到回调分发之后，第二路通话真正入列后才统计，双路置灰判定准确。隐患：RxBus 事件无去重，状态抖动时会连发多次；按钮最终一致性仍依赖"每个状态变更都触发刷新"这条约定，新增通话路径时仍可能再漏。

## 复盘经验
- 派生 UI 状态（按钮可用性=通话数量的函数）的刷新要挂在"所有能改变输入的状态迁移点"上，只挂在部分路径是这类 stale 状态 bug 的通病。
- 修复动作应放在数据真正就位之后（回调分发完/集合更新完），提前刷新读到旧快照等于没刷。
- 提交消息描述与 diff 不符（"修改数量计算" vs 实际补刷新）时，回看历史会被误导，写 commit 要按实际改动表述。
