# 无单号 · 主交互拉起导航逻辑添加配置项

- **提交**：`17358a35` | 2026-06-26 | ljl | SystemUI(DigitalKey) | feature
- **关联单**：模块号 LH2025028-1614（无缺陷关联）

## 需求/目标
给"主交互（数字钥匙上车进入仪表模式）后自动拉起导航到前台"的逻辑加一个总开关 `isNeedStartNavi`，为后续可能去掉拉导航行为预留配置位。顺带把 Linux 仪表形态的监听从"一次性观察"改为"持续观察"。

## 实现结构
- `DigitalKeyVehicleService.kt`：删除 `initLinuxState()` 中"displayState 有值只同步一次、无值才注册一次性 Observer（收到后 removeObserver）"的分支逻辑，统一改为 `displayState.observe(mLifecycleOwner)` 持续监听，每次变化都重置 `PageStateMachine.setCurState` 并调用 `handleDisplayState`。
- `PageStateMachine.kt`：新增 `isNeedStartNavi` 布尔配置（默认 true），在 `setNavForeground()` 入口、S1 进入处理器 `bringNavToForeground()` 调用点、`transitionTo` 内 B1+navForeground 自动流转 S4 的判断处共 4 处增加该开关短路判断。

数据流：Linux 侧 displayState → SystemSettingsControllerService (LiveData) → DigitalKeyVehicleService 常驻观察 → PageStateMachine 状态同步；导航拉起动作用 `isNeedStartNavi` 门禁。

实现讲解：开关采用"入口短路 + 判断点内联"的手法——不是把整个特性删掉，而是在所有拉导航触发点前置 `if (!isNeedStartNavi)`，行为可一键回切。displayState 观察从"消费一次即注销"改为常驻观察，修掉了"初始化时无值、注册观察后 Linux 端再变化则永远收不到"的时序隐患。

## 复盘与要点
- 可复用手法：对"后续可能要砍掉/可配的行为"，与其写死不如在触发点加单一布尔门禁，改动小且可逆；本提交 4 个判断点都收敛在 PageStateMachine 一个文件内，便于将来换成 SettingsProvider/车控配置源。
- 原一次性 Observer 写法（收到即 removeObserver）是典型的"初始化竞态补丁"，常驻观察更稳，但要注意回调里 `handleDisplayState` 会重复执行，需保证其幂等。
- 遗留风险：`isNeedStartNavi` 目前是硬编码 `true` 的成员变量，没有任何运行时配置来源，"配置项"名不副实，后续要真正可配还需接配置下发通道。
