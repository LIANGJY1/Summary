# SIR-6584 / SIR-6585 · 电话本号码 +86 171 3860 0000 未显示 +86

## 问题
蓝牙电话本中的手机号码 `+86 171 3860 0000` 在联系人列表里显示时丢失了 `+86` 国家码前缀。

## 根因分析
`ContactsAdapter` 绑定号码时取的是 `ContactData.PhoneItem.getNumber()`（规范化后的号码，可能已剥离 `+86`），再交给 `TelecomUtils.getFormattedNumberWithPlus()` 格式化。该方法的逻辑是按中国区格式化，且只有当"格式化结果不以 + 开头 && 原号码以 86 开头"时才补 `+`——对 `17138600000` 这种已无 86 前缀的规范化号码，它只会产出 `171 3860 0000`，永远补不回 `+86`。真正携带 `+86` 的 `PhoneItem.getRawNumber()` 根本没被使用。同时 `StringUtil` 里 `formatContactsListPhoneSpaces` 与 `formatPhoneSpaces` 存在两套近似的 70 行级重复实现（含 `getString86` 副本），搜索页与列表页行为不一致。

## 为什么能修复
展示来源从"规范化号码 + 电信工具按国内格式重排"改为"优先用带 + 的原始号码（rawNumber），再走自研 `formatPhoneSpaces`"：该方法解析 `+86` 国家码后对本地段做 3-4-4 分组，产出 `+86 171 3860 0000`，前缀不再丢失。两套格式化合并为一份实现，列表与搜索结果一致。附带变更：5 位服务号保持原样（修复 10086 被显示成 100 86 的衍生问题）。隐患：`formatPhoneSpaces` 的国家码表是硬编码白名单，未覆盖的国家码走"1~3 位兜底"，极长国际号码按规则原样展示。

## 复盘经验
- 数据模型里同时存在 normalized number 与 rawNumber 时，展示层必须明确优先级（带 + 的原始号优先），不要让"格式化工具"用猜测去重建国家码。
- `PhoneNumberUtils.formatNumber*` 强依赖 locale 假设（本例硬编码 CN），跨国号码场景慎用；自研格式化要集中一份实现。
- 复制出来的格式化函数（formatContactsListPhoneSpaces / formatPhoneSpaces）必然漂移，发现重复实现应立刻收敛。
