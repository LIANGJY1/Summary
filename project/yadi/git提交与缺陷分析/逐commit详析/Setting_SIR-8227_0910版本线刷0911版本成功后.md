# SIR-8227/8458 · 0910线刷0911后上电重启持续卡开机logo

- **提交**：`700f5aa8` | 2026-09-16 | sgh | Setting | bugfix
- **缺陷库**：等级 A · 频次 偶现-低于10% · 状态 关闭 · 域 开机动画

## 问题
0910 版本线刷升级到 0911 成功后，上电重启持续卡在开机 logo，无法进入系统，属 A 级阻塞类问题。

## 根因分析
`component/CommonTools` 的 `SeatUserManager`（object 单例）在 `init` 块里执行 `file.parentFile?.mkdirs()` 并 `loadFromDisk()`，而该单例在应用进程极早期（开机阶段）就会被触碰。线刷升级后首次上电属于"首次开机"场景，此时系统 `vold` 尚未完成 `/data/data` 的 CE（Credential Encrypted）用户存储准备，提前在 CE 路径创建目录/落盘会触发 `prepareUserStorage` 失败（ENOTEMPTY），进而阻塞系统启动流程，表现为卡开机 logo。原代码把"创建目录"放在了类初始化路径上（`init` 块），等于在存储未就绪的窗口期必然触碰 `/data`。

## 关键代码修改
改动文件：component/CommonTools/src/main/java/com/yadea/common/manager/SeatUserManager.kt
```diff
--- component/CommonTools/src/main/java/com/yadea/common/manager/SeatUserManager.kt
@@ init
     init {
-        file.parentFile?.mkdirs()
         cache = loadFromDisk()
         LogUtils.d(TAG, "init share config success，cache: $cache")
     }
@@ saveToDisk
+        val isReady = isUserStorageReady()
+        LogUtils.d(TAG, "isReady: $isReady")
+        if (!isReady) {
+            LogUtils.d(TAG, "saveToDisk skip: user CE storage not ready")
+            return
+        }
         var fos: FileOutputStream? = null
         try {
+            file.parentFile?.mkdirs()
             fos = atomicFile.startWrite()
@@ 新增门控
+    private fun isUserStorageReady(): Boolean {
+        return try {
+            val ctx = ContextGet.applicationContext() ?: return false
+            val um = ctx.getSystemService(Context.USER_SERVICE) as UserManager
+            um.isUserUnlocked(Process.myUserHandle())
+        } catch (e: Exception) {
+            LogUtils.e(TAG, "isUserStorageReady fail", e)
+            false
+        }
+    }
@@ addUser / userExists 同步门控
+        if (!isUserStorageReady()) {
+            LogUtils.d(TAG, "addUser skip: CE storage not ready, userId=$userId")
+            return -1
+        }
+        if (!isUserStorageReady()) {
+            return true   // userExists：解锁前视为已存在，防止调用方反复 addUser
+        }
```

## 为什么能修复
三处联动把"触碰 CE 存储"的时机整体推迟到 `UserManager.isUserUnlocked` 为真之后：初始化不再创建目录；写盘（`saveToDisk`）未就绪直接跳过，且 `mkdirs` 挪进写路径懒执行；`addUser` 在未就绪时返回 -1 防止"假成功"；`userExists` 未就绪时返回 true，避免 Launcher 的 `ensureCurrentUserExists` 在解锁前循环补建用户。开机关键路径上不再有任何对未就绪存储的写操作，卡 logo 的触发链被切断。隐患：未就绪期间的数据写入被丢弃（本次内存态仍在 `cache`），若恰有重要配置在解锁前产生，需依赖后续某次 `saveToDisk` 补写；`userExists` 恒真可能让解锁前的用户态查询拿到偏乐观结果。

## 复盘与经验
- 车机"首次开机/升级后首启"是存储就绪的最坏窗口：单例 `init` 块里绝不能做文件系统写操作（mkdirs/startWrite），一切落盘都要过 `isUserUnlocked` 门控。
- A 级卡开机问题的排查起点常在一个不起眼的工具类静态初始化——触碰即执行（object init / static block）的代码要按"开机关键路径"标准审查。
- 读路径不落盘（loadFromDisk 只读）所以无需门控，写路径才需要——门控粒度按读写区分，避免过度防御拖慢启动。
