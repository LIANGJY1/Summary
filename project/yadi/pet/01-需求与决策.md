## 1. 概述

萌宠是车机主界面上由 **Kanzi 实时渲染**的虚拟宠物角色，与 3D 车模共处同一 3D 场景（共享渲染画布 kanzi_surface），位于车模旁固定位置，主界面为核心展示区。Launcher 侧萌宠服务负责信号采集、动作仲裁与指令下发，是 VPA 的视觉反馈层。
职责红线：服务不关心显隐渲染细节与画面；显隐仅两个入口（G1 开关、G7 失败兜底）。

## 2. 全局决策（D）

- **D001 全新起步**：展车版本萌宠代码为 demo 废弃代码，这部分代码不要修改不要侵入不要使用就当不存在；设计可以适当参考；例外：音源监听（AudioSourceMonitor）、aiLit 语音链路属已实装基础设施，可复用能力。
- **D002 中断恢复统一走 setRenderStop/Start 记忆-恢复**：stop 记住当前动作，start 恢复并重新计时；状态型动作恢复前按实时信号校验重建，不机械还原。
- **D003 新旧两版共存 main，入口开关一键切换**：`Myapplication.USE_NEW_PET_SERVICE`（默认 false＝展车版）双闸生效——生命周期挂载二选一＋`KanziDataSourceManager` 的 `VPA.` 数据分流。两包互不引用；正式投入前 main 构建行为＝展车版。
- **D004 上电周期＝进程生命周期**：进程初始化即上电，进程重启即新周期；"每上电至多一次"类标记随进程内存，不持久化。
- **D005 前台判定统一走 Render，档位不参与萌宠判定**（2026-09-09 需求方勘误，**代码已实施同日**）：式样原文中所有档位判断（出场触发的 P 档、D/R 终止、循环/点击的"驻车桌面"前置等）均系"萌宠页面是否在前台"的误写。前台判定统一使用 Launcher 既有机制：**`setRenderStart()`＝萌宠页面在前台、`setRenderStop()`＝在后台**（既有仲裁点：`KanziDataSourceManager.checkAndPerformRenderState()`，按前台状态＋仪表形态∈{0,3}决定）。推论：①出场触发＝IviReady＋前台＋未插枪；②出场终止＝页面切后台（原 D/R 终止作废），回前台不恢复出场；③循环/点击前置＝前台；④档位信号与 GearValid 不再被萌宠需要（DEP-6 关闭）。实现：`GearChanged` 事件/档位订阅/gear 字段全部移除；`PetCore.onRender` 入口＋setRenderStart/Stop 处按入口开关透出；状态机默认前台（Launcher 开机即前台，首个生命周期沿对齐）。

| G7 | 保活不做；发送失败重试 1~2 次后调隐藏接口兜底 |

## 4. 术语（仅保留易混项）

- **萌宠形象开关 / 萌宠形象**：决定显隐的单一设置项（避免叫"萌宠开关"）／设置页可选外观，只决定呈现。
- **车控车设 / 萌宠 App / PPX 阶段**：设置数据现由 Setting 应用提供／未来承接萌宠设置的独立应用（尚未存在）／两者之间的过渡期。
- **出场动作**：上电一次性迎接动画，播完转常驻待机（避免：开场动作）。
- **常驻待机 / 常驻动作 / 随机动作**：默认持续状态（避免：常驻态）／两次随机之间的基础待机动作（5~10s）／循环中抽取的短微动作（无音效）。
- **驻车桌面**：~~P 档驻车状态下的桌面形态~~ **作废（D005）**——原以 P 档代指"萌宠页面在前台"，统一改用后者表述。
- **共享渲染画布**（kanzi_surface）：主界面唯一 Kanzi 驱动渲染区域（避免：双 surface）。
- **点击热区**：随萌宠屏幕位置动态变化的命中区域，Kanzi 判定。
- **动作开始回调 / 动作完成回调**：Kanzi→服务"已开始"/"已播完"事件；**动作终止信号**：服务→Kanzi"立即停止"指令。
