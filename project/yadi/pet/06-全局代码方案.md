# 全局代码方案（萌宠服务）

> 版本：v0.4（生产结构最优化＋测试代码最小化）　　日期：2026-08-27
> 输入：SRS_001~012 结论（04 档案）＋全局规则 G1~G7＋D001/D002（01-需求规格）
> 两条主线：①**生产代码按最优领域结构设计**——职责单一的类、端口注入（Scheduler/Clock/存储接口），
> 可测性来自端口而非砍类；②**测试代码最少**——场景表驱动＋3 个微型 Fake，
> 新增用例＝加一行数据，不写新测试类、不用 mock 框架。
> 未确定需求全部收敛到 PetConfig／stub 源／可整表替换的规则表，定一条落地一条。

## 1. 设计原则

1. **领域结构优先**：每个领域概念一个类（仲裁器、状态机、空闲循环各司其职），依赖只通过构造器注入端口——这是最优架构，也是可测性的来源（换 Fake 即测）。
2. **薄平台**：Android 侧只做采集（沿提取）/执行/持久化，全部接口化可替换。
3. **时间与随机注入**：Scheduler＋RandomSource 端口，测试手动推进、固定种子，确定性。
4. **不确定点隔离**：每个 TBD/TD/DEP ↔ 唯一落点（§5）；竞合规则表整体可换（F39）。
5. **职责红线**（F20/G6/G7）：只管动作轨；显隐仅两个入口；保活不做。

## 3. 协议与流转

**PetEvent**：SwitchChanged｜GearChanged｜PlugChanged｜BatteryLow(20% 沿)｜AudioStarted/Stopped｜
VoiceWake/VoiceEnd｜Clicked｜IviReady｜LongIdleSignal｜RenderStop/Start（Activity 生命周期＋非 P 档两路归一）｜
ActionStart/EndCallback(action)｜TimerFired(id)｜WeatherPushed｜BirthdaySignal｜FestivalSignal
（无 PowerOn：上电周期＝BootEpoch，进程重启不产生新周期，H1）

**PetCommand**：PlayAction｜StopAction｜Hide｜Show｜WearSkin｜PlaySound/StopSound｜
ScheduleTimer/CancelTimer｜SaveOnceMark｜ReportStatus（生日回传，M7）

**主流程**（规则见 01）：IviReady 沿→校验 P＋未插枪→出场 1 次（单次标记＋BootEpoch 防重）→
EndCallback(＝落位)→IdleLoop 启动→各联动沿申请→Arbiter 裁决→状态机出指令。
RenderStop/Start→快照/恢复（状态型先按实时信号重建）。PlayAction 即挂看门狗；
TimerFired 先于回调→失败处理或复位常驻（H2）。

## 4. 测试方案（已定稿：一键全量、代码最少）

**三项裁决**（2026-08-27）：
- **位置**：测试代码放 `application/Launcher/src/test/`，**仅本地使用、不提交仓库**
  （路径加入 `.git/info/exclude` 或本地分支保留；`test/fakes/` 即 `src/test` 内的 `pet/fakes` 包）。
- **断言粒度**：**按序包含**——期望指令按顺序出现于实际指令流即通过（抗噪；漏发关键指令仍失败）。
- **触发**：纯手动一键，不挂 git hook。

**形态**：一张场景表＋一个跑表器＋一条命令。

```
// PetScenarios.kt —— 全部用例＝这张表；加用例＝加一行，用例名＝场景描述
data class Step(val event: PetEvent? = null, val tick: Long = 0L)   // tick＝推进虚拟时钟 ms
val ALL = listOf(
    Case("开关关闭_下发隐藏", Step(SwitchChanged(false)), expect = listOf(Hide)),
    Case("首次上电_默认开启并常驻起步",
        Step(IviReady), Step(GearChanged(P)), Step(tick = 12_000),
        expect = listOf(PlayAction(RESIDENT), PlayAction(RANDOM_1))),
    /* 每条需求规则一行，约 60+ 行 */
)

// PetScenariosTest.kt —— runner 只写一次
@Test fun scenarios() = ALL.forEach { c -> PetHarness(MiniFakes()).run(c).assertInOrder(c.name) }
```

**一键命令**（写完功能→敲命令→全表红绿，失败行＝未实现/实现错的规则编号）：

```
./gradlew :application:Launcher:testDebugUnitTest --tests "*PetScenarios*"
```

| 层 | 覆盖 | 方式 |
|---|---|---|
| core 领域层＋装配 | 全部需求规则行为（开关/出场/竞合/恢复/看门狗/防抖/单次防重…）＋ Fake 装配冒烟 | 上表自动跑 |
| platform（真机画面/音频焦点实占/CAN 实采） | 不自动化 | 每阶段末手测冒烟 |

写法约束：不用 mock 框架、不用 Robolectric（core 零 Android 依赖）、固定随机种子、
时钟手动推进——无 sleep 无 flaky。每阶段先加该阶段规则场景行（RED）→实现（GREEN）→真机冒烟。

## 4A. 编码规范（写码铁律，萌宠包内全适用）

1. **注释**：
   - 每个类：一行职责说明（这个类管什么、不管什么）。
   - 每个方法：一行 KDoc——做什么＋关联规则编号（如 “竞合裁决。规则表＝02 矩阵（TD-17 待定稿），整表可换”）。
   - 关键分支/状态迁移处：一行行内注释讲**为什么**，不复述代码。言简意赅，禁止废话注释。
2. **日志**（统一用项目 `com.yadea.common.utils.LogUtils`，TAG＝类名）：
   - 每个方法入口（含关键入参）一条 `LogUtils.d`；出口/结果一条 `LogUtils.d`。
   - 关键节点用 `LogUtils.i`：状态迁移、指令下发、竞合裁决结果、看门狗触发、恢复重建、显隐切换。
   - **日志必须带规则编号**，联调时可直接对文档定位，例：`LogUtils.i(TAG, "dispatch: G1 off→hide")`。
3. **密度红线**：一次状态迁移＝1 条 d；裁决结果变更/看门狗触发/恢复重建＝1 条 i；**禁止循环内打日志**。
