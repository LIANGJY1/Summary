## 工作方式（已对齐）

- 我提 SRS 条目 → 在 04 追加条目（状态行＋事实 2~4 行＋问答有序列表、答案以 `QA:` 另起一行＋开放点挂条目下）；
  原文大表不保留，信息全部并入事实与问答。
- 澄清问题每题附推荐答案；我答复简短（"按推荐／记课题／忽略"）。
- 代码里查得到的信息（信号映射、工具类）自己去仓库查，不问我。
- 编号 F/D/G/TBD/TD/DEP 全局单调递增、永不复用；裁决后划线留痕并注明结论。
- 所有讨论结论必须落盘，不停留在聊天里。

## 编码铁律

- 注释：类一行职责；方法一行"做什么"；关键分支讲为什么。中文、言简意赅、不复述代码。
- 日志：一律英文；`com.yadea.common.utils.LogUtils`；TAG＝类名；方法进/出各一条 d；
  状态迁移/指令下发/裁决/看门狗等关键节点用 i；禁止循环内打日志。
- `init` 等入口必须幂等；未确定的点全部收敛到 `PetConfig` 或 stub 信号源，禁止硬编码散落。
- 代码注释/日志中禁止出现文档编号（F/G/TBD/TD/DEP）。

## 维护规则

1. 需求确定或变动 → 先改 04（必要时 01）→ 代码只动 PetConfig／对应 Source／规则表行 → 同步场景行与开放点。
2. 竞合规则变更只改 02（TD-17 修订时同步 01 的 F13）。
3. 决策/术语/事实/全局规则变更分别改 01 第 3/5/2/4 节；版本升级在 01 文头登记。
4. 本 README 只维护"状态快照＋流程纪律"，不重复定义上述文件中的内容。
