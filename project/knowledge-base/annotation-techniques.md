## 重标先考据当前版本机制

**一句话**：对已标注过的源码重新标注时，先用版本快照验证旧注释描述的机制是否仍然存在，再动笔——上游会移除机制，旧注释会沦为对不存在代码的"准确讲解"。

**应用场景**：迁移旧注释体系、按新规范重标、或给"当年看过"的文件做二轮深挖时。

**实例**（摘自 Glide `manager/RequestManagerRetriever.java` 标注实践）：旧注释用 22 处细致讲解"向宿主挂无头 Fragment 转发生命周期"（FRAGMENT_TAG、ActivityFragmentLifecycle……）；核对快照发现 `SupportRequestManagerFragment` 已是 `@Deprecated` 空壳、生命周期绑定整体迁往 androidx Lifecycle——旧注释越详尽，误导越深。重标时以空壳类的 `@Deprecated` Javadoc 与 `LifecycleRequestManagerRetriever` 现状为准，把无头 Fragment 叙事降级为【兼容性】历史注记。

**要点**：
- 旧注释的"详尽"与"正确"无关：写于旧版本的注释会对着残留空壳讲活机制；考据锚点是 `@Deprecated` 标记、空方法体、无引用常量（grep 引用数为零）；
- 修正不是抹掉历史：被移除的机制以【兼容性】注记留一行来历（"旧版本曾……现迁往……"），让读者对得上旧资料即可。

## 论断分级与专名回查

**一句话**：注释内容质量的两道闸——每个论断落笔前先定档（代码事实/考据/推断/外部观点，同块混档逐条标注），注释中每个专名（类/方法/常量/阈值/线程名）先 grep 当前源码确认存在。

**应用场景**：写【设计思想】【为什么】等高论断密度块时；结合外部文章调研落笔时（防版本错位与"看起来合理"的编造）；给他人或后续 AI 会复读的源码写注释时。

**实例**（摘自 Glide `fetch/HttpUrlFetcher.java` 标注实践 + 社区实证）：

```java
// 【线程模型】cancel 由列表复用/页面销毁在主线程触发，因此只置 volatile 标志位。
//   ——代码事实档：线程名与 volatile 均可 grep 验证，免标；
// 【注意事项】每次递归前必须 cleanup 关掉上一跳的流与连接（#2352：不关会泄漏连接）。
//   ——考据档：issue 号可回溯；若换成"据博客说 #2352 修复了泄漏"即外部观点，须过核实门禁。
```

社区实证（Simon Willison）：代码幻觉在编译/运行时立刻暴露，**注释幻觉没有任何检查机制、静默存活**；且后续 AI 会把错误注释当事实吸收，形成污染循环——专名回查是注释层唯一的"编译期"。

**要点**：
- 专名回查抓两类事故：编造的符号（API 名想当然）与版本错位（讲上游已改名/已移除的机制）；grep 不到即改写或降级 `[inferred]`；
- 分级的价值在混档标注：一块内"事实+推断"不标档位，读者会把整块当事实吸收；标注成本低（一个词），收益是整块可信度不被单条推断拖垮。

## 折行断点避开括注与句中成分

**一句话**：中文批注折行时，断点必须落在语义单元边界（顿号/分号/破折号后），绝不把括注、介词短语劈成两半；机械校验"每行以标点结尾"的自动补句号会在句中折行处插入句号，把一句话切成两句病句。

**应用场景**：批量补行尾标点、脚本自动修复、或长注释块手工折行时。

**实例**（摘自 Glide `load/engine/EngineJob.java` 标注实践）：自动补句号把"回调线程语义不同——into() 默认主线程排队"折在"默认"后，产出"——into() 默认。"＋"主线程排队……"两行病句；同类损伤还有"都先经。"＋"ErrorRequestCoordinator 裁决"（句号劈开动宾）、"已已完成（hasResource/hasLoadFailed）"括注跨行。重排原则：把括注整个挪到下一行行首，或让括注在本行内闭合。

**要点**：
- 行尾标点规范与"语义断点"联合使用：先按语义断行，再检查行尾——而不是机械给每行补句号；
- 校验脚本自动修复后必须抽检补写处（补号行往往正是折行错位行），括注跨行要在脚本里拦截（行内 （ 计数不平衡）；
- 终收口径定为"全绿且本轮零自动修复行"：校验输出的 `+ 补行尾句号` 清单即损伤清单，逐条按语义断点重排而非接受补号——一轮实测（Glide 解码管线批次）补出 9 处病句（"会共享状态。/互相污染""取全局。/服务而非"等动宾被句号劈开）；预防优先，续行落笔时就以标点收尾。

## 行尾注释触发代码序列误报

**一句话**：以"过滤 `//` 开头行后比对代码序列"为核心的注释校验，对"代码行尾注释内容变化"（`x = 1; // 注：…` 改标签）会误报"代码被改动"；验证代码完整性需先剥离行尾注释再比对。

**应用场景**：给行尾短注释迁移标签体系后跑校验闭环时。

**实例**（摘自 Glide `load/engine/Engine.java` 标注实践）：5 处构造器行尾注释 `// 注：惰性包装…` 改为 `// 【关键细节】惰性包装…`，代码部分逐字符未动，但脚本按行比对报"代码序列与 HEAD 不一致"；且该 FAIL 会让自动补标点修复静默跳过（写回被阻断），需人工补。用 `git show HEAD` + 同款过滤、再 `split("//")[0]` 剥离行尾注释比对，确认逐字节一致。

**要点**：
- 出现"代码序列不一致"先看 diff 里被改的行是纯注释行还是行尾注释——后者剥离注释再比对，前者必须逐字符回滚；
- 误报 FAIL 会连带阻断同一脚本的自动修复（写回有 FAIL 门），故该文件的手工修复要同时覆盖两类问题（代码完整性 + 行尾标点）。

## 替换后非注释行 diff 复核

**一句话**：任何 Edit 替换注释的操作落盘后，立刻跑"diff 中过滤纯注释行后剩余非注释行应为空"的复核——它能在编译前抓住 new_string 误带入代码行导致的重复声明级损伤。

**应用场景**：大段重写方法体周边注释时（old_string/new_string 都含代码行上下文），替换文本携带规则的人工比对容易漏。

**实例**（摘自 Glide `Glide.java` 标注实践）：给构造器补注释时 new_string 除注释外把 experiment 读取的 5 行代码也复制了一份（重复声明，必然编译失败），肉眼看不出来；`git diff | grep '^[+-]' | grep -vE '^[+-]// '` 一条命令暴露 5 行非注释 +/-，立即回滚修复。另外 `git show HEAD:<路径>` 报 "exists, but not" 是路径基准错了——git 仓库根（AndroidLibs）与库目录（glide/）不一致，脚本调用必须用仓库根 + 完整相对路径，查询为空先怀疑路径基准而非数据。

**要点**：
- "非注释行 diff 为空"是注释任务的完备验收条件，与 check_annotations.py 的代码序列检查互为备份（后者在 git 基准取不到时只能靠它）；
- new_string 以"只增注释行"为纪律：含代码上下文时，先在心里数一遍 old_string 里每行代码是否逐字符出现在 new_string 的注释区之外。

## 注释内嵌使用示例（两面讲解的代码部分）

**一句话**：讲"应用侧怎么用"时不许只给文字结论——把最小可运行示例（5-10 行）直接贴进行注释（缩进比引导行深一级），前面给一句场景、后面点一句"不用会怎样"。

**应用场景**：标注 API 入口、扩展点/配置点/回调契约（模块机制、Builder setter、Listener、自定义组件基类）时——这些地方的读者第一反应是"我要写什么代码、什么场景写、不写行不行"，纯文字描述回答不了。

**实例**（摘自 Glide `module/AppGlideModule.java` 标注实践）：初版类头只写"应用级定制入口，applyOptions 改全局配置"三行——用户反馈"作为刚接触的人根本不知道这些东西是什么、怎么用、什么场景用、为什么有这条路径"。重写为：接入三步 + 场景示例（`@GlideModule public class MyAppGlideModule extends AppGlideModule` + `builder.setMemoryCache(new LruResourceCache(20 * 1024 * 1024))`，场景"低内存设备调缓存上限"）+ "不写它也能跑（默认值清单）"。同一批 `LibraryGlideModule` 贴集成包注册网络栈的示例并标注 `[inferred]`（该包不在本仓检出）。

**要点**：
- 示例 = 最小可运行骨架，删到不能再删仍能说明用法；场景一句话贴在示例前，"不用会怎样"点在示例后；
- 专名纪律对示例代码同样生效：类名/方法名/参数回查当前源码，本仓未检出的依赖类标 `[inferred]` 示意；
- 示例只贴一次（概念本体类头处），流程方法处给角色定位与回指——重复贴会随上游演进失同步；
- 无 CJK 的示例代码行不参与行尾标点检查（check_annotations.py 口径），中文引导行仍要守标点规范；
- 配套校验闭环：SKILL.md §3.2"两面讲解 + 使用示例"、§6 Gate 14——把"贴示例"从个人习惯升级为 skill 硬规则，源于用户反馈"以后所有的源码分析都必须这样，要举一反三"。

## 中文块内嵌英文示例行的保护误报

**一句话**：中文注释块内嵌的纯英文代码示例行（无 CJK、长度 >15）一旦入库，后续批量重构删除该示例时，校验脚本的"上游英文注释保护"会误报 FAIL——它无法区分库作者注释与此前轮次的示例行。

**应用场景**：批量重构（四检）要删除此前轮次嵌入中文块的示例行时；或新写使用示例、决定示例行的书写形态时。

**实例**（glide Glide.java 注释重构批）：`initializeGlide` 第四步的示例行 `//   public void applyOptions(Context context, GlideBuilder builder) {` 由标注批次引入（`git log -S 'PREFER_RGB_565'` 考证为 commit abb55fe，Initial commit 无此行），删除仍报"上游英文注释被删"；处理：git 考证确认属此前轮次批注（本可授权删除），为保机械全绿口径选择原样保留。

**要点**：
- 新写示例时给纯代码示例行就近配 CJK 引导行，避免成片孤立的英文注释行——它们入库后会被后续校验当作"上游注释"保护；
- 删除已入库的纯英文注释行前先 `git log -S` 考证引入 commit：属标注批次即四检授权范围，属库作者原文则绝不动；考证结论与脚本误报如实记入汇报。

## 块注释风格批注与行注释校验脚本不兼容

**一句话**：代码序列/标点校验按行注释（`//`/`#`/`--`）设计，既有批注若是 Javadoc 块注释风格（`/** … */`），其内容行会被当代码行参与比对——改动必报"代码序列不一致"，标点检查也会对块内容行成片报警。

**应用场景**：接手前轮用 Javadoc 风格标注过的文件做四检修复时。

**实例**（摘自 retrofit `retrofit2/Utils.java`、`RequestBuilder.java` 标注实践）：两文件前轮批注全为中文 Javadoc 块注释；本轮只改注释行（git diff 非注释行计数 = 0），check_annotations.py 仍报"代码序列与 HEAD 不一致" + 约 40 处"行尾缺标点"，且未改动的同风格文件 ParameterHandler.java 同样 FAIL——证明 FAIL 是存量风格与脚本的系统性不兼容，不是本轮误伤。

**要点**：
- 判定本轮改动是否安全，用"diff 非注释行计数 = 0"复核，不依赖该脚本的代码序列项；
- 存量块注释文件的整批 FAIL 按预期状态记录并请示是否归一化为行注释【标签】风格，不当成本轮质量问题返工（成片改动需用户确认）；
- 脚本对块注释行失明意味着标点/宽度检查也不覆盖它们——自检时补一段自写校验（提取 diff 新增中文行、比对行尾标点集），脚本射程外的质量靠自己兜底（retrofit 标注实践）。

## 块注释归一化要按 HEAD 逐块拆分混合注释

**一句话**：把前轮的中文块注释批量迁移为行注释时，必须以 git HEAD 为参照逐块处理——前轮常把中文混写进上游英文 Javadoc 同一块，整块转换会把英文 Javadoc 一起改形，违反"上游 Javadoc 原样保留"。

**应用场景**：接手多轮、多风格批注的仓库做风格统一时。

**实例**（retrofit 核心模块 53 文件归一化实践）：扫描 HEAD 中每个含 CJK 的独立块，以"第一条含中文的内容行"为界拆分——界前的上游行还原为原始 `/** … */` 块（开行/内部行逐字保留），界后的中文保持 `//` 行；纯中文块（split 在首条内容行）不还原。迁移与还原各配"代码骨架比对"（剥离全部注释与非字符串空白后与 HEAD 逐字节比），任何一步不一致即拒写盘。

**要点**：
- 混合块的还原定位只能用"上游英文前缀"做锚（中文部分可能被后续轮次编辑过，整块产物比对会失配）；
- 还原上游块时开行要带上原始行首缩进（从块起点扫描会丢掉行首空白），收尾 `*/` 补齐对应缩进；
- 还原会为纯中文块插入空 `/** */` 残片，收尾要用"空块清理 + HEAD 无空块"护栏扫掉；
- 终验三层：骨架比对（代码零变更）→ 上游英文行在位抽查 → 校验脚本跑标点债计数（存量债可见化，不盲目补号）。

## 多行锚点在缩进中段匹配，替换带歪缩进

**一句话**：Edit 类替换的 old_string 若以"目标行的部分缩进"开头，会在真实缩进的中段完成子串匹配——替换后该行缩进被静默带歪，代码序列校验是唯一可靠的防线。

**应用场景**：给缩进层级深的嵌套类成员（如内部类方法、Registry 内的私有类）加注释时，凭记忆写锚点缩进最容易踩。

**实例**（SettingsProvider 标注实践）：`SettingsRegistry` 内的 `UpgradeController` 声明真实缩进 8 空格，锚点误写 4 空格；子串匹配从第 5 个空格起命中，替换后类声明与常量行被反缩进成 4 空格，`check_annotations.py` 的"代码序列与 HEAD 一致"项报出 4 行代码位移。

**要点**：
- 锚点拿不准缩进时，改用"含独特文本的代码行 + 紧随其后一行"整体做锚，或先 grep/sed 看真实缩进再落笔；
- 缩进损伤人眼 diff 极易漏看，每轮标注收尾必跑代码序列一致性校验（本 skill §3.4 九项之一）。

## 上游注释讲事实，中文层讲增量

**一句话**：库作者的英文注释原样保留，中文讲解层只在**空行隔断后**追加英文没讲的内容（锁序、动机、竞态细节），绝不复述英文已说清的部分。

**应用场景**：给 AOSP 这类注释完善的代码加中文学习批注——最容易犯的错是把英文注释翻译一遍，产出双语冗余。

**实例**（摘自 frameworks/native `libs/binder/ProcessState.cpp` getStrongProxyForHandle）：

```cpp
// We need to create a new BpBinder if there isn't currently one, OR we
// are unable to acquire a weak reference on this current one. ...
// attemptIncWeak() is safe because ... expungeHandle(), which acquires
// the same lock we are holding now. ...          <- 上游英文：事实层，原样保留
//
// 【关键细节】弱引用竞态：本线程拿到旧 entry 时，另一线程可能正在析构这个
// BpBinder（析构里的 expungeHandle 也要拿 mLock，被本锁挡住才不会清掉
// entry）——attemptIncWeak 成功则旧对象还活着，复用即可。  <- 中文层：换个角度讲
```

**要点**：
- 分工判据：上游注释说"代码做什么/为什么安全"（契约），中文层说"不这样会怎样/在链路中演什么角色"（讲解）——读者先读英文拿到事实，读中文拿到后果与场景。
- 中文块与上游注释之间必须空行隔断（脚本按块检查标签），直接紧跟会把两段合成一块，阅读时也分不清层次。

## 替换类工具的模糊匹配会让锚点笔误静默落盘

**一句话**：Edit 类工具对 old_string 做模糊匹配——锚点里凭记忆写错的方法名/常量名/空格也能匹配成功，并把错误文本随 new_string 写进文件，人完全无感。

**应用场景**：凭上一轮阅读记忆写锚点、而不是复制粘贴真实代码时，必踩。

**实例**（SettingsProvider/Settings 标注实践，一次会话两起）：① 把上游注释 `system server` 记成 `system_server`，替换后上游英文注释被改写，靠校验脚本"上游注释保护"项抓出；② old_string 里把 `AttributionSource` 打成 `AttributionSourceSource`，成功匹配并落盘，靠"代码序列与 HEAD 一致"项抓出。

**要点**：
- 锚点必须从源码复制粘贴，绝不凭记忆手写；
- 人眼 diff 看不出这类损伤（改动就在注释/单词内部），每轮标注收尾必跑校验脚本——机械校验是模糊匹配时代唯一的防线。
