## 第一部分 · 学习地图与心智模型

### 1.1 一句话认识这个项目

`NsrNetService` 是 **Honda 27M 车机的车联网网络服务**，负责把车辆数据安全地送到云端（**VSP** = Vehicle Service Platform，车辆服务平台，即 TSP 提供的主业务云），并接收云端指令。它由 8 个 Gradle 模块组成，实际是 **2 个可运行应用 + 6 个库**：

```
┌──────────────────────────────────────────────────────────────┐
│              两个可运行应用                                     │
│  NetSecurityService (系统服务App)      NetTestApp (演示App)    │
│  证书签发 / URL发现 / APN绑定          按钮驱动的测试台          │
│        ▲    跨进程通信 (RIpcCompat)     │                      │
│        └───────────────  ◄─────────────┘                      │
└──────────────────────────────────────────────────────────────┘
            │ VspSDK fat-AAR 打包了下面三个库
   ┌────────┼────────┬────────┐
 VspSDK   Http     NetSercuritySDK   ApnSDK
 (伞状SDK) (HTTP引擎) (安全SDK)       (蜂窝网络)
            │          │
            │       NetSecurityCore (IPC契约/共享接口)
            └── Soap (证书注册专用) ──┐
```

**模块职责速查表**：

| 模块 | 类型 | 一句话职责 |
|---|---|---|
| `Http` | 库 | Retrofit + OkHttp 封装，HTTP 引擎 |
| `VspSDK` | 库(fat-AAR) | 面向应用的伞状 SDK，整合 Http+安全+APN |
| `NetSecurityCore` | 库 | 跨进程共享的接口契约（AIDL/Parcelable） |
| `NetSercuritySDK` | 库(fat-AAR) | 客户端安全 SDK：拉取证书、重建 KeyStore |
| `NetSecurityService` | 应用 | 系统服务：证书签发、URL 发现、APN 绑定 |
| `ApnSDK` | 库 | 蜂窝网络通道绑定（APN1/APN2） |
| `Soap` | 库 | 老式 SOAP 协议（仅证书注册用） |
| `NetTestApp` | 应用 | 演示/测试 App |

**技术栈版本**：Retrofit 2.9.0 · OkHttp 4.12.0 · Gson · RxJava2 · HiveMQ MQTT Client 1.3.0 · ksoap2(vendored 3.6.4)

### 1.2 核心心智模型：网络 = 送快递

| 概念 | 类比 | 本项目对应 |
|---|---|---|
| IP 地址 | 城市地址 | 服务器域名解析后的 IP |
| 端口 | 楼内房间号（443=安全收件处） | `:443`、`:8883` |
| TCP | 挂号信（每封要回执，丢件重发） | 底层可靠通信 |
| UDP | 平信（不保证到达，快） | 本项目几乎不用 |
| 蜂窝网络 | 高速公路网（运营商铺设，车移动不断网） | ApnSDK / vlan11 / vlan21 |
| HTTP 请求 | 写给服务器的"订单信" | `@POST` 注解接口 |
| HTTPS | 挂号信 + 防伪印章 | OkHttp 的 TLS 配置 |
| **TLS** | 给信件套上的"加密+验证"信封 | `SSLUtil` 构建 TLSv1.2 通道 |
| 证书 | 公安局发的身份证 | 项目 80% 代码围绕它 |
| Token | 入场手环 | `Authorization: Bearer` 头 |
| MQTT（消息队列遥测传输） | 广播电台（服务器主动喊话） | `MqttClientManager` |
| SOAP（简单对象访问协议） | 政府专用表格（老式 XML） | 证书注册唯一场景 |
| TSP（车载信息服务提供商） | 车联网"云服务商"（提供 VSP 平台的公司） | `reachauto-mobility.com` 就是 TSP 的云 |
| 拦截器 | 出发前的检查站 | VspSDK 的 3 个拦截器 |

> **为什么源码分析看不懂？** 因为项目里 80% 的代码在解决"怎么安全地把数据送到云端"（证书、加密、IPC、APN），而不是"怎么发请求"。本指南从基础向上爬，最后才落到高级内容。

### 1.2.1 车联网生态全景：TSP 到底是谁

**TSP = Telematics Service Provider（车载信息服务提供商）**，通俗说就是**"车联网的云服务商"**——给车提供云端服务的公司。

**为什么会有 TSP 这个角色？** 因为一辆车联网，光有"网"不够，还得有人管"车的数据和业务"：

| 角色 | 类比 | 干什么 |
|---|---|---|
| **电信运营商**（移动/联通/电信） | 高速公路公司 | 铺蜂窝网络，让车能上网（只负责"管道"） |
| **TSP**（如本项目背后的 ReachAuto） | 城里的服务公司 | 在"路"上开服务：车辆数据平台、远程控制、OTA、账号体系 |
| **车厂**（Honda） | 车品牌 | 造车、卖车、定服务标准 |
| **车机（IVI）** | 车里的电脑 | 跑 App，用 TSP 的服务（本项目就是跑在车机里） |

**数据流向一句话**：

```
车机 App → 蜂窝网络(运营商管道) → 互联网 → TSP 云平台(VSP) → 车厂系统 / 车主手机App
```

**本项目里的 TSP 痕迹**（`reachauto-mobility.com` 就是 TSP 的云平台域名）：
- `hc34-vsp-mix-vehicle-3072.reachauto-mobility.com` → **VSP**（Vehicle Service Platform，车辆服务平台）主业务底座，VspSDK 连的就是它（VspSDK.java:301）
- `hc5-icp.reachauto-mobility.com` → ICP 配置发现服务器，开机时从它拿各业务域名（IcpUrlManager）
- `pki-test.hynex.com.cn` → TSP 合作的 CA（TopCA 天威诚信）注册中心，负责签发车辆证书
- 配套的账号体系（`RAccountCommonSDK`）、消息推送（`RMessageCenterSDK`）也都是 TSP 生态的组件

> 记住：**TSP 是"提供云端服务的人"，蜂窝网络是"把车接上云端的路"**。本项目 = 车机侧把所有 TSP 服务接通的那套代码。

### 1.2.2 TBOX：车里的通信盒子（"车的手机"）

**TBOX = Telematics BOX（远程信息处理终端，俗称"车联网盒子"）**——车上的**通信硬件**，是整车与云端通信的"门户"。

**它在车机网络中的位置**：

```
TSP 云平台 ←→ 蜂窝网络 ←→【TBOX】←→ 车机 IVI（屏幕/导航/娱乐）←→ 各 ECU（发动机/空调/锁）
                              ↑
                   车联网通信的"收发室"
```

**TBOX 与 IVI 的分工**：IVI 是"脸"（你摸得到的屏幕），TBOX 是"神经"（通信、定位、eCall）。不是替代关系。

**TBOX 硬件里有什么**：

| 组件 | 作用 | 本项目对应 |
|---|---|---|
| 4G/5G 通信模块（modem） | 蜂窝接入，插物联网 SIM 卡 | ApnSDK 申请的 `vlan11/vlan21` 网卡（modem 走 USB 接入） |
| GPS/北斗定位模块 | 车辆定位 | 位置上报、eCall 定位 |
| eCall 模块 + 独立电池 | 碰撞自动求救，**整车断电也能打电话** | APN1 紧急呼叫专网 |
| 安全存储（eMMC/安全芯片） | 存证书、密钥 | 航盛服务 `AochrKeyStoreManager` 存的证书 |
| MCU 处理器 + 天线 | 控制、收发 | — |

**为什么必须独立于 IVI**：
1. **安全隔离**：独立硬件+独立电源，撞车断电时 TBOX 仍能工作（eCall 救命）
2. **常电待机**：24 小时在线，远程控制（锁车/开空调）随时可唤醒
3. **硬件级安全**：证书/密钥放 TBOX 安全存储，比车机硬盘安全

> 一句话：**TBOX 是"车的手机"**——插 SIM 卡、装定位、连着急救专线，车上所有"和云有关的事"都从它进出。本项目的 `ApnSDK`（vlan11/vlan21）、eCall 专网、航盛证书存储，全是 TBOX 这台"车的手机"上的功能。

### 1.2.3 ICP：车联网的"查号台"（配置/域名发现服务）

**ICP 是 TSP 提供的一个配置下发服务器**，作用是：**告诉每台车"各业务服务器现在在哪个域名、哪个端口"**。

**为什么需要它？** 因为服务器域名会变（换机房、多环境、容灾切换）。与其把域名写死在车机代码里，不如让车开机时**问一次 ICP**，拿到当前的域名表。类比：

> **ICP = "114 查号台"**。车机拨过去说"我要找 VSP 业务、MQTT 推送、OTA 升级、数据上报"，ICP 回一张表："它们在 xxx.com:443、yyy.com:8883……"。以后服务器搬家了，只需改 ICP 上的记录，全车自动跟着走。

**项目实现**（`NetSecurityService/.../icp/IcpUrlManager.java`）：

```
① 开机（VIN 就绪）
② POST https://hc5-icp.reachauto-mobility.com/icps
      {"key":"VEHICLE-3072","platform":"V","value":<VIN>}
③ 响应 responseBody.domains：
      mqtt-server     → 写 BASE_MQTT_URL
      user-server     → 写 BASE_HTTP_URL（VSP 主业务底座）
      ota-server      → 写 BASE_OTA_URL
      data.sensorsdata→ 写 BASE_SENSOR_URL
      data.recommendCallback → 写 BASE_FUN_URL
④ 各业务模块从数据中心读自己的 URL
```

**关键细节**：
- **URL 加密**：ICP 地址是 AES 加密串（`IcpUrlManager.java:52-56`），构造时用 `qweasd123` 解密——防止把内部地址直接暴露在 APK 里
- **环境切换**：模拟器环境用模拟器 URL；真车根据航盛证书是否"已签发"决定走正式（formal）还是测试（test）ICP（:97-112）
- **失败重试**：请求失败每 10 秒重试（:192-194）；VIN 变化、ACC 上电都会重新拉取（:137-146, 303-312）
- **注意**：项目代码里**未标注 ICP 全称**。它的功能是"配置/域名发现"（类似 Apollo/Nacos 的轻量版），**与互联网常见的 ICP（Internet Content Provider，网站备案）完全是两码事**，别混淆。

> 记忆：**ICP = 车联网查号台**，车开机先问它"各服务在哪"，拿到域名表再开始干活。

> 📌 **括号里的数字是章节编号**：例如 `（6.0 的"通信耳朵"）` 意思是"这个概念在 6.0 节有完整讲解，这里只是引用"。`6.0` = 第六课的第 0 小节，`1.2.2` = 第一部分的 1.2.2 小节，以此类推——它们不是新概念，只是"详细讲解的位置"。

#### 先回答"为什么这么多概念"：概念分层地图

> 感觉概念爆炸？其实网络是**分层**的，概念跟着层走。全部概念就 **5 层、每层 1-2 个词**，加上几张"同物多名"的对照表：

```
══════════ 车联网网络概念全景图（从 App 到云，每层有什么概念）══════════

┌─ 第5层 业务协议 ────────────────────────────────────────────────┐
│  HTTP（一问一答）  MQTT（云主动推）  SOAP（老式XML）            │
│  Token（入场手环） ICP（查号台）   数据中心（公共黑板）          │
├─ 第4层 传输安全 ────────────────────────────────────────────────┤
│  TCP（挂号信）→ TLS（加密信封）→ 证书/mTLS（身份证，双向查验）   │
├─ 第3层 系统管理 ────────────────────────────────────────────────┤
│  ConnectivityManager（网络管家）                                │
│  NetworkRequest（申请条件）  bindProcessToNetwork（锁路由）      │
├─ 第2层 数据通道 ──── 同一个东西的 4 个名字！ ★核心 ★ ───────────┤
│   运营商视角：APN1 / APN2          （业务配置：走哪条数据业务）   │
│   3GPP 标准 ：PDN 连接             （端到端通道：各有IP/网关/QoS）│

│   Android视角：Network             （网络对象）                  │
├─ 第1层 物理硬件 ────────────────────────────────────────────────┤
│  TBOX（盒子）→ modem（翻译无线电）→ SIM（户口+指纹）→ 天线      │
│  → 无线电波 → 基站 → 运营商核心网 → 互联网 → TSP 云             │
└────────────────────────────────────────────────────────────────┘
```

**核心洞察**：你不是要记 20 个孤立名词，而是 **5 层、每层 1-2 个**，再加"同一东西多名字"的对照。**第 2 层的 4 个名字是同一个东西**（运营商叫 APN、标准叫 PDN、Linux 叫 vlan、Android 叫 Network）——认识第一个，后面三个全是别名。为什么代码里只见 vlan/Network 不见 APN？因为**项目代码工作在系统层**（APN 是运营商侧配置，代码碰不到）。

> 一句话：**概念多 ≠ 内容多。两个来源：① 网络分层（每层 1-2 个词）；② 同物多名（第2层 1 个东西 4 个名字）。去掉重复，真正的独立概念不超过 15 个。**

#### 知识域一：通信链路域 —— 数据怎么从车到云（物理通道）

**聚合的概念**：蜂窝网络、TBOX、modem、SIM 卡、APN、vlan11/vlan21、eCall、ConnectivityManager

**全貌链路**（一次看清所有概念的关系）：

```
车机App
  │  业务代码（OkHttp/Retrofit，跑在 AP 应用处理器上）
  ▼
TBOX（1.2.2 的"车的手机"）
  ├─ modem（6.0 的"通信耳朵"）：数字信号 ⇄ 无线电波
  ├─ SIM 卡（6.0 的"户口+指纹"）：鉴权通过才分配 IP
  └─ eCall 模块 + 独立电池：断电也能打紧急电话
  ▼
USB 虚拟网卡 vlan11（APN1）/ vlan21（APN2）  ← ApnSDK 在这里做文章
  ▼
ConnectivityManager（6.1 系统网络管家）
  ├─ requestNetwork(addTransportType(8))：申请蜂窝网络
  ├─ bindProcessToNetwork()：把整个进程流量绑到蜂窝
  └─ getSocketFactory()：给 OkHttp 指定走哪条通道
  ▼
无线电波 → 运营商基站 → 运营商核心网 → 互联网 → TSP 云平台
```

**三个核心组件的详细解析**：

| 组件 | 全名 | 职责 | 关键细节 | 项目对应 |
|---|---|---|---|---|
| **modem** | Modulator-Demodulator（调制解调器，"猫"） | 数字信号 ⇄ 无线电波的"翻译官" | 蜂窝收发、与基站交互、配合 SIM 鉴权；TBOX 内独立芯片，USB 接入 AP | `vlan11`/`vlan21` 虚拟网卡 |
| **SIM 卡** | Subscriber Identity Module（用户身份识别模块） | 证明"这台车有资格上网"，鉴权通过才分配 IP | 存 ICCID/IMSI/**Ki**（永不出卡）；挑战-应答鉴权，假卡过不了；车机用物联网卡 | 鉴权通过 → 才有 `vlan11`/`vlan21` 网络 |
| **eCall 模块** | Emergency Call（紧急呼叫） | 撞车/按 SOS 时自动呼救 | 独立电池（断电也能打）、独立 APN1 专网、自动上报 MSD（位置+VIN+时间）、接通 PSAP 语音；欧盟 2018 起强制标配 | VspSDK eCall 模式强制走 `getAPN1Socket()` |

**聚合要点**（关系，不是孤立定义）：
- **TBOX 是"硬件盒子"**，里面装着 modem 和 SIM 卡；modem 负责"翻译无线电波"，SIM 卡负责"证明身份换 IP"——三者是**包含与被包含**的关系
- **APN 是"选车道"**：同一个 modem+SIM，可以同时建两条数据通道（APN1 eCall 专网 / APN2 业务网），在 Linux 层呈现为 vlan11/vlan21 两张网卡
- **ApnSDK 是"车道管理员"**：它不造车道（APN 由 modem 预配置），只负责申请网络、把进程流量绑到车道、把车道的 SocketFactory 交给 OkHttp
- **eCall 是"优先级"**：救命数据强制走 APN1 专网（vlan11），普通业务走 APN2（vlan21）——即使欠费/拥堵，eCall 也能接通紧急电话

**那 APN1 和 APN2 最终会汇聚成一条通道吗？**

**物理上汇聚，逻辑上永远分开。** 两条通道共用同一个"发射口"（modem+天线+基站），但到核心网后就各走各的网关，**永远不会合并**：

```
vlan11（APN1/eCall）──┐
                      ├→ 同一个 modem + 天线 ─→ 同一个基站 ─→ 运营商核心网
vlan21（APN2/业务）───┘                                     │
                                            （核心网按"APN 标记"区分路由）
                                              ├→ APN1 网关 → eCall/PSAP 救援专网
                                              └→ APN2 网关 → 互联网 → VSP 云
```

| 路段 | 是否共享 | 说明 |
|---|---|---|
| 车机内（vlan11/vlan21 → USB → modem） | 逻辑独立、物理共享 | 两张网卡是两个**独立的 PDN 连接**，各有各的 IP、路由、QoS |
| 空中（天线 → 基站） | **物理汇聚** | 同一个天线、同一段无线电波发出去（直觉里"汇聚"的部分） |
| 核心网以后 | **逻辑分开** | 核心网根据数据包的 **APN 标记** 路由到**不同网关**：APN1→救援专网，APN2→互联网 |

**关键认知：数据靠"网卡绑定"分道扬镳（不是每包盖章）。** "盖 APN 标记"是简化比喻，实际机制是**绑定关系**：

```
第1步 建立：modem 为 APN1、APN2 各建立一条独立的 PDN 连接（各有自己的 IP、网关、QoS）
第2步 绑定：Linux 把 vlan11 网卡 ↔ APN1 连接绑定、vlan21 网卡 ↔ APN2 连接绑定（一一对应）
第3步 传输：数据包从 vlan11 进入 modem → 查"网卡↔连接"映射表 → 归入 APN1 的承载通道
             → 空口走 APN1 对应的无线承载 → 核心网路由到 APN1 网关
```

**新名词逐个解释：PDN 连接 / IP / 网关 / QoS**

| 名词 | 全称 | 通俗解释 | 类比 |
|---|---|---|---|
| **PDN 连接** | Packet Data Network（分组数据网络）连接 | 车通过运营商网络，与某个"数据网络"（互联网/专网）之间建立的**一条端到端数据通道**。每个 APN 对应一条 PDN 连接 | 办宽带时运营商给你家拉的"那条线路" |
| **IP（地址）** | Internet Protocol（网际协议） | 网络上的"门牌号"，数据包靠它找到目的地。**每条 PDN 连接分配一个独立 IP**（vlan11 和 vlan21 的 IP 不同） | 一个房子有两个门牌 |
| **网关** | Gateway | 通往其他网络的"大门/路由器"。车的数据要出运营商网络，必须经过**该连接自己的网关**（APN1→eCall 专网网关，APN2→互联网网关） | 小区大门：出门必经，不同目的走不同的门 |
| **QoS** | Quality of Service（服务质量） | 网络给数据的"待遇等级"：优先级、带宽、延迟保障。eCall 数据可享受高优先级（不拥堵、不丢），普通业务是"尽力而为" | 机场安检：头等舱优先，经济舱排队 |

**把四个名词串进场景**（以 APN2 业务网为例）：

```
建立 PDN 连接 → 运营商分配【IP】+ 指定【网关】+ 约定【QoS】
车机发数据（源 IP = 自己的 IP，目的 IP = VSP 云的 IP）
  → 数据交给默认【网关】
  → 网关按【QoS】决定这包数据的待遇（带宽/优先级）
  → 一路送到 VSP 云
```

> 一句话：**PDN 连接 = 租用的一条数据线路；IP = 线路上的门牌号；网关 = 线路出口的大门；QoS = 这条线路的服务等级。项目代码不直接碰它们（运营商/系统层的事），只通过 vlan11/vlan21 网卡间接使用。**

**区分数据靠"从哪个入口（网卡）进来"，不是数据本身带戳。** 类比地铁换乘：vlan11 = 1 号线入口、vlan21 = 2 号线入口——从哪个口进就自动坐哪条线，不需要每张票盖章。

**vlan11/vlan21 怎么理解？为什么不统一叫"APN 通道"？**

**vlan = Virtual LAN（虚拟局域网）**：一根物理线路，用软件划出多条**互不干扰**的"虚拟线路"。类比：一条大马路（物理线路）上画出**公交车专用道**——路还是那条路，但车道互相隔离。

**先搞懂"modem 的 USB 链路"是什么意思**：

- **USB = Universal Serial Bus（通用串行总线）**——最常见的硬件数据传输接口（手机连电脑那根"充电线"就是 USB）
- **modem 是独立硬件模块**，像"USB 随身 WiFi 棒"一样通过 USB 数据连接插在车机主板上——这就是"modem 通过 USB 接入车机"
- **"USB 链路" = 车机主板 ↔ modem 模块之间，通过 USB 总线传数据的这条内部通道**（车机内部硬件连接，不是对外网络）
- **"在 USB 链路上划出 vlan"**：Android App 数据走到 Linux 内核，内核在"USB 设备（modem）"之上创建两个虚拟网卡 vlan11/vlan21；数据从哪个网卡走，就经 USB 总线传给 modem，modem 再按对应 APN 发出去

```
Android App → socket → Linux 内核网络栈
  → vlan11 / vlan21（内核为 USB 上的 modem 创建的"虚拟网卡"）
  → USB 总线（数据包经 USB 线传给 modem）   ← "USB 链路"就是这一段
  → modem 固件（把 IP 包装进蜂窝协议，并按网卡绑定关系归入 APN1/APN2 对应的承载通道）
  → 无线电波 → 基站
```

> 为什么用 USB？因为车载 modem 模块（移远/华为/高通等）的**标准对外接口就是 USB**——插上即被系统识别为网络设备（Linux 的 usbnet/rndis 驱动自动虚拟成网卡），这是行业惯例。

**为什么不统一叫"APN 通道"？** 因为这是**同一个通道在两个不同层面的名字**：

| 视角 | 它叫什么 | 谁在用这个名字 |
|---|---|---|
| 运营商业务层 | **APN1 / APN2** | 运营商配置、SIM 卡 |
| 通信标准层 | **PDN 连接** | 3GPP 协议 |
| 车机 Linux 层 | **vlan11 / vlan21** | 系统网络接口 |
| Android 层 | **Network** | ConnectivityManager |

同一条路，不同系统的编号——交警叫"京藏高速"，地图软件叫"G6"。项目代码（ApnSDK）工作在**车机系统层**，所以代码里全是 `vlan11`/`vlan21`、`Network`、`NetworkRequest`，**永远不会出现"APN"字样的 API**——APN 配置在 modem/运营商侧，代码碰不到。

**为什么必须隔离**：① eCall 要保命（APN1 专网独立网关可做优先级保障，业务拥堵不影响紧急呼叫）；② 安全隔离（救援专网与互联网隔离）；③ 互不干扰（业务流量不挤占 eCall 通道）。

> 一句话：**APN1/APN2 在物理层（天线/无线电）确实"同框"，但逻辑上是两条永不相交的管道——靠 APN 标记在核心网分道扬镳，各去各的网关。汇聚的是"嘴"，分开的是"路"。**

**容易混的两个概念：USB 虚拟网卡 vs SIM 卡**

| | **SIM 卡** | **USB 虚拟网卡（vlan11/vlan21）** |
|---|---|---|
| 是什么 | 一张**物理卡片**（身份凭证） | 一个**软件网络接口**（Linux 虚拟网卡） |
| 本质 | 硬件介质，存身份密钥（Ki/IMSI） | 操作系统里的虚拟网络设备 |
| 干什么 | 证明身份、**鉴权换 IP** | **收发 IP 数据包**（数据通路） |
| 类比 | **身份证/户口本**（有资格上高速） | **车道出入口/收费站**（上高速后走的道） |
| 在哪 | TBOX 的 modem 里（物理卡槽） | 车机 Android 系统里（AP 侧，软件层面） |
| 谁碰它 | 运营商网络（鉴权系统） | 系统网络栈 + App（ConnectivityManager） |
| 状态 | 常驻卡槽 | 鉴权成功后才创建、才有 IP |

**先后关系**：`SIM 卡鉴权通过 → 运营商分配 IP → 系统创建 vlan11/vlan21 网卡 → App 通过网卡收发数据`。没有 SIM/鉴权失败 → 无 IP → 无网卡 → 没网。

> 一句话：**SIM 卡回答"你有资格上网吗"（身份认证）；USB 虚拟网卡负责"资格到手后的数据收发"（数据通路）。SIM 在 TBOX 物理卡槽里，网卡在系统软件里，中间隔着 modem 翻译。** 项目里 ApnSDK 不碰 SIM（运营商的事），只操作网卡这一层。

**又一个疑问点：ConnectivityManager 是软件，为什么在链路图里？**

你的直觉是对的——**ConnectivityManager 是 Android 系统里的软件服务（系统类），不是硬件**。它的职责：申请网络、监听网络变化、把进程绑定到指定网络（`bindProcessToNetwork`）。

**为什么它出现在链路图里？** 因为链路图是"**数据从车机 App 到云的完整旅程**"，不是"纯硬件图"。数据走完全程必然经过软件层，而 ConnectivityManager 恰好站在**软件 ↔ 硬件的交接关口**：

```
【软件层】(跑在 AP 上)
  App（业务代码）
    ↓ 调用系统 API
  Android 系统网络服务 = ConnectivityManager（网络管家）
    ↓ 调度内核
  内核网络栈 + 网卡驱动
    ↓
【硬件层】(TBOX 里)
  vlan11/vlan21 网卡（软件模拟的硬件接口）→ USB → modem 芯片 → SIM 卡 → 天线
    ↓ 无线电波
  基站 → 运营商核心网 → 互联网 → TSP 云
```

- **App 不直接碰硬件**（没权限、也太复杂），它只跟 ConnectivityManager 说"帮我申请一个蜂窝网络"
- **ConnectivityManager 调度内核**去操作网卡驱动，驱动通过 USB 指挥 modem
- 所以链路图里它是"**软件侧对硬件侧的控制入口**"——没有它，App 根本连不上网

**类比**：ConnectivityManager = **小区网管中心（软件）**。住户（App）不能自己拉网线，要报给网管，网管调度工人（内核/驱动）去接线路（modem/天线）。链路图把"报修→调度→接线→信号"整个过程画在一起，所以软件（网管）和硬件（线路）同框出现。

> 一句话：**ConnectivityManager 是纯软件，它在链路图里代表"App 通向硬件的必经关口"：App → 系统网络管家 → 内核驱动 → modem → 无线电。**

> **深入位置**：TBOX→1.2.2 · 蜂窝→6.0 · modem→6.0 · SIM→6.0 · Android 网络机制→6.1 · APN→6.2

#### 知识域二：身份信任域 —— 凭什么相信对方（安全体系）

**聚合的概念**：TLS、对称加密、非对称加密（RSA）、AES、证书、CA、RA、天威诚信（TopCA）、根证书、初始证书、CSR、mTLS 双向认证、AndroidKeyStore、航盛服务、TrustManager、主机名验证、安全弱点

**全貌链路**（一辆车的证书从出生到使用的一生）：

```
【出生】车出厂
  ├─ 预置"初始证书+私钥" → 存进航盛系统服务的 eMMC（8.4）
  └─ 车机里预装项目根证书（天威诚信体系）→ 作 TrustManager 唯一信任锚（4.3）
【领证】首次联网
  ├─ 车机生成 RSA3072 密钥对 → 组装 CSR（4.3.1）
  ├─ 用初始证书建立 mTLS 通道 → 连天威诚信 RA（ra.tca.topca.cn）
  ├─ RA 审核 → CA 用根私钥签发车辆证书（CA=发证机构，RA=办证窗口）
  └─ 证书返回 → 存进 AndroidKeyStore（4.4）
【使用】日常通信
  ├─ 双向 TLS：服务器亮证书 + 车机亮证书（4.4）
  ├─ 信任链验证：证书 → 谁签的？→ 项目根证书（4.3）
  └─ ⚠️ 项目关闭了主机名验证（hostnameVerifier 恒 true，第十课#1）
【传递】证书怎么到业务 App
  ├─ 系统服务 NtsPKIApi 拿证书 → IPC 广播 KeyStoreInfo（含私钥，8.3）
  └─ RNetManager 重建 AndroidKeyStore → RHttps.setKeyStore → OkHttp 使用
【续期】剩 ≤180 天自动重新申请；失败每 10s 重试（4.4）
```

**聚合要点**：
- **加密**解决"内容保密"（AES 对称 + RSA 非对称，4.1/4.2）；**证书**解决"你是谁"（4.3）；**双向 TLS** 解决"双方都可信"（4.4）——三者层层递进，缺一不可
- **CA/RA/天威诚信**是"发证机关体系"（4.3.1）：CA 盖章、RA 收件、天威诚信是持牌机构本身
- **AndroidKeyStore / eMMC / 航盛**是"证书的家"：AndroidKeyStore 是运行保险柜，eMMC 是持久备份，航盛是预置来源
- **信任锚**贯穿全程：根证书（TrustManager）是"验真"的起点，证书固定（4.3）就是"只认自家根"

### 证书体系零基础展开：证书是什么？五步全链路每步在干嘛？

**证书（Certificate）= 解决"你是谁"这个问题的电子身份证。**

```
证书 = 公钥 + 身份信息 + CA 的签名（盖章）
       （配对的）  （域名/厂牌/VIN）  （发证机构用自己私钥盖的章）
```

**有什么用（两件事）**：
1. **验证身份**：收到证书 → 验 CA 签名 → 确认"对方是真的"（警察查身份证看章）
2. **建立加密**：用证书里的公钥加密数据 → 只有对方私钥能解（用对方的"锁"锁箱子）

**为什么签名能证明"是真的"？** 数学保证：只有 CA 的私钥能盖出这个章，且盖章后内容改不了——所以"CA 签名有效" = "CA 亲自验过这个证书的主人" = 可信。

---

**【出生】车出厂 —— 种下"信任的种子"**

```
车出厂时预置两样东西：
① 初始证书 + 私钥 → 存进航盛服务的 eMMC（8.4）
② 项目根证书 → 装进 TrustManager，作为唯一信任锚（4.3）
```

- **为什么预置**：第一次联网时车和服务器还不认识对方，没有"信任种子"，第一次对话都无法安全进行
- **初始证书**：车的"临时身份证"，用于完成首次联网的信任建立（先办临时证，再办正式身份证）
- **eMMC**：车机的持久化存储芯片（断电不丢）；航盛服务负责安全读写
- **根证书 + TrustManager**：车机"只认自家 CA"——只有项目根证书签发的证书才被信任（证书固定）

---

**【领证】首次联网 —— 用临时证换正式证**

```
① 车机生成 RSA3072 密钥对（公钥 + 私钥）
② 组装 CSR（公钥 + 车辆身份 VIN → 打包成"申请表"）
③ 用初始证书建立 mTLS 通道（先证明"我是预置过信任的车"）
④ 连天威诚信 RA（ra.tca.topca.cn）提交 CSR
⑤ RA 审核身份 → CA 用根私钥签发车辆证书
⑥ 证书返回 → 存进 AndroidKeyStore
```

- **密钥对**：私钥**永远不出车**（只有它能解密），公钥交 CA 盖章做证书
- **CSR（证书签名请求）**：办证申请表——"我要申请证书，这是我的公钥，我的身份是 VIN xxx"
- **mTLS 通道**：初始证书让车先通过双向认证——只有预置过的车才能访问 RA
- **RA→CA**：天威诚信前台（RA）审材料、后台（CA）盖章出证（4.3.1）
- **AndroidKeyStore**：车机安全保险柜（硬件级保护，私钥存进去 App 都读不出）

---

**【使用】日常通信 —— 每次见面都亮证**

```
每次 HTTPS 请求：
① 服务器亮自己的证书 → 车验证（信任链）→ 确认服务器是真的
② 车亮车辆证书 → 服务器验证 → 确认车是合法的
③ 双方确认 → 建立加密通道 → 开始收发数据
```

**信任链验证怎么验？**

```
收到证书 → 看签名是谁盖的？→ 往上找那个 CA 的证书
  → 它又是谁盖的？→ 再往上 → 直到找到"项目根证书"
  → 根证书在 TrustManager 里 → 是 → 信任！✅
```

（像验钞票：看水印→防伪线→一直验到"央行发行"）

**⚠️ 项目弱点**：装完证书后主机名验证被关闭（hostnameVerifier 恒 true）——只要证书链对，域名对不对都放行（第十课#1）。

---

**【传递】证书怎么到业务 App —— 系统保管，App 申请**

**为什么证书放系统服务而不直接放 App？** ① **安全**：证书+私钥是贵重品，放独立进程隔离，App 被攻击也不泄密；② **共享**：一台车所有 App 用同一张车证书，集中管理一次搞定。

```
系统服务（NetSecurityService）             业务 App
  NtsPKIApi 拿到证书（AndroidKeyStore）
    → SecurityCertManager 通过 IPC
       广播 KeyStoreInfo（证书+私钥+根证书）──→ RNetManager 接收
    （8.3）                              → formatKeyStore() 重建 AndroidKeyStore
                                        → RHttps.setKeyStore() → OkHttp 双向 TLS
```

---

**【续期】证书到期 —— 自动续证**

- 证书有有效期（通常 1 年）；剩 **≤180 天** → 自动走"领证流程"重新申请
- 失败 → **每 10 秒重试**直到成功；过期证书直接删掉重办（`NtsPKIApi.java:179-187`）

---

> **五步串成一句话：出厂种信任种子（初始证书+根证书）→ 首次联网用临时证换正式证（CSR→RA→CA）→ 日常每次通信双向亮证（信任链验证）→ 证书由系统服务统一保管、App 经 IPC 申请 → 到期自动续证。整个体系回答一个问题："凭什么信任对方？"——因为每一张证都追溯到 CA 的根签名。**

## 第二课 · HTTP：网络世界的普通话

> 📎 本课属于【知识域三：应用交互域】，与 OkHttp/Retrofit、Token、MQTT、SOAP 聚合讲解，先看 1.4 的全貌再回这里读细节。

### 2.1 一次 HTTP 请求的解剖

点击按钮 → 代码发出 HTTP 请求 → 服务器返回数据。展开看有 4 个部分：

```
① 请求行:  POST /api/v1/hc5/vehicle/login HTTP/1.1
② 请求头:  Host: hc34-vsp-mix-vehicle.reachauto-mobility.com
           Authorization: Bearer 你的token
           Content-Type: application/json
③ 请求体:  {"vin":"LHGEJ8840R8000001", "password":"xxx"}
─── 网络传输（TCP + TLS 加密）───
④ 响应:    {"code":"000000", "description":"成功", "responseBody":{...}}
```

**项目代码对应**（`NetTestApp/.../vsp/TestVspSDKManager.java:79-113`）：

```java
@POST("hnms-facade-vehicle-production/api/v1/hc5/vehicle/login")
Call<NetworkResult<LoginResponse>> login(@Body LoginRequest request);
```

**这行接口 = ①的URL路径 + ③的请求体**。Retrofit 负责把 Java 接口翻译成真正的 HTTP 报文。

### 2.2 HTTP 方法（动词）

| 方法 | 用途 | 类比 |
|---|---|---|
| `GET` | 查询（只读） | 看菜单 |
| `POST` | 提交/创建 | 下单 |
| `PUT` | 整体替换 | 重做一桌菜 |
| `PATCH` | 局部修改 | 换一道菜 |
| `DELETE` | 删除 | 撤单 |

### 2.3 状态码（服务器暗号）

| 状态码 | 含义 | 本项目特殊用法 |
|---|---|---|
| 200 | 成功 | — |
| 201 | 创建成功 | — |
| **208** | 已报告 | **暗号：token 过期，新 token 在响应头里**（`BaseManager.java:165-175`） |
| 404 | 地址不存在 | — |
| 500 | 服务器内部错误 | — |

### 2.4 业务码 vs 状态码（本项目最精妙的设计）

状态码回答"**快递是否送达**"；业务码回答"**货物是否合格**"。服务器把业务结果放进响应体 `code` 字段：

| 业务码 | 含义 | 项目处理（`BaseManager.java`） |
|---|---|---|
| `000000` | 成功 | `onSuccess` 回调（:178-180） |
| `100005` | token 失效 | 自动刷新 token 后重发（:180-185） |
| `100015` | token 错误 | 通知重新登录（:186-191） |
| 其他 | 业务失败 | `onFail(code, description, time)` |

### 2.5 请求头 Header（快递单备注栏）

| Header | 作用 | 项目里谁加 |
|---|---|---|
| `Authorization: Bearer xxx` | 身份凭证 | `TokenInterceptor`（VspSDK.java:392-411） |
| `hc40_<包名>_sdk_version` | 版本上报 | 同一拦截器 |
| `Content-Type` | 请求体格式 | OkHttp 自动 |

> **划重点**：Header 是附加信息，Body 是主要内容。项目用拦截器统一加 Header，你写的每个接口无需手动加 token。

## 第三课 · OkHttp 与 Retrofit：司机与导航

> 📎 本课属于【知识域三：应用交互域】，与 HTTP、拦截器、Token、数据中心聚合讲解，先看 1.4 的全貌再回读细节。

### 3.1 为什么不用系统自带的 HttpURLConnection？

可以"走路"，但"开车 + 导航"更快更稳。OkHttp 是 Square 公司出品的高性能 HTTP 客户端，Retrofit 是它的"声明式接口层"。

### 3.2 OkHttp = 高性能司机

| 特性 | 类比 | 项目配置 |
|---|---|---|
| 连接池 | 车停停车场复用 | 默认：5 连接 / 5 分钟保活 |
| 超时 | 等多久算失败 | connect/read/write 各 30s（`RHttpAdapter.java:13-23`） |
| 重试 | 换条路走 | OkHttp 内部默认开启 |
| 拦截器 | 出发前/回来后的检查站 | 项目加了 3 个 |
| GZIP | 行李先压缩 | OkHttp 自动 |

### 3.3 项目的三个拦截器（最值得学的设计）

```
请求出发 ──► TokenInterceptor   （盖章：身份 + 版本）
         ──► BaseUrlInterceptor （改地址：换成当前云底座域名）
服务器返回 ─► LoggingInterceptor（记日志，BODY 级按 2001 字节分包）
```

**BaseUrlInterceptor**（VspSDK.java:413-449）的设计亮点：
接口写**相对路径**，运行时把服务器域名**动态替换**。服务器换机房/换域名，改一处配置全部生效——这就是"动态后端切换/容灾"。

### 3.4 Retrofit = 导航

```java
// 你写的（声明"我要什么"）
@GET("weather/query_now_weather_info")
Call<NetworkResult<WeatherResponse>> getWeather(@Query("vin") String vin);

// Retrofit 帮你做的
// 1. 拼 URL: GET https://.../weather/query_now_weather_info?vin=xxx
// 2. 交给 OkHttp 执行
// 3. Gson 把 JSON 自动转成 WeatherResponse 对象
```

| 注解 | 含义 | 项目例子 |
|---|---|---|
| `@GET` `@POST` `@DELETE` | HTTP 方法 | TestVspSDKManager.java:79-113 |
| `@Body` | 请求体（自动转 JSON） | `login(@Body LoginRequest)` |
| `@Query` | URL 问号参数 | `?vin=xxx` |
| `@Path` | URL 路径变量 | `/user/{id}` |
| `@Url` | 直接传完整 URL | 项目使用 |

### 3.5 同步 vs 异步

- **同步 `requestSync`**：站在快递柜前等，不拿到包裹不走（阻塞，只能子线程）

## 第四课 · HTTPS 与证书：给快递上锁（项目核心）

> 📎 本课属于【知识域二：身份信任域】，与 CA/天威、mTLS、AndroidKeyStore、航盛、安全弱点聚合讲解，先看 1.4 的全貌再回读细节。

> 这是本项目最核心、最绕的部分。分 5 小步理解，缺一不可。

### 4.0 TLS 到底是什么（先搞懂这个名字）

**TLS = Transport Layer Security（传输层安全协议）**，是所有现代"安全网络通信"的底层技术。

**一句话**：TLS 是给 TCP 信件套上的**加密 + 验证信封**。

| 协议 | 类比 | 保证什么 |
|---|---|---|
| TCP | 挂号信（可靠送达，丢件重发） | **送达**（不保证保密） |
| TLS | 加密信封 + 防伪封条 | **保密**（别人看不懂）+ **完整**（改不了）+ **验明正身**（不是假的） |
| HTTPS | = HTTP 信件装进 TLS 信封再寄 | HTTP 的安全版 |

**HTTPS 里的 "S" 就是 Secure，靠的就是 TLS**。平时说的"HTTPS 加密"、"SSL 加密"、"TLS 握手"，本质都是同一件事：走 TLS 协议。

**TLS 同时干三件事**（对应第四课后面三小节）：

1. **保密** → 加密（4.1 对称加密 + 4.2 非对称加密）
2. **验明正身** → 证书（4.3）
3. **双向认证** → mTLS（4.4，车联网特殊需求）

**TLS 握手过程（通俗版，一共四步）**：

```
① 车机: "你好，我支持这些加密算法，咱们聊聊用哪种"
② 服务器: "用这个。这是我的证书（身份证），请查验"
③ 车机: "证书是真的（信任链验证通过）→ 咱们生成一把只有咱俩知道的会话钥匙"
④ 之后: 双方用会话钥匙加密通信（对称加密，快）
```

**版本问题**：TLS 有 1.0/1.1/1.2/1.3 版本。本项目指定 **TLSv1.2**（`SSLUtil.java:25` 里 `SSLContext.getInstance("TLSv1.2")`）。老版本（1.0/1.1）有安全漏洞已被弃用。

**项目对应**：
- 谁负责把 TLS 信封组装好？→ `SSLUtil`（Http 模块）
- 谁把证书装进信封？→ `RHttps.setKeyStore()`（RHttps.java:98-110）
- 谁保障"服务器是真的"？→ 项目根证书当唯一信任锚（证书固定）

### 4.1 为什么需要加密？对称加密

- 车发"我的 VIN 是 xxx" → 明文 → 被窃听
- 用**同一把钥匙**加密解密 = 对称加密（AES）
- 致命问题：**钥匙怎么安全地交给对方？** 送钥匙的路上就被偷了。

### 4.1.1 什么是"AES 加密串"？

在项目代码里你经常看到"**AES 加密串**"这个词，比如 ICP 地址：

```java
private String icpUrl = "1et/R3PI30MtN3Xkgzp6HqkMXs5Ao/97NXDc4OWiKWo="; // 这就是一个 AES 加密串
```

**它是什么？** 一句话：**用 AES 算法加密后的"乱码文本"**。拆开理解三层：

| 层 | 是什么 |
|---|---|
| **AES** | 对称加密算法（上一节：同一把钥匙加密解密） |
| **加密** | 把原文（如真实 URL `https://hc5-icp.../icps`）用密钥 `qweasd123` 加密 → 二进制乱码 |
| **串** | 乱码是二进制，不能直接写进代码，再用 **Base64 编码**变成可见字符串 → 就是 `1et/R3PI30...` |

**项目里的一对操作**（`EncryptionManager.java`）：

```java
EncryptionManager em = new EncryptionManager();
String realUrl = em.decrypt(icpUrl);   // 解密：加密串 → 真实URL（运行时用）
String fakeUrl = em.encrypt(realUrl);  // 加密：真实URL → 加密串（写代码时用）
```

**为什么这么干？** 防止真实服务器地址**直接暴露在 APK 里**——反编译 APK 就能看到明文 URL。加密串至少增加逆向门槛。

**三个常见误区**：
1. 加密串 ≠ 乱码错误——是故意加密的，解不开才正常
2. 加密串 ≠ 不可逆——有密钥就能还原
3. **AES 加密串 ≠ TLS 加密**——前者只是"本地藏地址"的小手段，真正的传输保密靠 TLS（4.0）

> 一句话：**AES 加密串 = 用 AES+密钥把秘密文本（如服务器 URL）变成 Base64 乱码，运行时解密还原；目的是别让秘密直接躺在 APK 里。**

**项目里用的密钥：`qweasd123`（在哪、安全吗）**

| 项 | 内容 |
|---|---|
| 值 | `qweasd123` |
| 定义位置 | `Config/config.gradle:34` 的 `SECRE_KEY = "qweasd123"`（构建时注入） |
| 使用位置 | `EncryptionManager.java:40`，`AES/ECB/PKCS5Padding` 加解密（补零到 32 字节） |
| 干什么用 | 解密 ICP 地址（1.2.3）、TopCA RA 地址等服务器 URL |

**安全评价（重要）**：
- `qweasd123` 是键盘相邻键、无随机性、无长度
- 用 **ECB 模式**（最弱的加密模式：同样的明文块 → 同样的密文块）
- **硬编码在代码里**——反编译 APK 就能直接看到
- 所以它**根本不是安全措施，只是"混淆"（obfuscation）**：让真实 URL 不以明文躺在 APK 里、稍微增加逆向门槛。**真正保护通信的是 TLS，不是它**（见第十课弱点 #3）

> 一句话：**qweasd123 = 项目用来"藏地址"的 AES 混淆密钥，写在代码里、强度极低，防君子不防小人。**

### 4.1.2 全流程：一个 AES 加密串的一生（从生成到使用）

基于真实代码（`EncryptionManager.java` + 调用点）把完整链路走一遍：

**① 开发期：生成加密串**（只发生在开发者的电脑上）

开发者拿真实 URL，用**同款 AES 算法 + 密钥 `qweasd123`** 加密并 Base64，得到加密串：

```
真实URL:  https://hc5-icp.reachauto-mobility.com/icps
  │ AES/ECB/PKCS5Padding + qweasd123 加密 → 二进制乱码
  │ Base64 编码
  ▼
加密串:   "1et/R3PI30MtN3Xkgzp6HqkMXs5Ao/97NXDc4OWiKWo="
```

（项目代码里只有 `decrypt`，没有 `encrypt` 的调用——证实加密串是开发期预生成的，运行时只解密）

**② 编码期：加密串写进代码**（藏起来的位置）

| 位置 | 藏着什么 |
|---|---|
| `IcpUrlManager.java:52-56` | ICP 正式/测试地址（`formalIcpUrl`/`testIcpUrl`） |
| `Config.java:21,28` | TopCA RA 注册中心正式/测试地址（`url`/`urlTest`） |

**③ 构建期：密钥注入**

`Config/config.gradle:34` 定义 `SECRE_KEY = "qweasd123"`，构建时注入（EncryptionManager 里也硬编码了一份 `secretKey = "qweasd123"`）。

**④ 运行时：解密还原**（车机每次启动）

```java
// EncryptionManager.java:59-71 的真实解密步骤
public String decrypt(String base64Data) {
    byte[] data = base64Decode(base64Data);              // ① Base64 解码成字节
    Cipher cipher = Cipher.getInstance("AES/ECB/PKCS5Padding"); // ② 创建密码器
    cipher.init(Cipher.DECRYPT_MODE, getSecretKey(secretKey));  // ③ 解密模式+密钥
    byte[] result = cipher.doFinal(data);                // ④ 解密
    return new String(result, CHARSET_UTF8);             // ⑤ 转回文本 → 真实URL
}
// 密钥补齐细节：getSecretKey() 把 "qweasd123" 用 "0" 补齐到 32 字节（EncryptionManager.java:72-93）
```

**⑤ 使用：解密出的 URL 去干活**（两条链路）

```
链路A（ICP 查号台，1.2.3）：
  IcpUrlManager 构造解密(:82-87) → 按环境选中 icpUrl
  → getIcpUrl() POST 请求 → 拿域名表 → 写数据中心

链路B（TopCA 证书注册，4.3.1）：
  Config.getUrl() 解密(:33-40) → RA 地址 → CaManager SOAP 注册证书
```

**⑥ 弱点体检（第十课#3）**：ECB 模式（同明文→同密文，可被猜）、密钥硬编码在 APK、`qweasd123` 是键盘相邻弱密码——所以它只是"混淆"，**不是安全措施**，真正的保护靠 TLS。

> 一句话流程：**开发期加密（URL→乱码→Base64）→ 写进代码 → 运行时用同一密钥解密还原 → 拿真实地址去请求 ICP / 注册证书。**

### 4.2 非对称加密解决钥匙传递（RSA）

- 每方一对钥匙：**公钥**（可公开）+ **私钥**（死守）
- 公钥加密 → 只有对应私钥能解
- 流程：客户端用服务器公钥加密"钥匙"，服务器私钥解密 → 钥匙安全送达！

**项目里的 AES 用法**（`EncryptionManager.java:36-93`）：用 `AES/ECB/PKCS5Padding` + 密钥 `qweasd123` 加密服务器 URL——注意这里只是"混淆"，真正的加密靠 TLS。

### 4.3 证书 = 身份证，解决"这个公钥是不是真的"

**骗子问题**：收到一个"公钥"，怎么确定是官方服务器的，不是黑客冒充？

**解决**：CA（证书认证中心，本项目用 TopCA 天威诚信）给服务器签发证书：

```
证书 = 服务器公钥 + 服务器身份 + CA 的签名（CA 私钥盖章）
```

**信任链验证**：

```
车机 → 检查服务器证书 → 谁签的？→ 检查 CA 证书 → 是不是项目根证书签的？→ 是，信任！
```

**项目的"证书固定"机制**（`Http/.../SSLUtil.java:25-54`）：
把**项目自己的根证书**装进 `TrustManagerFactory`，只信任它签发的服务器证书。
> 比浏览器还严：浏览器信任几百个 CA，车机只信任自家一个。

### 4.3.1 CA 到底是什么？天威诚信是什么角色？（深度解析）

**CA（Certificate Authority，证书认证机构）** = 签发数字证书的**权威第三方**。它用自己严加保管的**根证书私钥**给"身份信息 + 公钥"盖签名章，形成证书。CA 是信任链的**顶端**：谁信任 CA 的根证书，谁就信任它签发的所有证书。

类比：

```
CA（公证处/公安局）      → 发身份证的权威机构
根证书（公安局公章印模）  → 验证一切签名的最高凭证
证书（身份证）          → 身份 + 照片(公钥) + 公章(CA签名)
车机/服务器（公民）      → 持证方
```

**天威诚信是什么角色？**

- **天威诚信 = 一家合法的"商业 CA"机构**（北京天威诚信电子商务服务有限公司，2000 年成立），**国家首批持牌 CA**：持有工信部《电子认证服务许可证》+ 国密局《电子认证服务使用密码许可证》，参与《电子签名法》起草——国内法律与技术双重可信
- **TopCA = 它运营的 CA 平台品牌**（官方 RA 服务中心 `topca.itrus.com.cn`）
- 本项目 TSP（ReachAuto）选择天威诚信作证书合作方，**车机用的车辆证书由天威诚信的根证书签发**

**CA 和 RA 的分工（"注册中心"就是 RA）**：

```
RA（Registration Authority，注册中心）= CA 的"前台窗口"
    收材料（CSR）、审核申请者身份、录入注册信息 → 交给 CA
CA（Certificate Authority，认证机构）  = CA 的"后台制证中心"
    真正用根私钥签发证书、管理续期/吊销
```

类比：**RA = 派出所窗口（收申请、审材料），CA = 制证中心（最终盖章出证）**。项目里 `service.ra.tca.topca.cn` 的 "ra" 就是 Registration Authority。

**项目里天威诚信的三处痕迹**：

| 痕迹 | 作用 |
|---|---|
| `cn.topca.api`（topca_3072 SDK） | 车机生成密钥对 + CSR（RSA3072/SHA256） |
| `service.ra.tca.topca.cn`（RA 服务器） | 车机提交 CSR、接收签发证书（SOAP 调用） |
| `Config` 里的 TopCA 许可证 JSON | 申请证书的授权凭证 |

**完整流程（车机视角）**：

```
车机生成 RSA3072 密钥对（公钥+私钥）
  → 组装 CSR（证书签名请求：公钥 + 车辆身份 VIN）
  → 用出厂预置的初始证书建立 mTLS 通道，连接天威诚信 RA
  → RA 审核身份 → 转交 CA 用根私钥签发车辆证书
  → 证书返回车机 → 存 AndroidKeyStore
  → 之后用这张证书与 TSP 云做双向 TLS
```

**为什么必须是第三方 CA，车厂不能自己签？**

信任需要**独立第三方**：如果本田自己签自己的证书，车主 App、其他服务方、监管凭什么信？——自己盖自己的章没有公信力。天威诚信是持牌独立 CA，**任何信任其根证书的一方都能验证车辆证书**，这才形成真正的信任体系。

> 一句话：**CA = 发身份证的权威机构（天威诚信），RA = 它的办证窗口（ra.tca.topca.cn），证书 = 车机的身份证，双向 TLS 就靠这张"身份证"互认身份。**

### 4.4 双向 TLS（mTLS）—— 车联网最独特的地方

普通 HTTPS 只有服务器亮证书。**车联网要双向认证**：

```
① 服务器亮证书 → 车机验证 → 确认"你是官方服务器"
② 车机亮证书 → 服务器验证 → 确认"你是合法车辆，不是黑客"
```

**这就是整个证书体系复杂的原因**：

```
车出厂 → 预置"初始证书"（航盛系统服务保管，存在 eMMC）
      → 首次联网 → 用初始证书向 TopCA 注册中心申请正式证书
      → 获得正式证书 + 私钥 → 存入 AndroidKeyStore（系统保险柜）
      → 之后每次 HTTPS 请求 → 双向认证 → 收发数据
```

**项目类与角色对照**：

| 项目类 | 角色 |
|---|---|
| `NtsPKIApi` | 证书管家：查库存、到期续、申请新证 |
| `CaSSL` | 用证书构建 TLS 通道的组装工 |
| `CaManager` | 打电话给 TopCA 注册中心申请证书的专员（SOAP） |
| `RNetManager` | 把证书从系统服务送到你 App 的信使 |
| `RHttps.setKeyStore` | 把证书装进 OkHttp 保险箱 |

**证书存储三处**（`NtsPKIApi.java:163-265`）：
1. **AndroidKeyStore**（别名：包名存客户端证书+私钥，`alias_root` 存根证书）
2. **eMMC 缓存**（航盛服务，防刷机/双系统丢失）
3. **TopCA 云端**（签发源）

**证书生命周期**：查 AndroidKeyStore → 有且未过期（剩 ≤180 天自动续）→ 直接用；没有 → 查 eMMC；还没有 → 生成 CSR 申请 → 安装 → 存 eMMC → 广播给所有 App。失败每 10s 重试。

> ⚠️ **隐藏弱点**：装完证书后项目**关闭了主机名验证**（`RHttps.java:103-108` hostnameVerifier 恒 true）。意思是"证书链对就行，域名对不对无所谓"。有 MITM 风险，但车机项目常见取舍。

## 第五课 · Token 会话与登录流程

> 📎 本课属于【知识域三：应用交互域】，与 HTTP、拦截器、NetworkResult、数据中心聚合讲解，先看 1.4 的全貌再回读细节。

### 5.1 为什么需要 Token？

证书解决"这台车是不是合法车辆"（设备级身份）；Token 解决"这个用户是谁、有没有权限"（用户级会话）。

类比：证书 = 身份证（证明我是公民）；Token = 入场手环（证明我买过票，不用反复查身份证）。

### 5.2 登录流程（项目实际）

```
① 车机拿到 VIN（数据中心）
② POST /vehicle/login {vin, password...}   → 服务器验证车架号
③ 响应返回 accessToken
④ VspSDK.setUserToken() → 存数据中心 → TokenInterceptor 生效
⑤ 后续所有请求自动带 Authorization: Bearer <token>
```

### 5.3 Token 自动刷新循环（项目最巧妙的机制之一）

```
业务请求发出 → 服务器返回 code=100005（token 失效）
  → BaseManager 通知 TokenListener.onTokenInvalid()
  → VspSDK 置 TOKEN_REFRESHING_FLAG = true
  → 数据中心的监听器触发 refreshToken()
  → 期间新请求被"缓存"进 RHttps 的 ConcurrentHashMap（putCache）
  → 新 token 到手 → TokenInterceptor.setToken()
  → setCache(false) → 缓存请求全部冲刷发出
```

**代码位置**：`VspSDK.java:149-158, 219-258` · `RHttps.java:139-191` · `BaseManager.java:180-191`

## 第六课 · Android 网络机制与 APN 蜂窝通道

> 📎 本课属于【知识域一：通信链路域】，与 TBOX、modem、SIM 卡、eCall 聚合讲解，先看 1.4 的全貌再回读细节。

### 6.0 蜂窝网络到底是什么（通俗版）

**蜂窝网络（Cellular Network）= 手机/车机的移动上网方式**，也就是大家常说的"4G 信号""5G 信号"。它是电信运营商（移动/联通/电信）铺设的广域无线网络。

**为什么叫"蜂窝"？（含命名历史）**

> **谁起的名字**：**1947年12月11日**，美国**贝尔实验室（Bell Labs）** 的工程师 **Douglas H. Ring** 在一份内部备忘录中首次提出了"蜂窝电话系统"构想（同年同事 **W. Rae Young** 参与完善）。1970 年代同一实验室的 Richard Frenkiel、Joel Engel、Amos Joel 等重新发掘并完善（尤其自动切换技术），1983 年芝加哥才开通世界首个商用蜂窝系统。所以"蜂窝"的命名源头是 **Ring 1947 年的备忘录**——他是公认的"蜂窝概念之父"。
>
> 有趣的是，"cellular（细胞的）"在 1970 年代以前**纯粹是生物学术语**（指生物细胞）。直到这个通信概念出现，才被借用指代移动通信网络。

想象一片大草原上均匀分布着很多**信号塔（基站）**，每个基站管一片**六边形区域**。无数个六边形拼在一起，就像**蜜蜂的蜂窝**：

```
      / \   / \   / \
     | 1 | | 2 | | 3 |     ← 每个格子 = 一个基站的覆盖范围
      \ /   \ /   \ /
      / \   / \   / \
     | 4 | | 5 | | 6 |     ← 格子之间无缝拼接（像蜂巢）
      \ /   \ /   \ /
```

**为什么偏偏是六边形？** 因为正六边形是唯一能在平面上**无缝密铺、无重叠无缝隙**的正多边形（圆形会重叠浪费，方形/三角形有覆盖死角）。设计图一画出来，一眼就是蜂巢的样子，于是就叫了"蜂窝"。

- 你的手机/车机插着 SIM 卡，通过**无线电波**连接最近的基站
- 你开车从格子 1 移动到格子 2 → 系统自动把连接"交接"给格子 2 的基站（叫**切换/Handover**）→ 一路上不断网
- **"蜂窝"名字还揭示了它的本质**：相隔足够远的格子可以**复用同一频率**（频率复用），让"用有限频谱服务无数用户"成为可能——这正是蜂窝网络与"一个大功率发射塔"的老式广播式电话的本质区别
- 这也是它跟 Wi-Fi 最大的区别：

| 对比 | Wi-Fi | 蜂窝网络 |
|---|---|---|
| 谁建的 | 自己家的路由器 | 运营商建的基站 |
| 覆盖范围 | 几十米 | 几百米~几公里 |
| 移动中 | 出了门就没信号 | 高速移动（120km/h）也不断网 |
| 谁付费 | 宽带费 | 流量费（车机用物联网卡） |
| 安全性 | 可设密码 | 运营商加密（+TLS 再加密） |

**车机里蜂窝网络长什么样？**

车机不是"自带信号塔"，而是内置了一个 **4G/5G 通信模块（modem）+ 物联网 SIM 卡**，就像一个永远开机的手机：

```
车机App → 网卡(vlan11/vlan21) → USB接口 → modem(4G/5G模块) → 无线电波
   → 运营商基站 → 运营商核心网 → 互联网 → TSP云平台(VSP)
```

**无线电波怎么理解？（链路图里"无线电波"那一跳）**

**无线电波 = 看不见的"快递传送带"，数据"装"在波里，光速飞向基站。**

- **本质**：电磁波的一种（和光、微波同族，只是频率不同）。两个关键特性：① **光速传播**（30 万公里/秒）；② **不需要线缆/介质**（真空也能传，声音做不到）——这就是"无线"二字的物理基础
- **数据怎么装进波里**：modem 把数字（0/1）调制成波的幅度/频率/相位变化发出去，基站收到再解调还原——和电台广播同理，只是**双向**的

```
数字: 0 1 1 0 1 0 0 1 ...
  │  modem 调制（把 0/1 变成波的某种变化）
  ▼
无线电波: ~~~~~~~~~~~~~~~（波的高低/疏密表示 0 和 1）
  │  基站天线接收 → 解调
  ▼
数字: 0 1 1 0 1 0 0 1 ...（还原成功）
```

- **蜂窝场景的 4 个要点**：
  1. **频率**：蜂窝用微波频段——4G 约 700MHz~2.6GHz，5G 有 sub-6GHz 和毫米波
  2. **共享介质**：同一片频率大家共用 → 有**频率复用**（蜂窝命名的原因）和**加密**（防截听）
  3. **会衰减**：距离远/遮挡/天气让信号变差 → 有"信号格"、有**基站切换**（开车换基站不断网）
  4. **双向**：车发上行（数据上报）、基站发下行（指令/推送）
- **项目里**：这是车机脱离物理线缆、进入运营商网络的**最后一跳**。代码完全不碰这一层（modem 内部处理），只需知道"无线电波 = 车和基站之间的无线通道"

> 一句话：**无线电波 = 车和基站之间的无线传送带；modem 把数据"装"进波里发出去，基站"卸"下来转成有线网络继续送。**

> ⚠️ **关键认知**：在车机系统里，蜂窝网络不是直接显示成一个普通网卡，而是 **modem 通过 USB 接入车机 SoC**，系统为它创建虚拟网卡 `vlan11`（APN1 通道）、`vlan21`（APN2 通道）。所以项目里申请蜂窝网络用的是 `addTransportType(8)`（8 = **USB 传输**，因为 modem 走 USB 接入）。

**modem 到底是个啥？**

**modem = Modulator-Demodulator（调制解调器）**，俗称"猫"。它负责把设备的数字信号（0/1）**调制**成适合在无线电波/电话线上传输的信号，接收时再**解调**回来——所以叫"调制解调器"。

- 上世纪拨号上网：电脑插一个"猫"接电话线，就是 modem
- 今天手机/车机里的 modem：就是那块 **4G/5G 通信芯片（基带）**，负责蜂窝网络的无线电收发、与基站交互、SIM 卡鉴权

**手机/车机的经典分工**：

```
AP（应用处理器）= 大脑：跑操作系统、App、业务逻辑（本项目代码跑在这）
modem（基带）  = 嘴和耳朵：只管无线通信，听不懂业务
     ↓ USB/PCIe 接口连接
```

**补充：AP 是什么？别和 App 搞混！**

**AP = Application Processor（应用处理器）**，是手机/车机里的**主 CPU 芯片**——跑操作系统（Android）、跑 App、跑业务逻辑的"大脑"。**它是硬件，不是软件。**

| | AP（应用处理器） | App（应用程序） |
|---|---|---|
| 是什么 | 硬件芯片（SoC 里的 CPU） | 软件程序 |
| 跑在哪 | 在手机/车机主板里 | 跑在 AP 上 |
| 例子 | 骁龙、麒麟、车规级 SoC | 微信、本项目 NetService |

**为什么分成 AP + modem 两颗芯片**：
1. **实时性**：通信协议栈对时序要求极高，独占一颗芯片更可靠
2. **功耗**：modem 可独立休眠，听网等来电不唤醒 AP
3. **专利**：基带通常含高通/华为等厂商专利，独立采购授权
4. **故障隔离**：通信模块崩了不影响操作系统和 App

**本项目里**：Android 系统 + 全部 8 个模块都跑在 AP 上。业务代码永远不直接碰 modem，只通过系统网络接口（ConnectivityManager）间接使用它。

- 业务代码（OkHttp/Retrofit）在 AP 上跑
- 发数据：AP 把数据通过 USB 交给 modem → modem 调制成无线电波发给基站
- 收数据：modem 收到电波解调成数字 → 通过 USB 传给 AP

**项目里的 modem**：车机的 modem 通过 USB 接入车机 SoC，系统为它创建虚拟网卡 `vlan11`/`vlan21`。所以 ApnSDK 申请网络用 `addTransportType(8)`（8 = **USB 传输**）——数据先到 USB，再进 modem，再上天。

> 一句话：**modem = 车的"通信耳朵"，负责把网络数据和无线电波互相翻译；本项目所有网络流量都经过它，但业务代码永远不直接碰它。**

**SIM 卡是干什么的？原理是什么？**

**SIM 卡（Subscriber Identity Module，用户身份识别模块）＝ 运营商发的"通信身份证"**。它让网络识别"你是谁、办了什么套餐、允许你联网"。类比：SIM 卡 = 小区门禁卡 + 身份证——**刷卡（身份）+ 指纹核验（鉴权）**，通过了才开门（上网）。

**卡里存了什么**：

| 内容 | 作用 |
|---|---|
| **ICCID** | 卡本身的唯一编号（出厂写死） |
| **IMSI**（国际移动用户识别码） | 你的"网络户口号"，15 位左右，网络靠它认人 |
| **Ki（鉴权密钥）** | ⭐ 最重要！跟运营商的"指纹"，**永不出卡** |
| PIN/PUK | 卡的锁屏密码 |
| 运营商配置 | 如 APN、短消息中心等 |

**原理：挑战-应答鉴权（核心）**——网络怎么确认"你是真卡，不是伪造的"？

```
① 车机/手机开机 → 向网络上报 IMSI（"我是这个户口号"）
② 网络查数据库：查这个 IMSI 对应的 Ki（运营商服务器里存着同一份 Ki）
③ 网络生成一个随机数 RAND → 发给 SIM 卡（明文，不怕偷听）
④ SIM 卡用「卡内 Ki + 标准算法」算出响应 SRES → 发回网络
⑤ 网络用「服务器里的同一份 Ki + 同一算法」自己也算一遍
⑥ 比对：两边算出的 SRES 一致 → 是真卡 ✅ → 分配 IP、开通数据通道
       不一致 → 拒之门外 ❌（假卡/复制卡）
```

**关键点**：Ki 从头到尾没有在网络上传输过，只存在于卡内和运营商服务器里。这就是"只有真卡才能通过认证"的原理——和 HTTPS 里"私钥不出门"是同一个思想。

**车联网里的 SIM 卡**：
- 车机一般用**物联网卡（IoT SIM）**，主要就是上网，不打电话
- 卡插在 **TBOX 的 modem 里**（见 1.2.2 的"车的手机"）
- 鉴权通过 → 运营商核心网给车分配 IP → 数据通道建立 → 对应到项目里的 `vlan11`/`vlan21` 网卡 → ApnSDK 才能申请到网络

> 一句话：**SIM 卡 = 车在运营商网络里的"户口+指纹"；鉴权通过才有 IP、才有蜂窝网络，之后才有本项目所有网络业务。**

**APN 是什么、项目怎么用它？** 见下面的 **6.2 小节**（APN 概念、ApnSDK 三件事、eCall 专网都在那里完整讲解）。

### 6.1 Android 网络机制基础

| 概念 | 说明 | 项目对应 |
|---|---|---|
| 权限 | `INTERNET`、`ACCESS_NETWORK_STATE` | 各模块 Manifest |
| ConnectivityManager | 系统网络管家 | `APNManager` |
| NetworkRequest | 声明"我要什么网" | `addTransportType(8)` |
| bindProcessToNetwork | 把整个进程的流量绑到某网 | APNManager.java:79 |

**"申请蜂窝网络"申请的是什么？**

申请的是**一个网络对象（Network）的使用权**，不是带宽、不是 IP。

Android 系统里同时可能存在**多个网络**——Wi-Fi、蜂窝（APN1/APN2 各算一个）、以太网、蓝牙共享等。每个 `Network` 对象代表"一套完整可用的网络连接"（网卡 + 路由 + DNS 配置）。

```
① App 写条件：NetworkRequest.Builder().addTransportType(8)  ← "我要 USB 传输类型（蜂窝modem）的网络"
② 交给系统：ConnectivityManager 扫描当前所有可用网络
③ 找到符合条件的一个 → 异步回调 onAvailable(network)  ← 把 Network 对象交给 App
```

类比：申请网络 = 到网管中心登记"给我一条符合条件（蜂窝）的线路"，系统把符合条件的线路（Network）指派给你——**拿到的是"线路的钥匙"**。

**"绑定进程到蜂窝"怎么理解？**

**`bindProcessToNetwork(network)` = 把这个进程发起的每一个网络连接，都强制从这条网络出去。**

关键前提：**默认情况下，App 流量走"系统默认网络"**（通常 Wi-Fi 优先）。车机可能同时连着车间 Wi-Fi 和蜂窝，如果不管理，业务流量可能跑 Wi-Fi 上。

```
绑定前：App 请求 → 系统默认路由（可能 Wi-Fi，可能蜂窝，系统说了算）
绑定后：App 请求 → 强制走蜂窝（vlan11/vlan21）→ 任何代码都无法改变
```

类比：平时寄快递默认走"系统选的快递公司"；`bindProcessToNetwork` 像给公司下了死命令——**"所有快递一律走蜂窝，谁都不许换"**。

**申请 + 绑定 = 完整的"抢道"流程（项目 APNManager 实际代码）**：

```
① requestNetwork(addTransportType(8))    申请：找到蜂窝网络（异步）
② onAvailable(network) 回调              拿到：Network 对象到手
③ bindProcessToNetwork(network)          绑定：进程全部流量强制走蜂窝
④ getSocketFactory()（可选）             或者：只把蜂窝的 SocketFactory 给某个 OkHttp 用（eCall 场景）
```

**为什么分两步**：申请是异步的（系统找网络要时间）；拿到 Network 后你才能选择"整个进程绑过去"（③）还是"个别连接用它"（④，eCall 只给紧急 OkHttp 用）。

> 一句话：**申请 = "我要蜂窝这条线"（拿钥匙）；绑定 = "所有流量都走这条线"（锁死路由）。**

### 6.2 APN 到底是什么（颠覆直觉）

> **这个项目根本不创建 APN。** 没有 ContentResolver/ApnSettings，没有 TelephonyManager。

APN 由车机 modem（通信模块）**预配置好**，在 Linux 层呈现为两个虚拟网卡：

| 通道 | 网卡接口名 | 用途 |
|---|---|---|
| APN1 | `vlan11` | eCall 紧急呼叫 |
| APN2 | `vlan21` | 常规 VSP 业务 |

`ApnSDK` 只做三件事（`APNManager.java`）：

1. **申请网络**：`requestNetwork(NetworkRequest.Builder().addTransportType(8)...)` — 8 = USB 传输（modem 走 USB 网卡）
2. **绑定进程**：`onAvailable` 回调里 `bindProcessToNetwork(network)`（:79）— 整个进程 socket 走蜂窝
3. **提供 SocketFactory**：`getAPN1Socket()/getAPN2Socket()` 返回 `network.getSocketFactory()`（:103-133），交给 OkHttp

**eCall 特殊路径**：VspSDK 构造时若 eCall 模式，`rHttps.setSocketFactory(APNManager.getAPN1Socket())`——紧急呼叫强制走 APN1 通道。

**权限**：`CONNECTIVITY_INTERNAL` 是系统签名权限，需要 platform keystore 签名（项目在 `Config/config.gradle` 配置了 `platform.keystore`）。

> **记忆口诀**：**蜂窝网络 = 运营商铺的"高速公路网"；APN = 你上高速时选走哪条"专用车道"；项目里的 ApnSDK 就是帮车选车道、并确保流量都走这条车道的代码。**

## 第七课 · MQTT 推送与 SOAP 遗留协议

> 📎 本课属于【知识域三：应用交互域】，与 HTTP、Token、ICP 聚合讲解，先看 1.4 的全貌再回读细节。

### 7.0 先建立直觉：MQTT 和 SOAP 是"两种完全不同的东西"

很多初学者把 MQTT 和 SOAP 放一起就晕了。其实它们**毫无关系**，只是恰好都出现在这个项目里：

| | MQTT | SOAP |
|---|---|---|
| 本质 | **通信模型**（怎么把消息送达） | **消息格式**（消息长什么样） |
| 年代 | 2010 年代 IoT 时代 | 1990~2000 年代 Web 时代 |
| 类比 | **对讲机/广播电台** | **政府专用表格** |
| 干什么 | 服务器主动往车里"喊话" | 把请求包成一段标准 XML 寄出去 |
| 项目用途 | 云端推送消息给车机 | 只有证书注册一个场景 |
| 现在还用吗 | 车联网标配，很流行 | 老系统才用，新项目不用 |

> 一句话：**MQTT 解决"怎么送"（推送到订阅者），SOAP 解决"怎么包"（用 XML 包请求）。** 它们完全可以同时存在于一个项目，各干各的。

### 7.1 MQTT —— 广播电台（下行推送）

**先回答一个根本问题：为什么车联网必须有 MQTT？**

因为 **HTTP 是"一问一答"，服务器没法主动找车**：

- HTTP 模型：车机问 → 服务器答。车不问，服务器就只能干等。
- 但车在运营商网络里**没有公网 IP**（被 NAT 藏起来了），服务器**根本没法主动发起连接**去找车。
- 可云端要主动推东西给车：远程开空调、OTA 升级通知、防盗报警……怎么办？

**答案：MQTT 的"订阅-发布"模型**。车主动连上服务器（MQTT Broker），然后一直挂着，服务器通过 Broker 中转把消息推给车。就像**广播电台**：

```
类比: 你(车机)一直开着收音机，调到你的专属频率
     电台(Broker)有人点歌给"车主8888" → 你立刻收到

MQTT: 车机 connect 到 Broker（长连接，保持在线）
     车机 subscribe("V/DA/轿车/LHGEJ8840R8000001")（订阅自己的频道）
     服务器 publish("V/DA/轿车/LHGEJ8840R8000001", "远程开空调指令")（往频道广播）
     Broker 推送给订阅了这个频道的车 → 车机收到消息
```

**MQTT 四大核心概念**：

| 概念 | 类比 | 说明 |
|---|---|---|
| **Broker** | 广播电台/邮局 | 中转站，所有消息经它转发（本项目是 TSP 的 MQTT 服务器） |
| **Topic** | 频道/频率 | 消息的分类地址，层级用 `/` 分隔：`V/DA/{车型}/{VIN}` |
| **Subscribe** | 收听频道 | 车机订阅自己的 Topic，之后该频道消息都推给你 |
| **Publish** | 往频道广播 | 发布者把消息发到某个 Topic |

**MQTT 关键配置（本项目全用上了）**：

| 概念 | 含义 | 项目配置 |
|---|---|---|
| QoS | 消息可靠等级 0/1/2 | `EXACTLY_ONCE`(2) 最可靠 |
| cleanStart | 是否清空旧会话 | `false` = 持久会话，断线不丢订阅 |
| keepAlive | 心跳间隔 | 120 秒 |
| 遗嘱消息 will | 异常掉线时替客户端发的遗言 | `willPublish().topic(topic).qos(2)` |
| sessionExpiry | 会话保留时长 | 3 天 |
| 自动重连 | 指数退避 | 1s→2s→4s→…→2min 封顶 |

**项目实现**（`NetTestApp/.../mqtt/MqttClientManager.java`，HiveMQ MQTT5 客户端）：

```
服务器地址：数据中心 BASE_MQTT_URL 动态获取（{"port":8883,"url":"hc5-daq..."}）
Topic：     V/DA/{VEHICLE_TYPE}/{VIN}
ClientId：  DA_{type}_{vin}
TLS：       用 AndroidKeyStore 客户端证书双向认证（.sslConfig().keyManagerFactory()...）
```

**MQTT vs HTTP 一句话**：

| | HTTP | MQTT |
|---|---|---|
| 通信方向 | 车 → 服务器（请求-响应） | 双向：服务器也能主动推给车 |
| 连接 | 用完就断（短连接） | 长连接（一直挂着） |
| 适合 | 登录、查天气、上报数据 | 远程控制、消息推送、状态通知 |

> 项目里两者配合：**HTTP 管"车主动问"（请求-响应），MQTT 管"云主动喊"（推送）**。

### 7.2 SOAP —— 政府专用表格（遗留协议）

**SOAP 是什么**：2000 年代的 XML 远程调用协议，又重又繁琐，现代项目基本不用。本项目**只在证书注册一个场景**用。

**关键认知**：`Soap` 模块**不是外部依赖**，而是把开源的 ksoap2-android 3.6.4 **源码复制进来改名**（`org.ksoap2` → `com.reachauto.soap.soap2`），User-Agent 还残留指纹 `ksoap2-android/2.6.0+;version=3.6.4`。

**用法**（`NetSecurityService/.../cert/CaManager.java`）：

```java
SoapObject rpc = new SoapObject("http://service.ra.tca.topca.cn/", "enrollCertAA");
rpc.addProperty("userInfo", userInfo);
rpc.addProperty("certReqBuf", csrStr);
envelope = new SoapSerializationEnvelope(SoapEnvelope.VER11);
transport.call("http://service.ra.tca.topca.cn/enrollCertAA", envelope);
```

**SOAP 报文样子**（发出去的 XML）：

```xml
<Envelope xmlns:v="...soap/envelope/" xmlns:i="...xsi" xmlns:d="...xsd" xmlns:c="...encoding">
  <Body>
    <enrollCertAA xmlns="http://service.ra.tca.topca.cn/">
      <userInfo>...</userInfo>
      <certReqBuf i:type="d:string">CSR内容</certReqBuf>
    </enrollCertAA>
  </Body>
</Envelope>
```

**调用链**：`NtsPKIApi.requestNewCert()` → `CaManager.enrollCert()` → `OKHttpsTransportSE.call()`（OkHttp 传输）→ TopCA 服务器 → 返回签名证书。

## 第八课 · IPC 跨进程通信

> 📎 本课属于【知识域四：系统架构域】，与模块划分、NetSecurityCore、RIpcCompat、启动流程聚合讲解，先看 1.4 的全貌再回读细节。

### 8.1 为什么需要 IPC？

证书存放在**系统服务进程**（NetSecurityService），而业务 App 在**另一个进程**。两个进程不能直接共享内存，必须走 Android 的进程间通信（IPC）。

### 8.2 项目用的是什么 IPC？

不是标准 AIDL Service，而是自研的 **RIpcCompat**（外部 AAR）：
- 服务端：`NetService extends RIPCService2`，`addInterface(实现类)` 注册接口（NetService.java:44-53）
- 客户端：`NetClient extends RIPCClient2`，绑定 `com.hynex.nsrnetservice.NetService`（NetClient.java:96-103）

### 8.3 共享契约模块 NetSecurityCore

两边都要知道"传什么数据、调什么方法"，于是把接口定义放在公共模块 `NetSecurityCore`：

```
NetSecurityCore
├── interfaces/ISecurityInterface.java   (getKeyStoreInfo, registerListener...)
├── interfaces/IcpInterface.java         (getBaseUrl)
├── interfaces/DataTrackInterface.java   (track)
├── model/KeyStoreInfo.java              (Parcelable: 证书+私钥+根证书)
└── aidl/ISecurityListener.aidl          (回调: onKeyStoreInfo)
    aidl/ISecurityErrorListener.aidl     (回调: onKeyStoreError)
```

**证书传递流程**：

```
NetSecurityService（服务端）                    App（客户端）
NtsPKIApi 拿到证书                              RNetManager
    │                                              │
SecurityCertManager.onKeyStoreInfo()               │ IPC 绑定
    │  通过 IPC 广播 KeyStoreInfo（含私钥）  ────────┤
    ▼                                              ▼
                                        formatKeyStore() → 重建 AndroidKeyStore
                                        → IKeyStoreListener.onKeyStore(keystore)
                                        → BaseManager → RHttps.setKeyStore()
```

> ⚠️ **架构弱点**：私钥以 Base64 字符串跨 binder 传输（`KeyStoreInfo.priKeyStr`），客户端进程内存里也持有私钥。

### 8.4 系统服务如何取到预置证书

`AochrKeyStoreManager`（NetSecurityService 内）绑定航盛（Hangsheng）系统服务：

```
bindService("com.alap.honda27hm.neusoft.commonservice")
  → IAppClientCert.Stub.asInterface(binder)
  → getCertifcateChain()   // 根证书链
```

## 附录 C · 自测题参考答案

### 第二课（HTTP）

**1. HTTP 有哪 4 个组成部件？请求头与请求体有什么区别？**

```
① 请求行:  POST /api/.../login HTTP/1.1   ← 方法 + 地址 + 版本
② 请求头:  Host / Authorization / Content-Type   ← 附加信息（给服务器的说明）
③ 请求体:  {"vin":"xxx", "password":"yyy"}   ← 真正要传的业务数据
④ 响应:    状态码 + 响应头 + 响应体（JSON）
```

区别：**请求头 = 快递单上的备注栏**（身份、格式、版本等说明），**请求体 = 快递里的货**（业务数据）。项目里 token 放请求头（`Authorization: Bearer`），登录参数放请求体（`@Body`）。

**2. 状态码 208 在本项目代表什么？在哪处理的？**

代表"**token 已过期，服务器在响应头里放了一个新 token**"。车机收到 208 就提取响应头里的新 token 并更新。处理位置：`BaseManager.java:165-175`。

**3. 业务码 100005 和 100015 有什么区别？**

| 业务码 | 含义 | 处理 |
|---|---|---|
| `100005` | token 失效（过期/被踢） | 自动刷新 token，刷新完重发请求（`onTokenInvalid`） |
| `100015` | token 错误（彻底无效） | 通知重新登录（`onTokenNull`） |

处理位置：`BaseManager.java:180-191`。

### 第三课（OkHttp/Retrofit）

**4. OkHttp 帮你解决了哪些底层问题（至少 4 个）？**

1. **连接池**：复用 TCP 连接，省去每次握手的开销（默认 5 连接/5 分钟保活）
2. **超时控制**：connect/read/write 超时（项目设 30s）
3. **自动重试**：连接失败自动换路径重试（`retryOnConnectionFailure` 默认开）
4. **GZIP 压缩**：请求/响应自动压缩解压，省流量
5. **拦截器体系**：统一的请求前后处理点（项目加了 3 个）
6. **线程调度**：异步请求自动丢到后台线程池执行

**5. 项目的 3 个拦截器分别做什么？BaseUrlInterceptor 为什么设计成"动态改域名"？**

- `TokenInterceptor`（VspSDK.java:392-411）：给每个请求加 `Authorization: Bearer <token>` + 版本头 `hc40_<包名>_sdk_version`
- `BaseUrlInterceptor`（VspSDK.java:413-449）：把请求的 scheme/host/port 改写成当前云底座 URL
- `LoggingInterceptor`：记录请求/响应日志（BODY 级）

**为什么动态改域名**：服务器换机房、换域名、多环境切换（测试/正式）时，只需要改一处配置（数据中心 `BASE_HTTP_URL`），所有业务请求自动跟着走，业务代码零改动——这就是容灾和多环境的基础。

**6. `@Body`、`@Query`、`@Path` 各自对应 URL 的哪部分？**

```
@GET("weather/query")            → 基础路径
  @Query("vin") String vin       → 拼在 ? 后面: ?vin=xxx
@GET("user/{id}")                → 路径变量
  @Path("id") long id            → 替换 {id}: /user/123
@POST("login")
  @Body LoginRequest req         → 变成请求体 JSON（不是 URL 的一部分）
```

**7. 同步和异步的区别？`requestSync` 为什么不能在主线程调用？**

- 同步：调用后**阻塞等待**结果返回；异步：调用后**立即返回**，结果通过回调（`onSuccess/onFail`）通知。
- `requestSync` 是 `call.execute()`，会阻塞当前线程。主线程被阻塞 → 界面卡死 → Android 系统 5 秒后弹 **ANR（应用无响应）**，所以同步只能在子线程调。

### 第四课（HTTPS/证书）

**8. 对称加密解决了什么、没解决什么？**

- **解决**：数据保密——同一把钥匙加解密，速度快，适合大数据量（AES）。
- **没解决**：**钥匙怎么安全地送到对方手里**。送钥匙的路上钥匙被偷，一切白搭。

**9. RSA 公钥/私钥怎么配合实现"钥匙安全传递"？**

```
① 服务器把自己的【公钥】公开给全世界（公钥不保密）
② 客户端用【服务器公钥】加密一把随机生成的"会话钥匙"
③ 只有服务器的【私钥】能解开，拿到会话钥匙
④ 之后双方用"会话钥匙"做对称加密（快），RSA 只用于开头这一次
```

核心：**RSA（非对称）只解决"钥匙分发"问题，真正的数据加密用对称加密（AES）**。项目里 `SSLUtil` 构建的 TLSv1.2 通道就是这个握手过程。

**10. 什么是证书？什么是信任链？**

- **证书** = 服务器公钥 + 服务器身份信息 + **CA 的签名**（CA 用自己私钥盖的章）。相当于"身份证"。
- **信任链** = 逐级验证：服务器证书是谁签的？→ 找那个 CA 的证书 → 它又是谁签的？→ …… → 一直到**受信任的根证书**为止。链条每一环都对上，才信任服务器。

**11. 什么是"证书固定"？项目怎么实现的？**

- **证书固定**：只信任**指定的证书/CA**，而不是信任系统里默认的一大堆公共 CA。
- 项目实现（`SSLUtil.java:25-54`）：把**项目自己的根证书**装进 `TrustManagerFactory` 作为**唯一信任锚**，`RHttps.setKeyStore()` 装进 OkHttp。所以服务器证书必须是项目根证书签发的，其他任何 CA 都不认——比浏览器（信任几百个 CA）严得多。

**12. 双向 TLS 和单向 HTTPS 的区别？项目为什么需要双向？**

| | 单向 HTTPS | 双向 mTLS |
|---|---|---|
| 服务器出示证书 | ✅ | ✅ |
| 客户端出示证书 | ❌ | ✅ |
| 服务器确认"车是谁" | 不能 | 能 |

车联网必须双向：**服务器要确认"你是合法车辆"（防伪造车/黑客盗用账号），车要确认"你是官方服务器"（防钓鱼/中间人）**。这就是项目整套证书体系（初始证书→正式证书→双向认证）存在的根本原因。

**13. 证书从出厂到日常使用的完整生命周期是什么？**

```
① 出厂: 预置"初始证书+私钥"（存在航盛系统服务的 eMMC 里）
② 首次联网: 用初始证书向 TopCA 注册中心申请正式证书（SOAP 调用）
③ 拿到: 正式证书+私钥 → 存进 AndroidKeyStore（系统保险柜）
④ 日常: 每次 HTTPS 请求都做双向 TLS 认证（出示正式证书）
⑤ 续期: 证书剩 ≤180 天到期 → 自动重新申请
⑥ 失败: 每 10 秒重试，直到成功
```

代码位置：`NtsPKIApi.java:163-265`（检查/续期）、`:284-408`（申请）。

**14. 证书存在哪三个地方？各自作用？**

| 位置 | 作用 |
|---|---|
| **AndroidKeyStore** | 运行时"保险柜"，App 每次用证书从这取（`NtsPKIApi` 管理） |
| **eMMC（航盛服务）** | 持久化备份，防止刷机/双系统切换后证书丢失（`saveToEmmc`） |
| **TopCA 云端** | 签发源，证书的真正"出生地"（`CaManager` 去申请） |

### 第五课（Token）

**15. 证书和 Token 分别解决什么问题？**

- **证书**：设备级身份——"这台车是合法的"（车机硬件与云端的信任关系）
- **Token**：用户级会话——"当前这个用户是谁、有没有权限"（车机内的业务身份）

类比：证书 = 身份证（证明我是公民），Token = 入场手环（证明我买过票）。

**16. token 失效后，项目如何自动刷新并重发请求（画流程图）？**

```
业务请求发出
  └─ 服务器返回 code=100005（token 失效）
       └─ BaseManager 通知 TokenListener.onTokenInvalid()
            └─ VspSDK 置 TOKEN_REFRESHING_FLAG = true
                 └─ 数据中心监听器触发 refreshToken()
                      ├─ 期间新请求被"缓存"进 RHttps.putCache()（ConcurrentHashMap）
                      └─ 新 token 到手 → TokenInterceptor.setToken()
                           └─ setCache(false) → 缓存请求全部自动重发 ✅
```

代码：`VspSDK.java:149-158, 219-258` · `RHttps.java:139-191`。

**17. NetworkResult 信封里有哪几个字段？success 和 code 什么关系？**

```java
public boolean notFound;   // 是否找不到
public boolean success;    // 是否成功（布尔）
public String code;        // 业务码（字符串："000000"）
public String description; // 描述
public String responseTime;// 响应时间
public T responseBody;     // 真正的业务数据
```

关系：**`success == true` 或 `code == "000000"` 都算成功**，两者是同一件事的两种表达；服务器可能只填其中一个，所以 `BaseManager` 两个都判断（`BaseManager.java:178-180`）。

### 第六课（Android/APN）

**18. 这个项目"创建 APN"吗？真正的 APN 在哪配置？**

**不创建。** 项目里没有 ContentResolver/ApnSettings，也没有 TelephonyManager。APN 由 **modem（通信模块）预配置**，在 Linux 层呈现为两个虚拟网卡：`vlan11`（APN1）、`vlan21`（APN2）。

`ApnSDK` 只做三件事：① `requestNetwork` 申请网络（`addTransportType(8)` = USB 传输）② `bindProcessToNetwork` 绑定进程流量 ③ 提供 `network.getSocketFactory()` 给 OkHttp。

**19. `bindProcessToNetwork` 的作用是什么？**

把**整个进程的所有 socket 流量**强制导向指定的网络（蜂窝通道）。调用之后，这个进程里发出的任何网络连接（不管代码里有没有指定）都会走这条网卡——这就是"车联网流量全部走蜂窝"的实现方式（`APNManager.java:79`）。

**20. eCall 为什么强制走 APN1 而不是 APN2？**

**eCall = 紧急呼叫**（碰撞自动求救、拨打紧急电话），是救命数据，必须用运营商专门为 eCall 配置的**高优先级专用通道 APN1**（`vlan11`）。APN2 是普通业务通道，可能拥堵、被限速，不能把救命数据押在它上面。所以 VspSDK 的 eCall 模式强制 `setSocketFactory(getAPN1Socket())`。

### 第七课（MQTT/SOAP）

**21. HTTP 和 MQTT 的应用场景区别是什么？**

| | HTTP | MQTT |
|---|---|---|
| 方向 | 车主动问，服务器答（拉） | 服务器也能主动推给车（推） |
| 连接 | 短连接，用完就断 | 长连接，一直挂着 |
| 适合 | 登录、查询、上报数据 | 远程控制、消息推送、状态通知 |

**根本原因**：车没有公网 IP，服务器没法主动找车；MQTT 让车主动连上 Broker 挂着，服务器借 Broker 中转推消息。

**22. 项目 MQTT 用了哪些关键配置？遗嘱消息的作用是什么？**

| 配置 | 值 | 含义 |
|---|---|---|
| QoS | EXACTLY_ONCE (2) | 消息最多一次，最可靠 |
| cleanStart | false | 持久会话，断线重连不丢订阅 |
| keepAlive | 120s | 心跳间隔 |
| 遗嘱消息 will | topic + qos(2) | 异常掉线时 Broker 替车发的"遗言" |
| sessionExpiry | 3 天 | 会话保留时长 |
| 自动重连 | 指数退避 | 1s→2s→4s→…→2min 封顶 |

**遗嘱消息作用**：车机正常退出会主动说"我要下线了"；但如果**异常掉线**（断电、断网），Broker 会替它发布遗嘱消息——让订阅方知道"这台车掉线了，不是静默消失"，云端可据此做异常处理。

**23. Soap 模块是外部依赖吗？它实际是什么？**

**不是外部依赖**。它是把开源 **ksoap2-android 3.6.4** 的**源码复制进项目并改包名**（`org.ksoap2` → `com.reachauto.soap.soap2`），User-Agent 还残留 `ksoap2-android/2.6.0+;version=3.6.4` 指纹。这么做的原因：老接口只需要其中一部分功能，vendored 方便定制（比如把底层传输换成 OkHttp）。

**24. 为什么证书注册用 SOAP 而业务用 JSON？**

因为 **TopCA 注册中心是老系统，只提供 SOAP 接口**（1990~2000 年代的协议），车机没得选，必须用 SOAP 兼容它。而 VSP 业务云是新一代系统，用轻量 JSON。所以项目里 **SOAP 只出现在证书注册一个场景**（`CaManager`），其他所有业务都走 JSON。

### 第八课（IPC）

**25. 项目用了什么 IPC 框架？和标准 AIDL Service 有什么区别？**

项目用 **RIpcCompat**（ReachAuto 自研 IPC 框架）：
- 服务端：`NetService extends RIPCService2`，`addInterface(实现类)` 注册接口（NetService.java:44-53）
- 客户端：`NetClient extends RIPCClient2`，绑定 `com.hynex.nsrnetservice.NetService`（NetClient.java:96-103）

区别：标准 AIDL 需要**手写 .aidl 接口文件**并生成 Stub；RIpcCompat 用**普通 Java 接口 + addInterface 注册 + 反射 invoke** 做远程调用，AIDL 只用于回调方向（`ISecurityListener`）。

**26. NetSecurityCore 在 IPC 中扮演什么角色？**

它是**共享契约模块**——IPC 双方（NetSecurityService 和 NetSercuritySDK）都依赖它，保证两边"说同一种语言"：
- 接口定义：`ISecurityInterface`（证书）、`IcpInterface`（URL）、`DataTrackInterface`（埋点）
- 数据模型：`KeyStoreInfo`（Parcelable：证书+私钥+根证书）
- 回调契约：`ISecurityListener` / `ISecurityErrorListener`（AIDL）

**27. 证书是如何从系统服务到达业务 App 的（完整链路）？**

```
服务端:  NtsPKIApi 拿到证书（AndroidKeyStore/eMMC/TopCA）
         → SecurityCertManager.onKeyStoreInfo()（IPC 广播 KeyStoreInfo）
客户端:  RNetManager 收到 → formatKeyStore() 重建 AndroidKeyStore
         → IKeyStoreListener.onKeyStore(keystore)
         → BaseManager → RHttps.setKeyStore() → OkHttp 双向 TLS 生效
```
