## 第1章 基础语法

**Q1: `0..list.size` 是什么、为什么越界？区间与整数除法有哪些静默陷阱？**

先说 `0..list.size` **是什么**：`..` 不是循环专属语法，而是中缀运算符——标准库函数 `rangeTo` 的语法糖（`0..3` 即 `0.rangeTo(3)`），把两个整数拼成一个 **`IntRange` 区间对象**。区间是普通的值，不依赖循环也能存在：

```kotlin
val r: IntRange = 0..3   // 表示 {0, 1, 2, 3} 四个整数，两端都含
println(2 in r)          // true——脱离循环，in 也能对区间做成员判断
```

真正驱动遍历的是 `for ... in`：对区间逐个取出整数赋给循环变量，循环轮数＝区间成员数。3 个元素的 list 配 `0..list.size`，区间是 `0..3`，**共 4 轮**——多出的那一轮就是越界现场。

而 `..` 构造的是**双闭区间**（两端都含），`0..list.size` 会一路走到下标 `size`——合法下标最大只到 `size - 1`，最后一轮 `list[3]` 越界抛 `IndexOutOfBoundsException`：

```kotlin
val list = listOf("a", "b", "c")
for (i in 0..list.size) print(list[i])       // ❌ i=3 越界崩溃
for (i in 0 until list.size) print(list[i])  // ✓ until＝左闭右开 [0, size)
for (i in list.indices) print(list[i])       // ✓ 合法下标集，意图最直白
```

区间三形态：`a..b` 闭、`a until b` 半开、`a downTo b` 递减闭，步长统一接 `step n`；坑全在右端点含不含——遍历容器下标永远 `until size` 或 `indices`，倒序 `list.size - 1 downTo 0`。

整数除法**向零截断**，不是四舍五入：`1 / 2 == 0`、`-1 / 2 == 0`（向零而非向下取整；floor 语义要 `Math.floorDiv(-1, 2) == -1`）。比例计算必踩：

```kotlin
val percent = battery / total * 100   // ❌ Int 先除后乘，battery < total 时恒为 0
val percent = battery * 100 / total   // ✓ 先乘后除；量级大先 toLong() 防溢出
```

两类陷阱的共性：**编译不报错、运行不崩溃，只是悄悄给错值**——比崩溃难发现一个量级。

## 第2章 函数与集合

**Q2: 什么是尾随 lambda（trailing lambda）？为什么 `sp.edit { putInt(...) }` 能这样写？**

**规则**：函数的最后一个参数是函数类型时，实参 lambda 可移出圆括号，括号为空则连括号省略。纯语法糖，实不变：

```kotlin
sources.startSwitch(initial, { on -> onEvent(PetEvent.SwitchChanged(on)) })
sources.startSwitch(initial) { on -> onEvent(PetEvent.SwitchChanged(on)) } // 尾随形式
```

"括号为空则连括号省略"补全演化链——同一个调用的三形态：

```kotlin
f({ ... })    // 原始形态：lambda 在括号里
f() { ... }   // 尾随：lambda 移出括号（合法但不惯用）
f { ... }     // 括号空了 → 连括号一起省
```

`startSwitch(initial) { ... }` 保留括号，因为移出后 `initial` 还在里面；`sp.edit { ... }` 敢省括号，是因为 `commit` 走默认值、括号里什么都不剩。

前提知识——**函数类型**：把"函数"本身当作一种类型，写作 `(参数类型) -> 返回类型`；函数类型作参数即"该参数接受一个 lambda 实参"，函数体内加括号调用它（`onEdge(true)`）。

`onEdge: (Boolean) -> Unit` 拆解：

- `(Boolean) -> Unit`：回调形状——事件发生时传入一个 Boolean（新状态），无返回值。
- `onEdge`：形参名，仅函数体内用于调用（`onEdge(true)`）。edge＝状态翻转事件，边沿触发语义：仅在状态改变瞬间回调（区别于电平触发）。调用方 lambda 内看不到此名字，`{ on -> ... }` 的 `on` 是调用方自己的参数名。

```kotlin
fun startSwitch(initial: Boolean, onEdge: (Boolean) -> Unit)   // 收一个 Boolean，无返回值

() -> Unit                 // 无参
(Int, String) -> Boolean   // 多参逗号隔开
((Int) -> Unit)?           // 函数本身可空，整体括起来
```

lambda 实参的格式是 `{ 参数名 -> 函数体 }`：单参不命名默认叫 `it`；函数体最后一个表达式的值就是返回值。`it` 绑定**最近的一层单参数 lambda**——嵌套时无参 lambda（如 `mainHandler.post { ... }`）不产生 `it`，内层 `forEach { dispatch(it) }` 的 `it` 是当前元素；参数两个及以上不能省名（`{ index, value -> }`）；多层 `it` 互相遮蔽时放弃 `it` 改显式命名。

Android KTX 的 `sp.edit { putInt(KEY_SWITCH, global) }` 一行叠了四个语法点（来源：androidx.core.content）：

```kotlin
inline fun SharedPreferences.edit(               // ① 扩展函数：外挂在 SharedPreferences 上
    commit: Boolean = false,                     // ④ 默认参数：不传即 apply()
    action: SharedPreferences.Editor.() -> Unit  // ② 带接收者的 lambda
) {
    val editor = edit()
    action(editor)
    if (commit) editor.commit() else editor.apply()
}
sp.edit { putInt(KEY_SWITCH, global) }           // ③ 尾随 lambda
```

④ 要同步落盘写 `sp.edit(commit = true) { ... }`。Java 等价物：`sp.edit().putInt(KEY, v).apply()`；一次写多个键时花括号作用域风格优势最明显。

② `SharedPreferences.Editor.() -> Unit` 是**带接收者的函数类型**（function type with receiver）：

- 语法：普通函数类型 `(Editor) -> Unit` 的参数列表 `()` 前加 `Editor.`。
- 该 `Editor.` 不是参数，写 lambda 时不传；由外层函数调用 lambda 时传入，成为体内隐式 `this`。
- 与扩展函数同机制：`fun Editor.f()` 体内可直接调 `putInt(...)`，此类型 lambda 体内同理。

花括号里的 `putInt(...)` 实为 `editor.putInt(...)`，解析链：

1. `action(editor)`：把 editor 实例绑定为 lambda 接收者，决定体内 `this`。
2. 裸调用 `putInt(KEY, v)` 的名字查找顺序：lambda 自身参数/局部变量 → 接收者 `this` 的成员/扩展 → 外层作用域；命中 `Editor.putInt`，解析为 `this.putInt(KEY, v)`。
3. `this` 即第 1 步传入的 editor。`this.` 可省略，与 lambda 自身参数/局部变量撞名时必须写。

字节码：`Editor.() -> Unit` 与 `(Editor) -> Unit` 同为 `Function1<SharedPreferences.Editor, Unit>`，接收者退化为第一个参数；差别仅在编译器对 lambda 体内裸名字的解析。

**辨别口诀**：读到 `xxx { }` 先找函数签名——花括号是某个函数类型形参的实参，是否带接收者看参数类型里有无 `.()`。

带接收者与普通函数类型在用法上的差别只剩一条——**lambda 里的 `this` 是谁**：

```kotlin
sp.edit { editor -> editor.putInt(KEY, v) }   // 声明为 (Editor) -> Unit：Editor 只是普通参数，每次都得写 editor.
sp.edit { putInt(KEY, v) }                    // 声明为 Editor.() -> Unit：this = editor，this 省略
```

标准库同机制练手：`apply { }`、`with(x) { }` 带接收者（体内 `this` 即对象本身），`let { }` 普通参数用 `it`，`thread { }` 无接收者无参数。

**Q3: Java 怎么调用 Kotlin 的函数类型参数？（Function1 与 fun interface）**

**SAM**（Single Abstract Method，单抽象方法接口）：Java lambda 的目标类型。Java 无函数类型，lambda 必须套在仅含一个抽象方法的接口上（`Runnable`、`Comparator`、`View.OnClickListener`）；`@FunctionalInterface` 仅做校验，可选。Java 惯例是手写回调接口作参数类型，代价是接口文件多。

`onEdge: (Boolean) -> Unit` 的 JVM 编译产物——参数类型为标准库接口 `kotlin.jvm.functions.Function1`（按参数个数有 Function0~Function22，更多参数走 FunctionN）：

```java
public final void startSwitch(boolean initialSwitch,
                              Function1<? super Boolean, Unit> onEdge)
```

```kotlin
public interface Function1<in P1, out R> : Function<R> {
    public operator fun invoke(p1: P1): R   // 唯一抽象方法
}
```

Function1 非业务方手写的回调接口，但其唯一抽象方法 `invoke` 满足 SAM 形状，Java lambda 可直接套用。两个别扭点：

```java
sources.startSwitch(initialSwitch, on -> {
    onEvent(PetEvent.SwitchChanged(on));
    return Unit.INSTANCE;   // Unit 返回值必须显式给，不能像 void 省略
});
```

- 回调类型是 `Function1` 而非业务接口：参数名、Javadoc 丢失，IDE 只提示 `invoke`。
- 必须补 `return Unit.INSTANCE;`：普通 Kotlin 函数 `fun f(): Unit` 编译为 `void`；函数类型是泛型接口，`invoke` 返回类型只能是 `Unit` 类——`Unit` 非 `void`，是全进程仅一个实例（`Unit.INSTANCE`）的单例类。Java 规则返回值非 void 必须写 return。

**折中**：`fun interface`（Kotlin 1.4+）声明函数式接口：

```kotlin
fun interface OnEdgeListener {
    fun onEdge(state: Boolean)   // 唯一抽象方法；可另挂带默认实现的方法
}
fun startSwitch(initial: Boolean, onEdge: OnEdgeListener)
```

- Java 侧：得到标准 SAM（`void onEdge(boolean)`），lambda 无需 return，参数名可见。
- Kotlin 侧：函数体内按接口方法调用（`onEdge.onEdge(false)`，不能写 `onEdge(false)`）；调用处传 lambda 自动 SAM 转换，`startSwitch(true) { on -> ... }` 照常能写。
- 选型：纯 Kotlin 模块用函数类型（省接口文件）；公开 API 面向 Java 调用方多时用 `fun interface`（互操作友好）。更上游的一问是"要不要为回调建命名接口"：回调有多个方法、或预期多个实现点（换测试替身、多处注入）——如 `PetLogger`（d/i/e 三方法）、`PetScheduler`——才定义普通 interface 把一组方法绑成契约；单方法、单实现点的一次性行为直接用函数类型，为它建接口只会留下一个永远不会有第二个实现、每个读者还要去确认"谁实现了它"的类型名。

**Q4: `listOf(...)` 是什么？返回的 List 为什么不能 `add`？**

`listOf` 是标准库的普通工厂函数（非语言关键字），把若干元素装进只读 List，等价 Java 的 `List.of(...)`：

```kotlin
public fun <T> listOf(vararg elements: T): List<T> =
    if (elements.isNotEmpty()) elements.asList() else emptyList()
```

- `vararg` 即 Java 的 `T...` 可变参数；无参调用返回 `emptyList()`——全局共享的空 List 单例，零分配。
- **不能 `add` 的原因**：Kotlin 把集合接口拆成两套——`List<T>`（get/size/遍历）与 `MutableList<T>`（另含 add/remove/set）。`listOf` 声明返回前者，编译器直接拦下变更调用；JVM 运行时两者同为 `java.util.List`，区别只在编译期——"用类型系统表达意图"：返回 `List` 即承诺"给你看，不给你改"。要可变用 `mutableListOf(...)`。
- 典型场景是状态机/决策函数返回"一帧指令清单"：分支可能产出 0/1/2 条指令，`listOf()` / `listOf(x)` / `listOf(x, y)` 零样板返回，调用方 `forEach` 消费，生产者不碰执行器（如 `enterResident(): List<PetCommand>` 返回 `listOf(Show, PlayAction(RESIDENT))`）。

**Q5: `mutableMapOf()` 与 `HashMap()` 怎么选？循环里反复 `filter` 为什么是坑？**

`mutableMapOf()` 返回 `LinkedHashMap`（记录插入顺序的哈希表），遍历顺序＝插入顺序；`HashMap()` 顺序不可预期。两者性能无实质差异，顺序可预期是纯赚——Kotlin 惯例默认 `mutableMapOf()`，`HashMap()` 留给与 Java API 交接处：

```kotlin
val timers = mutableMapOf<String, Runnable>()   // ✓ 惯例：遍历按插入序，逻辑可复现
val timers = HashMap<String, Runnable>()        // 合法但顺序不定；排查顺序相关 bug 时是干扰源
```

`filter`/`map`/`filterValues` 每次调用都**新建一个结果集合**，放进循环体＝每轮迭代白建一遍：

```kotlin
for (id in pendingIds) {
    val due = timers.filterValues { it <= now }   // ❌ 结果与 id 无关，每轮白建
}
val due = timers.filterValues { it <= now }        // ✓ 与循环变量无关 → 外提一次
```

判别口诀：集合操作符是"构建新集合"而非"免费视图"；写完看它是否在循环体内、结果是否依赖循环变量——不依赖就外提。

## 第3章 类型系统

**Q6: 安全调用 + Elvis 如何一次收口多重 null 来源？**

```kotlin
val initial = stores?.resolveSwitch() ?: true
// stores: PetStores?（var 成员），resolveSwitch(): Boolean?
```

`stores?.resolveSwitch()` 有**两条 null 路径**：`stores` 为 null 时整体短路成 null；`resolveSwitch()` 本身返回 null（首次上电无记录）。一个 `?:` 把全部 null 来源收口成 `true`。类型视角：`Boolean?` 经 Elvis 消除 null 得 `Boolean`，后续无需再判空。Java 等价物是"先声明可变变量 + if 判空逐条赋值"。Elvis 右侧除默认值外常接控制流：`val s = x ?: return`、`val s = x ?: error("未初始化")`。

注意：`stores` 在 `init()` 里刚赋过值仍要 `?.`——见 Q7，var 成员不能跨语句智能推断。

`?.` 短路的另一面是**静默失败**：链上任一环为 null，后续调用无声消失——无异常、无日志、无痕迹。`store?.saveOnceMark(key)` 在 store 未初始化时整条跳过，状态悄悄丢写。读值链配 Elvis 兜底是设计意图；**副作用型调用**（写存储、发指令、释放资源）裸用 `?.` 要慎重：空了要么记日志、要么宁可崩溃，静默跳过比崩溃难查一个量级。

**Q7: smart cast 的边界在哪里？为什么 var 成员不豁免，单例也一样？**

- **是什么**：判空或 `is` 检查通过后，编译器自动收窄变量类型，后续代码免手动强转：

```kotlin
fun printName(name: String?) {
    if (name != null) println(name.length)   // 收窄为非空 String
}

fun render(view: View) {
    if (view is TextView) view.text = "hi"   // 收窄为 TextView
}
```

- **为什么**：`PetStores?` 与 `PetStores` 是两种类型，不收窄则成员不可调用。编译器做流敏感分析（flow-sensitive typing），把控制流检查结论合并进类型信息。对比手动 `as`：转错抛 `ClassCastException`（运行时才暴露）；smart cast 的收窄由编译器证明，错误提前到编译期。
- **场景**：
  - 可空值判空后使用（最常见）。
  - `is` 检查 / `when` 类型分支内访问子类型成员。
  - `&&`/`||` 短路右侧复用左侧检查结论：`if (s != null && s.ready)`。
  - sealed class 穷尽 `when`，各分支自动收窄为对应子类（见 02 笔记 Q3）。
- **边界**：前提是编译器确信检查后变量不再改变；按声明形式执行保守规则：

| 声明形式 | 能否智能转换 |
|---|---|
| `val` 局部变量 | ✓（例外：委托属性，如 `by lazy`） |
| `var` 局部变量 | ✓ 需同时满足：检查与使用间无修改、未被修改它的 lambda 捕获、非委托属性 |
| `val` 成员属性 | ✓ 仅当 private/internal、或检查发生在声明同一模块，且无自定义 getter |
| `var` 成员属性 | **✗ 一律拒绝** |

```kotlin
object PetConfig {
    var stores: PetStores? = null
    fun init() {
        stores = loadStores()
        if (stores != null) stores.resolveSwitch()
        //                   ❌ Smart cast to 'PetStores' is impossible, because
        //                      'stores' is a mutable property that could have
        //                      been changed by this time
        stores?.resolveSwitch()   // ✓ 防御式写法，并非冗余
    }
}
```

- **`var` 成员一概拒绝的原因**：判空与使用是两次独立的字段读取（两条 GETFIELD），之间其他线程或间接调用（回调、监听器）可把字段改回 null。局部变量在栈上、仅当前函数路径可写，编译器可核实全程；成员属性全程序可写，逐例证明需全程序数据流分析，代价不可接受——按声明代替证明：`val` 豁免、局部变量有条件豁免、`var` 成员拒绝。自定义 getter 同理排除：每次访问重跑 getter，可能返回不同对象。`object` 单例不豁免：仅保证实例唯一，不保证状态不变。
- **恢复方式**：

```kotlin
val s = stores                     // ① 局部 val 快照（最常用）：局部变量才有智能转换资格
if (s != null) s.resolveSwitch()   //    或一行：val s = stores ?: return
// ② 字段改 val（生命周期上确实只赋一次时）
val initial = stores?.resolveSwitch() ?: true   // ③ 保持 ?. + Elvis 兜底（见 Q6）
```

- **延伸**：`checkNotNull(s)` / `requireNotNull(s)` / `error("...")` 调用后可触发 smart cast——contracts（Kotlin 1.3+）：函数签名声明"正常返回 ⇒ 参数非空"，编译器照契约收窄。

**Q8: `require`/`check`/`error` 三兄弟怎么选？**

按"是谁的错"选——异常类型即语义契约：

```kotlin
fun schedule(delayMs: Long) {
    require(delayMs >= 0) { "delayMs=$delayMs" }              // 调用方的错 → IllegalArgumentException
    check(this::bridge.isInitialized) { "init() not called" } // 自身状态的错 → IllegalStateException
}

fun legacy(code: Int): Action = when (code) {
    1 -> Action.START
    2 -> Action.STOP
    else -> error("unreachable code=$code")   // 逻辑上到不了，到了即崩 → IllegalStateException
}
```

- `require(condition) { msg }`：校验**入参**，违反＝调用方传错 → `IllegalArgumentException`。
- `check(condition) { msg }`：校验**对象自身状态**（初始化、时序），违反 → `IllegalStateException`。
- `error(msg)`：**逻辑上不可能**到达的分支，到达即抛 `IllegalStateException`——常作非 sealed 码值 `when` 的穷尽兜底。

三者失败即抛、消息 lambda 惰性求值，比手写 `if (!c) throw ...` 惯用且自带定位；`requireNotNull`/`checkNotNull` 正常返回后按 contracts 收窄非空（见 Q7 延伸）。选型口诀：参数坏用 require，状态坏用 check，世界坏了用 error。
