## 第2章 函数与集合

**Q1: 什么是尾随 lambda（trailing lambda）？为什么 `sp.edit { putInt(...) }` 能这样写？**

**规则**：函数的最后一个参数是函数类型时，实参 lambda 可移出圆括号，括号为空则连括号省略。纯语法糖，实不变：

```kotlin
sources.startSwitch(initial, { on -> onEvent(PetEvent.SwitchChanged(on)) })
sources.startSwitch(initial) { on -> onEvent(PetEvent.SwitchChanged(on)) } // 尾随形式
```

"括号为空则连括号省略"补全演化链——同一个调用的三形态：

```kotlin
f({ ... })    // 原始形态：lambda 在括号里
f() { ... }   // 尾随：lambda 移出括号（合法但不惯用）
f { ... }     // 括号空了 → 连括号一起省
```

`startSwitch(initial) { ... }` 保留括号，因为移出后 `initial` 还在里面；`sp.edit { ... }` 敢省括号，是因为 `commit` 走默认值、括号里什么都不剩。

前提知识——**函数类型**（把"函数"本身当作一种类型）写作 `(参数类型) -> 返回类型`；函数类型作参数即"该参数接受一个 lambda 实参"，函数体内直接加括号调用它（`onEdge(true)`）：

```kotlin
fun startSwitch(initial: Boolean, onEdge: (Boolean) -> Unit)   // 收一个 Boolean，无返回值

() -> Unit                 // 无参
(Int, String) -> Boolean   // 多参逗号隔开
((Int) -> Unit)?           // 函数本身可空，整体括起来
```

lambda 实参的格式是 `{ 参数名 -> 函数体 }`：单参不命名默认叫 `it`；函数体最后一个表达式的值就是返回值。

Android KTX 的 `sp.edit { putInt(KEY_SWITCH, global) }` 一行叠了四个语法点（来源：androidx.core.content）：

```kotlin
inline fun SharedPreferences.edit(               // ① 扩展函数：外挂在 SharedPreferences 上
    commit: Boolean = false,                     // ④ 默认参数：不传即 apply()
    action: SharedPreferences.Editor.() -> Unit  // ② 带接收者的 lambda
) {
    val editor = edit()
    action(editor)
    if (commit) editor.commit() else editor.apply()
}
sp.edit { putInt(KEY_SWITCH, global) }           // ③ 尾随 lambda
```

② 参数类型 `Editor.() -> Unit` 规定 lambda 体内 `this` 是 `Editor`，花括号里的 `putInt(...)` 实为 `editor.putInt(...)`；④ 要同步落盘写 `sp.edit(commit = true) { ... }`。Java 等价物是长链 `sp.edit().putInt(KEY, v).apply()`；一次写多个键时花括号作用域风格优势最明显。**辨别口诀**：读到 `xxx { }` 先找函数签名——花括号是某个函数类型形参的实参，是不是带接收者看参数类型里有没有 `.()`。

带接收者与普通函数类型的差别只在 **lambda 里的 `this` 是谁**（`edit` 函数体里的 `action(editor)` 就是把 editor 作为接收者喂进 lambda，之后裸写的 `putInt(...)` 由编译器解析成 `this.putInt(...)`）：

```kotlin
sp.edit { editor -> editor.putInt(KEY, v) }   // 声明为 (Editor) -> Unit：Editor 只是普通参数，每次都得写 editor.
sp.edit { putInt(KEY, v) }                    // 声明为 Editor.() -> Unit：this = editor，this 省略
```

标准库同机制练手：`apply { }`、`with(x) { }` 带接收者（体内 `this` 即对象本身），`let { }` 普通参数用 `it`，`thread { }` 无接收者无参数。

**Q2: Java 怎么调用 Kotlin 的函数类型参数？（Function1 与 fun interface）**

**SAM**（Single Abstract Method，单抽象方法接口）是 Java lambda 的目标类型：Java 没有"函数类型"这个一等公民，lambda 必须套在某个只有一个抽象方法的接口上——`Runnable`、`Comparator`、`View.OnClickListener` 皆是；`@FunctionalInterface` 注解可选，只做校验与文档。Java 惯例是先手写一个只为回调形状存在的接口再当参数类型，代价是多出这批接口文件。

Kotlin 参数 `onEdge: (Boolean) -> Unit` 编译后是标准库接口 `kotlin.jvm.functions.Function1<P, R>`（按参数个数有 Function0~N）。它"不是 Java 的 SAM"指的是**不是业务方手写的回调接口**；而 FunctionN 本身也只有一个抽象方法 `invoke`，恰好满足 SAM 形状，所以 Java lambda 能套上去用——只是形状别扭，两个别扭点：

```java
sources.startSwitch(initialSwitch, on -> {
    onEvent(PetEvent.SwitchChanged(on));
    return Unit.INSTANCE;   // Unit 返回值必须显式给，不能像 void 省略
});
```

一是回调类型是 `Function1` 而非业务接口；二是返回 `Unit` 的函数不能像 `void` 那样省略 return——`Unit` 不是 `void`，而是一个真实的单例类，`invoke` 的返回类型是它，Java 里返回值非 void 就必须写 return，所以只能补 `Unit.INSTANCE` 这个单例。**折中**：`fun interface`（Kotlin 1.4+）声明函数式接口，Java 侧立刻得到标准 SAM（回调是 void 方法，lambda 无需 return）；Kotlin 侧也不吃亏——函数体里按普通接口方法调用（`onEdge.onEdge(false)`，不能像函数类型那样 `onEdge(false)`），调用处传 lambda 则自动 SAM 转换，`startSwitch(true) { on -> ... }` 照常能写。选型：纯 Kotlin 模块用函数类型（最简，省接口文件），公开 API 面向 Java 调用方多时用 `fun interface`（互操作友好）。

## 第3章 类型系统

**Q3: 安全调用 + Elvis 如何一次收口多重 null 来源？**

```kotlin
val initial = stores?.resolveSwitch() ?: true
// stores: PetStores?（var 成员），resolveSwitch(): Boolean?
```

`stores?.resolveSwitch()` 有**两条 null 路径**：`stores` 为 null 时整体短路成 null；`resolveSwitch()` 本身返回 null（首次上电无记录）。一个 `?:` 把全部 null 来源收口成 `true`。类型视角：`Boolean?` 经 Elvis 消除 null 得 `Boolean`，后续无需再判空。Java 等价物是"先声明可变变量 + if 判空逐条赋值"。Elvis 右侧除默认值外常接控制流：`val s = x ?: return`、`val s = x ?: error("未初始化")`。

注意：`stores` 在 `init()` 里刚赋过值仍要 `?.`——见 Q4，var 成员不能跨语句智能推断。

**Q4: smart cast 的边界在哪里？为什么 var 成员不豁免，单例也一样？**

智能转换（判空或 `is` 检查后自动收窄类型）要求编译器确信**检查后变量不再改变**。它不逐例证明，而是按**声明形式**执行保守规则：

| 声明形式 | 能否智能转换 |
|---|---|
| `val` 局部变量 | ✓（未被会修改它的 lambda 捕获即可） |
| `var` 局部变量 | ✓ 条件更严：检查与使用之间无修改、未被修改型 lambda 捕获 |
| `val` 成员属性 | ✓ 仅当 private/internal、或检查发生在声明同一模块，且无自定义 getter |
| `var` 成员属性 | **✗ 一律拒绝** |

```kotlin
object PetConfig {
    var stores: PetStores? = null
    fun init() {
        stores = loadStores()
        if (stores != null) stores.resolveSwitch()
        // ❌ Smart cast to 'PetStores' is impossible, because 'stores'
        //    is a mutable property that could have been changed by this time
        stores?.resolveSwitch()          // ✓ 防御式写法，并非冗余
    }
}
```

`var` 成员一概拒绝的根源：判空通过与下一句执行之间存在**失控窗口**——另一个线程、或两句之间任何间接调用（回调、监听器）都可能把字段改回 null；逐例证明"没人改"需要全程序数据流分析，代价不可接受，于是语言设计**用声明代替证明**：`val` 承诺永不改（豁免），局部变量可见范围内可追踪（有条件豁免），`var` 成员谁都能改（拒绝）。`object` 单例同理不豁免——它只保证**实例唯一**，不保证**状态不变**，单例的其他方法、其他线程照样能赋 null。恢复方式三种：

```kotlin
val s = stores                     // ① 局部 val 快照（最常用）：局部变量才有智能转换资格
if (s != null) s.resolveSwitch()   //    或一行：val s = stores ?: return
// ② 字段改 val（生命周期上确实只赋一次时）
val initial = stores?.resolveSwitch() ?: true   // ③ 保持 ?. + Elvis 兜底（见 Q3）
```
