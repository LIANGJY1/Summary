## 第9章 异步与并发

**Q1: 注册监听只覆盖未来的变化——订阅后为什么必须对账初值？**

**现象**：典型的状态错位 bug——代码先读了初值、之后注册了变更监听（Android 的 `ContentObserver`（监听系统设置表变化的通知对象）、配置中心 listener、各类回调注册都属此类），运行中监听"明明注册了"，消费者记录的状态却与真实值永久错位，且恰好错过某一次变更。

**原因**：监听类 API 只报告"注册之后"发生的变化，**注册那一刻的当前值不回放**。而"读初值"与"注册"是两个动作，中间存在时间缝隙，缝隙内发生的变化两个来源都抓不到：

```
T0  读开关 = 关 → 状态机记住"关"
T0.5  用户打开开关        ← 趁监听还没注册
T1  注册 observer
    ← T0.5 的变化发生在注册之前，observer 永远不知道
结果：真实=开，状态机=关，"关→开"这一次永久丢失，从此错位
```

**误区**：直觉认为"注册了监听就万事大吉，observer 会告诉我一切"——漏掉了注册前的缝隙；以及反序写法"先读后注册"——读和注册之间同样有缝隙，一样丢。

**解决方案**（简化自萌宠服务读系统开关的 `startSwitch`）：**先注册、后读值**，再对账：

```kotlin
fun startSwitch(initialSwitch: Boolean, onEdge: (Boolean) -> Unit) {
    val observer = object : ContentObserver(Handler(Looper.getMainLooper())) {
        override fun onChange(selfChange: Boolean) {
            val on = readSwitchRaw()
            if (on != null) onEdge(on == 1)      // 只在有值时发沿
        }
    }
    context.contentResolver.registerContentObserver(uri, false, observer) // ① 先接上"未来"
    val now = readSwitchRaw()                                          // ② 再拍"现在"快照
    if (now != null && (now == 1) != initialSwitch) onEdge(now == 1)   // ③ 与消费者认知对账
}
```

①与②同在主线程、observer 回调也投递主线程，两者之间不可能插入回调——变化要么已反映在 `now` 里，要么必然由 observer 在之后报告，两个来源拼接无缝隙。③ 中 `initialSwitch` 是"状态机已信的值"，不一致说明缝隙里发生过它没看到的变化，补发一条**对齐沿**（合成事件）推到真实值；一致则不发，零噪音。读不到值（键不存在）宁可沉默，不发来历不明的状态。

**启示**：
- 消费者需要的是"**当前值 + 变化流**"，而底层 API 往往只卖"变化流"，前半截要自己补。`StateFlow`/`LiveData` 在收集时自动回放当前值，等于框架内置了对账；配置中心（Nacos/Apollo）的标准用法"注册 listener + 立即拉一次全量"同构。
- 可迁移检查清单：**凡"先读了状态 A、之后又注册监听"的代码，中间必有缝隙，注册之后必须再对一次账。**
- 思想备注：事件叫"沿"（借电路的上升/下降沿）——状态机消费的是"发生了跳变"而非"现在是什么"；对齐沿是相对消费者认知合成的等效跳变。
