## 第 4 章 类与对象

**Q1: 单例创建时需要注入依赖并控制初始化时序，应该选择 DCL、`object`，还是避免全局单例？**

两种写法都能安全地创建单例实例，但它们解决的是不同的初始化问题：

- `object`：实例没有构造参数，由 JVM 类初始化保证实例创建的线程安全。
- 双重检查锁（DCL，Double-Checked Locking）：首次调用工厂方法时携带参数创建实例。

```kotlin
object AppServices {
    lateinit var repository: Repository
        private set

    fun initialize(repository: Repository) {
        this.repository = repository
    }
}
```

`object` 的实例创建是线程安全的，不代表自定义 `initialize()` 自动具备幂等性或并发安全。上例仍有三种需要自行定义的行为：是否允许重复初始化、并发调用时谁生效、初始化前访问属性如何处理。

```kotlin
class AppServices private constructor(
    val repository: Repository,
) {
    companion object {
        @Volatile
        private var instance: AppServices? = null

        fun getInstance(repository: Repository): AppServices =
            instance ?: synchronized(this) {
                instance ?: AppServices(repository).also { instance = it }
            }
    }
}
```

DCL 中，外层判空避免初始化完成后继续加锁，内层判空防止并发创建多个实例，`@Volatile` 保证可见性并避免不安全发布。

这个 API 采用“首次调用生效”：实例创建后，后续调用传入的其他 `repository` 会被忽略。若初始化所有权不唯一，不应让每个调用方都携带依赖竞争首次初始化；应改用明确的初始化入口、无参访问器或依赖注入容器。

选择时先看生命周期契约：

- 依赖可在唯一、明确的启动点完成装配：优先 `object`，但要明确初始化时序。
- 实例必须在携带依赖后才能存在：构造函数能表达更强的不变量，可使用 DCL，或更常见地交给依赖注入容器管理。
- 需要测试隔离或多个配置实例：不要使用全局单例。

**Q2: 声明类级别的字符串或基本类型常量时，`const val` 可以放在哪里，为什么不能放在函数或普通实例中？**

`const val` 表示编译期常量，只能声明在文件顶层、`object` 或 `companion object` 中。它不能是局部变量或普通实例属性。

```kotlin
const val DEFAULT_PORT = 8080

class Client {
    companion object {
        const val TAG = "Client"
    }
}

object Protocol {
    const val VERSION = 2
}
```

常量类型只能是 `String` 或基本类型，初始化表达式必须能在编译期求值：

```kotlin
const val RETRY_COUNT = 3
const val ENDPOINT = "v1/items"

// const val ITEMS = listOf(1, 2, 3) // 编译错误：需要运行时创建对象
```

在 Kotlin/JVM 中，使用处通常会直接内联常量值。这带来两个影响：

- Java 可以按静态字段访问，但具体宿主类取决于声明位置和 `@file:JvmName` 等互操作配置。
- 跨模块修改常量后，未重新编译的调用方可能继续使用旧值，因此发布库时要把常量值视为 API 的一部分。

如果值需要运行时计算，使用普通 `val`；不要为了静态访问形式强行使用 `const`。

## 第 5 章 代数数据类型与模式匹配

**Q3: 建模一组数量有限、形态不同的状态或结果时，sealed 类型如何限制子类型并让 `when` 获得穷尽性检查？**

`sealed class` 和 `sealed interface` 用于表示一组受控的类型分支。编译器知道所有直接子类型，因此能检查针对该类型的 `when` 是否覆盖了全部情况。

```kotlin
sealed interface Result {
    data class Success(val value: String) : Result
    data class Failure(val cause: Throwable) : Result
    data object Loading : Result // Kotlin 1.9+
}

fun message(result: Result): String = when (result) {
    is Result.Success -> result.value
    is Result.Failure -> result.cause.message.orEmpty()
    Result.Loading -> "Loading"
}
```

在当前 Kotlin 规则下，sealed 类型的直接子类型必须位于**同一模块和同一包**，并具有完整名称；不能是局部类或匿名对象。Kotlin Multiplatform 还受到源集层级的额外限制。Kotlin 1.5 以前，sealed class 的直接子类要求更严格，必须与父类位于同一文件。

子类型通常按是否携带数据选择形态：

- 携带数据：使用普通类或 `data class`。
- 不携带数据：Kotlin 1.9+ 可使用已稳定的 `data object`；旧版工具链使用 `object`。

sealed class 的构造器默认是 `protected`，也可以显式设为 `private`，不能设为 `public` 或 `internal`。这个限制控制的是 sealed 父类如何被子类初始化，不是“封闭性”的唯一实现机制。

`when` 中的 `is Result.Success` 是类型检查；`Result.Loading` 是与单例值匹配。不要把两者都笼统理解为 `==` 判断。

**Q4: 使用 `when` 处理 sealed 类型的全部分支时，为什么添加 `else` 会让新增子类型逃过编译器检查？**

不写 `else` 时，编译器会检查所有类型分支是否齐全；新增 sealed 子类型后，遗漏分支的 `when` 会编译失败，迫使调用方处理新情况。

```kotlin
fun message(result: Result): String = when (result) {
    is Result.Success -> result.value
    is Result.Failure -> "Failed"
    Result.Loading -> "Loading"
}
```

如果加入 `else`，新增子类型会直接落入该分支，编译器不再提醒已有调用方：

```kotlin
fun message(result: Result): String = when (result) {
    is Result.Success -> result.value
    else -> "Unknown"
}
```

只有当“其余情况统一处理”本身就是稳定的业务语义时，才应使用 `else`。如果只是开发阶段暂未实现全部分支，应把它视为临时措施，并用测试或显式任务跟踪缺口。

## 第 6 章 多态与扩展

**Q5: 无法修改第三方类却想提供成员式调用时，扩展函数是否真的给类增加了方法，它的分派边界是什么？**

没有。扩展函数让调用形式看起来像成员方法，但不会修改被扩展的类，也不会获得其私有成员的访问权。

```kotlin
fun String.lastCharacter(): Char = this[length - 1]

val value = "Kotlin".lastCharacter()
```

在 Kotlin/JVM 中，扩展函数通常编译为静态方法，接收者作为第一个参数传入。默认宿主类名由源文件名生成；例如函数位于 `Strings.kt` 时，Java 通常通过 `StringsKt.lastCharacter("Kotlin")` 调用。`@file:JvmName` 可以改变这个名称。

扩展函数按调用处的**静态类型**解析，不参与成员函数的虚方法分派：

```kotlin
open class Shape
class Circle : Shape()

fun Shape.name() = "shape"
fun Circle.name() = "circle"

val shape: Shape = Circle()
println(shape.name()) // shape
```

还需记住两条优先级规则：

- 同名且签名适用时，真正的成员函数优先于扩展函数。
- 扩展函数的可用范围受导入和可见性控制。

`SharedPreferences.edit { ... }` 是扩展函数与带接收者 lambda 的组合，调用语法见 01 笔记 Q4。
