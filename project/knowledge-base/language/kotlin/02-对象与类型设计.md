## 第4章 类与对象

**Q1: 单例怎么选型？DCL 与 object + init 的语义差异是什么？**

Kotlin 里两条单例路线：

```kotlin
// 路线一：手写双重检查锁（DCL），Java 惯用法直译
class PetActionController private constructor(context: Context) {   // 展车版萌宠控制器
    companion object {
        @Volatile private var instance: PetActionController? = null
        @JvmStatic fun getInstance(context: Context): PetActionController =
            instance ?: synchronized(this) {
                instance ?: PetActionController(context.applicationContext).also { instance = it }
            }
    }
}

// 路线二：语言级单例 + init 注入
object PetCore {                          // 萌宠服务单例编排入口
    private lateinit var stateMachine: PetStateMachine
    fun init(context: Context) {
        if (this::stateMachine.isInitialized) return // 防重复 init
        // ...装配依赖
    }
}
```

- `object` 是单例语法糖：编译器生成静态 `INSTANCE`，线程安全由 JVM 类初始化保证；**不能有构造参数**，context 只能经 `init(context)` 注入，成员用 `lateinit` + `this::x.isInitialized` 防重复初始化。
- DCL 的两层 `?:` 判空 + `synchronized` 是双重检查：外层让已初始化后的调用不进锁，内层防并发重复创建；`@Volatile` 保可见性、禁重排序。
- **实质语义差异**：DCL 版实例与 context 绑死，**不存在"未初始化就被使用"的状态**（没调过 `getInstance` 就没有实例）；object 版对象第一次被访问就存在，未 init 就调其他方法抛 `UninitializedPropertyAccessException`——时序契约靠纪律维持，编译器只保证崩得早、崩得明显。
- **选型标准**：初始化点固定且唯一（如 Application 启动调用一次）→ `object` 更简洁且错误暴露早；希望实例不存在未初始化状态、或初始化时机分散（各处随手 `getInstance(ctx)` 兜底）→ DCL。初始化点固定时，构造参数往往是伪需求。

**Q2: `const val` 只能声明在哪些位置？为什么？**

`const` 是编译期常量：值必须编译期可算——基本类型或 `String` 的字面量、常量之间的运算（`const val LIST = listOf(1)` 就不行，listOf() 要运行时才执行），且不能挂任何运行时才存在的东西。能去的位置只有三个"无实例之家"：**文件顶层、`object` 体内、`companion object` 体内**——Kotlin 取消了 `static` 关键字，这三处就是它给"不挂实例"成员的显式归宿。普通类体直接写编译不过（`Modifier 'const' is not applicable to 'instance property'`：实例属性意味着每个实例各有一份，与"编译期内联、无实例参与"自相矛盾），函数体内局部变量同理不行——所以 `class PetArbiter` 这类普通类里的 TAG 必须包进 companion；而 `object PetCore` 本身就是"单例 + 静态之家"，TAG 直接写 object 体即可，再嵌 companion 纯属冗余（调用形式不变，只多编译出一个嵌套类）。

两种位置编译产物相同：外层类的 `private static final` 字段，且所有 Kotlin 使用处在编译期内联字面量：

```kotlin
Log.d(TAG, "decide")   // const：一条 LDC "PetArbiter"，直接从常量池加载
                       // 不写 const 的 companion val：GETSTATIC Companion → getTAG() 两次跳转
```

运行时连字段访问都没有（字段本身仍写进 class 文件供 Java 侧访问，无人引用时 R8 会剥除）。顺带的互操作红利：`const val` 在 Java 里就是可直接访问的静态字段 `PetArbiter.TAG`；不写 const 的 companion val，Java 得走 `PetArbiter.Companion.getTAG()`。内联的代价与 Java `static final` 同款：值被烤进每个调用点，**跨模块改 const 值后，未重新编译的模块仍用旧值**（陈旧常量）——改 const 要连同引用方一起重编。

## 第5章 代数数据类型与模式匹配

**Q3: sealed class 的封闭性与穷尽性指什么？子类有哪些形态？**

`sealed` 语义：所有子类必须与父类同包、同编译模块（**Kotlin 1.5 起放宽为同模块**，1.0/1.1 时代才要求同文件）。换来的核心能力：外部无法继承、`when` 作表达式时编译器**穷尽性检查**——漏子类直接编译报错；新增子类时所有消费它的 `when` 同时报错提醒补分支。消息协议（事件进、指令出）的可靠性就是这么交给编译器的。

子类两种形态（以车机萌宠事件协议为例）：

```kotlin
sealed class PetEvent {
    data class Init(val enabled: Boolean) : PetEvent() // 带载荷：data class
    data class TimerFired(val id: String) : PetEvent()
    object Clicked : PetEvent()                        // 无载荷：全进程单例变体
}
```

- 带载荷 → `data class`：构造参数即 `val` 属性，自动生成 `equals/hashCode/toString/copy/componentN`，对照 Java 16+ `record`。
- 无载荷 → `object`：该变体全进程一个实例，`==` 即引用相等；`: PetEvent()` 的括号是在调密封父类构造器（sealed 构造器默认 private、仅同包/同模块子类可调——"封闭"的实现机制）。
- 对照：enum 常量单例、结构固定，表达不了"同族但载荷各异"；Java 17 `sealed` 要求 `permits` 显式列全子类，Kotlin 同模块即封闭更省。

"`==` 即引用相等"的完整推理链：Kotlin 的 `==` 是**结构相等**，编译为 `a?.equals(b) ?: (b === null)`（null 安全），比的是内容；`===` 才是引用相等（同 Java 的 `==`）。`object` 变体没有可比较的字段、不重写 `equals`，走 `Any.equals` 的默认实现——默认实现恰好就是引用比较；再叠加实例唯一，结构相等与引用相等必然重合。对照带载荷变体：`Init(true) == Init(true)` 为 `true`（两个不同实例、data class 逐字段比），`Init(true) === Init(true)` 为 `false`。`when` 分支匹配用的就是 `==` 语义，单例变体因此只是一次 O(1) 引用判断——这是无载荷变体选 `object` 的回报之一：它的全部身份就是它自己，不存在"两个内容相同的实例"这种讨论。

**Q4: sealed + `when` 写了 `else`，穷尽性检查为什么就没了？**

穷尽性检查的前提是编译器确认**分支列表是显式列全的**；`else` 一出现，语义变成"其余全归 else"——此后新增子类，所有消费它的 `when` 不再报错，漏处理的变体被 `else` 静默吞掉：

```kotlin
when (command) {
    is PlayAction -> send(command)
    Hide, Show -> send(command)
    else -> log("unrouted")   // ❌ 写上 else：此后新增 StopAction/WearSkin…编译器永远沉默
}
when (command) {
    is PlayAction -> send(command)
    Hide, Show -> send(command)   // ✓ 不写 else：新增变体＝此处编译报错，编译器逼你补全
}
```

取舍：`else` 只在"其余统一处理"是**真实业务语义**（而非"以防万一"）时写。骨架期用 `else` 放行未实现分支是常见权宜——代价是关掉了编译器对新增变体的提醒，要靠场景表测试兜底，阶段推进后应删掉 `else` 让编译器接管。旁注：enum 的 `when` 同理，`else` 同样吞掉新增枚举值的提醒；语句位置的 `when` 对 sealed/enum 主体自 Kotlin 1.7 起也强制穷尽（1.6 警告、1.7 起报错）。

## 第6章 多态与扩展

**Q1: 扩展函数是什么？它真的给类"加"了方法吗？**

```kotlin
fun SharedPreferences.Editor.clearAndPut(key: String, v: Int) {
    clear()          // this = 调用者那个 Editor，可省略；与参数撞名时必须写 this.
    putInt(key, v)
}
sp.edit().clearAndPut(KEY, 1)   // 调用形状像成员函数
```

语法上"长在"别的类上——框架类、第三方类改不了源码也能外挂方法；**本质是糖衣顶层函数**：编译后 receiver 退化为第一个参数，Java 侧看到的是 `EditorExtKt.clearAndPut(editor, KEY, 1)`（文件名 + Kt 门面类的静态方法）。三个边界：不能访问 private 成员；分发是**静态的**——按编译期声明类型解析，没有多态重写；`this` 可显式写，仅在与参数名撞名时必须。01 笔记 Q1 里 KTX 的 `sp.edit { }` 就是"扩展函数 + 带接收者 lambda"的组合。
