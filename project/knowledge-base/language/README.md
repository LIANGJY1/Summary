# Language — 编程语言知识域（第二级分发）

> ROUTING.md 主判据链第 1 条的落点：凡「编程语言本身」的知识先进本目录，再按本文件分发。本文件是二级分发与新语言准入的单一事实源；维护者 session-to-knowledge。语言子目录变动只登记本文件「目录」节，不回填 ROUTING.md（路由表只到 language/ 粒度）。

## 边界

**收**：

- 某门语言的语法、类型系统、集合、并发模型、泛型/反射/元编程等语言特性与惯用法
- 该语言标准库与官方工具链行为（编译器、构建对语言特性的处理）
- 以「学会这门语言」为骨架的学习体系笔记，可含生态应用章（如 `kotlin/04-生态与应用.md`）；练习/实验项目（如 `C++/cpp_practice_project/`）

**不收**（退回 ROUTING.md 判据链 2–6）：

- 把语言名换掉结论仍成立的知识——通用设计思想 → design-principles.md；第三方框架/SDK 设计 → sdk-design.md；Android UI 坑 → android-ui.md
- 业务逻辑与工程模式，**即使示例代码是本语言写的**：判定看知识内核，不看代码语言——如「订阅监听后必须对账初值」换任何语言都成立，属工程模式不属 Kotlin 语法，归宿是项目文档或 design-principles.md，不是本域
- 同一主题两边都够格时各写各的角度、互相不复制（例：Kotlin 协程的挂起机制 → `kotlin/`；跨库并发设计思想条目 → sdk-design.md）

## 分发策略（三步判定，按序执行）

1. **替换语言测试**（再验入口）：把知识中的语言名换成任意另一门语言，结论仍成立 → 不是语言知识，退回 ROUTING.md；只在特定语言下成立 → 进第 2 步。
2. **复习场景定主语言**：六个月后要用这条知识时，我大概率在写哪门语言，就分发到哪门语言的目录。
   - 互操作/迁移类按消费语言归档：Kotlin 调 Java 的坑 → `kotlin/`（谁在写代码归谁）。
   - 对称的语言对比 → 归结论主要服务的语言；确实无主 → 问用户，或经用户确认建 `跨语言/` 子目录并在「目录」节登记。
3. **落点判定**（动态）：
   - 语言子目录已存在 → 进入并按「文件归并」落文件。
   - 不存在 → 新语言准入：用户确认开启该语言学习线，或手头已有 ≥2 条该语言知识 → 建目录（命名用官方惯用写法：`java/` `kotlin/`；带符号习用名保留：`C++/`）→ 在「目录」节登记一行。
   - 孤例（单条知识、不成学习线）→ 不强建目录，问用户去处。

## 文件归并

- 先找既有文件归并：主题相同/相邻并入既有文件；无处可归再新建，文件名用主题名（如 `java/泛型.md`），教学系列可用编号前缀（如 `kotlin/01-语法基础.md`），零散沉淀不编号。
- 讲解风格以本文件「问题式笔记写作规范」为准；所有新增与修订内容都必须遵守，不沿用生成模型的默认文风。
- **Q 序号＝文档位置序号**：问答标题（`**Qn:**`）按文中出现顺序从 Q1 起全文件连续编号——不按章重启、不按沉淀先后；后补的 Q 插进中间时，其后所有 Q 顺延重编，同文目录、文内交叉引用（如「见 Q7」）与跨文件引用（如「01 笔记 Q2」）一并同步更新。跨文件连续的只有章号，Q 号只保证单文件内连续。
- 与语言版本相关的结论在文内注明版本，不为版本另建目录。
- 本域笔记是人读散文：不强制条目格式与复习者测试（与条目大类的本质区别）；修订就地改，结论反转直接改写。

## 问题式笔记写作规范

本规范追求的不是“尽量短”，而是**用最少的必要信息把问题讲完整**。读者应当只看问题就知道讨论发生在什么场景，只看答案首段就得到结论，继续阅读时能沿着连续的因果链理解原因。

每次新增或重写问题，按以下顺序执行：先确定这个 Q 唯一要解决的核心问题，再写出包含必要语境的标题，然后围绕标题承诺组织答案，最后逐项执行本节末尾的验收清单。只有清单全部通过，内容才算完成。

### 1. 问题必须脱离上下文仍能成立

每个 Q 只解决一个核心问题，但标题不能缩成一个缺少前提的标签。问题通常应包含三类信息：

1. **场景或前提**：读者正在使用什么类型、语法或 API。
2. **现象或分歧**：出现了什么结果，或面临什么选择。
3. **学习目标**：需要理解原因、边界还是正确做法。

标题不强制套用固定句式，也不要求三部分机械齐全；判断标准是：从搜索结果单独看到这个标题时，读者能否准确判断它是不是自己遇到的问题。

反例：

- `整数除法为什么会得到错误的比例？`——没有说明操作数类型、计算表达式和错误现象。
- `为什么循环内反复 filter 是问题？`——没有说明过滤结果是否依赖循环变量，容易被误读成“循环里不能使用 filter”。

推荐写法：

- `使用 Int 计算百分比时，为什么 battery / total * 100 可能得到 0，应该怎样保留正确精度？`
- `循环处理多个元素时，为什么不应在每轮都执行与循环变量无关的 filter？`

如果一个标题需要用两个互不依赖的“为什么”连接，应优先拆成两个 Q，并同步更新目录、后续编号及交叉引用。

### 2. 答案先解决问题，再展开知识

- **首段直接回答**：先用 1～3 句话说明结果、原因和推荐做法，不从历史背景、术语定义或类比开始。
- **按需展开，不套模板**：示例、机制、边界、版本、选型只在有助于理解时出现；不要为了形式完整给每个 Q 填相同的小节。
- **保持因果连续**：优先按“前提 → 发生的行为 → 结果 → 正确做法”或“概念 → 机制 → 影响”展开。不要在语言语法、编译器实现、JVM 产物和工程建议之间来回跳跃。
- **先主线，后细节**：不影响正确使用的字节码、性能实现和互操作细节放在主结论之后；细节不能打断当前问题的解释。
- **结尾给可执行判断**：存在多种写法时，说明各自在什么条件下使用，不能只罗列 API 或优缺点。

列表用于并列条件、步骤或选项；能用连续两三句话说清的内容，不强行拆成列表。

### 3. 示例必须最小、完整、服务于当前结论

- 语言特性优先给脱离具体项目也能理解的最小示例；只有知识本身属于 Android、服务端或互操作场景时才引入对应平台类型。
- 示例应包含理解当前行为所需的声明、输入和调用；若不是完整代码，必须明确标出省略部分。
- 关键示例应写明编译结果、运行结果、异常或预期输出，不能让读者自行猜测。
- 错误示例与正确示例只保留造成差异的最小变量，避免业务命名遮蔽语言机制。
- 同一示例不要承担多个新概念；确实需要组合解释时，先分别讲清前置概念，再展示组合用法。

“示例驱动”不等于每个 Q 都必须先放代码。概念性结论用一句话已经足够时，不为满足格式而制造示例。

### 4. 术语、平台和版本必须准确

- 使用一个稳定术语指代一个概念，明确区分容易混淆的概念，例如只读与不可变、实例创建安全与初始化并发安全、结构相等与引用相等。
- 涉及 Kotlin/JVM、Kotlin Multiplatform、Android 或 Java 互操作时，明确结论适用的平台，不能把某个后端的实现写成 Kotlin 语言的普遍保证。
- 涉及版本演进时标出关键版本边界；无法确认当前行为时先查官方文档，不凭记忆写绝对结论。
- 避免“永远”“完全相同”“零开销”“只是语法糖”等过度概括；若结论存在例外，应在首次出现时限定范围，而不是等到后文推翻。
- 解释“为什么”时给出直接因果，不用未经证明的底层实现猜测代替语言规则。

### 5. 言简意赅的判定标准

应该删除：

- 重复表达同一结论的段落。
- 只增强语气、不增加信息的口诀和总结句。
- 与当前问题无关的知识扩展、业务背景和历史沿革。
- 已在其他 Q 完整解释、此处又从头复述的机制。
- 不能帮助读者做出判断的字节码或源码细节。

不应该为了缩短而删除：

- 问题成立所需的前提条件。
- 从现象到结论之间的关键因果。
- 会改变选型或正确性的边界条件。
- 最容易导致误用的反例。

因此，验收指标是“最短的完整解释”，不是字数、段落数或固定模板。宁可增加一句必要前提，也不要留下一个短而含糊的问题。

### 6. 跨问题与跨文件衔接

- 同一机制只在最匹配的 Q 中完整解释，其他位置用一句承接语和精确引用关联，不复制正文。
- 基础语法笔记负责语言机制；生态应用笔记负责平台用途与行为边界。示例使用某个平台 API，不代表整套平台知识都要塞进基础语法问题。
- 引用必须说明两部分内容的关系，例如“尾随 lambda 的调用规则见 01 笔记 Q3”，不能只写孤立的“见 Q3”。
- 后补内容应插入最合适的知识位置，而不是一律追加到文件末尾；随后按「Q 序号＝文档位置序号」同步重编号。

### 7. 正文按信息关系组织，不按想到的顺序堆叠

先判断每段内容承担什么作用，再决定用段落、列表、表格还是代码。表达形式必须服务于信息关系：

- **段落**：解释一个结论及其因果，适合需要连续推理的内容。
- **无序列表**：呈现并列条件、选项、收益、限制或注意事项。
- **有序列表**：呈现必须依次执行的步骤、因果阶段或明确的优先级。
- **表格**：多个对象需要沿相同维度逐项比较。
- **代码块**：展示只有通过语法、类型或运行结果才能说清的行为。

正文遵守以下顺序：

1. 先回答标题提出的具体问题。
2. 再解释导致该结果的直接机制。
3. 然后补充会改变结论的边界或反例。
4. 最后给出选择或使用规则。

这只是默认阅读顺序，不是固定模板。某个问题不需要其中一层时直接省略，不能用空泛内容补齐形式。

一个段落只承担一个主要作用。首句指出本段结论，后续句子只负责解释、证明或限定它；出现新的独立结论时另起段落。连续推理不能拆成互不相干的短句列表，也不能把多个主题压进一个超长段落。

章节和小标题按知识边界划分，不按篇幅划分。两个自然段能够讲完的局部解释不另建三级标题；当读者需要在多个独立部分间导航时才增加标题。

### 8. 列表要短、平行并且有明确分类维度

列表用于降低并列信息的扫描成本，不是默认排版方式。使用列表前先写一句引导语，明确列表回答的问题或比较维度。

正确写法：

```markdown
选择取决于结果需要：

- 只要整数百分比：先乘后除，必要时先转为 `Long` 防止溢出。
- 需要小数：除法前把至少一个操作数转为 `Double`。
- 需要向下取整：使用 `Math.floorDiv`，不要依赖整数除法的向零截断。
```

每个列表项必须满足：

- **语法平行**：同一列表都用结论句、条件句或动作句，不在不同语法结构间切换。
- **层级一致**：同一列表项处在相同抽象层，不能把“语言规则”“某个业务示例”和“延伸阅读”并列。
- **一项一意**：每项只表达一个条件或选择；出现独立的第二个结论时拆项。
- **关键词前置**：读者需要快速比较时，使用“**条件或对象**：结论”的结构。
- **解释紧随结论**：一项通常控制在一两句话；需要连续推理时移到列表后的段落中解释。

列表类型按语义选择：

- 条目没有先后关系时使用 `-`。
- 步骤必须依次完成，或顺序本身影响结果时使用 `1. 2. 3.`。
- 只是为了显得有结构时继续使用段落，不把说明文字伪装成步骤。

嵌套列表最多深入一层。第二层仍需展开长段解释时，改用小标题或独立段落。避免只有一个列表项的列表，也避免每项都是一大段正文的“列表墙”。

因果链不拆成无序列表。例如“判空成功 → 类型收窄 → 可以访问成员”是连续过程，应写成句子或有序步骤；拆成三个并列圆点会丢失方向关系。

### 9. 表格只用于同维度比较

满足以下条件时使用表格：

- 至少有两个比较对象。
- 每个对象都能沿相同字段回答，例如“是否可变、是否保证顺序、失败异常”。
- 读者的主要任务是横向比较，而不是理解一条连续因果链。

表头直接写比较维度，单元格只放短结论；复杂原因放在表格后说明。不要把长代码、多段解释或不同层级的信息塞进单元格，也不要为只有一行数据的内容创建表格。

表格前先给选择结论，表格用于验证和对照，不能要求读者从大量格子中自行推导作者观点。

### 10. 代码、强调和术语标记保持克制

- 文件名、类型、函数、属性、关键字、表达式和具体值使用行内代码，例如 `MutableList`、`filter`、`a until b`。
- 核心概念或选择条件可以加粗，但每段只突出真正决定理解的少数词；不要整句加粗。
- 代码块必须标注语言，并紧邻解释它的正文。代码前说明要观察什么，代码后说明结果为何如此。
- 错误与正确写法并列时，用注释标明差异发生的位置，不在两个大型代码块之间重复整段代码。
- 首次出现且不易从名称理解的术语，要用一句话定义；后续统一使用同一名称，不反复换同义词。

代码示例中的注释解释**当前行的结果或意图**，不承担正文级背景教学。注释长到需要两三句话时，把解释移出代码块。

### 11. 过渡句必须说明内容之间的关系

跨段落或跨层次时，用一句短过渡交代为什么下一部分值得读，例如：

- “上面解释了调用语法；下面只讨论接收者如何绑定为 `this`。”
- “实例创建虽然线程安全，但自定义初始化仍有独立的并发问题。”
- “只读限制作用于当前引用，并不能推出底层对象不可变。”

过渡句应指出递进、转折、因果或范围变化，不能只写“接下来介绍”“除此之外”“值得注意的是”。如果相邻两段不需要关系说明也能自然衔接，不额外添加过渡。

不要使用聊天式铺垫、设问式自答或情绪化评价推动正文，例如“你可能会问”“神奇的地方来了”“这个坑非常隐蔽”。直接陈述触发条件和后果。

### 12. 总结只提炼决策规则，不重复正文

总结的任务是让读者在以后复习时快速恢复**怎么判断、怎么选择、怎么避免错误**。它不是把前文换一组近义词再说一次。

按内容复杂度选择总结形式：

- 只有一个结论：用一句判断规则收尾，不加“总结”标题。
- 存在多个并列选择：用短列表写成“条件 → 做法”。
- 多个对象需要按固定维度比较：先给一句推荐，再使用表格。
- 正文已经很短：不再总结，避免结论重复两遍。

好的总结应保留：

- 决定结果的前提条件。
- 可以直接执行的做法。
- 最容易改变结论的边界。

好的总结应舍弃：

- 前文已经展示过的代码过程。
- 术语定义和历史背景。
- 为加强语气而添加的口号、口诀或“综上所述”。
- 没有选择意义的实现细节。

例如，解释整数百分比后可用下面三项收口：

- 需要整数结果：先乘后除，并检查溢出。
- 需要小数结果：除法前转换操作数类型。
- 需要特定舍入规则：显式选择对应的舍入 API。

这三项分别对应真实选择条件，比“整数除法容易出错，要多加注意”更适合复习和执行。

### 13. 生成或改写内容的固定执行流程

任何模型新增或重写语言笔记时，都按以下流程执行：

1. **定位**：阅读目标文件、相邻 Q 和本规范，确认内容归属及已有术语。
2. **定核**：用一句话写出本 Q 唯一要解决的问题；存在两个独立问题时先拆分。
3. **补境**：把问题成立所需的类型、表达式、调用场景或异常现象写入标题。
4. **直答**：先完成答案首段，确保不依赖后文也能回答标题。
5. **排因果**：列出读者从现象走到结论必须经过的推理节点，按依赖顺序组织。
6. **选形式**：连续推理用段落，并列条件用列表，真实步骤用有序列表，同维度比较用表格，语法行为用代码。
7. **补边界**：只加入会改变正确性、选型或理解的版本、平台、反例和实现细节。
8. **压缩**：删除重复结论、无关背景、口号、弱过渡和不能改变判断的细节。
9. **衔接**：检查相邻 Q 的前置关系；已有解释改用精确引用，不复制正文。
10. **校验**：执行下一节的逐题验收，并同步目录、Q 编号及所有交叉引用。

流程约束的是生成过程，不要求最终文章暴露这些步骤，也不要求每个答案长得一样。

### 14. 写完后的逐题验收

新增或重写 Q 后逐项检查：

- 只看标题，是否知道场景、具体困惑和回答目标？
- 标题是否只承诺一个核心问题？正文是否完整回答了这个承诺？
- 首段是否已经给出专业、明确的结论？
- 段落、列表、表格和代码是否与信息关系匹配，而不是为了排版随意选择？
- 每个段落是否只有一个主要作用，首句是否点明本段结论？
- 每个列表是否有明确引导语，列表项是否平行、同层级且一项一意？
- 有序列表是否确实存在执行顺序，无序列表是否确实是并列关系？
- 示例是否比文字更容易理解，并且没有引入无关概念？
- 代码前后是否分别说明观察目标和结果，读者是否无需猜测输出或错误？
- 解释能否沿一条因果链读完，中间是否突然跳到实现或工程话题？
- 是否漏掉会改变结论的平台、版本或边界条件？
- 过渡句是否明确表达递进、转折、因果或范围变化？
- 总结是否提炼成可执行的判断规则，而非复述正文？短答案是否省掉了多余总结？
- 是否存在可以删除而不损失信息的句子？
- 是否与其他 Q 重复？目录、编号和交叉引用是否已经同步？

任一项答不上来，继续修改，不以“语法正确”或“内容足够多”视为完成。
