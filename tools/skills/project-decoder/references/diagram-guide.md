# 架构图生成指南（SKILL.md §5 动笔前必读）

> 图不是"画画"，是把 §2 验证过的依赖事实翻译成图形语法。**先写正文模块表/类表（模型），再画图（视图）**——图里每个节点、每条边都必须能在正文 §3/§4/§7 找到对应（图与正文同源）。调研依据见 `skill-research/sources/G-架构图skill调研.md`。

## 图类型选择：回答什么问题，画什么图

| 图 | 回答的问题 | Mermaid 类型 | 默认 |
|---|---|---|---|
| 一图流（分层组件图） | 系统内部分层与模块依赖 | `graph TB`（链路长用 LR） | **必画** |
| 主链路时序图 | 一次典型请求跨模块的时序与线程切换 | `sequenceDiagram` | 主链 >5 环时**必画** |
| 上下文图 | 本系统与外部角色/系统/存储的边界 | `graph LR` | 外部依赖 ≥3 时画 |
| 状态机图 | 核心对象的状态转移（§4 深卡片涉及状态机时） | `stateDiagram-v2` | 有明确状态机时画 |
| 部署拓扑 | 运行时进程/容器/数据存储 | `graph TB` | **有 docker/k8s/构建部署文件作事实源才画**，README 不算 |

- 每张图开头一行写明"本图回答什么问题"；不要试图一张图回答所有问题。
- **不用 Mermaid 的 C4 图语法**（`C4Context` 等，官方标注 experimental，渲染支持参差）；C4 思想照用——分层画法（先上下文后内部）、每层明确 scope 与读者。
- **不 ASCII / Mermaid 双写**：两份图必漂移。默认只写 Mermaid（GitHub/VSCode/Typora 原生渲染）；用户环境确认不渲染才整体换 ASCII（规则同 architecture-doc-template）。

## Mermaid 语法军规（防渲染翻车）

1. **nodeId 一律 ASCII**（`Gateway`、`Cache`）；中文、括号、冒号等全部放进引号标签：`Gateway["API 网关（入口）"]`。
2. 节点文本内**禁裸 `()` `[]` `{}`**——形状在语法层选（`[矩形]` `(圆角)` `[(数据库)]` `{菱形}`），文本里不再嵌套括号字符。
3. subgraph 的 id 用 ASCII、标题走引号：`subgraph SG1["接入层"]`。
4. 样式克制：`classDef` ≤4 种（入口/存储/外部/核心），只服务语义分层不做装饰；形状优先于颜色（语义在黑白打印下也不丢）。
5. 每图 **≤12 节点、≤16 边**；超了拆图，或 subgraph 上卷成组、只画组间边。
6. 边上的动词标签（`-->|触发|`）用普通动词（触发/产出/查询/写入），不写方法签名；`[inferred]` 的边在图例行注明，不写进边标签。
7. 时序图参与者 ≤8；每条消息对应真实方法（file:line 挂在正文 §4 主链路，图保持干净）。

## 从代码生成（code-to-diagram 纪律）

- 先识别框架找已知形状（Spring Boot: Controller→Service→Repository；React: Component→Hook→API client），**但形状必须被本仓 import 图证实**，不许套模板。
- 部署拓扑只认 compose/k8s/构建部署文件；框架约定的"典型分层"若与本仓 import 方向矛盾，以本仓为准并写入「矛盾与意外」。

## 生成前检查（过完才落盘）

1. 跑机械校验：`python3 scripts/check_mermaid.py <落盘文档.md>` 全绿（引号配平、nodeId ASCII、节点/边数上限、图类型识别）。
2. 环境有 `mmdc`（mermaid-cli）时渲染验证：`mmdc -i block.mmd -o /tmp/out.svg`；无 mmdc 不强求，过第 1 步 + 逐行自查即可。
3. 同源抽查：随机抽图上 3 个节点，回正文找到对应模块/类条目；抽 2 条边，回 §2 分层验证核对方向。
4. 图例齐全：形状/样式含义、inferred 标记说明，图下一行说清。
