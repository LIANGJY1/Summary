# 类与模块卡片模板（SKILL.md §3/§4 用）

## 全类职责表（一行格式）

```
| 类 | 一行职责 | 关键协作 |
|---|---|---|
| RequestManager | 生命周期感知的请求入口与挂起/恢复总控（EX: RequestManager.java:40） | Target(Fragment/Activity) → RequestTracker |
```

**一行职责的好坏对照**（万金油测试：换掉类名句子还成立 = 不合格）：

- ❌ 「网络请求的核心处理类，职责清晰，是架构的重要一环」——套谁身上都行
- ✅ 「生命周期感知的请求总控：宿主启停时批量挂起/恢复请求，销毁时取消全部（EX: RequestManager.java:118）」——只有它成立

## 核心类深卡片（CRC 变体）

```md
### <类名>（<所在模块>）

**职责**：一句话（贴接口讲，不贴实现）。
**协作者**：它调用谁 / 谁调用它（file:line）；在主链的哪一段。
**设计动机**：解决什么矛盾 → 为什么这样设计（考据：commit <hash> 说…/测试 <名> 印证…）；
  动机写具体场景三元组（什么情境 → 应如何响应 → 怎么度量），不写"为了高性能/解耦"式空话；
  不这样设计的代价（考据得到才写）。
**不变量**：这个类始终维持的规则（如：状态机合法转移集、线程约定）。
```

深卡片只给：主链上的类、多实现接口、状态机/线程相关类、churn 高的类。**每张卡 ≥2 处 file:line**。

## 模块卡片

```md
### <模块名>

**职责**：一句话。
**对外接口**：caller 必须知道什么——入口方法/前置条件/错误模式（file:line）。
**关键协作**：依赖谁、被谁依赖（意外方向注明 ⚠）。
**设计动机**：为什么存在这个模块、为什么这样划边界（考据或 [inferred]）。
**雷区**：易误解处（看似 A 实为 B、隐藏时序/线程约定）。
```

## 附录：并行子代理探索报告格式（大项目分批用）

范围 >100 文件或 >10 模块时可按子系统派子代理并行探索，**提示词必须自包含**（子代理看不到主对话）：
项目根路径、该子系统的范围（目录清单）、报告格式、证据要求。主代理拿到报告后**禁止再重复读子系统源码**，只做合并与抽查。

每个子代理返回（NODE 报告，硬约束 5-12 个概念节点）：

```
## 节点：<概念名>
- 文件：<真实路径>（每节点 1-3 个主文件，必须真实读过）
- 职责：一句话
- 连接：触发/产出/查询 → <哪个概念>
- 关键片段：≤5 行真实代码（标注 file:line，绝不编造）
```

## 家族行（同构类族的覆盖形态，2026-09-06 新增）

桥接/插件模块常见"结构同构的类族"（如 retrofit converter 的 Factory+RequestBody+ResponseBody+Streaming 四件套 ×12 个生态）。逐类一行会产生 48 行几乎相同的表格——允许**家族行**压缩：

| 家族/类 | 一行职责 | 关键协作 |
|---|---|---|
| 各模块 XxxConverterFactory | Factory 实现：通吃型不返回 null / 专精型精确匹配 | Converter.Factory |
| 各模块 XxxRequestBodyConverter | 对象→RequestBody | 序列化库 API |

规则（缺一即退回逐类一行）：
1. **真正同构**才可用：成员间只差绑定的第三方库名与个别变体方法；族内有行为差异的例外类必须单列一行；
2. 行内**列全成员名**（或族名+成员数），职责列写出族内共性 + 分型差异；
3. 文档尾给覆盖算式（如"25 家族行覆盖 84 类"），覆盖率按类数计，不按行数计；
4. 核心模块、状态机/线程相关类、多实现接口**不适用**家族行——它们正是需要逐类深挖的对象。
