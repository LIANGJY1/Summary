# 语言问答提炼规则

在 `language-note` profile 下完整阅读本文件。它只规定从会话到语言问题的提炼判断；标题、列表、代码和排版细节以知识库 `language/README.md` 为唯一事实源。

## 优先级

发生取舍时依次保证：

```text
正确性 > 用户意图 > 问题边界 > 因果清晰 > 知识完整 > 排版风格
```

“知识完整”只要求当前问题得到完整解释，不要求顺带覆盖整个语法家族。

## 一问一约

每个最终 Q 都要能指回至少一个用户问题。先用一句话写出该 Q 的唯一承诺，再判断材料是否属于它：

- 直接回答承诺的内容进入主线。
- 缺少它就无法理解或正确使用结论的内容作为必要支撑。
- 只增加广度、不改变当前判断的内容移除。
- 用户随后明确追问的旁支重新建立自己的问题约定。

标题与正文必须**等宽**：标题承诺一个局部问题，正文就停在该问题得到回答的位置。正文出现第二套选型标准、另一组 API 总览或新的工程建议时，先检查用户是否提出过相应问题；没有就删除。

## 来源门

按以下顺序处理素材：

1. 用户原话决定主题集合与必要语境。
2. 用户补充和纠正覆盖助手此前理解。
3. 助手回答只提供待核验的候选结论与检索词。
4. 本地代码决定项目事实；官方规范和文档决定语言、标准库与平台事实。

助手主动给出的“顺带说”“最佳实践”“更地道写法”“一般来说”不自动获得主题资格。方法名、全大写变量名、调用链和常见架构只能支持语法观察，不能证明生命周期、单例、线程或业务契约。

## 合并与拆分

- 同一代码片段上的连续“是什么、为什么、什么时候用”通常合并为一条连续解释。
- 独立搜索入口、不同错误现象或不同选择条件应拆分。
- 用户单独重复追问某个术语，说明该术语值得拥有独立、短小的 Q。
- 同一机制已在其他 Q 解释时，用一句关系说明和精确引用衔接。

合并不是把所有回答拼接在一起。合并后仍按“结论 → 直接机制 → 改变结论的边界 → 使用判断”重排，并删除重复句。

## 停止扩写测试

逐段检查：

1. 这段回答标题中的哪个词或条件？
2. 删除后，读者是否仍能正确理解和使用结论？
3. 这段是否引入了用户没有提出的新选择？

无法回答第 1 项，或第 2 项为“是”，就删除。第 3 项为“是”且用户没有追问时，也删除。短答案可以只有首段；不能用固定模板补齐不存在的“原理、边界、最佳实践、关联问题”。

## 事实与示例

- 先核验事实，再润色表达。
- 限定词与结论同时出现，不能先写绝对结论、后文再推翻。
- 代码应声明理解行为所需的变量、类型和外层函数；多个替代方案不能写成会连续执行并提前崩溃的单段程序。
- 示例只证明当前结论。需要借用另一个语法点时，优先改为更小示例或引用已有 Q。
- 无法运行的片段明确标注“省略项目声明”；不能用完整代码块的外观掩盖缺失上下文。

## 写入前边界审计

为每个 Q 给出内部答案，全部为“是”才能写入：

- 能指出对应的用户问题吗？
- 标题包含理解问题所需的场景吗？
- 首段已经直接回答吗？
- 每一段都服务同一个问题承诺吗？
- 所有技术断言都有依据并带必要限定吗？
- 示例独立可读，且没有顺带教学其他主题吗？
- 与相邻 Q 没有重复解释吗？

最后反向检查用户问题清单：每个问题必须指向一个最终 Q、另一个已有 Q，或明确的非知识去向；不得静默遗漏。
