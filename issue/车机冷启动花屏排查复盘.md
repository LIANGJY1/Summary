# 车机冷启动花屏排查复盘

> 本文记录一次 Android/AAOS 启动阶段紫蓝色纹理异常的证据、当前边界与下一轮取证计划。现有证据支持“冷启动相关、概率性发生”，尚未锁定根因，也没有据此提出代码修复。

## 现象和触发条件

1. **可见表现：**2026-10-21 拍摄的视频在约 29 秒处显示中间渲染区域为紫蓝色、毛发状纹理，顶部状态图标及底部 Launcher 控件仍可辨认。视频是外部摄像机拍到的屏幕，不是设备内部截图，因此还不能仅凭它判断异常像素首先出现在哪一层。
2. **用户复现描述：**完全下电冷启动时有概率出现；只重启 Launcher 时未观察到。该差异提示冷启动独有的系统状态或初始化时序值得优先调查，但两种触发次数有限，不能证明故障层级。
3. **一次小样本：**用户报告 12:56 之后连续重启四次，前三次出现相同花屏，第四次正常。重启类型需逐次注明是否真正完全下电；四次记录不能推出稳定复现率，也不能把第四次正常当成修复。

## 已获得的证据

1. **Surface 生命周期相关性：**此前对这组启动日志的分析发现，三次花屏样本在 `Meter_Form` 出现短暂 `7→0` 变化后触发了 Kanzi Surface 重建；第四次正常样本只见到 `0`，没有相同重建过程。这是相关性线索，不是因果证明。还需要核对每条日志的时间基准、重建前后的首帧和实际屏幕画面。
2. **Kanzi 就绪事件可重复到达：**项目既有真机记录显示，切换萌宠形象会触发预制体二次加载，`CarModel.KanziLoadingComplete=1` 曾再次到达。因此该事件不能简单解释为“每次整机上电只发一次”。但这不证明每次 Activity 或 Surface 重建都会重新加载 Kanzi 场景，也不证明花屏由这个事件导致。项目依据见 `project/yadi/pet/entries/SRS_013.md`。
3. **两个回调来源不能混读：**Launcher 接收端分别处理 `CarModel.KanziLoadingComplete` 和 `Button.PreviewReturnBack`。两者都能调用同一个加载完成监听器，因此下游日志 `Kanzi load complete, fade out cover` 不是前一个事件的唯一证据。必须查看原始数据源名和值。
4. **贴图与异常页面已建立运行时关联：**用户通过替换一张贴图观察到花屏页面也随之改变。这比静态截图相似度更强，说明异常页面内容受这张贴图（或其参与的材质/资源链路）影响，支持“花屏实际呈现了法线贴图像素/由该贴图驱动输出”的判断。仍需区分是贴图被错误绑定到颜色/自发光输出、材质/shader 语义或变体异常，还是某种调试/资源预览路径；该对照本身尚不能判定是哪一种机制。`aipet_dog.kzb` 包含 `M_dog_body_Normal`、`T_dog_normal` 相关图像和 `NewFur_Normal` 材质，且该 KZB 与设备安装资源的 SHA-256 曾核对一致。
5. **参考图未确认来自同一张贴图：**对 `NsrLauncher` 中可识别的 PNG 资源做过扫描；没有找到与用户后续提供的完整法线贴图截图完全相同的可解码 PNG。候选贴图的紫蓝毛发细节相似，但 UV 岛和面部排布不同，也没有得到可靠的特征点几何对应。PNG/JPEG 文件头扫描无法覆盖所有专有压缩纹理，故“未找到”不等于已排除所有打包资源。
6. **当前连接报告的图形属性：**一次 ADB 连接读取到 `ro.hardware.egl=mesa`、`ro.hardware.gralloc=minigbm`、`ro.hardware.hwcomposer=ranchu`。这些是当时连接目标报告的属性，需先确认该目标与实际量产显示路径的关系，不能拿这组属性直接排除或确认实体设备图形硬件问题。配置变化时出现过 AFBC 相关 minigbm 日志，但当时未观察到花屏，不能据此归因。

## ADB 自动采集样本

1. **采集范围：**2026-10-22 的采集目录保留了 13 段 ADB 连接窗口，主机时间从 13:57 到 19:02；其中 9 段的设备 uptime 接近 0，说明采集覆盖到多次启动阶段。连接窗口不一定都等于一次完整冷启动，仍需结合断电方式和 boot ID 分类。
2. **截图观察：**可读取的启动截图显示车机 Launcher、摩托车模型和宠物画面，没有发现视频中那种铺满主渲染区域的紫蓝毛发纹理。部分截图是全黑、未完成或在 ADB 断开时截断；17:45 的宠物局部出现蓝紫色外观，但没有覆盖主渲染画面，不能与目标花屏等同。
3. **采样盲区：**截图约每 2 秒一次，而且采集从 ADB 恢复连接后开始。因此未捕获到目标花屏只能说明这些采样帧未显示该现象，不能排除 ADB 连上之前或两帧之间出现过短暂花屏。
4. **时间基准：**有些设备启动记录的 `date` 与主机目录时间不一致，设备墙上时钟出现过回退到较早日期的情况。后续不能只用 `logcat -v threadtime` 的墙上时间对齐录像，应同时保存主机时间、设备 uptime、boot ID 和显式事件标记。

## 当前假设和可证伪预测

1. **启动时序或 Kanzi Surface 生命周期：**若成立，失败应与 Surface 创建/销毁、`setRenderStart/Stop`、Kanzi 场景就绪和首帧的相对顺序稳定相关。需要在失败与正常样本中对齐这些事件，而不是只比较是否出现某一条日志。
2. **资源上传、材质或 shader 初始化：**贴图替换会改变异常页面，已支持该资源链路参与最终画面；下一步区分“错误的颜色槽/自发光槽绑定或 shader 变体”与“冷启动期间纹理/材质状态未就绪或陈旧”。若是固定错误绑定，同一构建和资源组合应稳定复现；若是初始化竞态，失败率应随冷启动时序/渲染首帧顺序变化。需记录异常帧实际材质属性、shader/变体、纹理槽、资源句柄及首帧时序。
3. **Buffer、HWC 或设备显示路径：**若 Android 截图已经异常，优先沿生产者 buffer、SurfaceFlinger layer 和 HWC 路径回溯；若同一时刻系统捕获正常而外部录像异常，则调查捕获路径之后的 HWC、显示控制器、接口和面板。两类采集必须对应同一时间窗和同一显示器。
4. **静态资源本身损坏：**如果相同资源每次都被相同场景使用，但只有部分冷启动出现异常，单纯的静态文件损坏解释力较弱；仍需确认资源是否被异步加载、解码或上传，以及失败时内容是否改变。不能仅凭“偶发”排除资源路径问题。

以上是假设及预测，不是根因结论。一次只改变一个条件，并观察失败率和对应证据是否按预测变化。

## 尚缺的关键证据

1. 尚未取得设备内部截图或 buffer 证据与外部摄像机花屏帧严格对齐的失败样本。
2. 尚未在同一软件版本、同一显示配置下建立足量的冷启动失败/正常对照组。
3. 虽然贴图替换试验已确认画面与该贴图链路相关，仍未在异常帧对应时刻确认实际活动的 Kanzi 页面、Prefab、材质、shader/变体、贴图槽、Surface 和 HWC 合成类型。
4. 尚未用显示控制器读回或其他设备侧证据确定错误是否发生在 Android 捕获路径之后。
5. 尚未确认当前 ADB 目标报告的 Mesa/minigbm/ranchu 图形栈是否就是目标量产设备所使用的实际图形实现。

## 下一次冷启动取证

1. **开始前：**记录软件构建、显示模式、启动方式和开始时间；保持完整 logcat 采集，不清空 log buffer。每轮标记为完全下电冷启、系统重启、Launcher 进程重启或 Activity/Surface 重建中的一种，并保存主机时间、设备 uptime 与 boot ID。设备墙上时钟可能在启动阶段变化。
2. **花屏出现时：**立即记下本地时间，并同时保存外部录像、设备内部截图、logcat 和可用的 SurfaceFlinger layer 列表/状态。若异常只持续几帧，优先连续录制或快速重复截图；单张事后截图可能已经错过故障。
3. **事件窗口：**保留异常前后至少一段连续日志，重点对齐 `Meter_Form`、Surface `created/destroyed`、Kanzi render start/stop、两种完成/返回数据源及值、首帧、BufferQueue、EGL/GLES、allocator、HWC 和显示驱动事件。过滤后的摘要可辅助定位，但要保留未过滤原始日志以便回看上下文。
4. **失败与正常成对比较：**每个样本记录 boot ID、uptime、应用进程代际、Kanzi 场景/资源是否重载、Surface 生命周期以及截图结果。将同一条件下的失败和未失败样本按时间对齐。
5. **确认画面来源：**先确认花屏属于哪个 Surface/layer；再确认该帧由哪个 Kanzi 场景和材质绘制；最后核验纹理与提交 buffer。颜色相似、资源包里存在或日志出现加载完成事件，都不足以单独确认“谁导致了花屏”。

## 可复用结论

这次排查最重要的经验是把“看起来像某张图”“包里存在该资源”“运行时引用该资源”和“该资源导致异常”当成四个不同的证据等级。遇到概率性冷启动问题，应保留失败与正常两类样本，沿像素生产到物理显示的边界逐层取证，并在证据到达哪一层时就把结论停在哪一层。
