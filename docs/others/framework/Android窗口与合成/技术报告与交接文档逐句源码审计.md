## 引言：为什么要逐句审计

这次核查直接影响改造与验收的结论有五条：

1. **`windowIsTranslucent=false` 不会自动把透明背景画成不透明。** 它影响遮挡判定；窗口实际画了什么，要单独检查背景、格式和内容。
2. **透明区域能否看到桌面，取决于桌面层是否仍参与该区域的合成。** 稳态已经隐藏桌面，不能证明转场期间也从未显示；`--list` 保留层名也不能证明该层仍可见。
3. **原报告的 StartingWindow 排除实验不成立。** 从系统来源启动时，主题校验对关闭起始窗属性有特殊处理；要直接观察起始窗口与异常帧的时间关系。
4. **设备出现的蓝灰色和 alpha 渐变尚未确定来源。** 源码给出了可检验的背景色与动画路径，但默认值和源码配置不能代替实机 trace。
5. **部分采集命令不适用于本树。** 验收应使用下文已核对的 WMS 和 SurfaceFlinger 入口，并将源码支持、设备配置和实测现象分别记录。

下文先列出十项重要发现，再按原文顺序给出逐条核查索引。完整机制及源码走读见原理篇。

## 第一部分：十个改写结论的发现

### 发现一：蓝灰蒙纱的底色不是 TaskDisplayArea 的固有颜色

**原文**（交接文档）："暴露其下系统 DefaultTaskDisplayArea 的蓝灰底色（约 RGB 76、83、88）"。

**核查**：0x4C5358 在 AAOS13 全树零命中（唯一命中是本仓自己的分析文档）；AOSP 默认暗背景是 #303030：

```xml
<color name="material_grey_850">#ff303030</color>
```

### 发现二：「Launcher 任务透明度逐步下降」不可能由默认动画产生

**原文**（交接文档）："捕获到 Setting 上升时 Launcher 任务透明度逐步下降"。

**核查**：本树默认走 legacy AppTransition（见发现六），退场动画的 AOSP 默认值 alpha 恒为 1：

```xml
<!-- frameworks/base/core/res/res/anim/activity_open_exit.xml（去版权头） -->
<alpha android:fromAlpha="1.0" android:toAlpha="1.0" android:duration="450" ... />
<translate android:fromXDelta="0" android:toXDelta="-10%" android:duration="450" ... />
```

而 yadea 当前构建的动画配置矩阵（全部仓内实证）是：

| 位置 | 配置 | 证据（yadea 仓） |
|---|---|---|
| Setting AppTheme1 | 清 7 项 enter 侧动画（windowEnter/windowShow/activityOpenEnter/launchTaskBehindTarget/taskToFrontEnter/wallpaperIntraOpenEnter/wallpaperOpenEnter 全 @null），**exit 未清** | Setting styles.xml:30-36 |
| Setting AppTheme1 windowAnimationStyle | 未设置 → AppCompat 非对话框主题也不设（themes_base.xml 仅 :546/:560/:587 对话框变体设置）→ 落回平台 Animation.Activity（themes.xml:185）→ exit=默认 activity_open_exit | Setting styles.xml:12-42 |
| Setting MainTheme | windowAnimationStyle=@null（全部无动画） | Setting styles.xml:54 |
| Launcher AppTheme1/AppListTheme | EmptyAnimation：open/close 四向全 @null | Launcher styles.xml:20/35/44-52 |
| Launcher 图标启动 | makeCustomAnimation(0,0) 零动画 | Launcher AppInfoUtils.java:287 |

**裁定与影响**：⬜（观测为实机事实）＋❌（默认机制无法产生该观测）。值得优先核查的来源包括：**remote animation runner**（Launcher/ROM 定制注册，`AppTransitionController.java:832-851` "Remote animations always win"）、**Shell Transitions**（`persist.wm.debug.shell_transit=true` 时 WMShell 的 DefaultTransitionHandler 播动画）、或**录像摄于旧包/旧 ROM**。上述配置可以作为推导起点；实际选中的动画、窗口覆盖关系及画面仍需通过设备 trace 确认。这些是排查假设，并非穷尽所有可能。可先检查：`getprop persist.wm.debug.shell_transit` + 复现路径上 `dumpsys window animator`。

### 发现三：StartingWindow 的排除实验不能证明其缺席

**原文**（报告第八章）："已排除：……StartingWindow（补 windowDisablePreview 后现象不变）"。

**核查**：本树对从系统界面发起的启动单独处理 `windowDisableStarting`：

```java
// frameworks/base/services/core/java/com/android/server/wm/ActivityRecord.java:2339-2343
private boolean launchedFromSystemSurface() {
    return mLaunchSourceType == LAUNCH_SOURCE_TYPE_SYSTEM
            || mLaunchSourceType == LAUNCH_SOURCE_TYPE_HOME
            || mLaunchSourceType == LAUNCH_SOURCE_TYPE_SYSTEMUI;
}
// :2395-2404（validateStartingWindowTheme 节选）
        // If this activity is launched from system surface, ignore windowDisableStarting
if (windowIsTranslucent || windowIsFloating) {
    return false;
}
...
if (windowDisableStarting && !launchedFromSystemSurface()) {
```

**这段代码能证明什么？** 当启动来源被记录为 SYSTEM、HOME 或 SYSTEMUI 时，最后的 `windowDisableStarting && !launchedFromSystemSurface()` 条件不会因该属性而拒绝起始窗主题。半透明或浮动主题则在前面的独立条件中被拒绝。两类判断不能合并为“系统面启动一定有 StartingWindow”。

**为什么原排除法不成立？** 如果目标复现路径确实被识别为上述系统来源，仅修改 `windowDisablePreview` 后现象不变，并没有证明起始窗口在实验前后消失；还要核实来源类型及其他起始窗条件。因此，该实验不足以排除 StartingWindow，也不足以证明它就是黑闪或蒙纱的来源。

**如何重做？** 保持原启动路径，采集窗口和图层 trace，确认 `TYPE_APPLICATION_STARTING` 是否出现、使用何种内容、何时移除，并与异常帧对齐。若增加非系统面启动作为对照，应同时记录启动来源和冷暖启动状态，避免把路径变化造成的差异误当作单一属性的效果。

**裁定：❌ 原排除法的证据不足；起始窗是否参与该次现象仍待实机确认。**

### 发现四：三条监控命令在本树跑不通

**原文**（报告 6.2 与第九章附录）：`dumpsys window transitions | grep mAppTransitionState`、`cmd surfaceflinger layer-tracing start`、`dumpsys window windows | grep -E "occludesParent|isOpaque"`。

**核查**：

1. 2. SurfaceFlinger 没有 shell 命令入口（grep onShellCommand/layer-tracing 零命中）；layer tracing 走 binder 事务码：

```cpp

case 1025: { // Set layer tracing
    ...
    ALOGD("LayerTracing enabled");
    tracingEnabledChanged = mLayerTracing.enable();
```

输出为 winscope 文件而非 perfetto（`frameworks/native/services/surfaceflinger/Tracing/LayerTracing.h`:71：`FILE_NAME = "/data/misc/wmtrace/layers_trace.winscope"`）。

3. `occludesParent=` 在 **dumpsys activity activities**（`ActivityRecord.java:1175`），不在 window windows；**isOpaque 没有任何文本 dump**（仅 ProtoLog，`WindowSurfaceController.java:226`）；frame 的输出格式是 `Frames: parent=... frame=...`（`WindowFrames.java:204-206`），grep "mFrame" 查不到内容。

### 发现五：Perfetto 数据源名与 atrace 类别写错

**原文**（报告 6.2）："Perfetto（linux.ftrace + atrace(wm,view,sf,app) + android.surfaceflinger.layers + frame_timeline）"。

**核查**：`android.surfaceflinger.layers` 全树零命中——那是 Android 14 的数据源。A13 的两个 SF 数据源是：

```cpp
// frameworks/native/services/surfaceflinger/FrameTracer/FrameTracer.h:72
static constexpr char kFrameTracerDataSource[] = "android.surfaceflinger.frame";
// frameworks/native/services/surfaceflinger/FrameTimeline/FrameTimeline.h:492
static constexpr char kFrameTimelineDataSource[] = "android.surfaceflinger.frametimeline";
```

层树 trace 在 A13 走 winscope 文件（发现四）。atrace 类别表（`frameworks/native/cmds/atrace/atrace.cpp`:102-128）有 gfx/view/wm/am 等，**无 "sf"**（SurfaceFlinger 自己就用 gfx 标签：`SurfaceFlinger.cpp:23 #define ATRACE_TAG ATRACE_TAG_GRAPHICS`）；**"app" 不是 atrace 类别**（ATRACE_TAG_APP 存在于 `system/core/libcutils/include/cutils/trace.h`:63，供应用内 Trace.beginSection，命令行侧用 `-a 包名` 启用）。

**裁定与影响**：❌（名称）。修正后的采集配方：`atrace gfx view wm am sched freq -a com.yadea.launcher,com.yadea.setting` + perfetto 数据源 android.surfaceflinger.frame / .frametimeline + `cmd window tracing`（窗口树）+ `service call SurfaceFlinger 1025`（层树）双 winscope。

### 发现六：转场走哪套状态机——本树默认 legacy，报告描述恰好是生效路径

**背景**：A13 两套转场体系并存。server 端权威判定是"有没有注册 TransitionPlayer"：

```java
    return mTransitionPlayer != null;

// frameworks/base/services/core/java/com/android/server/wm/AppTransition.java:1601-1603
if (mDisplayContent.mTransitionController.isShellTransitionsEnabled()) {
    return false;                    // Shell 接管时 legacy 直接让位
```

而 player 的注册受编译期常量门控：

```java
// frameworks/base/libs/WindowManager/Shell/src/com/android/wm/shell/transition/Transitions.java:91-92

        SystemProperties.getBoolean("persist.wm.debug.shell_transit", false);
// :201-205 为 true 才 registerTransitionPlayer(mPlayerImpl)
```

**裁定：🔶 本树默认配置支持 legacy 路径。** 设备属性、player 注册和厂商修改仍可能改变实际路径。验收时应记录 `getprop persist.wm.debug.shell_transit`，并结合转场 trace 核对。

### 发现七：overrideTaskTransition 是 AOSP 原生 key；"任务级忽略自定义动画"有了确切机制

**原文**（交接文档）："这是 Android 13 的内部 bundle 标志，依赖具体 ROM 实现；不要当作已验证成功"；"首次普通 ActivityOptions 自定义动画刷机后实测无效"。

**核查**：key 在 A13 AOSP 原生存在，且"普通自定义动画为何无效"正是同一处代码：


### 发现八：验收 C2 的判据命令有采样时机问题

**原文**（报告 6.1）："C2 合成：dumpsys SurfaceFlinger --list，Setting 前台时列表无 com.yadea.launcher 层"。

**核查**：--list 列的是**整棵层树，含 hidden 层**：

```cpp
// frameworks/native/services/surfaceflinger/SurfaceFlinger.cpp:5188-5191
void SurfaceFlinger::listLayersLocked(std::string& result) const {
    mCurrentState.traverseInZOrder(
            [&](Layer* layer) { StringAppendF(&result, "%s\n", layer->getDebugName()); });
}
```

`transaction.hide` 后层对象仍可能留在层树中，但不再作为可见层参与相应合成（见原理篇 §5.6）。因此，在 Surface 销毁前使用 `--list` 判断是否参与合成，可能误报。

**裁定：🔶 命令不能单独证明图层是否参与合成。** 应结合层的可见状态、可见区域和 trace 判断；即使 Activity 已停止，也应确认目标 Surface 的实际销毁状态。

验收时可分三步记录：先用 `--list` 定位候选层名；再查看同一时间点的 hidden、alpha 和可见区域；最后用连续 trace 判断动画期间是否有可见区域，以及消失发生在 hide 还是 Surface 销毁之后。这样可以同时回答“层对象是否存在”和“该帧是否贡献画面”，避免把两者当作同一个判据。

**核查**：窗口在首帧画完前**根本不显示**——不是"透明地摆在那"：

一种待验证的候选机制是：starting window 缺席/已撤而新窗口尚未 HAS_DRAWN 的空档期，露出 letterbox/显示背景（默认黑：`LetterboxUiController.java:734-737 return Color.valueOf(Color.BLACK);`）。`BlackFrame`（wm 目录）全树唯一使用者是旋转动画（`ScreenRotationAnimation.java:486`），与开页无关。

### 发现十：persistent 拒装归因正确，且有第二道检查；Setting 也已成 persistent

**原文**（交接文档）："SystemUI 是 persistent 系统应用，adb install -r 被设备拒绝"。

**核查**：安装路径上确有显式的 persistent 检查，普通 adb install 不带可跳过该检查的 INSTALL_STAGED 标志：

```java
// frameworks/base/services/core/java/com/android/server/pm/InstallPackageHelper.java:1335-1341
// Prevent persistent apps from being updated
if (oldPackage.isPersistent()
        && ((installFlags & PackageManager.INSTALL_STAGED) == 0)) {
    throw new PrepareFailure(PackageManager.INSTALL_FAILED_INVALID_APK,
            "Package " + oldPackage.getPackageName() + " is a persistent app. "
                    + "Persistent apps are not updateable.");
```

（INSTALL_STAGED 仅 staged 安装置位：`PackageInstallerSession.java:2738-2740`。）签名比对是并存的第二道检查（`PackageManagerServiceUtils.java:606-608` INSTALL_FAILED_UPDATE_INCOMPATIBLE "signatures do not match newer version"）。yadea SystemUI manifest:209 `android:persistent="true"` 属实。

**附带发现**：yadea 最近提交 637ecca9 给 **Setting** 也加了 `android:persistent="true"`——Setting 从此同样不可 adb install 更新，且获得"被杀约一秒自动重启"属性（重启为死亡回调内**同步** fork，无延迟无退避：`ActivityManagerService.java:13717-13760` → `ProcessList.java:1831/2571 Process.start`；对比服务重启才有 1s 退避 `ActivityManagerConstants.java:176`；"约一秒"=冷启动耗时）。**Atlas 推送流程需覆盖 Setting；kill-gap 取材法从此对 Setting 同样可用。**

### 附：其余两处轻量修正

## 第四部分：方法论小结——怎样的断言经得起源码审计

核查中反复出现的问题可归纳为四条写作纪律：

1. **区分"结果对"与"机制对"。**"声明不透明→桌面被裁出合成"结果对，机制错（WMS hide 而非 SF 裁剪）；"清零为不透明黑"结果对，字面错（清零值是透明黑，黑色来自按不透明显示）。机制错的句子在参数变化时最先崩塌——比如知道"是 WMS hide"才能推出"--list 有采样时机问题"（发现八）。
2. **命令必须落到服务端处理入口再写进文档。**三条命令失效（发现四/五）都不是编造，而是从别的版本/别的设备抄来没有对树核对。一条 grep（dump 分节列表、shell command 入口）的成本远低于验收现场卡壳。
3. **排除法要验证"变量真的被拨动了"。**发现三是最贵的一课：windowDisablePreview 在目标路径上被源码显式忽略，整个排除实验等于没做。写"已排除 X"之前，先证明干预在该路径上生效。
4. **版本口径要精确。**A13 与旧文的差异清单（translucent 不写 format、hideRobustly 已删、BlendMode::Skip 不存在、shell transitions 两套并存、perfetto 数据源更名）每一条都能让一段"正确的旧知识"变成错误的断言。引用机制时注明版本，审计时以本地树为准。
