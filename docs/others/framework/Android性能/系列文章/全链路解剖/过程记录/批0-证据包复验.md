## 二、本次复验新采到的追加证据（原证据包未含，供批06/07/08/09 引用）

- `NativePostImeInputStage id=0x3b3b7f02` rel 6,831,043,726，dur 3,885

- 判定：应用主线程收到事件后的 stage 顺序切片可见——批08 的直接 trace 证据。

### 2. 三通道分发序列（tid 1488，同一事件 ID 逐通道 prepare + enqueueDispatchEntriesLocked）
以 0x3b3b7f02 为例（其余各 ID 同模式）：
- AppList 主通道：prepare rel 6,830,576,688（5,846）→ enqueueDispatchEntriesLocked rel 6,830,592,265（5,769）
- Gesture Monitor 通道（`[Gesture Monitor] CustomGesture-touch (server)`）：prepare rel 6,830,822,342（5,615）→ enqueueDispatchEntriesLocked rel 6,830,835,226（5,616）
- PointerEventDispatcher2 通道：prepare rel 6,831,012,842（5,461）→ enqueueDispatchEntriesLocked rel 6,831,025,495（5,423）
- 同窗口更早事件（0x107fbc97，rel 6,772,756,188 deliver）呈现同一三通道模式。
- 判定：每条事件向三个 InputChannel 各 prepare/enqueue 一次——批06/07 讲 TouchedWindow/InputTarget 多目标与 Monitor 通道的直接证据；同 ID 三条 notifyMotion 的"同层三条"另有进程内重复 notify 语义（留批06 查证源码）。

### 3. InputReader（tid 1489）状态完整序列（窗口 6.78–6.82 s）
R 7,951,192 → Running 996,346 → S 3,852,692 → R 848,846 → Running 177,731 → R+ 461,962 → Running 120,884 → D 3,716,500（write_pmsg）→ R 1,602,116 → … → S 8,639,231 → …
- 判定：notifyMotion（6.795839）发生在第一个 Running 0.996 ms 窗口内；D 态出现在其后的事件处理循环中；write_pmsg 的 blocked_function 语义（不可中断等待写 /dev/pmsg）留批14 结合 sched.h 与 logd 讲解。

### 4. InputDispatcher（tid 1488）状态完整序列（窗口 6.77–6.84 s）
S 50,445,654 → R 35,308 → Running 1,009,154 → S 615,769 → R 6,164,154 → Running 194,230 → R 4,906,116 → …
- 判定：50.446 ms S 结束后的 R 0.035 ms/Running 1.009 ms 内完成 prepare（6.830577）与 enqueueDispatchEntries；其后仍有一段 6.164 ms R 与 4.906 ms R+（本窗口内无 S）——Dispatcher 并非被重复"卡住"，而是持续处理三通道队列。
