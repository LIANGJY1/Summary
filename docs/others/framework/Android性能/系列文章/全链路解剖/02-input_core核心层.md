# 02 · input core：输入状态如何组成事件包

input core 是 Linux 内核输入子系统的公共处理层，负责维护输入状态，并将事件交给下游处理器。

> 逐行分析：[内核源码详解 02](内核源码详解/02-input_core核心层.md)。沿用 kernel 5.15.41、HEAD `24d27dff64c4` 的原分析结论。

## 0. 本层解决什么问题

在 Android 本路径中，input core 将驱动上报的输入变化交给已连接的处理器 evdev。

1. 输入：virtio_input 调用 input_event 提交的 type、code、value。
2. 处理：检查设备能力、更新按键或坐标状态、积累待交付变化。
3. 输出：一批 input_value，经 evdev 转成用户态可读的 input_event。
4. 边界：它不创建 MotionEvent，不判定 Android 目标窗口，也不执行 View 手势识别。

## 1. 为什么驱动和 evdev 能接在一起

1. 设备驱动注册 input_dev，声明自己支持哪些事件、按键和坐标轴。
2. evdev 作为 input_handler 注册，按匹配规则连接设备。
3. input_handle 记录设备与处理者的连接，设备打开状态决定连接是否参与交付。
4. 因此设备注册与运行期事件分发是两个阶段。理解数据流不需要逐行阅读注册及失败清理代码。

## 2. 一组坐标怎样交付

下面以本系列的虚拟触摸设备为例，先准备设备和读取通道，再传递每组输入事件。箭头表示处理顺序；不同线程之间的箭头不表示同步调用。

**一、设备接入与准备**

```text
guest 中的 virtio_input 驱动
  → 注册输入设备，声明支持的事件、按键和坐标轴
  → input core 将输入设备与匹配的 evdev 处理器连接
  → 通过 /dev/input/eventX 提供用户态访问入口
  → Android EventHub 发现并打开节点，查询设备能力
  → InputReader 创建设备及相应的输入映射器
```

**二、事件上报与应用消费**

```text
手指触摸 → host 输入后端采集输入
  → virtio 输入设备将 type / code / value 写入 virtqueue 缓冲
  → guest 的 virtio_input 驱动取出事件并上报 input core
  → input core 检查事件类型与设备能力，更新并收集状态变化
  → 收到 SYN_REPORT，交付当前积累的事件
  → evdev 将事件写入各读取者的缓冲，通知等待者
  → EventHub 读取 input_event，整理为 RawEvent
  → InputReader 根据触点状态与设备配置转换事件
  → 输入监听器链 → InputDispatcher 选择目标窗口
  → InputChannel 将事件发送给应用
  → 应用主线程读取事件 → ViewRootImpl → View 树分发
  → 应用处理完成并返回回执
```

1. **驱动与处理器：**驱动负责把设备状态转成输入事件；input core 是连接驱动和处理器的公共层；evdev 是将事件提供给用户态的处理器。
2. **同步边界：**`SYN_REPORT` 标记一组输入状态更新结束。input core 也有容量兜底、按键重复等特殊路径，详见下一节。
3. **读取与分发：**evdev 通知数据可读后，线程还要获得 CPU 才能读取。InputReader 完成转换后，窗口选择和应用内部的 View 分发分别发生在不同阶段。
4. **其他入口与分支：**物理设备可直接由相应驱动上报，无须经过 virtio。Android 侧还可能经过 InputFilter 等处理路径；事件能否到达应用取决于过滤、目标窗口和连接状态。
5. **时间边界：**本设备的 virtio 输入记录不含 host 时间戳，guest 内部的事件时间不能还原手指接触屏幕的时刻。输入包、应用回调和显示帧也不保证一一对应。

以上省略设备卸载、错误恢复以及各组件内部的完整分支。注册与连接是准备阶段，不会在每一条事件上重复执行。

1. 多点触摸事件可能先选择 slot，再更新该触点的坐标或状态。slot 是内核记录多个触点状态的索引，不是 Android View 的编号。
2. 没有实质变化的重复值可能被省略。轴配置中的 fuzz 可影响坐标变化处理，因此“core 逐字透传所有值”不适合作为通用结论。
3. 常规 `SYN_REPORT` 使当前积累的变化交给下游，交付后开始下一批。
4. 这种积累由输入事件和同步标记驱动，不是等待下一次 VSync。输入包与显示帧没有固定一一对应关系。

源码识别入口为 input_event → input_handle_event → input_pass_values → handler 回调。evdev_events 是本路径的下游回调。

## 3. SYN_REPORT 是否都来自 host

常规流的同步标记来自 host，但 input core 在特定情形也能合成标记。

1. 待交付事件接近内部容量时，会强制交付并追加同步标记，避免继续堆积。
2. 内核按键自动重复可生成重复按键及同步标记，是否启用取决于设备能力和相关设置。
3. 改键或设备释放按键状态等路径也可能产生同步标记。
4. 原分析依据本样本设备能力、每包事件数和可见事件流排除了相关候选，不应把这个样本的排除结论解释为所有设备都不会合成。

本样本最大观测包长度为 4 条事件，原分析计算出的强制交付阈值为 78。阈值计算与适用前提保存在详细版 §4.4、§6.5、§7.4。

## 4. 这里的过滤与 Android InputFilter 有什么区别

1. 内核 input handler 的过滤与分发发生在 EventHub 读取之前，用于决定哪些输入值交给哪些内核处理者。
2. Android InputFilter 属于 Android 输入分发路径，发生在本篇之后，涉及 system_server 过滤和事件回注。
3. 两者名称相近，但不共享一条处理链。15 篇中的 34.738 ms 空档由 Android InputFilter 路径查证，不是内核 handler 的过滤耗时。
4. 触摸输入与按键重复也要区分：Android 13 中 Dispatcher 的按键重复合成，不等同本层的内核自动重复。

## 5. 哪些时刻可以比较

1. input core 把数据交给 evdev 是 guest 内核内部的处理阶段。本 trace 没有该函数入口的直接时刻，不能仅靠源码得出其精确执行耗时。
2. 约 `00:00:06.787410` 是输入事件时间与样本单点对齐的锚点，来源是 evdev 交付时的事件时间，不是 getevent 打印时刻。
3. InputReader 随后进入 R 状态，再获得 CPU 并读取、处理事件。这段调度等待与本层的同步事件处理不同，见 03、04、14 篇。
4. 源码中没有周期节流或睡眠机制，不等于运行耗时为零，也不能替代中断调度与 host 侧时间戳测量。

## 6. 本样本结论和边界

1. 已证的机制：本触摸事件路径没有通过定时器按显示周期释放事件；不同同步包正常交付后不会跨包继续积累。
2. 已证的机制：值级处理、容量兜底和按键重复有各自条件。原分析结合本流数据判断这些条件，不能把它简写为“input core 永不修改事件”。
3. 已证的顺序：notifyMotion 晚于本层对该事件的交付。notifyMotion→prepare 的 34.738 ms 区间不能归为本层仍持有该事件。
4. 未证：host 是否重发相同 ABS 值，以及部分单坐标包由 host 少发还是由 core 去重。
5. 盲区：host 配置动机、运行内核与源码配置的一致性，以及未采集的单次中断执行时长。

证据入口：`drivers/input/input.c:367-419`（事件处置）、`:128-164`（批量分发）、`:2040-2063`（时间接口）。本样本全部统计、能力位与原断言证明见详细版 §6、§7、§9～§13，过程记录为 `过程记录/批02-过程记录.md`。
