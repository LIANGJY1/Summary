# 15 · 诊断实战：全时序归因

本篇把同一事件 ID 的输入、分发、应用消费和帧活动放到统一时间轴，分别解释 43.597 ms、34.738 ms 和 50.928 ms。

> 数值纪律：本篇不执行任何新 trace 查询（新查询数＝0）；全部数值逐字取自契约第三节证据包、批0 三份复验记录与 01~14 各篇正文。凡由既有端点做减法/加法得到的数值，一律标"算术"并在过程记录 §三列账；端点减法允许 ±1 ns 取整差并逐处注明。
> 断言编号：本篇断言编号 N1 起列于 §10；前序篇断言引用格式为"批XX 断言 Xy"（批02/03 同用 B 序、批05/08 同用 C 序、批06/07 同用 E 序，故篇号前缀不可省略，编号体系对照见附录 B）。术语沿用 00 篇 §4 编号（如 #8 notifyMotion、#14 doFrame、#29 mInboundQueue、#30 waitQueue）。

## 0. 三态结论摘要

1. 已证：事件 `0x3b3b7f02` 从 eventTime 取时（`6,787,409,804`）到应用 deliverInputEvent 打点（`6,831,006,342`）的三段构成 8,428,845＋34,738,039＋429,654＝43,596,538 ns（§2 账 1），三段分别落在 guest 内核＋InputReader 段、InputFilter 消费-回注段、Dispatcher 发布段；三段账目与契约 :72 的 43.597 ms 闭合（§3.3）。
2. 已证：34.738 ms 空档的机制是 InputFilter 消费-回注路径（批06 断言 E13、候选 C1 五判据），不是 mInboundQueue 排队（iq 恒 0）、不是 waitQueue 占用、不是 monitor 堆积、不是 policy/转交调用本身（批06 E24）；九段里程碑分解逐 ns 闭合（§3.2.2）。
3. 已证：50.928 ms Launcher S 的解除由输入交付驱动——waker＝InputDispatcher tid 1488 直证（批0 复验二 §一）；S 窗口内 CPU4 有 idle 3,617,928 ns（批14-q13）、RenderThread 零 slice（批10 H16）、S 止点与下一个 onVsync 相距 11,271,615 ns（算术，批09 §13）——"等 CPU""等 RT""等 vsync"三候选均被排除；S 的具体等待条件保持盲区（00 篇 §3.7）。
4. 已证：S 本身不是异常状态——上一帧 doFrame 155803 止于 `6,777,630,419`（算术），其后主线程只剩两条收尾 slice，无排帧请求在身（`scheduleVsyncLocked` 首次出现于 S 止后的 `6,831,246,265`），无待处理输入（iq 恒 0 至 `6,830,307,188`）；主线程入睡是该状态下的正常行为（§3.1.4）。异常量落在"事件从 guest 取时到应用交付的 43.597 ms"与"filter 路径主体 33.8 ms"上（§3）。
5. 已证（算术）：S 窗口 50,928,000 ns 的四段账＝7,572,962（尚未到 guest 取时点）＋8,428,845（eventTime→notifyMotion 首条）＋34,468,539（notify→入队）＋457,654（入队→Launcher 醒）（§3.1.3）；末段 457,654 再拆为 23,615＋35,308＋109,307＋101,270＋188,154，188,154 恰为批07 五段的 P1＋P2＋P3（§3.1.3）。
6. 已证：各观测点计数互相不等价——event0 1195 报点、`RV Scroll` 855、doFrame 508、DrawFrames 508、queueBuffer（内层）1014、acquireBuffer 507、vg-kit 七窗均值 32.1 帧/s；全跨度 doFrame 均值 508/14.878662 s≈34.1 帧/s（内核详解13 V31）；"垂直帧率＝MOVE 处理率"维持禁复活（§4）。
7. 已证：本样本各环节无丢帧的直接证据齐备（getevent 无 SYN_DROPPED、Reader 一 packet 一 notifyMotion、iq/oq/wq 计数轨全程、DrawFrames 508:508:508、BLAST 提交全可见、SF 无新 buffer 不合成），但呈现末端（drm/virtio 事件未采、present fence 信号时刻）为盲区（§4.4）。
8. 已证：doFrame 155803→155812 的 token 差 9 不是帧序号差——vsyncId 是 SF 时间线档位编号（批09 G1）；65.630 ms 的四段分账 1,185,500＋2,206,423＋50,928,000＋11,310,076＝65,629,999 逐 ns 闭合（批09 G26），应用侧在该空档内没有排帧（§4.5）。
9. 未证：filter 路径主体 33.8 ms 内的竞争归因——主线程 R 双窗（9,313,231＋17,289,307）的窗口构成已测（内核详解14 §5.5），单线程致因与 34.738 ms 的因果未证（§3.2.3）。
10. 盲区：S 的具体等待条件（无 syscall/irq 事件）、host 侧全部行为（写 used ring 节奏、渲染节拍）、drm/virtio 命令序列与 present fence、LatencyAggregator 输出（§5）。
11. 全局前提：设备 build 与基准源码树逐文件一致性未验证（00 篇 §3.6）——本篇全部源码机制结论适用于 Android 13 基准源码树代码，套用到设备行为时以本样本 trace 实测为交叉证据。

### 2.1.1 本段机制四问

- 机制① SYN_REPORT 与 packet 边界。规则：SYN_REPORT 由 host 后端产生，guest 驱动透传；evdev 以它为包边界（`evdev.c:242-243`）。谁设置：host。谁执行：驱动透传＋evdev 读取侧。后果：一 packet 一 notifyMotion，间隔不均匀性不被抹平（批05 C24/C38）。
- 机制② eventTime 时源。规则：每次 FLUSH 到达 evdev 层取一次 `ktime_get()`（CLOCK_MONOTONIC）。谁设置：input core FLUSH 路径（`input.c:2055-2063`）。谁执行：`evdev_events`（`evdev.c:300`）。后果：eventTime 成为本篇 43.597 ms 的计时起点，且此后八站复制无改写（批05 C30）；MONO−BOOT 差在单点吻合精度内不可分辨（内核详解03 B22）。
- 机制③ 零塑造。规则：驱动无节流判据、input core 无队列无定时无睡眠、evdev 不改写内容与时戳。谁设置：不适用（判据代码不存在）。谁执行：三段各自同步推进。后果：1194 个间隔的分布形状成因只能在 host 侧（未证/盲区，内核详解01 A16-A17）。

走读：host→evdev 段的已证结论是"guest 内核（驱动＋input core＋evdev）对报点间隔零塑造"（内核详解03 B25，内核详解01 A10＋内核详解02 B30 联合）。间隔分布形状的成因在 host 侧（未证/盲区，内核详解01 A16-A17）。eventTime 是本表第一个可测时刻——43.597 ms 的计时起点（内核详解03 §10.3）。37.237 ms 的重点间隔（`00:00:06.750173→00:00:06.787410`）与随后 2.842/9.958/16.588/16.390 ms 四个节点间隔在本段同样零加工（契约 :76；内核详解01 §9.3）。

## 3. 三段时延逐段归因

### 3.1 第一段：50.928 ms Launcher S（战役问题 A）

#### 3.1.1 语义框架

S＝TASK_INTERRUPTIBLE，出队等待事件，不在任何就绪队列（内核详解14 §3）。S 时长＝事件产生延迟＋调度延迟（本例醒来侧调度延迟实测 R 33,923 ns，内核详解14 §8 表）。由此，"50.928 ms 为什么这么长"的归因对象不是线程状态本身，而是"等待的事件为什么 50.928 ms 才到"。以下逐候选过筛。

#### 3.1.2.1 A-1 判据展开

CPU4 在 S 窗口 [6,779,836,842, 6,830,764,842] 的 swapper/idle 共 26 段合计 3,617,928 ns（批14-q13）——主线程等待期间其所在核并非持续被占。同窗 CPU4 上运行的其他线程（HeapTaskDaemon 13,228,767、binder:756_2 7,986,539 ns 等）是构成性观测：它们运行时主线程是 S 不是 R，两者不竞争 CPU 时间片（内核详解14 §10.11 已证边界）。"把 S 线程挪到别的核会不会更快"不构成可判命题：S 线程不在任何就绪队列（内核详解14 §7.2），迁移判据根本不被触发；且本 trace 无负载均衡事件（内核详解14 §7.1），是否发生过均衡尝试未证。

#### 3.1.4 "S 是否异常"的判定框架

判定：S 本身不是异常状态。判据链（全部已证）：

1. S 起点之前的工作已清空：上一帧 doFrame 155803 止于 6,777,630,419【算术】，其后窗口（批09 段 B）只有两条收尾 slice——`RV Prefetch`（6,777,711,688/61,807）与 `reportTimeline`（6,779,772,265/31,423）；reportTimeline 止→S 起仅 33,154 ns【算术】。帧调度侧无排队工作（批09 G30：段 B 无 doFrame）。
2. 入睡时无帧请求在身：508 帧的 scheduleVsyncLocked:onVsync:doFrame 计数 508:508:508、无空帧（批09 §12/G9 拉式模型）——每帧都由回调内再请求；本窗的首次 scheduleVsyncLocked 在 S 止后的 6,831,246,265。即入睡时刻 mFrameScheduled 为假。
3. 入睡时无待处理输入：上一事件 0x107fbc97 的 deliver 在 6,772,756,188（批0 复验 §二.2），早于本事件的 guest 取时点；本事件直到 6,830,307,188 才入队（iq 恒 0，批06 E12）。
4. 睡眠的解除由输入交付触发：waker＝InputDispatcher tid 1488 直证（批0 复验二 §一），与 `:3311` 的 `mChannel->sendMessage`（批07 §11）对应。

结论：在该状态（无帧请求、无待输入）下主线程入睡是正常行为；异常量不在"睡了 50.928 ms"，而在"等的事件为何 43,355,038 ns 才送达"（账 7）——其中 34,468,539 ns 归问题 B（§3.2），7,572,962 ns 的无事件前段与 8,428,845 ns 的产生段的归属见 §3.3 与 §6。

#### 3.1.5 剩余未证与盲区（S 段）

- 盲区：S 的具体等待条件（哪个 fd/wait queue/超时）——无 syscall/irq 事件，唯一升级途径见补采方案 R3（§6）。

#### 3.2.3a 判读框架：filter 主窗的两种可分情形

按现有已证事实，33,818,269 ns 主窗（S2/S3/S4）的最终裁决只会落在两种情形之一，判读方法都已在 §6 备好：

1. 情形一（消息排队主导）：R1 的 post→onInputEvent 间隔占主体——即消息在主线程 Looper 队列中排队，竞争（R 双窗）只是排队的伴生观测。判据形态：R1 切分后"排队段"与 R 双窗时长解耦。
2. 情形二（竞争主导）：R1 切分后 onInputEvent 处理段很短、post 到处理起点的时间与 R 双窗（26,602,538 ns）同步伸缩——即主线程被唤醒后长期未获 CPU。判据形态：R3 修复后的 sched_waking/wakeup 给出两个 R 起点各自的唤醒与 pick 事件，与裁剪表对齐。
3. 两种情形共同的前提修正：S3 段（7,249,846 ns）的消息语义先由 R2 判定——若该段已处理本事件消息，主窗的构成还要再减一段。
4. 边界维持：在 R1/R2/R3 结果落地前，任何单线程命名（"谁拖慢了主线程"）都不构成已证结论——本篇对窗口 1/窗口 2 的 12/20 线程表只作构成性引用。

### 4.5 "丢三帧"表述的纠正

- token 非连续序号【已证】：doFrame slice 名尾部标识是 vsyncId——SF 时间线档位编号（`TokenManager::generateTokenForPredictions`，批09 G1、批12 §2.5）。本样本六帧编号差 8/8/9/8/7（批09 G1），档位差≠帧数差。
- 65.630 ms 的正确读法【已证】：四段分账（账 5）显示空档内应用侧没有排帧（段 C/D 的 S 均非排帧等待，批09 §10.2）；SF 侧在两帧之间推进了 9 个档位（批09 §10.2）——档位推进不产生应用帧，这是"有分配无执行"的档位计数现象，不是"丢帧"。
- 已执行帧序列完整【已证】：155787→155795→155803→155812→155820→155827 相邻出现，各自含 traversal/draw 全链（批09 G12），无中断帧。
- 判定：以 60 Hz 周期直觉从 65.630 ms 推出的"丢了 N 帧"不成立——该窗口内根本没有 N 个"应排而未排"的应用帧（无请求即无帧，批09 G9 拉式模型）；表述应改为"两帧之间存在 65.630 ms 的排帧空档，其构成为账 5 四段"。

| doFrame 数 ↔ vg-kit 计数 | 非法 | host 域命令侧 vs guest 用户态调度侧；无时戳对齐（内核详解13 §9.7/V30） |
| 任意计数 ↔ 物理面板新帧率 | 盲区 | 呈现末端不可观测（B6/B8）；唯一升级途径 R7 |
| 旧样本 ms ↔ 新样本 ms | 非法（绝对时刻） | 两样本 rel 原点不同（BOOTTIME vs 相对口径换算基点不同）；仅段长可比（批0 复验二 §三做法） |

本章结论句：可用口径只有三层——①各观测点内部的分布统计（event0 分位数、doFrame 间隔分账）；②同观测点跨样本的段长对照（§3.2.3 的四行对照表）；③跨观测点的机制衔接（T1~T11 的链式配对，如 508:508:508）。"上下 40 多 fps"在这三层下的最接近表述是：稳态 doFrame 间隔 17.3~26.9 ms（37~58 帧/s），均值被 65.630 ms 空档与 host 报点 >25 ms 间隔拉低。

## 8. 两个战役问题的最终归位

### 8.1 问题 A：50.928 ms Launcher Sleeping

- 已证：S 的语义与排除项（§3.1.2 九候选表：A-1~A-8 已证排除/归位）；S 的解除由输入交付驱动（waker 直证）；S 本身非异常（§3.1.4 四判据）；S 窗口四段账 50,928,000 闭合（§3.1.3）。
- 已证（归位）：S 窗口的主体 43,355,038 ns＝事件产生与交付的全链时延，其中 34,468,539 ns 是问题 B 的 filter 路径——问题 A 的异常量与问题 B 共享同一机制段。
- 未证：W1/W2 段的内部构成（§3.1.5）；R 双窗竞争对 W3 的贡献占比（§3.2.3）。
- 盲区：S 的具体等待条件（B1）。

### 8.2 问题 B：notifyMotion→prepare 34.738 ms

- 已证：机制＝InputFilter 消费-回注路径（批06 E13 五判据＋九候选排除表）；九段闭合；旧样本同构（E23）。
- 已证（构成）：主线程 R 双窗的 CPU2 竞争构成（12/20 线程裁剪表，内核详解14 §5.5）。
- 未证：竞争归因与因果（U1）；filter 内部语义（U3）；S3 段语义（B10）；条间间隔归因（U4）。
- 升级路径：R1（filter 带 id 埋点）＋R3（sched_waking/wakeup 修复）为最小集合（§6）。

### 8.3 一句话总结

两个问题的可测量异常共享一个已证机制段（filter 消费-回注，33.8 ms 级）＋一个未证归因层（该段内 CPU2 混合竞争的贡献）＋一个全局盲区（无 syscall/irq 的等待条件）。其余环节——guest 内核输入路径、Dispatcher 发布段（0.43 ms 无等待）、应用消费链（0.24 ms 醒后回调＋1.73 ms deliver）、帧调度（508:508:508）、HWUI/BLAST 提交、SF 合成提交——均已证在本事件上无秒级或十毫秒级等待点。
