## 3. 累加器状态机：MultiTouchMotionAccumulator::process

MultiTouchMotionAccumulator 是多点触摸状态累加器。它接收驱动上报的原始事件，按槽位保存触点的追踪 ID、坐标等状态，为同步边界到来时生成触点快照做准备。它不会直接决定事件发给哪个窗口。

### 3.1 协议判定：协议 B 与协议 A

**协议 B**（slot-based Multitouch Protocol B）在本篇定义为：驱动以 ABS_MT_SLOT 选槽、以 ABS_MT_TRACKING_ID 的赋值/负值维护触点生命周期的多点上报协议；**协议 A** 定义为：驱动以 SYN_MT_REPORT 分隔帧内各指、身份靠事件顺序隐式表达的协议。定义锚点是判定代码 `MultiTouchInputMapper.cpp:373-387`：

```cpp
            if (!mUsingSlotsProtocol) {
                slot->mInUse = true;
            }

            switch (rawEvent->code) { ... }

    } else if (rawEvent->type == EV_SYN && rawEvent->code == SYN_MT_REPORT) {
```

走读分四点：

1. **选槽**（:85-92）：协议 B 下 ABS_MT_SLOT 事件的 value 直接成为 `mCurrentSlot`；协议 A 下首次 EV_ABS 把 `mCurrentSlot` 置 0。此后每条 EV_ABS 都写入 `mSlots[mCurrentSlot]`。
2. **槽寄存器语义**（:111-157 的 switch）：每个 MT 轴 code 直接覆盖赋值——`ABS_MT_POSITION_X` 写 `slot->mAbsMTPositionX`（:112-115）、Y 同理（:116-119）、TOUCH_MAJOR（:120-122）、PRESSURE（:147-149）、TOOL_TYPE（:153-156）等。同一槽帧内被改写多次只留最后值；X/Y 写入前还调 `warnIfNotInUse`（:114/:118，槽未置 in-use 时打警告，:175-180）。
3. **TRACKING_ID 双分支**（:137-146）：触点生命周期的开关就在这里——

```cpp

                    if (mUsingSlotsProtocol && rawEvent->value < 0) {
                        // The slot is no longer in use but it retains its previous contents,
                        // which may be reused for subsequent touches.
                        slot->mInUse = false;
                    } else {
                        slot->mInUse = true;
                        slot->mAbsMTTrackingId = rawEvent->value;
```

   负值释放槽（mInUse=false，槽内容保留）；非负值占用槽并登记追踪号。协议 A 下 `mInUse` 只在事件到达时直接置位（:107-109），没有释放动作。
4. **SYN_MT_REPORT**（:159-162）：只有协议 A 使用——每遇到一条把 `mCurrentSlot` 加一，隐式切换到下一指；协议 B 的 #2 SYN_REPORT 不进入本函数的任何分支（:159 条件是 `code == SYN_MT_REPORT`）。

**本流的实际执行面**（全部已证，联合 §1 的位图与线格式实测）：窗口内无 ABS_MT_SLOT 事件 → `mCurrentSlot` 在整个窗口保持 configure 时从驱动查到的初始值不变（:63-70），10 个槽中只有初始槽被写；ABS_MT_TRACKING_ID 仅首 packet 一条非负值（0x2c）→ 该槽 `mInUse=true` 一次置位后全程保持（无负值释放）；窗口内写入槽寄存器的实际只有 X/Y（2350 条 ABS 中除 1 条 TRACKING_ID 外全是 POSITION_X/Y）与首 packet 的 TRACKING_ID；`warnIfNotInUse` 首条 X/Y 到达时该槽已由同 packet 前面的 TRACKING_ID 置 in-use，不打警告；SYN_MT_REPORT 分支全程休眠（SYN 全为 SYN_REPORT，批02 已证）。

```cpp
    BitSet32 lastIdBits = mLastCookedState.cookedPointerData.touchingIdBits;
    int32_t metaState = getContext()->getGlobalMetaState();
```

**历史采样**（history sample）定义为：一个 MotionEvent 里除当前采样外的先前采样，存于 `mSampleEventTimes`/`mSamplePointerCoords`。`InputTransport.cpp:945-970`：

## 10. 机制四问

### 10.1 协议 B 的 SLOT/TRACKING_ID 如何唯一确定触点生命周期

- **规则**：槽寄存器＋mInUse 开关。ABS_MT_SLOT 的 value 选槽（MTIM.cpp:86-89）；ABS_MT_TRACKING_ID 非负占用槽并登记追踪号、负值释放槽（:137-146）。非在用槽不进触点集合（:266-268）。
- **谁设置**：协议判据由驱动上报的轴能力决定（configureRawPointerAxes :373-387 四判据）；追踪号数值由 host 侧驱动产生——host 代码不在基准树（盲区，内核详解01 §4.5 同口径）；mapper 只是接收者。
- **谁执行**：MultiTouchMotionAccumulator::process（写槽）→ MultiTouchInputMapper::syncTouch（读槽、id 映射）。
- **后果**：追踪号 ↔ Android pointer id 的映射跨帧稳定（:326-336），应用以 pointer id 追踪同一根手指；追踪号消失（负值）→ 槽释放 → 下一帧该 id 不在集合 → dispatchTouches 差分出 upIdBits → POINTER_UP（多指）或归并 UP（单指）。**本样本的实况**：接触只见一次 DOWN/TRACKING_ID 无 UP（契约 :76）→ 全程没有出现 TRACKING_ID 负值事件（touch.txt 无对应序列，批02/03 已核）→ 触点生命周期在本采集窗口内未闭合（已证证据侧；"手势是否真正结束在窗口外"未证）。

### 10.2 DOWN/MOVE/UP 动作由什么源事件序列合成

- **规则**：动作不是某个单一源事件的直接翻译，而是帧间位集差分＋单指归并的合成（dispatchTouches :1949-2035＋dispatchMotion :3705-3721）。
- **触发的字段变化**：`touchingIdBits`（帧间比较对象）——由 syncTouch 的 markIdBit 写入（TouchInputMapper.h:82-88），其值由槽 mInUse（TRACKING_ID 生命周期，§10.1）与悬停判定（pressure ≤ 0 或 BTN_TOUCH 类按键态，MTIM.cpp:316-319）决定。
- **序列对应**：DOWN = 上帧空集→本帧单指非空（upIdBits/downIdBits/moveIdBits 差分 :1969-1972 后走 POINTER_DOWN 循环，单指归并 :3709-3710）；MOVE = 两帧位集相等且非空（:1955-1965）；UP = 本帧空集→差分 POINTER_UP→单指归并 :3711-3716。一个 SYN_REPORT 快照只推导一次动作。
- **后果**：报点序列里"坐标变化"本身不产生 DOWN/UP——只有位集成员变化才产生；纯坐标变化恒为 MOVE。本样本后续位置变化 6.800210/6.816798（契约 :70）对应的 MOVE 事件即此路径（trace 配对见 §11.2）。

### 10.3 一个 MotionEvent 的 eventTime 取哪个 packet 的时戳

- **规则**：未合批时，MotionEvent 的 eventTime = 它自己那条 packet（那个 SYN_REPORT）的 `RawEvent.when`（§7.1 八站复制链）。
- **合批时**：批内 N 条 InputMessage 各带各自 packet 的 eventTime；MotionEvent 的当前采样取批内**最后一条**的 eventTime（consumeSamples :961 先 initializeMotionEvent 吃第 0 条、后续 addSample 追加——`getEventTime()` 返回 `mSampleEventTimes[getHistorySize()]` 即数组末位＝最后追加的样本时刻，Input.h:612），前 N−1 条进历史采样，各带原值（InputTransport.cpp:1416）。**没有一个"合并时戳"或平均值**——每条样本保自己的时戳。
- **谁设置/谁执行**：值由 evdev 层产生（内核详解03 B17），经八站复制（谁执行：EventHub/mapper/dispatcher/InputTransport 各站的赋值行）。
- **后果**：合批后应用看到的"当前 eventTime"是该批最后报点的时刻，不是消费时刻——43.597 ms 的计时起点不因合批而漂移（已证，机制链）；batch 与消费节奏的关系在批08 归因。

### 10.4 VelocityTracker 在哪个层采样、丢帧对速度估计的后果

- **层**：触屏手势的速度采样在**应用层**（RecyclerView.java:2658/:2904/:2923 → VelocityTracker.java:323 → JNI → VelocityTracker.cpp:263）；Reader 层仅触控板/鼠标化触摸（POINTER 模式）在 TouchInputMapper.cpp:2719 采样（§9.1 已证）。Dispatcher 层无采样点（grep 无命中，过程记录留输出）。
- **条件**：应用对每个**收到的** MotionEvent 调一次 addMovement；native 侧只收 DOWN/POINTER_DOWN/MOVE/HOVER_MOVE，UP/POINTER_UP/CANCEL 不入样本（VelocityTracker.cpp:266-293）；合批事件的历史采样全部逐时刻展平入样（:314-323）。
- **丢帧的后果**：速度估计的输入是"应用收到的样本序列＋各自 eventTime"。（a）报点层丢帧（SYN_DROPPED/溢出）：样本根本不产生，速度样本序列里出现大间隙——超过 40 ms 触发 `mStrategy->clear()`（VelocityTracker.cpp:224-233），松手速度按停住处理；本样本 getevent 侧未溢出（批03 已证），EventHub 侧未证（内核详解03 B24）。（b）不丢帧但应用收得慢（合批堆积）：eventTime 差值保留（§10.3），展平后策略仍看到逐时刻样本——间隔 37.237/16.588 ms 等不均匀间隙直接进入估计；窗口内样本数由 HORIZON（LSQ/Impulse 100 ms，VelocityTracker.h:191/:303）截断，大间隙使窗口内样本更少、估计方差更大（策略内部权重不展开，契约 :115）。**"丢帧使速度估计变差"的具体量级在本 trace 不可测**（应用层样本序列无 trace 记录，盲区）。

### 11.3 "每秒平均 60 帧不等于均匀 16.67 ms 不等于 60fps"在本层的表现

- **均值≠均匀**：event0 1194 间隔均值 16.617 ms、P90 31.416、P95 36.122（契约 :76）。本层对这些间隔的全部加工是：逐 packet 快照（§4.1）＋逐快照动作推导（§6.1）——间隔分布原样映射为 notifyMotion 时刻序列的间隔分布，不均匀性不被本层抹平（已证，无任何定时/合并机制；§6.4 链条内无时间参数）。
- **≠60fps**：fps 是显示侧计数（vg-kit 计数口径≠物理新帧率，契约 :77；批12/13 划界）。在本层可断言的只有：报点次数（1195 packet）≥ notifyMotion 条数（1:1，§6.4）≥ 应用收到的 MotionEvent 条数（合批可小于 notifyMotion 条数，§8.3）——三个计数两两不等价的代码依据齐（已证机制；本 trace 的实际计数只有 event0 侧 1195 已证，notifyMotion 总条数与应用侧合并次数未从 trace 提取，未证）。"垂直帧率=MOVE 处理率"的旧表述按 00 篇 §5 禁复活口径处理。
- **丢帧后果的可测边界**：>25 ms 间隔占 17.5%（契约 :76）→ 速度估计（§9.4）在这些间隙处要么样本稀疏、要么超 40 ms 阈值清状态（VelocityTracker.cpp:225 阈值判据）；具体影响量级盲区（§10.4）。

## 12. 与两个问题的关联

**50.928 ms 主线程 Sleeping（00:00:06.779837–00:00:06.830765，契约 :69）**：本层全部计算发生在 InputReader 线程（tid=1489，契约 :62），与主线程无共享锁、无跨线程等待点（mapper 函数集内无 mutex/condvar；线程模型见批04）。主线程 S 期间（至 6.830765 止）本层的可见活动：notifyMotion 首条 6.795839 落在 S 窗口内——事件在主线程睡眠期间已产出并进入下游（已证 trace 事实）；这对 S 的归因意义（S 不是"没有事件可处理"）由批14/批15 使用，本层贡献是排除"mapper 拖延"候选（已证：notifyMotion 在 S 窗口内完成）。

**34.738 ms notifyMotion→prepare（00:00:06.795839→00:00:06.830577，契约 :72）**：空档起点是本层输出动作（notifyMotion）的 trace 时刻。本层在 6.795839 之后对该 ID 无任何动作（事件已交付 QueuedInputListener→监听器链，见批04/06）→ 空档不形成于本层（已证，机制排除）；候选全表在批06（契约 :123）。注意：本空档窗口内 event0 仍有后续报点（6.800210/6.816798，契约 :70）→ 对应的后续 MOVE 的 notifyMotion 时刻属于"同 ID 后续事件"，其与首条的编排关系（Dispatcher 入队裁决）在批06。

**批04 未交稿的衔接声明**：RawEvent 进入 mapper 前的分派（InputReader::loopOnce→processEventsLocked→InputDevice::process→mapper）细节一律"见批04"；本篇依赖的交接事实只有两条：RawEvent 双时戳由 EventHub 填（EventHub.h:54-63，批03/04）与逐条顺序分派（§3.4 顺序依据）。
