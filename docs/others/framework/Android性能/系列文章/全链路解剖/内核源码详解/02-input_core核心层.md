## 2. 四个结构体、一个数组和一组常量

### 2.1 input_value：handler 批量回调的元素类型

`include/linux/input.h:33-37`：

```c
struct input_value {
	__u16 type;
	__u16 code;
	__s32 value;
};
```

走读：三个字段与 #1 input_event 的事件载荷完全同型，只是没有 time 字段。它是 input core 内部攒批数组 `dev->vals` 的元素类型，也是 handler 批量回调 `handler->events` 的第二实参数组类型（`input.h:321-322`）。定义本篇要用的两个概念：本篇说 **处置位（disposition）** 指 `input_get_disposition` 返回的位掩码（`drivers/input/input.c:261-365`）；说 **packet** 指两条 EV_SYN/SYN_REPORT（#2）之间的 input_event 序列，定义锚点是 `include/linux/input.h:63-66` 的字段注释——

```c
 * @hint_events_per_packet: average number of events generated by the
 *	device in a packet (between EV_SYN/SYN_REPORT events). Used by
 *	event handlers to estimate size of the buffer needed to hold
 *	events.
```

### 2.2 struct input_dev 的字段分组

`include/linux/input.h:138-218` 定义 input_dev 全体。与本篇机制直接相关的字段按组读：

**能力位图组**（`input.h:144-154`）：`propbit/evbit/keybit/relbit/absbit/mscbit/ledbit/sndbit/ffbit/swbit` 十个位图。evbit 决定 `input_event()` 的合法性门（第 6.1 节），keybit/absbit 决定 EV_KEY/EV_ABS 分支的逐 code 合法性（第 6.3 节）。这些位由驱动在注册前装配；本设备的装配者是 `virtinput_cfg_bits`（`drivers/virtio/virtio_input.c:138-170`，见批01 §4.5）。

**repeat 三件套**（`input.h:172-175`）：

```c
	unsigned int repeat_key;
	struct timer_list timer;

	int rep[REP_CNT];
```

`repeat_key` 存当前重复键的 code，`timer` 是内核标准定时器对象，`rep[REP_DELAY]`/`rep[REP_PERIOD]` 是两个以毫秒为单位的参数。第 9.2 节按机制四问展开。

**MT 与 ABS 状态**（`input.h:177-179`）：`struct input_mt *mt` 指向多点触摸槽位状态（`include/linux/input/mt.h:43-51`，含 `num_slots`、`slot` 与 `slots[]` 数组）；`absinfo` 是每个 ABS 轴的 `input_absinfo` 数组（value/min/max/fuzz/flat/res）。`ABS_MT_FIRST = ABS_MT_TOUCH_MAJOR`（`include/linux/input.h:13`）。

**设备状态位图**（`input.h:181-184`）：`key/led/snd/sw` 四个位图记录按键、LED、声音、开关的当前状态。EV_KEY 分支的状态去重读写 `dev->key`（第 6.3 节）。

**四个回调**（`input.h:186-189`）：`open/close/flush/event`。`event` 是"事件发往设备"方向的回调，本设备的注册点是 `vi->idev->event = virtinput_status`（`drivers/virtio/virtio_input.c:282`，见批01 §4.5.3）；触发条件是处置位含 `INPUT_PASS_TO_DEVICE`（第 6.6 节）。

**grab 与两把锁**（`input.h:191-194`）：`grab` 是 RCU 保护的 `input_handle` 指针（EVIOCGRAB 独占）；`event_lock` 自旋锁的注释（`input.h:109-113`）写明其用途——

```c
 * @event_lock: this spinlock is taken when input core receives
 *	and processes a new event for the device (in input_event()).
 *	Code that accesses and/or modifies parameters of a device
 *	(such as keymap or absmin, absmax, absfuzz, etc.) after device
 *	has been registered with input core must take this lock.
```

`mutex` 串行化 open/close/flush。事件路径只碰 event_lock（第 7.5 节）。

**攒批数组三件套**（`input.h:204-206`）：

```c
	unsigned int num_vals;
	unsigned int max_vals;
	struct input_value *vals;
```

`vals` 是本篇核心结构：packet 攒批数组。`num_vals` 是当前 packet 已存事件数，`max_vals` 是数组容量。分配点在 `input_register_device`（第 4.4 节），释放点在 `input_dev_release`（`drivers/input/input.c:1587` 的 `kfree(dev->vals);`）。

**其余**：`users`（打开计数，第 4.10 节）、`going_away`（注销标记）、`h_list`（本设备的 handle 链表）、`node`（挂 `input_dev_list`）、`timestamp[INPUT_CLK_MAX]`（三时钟时戳槽，`input.h:210`，枚举 `INPUT_CLK_REAL/MONO/BOOT` 在 `:39-44`）、`inhibited`（抑制标记，`input.h:212`）。

### 2.3 struct input_handler 与回调契约

`include/linux/input.h:316-339` 定义 input_handler。七个回调字段（`:320-327`）：`event`（单事件回调）、`events`（批量回调）、`filter`（过滤钩子）、`match`（补充匹配）、`connect/disconnect`（挂接/摘除）、`start`（挂接后启动）。字段注释给两条硬契约（`:279-284`）：

```c
 * @event: event handler. This method is being called by input core with
 *	interrupts disabled and dev->event_lock spinlock held and so
 *	it may not sleep
 * @events: event sequence handler. This method is being called by
 *	input core with interrupts disabled and dev->event_lock
 *	spinlock held and so it may not sleep
```

两个回调都在关中断、持 `dev->event_lock` 的上下文执行、不可睡眠。这条契约是第 8 节中断路径判定的核心：input core 下发事件的全部代价都计入调用者（本设备为 virtio 硬中断）的上下文。`id_table`（`:333`）是匹配表；`h_list` 是该 handler 的 handle 链表，`node` 挂 `input_handler_list`。

### 4.3 EV_SYN 强制与位图清洗（:2282-2289）


### 4.4 packet 容量估计与 vals 分配（:2291-2300）

```c

	if (dev->hint_events_per_packet < packet_size)
		dev->hint_events_per_packet = packet_size;

	dev->max_vals = dev->hint_events_per_packet + 2;
	dev->vals = kcalloc(dev->max_vals, sizeof(*dev->vals), GFP_KERNEL);
	if (!dev->vals) {
		error = -ENOMEM;
		goto err_devres_free;

```

`input_estimate_events_per_packet`（`:2128-2159`）按能力位图估一个 packet 的事件数：`dev->mt` 存在时 `mt_slots = dev->mt->num_slots`（:2134-2135）；`events = mt_slots + 1`（:2146，注释 "count SYN_MT_REPORT and SYN_REPORT"）；EV_ABS 置位时对 absbit 每个轴加 `input_is_mt_axis(i) ? mt_slots : 1`（:2148-2150）；EV_REL 置位再加 relbit 权重（:2152-2153）；末尾 `events += 7`（:2156，注释 "Make room for KEY and MSC events"）。

落到本设备的计算链（每一项已证）：

1. `ABS_MT_SLOT` 在 absbit（input-devices.txt:45）→ `virtinput_probe` 调 `input_mt_init_slots(vi->idev, nslots, 0)`，`nslots = input_abs_get_max(vi->idev, ABS_MT_SLOT) + 1`（`virtio_input.c:309-311`）→ `nslots = 9 + 1 = 10` → `mt->num_slots = 10`（`drivers/input/input-mt.c:53`）。
2. `dev->mt` 非空 → `mt_slots = 10`（`input.c:2134-2135`）。
3. absbit 六个轴（input-devices.txt:45-50）全部落在 `ABS_MT_FIRST..ABS_MT_LAST` 或等于 `ABS_MT_SLOT`——`input_is_mt_value` 的判据是 `axis >= ABS_MT_FIRST && axis <= ABS_MT_LAST`（`include/linux/input/mt.h:90-93`），`input_is_mt_axis` 加上 `axis == ABS_MT_SLOT`（`mt.h:95-97`）——六个轴每个计 `mt_slots = 10`，共 60。
4. `events = 10 + 1 + 60 + 7 = 78`。
5. `virtio_input.c` 全文件没有 `input_set_events_per_packet` 调用（grep 无匹配，过程记录留有输出），`hint_events_per_packet` 保持 `kzalloc` 初值 0 → `:2292-2293` 取 78 → `max_vals = 80`（`:2295`）。

`max_vals = 80` 是第 9.1 节问一（攒批容量）与第 10.2 节（强制 flush 触发条件）的输入量。

3. FLUSH 后 `dev->timestamp[INPUT_CLK_MONO]` 重置为无效值 `ktime_set(0,0)`（:412）——批01 §8.2 证明的"eventTime 由 evdev 层现场取时"依赖这次重置：每 packet 的时戳都是 evdev 在下一次 `input_get_timestamp` 时现取的。

### 6.4 EV_ABS 细读：input_handle_abs_event（:211-259）

EV_ABS 分支（:310-314）先查 absbit（:311），再委托：


续（`:229-259`）：


2. **defuzz**（:243-245）：`input_defuzz_abs_event`（`:56-70`）在 `fuzz` 非 0 时按三档距离做平滑/合并，`fuzz` 为 0 时直接 `return value`（:58 的 `if (fuzz)` 不成立）。**本设备全部六轴 fuzz=0**（input-devices.txt:45-50）→ defuzz 对本流是恒等函数——已证（联合）。

4. **slot 冲刷**（:252-256）：MT 轴到来且 `mt->slot != input_abs_get_val(dev, ABS_MT_SLOT)` 时，先把 `absinfo[ABS_MT_SLOT].value` 更新为新 slot 并返回 `HANDLERS|INPUT_SLOT`——主体写入 vals 时（:389-394）会先插一条合成 `EV_ABS/ABS_MT_SLOT` 再插本事件。

**对 event0 的具体结论**（已证，联合）：host 从未上报 ABS_MT_SLOT（touch.txt 统计 ABS_MT_SLOT 0 条）→ :218-227 的暂存分支不执行；`mt->slot` 与 `absinfo[ABS_MT_SLOT].value` 的初值同为 0——`mt` 由 `input_mt_init_slots` 的 `kzalloc` 分配（`drivers/input/input-mt.c:49`），absinfo 数组由 `input_alloc_absinfo` 的 `kcalloc(ABS_CNT, ...)` 分配（`drivers/input/input.c:496`，全部字段含 `value` 置零），`input-mt.c:55` 的 `input_set_abs_params(dev, ABS_MT_SLOT, 0, num_slots - 1, 0, 0)` 再置其 min=0/max=9（min/max/fuzz/flat 四字段，不动 value）→ :253 条件恒假 → **INPUT_SLOT 合成机制对本流全程休眠**。

### 6.5 一次触摸 packet 在本层的状态迁移（对照样本实测）

touch.txt 的 event0 流按 SYN_REPORT 切开共 1195 个 packet，构成统计（awk 逐 packet 计数，过程记录留有命令与输出）：**1153 个 packet 含 2 条 EV_ABS（POSITION_X＋POSITION_Y）、41 个含 1 条（8 个只有 X、33 个只有 Y）、1 个含 4 条（首 packet：`ABS_MT_TRACKING_ID ABS_MT_POSITION_X ABS_MT_POSITION_Y BTN_TOUCH`），0 个空 packet**。以首 packet 为例走本层状态迁移：

1. `EV_ABS/ABS_MT_TRACKING_ID`（value=n）：:443 门过（EV_ABS 在 evbit）→ :311 absbit 过 → pold 指向 `mt->slots[0].abs[TRACKING_ID-ABS_MT_FIRST]`，其初值为 -1（`input-mt.c:92-93` 的初始化循环 `input_mt_set_value(&mt->slots[i], ABS_MT_TRACKING_ID, -1)`）→ n ≠ -1 → 不被去重 → vals[0]。
2. `EV_ABS/ABS_MT_POSITION_X`：pold 初值 0（kzalloc）→ 值不等 → vals[1]，`pold` 更新。
3. `EV_ABS/ABS_MT_POSITION_Y`：同上 → vals[2]。
4. `EV_KEY/BTN_TOUCH`（value=1）：:285 keybit 过（BTN_TOUCH 在 keybit，input-devices.txt:44）→ value≠2 → `dev->key` 位 0→1 翻转（:295）→ vals[3]。
5. `EV_SYN/SYN_REPORT`（value=0，touch.txt 实测该值；guest 驱动按 wire 值透传（批01 §8.1），host 侧以何种代码路径产生该值＝盲区——`include/linux/input.h:458-461` 的 `input_sync()` 是内核驱动等价的发起函数：`input_event(dev, EV_SYN, SYN_REPORT, 0)`）：处置 `HANDLERS|FLUSH`（:275-277）→ 本身入 vals[4]（:396-399）→ `num_vals=5 >= 2` → **一次 `input_pass_values` 下发全部 5 条**（:403-404）→ `num_vals=0`（:405）→ timestamp 重置（:412）。

后续 MOVE packet（X＋Y 两条＋SYN）走同一迁移，只是 `dev->key` 位已为 1 且无 BTN 事件。41 个单坐标 packet 表明该 packet 内另一轴"没有值变化"——成因两个候选：host 未发该轴的值，或 host 发了相同值被 :246-247 去重。现有采集（wire 侧无痕）不能区分 → **未证**。

### 6.6 设备方向分支：INPUT_PASS_TO_DEVICE 与 guest→host 回写

`:380-381` 的执行条件是处置位含 `INPUT_PASS_TO_DEVICE`。查 6.3 节总表：只有 SYN_CONFIG、EV_MSC、EV_LED、EV_SND、EV_REP、EV_FF、EV_PWR 七类会置位。本设备的 `dev->event = virtinput_status`（`virtio_input.c:282`）→ `virtinput_send_status`（`virtio_input.c:60-104`）把值打包成 wire 事件投入 status 队列回传 host（批01 §6.2）。批01 §6.1 引用的驱动注释（`virtio_input.c:68-81`）记录的 MSC_TIMESTAMP 回环放大缺陷，其机制根源正是 EV_MSC 的 `INPUT_PASS_TO_ALL` 处置：既进 vals 交给 handler，又调 `dev->event` 回写设备。

**对本流的判定（已证，联合）**：触摸主线事件 EV_ABS（HANDLERS）、EV_KEY/BTN_TOUCH（HANDLERS）、EV_SYN/SYN_REPORT（HANDLERS|FLUSH）**处置位都不含 `INPUT_PASS_TO_DEVICE`**（6.3 节总表行号）→ 触摸报点不会反向写入 status 队列；event0 能力位图无 MSC/LED/SND 位（input-devices.txt 无对应节）→ 这些类型在本设备根本过不了 :443 的门。touch.txt 全窗口 event0 无一条 EV_MSC/EV_REP/EV_LED/EV_SND → **回写通路在本采集窗口内零使用**。批01 §6.2 的"触摸报点不经过 status 通路"结论在本篇拿到完整的分支级行号证据。

### 7.1 input_pass_values（:128-164）


（`:128-151`，:152 空行。）四个行为：

1. **grab 优先**（:139-141）：`dev->grab` 非空（EVIOCGRAB 设置，`input_grab_device` :538-557 的 `rcu_assign_pointer(dev->grab, handle)` :552）时只发给被 grab 的 handle。本流无 grab 采集证据（未证其状态；EVIOCGRAB 由用户态触发）。

### 7.2 input_to_handler（:93-121）

```c
static unsigned int input_to_handler(struct input_handle *handle,
			struct input_value *vals, unsigned int count)
{
	struct input_handler *handler = handle->handler;
	struct input_value *end = vals;
	struct input_value *v;

	if (handler->filter) {
		for (v = vals; v != vals + count; v++) {
			if (handler->filter(handle, v->type, v->code, v->value))
				continue;
			if (end != v)
				*end = *v;
			end++;
		}
		count = end - vals;
	}

	if (!count)
		return 0;

	if (handler->events)
		handler->events(handle, vals, count);
	else if (handler->event)
		for (v = vals; v != vals + count; v++)
			handler->event(handle, v->type, v->code, v->value);

	return count;
}
```

（`:93-121`；函数上方的注释（`:88-92`）末句即 "This function is called with dev->event_lock held and interrupts disabled."。）三个行为：

1. **filter 钩子**（:100-109）：handler 声明了 `.filter` 时，每个值先问 filter；返回 true 的值被跳过（continue），其余值**就地压缩**（:104-106 的 `*end = *v` 直接改写 vals 数组），count 收缩。第 9.4 节展开。
2. **批量优先**（:114-115）：`handler->events` 存在则一次调用交出整个数组；否则退化为逐值调 `handler->event`（:116-118）。evdev 两者都注册（`evdev_handler` 的 `.event = evdev_event` :1425、`.events = evdev_events` :1426），**events 优先**——所以本设备的每次下发都是一次批量调用。
3. 返回处理后的 count（:120）。

### 7.5 锁与上下文小结

事件主线的锁序：`dev->event_lock`（`spin_lock_irqsave`，:445）覆盖 disposition 判定、vals 攒批、FLUSH、`input_pass_values`、`input_to_handler`、handler 回调全程；期间 `rcu_read_lock()`（:137）与 evdev 内部的 `client->buffer_lock`（`evdev.c:265`）嵌套。`input_mutex`（注册互斥）与 `dev->mutex`（open/close 串行）不出现在事件路径。handler 回调契约（`input.h:279-284`）与 `input_to_handler` 注释（`input.c:88-92`）一致声明：**回调在关中断＋event_lock 下执行，不可睡眠**。批01 已证回调本身运行于硬中断上下文（01-篇 §3.4），故本层的全部工作都发生在同一次硬中断里。

## 8. 中断路径概述：irqhandler → vring callback → input_event

**上下文判定（已证）**：以上全部 `request_irq` 调用未使用 `request_threaded_irq`，flags 无 `IRQF_ONESHOT` 线程化语义 → 中断处理函数运行于硬中断上下文；回调链条 `vm_interrupt/vp_interrupt → vring_interrupt → virtinput_recv_events → input_event` 全程在同一硬中断里同步执行。这与批01 断言 A6 一致（01-篇 §3.4：`virtio_pci_common.c:339-340/82-100`、`virtio_ring.c:2147-2168`）。**含义**：input core 的 disposition、攒批、FLUSH、handler 回调、evdev 写缓冲、wake_up 全部计入一次硬中断的执行时长；packet 越长（vals 越满）单次中断内的工作越多——第 9.1 节问一的可测量后果。

**对本设备的约束复核（已证）**：`virtinput_recv_events` 的 `input_event()` 在 :43/:48 的解锁窗口内调用（批01 §5.3 的死锁规避），而 `input_event` 内部再取 `dev->event_lock`（:445）。链条：hardirq → vi->lock（短暂）→ 解锁 → input_event → event_lock（全 packet 处置期间持有）→ evdev buffer_lock（嵌套）。三层锁都不是可睡眠锁，与 6.2-7.3 节的无睡眠走读一致。

## 9. 机制四问

### 9.1 问一：EV_ABS 为什么先缓存进 dev->vals、SYN_REPORT 时统一上抛

**规则是什么**：EV_ABS 类事件（含通过去重的值）不直接下发，写入 `dev->vals[dev->num_vals++]`（`drivers/input/input.c:396-399`）；直到处置位含 `INPUT_FLUSH` 的 `EV_SYN/SYN_REPORT`（:275-277）到达，才以一次 `input_pass_values` 把整个数组交给 handler（:402-405），随后归零（:405）。

**谁设置**：容量 `max_vals` 在注册期由 `input_estimate_events_per_packet` 与驱动 hint 取大后加 2 定出（:2291-2295，本设备 80，计算链见 4.4 节）；数组本体 `kcalloc`（:2296）。**谁执行**：`input_handle_event`（:367-419）在 `dev->event_lock` 下执行攒批与 flush；`input_pass_values`（:128-164）完成分发。**执行的后果**（三条都是代码可直接检出的形态，已证）：

1. **handler 拿到整包**：`handler->events(handle, vals, count)`（:114-115）一次收到 packet 全部值。evdev 端的对应收益：整包写 client 缓冲在**一次** `client->buffer_lock` 获取内完成（`evdev.c:265-285`），每个 packet 只有一次锁外 `wake_up_interruptible_poll`（:287-289）——若逐值下发（handler->event 路径 :116-118），锁获取与唤醒节奏都会变密。本设备走批量路径（evdev 同时注册了 `.event` 与 `.events`，:1425-1426，批量优先）。
2. **INPUT_SLOT 合成需要缓冲区**：新 slot 的首条 MT 数据到来时，合成 `EV_ABS/ABS_MT_SLOT` 必须排在数据值**之前**进入 vals（:389-394 在 :396-399 之前执行）——没有攒批数组就没有插入点。本流该机制休眠（6.4 节），但机制存在性已证。
3. **容量保护**：`num_vals` 达 `max_vals - 2` 时强制下发并追加合成 SYN_REPORT（:413-417）——避免只发值不发 SYN 的驱动把 80 槽的 vals 数组写越界。触发即 packet 被拆成两批（边界改变、时刻不变）。

**"为什么"的边界**：以上是代码可证的三点后果。设计意图层面的表述（例如"为了一次锁获取"）出自代码注释与结构（`input.h:63-66` 的 packet 概念注释、`evdev.c:264` 的锁注释），本篇不再外推。

**对本设备的量化**（已证，计算链）：max_vals=80；实测 packet 最大 4 条事件；强制 flush 与孤立 SYN 丢弃两个边界行为在本流均未触发（6.5 节统计 0 个空 packet、41 个单事件 packet 全部 ≥2 值含 SYN 可过 :403 门）。

### 9.2 问二：EV_REP 重复定时器由谁开启、超时后做什么

**规则是什么**：设备声明了 `EV_REP` 与 `EV_KEY` 位（:154 的双 test_bit）时，`input_pass_values` 在处理 `vals` 时对每个 `EV_KEY` 值判定（:156）：value 非 0 且非 2（按下）→ `input_start_autorepeat(dev, v->code)`；value 为 0（释放）→ `input_stop_autorepeat(dev)`。

`drivers/input/input.c:72-86`：

```c
static void input_start_autorepeat(struct input_dev *dev, int code)
{
	if (test_bit(EV_REP, dev->evbit) &&
	    dev->rep[REP_PERIOD] && dev->rep[REP_DELAY] &&
	    dev->timer.function) {
		dev->repeat_key = code;
		mod_timer(&dev->timer,
			  jiffies + msecs_to_jiffies(dev->rep[REP_DELAY]));
	}
}

static void input_stop_autorepeat(struct input_dev *dev)
{
	del_timer(&dev->timer);
}
```

**谁设置参数**（三条来源，均已证）：注册默认——`input_register_device` 在驱动未预置 `rep[]` 时调 `input_enable_softrepeat(dev, 250, 33)`（:2306-2307），把 `timer.function` 设为 `input_repeat_key` 并写 `REP_DELAY=250/REP_PERIOD=33`（:2220-2226）；运行期改值——EV_REP 类型事件更新 `dev->rep[code]`（:346-351），用户态经 EVIOCSREP ioctl 注入（`evdev.c:1067-1076` 的 `input_inject_event(&evdev->handle, EV_REP, REP_DELAY/PERIOD, u/v)`）；驱动预置则 core 不接管（:2302-2305 注释）。timer 本体在 `input_allocate_device` 里 `timer_setup(&dev->timer, NULL, 0)`（:1920）。

**谁执行**：内核定时器子系统。到期回调 `input_repeat_key`（:179-202）在定时器 softirq 上下文执行（`kernel/time/timer.c:2033` 的 `open_softirq(TIMER_SOFTIRQ, run_timer_softirq)` 与 :1752 的 `run_timer_softirq`）。

**超时后做什么**（`:179-202`）：


（:179-199，:201 的解锁恢复略。）键仍在按下态且 keybit 支持时：构造 `{EV_KEY, repeat_key, 2}`＋`input_value_sync` 两条值，`input_set_timestamp(dev, ktime_get())`（:193——这是 `input_set_timestamp` 在 input.c 事件处理函数内的唯一直接调用点；另一调用点 :2060 位于 `input_get_timestamp` 辅助函数内部，即第 7.3 节的现场取时，grep 全文件两处已核对；批01 §8.2 已核对），直接 `input_pass_values` 下发（:194，绕过 `input_handle_event` 的状态机），再以 `REP_PERIOD` 重挂定时器（:196-198）。value=2 的重复事件在 6.3 节 EV_KEY 分支走 :288-291 的直通路（不翻 `dev->key` 位），在 :156 的 autorepeat 判定里被 `v->value != 2` 排除（不会自己再 start）。

**执行的后果**：每 `REP_PERIOD`（默认 33 ms）一条 EV_KEY value=2＋一条 SYN_REPORT 进入分发——若设备有 EV_REP 位，这是本层唯一的定时合成事件源。

**对本设备的判定（已证，联合）**：event0 的 evbit 无 EV_REP 位（input-devices.txt 无 REP 节）→ :154 的 `test_bit(EV_REP, dev->evbit)` 失败、`input_start_autorepeat` 的 :74 同样失败 → **定时器全程未被武装**。trace 佐证：touch.txt 全窗口 event0 仅 1 条 EV_KEY（BTN_TOUCH DOWN）、无 value=2 形态、1195 条 EV_SYN 全部伴随 ≥1 条前置事件——没有任何 autorepeat 合成事件的痕迹。批01 §4.5.3 的"autorepeat 不可能周期性生成触摸 MOVE 报点"结论在本篇拿到分支级证明，且证据从"代码机制"升级为"机制＋本设备能力位图＋全窗口 trace 三重"。

### 9.4 问四：input_filter 在什么条件下被调用、调用者是谁

**规则是什么**：`handler->filter` 非空的 handler，其每个 handle 在收到值之前先过 filter；对 `vals` 中每个值调用 `handler->filter(handle, v->type, v->code, v->value)`（`drivers/input/input.c:100-109`），返回 true 的值被移除，其余**就地压缩**（:104-106 `*end = *v`），count 收缩（:108）。filter 返回 true 只表示"该值对这个 handle 不再透传"。

**调用者是谁**：`input_to_handler`（:93-121）是唯一调用点（grep 全文件无第二个 `handler->filter` 调用，已证）；`input_to_handler` 的调用者是 `input_pass_values` 的 :141（grab 路径）与 :145（h_list 遍历路径）——即**只有事件下发会触发 filter，注册/注销路径不触发**。

**执行条件与顺序**（已证）：

1. filter 型 handle 头插 `dev->h_list`（:2502-2505），普通型尾插——filter 先收到值。
2. `input_pass_values` 的 `count = input_to_handler(handle, vals, count)`（:145）把压缩结果传给下一个 handle；`if (!count) break;`（:146-147）在 filter 清空全部值时终止遍历——**filter 是本层唯一能让事件在 handle 之间"终止传递"的钩子**。
3. 因为压缩改写 `vals` 本体（:104-106），后续 handle 看到的数组是前序 filter 处理后的残余——多个 filter 串联时语义是顺序过滤。

**树内谁在用**（已证，grep 全量）：注册的十个 handler 中只有 `sysrq_handler`（`drivers/tty/sysrq.c:1025-1031`，`.filter = sysrq_filter` :1026，filter 函数 :927）与 `mac_hid_emumouse_handler`（`drivers/macintosh/mac_hid.c:154-155`）设置 `.filter`；其余八个（evdev/mousedev/joydev/input-leds/apmpower/kgdboc/evbug/kbd）无 `.filter` 字段（各结构体定义处，第 5 节表格）。defconfig 层面只有 sysrq 编入（`CONFIG_MAGIC_SYSRQ=y`，gki_defconfig:679），mac_hid 未编译。

**对本设备的判定（已证，联合）**：sysrq 要挂接到 event0 需要通过 `input_match_device_id` 的 keybit 子集判定（第 4.8 节：sysrq 要求 KEY_LEFTALT，event0 keybit 无）→ **event0 的 handle 集合中不存在 filter 型 handle** → 本流的每次下发（:143-148）没有 filter 参与，count 只会在唯一的 evdev handle 上保持原值。与 Android 侧 `filterInputEvent`（`IMS.java:3014`，批06 走读）的划界：那是 InputDispatcher 进程内的 Java 过滤器，与本层的 `handler->filter` 钩子（内核 handle 级）无任何代码关联，两者名字相近但层次不同。

## 10. trace 配对

### 10.1 驱动侧完成点（契约 ：97）

契约把"SYN_REPORT→input_pass_values→evdev 层的时刻"定义为**驱动侧完成点**。本篇给该定义的行号链条（已证）：

1. host 发出的 `EV_SYN/SYN_REPORT` 经 `virtinput_recv_events` 透传进 `input_event`（`virtio_input.c:44-47`，批01）。
2. 处置位 `INPUT_PASS_TO_HANDLERS | INPUT_FLUSH`（`input.c:275-277`）。
3. FLUSH 触发一次 `input_pass_values`（:402-405）。
4. `input_to_handler` 调 `handler->events`（:114-115）＝ `evdev_events`（`evdev.c:295`），事件写入 client 缓冲（:221）并唤醒读端（:287-289）。

**该完成点与 trace 数值的对应**：完成点是 guest 内核内的一次函数调用，本 trace 无内核函数级 trace 点，其时刻不能直接读出；能对齐的可见锚点是 event0 报点——"event0 坐标变化＋SYN_REPORT：约 00:00:06.787410，与事件 ID 0x3b3b7f02 的 eventTime 数值吻合（同源单点）"（契约 ：70）。机制上两者同源：getevent 读到的是 evdev client 缓冲内容（步 12 的写入），其时戳来自 `input_get_timestamp`（步 10 的 :300 现取）；Android 侧 eventTime 亦源自同一批 input_event 时戳（批01 §8.2 链条＋03 篇展开）。因此**完成点时刻 ≤ 00:00:06.787410 对应的物理时刻**（写入先于用户态读到），其差值（硬中断执行剩余部分＋唤醒＋调度）由 03/04/14 篇接手——InputReader 在 00:00:06.787427 起 R 态 7.951 ms（契约 ：71），该 R 窗口的起点已在完成点之后。

### 10.2 节点报点间隔分布在本层无改变机制（已证，穷尽证据）

判定文本：**均值 16.617 ms、中位 16.347、P90 31.416、P95 36.122、P99 40.936、最大 93.711 ms（>25 ms 209 个占 17.5%、<10 ms 253 个占 21.2%）的 1194 个间隔，以及重点间隔 37.237 ms（00:00:06.750173→00:00:06.787410）与其后的 2.842 / 9.958 / 16.588 / 16.390 ms，在 input core 入口（:438）与出口（:114-115）之间不存在任何产生、合并、延迟或重排机制。**（数值逐字引自契约 :76。）

五组证据：

1. **packet 不合并**：每次 FLUSH 后 `num_vals = 0`（:405），下一 packet 从空数组攒起；不同 packet 的值不会跨 FLUSH 累积。每个可见 SYN_REPORT（本流 1195 个，全部伴随 ≥1 条前置事件，6.5 节统计）触发恰好一次 `input_pass_values`。
2. **无定时器**：`grep -n "timer\|hrtimer\|work\|tasklet\|schedule\|delay\|sleep"` 在 input.c 的全部命中（过程记录留有输出）分两类——代码命中只在 autorepeat 定时器（:76/:78/:85/:179/:181/:197/:1920/:2192/:2220/:2222-2223），其余（:1966/:2215/:2303/:2451）均为注释文本。事件路径（:367-419、:128-164、:93-121）无任何时间机制。**autorepeat 只作用于 EV_KEY**：触发段的双位判据与 `v->type == EV_KEY`（:154-156）；触摸事件 EV_ABS/EV_SYN 的处置位与类型判定都不经过它（6.3 节总表 ：269-282/:310-314）。本设备无 EV_REP 位 → 定时器未武装（9.2 节）。
3. **无睡眠点**：事件路径全程持 `event_lock` 自旋锁（:445-447）运行；`input_pass_values` 只取 RCU 读锁（:137）；evdev 端只取自旋锁（`evdev.c:265`，注释明示 interrupts disabled）。无内存分配（`GFP_KERNEL` 调用只出现在注册路径 ：2296 等处）。
4. **值级改写清单（存在但不改时刻）**：本层能改变值的机制穷尽为四处——defuzz（:243-245，本设备 fuzz=0 恒等）、值级去重（:246-249，可能丢重复值）、SLOT 合成（:252-256＋:389-394，本流休眠）、强制 flush（:413-417，触发条件 78 不可达）。四处都不引入等待：被去重的值根本不进 vals（:246-247 的判定发生在攒批之前），只影响该 packet 的内容，不影响任何 SYN_REPORT 的到达时刻；强制 flush 若触发会把长 packet 拆两批（边界改、时刻不变，且本流不可达）。
5. **采集侧佐证**：touch.txt 的 event0 全窗口构成（2350 EV_ABS＋1 EV_KEY＋1195 EV_SYN 全 SYN_REPORT）与 getevent 能力位图（无 REP/MSC/LED/SND 节）一致，无任何合成事件或额外 SYN 的形态。

**推论与交接**：批01 的未证项 A19（"guest 内核路径无节流"）中 input core 段在本篇升级为已证（本节 1-4）；evdev 段（client 缓冲满时的 SYN_DROPPED 行为等）仍留 03 篇裁决。37.237 ms 重点间隔的产生点在完成点之前——host 侧或更上游（批01 §9.2 已把驱动段排除）；**host 报点节奏的具体成因 = 未证/盲区**（host 代码不在基准树），最终归因在批15。

## 11. 与两个问题的关联

**50.928 ms 主线程 Sleeping（00:00:06.779837–00:00:06.830765）**：input core 事件路径无可睡眠点、无队列、无定时（10.2 节证据 1-3）→ 主线程的 S 不可能在本层形成或延长——本层连一个可阻塞的对象都没有（自旋锁的持有者是同一次硬中断自身）。批00 §3.7 已声明"50.928 ms S 的具体等待条件"为全局盲区；本篇的贡献是把"input core 参与"从候选表里排除（已证），该排除依据供批15 使用。

**34.738 ms notifyMotion→prepare（00:00:06.795839→00:00:06.830577）**：该空档的起点（notifyMotion）晚于本层完成点，事件此刻已交付到 Android 读取段；input core 在这个时间窗内没有任何动作（事件早已交付完毕）→ 本层不参与该空档的形成（已证，机制排除）。候选全表与逐候选判据在批06（契约 :123）。

**37.237 ms 重点间隔**：完成点链条（10.1 节）证明该间隔的两个端点（6.750173→6.787410 的两个 SYN_REPORT）在 core 内的处理都是同步瞬时（同一次硬中断）；间隔由两次硬中断之间的时间决定，而后者由 host 写 used ring＋发中断的节奏决定（批01 §8.3 的先后关系），guest 侧的 input core 与 evdev 都不塑造它。已证（机制链）；host 节奏成因未证/盲区。

## 12. 未证边界与盲区清单

1. **盲区（host 配置）**：event0 全部能力位（keybit/absbit 范围/fuzz/EV_REP 缺席/propbit）由 host 配置空间决定；guest 内核位图已证（getevent 直读），host 声明动机不可证（批01 §4.5 同口径）。
2. **盲区（传输层）**：本设备走 virtio-mmio 还是 virtio-pci 由虚拟机配置决定，guest 源码内不可判定（第 8 节）；两条路径的硬中断结论相同，判定不受影响。
3. **未证（host 行为）**：host 是否重发过相同 ABS 值（决定 :246-249 去重在本流是否丢过值）；41 个单坐标 packet 是 host 少发还是 core 去重（6.5 节两候选）。
4. **盲区（运行时 handle 集合）**：event0 的 `dev->h_list` 全量成员无 /proc/bus/input/devices 采集；"evdev 在列、sysrq 不在列"已由能力位图＋defconfig 单独证明（4.8/9.4 节），其余成员的缺席判定依赖 defconfig 与设备 config 的一致性前提（批00 §3.6）。
5. **未证（采集窗口排除项）**：注销/改键/EVIOCGRAB/ inhibited 在窗口内未发生的完整排除依赖系统级事件缺失（7.4 节标注口径）。
6. **未测（时长）**：`add_input_randomness` 的单次执行时长（6.2 节）；硬中断单次执行总时长（无 irq trace 事件，契约盲区）。
7. **留待 03 篇**：evdev 段无节流的最终裁决（A19 剩余段）；client 缓冲尺寸数值（hint=78 的下游消费，`evdev.c:465-472`）；SYN_DROPPED 与读端 packet 化。
