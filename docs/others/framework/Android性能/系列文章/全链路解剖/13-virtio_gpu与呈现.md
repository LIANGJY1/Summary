# 13 · virtio-gpu：Android 提交之后如何到达 host

Android 显示提交进入 guest 驱动后，由虚拟设备转交 host 并接收响应。命令计数不能直接换算为物理新帧率。

> 逐行分析：[内核源码详解 13](内核源码详解/13-virtio_gpu与呈现.md)。沿用 kernel 5.15.41、HEAD `24d27dff64c4` 与 Android 13 基准源码树的原分析。

## 0. 本层接收什么

virtio-gpu 是虚拟机的图形设备接口及其相关驱动机制，让 guest 将图形资源和显示更新请求交给 host 侧虚拟设备处理。本篇讨论虚拟化交接，不把提交命令或响应直接当成物理屏幕已经显示。

SurfaceFlinger 完成合成和显示提交后，通过 HWC（Hardware Composer，硬件合成器）实现接入显示驱动。本分析基准的 HWC 为 external/drm_hwcomposer，使用 DRM（Direct Rendering Manager）原子提交路径，进入 guest 的 virtio-gpu。

1. 输入：显示缓冲、plane 与输出配置等提交状态。
2. 处理：guest 驱动按实际分支构造命令，通过 virtqueue 交给 host。
3. 输出：host 命令处理结果及相应完成通知。
4. 边界：guest 收到命令完成，不代表已测到物理面板出现新画面。

## 1. 提交流程是什么

下图是原基准中 2D plane 更新的概念流程。箭头表示处理关系，具体命令取决于缓冲类型、配置与更新区域，并非每次提交都执行全部步骤。

```text
SurfaceFlinger → HWC → DRM atomic 提交
  → guest 提交处理
  → 按条件上传内容 / 设置 scanout / flush resource
  → control virtqueue → host 处理
  → 响应 → guest 完成通知或 fence 信号
```

1. DRM 原子提交把一组显示状态作为一次提交处理。“原子”描述状态提交方式，不表示整条链没有等待，也不表示返回时画面已显示。
2. 非阻塞提交可把后续工作交给内核工作线程，用户态调用返回与内核处理结束要区分。
3. 驱动根据 plane 更新决定构造哪些命令，再通过 control virtqueue 发送。cursor 另有队列，不能把所有命令都视为应用内容帧。
4. host 处理命令后返回响应，guest 按响应更新完成状态。host 内部合成和面板扫描输出仍在这条可见链之外。

## 2. 三类命令各自做什么

1. **TRANSFER_TO_HOST_2D**：在相应 2D 缓冲路径中，把 guest 内容更新到 host 资源。它不是所有渲染模式都必须走的上传入口。
2. **SET_SCANOUT**：设置 host 显示输出所使用的资源和区域。scanout 是协议中的输出关联，不是“已扫描到物理屏幕”的时间戳。
3. **RESOURCE_FLUSH**：通知 host 处理资源更新。它是命令协议中的更新操作，不能直接当成一次 doFrame 或一张物理新帧。

原基准还有 3D EXECBUFFER/SUBMIT_3D 路径，不能把 2D transfer 解释强加给它。本设备实际启用的相关 feature、2D/3D 分支和部分缓冲类型缺少运行期观测，仍为未证。

## 3. fence 与等待怎样理解

fence 是表示某项工作完成的同步对象。等待者等到它被置为完成后才继续相应操作，但必须先确认该 fence 表示哪项工作。

1. guest 可为命令分配 fence_id，并在 host 响应后更新相应 fence。
2. 队列空间不足可能使提交者等待。等待发生在哪一段，需结合线程状态和对应事件确认。
3. 本树部分 fenced flush 分支含至多 50 ms 的等待，这是分支中的超时参数，不是本样本测得的每帧耗时，也不能证明该分支在设备上启用。
4. 命令 fence 完成与 Android 其他同步 fence 的职责不能仅凭名称混为一谈，更不能直接推为物理呈现完成。

## 4. 为什么 flush 计数不是物理帧率

1. 提交可因没有更新区域而不发相应 2D 命令，提交数与命令数不恒等。
2. 相同 framebuffer 的重复更新也可能触发 flush，命令数不能证明不同内容的画面数量。
3. RESOURCE_FLUSH 响应的 guest 可见上界是 host 对该命令的处理结果，协议没有给出该画面在物理面板呈现的时间。
4. host 合成和扫描输出节奏不可见，不能把 guest 命令处理时间补写为 host 呈现时间。

## 5. vg-kit 应怎样使用

1. 已有输出 Display0 序列为 16、39、34、30、31、40、35，属于 Yocto host 域显示计数的 2 秒窗口平均值。
2. 旧会话逆向结果把它关联到 scanout 对象计数和至少一条 RESOURCE_FLUSH 增量路径，这一关联仍带未证限定。工具源码、计数器精确定义和参数内部语义是盲区。
3. 输出没有可与 trace 对齐的共同时间戳，七个窗口不能直接按位置匹配 guest 线程活动。
4. 2 秒均值不保留帧间隔分布，也不是 Android doFrame 计数或已证物理新帧率。数值接近不能建立等价或因果关系。

## 6. 本 trace 能证明到哪里

1. guest 用户态帧生产、提交与合成的可见性由 09～12、15 篇说明，不因本篇简化而降级。
2. 原 trace 没有采到用于逐条还原该驱动提交的 virtio_gpu/drm 事件。未采到不等于命令没有发生。
3. 本设备具体命令频率、host 收到命令后的处理时长及物理新帧时刻仍不可直接量化。
4. 因此不能把 34.738 ms 的输入分发空档归到 GPU，也不能用 vg-kit 均值证明某一帧延迟的具体来源。
