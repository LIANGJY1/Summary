# 14 · 调度与线程状态：怎样读懂 Perfetto 中的等待

CFS 是 Linux 内核的调度器，用于安排普通调度类线程使用 CPU。本篇通过线程状态区分等待条件、等待 CPU 和实际运行，再结合唤醒、竞争窗口与阻塞函数分析等待。

> CFS（Completely Fair Scheduler，完全公平调度器）实现、选核、状态翻译和锁路径见[内核源码详解 14](内核源码详解/14-CFS调度与线程状态.md)。基准为 kernel 5.15.41、HEAD `24d27dff64c4`。

## 0. 先区分三种时间

分析一段事件为什么迟到，要先区分线程在等条件、等 CPU，还是已经执行代码。

1. 等条件：线程暂时不可运行，事件、锁或其他条件满足后才能继续。
2. 等 CPU：线程已可运行，但尚未被调度执行。
3. 正在运行：线程占用 CPU 执行，具体业务仍需查看对应 slice 或源码。

这三段的原因不同，不能把整个墙钟间隔都称为计算耗时或 CPU 竞争。

## 1. 状态怎样读取

1. **Running**：线程已在某个 CPU 上执行。它既可能执行用户态代码，也可能在该线程上下文执行内核代码。
2. **R**：线程可运行、尚未运行。唤醒后等待 CPU，或仍可运行但切出，都可能形成该状态。
3. **R+**：本基准的调度事件用加号标记经抢占入口切出的可运行任务。它仍需等待再次运行，不能理解为睡眠或已经获得更多 CPU。
4. **S**：TASK_INTERRUPTIBLE，可中断睡眠。线程在等条件，通常不处于可运行队列；允许被信号打断不等于睡眠一定由信号结束。
5. **D**：本篇讨论的纯 TASK_UNINTERRUPTIBLE，不可中断等待，不能用普通信号使它按 S 的方式退出。它不等同“必然是磁盘 I/O”；锁或其他内核等待也可能呈现该状态。带 KILLABLE 等组合状态需另看具体路径。

这些字母必须结合 Perfetto 的 thread_state 与 sched 原始事件读取，不能仅凭一个切出标记推断具体业务函数。

## 2. 从唤醒到执行还差什么

```text
等待中的线程（S / D）
  → 条件方发出唤醒
  → 线程变得可运行，选择目标 CPU 并入队
  → R：等待调度
  → Running：开始或继续执行
```

1. 唤醒表示线程具有继续执行的条件，不保证立即运行。
2. waker 关联的是触发唤醒记录的执行上下文，可帮助寻找直接唤醒者。中断相关上下文或 maybe interrupt 标记不能直接确定上层业务调用者。
3. target_cpu 是唤醒选择的目标，不能单独证明选核策略，也不能保证之后不迁移。
4. 真正执行仍由后续调度决定。分析唤醒延迟需把“条件尚未满足”和“已唤醒但没运行”分开统计。

## 3. 为什么 S 不能解释成 CPU 不够

1. S 线程在等待条件，增加可用 CPU 不能直接让未满足条件的线程继续执行。
2. 判断 CPU 竞争应先找 R/R+ 区间，再看目标 CPU 同期运行了谁、可用 CPU 掩码和调度条件。
3. 其他核有 idle，不能证明当前任务可以立即迁移。亲和性、cpuset、缓存局部性、调度与均衡时机等都可能约束选择。
4. 某线程与延迟区间同时运行，只能证明窗口构成，不能仅凭重叠就判定它是延迟根因。

## 4. 为什么看见 blocked_function 也不能直接定案

1. 本树 sched_blocked_reason 在相关不可中断等待的唤醒路径记录阻塞函数信息。S 没有同样记录，不代表它没有等待条件。
2. 函数级信息可把调查范围缩小到某条内核路径，不能保证区分函数内部的锁竞争和后端操作。
3. 本样本 InputReader 的 D 约 3.716 ms，blocked_function 指向 write_pmsg。已有源码分析确认其处于 pmsg 写入链，并包含互斥锁，不能称为自旋锁。
4. 锁持有者、等待各部分时长、触发写入的具体日志语句，以及该 D 与目标事件关键路径的因果关系仍未证。不能仅据函数名恢复“日志税为主因”等旧结论。

## 5. 本样本怎样逐段归位

以下数值沿用原查询结果，完整 SQL、原始输出与算术证明保存在过程记录。

1. Launcher 主线程 S：相对时间 6,779,836,842～6,830,764,842 ns，共 50,928,000 ns。已有记录中直接唤醒者为 InputDispatcher，醒后还有 R 33,923 ns。
2. 原查询在该 S 窗口的 CPU4 上统计到 26 段 idle，合计 3,617,928 ns。这与 S 等条件的语义相符，不能用同 CPU 其他线程占用解释为该线程正在等 CPU。
3. InputReader 的 R 从 6,787,426,919 ns 开始，持续 7,951,192 ns。这一段没有执行读取处理代码，应与之后的 Running 分开。
4. system_server 主线程两个 R 窗口分别为 9,313,231 ns 和 17,289,307 ns，原查询在 CPU2 上测得窗口内无 idle。竞争窗口构成已测，不等于某线程对 34.738 ms 路径的因果已经证明。
5. InputReader 的 D 为 6,801,836,572～6,805,553,072 ns，共 3,716,500 ns。它发生在首条 notifyMotion 之后，与同 ID 路径的因果仍未证。
6. Launcher 的 S 本身不是异常量的充分依据。15 篇以交付延迟约 43.597 ms 和 InputFilter 消费后回注的 34,738,039 ns 闭合路径说明实际问题，不能用“S 很长”替代这组证据。

## 6. 怎样用这套读法继续分析

1. 先定位目标事件 ID 和起止点，避免把不同事件、不同线程的区间拼成一条链。
2. 沿相关线程分别统计 S/D、R/R+ 和 Running，确认哪些区间在关键路径内。
3. S/D 查等待对象与唤醒条件，R/R+ 查调度竞争，Running 查实际执行。缺少 syscall、irq 或锁事件时，明确保留盲区。
4. 用同域时间与事件关系闭合链路，再判断因果。窗口内存在活动、函数名命中或其他 CPU 空闲，都只能作为对应层面的证据。
