## 2. 审计方法（三重检验的操作化）

### 2.1 源码检验

断言引用的机制先在基准源码树定位到函数与行号；旧文档使用的组件名先做存在性查证再判（例如"libinput"——Linux 桌面输入库的名称，在 Android A13 输入栈基准源码树内无该组件，Android 对应物为 InputReader/InputDispatcher/EventHub）。判定规则：机制与基准源码树一致→引用 01~13 行号支持；机制名存在但行为描述与源码不符→❌ 或 🟡 并写明差异行号；机制在基准源码树无对应物且设备 ROM 未经核对→⬜（不得判 ❌，因批00 §3.6 基准源码树与设备一致性本身是盲区）。

### 2.2 trace 检验

对断言引用的每个可复算数值用同一 SQL 口径重算：

- thread_state 求和：`sum(dur) group by state`，全 trace 跨度（cont/r2 系旧文档未声明手势窗口，本篇按全跨度口径复算并在对照表标注）。
- slice 计数与间隔直方图：按 thread_track 绑定 launcher 主线程；间隔直方图桶取 14–18/18–25/25–34/>34 ms（旧文档 CAP:59-62 口径）。
- blocked_function 分解：D 态 thread_state 按 blocked_function 求和（判"日志写阻塞"归属的直接证据）。
- 复算口径与声称值的差分两类处理：**数值差**（同口径下不等）记为出入并给数值；**口径差**（窗口/分母/桶边界不同导致的系统偏差）单独列出、不计为数值错误。无法判定属于哪类的（如 cont_H_I"命中60 71.1%"）标注"口径不明"。

### 2.3 方法论检验

四类检查项：①样本量——除日志 A/B（07–15，A/B/A 与 B/A/B 结构）外，对照矩阵每条件 n=1；②反馈系统——WAIT_FOR_FINISH 同步注入使事件数随处理速度变化；③口径声明——准时率分母、计数窗口、CPU 表滑窗起点、"命中 60"桶定义；④存档完整性——原始 logcat/loadavg/单滑 gfxinfo/vg-kit 时戳缺失。与 evidence-audit.md 既有判定对齐：其 §3（A/B 重算）、§6.1（反馈系统）、§6.3（非随机大样本）、§6.4（vg 窗口未对齐）、§7（解释规则）直接沿用，不重复降级也不升级。

### 2.4 判定纪律

- 00 篇 §5 已降级的 22 条表述：本篇复核后可扩充降级清单、不可缩减；任何"升级"必须引用 01~13 的具体新证据行号（本篇仅一处降级后仍保留结构判定的情形：D-DER-04b 概率式，条件已收窄）。
- 旧文档内自洽但与本系列已证机制矛盾的判 ❌ 或 🟡 并写明矛盾点（§5 清单）。
- "没查到"不等于"不存在"：10 份文档中未出现契约降级清单的第 6/7 条表述（"31 ms 睡眠期间节点必然无上报""prepare 早于 eventTime"），按 ⬜ 登记而非判 ❌（D-SET-02/03）。

## 3. 按主题分组的判定详述

### 3.1 输入链主题（送达、notify/prepare、filter）

**3.1.1 背景锚点（01~13 已证）**。notifyMotion 在 Reader 线程打出三条同 ID slice（06 E11，InputListener.cpp:340-364）；装有 InputFilter 时事件转交 system_server 主线程处理、以原 id 经 injectInputEvent 回注入队（06 §4.5/§4.7，InputDispatcher.cpp:4029-4052/:4282/:4335-4345）；新样本 34.738 ms 空档九段分解逐 ns 闭合于该路径（06 §4.9），旧样本同构 5,167,308 ns（批0 复验二，0x37ee8b11）；分发→应用经 oq/wq 计数轨与 waker 链直证（07 §4.5；批0 复验二 §一：Launcher S 终点 waker=InputDispatcher tid=1488）。

**3.1.2 "input 处理 17→24ms/事件"（D-CAP-04c／D-CONT-05c）**。复算：cont_V_I deliverInputEvent 间隔均值 17.16 ms（n=292）、cont_V_D 24.32 ms（n=206）——声称值 17.03/23.99 ms（CONT:13-14）复现（差 0.7%）。但"事件"的实体是应用侧 deliver 回调，不是硬件报点：`input swipe` 的 MOVE 由 `InputShellCommand.sendSwipe` 循环注入（frameworks/base/services/core/java/com/android/server/input/InputShellCommand.java:397-427），每次 `injectMotionEvent` 以 `INJECT_INPUT_EVENT_MODE_WAIT_FOR_FINISH` 同步等待应用 finish（:181-182）后才注入下一个，循环体内无 sleep（:418-424）。因此 deliver 间隔=单事件端到端处理时长，开日志变慢时该值变大——这是反馈系统的读数（evidence-audit.md:96 既有判定的源码落点），不是"送达变慢"。round2 自家数据反转了因果句：r2_V_D deliver 均值 12.74 ms（比 r2_V_I 的 17.09 ms 更快）而 doFrame 间隔均值 28.60 ms——R2:13 已据此改口"input 投递不是瓶颈"。判定 🟡：数值可保留；"input 分发被拖慢"的因果句按反馈系统口径改写；两条件各 n=1、无置信区间。

**3.1.3 "input 准时率"（D-CAP-03b/D-DIFF-03a/D-DIFF-02）**。旧文档把"准时率(≤17 ms)"作为核心对照量：垂直 ~96%、水平 57.2%（DIFF:17）、cont_V_I 96.6%（CONT:13）。本篇以 deliverInputEvent 间隔 ≤17 ms 复算：finger 垂直 58.3%（628/1,078）、finger_h 水平 57.2%（n=899，逐字复现声称值）、cont_V_I 96.6%（282/292，逐字复现声称值）。同一度量法在水平与 cont_V_I 上精确复现、在真手指垂直上差 38 个百分点——96% 不可复现，且旧文档未写明其分母与窗口。三个旁证：eventTime 差 ≤17 ms 占 68.0%（Q10，finger）；RV Scroll 间隔 ≤17 ms 占 58.2%（627/1,078，Q9）；deliver 均值 16.67 ms 与声称 16.56 ms 吻合——均值口径成立、准时率口径不成立。由此，"垂直 input 更准时、水平 input 更抖"的对照（CAP:38、DIFF:17、DERIVE:72）前提不成立；两方向 input 抖动同量级，帧稳定性差异只能归因于帧时钟来源（animation 计数差，Q4：垂直 0 vs 水平 919）。判定：D-CAP-03b/D-DIFF-03a ❌，D-DIFF-02 🟡。

## 7. 补采建议汇总

按对未决判定的影响排序（每条给可判定判据）：

1. **VelocityTracker 日志产生者定位**（D-CAP-04a/D-QA-06a ⬜ → 可升级）：在设备上抓取 `logcat -s VelocityTrackerVelocity -s VelocityTrackerStrategy -s VelocityTrackerImpulse -s VelocityTracker` 实测每 MOVE 行数与实际 tag；核对 ROM framework 的 isLoggable 调用点。判据：行数≥1/MOVE 且 tag 命中其一→机制句升级为已证（ROM 口径）；零命中→机制句改写为"开关与指标改善的因果已证，日志产生者未定位"。
2. **原始 logcat 存档**（D-CAP-04d/D-REP-03c ⬜）：开/关日志各采一次完整 logcat 存盘，复算 12534/14 行。判据：两值在 ±10% 内复现→⬜ 升 ✅。
3. **D 态逐段归因**（D-CONT-05d/D-R2-03a）：对 r2_V_D 的 wait_on_page_bit_common 272.8 ms 采集 sched_blocked_reason 关联的文件/页类型（trace 已含 sched_blocked_reason 事件面，需按 utid+窗口提取）。判据：确认其属于日志分配路径→"日志税"归因面扩大；属于其他文件读→r2 表的 D 列改注。
4. **同负载手指 vs adb 隔离实验**（D-DIFF-04）：QA:165 自家提出的方案——保持 load≈12，真手指与 adb 各采一次，加内核 input 侧打点。判据：同负载下两者 doFrame 分布差<5%→"注入轻"候选排除。
5. **"input 准时率"口径统一**（D-CAP-03b）：固定分母（deliverInputEvent 间隔）与窗口（手势段），重算垂直值替换 96%。判据：重算值与 58.3% 一致→旧值作废登记。
6. **直方图分窗配对**（D-CAP-06）：按输入间隔把 doFrame 间隔分窗，区分"缺条件 A"与"缺条件 B"两种慢帧。判据：25–34 ms 慢帧中输入间隔同段占比>80%→慢帧主因=输入供给。
7. **vg-kit 时戳对齐**（D-R2-04a）：vg 输出加设备时间戳或与 trace 同源时标。判据：窗口可与 trace 对齐→"三方一致"可检验；否则 R2:32 维持 ❌。
8. **loadavg 快照存档**（D-DER-05d/D-REP-07e）：每轮实验记录 /proc/loadavg。判据：存档后 load≈12/11 可复现与否直接判定。
9. **对照矩阵重复轮次**（D-CONT-02/D-R2-01）：每条件 n≥3＋随机交叉（evidence-audit.md:135 第 3 条既有要求）。判据：给出置信区间后，🟡 数值条目可升级或维持。
10. **dequeueBuffer/逐秒 doFrame 序列复算**（D-REP-01c/D-E1-02 ⬜）：trace_v/trace_h 的 RenderThread slice 与逐秒计数，方法已由批10/批09 建立（SQL 模板见过程记录），可直接执行无需新采集。
