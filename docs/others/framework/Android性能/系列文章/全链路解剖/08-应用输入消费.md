## 3. socket 收端注册：fd 进主线程 Looper（机制①第一半）

InputEventReceiver 是应用侧接收输入事件的组件。窗口建立输入通道后，它将通道的文件描述符注册到应用线程的 Looper；通道可读时，Looper 回调接收器读取事件。

## 10. 机制四问

### 10.1 socket 收端：fd 注册与消费循环

- **规则**：InputChannel 的 fd 以 ALOOPER_EVENT_INPUT 注册进主线程 Looper；fd 可读 → Looper 回调 handleEvent → consumeEvents 循环读 InputMessage → 逐条回调 dispatchInputEvent（§3.1/§4.2）。
- **谁设置**：注册在窗口创建链内——ViewRootImpl.setView :1381 new WindowInputEventReceiver（WMS 回传 channel 后）→ 构造器 nativeInit → initialize → setFdEvents → Looper.addFd；removeFd 在 dispose（:102-121/:147-153）。
- **谁执行**：主线程 Looper（epoll）触发回调；消费在主线程栈上同步完成（NativeInputEventReceiver::consumeEvents 全循环）。
- **后果**：一次 Looper 唤醒消费到 socket 读空为止（§4.2 for(;;)）；批量 MOVE 攒下不回调（:792 push_back 后 break），等 CALLBACK_INPUT 或终结事件再取（§4.3）；回执不写则对端 waitQueue 滞留（§2.4/§4.4，批07 衔接）。

### 10.2 ViewPostIme 到 View.dispatchTouchEvent 的窗口查找

- **规则**：ViewPostImeInputStage.processPointerEvent :6757 `mView.dispatchPointerEvent(event)`——mView 是 DecorView；DecorView.dispatchTouchEvent 经 Activity 回调回环到 ViewGroup.dispatchTouchEvent；ViewGroup 对 DOWN 清旧 target、按拦截规则询问 onInterceptTouchEvent，未拦截则从绘制序前端逐 child 扫描，两道门 `canReceivePointerEvents()` ＋ `isTransformedTouchPointInView()`（坐标换算后落在 child 内），命中者成为 TouchTarget 并 `dispatchTransformedTouchEvent` 递归（§7.2）。
- **谁设置**：View 树结构本身（AppList 布局）；mTouchSlop/mGroupFlags 等参数由 ViewConfiguration 与 ViewGroup 缺省值。
- **谁执行**：主线程同栈串行——ViewGroup/View/RecyclerView 的 dispatch 系列方法都在 ViewPostImeInputStage 的 1,578,231 ns slice 内。
- **后果**：坐标不在任何 child 内且自身不消费 → handled=false → FINISH_NOT_HANDLED/FORWARD（:6767）→ 回执 handled=false（批07 侧语义：不回收窗口的 ANR 计时，见其 waitQueue 描述）。命中 RecyclerView 后进入 §8。

### 10.3 scrollByInternal 后 invalidate → 谁请求 vsync

- **规则**：滚动消费后两个失效入口（:1676/:1698）→ invalidate 链上抛至 ViewRootImpl → scheduleTraversals（去重标志 mTraversalScheduled）→ 插同步屏障＋postCallback(CALLBACK_TRAVERSAL) → Choreographer scheduleFrameLocked → scheduleVsyncLocked → scheduleVsync() 向显示侧请求 vsync（§8.2/§8.3）。
- **谁设置**：mTraversalScheduled/mFrameScheduled 两级去重位；CALLBACK_TRAVERSAL 档位由 ViewRootImpl 指定。
- **谁执行**：主线程（invalidate 与 scheduleTraversals 同线程）；vsync 请求经 DisplayEventReceiver 的另一条 socket（本篇不展开，批09）。
- **后果**：同一帧窗口内多次 invalidate 合并成一次遍历（mTraversalScheduled 为真时 :2322 拦截）；vsync 到达前主线程可以再处理输入（输入消息是异步消息可穿屏障，§5.2）——本 trace 中 scheduleVsyncLocked（6,831,246,265）到 onVsync 155812（6,842,036,457）间隔 10.790 ms（批0 复验 §二.5），期间 deliver slice 已结束、主线程 S（6,832,783,072 起）等待 vsync；doFrame 155812 的内部"见批09"。

### 10.4 应用层 VelocityTracker 采样点条件

- **规则**：internal RV 三个采样点（§9.1 表）把收到的每条事件送 addMovement；native 只把 DOWN/POINTER_DOWN/MOVE（含 HOVER 变体）记为样本，UP 类动作就地丢弃（VelocityTracker.cpp:265-293）；合批事件的 history 逐时刻展平入样（:314-323）；40 ms 间隙清策略（:56-62）。
- **谁设置**：采样点调用方是 RecyclerView（AndroidX 对齐行为一致，本树以 internal 版为基准）；策略选择由 obtain 缺省（VELOCITY_TRACKER_STRATEGY_DEFAULT=-1 → native DEFAULT_STRATEGY=LSQ2，VelocityTracker.h:126）＋ `velocitytracker_strategy` 系统属性覆盖（VelocityTracker.java:280-287）。
- **谁执行**：Java 主线程（三采样点都在 ViewPostIme slice 内）；计算在 computeCurrentVelocity 调用时同步完成（:2906）。
- **后果**：松手速度＝最后一条 MOVE 之前样本的最小二乘拟合（策略内部）；样本稀疏或 40 ms 级间隙（契约 :76 的 >25 ms 间隔占 17.5%）使窗口内样本减少或清空——fling 起步速度的品质受报点节奏影响；量级不可测（应用侧样本序列无 trace 记录，盲区，承批05 §10.4）。

### 10.5 主线程醒后到 scheduleVsyncLocked 的时间轴（机制④之外补充第五问）

- **规则**：S 结束 → R（可运行）→ Running → Looper 派发 → onInputEvent（processInputEventForCompatibility slice）→ enqueueInputEvent → doProcessInputEvents → deliverInputEvent slice → 四段 stage slice → View 树 → RV Scroll → invalidate → scheduleVsyncLocked slice → （继续收尾）→ Running 结束转 S 等 vsync。

- **谁执行**：主线程 tid=1909 全程单栈；waker=InputDispatcher tid=1488（批0 复验二，trace 直证）。
- **后果**：见 §11.3 逐段拆解——"醒后 0.241 ms 开始回调"与"本次输入回调总耗时 1.734 ms"是两个不同口径，二者都以实测 slice 端点差给出。

## 12. 与两个问题的关联

**50.928 ms 主线程 Sleeping（00:00:06.779837–00:00:06.830765）**：本篇证明的是 S 的**结束侧**——S 结束后 241.5 μs 内输入回调开始（§11.3 口径一），消费全程 1.73 ms 完成并请求下一帧（§8.3），无任何长阻塞点出现在收端代码路径（§3-§8 全链无 sleep/锁等待调用；InputConsumer::consume 的 WOULD_BLOCK 立即返回）。S 的具体等待条件保持 00 篇 §3.7 盲区；本篇可排除的候选只有一个：**"主线程在 S 期间已在处理输入"不成立**——deliver slice 起点在 S 结束之后 241.5 μs（已证，trace 时序）。
