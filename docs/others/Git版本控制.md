# Git 分支整合与提交迁移

> Git 学习资料，聚焦分支合并、压缩合并、提交迁移与拉取前的工作区处理。命令最终效果应结合当前分支、上游配置与团队评审流程判断。

**Q1: 目标分支没有新提交、功能分支包含多个提交时，怎样把功能分支合入目标分支？**

先切换到目标分支并更新它，再执行 `git merge <功能分支>`。若目标分支是功能分支的祖先，默认 merge 通常只把目标分支指针快进到功能分支，不额外创建合并提交；若想即使可快进也保留一次合并节点，可使用 `git merge --no-ff <功能分支>`。

合并后检查工作区与提交图，再按团队配置推送目标分支。具体代码评审分支引用方式由托管平台约定，不是 Git merge 的通用语法。

**Q2: `git merge`、`--no-ff` 和 `--squash` 会怎样改变历史？**

`git merge` 尽可能快进；若两个分支已分叉，则通常创建有两个父提交的 merge commit。`--no-ff` 即使可以快进也创建 merge commit，保留分支整合节点。`--squash` 把另一分支的合并效果放入工作区和暂存区，但不移动 HEAD，也不记录 MERGE_HEAD，后续需由用户创建一个普通提交。

选择依据是是否要保留源分支的逐条提交与拓扑关系。Squash 适合把一组提交作为单个逻辑改动提交，但之后 Git 不会把它记录成与源分支已完成合并，重复合并时仍需理解两边历史。

**Q3: 两个分支各自有新提交时，merge 和 squash 的结果有什么区别？**

分支已经分叉时，普通 `git merge` 会结合共同祖先与双方改动；成功后默认生成一个记录双方父提交的合并提交。此时 `--no-ff` 通常不再改变结果，因为快进本来就不可能。

`git merge --squash <分支>` 计算合并后的文件树并暂存差异，但不把对方提交接入当前历史；检查后需要自行提交。若发生冲突，先编辑冲突文件并检查暂存差异；普通 merge 用 `git merge --continue` 完成或用 `git merge --abort` 放弃。Squash 结束后则按普通暂存区提交流程处理。

**Q4: `git cherry-pick` 适合什么场景，冲突时怎样完成或放弃？**

Cherry-pick 把指定提交引入的改动应用到当前分支，并通常为该改动创建一个新的提交；它迁移提交效果，不会把源分支的整个合并关系接入目标历史。它适合把单个修复回移到维护分支等需要选择特定提交的场景。

执行前确认当前分支和工作区状态，再用 `git cherry-pick <commit>`。若冲突，解决文件、暂存结果并运行 `git cherry-pick --continue`；要取消当前操作用 `git cherry-pick --abort`。迁移后还要检查是否依赖源分支中未一并迁移的提交。

**Q5: 本地有未提交修改时，运行 `git pull` 前应检查什么？**

`git pull` 先执行 fetch，再按配置用快进、merge 或 rebase 整合远端上游。开始前确认当前分支的上游和整合策略，并检查工作区修改；Git 能保留不重叠的本地修改，但若远端更新与本地修改冲突，整合会失败或需要解决冲突。

重要工作先提交成可恢复的提交；暂时不适合提交时可用 stash 暂存工作区，并在拉取后再恢复。多人协作中还要遵循团队约定的 merge/rebase 策略，避免对已共享提交做未经协调的改写。
