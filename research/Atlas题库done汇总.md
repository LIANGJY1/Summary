### 04-language/C++/02-编译与链接.md（7 题）

**Q2：多文件的 C++ 工程为什么需要头文件？声明在编译和链接阶段各起什么作用？**

C++ 通常按翻译单元独立编译。编译器处理一个 `.cpp` 时不会读取其他 `.cpp`，而是分别生成目标文件，再由链接器解析跨文件的符号引用。头文件提供可共享的声明，使调用方能在编译期检查调用，链接器随后将引用与定义关联。

**Q3：头文件中的 #pragma once 是什么？**

`#pragma once` 是放在头文件中的编译器指令，告诉支持它的编译器：处理同一个翻译单元时，该头文件只需包含一次，避免其中的类型等被重复定义。

**Q5：#include "util.h" 与 #include <util.h> 的搜索范围有何不同，项目头文件应该用哪种？**

两种写法的主要区别是搜索规则：具体搜索位置由实现和构建选项决定。常见编译器会让 `"..."` 先搜索发起包含的文件所在目录，再搜索常规头文件路径。`<...>` 使用常规头文件搜索路径。通常用尖括号包含标准库或外部依赖头文件，用引号包含项目头文件。

**Q6：头文件中的 #ifndef、#define、#endif 有何作用？#pragma once 能否替代？**

这三行构成头文件保护宏（include guard），用于避免同一翻译单元重复处理头文件内容。`#pragma once` 是常见替代写法，但不属于 ISO C++ 标准。

### 01-android/01-architecture/11-SELinux.md（4 题）

**Q1：[tags:SELinux] Android SELinux 是什么？它补上了 Android 哪类访问控制缺口？**

SELinux（Security-Enhanced Linux，安全增强型 Linux）是 Android 基于 Linux LSM（Linux Security Modules）实现的**强制访问控制**机制。它给进程主体标记域、给受保护对象标记类型，再由内核或相应的用户态对象管理器按 `allow 域 类型:类 权限` 规则检查访问。没有匹配授权时默认拒绝。

**Q2：SELinux 的判定机制分哪几步？一次访问是怎么被放行或拒绝的？**

判定机制分三步——建立安全上下文、编译并装载规则、逐次判定：策略在构建与启动阶段准备，进程和对象在创建、标记或查询映射时取得上下文。内核或用户态对象管理器再按访问请求执行判定，没有匹配授权即拒绝。

**Q4：作为上层应用开发者，SELinux 的实际应用场景都是什么？**

应用开发者通常“被 SELinux 约束”而不是配置它：能做的是识别拒绝、改走合规通道，改 sepolicy 不是应用侧的选项。应用无法自行选择域。平台按 seapp_contexts 中的匹配条件确定域，输入不止签名或 targetSdkVersion。

**Q6：一条 avc 日志里 pid、uid、name、scontext、tcontext、permissive 各字段分别由谁拼出？**

每个字段的拼装者分三层：libselinux 的 `avc_audit` 拼模板与上下文段，servicemanager 注册的审计回调拼业务字段，logcat 行首的 tag 与 pid 来自写入进程自身。

### 01-android/08-内存与存储/05-分区与挂载.md（12 题）

**Q1：Android 分区是什么，如何理解？**

Android 分区是设备存储中为特定用途划出的存储区域或逻辑存储空间，用来组织启动文件、系统软件和用户数据等内容。一个设备有多个分区，可以让不同内容分别管理、更新和保护。

**Q2：Android 常见分区各有什么作用？**

Android 将启动、系统软件、厂商适配和用户数据组织到不同分区。分区名称和是否存在取决于设备配置、首次发布时的 Android 版本及升级方案，不能假定每台设备都有以下所有分区。

**Q3：Android 的动态分区是什么？**

动态分区是 Android 的一种分区管理方式：在 `super` 物理分区中划分 system、vendor 等**逻辑分区**，并用元数据记录它们占用的空间。系统可以在允许的容量范围内调整这些逻辑分区，而不必重新划分物理分区表。

**Q4：Android /system/etc 目录是什么？**

/system/etc 是 Android 系统分区的配置文件目录，承担 Unix 传统中 /etc 的角色：init 的 rc 文件、权限 XML、音频策略等出厂配置都在这里。根目录被分区挂载点占满，Android 没有独立的 /etc，配置就随系统分区放在这里。

**Q5：Android 的 super 是什么，解决了什么问题？**

`super` 是 Android 动态分区方案中的物理分区，用来容纳和管理 system、vendor 等逻辑分区。它让这些分区在同一个容器内分配空间，便于系统升级时调整各自的容量。

**Q6：Android 的 super 为什么通常不包含 userdata？**

在常见的 Android 动态分区布局中，`super` 容纳 system、vendor 等系统逻辑分区，`userdata` 通常是独立分区。`/data` 是 userdata 上文件系统的挂载点，不是分区名。

**Q7：Android 的 scratch 是什么，怎样为 OverlayFS 提供可写空间？**

scratch 是 Android 在部分设备上为调试性 OverlayFS 准备的可写工作空间。它解决的问题是：系统分区可能使用只读文件系统，开发时需要临时替换文件，却不能直接向原分区写入。scratch 提供另外一处存储，OverlayFS 再把这处修改与原系统文件合并，让程序仍通过原路径访问。

**Q8：adb remount 的原理是什么？**

adb remount 请求设备端为可调试系统分区准备可写访问，具体可能是直接重新挂载，也可能在只读文件系统上建立 OverlayFS。它不把 EROFS 本身变为可写格式。

**Q9：/dev/block/dm-0 /mnt/scratch f2fs rw 如何解析？**

这行表示当时把设备映射节点 dm-0 提供的 F2FS 文件系统以读写方式挂载到 /mnt/scratch。dm-0 是运行时 device-mapper 编号，不是稳定的物理设备身份；仅凭这一行不能判断其最终后端是否在 super 或数据分区。

**Q10：Android 的 verity 是什么，为什么启用后可能清理 OverlayFS？**

Android 中讨论分区校验时，verity 通常指 **dm-verity**。其中 dm 指 device-mapper（设备映射器），是 Linux 提供的虚拟块设备框架；verity 表示完整性验证。dm-verity 是建立在 device-mapper 上的块设备校验机制，在读取受保护分区的数据时检查其是否与可信的校验信息一致，帮助发现系统分区被篡改或数据损坏。

**Q11：U 盘系统升级后为什么可能再次看到旧文件？**

升级可能更新系统镜像中的 lower，而独立的持久化 upper 未清理；如果之后再次挂载覆盖层，upper 的同路径旧文件可能遮蔽新 lower。U 盘只是升级包的载体，实际写入和擦除范围由升级方案决定。

**Q12：如何确认升级前后的 upper 是否是同一持久化对象？**

需要建立跨时间的设备和文件证据链，不能只比较 /mnt/scratch 路径或 dm 编号。记录每次启动的 boot ID、slot、mountinfo、设备映射和动态分区信息，再比较 upper 文件清单与哈希；任一后端重建、路径变化或采集权限不足都可能改变判断。

**Q1：位图是什么？**

位图用二维像素网格表示图像，每个像素记录颜色及可选的透明度，适合照片和纹理丰富的图像，因为能逐像素保存细节。放大时可能出现明显像素化。位图是一种表示方式，不等同于某种压缩算法。

**Q2：矢量图形是什么？**

矢量图形用点、线、曲线和路径等几何对象及其填充、描边属性描述画面，适合图标、标志和简单线稿，因为可按目标尺寸绘制并保持边缘清晰。照片若用大量几何对象描述，通常不如位图合适。

**Q3：栅格化是什么？**

栅格化（rasterization）是把路径、曲线等矢量图形描述映射为目标尺寸上的像素，用于显示或输出的过程。渲染器据图形覆盖范围确定像素颜色和透明度，抗锯齿可平滑边缘。SVG 或 VectorDrawable 可按新的目标尺寸重新栅格化。位图放大只能插值，不能恢复矢量细节。

### 01-android/14-performance/01-应用/06-图片加载/02-解码与内存.md（6 题）

**Q1：压缩文件很小，为什么解码后仍可能占大量内存？**

压缩文件大小表示编码数据量，不能代表解码后的 Bitmap 内存。像素内存主要由解码输出尺寸和像素配置决定。

**Q2：怎样减少 Bitmap 解码临时缓冲区的重复分配？**

Android 11 的 BitmapFactory.decodeStream 默认使用约 16 KiB 临时缓冲。频繁解码时，可通过 BitmapFactory.Options.inTempStorage 复用该数组，减少小额重复分配。这不会减少 Bitmap 像素内存。

**Q3：Bitmap 复用为什么可能保留较大的分配容量？**

大 Bitmap 被复用来存放较小结果时，当前像素量会减少，但底层分配容量可能不变。对象留在缓存或池中时，这部分容量仍被占用。

堆转储能显示 Bitmap 的 Java 包装对象及其引用链。沿引用链可判断它由界面、缓存还是对象池持有。

**Q5：如何限制或清理过大的 Bitmap 闲置对象？**

为图片缓存和对象池设置字节上限。超限或界面退出时，淘汰可重建且不再使用的 Bitmap。

**Q6：Bitmap 像素数据为什么放在 Native Heap，而不是 Java Heap？**

Android 8.0（API 26）起，普通软件 Bitmap 的 Java 包装对象在 Java 堆，像素缓冲在 Native Heap。这样可避免大块像素数据占用 Java 堆，但只是改变内存归属，进程总内存仍会增加。

### 02-os/01-文件系统/02-文件操作模型.md（5 题）

**Q1：文件描述符 fd 是什么？**

文件描述符（file descriptor，fd）是进程用来引用已打开对象的非负整数，对象可以是普通文件、管道或套接字。内核维护按进程区分的 fd 表；进程把 fd 传给 `read()`、`write()`、`lseek()`、`close()` 等系统调用时，内核在发起调用的进程表中查找对应的打开文件描述。因此，fd 是进程上下文中的编号，不是文件名、文件内容或打开对象本身。

**Q2：标准输入、标准输出和标准错误是什么，怎样重定向？**

标准输入、标准输出和标准错误是程序约定使用的三个输入输出通道。在 POSIX 环境中，它们通常对应文件描述符 0、1、2，让程序通过统一接口读写终端、文件或管道。

**Q3：UNIX 不带缓冲的文件 I/O 是什么？**

“不带缓冲”指 read 和 write 使用文件描述符发出读写请求，不经过 C 标准 I/O 库的流缓冲区。这不意味着没有任何缓冲，也不等于直接 I/O 或数据已经持久化。

**Q4：C 标准 I/O 与文件描述符 I/O 有什么区别？**

C 标准 I/O 使用 `<stdio.h>` 提供的 FILE 流和函数，通常在用户空间缓冲数据，并提供格式化、字符与行处理。POSIX 的 read 和 write 使用文件描述符进行字节传输，不提供同一层自动流缓冲。

**Q8：fcntl() 函数是什么，如何使用？**

`fcntl()` 是 POSIX 文件控制接口，通过文件描述符查询或修改相关属性，也可复制描述符或管理文件锁。它声明在 `<fcntl.h>` 中，语法为 `fcntl(fd, cmd, ...)`：`fd` 是已打开的文件描述符，`cmd` 指定操作，是否需要第三个参数取决于命令。

OverlayFS 是 Linux 的联合文件系统：它把一个或多个下层目录与可选的上层目录组合成一个合并视图，应用通过挂载点访问结果。它提供统一的路径视图，不取代存储设备或底层文件系统。

### 02-os/01-文件系统/07-块设备与存储.md（6 题）

**Q1：块设备是什么？**

块设备是以“块”为单位读写的设备文件：数据按固定大小的块组织，每个块可寻址，支持跳到任意块直接访问。磁盘、固态盘、分区和 loop 设备都是块设备。字符设备则以字节流顺序访问，如键盘和串口。两者的区别集中在访问方式、内核路径和系统里的呈现。

**Q4：如何创建普通文件和设备节点，并检查文件类型？**

普通文件可由 `touch` 或 Shell 重定向创建。设备节点是携带设备号的特殊文件，通常用 `mknod` 创建，创建节点不等于创建设备或驱动。

**Q8：什么是 loop 设备，它怎么把普通文件变成块设备？**

loop 设备是 Linux 提供的虚拟块设备。它把对块设备的读写转发到关联的后备文件或设备，使需要块设备接口的操作可以访问其中的内容。

**Q13：device-mapper 是什么？Android 如何用它访问动态分区？**

device-mapper（设备映射器，简称 dm）是 Linux 内核中的虚拟块设备框架。它根据映射表，在已有块设备之上提供新的块设备；上层读写新设备时，内核按映射规则处理请求，再访问对应的底层设备。

**Q14：PCIe 是什么？**

PCIe（Peripheral Component Interconnect Express，外围组件互连express）是主机与设备间的高速串行点对点总线：NVMe 固态盘、显卡、网卡等挂在它上面，经它与 CPU 和内存交换命令与数据。它决定运力，不决定设备语义。

**Q15：NVMe 是什么？/dev/nvme1n1p4 怎么理解？**

NVMe（Non-Volatile Memory Express，非易失性内存主机控制器接口规范）规定主机与存储控制器怎样交换命令和数据。**NVMe 存储**通常指采用 NVMe 规范供主机访问的存储设备或存储资源，例如通过 PCIe 连接的 NVMe 固态硬盘。NVMe 是接口规范，固态硬盘则是实际提供持久化存储的设备。

### 02-os/03-进程与通信/01-进程与调度.md（3 题）

**Q1：内核有“进程”这个概念吗？内核为什么能运行？**

进程是内核管理的任务，不是内核运行的前提。内核启动初期由 CPU 直接执行特权代码。完成基础初始化后，才创建并调度内核线程和用户进程。

程序是可供执行的指令和数据，进程是程序的一次执行活动，进程映像描述进程运行时的内容和状态。

**Q3：UNIX 进程控制中的 fork、exec 和 waitpid 如何配合？**

进程控制是创建、运行、等待和终止进程等管理操作。执行外部程序的常见路径是父进程用 fork 创建子进程，子进程用 exec 系列替换自身程序映像，父进程用 waitpid 获取子进程状态并回收已终止子进程。

### 02-os/03-进程与通信/03-套接字接口.md（25 题）

**Q1：网络进程间通信是什么？**

网络进程间通信（network IPC）是不同计算机上的进程借助网络交换数据。套接字接口为进程提供统一的通信操作，既能配合网络协议跨机器通信，也能配合本机通信域在同一台机器内通信。

**Q2：通信接口和通信端点有什么区别？**

通信接口是程序请求通信操作的方式，通信端点是参与通信的一端。套接字 API 提供创建、绑定、连接和收发等操作，套接字对象则代表一个具体端点。

**Q3：协议栈是什么，蓝牙协议栈和 TCP/IP 协议栈如何理解？**

协议栈是围绕通信任务协作的分层协议及其实现。每层处理部分通信问题，并与相邻层配合。TCP/IP 协议栈用于 IP 网络通信，蓝牙协议栈用于蓝牙设备通信，二者都不是单一协议。

**Q4：套接字和套接字描述符分别是什么？由谁维护，数量由什么决定？**

套接字是内核维护的通信端点，套接字描述符是进程访问它的整数 fd。对象与编号分属内核和进程两侧，数量随创建与关闭动态变化，受 fd 上限、系统文件表和内存限制。

**Q5：理解和使用套接字需要关注哪些关键点？**

套接字是通信端点，使用时要同时明确地址、交付方式、通信状态和资源生命周期，才能判断数据如何到达对端以及程序何时结束通信。

**Q6：套接字为什么既可以本机通信也可以跨机通信？**

套接字提供统一的通信接口，内核根据创建时选择的通信域，使用相应的地址和通信机制。因此应用使用相似的收发接口，就可以在本机进程之间或跨机器通信。

**Q7：套接字如何标识一个目标通信进程？**

套接字通信通常先用地址定位目标通信端点，再由目标系统把数据交给绑定或关联该端点的套接字及其进程。地址标识的是通信端点，不是进程 ID。

**Q8：POSIX.1 标准是什么，如何理解？**

POSIX（Portable Operating System Interface，可移植操作系统接口）是一组操作系统接口标准。POSIX.1 规定了包括 socket、bind、connect、send 和 shutdown 在内的接口契约，使遵循标准的程序更容易在不同系统间移植。

**Q9：如何创建一个套接字？**

调用 socket 创建一个通信端点。成功时返回文件描述符 fd，供程序操作该端点。失败时返回 -1，并设置 errno。

**Q10：套接字通信域是什么？**

套接字通信域决定端点使用的地址体系及对应协议族。创建套接字时通过 socket 的 domain 参数选择，通信域不单独决定数据是否可靠或保留消息边界。

**Q11：套接字有哪些类型？**

套接字类型决定应用如何收发数据，包括是否面向连接以及是否保留消息边界。类型不能与具体协议画等号，具体支持情况和可靠性还取决于通信域、协议与系统实现。

**Q12：套接字协议是什么？**

套接字协议是通信双方遵循的具体规则，由 socket 的 protocol 参数在通信域和类型允许的范围内选择。例如 IPv4 字节流通常使用 TCP，IPv4 数据报通常使用 UDP。传入 0 请求系统选择该组合的默认协议，组合不受支持时创建会失败。

**Q13：套接字什么时候保留连接或直接 close，何时才需要 shutdown？**

如果这条连接以后既不发送、不接收，也不复用，直接 close(fd)，不需要先 shutdown。shutdown 主要用于还不能关闭整个连接，却要先结束一个收发方向的情况，例如结束发送后继续接收响应。close 释放当前 fd 引用，shutdown 改变套接字的收发方向但不释放 fd，最终仍需 close。

**Q14：接受文件描述符的函数，为什么不一定能用于套接字？**

文件描述符统一了访问入口，没有统一所有对象的能力。判断某个函数能否用于套接字，要看它要求底层对象提供什么语义。

**Q15：套接字的地址结构解析？**

套接字地址包含**地址族**和该族的**定位信息**。地址族决定后面的字段怎样解释，定位信息指出具体端点。程序按地址族创建实际结构，以下代码只摘录关键字段，省略了实现可能添加的填充字段。

**Q16：BSD 网络软件与套接字接口是什么关系？**

BSD 可以理解为一类操作系统的基础，类似你运行应用所依赖的 Linux 系统。BSD（Berkeley Software Distribution，伯克利软件发行版）是加州大学伯克利分发的 Unix 系统软件系列。它最初是对 Unix 的扩展，后来发展出包含内核、系统库和工具的软件系统，FreeBSD 等操作系统源自这一系列。

**Q17：网络配置信息有哪些，存在哪里，应用如何查询？**

网络配置信息是系统和应用用于确定本机网络入口、目的地址和通信路径的数据。它按用途分布在内核运行时状态、本地文件和名称服务中，不是一份固定的文件。

**Q18：主机名、网络名称和网络编号分别标识什么？**

主机名是供人使用的主机名称，网络名称是某个网络的符号名称，网络编号用于表示网络地址或网络部分。名称是映射记录，不能直接等同于实际地址或证明网络可达。

**Q19：网络接口和网卡有什么区别，数据包如何经过它们？**

网卡是连接网络介质的硬件设备，网络接口是操作系统提供的网络收发端点抽象，系统用接口名称、状态和地址等信息管理网络收发。接口可以对应物理网卡，也可以是环回、隧道等虚拟接口，因此不能将接口与实体网卡一一等同。

**Q20：如何将套接字与地址关联？**

bind 的作用是把本地地址关联到已创建的套接字。服务端通常显式绑定稳定的本地入口，客户端一般由系统在连接时选择本地地址和端口，也可在有特定需求时提前绑定。下面的代码片段省略头文件和错误处理。

**Q21：面向连接的套接字如何建立连接？**

面向连接的套接字（`SOCK_STREAM` 或 `SOCK_SEQPACKET`）要先建立两端关系，之后才能交换数据。客户端用 `connect` 发起连接；服务器用监听套接字接入请求，再由 `accept` 取出连接并返回专门收发数据的新套接字。

**Q22：主机、网络、协议和服务数据库分别查什么？**

**Q23：指数退避重试的设计原理是什么？**

指数退避是重试策略：失败后逐次增大重试间隔，让暂时过载或不可用的服务有恢复时间，同时避免客户端紧密重试持续增加负载。它提高恢复机会，但不能保证服务一定恢复。

**Q24：TCP 客户端与服务端的 bind、listen、connect 和 accept 如何协作？**

服务端先建立可发现的监听入口，客户端向该入口发起连接，服务端再从监听队列取得连接。bind 确定本地地址，listen 启用被动接入，connect 指定对端并发起连接，accept 返回用于该连接的新描述符。

### 02-os/04-虚拟化/01-虚拟化.md（9 题）

**Q1：虚拟机和 VMM 是什么，为什么使用虚拟机？**

虚拟机（VM，Virtual Machine）是由虚拟 CPU、内存和设备组成的运行环境，可以运行客体操作系统或其他程序。虚拟机监控程序（VMM，Virtual Machine Monitor）负责创建和管理虚拟机，并协调客体对硬件资源的使用。

**Q2：hypervisor 是什么，与 VMM 有什么区别？**

hypervisor 是管理虚拟机运行的虚拟化层，负责协调客体对 CPU、内存和设备的访问。hypervisor 和 VMM（Virtual Machine Monitor）在广义上常作同义词；在具体实现中，也可能分别指承担不同职责的组件。

**Q3：车机为什么会同时运行 Linux 和 Android，怎样判断双系统是否采用虚拟化？**

采用虚拟化的动机通常是让两套需要独立内核的系统复用一套硬件，同时明确分配 CPU、内存和设备。例如产品可以让 Linux 承载一类设备服务、Android 承载交互界面，但具体分工取决于产品。看到两者并存只能说明有两个软件环境，必须再确认它们是否同时运行、是否共用内核与处理器资源，才能判断是否存在虚拟机。

**Q4：操作系统容器是什么，它与虚拟机的内核有什么区别？**

普通 Linux 容器是运行在同一个 Linux 内核上的一组隔离进程。虚拟机则提供虚拟机器；如果其中运行 Linux、Android 等完整操作系统，该系统会启动自己的内核实例。

**Q5：虚拟化中的 host、guest 与 virtio 前端、后端是什么关系？**

host（宿主侧）是为虚拟机提供资源和设备服务的一侧。guest（客体侧）是运行在虚拟机内的操作系统及应用。对于 virtio 设备，前端通常是 guest 内的设备驱动，后端实现虚拟设备行为，并连接实际资源或其他服务。

**Q6：host 内核与 guest 内核怎样协作运行虚拟机？**

以 Linux 宿主使用 QEMU 和 KVM（Kernel-based Virtual Machine）运行 Linux 虚拟机为例，**guest 内核管理虚拟机内的程序和虚拟设备；host 内核管理宿主资源，并通过 KVM 和硬件虚拟化机制支持 guest 运行**。两者是独立运行的内核实例。

**Q7：QEMU 是什么，怎样模拟和运行客体系统？**

QEMU 是开源的通用**机器模拟器**与**虚拟化工具**，为虚拟机提供 CPU、内存和设备的机器模型，既能启动完整客体操作系统，也能运行单个跨架构程序。它可以用软件动态翻译执行客体指令，也能借助 KVM 等硬件虚拟化加速。

**Q8：KVM 是什么？**

KVM（Kernel-based Virtual Machine）是 Linux 宿主内核中的虚拟化功能，属于内核侧。QEMU 运行在用户态，通过 KVM 使用 CPU 的硬件虚拟化能力，让客体的大部分指令受控地在真实 CPU 上执行。宿主内核仍负责调度和资源管理。

**Q11：virtio 是什么，它怎样让不同虚拟机实现复用设备驱动？**

virtio（Virtual I/O）是一族标准化的虚拟 I/O 设备接口。它规定 guest 驱动与设备之间的协议，让支持同一设备类型和协商能力的实现互通，而不要求照搬某个物理控制器。

### 02-os/05-Linux构建与启动/03-Linux启动.md（11 题）

**Q1：initramfs 的制作和启动流程是什么，哪些步骤可以变化？**

制作流程是准备早期程序及依赖 → 组织文件和路径 → 生成内核支持的归档 → 检查归档 → 交给内核并验证启动。具体程序、压缩方式和加载方式可按环境选择。

**Q2：制作并用 QEMU 启动 initramfs 时，rootfs/ 要准备什么，/init、/dev/console 和 console= 如何配合？**

`rootfs/` 是 initramfs 的打包目录。内核解包后，其内容成为运行时根目录 `/`，并执行其中的 `/init` 作为 PID 1。要让用户态和内核日志都能通过 QEMU 串口显示，还需准备控制台设备节点、匹配的内核参数和 QEMU 串口连接。

**Q5：怎样检查 initramfs 归档是否完整、内容是否正确？**

先验证压缩数据，再检查归档中的路径、权限和设备号。两项检查分别判断数据是否损坏和打包内容是否符合预期。确认入口能否执行还需要启动验证。

**Q6：Linux 中 std::cout 的输出如何到达 QEMU 宿主机终端？**

输出链路从 `std::cout` 写入标准输出开始，经过 `/dev/console`、Linux 控制台和 QEMU 虚拟串口，最后到达宿主终端。要显示日志，init 的标准输出须连接到 `/dev/console`，内核参数须选择对应串口，QEMU 也须把该串口连接到宿主终端。

**Q7：内核怎样为早期 init 建立标准输出？**

内核启动早期 init 前，尝试打开 `/dev/console`，并将其连接到 PID 1 的标准输入、标准输出和标准错误。执行 `/init` 后，程序沿用这些文件描述符。

**Q8：为什么 initramfs 要预置 /dev/console，等 /init 挂好 devtmpfs 不行吗？**

不能等。devtmpfs 要由 `/init` 运行后执行挂载才会生成节点，而内核在启动 `/init` 前就要打开 `/dev/console`，把它接到早期用户态的标准输入、输出和错误——时序上 devtmpfs 帮不上忙，与本内核是否编译 devtmpfs 无关。节点缺失时，这条控制台通路无法按预期建立。

**Q9：QEMU 在前台运行且终端没有提示符、串口空白，能判断 Linux 内核卡住了吗？**

不能。没有提示符只表示宿主 Shell 还在等待前台 QEMU 退出；QEMU 进程存活也不代表客体内核仍在正常执行。串口空白只能说明当前终端没有收到串口字符，无法单独判断是内核没有输出、Linux 没选中串口控制台，还是 QEMU 没把虚拟串口接到终端。

**Q10：已看到 earlycon 内核日志，却没有 /init 输出，说明什么？**

这只说明早期日志通道已经输出成功，不代表正式的 `ttyS0` 串口驱动已注册。`earlycon` 在正式驱动初始化前直接输出内核早期信息。`/init` 的输出则需要正式串口控制台、`/dev/console` 和 QEMU 串口连接组成完整通路。

**Q11：8250 串口数设为 0 时为什么没有 ttyS0，8250.nr_uarts=1 有什么作用？**

`CONFIG_SERIAL_8250_RUNTIME_UARTS=0` 让 8250 驱动启动时注册 0 个串口，因此不会提供正式的 `ttyS0`。这是内核驱动的注册数量设置，不代表 QEMU 没有模拟 COM1。

**Q12：启动日志 Serial: 8250/16550 driver 和 Run /init as init process 各说明到哪一步？**

这两条日志分别标记了串口驱动初始化和内核尝试启动 `/init`，都不能单独证明整条输出链路已经正常。

**Q13：怎么把制作好的 system.img 作为 virtio 磁盘交给 QEMU 启动，命令各参数是什么意思，启动后会发生什么？**

QEMU 在模拟一台完整的电脑，每条参数都是往虚拟机上焊硬件或规定行为：`-m` 插内存条，`-kernel` 与 `-initrd` 绕过硬盘引导、直接把内核和初始内存盘交给这台机器，`-append` 写内核启动参数，`-drive` 焊一块盘片为宿主机 system.img 文件的硬盘，其余参数规定输出与退出行为。

### 02-os/05-Linux构建与启动/02-镜像与产物.md（6 题）

**Q1：镜像是什么？**

镜像是按特定格式保存某个系统、存储对象或运行状态的表示，供加载、恢复或分析。它可以由已有对象复制，也可以从文件和配置直接生成，不一定包含原对象的每个字节。

**Q2：归档是什么，与 tar、zip、gzip、cpio 有什么关系？**

归档把一个或多个文件及相关路径、元数据组织成可保存或传输的数据。压缩则减少数据体积，两者可以配合，也可以分别使用。

**Q6：ISO 镜像是什么，为什么有些可以启动安装程序？**

ISO 镜像通常是包含光盘文件系统内容的镜像文件，可以从已有光盘复制，也可以由文件树和构建工具生成。`.iso` 常用于分发系统安装介质，但扩展名本身不保证镜像可启动。

**Q7：Ubuntu 安装镜像如何启动并安装系统？**

安装镜像先让设备启动安装环境，安装器再把系统部署到用户选择的目标磁盘。具体界面、文件系统和引导程序取决于发行版、版本与安装选项。

**Q8：ext4 system 镜像是什么，如何使用？**

ext4 system 镜像是包含 ext4 文件系统内容的镜像文件，可由构建工具直接生成，不要求先复制一块已有分区。能否直接挂载取决于镜像是否为内核可识别的原始文件系统格式。

**Q9：mkfs.ext4 全解析**

`mkfs.ext4` 在块设备或镜像文件上创建 ext4 文件系统，调用形式为 `mkfs.ext4 [选项] 设备 [块数]`。设备必须是已存在的分区、loop 设备或普通镜像文件。省略块数时文件系统使用整个设备。它是 e2fsprogs 里 mke2fs 的别名，`mke2fs -t ext4 设备` 与 `mkfs.ext4 设备` 等价，调用名只决定默认文件系统类型。

**Q1：UART 串口与 USB 有什么区别，适合什么场景？**

UART（Universal Asynchronous Receiver/Transmitter）是异步串行收发器。USB（Universal Serial Bus）也是串行通信，但使用主机管理的总线协议。两者的连接和使用方式不同。
