### 04-language/C++/02-编译与链接.md（7 题）

**Q2：多文件的 C++ 工程为什么需要头文件？声明在编译和链接阶段各起什么作用？**

C++ 通常按翻译单元独立编译。编译器处理一个 `.cpp` 时不会读取其他 `.cpp`，而是分别生成目标文件，再由链接器解析跨文件的符号引用。头文件提供可共享的声明，使调用方能在编译期检查调用，链接器随后将引用与定义关联。

**Q3：头文件中的 #pragma once 是什么？**

`#pragma once` 是放在头文件中的编译器指令，告诉支持它的编译器：处理同一个翻译单元时，该头文件只需包含一次，避免其中的类型等被重复定义。

**Q5：#include "util.h" 与 #include <util.h> 的搜索范围有何不同，项目头文件应该用哪种？**

两种写法的主要区别是搜索规则：具体搜索位置由实现和构建选项决定。常见编译器会让 `"..."` 先搜索发起包含的文件所在目录，再搜索常规头文件路径。`<...>` 使用常规头文件搜索路径。通常用尖括号包含标准库或外部依赖头文件，用引号包含项目头文件。

**Q6：头文件中的 #ifndef、#define、#endif 有何作用？#pragma once 能否替代？**

这三行构成头文件保护宏（include guard），用于避免同一翻译单元重复处理头文件内容。`#pragma once` 是常见替代写法，但不属于 ISO C++ 标准。

### 01-android/01-architecture/11-SELinux.md（4 题）

**Q1：[tags:SELinux] Android SELinux 是什么？它补上了 Android 哪类访问控制缺口？**

SELinux（Security-Enhanced Linux，安全增强型 Linux）是 Android 基于 Linux LSM（Linux Security Modules）实现的**强制访问控制**机制。它给进程主体标记域、给受保护对象标记类型，再由内核或相应的用户态对象管理器按 `allow 域 类型:类 权限` 规则检查访问。没有匹配授权时默认拒绝。

**Q2：SELinux 的判定机制分哪几步？一次访问是怎么被放行或拒绝的？**

判定机制分三步——建立安全上下文、编译并装载规则、逐次判定：策略在构建与启动阶段准备，进程和对象在创建、标记或查询映射时取得上下文。内核或用户态对象管理器再按访问请求执行判定，没有匹配授权即拒绝。

**Q4：作为上层应用开发者，SELinux 的实际应用场景都是什么？**

应用开发者通常“被 SELinux 约束”而不是配置它：能做的是识别拒绝、改走合规通道，改 sepolicy 不是应用侧的选项。应用无法自行选择域。平台按 seapp_contexts 中的匹配条件确定域，输入不止签名或 targetSdkVersion。

**Q6：一条 avc 日志里 pid、uid、name、scontext、tcontext、permissive 各字段分别由谁拼出？**

每个字段的拼装者分三层：libselinux 的 `avc_audit` 拼模板与上下文段，servicemanager 注册的审计回调拼业务字段，logcat 行首的 tag 与 pid 来自写入进程自身。

### 01-android/07-内存与存储/05-分区与挂载.md（12 题）

**Q1：Android 分区是什么，如何理解？**

Android 分区是设备存储中为特定用途划出的存储区域或逻辑存储空间，用来组织启动文件、系统软件和用户数据等内容。一个设备有多个分区，可以让不同内容分别管理、更新和保护。

**Q2：Android 常见分区各有什么作用？**

Android 将启动、系统软件、厂商适配和用户数据组织到不同分区。分区名称和是否存在取决于设备配置、首次发布时的 Android 版本及升级方案，不能假定每台设备都有以下所有分区。

**Q3：Android 的动态分区是什么？**

动态分区是 Android 的一种分区管理方式：在 `super` 物理分区中划分 system、vendor 等**逻辑分区**，并用元数据记录它们占用的空间。系统可以在允许的容量范围内调整这些逻辑分区，而不必重新划分物理分区表。

**Q4：Android /system/etc 目录是什么？**

/system/etc 是 Android 系统分区的配置文件目录，承担 Unix 传统中 /etc 的角色：init 的 rc 文件、权限 XML、音频策略等出厂配置都在这里。根目录被分区挂载点占满，Android 没有独立的 /etc，配置就随系统分区放在这里。

**Q5：Android 的 super 是什么，解决了什么问题？**

`super` 是 Android 动态分区方案中的物理分区，用来容纳和管理 system、vendor 等逻辑分区。它让这些分区在同一个容器内分配空间，便于系统升级时调整各自的容量。

**Q6：Android 的 super 为什么通常不包含 userdata？**

在常见的 Android 动态分区布局中，`super` 容纳 system、vendor 等系统逻辑分区，`userdata` 通常是独立分区。`/data` 是 userdata 上文件系统的挂载点，不是分区名。

**Q7：Android 的 scratch 是什么，怎样为 OverlayFS 提供可写空间？**

scratch 是 Android 在部分设备上为调试性 OverlayFS 准备的可写工作空间。它解决的问题是：系统分区可能使用只读文件系统，开发时需要临时替换文件，却不能直接向原分区写入。scratch 提供另外一处存储，OverlayFS 再把这处修改与原系统文件合并，让程序仍通过原路径访问。

**Q8：adb remount 的原理是什么？**

adb remount 请求设备端为可调试系统分区准备可写访问，具体可能是直接重新挂载，也可能在只读文件系统上建立 OverlayFS。它不把 EROFS 本身变为可写格式。

**Q9：/dev/block/dm-0 /mnt/scratch f2fs rw 如何解析？**

这行表示当时把设备映射节点 dm-0 提供的 F2FS 文件系统以读写方式挂载到 /mnt/scratch。dm-0 是运行时 device-mapper 编号，不是稳定的物理设备身份；仅凭这一行不能判断其最终后端是否在 super 或数据分区。

**Q10：Android 的 verity 是什么，为什么启用后可能清理 OverlayFS？**

Android 中讨论分区校验时，verity 通常指 **dm-verity**。其中 dm 指 device-mapper（设备映射器），是 Linux 提供的虚拟块设备框架；verity 表示完整性验证。dm-verity 是建立在 device-mapper 上的块设备校验机制，在读取受保护分区的数据时检查其是否与可信的校验信息一致，帮助发现系统分区被篡改或数据损坏。

**Q11：U 盘系统升级后为什么可能再次看到旧文件？**

升级可能更新系统镜像中的 lower，而独立的持久化 upper 未清理；如果之后再次挂载覆盖层，upper 的同路径旧文件可能遮蔽新 lower。U 盘只是升级包的载体，实际写入和擦除范围由升级方案决定。

**Q12：如何确认升级前后的 upper 是否是同一持久化对象？**

需要建立跨时间的设备和文件证据链，不能只比较 /mnt/scratch 路径或 dm 编号。记录每次启动的 boot ID、slot、mountinfo、设备映射和动态分区信息，再比较 upper 文件清单与哈希；任一后端重建、路径变化或采集权限不足都可能改变判断。

**Q1：位图是什么？**

位图用二维像素网格表示图像，每个像素记录颜色及可选的透明度，适合照片和纹理丰富的图像，因为能逐像素保存细节。放大时可能出现明显像素化。位图是一种表示方式，不等同于某种压缩算法。

**Q2：矢量图形是什么？**

矢量图形用点、线、曲线和路径等几何对象及其填充、描边属性描述画面，适合图标、标志和简单线稿，因为可按目标尺寸绘制并保持边缘清晰。照片若用大量几何对象描述，通常不如位图合适。

**Q3：栅格化是什么？**

栅格化（rasterization）是把路径、曲线等矢量图形描述映射为目标尺寸上的像素，用于显示或输出的过程。渲染器据图形覆盖范围确定像素颜色和透明度，抗锯齿可平滑边缘。SVG 或 VectorDrawable 可按新的目标尺寸重新栅格化。位图放大只能插值，不能恢复矢量细节。

### 01-android/13-performance/01-应用/06-图片加载/02-解码与内存.md（6 题）

**Q1：压缩文件很小，为什么解码后仍可能占大量内存？**

压缩文件大小表示编码数据量，不能代表解码后的 Bitmap 内存。像素内存主要由解码输出尺寸和像素配置决定。

**Q2：怎样减少 Bitmap 解码临时缓冲区的重复分配？**

Android 11 的 BitmapFactory.decodeStream 默认使用约 16 KiB 临时缓冲。频繁解码时，可通过 BitmapFactory.Options.inTempStorage 复用该数组，减少小额重复分配。这不会减少 Bitmap 像素内存。

**Q3：Bitmap 复用为什么可能保留较大的分配容量？**

大 Bitmap 被复用来存放较小结果时，当前像素量会减少，但底层分配容量可能不变。对象留在缓存或池中时，这部分容量仍被占用。

**Q4：Android Studio Memory Profiler 怎样判断 Bitmap 由谁持有？**

堆转储能显示 Bitmap 的 Java 包装对象及其引用链。沿引用链可判断它由界面、缓存还是对象池持有。

**Q5：如何限制或清理过大的 Bitmap 闲置对象？**

为图片缓存和对象池设置字节上限。超限或界面退出时，淘汰可重建且不再使用的 Bitmap。

**Q6：Bitmap 像素数据为什么放在 Native Heap，而不是 Java Heap？**

Android 8.0（API 26）起，普通软件 Bitmap 的 Java 包装对象在 Java 堆，像素缓冲在 Native Heap。这样可避免大块像素数据占用 Java 堆，但只是改变内存归属，进程总内存仍会增加。

### 02-os/05-Linux启动/01-Linux启动.md（14 题）

**Q1：制作并用 QEMU 启动 initramfs 时，rootfs/ 要准备什么，/init、/dev/console 和 console= 如何配合？**

`rootfs/` 是 initramfs 的打包目录。内核解包后，其内容成为运行时根目录 `/`，并执行其中的 `/init` 作为 PID 1。要让用户态和内核日志都能通过 QEMU 串口显示，还需准备控制台设备节点、匹配的内核参数和 QEMU 串口连接。

**Q2：Linux 中 std::cout 的输出如何到达 QEMU 宿主机终端？**

输出链路从 `std::cout` 写入标准输出开始，经过 `/dev/console`、Linux 控制台和 QEMU 虚拟串口，最后到达宿主终端。要显示日志，init 的标准输出须连接到 `/dev/console`，内核参数须选择对应串口，QEMU 也须把该串口连接到宿主终端。

**Q3：为什么 initramfs 要预置 /dev/console，等 /init 挂好 devtmpfs 不行吗？**

不能等。devtmpfs 要由 `/init` 运行后执行挂载才会生成节点，而内核在启动 `/init` 前就要打开 `/dev/console`，把它接到早期用户态的标准输入、输出和错误——时序上 devtmpfs 帮不上忙，与本内核是否编译 devtmpfs 无关。节点缺失时，这条控制台通路无法按预期建立。

**Q4：如何用 find、cpio 和 gzip 打包并检查 initramfs？**

`rootfs/` 是主机上的目录，内核启动时拿到的是 initramfs 镜像数据，不能直接遍历这个目录。因此使用 `cpio` 将文件路径和元数据编码成归档。`newc` 是内核支持的归档格式，能记录权限和设备节点等信息。内核据此还原初始根文件系统。`gzip` 用来减小镜像体积。打包后检查压缩流并列出归档内容，可提前发现损坏或漏文件，不必解包。

**Q6：QEMU 在前台运行且终端没有提示符、串口空白，能判断 Linux 内核卡住了吗？**

不能。没有提示符只表示宿主 Shell 还在等待前台 QEMU 退出；QEMU 进程存活也不代表客体内核仍在正常执行。串口空白只能说明当前终端没有收到串口字符，无法单独判断是内核没有输出、Linux 没选中串口控制台，还是 QEMU 没把虚拟串口接到终端。

**Q7：已看到 earlycon 内核日志，却没有 /init 输出，说明什么？**

这只说明早期日志通道已经输出成功，不代表正式的 `ttyS0` 串口驱动已注册。`earlycon` 在正式驱动初始化前直接输出内核早期信息。`/init` 的输出则需要正式串口控制台、`/dev/console` 和 QEMU 串口连接组成完整通路。

**Q8：8250 串口数设为 0 时为什么没有 ttyS0，8250.nr_uarts=1 有什么作用？**

`CONFIG_SERIAL_8250_RUNTIME_UARTS=0` 让 8250 驱动启动时注册 0 个串口，因此不会提供正式的 `ttyS0`。这是内核驱动的注册数量设置，不代表 QEMU 没有模拟 COM1。

**Q9：启动日志 Serial: 8250/16550 driver 和 Run /init as init process 各说明到哪一步？**

这两条日志分别标记了串口驱动初始化和内核尝试启动 `/init`，都不能单独证明整条输出链路已经正常。

**Q10：Linux 中文件描述符 1 为什么不固定指向屏幕，Mini_Android 的 /init 又如何获得标准输出？**

文件描述符 `1` 是进程打开对象清单中的编号，按约定承担标准输出的作用。它指向哪里，由启动程序的一方安排，可以是终端、文件或管道。

**Q11：如何创建普通文件和设备节点？**

`touch` 可创建空普通文件，shell 重定向可创建并写入内容，设备节点则用 `mknod` 创建。设备节点是文件系统中的特殊文件，不存放普通文件数据，也不等于设备本身。

### 02-os/01-文件系统/01-文件与目录.md（5 题）

**Q1：块设备是什么？**

块设备是以“块”为单位读写的设备文件：数据按固定大小的块组织，每个块可寻址，支持跳到任意块直接访问。磁盘、固态盘、分区和 loop 设备都是块设备。字符设备则以字节流顺序访问，如键盘和串口。两者的区别集中在访问方式、内核路径和系统里的呈现。

**Q3：NVMe 是什么？/dev/nvme1n1p4 怎么理解？**

NVMe（Non-Volatile Memory Express，非易失性内存主机控制器接口规范）规定主机与存储控制器怎样交换命令和数据。**NVMe 存储**通常指采用 NVMe 规范供主机访问的存储设备或存储资源，例如通过 PCIe 连接的 NVMe 固态硬盘。NVMe 是接口规范，固态硬盘则是实际提供持久化存储的设备。

**Q4：PCIe 是什么？**

PCIe（Peripheral Component Interconnect Express，外围组件互连express）是主机与设备间的高速串行点对点总线：NVMe 固态盘、显卡、网卡等挂在它上面，经它与 CPU 和内存交换命令与数据。它决定运力，不决定设备语义。

**Q12：什么是 loop 设备，它怎么把普通文件变成块设备？**

loop 设备是 Linux 提供的虚拟块设备：背后没有物理磁盘，而是把一个普通文件当作“盘体”，让这个文件以块设备的身份被访问。挂载镜像、把镜像交给虚拟机，都是先把镜像文件关联到某个 /dev/loopN，再按块设备使用。

**Q23：device-mapper 是什么？Android 如何用它访问动态分区？**

device-mapper（设备映射器，简称 dm）是 Linux 内核中的虚拟块设备框架。它根据映射表，在已有块设备之上提供新的块设备；上层读写新设备时，内核按映射规则处理请求，再访问对应的底层设备。

### 02-os/01-文件系统/02-文件操作模型.md（1 题）

**Q1：文件描述符 fd 是什么？**

文件描述符（file descriptor，fd）是进程用来引用已打开对象的非负整数，对象可以是普通文件、管道或套接字。内核维护按进程区分的 fd 表；进程把 fd 传给 `read()`、`write()`、`lseek()`、`close()` 等系统调用时，内核在发起调用的进程表中查找对应的打开文件描述。因此，fd 是进程上下文中的编号，不是文件名、文件内容或打开对象本身。

### 02-os/01-文件系统/05-VFS与挂载.md（5 题）

**Q1：文件系统实例是什么？为什么需要挂载才能按路径访问？**

文件系统实例是内核管理的一套具体文件系统。例如，ext4 是文件系统类型，某个分区上的 ext4 文件系统是具体实例。**挂载**将实例的根目录接入进程可见的目录树，使应用能从挂载点按路径访问其中的文件。

**Q2：VFS 是什么，解决了什么问题？**

VFS（Virtual File System，虚拟文件系统）是内核中的文件系统抽象层。它的主要目的是**统一文件访问接口，并让不同文件系统接入同一目录树**：应用使用 open、read、write 等接口，内核再将操作交给对应的文件系统实现。

**Q3：通用 Linux 的 fstab 是什么，系统怎样使用它？**

fstab 是 file system table（文件系统表）的缩写。通用 Linux 使用 `/etc/fstab` 保存文件系统的挂载配置：每条配置说明一个文件系统从哪里来、挂载到哪个目录，以及如何挂载。这样，系统启动时就可以根据预先写好的配置安排挂载，不必每次都由用户手动指定。

**Q4：OverlayFS 是什么？如何合并目录，以及处理读写和删除？**

OverlayFS 是 Linux 的联合文件系统：它把一个或多个下层目录与可选的上层目录组合成一个合并视图，应用通过挂载点访问结果。它提供统一的路径视图，不取代存储设备或底层文件系统。

**Q5：OverlayFS 中的upper重启后还会生效吗？如何恢复？**

**可能会。**如果通过 `adb remount` 建立了 OverlayFS，再用 `adb push` 替换系统 APK，测试版通常保存在 upper，原 APK 仍在 lower。upper 的后端未被清理且数据已持久化时，重启后文件可能保留；只有对应覆盖层重新挂载，上层文件才会再次遮蔽原 APK。

面向连接的套接字（`SOCK_STREAM` 或 `SOCK_SEQPACKET`）要先建立两端关系，之后才能交换数据。客户端用 `connect` 发起连接；服务器用监听套接字接入请求，再由 `accept` 取出连接并返回专门收发数据的新套接字。

### 02-os/04-virtualization/01-虚拟化.md（3 题）

**Q1：虚拟机和虚拟机监控程序有什么区别，VMM 的两种类型如何划分？**

虚拟机（VM，Virtual Machine）是由虚拟 CPU、内存和设备组成的运行环境，可以在其中运行客体操作系统及应用。虚拟机监控程序（VMM，Virtual Machine Monitor）是创建和运行虚拟机的管理软件，负责协调虚拟资源、执行客体并处理或委托设备访问。虚拟机是客体使用的环境，VMM 是提供和管理这个环境的组件。

**Q2：hypervisor 是什么，与 VMM 有什么区别？**

hypervisor（虚拟机监控程序）是管理虚拟机运行的虚拟化层，负责让多个客体系统共享物理资源，并约束它们对 CPU、内存和设备的访问。它提供客体运行所需的隔离与仲裁机制，让每个客体看到分配给自己的虚拟机器。

**Q3：车机为什么会同时运行 Linux 和 Android，怎样判断双系统是否采用虚拟化？**

采用虚拟化的动机通常是让两套需要独立内核的系统复用一套硬件，同时明确分配 CPU、内存和设备。例如产品可以让 Linux 承载一类设备服务、Android 承载交互界面，但具体分工取决于产品。看到两者并存只能说明有两个软件环境，必须再确认它们是否同时运行、是否共用内核与处理器资源，才能判断是否存在虚拟机。
