# 架构文档模板（SKILL.md §5 动笔前必读）

落盘文档的完整骨架。按实际裁剪：小项目可合并节，但 **①头锚点、③图、⑦开放问题三节不可省**。

````md
# <项目名> 架构解码

> 源码锚点：commit `<hash>`（<分支/标签>）｜ 生成：<YYYY-MM-DD> ｜ 范围：<全项目/子系统>
> 文档有效性以锚点 commit 为准；上游演进后重跑本 skill 走增量更新。

## 1. 一图流

<Mermaid 代码块（```mermaid graph TB …）：5-12 个**概念节点**（是"概念"不是"函数"），
主链加粗；图型选择、语法军规、生成前检查一律按 `references/diagram-guide.md`（单一事实源）。
节点是压缩后的心智模型，塞不下就说明还没压缩够。每张图开头一行写明"本图回答什么问题"。>

## 2. 快速上手阅读路径

<给三个月后的自己/新同事的文件阅读顺序，每步一个问题。通常 5-10 步：>
1. `path/to/Entry.java` —— 请求从哪进来？（看到什么算懂：能指出分发到第一个模块的行）
2. ……

## 3. 分层与模块地图

<表格：模块 | 一行职责 | 依赖谁 | 被谁依赖。分层验证（SKILL.md §2.2）发现的
意外依赖方向在此注明 ⚠。>

## 4. 主链路

<按 §2.1 追踪的一条典型场景，箭头化：A → B → C，每段一行说明阶段职责，
file:line 锚定入口与交接点。>

## 5. 模块卡片

<核心模块，每张卡：职责 / 对外接口 / 关键协作 / 设计动机 / 雷区。
动机分档标注：无标记=代码可证；`[inferred]`=推断；引 commit=考据。>

## 6. 核心类深卡片

<按 class-card.md 模板，只放核心类。>

## 7. 全类职责表

<公共类全覆盖：类 | 一行职责 | 关键协作。跳过清单（生成物/DTO/测试）附理由，
报覆盖率实数。大项目此节可指向拆分文件。>

## 8. 看着糟但其实没问题

<考虑过要标"问题/坏味道"但判定为合理的设计，及理由。**此节为空 = 没看够**。
小项目允许写"本轮范围小，未遇到"。>

## 9. 开放问题

<[inferred] 汇总 + 需人确认的点 + 本轮未深挖的范围。诚实清单，防装懂。>
````

## 图规范

**语法、图型选择、校验流程的单一事实源是 `references/diagram-guide.md`**，此处只保留文档结构相关的两条：

- 每张图开头一行写明"回答什么问题、不包含什么"；说不清的关系说明还没理解——标 `[inferred]` 或删。
- 隐藏耦合（Reflexion absent 档，SKILL.md §2.2）在图上 ⚠ 标注或单独成节，不混进正常依赖里。

## 增量更新标记

对照旧文档逐节标注（放各节标题行尾）：

- `（NEW）` 本轮新增节/卡片
- `（CHANGED 2026-09-06：一句话改了什么）` 结论被修正
- 无标记 = UNCHANGED，正文不动

整节被推翻时保留旧结论一行 `旧判（已修正）：…`，不静默删除——理解的时间线由文档自己记录。
