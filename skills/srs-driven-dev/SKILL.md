# SRS-Driven Dev（条目驱动：需求→落盘→审查→方案→开发）

## Overview

两条锚：①**需求条目是唯一工作单元**——用户给一条、澄清一条、落盘一条，聊过的结论绝不停留在聊天里；
②**未确定的需求用唯一落点隔离**——每个 TBD 在代码方案里对应一个配置项或 stub，需求定一条落地一条，变动只动局部。

## When to Use

- 用户将逐条提供需求（SRS 表格/条目），要求讨论、澄清、结论落盘
- 需求未全部确定但要求先出全局代码方案、分阶段开发
- 条目收齐后需要交叉审查（条目结论 vs 规则矩阵/竞合表的矛盾）
- 已有工作区，新条目继续按既定格式追加

**When NOT to use**：一次性小需求（直接做）；只要规格发布到 tracker（to-spec）；纯头脑风暴无落盘诉求（grill-with-docs）。

## 工作区（首次创建）

用户给出落盘目录后，运行 `bash <skill目录>/scripts/scaffold.sh <目录> <特性名>` 生成骨架：

| 文件 | 唯一职责（单一事实源，禁止跨文件重复定义） |
|---|---|
| README.md | 文档索引＋维护规则 |
| 01-需求规格.md | 全局登记表：事实 F／决策 D／全局规则 G／术语表／接口清单／条目目录 |
| 02-规则矩阵.md | 冲突/竞合规则唯一权威（若有；未定稿则文头标"整体 TBD"） |
| 03-条目档案.md | 每条需求：状态行＋事实＋问答＋开放点；文末「跨条目开放点」 |
| 04-代码方案.md | 分层架构＋不确定点隔离表＋落地阶段 |

**完成判据**：目录含上述 5 文件，各文件头有职责声明；01 的 F/D/G 表已建空表。

## 逐条澄清循环（核心流程）

用户发来一条需求原文后：

1. **建档**：在 03 追加该条目，先只写状态行"🔶 讨论中"。
2. **代查事实**：条目里的信号名/通路/接口先自己去代码库核实（grep 平台库），**查得到的绝不问用户**；查不到的列为待定项。
3. **提澄清问题**：只提"答案会改变设计"的问题，每题附推荐答案（⭐用户习惯简短答复"按推荐/记课题/忽略"，推荐必须具体到可选方案）；问题覆盖：数据模型、触发/中断/恢复语义、异常兜底、与规则矩阵的矛盾点、外部依赖。
4. **固化**：用户答复后写入该条目——**事实**（2~4 行，挂全局 F 编号）＋**问答**（有序列表，答案另起一行以 `QA:` 开头）＋**开放点**（TBD/TD/DEP 挂本条目下，已解决划线留痕）。原文表格不保留，其信息全部并入事实与问答。
5. **同步**：新 F/D/G 进 01 对应表；开放点变化同步 03；版本与日志在 01 文头/附录登记。

**完成判据**：该条目状态变 ✅，其原文信息可在事实或 QA 中全部找到；01 与 03 无内容重复（只有编号引用）。

## 登记制度

- F（事实）/D（决策）/G（全局规则）全局单调递增，**永不重排、永不复用编号**；推翻旧结论＝新增条目注明"取代 Fx"。
- TBD（需求待定）/TD（课题）/DEP（外部依赖）编号同理；裁决后划线留痕并注明日期与结论。
- 每类内容只有一个定义处；他处引用只给编号或链接。

## 交叉审查（条目收齐后触发）

逐格核对"全部条目结论 × 规则矩阵"，另做场景推演。产出问题清单按 **高（架构级缺口/线上挂死）/中（职责缺口）/低（澄清级）** 分级，每条附建议；用户裁决后回填条目与矩阵修订记录。

**完成判据**：报告落盘（可并入 04 附录）；每条问题有裁决与去向（修复/挂起/关闭）。

## 全局代码方案（04）

固定骨架，不确定点全部进隔离表：

- **三层架构**：信号源层（只采集，只发语义沿，回调统一切主线程）→ 核心层（状态机＋可整体替换的规则表）→ 执行层（桥＋播放器）。
- **隔离表**：每个 TBD/TD/DEP ↔ 唯一代码落点（Config 常量或 stub Source），需求敲定＝改配置/换 stub。
- **落地阶段表**：每阶段＝一次可验证交付，标确定度、验收标准、外部前置；先 Fake 桥自验再联调。

**完成判据**：隔离表覆盖 03 全部活跃开放点；每阶段验收标准可离线判定。

## 方案审查镜头（方案成稿后逐项过）

1. **每上电/每会话一次**的标记：锚定真实上电周期（BootEpoch），与进程重启解耦？
2. **一切跨进程等待**有超时出口（回调看门狗），不会挂死？
3. **外部联定义物**（协议码表/资源包）入了隔离表并标为阶段前置？
4. 信号源层做**沿提取**（阈值/状态变化才发事件），连续量不冲击事件流？
5. 失败重试有落点；资源归属有人认领；对外链路双向（入口＋回传）都定义了？
6. 宿主生命周期（Activity 重建/挂载时序/重绑幂等）有契约？

**完成判据**：六问各有明确答案或列入开放点；修复回填后方案版本号递增并在 01 日志登记。

## Quick Reference

| 情况 | 动作 |
|---|---|
| 用户发新需求条目 | 建档→代查→提问（带推荐）→等答复 |
| 用户答复"按推荐/记课题/忽略" | 固化结论/登记 TBD/TD/关闭该问 |
| 条目收齐 | 交叉审查（分级→裁决→回填） |
| 要开工但需求未全定 | 出 04 方案（隔离表＋阶段表），按确定度排序开工 |
| 需求变动 | 先改 03（必要时 01）→只动对应 Source/Config/规则行→同步开放点 |
| 文档变多/重复 | 回归单一事实源：合并、职责重划、编号引用 |

## Common Mistakes

- ❌ 用户还没给需求就自拟问题清单 → ✅ 等条目到了再针对该条提问
- ❌ 存档保留原文大表＋长篇推演 → ✅ 事实 2~4 行＋QA 一问一行结论
- ❌ 问答写成表格或答案不换行 → ✅ 有序列表，答案另起一行 `QA: ` 开头
- ❌ 开放点堆在文末大表 → ✅ 按需求 ID 归属到条目下，仅跨条目项收文末
- ❌ 同一规则在多个文档重复定义 → ✅ 单一定义处＋编号引用
- ❌ 代码里查得到的东西去问用户 → ✅ 先 grep 平台库，查不到才列待定
- ❌ 把未定稿的规则矩阵当权威 → ✅ 文头标"整体 TBD"，代码按可替换规则表实现
