# 会话知识沉淀

## Overview

把会话结论变成脱离原对话仍能检索和复用的知识资产。核心顺序是：**先判产品 profile，再按知识主题路由，再过证据与价值门，最后在用户授权后写入并验证**。用户说“都记下”不等于保存流水账、凭据或未经验证的推断。

## 适用边界

- 普通摘要（未要求持久化）只回复，不写文件。
- 可重复执行的流程、提示词或代理协议走 `session-to-skill`；陈述性事实、机制、坑和权衡走本 skill。
- 源码阅读/注释任务的源码与库级沉淀走 `source-annotator`；本 skill 只接收其中明确分出的跨库知识候选。
- 下一位 agent 续做的上下文走 `handoff`。
- 固定知识库：`/home/liang/Project/MyProject/Summary/project/knowledge-base/`。路径不存在、不可读或无法唯一确认时停止并询问，不静默创建替代库。

## 两种落盘 profile

先按知识内核选择 profile；不要按会话顺序或用户发言顺序建“会话总结.md”。

| Profile | 落点 | 质量门 | 形态与校验 |
|---|---|---|---|
| `knowledge-entry` | 根目录条目型大类 | 每条必须通过复习者测试、证据可追溯、无敏感信息 | 服从目标大类 `边界/规则`；通常为扁平 `##` 条目；用 `check_kb.py --profile entry` |
| `language-note` | `language/` 及语言子目录 | 服从 `language/README.md` 边界；仍须事实可核验、脱敏、冷可读 | 示例驱动散文；不套五段式、不强制复习者测试；用 `check_kb.py --profile language` 检查链接 |

`≤3 条` 已废止：本 skill 不设单次候选或落盘数量上限。数量不替代质量门；候选越多，仍须逐条给出复习场景、路由、动作和依据。

## 权威文件与职责

动笔前读取：

1. `project/knowledge-base/CONTEXT.md`：术语、profile、生命周期关系。
2. `project/knowledge-base/ROUTING.md`：按主题决定候选大类的唯一路由表。
3. 目标大类或 `language/README.md`：收/不收边界、条目格式和归并规则。

路由按知识主题唯一决定落点；表中的维护者是责任/复核标记，不是另立近义大类的理由，也不阻断共享写入协议。所有直接写入 knowledge-base 的 skill 都必须使用同一校验器并报告结果。

## 流程

### 1. 锁定主旨与输入边界

从用户当前请求或会话上下文提取一句话主旨；已有清晰主旨时直接使用，不重复追问。只有主旨缺失、范围会改变落盘结果或用户指定范围互相矛盾时才提问。

同时记录范围：当前会话、用户指定主题/文件、是否允许修改已有条目。保留工作树已有未提交修改，不清理、不覆盖、不回滚。

**完成判据**：主旨、范围和持久化意图各有明确文字；若会话没有可沉淀内容，明确报告 0 条并结束。

### 2. 证据盘点与脱敏

只读检查会话中的代码、命令输出、文档和版本信息；缺失来源不补写。给每个事实标证据等级：

- `observed`：直接看到的代码/输出/复现结果。
- `verified`：由两个独立证据或可重复命令交叉确认。
- `inferred`：基于现有证据的推断，必须显式标注“未验证/推断”。
- `external`：外部资料观点；只有与本地事实核对后才可采用，并保留来源。

扫描候选、依据、正文和汇报：密钥、token、密码、个人信息、内网地址、私有链接及可重建片段一律删除或替换为 `[已脱敏：类型]`。疑似秘密不引用原文；脱敏后仍无法安全表达的候选拒收。

**完成判据**：每个候选都有来源位置或明确“未验证”；敏感扫描完成；没有把环境偶然状态伪装成跨项目知识。

### 3. 原子化、profile 化、按主题路由

把主旨拆成最小独立命题，每条只回答一个可复习问题。对每条依次执行：

1. 通过“换项目仍成立”与复习者测试（`language-note` 改用其 README 边界）。
2. 查 `ROUTING.md`，按知识内核选择唯一候选大类；语言本身优先进入 `language/`，业务/项目操作不要因示例使用某语言而进入语言域。
3. 读取目标文件的 `边界` 与 `规则`，决定收、并入、修订或拒收。
4. 查标题、同义命题和相邻条目；相同知识并入，不复制两份。

候选清单必须完整展示真实动作，而不是只写“新增”：

```text
1. profile=knowledge-entry | 目标=android-ui.md
   命题：构造期消费的配置不会被运行期 setter 自动重新消费
   复习场景：改了组件属性但 UI 不变时
   依据：<文件路径/命令输出> | 动作：并入「构造期配置与运行期 API 存在断层」
2. profile=language-note | 目标=language/kotlin/03-函数式与并发.md
   命题：<语言机制命题> | 复习场景：<具体编程问题>
   依据：<最小可运行示例> | 动作：追加章节
```

**完成判据**：每条都有 profile、唯一目标、完整命题、复习场景、依据和动作；未通过价值门的内容单列拒收原因。

### 4. 授权与冲突裁决

默认先展示候选清单，用户逐条确认或整体确认后再写。用户明确说“直接写”只可跳过候选清单确认，不能跳过价值门、脱敏、路由、冲突裁决或校验。

冲突先分类：

- **补充/收窄适用条件**：并入或就地修订，并保留旧证据；不强制写日期，时间线交给 git。
- **结论反转**：必须得到该条冲突的明确裁决；确认后新条目声明 `supersedes` 旧条目，旧正文保留并在标题后或紧邻状态行标明“已被替代”。
- **无法判定**：暂不写入，列为开放问题。

不使用含糊的“两者并存”默认动作。若确实需要保留两套结论，必须写出互斥适用条件、各自证据和检索入口，并由用户明确确认。

**完成判据**：每个会落盘动作有授权；每个冲突有独立裁决或明确暂缓；没有用全局“确认写入”替代冲突授权。

### 5. 写入与生命周期

授权后立即重读 `CONTEXT.md`、`ROUTING.md` 和目标文件，检查工作树是否出现新改动，再使用 `apply_patch` 精确修改：

- 新大类：先建立标题、维护者引言、`边界`、`规则`、`目录` 和模板，再写条目，并回填 `ROUTING.md`。
- 新条目：同时更新目录与正文；标题用完整命题，正文删掉会话专名后仍可理解；代码行为附 ≤10 行最小示例及来源路径。
- 并入：在原条目增加新证据或适用条件，不另开同义节。
- 修订：只改需要变化的语义；正文保持 timeless，修订原因交给 git。
- `language-note`：遵守目标笔记既有章节、编号、示例和版本写法，不强套普通条目模板。

发现目标大类由另一个 skill 标记维护时，仍按主题使用该大类，不新建近义文件；由执行中的写入 skill 按共享契约写入并在报告中标出维护者。任何写入都不得覆盖用户已有改动。

**完成判据**：每个动作都能在 diff 中定位；新大类已注册路由；目录与正文同步；没有敏感原文、重复条目或被静默删除的旧结论。

### 6. 验证与健康报告

普通条目型文档运行：

```bash
python3 /home/liang/.agents/skills/session-to-knowledge/scripts/check_kb.py <本轮触及文档...> --profile entry
```

语言笔记运行：

```bash
python3 /home/liang/.agents/skills/session-to-knowledge/scripts/check_kb.py <本轮触及 language 文档...> --profile language
```

新大类或路由变更追加：

```bash
python3 /home/liang/.agents/skills/session-to-knowledge/scripts/check_kb.py --routing /home/liang/Project/MyProject/Summary/project/knowledge-base/ROUTING.md
```

校验器是结构契约门，不替代语义审读：它检查 UTF-8、骨架、目录↔正文计数、真实锚点、重复标题/目录项、相对链接和路由注册；`language` profile 只检查链接。失败先修复或报告阻塞，不宣称完成。

**完成判据**：本轮触及 profile 的检查命令全绿；若全库健康检查仍有存量问题，单独报告存量基线，不把它冒充为本轮回归失败或成功。

### 7. 收尾汇报

按以下固定字段报告：

1. 主旨与 profile 分布。
2. 提取、收录、并入、修订、supersedes、拒收、暂缓的数量（不设上限）。
3. 每个文件及条目的动作、证据等级和校验命令结果。
4. 脱敏处理、冲突裁决、维护者提示和未解决问题。
5. 明确提醒：Summary 是 git 仓库，不自动 commit。

**完成判据**：用户能知道写了什么、为什么写、什么被拒、什么尚未写，以及下一步如何复核。

## Quick Reference

| 信号 | 动作 |
|---|---|
| “总结一下”且未要求持久化 | 直接聊天回复 |
| 可重复流程/提示词/代理协议 | `session-to-skill` |
| 源码注释或源码阅读产物 | `source-annotator` |
| 续做上下文 | `handoff` |
| 语言语法/类型/并发机制 | `language-note` |
| 跨项目的机制坑/事实/权衡 | `knowledge-entry` |
| 相同命题已有条目 | 并入，不重复开节 |
| 结论反转 | 明确裁决后新条目 `supersedes` 旧条目 |
| 目标库缺失或来源不足 | 停止写入并报告，不猜、不建替代库 |

## Common Mistakes

- ❌ 按会话顺序建总结合集 → ✅ 按知识内核拆分并路由。
- ❌ “用户说都记下”就收常识、流水账、凭据 → ✅ 逐条过 profile 边界、证据门和脱敏门。
- ❌ 设计知识命中 source-owned 文件就新建近义大类 → ✅ 主题决定唯一落点，维护者只做责任标记。
- ❌ 结论反转时覆盖旧正文或写普通修订注记 → ✅ 新旧双向 `supersedes` 关系，旧证据保留。
- ❌ 把“直接写”当作跳过所有门禁 → ✅ 只跳过候选确认，冲突、脱敏和校验仍是硬门。
- ❌ 用“未报错”证明机制 → ✅ 标 `observed/verified/inferred`，缺证据就暂缓。
- ❌ 将语言示例代码误判为语言知识 → ✅ 看知识内核；跨语言仍成立的内容离开 `language/`。
- ❌ 用全库存量失败阻断本轮结论，或反过来只校验一篇就宣称全库健康 → ✅ 区分本轮触及校验与全库健康审计。

## Red Flags

出现以下任一念头就停下来重跑对应步骤：

- “先全部写进去，之后再拆/脱敏/补证据。”
- “用户说别问了，所以冲突也可以我替他决定。”
- “这是 private 仓库，密钥/内网 URL 可以保留。”
- “维护者不是权限，另建一个近义文件更快。”
- “看起来合理，先把推断写成事实。”
- “校验器没报错，所以整库一定健康。”
