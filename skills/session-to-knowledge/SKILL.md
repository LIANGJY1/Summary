# 会话知识沉淀

## Overview

默认拒绝的知识沉淀：只收通过**复习者测试**的可迁移知识（六个月后遇到什么问题会翻到它、翻到后能直接用），单次 ≤ 3 条，允许 0 条。你不是在写总结报告，而是在维护一份"条条可复习"的知识库（门槛的来龙去脉见知识库 `docs/adr/0004-default-deny-quality-gate.md`）。

## When to Use

先限定输入，再判断该不该自己干：

- 用户说"总结一下 / 概括一下"但未要求持久化 → 普通聊天摘要，直接回复，不碰知识库。
- 会话主体是读/标注某个库的源码 → 提示走 source-annotator（它维护既有大类）。
- 产出是可重复的流程 → 提示走 session-to-skill；要交给下一个 agent 续做 → 提示走 handoff。
- 用户指定更窄范围 → 遵守该范围。
- 知识库路径固定：`/home/liang/Project/MyProject/Summary/project/knowledge-base/`，任何 workspace 都写这里；动笔前先读其 `CONTEXT.md`（术语表）与根目录 `ROUTING.md`（知识路由：候选大类与分流判据的单一事实源，背景见 `docs/adr/0005-two-level-knowledge-routing.md`）。格式契约由本文档自带，不依赖任何既有大类作范本：新大类沿用骨架——标题 > 引言 blockquote（一句话定位 + **维护者**）> `## 边界`（收什么/不收什么/与兄弟文档分工）> `## 规则`（条目格式定义）> `## 目录` > `<!-- 条目模板 -->` > 扁平 `## 条目名` 节。空的大类文档视为待填充，先补全骨架再写条目。

- **地盘**：只写入引言 blockquote 标明由 session-to-knowledge 维护的大类，或本次新建的大类。source-annotator 维护的文档（引言有它的名字）主题再匹配也不碰——宁可新开大类，并在边界里与它分工。

默认条目模板：**踩坑五段——现象 → 原因 → 误区 → 解决方案 → 启示**。标题与各加粗首句构成 skim 层，复习时先扫标题再进段。蒸馏自联想复盘（评估结果找差距、刨根问底、总结规律）、SRE 无责复盘（影响与复现、root cause、行动项）、错误日志法（负知识单独成段）。可按知识形态调整，调整结果写进该大类的 `## 规则`。

```md
## 条目名（完整命题："X 条件下会 Y"，复习时靠它检索）

**现象**：症状 + 环境（设备/系统/组件版本，了解多少写多少）+ 手顺（复现步骤）；不可复现的如实写"未独立复现"，只给已知证据。

**原因**：机制层因果链，刨到"为什么这必然发生"——表面事件不是根因。涉及代码行为必须附 ≤ 10 行最小示例，标来源库/项目与文件路径。

**误区**：直觉会怎么想错、排查最容易走进哪条岔路。写不出真实误区 → 多半是常识或流水账，价值门拒收。

**解决方案**：可直接执行的做法（代码/配置/命令）。

**启示**：
- 跨场景可迁移的结论（适用条件：什么信号下用它、不适用会怎样）
```

填好的实例：知识库 [android-ui.md](file:///home/liang/Project/MyProject/Summary/project/knowledge-base/android-ui.md) 的各条目即五段式的落盘形态（黄金对照 ✓ 条目「构造期配置与运行期 API 存在断层」为首条）——写入前重读目标大类，按其真实条目仿写，不在本 skill 内复制实例（避免双份漂移）。

## 价值门（先于一切写入判断）

**复习者测试**：每条候选必须能写出"六个月后遇到什么问题会翻到它、翻到后能直接拿去用"。写不出 = 不收。

**显式排除**（命中即拒）：
- 行业常识、官方文档现成可得的知识——写它只是证明"这次学过东西"，无复习价值
- 本次任务的操作步骤、分工与流程结论（"这次我们怎么收编"）——工作记录，离开任务即失效，归宿是项目文档/交接
- 只对当前项目有意义的细节
- 流水账、过程记录、一次性报错、无依据猜测

**黄金对照**（真实事故校准，勿重蹈）：
- ✗ 「View 背景不响应 padding」——Android 基础事实，拒
- ✗ 「差异三分类决定收编路径」——收编任务的操作结论，拒
- ✓ 「构造期配置与运行期 API 存在断层」——任何"改了 setter UI 没反应"的排查都用得上，换一个 AAR 组件依然成立，收

## 流程

### 1. 要主旨

先问用户要一句："本次会话核心搞清楚了什么？"长会话早期内容可能已被上下文压缩，这句是防漏锚点。

**完成判据**：拿到一句话主旨。用户答"没什么"或会话确实空洞 → 按"无沉淀价值"收场，不动文件——没有结果也算成功。

### 2. 出候选清单

按价值门分捡**原子单元**（稳定事实 / 设计决策 / 失败经验 / 可迁移思想），列清单给用户勾选。每条含：**目标大类**（按 `ROUTING.md` 主判据链路由出的既有大类，或建议新立：文档名 + 一句定位 + 条目格式草案）、**一句话论点**、**复习场景**（一行）、**动作**（并入 / 修订 / 新条目）。示例：

- `android-ui.md`（本 skill 维护）← 并入既有条目「构造期配置与运行期 API 存在断层」（新证据：另一组件同症状）。复习场景：改了组件属性 UI 没反应时
- 新大类 `gradle-pitfalls.md`（构建踩坑）← 条目「kapt 与 configuration cache 不兼容」。复习场景：构建配置改动后缓存行为诡异时

上限 ≤ 3 条：8 条低分条目不如 1 条真知，清单为空是正常结果。

**脱敏**：起草前扫全部输入。密钥、个人信息、内部链接的原文与可重建片段不得出现在提案、依据或汇报里，用 `[已脱敏：API 密钥]` 占位；疑似秘密直接排除；拿不准敏感性的不引用原文，先问用户。

**完成判据**：每条都有一行复习场景、已过脱敏扫描，且拿到用户明确答复（"确认写入 / 按提案落盘"）。含义不明继续讨论；扩大范围重新确认。

### 3. 确认后写入

写入前**立即重读目标文件**，再次查重与冲突，然后：

- **新立大类**：`ROUTING.md` 判据链不中、用户确认新立后——按 §When to Use 骨架建文档（引言标维护者、头部立「边界」与「规则」）→ 写入条目 → **回填 `ROUTING.md` 路由表**（新增一行：大类 | 维护者 | 一句话判据 | 相邻去向）。**完成判据**：新大类已出现在路由表中——不回填即本轮没做完。
- **新条目**：追加 `## 条目名` 节 + 目录行，格式按该大类规则填写（新大类用 §When to Use 的默认模板）。**冷可读硬标准**：删掉会话专名仍能读懂——专名首现必须带括注（如 `HCTabBar（车机项目的自定义标签栏组件）`）；"原因/误区"要写透；涉及代码行为的条目必须带 ≤ 10 行最小代码示例（标来源库/项目与文件路径）。正文 timeless，不写日期、不带元数据行。
- **Language 域**（ROUTING 判据链第 1 条，落点 `language/`）：分发、新语言准入与收/不收标准都按其 [README](file:///home/liang/Project/MyProject/Summary/project/knowledge-base/language/README.md)——该域是人读散文，不强制复习者测试，价值门以 README「边界」为准。讲解**示例驱动、通俗易懂**：先给可运行的最小代码示例再讲机制，术语首现带一句白话括注，能靠代码对照或类比讲清的不堆术语。格式跟随目标文件既有体例（章内目录、Q&A 编号等照旧续写）；新建文件不套默认五段模板。结构校验不跑 check_kb（它按条目大类设计，会把章节误报为未登记条目），改为自查相对链接与示例可运行性——完成判据以自查通过替代「check_kb 全绿」。
- **同名/同主题条目**：并入既有条目（可并列第二个来源），不开新节——同一知识两处演化，复习时会互相矛盾。完全重复保持不动；新来源明显更强才补充。
- **小修订**：就地改旧条目，末尾加修订注记 `（2026-09-04 修订：xxx）`。
- **结论冲突**：不静默裁决，逐条让用户四选一：保留旧结论 / 采用新结论 / 两者并存 / 不写入。采用新结论时旧条目留一行 `取代于：<新条目名>`，正文不删。全局写入确认 ≠ 冲突裁决授权。
- 结构校验：`python3 /home/liang/.agents/skills/session-to-knowledge/scripts/check_kb.py <目标文档>`（机械检查：目录↔条目双向一致、相对链接存在）。

**完成判据**：check_kb 全绿；汇报已按 §4 发出。

### 4. 收尾汇报

报告：提取 / 收下 / 被价值门拦下的数量；新建或更新的文件与每条动作（新增 / 并入 / 修订 / 取代）；冲突与脱敏情况。提醒用户 Summary 是 git 仓库，可 commit 固化（不要自动 commit）。

**完成判据**：四类信息齐全，用户清楚知识库变了什么、为什么没变的没变。

## Quick Reference

| 情况 | 动作 |
|---|---|
| 大类已有近义条目 | 并入（可并列第二来源） |
| 既有条目缺一小块 | 就地修订 + 修订注记 |
| 新结论推翻旧结论 | 新条目 + 旧条目标"取代于"，逐条经用户裁决 |
| 全新主题 | 新大类：先立边界与条目格式，写条目，回填 `ROUTING.md` 路由表 |
| 候选全被价值门拦下 | 报告 0 条，保持文件不动 |

| 会话类型 | 去处 |
|---|---|
| 源码阅读/标注 | source-annotator |
| 可重复流程 | session-to-skill |
| 交接续做 | handoff |
| 聊天摘要（未要求持久化） | 直接回复 |
| 可迁移知识 | 本 skill |

## Common Mistakes

- ❌ 把任务操作结论写成条目（"这次怎么收编"）→ ✅ 只收换项目仍成立的，操作结论给项目文档/交接
- ❌ 一口气 8 条显得丰收 → ✅ ≤ 3 条，0 条也是成功
- ❌ 条目裸用会话专名（HCTabBar、五档）→ ✅ 首现带括注，删掉专名仍能读
- ❌ 降门槛重写常识凑数 → ✅ 命中排除清单即拒，如实报告拦下了什么
- ❌ 条目名用名词短语（"缓存问题"）→ ✅ 完整命题（"配置期收集、执行期分发"），复习时靠标题检索
- ❌ 根因停在表面事件（"忘加锁了"）→ ✅ 追到机制层（这类结构为何必然产生该竞态）
- ❌ 静默采用新结论 → ✅ 冲突逐条让用户四选一

## Edge cases

- 知识库目录不存在（新机器）→ 先创建再走流程。
- 用户指名的大类与内容不匹配其 `## 边界` → 指出冲突，以边界为准，或请用户先改边界。
- 会话横跨源码标注与其他内容 → 只沉淀非标注部分，标注部分提示交给 source-annotator。
- 用户要求跳过确认直接写 → 跳过 §3 的确认与冲突询问，但价值门与上限照常执行，冲突按"两者并存"落盘并在汇报里显著标出。
