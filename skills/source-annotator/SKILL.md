# 源码标注

## Overview

把源码分析转化为三层学习产出：源码行旁的微观批注、库目录根部的宏观讲解文档、跨库知识库中的高质量知识。只新增或修改注释及授权范围内的文档，不改变代码行为。

## When to Use

- 用户明确要求标注、注释、精读、学习并沉淀本地源码。
- 用户要求解释类、方法、调用链、线程模型、设计思想，并希望结论落盘。
- 用户要求压缩或精炼既有中文学习批注。
- 用户要求结合外部资料；外部观点必须经过本地源码核实。

仅问“是什么 / 为什么 / 讲讲”时只在回复中回答，不写任何文件；若希望保留候选，先取得独立授权。引用本 skill 视为标注意图，除非用户明确说“只回答、不要改注释”。

## 核心流程

### 1. 锁定范围

确认源码版本或 commit。范围不明确时先扫描模块、包和入口，列出主链机制与建议起点并询问；范围明确并获得用户授权后，授权范围内的源码、上下游依赖、库文档、跨库知识库和 `ROUTING.md` 均可读写，不再按文件、类或调用链收紧写权限。超出授权范围仍需确认。

超过约 8 个文件或 3 个机制时，先固定本批“纳入 / 跳过 / 仅读取”清单，按机制分批；用户说“继续”才开始下一批。

**完成判据**：每个纳入目标有版本锚点、角色、上下游和证据档位；跳过项有理由；主链能从入口走到出口；写范围未因追链扩大。

### 2. 读取与建模

用 Read / Grep / Glob 定位入口、关键方法及调用链，通读必要上下游。先列读者画像和阻力点，再判定代码类型与注释块形状。逐一标出重要字段、方法内部决策点和跨方法/跨线程交接点，给每处确定贴近代码的注释落点；类头、方法头只承担总览。落笔前按需读取：

- 内容、读者、阻力点和判型 → `references/annotation-guide.md` 的“写前”部分。
- 标签、块形状、换行和示例 → 该指南的“写中”部分。
- 质量门、死注释和验收 → 该指南的“写后”部分。
- 外部资料调研 → `references/research-protocol.md`。

围绕三问分析：解决什么问题；为什么这样设计、不这样会怎样；与上下游如何交接。遇到新角色，补充其职责、解决的矛盾、可迁移手法、适用条件和反例代价。主链优先，扩展到能预测后续形态即收口。

**完成判据**：重要字段、方法内部决策和主链交接点均已逐处列入落点清单；每个设计论断都有代码事实、git/issue 考据、外部已核实证据或 `[inferred]` 标记；未找到的实现明确记录，不用常识补全。

### 3. 写学习批注

只使用所在语言的行注释（`//`、`#`、`--`），不改 Javadoc/KDoc、license、上游英文注释或代码字符。默认跳过 auto-generated / DO NOT MODIFY 文件、测试代码和已完整标注文件；编译期装配核心可例外标注，测试名只作考据。

批注块只能使用指南规定的 17 个标签；类头总论不加标签。类头和复杂方法头用简短总览建立地图，再按落点清单把解释写在字段声明、关键分支、状态变化、锁/线程切换、调用与回调交接的代码旁；总览不能代替这些局部批注。解释代码读不出的原因、边界、后果、去向和使用方式，不翻译或复述代码。API、配置点、回调和扩展点必须给最小示例、真实场景和不接入后果。推断标 `[inferred]`，专名与跨层签名落笔前回查。

设计点按“根因 → 做法 → 收益 → 替代代价 → 适用条件 → 反例”收束，并以“对 SDK 设计的启示是……”结束。大篇幅只用于读者会大面积卡住的概念；逐行通读仅在用户明确要求时使用。

**完成判据**：逐处对照落点清单：每个重要字段、方法内部决策和主链交接点，要么有紧邻代码、讲清原因/后果的批注，要么有“代码自明”的具体理由；只有类头/方法头长段说明而局部落点空白，不算完成。每个新增块对应真实阻力点；通过删除测试、首句测试和链条检查；代码序列与上游注释未变；没有复述型、翻译型、日记型、万金油型、漂移型或占位型死注释。

### 4. 更新宏观文档

在库目录根部维护 `<库名>.md`，头部记录源码版本或 commit。每个机制按“三问结论 → 代码链路 → 设计思想 → 易错点”组织；小范围可裁剪为代码链路和设计思想。已有机制原地更新，新机制按层级追加；不要把源码批注原文复制进文档。

**完成判据**：文档只表达宏观最佳理解，能让不翻源码的读者学会用法和取舍；同一机制没有重复章节；存量旧结构不顺手全局重构。

### 5. 形成跨库候选

若发现可迁移的 SDK 做法、设计思想或注解技术，先读取知识库 `ROUTING.md` 和目标大类规则，直接将高质量内容写入唯一落点。条目必须带证据、来源、适用条件和目标落点；同一命题只保留一个落点。写入后运行 `check_kb.py`；冲突、重复和存量基线问题列入汇报。

**完成判据**：每条高质量知识已直接同步并校验；低质量、证据不足或无法归类的内容不写入；冲突、重复和存量基线问题均已列出。

### 6. 验收与汇报

先人工自查，再运行：

```bash
python3 scripts/check_annotations.py --self-test
python3 scripts/check_annotations.py <仓库根> <本轮改动文件...>
```

批量任务还要完成规定语义抽检，并披露纳入、跳过、失败和未逐条审读文件。若同步发布副本，再加 `--mirror <副本目录>`。校验失败先修复；默认不使用 `--fix` 自动改写自然语言。

固定四段汇报：

1. 三问结论与本轮学习点（思想/模式/坑、适用条件、深入位置）。
2. 已修改注释的文件和代码位置。
3. 库文档章节与跨库知识条目。
4. 尚未核实、低质量未写入、冲突、跳过和失败项。

## 常见误区

- 纯问答写盘 → 只回复；明确标注意图并授权范围后才写入。
- 读上下游就顺手改依赖 → 读写范围分离。
- 把外部文章当源码事实 → 逐条核实并标版本。
- 把机械全绿说成语义全验 → 披露抽检和未审读边界。
- 为满足同步质量门写入低质量知识 → 先做证据、重复和适用条件检查，不合格内容不写入。

详细格式、示例、质量反例和历史决策分别见 `references/annotation-guide.md`、`references/research-protocol.md` 与发布归档目录。
