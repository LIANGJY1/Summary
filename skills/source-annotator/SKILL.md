# Source Annotator（源码标注解释工具）

把源码分析写进源码本身：注释承载微观细节（贴着代码讲），库级沉淀文档承载宏观结论（问题背景、链路、设计思想）。标注落盘即学习产出——无进度文件、无复述验证、不自动操作 git。

**本质目的（v1.22 定位升级）**：读源码就是为了学习——学设计思想、学代码精华、学可复用的好东西，学会怎么使用、什么时候使用，丰富架构思想。用户原话："你必须让我学习这些东西。"本 skill 的一切规则都是手段，唯一检验标准是**用户能带走什么**：

- 每个新概念被讲懂（§3.2 两面讲解 + 使用示例：是什么/怎么接入/什么场景/不用会怎样）；
- 每个可复用手法带适用条件沉淀（§3.3 新角色习惯 + 启示三件套：做法/适用条件/反例代价）；
- 每轮汇报明确列出**本轮学习点**（§5 第 1 段）。

学习路径三层，产出分散在三处、各有分工：**注释就地学**（贴着代码的微观细节、示例与设计思想，读码时当场吸收）→ **沉淀文档系统学**（机制章按三问/链路/设计思想/易错点组织，只看文档应能学会该机制的用法与设计）→ **知识库跨库复习**（sdk-design.md/design-principles.md 是跨库累积的思想资产，架构思想在这里变厚）。

## 0. 铁律（先读）

1. **只新增/修改注释**。绝不改代码逻辑、变量名、签名、格式。
2. 新增中文注释用**所在语言的行注释语法**（`//` / `#` / `--`，见 §3.5），不用块注释；注释块以【标签】开头（16 标签体系，见 §3.0）；**原有 Javadoc/KDoc/文档注释原样保留**；原有 license/header 保留。与原有 Javadoc 并存时各司其职：Javadoc 是库作者的契约（IDE 悬浮展示用），中文行注释是学习讲解层，互不改写。**块注释扩展禁令**：给既有类头 `/* */` 追加内容（族谱、总论块等）时，新内容用行注释接在块注释**之后**，不写进块注释内部——原块注释一字不动（往里追加最顺手，也最容易违这条）。
3. **上游注释保护**：库作者的原始注释（文档注释与行注释，含英文行注释）只读——发现可疑记入汇报（§5 第 4 段），不直接删改；四检（§3.4）范围仅限此前轮次的中文学习批注。每条注释必须锚定紧邻代码、可追溯；**专名回查**：注释中的类名/方法名/常量名/数值阈值/线程名，落笔前 grep 当前源码确认存在且拼写一致；推断的内容标 `[inferred]`，绝不把猜测写成作者意图。
4. 不执行任何**改变仓库状态**的 git 操作（commit/push/checkout/reset 等）；只读检索（git log / git blame）可用于考证注释事实。不创建学习进度/状态文件、自测题。
5. 范围未明确时**先主动问**（见 §1），确认后才落盘。
6. **外部资料核实门禁**：博客/文章/文档等外部观点未经本地源码逐条核实，**不得写进注释**——核实通过才落笔；核实不了又确有价值的标 `[inferred]` 并在沉淀文档注明来源；与源码冲突的说法绝不采纳，一律进沉淀文档「参考资料」勘误小节（§4）。（真实教训：两处流行的 Glide 说法——DecodeJob 优先级顺序、"5.0 默认网络栈是 OkHttp"——与源码相反，直接采纳即污染源码。）

## 1. 输入契约与范围确认

用户通常提供：库名、机制/主题、范围（类/方法/调用链）、密度要求。均可省略，省略项取默认。

- **范围未给**（如只说"标注某个库"）：先扫库结构（模块、包、入口类），列出**主链机制清单 + 建议起点**，主动问用户确认后再动手。标注是落盘操作，方向猜错的代价远大于一次确认。
- **范围已明确**（如"标注 X 类的 Y 方法调用链"）：直接执行，不再确认。
- **提问与落盘的硬边界**：只有明确的标注意图（标注 / 注释 / 标进去 / 沉淀 / 压缩）才修改源码注释；"X 是什么 / 为什么 / 讲讲"这类纯提问**只回答，绝不动源码注释**——但结论要**言简意赅**地总结进沉淀文档（§4），不让问答蒸发。
- **引用即意图**（上条细化）：消息中引用了本 skill（$source-annotator）即视为有标注意图——即使措辞是"分析 / 讲讲 / 为什么"，也应把结论同时落进源码注释；仅当用户明说"只回答、不要动注释"时才纯回答。（真实教训：带 skill 引用的"分析为什么"被当纯提问处理，用户本意是要注释。）
- **大范围自动分批**：范围超过约 8 个文件或 3 个机制时，按机制拆批；每批结束输出完整四段汇报（§5），用户说"继续"才走下一批。小任务照旧一次跑完。
- 密度默认**自适应**（§3.4）；"逐行通读"与"压缩"是用户可显式要求的两个动作。"压缩"未指明对象时，先列出候选（如现存逐行草稿注释）请用户确认再动手。

### 关键模糊点 → 升级提问（grill-with-docs）

遇到**关键的、答案会改变落盘行为的模糊点**时，直接调用 `grill-with-docs` skill 对用户提问（本机无该 skill 时，按同规则直接提问）——不擅自假设，也不事事都问，尺度自把握：

- **该问**：落盘方向类决策——范围与起点、密度形态、文档结构与幂等规则、与既有共识/规范冲突、破坏性或难回滚的操作（成片删除/重写**有信息量的**既有注释、覆盖沉淀文档章节）、**存量沉淀文档的全局重构**（旧结构改新模板属成片改动，另立任务并确认范围，§4）。废话注释的重构是常授权，不问。
- **不该问**：能从代码或工作区文档（CONTEXT.md、docs/adr、沉淀文档）查证的事实；已有共识覆盖的事；不影响落盘结果的小事。
- **问法**：一轮 ≤ 3 问，每问带推荐答案；拿到答案立即执行并落盘，已决事项不再重复追问。

## 2. 分析流程

1. **锁版本**：动手前确认工作区源码的版本/commit，记入沉淀文档头部——注释的有效性以该版本为准，日后才能区分"当初写错"与"上游改了"。
2. **定位**：Read / Grep / Glob 定位目标类、方法及其调用链；通读相关代码与上下游依赖（谁调它、它调谁），让注释解释"链路中的角色"而非局部行为。阅读是非线性的：一次只看懂一两层调用，来回跳是常态。
3. **判型 + 读格式卡**：先判断目标代码属于哪一类（见 §3.2 六分类），类型决定注释侧重——不是所有代码都只讲"为什么"。**落笔前必读 `references/annotation-format.md`**（标签模板总集与换行折行规范的完整版）——版式细节不凭记忆写，遗忘即重读，不猜。
4. **三问先行**（全部分析的主轴，注释与文档都要落到答案）：
   - 这段代码解决什么问题？
   - 为什么这样设计？不这样设计的后果是什么？
   - 与上下游组件是什么关系？
   每遇到**新的类/新角色**（本库分析中首次出现的组件），像人读码一样举一反三，追加角色自问（§3.3 新角色习惯）：
   - 它在整体里扮演什么角色、解决什么矛盾？谁依赖它、它依赖谁？
   - 这个处理手法（模式/结构/约定）我以后写代码能不能用上？
   - 什么环境下适用、怎么用？不适用/选错会怎样？
5. **主链优先**：先走通最简单、最快速的核心调用链；扩展链路（缓存命中、异常分支、特殊格式等）在主链标注完成后再展开。**追 3~5 条线程即收口**——当能预测下一条扩展链路的样子时，就已掌握系统语法，停止外扩，防止"无限理解而不交付"。
6. **场景切入**：分析库时从使用者的典型使用场景出发——先摆一行典型用法（如 `Glide.with(this).load(url).into(view)`），再下钻这行代码背后发生了什么；注释里的"两面讲解"都要落在具体场景上，不空谈用法。在此之上对关键链路逐行/逐块解读，但避免逐字翻译。重点讲四件事：设计意图、并发安全、性能考量、应用侧使用方式。
7. **装配/生成组件**（编译期生成、反射装配、SPI/服务发现注册等初始化机制，若在范围内）：必须给出"编译期 → 运行时"完整链路与应用/库侧接入步骤，**只讲一次**，不在多处重复。讲解落点分工：流程方法处只给角色定位与回指，完整讲解（概念是什么/怎么接入/示例/场景/不用会怎样）落在概念本体的类头（§3.2 两面讲解 + 使用示例）。

### 外部资料调研（条件触发的三步闭环）

博客/技术文章是关键 why 的补充来源——代码只留 what，设计意图常无痕迹可考，外部资料是本地考据天花板（代码 + git 考据）之外的唯一补强。**默认不调研**；满足任一条件才启动：

- 本地代码与 git 考据回答不了关键 why（设计意图无痕迹可考、历史 issue 无从查起）；
- 用户措辞含"深入 / 结合博客 / 高质量文章 / 全网调研 / 参考文章"等外部资料诉求。

三步闭环（执行要点清单与固定返回 schema 见附属文件 `references/research-protocol.md`；**用后台 general-purpose 代理执行**——系统性调研动辄数十万 token，主对话自己零敲碎打地搜会挤压标注上下文；代理提示词必须自包含，§3.4 教训适用）：

1. **带主题清单派调研**：按当前库的机制/链路逐个拆主题，只收确凿事实 + 来源 URL，不照抄其他库的清单形状；
2. **核实后才落笔**（铁律 6）：调研结论逐条对照本地源码验证，验实才写进注释；版本错位（文章讲旧版本机制）以本地快照为准，演进差异按【兼容性】处理；
3. **文章当考据对象**：与源码冲突的流行说法沉淀为「参考资料」勘误小节（§4），绝不采纳进注释。

注释不写"据 xx 博客"——注释只锚定代码事实，来源统一沉淀到文档「参考资料」节。

**默认跳过**（不加注释）：纯生成物（pb / databinding / build 产物）、test / `androidTest` 测试代码、已注释完善的文件。两个例外：① 编译期生成的**装配核心**（如 `GeneratedAppGlideModule`）是链路关键角色，正常标注；② 测试代码虽不注释，但**测试名是意图的最佳考证材料**，分析时要读。

**意图推断线索**（写【设计思想】块前，从这些痕迹推断作者意图；推断才标 `[inferred]`）：类型守卫与强制转换（暗示参数的预期域）、默认值写法、调试日志痕迹、反射/元编程、变量的完整生命周期（谁初始化、谁修改、何时失效）、多个布尔量组合出的隐藏状态机（`!isReady && isFinished` 这类非法组合往往是 bug 温床）。

## 3. 注释规范（微观层）

### 3.0 标签体系总纲

**注释六原则**（每条注释落笔前对照）：

- **言简意赅**：不解释代码本身已经表达清楚的内容；
- **重点突出**：优先解释设计意图、调用关系、关键机制和容易误解的细节；
- **上下连贯**：前后注释沿阅读链形成完整路径，避免零散堆砌；
- **术语准确**：保留 Android / Java / Binder / AMS / WMS 等专业术语；
- **贴近源码**：解释当前代码真实行为，不作无依据推测；
- **解释原因**：对"为什么这样写"的代码，优先解释原因而非重复行为。

**16 标签体系**：注释块一律以【标签】开头（标签后不加冒号），取代旧的 `// 注：` 统一前缀；检索锚点为 `grep "【"`——批量压缩/重构、迁移检查都以此定位学习批注。标签按读者疑问组成阅读链——是什么 → 做什么/怎么运行 → 为什么 → 什么时候 → 和谁交互 → 有什么坑；按内容就近取用，不硬凑全套。

| 标签 | 用途 |
|------|------|
| 设计思想 | 解释架构设计、核心理念 |
| 核心流程 | 说明关键执行链路 |
| 调用关系 | 说明调用者、被调用者及上下游 |
| 数据流 | 说明关键数据的流转过程 |
| 执行时机 | 说明代码在什么情况下执行 |
| 生命周期 | 说明组件或对象所处的生命周期阶段 |
| 线程模型 | 说明代码运行线程、Handler、Binder 线程等 |
| 状态管理 | 说明状态变化、状态机、标志位 |
| 为什么 | 解释非直观代码背后的原因 |
| 关键细节 | 解释容易遗漏或误解的实现细节 |
| 性能考虑 | 解释缓存、批处理、懒加载等性能设计 |
| 安全考虑 | 解释权限、身份校验、攻击面等安全逻辑 |
| 兼容性 | 解释版本兼容、历史遗留逻辑 |
| 注意事项 | 提醒修改代码时容易踩坑的地方 |
| 关联代码 | 指向值得继续阅读的相关代码 |
| TODO | 标记尚未分析清楚、需要进一步研究的内容 |

迁移说明（历史兼容，非标签用途）：旧体系的【阶段】块并入【核心流程】；旧【注意】即现在的【注意事项】。

**伪标签禁令**（标签形式规则）：除 16 个【】标签外，注释中不得出现"引导词："形式的伪标签（如 目的：/收益：/替代：/防线检查：）；骨架类内容一律用 1. 2. 3. 完整句分点表达，启示以"对 SDK 设计的启示是…"完整句收尾。

**类头总论不带标签**：类/接口顶部的概括总论（§3.1 的"它是什么"层）是阅读入口，直接以内容开篇，**不加任何【标签】**；16 标签用于总论之下的分类标注（【线程模型】【调用关系】等段）与方法/行级注释。

**问答式**（仅【为什么】标签）：问题以问号结尾，答案另起一行，分点 1. 2. 3.、每点尽量一行；陈述式标签不硬凑问句。

**版式速览**：列表化一行一项、链路箭头化一行一链段、块间空注释行隔断、每行以标点结尾；**行宽自适应**——上限 = 所在文件 HEAD 既有行最大显示列（中文按 2 列计），下限 130，校验脚本自动探测。完整换行/折行规范与全部标签示例（每标签一例）见 `references/annotation-format.md`，落笔前必读（§2 步骤 3）。

代表性示例两则（其余标签示例见格式卡）：

```java
// 【设计思想】一个 URL 三种表示：原始串 / 转义串 / 廉价缓存键。
// 1. 根因是 URL 常含中文、空格等非法字符——HTTP 请求要求百分号编码转义（空格 → %20），
//   否则请求会失败，而磁盘缓存键若用转义串则每次算键都得先做昂贵转义。
// 2. 实现上构造只存原始串。
//   - getSafeStringUrl/getSafeUrl 首次调用才按白名单 ALLOWED_URI_CHARS 转义并缓存。
//   - getCacheKey 直接返回原始串，不转义也不含 headers。
// 3. 收益是缓存键计算 O(1)，转义一次成本摊薄到所有请求，URL/String 两种构造方式行为一致。
// 4. 若构造时就 new URL + 全量转义，只为算缓存键的路径也得付解析和分配的代价。
// 5. 对 SDK 设计的启示是同一数据的多形态表示按使用场景惰性生成。
//   昂贵的规范化只在实际用到该形态时做，廉价路径永远走最便宜的表达。
```

```java
// 【为什么】load() 不立即解析出 ModelLoader？
// - model 类型×解码路径的组合在配置期并不完整（target 尺寸、options 都会影响选路）。
```

### 3.1 位置分工与阅读梯度

**阅读梯度四层**——每层回答一个问题，读者停在任何一层都得到完整回答；下方条目即各层的标注要求：

| 层 | 注释位置 | 回答的问题 |
|----|---------|-----------|
| 为什么有它 | 文件头总论块 | 这个文件解决什么问题、在链路中承担什么 |
| 它是什么 | 类/接口头、实现族谱 | 职责、协作对象、怎么选实现 |
| 怎么工作 | 方法/代码块旁 | 流程怎么走、阶段怎么交接 |
| 为什么这么写 | 关键行旁 | 这一行防什么、锁什么、换什么 |

**各层的标注要求**：

- **文件头总论块**（链路型任务）：一句话总论 + 主链 ASCII（`A → B → C`）+ 阶段骨架及各阶段所在位置。画不出来就写清楚，不硬画。
- **类/接口顶部（必选）**：总论不带标签（§3.0），2-5 行讲清职责、设计思想、在框架中的位置、关键协作对象；简单类（纯数据持有、纯委托）一行即可。**禁止**把详细分析全堆在类开头；已有类头注释的按路过即全检（§3.4）处理。
- **多实现族谱**：接口/抽象类有多个实现时，在类顶部概括之后追加实现清单——**每个实现一行三要素：是什么、为什么存在（解决什么矛盾）、对应什么应用场景**，让读者不点进任何子类就能选对实现。
- **复杂方法顶部（必选）**：判定为复杂的方法（多阶段、多分支、锁/线程切换、隐藏状态机、链路中转枢纽），方法顶部**必加** 2-4 行概括——职责一句话 + 关键机制/阶段骨架 + 边界（线程/时序/前置条件）；内部细节仍落在关联代码处。简单方法不加头注释，直接标关键行。
- **详细解释放关联代码处**：字段说明放字段旁；实现细节放对应方法/代码块旁；设计原因放在做出该设计选择的代码附近。
- **关键代码行**：判空、加锁、反射、回调、单例写回、生命周期转发、线程切换、缓存读写等一眼看不出的行，直接加简短注释。
- **"伤疤"类行优先注释**：看似多余的判空/防御代码、看似普通实则怪异的条件、看似死代码实则存活（被反射/定时任务/feature flag 调用）——这类多是历史事故的修复现场，注释要指出"它防的是什么事故"。拿不准就只读 git log/blame 考证，考不出标 `[inferred]`。
- **核心数据结构的字段逐个注释**：结构与不变量是库的地基（中文注释流派惯例，参考 redis-annotated）。

**梯度纪律**：

- **上层不下沉细节**：文件头不展开方法内部逻辑，类头不逐方法讲；**下层不重复上层**：行注释不复述方法头已说的职责，只补这一行独有的信息。
- **沿链落笔**：按链路顺序（入口 → … → 出口）标注，先立文件头主链与阶段编号，再逐阶段展开；阶段注释回指编号，不引用尚未标注的内容。
- **每条注释内部递进**：先事实（紧邻代码在做什么）→ 再解释（为什么/意味着什么）→ 只抬一层抽象。事实没看清就不落笔。
- **复杂度递增**：主链先、扩展后（§2）；同一文件先骨架后细节，难懂的块先给一句话定位再展开。
- **链路总览前置**：分析全调用链时，在**入口方法的开头**先给完整调用链 ASCII，再逐段展开——读者从触发点一眼看到终点，之后每段注释都能对号入座。**总论只落一处**：完整 ASCII 落在链路枢纽方法（或入口文件）一处；其余入口已有的局部链路列表改为**编号回指总论**（"见 X 处【核心流程】总论"），不重复展开——重复的链路列表会随演进失同步。

### 3.2 判型与内容标准

**先判型，再落笔**——六类代码，注释侧重各不同：

| 类型 | 注释侧重 |
|------|---------|
| 胶水/适配代码 | 两侧接口的形状差异；错误如何处理：抛出、丢弃坏值还是有损转换 |
| 接口/抽象类 | 契约与保证；每个实现者必须遵守什么；哪些内部细节不许泄漏；多实现时附实现族谱（§3.1） |
| 实现代码 | 如何嵌入整体；输入是否需要校验；改这里的风险波及范围 |
| 算法代码 | **例外：需要"是什么"的解释**；真实的数据结构；复杂度线索（嵌套循环 + 查找） |
| 配置代码 | 哪些自由度是真实的；选项组合爆炸点（组合 bug 的温床）；配置的生命周期 |
| 编排/流程代码 | 事务性（关键操作恰好执行一次）；可恢复性；顺序约束 |

**判型 → 常用标签映射**（判型决定侧重，侧重落到标签；映射是默认起点，实际按内容就近取用）：

| 判型 | 常用标签 | 落笔侧重 |
|------|---------|---------|
| 胶水/适配 | 【调用关系】【关键细节】 | 两侧接口的形状差异；错误如何处理 |
| 接口/抽象类 | 【调用关系】+ 实现族谱 | 契约与保证；实现者必须遵守什么 |
| 实现代码 | 【为什么】【关键细节】 | 如何嵌入整体；改动的风险波及范围 |
| 算法代码 | 【关键细节】（附"是什么"解释） | 真实数据结构；复杂度线索 |
| 配置代码 | 【注意事项】【执行时机】 | 真实自由度；组合爆炸点；生命周期 |
| 编排/流程 | 【核心流程】【状态管理】 | 事务性；可恢复性；顺序约束 |

**论断分级**：每条论断落笔前自定档位——**代码事实**（当前源码可见，默认档，免标）/ **考据**（git log、issue 号，注释可直接引 #编号）/ **推断**（标 `[inferred]`）/ **外部观点**（过铁律 6 门禁，来源进沉淀文档）。同块混档必须逐条标注——把推断写成事实是最常见的质量事故，且注释层没有编译期检查兜底（后续 AI 会把错误注释当事实吸收）。

**精确性禁令**：无证据不写"大概 / 应该 / 基本上 / 一般来说"；可量化处必须量化（阈值、条数、线程名、复杂度级别）；真不确定 → 降级 `[inferred]` 或【TODO】，宁可留白不填"看起来合理的"。

内容标准：

- 讲核心思想，不复述代码自明的内容；禁止无意义注释（`// if 结束`、`// 方法结束`、`// while 结束`）。
- **两面讲解 + 使用示例**（v1.22 新增，用户硬要求"以后所有源码分析都这样"）：源码侧在做什么 + 应用侧怎么用。凡 API 入口、扩展点/配置点/回调契约（模块机制、Builder setter、Listener、自定义组件基类），注释必须**内嵌最小使用示例**（5-10 行所在语言代码，行注释内缩进贴出）+ 一句**使用场景**（什么情况下用它），并点明**不接/不用会怎样**。新手视角自检：概念首次出现必须解释，禁止"默认读者已懂"的跳步。示例中的类名/方法名/参数一律回查当前源码，本仓未检出的依赖类标注示意 `[inferred]`；格式模板见 `references/annotation-format.md`「使用示例块」。
- **过程推断两问**：正向——正确使用它需要满足什么条件（前置条件/不变量）；反向——执行到这里之前发生了什么、状态从哪里建立。
- **零编造**：查不到的实现就明说"未找到对应实现，检索关键词为 X"，宁可空着。
- 副作用（IO、锁、全局状态变更、线程切换）必须标注。
- 简单 getter/setter、纯委托、逐字翻译 → 不注释。
- 语言用白话直说（中文注释流派共识），不端术语架子；抽象模型跟在代码事实之后，同一处只抬一层抽象；源码只支撑"分发"就不要拔高成"治理体系"。
- **六类死注释**（复述型/翻译型/日记型/万金油型/漂移型/占位型）的病例与处方见 `references/quality-rubric.md`——自评或抽检发现 ≥2 处时重读该文件再返工。

### 3.3 设计点标注约定

设计思想必须深入分析、举一反三。重要设计点用【设计思想】块贴在关键节点（入口分发、状态收口、桥接层、交接点）。内容用 1. 2. 3. 完整句分点组织（根因 → 实现 → 收益 → 替代的代价 → 启示），**禁止出现"目的：""收益："这类冒号式伪标签**；完整模板与全部标签示例见 `references/annotation-format.md`。

"为什么 / 为什么不"类内容优先用【为什么】问句形态（问答式）。

**SDK 设计启示**（v1.22 扩展：触发点从"设计精妙处"放宽为**每个新的类/新角色**——用户要求像人读码一样对每个新组件举一反三）：遇到新类/新角色先过一遍复用思考——它承担什么角色、用什么手法解决矛盾、我以后写代码能否用上、什么环境下怎么用。产出分级防噪音：

- 简单角色（纯委托、纯数据持有、纯胶水）：类头一句话点出角色即可，不落【设计思想】块——机械套用会产生噪音。
- 可复用手法（模板方法、注册表、生命周期桥接、池化复用、双集合补位、惰性断环等）：除回答"为什么这么设计、使用者得到什么好处"外，还要答第三问——**我以后写代码/设计 SDK 时应该怎么做**，以"对 SDK 设计的启示是…"完整句分点落在【设计思想】块末尾。**每条启示必须带适用条件**：什么信号/环境下用它、怎么用、不适用或选错会怎样——没有适用条件的启示是口号，"我知道有这个模式"不等于"我会在对的地方用它"。
- 同步：库沉淀文档"设计思想"节 + 跨库知识库（§4，"做法"入 sdk-design.md、"思想"入 design-principles.md，各自条目模板里的可执行做法/思想提炼同样要含适用条件）。

四问后再落笔：①根因（解决的矛盾、被简单方案遗漏的关键信息属于谁）②代价（直观替代方案为何不可行）③场景（每条分支对应什么真实场景）④反例（选错的后果）；最后点出收敛点——表面多样在哪个 key/接口/时机上统一。

### 3.4 密度自适应（无固定档位）

- 默认克制：只标职责、核心方法、关键机制、设计抽象、边界提醒。
- **重要设计点、难点处加大力度**：允许连续多行【设计思想】块、【核心流程】阶段边界四问注释（谁触发 / 负责什么 / 在哪交接 / 谁接管）、【注意事项】块。分析中"说不清"的函数正是信号——说不清说明值得下钻。
- **关键机制可展开大篇幅，但不许说废话**（v1.22 新增）：概念本体、入口分发、初始化链等新手卡点，允许大段讲解 + 内嵌示例代码；衡量标准是**每行都有信息增量**——概念没解释、场景没给、示例没贴、"没有会怎样"没说是欠账，必须补；复述代码、空话过渡、同一结论重复是超支，必须删。大篇幅授权 ≠ 注水授权。
- 用户显式要求"逐行通读"时：密集贴行草稿注释——啃硬代码的脚手架，不是终稿形态。
- 用户说"压缩"时：按序删除铺垫、重复论证、多行设计块，保留主链、关键边界、一层抽象。
- **路过即全检**：标注路过**此前轮次的中文学习批注**时，对每一行做四检——①**准确**：解释与代码行为不符的要修正（拿不准就标 `[inferred]` 或记入汇报）；②**清楚**：含糊、跳步的改明确；③**合并**：同一处多条可并的并；④**冗余**：复述代码、重复结论的删。精炼后要能体现该方法/代码块的**核心思想**，而非零散行语。护栏：只精炼不丢信息，有信息量的注释不删只精炼；`/** */` Javadoc 与上游作者注释原样保留（铁律 3），发现其内容有误时记入汇报待确认、不直接改；重构点列入汇报（§5 第 2 段）。
- **批量重构的校验闭环**（≥ 约 20 行的删/改注释操作必须走）：校验脚本已固化为本 skill 附属文件 `scripts/check_annotations.py`（v2）——九项一键：代码序列一致（含行尾注释剥离，`x = 1; // 改注释` 不误报）/ 体系外【标签】/ 冒号式伪标签 / 旧 `注：` 前缀 / 行宽自适应上限（所在文件 HEAD 最大显示列，下限 130，`--max-width` 覆盖）/ 圈号残留 / 行尾标点（**默认报错不写盘**，`--fix` 才补号——补号会把句中折行切成病句，优先按语义断点人工重排）/ 上游英文注释保护（删改 HEAD 英文散文行 → FAIL）/ 未带标签新块（? WARN）。改脚本后先跑 `--self-test`（内置回归夹具）。九项全绿后才跑人工语义抽检。真实教训：补写"收敛说明"注释时最容易吞掉代码字符（曾丢分号被抓出）；git 路径基准统一用 `git -C <仓库根>` + 仓库根相对路径，查询为空先怀疑路径基准而非数据；删除模式要加结构残片正则，收尾跑"残留空注释行"计数复检；终收口径 = 全绿且本轮零自动修复行。
- **覆盖审计多口径、缺口结论先核实**：统计标注覆盖必须同时数三种形态——【标签】块、旧 `// 注：` 前缀、无标签类头总论（类头按 §3.0 不带标签，只 grep 【 必然漏计）；宣布"文件/方法未标注"前先做方法级抽查核实（注释窗口 ≥10 行、正则按真实签名写——修饰符/跨行签名会让字面 grep 漏配）。真实教训：单口径 grep 把一批旧注体文件误报成"零标注缺口"，被用户当场质疑"根本不是全链路"——覆盖类结论先核实再落汇报，口径错误会透支信任。
- **替换文本携带规则**（单条 Edit / 脚本替换通用）：`new` 必须逐字符保留 `old` 的全部代码部分——只增注释行；锚点尾部与相邻的代码行最容易漏带（真实损伤两例：字段被替换出重复声明、类声明被吞进注释行）。落盘前先做一遍"代码部分逐字符比对"。
- **子代理批量标注**（范围超约 30 个文件的重建/标注）：并发先探上限（本环境实测 ≤2，4 并行会撞 limit——换环境先重探，失败组改串行重发，重发前全量校验兜底）；提示词必须**自包含**——完整规范 + 内嵌自校验脚本（子代理自检能抓回自己的误删英文 Javadoc、缩进偏移，实测有效）；分组清单落盘前逐一验证路径存在（路径笔误会静默漏分组，如漏写包前缀）；验收分级——机械校验（check_annotations.py 九项 + 无块注释 / 残片计数）全量跑，语义质量每组抽检 ≥2 文件，汇报必须明示"语义未逐条审读"的边界。

### 3.5 语言适配

- 注释语言默认中文（用户另有要求除外）。
- 注释语法随所在语言：`//`（Java/Kotlin/C/C++/JS/TS/Go/Rust/C#）、`#`（Python/Shell/YAML/TOML/Ruby）、`--`（SQL/Lua/Haskell）。**规范与示例以 Java 表达，规则跨语言适用**；校验脚本支持全部三种前缀。新注释统一用该语言行注释，不用块注释；原有文档注释原样保留。

## 4. 文档沉淀（宏观层）

- 每库一份沉淀文档：**库目录根部 `<库名>.md`**（如 `Glide.md`、`Retrofit.md`）；文档头部记录源码版本/commit 锚点。库目录结构识别不了时，问用户文档放哪。
- 内容六要素：问题背景、代码链路、设计思想、组件关系、应用侧使用方式、易错点。
- 沉淀文档以**教读者**为目标：假想读者只看文档（不翻源码），也应当能学会该机制的用法、理解设计取舍——写法上是教学口吻而非分析笔记。
- **机制章节模板**：每机制一章，内部固定四小节——`三问结论`（问题背景并入）→ `代码链路`（组件关系、应用侧用法并入）→ `设计思想` → `易错点`。形状统一便于复习、检索与横向对比；小机制按篇幅裁剪规则压缩为两节。
- **幂等更新**：同一机制已有章节 → **原地更新**，文档始终是"当前最佳理解"的快照，理解演进的时间线由 git 提供；仅当用户明说"保留旧分析做对比"时才另立章节。新机制 → 注意 `## / ### / ####` 层级，新增章节并与已有内容衔接；文档不存在 → 创建骨架后写入。
- **存量文档迁移规则**：沉淀文档旧结构与新模板冲突（旧章节形状、废弃圈号编号、失效外链、缺版本锚点）时——新增章节按模板衔接，**旧结构不顺手全局重构**；问题清单记入 §5 第 4 段请用户确认，全局重构属"该问"级任务（§1），另立任务确认范围后执行。
- **外链卫生**：「参考资料」收"文字结论 + URL"，不嵌依赖签名/时效的图床外链（会过期裂图）。

## 6. Quality Gates（交付前自检）

**机械门先跑（单一事实源是脚本，不在脑内重演清单）**：`python3 scripts/check_annotations.py <仓库根> <本轮改动文件...>` 九项全绿才算过——代码序列与 HEAD 一致（含行尾注释剥离）/ 上游英文注释保护 / 体系外【标签】 / 冒号式伪标签 / 旧 `注：` 前缀 / 行宽自适应 / 圈号残留 / 行尾标点（默认报错不写盘，`--fix` 才补号）/ 未带标签新块（? WARN，类头总论/方法头则罢）。任何 FAIL 先修再继续；改过脚本先跑 `--self-test`。

**语义三问**（每块新注释过一遍——机械门保证"不坏"，三问保证"好"）：

1. **删除测试**：删掉这条注释，读者会损失什么？——答不出损失即为死注释（对照 `references/quality-rubric.md` 六类），删；
2. **专名回查**：块内每个类名/方法名/常量名/阈值/线程名都 grep 过当前源码吗？——回查不过的改写或删（注释幻觉没有编译期检查，这是注释层唯一的机械防线）；
3. **链条检查**：它与前后注释构成阅读路径吗（沿链呼应、编号回指、上下连贯）？——孤立堆砌的重新组织。

**内容门**（逐条核对）：

1. 论断可回溯：每条论断自定档（代码事实 / 考据 / 推断 `[inferred]` / 外部观点过铁律 6），混档逐条标注；无"大概/应该/基本上"；每条注释锚定紧邻代码；查不到的明说未找到，没有"看起来合理"的编造
2. 覆盖完整：范围内新类均有类头概括（≤ 5 行）、复杂方法均有方法头（≤ 4 行），细节在关联代码处；多实现接口附了实现族谱；全链路分析已在入口方法开头给出完整调用链
3. 梯度与密度：四层梯度清晰，上层不下沉细节、下层不重复上层，沿链落笔前后呼应；重点重锤、平铺处克制；无无意义注释、无逐字翻译、无同一结论多处重复
4. 设计沉淀：重要设计点有【设计思想】块（或【为什么】问句形态）且回答了"为什么"；精妙处以"对 SDK 设计的启示是…"分点收尾、每条带适用条件；已按 `ROUTING.md` 路由同步沉淀文档与知识库对应大类；发现的注解技术已沉淀 `annotation-techniques.md`
5. 两面讲解：扩展点/配置点/回调契约均内嵌最小使用示例 + 场景 + "不用会怎样"（§3.2）；示例专名已回查（未检出标 `[inferred]`）；概念首次出现有解释、无默认读者已懂的跳步
6. 新角色习惯：分析中每个新类/新角色都过了复用思考（§3.3），够格的手法落了【设计思想】块
7. 路过即全检：既有中文学习批注已四检（准确/清楚/合并/删冗）且信息未丢；Javadoc 与上游作者注释零删改（发现其内容有误只记汇报待确认，不直接改）
8. 沉淀文档是宏观组织、未复制注释；新增章节与存量文档衔接时未顺手全局重构旧结构（§4）
9. 输出四段齐全，学习点可带走（思想/模式/坑 + 适用条件 + 深入去处），新概念均有讲解落点（§ 开头本质目的）——"分析完了但用户没学到东西"即本轮不合格
