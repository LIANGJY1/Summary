# 外部资料调研协议（SKILL.md §2 附属）

SKILL.md §2「外部资料调研（条件触发的三步闭环）」的执行要点清单。本文件只定**要求**，不定措辞——主题清单每次按目标库重新生成，防止照抄过期结构（Glide 有效的 9 主题清单换到 OkHttp/Retrofit 即不适用）。

## 要素清单（调研代理提示词必须包含）

1. **按机制拆主题**：主题清单按当前库的机制/链路逐个列出（Glide 主链批次实例：生命周期绑定 / into 复用与请求树 / 请求状态机与尺寸协商 / 三级内存缓存与引用计数 / EngineJob-DecodeJob 线程模型 / 三环 Generator 调度 / 解码采样与变换 / 回调线程切换 / 易踩坑）。
2. **来源与质量要求**：中文技术社区（掘金 / 知乎 / CSDN / 博客园 / 厂商技术团队 / 知名个人博客）+ 官方文档；逐主题给"机制描述（2-5 句）+ 深入设计观点 / 易忽略细节 + 来源 URL"。
3. **只收确凿事实**：明确指示不猜测、不填"看起来合理的"；每条观点可回溯到具体文章；按主题组织浓缩结论返回。
4. **逐条对照本地源码验证**：要求代理用本地检出的源码逐条核实（提示词内给出源码路径与版本快照信息）——重点核实与"流行说法"冲突处、版本演进差异处（如文章讲 4.x 无头 Fragment 方案而本地是 5.x androidx Lifecycle）；验证结论随主题一并返回。
5. **勘误收集**：与本地源码冲突的流行说法单列一节——说法原文 + 源码证据 + 结论，供沉淀文档「参考资料」勘误小节收录（§4）。
6. **自包含**：代理看不到主对话上下文——本地源码路径、版本快照、主题清单、验证要求全部写进提示词（§3.4 子代理自包含教训适用）。

## 执行形态

- **后台 general-purpose 代理执行**（实测约百万 token、10+ 分钟），主对话只消化返回的浓缩结论，不自己零敲碎打地搜。
- 主对话消化分流：验实的观点 → 按需写进注释 / 沉淀文档；未验实但有价值 → 标 `[inferred]` 并注明来源（铁律 6）；冲突说法 → 勘误小节。
- 版本错位（文章讲旧版本机制）以本地快照为准：能对应本地仍存在的代码才可用；机制已移除的按【兼容性】注记处理，不进正文注释。

## 返回格式（固定 schema，主对话按此逐条消化）

每主题一节，观点逐条带验证状态；代理返回不合规格式时，主对话按此重整后再消化：

```
## <主题名>
- 【验实】观点（1-3 句）——佐证：<本地文件:行 或 机制名>
- 【未验实】观点（1-3 句）——来源：<URL>
- 【冲突】流行说法原文——本地源码证据 + 结论（供勘误小节收录）

## 勘误汇总
（与本地源码冲突的说法集中一节；无则省略）
```

验证状态只有三档：验实（代理已对照本地快照源码核实）/ 未验实（有价值但没核到）/ 冲突（与本地源码相反）。

## 实例锚点

Glide 主链批次（2026-08）：9 主题调研约 50 篇文章 → 抓出 2 处勘误（DecodeJob 优先级顺序说反、"5.0 默认 OkHttp"未证实）→ 落地为 DecodeJob.reschedule【为什么】块（磁盘缓存执行器单线程会饿死全局缓存读取）+ Glide.md「参考资料」节 + 知识库 design-principles 条目「执行器按任务耗时分区」。
