# 六类死注释病例集（SKILL.md §3.2/§6 附属）

低质量注释的症状与处方。自评（§6 三问）或抽检发现死注释 → 按处方返工；同类 ≥2 处 → 重读本文件再动手。六类的共同点：都违反注释六原则第一条"言简意赅"——**删掉这条注释，读者什么都没损失**。

## 1. 复述型

**病**：复述代码自明的行为——代码本身就是那句话的更精确表达。

```java
// 病：
// 【核心流程】onStart 里调用 Util.getSnapshot 拿快照然后遍历。

// 处方——讲行为背后非直观的部分：
// 【关键细节】先拍快照再迭代：onStart 等回调里可能再 track/untrack 改集合，
//   直接迭代 WeakHashMap 的 set 视图会抛 ConcurrentModificationException。
```

## 2. 翻译型

**病**：把标识符/条件逐字翻成中文（`// 如果 target 不为空则返回 true`）。

**处方**：写"这意味着什么"——空说明尚未登记、返回 true 说明已在册；或按判型讲边界与风险。翻译型与复述型常相伴出现：先问"删掉损失什么"，答不出即删。

## 3. 日记型

**病**：分析过程的叙事残留混进终稿（"接下来看 Engine.load 如何实现""这里我一开始理解错了"）。

**处方**：删除；链路走向改用【调用关系】回指具体符号（"下一环 HttpGlideUrlLoader"），不用"我接下来去看"的口吻。分析记录属于会话，不属于源码。

## 4. 万金油型

**病**：套在哪个类上都成立的话（"在整个架构中起承上启下的重要作用""体现了高内聚低耦合的设计思想"）。

**处方**：只写能唯一标识该处的信息——把类名换成隔壁类句子就塌，才有资格留下。判据来自 §3.2 论断分级：说不出"为什么是这里、为什么是这样"就不写。

## 5. 漂移型

**病**：注释与当前版本代码不符——上游演进了、或按旧版本文章/记忆写的（对着已 `@Deprecated` 的空壳讲活机制是重灾区）。

**处方**：以本地快照为准逐条核实（铁律 6、专名回查）；确认错误必须改，不将就；版本演进差异按【兼容性】注记处理。详见知识库条目「重标先考据当前版本机制」。

## 6. 占位型

**病**：有标签无内容——【设计思想】块只有一句"该类采用了优秀的设计模式"；或【TODO】烂尾（不说不清什么、不给检索线索）。

**处方**：说不清就不写，宁缺勿滥；【TODO】必须带"哪里没分析清楚 + 下一步查什么"（如"keep-alive 连接复用对并发上限的影响未确认，查 HttpURLConnection 对象复用条件"）。
