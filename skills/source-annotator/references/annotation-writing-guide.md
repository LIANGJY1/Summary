# 注释写作指南（内容质量，v1.26 新增）

> 本指南管注释"写什么、怎么说明白"；形状（标点/折行/标签合法）归 annotation-format.md，
> 机械校验归 check_annotations.py。全部示例取自真实标注（AAOS13 输入系统四批），
> before 为初版落盘原文——它们不是假想反例，是真实产出。

## 1. 总纲：先问对问题，再平实作答

源码注释与语言笔记（问答式笔记）的三点差异，决定了质量门形态不同：

| | 语言笔记 | 源码注释 | 推论 |
|---|---|---|---|
| 问题来源 | 用户问了，笔记回答 | 没人提问，注释者替读者**预判**问题 | 问题只存在于写前：来自阅读阻力点（§3），是**选材纪律** |
| 与载体关系 | 笔记自足 | 注释与代码共生，代码就在读者眼前 | 唯一价值=代码读不出来的那层（为什么/边界/后果/去向） |
| 错误代价 | 人读时可能起疑 | 被未来的人和 AI 当事实吸收 | 正确性永远第一 |

**平实三则**（"说不明白话"的三大病根）：
1. 一句一事：一个句子只表达一个意思；长句拆短句。
2. 不拿读者考试：问句仅限【为什么】标签，其余块用陈述句直答。
3. 少嵌套：括注最多一层，破折号解释一句话内最多一次。

**起草期真实教训**（指南自身犯过，引以为戒）：曾把方法头骨架改写成
`读线程为何分"取—加工—投递"三段、且加工与投递必须换锁？批量拉取摊薄锁与系统调用开销；……`
被用户否决，病根三条：问句开场用了读者还不懂的黑话；骨架地图被删，读者失去定位；
一个长因果链塞了三件事。修正后（骨架保留、why 就近括注、高危点单独一句）：

```
// 【核心流程】主循环每圈五个阶段，一次只拉一批（摊薄锁与系统调用开销）：
//   1.锁内取待刷新配置与最近超时 → 2.getEvents 阻塞拉取 → 3.锁内加工 → 4.定时器检查 → 5.锁外 flush。
//   flush 必须锁外：下游会回调回来抢 mLock，锁内 flush 即死锁。
```

## 2. 读者画像：写什么由谁读决定

| 读者 | 阅读模式 | 要什么 | 对应标签 |
|---|---|---|---|
| 路过者 | 追一个调用跳进来 | 一句话定位：这块的角色、出口在哪 | 【调用关系】、类头一句话 |
| 通读者 | 顺主链读 | 链路图、阶段交接、每个"为什么在这等/锁/排队" | 【核心流程】【线程模型】 |
| 改动者 | 要改这块代码 | 不变量、顺序契约、波及范围 | 【注意事项】【状态管理】 |
| 学习者 | 提炼设计思想 | 矛盾→解法→代价→可迁移 | 【设计思想】【为什么】 |

- S1：主链枢纽处四类兼顾——文件头服务路过者，方法头服务通读者，伤疤服务改动者，设计思想服务学习者；别把四类内容全堆在类头。
- S2：写前判定本仓主要读者。学习型仓库（如 AAOS13_study）以通读者+学习者为主，重机制因果与设计思想；业务仓库以改动者为主，重不变量与坑。同一处代码，两种仓的注释重心不同。

## 3. 阻力点清单：问题的 12 个来源

问题不是凭空的，来自代码的阅读阻力。每类阻力=读者心里的一句原话。

| # | 阻力点 | 读者原话 | 实例（本会话） |
|---|---|---|---|
| 1 | 链路交接 | 到这儿之后去哪了？ | NotifyKeyArgs 入队后流向何处 |
| 2 | 线程/锁边界 | 这谁在调？锁着吗？ | loopOnce 的 flush 为何在锁外 |
| 3 | 顺序契约 | 为什么必须先 A 后 B？ | 设备增删事件先于数据事件上报 |
| 4 | 状态机 | 这个标志/队列何时变？ | mFirstTouchTarget 链、last/current 双快照 |
| 5 | 伤疤/防御 | 这行防什么事故？ | SYN_DROPPED 自愈 |
| 6 | 魔法数/阈值 | 为什么是这个数？ | ANR 5s、app switch 0.5s、socket 32KB |
| 7 | 跨进程/协议 | 对面是谁？断了怎样？ | socketpair 双端、DEAD_OBJECT 拆连接 |
| 8 | 性能取舍 | 为什么绕这么远/攒批？ | MOVE 攒批对齐 vsync、批量拉取 256 |
| 9 | 历史兼容 | 为什么还留着？ | setInputWindows 遗留接口 |
| 10 | 生命周期 | 谁创建谁销毁、何时？ | Connection 与窗口存活绑定 |
| 11 | 扩展点/契约 | 我怎么接？不接会怎样？ | onInterceptTouchEvent |
| 12 | 反直觉设计 | 为什么不直接做？ | key repeat 为何用户态合成 |

**用法**：写前扫目标代码，标出命中的阻力点——这份清单就是写作任务清单。
**先有问题清单，后写注释**；写完的每块都能对号入座一类，对不上的块删。

## 4. 块分三种，形状各不同

写前先认定这块是什么性质，按性质选形状——**别用论证块取代地图块**（§1 教训即此）：

| 块型 | 回答的问题 | 形状 | 常见位置 |
|---|---|---|---|
| 地图块 | 这块的结构/流程是什么 | 骨架、阶段链、编号列表合法且必要；why 用括注就近挂 | 文件头、方法头 |
| 释义块 | 这行/这字段是干什么的、防什么 | 首句直给结论，一到两句，不展开 | 行旁、字段旁 |
| 论证块 | 为什么这样设计、可迁移什么 | 根因→实现→收益→代价→启示；只有这里允许展开与问句（【为什么】） | 设计节点 |

## 5. 内容六约束（优先级：正确性 > 平实易懂 > 结论先行 > 最短完整 > 因果后果 > 示例完备）

冲突时舍后者保前者。每条给定义、自查、真实 before→after。

### 5.1 正确性
事实核验（脚本第 10 项是底线不是替代）；跨层调用论断（"经 X 的返回值/出参回传"类）必须
grep 方法签名本体——真实事故：addToDisplay 的通道经出参 outInputChannel 回传，被误写为返回值。

### 5.2 平实易懂
一句一事、短句、不考试、少嵌套。自查：朗读一遍，凡需要换气才能读完的句子重写。

### 5.3 结论先行
首句给答案/定位，分类词与铺垫后移。
- before：`与 notifyKey 同构的触摸入站：校验 action/pointer 一致性，锁外 policy 预处理，打包 MotionEntry 入队。`
- after：`【核心流程】触摸"派给谁"入队时决定不了（要等坐标命中状态机），入队这里只做一致性校验与 policy 预处理——拦截点后移是触摸与按键流程的本质差异。`

### 5.4 最短完整
删除测试（删了损失什么）+ 段落测试（同块内两句讲同一件事的合并）。

### 5.5 因果后果
机制必须连着"不这样会怎样"，就近挂（括注或紧随句），不单独成段议论。
- before：`【数据流】出口：打包 NotifyKeyArgs 进入 QueuedInputListener 队列，flush 后流向 Dispatcher 链。`
- after：`【数据流】出口：入队即返回，不直接调下游——直接调会让 Reader 持锁状态被 Dispatcher 侧回调撞死锁；队列把"产出（持锁）"与"投递（锁外 flush）"切成两个加锁期。`

### 5.6 示例完备
凡阻力点 11（扩展点/契约）及应用可感知机制，必须内嵌最小示例+场景+不用会怎样。
四批 29 文件此条执行率为零——历史欠账，新标注不得再犯（InputListener.h 的接入示例即补写样板）。

## 6. 表达细则（横切六则，与六约束并列逐块检查）

1. **列表优先**：可枚举内容（并列/步骤/分支/条件）一律转列表（有序 1. 2. 3.，无序 -），不挤进长句。自查：一段话里出现两个以上分号并列，就是该列表没列表。
2. **换行美观**：列表项一行一义、项尾带标点；项内续行比首行内容再缩进一级对齐；相邻列表项长度宜均匀，避免锯齿状长短交替。自查：遮住文字看行尾轮廓是否整齐。
3. **术语一致**：同一概念全篇同一个词（"通道"与"连接"二选一），缩写/全称首次出现时给定义。自查：改词时全局搜索旧词，防漂移。
4. **主动语态**：动词开头、主语明确（"检查超时"而非"超时被检查"）；"被"字句只在真正强调受事时用。自查：数"被"字。
5. **主旨自足、细节指针**：单块主旨不翻别的文件就能懂；细节走指针（见 X 处【标签】）不复制——平衡点是"结论自足，论据可跳转"。自查：遮住指针，块内结论仍成立吗。
6. **数字带单位与出处**：阈值/时长写成"5s（DEFAULT_INPUT_DISPATCHING_TIMEOUT，5s×硬件倍率）"而非裸数；单位全篇统一。自查：每个裸数字问"从哪来、单位是什么"。

## 7. 深度组合（L1 是什么 / L2 怎么工作 / L3 为什么 / L4 何时失效 / L5 可迁移）

- L1 禁止单独出现，只能作 L2/L3 的开头事实句；"逐字翻译"与"结构化骨架"的区别在于
  骨架是否压缩了信息（五阶段链压缩 60 行代码=合法；翻译 if 条件=死注释）。
- 组合公式：主链枢纽=L2+L3；伤疤=L4；设计节点=L3+L5；数据结构字段=L2（不变量）；扩展点=L2+契约。

## 8. 五个场景模板

1. 链路交接：【数据流】X 打包 → 入队 → 锁外 flush → 下一站；不直接调的原因。
2. 伤疤：【注意事项】症状（看似多余）→ 防的事故（依据）→ 失效后果。
3. 契约/扩展点：【关键细节】契约一句话 → 怎么接（最小示例）→ 场景 → 不接/接错会怎样。
4. 状态机：【状态管理】不变量 → 合法转移 → 非法转移的防线 → 双账本指认。
5. 设计思想：根因 → 实现 → 收益 → 代价 → 启示（带适用条件）。

## 9. 生成与改写流程

写前三步：判读者画像（S2）→ 列阻力点清单（§3）→ 定批次主链与块型（§4）。
写中：按模板形状写；落笔前默念对应阻力点的读者原话。
写后三测（逐块）：问题测试（能对号一个阻力点吗）、首句测试（第一句给答案了吗）、
删除测试（删了损失什么）。

写后自查（跑脚本前，拦住惯性错误、省一轮全量校验）：
- 每行行尾有标点（续行也算）；括号/引号配平、括注不跨行；
- 无 Xxx/占位词；专名与仓内写法逐字一致（含大小写）。

自查通过再跑机械门；格式修正的迭代轮用 `--fast`（跳过专名回查，秒级），
交付前必须跑一次不带 `--fast` 的全量。
