# 源码批注指南

本文件是运行时唯一的内容与版式指南。历史范文和完整演进记录在 `../archive/references/`，只在回归或追溯时读取。

## 写前：决定讲什么

### 读者与阻力点

先判断主要读者：路过者需要角色定位，通读者需要链路和阶段交接，改动者需要不变量与风险，学习者需要设计取舍和可迁移启示。

从代码列出阻力点清单，每个新增块至少对应一个阻力点：

1. 链路交接：这之后去哪？
2. 线程或锁边界：谁在调、锁着吗？
3. 顺序契约：为什么必须先 A 后 B？
4. 状态机：标志、队列和双集合何时变化？
5. 伤疤防御：这行防什么事故？
6. 魔数阈值：为什么是这个数，改了会怎样？
7. 跨进程协议：对面是谁，断了怎样？
8. 性能取舍：为什么绕路、攒批或懒加载？
9. 历史兼容：为什么还保留？
10. 生命周期：谁创建、谁销毁、何时发生？
11. 扩展契约：怎么接入，不接会怎样？
12. 反直觉设计：为什么不直接做？

### 代码判型

先判型再落笔：胶水/适配讲两侧接口差异与错误处理；接口/抽象类讲契约和实现族谱；实现代码讲嵌入整体的方式与改动风险；算法讲真实数据结构和复杂度；配置讲自由度、组合风险和生命周期；编排流程讲顺序约束、事务性和可恢复性。

## 写中：信息梯度与形状

四层阅读梯度：文件头回答“为什么有它”，类头回答“它是什么”，方法头回答“怎么工作”，关键行回答“为什么这样写”。上层不下沉细节，下层不重复上层。

文件头可放一句总论、主链 `A → B → C` 和阶段位置；类头通常 2–5 行，简单委托类只写一句；复杂方法头写职责、阶段骨架和线程/时序边界；字段说明紧邻字段，设计原因紧邻决策代码。

三种块形状：

- 地图块：总论、阶段链和编号骨架。
- 释义块：首句直接给结论，通常一两句。
- 论证块：根因 → 实现 → 收益 → 代价 → 可迁移启示，唯一允许展开问答。

调用链用箭头，层级用 `└─`/`├─` 树；编号必须与真实执行顺序一致；跨文件导引用【关联代码】。块间用空注释行分隔，空行会开启新块。

## 标签与语言

注释块必须以以下 17 个标签之一开头：

`【设计思想】` `【核心流程】` `【调用关系】` `【数据流】` `【执行时机】` `【生命周期】` `【线程模型】` `【状态管理】` `【为什么】` `【关键细节】` `【性能考虑】` `【安全考虑】` `【兼容性】` `【注意事项】` `【关联代码】` `【TODO】` `【面试高频】`。

类头总论不加标签；不要发明新标签。`目的：`、`实现：`、`收益：`、`替代：`、`启示：`、`根因：`、`防线检查：`只可作为禁止的伪标签，字段档案中的“是什么：”等内容引导词合法。

### 17 个标签的统一版式与示例

所有标签都采用同一套视觉语法：

- 首行直接给结论，不先铺垫；
- 后续每行只表达一个信息点，默认使用 `// 1.`、`// 2.` 排列；仅明确无顺序时使用 `// -`；
- 原因、后果、边界和证据分行写，不用分号挤在一行；
- 示例代码使用真实代码行，不能把整段代码伪装成注释；
- 相邻但独立的注释块之间留一行空注释。

### 有序列表与无序列表

列表不是装饰，而是表达关系的工具：

| 形式 | 什么时候用 | 示例语义 |
|---|---|---|
| 有序列表 `1. 2. 3.` | 默认选择；用于真实先后、阶段、优先级、操作步骤，或前置句明确说“几个/多个/分为” | 先校验，再入队，最后回调 |
| 无序列表 `-` | 仅在明确强调“无顺序”的集合、属性、风险或候选项时使用 | 一组可任意交换顺序的属性 |
| 嵌套列表 `  -` | 一个步骤下还有并列子项 | 某阶段包含两个检查点 |

使用规则：

- 默认优先使用有序列表；读者可以按编号扫描、复述和回指；
- 只有明确表达无顺序的集合、属性、风险或候选项时，才使用无序列表；
- 顺序改变会改变结果时，必须使用有序列表；
- 前置句出现“三个问题”“两个阶段”“以下几点”“分为几步”等数量或结构提示时，后续统一使用有序列表；
- 前置句以冒号引出列表时，冒号前必须是完整结论；列表项数量必须与前置句声明的数量严格一致；
- 代价、适用条件、反例等收束内容不占用编号，放在列表后用完整句补充；
- 同一层不要混用 `1.`、`-`、`*`；
- 只有主流程使用有序列表时，子项才使用缩进的无序列表；
- 每一项都是完整句子，以标点结束；
- 不要把多个并列事项写成一行分号串列；
- 列表项超过约 5 项时，优先合并同类项或拆成两个注释块。

```java
//【核心流程】请求处理必须按以下顺序推进。
// 1. 先校验请求参数，拒绝不满足前置条件的请求。
// 2. 再将请求放入队列，交给执行线程处理。
// 3. 最后在锁外触发回调，避免外部代码重新进入当前对象。

//【设计思想】这个阶段同时解决三个彼此独立的问题。
// 1. 降低锁竞争，缩短持锁时间。
// 2. 隔离外部回调，避免死锁。
// 3. 延迟昂贵操作，减少无效分配。

//【核心流程】一个阶段包含多个并列检查点。
// 1. 进入调度阶段。
//   - 检查任务是否已取消。
//   - 检查是否已有相同任务在执行。
// 2. 进入执行阶段。
```

| 标签 | 适合回答的问题 | 推荐内容顺序 | 示例首句 |
|---|---|---|---|
| `【设计思想】` | 为什么采用这种结构？ | 矛盾 → 做法 → 收益 → 代价 → 适用条件 | `【设计思想】把持锁生产和锁外投递拆成两个阶段：` |
| `【核心流程】` | 主链路怎么走？ | 入口 → 阶段 → 出口 | `【核心流程】请求沿入口、调度器、执行器到达回调。` |
| `【调用关系】` | 谁调用谁？ | 调用者 → 被调者 → 回传 | `【调用关系】Reader 生成事件后交给 Dispatcher。` |
| `【数据流】` | 数据如何变化和流转？ | 来源 → 转换 → 去向 | `【数据流】原始 URL 先规范化，再生成缓存键。` |
| `【执行时机】` | 什么时候执行？ | 触发条件 → 执行点 → 跳过条件 | `【执行时机】只有请求首次进入时才创建任务。` |
| `【生命周期】` | 谁创建、谁持有、谁销毁？ | 创建 → 使用 → 释放 | `【生命周期】对象由请求创建，完成回调后释放。` |
| `【线程模型】` | 在哪个线程运行？ | 线程归属 → 切换点 → 同步边界 | `【线程模型】读取在线程池执行，回调切回主线程。` |
| `【状态管理】` | 状态如何转移？ | 不变量 → 合法转移 → 防线 | `【状态管理】只有排队状态的任务才能进入执行态。` |
| `【为什么】` | 为什么不能直接这么做？ | 问题 → 原因 → 后果 | `【为什么】为什么先入队再回调？` |
| `【关键细节】` | 哪个细节最容易漏？ | 细节 → 影响 → 使用方式 | `【关键细节】缓存键不包含请求头。` |
| `【性能考虑】` | 性能取舍是什么？ | 瓶颈 → 优化 → 代价 | `【性能考虑】缓存键保持廉价，避免重复解析 URL。` |
| `【安全考虑】` | 防什么攻击或误用？ | 入口 → 校验 → 失败后果 | `【安全考虑】跨进程请求必须先校验调用者身份。` |
| `【兼容性】` | 为什么保留旧逻辑？ | 旧行为 → 兼容分支 → 移除条件 | `【兼容性】旧版本未提供该回调，因此保留空实现。` |
| `【注意事项】` | 修改时最容易踩什么坑？ | 风险 → 事故 → 修改边界 | `【注意事项】此处不能提前释放引用，否则回调会丢失。` |
| `【关联代码】` | 下一步读哪里？ | 当前角色 → 关联位置 → 阅读目的 | `【关联代码】继续阅读 EngineJob，理解结果合并。` |
| `【TODO】` | 哪个事实尚未核实？ | 未知点 → 检索线索 → 完成条件 | `【TODO】尚未确认该回调是否总在主线程执行。` |
| `【面试高频】` | 面试如何简洁回答？ | 一句话结论 → 关键机制 → 常见追问 | `【面试高频】这里考查的是生产与投递的解耦。` |

下面给出可直接贴到源码旁的排版样式。多行块统一“标签首句 + 缩进列表”；标签必须紧贴注释符号，写成 `//【标签】`，不写成 `// 【标签】`；单句标签只保留一行，避免为了凑格式增加空话。

```java
//【设计思想】把持锁生产和锁外投递拆成两个阶段：
// 1. 持锁阶段只负责生成事件，避免回调外部组件。
// 2. 锁外阶段再投递事件，降低死锁和长时间占锁的风险。
// 这一拆分会引入额外队列和一次状态交接，仅在存在外部回调时才值得采用。

//【核心流程】请求沿入口、调度器、执行器到达回调。
// - RequestBuilder → Dispatcher → Executor → Callback。

//【调用关系】Reader 生成事件后交给 Dispatcher；Dispatcher 处理完成后回传结果。

//【数据流】原始 URL → 规范化 URL → 缓存键 → 磁盘查找。

//【执行时机】只有请求首次进入时才创建任务；命中缓存时直接返回，不再创建执行任务。

//【生命周期】对象由请求创建，执行期间由任务持有，完成回调后释放。

//【线程模型】读取在线程池执行，结果通过 Handler 切回主线程；锁只覆盖状态更新。

//【状态管理】只有排队状态的任务才能进入执行态；完成态和取消态都禁止再次入队。

//【为什么】为什么先入队再回调？
// 1. 入队时仍持有内部锁，直接回调可能重新进入当前对象并形成死锁。
// 2. 先入队再在锁外投递，可以把状态更新和外部调用隔离开。

//【关键细节】缓存键不包含请求头；请求头只影响网络请求，不影响同一资源的内容缓存。

//【性能考虑】缓存键保持廉价，避免每次查缓存都重新解析和分配 URL 对象。

//【安全考虑】跨进程请求必须先校验调用者身份；校验失败时直接拒绝，不进入后续状态机。

//【兼容性】旧版本未提供该回调，因此保留空实现；只有目标版本都支持新回调后才能移除。

//【注意事项】此处不能提前释放引用，否则异步完成时回调对象可能已经不可达。

//【关联代码】继续阅读 EngineJob，理解多个请求如何合并同一份结果。

//【TODO】尚未确认该回调是否总在主线程执行；需要继续检查调用方的线程切换点。

//【面试高频】这里考查的是生产与投递的解耦。
// 1. 生产阶段保护内部状态，投递阶段隔离外部回调。
// 2. 这样既降低死锁风险，也让线程边界更容易测试。
```

新注释使用所在语言的行注释：`//`、`#` 或 `--`。原有 Javadoc、KDoc、license 和上游行注释保持原样。

每行以标点结束；括号不跨行；箭头不悬在行尾；列表一项一义；行宽不超过宿主文件 HEAD 既有最大显示列（下限 130）。

## 内容质量门

每条批注按以下优先级自检：

1. 正确性：专名、签名、常量、线程和阈值已回查当前源码；跨层论断核对方法签名。
2. 易懂：一句一事，短句，少嵌套，结论先行。
3. 增量：解释代码读不出的原因、边界、后果或去向，不复述代码。
4. 因果：机制说明紧邻“不这样会怎样”。
5. 证据：代码事实免标；git/issue 为考据；推断标 `[inferred]`；外部观点先核实。
6. 连贯：沿入口到出口组织，单一总论只出现一次。

重要设计点的【设计思想】必须说明解决的矛盾、实现、收益、替代代价和“对 SDK 设计的启示”；启示同时给适用条件和选错代价。

API、配置点、回调和扩展点必须给最小示例、真实使用场景以及不接入的后果。示例中的符号先回查，未检出的依赖标 `[inferred]`。

## 五种高频模板

1. 链路交接：`【数据流】产出 → 入队 → 锁外投递 → 下一站`，补充不直接调用的原因。
2. 伤疤防御：`【注意事项】看似多余的条件 → 防止的事故 → 失效后果`。
3. 扩展契约：`【关键细节】契约 → 最小示例 → 使用场景 → 不接后果`。
4. 状态机：`【状态管理】不变量 → 合法转移 → 非法转移防线`。
5. 设计思想：根因 → 做法 → 收益 → 代价 → 适用条件 → 反例。

## 字段档案与大篇幅讲义

多赋值、跨生命周期且难从名字理解的字段，用【关键细节】字段档案：是什么、全部赋值点及触发时机、取值域、赋值链路。

只有读者会在概念上大面积卡住时才使用分章讲义。用 `════` 分章和序号章题；普通服务保持克制。逐行通读是用户显式要求的草稿模式，不是默认终稿。

## 写后验收

逐块执行三测：删掉会损失什么；首句是否直接回答；是否能对应一个阻力点。再检查无死注释、无半截句、无逐字重复、无上游注释改写。

六类死注释：复述型、翻译型、日记型、万金油型、漂移型、占位型。发现同类达到两处时，读取归档的 `quality-rubric.md` 返工。

机械验收使用 `scripts/check_annotations.py`：十项全量检查通过后，再做语义抽检。批量任务还要报告纳入、跳过、失败和未逐条审读文件。

## 两面讲解示例

两面讲解应保持为一块贴近代码的注释：首句说明接入场景，次句说明使用方式和不接入后果，示例代码紧跟其后。不要把解释拆成文档标题，也不要把整段 Java 代码伪装成注释。

```java
//【关键细节】应用侧接入缓存扩展点。
// - 场景：需要替换默认缓存策略时，在构建客户端前配置自定义缓存。
// - 接入：使用缓存扩展点设置自定义容量和淘汰策略。
// - 不接入：继续使用默认缓存策略。
// - 接错扩展点：代码可以编译，但自定义配置不会生效。
builder.setMemoryCache(new LruResourceCache(20 * 1024 * 1024));
```
