# Source Analysis Inline Annotation Skill（源码注释化分析）

## Purpose

这个 skill 把"源码分析"直接落进源码本身——以注释形式标注分析结论，**不再单独输出文章或文档**。

分析结论以注释形态分布在代码中：

1. 文件头注释块 = 一句话总论 + 主链 + 阶段骨架
2. 阶段边界注释 = 阶段拆分，贴在边界代码处
3. 设计点注释 = 设计思想，贴在关键节点
4. 稀疏行内注释 = WHY / 边界 / 误区

核心目标只有四个（形态变了，目标不变）：

- 结论必须有源码依据 → 每条注释都锚定紧邻代码，推断标 `[inferred]`；
- 分析必须先切阶段边界 → 边界处落【阶段】注释，而不是在文章里切；
- 设计思想必须讲，但不能空泛 → 【设计】注释块贴着源码写；
- 表达必须简洁，避免教程式堆砌 → 注释比文章更克制，不逐行解释。

全流程 / 全链路 / 架构解析型任务的额外目标（以注释形态落实）：

- 先讲要解决的问题 → 文件头注释块的问题背景
- 先讲核心矛盾 → 【设计】注释块
- 先给分层架构 → 类 / 模块头注释
- 提炼可复用模式 → 文件头收口注释或关键设计点

## When To Use

出现以下任务时应优先使用本 skill：

- "直接在源码里用注释标注这条链路 / 这个机制"
- "把这个分析写进源码注释，不要单独出文档"
- "给这段源码加带设计思想的分析注释"
- "在注释里把阶段边界标清楚"
- "补设计思想 / 架构思维 / 关键点注释"
- "注释太啰嗦了，压缩成更抽象的表达"

## Input Contract

用户最好提供：

- 主题或机制名称
- 分析范围（文件、类、方法、入口）
- 想解决的核心问题或读者最关心的疑问
- 注释风格要求：
  - 注释语言：中文 / 英文（默认跟随文件现有注释语言，混合时取主流）
  - 密度：只标关键节点 / 尽量全面
  - 是否保留设计思想注释
  - 标记风格：是否使用【阶段】/【设计】等前缀
  - 是否加文件头总论注释块
  - 是否用 ASCII 主链

范围不明确 → 先收窄边界（确认文件、入口、阶段数），再落注释，不猜测。

全流程任务还需主动确认或补足：

- **问题背景**：这个机制在解决什么问题，不这么设计会有什么后果。
- **核心矛盾**：速度与准确性、统一入口与职责分离、生命周期与可见性边界、控制权与执行权分离等。
- **读者目的**：理解源码实现 / 复用架构思路 / 技术分享。

## Core Workflow

### 1. Source Grounding

先通读，再落笔。每条注释必须能锚定到紧邻的代码：

- 文件路径
- 类 / 方法
- 代码行为或调用结果

禁止先凭印象写设计注释，再反向找源码凑证据。推断的内容标注 `[inferred]`。

### 2. Stage Boundary First

先切阶段，再在边界代码处落注释。

推荐边界：

- 生命周期边界
- 进程 / IPC 边界
- 模块职责边界

每条阶段边界注释至少回答四件事，直接写在边界代码上方：

1. 谁触发这一阶段
2. 这一阶段负责什么
3. 交接发生在哪里
4. 下一阶段由谁接管

阶段骨架（含主链）先落在文件头注释块，再在每处边界代码展开局部注释。

全流程任务在阶段骨架之前先立"架构骨架"，也放在文件头注释块：

1. 这个系统要解决什么核心问题
2. 这条链路背后的核心矛盾是什么
3. 为什么必须拆层，而不是做成一个大函数 / 大模块
4. 每一层各自回答什么问题

成熟的分析顺序（注释形态）：

> 文件头（问题背景 → 核心矛盾 → 分层 → 主链）→ 阶段边界注释 → 关键机制注释 → 设计抽象注释

### 3. Concrete First, Then Lift Once

每条注释的表达顺序：

1. 先描述紧邻代码在做什么（事实）
2. 再给一句解释
3. 最后只抬一层抽象，点设计价值

同一处只允许一层抽象。不要在同一处连续堆叠（架构、模式、可维护性、扩展性一起讲），不要在同一处连续更换命名。

### 4. Design Thinking Must Stay Source-Backed

设计思想以【设计】注释块贴在关键节点，紧凑格式：

1. **设计目的**：解决什么矛盾。
2. **实现方式**：源码里由哪些层 / 对象承担。
3. **收益**：1-3 个（解耦、扩展、容错、定位清晰）。
4. **替代方案**：一句话点出一种更直观却更差的组织方式。

替代方案不展开成长篇评审，但至少让读者知道这是权衡后的写法。

抽象模型表达（用户偏好时），写在源码解释之后：

> UI事件 → 统一入口 → 数据识别 → 策略分发 → 行为执行
> 本质：事件驱动 + 数据驱动 + 策略执行。价值：入口统一、分支清晰、扩展方便。

注意：

- 抽象模型必须紧跟代码事实；
- 不能反复重复同一个模型；
- 源码只支撑"分发"，就不要拔高成"完整治理体系"。

**通用"为什么这么设计"分析模板（一句话）**：

> 问四问再落注释：① 根因——此设计解决的矛盾，及被更简单方案遗漏的关键信息属于谁；② 代价——更直观的替代方案（如统一入口/单一路径）为何不可行，强行简化的代价；③ 场景——每条分支/入口对应什么真实场景，让读者对号入座；④ 反例——简化后或选错分支的具体后果。最后点出内在收敛点——表面多样在哪个 key/接口/时机上统一。
>
> 落注释：决策点上方一个【设计】总注（根因→代价→场景→反例→收敛点，集中讲设计），每条分支只留一行场景标注，执行/分发处标注"场景 X 的实现"。

> 案例：`Glide.with(Context/Activity/Fragment/View)` —— ① 根因：生命周期属于 Activity/Fragment，Context 拿不到；② 代价：统一成 Context 只能运行时 instanceof 猜，猜错不报编译错、行为不可预期；③ 场景：页面/列表页/通知/自定义 View 四种加载；④ 反例：页面用应用级入口永不暂停浪费流量、列表页用 Activity 入口屏外继续加载；收敛点：多入口只是"如何拿 Lifecycle key"的差异，真正统一在内部。


### 5. Depth Control

注释密度控制。每层只保留：

- 职责
- 核心方法
- 关键机制
- 设计抽象
- 需要提醒的边界或限制

优先压缩：

- 基础概念科普
- 重复 paraphrase
- 逐行解释且无新增信息的代码说明
- 多个注释重复同一结论
- 用不同术语重复讲同一设计点

默认目标不是"讲全"，而是"讲准以后再讲尖"，且注释密度低于文章。

## Annotation Placement（注释放置规范）

按以下层级落注释，形成"读者沿注释就能走完的链路"。

### 文件头注释块（总论 + 主链 + 阶段骨架）

放在第一个类 / 入口函数之前（保留原有 license / header）：

```
/**
 * 一句话总论：本模块在链路中承担 X。
 *
 * 主链：A → B → C → D
 *
 * 阶段骨架：
 *   阶段 1 触发：xxx()       ← 位置
 *   阶段 2 交接：xxx() → yyy()  ← 位置
 *   阶段 3 收口：xxx()       ← 位置
 *
 * 问题背景 / 核心矛盾 / 分层（全流程任务）
 */
```

### 类级注释（职责 + 设计抽象）

对核心类补文档风格头注释：职责一句话、关键机制、设计抽象、边界。不逐类覆盖，只标核心类。

### 阶段边界注释（四问）

写在边界代码上方：

```
// 【阶段 2】参数校验 → 状态收口
// 触发：阶段 1 的 dispatch() 调用本方法
// 职责：校验入参并组装内部状态
// 交接：onReady() 回调交给阶段 3
// 接管：Handler.post 的 stage3 任务
```

### 方法级注释（职责 / 机制 / 边界）

只对非显而易见的方法补注释：职责、关键机制、线程 / 时序 / 版本边界。明显的 getter/setter、纯委托不注释。

### 行内 WHY 注释（稀疏）

只在不看注释就看不懂的地方落：

- trade-off：`// 自研池替代库内置 —— 需要自定义重试逻辑`
- 不变量：`// 必须在主线程 —— 内部切后台做 IO`
- 顺序依赖：`// 必须先 super.onCreate 再注册观察者`
- 会破坏什么：`// 调序会破坏 ViewHolder 缓存复用`

### 设计点注释块

贴在关键节点（入口分发、状态收口、桥接层、交接点）：

```
// 【设计】统一入口 + 状态分流
// 目的：把"谁能做什么"和"怎么做"解耦
// 实现：XxxDispatcher 统一收口，按 tag 分发
// 收益：入口唯一、分支清晰、扩展只需加 tag
// 替代：if/else 直写 —— 更直观，但分支散落、新增逻辑要改入口
```

### 误区 / 注意点注释

贴在实际容易写错的代码位置：

```
// 【注意】这里不能提前 return —— 否则后续清理不会执行
```

## Annotation Rules（标注规则）

### Rule 1: 先给链路，再拆细节

文件头注释块先给一条 ASCII 主链，再在各阶段边界处展开局部细节。

### Rule 2: 复杂处才画"图"

源码注释里 Mermaid 不渲染，改用紧凑 ASCII：

- 主链：单行 `A → B → C`
- 跨层交接：阶段注释的"交接"行
- 真正的边界 / 职责分离：不超过 3-5 行的分层 ASCII 块

画不出来就写清楚，不硬画。自检三问：

1. 这条 ASCII 是在解释顺序，还是在解释边界 / 职责？
2. 没有它，读者能不能一次看清跨层交接？
3. 它是降低理解成本，还是在装饰注释？

### Rule 3: 设计思想要短促、点透

【设计】注释块默认密度：抽象模型一句 → 本质判断一句 → 1-3 个价值点。不展开成长教程。

### Rule 4: 用户说"太啰嗦"时如何收缩

按顺序删减：

1. 删除铺垫和过渡注释
2. 删除重复的"为什么重要"
3. 多行设计注释压成一行抽象
4. 保留：文件头主链、阶段边界、一层设计抽象

默认保留：主链、关键边界、一层设计抽象、必要 ASCII。

### Rule 5: 用户说"设计思想优先级高"时如何补强

不增加注释长度，在关键节点补 1-3 句【设计】注释：

- 这层负责什么
- 为什么放在这一层
- 这种组织方式解决了什么问题

优先补的位置：入口分发、状态收口、桥接层、Binder / 系统服务交接点、文件头的问题背景与核心矛盾。

## Knowledge-Point Mode（知识点型注释）

目标是单个类 / 机制而非链路时，用一处连贯注释块替代文章式拆解，落在该类 / 机制的头注释中：

1. 主题定义
2. 核心作用
3. 关键结构或核心方法
4. 工作流程 / 调用链（一行 ASCII）
5. 设计要点 / 易错点（【注意】）
6. 总结（一句话）

## Quality Gates

交付前检查：

1. 每条注释是否都锚定紧邻代码，没有悬空
2. 是否先标边界，再讲细节
3. 设计思想是否贴着源码，没有空谈
4. 是否有多个注释重复同一件事
5. ASCII 主链是否真的降低理解成本
6. 注释密度是否克制（没有逐行注释）
7. 同一处是否只抬一层抽象
8. 推断内容是否标注 `[inferred]`
9. 注释语言 / 风格是否与文件现有注释一致
10. 是否停在当前阶段边界，没有偷渡下一阶段内容

全流程任务再检查：

11. 文件头是否写清问题背景，而不是直接冲进流程
12. 是否至少有一组核心矛盾或 trade-off（【设计】注释）
13. 是否有分层表达，而不是只有调用顺序
14. 关键设计点是否回答了"为什么这么设计"
15. 是否提炼出可复用模式（文件头收口）

## Must Not Do

- 不要凭印象写注释
- 不要把后续阶段内容混入当前阶段注释
- 不要用"架构思维"替代具体分析
- 不要把设计思想写成空泛套话
- 不要在用户要求简洁时堆注释
- 不要为了完整重复同一结论
- 不要逐行注释，或注释明显代码
- 不要在同一处反复更换命名 / 标记
- 不要先给大抽象，再回头补源码证据
- 不要把某个案例术语当成通用模板
- 不要把设计智慧写成没有 trade-off、没有边界的空洞赞美
- **不要修改任何代码逻辑、变量名、签名、格式 —— 只加注释**
- **不要创建并行文档文件（除非用户明确要求）**

## Output Contract

交付形态：

- 源码内的注释：文件头总论块（主链 + 阶段骨架）+ 阶段边界注释 + 设计点注释 + 稀疏 WHY 注释
- 简短报告：标注了哪些文件 / 类 / 阶段，跳过哪些及原因

最终注释应满足：

- 注释与代码同位，可追溯
- 边界清晰
- 设计分析贴着源码
- 抽象层级受控
- 密度克制

一句话标准：

> 把分析写进源码，读者沿注释就能走完整条链路——先标边界，再给代码证据，只抬一层抽象，密度比文章更克制。
