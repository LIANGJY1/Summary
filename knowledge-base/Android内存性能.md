**Q1:** 分析进程内存时,dumpsys meminfo 输出怎么读:先看哪个数,PSS、RSS、私有脏页分别说明什么?

先看 App Summary 区的 TOTAL PSS,它是唯一适合跨进程、跨时间比较的口径;判断"还能不能压"则看 Private Dirty 的分布。各列含义如下:

1. PSS(Proportional Set Size,按比例分摊的驻留内存):私有页全额计入,共享页按共享进程数均摊;跨进程、跨时间比较只用它。
2. RSS(Resident Set Size,常驻内存):凡映射进本进程的页全部计入,共享库重复计算;同一快照实测 PSS 87.5 MB 而 RSS 172.5 MB,差出一倍多,不能用于进程间比较。
3. Private Dirty:本进程独占且被写过的页,系统最难回收;判断还有没有优化空间主要看它的分布。
4. Private Clean:本进程独占但未改写的文件映射页,内存紧张时可直接丢弃。
5. SwapPss Dirty:已被 zram 压缩换出的部分;闲置进程可能很高,评估真实足迹时需与 PSS 相加。

日常分析路径按依赖顺序走:

1. TOTAL PSS 定位总量与变化幅度。
2. App Summary 七分类(Java Heap、Native Heap、Code、Stack、Graphics、Private Other、System)看构成。
3. 可疑分类回详细区段定位到具体对象(如 .so mmap、Dalvik Other、Unknown)。
4. Objects 区(Activities、AppContexts、Views)看泄漏线索:反复进出页面后单调增长是泄漏,复原是正常。

边界:Graphics 一列在部分平台恒为 0,不代表没有 GPU 或解码器缓冲,不能据此断言图形内存为零。

**Q2:** 对象已经释放、堆占用不高,进程 PSS 为什么仍降不回冷启动值?

因为 PSS 度量的是驻留在内存里的页,不是活着的对象:对象释放只是把内存交回进程内部分配器的空闲链表,或者它本来就是不会主动归还的映射页。实测销毁媒体详情页返回列表后,Java 堆仅比冷启动基线多 0.7 MB、Native 堆反而更低,说明存活对象已释放干净,但 PSS 仍停在高出基线约 14 MB 的平台。这 14 MB 的分类对账如下:

1. .so 代码页 +5.1 MB:视频播放加载的播放器与解码库,文件映射页读过即常驻,进程不死不卸载。
2. System 共享脏页 +4.3 MB:窗口、Surface 的共享脏页按比例计入本进程。
3. Dalvik Other +1.4 MB:JIT 代码缓存等运行时元数据,只增不减。
4. 杂项私有页与栈 +4.6 MB:匿名映射缓冲等。

结论:这部分是"进程完整运行过一轮"的驻留成本,Android 只在内存压力或进程死亡时回收,应用侧无手段也无需去压。判断释放机制是否正常,看分类对账(存活堆是否回落),而不是看 PSS 总数回不回落。

**Q3:** 怎么判定 PSS 的高位平台是一次性高水位,还是持续泄漏?

用棘轮实验判定:同一进程内重复完全相同的操作路线,在固定检查点采样;各轮收敛即一次性高水位,逐轮抬升才是泄漏嫌疑。单次高峰没有结论,趋势才有。实验步骤:

1. 强制停止应用后冷启动,取得基线。
2. 按固定路线遍历各页面,每步固定等待,并在固定检查点采样。
3. 返回起点后按 0/2/10/30 秒采样,观察回落速度与落点。
4. 不杀进程,重复同一路线至少 3 轮,对比各轮同一检查点的数值。

判读标准:同一检查点各轮差值在一两 MB 内且不随轮次抬升,是一次性高水位(分配器空闲页与驻留页);逐轮抬升则是泄漏嫌疑,转入 heap dump 做对象级分析。两条辅证:销毁页面时 PSS 大幅回落说明释放机制活着;闲置后自然回落同样说明有界。实测:退出重进循环三轮的峰值 106.9 → 95.3 → 95.7 MB,有界;一次 125.3 MB 的峰值在同一进程 17 分钟后自然回落到 95.7 MB。

**Q4:** Android 8.0 之后 heap dump 里 Bitmap 的 Shallow Size 很小而 Native Size 很大,怎么利用这一点?

Android 8.0(API 26)起位图像素数据存放在 native 堆,Java 层 Bitmap 对象只剩几十字节的壳,像素成本全部记在 Native Size 列。Native Size 等于宽 × 高 × 每像素字节数(ARGB_8888 为 4 字节),据此可以反推每张位图的"尺寸指纹"。利用方式:

1. 在 heap dump 中按 Native Size 排序定位内存大头,进入实例列表逐个核对尺寸。
2. 由 Native Size 反推分辨率,判断解码尺寸是否超过展示需求:实测 3686401 字节约为 1280×720×4(全屏图),135721 字节约为 261×130×4(列表缩略图)。
3. 多张同尺寸位图同时存在时,先核对是否分页预载的机制形态,再谈优化或泄漏。

边界:heap dump 只覆盖 Java 堆可见对象,视频解码器与其采样缓冲不在其中,视频播放的内存不能用它分析;视频侧的内存变量是码率与缓冲窗口,需换用系统级工具观察。

**Q5:** 整屏大图的解码内存怎么省:为什么按 View 边界降采样、怎么落地?

位图内存等于解码后尺寸乘每像素字节数,与源文件的像素数无关;把解码尺寸限制到展示尺寸,内存按比例下降。实测同页 A/B:把解码上限从源图 2560×1440(14.1 MB/张)限制到 1280×720(3.5 MB/张)后,返回列表的稳态 Native Heap 从 44.0 MB 降到 22.1 MB。Glide 用 override(w, h) 指定解码尺寸,策略应统一封装,要点:

1. 大 View 封顶:超过屏幕尺寸的 View 一律按参考尺寸(如 1280×720)解码。
2. 小 View 不放大:View 小于参考尺寸时按 View 自身边界解码,避免放大浪费。
3. 无效回退:View 尚未完成布局时宽高为 0,必须回退到参考尺寸,否则会按源图全尺寸解码。
4. 唯一入口:策略集中在适配器绑定处调用,避免个别调用点漏加 override 造成策略失效。

边界:override 不保持宽高比,展示端通常配合 centerCrop 类裁剪使用;源图与目标宽高比差异大时,需人工核验观感后再上线。

**Q6:** 视频播放的内存大头在哪,怎么用 LoadControl 给缓冲设预算?

本地与流媒体播放的内存大头是媒体采样缓冲(读入内存的压缩数据,按 64 KB 分块)和解码器;缓冲按时间窗攒数据,需求 = 码率 × 窗口时长,所以高码率片源是首要变量。ExoPlayer 2.19.1 用 DefaultLoadControl 显式设预算,各配置项含义与省略后果如下:

1. setBufferDurationsMs(15000, 30000, 2500, 5000):依次为最小缓冲、最大缓冲、起播所需缓冲、重缓冲后起播缓冲,单位毫秒。显式收缩最小缓冲窗(ExoPlayer 2.19.1 默认 50 秒)是省内存的核心;省略则按 50 秒窗攒数据,高码率片源需数十 MB。
2. setTargetBufferBytes(4 × 1024 × 1024):采样缓冲的字节上限,4 MB 封顶;省略时按缓冲时长与轨道码率推算。
3. setBackBuffer(0, false):已播内容保留 0 秒、不保留任何回看数据;ExoPlayer 默认本就不保留回看,显式写 0 的作用是防止后续改动无意引入回看开销。仅存在回看交互的业务才应设非零值。

机制澄清一个常见误解:同一时刻只应有一个活跃播放器——选中页创建播放器、失选立即 release;多段视频连播后 PSS 不回落,是释放的页被进程分配器复用形成高水位,不是多份缓冲共存。

**Q7:** Glide 的内存缓存和 BitmapPool 为什么会占内存,怎么设上限?

Glide 默认按屏幕大小分配内存缓存(约两屏的解码结果)与 BitmapPool(约一屏的可复用位图,均由 MemorySizeCalculator 按屏幕推算),媒体密集应用反复浏览时这部分持续进驻。做法是自定义 AppGlideModule 设上限:

1. 注册:类上加 @GlideModule 注解,并在依赖中加入 annotationProcessor 声明的 glide:compiler;省略注解处理器时模块不生效,静默回退默认配置。
2. applyOptions 中调用 setMemoryCache(LruResourceCache(2 MiB)) 与 setBitmapPool(LruBitmapPool(2 MiB)):把内存缓存与可复用位图池各限为 2 MiB;省略时按 MemorySizeCalculator 的屏幕推算值。
3. isManifestParsingEnabled 返回 false:关闭旧版 manifest 扫描,与注解注册方式配套。

边界:上限只约束缓存与对象池,不约束活跃 ImageView 正持有的位图;页面销毁时调用 Glide 的 clearMemory,才能把引用已释放的缓存像素立即归还。

**Q8:** ViewPager2 滑动时为什么恒有约 3 张整屏位图同时驻留?

ViewPager2 的 offscreenPageLimit 最小合法值是 1(传入 0 直接抛 IllegalArgumentException),因此当前页左右相邻页的内容恒被预载;整屏图场景下就是 3 张大位图共存。heap dump 中看到 3 张同尺寸全屏位图,是预载机制的正常形态,不是泄漏。想减少数量只能自研分页容器,成本与风险不成比例;实际优化方向是压单张成本(降采样、RGB_565 格式),单张减半即总量减半。

**Q9:** 从 dumpsys meminfo 输出提取总 PSS,直接搜 TOTAL 为什么会出错,怎么写才可靠?

输出里有两类含 TOTAL 的行:汇总区尾部的 TOTAL PSS: 87537 是给人读的文本行,详细表尾的 TOTAL 87537 58184 ... 才是数据行,且数据行的列宽随数值位数变化,固定列位或简单匹配 TOTAL 都会拿错。可靠提取式:

```bash
awk '$1=="TOTAL" && $2 ~ /^[0-9]+$/ {print $2}'
```

第一个条件排除文本行(其第二字段是 PSS: 而非数字),正则再排除异常行。配套纪律:序列采样按固定间隔使用同一解析式;每个检查点把完整输出落盘,后续的分类对账与 Objects 区分析都要用原始文件,不能只存提取后的数字。

**Q10:** 应用内的无操作自动跳页机制为什么会污染性能测量?

演示类应用常带"无操作自动轮播":固定秒数无触摸即自动进入全屏轮播页,一次性带来整屏位图加新 Activity 的内存增量。测量期间一旦停手超过阈值,这次自动跳页会被误归因为手顺操作。实测某演示应用停手 6 秒后 PSS +5.5 MB(1280×720 解码位图 3.5 MB 加窗口约 2 MB),并且曾在快速连点时因点击被转场动画吞掉、出现 6 秒空闲而意外触发,污染了整轮数据。对策:

1. 测量期间保持连续操作,任何触摸都会重置空闲计时器。
2. 测试构建中禁用自动轮播开关。
3. 测前审计源码,确认是否存在定时器驱动的隐式跳页或自动播放机制。

**Q11:** 进程消失了,怎么判断是应用崩溃还是被外部杀死?

判断依据是日志组合,而不是"进程没了"本身;被 signal 9 杀死且没有任何崩溃痕迹,就是外部杀死,不是应用缺陷。判据:

1. Java 崩溃:logcat 的 crash 缓冲出现 AndroidRuntime FATAL,dropbox 新增 data_app_crash 记录。
2. Native 崩溃:出现 DEBUG 标签与 tombstone 记录。
3. 低内存杀死:lmkd 或 lowmemorykiller 日志。
4. 外部杀死(am force-stop、IDE 的 Stop、kill 命令):仅有 Zygote 的 "Process N exited due to signal 9 (Killed)" 一行,以上痕迹全部没有。

实测曾把 IDE 侧的 Stop 误判为应用崩溃,按此清单复核后撤回。另注意:IDE 调试代理会向被测进程注入 instrumentation,并产生网络请求日志,属测量副作用,与应用无关。

**Q12:** 后台闲置进程的 PSS 回落,为什么不能全部当成释放?

启用 zram 的设备上,闲置进程的部分页会被压缩换出;PSS 下降可能只是换出而非释放。实测某闲置进程的 SwapPss 高达 43.9 MB,此时真实足迹应为 PSS 与 SwapPss 之和。判读:

1. 前台活跃态:工作集页很少被换出,PSS 可以直接比较。
2. 后台闲置态:必须并入 SwapPss 再解读;后台进程的最终归宿是低内存时被整体回收,而不是渐进归还。

**Q13:** 同分辨率的两段视频体积差 4 倍,怎么定位并压缩?

用 ffprobe 读码率即可定位:实测同为 1280×720 的 H.264,一段 5.44 Mbps(73 秒,49.2 MB),另一段 1.37 Mbps(105 秒,19.6 MB)。码率是"每秒内容用多少字节承载"的直接变量:联网场景下载量 = 码率 × 时长;安装包内 raw 资源按原文件打包,文件省多少包体省多少。压缩命令及逐项含义:

1. -b:v 1500k:视频目标码率,决定体积的主变量。
2. -maxrate 2000k 与 -bufsize 3000k:峰值码率上限与其解码缓冲,平滑码率波动;省略则码率波动不受限。
3. -c:a copy:音频流直拷、不重编码;省略时音频被默认重编码,多一次有损转码。
4. -movflags +faststart:把 moov 索引移到文件头;省略时索引留在尾部,联网渐进播放需等整个文件下载完。

实测同一片源 49.2 MB 压到 1500k 档 13.0 MB、2500k 档 20.1 MB。边界:画质损失需人工逐段验收,重点看暗场与快速运动;片源若属营销素材,替换前需内容方确认。

**Q14:** 内存性能的 A/B 对比实验,怎么做结论才可信?

可信的结论来自单变量、可复现、全程留痕的实验;任何一次"看起来变好了"都应能被后续轮次重复。要点:

1. 只变一个因素:同设备、同路线、同等待时长,只换代码版本。
2. 检查点三件套:完整 dumpsys meminfo 落盘、UI 标题验证确认真的在目标页、Activity 栈核实没有隐式跳页。
3. 防输入不可靠:转场动画会吞掉点击,每步导航后验证结果并对未生效的操作重试。
4. 对账闭环:各内存分类的增量之和应约等于总量增量,对不上说明存在未解释项,结论不完整。
5. 结论分级:实测数字与机制推断分开表述;一次峰值与稳定平台分开表述,不互相替代。

反例:连点导航时一击被吞导致少进一页,后续所有检查点错位;实验中途的外部操作(IDE 停止进程)使进程消失,数据被误读为应用崩溃。

**Q15:** 磁盘上只有几 MB 的图片,解码后为什么会占用 10 MB 以上内存?

磁盘大小是压缩编码后的大小,内存里必须放解压后的原始像素,占用 = 宽 × 高 × 每像素字节数。2560×1440 的 PNG 按默认 ARGB_8888 解码即约 14.1 MB,与文件是否只有 2 MB 无关。

1. 解压不可省略:GPU 与显示管线要按坐标随机访问任意像素,而 PNG 的 DEFLATE 熵编码是串行依赖的、无法按坐标寻址,所以无论选什么压缩格式,解码这一步都省不掉。
2. 压缩率只作用于磁盘:海报类图像大面积纯色,PNG 无损压缩到原大的 1/4 至 1/5 常见;换 WebP 只进一步省磁盘与解码耗时,解码后的字节数仍按同一公式计算。
3. 密度桶决定解码倍率:放在 drawable-mdpi 的图在 160 dpi 屏按 1:1 解码;同一资源落到 480 dpi 设备会被放大 3 倍解码,宽高各乘 3、内存放大 9 倍。大图放低密度桶是常见埋雷点。
4. 省内存的杠杆都在像素侧:限制解码尺寸(宽高各减半、内存降为 1/4)与更换像素格式(RGB_565 每像素 2 字节、减半)是仅有的两个;转码格式不在其中。

排查"图很大"与"图占内存大"要分开:先核对资源尺寸与所在密度桶,再用 heap dump 的 Native Size 核对实际解码尺寸,不能拿文件大小反推内存。

**Q16:** 判断应用的 PSS 水位是否真的过高,为什么需要分场景基线和同机横向对比?

单点数值没有判定力:不同内容形态的稳态可差数倍,拿视频页峰值对标图文应用只能制造伪指摘。完整的论证至少需要三条互相独立的证据链:

1. 分场景基线:对每种内容形态(图文页、全屏视频、列表)分别进入后等稳定再采样。实测某展示应用冷启动 48 MB、图文页稳态 53-58 MB、全屏视频稳态 111-130 MB,不同形态差 2 倍以上,混在一条曲线里没有意义。
2. 时间趋势:单场景内每 30 秒采样、持续 3-5 分钟。该应用 8 个采样点在 111-130 MB 间振荡、无单调增长,是媒体缓冲随内容变化的工作集特征;持续爬升才是泄漏嫌疑。
3. 同机横向对比:同一命令遍历设备上同类应用。实测同机桌面 142 MB、行车记录 110 MB、视频剪辑 77 MB,均不低于被指摘应用,即可证明该形态属于平台合理水位,而非应用缺陷。

测量纪律:自动轮播类应用会自行切换页面,采样前必须用 am start 显式锁定目标页面,否则相邻两次采样可能来自不同状态,数据不可比。

三条链分别回答"基线是多少""是否在增长""同类是什么水平";三条都指向异常才值得转入对象级分析,任何一条正常都足以驳回"过高"的指摘。

**Q17:** 页面只是退到后台(Home)而未销毁,位图为什么不释放?手动触发内存裁剪为什么也无效?

退后台只触发 onStop,页面与 View 树完整存活,ImageView、Glide 的活动资源与内存缓存都还持有位图强引用;系统裁剪回调只能回收无引用的缓存副本,钉在 View 上的位图任何裁剪级别都挤不掉。实测对全屏视频轮播应用发送 TRIM_MEMORY_COMPLETE 后总占用一分未降。

1. 生命周期事实:Home 键让 Activity 走 onPause → onStop,只有返回键或 finish 才走 onDestroy;"页面隐藏"与"页面销毁"是两种内存状态,前者几乎不释放任何东西。
2. 引用链构成:位图被 ImageView 持有,ImageView 挂在 DecorView 上,Activity 又被系统返回栈和应用自维护的 Activity 栈管理器持有;Glide 解码结果先进入活动资源表,页面切换后转入 LRU 内存缓存继续持有。
3. 裁剪的真实语义:trimMemory 只通知应用收缩缓存,收到后也只能清出无引用的副本;被存活 View 直接钉住的位图不在可回收范围,所以实测响应为 0。
4. 真正可回收的动作:销毁页面(返回出栈);清空非当前页的 ImageView(置 null 或 Glide clear);应用整体退后台时调用缓存清理接口释放无引用副本。

排查后台占用时先确认页面处于 stopped 还是 destroyed,再决定是查引用链还是查缓存;混同两者会把正常驻留误判为泄漏。

**Q18:** ExoPlayer 的 pause 与 release 内存差异有多大?页面退后台应该怎么选?

pause 只置 playWhenReady = false,播放器实例、已缓冲样本、MediaCodec 编解码器与播放器线程组全部原样驻留;需要归还内存必须 release,退后台选 release、回前台重新 prepare。

1. pause 驻留明细:已缓冲媒体样本按缓冲窗计(15-30 秒窗对本地视频约 11-26 MB);MediaCodec 实例在原生侧数 MB;播放、加载、编解码线程组仅随 release 退出。体现在 Native Heap 与 Stack 的增长上。
2. release 归还范围:以上全部归还,同时解除 Surface 关联;恢复播放需重建播放器并重新 prepare。
3. 挂点选择:页面级在 onStop 触发 release;列表内多播放器场景在取消选中回调触发,保证同屏只有一个活跃实例。
4. 代价评估:本地资源重新 prepare 为百毫秒级,展示类应用可接受;在线流媒体需权衡重缓冲的网络成本,可先收窄缓冲窗而非放弃 release。
5. 例外:需要退后台继续出声的场景(画中画、后台音乐)不能释放,此时至少确认音频焦点持有并考虑收窄缓冲上限。

**Q19:** 全局启用 RGB_565 能省多少位图内存?前提与代价是什么?

RGB_565 每像素 2 字节(ARGB_8888 为 4),位图内存直接减半:5 张全屏 1280×720 位图可省约 8.8 MB。前提是内容不依赖透明通道。

1. 启用方式:自定义 AppGlideModule,在 applyOptions 中把带 format(DecodeFormat.PREFER_RGB_565) 的 RequestOptions 设为全局默认;需同时引入 glide 注解处理器,否则模块不生效、静默回退默认配置。
2. 适用判断:照片、视频帧、海报等不透明内容适用;图标与带透明区域的 UI 切图不适用——565 没有 alpha 通道,透明区域会变黑。
3. 画质代价:每通道位数下降,大范围渐变可能出现色带;全屏大图上线前人工抽查即可。
4. 默认值边界:Glide 在 isLowRamDevice 为 true 的设备上默认就是 PREFER_RGB_565,显式设置前先确认目标设备档位,避免冗余声明。
5. 生效边界:配置只影响之后的解码,已生成的 8888 缓存不被追溯转换,进程重启后才全量生效。

**Q20:** 正式包(非 debuggable)要定位原生内存归属,malloc debug 与 heapprofd 各有什么限制?

三条路径可用性递减:malloc debug 需要属性加框架重启且依赖构建开放;heapprofd 要求应用可被性能分析,root 也不能豁免;都被裁剪时只剩场景差分加 smaps 归属,而后者在工程实践中反而是主力。

1. malloc debug:stop 后设置 libc.debug.malloc.program(包名过滤)、libc.debug.malloc.options(如 backtrace)、libc.debug.malloc = 1,再 start 重启框架,随后启动目标应用并用 am dumpheap -n 导出带调用栈的原生堆。属性在进程创建时被 libc 消费,只 force-stop 应用而不重启框架不会生效。

    1. 构建边界:注入行为随厂商构建差异很大,部分车机系统对 zygote 子进程直接裁剪了注入逻辑(属性齐备仍不生效,进程映射里查不到 malloc_debug);遇到时不要反复重试属性组合,直接转黑盒差分。

2. heapprofd:通过 perfetto 配置 android.heapprofd 数据源采样;官方口径要求应用可被性能分析,实测 root 车机上对普通正式包只采到几十字节的空轨迹,说明钩子未安装,该路不通。
3. 黑盒退路:分场景采集 dumpsys meminfo 与 /proc/进程号/smaps,用场景开启前后的分类与映射增量定位归属。实测案例:视频播放 4 分钟后 Native Heap 从 12 MB 涨到 59 MB,同时 .so 映射增长 15 MB 且媒体编解码库全部加载——不依赖任何注入即可锁定媒体工作集。

操作纪律:stop/start 会重启整个框架,只能在独占台架执行;libc.debug.malloc、heapprofd.enable 等调试属性用完必须恢复原值,否则残留行为影响后续测量。

**Q21:** 没有 MAT 时,如何用脚本从 hprof 统计各尺寸 Bitmap?

root 设备上 am dumpheap 对非 debuggable 应用同样可用,产物经 hprof-conv 转换后可脚本解析;当全流式解析被格式变体卡住时,按实例记录的固定布局做字节模式扫描是更抗造的捷径。

1. 抓取与转换:导出后用 SDK 自带的 hprof-conv 转换,消除 ART 与标准格式的差异(如标识符宽度)。
2. 类型表是第一坑:HPROF 基本类型号为 4=boolean、5=char(2 字节)、6=float、7=double、8=byte、9=short、10=int、11=long;把类型号直接当尺寸用、或把 5 号 char 当 double 按 8 字节跳过,解析流会整体失步——这是手写解析最常见的错误。
3. 布局差异:不同设备的 hprof-conv 对基本类型数组的字段顺序存在差异(实测某车机为"元素数在前、类型在后");解析前取小样本人工核对字节,不要假设单一规范布局。
4. 模式扫描法:实例记录布局固定为"标签 0x21 + 对象 id + 栈序号 + 类 id + 字节长 + 字段区"。先由 LOAD_CLASS 记录建立类 id 与类名映射,再把目标类 id 连同前置标签字节做全文搜索,命中处按布局读出字段区,即可绕过全流解析直接统计。
5. 字段定位:不同版本 Bitmap 的字段偏移有差异,用统计法定位——把全部实例的字段区并排打印,取值恒为 160 的字是密度,在合理值域(如 24/130/720)内变化的两处即高与宽,再用已知布局尺寸交叉验证。
6. 适用边界:手写解析是黑盒环境的退路,有 Android Studio 时优先用其 heap dump 界面,读数等价且零实现成本;脚本的价值在于可批量执行、可自动化对比前后两个状态。

**Q22:** allocation tracking 与 heap dump 各回答什么问题,调用栈视图里怎么识别剖析工具自身的测量开销?

allocation tracking 记录"时间窗内的分配事件",回答谁在持续分配、分配多少次多少字节(churn 与 GC 压力来源);heap dump 记录"某一瞬的活对象快照",回答内存现在被谁持有(驻留与泄漏);两种口径互不替代。调用栈视图里若大量分配集中在 binder 线程、栈链为 execTransact → onTransact → dumpMemInfo,那是剖析工具自己在查询进程内存信息,属观察者效应,应整棵子树排除后再分析业务代码。

两种口径的分工与各自关键读数:

1. **allocation tracking(事件口径):**表格按类或调用栈分组,列为 Allocations(窗内分配次数)、Deallocations(窗内已回收次数)、Total Count(窗末仍活着)、Shallow Size(窗内分配字节数)。Allocations 与 Deallocations 接近说明是随生随灭的临时对象,压力在 GC;Total Count 跨多次采集单调上升才是泄漏嫌疑。调用栈分组首层是线程,逐层展开是栈帧,行上数字含其子树;沿 Shallow Size 最大的子节点下钻到自己包名的帧,即业务分配热点。
2. **heap dump(快照口径):**类表按尺寸定位大头,实例列表加引用面板回答"谁持有这个对象",结合 GC root 回答"为什么收不掉"。它与事件口径的差别:不告诉分配点,只给当前持有链。

观察者效应的识别特征与处理:

1. **来源:**剖析工具在录制期间经 IPC 周期性查询进程内存信息,应用的 binder 线程执行 dumpMemInfo 生成报告,报告格式化产生大量 Formatter 内部类、char[]、String 的临时分配。
2. **特征:**调用栈链固定为 Binder.execTransact → 应用线程 stub 的 onTransact → dumpMemInfo;分配与回收几乎相等;类视图同时出现大量 Formatter 族内部类。
3. **处理:**整棵子树排除后再分析主线程等业务线程;这部分分配不计入业务缺陷,也不代表业务内存占用。

边界:

1. 录制模式需 Full 才有完整调用栈,采样模式只抽样。
2. 时间轴选区必须只覆盖录制区间,选入未录制区间会使调用栈数据不全,工具会明确警告数据可能不准。
3. 事件口径的"仍活着"只是窗末状态,跨窗驻留结论要以 heap dump 与 meminfo 为准。

**Q23:** dumpsys meminfo 里 Heap Size 与 Heap Alloc 的差值说明什么,为什么 native 堆占用在对象释放后不立即下降?

Heap Size 是分配器向系统持有的内存总量,Heap Alloc 是当前活对象占用字节,两者之差是"已释放但未归还系统"的空闲竞技场,即碎片水位。native 分配器以竞技场为单位管理内存、整场清空才归还,所以高频分配潮过后 PSS 会长时间停在高位;Java 大对象空间相反,每个大对象独立 mmap、回收即 munmap 归还。

三个数字与差值的读法:

1. **Heap Size:**分配器从系统持有并尚未归还的内存,含空闲竞技场。
2. **Heap Alloc:**活对象占用字节,对应"仍被持有"的口径。
3. **差值(Size 减 Alloc):**已释放未归还部分;碎片水位的长期监控指标是这个差值,不是 PSS 总量。

两类堆行为不同的机制:

1. **native 堆:**Android 11 起默认 native 分配器为 scudo,以竞技场为单位向系统取内存并管理(showmap 中为 `anon:scudo:primary` 与 `anon:scudo:secondary` 大块区);释放的内存留在场内空闲列表等待复用,整场清空才归还系统。实测某进程 native Heap Size 115 MB 而 Alloc 仅 28 MB,showmap 单场最大 24.8 MB,即约 45 MB 空场未归还——这部分是历史 churn 的后遗症,不是当前业务占用。
2. **Java 大对象空间:**超过大对象阈值的对象进入独立的大对象空间(showmap 中为 `anon:dalvik-free list large object space`),每块独立 mmap;GC 回收后直接 munmap 归还系统,所以 Java 大对象占用在回收后立即下降,没有竞技场水位问题。

分析时的两个辅助判断:

1. **排除单个大缓冲:**看 scudo secondary 的大块分布;实测单块最大仅 1.6 MB,说明数十 MB 的 native 占用是大量中小块与空场的积累,不是某个 native 大缓冲。
2. **降水位的方向:**治理高频临时分配让竞技场清空;应用侧没有强制 native 分配器归还的接口,不要寻找这类开关。

**Q24:** 对象已经不可达,为什么 heap dump 和 meminfo 里仍占内存,怎么判定是"待回收垃圾"还是"仍被持有"?

释放最后引用只让对象变得可回收,真正回收发生在 GC 的 sweep 阶段;"释放"与"sweep"之间对象不可达但字节仍占堆,meminfo 的 Alloc 与未先 GC 的 heap dump 都会计入它。判定方法是看 heap dump 里该对象的 GC root 与入边引用:两者皆无即待回收垃圾,任一存在即仍被持有。

从可达性到回收的机制链:

1. **可达性判定:**GC 以对象能否从根集合(线程栈、静态字段、JNI 引用等)到达决定可回收性;不可达对象不会立即 freeing,要等 sweep 阶段。
2. **触发条件:**ART 并发 GC 主要由分配压力与空闲维护触发;实测某进程退后台后不再有新分配,9 个共 59 MB 的大数组在释放后超过 7 分钟仍未被回收——无分配的闲置进程可以长时间等不到回收触发。
3. **记账口径:**分配器在 sweep 时才递减 Alloc,所以回收前 meminfo 的 Dalvik Alloc 仍包含这批垃圾,showmap 中对应的大对象空间映射也仍驻留。

同一时点两种抓取工具结论不同的原因:

1. **命令行 am dumpheap:**不先触发 GC,dump 包含不可达尸首,适合观察"刚被释放还没回收"的状态。
2. **Android Studio 的 heap dump:**抓取流程会先 GC;实测同一时点界面显示对象仍被引用持有、同进程命令行 dump 显示无任何 root,差异正来自是否先 GC;它给出的是活视图。
3. **两者不矛盾:**分别是"回收前"与"回收后"的快照;读数冲突时先问是否先 GC,再比较。

实操判定步骤:

1. 抓 heap dump,查目标对象的 root 类型与入边引用:全为零即待回收垃圾。
2. 与 meminfo 时间线对账:Alloc 含未回收垃圾,会高于真实活对象值。
3. 切回前台或等待一次 GC 后再抓:目标消失即确认垃圾;仍在且带 root 则转持有链分析。
4. 物理页视角:Java 大对象独立 mmap,sweep 后 munmap 立即归还系统,所以这类占用会自愈;真正要回答的是峰值为什么这么大、为什么分配这么多份。

**Q25:** 手写解析 heap dump 做持有者归因时,记录结构与 root 类型是什么,解析失步怎么校准?

hprof 是"字符串表 + 类表 + 堆指针图"的二进制快照:顶层为 tag-长度-body 的记录流,堆内容集中在堆段记录内,段内子记录分 root 与对象定义两类;持有者归因就是对目标对象做两遍扫描重建入边。该格式无校验和,错一个字节后面全部雪崩,且常常不报错、只安静地输出空结果,所以失步必须靠失败点 hexdump 的步长校准,不能猜。

三层结构:

1. **文件头:**格式串(如 `JAVA PROFILE 1.0.3`)、标识符宽度、时间戳;记录流从头部之后开始,不是偏移 0。
2. **顶层记录流:**`0x01` 字符串表(id 到文本,所有名字都经它间接引用)、`0x02` 类登记(类对象 id 绑定名字 id)、`0x0C` 与 `0x1C` 堆段记录。
3. **段内子记录:**root 类有 `0x01` JNI 全局引用(id 加引用 id)、`0x02` JNI 局部与 `0x03` Java 栈帧(均 id 加线程号加帧号)、`0x05` sticky class(id)、`0x08` 线程对象(id 加线程号加序号),以及 `0x8D` 等只带 id 的老规格扩展子类型;对象定义类有 `0x20` 类字段表、`0x21` 实例(类 id 加字段原始字节)、`0x22` 对象数组(元素 id 序列)、`0x23` 基本类型数组(长度加数据)。

两遍扫描法:

1. **第一遍建目标:**字符串表、类表;把超过尺寸阈值的基本类型数组与目标类实例记入目标 id 集合。
2. **第二遍收入边证据:**带目标重扫全堆,记录四类证据:root 命中(带 root 类型与线程号)、实例 object 型字段命中(持有者类与字段名)、对象数组元素命中、静态字段命中;四类全零即该对象不可达。
3. **字段切分:**实例字段字节按类字段表切槽:祖先类在前、声明顺序、宽度按类型(对象引用等于标识符宽度、int 4 字节、long 8 字节、boolean 1 字节,并按对齐);object 型槽位的值即指向其他对象的指针。

失步校准与常见坑:

1. **校准方法:**报未知子标签时,hexdump 失败点前后 64 字节,按记录步长反推真实布局;实测 9 字节步长(1 标签加 4 id 加 4 引用)证明那段记录是 JNI 全局 root,据此确定该子标签的载荷字节数。
2. **坑一,起始偏移:**记录流从偏移 0 读会把格式串首字节当第一条 tag,其"长度"吞掉整个文件,表现为"全文件只有一条记录、统计全零"的安静错误。
3. **坑二,段标签:**堆段 tag 是 `0x1C`,写成 `0x0D` 会让堆内容整体不可见,而字符串表与类表看似正常。
4. **坑三,表外子标签:**`0x8D` 一类老规格扩展 root 子类型不在表里,直接崩溃或失步。
5. **坑四,root 载荷字节数:**JNI 局部与 Java 栈帧为 id 加线程号加帧号共 12 字节,线程对象为 id 加线程号加序号共 12 字节;少算 4 字节会在记录串中段失步,把数据字节当 tag 报错。

root 类型的含义(决定"谁算活着"的起点):

1. **Java 栈帧、JNI 局部:**某线程栈还拿着它,持有者就是那段栈上代码。
2. **JNI 全局:**native 代码注册的全局引用,持有者在 native 侧。
3. **sticky class:**被静态字段钉住。
4. **运行时内部类 root(如 `0x8D`):**被运行时内部表钉住,如 direct buffer 的注册表;这类 root 的对象在 Java 代码层永远追不到所有者,只能靠运行时抓分配调用栈定位分配点。

**Q26:** 引用链断在 native root 时,怎么识别匿名大数组的用途与来源?

把数组内容本身从 heap dump 抽出来做识别:头部魔数回答"是什么格式",内嵌元数据回答"是谁的",同尺寸数组的字节级哈希对比回答"有几份重复"。实测案例:9 个约 6.5 MB、无 root 无持有者的匿名 byte[],据此认定为 MiSans 字族三个字体文件、各被冗余加载 3 份。

为什么看内容与怎么抽:

1. **为什么:**持有者是 native root(JNI 全局或运行时内部表)时,Java 引用链在根处即断,静态 dump 无法回答"哪段业务分配了它";而 hprof 的基本类型数组记录带数据字节,内容是剩下的最直接证据。
2. **怎么:**按记录长度定位目标数组,把字节写出为文件离线识别。

识别三步:

1. **看头部魔数:**魔数是文件或结构头部的固定标识字节,与扩展名无关地判定格式。实测数组头部为 `OTTO` 加表标签 `CFF ` 与 `DSIG`:`OTTO` 是带 CFF(Compact Font Format)轮廓的 OpenType 字体的 4 字节版本标签,`DSIG` 是数字签名表;再从 name 表读出字族名与版权信息,直接认定文件身份。其他常见魔数:PNG 为 `89 50 4E 47`,ZIP 为 `50 4B`,gzip 为 `1F 8B`。
2. **看熵与可读字符串:**抽样熵高于 7.3 比特每字节是压缩或加密内容;熵低且可读字符串多的是结构化明文;可读字符串常自带厂商、版本等来源信息。
3. **同尺寸数组比哈希:**全同即同一文件被重复读取多份;不同即不同数据。这一步同时区分"重复加载"与"流水线缓冲":多阶段流水线缓冲存的是不同阶段的数据,不会字节级相同。

来源认定与边界:

1. **与仓库资源比对:**数组字节与候选资源文件逐字节比对;实测数组等于 4 字节零加完整字体文件加 3 字节填充,即带预留头部的缓冲包装形态,偏移对齐后完全吻合,确认数组是该资源文件的内存副本。
2. **结合声明文件:**资源目录与字体族声明文件交叉回答"打包几个、声明几个、引用几个":实测打包 10 个字重、声明 3 个、引用 3 个、每个 3 份副本。
3. **边界:**内容识别回答"是什么、几份重复、来自哪个资源",不回答"哪行代码分配";后者要靠运行时分配调用栈录制。

**Q27:** 同一字体资源为什么会在进程内存里出现多份字节相同的副本,怎么判定与修复?

实测某车机应用三个字体字重各在 Java 堆出现 3 份字节相同的 6.5 MB 副本、共 59 MB:直接成因是多条互不共享的加载路径各自把资源整份读进自己的缓冲,加上并发首用在缓存填充前竞态出并列副本。它随页面退出一起释放,不是崩溃级缺陷,但是值得修复的工程缺陷(峰值占用与安装体积)。

字重(weight)是同一字族的粗细变体;本例涉及 Regular、Medium、Demibold 三个字重,对应 400、500、700。

证据链与判定:

1. **哈希相同:**同尺寸数组哈希全同,先排除流水线缓冲,确认是同一文件的重复读取。
2. **双属性声明:**字体族声明文件里每个字体项同时写系统命名空间与兼容库命名空间两套字体属性,等于启用两条加载路径:系统路径按 mmap 共享资源、不产生 Java 堆副本;兼容库的字体组件会把资源字体整份读入内存缓冲再交给 native(此机制为由堆形态与组件行为作出的推断,未逐行核对兼容库源码),产生堆中观察到的 byte[] 副本。
3. **并发首用:**字体族被主题与多个样式引用,首帧并发 inflate 多个带该样式的控件,异步加载在缓存填充前为同一资源各发一次读取任务,副本数等于并发首用数。
4. **同生同死:**每份副本被各自的字体实例与 native 注册表钉住,UI 销毁时一起释放;实测页面退出后全部一起释放,无硬泄漏。

修复清单按性价比排序:

1. **砍双路径:**声明文件只保留一套命名空间的字体属性。
2. **消竞态:**启动时对每个字重同步预加载一次并全局复用,并发首用不再各读一份。
3. **用零拷贝路径:**只留系统命名空间属性,系统路径 mmap 共享资源,Java 堆零副本。
4. **瘦安装体积:**删除未使用字重;实测打包 10 个字重只用 3 个,删除可省 40 MB 以上。
5. **长期子集化:**全 CJK 字库每字重约 6.5 MB,按 UI 实际用字子集化可降到 1 至 2 MB。

判定边界:多份同尺寸大数组共存时,先用哈希区分"重复加载"与"流水线缓冲";再用是否随页面退出一起释放区分"缺陷"与"泄漏"。
