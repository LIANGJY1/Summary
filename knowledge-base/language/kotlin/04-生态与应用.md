## 第 11 章 Android 生态

**Q1: 使用 Kotlin 编写 Android 代码时，Android KTX 除了缩短调用形式，还可能提供哪些生命周期或默认行为？**

Android KTX（Kotlin Extensions）是 Android Jetpack 和其他 Android 库面向 Kotlin 提供的一组 API。它利用扩展函数、扩展属性、命名参数、默认参数和协程等 Kotlin 能力，让 Android API 更符合 Kotlin 的使用习惯。

```kotlin
// 原始 SharedPreferences API
val editor = preferences.edit()
editor.putInt(KEY_COUNT, 1)
editor.apply()

// core-ktx
preferences.edit {
    putInt(KEY_COUNT, 1)
}
```

KTX 不应一概称为“纯语法糖”。不同 API 提供的价值不同：

- `String.toUri()`、`bundleOf()`：封装常见的对象创建和参数处理。
- `SharedPreferences.edit { ... }`：管理 `Editor` 的获取与提交，并提供带接收者的 lambda 作用域。
- `lifecycleScope`、`viewModelScope`：提供与生命周期绑定的协程作用域，包含实际的取消语义。

```kotlin
viewLifecycleOwner.lifecycleScope.launch {
    viewModel.uiState.collect { state ->
        render(state)
    }
}
```

因此，理解一个 KTX API 时，不要只看调用是否更短，还要查看它是否管理了生命周期、线程、资源释放或默认行为。

KTX 不会修改原有 Java 类。扩展函数在 JVM 上通常表现为静态方法，Java 理论上可以调用其中一部分，但调用形式通常不如 Kotlin 自然。Java 代码仍可继续使用原始 Android API。

`SharedPreferences.edit { ... }` 涉及的尾随 lambda 与带接收者函数类型见 01 笔记 Q3～Q4；扩展函数的静态解析规则见 02 笔记 Q7。

**Q2: 为什么 `const val X = R.raw.xxx` 会报“Const 'val' initializer must be a constant value”？**

因为 `const val` 的初始化器必须是**编译期常量**（编译器会把值直接内联进每个使用处），而 R 类的字段由 AGP 在构建期生成，它算不算编译期常量取决于最终 R 的形态——不能把 R 字段当作可靠的常量来源。

来源：雅迪车机 Launcher `application/Launcher/src/main/java/com/yadea/launcher/pet/PetConfig.kt`：

```kotlin
object PetConfig {
    // 编译报错：Const 'val' initializer must be a constant value.
    const val SOUND_RES_CLICK = R.raw.pet_sound_click
    // 正确：资源引用一律用普通 val
    val SOUND_RES_CLICK = R.raw.pet_sound_click
}
```

这个坑麻烦在“时有时无”：应用模块最终产物的 R 字段是 `public static final int`，是常量，所以命令行 `gradlew` 有时能编译通过；但 IDE 常解析到中间形态或库形态的 R（字段非 final，AGP 对库模块就是生成非 final 的 R），按 const 规则直接标红。也就是说“能不能过”取决于模块形态、构建变体和 AGP 行为，随时可能从能过翻成编不过。

判断规则只有一条：`const val` 留给真正的字面量常量（Int、String 等）或其它 const；一切 R 资源引用用普通 `val`。运行时取值没有性能差异——const 的唯一效果是内联，而把资源 ID 内联进各使用处，反而会在资源变动时扩大重编范围。
