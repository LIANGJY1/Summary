# 问题式语言笔记写作指南

本指南规定问题式笔记（Q&A）的表达方式，适用于 knowledge-base 全域的问答式内容。语言笔记的准入、路由、文件归并、Q 编号和强制质量门以 [`03-language/README.md`](03-language/README.md) 为准。

目标不是“尽量短”，而是用最少的必要信息把问题讲完整：标题提供足够语境，首段直接回答，正文沿一条因果链展开，并在问题解决时停止。

> **强制要求：答案能以列表承载时，必须优先使用列表，不得为了行文连贯而摊成连续段落；无序与有序列表都适用时，必须优先使用有序列表；同一文档中的列表风格必须保持一致。** 这条规则是写作与验收的硬性门槛，不是可选的格式建议。

> **强制质量门：每个回答都必须达到资深面试级。** 不止给定义或结论，还要讲清成立条件、关键机制与因果；涉及实现时说明重要边界、取舍或版本差异，并给出有依据、可用于分析实际问题的判断。深度由问题决定，不靠堆术语、罗列源码或拉长篇幅；不能为追求简短而省略回答问题所必需的机制与边界。

## 1. 文件名与基础格式

- 文件名使用简短、稳定的英文主题词；需要表示学习顺序时使用两位数字前缀，例如 `01-activity.md`、`02-view.md`。不要把完整标题、问题描述或多个主题堆进文件名。文档正文仍可使用中文标题。
- 有序列表必须在源文档中显式递增编号，如 `1.`、`2.`、`3.`；同一列表不得把每一项都写成 `1.`。新列表重新从 `1.` 开始。不要依赖 Markdown 渲染器自动改写重复编号。
- 用户未明确要求超链接时，默认不新增 Markdown 链接。需要注明资料来源时，写来源名称或文档路径即可；只有用户明确要求可点击链接，或任务目标本身就是提供链接时才添加。
- 粗体与行内代码不能同时套在同一文本上。需要强调时使用 `**重点**`；需要呈现代码时使用单反引号；同一处二选一。
- 尽量少用单反引号。只有在代码语法、命令、路径、快捷键或精确字面量需要与普通文字区分时才使用；一般 API 名称、类型名和术语在上下文清楚时直接书写。不要为了视觉强调给普通词语加反引号。

## 2. 问题标题

一个问题通常需要包含：

1. **场景或前提**：正在使用的类型、表达式、API 或操作。
2. **现象或分歧**：实际结果、错误表现或面临的选择。
3. **回答目标**：需要理解原因、边界还是正确做法。

不强制套句式。判断标准是：只从搜索结果看到标题，读者能否确认这是自己遇到的问题。

反例：

- `整数除法为什么会得到错误的比例？`
- `为什么循环内反复 filter 是问题？`

推荐：

- `使用 Int 计算百分比时，为什么 battery / total * 100 可能得到 0，应该怎样保留正确精度？`
- `循环处理多个元素时，为什么不应在每轮都执行与循环变量无关的 filter？`

标题包含两个互不依赖的“为什么”时，拆成两个 Q。连续追问同一代码片段的“是什么、为什么、什么时候用”可以合并，但正文仍只围绕一个复习入口。

标题删去不承担区分作用的词（“典型对象代表”→“典型对象”）；问题中的动作要有明确主语（“会修改什么”→“厂商会修改什么”）。

## 3. 答案结构

首段用一至三句话给出结果、直接原因和推荐做法。不要从历史背景、术语目录或类比开始。

后续内容按依赖关系选择：

- 连续因果：前提 → 实际行为 → 结果 → 正确做法。
- 概念解释：概念 → 机制 → 对使用者的影响。
- 多种选择：先给选择依据，再列“条件 → 做法”。
- **格式与表示选择：**回答“为什么用 X 而不是 Y”时，说明下游实际接收什么、原始对象为什么不能直接使用，以及所选格式如何表达下游需要的结构和元数据。不能只说“X 用于 Y”。
- **命令链解释：**先说明整条命令链的目标，再按顺序解释每步的输入、作用和输出；只补充会改变结果的省略后果，避免逐字翻译命令或堆叠选项释义。
- **诊断输出：**多条输出看似矛盾时，先说明它们分别观察什么、数据是否实时，再按时间顺序解释状态变化。不要把“工作区干净”与“远端已同步”等不同状态混为一谈。

机制、边界、版本、示例和选型都是可选内容。它们只有在帮助理解或改变正确使用时才出现。问题两三句话已经讲清时直接结束，不补“总结”或延伸阅读。

正文每段只承担一个作用。首句指出结论，后续句子解释、证明或限定它；出现独立结论时另起段落或另建 Q。

## 4. 标题与正文等宽

标题是答案的内容契约。每一段都应能回答“它解释了标题中的哪个词或条件”。

写完后做删除测试：

1. 删除这段，读者是否仍能正确理解和使用结论？
2. 这段是否引入了标题没有承诺的新 API、选型或工程建议？

第一项为“是”，或第二项为“是”且用户没有相应问题时，删除。不要从一个局部语法问题扩展成语法家族总览。

## 5. 示例

示例必须最小、完整，并且只证明当前结论：

- 包含理解行为所需的声明、输入、外层函数和调用。
- 关键示例写明编译结果、运行结果、异常或预期输出。
- **配置属性讲解强制逐项覆盖：**示例出现构建属性、配置键、函数参数、命令行选项等时，必须解释每个属性名及其实际值；列表和映射中的每个有意义条目也必须说明，不能只概括整组配置。
- 对每个属性，必须说明它控制什么、当前值会产生什么具体效果，以及为什么在此处显式设置。还必须说明省略它时的行为和后果，包括默认值、继承/推导值、必填错误或行为差异；“省略”不能未经核实就当成 `false`、空值或当前值的反面。
- 默认值或省略行为随平台、构建系统版本、上下文变化时，必须写明适用版本与条件，并查对应版本的官方文档或实现；查不到时明确标注未知及需要核对的来源，不得猜测。若属性显式值等于默认值，也要说明这次显式声明的理由，或指出它只是冗余声明。
- 配置片段较大时，按职责拆成多个短片段或分组讲解；拆分不能成为漏讲属性、列表成员或省略后果的理由。
- **长源码按一级讲解分组：**不要一次贴出整份长声明，再要求读者在代码和解释间来回查找。按答案的一级列表分组，每组放一个对应片段；保留必要的最外层模块、类或函数闭包，片段内部只保留本组讲解的代码，其余内容用省略号表示。组内子项以文字解释为主，只有理解机制确实需要时才继续拆代码。
- **省略号必须对应真实省略：**先对照完整源码，确认省略号前后确实删去了内容；源码中紧邻的代码之间没有省略内容时，不要插入省略号。代码片段不是完整可编译代码时，应说明省略标记只是摘录占位符。
- 错误与正确示例只保留造成差异的变量。
- 非完整项目代码明确标出省略部分，不用完整代码块的外观掩盖缺失上下文。
- 多个替代方案分别展示，不能顺序写进同一程序，导致前一个方案提前返回或抛异常。
- 示例引入另一个尚未解释的概念时，缩小示例或链接到已有 Q。

“示例驱动”不等于每题必须有代码。一句话足以证明的概念不制造示例。

## 6. 术语、平台与版本

- 一个概念始终使用一个稳定术语，例如区分“只读”和“不可变”、“实例创建安全”和“初始化逻辑并发安全”。
- **首次定义陌生术语时先说明类别：**指出它是工具、数据格式、归档格式、压缩算法、文件系统还是协议，再解释它处理或规定什么，以及容易混淆的边界。只写用途不足以解释概念。
- 同一写法贯穿标题、首段和列表项；确需别名时在首次出现处括注一次，如“缓存进程冻结器（Freezer）”，后文只用一种写法。
- 明确区分 Kotlin 语言、Kotlin/JVM、Java 互操作、Android 和 Multiplatform 行为。
- 版本会改变结论时标注关键版本；不确定时查官方资料。
- “始终”“完全相同”“全进程唯一”“只是语法糖”等绝对表达必须有直接依据，并在首次出现时给出限定。
- 解释原因时使用语言规则和可观察行为，不用未经证实的字节码、生命周期或架构猜测。

## 7. 段落、列表、表格和代码

根据内容关系选择形式：

- **段落**：连续解释一个结论及其因果。
- **无序列表**：没有先后关系的并列条件、选项或限制。
- **有序列表**：必须依次执行的步骤或顺序本身影响结果的阶段。
- **表格**：尽量不用；仅当多个对象沿相同字段、单元格都是短结论、列表已承载不动时作为速查表使用。两三个对象的对照写成连续句子或列表项，不进表格。
- **代码块**：只有通过语法、类型或运行结果才能说清的行为。

**强制要求：**答案能以列表承载时，必须用列表回答，不得摊成连续段落；无序与有序皆可表达时，必须优先有序列表；同一文档必须保持一种列表风格，不得在同层级、承担相同表达作用的列表之间混用有序与无序形式。只有连续因果、连续解释等确实不适合列表的内容才保留为段落。

引导句给出计数时（“三部分”“四套”），数量必须与紧随的列表或表格条目一致；对不上时改写引导句，把不属于该计数的内容单独交代（如“三部分完成传输，AIDL 在其上提供接口契约”）。一个列表项内出现对多个子项的逐项解释（如四种线程状态的含义与排查方向）时，把子项提取为独立的列表或段落，列表项只留一句结论。

列表前用一句话说明分类维度。列表项保持语法平行、抽象层一致、一项一意，并把比较关键词放在前面，回答保持言简意赅。嵌套最多一层；需要长解释时改用段落。

**分号分项强制换行：**正文或列表项用分号连接不同职责、属性、条件或结论时，必须改为真正的 Markdown 列表项，让每项单独显示。已有外层编号时，外层只写短引导句，下一层使用缩进四空格且显式递增编号的有序子列表。没有外层编号时，直接拆成同层列表。单纯在源码中换行、加行末空格或插入 `<br>` 都不能表达并列层级。连续因果改成短句，不为换行制造无意义的子列表。代码和原文引述中的分号不受此规则约束。

表格单元格只放短结论，复杂原因放在表格后。表格前先给选择结论，不能要求读者自行从大量格子推导观点。

代码块标注语言。代码前说明观察目标，代码后说明结果和原因。需要精确呈现的代码、路径、命令和字面量使用行内代码；一般类型名、函数名和术语在语境清楚时直接书写。粗体只用于少数关键概念，不能与行内代码叠加。中文与英文、数字之间加空格。

## 8. 连贯与复用

先讲主线，再讲会改变结论的细节。过渡句只在需要说明递进、转折、因果或范围变化时出现，例如：“上面解释调用语法；下面只讨论接收者如何绑定为 `this`。”

不用“接下来介绍”“值得注意的是”“你可能会问”等聊天式铺垫。每题自成完整回答：回答当前问题所需的例子、数据与判断方法在题内给全，不用“见 Qn”把内容推给其他 Q；为自足而产生的题间重复可以接受，各题用自己的角度组织内容。文内指称必须落地：“图中”“如表所示”只能指向本文档实际存在的内容；从带图表的源材料沉淀时，删除图或改写为指向文内表格、列表，不留指向不存在对象的引用。

基础语法笔记解释语言机制；生态应用笔记解释平台用途与行为边界。示例用了 Android API，不等于整套 Android 行为都要进入基础语法题。

## 9. 列表的言简意赅写法

适合列表的内容应有明确、单一的分类维度，例如：

```markdown
选择取决于结果需要：

1. **只要整数百分比**：先乘后除，必要时先转为 `Long` 防止溢出。
2. **需要小数**：除法前把至少一个操作数转为 `Double`。
3. **需要向下取整**：使用 `Math.floorDiv`，不要依赖整数除法的向零截断。
```

不要把语言规则、业务示例、风险和延伸阅读并列在同一个列表中。因果链也不要拆成无序圆点；“判空成功 → 类型收窄 → 可以访问成员”应写成连续句子或真正有顺序的步骤。

反过来，正文和列表项都不能用分号或序词（“其一……其二……”）把可独立解释的并列项挤在同一行。已有外层主题时，按下面的形式排版：

```markdown
1. **文件作用：**两份文件按职责分工：

    1. `version_defaults.mk`：提供版本默认值。
    2. `version_util.mk`：计算最终版本。
```

子项以“名称：解释”开头，保持短而平行。若两个分句必须连起来才构成一个因果解释，就改成两个短句，不拆列表。

## 10. 总结

总结只恢复“怎么判断、怎么选择、怎么避免错误”：

- 单一结论：用一句判断规则收尾，通常不加标题。
- 多个并列选择：使用短的“条件 → 做法”列表。
- 同维度比较：先给推荐，再用列表逐项对照。
- 正文本身很短：不再总结。

不重复代码过程、术语定义、历史背景和已经说过的结论，也不用口诀或口号加强语气。

## 11. 生成与改写流程

1. **定位**：阅读目标文件、相邻 Q、`README.md` 和本指南。确定写入位置前，核对候选目录和文件的职责、内容边界及已有题目。按题目实际要解释的知识目标选择落点，不按会话顺序或示例出现的场景归档；用户明确指定现有文件时，优先遵从并检查是否符合该文件边界。
2. **定核**：用一句话写出 Q 唯一解决的问题，独立问题先拆分。
3. **补境**：把成立所需的类型、表达式、场景或异常写入标题。
4. **直答**：先写首段，确保它不依赖后文也能回答标题。
5. **排因果**：只列读者从现象到结论必须经过的节点，并按依赖排序。
6. **选形式**：连续推理用段落，并列项必须用列表，真实步骤用有序列表，同维度比较用表格；答案能以列表承载时不得写成连续段落，无序与有序皆可表达时必须选有序列表，并统一全文列表风格。
7. **补边界**：只加入会改变正确性、选择或理解的版本、平台与反例。
8. **压缩**：删除重复、旁支、口号、弱过渡和不改变判断的细节。
9. **衔接**：已有解释改用精确引用；后补内容插入最合适的位置。
10. **校验**：完成逐题验收，并同步目录、编号、题数和交叉引用。更新 README 时，按实际目录列出每篇文档并简述内容，核对目录篇数、题数与总数。

流程约束生成过程，不要求文章暴露这些步骤，也不要求每个答案长得一样。

## 12. 逐题验收

- 只看标题，能否知道场景、困惑和回答目标？
- 标题是否只承诺一个核心问题？
- 首段是否已经给出明确结论？
- **强制质量门：**回答是否达到资深面试级，讲清结论成立的条件、关键机制与因果，并覆盖会改变结论的重要边界、取舍或版本差异？是否能据此分析实际问题，而非停留在定义、结论或术语罗列？
- 每一段是否都服务于标题承诺？
- 因果能否连续读完，是否突然跳到另一套 API 或工程建议？
- 列表是否有单一维度，列表项是否平行且同层级？
- **强制门槛：**能用列表回答的答案是否全部改用列表、没有摊成连续段落？无序与有序皆可表达时是否选了有序列表？同一文档的列表风格是否一致？任一项不满足，必须修改后才能通过验收；有序列表还要检查源文本中的编号显式连续递增。
- **强制门槛：**配置或代码示例中的属性名、属性值及有意义的列表/映射成员是否逐项解释？是否说明每项的具体作用、为何显式设置，以及省略后的默认行为和实际后果？默认随版本或上下文变化时是否注明依据，未知时是否明确标出而没有猜测？任一项缺失，必须补全后才能通过验收。
- 长源码是否按一级讲解内容拆成片段，并保留必要的外层闭包？每个省略号是否都对应真实省略的源码？
- 是否尽量避开了表格？表格是否只承担多对象同字段的速查职责？
- 引导句的计数是否与列表、表格条目数一致？“图中”“上表”类指称是否都指向实际存在的内容？
- 段落或列表项里用分号、序词串起的并列信息是否已逐项换行？外层已有编号时，是否使用不超过一层的有序子列表，并检查实际渲染的缩进与编号？
- 示例是否完整、可解释结果，并且没有引入无关概念？
- 是否同时给出了会改变结论的平台、版本或前提？
- 同一概念的写法在标题、首段和列表项中是否一致？中文与英文、数字之间是否加了空格？
