# 设计模式

> 学习资料。前 16 题讨论创建型、结构型与行为型模式，Q17–Q23 讨论面向对象设计原则，Q24 讨论应用中的事件分发与策略路由。重点是辨认各模式解决的问题、变化点与代价，不把模式名当作引入抽象的理由。

**Q1: [learning] [tags:设计模式] 简单工厂模式怎样根据输入创建不同产品？它的扩展边界在哪里？**

简单工厂把具体产品选择集中在一个创建入口：客户端提供类型或配置，工厂在内部选择实现并返回共同抽象。调用方只依赖抽象产品，创建规则也有单一维护位置，但简单工厂不是 GoF 独立模式目录中的经典模式，通常指这种集中创建的惯用结构。

当产品种类少、选择规则稳定、多个调用方需要共享同一校验或默认值时，它能减少重复分支。新增产品仍要修改工厂的选择逻辑。若产品集合由插件扩展，或新增类型频繁，条件分支会成为集中变化点，此时可改用工厂方法、注册机制或依赖注入。注册表也会带来注册顺序、重复键与缺失实现等运行期错误，需要结合扩展方式选择。

**Q2: [learning] 工厂方法与简单工厂在新增产品时的变化点有什么不同？**

工厂方法将“创建哪一种产品”延迟给具体创建者：抽象创建者提供工厂方法，具体创建者覆写它并返回相应产品。简单工厂则由同一个创建入口根据参数作条件分支。二者的差别在变化位置：工厂方法通过增加创建者扩展产品类型，简单工厂通常通过修改既有选择逻辑扩展。

当不同产品有各自创建依赖、初始化规则或扩展团队，且这些扩展点值得长期稳定时，工厂方法可以避免不断改动一个集中分支。代价是产品实现通常要配套一个创建者，调用方还要选择具体创建者。若类型少且变化很少，简单工厂的直接分支更容易理解。工厂方法也不能自动保证高层策略不依赖具体工厂，客户端如何取得创建者仍需设计。

**Q3: [learning] 抽象工厂模式怎样保证一组相关产品来自同一产品族？**

抽象工厂为一组彼此相关的产品角色定义创建接口。每个具体工厂为这些角色提供同一产品族的实现。客户端在一个工厂上创建按钮、菜单等对象，因而在组合层面不容易混用不兼容的产品族。

例如 Windows 工厂为按钮与菜单都创建 Windows 风格实现，Mac 工厂则为两者创建 Mac 风格实现。具体产品实现共同遵循抽象接口，族内兼容性仍依赖具体工厂遵守契约，并非类型系统自动证明。新增产品族较直接，只需增加一套工厂和产品。新增产品角色则要扩展抽象工厂接口及所有具体工厂，属于横向扩展成本较高的结构。若产品之间并无配套关系，只是各自可替换，抽象工厂通常过度设计。

**Q4: [learning] 工厂方法与抽象工厂应该如何区分？**

判断看创建契约覆盖的产品角色数，以及这些产品是否必须协同变化：

1. **一种产品角色**需要不同实现时，工厂方法封装该产品的创建。新增实现通常新增具体创建者。
2. **多个相关产品角色**必须成组选择时，抽象工厂一次提供整组创建能力。新增产品族容易，新增产品角色则会影响所有工厂。

两者可以组合，例如抽象工厂中的某个创建方法内部也采用工厂方法。名称不是判断依据。如果客户端拿到多个互不相关产品，抽象工厂并不会凭接口名称保证它们的业务兼容性。

**Q5: [learning] 建造者模式解决了复杂对象创建中的什么问题？**

建造者把复杂对象的构造过程与最终表示分开，让调用方按步骤提供配置，并在构建阶段集中处理默认值、校验和组装。它适合构造参数多、可选字段多或构造顺序需要表达的对象。

1. **构造器**保存逐步收集的配置或部件。
2. **构建操作**检查必需条件并生成目标对象。
3. **目标对象**只暴露有效状态，避免大量难以辨认的重载构造函数。

不复杂的对象无需为每个构造过程单独引入 Builder。若允许任意步骤顺序，也要明确哪些配置可重复或互相覆盖。

**Q6: [learning] 建造者模式中的 Director 是否是必需角色？**

Director 不是必需角色。它负责把稳定的构造顺序封装成可复用流程，Builder 则负责收集参数、校验约束并生成目标对象。当多处调用都需要相同的构造配方，Director 能防止步骤遗漏或顺序漂移。

若只有一种简单配方，或调用方必须动态决定每一步，直接调用 Builder 更灵活，也少一层类型。是否引入 Director 取决于“构造流程是否本身是需要复用的业务规则”，而不是建造者模式必须凑齐多少角色。

**Q7: [learning] 装饰器怎样在不改目标类的前提下组合附加行为？**

装饰器实现与被包装对象相同的抽象接口，并持有一个同类型对象。调用时先执行附加行为，再委托核心操作，或在返回后加工结果。多个装饰器可以嵌套，使功能组合不必为每种组合都创建一个子类。

咖啡订单可以先包装基础咖啡，再依次包装牛奶或糖，每层按自身规则更新描述和价格。装饰器适合职责可独立组合、包装顺序有意义且调用方只依赖共同接口的场景。若附加行为要求访问被包装对象的具体类型、顺序组合含义不明确或包装层很多，运行时对象链会增加调试与状态追踪成本。此时显式组合对象或配置式管线可能更清楚。

**Q8: [learning] 装饰器与代理都包装对象，怎样按意图区分？**

两者常有相同的结构：都实现与目标相同的接口，并将调用转发给目标。区分看主要意图：装饰器让调用方选择叠加的附加职责。代理代替调用方控制目标访问，例如延迟创建、权限检查、远程边界或缓存。

如果调用者可以自由叠加多个行为且包装顺序属于功能组合，采用装饰器语义。如果调用者只需要像使用目标一样使用一个受控入口，代理语义更合适。代理也能执行附加逻辑，装饰器也能缓存，因此应按对象所有权、替换方式与公开给调用方的配置能力判别，而不能只看类图。

**Q9: [learning] 责任链模式怎样处理多个可能的请求处理者？**

责任链把一组候选处理者组织成有序链，请求沿链交给处理者判断：处理者可以处理后终止，也可以拒绝或继续传递。发送者只提交请求，不必直接选择具体处理类。

设计时要明确每个节点的处理契约、链顺序是否影响结果、是否允许多个节点处理同一请求，以及遍历到链尾仍无人处理时如何失败或回退。若所有请求最终都固定交给同一处理器，直接调用通常更简单。链还会增加追踪实际处理者的成本，调试日志应能识别请求经过的节点。

**Q10: [learning] 责任链与装饰器的调用结果语义有什么不同？**

判断结果语义而不是类图：

1. **责任链**在多个候选者之间传递处理权。处理者可以接收并终止，也可以把请求交给下一个节点。链可能没有节点接收请求，或由多个节点按契约共同处理。
2. **装饰器**围绕一个核心对象叠加职责。包装层通常会委托核心操作，并可在委托前后改变行为或结果。

要选择“由谁处理”用责任链，要选择“给同一个对象组合哪些职责”用装饰器。若链中每个节点都必须执行前置/后置逻辑，结构可能更接近装饰器。应由处理权是否转移来决定语义。

**Q11: [learning] 观察者模式怎样让状态变化通知多个订阅者？**

主题保存订阅关系，并在约定事件发生时通知观察者。通知可以带上事件或状态，也可以只提示观察者重新查询。主题面向观察者抽象，使新增订阅者不必修改主题内部的具体调用列表。

实现需要定义注册/注销时机、通知顺序、并发修改订阅集合时的处理方式，以及回调抛错是否阻断后续观察者。若主题强引用观察者，短生命周期对象必须及时注销或使用生命周期感知的订阅机制，否则会延长对象存活时间。弱引用不是自动的正确替代，因为订阅者可能被意外回收。通知只携带信号时还要避免观察者读到与事件不一致的状态快照。

**Q12: [learning] 观察者通知采用推模型还是拉模型？**

推模型由主题把事件数据或新值直接传给观察者，观察者不必额外读取。它适合事件不可重建、或必须处理准确变化值的场景，但主题要定义稳定载荷，慢观察者也可能承受过多推送。拉模型只发送“状态已变化”的通知，观察者按需查询当前状态，能合并多次变化并降低主题对订阅者需求的了解，但读取可能较贵，或读到更新后的状态而不是触发通知时的快照。

如果业务关心每个事件，选择推送不可丢失的事件载荷。如果只关心最终状态，可采用拉取或带版本号的状态快照。异步场景还要明确顺序、背压、合并、丢失、重试与取消，否则推拉方式本身不能提供可靠投递保证。

**Q13: [learning] 策略模式怎样隔离可替换的算法？**

策略模式把一组可互换的行为封装在共同契约后，由上下文委托当前策略执行，从而把算法细节和主流程分开。策略应表达“如何完成同一目标”，而不是仅仅把几行代码搬进不同类。输入、输出与错误语义应足够一致，使调用方能替换实现。

它适合算法分支会扩展、需要独立测试或需在运行时按条件切换的情形。策略选择可以由调用方、配置或专用选择器完成，策略模式本身不解决选择规则。只有一个稳定实现时，引入接口和对象组装会增加间接层。若算法差异只是一两个简单表达式，普通条件分支可能更易读。

**Q14: [learning] 策略模式和简单工厂可以怎样协作？**

策略接口定义一类算法的输入输出契约。工厂或选择器可以依据配置、请求类型和运行环境选择并创建具体策略。策略让执行算法可替换，工厂集中创建规则，两者可组合，但工厂并不负责算法正确性，策略接口也不必然要求工厂。

当策略创建需要依赖注入、生命周期管理或复杂配置时，由工厂组装能避免业务调用方了解实现类。如果调用点本来就明确持有策略，直接注入即可。选择规则频繁变化时，应把规则显式放在选择器中，避免再次把大段条件塞回上下文。

**Q15: [learning] 代理模式通过什么方式控制对目标对象的访问？**

代理实现与目标相同的抽象契约，并代表客户端持有或取得目标对象。调用方通过代理访问目标，不需要知道代理何时创建目标或是否跨越边界。代理可提供访问控制、延迟初始化、缓存、远程调用或生命周期控制，但这些行为会改变调用失败、时延和可见副作用，必须保持接口契约可理解。

代理有明确价值的条件是访问本身需要被管理，而不是只为“多一层抽象”。例如延迟代理的首次调用可能承担初始化成本，远程代理可能失败或超时，缓存代理需定义失效策略。若调用方需要直接组合可选附加职责，装饰器的意图通常更清楚。

**Q16: [learning] 静态代理和动态代理的实现成本有何区别？**

静态代理由开发者为具体接口显式编写代理类，编译器能检查方法签名，逻辑也容易跳转调试。缺点是接口扩展时代理要同步维护，多个接口会重复转发代码。动态代理在运行时创建转发实现，适合横切逻辑需要覆盖许多接口方法或目标类型时减少样板代码，但调用路径更间接，常涉及反射或字节码生成，类型错误和性能成本可能推迟到运行期暴露。

Java 标准库 `java.lang.reflect.Proxy` 创建的是接口代理，目标类型必须实现至少一个接口。代理方法通过 `InvocationHandler` 接收并分派。代理类本身不能直接代理任意具体类。基于子类字节码生成的库使用不同机制，可能受 final 类/方法、构造器和运行时限制影响，不能把这些能力归到 JDK 接口代理。若只有少数稳定方法，静态代理更直观。采用动态代理前应核对所用技术的目标类型限制和异常包装行为。

**Q17: [learning] 单一职责原则中的“单一”应如何理解？**

单一职责原则中的“单一”指模块围绕一类紧密相关的变化原因负责，不是类只能有一个方法。职责边界可从变化触发者与变化理由观察：若两个变化由不同需求驱动、各自修改却总要连带回归另一部分，模块可能承载了多个职责。

重构时按稳定的业务能力或变化原因划分，并检查拆分后依赖方向与协作是否清楚。拆得太细会增加对象组装、跨模块调用和排查路径。因此方法数、代码行数或“看起来很多功能”都不能单独证明违反 SRP。

**Q18: [learning] 开放封闭原则怎样与实际扩展需求平衡？**

开放封闭原则（OCP）要求模块对已识别的变化方向可扩展，同时尽量不反复改动已稳定的核心逻辑。它不是禁止修改既有代码。实际做法是观察真实需求变化，找到反复变动而相对稳定的边界，再通过多态、组合、策略或注册点容纳变化。

扩展点本身有设计和维护成本，过早为想象中的变化预留抽象会让阅读与调试更复杂。面对仅出现一次、尚无稳定规律的变化，直接修改通常更经济。当多个独立实现已经沿同一维度变化时，再抽取扩展接口更有证据。OCP 的“关闭”只针对该扩展维度，并不保证系统其他方面无需改动。

**Q19: [learning] 里氏替换原则如何判断子类型是否能替代父类型？**

里氏替换原则要求：凡是依赖父类型契约的客户端，在传入子类型后仍能满足预期行为。判断不是看是否能赋值或通过编译，而是检查子类型是否维持父类型对输入、输出、异常和状态不变量的承诺。

子类型不能要求更强的调用前提、提供更弱的结果保证，也不能破坏父类型承诺的不变量。新增限制或改变副作用都可能破坏替换。若子类为了适应自身实现而拒绝父类型允许的操作，通常说明继承关系或父类契约不合理，应重构成组合、能力接口或不同抽象，而不是用类型转换在调用方补洞。

**Q20: [learning] 依赖倒置原则与依赖注入分别强调什么？**

两者分别回答“依赖关系如何设计”与“依赖实例如何提供”：

1. **依赖倒置原则（DIP）**约束源码依赖方向：高层业务策略不应直接依赖易变的底层细节，双方应依赖稳定抽象，具体细节再实现该抽象。
2. **依赖注入（DI）**是一种对象组装方式：由调用方、容器或构造器把依赖实例提供给使用者。

DI 是落实 DIP 的常见手段，却不会自动产生良好架构：若高层仍依赖一个暴露底层细节的抽象，方向虽经接口包装仍可能没有倒置。反过来，也可用工厂或模块边界落实依赖倒置，而不必使用大型 DI 容器。抽象应由高层所需能力定义，避免成为底层 API 的机械镜像。

**Q21: [learning] 接口隔离原则怎样减少调用方对无关能力的依赖？**

接口隔离原则（ISP）要求客户端只依赖完成自身任务所需的操作，避免一个变化或未实现的方法迫使所有实现者和调用方承受无关能力。接口应依据真实客户端职责划分：

1. **分离无关能力**：只读消费者依赖查询接口，管理端才依赖修改接口。
2. **维持概念内聚**：若多数客户端总是共同使用一组操作，拆开会让组装更复杂，通常没有收益。

接口不能无限拆小，否则客户端必须组装大量接口而难以定位概念。默认方法或空实现也不能自动解决职责过宽的问题。

**Q22: [learning] 迪米特法则怎样减少对象对协作对象内部结构的了解？**

迪米特法则强调减少对象对协作对象内部结构的了解：调用方应通过直接协作者提供的稳定业务操作完成工作，避免依赖一串内部对象关系。这样内部结构变化可封装在拥有该关系的对象中，调用方不必跟着改动。

它不是禁止点号链，也不是规定每个访问都增加转发方法。若链式调用表达稳定的数据导航，或调用方确实需要该对象组合，封装转发反而制造重复 API。判断重点是调用方是否依赖了不属于自身职责的内部关系，以及内部变化是否会迫使它修改。

**Q23: [learning] 合成复用原则为什么通常偏向组合而不是继承？**

合成复用原则（CRP）倾向通过组合与委托复用已有行为，而非继承父类实现。组合允许按对象组装能力、运行时替换协作者，并避免子类绑定父类内部实现。继承则可用于真实的可替换子类型关系，或框架提供的稳定受控扩展点。

选择取决于三个方面：行为是否需独立替换、父类实现和契约是否稳定、子类是否能满足替换原则。组合会增加依赖装配与委托代码，继承会增加层级耦合与脆弱基类风险，两者都不是默认无成本。

**Q24: [learning] 统一分发与策略路由怎样降低事件入口和业务执行之间的耦合？**

统一分发将多个入口产生的同类请求汇入稳定边界。分发器先执行共同校验与记录，再根据请求类型将工作交给相应策略。策略封装各自的业务动作，因而新增动作不必让每个入口重复写路由和横切逻辑。职责边界可按执行顺序划分：

1. **入口适配**：把 UI、系统回调或外部命令转换成稳定请求，不把 View 或回调对象传入业务核心。
2. **共同分发**：执行所有请求都需要的校验、鉴权、去重与日志，并记录路由决策。
3. **策略执行**：处理具体业务，返回明确成功、失败或异步结果。

请求应使用稳定的数据契约表达意图，让业务策略不依赖具体 View 或 UI 回调。这样才能在 UI 外构造请求并验证分发结果。应明确未知类型、缺失策略、执行失败和异步结果如何返回，并为路由决策保留可观测记录。统一入口会成为关键依赖，若它开始承载每种业务细节或维护复杂隐式映射，就会变成新的万能类。此时需拆分路由域或把分发下沉到各自业务模块。
