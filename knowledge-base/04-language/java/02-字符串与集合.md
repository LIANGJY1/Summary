# 字符串与集合

> Java 字符串与常用集合学习资料（2026-10-05 重构，自 core-types-and-collections.md 拆出）：String 的相等语义与常量池、拼接成本、数组与 List 的类型检查差异、ArrayList 与 LinkedList 的成本模型。结论按 Java 语言与标准库口径（JDK 8+ 为基线）。Q 序列即结构，供 atlas 同源直读。

**Q1: [learning] 数组与 ArrayList 在容量与类型检查上有什么区别？各自适合什么场景？**

数组长度创建后固定，运行时保留组件类型并检查存储。`ArrayList` 是可调整容量的泛型集合，编译期提供泛型类型检查，内部容量随元素数增长。数组适合固定长度或与要求数组的 API 交互，集合适合动态增删。

1. **类型检查时机**：数组协变且运行时检查——把 `Cat[]` 赋给 `Animal[]` 后写入 Dog 会在运行时抛出 `ArrayStoreException`。泛型集合不变，不匹配在编译期被拒绝。
2. **容量**：数组定长。ArrayList 底层数组扩容拷贝，适合尾部追加为主的场景。
3. **选择**：与底层 API 交互、性能敏感的定长数据用数组。日常动态数据用集合。

**Q2: [learning] 字符串字面量与 new String 用 == 比较为什么会得到不同结果？判断内容相等应该用什么？**

对引用类型，`==` 比较两个引用是否指向同一对象。`String.equals` 比较字符序列内容。字符串字面量可能通过常量池共享同一对象，`new String(...)` 则必然创建新对象，因此不能用 `==` 判断内容相同。

1. **常量池**：相同字面量在编译期合并，运行时指向池中同一实例。`==` 对字面量比较常“碰巧”为 true，这是陷阱而非保证。
2. **运行期拼接**：变量参与的拼接在运行时产生新对象，不再与池中字面量同引用。
3. **实践规则**：内容相等一律用 equals。需要规范引用（如加锁对象、去重）才考虑 ==，并确保来源可控。

**Q3: [learning] 循环中拼接字符串为什么可能变慢？何时必须换 StringBuilder？**

`String` 不可变，每次拼接产生新的结果对象，循环累积会反复分配并拷贝。`StringBuilder` 在可变缓冲区上追加，最后一次 toString 才生成字符串。

1. **成本来源**：n 次循环拼接的字符串方案是 O(n²) 量级的分配与拷贝。StringBuilder 均摊接近 O(n)。
2. **例外**：少量、编译期可确定的拼接由编译器优化即可，不必手动创建 Builder。
3. **线程边界**：StringBuilder 非线程安全。单线程内使用，多线程共享场景改用局部变量收敛或 StringBuffer。

**Q4: [learning] ArrayList 与 LinkedList 的增删查成本为什么取决于操作位置？**

`ArrayList` 以连续数组存储，随机读取为常数时间，但中间插入删除要移动后续元素。`LinkedList` 以节点链接存储，已持有节点时改链接成本低，但按索引定位需要遍历。内存局部性与额外节点开销也影响实际表现。

1. **读取**：ArrayList 常数时间随机访问。LinkedList 定位是线性的。
2. **插入删除**：ArrayList 头部与中间操作要搬移元素。LinkedList 在已定位节点处改链接快，但“先定位”的成本仍是线性的——“链表插入总是 O(1)”不成立。
3. **实践**：绝大多数场景默认 ArrayList。仅当算法天然沿节点遍历并就地增删时才考虑 LinkedList。
