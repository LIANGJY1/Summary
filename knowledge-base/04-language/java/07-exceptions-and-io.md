# 异常与 I/O

> Java 异常与输入输出学习资料（2026-10-05 重构，自 exceptions-io-and-files.md 拆出异常与流两族）：受检异常的处理契约、路径抽象与内容传输的分工、流族的选型与字符集、try-with-resources 的关闭语义。序列化主题另见 [08-serialization.md](./08-serialization.md)。结论按 Java 标准库口径（JDK 8+ 为基线，NIO.2 自 Java 7）。Q 序列即结构，供 atlas 同源直读。

**Q1: [learning] 受检异常为什么强制调用方处理？RuntimeException 与 Error 为什么不受此约束？**

受检异常要求调用方捕获或在方法签名中继续声明，编译器以此把“调用者可能恢复的失败”编码进类型签名；非受检异常（RuntimeException 及其子类与 Error）不受这项编译期义务，因为它们表达编程错误或不应指望应用处理的系统级失败。

1. **类型分层**：Throwable 下分 Error（如 OutOfMemoryError，表示不应捕获恢复的严重失败）与 Exception；Exception 中除 RuntimeException 之外的都是受检异常。
2. **设计意图**：受检=调用方可有应对策略的外部条件（IO 失败、配置缺失）；非受检=应通过修复代码消除的缺陷，到处声明只会淹没签名。
3. **处理规则**：捕获后要么恢复、要么转换成更合适的异常（保留 cause）再抛、要么记录后上抛；静默吞掉异常会让失败点与发现点分离。
4. **边界**：不要为绕过编译检查随手包装成 RuntimeException；也不要把所有失败都压成同一异常类型，异常类型本身是调用方的分支依据。

**Q2: [learning] File 对象存在不代表文件存在——路径抽象与内容传输如何分工？新代码为什么改用 Path 与 Files？**

`File` 表示路径名及文件系统操作入口，不承载文件内容；字节或字符的传输由输入输出流完成。`File` 对象创建成功不代表对应路径存在，也不保证后续操作成功。

1. **职责分离**：路径抽象（定位、元数据、增删）与内容读写（流）是两套 API；操作文件要先在路径层定位，再经流传输内容。
2. **NIO.2 取代**：Java 7 起的 `Path` 不可变、`Files` 提供更完整的属性、符号链接与异常语义，新代码优先使用；旧 API 与之可经 `File.toPath()` 互转。
3. **失败模式**：文件操作受权限、并发变化与平台路径差异影响，必须显式检查异常与返回状态，不能以对象存在为前提。

**Q3: [learning] 字节流、字符流与缓冲流分别解决什么问题？处理文本为什么必须显式指定字符集？**

按处理单位选流族，按访问粒度加缓冲：

1. **二进制数据**：`InputStream`/`OutputStream` 处理原始字节，适合图片、压缩包等。
2. **文本数据**：`Reader`/`Writer` 按字符处理并涉及字符集编码；字节与字符的转换须显式配置字符集——依赖平台默认编码会让同一份数据在不同环境解出不同文本。
3. **大量小块访问**：在基础流外包缓冲层（如 BufferedInputStream）减少系统调用次数；无论哪族，结束时都要正确关闭资源。

**Q4: [learning] 为什么流必须在确定路径上关闭？try-with-resources 在异常与关闭失败时各做什么？**

实现 `AutoCloseable` 的资源可由 try-with-resources 在退出作用域时自动关闭，包括发生异常的路径；比依赖调用者记住所有分支上的 `close()` 更可靠。

1. **异常路径覆盖**：try 体抛异常时资源仍会关闭，手写 finally 容易在异常路径遗漏。
2. **抑制异常**：若关闭本身也失败，Java 保留 try 体的主异常，把关闭异常作为 suppressed exception 挂在其上——主失败原因不会被关闭失败覆盖；手写嵌套 finally 反而常见主异常丢失。
3. **关闭顺序**：多个资源按声明的逆序关闭，与依赖方向一致。
