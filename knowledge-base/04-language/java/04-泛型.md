# Java 泛型

> Java 泛型学习资料。主线：泛型的编译期检查价值、类型擦除及其设计权衡、通配符与 PECS、泛型数组与堆污染、签名元数据与反射可见性。结论按 Java 语言规范口径（JDK 8+ 为基线，C#/CLR 对照仅用于说明设计取舍）；Android 侧泛型实践归 ../../01-android/ 对应册。Q 序列即结构，供 atlas 同源直读。

**Q1: [learning] Java 为什么需要泛型，泛型有什么用？**

泛型解决的核心问题是“容器与算法同元素类型之间的耦合”：没有泛型时，集合只能以 Object 承载元素，取出来要手动强转，把错误类型放进去也能编译通过，直到运行时抛出 ClassCastException。泛型把类型提升为参数，把这类检查从运行时提前到编译期。

收益有三点：

1. **编译期类型检查**：List<String> 只能加入字符串，放错位置在编译时报错，而不是运行时崩溃。
2. **消除显式强转**：读取侧由编译器插入隐式转换，代码里不再出现 (String) list.get(0) 这类样板。
3. **一套代码复用多种类型**：ArrayList<T>、Map<K, V> 等容器与算法只需实现一次，按实参适配各类型。

泛型不改变字节码层面的运行机制——实参编译后被擦除、运行时不保留——它的本质是把“运行时才发现的类型错误”变成“编译期直接拒绝”。



**Q2: [learning] Java 泛型如何在复用代码时保留编译期类型检查？**

泛型把类型参数写入类、接口或方法声明，使编译器能在调用点检查类型并减少显式转换。Java 泛型主要通过类型擦除实现：大多数泛型类型实参不会作为独立运行时类型保留，编译器会插入必要的转换并按边界擦除。



**Q3: [learning] 为什么 List<Integer> 不能赋值给 List<Number>？**

Java 泛型类型通常是不变的。若允许这种赋值，接收方就能把 Double 写进原本只接受 Integer 的列表，破坏类型安全。需要表示协变读取或逆变写入时，可使用有界通配符。

不变约束的是参数化类型之间，并不否定元素本身的 is-a 兼容关系，List<Number> 变量仍可以加入 Integer、Double 实例。坚持不变还因为泛型经擦除实现，运行时没有实参类型可用于写入检查，即便放行协变赋值，也无法像数组那样靠运行时存储检查补救，只能在编译期直接拒绝。



**Q4: [learning] Java 泛型中的上界和下界通配符分别适合怎样的操作？**

`? extends T` 表示未知的 T 子类型，适合从集合读取为 T。`? super T` 表示未知的 T 父类型，适合向集合写入 T。通用记忆规则是 PECS：生产者用 extends，消费者用 super。

通配符会限制可安全执行的操作：`List<? extends Number>` 可读出 Number，但不能安全地加入某个具体 Number。`List<? super Integer>` 可加入 Integer，但读出时只能保证是 Object。同一集合既要按 T 读取又要写入 T 时，任何一个方向的通配符都无法满足，应使用精确的元素类型。



**Q5: [learning] 为什么 Java 不能直接创建泛型类型的数组？**

数组是协变的且在运行时保留元素类型：`Cat[]` 可以赋给 `Animal[]`，随后向其写入 Dog 会触发运行时存储检查并抛出 ArrayStoreException。泛型实参通常经擦除后不保留，若放行创建 `T[]` 或 `List<String>[]`，协变赋值后的写入将没有实参类型可供检查，堆污染会潜伏到读取处才抛出 ClassCastException。因此 Java 在语言层面禁止直接创建泛型数组。常见替代是使用泛型集合，或在明确边界时借助反射创建数组并集中封装转换。



**Q6: [learning] 类型擦除后，泛型方法重载为什么可能发生名称冲突？**

若两个重载只在类型参数上不同，擦除后它们可能具有相同的 JVM 方法签名，无法同时生成。设计 API 时应让擦除后的参数类型仍可区分，不能依赖泛型实参构成运行时重载。



**Q7: [learning] Java 泛型中的 List<?> 与原始类型 List 有什么区别？**

`List<?>` 表示元素类型未知但仍受泛型类型系统约束的列表。可以安全读取为 `Object`，但不能加入任意元素（除 null）。原始类型 `List` 则绕过泛型检查，允许不安全写入，可能把类型错误推迟到运行时。

新代码应使用具体泛型或通配符表达类型边界。原始类型只适合与未泛型化的旧 API 互操作，并应尽量把未检查转换限制在边界处。



**Q8: [learning] Java 泛型擦除后为什么还能通过反射看到部分泛型信息？**

泛型实参通常不参与对象运行时类型检查，运行期的 `List<String>` 与 `List<Integer>` 都是原始类 `List`。但编译器可在 class 文件的 Signature 元数据中保留类、字段或方法声明上的泛型签名，反射 API 因而能读取声明级泛型信息。

这不代表运行时能从任意集合实例恢复每个元素的真实类型。通过原始类型、反射或不安全转换写入的数据仍可能违反声明。反射读到签名元数据与对象实例携带完整泛型类型是两件不同的事。



**Q9: [learning] Java 泛型方法的类型推断怎样确定类型实参？**

调用泛型方法时，编译器会依据实参类型、目标类型和类型参数的上下界约束推断可用类型。能够唯一确定时通常无需显式写类型实参。推断仍受方法签名与上下文约束，不会在运行时根据对象内容重新选择类型。

如果多个约束不兼容或上下文不足，编译器会报告类型推断失败。可通过显式类型实参或调整参数/返回类型表达期望，但不应靠未经检查的强转绕过约束。



**Q10: [learning] Java 泛型上界与多重边界限制了什么？**

类型参数可用上界限制可接受的类型，并获得该边界声明的方法能力。多重边界可同时要求一个类边界和多个接口边界，例如 `<T extends Base & Closeable & Comparable<T>>`。若指定类边界，它必须排在最前面。

边界只约束编译期可接受类型，不会改变 Java 单继承规则，也不会让运行时保留完整类型实参。设计边界时只声明方法实现真正依赖的能力，过多限制会降低 API 的可复用性。



**Q11: [learning] 声明泛型 Person<T> 再以 Person<Student> 使用时，类型参数与类型实参有什么区别？**

类型参数是声明处的编译期占位符，类型实参则是使用处绑定到占位符的具体类型。Person<T> 整体是泛型类型，Person<Student> 整体是参数化类型。

可以从三个视角区分二者：

1. **声明处**：类型参数的作用域限于所在类、接口或方法声明，同一个 Person<T> 每次使用时可以绑定不同的类型实参。
2. **使用处**：类型实参必须是引用类型，`List<int>` 无法编译。编译器以实参为准，检查该使用处对元素的读写。
3. **反射视角**：参数化类型以 ParameterizedType 表示，配合 class 文件保留的签名元数据，可以在声明级别还原绑定的具体实参。



**Q12: [learning] Java 泛型为什么采用编译期擦除实现，而不在运行时保留类型实参？**

擦除是 JDK 5 引入泛型时为兼容旧生态做出的权衡：类型实参只参与编译期检查，随后从字节码中抹去，运行时不存在独立的泛型类型，因此 Java 泛型常被称为伪泛型。

JDK 5 之前部署的 JVM 和类文件格式都不认识泛型。若让泛型实体化（在运行时保留类型实参），就需要新的字节码表示与运行时支持，旧环境将无法运行新代码。C# 的 CLR 走了实体化这条路，Java 则让泛型类擦除后仍以普通类的形式存在，与泛型化之前编译的字节码直接互操作，没有类型实参的原始类型就是为这种衔接保留的合法形式。

运行时没有类型实参，一批写法因此被语言直接禁止：

1. 不能创建泛型数组，擦除后数组拿不到真实的元素类型，存储检查无从拦截错误写入。
2. 不能只按泛型实参区分方法重载，擦除后这些重载的方法签名相同。
3. 不能对具体泛型实参做 `instanceof` 判断，`obj instanceof List<String>` 无法编译，只能判断到 `List<?>`。

确实需要泛型信息时，只能经反射读取类、字段、方法声明上保留的签名元数据。

**Q13: [learning] 泛型可变参数（T...）为什么会带来堆污染？@SafeVarargs 解决什么问题？**

声明 `test(List<String>... lists)` 这类泛型可变参数时，编译器在调用处创建一个 List<String>[] 数组装载实参——而这正是语言禁止开发者亲手创建的泛型数组。数组的运行时类型被擦除为 List[]，任何 List 都能放进去。一旦某个元素实际是 List<Integer>，它就混进了“声称全是 List<String>”的数组，这种参数化类型变量引用了不属于其实参类型的对象的状态就是堆污染，后果是读取元素时在意想不到的位置抛出 ClassCastException。

堆污染不必然发生：可变参数数组只要只被读取、不把数组本身（或其别名）泄漏给会写入 List 的代码，就是安全的。@SafeVarargs 是开发者的显式承诺——注解声明“方法体不会对可变参数数组做写入或泄漏”，编译器据此压制调用处的 unchecked 警告。它只允许标注 static、private、final 方法与构造器（构造器自 Java 9 起）：实例方法可被子类重写，重写实现可能违背承诺，因此不允许标注。

判断规则：确信方法体对可变参数只读时加 @SafeVarargs 消除警告。只要数组可能被写入或传出方法，就改为接收 List<List<String>> 这样的显式参数，让类型检查重新生效。
