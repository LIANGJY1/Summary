# C++ 语言基础

> 本文介绍 C++ 的词法与对象基础、编程范式、命名空间与 static 链接性、程序入口和基础 I/O。

**Q1: [done] C++ 命名空间如何组织名称、区分同名实体并控制名称查找？**

命名空间为函数、类型和变量等名称提供独立作用域，用于组织相关代码并避免不同模块的名称冲突。它参与编译期名称查找，不是访问控制机制。

例如，两个模块各有 `init::start()`，可用限定名区分，也可在命名空间外定义已声明的函数：

```cpp
namespace android { namespace init { int start(); } }
namespace vendor { namespace init { int start() { return 2; } } }

int android::init::start() { return 1; }

int main() {
    return ::android::init::start() + vendor::init::start();
}
```

`::` 是作用域解析运算符，前导 `::` 从全局作用域开始查找。命名空间外的定义须与已有声明指向同一实体；名称或作用域不匹配可能导致编译错误或链接不到定义。

访问标准库名称时，头文件和名称查找各有作用：

1. **头文件：**`#include <iostream>` 提供声明，不会把 `std::cout` 移出 `std` 命名空间。`using` 也不能代替包含所需头文件。
2. **限定名：**直接使用 `std::cout`，明确名称归属。
3. **using 声明：**`using std::cout;` 引入单个名称，可在适当作用域内简化使用。
4. **using 指令：**`using namespace std;` 使非限定名称查找考虑 `std` 中的声明。它要求后面是命名空间名，不能写成 `using namespace std::cout;`。

应避免在头文件中使用 `using namespace std;`：该指令会影响包含该头文件后续代码的名称查找，增加冲突或歧义的风险。只需少量名称时，优先使用限定名或作用域较小的 using 声明。









**Q2: [done] C++ 的翻译单元是什么？**

翻译单元是编译器处理的一份源码单元。通常一个 `.cpp` 文件经过预处理后，连同展开的头文件内容形成一个翻译单元；不同 `.cpp` 文件通常分别编译，之后再链接。

例如，`a.cpp` 和 `b.cpp` 都包含 `util.h`，则该头文件的内容分别参与两个翻译单元的编译。头文件通常不是独立编译的翻译单元，但也可以由构建命令直接作为输入。预处理条件和宏可能使同一头文件在两个翻译单元中的展开结果不同。







**Q3: [done] 内部链接是什么？**

内部链接（internal linkage）表示一个名称对应的实体只能在同一翻译单元内通过该名称引用。

例如，把变量定义放在头文件中，再由两个源文件分别包含：

```cpp
// counter.h
static int count = 0;
```

```cpp
// a.cpp
#include "counter.h"
int next_a() { return ++count; }
```

```cpp
// b.cpp
#include "counter.h"
#include <iostream>

int next_a();
int next_b() { return ++count; }

int main() {
    std::cout << next_a() << '\n';  // 1
    std::cout << next_a() << '\n';  // 2
    std::cout << next_b() << '\n';  // 1
}
```

`#include` 将头文件内容分别纳入 `a.cpp` 和 `b.cpp` 的翻译单元。由于 `count` 具有内部链接，两处定义形成两个独立变量：前两次调用修改 `a.cpp` 的 `count`，最后一次调用修改 `b.cpp` 的 `count`，所以输出依次为 `1`、`2`、`1`。头文件保护宏只能防止同一翻译单元重复包含，不能让两个变量共享状态。



**Q4: [learning] static 关键字在不同位置分别起什么作用？**

`static` 的作用取决于声明位置：

1. **命名空间作用域：限制链接。**静态函数或变量具有内部链接，只能在当前翻译单元中通过名称引用。翻译单元是源文件预处理后的结果。

    ```cpp
    // util.cpp
    static int count = 0;
    int next() { return ++count; }
    ```

    其他源文件不能直接引用这里的 `count`，但可调用对外声明的 `next()`。如果把 `static` 定义放在头文件中，每个包含它的翻译单元各有独立副本，状态不共享。

2. **块作用域：保留局部变量的值。**静态局部变量只能在所在块内访问，存储持续到程序结束，多次调用共享其值。

    ```cpp
    int next() {
        static int count = 0;
        return ++count;
    }
    ```

    连续调用返回 `1`、`2`、`3`。常量初始化可在首次执行声明前完成，动态初始化在首次执行到声明时进行。C++11 起，并发首次初始化时其他线程会等待，但后续读写仍需同步。

3. **类成员：属于类而非对象。**静态数据成员不随对象复制，静态成员函数没有 `this`，不能直接访问非静态成员。

    ```cpp
    struct Counter {
        static int count;
        static void increment() { ++count; }
    };
    int Counter::count = 0;
    ```

    `Counter::increment()` 修改的是类共享的 `count`，无需创建对象。类模板的不同特化各有自己的静态成员。







**Q5: [learning] 什么是词法记号（token）？标识符与它是什么关系？**

词法记号（token）是词法分析阶段识别的基本单元，包括关键字、标识符、字面量、运算符和标点符号。标识符是其中一类，用于命名变量、函数和类型等实体。









**Q6: [learning] 字符串字面量在翻译中如何处理？**

双引号括起的内容作为程序数据参与后续翻译。









**Q7: [learning] 注释在翻译中如何处理？**

注释不作为程序语句执行，翻译阶段被替换为空格。

1. `//` 注释延续到当前行末。
2. `/* ... */` 注释延续到结束标记。普通块注释不支持嵌套。









**Q8: [learning] int carrots; 是声明还是定义？**

在函数块内，`int carrots;` 定义具有自动存储期的 `int` 对象，生命周期随所在块的执行结束而终止。编译器不一定把对象实际放在栈上。

1. **定义：**声明实体并提供存储。
2. **声明：**引入名称和类型信息，如 `extern int carrots;` 通常声明在其他位置定义的对象。









**Q9: [learning] carrots = 25; 做了什么，赋值表达式还有什么结果？**

赋值将右侧值转换为左侧对象的类型并更新该对象。内建赋值表达式的结果是左侧对象的左值，因此 `a = b = 25` 按 `a = (b = 25)` 求值。









**Q10: [learning] 编程范式是什么，C++ 支持哪些范式？**

编程范式是组织程序结构与表达计算过程的一类方法。C++ 支持多种范式，可在同一程序中组合使用。

1. **过程式：**以函数和顺序控制组织操作步骤。
2. **面向对象：**以类封装状态和操作，并通过对象表达程序实体。
3. **泛型：**通过模板编写适用于多种类型的算法和容器，并在编译期检查类型。
4. **函数式风格：**使用函数对象、lambda 表达式和算法组合等方式组织计算。C++ 并非纯函数式语言。









**Q11: [learning] C++ 中的类和对象分别是什么？**

类定义用户自定义类型及其成员。对象是该类型的实体，具有相应的生命周期和状态。静态数据成员属于类，不会为每个对象分别存储一份。









**Q12: [learning] 为什么 <iostream> 与 <unistd.h> 的扩展名不同？**

这是标准来源和命名约定不同造成的。扩展名本身不决定文件是否为头文件。

1. `<iostream>` 是 ISO C++ 标准库头文件，标准名称不带扩展名，其中的标准库名称属于 `std` 命名空间。
2. `<unistd.h>` 是 POSIX 头文件，不属于 ISO C++ 标准库。只有提供相应 POSIX 接口的平台才能使用。









**Q13: [learning] C 头文件在 C++ 中有哪些对应写法？**

C++ 为多数 C 标准库头文件提供了去掉 `.h` 并添加 `c` 前缀的对应形式，例如 `<stdio.h>` 对应 `<cstdio>`，`<math.h>` 对应 `<cmath>`。

使用 C++ 形式时，可通过 `std::` 访问对应标准库名称。旧式 `.h` 头文件在不少实现中仍可用，但名称是否同时暴露在全局命名空间没有可移植保证。POSIX 头文件如 `<unistd.h>` 没有标准 C++ 对应形式。









**Q14: [learning] C 程序通常如何生成机器码？**

C 通常由编译器编译为目标平台的机器码，再由操作系统装载执行。生成机器码描述的是编译产物，不意味着程序不依赖运行时支持。









**Q15: [learning] C/C++ 程序运行时通常依赖哪些支持？**

运行时是程序执行所需的支持代码与环境，包括启动代码、语言运行库和操作系统服务。C/C++ 程序可以依赖运行库，但通常不需要托管虚拟机。









**Q16: [learning] C++ 程序的可移植性如何体现，与 Java 有何差异？**

可移植性指程序迁移到不同硬件或操作系统后仍能正确运行的能力。C++ 和 Java 都可编写可移植源代码，但编译产物和运行条件不同。

1. **C++：**通常针对目标平台重新编译为机器码。源代码复用取决于是否使用标准语言特性和可移植库。
2. **Java：**通常编译为字节码，由兼容的 Java 虚拟机（JVM，Java Virtual Machine）执行。
3. **共同限制：**使用平台专属应用程序编程接口（API，Application Programming Interface）、应用二进制接口（ABI，Application Binary Interface）或硬件功能时，两者都需要适配。









**Q17: [learning] int main()、int main(void) 和 void main() 有什么区别？**

在提供托管执行环境的实现（hosted implementation）中，`int main()` 与 `int main(void)` 都表示无参数并返回 `int`。标准规定的程序入口形式返回类型为 `int`。

`void main()` 不符合标准 C++ 对 hosted 程序入口函数的要求。部分编译器可能将其作为扩展接受，不应依赖这种行为。









**Q18: [learning] main() 需要显式写 return 0; 吗？**

不需要。控制流到达 `main()` 函数末尾时，等价于返回 `0`，表示正常终止。

1. 该规则仅适用于 `main()`。
2. 普通非 `void` 函数必须在每条可能正常结束的路径上返回值。









**Q19: [learning] freestanding C++ 程序必须定义 main() 吗？**

桌面和 Android 用户空间程序通常采用 hosted 实现，程序入口由实现规定为 `main()`。freestanding 实现不要求采用 hosted 程序的 `main()` 形式，启动入口由实现定义，因此不能将 `main()` 视为所有嵌入式程序的标准入口。









**Q20: [learning] _tmain() 是什么，能否用于标准 C++ 程序？**

`_tmain` 是 Microsoft TCHAR 兼容层提供的入口名称，不属于 ISO C++ 标准。它依据 `_UNICODE` 等字符集配置映射到 `main` 或 Microsoft 扩展 `wmain`。

跨平台程序应使用标准 `main()`。仅在使用 Microsoft 工具链和 TCHAR 约定时考虑 `_tmain()`。









**Q21: [learning] Linux hosted 程序如何从 ELF 入口执行到 main？**

在以 ELF 和 glibc 为例的 Linux hosted 程序中，执行从 ELF 启动入口开始，经 C 运行时初始化后调用 `main`。因此 `main` 是运行时约定的入口函数，不是内核直接调用的函数。典型顺序如下：

1. **ELF 装载：**ELF 指定了动态装载器时，内核把控制权交给装载器，装载和重定位完成后跳转到主程序入口。未指定时内核直接跳转到主程序入口。入口通常对应启动文件提供的 `_start`。
2. **运行时初始化：**以 glibc 为例，启动代码调用 `__libc_start_main`，完成必要初始化后调用 `main`。全局对象的动态初始化通常在 `main` 前执行，具体顺序受标准和实现规则限制。
3. **返回与终止：**`main` 返回后，运行时按进程终止约定处理返回状态。调用链和符号取决于平台、C 运行时及链接配置。

在 Linux ELF 环境中，可用 `readelf -h` 查看入口地址，用 `nm` 查看符号表中的 `_start` 和 `main`。`build/init-second-stage` 是示例路径，应替换为待检查的 ELF 文件。`grep` 筛选所需字段和符号：

```bash
readelf -h build/init-second-stage | grep 'Entry point'
nm build/init-second-stage | grep -E ' (_start|main)$'
```

ELF 入口地址通常对应 `_start`，而 `main` 是由启动代码调用的符号。具体结果受架构、链接器和 C 运行时影响。









**Q22: [learning] std::cout 是对象吗？**

是。`std::cout` 是标准库提供的 `std::ostream` 对象，关联标准输出流。标准输出可重定向到文件或管道，因此 `std::cout` 不等同于屏幕。









**Q23: [learning] std::cout 输出字符串和整数时有何区别？**

两者调用不同的插入运算符重载：前者输出字符串字面量，后者按流的格式设置将 `int` 转换为文本。无需手写 `printf` 风格的格式占位符。









**Q24: [learning] 流插入运算符为什么可以连续使用？**

流插入运算符返回流引用，因此表达式按左结合连续作用于同一个流：`((std::cout << "A") << "B") << carrots`。









**Q25: [done] std::cerr 与 std::endl 如何刷新输出？**

`std::cerr` 是标准错误流，默认设置 `unitbuf`，输出操作后会刷新关联的流缓冲区。`std::endl` 写入换行符并显式刷新所作用的流。`<<` 负责将内容插入流。









**Q26: [done] std::cout 输出后程序阻塞，如何确保内容已刷新？**

例如：

```cpp
std::cout << "Mini-Android init";
while (true) {
    pause();
}
```

插入操作可能只把字符写入 std::cout 的缓冲区。`pause()` 等待信号，不会刷新该流，因此日志可能尚未送往终端。刷新方式如下：

1. std::endl：写入换行并刷新。
2. std::flush：只刷新，不写入换行。
3. \n：只写入换行符，不会主动刷新流。

例如：

```cpp
std::cout << "Mini-Android init" << std::endl;
```









**Q27: [learning] std::cin.get() 放在程序末尾有什么作用？**

无参数的 `get()` 从输入流读取一个字符并返回，因此可等待输入。但它可能读取此前已缓冲的字符，不是通用的程序暂停机制。

调试时应使用断点。需要交互时，应明确读取并处理输入，而不要依赖控制台窗口行为。







**Q28: [learning] 头文件中的独立副本是什么？**

独立副本指多个翻译单元各自拥有的不同实体，修改其中一个变量不会改变另一个。是否产生独立实体取决于声明及其链接性，不能只因内容来自同一个头文件就认定它们共享。

例如，头文件定义内部链接变量：

```cpp
// counter.h
static int count = 0;
```

`a.cpp` 和 `b.cpp` 分别包含该头文件后，各自拥有一个 `count`。`a.cpp` 中将它加一，不会改变 `b.cpp` 中的 `count`。相反，头文件中的 `extern int count;` 只是声明，可由一个源文件提供外部链接的定义，让多个翻译单元引用同一变量。







**Q29: [learning] 外部链接是什么？**

外部链接（external linkage）允许不同翻译单元中的声明指向同一实体，使多个源文件能够使用同一函数或变量。声明还须满足类型、作用域等匹配条件，并按单一定义规则提供所需定义。

例如，两个源文件共享一个变量：

```cpp
// counter.cpp
int count = 0;  // 定义变量
```

```cpp
// main.cpp
extern int count;  // 声明同一个变量
int main() { return ++count; }
```

分别编译并链接两个源文件后，`main.cpp` 访问的是 `counter.cpp` 定义的 `count`。若该定义改为 `static int count = 0;`，它就具有内部链接，不能满足另一个翻译单元的外部引用。







**Q30: [learning] C++ 的作用域是什么？**

作用域是名称在程序中可以被名称查找使用的范围。例如，块作用域内声明的局部变量在该块内可用，离开块后名称不可用。

```cpp
int main() {
    int value = 1;
    {
        int value = 2;  // 隐藏外层同名变量
    }
    return value;       // 使用外层变量，返回 1
}
```

作用域不等于存储期或链接性：作用域决定名称在哪里可被查找，存储期涉及对象的存储持续时间，链接性决定不同声明能否指向同一实体。例如，`static` 局部变量的名称仍限于所在块，但它具有静态存储期。







**Q31: [learning] 声明与定义有什么区别，extern 一定只是声明吗？**

声明引入名称并说明类型。定义还提供实体的完整内容，例如变量定义创建对象，函数定义提供函数体。一个实体可以有多个一致的声明，定义则受单一定义规则约束。

下面的片段比较变量与函数的声明和定义，省略了调用代码：

```cpp
extern int total;       // 声明，不定义变量
int total = 1;          // 定义变量
extern int limit = 10;  // 带初始化式，也是定义
int add(int, int);      // 函数声明
int add(int a, int b) { return a + b; }  // 函数定义
```

`extern` 表明变量声明可引用别处的实体，但带初始化式时仍是定义。类型、命名空间或参数不匹配时，声明可能指向不同实体或使程序不合法。







**Q32: [learning] C++ 的内部链接、外部链接和无链接分别是什么？**

链接性决定不同声明能否指向同一实体，不决定对象存活多久。以下是普通非模块程序中的常见情况：

1. **内部链接：**命名空间作用域的 `static int a = 0;` 只能在当前翻译单元中通过名称引用。其他翻译单元的同名内部链接变量是不同实体。
2. **外部链接：**命名空间作用域的 `int b = 0;` 通常具有外部链接，其他翻译单元可用匹配的 `extern int b;` 声明引用它。
3. **无链接：**普通局部变量如 `void f() { int c = 0; }` 的名称没有链接性，另一个函数或块里的同名变量是不同实体。

C++20 命名模块还引入模块链接，部分非导出名称可在同一命名模块的多个单元中关联，不能简单归入内部链接或外部链接。







**Q33: [learning] 作用域、链接性、存储期和生命周期如何区分？**

四者分别回答名称查找、实体关联和对象存在时间的问题：

1. **作用域：**名称在哪里可被查找。例如局部变量的名称限于所在块。
2. **链接性：**不同声明能否指向同一实体。例如内部链接名称不能跨翻译单元指向同一实体。
3. **存储期：**对象所用存储空间的最短潜在存在时间，分为自动、静态、线程和动态存储期。
4. **生命周期：**对象从满足创建和初始化条件到析构或存储复用、释放等情形结束的期间。存储仍在不代表原对象仍存活。

例如，函数里的 `static int count = 0;` 名称具有块作用域且无链接，变量具有静态存储期。函数返回后名称不可在函数外查找，但下次调用仍可访问同一个变量。







**Q34: [learning] const、extern 和 inline 如何影响命名空间作用域变量的链接性？**

在普通非模块代码中，命名空间作用域的非模板、非 `volatile` 的 `const` 变量通常具有内部链接。`extern`、`inline` 或之前已有的声明等可能改变结果，因此应结合完整声明判断。

```cpp
const int local_limit = 10;         // 通常为内部链接
extern const int shared_limit;       // 声明，定义放在一个 .cpp 中
inline const int max_size = 100;    // C++17：可放在头文件中
```

`shared_limit` 需要匹配的定义。`inline` 变量在满足单一定义规则时，可在多个翻译单元中定义同一实体，不是每个翻译单元一份独立变量。命名模块有额外规则。







**Q35: [learning] 未命名命名空间与 static 如何限制跨文件名称？**

两者都可让命名空间作用域的函数或变量具有内部链接。未命名命名空间还适合限制类型等名称的链接范围。

```cpp
namespace {
struct State { int value; };
int count = 0;
}
```

这些名称可在当前翻译单元的适当位置使用，其他翻译单元中的同名实体彼此独立。若把未命名命名空间放入头文件，每个包含它的翻译单元也会获得各自的实体，因此不要用它实现跨文件共享状态。







**Q36: [learning] 单一定义规则是什么，头文件保护宏能防止哪些重复定义？**

单一定义规则（ODR，One Definition Rule）约束同一翻译单元和整个程序中实体的定义。一个翻译单元不能出现同一可定义实体的多次定义。程序中被使用且需要定义的非内联函数或变量通常必须有且只有一个定义。

1. **同一翻译单元重复包含：**头文件保护宏或 `#pragma once` 可防止头文件内容在该翻译单元中重复展开。
2. **不同翻译单元分别包含：**保护宏不会合并跨翻译单元的定义。若普通头文件定义非 `inline` 的外部链接变量 `int count = 0;`，被多个 `.cpp` 包含后会违反单一定义规则。
3. **允许多处定义：**类、模板、`inline` 函数和 C++17 起的 `inline` 变量等在满足相应一致性条件时可出现在多个翻译单元中。定义不一致仍违反规则，且不一定得到诊断。

通常把共享变量的 `extern` 声明放在头文件，在一个 `.cpp` 中提供定义。需要在头文件中定义共享变量时，可按 C++17 的 `inline` 变量规则处理。







**Q37: [learning] 头文件中的 inline 函数和 inline 变量为什么可以被多个源文件包含？**

对于具有外部链接的实体，`inline` 允许符合规则的定义出现在多个翻译单元中，仍按一个实体使用。它不保证编译器实际把函数调用展开。

下面的头文件片段使用 C++17 的 `inline` 变量：

```cpp
// counter.h，C++17
inline int count = 0;
inline int next() { return ++count; }
```

多个源文件包含该头文件时，符合单一定义规则的各处定义指向同一个外部链接 `count`，调用 `next()` 修改同一状态。不同翻译单元中的定义必须满足标准要求，例如相同的记号序列及相应名称查找一致。此处的 `inline` 变量需要 C++17，`inline` 函数在更早版本已支持。







**Q38: [learning] 名称隐藏是什么，如何访问被隐藏的外层名称？**

内层作用域声明同名实体后，非限定名称查找通常先找到内层名称，外层同名名称被隐藏。限定名可在适用时明确指定外层作用域。

```cpp
int value = 1;
int read_value() {
    int value = 2;
    return value + ::value;  // 局部变量 2 + 全局变量 1
}
```

名称隐藏不改变外层对象的值或生命周期。`::value` 从全局作用域查找，不能用来访问任意函数外层块的局部变量。函数重载、类继承等场景的查找还有各自规则。







**Q39: [learning] 自动、静态、线程和动态存储期各表示什么？**

存储期描述对象所用存储空间的持续方式，不保证对象在整段存储期内始终存活：

1. **自动存储期：**普通局部变量的存储通常随所在块执行开始和结束，例如 `int n = 0;`。
2. **静态存储期：**普通命名空间作用域变量和 `static` 局部变量的存储持续整个程序，例如 `static int n = 0;`。
3. **线程存储期：**`thread_local int n = 0;` 为每个线程提供各自对象，其存储持续相应线程的整个执行期。
4. **动态存储期：**由 `new` 创建的对象使用动态存储，释放时间由匹配的 `delete` 或资源管理对象控制，不随创建它的函数返回自动释放。

对象的构造、析构与存储复用还影响其实际生命周期。局部变量的地址在对应对象生命周期结束后不能继续用来访问该对象。







**Q40: [learning] 跨文件编译时，未声明、未定义和重复定义分别会发生什么？**

错误出现的阶段取决于缺失或冲突的信息：

1. **调用处没有声明：**编译器无法进行名称查找或检查调用，通常在编译该翻译单元时报错。
2. **有声明但缺少所需定义：**调用处可以编译，链接时通常报告未解析的引用。例如只写 `extern int count;` 并实际使用它，却没有提供定义。
3. **普通外部实体重复定义：**多个 `.cpp` 各定义同一个非 `inline` 全局变量，通常在链接时报重复符号。不同翻译单元中的同名 `static` 变量是独立实体，不属于这个情况。
4. **多处定义不一致：**某些单一定义规则违反不要求实现诊断，链接成功也不能证明程序符合规则。

排查时先确认声明与定义的名称、类型、命名空间和链接性，再检查对应源文件或库是否参与链接。







**Q41: [learning] extern "C" 与变量声明中的 extern 有什么区别？**

`extern "C"` 是语言链接说明，用于声明具有 C 语言链接的函数或名称。普通 `extern` 是存储类说明符，常用于声明在别处定义的变量。两者解决的问题不同。

```cpp
extern "C" int read_sensor();  // 按 C 语言链接约定声明函数
extern int count;              // 声明变量，不提供定义
```

C++ 调用由 C 编译的库时，接口声明与实际定义须使用兼容的语言链接和平台调用约定，否则可能无法链接。`extern "C"` 不会把 C++ 代码改成 C，也不自动保证结构体布局或跨编译器的应用二进制接口（ABI，Application Binary Interface）兼容。







**Q42: [learning] C++20 模块链接与内部链接、外部链接有什么关系？**

模块链接是 C++20 命名模块中的一种链接性：适用名称可以在同一命名模块的不同模块单元中关联，同时不作为其他模块可直接使用的外部接口。

1. **内部链接：**实体的相关声明限于同一翻译单元。
2. **模块链接：**符合条件的非导出名称可在同一命名模块的不同单元关联。
3. **外部链接：**适用声明可跨翻译单元关联，模块接口可通过 `export` 暴露声明供导入方使用。

模块归属、`export` 和声明上下文共同决定可见性与链接性。模块链接不等同于 `static`，也不意味着导入模块后其所有内部名称都可见。

依据：C++ 标准草案 `[basic.link]`、`[basic.def.odr]` 和 `[basic.stc]`。
