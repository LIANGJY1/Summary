# C++ 编译与链接

> 本文说明 C++ 从源代码到可执行文件的构建阶段——包括头文件与保护宏在其中承担的职责——以及工具链选项和产物检查。

**Q1: [done] 多文件的 C++ 工程为什么需要头文件？声明在编译和链接阶段各起什么作用？**

C++ 按翻译单元独立编译：编译器编译某个 .cpp 时看不到其他 .cpp，各自生成目标文件，最后由链接器把跨文件的符号引用与定义拼成可执行文件。头文件就是为这个模型补上"跨文件可见的声明"——调用方和实现方都 include 同一份声明，编译器据此做类型检查，函数体在链接阶段才由链接器接上。

1. **独立编译要求声明在场**：编译 first_stage_main.cpp 遇到 FirstStageMain(argc, argv) 调用时，编译器不会去翻 first_stage_init.cpp，它需要一份"承诺书"——名字存在、参数是 (int, char*[])、返回 int——才能生成调用代码并做类型检查。这份承诺书就是函数声明：返回类型、名字、参数列表加一个分号，没有函数体；带函数体的叫定义，放 .cpp 里。
2. **头文件的价值是单一事实来源**：不用头文件也可以在每个调用方手写等价声明——把 `#include "first_stage_init.h"` 换成手写 `namespace mini { int FirstStageMain(int, char*[]); }` 照样能编译，因为预处理器本来就是把头文件内容粘贴进来，等价声明自然等价。但声明只写一份、大家 include，签名变化时只改一处；各自手抄的写法抄错任何一处，各文件编译时都查不出来。
3. **编译期与链接期报错的分界**：声明缺失或调用写法与声明不符，编译当下就报错；声明了但没有对应定义，各文件编译都通过，到链接阶段才报 undefined reference。例如把声明改成 `int FirstStageMain(int)` 而实现保持原签名，两个文件都能编译，链接时报 undefined reference——亲手看一次这两种报错，编译与链接的分界就清楚了。







**Q2: [done] 头文件开头的 #ifndef/#define/#endif 是做什么的？#pragma once 能替代它吗？**

这三行是头文件保护宏（include guard）：用预处理条件编译保证同一翻译单元内头文件内容只被粘贴一次，防止重复包含引发重定义编译错误。#pragma once 是主流编译器普遍支持的替代写法，但它是编译器扩展，不在 C++ 标准内。

1. **以 # 开头的是预处理指令，不是 C++ 语句**：预处理在真正编译前运行，做最原始的文本工作——#include 把目标文件内容原样粘贴进当前翻译单元，#define 定义文本替换宏，#ifndef 表示"如果没定义过"。
2. **保护宏的机制**：头文件第一次被包含时，形如 MINI_ANDROID_FIRST_STAGE_INIT_H 的宏还没人定义过 → #ifndef 条件成立 → 处理中间内容，#define 顺手把这个宏定义了；同一翻译单元第二次包含它时宏已存在 → #ifndef 不成立 → 预处理器直接跳到 #endif，中间内容全部忽略。
3. **为什么是工程必需而非语法要求**：a.h 和 b.h 都包含 x.h，某个 .cpp 又同时包含两者时，x.h 的内容在同一个文件里出现两遍。头文件只有函数声明时，重复声明侥幸无害；有类定义或内联定义时，第二遍就是重定义编译错误。
4. **宏名必须全局唯一**：习惯用"项目路径+文件名"全大写（如 MINI_ANDROID_FIRST_STAGE_INIT_H）。两个头文件用了同一个宏名，后包含的会被前一个"吞掉"，报错极其隐晦。#endif 后面的注释 `// MINI_ANDROID_FIRST_STAGE_INIT_H` 不是语法，是给人看的配对标记。
5. **#pragma once 的边界**：写在文件首行，由编译器保证该文件只被包含一次；GCC、Clang、MSVC 等主流编译器都支持。因为不是标准，极端可移植场景仍以传统保护宏为准，AAOS/Google 风格也沿用保护宏。



**Q3: [done] 用 `g++` 静态链接 `init.cpp` 时，各选项做什么，为什么产物通常比动态链接的大？**

静态链接会把所需静态库代码并入输出的可执行文件；两种构建都启用 `-g` 时，静态链接产物通常更大。下面的命令示范主机工具链，不保证产物可直接作为目标设备的 `/init`。

```bash
g++ -std=c++17 -Wall -Wextra -g -static src/init.cpp -o build/init-static
```

1. `g++`：编译器驱动，调用编译和链接步骤；省略它就没有执行构建的命令。
2. `-std=c++17`：选择 C++17；省略时使用该编译器版本的默认标准。
3. `-Wall -Wextra`：启用两组常见警告；省略后仍可构建，但不会报告这些警告。
4. `-g`：请求生成调试信息；省略后通常不生成，除非其他选项另行启用。
5. `-static`：要求静态链接。省略时通常动态链接。静态链接把所需静态库代码并入 `-o` 指定的可执行文件。动态链接的可执行文件记录共享库依赖，由运行时动态链接器加载共享库。所需静态库不可用时，链接会失败。
6. `src/init.cpp`：指定输入源文件；省略后没有本命令指定的编译输入。
7. `-o build/init-static`：指定输出路径和文件名；这里的可执行文件是 `build/init-static`，不是 `init.cpp` 或库文件。省略 `-o` 时使用驱动的默认输出名；`build` 目录必须预先存在。

链接器通常只纳入需要的静态库成员，不会复制整套库。`-g` 也会增大文件。两种方式都使用 `-g` 时，大小差异通常主要来自链接进产物的代码和数据。

命令结束后检查退出码，`0` 表示成功。仅看到命令提示符返回不能说明构建成功。











**Q4: [done] 如何用 g++ 编译 C++ 程序，并运行生成的可执行文件？**

先用 `g++` 编译源文件，并通过 `-o` 指定生成文件的位置。编译成功后，执行该文件的路径即可运行程序：

```bash
g++ -std=c++17 -Wall -Wextra -g -static src/init.cpp -o build/init-static
./build/init-static
```

1. **编译：**`g++` 是 C++ 编译器命令。它读取 `src/init.cpp`，并将编译结果写到 `-o` 指定的 `build/init-static`。
2. **运行：**在路径 `./build/init-static` 中，`.` 表示当前工作目录，`/` 是目录分隔符，因此整条路径表示从当前目录进入 `build/`，再运行 `init-static`。这一步运行已生成的程序，不会再次调用 `g++`。







**Q5: [done] `#include "util.h"` 与 `#include <util.h>` 的搜索范围有何不同，项目头文件应该用哪种？**

两种写法的唯一区别是搜索范围：`<...>` 只在实现定义的位置（编译器内置的系统目录与构建选项加入的路径）中查找；`"..."` 通常先在发起包含的源文件所在目录查找，未命中再退回到 `<...>` 的路径。约定是标准库和系统头用 `<>`，本项目头用 `""`。

1. **尖括号形式的搜索范围：**标准只规定它搜索一串实现定义的位置。具体位置由编译器和构建选项决定，包括编译器自带的系统头目录和 `-I` 加入的路径；它不搜索源文件所在目录。
2. **引号形式的搜索范围：**搜索方式同样由实现定义，GCC、Clang、MSVC 的做法都是先找发起包含的源文件所在目录，未命中再按尖括号的路径继续。标准还规定：若该搜索不被支持或失败，指令按尖括号形式重新处理，序列不变。
3. **写反了会怎样：**用引号包含系统头通常仍能编译，因为第一步没找到后会退回尖括号路径，但这依赖实现定义的第一步，不应作为可移植依赖。用尖括号包含项目头则直接找不到，除非把项目目录加进包含路径；GCC 的 `-iquote` 只加入引号形式的搜索路径，`-I` 对两种写法都生效。
4. **选择依据：**按头文件归属而非找法决定。随编译器或平台提供的（如 `<unistd.h>`）、随第三方库安装的用 `<>`；本仓库源码树内的用 `""`，这类头不会因更换构建目录或构建配置而丢失。

例如，自建头与源文件同目录时：

```
src/main.cpp
src/util.h
```

```bash
g++ -std=c++17 -Wall src/main.cpp -o build/init
```

main.cpp 写 `#include "util.h"` 时该命令通过：引号形式先在 main.cpp 所在目录找到 util.h。同一文件改用 `#include <util.h>` 后，同一命令报 `fatal error: util.h: No such file or directory`；尖括号形式不搜索源文件所在目录，补上 `-I src` 后才重新找到。



**Q6: [learning] C++ 源代码如何经过构建阶段变成可执行文件？**

常见构建流程由预处理、编译、汇编和链接组成。`g++` 是驱动程序，会按配置协调这些工具。

1. **预处理：**展开宏、处理 `#include` 等指令，形成翻译单元。
2. **编译：**分析翻译单元并生成汇编或目标代码。
3. **汇编：**将汇编指令转换为目标文件，例如 `.o`。
4. **链接：**解析跨目标文件的符号引用，并组合启动代码和所需库，生成可执行文件或共享库。

目标文件通常还不能独立运行。具体中间步骤可能被编译器驱动隐藏或合并。











**Q7: [learning] C++ 预处理器由谁运行，`#include <iostream>` 会做什么？**

预处理器是构建工具链的一部分。执行 `g++ main.cpp` 时，`g++` 驱动通常会自动调用预处理阶段，无需手动运行预处理器。

`#include` 会按搜索路径找到头文件，并将其内容纳入当前翻译单元的处理过程。相关影响有三点：

1. 头文件可能继续包含其他头文件，增大翻译单元并延长编译时间。
2. 最终可执行文件不会简单地按包含行数成比例增大，优化和链接会影响实际产物。
3. C++20 模块提供另一种组织接口与编译依赖的机制，但没有让传统头文件立即消失。




**Q8: [learning] C++ 的 `#include` 与 Java 的 `import` 有什么区别？**

`#include` 是 C++ 预处理指令，会把头文件内容纳入当前翻译单元。Java 的 `import` 用于简化类型名称的引用，不会把被导入类的源码文本复制进当前源文件。











**Q9: [learning] C++ 源文件扩展名有什么约定，“编译清单”是什么？**

C++ 标准不规定源码文件必须使用哪种扩展名。扩展名主要帮助构建工具判断如何处理文件。

1. **实现文件：**常见 `.cpp`、`.cc`、`.cxx`。具体识别规则由编译器和构建系统决定。
2. **头文件：**常见 `.h`、`.hpp`、`.hxx`，扩展名本身不改变语言规则。
3. **编译清单：**若此处指 compiler listing，它是工具生成的源码、汇编或诊断信息报告，不是源文件扩展名，也不是 C++ 标准规定的必需产物。构建项目中的源文件清单则是构建配置显式列出的输入文件，两者不要混为一谈。











**Q10: [learning] `file` 和 `ldd` 能否证明程序可作为 initramfs 的 `/init` 启动？**

不能。它们能帮助检查文件格式、架构和动态依赖，不能验证内核、initramfs 布局及 PID 1 行为。

1. `file`：可报告可执行与可链接格式（ELF，Executable and Linkable Format）、目标架构以及识别到的静态或动态链接信息。显示 `x86-64` 只说明目标架构，仍需与内核架构匹配。
2. `ldd`：用于查看动态依赖。对静态 ELF 显示 `not a dynamic executable` 与其没有常规动态库依赖相符，不是错误。
3. **启动条件：**还要确认文件位于初始 RAM 文件系统（initramfs）根目录并命名为 `/init`，应用二进制接口（ABI，Application Binary Interface）和运行库适配目标环境，而且程序能持续履行进程标识符 1（PID 1，Process ID 1）的职责。打印后退出的示例程序不是可用的系统 init。
