# C++ 编译与链接

> 本文说明 C++ 从源代码到可执行文件的构建阶段——包括头文件与保护宏在其中承担的职责——以及工具链选项和产物检查。

**Q1: [learning] C++ 源代码如何经过构建阶段变成可执行文件？**

常见构建流程包含预处理、编译、汇编和链接。`g++` 是协调这些步骤的驱动程序。

1. **预处理：**处理宏和 `#include` 等指令，形成翻译单元。
2. **编译：**分析翻译单元并生成汇编或目标代码。
3. **汇编：**将汇编指令转换为目标文件，例如 `.o`。
4. **链接：**解析跨目标文件的符号引用，并组合启动代码和所需库，生成可执行文件或共享库。

目标文件通常还不能独立运行。具体中间步骤可能被编译器驱动隐藏或合并。

**Q2: [done] 多文件的 C++ 工程为什么需要头文件？声明在编译和链接阶段各起什么作用？**

C++ 通常按翻译单元独立编译。编译器处理一个 `.cpp` 时不会读取其他 `.cpp`，而是分别生成目标文件，再由链接器解析跨文件的符号引用。头文件提供可共享的声明，使调用方能在编译期检查调用，链接器随后将引用与定义关联。

1. **编译期检查：**调用方必须先看到函数声明，编译器才能检查函数名、参数和返回类型。例如声明 `int FirstStageMain(int, char*[])` 后，调用方可以独立编译，不需要读取实现文件。
2. **共享声明：**将声明放入头文件可提供单一事实来源。手写重复声明虽可编译，但签名变化时容易不同步；通过 `#include` 共享声明可避免这种偏差。
3. **错误阶段：**声明缺失或调用不匹配会在编译期报错；声明存在但没有对应定义时，相关翻译单元仍可编译，链接阶段才会报告未解析符号。

**Q3: [learning] C++ 预处理器由谁运行，#include <iostream> 会做什么？**

预处理器是构建工具链的一部分。执行 `g++ main.cpp` 时，驱动通常会自动执行预处理，无需单独调用预处理器。

`#include` 按搜索规则找到头文件，并将其内容纳入当前翻译单元。其影响包括：

1. 头文件可能继续包含其他头文件，增大翻译单元并延长编译时间。
2. 最终可执行文件不会简单地按包含行数成比例增大，优化和链接会影响实际产物。
3. C++20 模块提供另一种组织接口和编译依赖的机制，但不意味着传统头文件已被取代。

**Q4: [done] #include "util.h" 与 #include <util.h> 的搜索范围有何不同，项目头文件应该用哪种？**

两种写法的主要区别是搜索规则：具体搜索位置由实现和构建选项决定。常见编译器会让 `"..."` 先搜索发起包含的文件所在目录，再搜索常规头文件路径；`<...>` 使用常规头文件搜索路径。通常用尖括号包含标准库或外部依赖头文件，用引号包含项目头文件。

1. **尖括号形式的搜索范围：**标准只规定它搜索一串实现定义的位置。具体位置由编译器和构建选项决定，通常包括编译器自带的系统头目录和 `-I` 加入的路径；标准不保证搜索发起包含的源文件所在目录。
2. **引号形式的搜索范围：**搜索方式同样由实现定义，GCC、Clang、MSVC 的做法都是先找发起包含的源文件所在目录，未命中再按尖括号的路径继续。标准还规定：若该搜索不被支持或失败，指令按尖括号形式重新处理，序列不变。
3. **写反了会怎样：**用引号包含系统头通常仍能编译，因为第一步没找到后会退回尖括号路径，但这依赖实现定义的第一步，不应作为可移植依赖。用尖括号包含项目头则直接找不到，除非把项目目录加进包含路径；GCC 的 `-iquote` 只加入引号形式的搜索路径，`-I` 对两种写法都生效。
4. **选择依据：**按头文件归属选择写法。编译器、平台或第三方库提供的头文件通常用 `<>`；项目源码中的头文件通常用 `""`。

例如，头文件与源文件位于同一目录时：

```
src/main.cpp
src/util.h
```

```bash
g++ -std=c++17 -Wall src/main.cpp -o build/init
```

`main.cpp` 使用 `#include "util.h"` 时，常见编译器会先在源文件所在目录找到该头文件。改为 `#include <util.h>` 后，命令通常会因搜索路径未包含 `src` 而失败；添加 `-I src` 可将该目录加入常规搜索路径。

**Q5: [done] 头文件中的 #ifndef、#define、#endif 有何作用？#pragma once 能否替代？**

这三行构成头文件保护宏（include guard），用于避免同一翻译单元重复处理头文件内容。`#pragma once` 是常见替代写法，但不属于 ISO C++ 标准。

1. **预处理指令：**以 `#` 开头的指令在编译前处理。`#include` 纳入头文件内容，`#define` 定义宏，`#ifndef` 检查宏是否尚未定义。
2. **保护宏机制：**首次包含时，保护宏未定义，预处理器处理文件内容并执行 `#define`；同一翻译单元再次包含时，条件不成立，文件主体被跳过。
3. **防止重复定义：**多个头文件可能间接包含同一头文件。保护宏可避免其内容在一个翻译单元中重复出现，防止类定义等造成重定义错误。
4. **宏名：**应使用由项目路径和文件名组成的唯一名称。不同头文件若误用同一保护宏，后续文件主体会被跳过。`#endif` 后的注释只是配对提示。
5. **`#pragma once`：**GCC、Clang 和 MSVC 等常见编译器支持该指令，但它不是标准 C++ 语法。需要严格遵守标准可移植性时使用保护宏。

**Q6: [learning] C++ 的 #include 与 Java 的 import 有什么区别？**

`#include` 是 C++ 预处理指令，会将头文件内容纳入当前翻译单元。Java 的 `import` 使类型可通过简名引用，不会把被导入类型的源码复制到当前文件。

**Q7: [done] 如何用 g++ 编译 C++ 程序并运行生成的可执行文件？**

先用 `g++` 编译源文件，并通过 `-o` 指定输出路径。编译成功后，执行生成文件即可运行程序：

```bash
g++ src/init.cpp -o build/init
./build/init
```

1. **编译：**`g++` 读取 `src/init.cpp`，并将结果写入 `-o` 指定的 `build/init`。输出目录必须已存在。
2. **运行：**`./build/init` 表示从当前工作目录进入 `build/` 并执行该文件；此步骤不会再次调用编译器。

**Q8: [done] 用 g++ 静态链接 init.cpp 时，各选项做什么，为什么产物通常比动态链接的大？**

静态链接会把所需静态库代码并入输出的可执行文件；两种构建都启用 `-g` 时，静态链接产物通常更大。下面的命令示范主机工具链，不保证产物可直接作为目标设备的 `/init`。

```bash
g++ -std=c++17 -Wall -Wextra -g -static src/init.cpp -o build/init-static
```

1. `g++`：编译器驱动，协调编译与链接步骤。
2. `-std=c++17`：选择 C++17；省略时采用该编译器版本的默认标准。
3. `-Wall -Wextra`：启用常见警告；省略后仍可构建，但不会启用这两组警告。
4. `-g`：请求生成调试信息；省略时通常不生成，除非其他选项另行启用。
5. `-static`：要求静态链接；省略时通常采用动态链接。静态链接将所需库代码纳入可执行文件，动态链接则记录共享库依赖，由运行时装载器加载。缺少所需静态库时链接失败。
6. `src/init.cpp`：指定输入源文件。
7. `-o build/init-static`：指定输出文件路径。省略时使用驱动的默认文件名；`build` 目录必须预先存在。

链接器通常只纳入需要的静态库成员，不会复制整套库。`-g` 也会增大文件。两种方式都使用 `-g` 时，大小差异通常主要来自链接进产物的代码和数据。

命令结束后检查退出码，`0` 表示成功。仅看到命令提示符返回不能说明构建成功。

**Q9: [learning] C++ 源文件扩展名由谁决定？**

C++ 标准不规定源码文件必须使用哪种扩展名。扩展名主要帮助构建工具判断如何处理文件。

1. **实现文件：**常见 `.cpp`、`.cc`、`.cxx`。具体识别规则由编译器和构建系统决定。
2. **头文件：**常见 `.h`、`.hpp`、`.hxx`，扩展名本身不改变语言规则。

**Q10: [learning] 编译器 listing 与构建源文件清单有何区别？**

编译器 listing 是工具生成的源码、汇编或诊断报告，不是 C++ 标准规定的必需产物。构建配置中的源文件清单则是构建输入；两者用途不同，需结合具体工具语境判断。

**Q11: [learning] file 和 ldd 能否证明程序可作为 initramfs 的 /init 启动？**

不能。它们可检查文件格式、架构或动态依赖，但不能验证目标内核、initramfs 布局或 PID 1 的运行行为。

1. `file`：可报告可执行与可链接格式（ELF，Executable and Linkable Format）、目标架构及部分链接信息。显示 `x86-64` 不代表它与目标内核架构匹配。
2. `ldd`：查看动态依赖。静态 ELF 显示 `not a dynamic executable` 通常表示没有常规动态库依赖，并非错误。不要对不可信可执行文件运行 `ldd`；可用 `readelf -d` 检查动态段。
3. **启动条件：**还要确认文件位于初始 RAM 文件系统（initramfs）根目录并命名为 `/init`，应用二进制接口（ABI，Application Binary Interface）和运行库适配目标环境，而且程序能持续履行进程标识符 1（PID 1，Process ID 1）的职责。打印后退出的示例程序不是可用的系统 init。
