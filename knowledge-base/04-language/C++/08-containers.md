# C++ 标准库容器

> 本文说明标准库序列容器 `std::vector` 与数组的关系、存储模型、容量管理、迭代器失效规则和常用操作惯用法。标注“实测”的行为在本机 g++ 11.4.0（libstdc++，x86-64）验证，实现相关的数值不可移植。

**Q1: [learning] C++ vector 解析：vector 是数组吗？**

vector 是标准库的序列容器：按插入顺序保存元素，支持按下标随机访问。它不是数组，但元素确实存放在一块数组式的连续存储中。判断“是不是数组”要分两层：内存布局层面与数组一致，类型本质层面是独立的容器对象，那块连续存储只是它管理的资源。

1. **布局层面像数组：**C++ 标准要求，对除 `vector<bool>` 之外的 vector，`&v[n] == &v[0] + n` 对所有合法下标成立。因此 `v.data()` 返回的首元素指针可以按偏移访问任意元素，也能直接传给要求元素指针的 C 接口。
2. **类型层面不是数组：**数组的存储是对象本体的一部分，vector 对象本身只保存三个指针——元素序列的起始位置、已存元素的尾后位置和已分配存储的尾后位置。全部元素放在堆上的连续存储里，与 vector 对象自身位于栈上还是堆上无关，元素增多时变的只是那块堆存储，不是对象本身。默认构造的空 vector 三个指针全为空、容量为 0，实测未发生堆分配。

sizeof 的对比可以直接观察到这种分离：

```cpp
int arr[5];               // 实测 sizeof 为 20：这 20 字节就是数组本体
std::vector<int> v(5);    // 实测 sizeof 为 24：本体只有三个指针，5 个元素在堆上
```

由对象与存储分离出发，vector 有四种数组没有的行为：

1. **长度运行期可变：**数组长度是类型的一部分（int[5] 与 int[3] 是不同类型），声明后不能改变。vector 的长度和容量在运行期伸缩。
2. **自管理生命周期：**vector 析构时销毁全部元素并释放堆上存储。动态数组 new[] 必须与 delete[] 手动配对。
3. **随身携带元数据：**vector 随时知道自己的 size 和 capacity。数组退化为指针后长度信息即丢失。
4. **地址会搬家：**扩容时堆上存储被整体替换成新块，原有指针、引用和迭代器全部失效。真正的数组没有搬家概念，地址永不移动。

两条补充边界：

1. **“动态数组”叫法：**描述的是布局与用法（连续、可下标、长度可变），容易让人误以为 vector 就是数组本身。严格说 vector 是容器对象，那块数组只是它管理的、可整块换掉的资源。
2. **真正数组式的容器：**需要元素存储内嵌在对象本身、长度编译期固定时，应使用 `std::array<T, N>`。

**Q2: [learning] size 和 capacity 分别表示什么？**

`size()` 是容器当前持有的元素个数，`capacity()` 是当前存储在不重新分配的前提下最多能容纳的元素总数，恒有 size() 不超过 capacity()。两者分开保存，使逻辑长度与物理容量独立变化：追加元素只改 size，直到 size 达到 capacity 才触发重新分配。

1. **capacity 的承诺：**只要插入后 size 不超过 capacity，插入就发生在已有存储内，全部元素地址保持不变。实测向容量充足的 vector 连续 push_back，`data()` 指针不变。
2. **capacity 只增不减：**push_back、insert、resize 都可能提升容量。元素被删除时 capacity 不自动缩小。
3. **均摊分配的基础：**正因为容量按块预留，绝大多数追加操作完全不做内存分配，偶发的重新分配被摊到多次插入上，单次成本仍近似常数。

**Q3: [learning] vector 扩容时会发生什么？为什么容量按倍数增长？**

当插入使 size 超过 capacity 时，vector 执行重新分配：分配一块更大的存储，把现有元素搬移过去，析构旧元素并释放旧存储。原有迭代器、指针和引用随之全部失效。容量按倍数增长，是为了把 n 次尾部插入的总搬移量控制在 O(n)，使单次 push_back 均摊为常数时间。

1. **增长因子由实现决定：**标准不规定倍数。实测 libstdc++ 按 2 倍增长，容量依次为 1、2、4、8、16。MSVC 标准库约按 1.5 倍增长。依赖具体倍数或容量精确值的代码不可移植。
2. **倍增摊薄搬移成本：**从容量 1 倍增到容纳 n 个元素，历次重新分配搬移的元素总数约为 1 + 2 + 4 + … + n/2 ≈ n，摊到 n 次插入上每次近似常数。若每次只增加固定槽位（比如每次多分配 10 个），插入 n 个元素的总搬移量为 O(n²)，尾部插入就不再均摊常数。
3. **失效是全量失效：**重新分配后旧存储已释放，指向旧元素的迭代器、指针和引用全部失效，包括 `end()`。实测保存 `v[0]` 的引用再连续扩容，读取该引用得到的是无意义垃圾值——这是未定义行为，任何输出都不代表真实数据。

**Q4: [learning] reserve 和 resize 分别改变什么？**

reserve 只提高 capacity，不创建元素、不改变 size。resize 直接把 size 改为目标值，需要时创建或销毁元素。两者都只增不减：reserve 不缩小容量，resize 截断元素也不归还内存。

1. **reserve(n)：**n 超过当前 capacity 时重新分配，保证容量至少为 n，实现可能分配更多。n 不超过 capacity 时调用无事发生。适合已知元素规模时一次性备好存储。
2. **resize(n)：**n 大于当前 size 时在尾部追加 n − size 个新元素，数值类型值初始化为 0，类类型调用默认构造，也可用 `resize(n, value)` 指定填充值。n 小于当前 size 时从尾部截断并销毁多余元素，容量保持不变。
3. **选用规则：**提前知道最终规模就先 reserve 再 push_back，避免多次重新分配。需要容器立刻拥有 n 个可用元素（例如随后按下标赋值）才用 resize。

```cpp
std::vector<int> a;
a.reserve(100);   // size=0，capacity 至少 100，还没有任何元素
a.push_back(1);   // size=1，实测未发生重新分配

std::vector<int> b;
b.resize(3);      // size=3，实测元素为 0 0 0
b.resize(5, 9);   // size=5，实测元素为 0 0 0 9 9
```

reserve 之后容器里没有任何元素，push_back 直接写进预留的存储。resize 生成的元素立即可按下标访问。

**Q5: [learning] 为什么放进 vector 的类应把移动构造函数声明为 noexcept？**

扩容搬移元素时，vector 按 `std::move_if_noexcept` 的逻辑选择搬移方式：移动构造是 noexcept 的类型被移动，否则只要类型可拷贝就退化为逐元素拷贝。原因是强异常安全——若在搬移中途抛出异常，被搬移的源对象可能已经破坏，只有拷贝能保证扩容失败时原 vector 原样保留。

1. **选择逻辑：**`std::move_if_noexcept` 对 noexcept 移动构造返回右值引用，容器搬移时执行移动。否则对可拷贝类型返回 const 左值引用，退化为拷贝。类型既不可拷贝、移动又可能抛出时才被迫移动，此时扩容只保留基本异常安全。
2. **实测对比：**可拷贝、移动构造未标 noexcept 的类插入 3 个元素触发两次扩容，实际发生 3 次拷贝、0 次移动。把移动构造加上 noexcept 后，同样的代码 0 次拷贝。
3. **忘标的典型场景：**类管理堆资源、手写了移动构造却漏写 noexcept，扩容就退化为深拷贝，规模大时代价隐蔽。实测 `std::string` 的移动构造是 noexcept 的（C++17 起标准保证），成员只有它的类经编译器生成的移动构造同样是 noexcept。

```cpp
struct S {
    S() = default;
    S(S&&) {}                        // 未标 noexcept
    S(const S&) { ++copies; }
    static inline int copies = 0;    // C++17 起
};

int main() {
    std::vector<S> v;
    v.emplace_back(); v.emplace_back(); v.emplace_back();
    // 实测 S::copies 为 3：两次扩容都走了拷贝
}
```

**Q6: [learning] 哪些操作会使 vector 的迭代器、指针和引用失效？**

扩容类操作使全部迭代器、指针和引用失效，其余操作只影响操作点及其后的部分。具体规则如下：

1. **扩容的插入：**push_back、emplace_back、insert、resize 触发重新分配时，全部迭代器（含 `end()`）、指针和引用失效。
2. **未扩容的 push_back 和 emplace_back：**只有 `end()` 迭代器失效，已有元素的地址不变。
3. **insert：**重新分配时全部失效。否则插入点之前的保持有效，插入点及其后失效。
4. **erase：**擦除点及其后失效，之前的保持有效。
5. **clear 与 reserve：**clear 使全部失效。reserve 只在真正重新分配时失效，容量足够时不改变任何东西。

**Q7: [learning] push_back 和 emplace_back 有何区别？**

push_back 接收一个现成对象，把它拷贝或移动进容器。emplace_back 把构造参数原样转发到容器存储内直接构造元素，省掉“构造临时对象再移动”的中间步骤。两者按同一套规则触发扩容和失效，区别只在元素的构造方式。

1. **典型差异：**`v.push_back("abc")` 先用字面量构造临时 string，再把临时对象移动进容器。`v.emplace_back("abc")` 直接在容器存储内用字面量构造，少一次移动。
2. **explicit 边界：**emplace_back 按直接初始化调用构造函数，explicit 构造函数可用。push_back 按拷贝初始化，explicit 构造函数被排除，emplace_back 因此可能构造出 push_back 写法不接受的类型。
3. **返回值版本差异：**emplace_back 自 C++17 起返回新元素的引用，此前返回 void。push_back 的两个重载一直返回 void。实测 g++ 11.4.0 在 `-std=c++14` 下取 emplace_back 返回值编译报错，`-std=c++17` 下通过。

```cpp
std::vector<std::string> v;
v.push_back("abc");       // 构造临时 string，再移动入容器
v.emplace_back("abc");    // 在容器存储内直接构造
```

**Q8: [learning] clear 之后 capacity 为什么不缩小，怎样才能真正释放内存？**

clear() 析构全部元素并把 size 归零，capacity 和堆上存储原样保留，这是为“清空后继续装填”的复用场景避免再次分配。真正缩小占用需要显式请求：`shrink_to_fit()` 或与空 vector 交换。

1. **实测行为：**容量增到 16 后调用 clear()，size 为 0 而 capacity 仍为 16。再调用 `shrink_to_fit()`，容量归 0。
2. **shrink_to_fit 是请求不是命令：**标准称之为非绑定请求，实现可以拒绝。一旦执行就是一次重新分配，全部迭代器、指针和引用失效。
3. **交换惯用法：**`std::vector<T>().swap(v)` 让 v 与一个空的临时 vector 交换，v 立刻得到空存储，旧存储随临时对象析构释放。这是 shrink_to_fit 出现之前的经典写法。

**Q9: [learning] 删除 vector 中所有满足条件的元素，为什么常用 erase-remove 惯用法？**

因为 `std::remove` 和 `std::remove_if` 是算法，手里只有迭代器，无法改变容器长度：它们把不删除的元素依次前移，返回新序列的逻辑尾，size 和尾部遗留值都不动。必须再由容器调用 erase，把逻辑尾之后的区间真正删掉。

1. **单用 remove 的效果：**实测对 {1, 5, 2, 5, 3} 执行 remove 后，size 仍为 5，新逻辑长度为 3，尾部遗留旧值 5 和 3。遗留值可以读，但不属于有效序列。
2. **惯用法与复杂度：**`v.erase(std::remove(v.begin(), v.end(), 5), v.end())` 一次前移加一次截断，整体 O(n)。写成循环内逐个 erase 是 O(n²)，还要处理迭代器失效。
3. **C++20 起一步完成：**非成员函数 `std::erase_if(v, pred)` 合并两步，实测删除偶数后得到 {1, 3, 5}。
4. **遍历中删除单个元素：**erase 返回指向被删元素之后第一个有效位置的迭代器，应写成 `it = v.erase(it)` 接续遍历，而不是 ++it。

```cpp
std::vector<int> v{1, 5, 2, 5, 3};
auto new_end = std::remove(v.begin(), v.end(), 5);
// 实测：new_end - v.begin() 为 3，v 仍为 {1, 2, 3, 5, 3}，size 仍为 5
v.erase(new_end, v.end());   // 此刻才真正变短：{1, 2, 3}
```

**Q10: [learning] operator[] 与 at() 越界访问的行为有何不同？**

operator[] 的前置条件是下标小于 size()，违反前置条件就是未定义行为，结果不可预期。at() 检查下标并在越界时抛出 `std::out_of_range`。检查被设计成可选，是为了不让每次下标访问都付出一次分支判断的代价，把选择权交给调用方。

1. **operator[]：**实测越界读既可能读到无关内存的值，也可能直接崩溃，优化后行为更不可预测，这类错误可能潜伏到很远的位置才表现为数据损坏。调试构建可用 libstdc++ 的 _GLIBCXX_ASSERTIONS（GCC 8 起提供）恢复检查，实测越界下标在断言构建中立即中止。
2. **at()：**实测越界抛出 `std::out_of_range`，`what()` 给出下标与 size 的具体数值。每次访问多一次范围检查，性能敏感的内层循环不宜使用。
3. **同类边界：**对空 vector 调用 front()、back() 同样是未定义行为。`data()` 对空 vector 返回空指针（实测为 nullptr），不能解引用。

**Q11: [learning] vector 的 bool 特化与其他 vector 有什么本质区别？**

`vector<bool>` 是按位压缩的特化：每个元素只占 1 位，`operator[]` 返回的不是 `bool&`，而是一个代理类对象，通过它间接读写对应的位。它因此不满足标准对其他 vector 的连续存储承诺，取元素地址和依赖 `bool&` 的泛型代码都会失效。

1. **代理对象：**实测 `vb[0]` 的类型是 libstdc++ 内部的 `_Bit_reference` 而非 `bool&`，对它赋值确实改写对应的位。但 `auto c = vb[0]` 拷贝的是代理对象而不是 bool 值，vector 随后变化时该代理可能悬垂。
2. **无法取地址：**对 `vb[0]` 取地址得到的是代理对象的地址，不是指向某个 bool 元素的指针。连续存储承诺 `&v[n] == &v[0] + n` 在标准中被明确限定为 bool 除外。
3. **共享字节的并发边界：**相邻元素共享同一字节，两个线程不加同步分别写 `vb[0]` 和 `vb[1]` 是对同一内存位置的数据竞争。
4. **替代选择：**按需求选择：

    1. 需要真正的 bool 元素序列：用 `std::deque<bool>`，它没有位压缩特化。
    2. 编译期已知长度的位集合：用 `std::bitset`。
    3. 只需紧凑存储且不依赖 `bool&`：用 `vector<char>`。
