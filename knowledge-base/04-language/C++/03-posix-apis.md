# C++ 中的 POSIX 接口

> 本文说明 C++ 程序使用 POSIX 接口的边界，以及 `pause()` 的等待行为。

**Q1: [done] 什么是 POSIX 函数，C++ 程序何时使用？**

POSIX 函数是 POSIX（Portable Operating System Interface，可移植操作系统接口）定义的操作系统接口，不属于 ISO C++ 标准库。目标平台提供该接口时，C++ 程序可以调用。

1. **需要系统能力：**操作文件描述符、进程或信号时，可使用目标系统提供的 POSIX API。
2. **需要跨平台：**优先用 C++ 标准库，或把 POSIX 调用封装在平台适配层。某个平台有 `<unistd.h>`，不代表所有 C++ 环境都有。

**Q2: [done] C++ 调用 POSIX 函数需要包含什么头文件、链接什么库？**

头文件提供函数声明，链接步骤提供实现。具体要求取决于函数和目标平台，不存在可供所有 POSIX 函数统一链接的 `libposix`。

1. **头文件：**按函数文档包含声明所在的头文件，例如 `pause()` 声明在 `<unistd.h>`。
2. **链接库：**Linux 上 `pause()` 由系统 C 库提供，常规 `g++` 链接流程会自动处理，不需要额外写 `-lposix` 或 `-lc`。
3. **平台差异：**其他函数可能需要额外库、特性宏或链接选项，应查目标平台文档。

**Q3: [done] Linux 中调用 `pause()` 会怎样等待信号，为什么它不能单独实现完整的 PID 1 init？**

`pause()` 挂起调用进程，直到捕获一个信号并运行其处理函数；处理函数返回后，`pause()` 返回 `-1`，并将 `errno` 设为 `EINTR`。它只提供等待机制，本身不负责信号策略、服务管理或回收子进程，因此不能单独实现完整的 PID 1 init。

1. 未注册信号处理函数时，常规信号按默认处置处理，程序无法执行 init 所需的信号处理逻辑。
2. Linux 对 PID 1 的信号处理有特殊规则，不能假设任意信号都会使 `pause()` 返回。

**Q4: [done] mkdir 如何使用？**

`mkdir` 声明在 `<sys/stat.h>`，调用形式为 `mkdir(路径, 模式)`：创建成功返回 `0`，失败返回 `-1` 并把原因写入 `errno`。路径以 `/` 开头为绝对路径，否则相对进程的当前工作目录。使用步骤是先按返回值判断成败，失败后再读 `errno` 区分原因，其中“路径已存在”（`EEXIST`）在幂等准备场景下不算错误。

1. **调用形式：**两个参数依次是目标目录路径和新目录权限位，权限位写成八进制字面量（前导 `0`），`0555` 即 `r-xr-xr-x`。
2. **路径参数如何解析：**绝对路径以 `/` 开头，相对于文件系统根；相对路径相对于调用进程的当前工作目录。当前工作目录是进程属性，由 `chdir()` 改变、`fork()` 继承，不是 mkdir 自身决定的。
3. **Android init 为何用绝对路径：**first stage init 以 root 运行，挂载 `/system` 之前先创建挂载点目录，此时写绝对路径把创建位置固定在文件系统根下，与 init 运行在哪个目录无关；改用相对路径则会建到当前工作目录下，一旦 cwd 不在预期位置就建错地方。系统代码统一使用绝对路径也源于此。
4. **返回值约定：**成功返回 `0`；失败返回 `-1` 并设置 `errno`。成败只按返回值判断——成功时 `errno` 保持旧值，不能反过来先检测它。
5. **模式如何实际生效：**新目录权限为模式与进程 umask 取掩码的结果。`0555` 不含写位，常见 umask（如 `022`）不改变它；需要权限与模式完全一致时，创建后再 `chmod`。
6. **失败后用 errno 判断原因：**`errno` 是线程局部变量，只有返回 `-1` 后读取才有效。常见值：`EEXIST` 路径已存在、`EACCES` 父目录不可写、`ENOENT` 父目录不存在、`ENOSPC` 空间不足。
7. **“已存在”如何处理：**`mkdir` 只创建最后一级；目标已存在时它不修改该目录的内容与权限。把“确保目录存在”当目标时，`errno == EEXIST` 不按错误处理；已存在路径是普通文件时同样返回 `EEXIST`，需要区分时用 `stat` 检查文件类型。

例如，按上述用法做一次幂等准备：

```cpp
#include <cerrno>
#include <sys/stat.h>

int prepare() {
    if (mkdir("/system", 0555) == -1 && errno != EEXIST) {
        return errno;  // 失败原因不是“已存在”才透传
    }
    return 0;         // 成功或已存在都视为就绪
}
```

`== -1` 先确认失败，`&&` 短路后 `errno` 只在失败时被读取；条件为真即“失败且不是已存在”，这才是需要调用方处理的错误。

**Q5: [learning] C++ 中 exec 怎么使用全解析**

`exec` 家族函数把一个正在运行的程序换成另一个：内核把新程序的代码和数据装入当前进程的地址空间，从新程序的入口重新执行，进程号不变；调用成功时不返回，失败时返回 `-1` 并设置 `errno`。C++ 中经 `<unistd.h>` 调用，Linux 上由系统 C 库提供，不需要额外链接库；共 6 个成员，按参数形式和是否搜索 PATH 选择。

1. **六个成员与命名规则：**`exec` 之后的第一段表示参数形式：`l`（list）用可变参数逐个传递，以 `(char *)nullptr` 结束；`v`（vector）用字符指针数组传递，数组末元素同样必须是空指针。后缀 `p` 表示按 PATH 搜索可执行文件名，`e` 表示传入自定义环境变量数组。组合后为 execl、execlp、execle、execv、execvp、execvpe，其中 execvpe 是 glibc 扩展，POSIX 未规定。
2. **参数约定：**可执行文件参数之后的第一项按约定是 argv[0]，通常放程序名，再接实际参数。漏写 `(char *)nullptr` 或数组成员的空指针结尾，exec 会继续越界读取参数。
3. **返回值与 errno：**成功时不返回；失败返回 `-1`，调用方继续执行。常见 errno：`ENOENT` 找不到文件或 PATH 中无匹配、`EACCES` 没有执行权限、`ENOEXEC` 不是可识别的可执行格式。
4. **路径形式的选择：**带 `p` 的 execlp、execvp 只写程序名，由 exec 按 PATH 查找；execl、execv、execle 要求给出路径。init 等系统程序通常直接使用绝对路径。
5. **典型模式 fork 后 exec：**因为成功后自身映像被替换，想在运行其他程序后继续原流程，就先 `fork()`，在子进程中调用 exec，父进程用 `waitpid()` 等待回收。exec 成功后 PID 不变，已打开的文件描述符继续保留（未设置 close-on-exec 时）。

例如，可变参数形式与失败处理：

```cpp
#include <cerrno>
#include <cstdio>
#include <unistd.h>

int run_echo() {
    execl("/bin/echo", "echo", "hello", (char *)nullptr);
    // 只有 exec 失败才会执行到这里
    std::printf("exec failed, errno = %d\n", errno);
    return -1;
}
```

数组形式单独写，两种形式不能在同一个执行流里先后调用——前者成功就替换了进程映像：

```cpp
char arg0[] = "echo";
char arg1[] = "hello";
char *const argv[] = {arg0, arg1, nullptr};
execv("/bin/echo", argv);  // 成功则后续代码不再执行
```

第一个例子中 `(char *)nullptr` 结束可变参数列表；第二个例子里 `argv` 末元素必须是空指针，用字符数组而不是字符串字面量，避免 C++ 不允许字面量到 `char*` 的转换。


**Q6: [learning] execv 怎么使用，`execv("/system/bin/init", next_argv)` 的两个参数分别要求什么？**

execv 把一个正在运行的程序换成另一个：内核把新程序的代码和数据装入当前进程的地址空间，从新程序的入口重新执行，原程序调用点往后的代码永远不会执行；进程号不变，换的只是里面跑的程序。execv 声明在 `<unistd.h>`。第一个参数是目标可执行文件的路径，第二个参数是新程序的 argv 数组——`char*` 序列、以空指针结尾，首项按约定放程序名。调用成功时不返回；只有失败才返回 `-1` 并设置 `errno`。

1. **签名与第一个参数：**`int execv(const char *path, char *const argv[])`。path 是要执行的程序路径，写绝对路径或相对于进程当前工作目录的相对路径。execv 不做 PATH 搜索——只给程序名会以 ENOENT 失败，需要按 PATH 查找时用 execvp。
2. **第二个参数 argv 的要求：**元素是 `char*`，每个指向一个参数字符串；`argv[0]` 按约定放程序名，实际参数从 `argv[1]` 起，末元素必须是空指针。这个数组就是新程序 `main` 收到的 argv，元素个数由空指针的位置推断。
3. **“替换进程映像”具体指什么：**被替换的是原程序的代码、数据和栈——调用点往后的旧代码不再存在；保留的是进程号和已打开且未设 close-on-exec 的文件描述符。argv 和环境变量由内核摆到新进程栈顶，新程序的 `main` 直接收到。因此成功时不存在“成功返回”，判断成败只看有没有从调用点继续执行。
4. **失败时的 errno：**常见值有 ENOENT（路径不存在）、EACCES（没有执行权限）、ENOEXEC（不是可识别的可执行格式）、ENOMEM。失败后原程序继续运行，应在调用点后按 errno 处理，例如记录日志或回退到其他启动路径。
5. **与 execl 的选择：**两者功能相同、传参形式不同——execl 逐个传参数并以 `(char *)nullptr` 结尾，execv 把参数预先组进数组。参数来自运行时变量或数量不定时用 execv 的数组形式更自然。

例如，init 第一阶段的典型调用：

```cpp
char *next_argv[] = {(char *)"/system/bin/init", (char *)"selinux_setup", nullptr};
if (execv("/system/bin/init", next_argv) == -1) {
    // 只有 execv 失败才会执行到这里
}
```

path 用绝对路径，与 `next_argv[0]` 一致；`next_argv` 末元素空指针标记参数结束；if 分支是纯失败路径。


**Q7: [learning] execv 的使用场景有哪些，什么时候该用？**

execv 适合两类场景：程序准备好环境后把自己换成目标程序，交棒后不再返回；或 fork 出的子进程里执行另一个程序，父进程保留控制权。判断依据是“换掉原程序后，还需不需要它的代码继续跑”。

1. **自我替换、交棒即终点：**原程序只负责准备工作，完成后没有后续逻辑，直接换成目标程序。AAOS 13 的 first_stage_init 正是如此：完成首阶段挂载、把标准输出改接到内核日志后，execv 到 `/system/bin/init` 并传入 `selinux_setup` 参数——成功则同一个 PID 1 从系统分区的 init 重新开始，首阶段代码到此终止。这类场景不需要 fork，因为旧代码不再需要。
2. **fork 后子进程执行、父进程继续：**目标程序运行期间原程序还要保留控制权（等待、回收或继续处理），就先 fork，在子进程里 execv，父进程 waitpid。shell 执行命令、服务管理器拉起工作进程都是这个形态。
3. **调用点的写法：**execv 只在失败时返回，所以调用之后直接写失败处理即可，不需要为“成功”分支安排代码——成功路径就是没有下文。AAOS 首阶段的写法是 execv 后紧跟一条 FATAL 日志：首阶段没有回退余地，记录日志后直接终止进程。
4. **参数形态决定传参形式：**参数来自运行时变量或已组好数组时用 execv 的数组形式；固定两三个字面量参数用 execl 的列表形式更短。两者功能相同，选的只是传参形式。
5. **边界：**只想执行命令并捕获输出，用 system 或 popen，不必自己 fork 再加 execv；需要跨程序保留的数据若只存在于内存，execv 帮不上忙——替换后旧程序的堆和栈都没有了，只能借助文件、环境变量或进程间通信传递。

例如，首阶段交棒给系统 init 的最小形态（AAOS 13 first_stage_init 实测结构）：

```cpp
const char* path = "/system/bin/init";
const char* args[] = {path, "selinux_setup", nullptr};
execv(path, const_cast<char**>(args));
PLOG(FATAL) << "execv(\"" << path << "\") failed";
```

execv 成功后不会返回，末行的失败日志只在调用失败时执行得到；标准输出已在 execv 前改接到内核日志，跨 exec 保留，新阶段继续沿用。
