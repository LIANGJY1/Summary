# 设计模式

> 学习资料。按创建型、结构型和行为型模式组织问题；题序即文档结构。

**Q1: [tags:设计模式] 简单工厂模式怎样根据输入创建不同产品？它的扩展边界在哪里？**

简单工厂把具体产品的创建集中在一个工厂中，客户端传入类型或配置，工厂选择并返回抽象产品。它降低客户端对具体类的依赖，但新增产品类型通常仍要修改工厂的选择逻辑。

适合产品种类有限、创建规则相对稳定且集中创建能简化调用方的场景。若产品类型持续增加，工厂内部的条件分支会变成变化中心；此时可考虑工厂方法或注册表等结构。

**Q2: 工厂方法与简单工厂在新增产品时的变化点有什么不同？**

工厂方法把创建动作交给具体工厂子类实现，客户端通过抽象工厂创建抽象产品；简单工厂则由单个工厂按条件选择具体产品。工厂方法把新增类型的变化从既有选择分支移到新增工厂实现，但会增加工厂类型。

当新增产品需要独立创建逻辑、且扩展点值得长期维护时，工厂方法更合适；只有少量固定类型时，简单工厂通常更直接。

**Q3: 抽象工厂模式怎样保证一组相关产品来自同一产品族？**

抽象工厂声明创建多个相关产品的接口；每个具体工厂实现整组创建方法，返回相互兼容的产品族。客户端依赖抽象工厂和抽象产品，不直接选择各个具体产品类。

例如 GUI 工厂可以同时创建按钮、菜单和复选框；Windows 工厂统一返回 Windows 风格产品，Mac 工厂统一返回 Mac 风格产品。这样新增产品族容易，但为所有工厂新增一种产品角色时，抽象工厂接口及其实现都要扩展。

**Q4: 工厂方法与抽象工厂应该如何区分？**

工厂方法通常封装一种产品的创建；抽象工厂封装一组相关产品的创建。判断依据是客户端是否需要保证多个产品属于同一兼容族，而不是类名里是否出现“工厂”。

**Q5: 建造者模式解决了复杂对象创建中的什么问题？**

建造者把复杂对象的构造过程与最终表示分开，让调用方按步骤提供配置，并在构建阶段集中处理默认值、校验和组装。它适合构造参数多、可选字段多或构造顺序需要表达的对象。

1. **构造器**保存逐步收集的配置或部件。
2. **构建操作**检查必需条件并生成目标对象。
3. **目标对象**只暴露有效状态，避免大量难以辨认的重载构造函数。

不复杂的对象无需为每个构造过程单独引入 Builder；若允许任意步骤顺序，也要明确哪些配置可重复或互相覆盖。

**Q6: 建造者模式中的 Director 是否是必需角色？**

Director 不是必需角色。它可以封装一套固定的构造步骤，适用于多处需要重复构造同一流程的场景；若调用方需要灵活选择步骤，直接使用 Builder 往往更简单。

**Q7: 装饰器怎样在不改目标类的前提下组合附加行为？**

装饰器与被包装对象实现同一抽象接口，并持有另一个该接口实例；装饰器在调用前后增加行为，再把核心操作委托给被包装对象。多个装饰器可以按顺序嵌套，从而组合可选功能。

例如咖啡订单可先包装基础咖啡，再逐层增加牛奶或糖的价格与描述。装饰器适合行为可组合且不希望为每种组合创建子类的场景；层层包装会增加运行时对象和调试路径。

**Q8: 装饰器与代理都包装对象，怎样按意图区分？**

两者都可持有同一接口的目标对象，但装饰器主要组合附加职责，代理主要控制目标访问、延迟创建或跨越访问边界。类结构相似时，应根据调用者需要的意图与对象所有权来命名和设计。

**Q9: 责任链模式怎样处理多个可能的请求处理者？**

责任链把处理者按顺序连接，请求沿链传递；每个处理者可处理、拒绝或继续传递。它让发送者不必知道最终由哪个处理者完成请求。

链可以是一个处理者处理后继续，也可以在首个处理者接收后短路结束。设计时必须规定无处理者接收时的结果、链顺序以及处理者是否允许修改请求。

**Q10: 责任链与装饰器的调用结果语义有什么不同？**

责任链的核心是处理权在多个候选者间传递，某个处理者可能终止传播；装饰器的核心是多个包装层围绕同一个对象叠加职责，通常继续委托核心操作。需要确定谁负责处理请求时用责任链，需要组合前后附加行为时用装饰器。

**Q11: 观察者模式怎样让状态变化通知多个订阅者？**

主题维护观察者集合；当主题状态变化时，按约定通知观察者，使它们读取新状态或消费变更。主题依赖抽象观察者接口，不直接依赖每个具体订阅者。

订阅方要在生命周期结束时取消订阅，否则主题持有观察者引用可能导致对象无法回收。通知既可携带变化数据，也可只发信号让观察者重新读取状态；选择取决于一致性和耦合要求。

**Q12: 观察者通知采用推模型还是拉模型？**

推模型由主题把变化数据传给观察者，减少重复读取但会让主题了解通知载荷；拉模型只通知状态已变化，由观察者按需读取主题，降低载荷耦合但可能产生额外读取。异步通知还需定义顺序、丢失、重试和取消语义。

**Q13: 策略模式怎样隔离可替换的算法？**

策略模式把一组可互换算法封装成共同接口，客户端选择并持有一种策略，通过接口执行，而不把算法分支写进客户端。新增算法可以作为新策略加入，选择策略的责任仍需由调用方、配置或独立选择器承担。

适合算法会变化、算法分支影响主流程或需要独立测试时；若只有一个稳定实现，抽象策略会增加不必要的类型和间接层。

**Q14: 策略模式和简单工厂可以怎样协作？**

策略接口定义“怎样执行”，工厂可以根据配置创建或选择具体策略。工厂解决创建与选择集中化，策略解决算法实现可替换，两者可组合但职责不同。

**Q15: 代理模式通过什么方式控制对目标对象的访问？**

代理实现与目标相同的接口，并在调用时代表调用方访问目标；代理可在转发前后进行权限检查、延迟创建、缓存或远程调用封装。只有实际增加了访问控制或间接访问需求时，代理才有明确价值。

**Q16: 静态代理和动态代理的实现成本有何区别？**

静态代理由开发者显式编写代理类，类型检查清楚但每个接口和方法都可能需要重复代码；动态代理在运行时生成或构造转发层，能减少重复实现，但调用依赖反射或运行时生成机制，错误更可能在运行时暴露。

Java 动态代理可代理接口调用；能否代理类、具体限制和实现方式取决于采用的代理技术。不要把 JDK 接口代理与字节码生成类代理混为一谈。

**Q17: 单一职责原则中的“单一”应如何理解？**

单一职责不是要求类只含一个方法，而是要求一个模块围绕一类相近变化原因组织。若两个需求变化经常由不同角色推动，且修改其中一个总迫使另一个一起回归，就应检查是否存在多个职责。

拆分也有成本：过度细分会增加对象协作和定位难度。边界要以变化原因和调用关系为依据，而不是机械按方法数量划分。

**Q18: 开放封闭原则怎样与实际扩展需求平衡？**

开放封闭原则要求稳定代码面对已知变化点可通过扩展来容纳新行为，减少反复改动核心逻辑；它不意味着代码永远不能修改。应先从真实变化频率和稳定接口识别扩展点，再决定是否引入多态、组合或注册机制。

**Q19: 里氏替换原则如何判断子类型是否能替代父类型？**

子类型应满足父类型对调用者承诺的前置条件、后置条件和不变量，使依赖父类型的客户端换用子类型后仍能正确工作。仅仅继承了父类并通过编译，不足以说明替换成立。

子类型不应加强调用前提、削弱调用结果保证，或通过违背不变量的方式改变既有语义；若两者行为契约不同，应重新设计抽象关系。

**Q20: 依赖倒置原则与依赖注入分别强调什么？**

依赖倒置强调高层策略和底层实现都依赖稳定抽象，细节通过抽象接入；依赖注入是把依赖对象从外部提供给使用者的一种组装方式。依赖注入可帮助落实依赖倒置，但二者不是同义词。

**Q21: 接口隔离原则怎样减少调用方对无关能力的依赖？**

接口隔离要求调用者依赖与其用途相称的小接口，避免被迫实现或依赖无关操作。拆分应围绕实际客户端职责，避免为了接口数量最少而制造巨型接口。

**Q22: 迪米特法则怎样减少对象对协作对象内部结构的了解？**

迪米特法则要求对象优先与直接协作者交互，避免沿着多个对象的内部关系层层访问。封装稳定的业务操作到直接协作者中，可以减少调用方受内部结构变化影响；机械地把每次链式调用都包装成转发方法也会制造冗余。

**Q23: 合成复用原则为什么通常偏向组合而不是继承？**

组合通过持有协作者来复用行为，允许在运行时替换策略并减少子类与父类实现细节的耦合；继承适合稳定的“是一个”关系和受控扩展点。组合并非没有成本，它会增加对象装配和委托代码。

选择时关注变化是否需要独立替换、父类实现是否稳定，以及替换后是否仍满足抽象契约。
**Q24: 统一分发与策略路由怎样降低事件入口和业务执行之间的耦合？**

统一分发把多个触发点收口到一个入口，策略路由再依据请求携带的数据或类型选择执行者；入口负责校验、记录与路由，业务模块负责具体动作。这样可以把鉴权、去重或日志等横切规则放在共同入口，也让策略可以独立替换。

请求应以稳定的数据契约表达意图，而不是把具体 View 或回调对象传进业务核心；分发器才能脱离 UI 独立测试。集中入口也会成为关键依赖，需避免把分发器做成承载所有业务逻辑的“万能类”，并通过显式注册、清晰策略边界和可观测失败结果控制复杂度。
