# VFS 与挂载

> 通用操作系统虚拟文件系统与挂载学习资料。主线：VFS 的统一接口与分派、vnode 与 inode 的概念辨析、挂载的目的与必要性、挂载后路径查找的变化、bind mount、mount namespace 与 overlayfs。原 07 册更名并补规范格式；2026-10-06 按 kernel.org 与 AOSP fs_mgr 官方文档口径扩充 bind mount、mount namespace 与 overlayfs 三题；2026-10-08 增补挂载目的与必要性一题。Q 序列即结构，供 atlas 同源直读。

**Q1: [done] 分区上的文件系统为什么必须挂载后才能按路径访问？挂载的目的是什么？**

挂载的目的是把一个已组织好的文件系统实例接到当前目录树的某个路径（挂载点）上，使其中的文件可以按路径命名和访问。之所以必须挂载：进程能指名的对象只有路径，而文件系统的目录树在挂载前只存在于块设备上，不接入任何可见的树，应用因此无法指名其中任何文件。

挂载的必要性可以拆成四层：

1. **路径是唯一的命名入口**：应用打开文件只能给路径，内核沿目录树逐段解析定位文件；块设备本身是可按块编址的线性序列，文件系统把它组织成目录树，但挂载前这棵树不接入任何路径，从树根解析永远走不到它。此时数据并非不可触达——仍可经设备节点整块读写（如 `dd`），只是无法按路径指名其中某个文件，两种接口面向不同层次。
2. **单一目录树要求显式接入点**：进程看到的是一棵目录树，没有 Windows 盘符那样每个卷自带一个命名入口的模型；树根覆盖的只有挂载为根的那个文件系统，其余卷（其他分区、可移动介质、网络共享）要可见，唯一途径就是选定一个已有目录作挂载点接上去。
3. **挂载是 VFS 统一接口的生效时机**：挂载时内核读取该文件系统的超级块、实例化根 inode，并建立挂载结构把挂载点与这个根绑定；此后发往挂载点子树的请求才会经 VFS 分派落到这个具体文件系统的操作表上。procfs、sysfs、tmpfs 这类虚拟文件系统没有任何设备，也必须挂载后才可见——挂载的本质是"把文件系统实例接入目录树"，而不是"把一块硬件接进来"。
4. **挂载给出文件系统的可见生命周期**：挂载即对外可见，卸载即从树中摘除；默认卸载要求没有进程仍打开其中文件或将其作为工作目录，摘除前先回写脏数据，保证此后数据完整（Linux 另提供 `MNT_DETACH` 延迟卸载，先摘视图、等占用释放后再收尾）。

挂载的发起与时机由用户态安排：内核在启动早期只挂好根文件系统，其余卷由 init 等用户态进程通过 `mount()` 系统调用按配置挂载（传统 Linux 以 `/etc/fstab` 声明），可移动介质在插入时挂载，容器则按 mount namespace 构造各自视图。

挂载点一般选空目录：挂载后该目录原有内容会被遮蔽，卸载后才恢复可见。



**Q2: [learning] VFS 怎样让应用用统一接口访问不同文件系统？**

虚拟文件系统在具体文件系统之上提供通用操作入口，并把操作分派给对应文件系统实现。应用按路径和通用文件操作访问对象，不必为每种文件系统编写一套调用接口。



**Q3: [learning] vnode 和 inode 是同一个对象吗？**

这两个名称不表示所有操作系统中固定的一对不同对象。BSD 等系统常以 vnode 称呼 VFS 层的文件对象；Linux 使用 VFS inode 表示内存中的文件元数据与操作接口，并由具体文件系统提供其实现和持久化格式。它们在概念上都承担统一文件对象或元数据访问职责，但类型、缓存关系和持久化布局依操作系统而异。

因此，不能笼统说 vnode 是一个对象、inode 是另一个对象，也不能假定每次打开文件都会把磁盘 inode 完整复制成 vnode。讨论具体实现时应标出内核与文件系统；路径名、目录项缓存、内存中的 inode/vnode 和磁盘元数据也不是同一个概念。



**Q4: [learning] 文件系统挂载后，路径查找发生了什么变化？**

挂载把一个文件系统的根接到现有目录树中的挂载点；路径遍历到该挂载点时，后续查找转入被挂载文件系统。挂载通常需要注册文件系统类型、准备超级块或根对象并建立挂载关系，具体步骤随操作系统与文件系统实现而异。



**Q5: [learning] bind mount 与普通挂载有什么区别？它解决了什么问题？**

普通挂载把一个独立文件系统的根接到目录树；bind mount 则把"已有目录树中的某段子树"重新映射到另一个挂载点——两端是同一文件系统的同一份内容，不新建文件系统、不存在格式化对象，只是命名空间里多了一个入口视图。

1. **语义**：挂载点是子树的别名，经任一路径的修改都作用于同一数据；卸载别名不影响原路径。
2. **用途**：为容器/chroot 补齐 /proc、/dev 等入口；把只读位置以只读标志重新暴露；Android 开发期的 adb remount 也用 bind/overlay 组合在只读分区上提供可写视图（平台细节归 `../../01-android/10-build-system/01-product-config.md` 相邻主题）。
3. **边界**：bind mount 的复制是挂载动作而非数据拷贝；移动（rename）挂载点下的内容与普通文件操作相同。



**Q6: [learning] mount namespace 是什么？它如何让不同进程看到不同的挂载布局？**

mount namespace 是内核提供的挂载视图隔离：每个命名空间持有独立的"挂载点集合"，进程关联到某个 namespace 后，它看到的目录树就由该集合决定。新建 namespace（clone/unshare 带 `CLONE_NEWNS`）会复制父视图，此后原视图与新视图各自 add mount / umount 互不可见。

1. **复制语义**：新 namespace 从父视图快照起步；此后一侧的新挂载不会出现在另一侧。
2. **传播关系**：视图间可配置挂载传播（private、shared、slave 等），shared 使挂载事件在多个 namespace 间广播，private 则完全隔离——容器运行时据此决定宿主新挂载是否渗入容器。
3. **用途**：容器与沙箱为每个实例构造独立挂载布局；Android 的应用隔离与多用户也在内核 mount namespace 之上叠加视图（平台侧实现归 `../../01-android/` 沙箱与存储专题）。



**Q7: [learning] overlayfs 的上下层语义是什么？Android 为什么用它给只读分区提供可写视图？**

overlayfs 把多个目录叠加成单个合并视图：lower 层只读（可多层叠放，通常来自只读分区或镜像），upper 层可写，合并结果对应用表现为一个普通目录。写路径的规则是"写时上提"：

1. **读取**：upper 有该文件用 upper，否则逐层向下找 lower，取最上层命中。
2. **修改与新建**：首次修改 lower 文件时把它整体复制到 upper（copy-up）再改；新建文件直接落 upper。
3. **删除与遮挡**：删除 lower 文件在 upper 建 whiteout 遮挡条目屏蔽下层的同名对象；同目录合并时有重叠冲突语义。
4. **Android 场景**：A/B 动态分区后 system/vendor 分区运行期只读，开发与调试用 overlayfs 在只读分区上叠加可写 upper（AOSP `fs_mgr` 的 overlayfs remount，需内核 `CONFIG_OVERLAY_FS`）；对生产系统它不是可写的持久化方案——upper 通常落在临时或调试专用空间，重启即按配置回收。
