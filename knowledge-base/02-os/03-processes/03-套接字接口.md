# 套接字接口、寻址与数据传输

> 范围：POSIX/Linux 套接字的创建、寻址、连接、数据传输与选项。接口行为以 POSIX 定义和 Linux man-pages 的对应手册为依据。通用 TCP/IP 协议原理归网络知识库。

**Q1: [done] 套接字是什么？套接字描述符是什么？**

1. **套接字：**内核维护的通信端点，是通信一方用来收发数据的对象。内核保存它的状态和收发队列。
2. **套接字描述符：**进程用来访问该端点的文件描述符（fd，file descriptor），本质是一个整数编号。进程把它传给 send、recv 等调用。fd 不是套接字本身，编号只在本进程内有意义。

调用 socket 与 open 类似，成功时都返回可用于 I/O 的 fd。不再需要时，close 释放当前 fd 编号供重用。但函数接受 fd 参数，不代表它一定对套接字有适用的行为。

图中两行是独立示例，不表示两个套接字已连通。连线只表示访问关系，省略中间的打开文件表项。













**Q2: [done] 套接字和描述符由谁维护，数量怎样确定？**

内核维护套接字对象和各进程的 fd 表。套接字数量随调用动态变化，受 fd 上限、系统文件表和内存等资源限制。















**Q3: [done] socket 函数的声明、参数和返回值怎样读？**

```c
#include <sys/socket.h>
int socket(int domain, int type, int protocol);
```

socket() 接收三个参数，依次是通信域、套接字类型和具体协议。它们共同决定要创建哪种通信端点。调用成功返回 fd；失败返回 -1 并设置 errno。下面按参数顺序说明各自的作用。

1. **domain（通信域）：选择在哪类通信体系中通信。**常量前缀 AF 是 Address Family（地址族）的缩写。domain 选择通信所用的地址族，并决定后续地址格式。常见值有：
    1. `AF_UNIX`：本机进程间通信，地址通常是本地路径，不使用 IP 地址和网络端口。
    2. `AF_INET`：IPv4 通信，后续地址通常用 `sockaddr_in` 表示。
    3. `AF_INET6`：IPv6 通信，后续地址通常用 `sockaddr_in6` 表示。

2. **type（套接字类型）：选择数据如何交付给应用。**
    1. `SOCK_STREAM`：把数据当作连续字节流。假设发送方先后发送“ABC”和“DEF”，接收方可能一次读到“ABCDEF”，也可能分几次读到；收发调用的边界不会保留。因此应用协议要规定如何识别一条完整消息，例如用长度字段或分隔符。TCP 常使用这种类型；`AF_UNIX` 也可提供相同的流式收发方式，用于本机进程通信。
    2. `SOCK_DGRAM`：把数据当作一条条独立报文。每次发送形成一条数据报，接收方按报文读取，边界会保留。IPv4/IPv6 常用 UDP 承载这类报文；UDP 报文可能丢失或乱序。`SOCK_DGRAM` 是数据交付类型，UDP 是具体协议，不能画等号；其他通信域的数据报有各自的交付保证。

   所以，`SOCK_STREAM` 收发的是连续字节，消息边界由应用定义；`SOCK_DGRAM` 收发的是有边界的报文。类型描述交付方式，不单独指定具体协议。

3. **protocol（具体协议）：在 domain 和 type 允许的范围内选择协议。**传 `0` 表示让系统为该组合选择默认协议，不是“没有协议”。例如 IPv4 的 `SOCK_STREAM` 通常默认 TCP，IPv4 的 `SOCK_DGRAM` 通常默认 UDP；需要明确指定时可传 `IPPROTO_TCP` 或 `IPPROTO_UDP`。protocol 也不是端口号。

看三个组合的差别：

1. `socket(AF_UNIX, SOCK_STREAM, 0)`：本机地址体系 + 字节流语义 + 该组合的默认协议。
2. `socket(AF_INET, SOCK_STREAM, 0)`：IPv4 地址体系 + 字节流语义 + 通常为 TCP。
3. `socket(AF_INET, SOCK_DGRAM, 0)`：IPv4 地址体系 + 数据报语义 + 通常为 UDP。

调用成功只创建本地套接字并返回 fd；还没有指定本地地址、连接对端或开始收发。后续是否需要 bind、connect 或 listen，由通信角色和类型决定。















**Q4: [done] SOCK_DGRAM 和 SOCK_STREAM 的区别？**

两者的核心区别是通信是否先建立逻辑连接，以及应用接收的是独立报文还是连续字节流。

1. **SOCK_DGRAM：**通常无需先连接对端。每次发送一条自包含报文。未设置默认对端时，每条报文需指定目的地址，因此不同报文可以发往不同对端。接收方能识别报文边界。常见的 UDP 数据报不保证送达或顺序，不能仅凭发送成功推断对端已收到。对数据报套接字调用 connect 只会设置默认对端，不会建立 TCP 式连接。
2. **SOCK_STREAM：**收发前须在两端套接字之间建立逻辑连接。连接确定通信对端，后续收发不必逐次指定地址。它提供有序字节流，但不保留每次 write 或 send 的边界：发送方分两次写入的数据，接收方可能一次读到，也可能要读多次。应用应循环读取，并自行约定如何识别完整消息。连接中断时不能保证取得全部已发送数据。













**Q5: [done] SOCK_SEQPACKET 和 SOCK_RAW 分别提供什么服务？**

SOCK_SEQPACKET 关注有连接的记录交付，SOCK_RAW 允许应用接触较低层协议数据。它们都是套接字类型，但各自支持范围由通信域与协议决定。

1. **SOCK_SEQPACKET：**面向连接，按顺序保留记录边界。它与流的区别是应用仍能识别记录，与数据报的区别是要求相应的连接语义。接收缓冲区不足仍可能截断，保留边界不等于自动分配足够内存。
2. **SOCK_RAW：**允许直接使用较低层协议，例如 IP 原始套接字。应用需要处理哪些头部由协议与选项决定，不能一概说所有 IP 头都必须手工生成。Linux 创建原始 IP 套接字，需要在管理该网络命名空间的用户命名空间中拥有 CAP_NET_RAW 能力。
3. **支持关系：**内核不保证每个通信域都支持所有类型。创建失败时需区分组合不支持和权限不足，不能只修改 protocol 参数反复试错。

类型名称说明交付目标，具体可用组合应查 socket(2)、raw(7) 及相应协议手册。









**Q6: [done] 套接字什么时候保留连接或直接 close，何时才需要 shutdown？**

如果这条连接以后既不发送、不接收，也不复用，直接 close(fd)，不需要先 shutdown。shutdown 主要用于还不能关闭整个连接，却要先结束一个收发方向的情况，例如结束发送后继续接收响应。close 释放当前 fd 引用，shutdown 改变套接字的收发方向但不释放 fd，最终仍需 close。

```c
#include <sys/socket.h>
int shutdown(int sockfd, int how);
```

shutdown 成功返回 0，失败返回 -1 并设置 errno。要观察关闭对读取的影响，先认识 recv：`recv(fd, buf, n, 0)` 从 fd 对应的套接字把最多 n 个字节读入 buf。对于已连接的 TCP 字节流，要求 n 大于 0 时，按返回值区分结果：

1. **返回正数：**读到了这么多字节，不代表整条业务消息已读完。
2. **返回 0：**本端读方向仍开放时，通常表示对端已正常结束发送，而且此前收到的字节已读完。这个结果称为 EOF（End of File，流结束），不是对端发送了一个特殊字节。若本端自己调用过 SHUT_RD，不能仅凭随后读取到的 0 推断对端已结束发送。
3. **返回 -1：**发生错误，按 errno 区分原因。若连接还开着但暂时无数据，阻塞调用会等待，非阻塞调用通常返回 -1 并报告 EAGAIN 或 EWOULDBLOCK，不会把“暂时无数据”报告为 EOF。

这里要求 n 大于 0，是因为请求读取 0 字节本身也可能返回 0。请求读 1 字节只是最小示例，读更大的正数也能判断 EOF。以下假设 A、B 之间是正常工作的 TCP 连接，A → B 和 B → A 是独立的两个发送方向：

1. **A 关闭写方向 SHUT_WR：**A 不能再发送，但仍能接收 B 发来的数据。TCP 在 A 已排队的数据之后发送 FIN，表示 A → B 不会再有字节。B 的 recv 先读出剩余数据，收到 FIN 且读完数据后再读才返回 0。B 仍可向 A 发送响应。
2. **B 关闭写方向 SHUT_WR：**过程对称。B 不能再发送，但仍能接收 A 的数据。A 读完 B 已发送的数据并收到 FIN 后，recv 才返回 0。这不妨碍 A 继续向 B 发送。
3. **A 关闭读方向 SHUT_RD：**A 不再接收 B → A 的数据，但 A → B 的发送方向没有关闭。B 不会因为 A 关闭读方向就从自己的 recv 读到 EOF，也不能靠这个调用得知自己应停止发送。需要停止发送的约定时，应使用应用协议通知 B。
4. **A 关闭双向 SHUT_RDWR：**相当于同时停用 A 的读、写方向。正常有序结束 A → B 时，B 读完 A 已发送的数据后可观察到 EOF。A 已不能接收 B → A 的数据，但 B 的写方向并不会被这个调用自动关闭。A 最终仍需 close 释放 fd。

按实际目标选择：

1. **之后不再使用连接：**服务端收完请求并发完响应，且不打算复用这条连接时，调用 close(fd)。它不能再通过这个 fd 收发。如果没有其他引用，套接字随后释放。此时无需先调用 shutdown(fd, SHUT_RDWR)。
2. **后续还要复用连接：**不要仅因一次请求完成就 close。保留连接可省去下次建连的延迟，但它仍占用 fd 和内核连接状态，排队数据也会占用缓冲区。空闲连接通常不会持续忙占 CPU，启用保活探测或应用心跳时则会产生流量与处理开销。连接数量多时应限制空闲连接数和闲置时长，并在复用失败时重新连接。shutdown 不释放 fd，不能替代 close 回收套接字资源。
3. **发送完毕，但还要接收响应：**假设 TCP 应用协议约定“读到 EOF 才算请求结束”。客户端发完请求后若直接等响应，服务端仍在等 EOF，双方就会互相等待。只有一个 fd 时，客户端若直接 close(fd)，虽然能结束发送，却无法再读取响应。此时应调用 shutdown(fd, SHUT_WR)，让服务端读完请求后读到 EOF 并返回响应。客户端继续读取响应，最后 close(fd)。若协议已有长度字段或分隔符，服务端无须等待 EOF，客户端可在读完响应后直接 close，通常不需要 shutdown。
4. **同一套接字有多个 fd 引用：**假设 fd2 = dup(fd1)。close(fd1) 只释放一个引用，fd2 仍可收发。若要立即停止这条连接的发送方向，调用 shutdown(fd1, SHUT_WR) 会让 fd2 也不能再发送。用完后仍要分别关闭持有的 fd。











**Q7: [done] 32 位整数的大小端如何影响内存字节排列和跨主机解释？**

字节序改变多字节整数在内存中的排列，不改变整数的数值。以值 0x04030201 为例，最高有效字节是 0x04，最低有效字节是 0x01。假设字符指针 cp 指向该整数的最低内存地址，从低地址到高地址读取四个字节：

1. **大端：**依次读到 `04 03 02 01`，因此 cp[0] 是 0x04，cp[3] 是 0x01。
2. **小端：**依次读到 `01 02 03 04`，因此 cp[0] 是 0x01，cp[3] 是 0x04。

十六进制数值写法中的最高有效字节始终在左，不能据此推断它在内存中的地址。若小端主机直接发送该整数的四个内存字节，大端主机按本机整数解释 `01 02 03 04`，得到的会是 0x01020304。TCP/IP 协议字段使用大端的网络字节序。传输约定为网络字节序的 32 位字段时，发送方须将原值表示为 `04 03 02 01`，接收方再转回主机字节序。同一台计算机上的进程若采用相同的本机表示，通常不需要转换，但仍须遵守双方约定的数据格式。









**Q8: [done] 接受文件描述符的函数，为什么不一定能用于套接字？**

文件描述符统一了访问入口，没有统一所有对象的能力。判断某个函数能否用于套接字，要看它要求底层对象提供什么语义。

1. **管理引用的操作可以复用：**close 释放当前描述符，dup 复制引用，fork 继承引用。这些操作不要求对象是磁盘文件。
2. **顺序收发可以复用：**已连接的流套接字可以使用 read、write、readv 和 writev。内核从接收队列取字节、向发送队列交字节，而不是读写磁盘上的某个位置。
3. **依赖文件偏移的操作不能照搬：**lseek 的含义是改变下一次文件读写的位置，套接字没有这种位置。已经接收并取走的字节不能靠 lseek 再读，想重读必须由应用自己缓存。在 Linux 上，对套接字调用 lseek 会以 ESPIPE 失败。
4. **函数可调用不等于字段含义相同：**fstat 可以识别套接字对象，但不能把它的大小等字段解释为“还有多少业务数据”。检查可读性使用 select/poll，取得数据使用接收接口。
5. **未指定和由实现定义要分别理解：**前者没有可依赖的标准结果，后者要求查具体系统的约定。它们不都等于必然报错，也不能因为函数参数是 int fd 就假定有效。









**Q9: [done] 套接字的地址结构解析？**

套接字地址包含**地址族**和该族的**定位信息**。地址族决定后面的字段怎样解释，定位信息指出具体端点。程序按地址族创建实际结构，以下代码只摘录关键字段，省略了实现可能添加的填充字段。

1. **本机 Unix 域：用路径定位。**

    ```c
    struct sockaddr_un {
        sa_family_t sun_family;    /* AF_UNIX */
        char        sun_path[108]; /* Linux 中的长度 */
    };
    ```

    `sun_family` 表示本机 Unix 域。路径型地址把 `/tmp/demo.sock` 放入 `sun_path`，不使用 IP 或端口。108 只适用于 Linux。Unix 域也允许没有路径的未命名端点。

2. **IPv4 网络域：用 IPv4 地址和端口定位。**

    ```c
    struct in_addr { in_addr_t s_addr; };
    struct sockaddr_in {
        sa_family_t    sin_family; /* AF_INET */
        in_port_t      sin_port;   /* 16 位端口 */
        struct in_addr sin_addr;   /* IPv4 地址 */
    };
    ```

    对 `127.0.0.1:8080`，`sin_family` 是 AF_INET，`sin_port` 存网络序的 8080，`sin_addr.s_addr` 存 32 位二进制 IPv4 地址。in_port_t 是 16 位，in_addr_t 是 32 位。引文中的 `struct in6_addr sin6_addr` 是笔误，IPv4 成员应为 `struct in_addr sin_addr`。

3. **IPv6 网络域：用 IPv6 地址和端口定位。**

    ```c
    struct in6_addr { uint8_t s6_addr[16]; };
    struct sockaddr_in6 {
        sa_family_t     sin6_family;   /* AF_INET6 */
        in_port_t       sin6_port;     /* 16 位端口 */
        uint32_t        sin6_flowinfo; /* 流信息 */
        struct in6_addr sin6_addr;     /* IPv6 地址 */
        uint32_t        sin6_scope_id; /* 作用域标识 */
    };
    ```

    `sin6_addr.s6_addr` 的 16 个字节保存 128 位 IPv6 地址。`sin6_port` 与 IPv4 一样是网络序端口。`sin6_scope_id` 可在链路本地地址需要区分网卡时指定接口。一般不用流信息时将 `sin6_flowinfo` 置零。

4. **通用接口 sockaddr：只统一函数参数，不替代上述实际结构。**

    ```c
    struct sockaddr {
        sa_family_t sa_family;
        char        sa_data[];
    };

    int connect(int fd, const struct sockaddr *addr, socklen_t addrlen);
    ```

    `addr` 指向实际地址对象，`addrlen` 是它的字节长度，类型为 socklen_t。若 `peer` 是已填好的 sockaddr_in，调用 `connect(fd, (const struct sockaddr *)&peer, sizeof(peer))`。转换只改变指针类型，不复制对象。`sizeof(peer)` 是结构大小，不能写成 `sizeof(&peer)`。系统根据地址族和长度解释原对象，**无需另建 sockaddr 或手工填写 sa_data**。Linux 的 `sa_data[14]` 不限制 IPv6 地址长度。FreeBSD 还在结构开头增加 `sa_len`，具体布局以系统头文件为准。

    接收未知地址族的地址时，可先提供足够大且对齐的 sockaddr_storage 缓冲区和容量。accept、getsockname 等返回实际地址长度后，再按地址族读取对应结构。







**Q10: [done] gethostent 等枚举接口如何管理遍历状态和返回结果？**

这组函数用于**逐条遍历主机记录**。这里的“主机记录库”不是固定的一份系统文件，而是主机信息的逻辑集合。每条记录描述一个主机名及其 IP 地址。

在 Linux 上，主机信息可能来自不同地方，`/etc/nsswitch.conf` 决定名称查询使用哪些来源及其顺序：

1. **本地文件：**`/etc/hosts` 是普通文本文件，每行可写一个 IP 地址、主机名和别名，例如 `192.0.2.10 buildbox buildbox.local`。
2. **DNS：**主机记录保存在 DNS 服务器上，系统按主机名向服务器查询 A 或 AAAA 等记录。DNS 是分布式查询服务，不是本机保存的一张可从头读到尾的完整主机表。
3. **其他来源：**系统也可能配置 NIS、LDAP 等名称服务。具体有哪些来源取决于系统安装和配置。

`/etc/nsswitch.conf` 只配置“去哪里查、按什么顺序查”，不保存主机记录本身。`gethostent` 的顺序枚举能力则取决于实现和数据源；它不能保证枚举 DNS 或其他远程服务里的全部主机。

调用顺序表示的是遍历状态：`sethostent` 将下一次读取设为第一条，`gethostent` 每次取一条，`endhostent` 结束遍历。

1. **sethostent(int stayopen)：**开始从当前实现支持枚举的数据源读取，并将位置设到第一条记录。`stayopen` 非零时，请求在连续读取期间保持数据源连接。为 0 时不请求保持连接。
2. **gethostent(void)：**读取下一条可枚举的记录，返回指向 hostent 的指针。
3. **endhostent(void)：**结束这次遍历并释放相关资源。它不操作应用用于通信的套接字。

**hostent 是什么：**它是 `<netdb.h>` 定义的 C 结构，用来把一条主机记录的名称和地址交给调用者。POSIX 要求它至少包含以下成员：

```c
struct hostent {
    char  *h_name;       /* 主机的正式名称 */
    char **h_aliases;    /* 别名列表 */
    int    h_addrtype;   /* 地址族，例如 AF_INET */
    int    h_length;     /* 每个地址的字节数 */
    char **h_addr_list;  /* 地址列表 */
};
```

字段按用途理解：

1. **名称：**h_name 是主机正式名称。h_aliases 是以 NULL 指针结尾的别名数组。
2. **地址类型和长度：**h_addrtype 表示地址族，h_length 表示列表中每个地址所占的字节数。例如 IPv4 地址长度为 4 字节，IPv6 地址长度为 16 字节。
3. **地址列表：**h_addr_list 是以 NULL 指针结尾的地址数组。每个元素是二进制地址，采用网络字节序，不是 `"192.0.2.10"` 这样的文本，也不包含端口。打印地址时，应按 h_addrtype 选择地址格式转换函数。

下面的例子逐条打印当前实现能够枚举到的主机名：

```c
#include <netdb.h>
#include <stdio.h>

void print_host_entries(void) {
    struct hostent *entry;
    sethostent(1);
    while ((entry = gethostent()) != NULL)
        puts(entry->h_name);
    endhostent();
}
```

循环每次取一条记录，直到 gethostent 返回 NULL。NULL 表示没有取得下一条记录，常见情况是当前数据源已经读完。接口不保证仅凭 NULL 就能区分遍历结束和其他查询问题。`sethostent(1)` 请求在连续读取时保持数据源连接。示例输出取决于系统配置，不代表 DNS 全量主机列表。

gethostent 返回的 hostent 及其内部指针可能指向函数内部的静态数据缓冲区。下一次调用 gethostent 时，这些内容可能被覆盖或失效。需要留存时必须复制结构及其引用的数据，不能只复制结构本身。也不要对库返回的指针调用 free。

这类接口适合检查当前数据源支持枚举的主机记录。若要按主机名查询可用于连接的地址，应使用 getaddrinfo。网络、协议和服务记录也有对应的 set*ent、get*ent、end*ent 遍历接口。依据：POSIX.1 的主机数据库接口规范、Linux man-pages 的 gethostbyname(3) 说明及 glibc 手册的主机名数据库说明。



**Q11: [done] 主机、网络、协议和服务数据库分别查什么？**

Q10 讲的是**怎样逐条遍历主机记录**，包括 sethostent、gethostent、endhostent 和 hostent 的返回内容。Q19 讲的是**四类记录各自查什么、按什么条件查、何时使用**。这些接口只查询名称或编号资料，不创建套接字、不连接远端，也不证明相应服务正在运行。

`<netdb.h>` 为不同类别定义了对应的结构和查询函数。名称列表都是以 NULL 指针结束的数组。

1. **主机 hostent：查主机名与 IP 地址。**Q10 解释了 hostent 字段和逐条读取方式。若要按名称或地址单独查一台主机，旧接口是 gethostbyname、gethostbyaddr。它们适合读懂旧代码；新程序应使用 getaddrinfo。比如连接 `example.com` 时，用 getaddrinfo 获取可连接的地址。

2. **网络 netent：查网络名称和网络编号。**

    ```c
    struct netent {
        char     *n_name;     /* 网络正式名称 */
        char    **n_aliases;  /* 网络别名列表 */
        int       n_addrtype; /* 地址族 */
        uint32_t  n_net;      /* 网络编号 */
    };

    struct netent *getnetbyname(const char *name);
    struct netent *getnetbyaddr(uint32_t net, int type);
    struct netent *getnetent(void);
    void setnetent(int stayopen);
    void endnetent(void);
    ```

    n_name 和 n_aliases 是网络名称。n_addrtype 表示网络编号所属的地址族，Linux 上是 AF_INET。n_net 是网络编号，不是某台主机的 IP，也不是端口。Linux 上 n_net 和 getnetbyaddr 的 net 参数使用主机字节序。需要查看旧式网络名与网络号映射时，按名称调用 getnetbyname，按编号调用 getnetbyaddr。本机 files 来源通常对应 `/etc/networks`。现代连接程序通常不需要查询它。

3. **协议 protoent：查协议名称和协议编号。**

    ```c
    struct protoent {
        char  *p_name;     /* 协议正式名称 */
        char **p_aliases;  /* 协议别名列表 */
        int    p_proto;    /* 协议编号 */
    };

    struct protoent *getprotobyname(const char *name);
    struct protoent *getprotobynumber(int proto);
    struct protoent *getprotoent(void);
    void setprotoent(int stayopen);
    void endprotoent(void);
    ```

    p_name 和 p_aliases 保存名称，p_proto 是 TCP、UDP 等协议的编号，不是服务端口。需要编写读取协议配置的诊断工具时，可把名称转换成协议记录，例如 `getprotobyname("tcp")`。反向查询使用 getprotobynumber。普通套接字程序通常直接使用 IPPROTO_TCP 等常量，不必查询协议库。本机 files 来源通常对应 `/etc/protocols`。

4. **服务 servent：查服务名称、传输协议和端口。**

    ```c
    struct servent {
        char  *s_name;     /* 服务正式名称 */
        char **s_aliases;  /* 服务别名列表 */
        int    s_port;     /* 网络字节序端口 */
        char  *s_proto;    /* 传输协议名称 */
    };

    struct servent *getservbyname(const char *name, const char *proto);
    struct servent *getservbyport(int port, const char *proto);
    struct servent *getservent(void);
    void setservent(int stayopen);
    void endservent(void);
    ```

    s_name 和 s_aliases 是服务名称，s_proto 通常是 `tcp` 或 `udp`，s_port 是网络字节序端口。需要把服务名解析为端口时，例如调用 `getservbyname("http", "tcp")`。反查 `80/tcp` 时可用 `getservbyport(htons(80), "tcp")`，因为 port 参数要求网络字节序。传入协议可以区分同号的 TCP 与 UDP 服务。Linux 上 proto 为 NULL 时可匹配任一协议。本机 files 来源通常对应 `/etc/services`。新程序需要同时解析主机和服务时，通常用 getaddrinfo。

5. **按名称查询与逐条遍历不同：**getnetbyname、getprotobynumber、getservbyport 等按给定键查匹配记录。get*ent 才是每次取下一条，set*ent 从第一条重新开始，end*ent 结束访问。顺序枚举是否可用取决于数据源。返回结构及其内部指针可能在后续查询时被覆盖。需要留存时要复制结构及其引用的数据，不能只复制结构，也不能对返回指针调用 free。

6. **组合连接地址：**旧接口分开查主机和服务。hostent 提供 IP 地址，servent 提供端口，程序还要选定地址族和协议，再填写 sockaddr_in 或 sockaddr_in6。getaddrinfo 可以把主机和服务合并查询，返回可供 socket 与 connect 使用的候选组合。

**Q12: [learning] IPPROTO 常量与套接字类型、服务端口有什么区别？**

IPPROTO 常量标识 IP 协议或套接字选项所处协议层，SOCK 常量选择交付类型，端口用来定位对应传输协议上的服务。三者不能相互替换。

1. **IPPROTO_TCP、IPPROTO_UDP：**分别表示 TCP（Transmission Control Protocol）与 UDP（User Datagram Protocol）。例如 IPv4 字节流通常选择 TCP，IPv4 数据报通常选择 UDP。
2. **IPPROTO_ICMP：**表示 IPv4 的 ICMP（Internet Control Message Protocol），它与错误报告和诊断有关，不是应用服务的端口号。
3. **IPPROTO_IP、IPPROTO_IPV6：**常用于 setsockopt 的 level，分别选择 IPv4、IPv6 协议层。不能因为它们出现在常量列表里，就认为都能作为任意 socket 组合的传输协议。
4. **IPPROTO_RAW：**在 Linux 原始 IPv4 套接字中有特殊发送语义，不是“自动接收所有 IP 协议”的开关。普通应用无须为使用 TCP/UDP 设置它。
5. **protocol 为 0：**请求为 domain 与 type 组合选择默认协议。这里的 0 是 socket 的参数约定，不表示服务端口为 0。

例如 TCP 与 UDP 可以使用相同数字端口，但由不同协议的端点接收。依据：socket(2)、ip(7)、raw(7)。









**Q13: [learning] htons、htonl、ntohs 和 ntohl 应在什么位置调用？**

在“主机中的数值”和“协议规定的网络序字段”交界处转换。发送前转成协议表示，接收后转回本机数值，不能把所有缓冲区一律反转。

```c
#include <arpa/inet.h>
uint16_t htons(uint16_t host16);
uint32_t htonl(uint32_t host32);
uint16_t ntohs(uint16_t net16);
uint32_t ntohl(uint32_t net32);
```

1. **名称和宽度：**h 表示 host，n 表示 network。s 对应 16 位，即 2 字节，l 对应 32 位，即 4 字节，不随当前平台 C 语言 long 的宽度变化。教材将 s 写成 4 字节属于文字错误。
2. **填写端口：**程序中的端口数值 8080 是主机序，写入 sockaddr_in.sin_port 时使用 htons(8080)。从这个字段打印端口时用 ntohs，否则小端主机会把字节位置解释反。
3. **发送整数：**协议若规定一个 32 位长度字段为网络序，先对长度调用 htonl，再发送其四个内存字节。接收方收齐四字节后调用 ntohl，才用它决定正文长度。
4. **不需要再次转换：**inet_pton 和 getaddrinfo 已产生符合地址接口要求的二进制地址，不能再把其中每个整数随意 hton。文本字符串也没有这种整数转换要求。
5. **不手工固定反转：**在大端主机上转换可能不改字节，在小端主机上才交换。无条件反转只能适配其中一种主机，使用这组函数才能表达“转换到指定字节序”的意图。









**Q14: [learning] 怎样填写 IPv4 的 sockaddr_in 地址？**

sockaddr_in 将地址族、IPv4 地址和端口组成一个端点。地址族按本机常量填写，地址与端口按网络字节序存储。

下面的完整程序只构造并打印端点，不创建连接：

```c
#include <arpa/inet.h>
#include <stdio.h>

int main(void) {
    struct sockaddr_in addr = {0};
    char text[INET_ADDRSTRLEN];
    addr.sin_family = AF_INET;
    addr.sin_port = htons(8080);
    if (inet_pton(AF_INET, "127.0.0.1", &addr.sin_addr) != 1)
        return 1;
    if (inet_ntop(AF_INET, &addr.sin_addr, text, sizeof(text)) == NULL)
        return 1;
    printf("%s:%u\n", text, (unsigned)ntohs(addr.sin_port));
    return 0;
}
```

1. **初始化为零：**让未使用字段和填充区有确定内容，之后仍须显式填写有效字段，清零不能代替设置地址族。
2. **sin_family = AF_INET：**声明这是 IPv4 地址，不能对该字段调用 htons。
3. **sin_port = htons(8080)：**服务端口是 8080，转成 16 位网络序。若保留零并用于 bind，则表示请求内核分配端口。
4. **sin_addr：**其 s_addr 成员保存 32 位地址。inet_pton 将环回地址文本写为二进制地址，所以不再调用 htonl。环回地址表示本机通信，不能拿它访问另一台主机。
5. **输出：**INET_ADDRSTRLEN 为 IPv4 地址文本连同结尾 NUL 提供容量，sizeof(text) 告诉 inet_ntop 实际容量。程序输出 `127.0.0.1:8080`，打印端口之前必须转回主机序。

端口需要与地址及传输协议一起理解。同一个数字端口可以分别用于 TCP 和 UDP，不能把它当成系统中唯一的进程编号。









**Q15: [learning] IPv6 的 sockaddr_in6 为什么还需要作用域信息？**

sockaddr_in6 除了容纳更长的 IPv6 地址，还能说明地址所属的作用域。对于链路本地地址，仅有地址文本可能无法确定应走哪个网络接口。

1. **sin6_family：**填写 AF_INET6，使内核按 IPv6 结构解释地址。
2. **sin6_port：**仍是 16 位网络序端口，使用 htons 和 ntohs，与地址从 32 位变为 128 位无关。
3. **sin6_addr：**保存 16 字节 IPv6 地址，可由 inet_pton(AF_INET6, ...) 或 getaddrinfo 填充，不能把冒号分隔的文本直接复制进去。
4. **sin6_scope_id：**Linux 对链路本地地址用接口索引标识链路。例如两张网卡所在链路都可能出现相同的链路本地地址，仅给地址不能区分目标在哪条链路上。
5. **sin6_flowinfo：**承载 IPv6 流信息。普通应用通常清零，不应把它当作端口或接口索引。

结构大小、字段位置以及部分字段支持情况按目标系统头文件和 ipv6(7) 核对，不把 IPv4 结构强行扩大后用于 IPv6。









**Q16: [learning] inet_pton 和 inet_ntop 怎样在地址文本与二进制地址之间转换？**

inet_pton 把数字形式的地址文本解析为网络序地址字节，inet_ntop 做反向格式化。它们只处理地址，不查询主机名，也不处理端口。

```c
#include <arpa/inet.h>
int inet_pton(int af, const char *src, void *dst);
const char *inet_ntop(int af, const void *src, char *dst, socklen_t size);
```

1. **解析方向：**af 为 AF_INET 时，dst 指向 in_addr。为 AF_INET6 时，指向 in6_addr。src 必须是对应格式的数字地址，传入主机名不会触发域名查询。
2. **解析结果：**inet_pton 返回 1 才能使用结果。返回 0 表示文本不符合地址格式，返回 -1 表示调用错误，例如不支持的地址族，并设置 errno。
3. **格式化方向：**inet_ntop 的 src 指向地址字节，dst 是调用者提供的字符缓冲区，size 是其容量。成功返回 dst，失败返回 NULL 并设置 errno。
4. **容量选择：**IPv4 使用 INET_ADDRSTRLEN，IPv6 使用 INET6_ADDRSTRLEN，容量包括字符串结尾。不能按二进制地址的 4 或 16 字节分配文本缓冲区。
5. **选择边界：**已有数字地址时用这组函数。输入可能是主机名、服务名，或希望同时获得多个地址族的连接候选时，用 getaddrinfo。旧 inet_addr、inet_ntoa 只适用于 IPv4，不是统一的双栈解析入口。









**Q17: [learning] 套接字地址查询？**

16.3.3 的核心是：**把人可读的名字转换为套接字接口可用的地址，也能把已有地址转回可读名称。**查询只准备地址信息，不替应用建立连接。这里的两个“名字”分别是：

1. **主机名：**例如 `example.com`，是网络目标的可读名称。查询后可得到一个或多个 IPv4、IPv6 地址，用来确定网络上的目标位置。它不是 IP 地址本身。
2. **服务名：**例如 `http`，是服务入口的可读名称。查询后可得到端口及对应的传输协议，常见映射为 `80/tcp`，用来确定目标主机上的访问入口。它不是远端进程名，映射存在也不证明服务正在运行。

应用最终把查得的地址指针及长度交给 connect（目标地址）或 bind（本地地址），无须自行拆解 IPv4、IPv6 结构。

按查询链路及旧接口的作用理解本节：

1. **还要确定通信方式。**IP、端口是地址信息，套接字是由 socket 创建的通信端点。若程序要 TCP 字节流，查询时须限定流式套接字和 TCP，不能仅凭主机名或服务名推断通信方式。
2. **查询来源由系统选择。**`/etc/hosts` 是本机“主机名 → IP”记录，DNS（Domain Name System，域名系统）可提供主机地址记录。`/etc/services` 是“服务名 → 端口/协议”记录，例如 `http → 80/tcp`。教材还提到 NIS（Network Information Service，网络信息服务）。这些是**数据来源**，不是应用必须逐个调用的 API。在 Linux/glibc 中，`/etc/nsswitch.conf` 等配置决定相应数据库使用哪些来源及查询顺序。数字 IP 或数字端口也可直接作为输入，无须再做对应的名称转换。
3. **旧接口按记录种类分开查。**早期 BSD 网络数据库接口使用 netdb.h 中的记录结构体，它们不是套接字地址。四类记录各回答一个问题：

    1. hostent：gethostbyname 或 gethostbyaddr 按名字或地址查主机。h_name 是正式名称，h_aliases 是别名，h_addrtype 与 h_length 说明地址族和每个地址的字节数，h_addr_list 保存网络字节序的二进制地址列表。不含服务端口。
    2. netent：getnetbyname 或 getnetbyaddr 查网络名与网络编号。n_name、n_aliases 保存名称，n_addrtype 说明地址族，n_net 是网络编号，不是某台主机的 IP。Linux 的 n_net 按主机字节序解释，不能照搬教材的“网络字节序”说法，依据见 getnetent(3)。
    3. protoent：getprotobyname 或 getprotobynumber 查协议名与编号。p_name、p_aliases 保存名称，p_proto 是 TCP 等协议的编号，不是端口。
    4. servent：getservbyname 或 getservbyport 查服务名、协议名与端口。s_name、s_aliases 保存名称，s_proto 区分 tcp、udp 等协议，s_port 是网络字节序端口。记录存在不表示服务正在运行。

4. **旧接口的遍历不是按名字查询。**以主机记录为例，sethostent 重置遍历，反复调用 gethostent 取得下一条，最后由 endhostent 结束。网络、协议、服务记录各有对应的 set/get/end 函数。stayopen 非零请求保持数据库连接，不表示结果永久有效。传统结果可能指向下一次调用就会被覆盖的静态存储，需长期保存时应复制内部引用的字符串和地址。数据来源未必真是一个打开的文件，gethostent 也不能枚举 DNS 中的所有主机。旧式连接代码还要把查得的主机地址与服务端口拼成套接字地址。gethostbyname、gethostbyaddr 已从 POSIX.1-2008 移除，新代码优先用 getaddrinfo、getnameinfo，依据见 gethostbyname(3)。
5. **新接口把主机和服务合在一次查询中。**getaddrinfo 接收 node（主机名或数字 IP）、service（服务名或数字端口）和可选的 hints 筛选条件，至少提供 node、service 之一。下面仅保留核心调用，省略头文件和错误处理，不是完整程序：

    ```c
    struct addrinfo hints = {0}, *res;
    hints.ai_family = AF_UNSPEC;
    hints.ai_socktype = SOCK_STREAM;
    hints.ai_protocol = IPPROTO_TCP;
    int rc = getaddrinfo("example.com", "http", &hints, &res);
    ```

    AF_UNSPEC 允许 IPv4、IPv6，SOCK_STREAM 限定字节流，IPPROTO_TCP 明确限定 TCP。清零使 ai_flags 为 0，表示不加额外解析标志。其余输出字段在 hints 中必须保持零或空指针。若省略 ai_family 或 ai_protocol 的赋值，它们仍为 0，表示不额外限制。省略 ai_socktype 则可能返回数据报等其他类型。这里显式写 AF_UNSPEC 是为表明接受两种 IP 地址族。服务器若以 node 为 NULL 并设置 AI_PASSIVE，可取得适合 bind 的通配地址。本客户端示例不需要。Linux/glibc 中直接传 NULL hints 的默认标志与这个清零模板并不完全相同，依据见 getaddrinfo(3)。
6. **结果是一组可尝试的组合。**仅当 rc 为 0 时，res 才指向 addrinfo 链表。每项的 ai_family、ai_socktype、ai_protocol 是调用 socket 的参数，ai_addr 与 ai_addrlen 是交给 bind 或 connect 的完整地址及长度，ai_next 指向下一项。ai_addr 是通用 sockaddr 指针，实际可指向 IPv4 或 IPv6 地址结构。应用只传递它，不必读取专用字段。一个主机名可能有多个地址，不限定类型的服务也可能同时产生 TCP、UDP 候选。教材的 `harry nfs` 在其测试机上就产生了流/TCP 与数据报/UDP 两项，不能据此推断所有机器的查询结果相同。下面的片段只示意如何使用当前候选 p，省略返回值检查和失败清理：

    ```c
    struct addrinfo *p = res;  // 已确认查询成功，示意首个候选
    int fd = socket(p->ai_family, p->ai_socktype, p->ai_protocol);
    connect(fd, p->ai_addr, p->ai_addrlen);
    ```

    实际连接时应逐项尝试，失败关闭本次 fd，再换下一项。用完调用 freeaddrinfo。getaddrinfo 失败时用 gai_strerror 解释其非零返回码，不直接交给 perror。若错误码为 EAI_SYSTEM，还需检查 errno。若设置 AI_CANONNAME，可在结果首节点的 ai_canonname 读取规范主机名。
7. **反向查询把地址变成人能读的文本。**getnameinfo 接收已有的 sockaddr 地址和长度，把主机、服务写入调用者提供的两个缓冲区。默认可能查询名称。设置 NI_NUMERICHOST、NI_NUMERICSERV 则分别要求数字 IP 和数字端口，避免相应的名称查询。它用于展示或记录地址，不负责建立连接。失败时同样使用 gai_strerror 解释返回码。

8. **复用地址处理代码有前提。**应用不依赖某个协议的专用字段，且候选提供相同类型的通信服务。例如同一段候选遍历代码可尝试 IPv4、IPv6 的 TCP 地址，但不会自动把 TCP 程序变成 UDP 程序。
9. **UNIX 域不走上述 IP 名称解析链路。**它通常直接用 sockaddr_un 的本机路径寻址，无须查 IP 或端口。Linux 也支持抽象地址。socketpair 甚至不需要地址。








**Q18: [learning] 地址查询怎样隔离地址结构与信息来源？**

“隔离”有两层：**应用不必自己拆解每种地址结构**，也**不必写死查询数据来自哪个文件或服务器**。例如同样是连接 TCP 服务，IPv4 与 IPv6 候选可由同一段代码处理，但必须使用每个候选自己的地址族和长度。

1. **地址结构交给查询结果：**getaddrinfo 返回 addrinfo 候选。每项的 ai_family、ai_socktype、ai_protocol 用来创建 socket，ai_addr 是指向具体地址结构的通用 sockaddr 指针，ai_addrlen 是该结构的字节长度。应用把这对地址参数原样交给 connect，无须把 IPv6 强转为 sockaddr_in，也无须读取 IP 字段。
2. **数据来源交给名称服务：**`/etc/hosts` 可记录“主机名 → IP”，`/etc/services` 可记录“服务名 → 端口/协议”。主机名还可能从 DNS（Domain Name System，域名系统）查询。书中的 NIS（Network Information Service，网络信息服务）是另一类可配置来源。在 Linux/glibc 中，名称服务开关（NSS，Name Service Switch）按 `/etc/nsswitch.conf` 选择各类记录的查询来源和顺序，依据见 nsswitch.conf(5)。应用仍调用同一接口，结果、耗时及是否需要网络查询则可能不同。
3. **从旧接口到统一入口：**早期 BSD 接口把主机、服务等记录分开查询，例如 gethostbyname 和 getservbyname，程序还得自行拼地址。getaddrinfo 合并主机与服务，返回可直接用于建套接字和连接的候选。getnameinfo 则把已有地址反向表示为主机与服务文本。
4. **按完整链路理解：**

    ```text
    主机名 + 服务名
         ↓ getaddrinfo（按系统配置查询名称与服务记录）
    候选链表：[候选 1] ──ai_next──▶ [候选 2] ...
         ↓ 应用从首节点开始逐项尝试
    socket(地址族, 类型, 协议) → connect(fd, 地址指针, 长度)
    ```

    链表中的候选是**可以尝试的地址组合**，不是已经建立的连接，也不证明目标服务正在运行。若程序要读取或修改 IPv6 专有字段，或改用与 TCP 不同的 UDP 收发规则，仍需处理协议相关细节。







**Q19: [learning] /etc/hosts、DNS、/etc/services 分别是什么？**

`/etc/hosts` 和 DNS 都可回答“主机名对应哪个 IP 地址”；`/etc/services` 回答“服务名对应哪个端口和传输协议”。前两者定位主机，后者确定访问该主机时要用的端口。

1. **本机静态主机名表：**`/etc/hosts` 一行可写 `127.0.0.1 localhost`，表示把 localhost 解析为本机回环地址。它由本机维护，不会自动成为其他机器的配置。
2. **DNS（Domain Name System，域名系统）：分布式的名称查询系统。**解析器可向 DNS 查询主机名的 A（IPv4）或 AAAA（IPv6）记录，取得 IP 地址。它查询的是名称记录，不负责建立到目标服务的连接。
3. **本机服务名称表：**`/etc/services` 一行如 `https 443/tcp`，表示服务名 https 对应 TCP 端口 443。这里的 tcp 用于区分传输协议。表里有这条记录，不代表 443 端口上正在运行服务。

例如调用 `getaddrinfo("example.com", "https", ...)` 时，系统可按本机名称服务配置从 `/etc/hosts` 或 DNS 等来源查主机地址，再把 https 查成端口和协议，组合出套接字地址候选。**不固定先查 hosts 再查 DNS**：Linux/glibc 的实际来源和顺序由 `/etc/nsswitch.conf` 等配置决定。








**Q20: [learning] getaddrinfo 怎样把主机和服务解析成可用的连接候选？**

getaddrinfo 把“主机名或 IP”与“服务名或端口”合成**可用的连接或绑定候选**。每个候选包含创建 socket 所需的地址族、类型、协议，以及传给 connect/bind 的完整地址和长度。查询不会替应用创建目标套接字，也不保证远端有服务正在运行。一个名字可能对应多个 IP，同一服务也可能同时有 TCP、UDP 记录，所以结果是链表，不保证只有一项。

```c
#include <sys/socket.h>
#include <netdb.h>
int getaddrinfo(const char *node, const char *service,
                const struct addrinfo *hints, struct addrinfo **res);
void freeaddrinfo(struct addrinfo *res);
const char *gai_strerror(int errcode);
```

同一类型 addrinfo 既可用作输入筛选模板，也可作为输出节点。以下是关键字段摘录，不需要在应用中重新定义：

```c
struct addrinfo {
    int              ai_flags;
    int              ai_family;
    int              ai_socktype;
    int              ai_protocol;
    socklen_t        ai_addrlen;
    struct sockaddr *ai_addr;
    char            *ai_canonname;
    struct addrinfo *ai_next;
};
```

按一次客户端查询理解四个参数：

1. **node：**主机名或数字 IP，例如 `"example.com"` 或 `"192.0.2.10"`。它回答“要找哪台主机”。
2. **service：**服务名或数字端口字符串，例如 `"http"` 或 `"80"`。它回答“要找该主机上的哪个端口”。服务名查询是查名称映射，不是向服务端发送请求。
3. **hints：**可选的筛选模板，告诉函数需要什么地址族、套接字类型、协议或解析行为。使用时先清零，再填写需要限制的字段：

    1. ai_family 限制地址族。AF_UNSPEC 表示 IPv4/IPv6 都可。
    2. ai_socktype 限制套接字类型。SOCK_STREAM 只要流式候选。
    3. ai_protocol 限制具体协议。0 表示不额外限制。
    4. ai_flags 控制解析方式，例如是否生成适合 bind 的地址。

    ai_addr、ai_canonname、ai_next 是结果字段，在输入模板中置为 NULL；其余未使用的整数字段置为 0。`hints == NULL` 时，POSIX 规定的默认标志与 Linux/glibc 实际采用的默认标志不同，因此需要明确筛选时应传入初始化过的模板。
4. **res：**这是输出参数，类型是“指向 addrinfo 指针的指针”。成功时函数把结果链表头写入 `*res`。每个节点提供一套可尝试的参数：ai_family、ai_socktype、ai_protocol 可传给 socket；ai_addr 和 ai_addrlen 是完整套接字地址及其长度，可传给 connect 或 bind；ai_next 指向下一个候选。若请求 AI_CANONNAME，规范主机名通常放在首节点的 ai_canonname。

查询至少要提供 node、service 中的一个，不能两者都为 NULL。函数返回 0 表示成功，非零值是 EAI_* 错误码。它只生成候选，不创建套接字，也不保证远端地址可达或服务正在运行。

使用候选时沿 ai_next 逐项尝试。每项的三个 socket 参数必须来自同一个节点，不能把一个候选的地址与另一个候选的协议拼起来。失败后关闭本次创建的 fd，再尝试下一项。查询成功后，使用完毕调用 freeaddrinfo 释放整条链表，之后不再访问其中的指针。查询失败时用 gai_strerror 解释返回码，不能直接交给 perror；若返回 EAI_SYSTEM，再检查 errno。

下面是核心调用形态，省略头文件、候选连接循环和错误处理：

```c
struct addrinfo hints = {0};
struct addrinfo *res = NULL;

hints.ai_family = AF_UNSPEC;
hints.ai_socktype = SOCK_STREAM;
hints.ai_protocol = IPPROTO_TCP;

int err = getaddrinfo("example.com", "http", &hints, &res);
/* err == 0 时遍历 res，使用后调用 freeaddrinfo(res) */
```

这里 node 是主机名，service 是服务名。AF_UNSPEC 接受 IPv4 和 IPv6，SOCK_STREAM 与 IPPROTO_TCP 限定为 TCP 流式候选。hints 被清零，所以 ai_flags 为 0，不附加特殊解析要求。若返回成功，res 指向一条候选链表；并不意味着已经连接成功。

教材测试机的输出可这样读，IP 换成文档示例地址。箭头 `ai_next` 只表示链表顺序：

```text
输入：主机 harry + 服务 nfs
  ↓ getaddrinfo
候选 1：192.0.2.10:2049 + SOCK_STREAM + TCP
  ↓ ai_next
候选 2：192.0.2.10:2049 + SOCK_DGRAM  + UDP
```

这是**两个通信方式候选**，不是两台主机，也不证明两种服务都在运行。其他机器的名称配置可能给出不同结果。







**Q21: [learning] getaddrinfo 的解析标志怎样改变结果？**

ai_flags 控制“怎样生成候选”，不负责建连。选择标志应对应调用者准备把结果用于 bind、connect 还是展示名称。

1. **AI_PASSIVE：**node 为 NULL 时产生适合本地 bind 的通配地址。不设置它时，NULL node 通常产生环回地址，适合连接本机服务。有明确 node 时，该标志不会把给定地址自动改成通配地址。
2. **AI_NUMERICHOST、AI_NUMERICSERV：**分别要求主机参数为数字地址、服务参数为数字端口。它们限制输入并避免对应名称查询，不会将无效名字自动变为数字。
3. **AI_CANONNAME：**请求规范主机名，结果放在首节点的 ai_canonname。node 必须提供主机名或地址，不能为 NULL。它是名称解析结果，不是对端身份认证。
4. **AI_ADDRCONFIG：**按本机配置的 IP 地址族筛选候选。Linux/glibc 不把环回地址算作此处的有效配置，因此只有环回接口的环境可能得不到预期结果。
5. **AI_V4MAPPED：**当 ai_family 为 AF_INET6 且未找到 IPv6 地址时，允许把 IPv4 结果表示为 IPv4 映射的 IPv6 地址。它不把远端服务器改造成原生 IPv6 服务。
6. **AI_ALL：**与 AI_V4MAPPED 配合，请求同时保留 IPv6 结果和映射后的 IPv4 结果，单独设置不能表达同样效果。

Linux/glibc 对 hints 为 NULL 的默认标志与“显式清零的 hints”不完全相同。若需要明确控制候选，提供已初始化的 hints，不靠省略参数猜测默认行为。依据：getaddrinfo(3)。









**Q22: [learning] getnameinfo 怎样把套接字地址用于日志和名称展示？**

getnameinfo 做与 getaddrinfo 相反方向的转换：输入**已存在的完整因特网套接字地址**，分别输出主机和服务文本。它比只转换 IP 字段的 inet_ntop 多处理了端口，也可查询名称。它不建立连接。日志通常指定数字输出，以免为了记录连接而等待名称查询。

```c
#include <netdb.h>
int getnameinfo(const struct sockaddr *addr, socklen_t addrlen,
                char *host, socklen_t hostlen,
                char *serv, socklen_t servlen, int flags);
```

1. **输入地址：**addr 和 addrlen 必须来自同一个完整端点，例如 accept 返回的地址。函数根据地址族解释地址和端口。
2. **输出缓冲区：**host、serv 分别接收主机文本和服务文本，hostlen、servlen 分别是对应缓冲区的字节容量。只需要其中一个结果时可以省略另一个，不能把两种长度混用。成功写入的字符串以空字符结尾，容量不足会返回错误。
3. **数字日志：**NI_NUMERICHOST 输出数字 IP，NI_NUMERICSERV 输出数字端口，两者按位或组合。serv 表示服务，不是另一个主机名。
4. **名称展示：**不强制数字输出时可能执行反向名称查询。NI_NAMEREQD 要求找到主机名，否则报错。NI_NOFQDN 可要求本地主机的短名称。NI_DGRAM 表示按数据报服务解释端口，避免把同一端口的 UDP 服务当成 TCP 服务。
5. **结果处理：**成功返回 0，错误码用 gai_strerror 解释。若错误为 EAI_SYSTEM，还要检查 errno。名称查询成功不证明对端身份可信，缓存、名称配置和实际持有连接的进程是不同对象。

下面的代码片段假设 addr 和 addrlen 已指向有效的套接字地址，展示如何生成适合日志的数字地址。它省略了错误处理：

```c
char host[NI_MAXHOST];
char serv[NI_MAXSERV];

int err = getnameinfo(addr, addrlen,
                      host, sizeof(host),
                      serv, sizeof(serv),
                      NI_NUMERICHOST | NI_NUMERICSERV);
```

NI_MAXHOST 和 NI_MAXSERV 分别提供足以保存主机文本与服务文本的缓冲区容量。调用成功后，host 是数字 IP，serv 是数字端口。若只需要主机，可将 serv 设为 NULL 并把 servlen 设为 0。

例如，输入装有 `127.0.0.1:8080` 的 sockaddr，并同时设置 NI_NUMERICHOST、NI_NUMERICSERV，host 得到 `"127.0.0.1"`，serv 得到 `"8080"`。不设置数字标志时，名称取决于当前名称服务配置，不能假定一定返回 `"localhost"` 或某个服务名。









**Q23: [learning] bind 怎样确定本地地址，通配地址和端口 0 各是什么意思？**

bind 把一个本地地址关联到套接字。服务端通常需要明确入口，客户端通常可让内核选择本地地址和临时端口。

```c
#include <sys/socket.h>
int bind(int sockfd, const struct sockaddr *addr, socklen_t addrlen);
```

1. **输入与结果：**sockfd 是待绑定套接字，addr 是同一地址族的本地地址，addrlen 是该地址长度。成功返回 0，失败返回 -1 并设置 errno。成功绑定不等于开始监听。
2. **指定本机地址：**例如绑定某张网卡的地址，服务只在该本地地址接收。通常不能绑定不属于本机的任意地址，特殊系统选项另有规则。
3. **通配地址：**IPv4 的 INADDR_ANY、IPv6 的未指定地址表示接受适用本地地址上的通信。它不是某个远端目标，也不保证外部一定可达，实际还受路由和访问策略影响。
4. **环回地址：**绑定 127.0.0.1 或 ::1 限定本机访问，适合本地服务。它与“绑定所有本地接口”不同。
5. **端口选择：**固定端口便于客户端找到服务。端口 0 请求内核分配可用端口，随后调用 getsockname 查询实际值，并另行告知客户端。
6. **失败判断：**EADDRINUSE 常表示地址组合冲突，EADDRNOTAVAIL 常表示地址不可用，EACCES 可能涉及权限。教材的低于 1024 端口限制是传统规则，Linux 还受能力和系统配置影响，不能简单写成只有 root 才能绑定。









**Q24: [learning] getsockname 与 getpeername 的地址长度参数怎样使用？**

getsockname 查询本地端点，getpeername 查询已关联的对端。调用者提供存储，长度参数先传容量，返回后再按实际长度和地址族解释。

```c
#include <sys/socket.h>
int getsockname(int sockfd, struct sockaddr *addr, socklen_t *addrlen);
int getpeername(int sockfd, struct sockaddr *addr, socklen_t *addrlen);
```

1. **调用前：**准备 sockaddr_storage，并令 socklen_t 变量等于它的 sizeof。将结构地址和长度变量地址传入，不能把未初始化的长度交给内核。
2. **调用后：**返回 0 才读取结果。若实际地址长度大于提供容量，说明输出没有完整装下，应处理截断，不能盲目把地址当成字符串。
3. **本地查询场景：**bind 端口 0 后取得分配端口，或 connect 后查看内核选出的本地 IP 和端口。尚未选定的本地地址可能仍表现为未指定地址。
4. **对端查询场景：**已连接 TCP 套接字可取得远端端点，connect 过的 UDP 套接字可取得默认对端。未关联对端时会失败，不会返回“最近一个发来数据报的人”。
5. **输出给人看：**把返回的 sockaddr 交给 getnameinfo，或按地址族使用 inet_ntop，并把端口从网络序转换回来。地址反映通信端点，不直接表示用户身份。









**Q25: [learning] TCP connect 成功说明什么，失败后怎样重试？**

阻塞式 connect 成功说明 TCP 连接已建立，可以开始收发，不说明服务端已执行 accept、已读请求或已完成业务。失败后的可移植重试方式是关闭当前套接字，再创建新套接字。

```c
#include <sys/socket.h>
int connect(int sockfd, const struct sockaddr *addr, socklen_t addrlen);
```

1. **发起连接：**addr 是远端地址，addrlen 是它的长度。未提前 bind 时，内核会选择合适的本地地址和临时端口，并发起 TCP 建连。
2. **判断结果：**成功返回 0。返回 -1 时检查 errno，例如 ECONNREFUSED 表示连接被拒绝，ETIMEDOUT 表示建连超时。错误原因不能统一解释成“服务器进程不存在”。
3. **重建套接字：**真正连接失败后的状态不可按跨平台统一规则重用。教材改进版 connect_retry 在每次尝试中重新 socket，成功返回新 fd，因此辅助函数不再只是返回 0 或 -1。
4. **退避重试：**服务可能尚未启动时，间隔按 1、2、4 等秒数递增可避免忙循环。参数错误或权限问题通常需要修正条件，重复调用本身不会解决。
5. **限制总等待：**sleep 的累计时间不等于全过程时限，因为每次 connect 本身也可能等待。需要严格截止时间时，要控制连接阶段本身，而不只限制重试次数。









**Q26: [learning] UDP 调用 connect 后，收发方式改变了什么？**

UDP connect 在本地记录默认对端，并限制接收来源，不执行 TCP 握手，也不增加可靠传输保证。

1. **未 connect：**每次 sendto 传目的地址，recvfrom 取得当前数据报的来源。同一个套接字可以先后与不同对端交换报文。
2. **connect 之后：**可以使用 send 或 write，因为内核已经知道默认目的地址。recv 或 read 只接收匹配该关联对端的报文，具体规则以目标系统为准。
3. **成功的含义：**通常只是本地关联设置完成，远端可能没有服务运行。问题可能在后续发送或接收时以异步错误暴露，也可能表现为一直等不到响应。
4. **不变的语义：**每次发送仍是一条数据报，接收仍有报文边界，仍需按业务需要处理丢失、重复和乱序。不能因函数名是 connect 就套用 TCP 的 EOF 和连接可靠性。

例如只与一个固定服务器通信的 UDP 客户端可以 connect 后简化收发。面向多个客户的 UDP 服务通常保留 recvfrom/sendto，以便按每条请求的来源回复。









**Q27: [learning] listen 与 accept 为什么需要两个不同的套接字？**

监听套接字负责接入新连接，accept 返回的连接套接字负责与某个客户端收发。这样服务端处理已有客户端时，仍能接受新的客户端。

```c
#include <sys/socket.h>
int listen(int sockfd, int backlog);
int accept(int sockfd, struct sockaddr *addr, socklen_t *addrlen);
```

1. **进入监听：**服务端通常先 socket、bind，再 listen。listen 成功返回 0，把支持连接的套接字变为被动接入端点，不在这个 fd 上接收客户端业务正文。
2. **排队等待：**backlog 是待接收连接队列的请求上限，不是服务器一生或同时能服务的客户端总数。Linux 2.2 以后的 TCP listen 主要限制已完成握手、尚未 accept 的队列，未完成握手队列另有控制。
3. **取出连接：**accept 成功返回新 fd，原监听 fd 不变。客户端地址写到 addr，addrlen 先给容量再返回长度。不需要地址时可把两个参数都传 NULL。
4. **无连接可取：**阻塞 accept 等待，非阻塞 accept 返回 -1，errno 为 EAGAIN 或 EWOULDBLOCK。监听 fd 可读意味着应尝试 accept，不意味着可直接 recv 业务数据。
5. **处理与关闭：**客户端 A、B 分别对应两个连接 fd。关闭 A 的 fd 不影响继续 accept B。关闭监听 fd 也不自动关闭已经取得的连接 fd。
6. **队列满：**客户端可能被拒绝，也可能等待重传后才建立连接，不能把 backlog 满写成必然立即报错。实际行为受协议和内核配置影响。









**Q28: [learning] 怎样把解析、socket、bind 和 listen 组合成服务器初始化？**

服务器初始化的输出应是可用的监听 fd，失败时应清理本次创建的资源。解析得到多个地址时，还要明确是“选一个入口”还是“同时开放多个入口”。

1. **取得地址：**用 getaddrinfo 指定服务端口、套接字类型及所需地址族。希望绑定通配地址时，node 为 NULL 并指定 AI_PASSIVE。
2. **逐项创建：**每个候选都用它自己的 family、type、protocol 创建 socket。需要影响绑定的选项，例如 SO_REUSEADDR，应在 bind 前设置。
3. **绑定与监听：**用该项的 ai_addr 和 ai_addrlen 调用 bind。SOCK_STREAM 或支持的 SOCK_SEQPACKET 再调用 listen，数据报服务无需这一步。
4. **失败回收：**某一步失败就保存 errno，close 本次 fd，再继续尝试或返回错误。保存 errno 是为了防止清理操作覆盖真正的失败原因。
5. **多个入口：**教材 initserver 返回一个 fd，ruptime 服务在首个成功候选上进入服务循环，因此不等于监听所有解析结果。需要同时提供 IPv4 和 IPv6 等入口时，应保留所需的多个监听 fd，统一等待各自的接入事件。
6. **结束解析：**所有所需地址使用完毕后 freeaddrinfo。监听 fd 和地址链表是两类资源，不能只释放其中一种。









**Q29: [learning] send、sendto 与 sendmsg 应怎样选择？**

三者都发送数据，区别在于需要额外描述什么。已有对端且正文连续时用 send，每次需要指定目的地址时用 sendto，需要多段正文或辅助数据时用 sendmsg。

```c
#include <sys/socket.h>
ssize_t send(int fd, const void *buf, size_t len, int flags);
ssize_t sendto(int fd, const void *buf, size_t len, int flags,
               const struct sockaddr *dest, socklen_t destlen);
ssize_t sendmsg(int fd, const struct msghdr *msg, int flags);
```

1. **共同参数：**fd 指定发送端点，buf 和 len 给出正文起始位置和字节数，flags 选择本次发送行为。flags 为 0 表示不额外启用发送标志。成功返回本次接受的正文长度，失败返回 -1 并设置 errno。
2. **send：**从套接字的连接或关联状态取得对端。TCP 建连后、UDP 设置默认对端后都可使用。flags 为 0 时，其基本发送语义与 write 相同。
3. **sendto：**dest 与 destlen 指定本次目的地址，适合未 connect 的数据报端点。对已连接的流端点，不用这两个参数切换对端。目的地址被忽略或引发错误的细节依平台而定。
4. **sendmsg：**msg 将正文缓冲区、可选地址和控制消息组织在一起。多个正文缓冲区不等于发送多条数据报，它们按顺序组成同一次发送的正文。

声明展示的是调用接口，不是完整程序。选择接口不会改变底层套接字类型的消息边界或可靠性。









**Q30: [learning] send 成功后，怎样判断发送进度和对端处理进度？**

send 的正返回值只说明本次有这么多正文交给了本地发送机制，不能证明对端应用已读取或处理。字节流还必须依据实际返回值推进发送位置。

1. **短写：**请求发送 1000 字节却返回 300，下一次应从偏移 300 继续发送剩余 700 字节。重发全部会重复数据，只调用一次会遗漏数据。阻塞模式也不能省略这个判断。
2. **暂时无法发送：**非阻塞调用返回 EAGAIN 或 EWOULDBLOCK 时，保留尚未发送的数据，等待可写后继续。可写不保证剩余的所有字节都能一次写完。
3. **信号与错误：**返回 -1 且 errno 为 EINTR 时，没有报告正的发送进度，应按程序的取消策略决定是否重试。其他错误可能意味着连接不可再用，不能无条件循环。
4. **业务完成：**对端 TCP 确认的是其协议栈接收情况。若要确认文件落盘、订单执行等结果，应由应用协议返回相应结果。连接断开后重试请求，还要处理“服务已执行但响应丢失”的重复执行问题。
5. **数据报限制：**一条报文过大可能以 EMSGSIZE 失败。不能照搬字节流的短写循环，把剩余部分作为另一条数据报发送，除非应用协议本来就定义了分片。









**Q31: [learning] 发送标志怎样改变一次 send 的行为？**

flags 只选择本次调用的行为，不能代替套接字类型和应用协议。多个支持的标志可以按位或组合，使用前需确认平台及协议支持。

1. **MSG_DONTWAIT：**Linux 上使本次发送不等待缓冲空间。与 O_NONBLOCK 的区别是作用范围仅限本次调用，不改变共享打开文件描述上的状态。
2. **MSG_NOSIGNAL：**Linux 上抑制本次发送引起的 SIGPIPE，仍通过 EPIPE 报告错误。未处理的 SIGPIPE 默认可终止进程，所以屏蔽信号后仍须检查返回值。
3. **MSG_DONTROUTE：**请求不经网关路由，适用于支持此语义的路由协议，常用于本地链路诊断。它不是绕过网络权限检查。
4. **MSG_EOR：**标明记录结束，只有支持记录语义的协议才有相应意义。不能用它给 TCP 自动增加消息边界。
5. **MSG_OOB：**请求发送协议支持的带外数据。TCP 的紧急数据有专门语义，不能据此承诺一条独立的可靠高优先级通道。

不设置某标志就沿用套接字及协议的普通行为，例如未设 MSG_DONTWAIT 时是否阻塞还取决于 O_NONBLOCK。依据：Linux send(2)。









**Q32: [learning] recv 的返回值和接收标志怎样一起解释？**

recv 从接收队列取出数据，返回值表示本次读取结果，flags 改变读取方式。必须先区分流与数据报，再解释 0、短读和等待行为。

```c
#include <sys/socket.h>
ssize_t recv(int fd, void *buf, size_t len, int flags);
```

1. **参数：**fd 是接收端点，buf 是调用者提供的存储，len 是最多可写入的字节数。flags 为 0 表示普通接收。返回正数时，只能处理 buf 中前这么多字节，函数不会自动补字符串结尾。
2. **流上的 0：**在 len 大于 0、未自行关闭读方向的正常场景下，表示对端有序结束发送且排队数据已读完。连接仍开放但暂时没数据时，阻塞调用等待，非阻塞调用返回 EAGAIN 或 EWOULDBLOCK。
3. **数据报上的 0：**可能成功读到一个零长度报文，不能解释成 TCP 式 EOF。len 为 0 的调用也不能用来判断对端生命周期。
4. **MSG_PEEK：**查看队列中的数据但不消费。连续 peek 可能反复看到同一批数据，因此它不负责推进业务解析。
5. **MSG_WAITALL：**在适用的流上尽量等到请求长度，但遇到信号、错误或断连仍可能少返回。它也不知道业务消息长度，长度填错仍会等待或读入下一条消息。
6. **MSG_DONTWAIT：**Linux 上让本次读取不阻塞，无数据时用错误码报告。它不能保证本次一定读到数据。

流式读取默认可在已有部分数据时返回，不能把缓冲区容量理解成“内核保证凑齐的消息长度”。









**Q33: [learning] recvfrom 如何取得数据报来源并正确回复？**

recvfrom 同时接收一条报文和其源地址。服务器应把本次请求与本次源地址一起保存，再用 sendto 回复，不能依赖一个被下一次接收覆盖的公共地址变量。

```c
#include <sys/socket.h>
ssize_t recvfrom(int fd, void *buf, size_t len, int flags,
                 struct sockaddr *src, socklen_t *srclen);
```

1. **正文：**buf、len、flags 与 recv 的含义一致。返回值是正文长度，不包括地址长度。
2. **来源存储：**src 指向可容纳地址的缓冲区，srclen 指向长度变量。每次接收前把该变量恢复为实际缓冲区容量，调用后它变成源地址的长度。
3. **回复：**将本次地址与返回长度原样交给 sendto。地址族未知时可用 sockaddr_storage，不应固定假定所有客户端都使用 IPv4。
4. **不需要来源：**src、srclen 可以都传 NULL，但随后便不能凭这次调用得知应回复谁。已关联固定对端的套接字可使用 recv。
5. **并发处理：**工作线程或异步任务需要持有自己的地址副本和正文副本。收到客户端 A 后又接收 B，若地址变量被覆盖，A 的响应就可能误发给 B。

收到源地址只提供回复位置，不构成对用户身份的认证。









**Q34: [learning] msghdr 如何组织正文、地址与辅助数据？**

msghdr 是 sendmsg/recvmsg 的消息描述结构，分别描述普通正文、可选端点地址与控制信息。它本身是本地调用参数，不作为一个 C 结构原样发送给对端。

按字段承担的作用理解：

1. **msg_name、msg_namelen：**发送时提供可选目的地址和长度，接收时提供来源地址缓冲区和容量。已连接流通常将它们置为 NULL 和 0。
2. **msg_iov、msg_iovlen：**指向 iovec 数组并给出元素数。每个 iovec 的 iov_base 指向一段正文，iov_len 是该段字节数。例如协议头和正文分开存储时，可用两个元素按顺序发送，避免先在用户态拼成一个大数组。
3. **msg_control、msg_controllen：**指向辅助数据区域并给出长度。发送时放准备好的控制消息，接收时先给容量。接收后该长度反映返回的控制数据量。无需辅助数据时置为 NULL 和 0。
4. **msg_flags：**recvmsg 返回消息特征的位置，调用前的值不用于选择接收方式。控制本次行为应使用 recvmsg 的独立 flags 参数。sendmsg 不以这个成员选择发送标志。
5. **重复接收：**msg_namelen 和 msg_controllen 是输入输出字段，每次调用前须重置容量。否则上次较短结果可能令下次控制区或地址区被错误截短。

多个 iovec 只是在内存中分散，不能据此宣称零拷贝。返回值计数普通正文，不把辅助数据字节加进去。各字段的具体 C 类型以系统头文件为准。









**Q35: [learning] 数据报被截断后，为什么不能再读剩余部分？**

数据报接收以报文为单位。一次接收的正文缓冲区不足时，通常只保留装得下的部分，其余部分被丢弃，下一次读取会处理下一条报文。

1. **具体例子：**发送一条 100 字节报文，接收方只给 60 字节容量，读到前 60 字节不意味着还可再读余下 40 字节。应用应按协议允许的最大报文配置容量或拒绝截断结果。
2. **MSG_TRUNC：**recvmsg 的输出 msg_flags 可报告正文截断。Linux 对部分数据报协议还允许输入 MSG_TRUNC，使返回值报告原报文长度。此时返回值可能大于实际缓冲区，不能按返回值越界访问 buf。
3. **MSG_CTRUNC：**报告辅助数据截断，不能与正文截断混为一谈。普通正文完整不代表文件描述符等控制消息也完整。
4. **MSG_EOR：**在支持记录语义的套接字上表示记录结束。它不是所有 TCP 接收都应检查的业务帧结束标志。

如果应用把多条 UDP 报文组合成一条业务消息，编号、重组与缺片检测属于应用协议，和一次接收的截断补救是两回事。









**Q36: [learning] TCP 应用怎样从连续字节中识别完整消息？**

TCP 只交付有序字节，业务协议必须约定边界，并在多次接收之间保存未完成的数据。读到多少由本次接收结果决定，消息有多长由协议决定。

按协议形式处理：

1. **固定长度：**每条记录都为 N 字节，累计到 N 才交给业务。接收不足就继续等，剩余字节留给下一条。
2. **长度前缀：**先收齐定长头部，按约定字节序解出正文长度，检查上限后再累计正文。不能先按未经检查的长度分配任意大小内存。
3. **分隔符：**持续累计直到找到约定符号，并明确正文中出现同一符号时如何转义。一次 recv 可能含两条消息，也可能只含半条。
4. **以 EOF 结束：**一条请求或响应占用整个发送方向，读到有序结束才完整。发送方必要时用 shutdown(SHUT_WR) 通知结束并保留反向接收能力。此方式不适合在同一方向继续发送下一条消息。

例如两次发送 ABC、DEF，接收方可能读到 AB 和 CDEF。若协议规定每条 3 字节，解析器应产出 ABC、DEF。MSG_WAITALL 和增大缓冲区都不能替代这个协议判断。









**Q37: [learning] TCP 版 ruptime 怎样把命令输出送到客户端？**

教材的 ruptime 是一次连接返回一次 uptime 输出的服务。客户端循环接收至 EOF，服务端关闭该连接来表示响应结束，因而连接生命周期就是这次响应的边界。

1. **客户端解析：**getaddrinfo 查服务地址，逐个候选尝试创建并连接，失败候选的 fd 要关闭。服务名称必须有对应配置，解析成功并不代表服务器已启动。
2. **服务端初始化：**取得主机名并解析服务地址，在可用候选上 bind、listen。教材选择首个成功入口，不能据此推断它同时覆盖所有网卡及地址族。
3. **接收请求：**accept 得到连接 fd。服务只有一种操作，建立连接就足以触发执行，所以客户端无需再发送一条命令正文。
4. **生成响应：**服务端通过 popen 运行 uptime，从命令输出管道读取文本，再通过连接 fd 发送。实际实现仍应处理短写、命令失败和连接错误。
5. **结束响应：**服务端完成输出并关闭连接，客户端 recv 循环读完剩余字节后得到 0，再关闭自己的 fd。一次 recv 不能保证取得整段文本。

gethostname 的输出还需确认缓冲区容量与终止符，不能把示例的一个固定长度当成所有平台的最大值。服务若改为保持连接，必须另外定义响应长度或分隔符。









**Q38: [learning] dup2 为什么能让普通命令直接向套接字输出？**

程序向标准输出写入时使用的是 fd 1，不要求底层对象一定是终端。子进程用 dup2 将已连接套接字接到标准输出和标准错误后，exec 出来的命令便可直接把输出发给客户端。

1. **建立继承：**父进程 accept 后 fork，父子都引用连接端点。子进程关闭不用的监听引用，保留本次连接。
2. **重新接线：**子进程把连接 fd 复制到 STDOUT_FILENO 和 STDERR_FILENO，标准输入接到 /dev/null 或明确安排的输入源。两个标准输出方向引用同一个连接端点。
3. **执行命令：**exec 替换进程程序，但保留未被 FD_CLOEXEC 关闭的描述符。命令照常 write 标准输出，内核实际执行套接字发送。
4. **释放多余引用：**dup2 完成后关闭不再需要的原 fd，父进程也关闭自己的连接引用。父进程关闭不会提前破坏子进程持有的端点，但若忘记关闭会延迟客户端看到 EOF。
5. **处理并发：**教材父进程等待当前子进程结束后才继续 accept，虽然使用了 fork，服务仍按请求串行。若要并发，需继续接入并独立回收子进程，同时限制资源使用。

相比 popen 后由父进程转发，这种方式省掉了父进程的中转循环。它也意味着子进程的标准错误会传给远端，输出范围应符合服务协议。









**Q39: [learning] UDP 版 ruptime 为什么要先发送请求并设置等待期限？**

UDP 没有连接到达事件供服务器触发服务。客户端必须发送一个请求报文，服务器从报文取得回复地址，客户端还需限制等待响应的时间。

1. **触发：**教材客户端发送 1 字节数据。服务只有一种操作，因此这个字节的内容不重要，它的到达表示请求服务。
2. **回复：**服务器 recvfrom 得到请求及源地址，运行 uptime，再 sendto 到该来源。连接 fd 不会像 TCP accept 那样为每个客户端单独产生。
3. **超时：**请求或响应可能丢失，服务器也可能未运行。sendto 成功通常不能立即发现这些情况，不能把后续阻塞接收当成一定会完成。
4. **教材的 alarm：**用 SIGALRM 中断等待，并在成功后取消定时器。依赖信号中断时要考虑 SA_RESTART、信号与进入接收之间的竞态，以及其他信号同样可能造成 EINTR。
5. **按截止时间等待：**使用可控制超时的等待机制并核对剩余时间，超时后由协议决定报错或重试。重试需要考虑迟到响应和重复请求，不能把任何收到的报文都当成本次正确响应。

教材的一报文响应适合短输出。如果输出需要多条 UDP 报文，就需额外定义顺序和完整性，不能照搬“读到 0 即结束”的 TCP 客户端。









**Q40: [learning] 选择 TCP 或 UDP 时，应怎样衡量应用自己承担的工作？**

选择取决于所需的数据交付语义和允许的失败处理。TCP 提供有序字节流及重传机制，UDP 保留报文边界但不保证送达和顺序，应用承担的工作因此不同。

1. **需要连续可靠字节：**TCP 通常更直接，但仍要定义业务消息边界、连接失败与应用确认。协议可靠不能代替业务执行结果。
2. **允许丢弃过时数据：**UDP 适合可容忍部分丢失的报文场景，但接收端仍要检查来源、长度及内容有效性。
3. **想在 UDP 上提供可靠请求：**需要超时、重传、序号、重复检测等机制。延迟报文可能在重传后才到达，不能把“再发一遍”当作没有副作用。
4. **成本：**TCP 有建连和每连接状态开销，保持连接可摊薄建连成本。UDP 的接口简单不意味着应用整体更简单，应把自行实现的可靠性机制一起计算。

这些比较限定在 TCP 与 UDP，不能把 UDP 的不可靠性推广到所有 SOCK_DGRAM，例如 Linux 的 Unix 域数据报具有不同保证。









**Q41: [learning] setsockopt 与 getsockopt 的参数怎样读？**

套接字选项控制端点或协议的行为。level 选择解释选项的层，option 选择该层内的具体选项，value 与 length 描述选项值的实际类型及大小。

```c
#include <sys/socket.h>
int setsockopt(int fd, int level, int option,
               const void *value, socklen_t length);
int getsockopt(int fd, int level, int option,
               void *value, socklen_t *length);
```

1. **fd：**被设置或查询的套接字。影响 bind 或连接建立的选项须在相应操作前设置，不能一律等到建连后才调用。
2. **level：**通用套接字层使用 SOL_SOCKET，TCP 层使用 IPPROTO_TCP，IPv4 层使用 IPPROTO_IP。层与选项名不匹配会导致调用失败。
3. **option：**在该层选择具体行为，例如 SO_REUSEADDR。它是选项标识，不是期望设置的值。
4. **value：**指向选项值，而不是把整数当指针传入。开关类选项常用 int 的零与非零表示禁用、启用，但 SO_LINGER 等使用结构，不能统一当成 int。
5. **length：**设置时给 value 对象的字节数。查询时先给可用容量，成功后按返回长度解释结果。两种函数均成功返回 0，失败返回 -1 并设置 errno。

未设置时采用该选项的平台默认值，默认值与可修改性应逐项查询，不能笼统假设全部为 0。









**Q42: [learning] SO_REUSEADDR 为什么有助于服务重启？**

TCP 连接关闭后可能仍有 TIME_WAIT 等协议状态占用地址组合。SO_REUSEADDR 调整 bind 的地址复用检查，使符合条件的服务器能更方便地重新绑定，但它不允许任意抢占正在监听的地址。

下面是设置片段，假定 fd 已由 socket 成功创建，下一步才调用 bind：

```c
int enabled = 1;
if (setsockopt(fd, SOL_SOCKET, SO_REUSEADDR,
               &enabled, sizeof(enabled)) == -1) {
    /* 本次初始化失败，调用者应记录错误并关闭 fd。 */
}
```

1. **SOL_SOCKET：**选项属于套接字层，不能写成 IPPROTO_TCP。
2. **SO_REUSEADDR 与 enabled = 1：**显式启用地址复用。新建 Linux 套接字默认未启用，省略设置可能在重启 bind 时遇到 EADDRINUSE。
3. **地址和长度：**传 &enabled 让内核读取 int 值，sizeof(enabled) 给出实际大小。
4. **时机：**在 bind 前设置，让绑定检查使用该规则。已经失败的 bind 不会因之后设置选项而自动成功。
5. **平台边界：**Linux 要求相关旧套接字与新套接字都按规则启用复用，与部分 BSD 行为不同。仍有活动监听者、通配地址冲突等情况时依然可能失败。

SO_REUSEPORT 是另一组选项语义，不能用 SO_REUSEADDR 推导多进程共享监听端口。依据：Linux socket(7)。









**Q43: [learning] SO_TYPE、SO_ACCEPTCONN 和 SO_ERROR 能查询什么？**

这三个套接字层选项分别查询类型、监听状态和待处理错误。它们读取的是不同状态，不能用其中一个替代另一个。

1. **SO_TYPE：**返回 SOCK_STREAM、SOCK_DGRAM 等类型，帮助理解读写语义，不返回当前连接是否健康。
2. **SO_ACCEPTCONN：**返回是否处于接受连接的监听状态。已 accept 的连接 fd 不是监听端点，即使它与监听 fd 有相同地址族和类型。
3. **SO_ERROR：**取得并清除待处理错误。getsockopt 自身返回 0 只说明查询成功，必须继续看取出的错误值，值为 0 才表示这次没有待处理错误。

例如非阻塞 TCP connect 等到可写后，查询 SO_ERROR，查询成功且值为 0 才按建连成功处理。不要在多个线程中无协调地反复读取这个会清除错误的状态。









**Q44: [learning] SO_KEEPALIVE 能证明远端应用仍正常服务吗？**

不能。SO_KEEPALIVE 启用适用连接协议的空闲探测，主要帮助识别失联连接。对端内核仍能回应探测时，对端业务线程即使卡住，也可能被视为连接存活。

1. **启用方式：**在 SOL_SOCKET 层传非零 int。Linux 新套接字默认关闭，未设置时不会因为应用空闲就自动按该选项探测。
2. **探测时机：**启用开关不等于立即发送探测。TCP 的空闲时间、间隔及次数由系统或对应 TCP 选项决定，不能把某台机器的默认秒数当成协议保证。
3. **发现故障：**连续探测未获回应后，协议栈最终使连接失败，应用通过后续 I/O 或错误状态得知。它不是瞬时断线通知。
4. **业务健康：**需要知道服务能否处理请求，应定义有期限的请求响应或应用心跳，并区分网络故障与业务超时。









**Q45: [learning] 套接字缓冲区大小与低水位分别影响什么？**

缓冲区大小影响内核可排队的数据量，低水位影响何时认为接收等条件已满足。两者都不定义业务消息长度。

1. **SO_SNDBUF：**影响发送缓冲容量。接收方或网络处理慢时，缓冲空间最终耗尽，发送会阻塞或报告暂时不可写。增大它不能保证对端更快消费。
2. **SO_RCVBUF：**影响接收缓冲容量。应用持续不读取时，TCP 可通过流量控制施加背压，UDP 则可能丢报文，效果依协议而异。
3. **Linux 的查询数值：**内核会为管理开销对 SO_SNDBUF、SO_RCVBUF 的设定值作加倍处理并受系统上下限约束。因此 getsockopt 返回值不能直接当作可容纳的纯业务字节数。
4. **SO_RCVLOWAT：**设置接收低水位。Linux 2.6.28 起 select/poll 等会按它报告正常接收就绪，但 EOF 和错误等终止条件仍需处理，不能把它当成必须凑齐一整帧的契约。
5. **SO_SNDLOWAT：**表示发送低水位，但 Linux 不允许通过 setsockopt 修改它。选项存在不代表所有系统都允许配置。

容量默认值及自动调节依协议和系统配置变化。低水位在 Linux 默认是 1，应通过目标系统手册和查询结果确认。依据：socket(7)。









**Q46: [learning] 收发超时和 SO_LINGER 分别限制哪一段等待？**

SO_RCVTIMEO、SO_SNDTIMEO 限制适用阻塞 I/O 的等待，SO_LINGER 控制关闭时对待发数据的处理。它们不是同一个业务请求的总超时。

1. **收发超时值：**Linux 使用 timeval 的秒与微秒字段。默认零表示不设置这类超时。超时前已传输部分数据时可返回部分进度，无进度时通常报告 EAGAIN 或 EWOULDBLOCK，连接建立等操作有自己的错误规则。
2. **作用范围：**收发超时不替代 select、poll 自身的超时参数。连续多次调用也可能分别消耗各自的等待额度，严格总时限需由应用维护截止时间。
3. **SO_LINGER：**使用 linger 结构，l_onoff 决定是否启用，l_linger 给出等待秒数。Linux 默认未启用时，close 通常快速返回，待发数据可由内核继续处理。
4. **正等待值：**启用后，关闭可能等待队列数据处理或等待期限结束，具体阻塞行为取决于系统和描述符模式。close 返回仍不等于远端应用已完成业务。
5. **零等待值：**Linux TCP 上启用 linger 且时间为 0 常用于中止式关闭，可能丢弃待发数据并让对端见到复位，不能把它当成普通优化。

若目标是发完请求再收响应，应考虑 shutdown 的半关闭语义，而不是用 linger 代替应用协议。









**Q47: [learning] SO_BROADCAST、SO_DONTROUTE 和 SO_DEBUG 各有什么用途？**

这些选项分别影响广播权限、路由选择和协议调试，不是所有套接字通用的性能开关。

1. **SO_BROADCAST：**允许适用的数据报套接字发送广播，例如 IPv4 UDP 广播。Linux 默认关闭。它不把普通单播地址改成广播地址，也不保证网络中所有主机都会收到。
2. **SO_DONTROUTE：**要求适用报文直接发往可达的本地网络，不经网关。它比一次发送的 MSG_DONTROUTE 作用范围更长，默认关闭时使用普通路由规则。
3. **SO_DEBUG：**请求协议调试功能。Linux 设置需要相应权限，实际可用性依协议实现，默认关闭。不能假定打开后就会得到应用层可读的完整报文日志。

应针对明确需求设置，并检查 setsockopt 返回值。不支持的选项不应被静默当作已经生效。









**Q48: [learning] TCP 紧急数据怎样通知接收方，为什么不是独立优先通道？**

TCP 紧急机制在同一连接的数据流上标记紧急位置，套接字 API 用 MSG_OOB 等接口暴露它。它没有建立另一条绕过连接阻塞和拥塞的可靠业务通道。

1. **发送：**在支持的 TCP 发送调用中指定 MSG_OOB。传统套接字接口突出处理一个紧急字节，不能把任意长度的控制消息都当作独立带外记录。
2. **通知：**配置套接字信号接收者后可收到 SIGURG，也可通过 select 的异常集合或 poll 的 POLLPRI 发现紧急条件。异常集合不等于“所有 socket 错误的集合”。
3. **独立读取：**未启用 SO_OOBINLINE 时，使用 recv 的 MSG_OOB 读取相应紧急字节。连续紧急指示不是可靠队列，旧紧急标记可能被覆盖。
4. **内联读取：**启用 SO_OOBINLINE 后，通过普通读取取得紧急数据。sockatmark 返回 1 表示处于紧急标记，返回 0 表示不在，返回 -1 表示错误，它不会替应用消费数据。
5. **适用边界：**不同实现对紧急指针存在历史差异。普通新协议应明确设计控制消息及其优先级需求，不能依赖“紧急数据一定越过所有普通数据先到达”的说法。

Linux 默认不启用 SO_OOBINLINE。该选项应与所选接收方式一致，依据为 tcp(7) 和 socket(7)。









**Q49: [learning] 非阻塞 I/O 和 select、poll 怎样配合？**

非阻塞模式使一次 I/O 在当前无法推进时立即返回，select/poll 则负责等待可能推进的条件。两者配合让单个线程管理多个连接，而不因一个暂时无数据的连接停住全部工作。

1. **设置状态：**使用 fcntl 的 F_GETFL 读取原标志，再通过 F_SETFL 保留原标志并加入 O_NONBLOCK。直接覆盖标志可能丢失已有设置。这个状态属于打开文件描述，dup 或 fork 后的共享引用也会受影响。
2. **等待可读：**就绪可能表示有数据、EOF 或错误。调用 recv 后依据结果处理，不能把可读直接等同于收到完整业务请求。
3. **等待可写：**队列有空间时尝试发送，按正返回值推进偏移。只在有待发数据时关注可写，避免空转。
4. **竞争变化：**就绪是状态快照，另一线程可能已取走数据。因此仍需处理 EAGAIN、EWOULDBLOCK 和 EINTR，不能认为等待返回后所有 I/O 都不会阻塞。
5. **单次非阻塞：**Linux 的 MSG_DONTWAIT 只作用于当前 send/recv 调用，适合不想修改共享状态的场景，不会让整个事件循环自动异步执行。









**Q50: [learning] 非阻塞 connect 返回 EINPROGRESS 后怎样确认结果？**

EINPROGRESS 表示连接尚在进行。等待可写只说明连接过程有结果可检查，最终成功与否必须通过 SO_ERROR 判断。

1. **发起：**对非阻塞 TCP 套接字调用 connect。立即返回 0 可按成功处理，返回 -1 且为 EINPROGRESS 时登记该 fd 等待完成。其他错误按具体原因处理。
2. **等待：**用 select 或 poll 等待可写及错误相关事件，并设置业务允许的截止时间。超时后若放弃本次连接，应关闭 fd，避免后台连接继续占用资源。
3. **读取结果：**给 getsockopt 准备 int error 和长度 sizeof(error)，使用 SOL_SOCKET、SO_ERROR 查询。先检查函数是否成功，再判断 error 是否为 0。
4. **成功后：**继续按非阻塞收发规则运行。建连成功不自动清除 O_NONBLOCK。
5. **失败后：**记录查询出的错误，关闭套接字。若要重试，重新创建套接字并按退避策略尝试，不对失败对象无休止重复 connect。

例如连接被拒绝同样可以使等待返回，此时 error 为 ECONNREFUSED。教材“可写则连接完成”应理解为完成待检查，不能省略错误值检查。依据：Linux connect(2)。









**Q51: [learning] SIGIO 信号驱动 I/O 与异步完成通知有什么不同？**

SIGIO 通知的是套接字可能可读或可写，数据仍需应用调用收发函数搬运。它属于就绪通知，不意味着一项预先提交的 I/O 已经替应用完成。

1. **选择接收者：**通过 fcntl 的 F_SETOWN 配置进程或进程组，F_GETOWN 查询当前配置。这里的所有权指信号投递目标，不是文件的 UID 所有者。
2. **启用通知：**在支持的平台上保留原文件标志并加入 O_ASYNC。O_ASYNC 控制通知，O_NONBLOCK 控制调用是否等待，二者不是替代关系。
3. **收到信号：**回到安全的处理位置检查就绪状态并执行 I/O，仍处理 EAGAIN 等结果。不能假设一次信号严格对应一条消息，也不应在信号处理函数中任意调用非异步信号安全函数。
4. **区分 SIGURG：**它用于紧急条件通知，和普通读写就绪的 SIGIO 分工不同。
5. **移植：**教材还列出 FIOSETOWN、SIOCSPGRP、FIOASYNC 等 ioctl 方案，支持范围依平台变化。不能把书中旧版系统矩阵推广到当前所有 Unix 系统。

依据：Linux socket(7)、fcntl(2)。新套接字不会自动按此方式发出普通异步 I/O 信号，必须完成接收者和通知开关的配置。
