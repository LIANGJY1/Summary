# Unix domain 套接字与描述符传递

> 范围：Unix domain 套接字的本机寻址、描述符与凭据传递、多客户端服务模型。平台行为以 Linux man-pages 的 unix、socketpair、sendmsg、recvmsg、cmsg、open、dup 与 credentials 手册为依据。

**Q1: [learning] Unix domain 套接字是什么，与经环回地址通信的 TCP 套接字有什么不同？**

Unix domain 套接字是同一台机器上的进程间通信端点，使用 AF_UNIX 或 AF_LOCAL 域。它沿用 socket、bind、connect、send、recv 等接口，但不通过 IP 地址和端口寻址，也不需要把本机数据按 TCP/IP 网络路径发送。

1. **地址：**可用文件系统路径或 Linux 抽象命名空间，也可创建无名的已连接套接字对。
2. **传输类型：**Linux 支持 SOCK_STREAM、SOCK_DGRAM 和 SOCK_SEQPACKET。流、数据报和顺序分组的消息边界仍按各自类型判断。
3. **额外能力：**可通过辅助数据传递打开文件描述符和经过内核检查的进程凭据，普通 TCP 套接字不提供同一套本机对象传递语义。
4. **边界：**它不能直接连接另一台机器。性能可能受复制次数、消息大小和实现影响，不能笼统声称一定比环回 TCP 快。

**Q2: [learning] Unix domain 的 SOCK_STREAM、SOCK_DGRAM 与 SOCK_SEQPACKET 怎样区分？**

三种类型主要按连接方式与消息边界区分，不应因为都在本机就假定表现完全一样。

1. **SOCK_STREAM：**面向连接、按序交付字节，不保留每次 write 的边界。需要应用协议自己定义消息长度。
2. **SOCK_DGRAM：**每次发送是一条独立消息，接收保留边界。Linux unix(7) 明确说明其本地数据报可靠且不会重排，但这不是 UDP 的语义，也不代表接收进程已经处理消息。
3. **SOCK_SEQPACKET：**面向连接、按序且保留消息边界。需要同时获得连接状态和记录边界时，可先检查目标内核及系统接口是否支持。

**Q3: [learning] socketpair() 创建的两个端点是什么，为什么适合父子进程通信？**

socketpair 一次创建两个已相互连接且无名的套接字，把两个 fd 写入调用者提供的数组。常见组合是 AF_UNIX、SOCK_STREAM、协议参数 0。每一端都可收发，因此能建立全双工的本机通道。

1. **创建时：**调用者拿到两个独立 fd。没有服务器路径、bind、listen 或 accept 步骤。
2. **fork 后：**父子进程继承两个 fd，各自关闭不使用的一端，就能通过保留的一端通信。
3. **生命周期：**进程需要关闭不用的引用，否则对端可能迟迟收不到预期 EOF。

socketpair 适合已有继承关系或能够直接交付 fd 的进程。彼此无关的进程通常需要有名的服务地址或其他 fd 交付途径。

**Q4: [learning] socketpair 与 pipe 都能连接父子进程，为什么两者不能完全互换？**

pipe 通常提供单向字节通道。socketpair 的两个端点都可双向通信，并可在 Unix domain 上使用套接字消息及辅助数据能力。因此是否只需传字节、是否要全双工以及是否要传 fd，决定了选择。

1. **单向数据流：**pipe 结构简单，适合一个写端到一个读端。
2. **双向对话：**socketpair 不需两条 pipe 就能让两端互发请求与响应。
3. **传递内核对象引用：**需要 SCM_RIGHTS 传文件描述符时，Unix domain 套接字提供对应辅助数据机制，普通 pipe 的字节流不提供此能力。

把数字 fd 写进 pipe 只发送一个整数，不会在另一进程的 fd 表里创建指向同一对象的引用。

**Q5: [learning] sockaddr_un 中 sun_family 与 sun_path 各表示什么？**

sockaddr_un 是 Unix domain 套接字使用的地址结构。sun_family 标记 AF_UNIX，sun_path 保存路径名地址或 Linux 抽象地址的字节。它们共同构成可传给 bind、connect 等接口的本地地址。

1. **路径名地址：**sun_path 保存以 NUL 结尾的文件系统路径，路径字节数不得超过目标系统字段容量。
2. **抽象地址：**Linux 中 sun_path 的首字节为 NUL，后续名称由传入的 addrlen 界定。它不是 C 字符串，也不对应文件系统路径。
3. **无名套接字：**未 bind 的流端点或 socketpair 端点可能没有可读取的路径名，不能假定 sun_path 总有内容。

sun_path 长度在不同系统上可能不同。避免把 Linux 的固定容量写成跨 POSIX 平台保证。

**Q6: [learning] Unix domain 路径名地址与 Linux 抽象地址在可见性、权限和清理上有什么区别？**

两者都能命名本机端点，但名字存在的位置不同，安全边界也不同。

1. **路径名地址：**bind 在文件系统中创建套接字类型的目录项。路径所在目录的权限影响创建与访问。关闭 fd 不自动删除路径名，服务应在合适时机 unlink 自己创建的条目。
2. **抽象地址：**Linux 专有命名空间，不创建路径文件。文件 mode、umask 和 chmod 不控制它的访问。所有引用关闭后，抽象名字随端点消失。
3. **可移植性：**路径名地址更便于跨 Unix 系统设计。抽象命名空间是 Linux 扩展，不能作为 POSIX 通用接口要求。

无论使用哪种地址，都不能单靠“别人不知道名字”作为访问控制。敏感服务应核验对端身份与实际授权。

**Q7: [learning] 计算 Unix domain 地址长度时，为什么要用 offsetof 而不是盲传路径字符串长度？**

系统调用的 addrlen 描述整个 sockaddr_un 地址结构中实际参与寻址的字节，不只是 sun_path 里的字符数。offsetof(struct sockaddr_un, sun_path) 给出路径字段起始偏移，能适应结构前部在不同系统上的布局差异。

1. **路径名地址：**长度通常至少包含字段偏移、路径字节及终止 NUL。Linux unix(7) 给出 `offsetof(struct sockaddr_un, sun_path) + strlen(sun_path) + 1` 的计算方式。
2. **抽象地址：**首个 NUL 是命名空间标记，其后的名称按精确字节长度计算，可包含 NUL。不能用 strlen 决定长度。
3. **输出地址：**getsockname、getpeername 或 accept 返回的地址长度须先与提供的容量比较。输出被截断时，sun_path 不保证有字符串终止符。

sizeof(sockaddr_un) 可在一些路径名调用中使用，但精确长度更能表达地址实际内容。字段容量和调用契约仍以目标平台手册为准。

**Q8: [learning] 路径名 Unix socket 文件是否保存消息内容，进程退出后为什么可能留下失效路径？**

路径名套接字在文件系统中的条目只用于命名内核通信端点，不保存发送的消息正文，不能像普通文件那样 open 并读取消息。消息经内核套接字队列在进程间交付。

1. **服务运行时：**bind 创建名称，客户端用该名称 connect 或 sendto 找到端点。
2. **服务退出后：**fd 关闭可释放内核端点，但路径目录项可能仍存在。下一次 bind 同一路径会遇到 EADDRINUSE。
3. **清理时：**服务只能安全清理确认属于自己的路径。简单“先 unlink 再 bind”若目录可被其他进程写入，可能删除别人的端点或遇到替换竞态。

可将 socket 放在受控目录，限定目录所有权和权限，再设计启动、异常退出与清理流程。

**Q9: [learning] 文件系统权限与 Unix socket 对端身份验证是什么关系？**

路径目录与套接字文件权限可限制谁能创建或连接，但它们不完整证明“当前连接者是谁”。Linux 会在连接路径名流套接字或向路径名数据报套接字发送时检查权限。POSIX 不保证所有系统都以相同方式使用 socket 文件权限。

1. **目录权限：**控制谁能搜索目录或创建、替换路径条目，是防止服务地址被抢占的第一层边界。
2. **套接字 mode：**在 Linux 上可约束谁能连接或发送，但不能把跨系统一致性当作前提。
3. **对端凭据：**需要按 UID/GID 授权时，应使用目标平台提供的内核凭据机制，如 Linux 的 SO_PEERCRED 或 SCM_CREDENTIALS。

读到一个客户端自称的 PID、UID，或 stat 到一个客户端路径的 owner，都不能独立完成安全认证。路径可能被替换，身份也可能与持有路径者不同。

**Q10: [learning] 无继承关系的两个本机进程怎样建立 Unix domain 流连接？**

服务器创建 AF_UNIX 流套接字，bind 到受控路径并 listen。客户端创建自己的 AF_UNIX 流套接字，connect 到服务器路径。服务器 accept 后得到只用于该客户端的新 fd，监听 fd 继续等待其他客户端。

1. **服务器地址：**必须在客户端可访问的目录中创建，并处理残留路径与启动竞态。
2. **客户端地址：**流客户端通常不必自行 bind 路径。服务端可在 accept 后通过内核凭据机制取得连接者身份，不应为识别客户端而强制每个客户端制造可被伪造或竞态替换的路径。
3. **消息协议：**连接建立后仍要定义请求长度、响应状态、超时与关闭方式，因为 SOCK_STREAM 不保留调用边界。

本地连接避免网络寻址，但不自动解决并发、鉴权和协议成帧。

**Q11: [learning] 教材的 serv_listen、serv_accept 和 cli_conn 分别做什么，为什么不能把它们当成标准套接字 API？**

这三个名字是教材为 Unix domain 流连接编写的辅助函数，不是 POSIX socket 接口。它们把 socket、bind、listen、accept、connect 等系统调用组合起来，便于演示无继承关系进程之间的一对一连接。

1. **serv_listen：**创建服务器套接字，将其绑定到约定的文件系统路径并开始监听，返回监听 fd。路径所有权、残留条目清理和权限都要由实现者负责。
2. **serv_accept：**在监听 fd 上接受一个客户端，返回该连接独有的 fd。教材实现还尝试通过客户端绑定的路径读取 UID，这属于该示例的身份推断，不是 accept 的标准返回值。
3. **cli_conn：**客户端创建套接字并连接服务器地址。教材先将客户端绑定到包含 PID 的专有路径，是为了让服务端看到一个路径名。普通 Unix domain 流客户端通常无须这样 bind。

PID 路径并不天然唯一或可信。PID 可复用，目录项可被替换，路径的 owner 也未必代表当前连接进程。需要核验身份时，在 Linux 上应结合受控目录与 SO_PEERCRED 等内核凭据机制，再执行授权判断。

**Q12: [learning] 把一个打开的 fd 发给另一进程，为什么不能只发送它的整数值？**

fd 整数只在发送进程自己的描述符表中有意义。另一进程的同号 fd 可能引用完全不同的对象，甚至尚未打开。真正的描述符传递要求内核在接收进程的描述符表中建立新的引用。

1. **发送方：**持有某个打开文件描述对应的 fd，可通过 Unix domain 套接字的 SCM_RIGHTS 辅助数据请求内核传递引用。
2. **接收方：**recvmsg 后获得本进程可用的新 fd 编号。编号通常与发送方不同，但指向同一打开文件描述。
3. **引用生命周期：**发送方之后关闭自己的 fd，不会自动使接收方的引用失效。只有最后引用释放后，底层打开对象才按其规则清理。

因此“传 fd”是传内核对象引用的能力交付，不是拷贝一个整数或重新按路径 open 文件。

**Q13: [learning] SCM_RIGHTS 传递后的两个 fd 共享什么，不共享什么？**

SCM_RIGHTS 的效果近似于把同一打开文件描述复制进另一个进程的 fd 表。两个进程的 fd 编号和描述符级标志各自独立，但共享打开文件描述关联的状态。

1. **共享：**若传的是普通文件，文件偏移及文件状态标志如 O_NONBLOCK 属于打开文件描述，可能被两端共同观察或修改。传 socket 时，两端引用同一个套接字端点状态。
2. **独立：**fd 数字由接收进程分配。FD_CLOEXEC 是描述符级标志，不因两个 fd 指向同一打开文件描述就自动同步。
3. **权限含义：**接收方可使用已经打开的能力，即使它自己不能重新按路径打开该文件。服务器传递前必须验证请求并限制交付对象。

共享文件偏移会影响并发读取位置。需要独立偏移时，不应把“传同一打开文件描述”误当成重新 open。

**Q14: [learning] cmsghdr 的 cmsg_len、cmsg_level、cmsg_type 和数据区各表示什么？**

cmsghdr 是 sendmsg/recvmsg 控制消息的头部。一条控制消息由头部和随后数据组成，可表达文件描述符、凭据等不属于普通正文的内容。

1. **cmsg_len：**该条控制消息的实际长度，包含头部及数据，不等同于整个控制缓冲区的分配容量。
2. **cmsg_level：**指明控制消息所属协议层。Unix domain 的 SCM_RIGHTS 和 SCM_CREDENTIALS 使用 SOL_SOCKET。
3. **cmsg_type：**在对应层内指定消息类型。SCM_RIGHTS 表示传打开文件描述的引用，SCM_CREDENTIALS 表示传内核检查的进程凭据。
4. **数据区：**按类型解释。SCM_RIGHTS 的数据是 fd 整数数组，接收后的整数属于接收进程自己的 fd 表。

控制区可能包含多条消息，还要满足内存对齐要求，因此不能把 msg_control 当成单个固定结构直接强制转换后使用。

**Q15: [learning] CMSG_SPACE、CMSG_LEN、CMSG_DATA、CMSG_FIRSTHDR 与 CMSG_NXTHDR 怎样配合？**

这些宏帮助调用者按平台要求的对齐方式分配、填写和遍历辅助数据。手动假定头部紧贴下一个头部，可能在不同 ABI 上解析错位。

1. **CMSG_SPACE：**计算一条控制消息连同头部、数据及对齐填充所需的缓冲区容量。分配 msg_control 时使用。
2. **CMSG_LEN：**计算这条消息应写入 cmsg_len 的实际长度，不把尾部为下一条消息准备的填充误算进本条内容。
3. **CMSG_DATA：**取得某个 cmsghdr 后的数据区指针。对需要对齐的数据类型，可用 memcpy 与合适的本地对象交换，不假定返回指针满足任意类型对齐。
4. **CMSG_FIRSTHDR：**从 msghdr 控制区取得第一条消息，容量不足时返回 NULL。
5. **CMSG_NXTHDR：**从当前消息移动到下一条合法消息，到末尾或空间不足时返回 NULL。

发送前要清零控制缓冲区并写对 level、type、长度。接收后遍历每条消息时仍要检查类型、长度和 MSG_CTRUNC，不能只看第一条。

**Q16: [learning] sendmsg/recvmsg 通过 SCM_RIGHTS 传递文件描述符的基本过程是什么？**

发送进程把待传 fd 放进 Unix domain 套接字的 SCM_RIGHTS 控制消息，接收进程用 recvmsg 取出新 fd。正文和控制消息由同一次发送关联，应用协议还需说明这个 fd 对应什么请求与用途。

1. **发送端：**准备正文 iovec 和足够的控制缓冲区。将 cmsghdr 的 level 设为 SOL_SOCKET、type 设为 SCM_RIGHTS，数据区放入有效 fd 的整数数组，再调用 sendmsg。
2. **接收端：**准备正文、控制区及容量，用 recvmsg 接收。检查返回值和 msg_flags，遍历 cmsghdr 找到匹配的 SCM_RIGHTS，再按实际数据长度取出全部 fd。
3. **移交责任：**双方协议应明确谁在什么时候 close。发送成功后发送端可关闭自己的引用，但应先确认协议是否还需要重试或继续使用它。

Linux 的 Unix domain 流套接字传控制消息时还须伴随至少一个普通数据字节。只传控制区而不给正文，不能作为通用做法。

**Q17: [learning] 接收 SCM_RIGHTS 时为什么必须检查 MSG_CTRUNC、fd 数量和 FD_CLOEXEC？**

收到部分控制消息却当作完整请求，会造成资源泄漏或错误使用对象。接收端应把控制区容量、实际数量与协议上限一起检查。

1. **MSG_CTRUNC：**表示控制区不足，消息可能被截断。Linux 会关闭因截断无法交付的多余 fd，但已交付的 fd 仍需接收方妥善处理。
2. **数量与类型：**先验证 cmsghdr 的 level、type 和长度，再算出收到几个 fd。数量不符时关闭所有已经取得的 fd，并拒绝该请求。
3. **FD_CLOEXEC：**接收的新 fd 不应无意泄露给后续 exec 的程序。Linux recvmsg 可用 MSG_CMSG_CLOEXEC 在接收时原子设置 close-on-exec，或按平台支持使用等价机制。
4. **容量上限：**发送和接收都受每进程 fd 限额与内核辅助数据上限约束，不能无限制地传 fd 数组。

资源清理必须覆盖成功、协议错误、接收截断和后续业务处理失败四种路径。

**Q18: [learning] SO_PEERCRED、SO_PASSCRED 和 SCM_CREDENTIALS 分别用于哪种对端身份场景？**

三者都与 Linux Unix domain 对端凭据有关，但观察时机和取得方式不同。它们返回的是内核认可的进程凭据线索，业务仍须按 UID/GID 等策略授权。

1. **SO_PEERCRED：**对适用的已连接 Unix domain 套接字，通过 getsockopt 查询对端凭据。Linux 返回的是连接建立或 socketpair 创建等特定时点的凭据快照。
2. **SO_PASSCRED：**在接收端启用后，使后续消息可以带 SCM_CREDENTIALS 控制消息，适合按消息观察发送方。
3. **SCM_CREDENTIALS：**控制消息里的 ucred 含 pid、uid、gid。发送方若显式给出凭据，内核会按权限检查。没有显式给出时可使用系统提供的默认凭据。

不能把对端路径名的 owner 或应用自己在正文填写的 UID 当成等价机制。若进程能切换身份，还要区分连接时快照与每条消息的发送时身份。

**Q19: [learning] Unix domain 服务如何把“客户端能连接”与“客户端有权打开某文件”分开判断？**

连接本地 socket 只说明通信通道建立，不等于客户端获准使用服务进程的文件访问能力。书中的 open 服务例子让服务器代客户端执行 open，再把打开的 fd 传回。这样的设计必须明确授权边界，否则就会成为绕过文件权限的代理。

1. **身份：**用内核凭据机制识别连接者，不能仅相信客户端传来的 UID 或路径名。
2. **请求：**定义允许的操作、路径范围和打开标志。解析请求时检查长度、编码、参数个数和每个标志的授权，不把任意字符串直接交给高权限 open。
3. **执行：**在受限权限或受控目录中打开目标，处理符号链接、路径穿越及检查与使用之间的竞态。
4. **响应：**成功时传 fd，失败时传明确错误码。客户端必须区分“服务器已接收请求”与“文件已安全打开”。

教材的服务器展示描述符传递机制，不构成可直接部署的高权限文件服务方案。

**Q20: [learning] 为什么 fd 传递协议仍需要正文中的状态、请求 ID 或错误信息？**

SCM_RIGHTS 只传递一个或多个打开对象引用，不告诉接收方这些对象对应哪次业务请求、是什么类型或失败时发生了什么。双方必须为控制消息之外的语义定义正文协议。

1. **请求关联：**标识哪个请求得到哪个 fd，防止并发响应错配。
2. **成功状态：**约定成功时应收到的 fd 类型和数量。没有 fd 不可被默认为空文件。
3. **失败状态：**明确返回错误类别和可诊断信息，避免把传输中断与权限拒绝混为一谈。
4. **边界和版本：**给消息长度上限与协议版本，防止旧客户端把新字段误读为路径或标志。

若用 SOCK_STREAM 承载，还必须成帧。一个 sendmsg 的正文边界不自动成为一个 recvmsg 的业务消息边界。

**Q21: [learning] 每个客户端一个子进程与单进程处理多个 Unix domain 客户端，各有什么资源与状态代价？**

这两种模型都可通过 Unix domain socket 接入客户端，区别在服务如何隔离并发请求与管理已连接 fd。

1. **每客户端子进程：**父进程 accept 或创建通道后把请求交给子进程。进程隔离清楚，崩溃影响面较小，但 fork/exec、进程数、子进程回收和 fd 继承成本需要管理。
2. **单进程事件循环：**一套服务进程用 select、poll 或同类机制监视监听 fd 与多个连接 fd。减少进程创建，但必须为每个客户端独立保存解析进度、身份、待发数据与超时。
3. **共同约束：**两者都要关闭不用的 fd、限制客户端数、拒绝超长请求，并在客户端断开时清理控制消息中取得的资源。

性能选择需按请求耗时、连接数、隔离要求和实测决定。书中两个 open 服务器版本是模型示例，不是固定性能排序。

**Q22: [learning] select 或 poll 同时监视监听 fd 和客户端 fd 时，哪两类可读事件必须区分？**

监听 fd 可读通常意味着有连接等待 accept。客户端连接 fd 可读则表示有正文、对端关闭或错误需要处理。两者都称“可读”，下一步调用却不同。

1. **监听 fd：**执行 accept，给新客户端分配连接状态并纳入监视集合。监听 fd 自身不承载该客户端的业务正文。
2. **客户端 fd：**执行 recv 或 read，把字节放进该客户端的独立缓冲区，按协议帧解析。返回 0 时按流式 EOF 处理并释放连接状态。
3. **写就绪：**只有待发数据需要继续发送时才关注可写，处理短写后更新偏移，避免长期监视始终可写的 fd 造成空转。

就绪列表只是一份时点快照。实际读写仍要处理 EINTR、EAGAIN、断连以及 fd 被关闭或重用的情况。

**Q23: [learning] 为什么 Unix domain socketpair 可以辅助监视原本只有阻塞读取接口的消息队列？**

书中的技巧是让专门线程阻塞在消息队列读取接口，收到消息后写入 socketpair 的一端。主线程通过 poll 或 select 监视另一端，于是把“消息队列有消息”转成“一个 fd 可读”。这是一种桥接模型，并非消息队列本身突然变成了可轮询 fd。

1. **工作线程：**每个无法直接被主循环等待的队列需要对应的阻塞接收者，并负责把消息或通知转送到 socket。
2. **主循环：**只监视 socket fd，再按转送协议还原消息来源与长度。
3. **代价：**线程数量、双重排队、关闭顺序和背压都会增加。若目标系统已有可轮询的原生队列接口，应优先核对其能力。

桥接使用 SOCK_DGRAM 时可保留每条通知的边界，但仍要检查数据长度与缓冲区上限。不能由此推断所有 IPC 对象都能直接交给 poll。

**Q24: [learning] open 服务示例里的 getopt、optstring、optarg、optind、opterr 和 optopt 各有什么含义？**

getopt 是解析进程命令行短选项的库函数，不处理 socket 协议。书中的常驻服务通过它解析是否以前台或守护进程方式运行的启动选项。解析选项与处理客户端传来的请求是两条独立输入边界。

1. **argc/argv：**进程启动时 main 收到的参数个数与参数数组，getopt 从中逐项扫描选项。
2. **optstring：**列出允许的短选项字符。某字符后紧跟冒号表示该选项必须有参数。
3. **返回值：**找到选项时返回该字符，没有更多选项时返回 -1。未知选项通常返回问号。缺少必需参数时可用以冒号开头的 optstring 区分返回冒号。
4. **optarg：**当前带参数选项的参数文本指针。
5. **optind：**下一待处理 argv 元素的索引。选项扫描结束后，可据此定位非选项参数。
6. **opterr：**控制 getopt 是否自行向标准错误输出诊断。设为 0 后应用需自行处理错误返回。
7. **optopt：**记录出错的选项字符，便于应用构造自己的错误消息。

glibc 对非选项参数顺序还提供扩展行为。需要跨 POSIX 系统一致解析时，应按目标 libc 的 getopt 手册核对，而不能从书中某个启动命令推断全部行为。

**Q25: [learning] 用 select 管理多个 Unix domain 客户端时，fd_set 与最大 fd 参数分别表达什么？**

select 让单线程等待一组 fd 的读、写或异常就绪。调用者在每次调用前构建 fd_set，传入“本次监视的最大 fd 加 1”，返回后集合被改写为本次就绪的 fd。

1. **监听集合：**监听 fd 出现在可读集合时，尝试 accept 新连接。
2. **客户集合：**连接 fd 出现在可读集合时，尝试读取正文或处理 EOF。存在待发数据时再把它放入可写集合。
3. **每轮重建：**select 修改传入的集合，下一轮不能直接拿上次返回的集合继续等待。
4. **容量边界：**固定 fd_set 容量与 FD_SETSIZE 限制使高编号 fd 不适合直接放入传统 select 集合。不能仅按客户端数量判断是否安全。

select 返回“就绪数量”而不是一次替应用处理这些连接。实际读写和每个客户端的解析状态仍由服务维护。

**Q26: [learning] pollfd 的 fd、events、revents 与 select 的 fd_set 模型有什么不同？**

poll 用 pollfd 数组描述每个要监视的 fd，以及希望观察的事件。返回后每个元素的 revents 给出实际发生的事件，不需要像 select 那样用最大 fd 加 1 指定扫描范围。

1. **fd：**要监视的文件描述符。Linux 中负值 fd 项可用于暂时忽略该元素，不必移动数组中的其他客户端。
2. **events：**调用前指定想观察的事件，例如 POLLIN 表示可读、POLLOUT 表示可写。
3. **revents：**调用后检查实际事件，也包括 POLLERR、POLLHUP 或 POLLNVAL 等异常状态。不能只处理 events 中显式请求的位。
4. **timeout：**限制本次等待的时间。返回 0 表示本次等待超时，不表示所有客户端都已断开。

poll 避免传统 fd_set 的固定编号上限，但数组扫描仍有成本。连接规模、平台能力及实现复杂度决定是否改用其他事件机制。
