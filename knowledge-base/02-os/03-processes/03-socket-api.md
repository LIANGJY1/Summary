# 套接字接口、寻址与数据传输

> 范围：POSIX/Linux 套接字的创建、寻址、连接、数据传输与选项。接口行为以 POSIX 定义和 Linux man-pages 的对应手册为依据。通用 TCP/IP 协议原理归网络知识库。

**Q1: [learning] socket() 创建了什么？domain、type、protocol 三个参数分别决定什么？**

socket() 请求内核创建一个通信端点，成功时返回当前进程可使用的文件描述符，失败时返回 -1 并设置 errno。文件描述符只是进程内的句柄，不是对端地址，也不是通信连接已经建立的证明。

三个参数沿不同维度选择通信行为：

1. **domain：**选择协议族及地址格式。AF_UNIX 用于本机进程通信，AF_INET 与 AF_INET6 分别选择 IPv4 与 IPv6。域不单独决定传输可靠性。
2. **type：**选择数据交付语义，例如 SOCK_STREAM 的字节流、SOCK_DGRAM 的数据报，或 SOCK_SEQPACKET 的保留消息边界的顺序分组。
3. **protocol：**在域与类型允许多个具体协议时选择其中一个。传 0 表示选择该组合的默认协议，不表示“没有协议”。例如 AF_INET 与 SOCK_STREAM 常选择 TCP，AF_INET 与 SOCK_DGRAM 常选择 UDP。

三者必须构成目标系统支持的组合。创建成功只得到本地端点，后续还要按角色决定是否 bind、connect、listen 或直接发送数据报。

**Q2: [learning] SOCK_STREAM、SOCK_DGRAM、SOCK_SEQPACKET、SOCK_RAW 与 SOCK_RDM 的语义分别是什么？**

套接字类型描述应用看见的数据单位和连接方式，不能仅靠类型名推断底层协议及所有可靠性保证。

1. **SOCK_STREAM：**提供双向、有序字节流，不保留 send 或 write 的调用边界。使用前通常先建立连接。TCP 与 Unix domain stream 是不同域里的例子。
2. **SOCK_DGRAM：**每次发送形成一条有长度上限的数据报，接收端保留报文边界，通常不需预先建立逻辑连接。IPv4/IPv6 中常对应 UDP，UDP 不保证交付或顺序。Linux Unix domain 数据报则有可靠、不会重排的本地语义，不能把 UDP 的特征强加给所有 SOCK_DGRAM。
3. **SOCK_SEQPACKET：**提供面向连接、有序、可靠且保留记录边界的数据传输。是否支持取决于通信域和协议，不能把它当作所有平台都有的通用替代品。
4. **SOCK_RAW：**允许应用访问较低层的协议数据，具体可构造或接收哪些头部取决于协议族。Linux 创建原始 IP 套接字通常要求 CAP_NET_RAW 能力，不等同于“必须以 root 身份运行”。
5. **SOCK_RDM：**表示可靠但不保证顺序的数据报类型。它不是通用 TCP/IP 应用开发的常用选择，支持范围由具体系统与协议决定。

**Q3: [learning] IPPROTO_IP、IPPROTO_IPV6、IPPROTO_TCP、IPPROTO_UDP、IPPROTO_ICMP 与 IPPROTO_RAW 分别标识什么？**

IPPROTO 常量是在 IP 协议族中指明协议或选项层级的编号，不是套接字类型，也不是端口号。它们出现的位置不同，含义也需按接口理解。

1. **IPPROTO_IP：**IPv4 协议层常量，可用于选择 IPv4 层的套接字选项。
2. **IPPROTO_IPV6：**IPv6 协议层常量，用于 IPv6 层的相关选项。
3. **IPPROTO_TCP：**TCP 协议编号。与 AF_INET/AF_INET6 的 SOCK_STREAM 组合时通常可显式选择 TCP，也可用于 TCP 层选项。
4. **IPPROTO_UDP：**UDP 协议编号。与 SOCK_DGRAM 组合时通常可显式选择 UDP。
5. **IPPROTO_ICMP：**IPv4 ICMP 协议编号，不表示普通应用通过 SOCK_STREAM 就能发送 ICMP。
6. **IPPROTO_RAW：**Linux 原始 IP 套接字相关的特殊协议值。如何构造 IP 头及所需权限取决于原始套接字接口，不能按 TCP/UDP 调用方式类推。

应用调用 socket 时协议参数传 0，表示为已选域与类型选择默认协议。只有明确需要特定协议或协议层选项时，才应传入相应常量。

**Q4: [learning] 套接字描述符与普通文件描述符有哪些共同点和不同点？**

套接字描述符同样由进程的文件描述符表管理，可通过 close 释放，也可在适用的连接类型上用 read、write 或 poll 等接口操作。但套接字表示通信端点，没有普通文件可随机定位的文件偏移，因此 lseek 不适用。

判断一个文件描述符操作能否用于套接字，应看该操作要求的对象能力：

1. **引用管理：**dup 或 fork 可以形成多个引用，同一个内核套接字不会因为其中一个引用关闭就立即消失。
2. **顺序 I/O：**对已连接的流套接字可用 read 和 write。发送目标地址、接收发送者地址、消息标志或辅助数据时则需要 send、recv 家族。
3. **定位与映射：**不能把套接字当成可 seek 的普通文件，也不能因为它有 fd 就推断 mmap、锁或文件状态查询具有普通文件的语义。

**Q5: [learning] close() 与 shutdown() 怎样影响共享引用和双向连接？**

close() 关闭当前文件描述符引用。shutdown() 对套接字通信方向生效，即使同一套接字还有由 dup 或 fork 形成的其他描述符引用，也可以先禁止某个方向继续收发。

1. **SHUT_RD：**禁止后续接收。具体已排队数据的处理依协议和实现，不应用它代替读取剩余响应。
2. **SHUT_WR：**禁止后续发送。对 TCP 连接通常使对端在读完已发送数据后看到写方向结束，本端仍可继续读取对端响应。这是请求发完、仍需收回复时常用的半关闭。
3. **SHUT_RDWR：**同时禁止收发。它不负责关闭当前 fd，完成后仍须 close。

对端看到 EOF 的时间还受已排队数据、协议状态和所有引用生命周期影响。只调用 close 而保留其他引用，不等于已经明确发出了应用预期的半关闭信号。

**Q6: [learning] 主机字节序、网络字节序与大小端分别是什么意思？**

字节序决定一个多字节整数在连续字节中的排列。网络字节序按大端排列，即最高有效字节位于最低地址。主机字节序由运行机器决定，可以与网络字节序相同，也可以不同。

以 32 位值 0x01020304 为例：

1. **大端：**低地址到高地址依次存放 01、02、03、04。
2. **小端：**低地址到高地址依次存放 04、03、02、01。

字节序描述存储排列，不改变整数的数学值，也不等于“字符串从左往右如何书写”。跨机器通信时先按协议规定的字节序序列化字段，接收端再转换，避免把本机内存表示直接当作网络格式。

**Q7: [learning] htons、htonl、ntohs 和 ntohl 各转换什么？为什么不能手写固定交换顺序？**

这四个接口在主机字节序与网络字节序之间转换整数。它们按运行平台决定是否交换字节，因此同一源码在大端与小端机器上都能产生协议规定的表示。

1. **htons：**把 16 位主机序值转为网络序，常用于端口号。
2. **htonl：**把 32 位主机序值转为网络序，常用于 IPv4 地址字段或协议中的 32 位整数。
3. **ntohs：**把 16 位网络序值转为主机序。
4. **ntohl：**把 32 位网络序值转为主机序。

地址中的原始字节数组、文本 IP 字符串和已经按网络序保存的字段不能无条件再交换。类型宽度也必须匹配。手写“总是反转字节”会在大端机器上把正确数据改错。

**Q8: [learning] 为什么套接字 API 使用 sockaddr 指针与地址长度，而不只传一个 IP 字符串？**

不同通信域的地址结构不同。通用接口把具体地址结构的指针视为 sockaddr，并另外传入 socklen_t 长度，使 bind、connect 和 accept 等接口能处理多种地址族。IP 文本只是可供人阅读的一部分，不能表达端口、IPv6 scope ID 或 Unix domain 路径等全部信息。

1. **输入地址：**调用方按地址族填充具体结构，再将其地址与实际结构长度传给接口。结构中的 family 必须与创建套接字的域兼容。
2. **输出地址：**调用前提供缓冲区及容量。返回后长度值表示内核写入或需要的地址长度，应用必须按接口契约检查截断。
3. **字节布局：**不可假定不同系统的 sockaddr 具体结构完全一样，也不要用固定 sizeof(sockaddr) 代替实际 sockaddr_in、sockaddr_in6 或 sockaddr_un 的长度。

**Q9: [learning] sockaddr_in 的 family、port、address 分别是什么格式？**

sockaddr_in 表示 IPv4 套接字地址，由协议族、传输端口和 32 位 IPv4 地址共同定位一个网络端点。

1. **sin_family：**填 AF_INET，表示这个结构按 IPv4 地址格式解释。
2. **sin_port：**16 位端口，存为网络字节序。应用以数字端口构造地址时使用 htons，读取后可用 ntohs。
3. **sin_addr：**32 位 IPv4 地址，以网络字节序的地址表示保存。优先使用 inet_pton 或 getaddrinfo 构造，避免把点分十进制文本或主机序整数直接写入该字段。
4. **填充字段：**实现可能有用于结构布局的字段。构造时通常先清零整个结构，再设置必要成员，避免把未初始化字节带给系统调用。

同一端口可因本地 IP、协议和地址族不同而对应不同的绑定关系。端口号本身不能唯一识别一个跨网络进程。

**Q10: [learning] sockaddr_in6 比 IPv4 地址结构多了什么，scope ID 何时不可省略？**

sockaddr_in6 表示 IPv6 端点，包含 family、端口、128 位地址，以及 flowinfo 和 scope ID 等 IPv6 专有信息。端口仍采用网络字节序，128 位地址应由标准解析接口填充。

1. **sin6_family：**填 AF_INET6，避免把 IPv6 地址结构误交给 IPv4 套接字。
2. **sin6_port：**16 位传输端口，使用 htons 和 ntohs 在主机序与网络序之间转换。
3. **sin6_addr：**128 位 IPv6 地址。字符串压缩写法只是文本形式，不能直接复制到二进制字段。
4. **sin6_scope_id：**指定链路本地等带作用域地址所处的网络接口。相同链路本地地址可能出现在不同接口，不指定接口就无法唯一确定目的范围。
5. **sin6_flowinfo：**与 IPv6 流标记有关。普通应用不应猜填，具体使用按平台接口要求处理。

不能因 IPv6 地址更长就只扩大缓冲区。IPv6 文本解析、作用域和接口选择都是额外的语义条件。

**Q11: [learning] inet_pton 与 inet_ntop 分别转换什么，和旧 IPv4 专用转换接口有什么差别？**

inet_pton 把可打印的 IPv4 或 IPv6 地址文本转为二进制地址。inet_ntop 做反向转换。调用者必须同时提供 AF_INET 或 AF_INET6，接口不会从任意字符串猜测协议族。

1. **inet_pton：**返回 1 表示文本有效并已转换，返回 0 表示文本不是该地址族的有效格式，返回 -1 表示调用错误并设置 errno。应分别处理“格式不合法”与“接口调用失败”。
2. **inet_ntop：**需要调用者提供足够长的输出缓冲区。通常按 INET_ADDRSTRLEN 或 INET6_ADDRSTRLEN 选择容量，返回文本指针。容量不足或参数错误时返回 NULL。
3. **旧接口：**inet_addr 和 inet_ntoa 只针对 IPv4，且返回值或静态存储等行为不利于稳健处理。新代码优先使用支持两个地址族的接口。

这里处理的是数值地址文本，不执行 DNS 查询。主机名到地址要交给 getaddrinfo。

**Q12: [learning] gethostent、getnetent、getprotoent 和 getservent 查询的分别是什么？为什么新代码不应把它们作为统一寻址入口？**

这些传统 netdb 接口分别查询主机、网络、协议和服务数据库。它们说明“主机名、协议名、服务名”不是同一个命名空间，但其返回结构和查询行为受系统配置影响，不适合作为现代 IPv4/IPv6 通用解析的唯一入口。

1. **gethostent：**按数据库顺序取得主机记录，相关旧接口可按主机名或地址查询。传统 hostent 表示主机名、别名、地址类型和地址列表。
2. **getnetent：**取得网络数据库记录，涉及网络名称、别名和网络编号，并非查询一个服务端进程。
3. **getprotoent：**取得协议数据库记录，把 TCP 等协议名映射到协议编号，不返回 IP 地址或 TCP 端口。
4. **getservent：**取得服务数据库记录，把服务名和传输协议映射到端口。例如同名服务在 TCP 与 UDP 下可有不同记录。

数据库可能来自本地文件或系统配置的其他来源。面向连接或监听的应用优先用 getaddrinfo 从主机名与服务名取得可直接尝试的地址列表，再用 freeaddrinfo 释放结果。

**Q13: [learning] gethostbyname、gethostbyaddr、getservbyname 和 getservbyport 与 getaddrinfo 的关系是什么？**

这些旧查询接口分别围绕主机记录或服务记录工作。getaddrinfo 则把主机与服务解析统一为可直接给 socket、bind 或 connect 使用的候选地址链，通常更适合新代码处理 IPv4/IPv6。

1. **gethostbyname：**按主机名查传统 hostent 记录。不能仅凭名字推断全部 IPv6 地址与目标连接能力。
2. **gethostbyaddr：**按二进制地址查询主机记录，属于反向名字查询，不证明结果名称可信。
3. **getservbyname：**按服务名及协议名查询端口记录，不能替代主机地址解析。
4. **getservbyport：**按端口及协议名查询服务记录，返回的是数据库登记名称，不证明该端口上真的有进程监听。

getaddrinfo 与 getnameinfo 覆盖现代应用常见的正向和反向转换。旧接口在历史代码中仍需识别，但不应把名称数据库记录当作远端服务状态。

**Q14: [learning] hostent、netent、protoent 和 servent 结构里的名称、别名、编号分别指什么？**

四种结构记录的是不同数据库对象。都可能带主名称和别名，但其编号或地址字段不能互换。

1. **hostent：**h_name 是规范主机名，h_aliases 是别名列表，h_addrtype 和 h_length 描述地址类型与长度，h_addr_list 保存二进制地址列表。一个主机可有多个地址。
2. **netent：**n_name 和 n_aliases 标识网络名称，n_addrtype 标识地址类型，n_net 是网络编号，不是某台主机的完整地址。
3. **protoent：**p_name 和 p_aliases 标识协议名称，p_proto 是协议编号，不是应用服务端口。
4. **servent：**s_name 和 s_aliases 标识服务名称，s_port 是网络字节序的端口值，s_proto 指定 TCP 或 UDP 等传输协议名称。

这些传统记录可帮助读懂旧代码，但不能从数据库记录推断主机在线、端口可达或业务已通过认证。

**Q15: [learning] gethostent 等逐条查询接口为什么还有 set*ent 与 end*ent 配套函数？**

传统 netdb 接口可按数据库顺序逐条枚举记录。对应的 sethostent、setnetent、setprotoent、setservent 用于开始或重置某类数据库遍历，endhostent、endnetent、endprotoent、endservent 用于结束该类查询并释放相关资源。

1. **开始遍历：**set*ent 可重置读取位置，某些接口还允许提示是否在连续查询间保持数据库打开。
2. **取得记录：**重复 get*ent，直到返回空指针或查询结束。返回的存储可能由库内部管理，不能默认长期持有指针。
3. **结束遍历：**调用相应 end*ent 清理数据库访问状态。不同类别各有自己的函数，不用主机数据库关闭函数替代服务数据库关闭函数。

现代多线程和 IPv4/IPv6 通用客户端通常优先用 getaddrinfo/getnameinfo。旧枚举 API 的线程安全性与数据库来源需按 libc 版本核对。

**Q16: [learning] getaddrinfo 如何把主机名与服务名解析为可用的套接字地址？**

getaddrinfo 把 node 和 service 转为 addrinfo 结果链表。每个结果同时给出地址族、套接字类型、协议、地址指针及长度，使客户端可以逐项尝试连接，服务器可以选择合适地址绑定。node 与 service 至少提供一个。

使用结果的关键步骤是：

1. **给定限制：**用 hints 约束 ai_family、ai_socktype、ai_protocol 和需要的 ai_flags。未指定地址族时可能得到 IPv4 与 IPv6 等多个候选，不应只取第一项就假定必定可用。
2. **遍历结果：**对每项使用它自己的 ai_family、ai_socktype、ai_protocol 创建 socket，再使用 ai_addr 与 ai_addrlen 调用 bind 或 connect。失败时关闭该 fd，再尝试下一项。
3. **处理错误：**getaddrinfo 返回的是 EAI 系列错误码，不按普通系统调用的 -1/errno 契约报告一般解析错误。可用 gai_strerror 解释该返回码。
4. **释放结果：**用 freeaddrinfo 释放成功返回的结果链表。链表内的地址指针随之失效，不能继续保存并引用它。

解析结果只给出候选地址。DNS 成功不证明目标服务在监听，也不证明连接可以建立。

**Q17: [learning] getaddrinfo 的 AI_PASSIVE、AI_CANONNAME、AI_NUMERICHOST、AI_NUMERICSERV、AI_ADDRCONFIG 和 AI_V4MAPPED 各改变什么？**

这些标志放在 hints.ai_flags 中，用于约束地址生成或解析行为。是否支持、默认行为和不同 libc 的细节需以目标系统手册为准。

1. **AI_PASSIVE：**为 bind 生成适合被动监听的地址。node 为 NULL 时通常产生通配本地地址。不设置时，NULL node 通常产生环回地址，适合仅本机访问。
2. **AI_CANONNAME：**请求返回规范主机名，结果中的 ai_canonname 不应被当成已经验证的服务身份。
3. **AI_NUMERICHOST：**要求 node 是数值地址，不再把它作为主机名解析。适用于必须避免名字服务查询的场景。
4. **AI_NUMERICSERV：**要求 service 是数字端口，不再查询服务名数据库。
5. **AI_ADDRCONFIG：**按本机已配置的地址族筛选结果。它可能受本机接口配置影响，测试只有环回接口的环境时要核对实际结果。
6. **AI_V4MAPPED：**在请求 IPv6 结果且条件满足时，允许以 IPv4 映射 IPv6 地址表示 IPv4 目标。它与 IPv6 套接字是否允许双栈连接还受平台配置影响。

标志不提供远端可达性保证。服务器是否对外开放，还取决于实际 bind 地址、防火墙和网络命名空间。

**Q18: [learning] getnameinfo 如何把套接字地址转换成主机名和服务名，为什么日志常用数字形式？**

getnameinfo 接收完整的 sockaddr 及其长度，将其转换为主机和服务的可读字符串。它是 getaddrinfo 的反向入口，但“地址转名字”可能涉及反向解析或服务数据库查询，结果不等于对端真实身份。

1. **主机输出：**调用者提供字符缓冲区及长度。NI_NUMERICHOST 要求直接输出数值地址，避免反向名字查询。
2. **服务输出：**调用者提供独立缓冲区及长度。NI_NUMERICSERV 要求输出数字端口，不查询服务名。
3. **错误处理：**函数返回 EAI 系列状态码，不能只检查 errno。缓冲区不足应增大容量或按需要改用数字输出。

诊断日志优先记录数字地址、端口和地址族。反向 DNS 可能慢、缺失或受环境影响，且解析得到的名字不是安全认证证据。

**Q19: [learning] bind 将什么关联到套接字，为什么服务端常调用它？**

bind 把本地通信地址关联到一个已创建的套接字。服务器需要客户端按稳定地址找到它，因而通常在 listen 或接收数据报前 bind。客户端未显式 bind 时，IP 协议栈通常在 connect 或首次发送时选择本地地址与临时端口。

1. **sockfd：**必须是已创建且适用于该地址族的套接字描述符。
2. **addr：**指向具体地址结构，经 sockaddr 指针传入，结构的地址族须与套接字兼容。
3. **addrlen：**传入实际地址结构长度，不是地址文本的字符数。

绑定可能因地址已占用、权限不足或地址不属于本机而失败。bind 成功说明本地命名完成，不表示网络接口可达，也不表示服务器已开始监听。

**Q20: [learning] 通配 IP 地址、环回地址、端口 0 和固定端口分别意味着什么？**

bind 的本地地址选择决定服务监听范围与端口取得方式。四种常见选择回答的是不同问题：监听哪些接口，以及端口由谁分配。

1. **通配地址：**IPv4 的 INADDR_ANY 或 IPv6 的通配地址表示接收适用本地接口上的连接。它不等于自动开放给外部，实际还受路由、防火墙、命名空间及 IPv6 双栈配置影响。
2. **环回地址：**只在本机相应环回接口可达。若服务仅供本机进程使用，它比通配监听缩小了网络暴露面。
3. **端口 0：**请求内核分配可用临时端口。bind 成功后用 getsockname 查询实际端口，不能把 0 当作服务的对外端口。
4. **固定端口：**给客户端稳定入口，但必须处理占用冲突与特权端口限制。

服务发现还需告诉客户端最终地址。只绑定通配地址不产生可供远端直接连接的具体目的 IP。

**Q21: [learning] getsockname 与 getpeername 各查询哪一端地址？**

getsockname 查询当前套接字的本地地址。getpeername 查询已关联的对端地址。它们读取内核维护的地址状态，不做服务名解析。

1. **本地地址：**客户端自动分配端口后，或服务器 bind 端口 0 后，用 getsockname 确认实际地址与端口。
2. **对端地址：**流连接建立或 accept 成功后，可用 getpeername 查询与该连接关联的对端地址。
3. **缓冲区契约：**调用方传入 sockaddr 缓冲区及容量指针，返回的长度需按实际地址族解释。

地址只能表明协议栈观察到的端点。NAT、代理或 Unix domain 路径命名会改变它与业务用户身份的关系，不能用地址代替认证。

**Q22: [learning] 面向连接的客户端调用 connect 时发生什么，成功返回能证明什么？**

connect 为流式套接字发起与指定对端的连接。对 TCP 而言，阻塞调用成功表示传输连接已建立，可以开始收发字节。它不证明应用协议握手、用户鉴权或服务端业务处理成功。

调用方必须提供对端 sockaddr 与实际长度。连接失败要按错误原因区分：

1. **地址或路由不可达：**先检查目标地址、本地选路和过滤规则。
2. **连接被拒绝：**可能是目标端口没有监听，或网络设备主动拒绝。
3. **超时：**说明建立阶段未在规定时间内完成，不能只凭超时断定服务进程不存在。

Linux 手册指出 connect 失败后套接字状态可能不适合继续重试。稳健做法是关闭失败 fd，为下一次地址尝试或重试新建套接字。

**Q23: [learning] connect 遇到瞬时失败时怎样重试，为什么不能对所有错误无限重连？**

重试只适合可能随时间恢复的故障，且每次应有明确超时、次数和退避。对配置错误、权限拒绝或地址格式错误持续重连只会增加负载，并掩盖真正原因。

1. **先分类：**记录目标候选地址及 errno，区分拒绝、超时、网络不可达和参数错误。
2. **重建状态：**失败连接的 fd 关闭后重新 socket，再尝试下一地址或稍后重试同一地址。
3. **限制频率：**对瞬时失败采用有上限的退避，避免大量客户端同时重连造成服务端雪崩。
4. **保留边界：**总时限到了应向上层报告失败。连接成功后还要分别验证协议握手与业务响应。

**Q24: [learning] 非阻塞 connect 返回 EINPROGRESS 后如何判断连接最终是否建立？**

对设为 O_NONBLOCK 的流套接字，connect 可能立即返回 -1 和 EINPROGRESS，表示连接正在进行，并非已经失败或成功。应用应等待该 fd 可写，再用 getsockopt 读取 SOL_SOCKET 层的 SO_ERROR 判断最终结果。

1. **启动：**先设置非阻塞，调用 connect。立即返回 0 表示已经完成。EINPROGRESS 表示继续等待。
2. **等待：**用 poll、select 或其他就绪机制观察可写，同时设置总体连接超时。
3. **裁决：**可写只表示连接过程有结果。SO_ERROR 为 0 才能当作连接成功，非 0 则是连接错误。

不能把 poll 报可写当作 TCP 已连通的充分条件。超时后关闭 fd，避免连接仍在后台完成而业务却认为已取消。

**Q25: [learning] 对数据报套接字调用 connect 是否建立了 TCP 式连接？**

不是。对常见的 UDP 数据报套接字，connect 在内核中设置默认发送目的和接收来源过滤条件，不执行 TCP 三次握手，也不把 UDP 变成可靠流。之后可以用 send 与 recv，而不必每次调用 sendto 都给目的地址。

1. **目的选择：**未 connect 的数据报套接字通常每次 sendto 指定目的地址。connect 后默认目的固定，后续是否可重新关联取决于协议和平台。
2. **接收过滤：**内核只把与关联对端匹配的数据报交给该套接字，减少应用自己筛选来源的工作。
3. **失败边界：**UDP connect 返回成功不证明目标服务存在。后续错误可能在发送或接收阶段才暴露。

应用层仍需按需求处理超时、重复、乱序与认证。数据报套接字的 connect 是关联端点，不是交付保证。

**Q26: [learning] listen 将套接字变成什么状态，backlog 控制的是什么？**

listen 让已绑定的面向连接套接字接受连接请求。该 fd 成为监听套接字，供 accept 取得已建立的客户端连接。backlog 是内核用于未被应用 accept 的待处理连接队列的请求值，不是服务器最多能服务的客户端总数。

1. **调用顺序：**典型服务器先 socket，后 bind，再 listen。只 bind 而不 listen 的 TCP 服务不会按流服务器方式接受连接。
2. **backlog：**实际生效值可被内核上限和协议实现调整。Linux TCP 对已完成握手、等待 accept 的连接队列使用 backlog，未完成握手队列还有独立的内核策略。
3. **容量边界：**队列满后的客户端表现取决于内核配置和协议，可能等待、重试或失败。不能把 backlog 写成精确的并发连接上限。

**Q27: [learning] accept 返回的 fd 与监听 fd 有什么区别，客户端地址从哪里取得？**

accept 从监听套接字队列取出一个连接，并返回新的已连接 fd。原监听 fd 继续接收其他客户端，新 fd 专供本次连接的收发。这两个 fd 的生命周期和用途必须分开。

1. **监听 fd：**通常长期保留在服务端，继续调用 accept 或被就绪机制监视。
2. **连接 fd：**每个成功 accept 的连接都有自己的 fd，服务端通过它与相应客户端收发数据，完成后关闭。
3. **对端地址：**可向 accept 提供 sockaddr 缓冲区和长度指针以接收客户端地址。不需要地址时，两者都可传 NULL。之后也可用 getpeername 查询。

连接地址不是业务身份。多客户端服务必须按连接维护独立状态，不能把最后一次 accept 的客户端地址当成所有连接的对端。

**Q28: [learning] 阻塞与非阻塞 accept 在没有待处理连接时分别怎样表现？**

阻塞监听 fd 上的 accept 通常等待连接到达。非阻塞监听 fd 若当前没有可取连接，则返回 -1，并把 errno 设为 EAGAIN 或 EWOULDBLOCK。这是“暂时没有工作”，不应记录成永久故障。

1. **阻塞模型：**适合简单服务或由专门线程等待新连接，必须确保停止服务时能够解除等待。
2. **就绪模型：**poll 或 select 提示监听 fd 可读时再 accept。多个连接可能已排队，通常循环 accept 到 EAGAIN，以免遗漏当前批次。
3. **竞态：**就绪提示与 accept 之间状态可能改变。监听 fd 设为非阻塞，才能避免这种竞态使事件循环意外卡住。

Linux accept4 可按请求为新 fd 设置 SOCK_NONBLOCK 或 SOCK_CLOEXEC。它是 Linux 扩展，跨 POSIX 平台需确认支持。

**Q29: [learning] 什么时候选字节流，什么时候选数据报？**

选择取决于应用是否需要内核提供有序字节流，以及业务是否需要保留独立消息边界。通信域和具体协议仍会改变可靠性、大小限制及权限条件。

1. **字节流：**适合需要连续、有序数据且能自行定义消息帧的协议。TCP 帮助处理丢包重传与顺序，但应用仍需定义一条业务消息何时结束。
2. **数据报：**适合消息天然独立、大小有上限的通信。每次发送是一个报文，接收可保留边界。若选 UDP，应用必须决定丢包、重复、乱序和超时对业务是否可接受。
3. **顺序分组：**当需要连接、顺序及消息边界同时成立时，可核对目标域是否支持 SOCK_SEQPACKET，而不是假定 TCP 会保存 write 边界。

不能用“面向连接一定可靠、无连接一定不可靠”代替具体协议判断。Linux Unix domain 数据报就是反例。

**Q30: [learning] 已连接套接字为什么既能用 read/write，也能用 send/recv？**

套接字有 fd，因此普通顺序 I/O 接口可以在适用场景中收发数据。send 与 recv 家族在此基础上提供每次调用的标志、目标或来源地址，以及辅助数据能力。

1. **read/write：**处理字节或数据报的基本收发，不提供套接字专用的 flags 参数。
2. **send/recv：**对已连接套接字，flags 为 0 时一般接近 write/read。差异在于可加 MSG_DONTWAIT、MSG_PEEK 等单次调用控制，具体标志按协议与平台支持判断。
3. **sendto/recvfrom：**处理逐报文目的或来源地址，常见于未连接的数据报套接字。
4. **sendmsg/recvmsg：**支持分散缓冲区、目标或来源地址、控制消息等复合信息。

选择 API 应由所需信息决定，不能因为 read/write 能工作就忽略短读、短写或消息边界。

**Q31: [learning] send 返回成功的字节数能证明什么，为什么流套接字还要处理短写？**

send 的非负返回值表示本次调用被本地套接字层接受处理的字节数。它不证明对端进程已经读取、处理或持久化数据，也不自带远端交付失败通知。流套接字一次调用可能只接收部分待发字节。

1. **部分发送：**返回值小于请求长度时，应用应从未发送的偏移继续发送，直到业务帧全部交给内核或发生错误。
2. **暂不可写：**非阻塞 fd 在发送缓冲暂不能接收更多数据时可返回 EAGAIN 或 EWOULDBLOCK，等待可写后继续。
3. **连接破裂：**向已关闭读端的流连接发送可能触发 SIGPIPE，并返回 EPIPE。Linux 可用单次调用的 MSG_NOSIGNAL 避免信号，仍须处理错误返回。
4. **交付确认：**要证明业务处理成功，必须由应用协议设计响应、序号或其他确认，不能把 send 成功当作业务 ACK。

**Q32: [learning] sendto 比 send 多了什么，什么时候需要显式目的地址？**

sendto 在发送缓冲区、长度和 flags 之外，还接收目标 sockaddr 与地址长度。它主要用于未 connect 的数据报套接字，让每条报文可以指定不同目的地。

1. **未关联对端：**每次 sendto 给出目的地址，内核按该地址路由报文。
2. **已关联对端：**通常可用 send，不必重复写目的地址。对已连接流套接字提供非空目的地址的行为应按接口规则处理，不能用 sendto 任意更换连接对端。
3. **单报文限制：**对数据报而言，一次调用是一条消息。超过协议允许的原子发送长度可能报 EMSGSIZE，不能假定内核会透明拆成多个业务数据报。

目的地址只决定传输目标，远端是否存在、能否处理仍需上层确认。

**Q33: [learning] msghdr 与 iovec 各组织哪部分数据，sendmsg 能额外发送什么？**

sendmsg 用 msghdr 描述一次发送请求。iovec 数组把消息正文分成多个内存片段，避免调用方为了拼出连续缓冲区而额外复制。msghdr 还可以携带目标地址和辅助控制消息。

1. **msg_name/msg_namelen：**可选目标地址及其长度，主要用于需要逐次指定对端的通信。
2. **msg_iov/msg_iovlen：**iovec 数组及元素个数。每个 iovec 用基址与长度描述一段正文，内核按数组顺序处理。
3. **msg_control/msg_controllen：**控制消息缓冲区及字节数。Unix domain 描述符传递、凭据等不属于普通消息正文，就放在这里。
4. **flags 参数：**控制本次 sendmsg 的发送行为，与 msghdr 里的输出状态字段不是同一用途。

分散发送减少应用侧拼包，不改变 TCP 是字节流的事实。对端仍可能用多次读取取得这批正文。

**Q34: [learning] recv 默认等到什么程度才返回，MSG_PEEK、MSG_DONTWAIT 与 MSG_WAITALL 分别改变什么？**

recv 通常在有可用数据时返回实际读取的字节数，不保证填满调用者给出的缓冲区。单次调用标志可改变观察或等待方式，但不能替代应用协议的消息长度定义。

1. **MSG_PEEK：**查看接收队列中的数据而不从队列移除。其他线程或后续报文可能改变下次读取结果，不能把窥视结果当成永久预留。
2. **MSG_DONTWAIT：**仅本次接收按非阻塞方式尝试。没有数据时返回 EAGAIN 或 EWOULDBLOCK，不等于连接关闭。
3. **MSG_WAITALL：**对适用的流套接字尽量等待指定字节数，但信号、错误或连接关闭等情况仍可导致提前返回。调用者仍要检查实际返回长度。

对数据报，接收单位是报文。读取缓冲区过小可能丢弃报文剩余部分，不能用多次 recv 像流一样续读同一报文。

**Q35: [learning] recv 返回 0、EAGAIN 和正数分别意味着什么？**

返回值必须结合套接字类型、请求长度和状态解释。对请求读取正数长度的 TCP 字节流，recv 返回正数表示实际得到的字节数，返回 0 通常表示对端有序关闭写方向且已排队数据读完。非阻塞时暂时无数据则是 -1 与 EAGAIN/EWOULDBLOCK，不是 EOF。

1. **正数：**只处理返回的实际长度。它可短于期望长度，并不自动构成完整业务消息。
2. **流式 0：**按协议结束或半关闭处理，仍要考虑本端是否需要发送剩余响应。请求长度本身为 0 时不能用返回 0 推断 EOF。
3. **数据报 0：**零长度数据报是合法消息，因此不能直接套用 TCP 的 EOF 规则。
4. **-1：**检查 errno。EINTR、EAGAIN、连接错误或参数错误的处理方式不同。

**Q36: [learning] recvfrom 返回发送方地址时，地址缓冲区和长度参数怎样配合？**

recvfrom 可在接收数据报的同时返回发送方地址。调用前将地址长度变量设为缓冲区容量，调用后再按返回长度和地址族解释结果。

1. **数据缓冲区：**返回值是此次接收的正文长度，不能以字符串结尾符判断。二进制或零长度报文均可能出现。
2. **src_addr：**指向存放发送方 sockaddr 的缓冲区。无需来源地址时可传 NULL，并按接口要求让长度指针也为 NULL。
3. **addrlen：**输入时是容量，输出时反映实际地址长度。传错大小可能造成地址截断或无法正确识别。

来源 IP 与端口是网络层观察值，可能经过 NAT 或代理。应用不能只凭它授权危险操作。

**Q37: [learning] recvmsg 怎样同时取得正文、来源地址和辅助数据？**

recvmsg 把一次接收的不同部分填入 msghdr：正文进入 iovec 指向的缓冲区，来源地址进入 msg_name，控制消息进入 msg_control。函数返回正文长度，控制区长度和 msg_flags 还需单独检查。

1. **接收前：**设置每个 iovec 的容量、地址缓冲区容量及控制缓冲区容量。没有准备控制区就无法可靠接收描述符或凭据。
2. **接收后：**按返回的正文长度解释数据，按 msg_namelen 解释来源地址，按 msg_controllen 遍历收到的控制消息。
3. **截断标志：**MSG_TRUNC 表明数据报正文可能被截断，MSG_CTRUNC 表明辅助数据空间不足。传递文件描述符时若忽略控制区截断，可能丢失资源或错误理解消息。

msghdr 的 msg_flags 是接收后的状态信息，不应与传给 recvmsg 的调用标志混为一谈。是否提供某类控制消息还取决于套接字域和协议。

**Q38: [learning] recvmsg 的 MSG_EOR、MSG_TRUNC 与 MSG_CTRUNC 各报告哪一类接收结果？**

这三个标志出现在接收后的 msghdr.msg_flags 中，分别描述记录结束、正文截断和辅助数据截断。它们不等于 recvmsg 的返回字节数，也不能互相代替。

1. **MSG_EOR：**在支持记录语义的套接字与协议上标明本次数据达到一条记录的结尾。TCP 字节流不因一次 sendmsg 就自动产生业务记录边界。
2. **MSG_TRUNC：**说明一条数据报的正文大于提供的正文缓冲区。应用应按协议拒绝不完整消息，不能把收到的前缀当成完整请求。
3. **MSG_CTRUNC：**说明控制消息缓冲区不足，辅助数据已截断。接收 fd 或凭据时必须检查，否则可能只看到一部分控制信息。

是否能取得原始完整报文长度，取决于具体协议和所用接收标志，不能只由 MSG_TRUNC 这一位推出。

**Q39: [learning] 为什么一次 write 不对应一次 read，流式协议要怎样划定业务消息边界？**

SOCK_STREAM 只保证按顺序交付字节，不保留应用的 write 或 send 调用边界。一次发送可能被多次读取，一次读取也可能包含多次发送的内容。接收端必须按自己的协议识别完整消息。

常见的成帧方法按消息特征选择：

1. **固定长度：**所有消息结构等长。接收端循环读取，直到累积到规定字节数。
2. **长度前缀：**先读取固定格式的长度字段，再按长度读取正文。必须限制最大长度，避免恶意长度耗尽内存。
3. **分隔符：**读取到换行等转义明确的分隔符才算一条消息。正文若可包含分隔符，就需要转义或编码规则。
4. **关闭界定：**协议约定发送方半关闭或断开表示正文结束。适用于一次性响应，但不支持在同一连接上自然区分多个请求。

TCP 的有序性只解决字节顺序，不替应用定义“一个命令从哪里到哪里”。

**Q40: [learning] 数据报接收缓冲区不足时会发生什么，为什么不能按字节流方式补读剩余部分？**

数据报保留一条消息的边界。一次 recv、recvfrom 或 recvmsg 接收一条报文时，若缓冲区不足，超出部分通常会按具体协议与调用方式被丢弃或以截断状态报告。下一次接收取的是下一条报文，不是上一条的剩余字节。

1. **发送前限制：**协议规定最大报文长度，防止接收端被任意大消息占用内存。
2. **接收时辨别：**使用目标平台支持的 MSG_TRUNC 等能力检查是否截断，并拒绝把不完整报文当作合法请求。
3. **需要大数据时：**按应用协议分块，给每块序号、总量与重组期限，或改用适合连续传输的流式协议。

数据报最大长度还受传输协议、路径 MTU 与系统实现影响，不能只用应用缓冲区大小推断网络一定能发送成功。

**Q41: [learning] setsockopt 与 getsockopt 的 level、option、value、length 各承担什么角色？**

套接字选项让应用设置或查询内核对某个端点的行为。level 选择选项所属层，optname 选择具体选项，值缓冲区及其长度承载该选项要求的数据类型。

1. **level：**SOL_SOCKET 表示通用套接字层。IPPROTO_TCP、IPPROTO_IP 等表示具体协议层，不能把不同层的同名行为混用。
2. **optname：**指定选项，例如 SO_REUSEADDR。选项是否可用于某个域与类型取决于系统实现。
3. **optval：**设置时指向输入值，查询时指向输出缓冲区。布尔选项常用 int，但并非所有选项都使用 int。
4. **optlen：**设置时是输入值字节长度，查询时先给容量，返回实际长度。传错长度可能得到 EINVAL 或错误解释结果。

某些选项必须在 bind、listen 或 connect 之前设置才能影响对应阶段。设置成功不代表所有协议或设备都按应用预期运行，需用查询和实际行为验证。

**Q42: [learning] SO_REUSEADDR 解决什么问题，为什么它不等于允许任意两个服务同时绑定同一端口？**

SO_REUSEADDR 放宽某些本地地址重用条件，常用于服务重启后的绑定场景。它的具体作用依系统、协议、是否绑定通配地址及先前套接字状态而不同，不能把它理解为“端口占用一律可绕过”。

1. **设置时机：**通常在 bind 前设置。bind 后才设置不能补救已经失败的绑定。
2. **重启场景：**TCP 服务退出后，既有连接和 TIME_WAIT 可能影响新实例对相同本地地址的绑定，具体能否复用按内核规则判断。
3. **同端口多监听：**Linux 的 SO_REUSEPORT 是另一种选项，具有自己的绑定与权限规则。SO_REUSEADDR 不自动赋予任意进程共同监听同一地址与端口的能力。

遇到 EADDRINUSE，应先确认地址族、绑定 IP、存活进程与连接状态，再决定是否使用复用选项。不要为了绕过错误盲目开启。

**Q43: [learning] SO_TYPE、SO_ERROR 与 SO_KEEPALIVE 分别查询或改变什么？**

这三个通用套接字选项分别用于确认端点类型、读取待处理错误和启用连接存活探测，作用不应混为一谈。

1. **SO_TYPE：**只读查询当前套接字类型，例如 SOCK_STREAM 或 SOCK_DGRAM。它不返回实际协议名、连接状态或远端身份。
2. **SO_ERROR：**只读取得并清除挂起的套接字错误。非阻塞 connect 完成通知后，应读取此值判断成功还是失败，不能只看可写事件。
3. **SO_KEEPALIVE：**对支持的面向连接协议启用内核保活探测。它用于探测长时间无活动的失效连接，不是应用请求的业务响应确认，也不能替代心跳语义。

选项可用性和保活计时参数依协议与系统实现决定。没有启用保活也不意味着正常 TCP 数据完全不检查连接错误。

**Q44: [learning] SO_RCVBUF、SO_SNDBUF、SO_RCVLOWAT 与 SO_SNDLOWAT 分别控制哪一层缓冲和阈值？**

缓冲区选项影响内核收发队列容量，低水位选项影响何时认为数据量达到可交付阈值。它们不是应用消息长度或网络链路带宽的声明。

1. **SO_RCVBUF：**设置或查询接收缓冲区容量。Linux 可能为管理开销调整报告值，并受系统上限限制。
2. **SO_SNDBUF：**设置或查询发送缓冲区容量。增大容量可容纳更多待发数据，但不能保证对端处理更快，也可能增加排队延迟。
3. **SO_RCVLOWAT：**接收低水位，影响部分读取及就绪判断。Linux 的 poll/select 对它的支持有版本边界，目标系统需核对。
4. **SO_SNDLOWAT：**发送低水位。Linux 手册明确其值不能通过 setsockopt 修改，不能把教材中的名称当成可调参数。

遇到大消息、短读或高延迟，应先区分应用成帧、传输窗口、内核队列和对端处理瓶颈，再决定是否调整缓冲。

**Q45: [learning] SO_RCVTIMEO、SO_SNDTIMEO 和 SO_LINGER 分别限制什么等待？**

前两个选项约束阻塞套接字 I/O 调用的等待时间，SO_LINGER 则影响关闭时对未完成发送的处理。它们并不共同构成一个完整的业务请求截止时间。

1. **SO_RCVTIMEO：**接收操作阻塞达到超时时间且没有取得数据时可返回 EAGAIN/EWOULDBLOCK。若已取得部分数据，调用仍可能返回实际长度。
2. **SO_SNDTIMEO：**发送操作阻塞达到超时时间时按类似规则返回。它不证明已发送字节被远端应用读取。
3. **SO_LINGER：**由启用标志和秒数构成。启用后，close 或 shutdown 的返回时机可受排队数据发送完成或超时约束。具体异常关闭语义还应按协议与平台验证。

Linux 的接收与发送超时不改变 poll/select 自己的等待超时。应用若要求“请求从开始到收到响应最多 3 秒”，仍应维护覆盖解析、重试与收发全过程的截止时间。

**Q46: [learning] SO_BROADCAST、SO_DONTROUTE、SO_DEBUG 与 SO_OOBINLINE 分别适用于什么场景？**

这些选项处理不同的协议能力与调试需求，不能因为同属 SOL_SOCKET 就统一开启。

1. **SO_BROADCAST：**允许适用的数据报套接字向广播地址发送。它不让流套接字变成广播通道，也不保证交换机或网络允许广播通过。
2. **SO_DONTROUTE：**要求适用的发送尽量只到直接连接的目标，不经网关。它不能代替路由表或完整网络隔离策略。
3. **SO_DEBUG：**请求内核启用协议调试信息，支持与权限依平台而异。正常业务不应依赖它改变交付语义。
4. **SO_OOBINLINE：**让 TCP 紧急字节留在正常接收流中。它只影响带外数据的接收表示，不提供真正的业务优先级调度。

**Q47: [learning] TCP 的带外数据和紧急标记是什么，为什么不宜把它当成通用高优先级业务通道？**

TCP urgent 机制用紧急指针在同一字节流中标记一个位置。套接字 API 可通过 MSG_OOB、SO_OOBINLINE 和 sockatmark 暴露相关行为，但这不是一条独立、可靠抢占普通数据的高速通道。

1. **发送：**MSG_OOB 请求使用该协议的带外能力。TCP 各系统对紧急字节的处理存在兼容差异，不能推断整段“紧急消息”会优先到达。
2. **接收：**SO_OOBINLINE 决定紧急字节是否留在普通接收流中，sockatmark 可判断当前读取位置是否到达紧急标记附近。
3. **通知：**Linux 可将 SIGURG 交给指定进程或进程组，但信号只提示状态变化，不替代读取、边界解析或业务确认。

新协议若需要高优先级命令，应明确调度、队列、超时和确认机制，不应把 TCP urgent 误当成通用 QoS 保证。

**Q48: [learning] O_NONBLOCK、MSG_DONTWAIT、poll/select 和信号驱动 I/O 分别解决什么问题？**

这些机制分别控制一次调用是否等待、如何得知 fd 可能可操作，以及是否由信号通知进程。它们不是同一层的“异步”开关。

1. **O_NONBLOCK：**通过 fcntl 设置在打开文件描述上的非阻塞状态，使后续适用 I/O 调用不能立即完成时返回 EAGAIN/EWOULDBLOCK。共享同一打开文件描述的 fd 可能互相影响。
2. **MSG_DONTWAIT：**Linux 发送或接收调用的单次非阻塞标志，不永久改变 fd 的状态。
3. **poll/select：**等待多个 fd 出现可读、可写或异常条件。就绪只说明操作值得尝试，实际调用仍可能得到 EAGAIN，因此事件循环通常配合非阻塞 fd。
4. **信号驱动 I/O：**设置接收通知的进程或进程组并启用相关异步标志后，内核可用 SIGIO 等信号提示事件。信号处理复杂且仍要真正读取数据，不等于内核自动完成读写。

非阻塞返回是控制流的一部分，不是故障。服务端选择模型时还应考虑连接数、取消、超时和清理方式。

**Q49: [learning] F_SETOWN、F_GETOWN、O_ASYNC、SIGIO 和 SIGURG 在信号驱动套接字 I/O 中如何分工？**

信号驱动 I/O 先指定谁接收信号，再启用相应通知，事件到来时应用仍需执行实际收发。它与内核替应用完成异步读写不同。

1. **F_SETOWN：**通过 fcntl 指定接收相关套接字信号的进程或进程组。目标不是通信对端，而是本机被通知者。
2. **F_GETOWN：**查询当前配置的信号接收目标。
3. **O_ASYNC：**启用 I/O 状态变化时的信号通知。应用还需安装合适的信号处理逻辑，并处理事件合并与竞态。
4. **SIGIO：**提示普通 I/O 就绪相关事件。收到它只说明应该检查端点状态，不能推断数据已经读入应用缓冲区。
5. **SIGURG：**与支持带外或紧急数据的协议事件有关。它不为普通业务消息提供队列优先级保证。

信号处理函数应遵守异步信号安全限制。复杂服务通常选择可统一管理超时与连接状态的事件循环，而不是在信号处理函数中解析完整请求。

**Q50: [learning] 一个 TCP 服务器从启动到处理多个客户端，套接字调用顺序与职责边界是什么？**

典型顺序是 socket → bind → listen → accept → 在连接 fd 上收发 → close 连接 fd，退出时再 close 监听 fd。每一步只建立下一步所需的状态，不应把 bind 成功当作已经接受客户端。

1. **准备监听：**通过 getaddrinfo 或明确地址得到绑定参数，创建套接字，必要时在 bind 前设置选项，再 listen。
2. **取得连接：**accept 每次产生一个已连接 fd。监听 fd 保持开放，继续服务其他客户端。
3. **处理请求：**对子连接按协议成帧、限制长度、处理短读与短写，并把业务响应与传输成功区分。
4. **并发与清理：**可为客户端分配线程或进程，也可用非阻塞事件循环。任何模式都要管理连接状态、超时、fd 上限和关闭路径。

示例程序里的 fork、exec、dup2 只是处理方式之一，不是所有服务器必须采用的结构。

**Q51: [learning] 无连接数据报服务器的接收与回复为什么必须保存每条请求的发送方地址？**

未 connect 的数据报服务器通常先 socket、bind，然后循环 recvfrom 取出请求及该报文的发送方地址，再用 sendto 把响应发回该地址。单个 socket 可处理多个发送方，但地址必须和对应请求一起保存。

1. **请求身份：**recvfrom 的地址回答这条报文从哪个传输端点到达，不等于该发送方已通过业务鉴权。
2. **回复关联：**并发处理时应连同请求 ID 保存地址。若只用“最近一个客户端地址”，迟来的处理结果可能发给错误客户端。
3. **失败与重试：**UDP 发送成功不代表对端收到。若业务要求可靠结果，需要应用层超时、去重、重传和完整性校验。

零长度报文也可以是合法请求。不能把 recvfrom 返回 0 与 TCP 连接关闭混淆。
