# 中断与下半部

> 通用操作系统中断处理学习资料。边界：本文回答“中断上半部与下半部的分工、softirq/tasklet/workqueue 三种延迟机制、中断上下文的睡眠约束、线程化中断与观测入口”；Linux 启动期与设备驱动的 open/read 分发见 [../01-android/10-原生层/02-驱动运行时.md](../../01-android/10-原生层/02-驱动运行时.md)。机制按本地 Linux 内核树（AAOS13_kernel/common，include/linux/interrupt.h 与 kernel/softirq.c）核对。Q 序列即结构，供 atlas 同源直读。

**Q1: [learning] 中断处理为什么要分成上半部与下半部？**

上半部要快，下半部要做完：硬件中断发生时 CPU 必须尽快响应并返回，否则同线或同 CPU 上的其他中断被延迟、系统响应性下降。但设备的数据搬运、协议解析往往远超“快速”的范围。因此内核把中断处理拆成两段——上半部（hardirq）只做应答硬件、读取状态、把数据摘下来登记，然后立刻让出 CPU。剩下的耗时工作推迟到下半部在更宽松的环境里完成。

两段的职责与约束如下：

1. **上半部（hardirq）**：运行在硬件中断上下文，对应驱动经 request_irq 注册的 handler。它在一个关闭（或屏蔽）本中断的环境里执行，通常不做耗时工作，也不能睡眠。上半部的耗时直接体现为其他中断的延迟，这是它必须短小的根本原因。
2. **下半部（bottom half）**：承载被推迟的工作。内核提供 softirq、tasklet 与 workqueue 三种机制，执行上下文与可执行的操作各不相同，按工作是否需要睡眠选择。
3. **判定边界**：不是所有设备都显式分两段。工作极短的中断（例如应答一个寄存器位）可以在上半部直接完成。分段的收益来自“响应及时”与“处理充分”两个目标之间的冲突强度。

依据：本地内核树 include/linux/interrupt.h 的 irqaction 定义（handler 与 thread_fn 并存）与 kernel/softirq.c。

**Q2: [learning] softirq、tasklet 与 workqueue 三种延迟机制怎么选？**

选择取决于工作能否睡眠：需要睡眠（分配内存、拿互斥锁、做 I/O）就必须用 workqueue。不需要睡眠的短任务才考虑 softirq 或 tasklet。三者按执行上下文区分：

1. **softirq**：在最底层运行，同一类型可以在多个 CPU 上并发执行，因此处理函数必须使用 per-CPU 或加锁数据。内核自身使用固定的一组 softirq（本地树 include/linux/interrupt.h 定义 HI_SOFTIRQ=0 至 RCU_SOFTIRQ 共 10 类），驱动一般不新增 softirq，而是使用其上的机制。
2. **tasklet**：构建在 TASKLET_SOFTIRQ 之上，同一 tasklet 在任意时刻只在一个 CPU 上执行，串行性由机制保证，驱动因此不必自己加锁。它同样运行在中断上下文，不能睡眠；现代内核已不鼓励新增 tasklet，倾向用线程化中断或 workqueue。
3. **workqueue**：工作项在内核线程（进程上下文）中执行，可以睡眠、分配 GFP_KERNEL 内存、拿互斥锁并做阻塞 I/O。代价是调度延迟高于 softirq 一族，不适合纳秒级时效的场景。

选型规则按依赖关系排列：

1. 工作需要睡眠 → workqueue，没有别的选项。
2. 工作极短、无需睡眠、且对吞吐或时延敏感 → 优先考虑线程化中断的线程部分，其次 tasklet。
3. 需要跨 CPU 并发处理高频事件（如网络收包）→ 内核自用的 softirq，驱动层面通常不直接使用。

依据：本地内核树 include/linux/interrupt.h（softirq 枚举与 tasklet 声明）、kernel/workqueue.c（worker 进程上下文，may_sleep 路径经 might_sleep 断言）。

**Q3: [learning] 为什么中断上下文里不能睡眠？**

睡眠的本质是“当前执行流挂起，调度器选择其他任务运行”，而中断上下文不满足这个前提。级联关系如下：

1. **没有可挂起的进程身份**：hardirq 与 softirq 运行时，current 指向的是被中断打断的那个任务，中断处理本身不是独立可调度的实体。它若“睡下”，被换出的却是无辜的用户任务，唤醒时机也无人管理。
2. **调度器不可重入**：睡眠路径会调用调度器，而调度器自身的部分状态在 IRQ 路径上不安全。内核用 might_sleep() 这类断言在可抢占配置下直接报警（本地树 kernel/workqueue.c 的 worker 路径即含该断言）。
3. **内存分配受限**：GFP_KERNEL 允许在内存不足时回收页并等待，等待即睡眠，因此中断上下文只能用 GFP_ATOMIC——它绝不阻塞，代价是可能分配失败，调用方必须处理失败分支。
4. **锁语义收窄**：互斥锁（mutex）在拿不到时会睡眠，中断上下文只能用自旋锁；而持自旋锁期间又禁止抢占，进一步约束了上半部能做的事。

由此得出驱动的通用纪律：上半部只摘数据、做标记，把一切可能睡眠的工作（分配缓冲、复制到用户、阻塞 I/O）交给 workqueue 或线程化中断的线程部分。

依据：本地内核树 include/linux/gfp.h 的 GFP_ATOMIC 语义、kernel/workqueue.c 的 might_sleep 断言。

**Q4: [learning] 线程化中断（request_threaded_irq）解决了什么问题？**

它把“必须快速返回的中断响应”与“可以调度的处理工作”合并到一个注册接口里：handler 仍运行在硬中断上下文负责快速检查与应答，thread_fn 则运行在一个专用的内核线程中，具备进程上下文的全部能力——可睡眠、可分配 GFP_KERNEL、可拿互斥锁。注册原型在本地树 include/linux/interrupt.h：request_threaded_irq(unsigned int irq, irq_handler_t handler, irq_handler_t thread_fn, ...)。

相对“request_irq 上半部 + 自己起 workqueue”的传统组合，它的收益与代价如下：

1. **收益**：处理工作成为可调度的任务，能参与优先级与 CPU 亲和性管理，对实时系统尤其重要——RT 路径甚至可以把全部中断强制线程化（force irqthreads）统一按线程调度。每中断一线程让“哪个设备的中断处理慢”在调度数据里直接可见。
2. **快速路径保留**：handler 返回 IRQ_WAKE_THREAD 时内核唤醒线程，返回 IRQ_HANDLED 时直接结束；检查失败的开销保持在上半部的量级。
3. **一次性语义**：thread_fn 执行期间内核默认持有该中断线（IRQF_ONESHOT 语义），避免处理未完成时同一中断反复进入；这消除了驱动手工 mask/unmask 的常见错误源。
4. **代价**：每个中断多一个线程的内存与调度开销。上下文切换使单次处理的绝对延迟略高于纯 softirq 路径，收益换来的是可调度性与睡眠能力。

选型判断：设备处理需要睡眠（多数 I2C/SPI 传感器、需要拿设备互斥锁的场景）选线程化中断；硬实时且处理极短的传统场景保留纯上半部加 tasklet/softirq。

依据：本地内核树 include/linux/interrupt.h 第 147 行起的 request_threaded_irq 原型与注释、kernel/irq/manage.c 的 IRQF_ONESHOT 处理。

**Q5: [learning] /proc/interrupts 与 /proc/softirqs 怎么读？增长模式能说明什么？**

两个文件分别回答“硬件中断打到了哪个 CPU”与“各类软中断被触发了多少次”，是定位中断风暴与负载不均的第一手证据。

读法与判读：

1. **/proc/interrupts**：每行一个中断源（中断号加名称），每个 CPU 一列计数。单列独大说明该中断的亲和性固定在某个 CPU 或设备流量集中；所有列同步增长的中断通常是广播型或定时器类。行尾名称（如 i2c、eth、mmc）对应驱动注册时的名字。
2. **/proc/softirqs**：每行一类 softirq（本地树共 10 类，与 include/linux/interrupt.h 枚举一致），每 CPU 一列。NET_RX 持续高增长对应高网络收包负载；TIMER 与 SCHED 的增长属于常态，需关注的是速率突变。
3. **增长模式判断**：中断计数以极高且稳定速率增长、同时 CPU 的 system 占比抬升，指向中断风暴——驱动可能在中断里没有正确清除硬件条件，导致同一中断被反复触发。此时先看 /proc/interrupts 定位中断源，再用 ftrace 的 irq 相关事件对齐时间线。
4. **边界**：计数是累计值且各 CPU 独立采样时刻略有差异，读数不能直接当速率用，需要两次采样做差并换算时间窗。/proc/interrupts 的存在与格式随内核配置变化，最小化内核可能裁剪部分条目。

依据：本地内核树 fs/proc/interrupts.c 与 fs/proc/softirqs.c 的展示逻辑、include/linux/interrupt.h 的 softirq_to_name。
