# Linux 设备驱动

> 通用 Linux 字符设备、用户态接口与寄存器访问。Android 专属设备接入归 Android 原生层。

**Q1: [learning] 用户态调用 open、read 或 write 后，VFS 如何把操作分发到设备驱动？**

系统调用进入内核后由 VFS 根据路径和对象类型选择实现。对字符设备节点，设备号关联字符设备驱动，文件操作最终可分发到驱动注册的 `file_operations` 回调。

具体机制和边界如下：

1. 用户态通过文件描述符操作已打开对象。内核中的 fd 表项引用 `struct file`。其 `f_op` 指向相应文件操作函数表。字符设备路径还涉及 inode 中的设备号及内核注册的字符设备范围/操作集。普通文件、socket 和字符设备虽然共享 `read`/`write` 等调用形式，底层分发目标不同。
2. 实际调用会经过权限检查、VFS 与具体子系统代码，不宜把它简化成“`sys_write` 直接按 fd 找到驱动函数”。追踪某个具体设备时，应从设备节点、设备号、注册调用和回调实现逐层确认。

**Q2: [learning] struct file、文件描述符、struct inode 和 file_operations 各是什么关系？**

文件描述符是进程 fd 表中的整数索引，`struct file` 表示一次打开的内核文件对象，`struct inode` 描述文件对象及其类型/元数据，`file_operations` 则提供该对象可调用的操作实现。

具体机制和边界如下：

1. 对于字符设备，inode 可包含设备号。`struct file` 保存打开标志、当前位置等每次打开相关状态，并通过 `f_op` 连接到读写回调。驱动可以在 `.open` 中把设备实例或私有状态挂到 `file->private_data`，后续 `.read`、`.write`、`.unlocked_ioctl`、`.release` 再使用该状态。多个 fd 可以指向同一个打开对象，重复 `open` 通常会创建新的打开状态。
2. `f_pos` 是否有意义取决于设备语义。流式设备不一定像普通文件一样支持随机访问。具体结构字段随内核版本变化，不应照抄某个版本的完整结构体定义。

**Q3: [learning] 字符设备的主设备号、次设备号和 /dev 节点各负责标识什么？**

设备号是内核侧字符设备标识，由主设备号和次设备号组成。主设备号用于关联驱动操作集，次设备号通常用于区分同一驱动管理的设备实例。`/dev` 节点是用户空间访问该设备的文件系统入口。

具体机制和边界如下：

1. 驱动可动态申请设备号范围，也可在确有需要时使用固定范围。随后注册字符设备操作集，并建立设备对象/节点或由设备管理机制创建设备节点。节点的 major/minor 必须与驱动注册范围相符。仅有驱动代码或仅有 `/dev` 文件都不等于设备已正确可用。
2. 设备节点的创建方式与权限取决于设备模型和用户空间管理机制。不要假设调用 `device_create` 就解决了全部访问控制。

**Q4: [learning] 字符设备 open 到 release 的生命周期应如何设计？**

`open` 在一次打开时建立或引用设备状态，读写/ioctl 在打开期间执行操作，最后一次关闭对应的 `release` 释放该打开实例的资源。驱动需保证每个失败路径和并发路径都能正确清理。

具体机制和边界如下：

1. 字符设备驱动通常在初始化阶段申请设备号、初始化/注册 `cdev` 或等价设备对象，并按需要创建 class/device 节点。退出阶段撤销节点、注销设备并释放号码。`file_operations` 中按需实现 `.open`、`.read`、`.write`、`.unlocked_ioctl`、`.release` 等方法。`.owner = THIS_MODULE` 等模块引用管理细节用于避免模块仍在被使用时卸载。
2. 回调应定义明确的缓冲区、偏移、并发、错误码和生命周期语义。没有实现的方法不应假设会自动操作硬件。用户接口需兼容 32/64 位 ioctl 等场景时还要考虑 compat 处理。

**Q5: [learning] 为什么驱动不能直接解引用用户传入的指针，copy_from_user 与 copy_to_user 如何使用？**

用户地址不能作为可信内核指针直接解引用。驱动应通过 `copy_from_user`/`copy_to_user` 在用户空间与内核缓冲区之间安全拷贝，并处理拷贝未完成的返回值。

具体机制和边界如下：

1. 写回调收到 `const char __user *buf` 时，先检查请求长度是否在允许范围内，再分配或选择有界内核缓冲区，执行 `copy_from_user`，最后按设备协议处理数据。读回调准备好内核数据后再 `copy_to_user`。这两个函数的非零返回表示仍有字节未成功拷贝，通常需转换为合适的错误或部分传输结果，不能无视失败并返回完整长度。
2. 输入大小可能远大于固定缓冲区，若不限制长度就会越界。还需处理整数溢出、并发访问、阻塞语义与部分读写。驱动接口的长度与格式检查是内核安全边界。

**Q6: [learning] 驱动访问 MMIO 寄存器时，为什么不应把固定物理地址强转成指针后直接读写？**

固定物理地址直接解引用既不具备可移植性，也绕开了内核对 I/O 地址映射、访问顺序和体系结构差异的处理。驱动应使用资源管理及硬件子系统提供的映射/API，例如设备资源映射后使用 `readl`/`writel`，或使用 GPIO、I2C、SPI、regmap 等框架。

具体机制和边界如下：

1. 物理地址取决于具体 SoC/板级描述，寄存器访问还可能涉及字节序、访问宽度、屏障、时钟/电源状态和并发保护。`volatile` 不能替代 MMIO 映射、总线访问器或内存屏障。通过 GPIO/I2C/SPI 子系统访问时，框架负责相应资源与总线约定，驱动不必自行硬编码寄存器。
2. 设备的寄存器地址应从目标硬件资源获取，不能照搬其他设备的地址。

**Q7: [learning] ioctl 和 mmap 什么时候适合用于设备接口，它们增加了哪些设计责任？**

`ioctl` 适用于不自然映射成字节流读写的设备控制命令。`mmap` 可用于把受控设备/缓冲区映射到用户空间以支持特定共享或高吞吐场景。二者都扩大了接口复杂度和安全审查范围。

具体机制和边界如下：

1. `ioctl` 命令需定义稳定的命令号、结构布局、尺寸与兼容规则，并验证用户数据和调用权限。`mmap` 需严格限制可映射区域、长度、权限、缓存属性与生命周期，不能让用户映射任意物理内存。很多设备已有成熟内核子系统或 dma-buf 等机制，应优先复用而不是自创裸接口。
2. 普通 `read`/`write` 可表达顺序数据通道时，优先保持简单的流式接口。只有控制语义或性能要求确实需要时才引入 ioctl/mmap。

**Q8: [learning] 为什么 /dev/hello 不一定会随着驱动注册自动出现，驱动卸载时又应如何处理？**

设备节点创建取决于驱动采用的设备模型和系统用户空间管理方式。注册字符设备操作集与创建 `/dev` 节点是相关但分离的步骤。动态主次设备号也需要被正确关联到节点。

具体机制和边界如下：

1. 驱动可使用 `cdev` 与设备模型接口注册设备，并按系统配置通过 devtmpfs/udev/init 等机制创建设备节点。卸载时应先阻止新访问、撤销节点/设备对象，再注销字符设备和释放号码。存在打开引用或并发回调时，必须确保对象不会提前释放。
2. `insmod` 成功但 `/dev/hello` 不存在时，应检查是否注册设备对象、devtmpfs 是否挂载、设备管理规则是否生效，以及设备号是否正确。

**Q9: [learning] Linux 平台设备怎样匹配驱动并执行 probe，未绑定时查什么？**

驱动注册后，Linux 驱动核心通过总线规则寻找匹配设备。匹配成功后调用 probe 初始化具体设备实例，初始化成功才完成绑定。因此模块已加载只能证明模块进入了内核。

1. **设备出现**。平台代码或设备树等固件描述提供设备实例及资源，例如寄存器地址和中断。设备未被枚举时，驱动没有对应实例可绑定。
2. **驱动匹配**。平台总线按设备来源应用相应规则。用设备树描述的设备通常通过 compatible 字符串与驱动支持的匹配项关联。
3. **实例初始化**。probe 获取设备资源并建立运行状态。若所依赖的供电或时钟提供者尚未就绪，驱动可报告延迟探测，内核会在之后重试。其他初始化失败原因需要结合返回状态和内核日志判断。
4. **分层排查**。先确认设备是否出现在平台总线，再检查是否已有驱动绑定，最后查看 probe 的错误或延期原因。绑定完成后是否出现设备节点，还取决于驱动是否提供相应用户态接口。

依据：Linux 内核文档 Platform Devices and Drivers 与 Device Drivers 的 probe 说明。
