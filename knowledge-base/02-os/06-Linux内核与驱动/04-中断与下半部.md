**Q1: [learning] 中断发生后，内核如何找到对应的处理函数？**

内核不按设备名查找处理函数，而是以 Linux 中断号为索引找到中断描述符 irq_desc，先执行描述符上绑定的流处理函数完成屏蔽、应答等控制器级动作，再遍历描述符上注册的 action 链，逐个调用驱动注册的处理函数。整条路径如下：

1. **架构入口**：CPU 响应中断后进入架构相关的入口代码，把硬件中断号转换成 Linux 中断号，调用通用分发入口（如 generic_handle_irq）。
2. **定位描述符**：以 Linux 中断号索引 irq_desc。每个中断号对应一个描述符，其中保存流处理函数 handle_irq、指向 irqaction 链表的 action 指针、中断状态与统计计数。
3. **执行流处理函数**：generic_handle_irq_desc 直接调用 desc->handle_irq(desc)。流处理函数由中断控制器驱动在初始化时设置，负责屏蔽、应答、EOI（End Of Interrupt，中断结束信号）等与触发方式相关的动作，不同触发方式对应不同实现。
4. **遍历 action 链**：流处理函数调用 handle_irq_event，后者经 __handle_irq_event_percpu 用 for_each_action_of_desc 遍历链表，对每个节点调用 action->handler(irq, action->dev_id)。dev_id 是驱动注册时传入的标识，共享中断时用于区分设备。
5. **汇总返回值**：各 handler 的返回值按位或汇总。全部返回 IRQ_NONE 时内核判定本次中断无人认领，累计到阈值会按伪中断处理，禁用该中断线并报告。

驱动经 request_irq 注册时，内核分配一个 irqaction 节点挂到对应描述符的 action 链上。request_irq 本身是 request_threaded_irq 的封装，thread_fn 传 NULL 即纯上半部模式。

依据：本地内核树 include/linux/irqdesc.h 的 generic_handle_irq_desc、kernel/irq/handle.c 的 __handle_irq_event_percpu、kernel/irq/spurious.c 的伪中断判定。

**Q2: [learning] 电平触发与边沿触发中断有什么区别，内核如何处理？**

区别在于中断请求信号的保持方式：电平触发在条件满足期间持续保持有效电平，边沿触发只在跳变瞬间产生一次请求。内核为两者配备不同的流处理函数，核心差异是“处理期间如何防止同一中断重复进入”。本地树 kernel/irq/chip.c 提供三种主要实现：

1. **handle_level_irq（电平触发）**：进入时先 mask_ack_irq 屏蔽并应答，再调用驱动 handler，结束后 cond_unmask_irq 解除屏蔽。处理期间必须屏蔽：电平信号在设备条件清除前一直有效，不屏蔽会让同一中断在 handler 执行中反复进入。
2. **handle_edge_irq（边沿触发）**：进入时先 irq_ack 应答，然后循环调用 handler。处理期间到达的新边沿被记为 IRQS_PENDING，循环检测到该标志就再处理一轮，直到没有新边沿。边沿信号不会持续保持，因此无需屏蔽，代价是要用循环补住处理窗口内丢失的边沿。
3. **handle_fasteoi_irq（快速 EOI）**：进入时不做屏蔽和应答（线程化中断的 ONESHOT 场景除外），handler 执行完后才发送 EOI（End Of Interrupt，中断结束信号）。适用于 GIC 这类在控制器内部维护优先级与活跃状态的现代中断控制器，把屏蔽与应答的开销从关键路径上移走。

对驱动的影响按触发方式分两种情况：

1. **电平触发**：设备必须在 handler 里清除设备侧的中断条件，否则解除屏蔽后信号仍然有效，中断会立刻再次进入，表现为中断风暴。
2. **边沿触发**：若清除条件与应答之间存在竞态，可能丢失一次边沿，驱动需要靠状态寄存器复查兜底。

依据：本地内核树 kernel/irq/chip.c 的 handle_level_irq、handle_edge_irq、handle_fasteoi_irq 实现。

**Q3: [learning] irq_domain 是什么，为什么需要它？**

irq_domain 是中断控制器驱动提供的映射层，把控制器本地的硬件中断号 hwirq 翻译成全局唯一的 Linux 中断号 virq。需要它的原因是 hwirq 只在单个控制器内部有意义：系统里可以有多个中断控制器，各自的编号空间互相重叠，设备树里引用的也是控制器本地编号，内核必须有一层机制把它们统一纳入自己的编号空间。

映射的建立与使用分三步：

1. **注册 domain**：中断控制器驱动初始化时注册一个 irq_domain，附带 irq_domain_ops 回调。map 回调在映射建立时配置硬件，xlate 回调把设备树的中断描述解析成 hwirq 与触发类型。层级 domain 还有 alloc、translate 等回调。
2. **建立映射**：irq_create_mapping_affinity 先经 irq_find_mapping 查找已有映射，没有则经 irq_domain_alloc_descs 分配 virq 与 irq_desc，再调用 map 回调完成硬件配置。同一个 hwirq 重复请求会复用已有 virq。
3. **使用映射**：驱动从设备树或 ACPI 拿到的中断资源已经是 virq，直接传给 request_irq。中断到达时架构入口也经 domain 反查，把 hwirq 还原成 virq 再分发。

由此形成两条边界：

1. request_irq 的参数是 virq 而不是 hwirq，把设备树里的原始编号直接当 Linux 中断号用是常见错误。
2. virq 是内核动态分配的，同一个设备在不同启动、不同内核配置下编号可能不同，脚本和日志分析不能把中断号当稳定标识，应结合 /proc/interrupts 行尾的名称定位。

依据：本地内核树 include/linux/irqdomain.h 的 irq_domain_ops、kernel/irq/irqdomain.c 的 irq_create_mapping_affinity 与 irq_find_mapping。

**Q4: [learning] 中断共享 IRQF_SHARED 是怎么工作的？**

IRQF_SHARED 允许多个设备共用一条中断线：内核把它们的 irqaction 挂到同一个描述符的 action 链上，中断到来时逐个调用所有 handler，由每个 handler 自行判断是不是自己的设备触发了中断。这套机制的约束与责任如下：

1. **注册校验**：__setup_irq 要求链上已有 action 与新 action 都带 IRQF_SHARED，触发类型一致，IRQF_ONESHOT 与 IRQF_PERCPU 标志一致，任一不满足返回 -EBUSY。NMI 线不允许共享。共享注册还必须传入非 NULL 的 dev_id，它是 handler 区分设备的依据，也是 free_irq 时定位要释放哪个 action 的键。
2. **逐个询问**：中断到来时 action 链上每个 handler 都会被调用。handler 必须先读自己设备的状态寄存器确认是否由本设备触发：是则处理并返回 IRQ_HANDLED，否则返回 IRQ_NONE。不能假设“轮到我一定是我的设备”。
3. **伪中断保护**：所有 handler 都返回 IRQ_NONE 的中断被计为无人认领，累计过多会触发内核的伪中断保护，禁用该线。共享线上某个设备异常拉低中断却无人处理，会连累同线其他设备。

适用边界：共享是引脚中断时代的产物，PCI 传统 INTx 中断常因引脚复用而共享，MSI/MSI-X 中断天然不共享。现代设备驱动若硬件支持，应优先申请独立中断而不是依赖共享。

依据：本地内核树 kernel/irq/manage.c 的 __setup_irq 共享校验与 request_threaded_irq 的 dev_id 检查、kernel/irq/handle.c 的 action 链遍历。

**Q5: [learning] 中断处理为什么要分成上半部与下半部？**

上半部要快，下半部要做完：硬件中断发生时 CPU 必须尽快响应并返回，否则同线或同 CPU 上的其他中断被延迟、系统响应性下降。但设备的数据搬运、协议解析往往远超“快速”的范围。因此内核把中断处理拆成两段——上半部（hardirq）只做应答硬件、读取状态、把数据摘下来登记，然后立刻让出 CPU。剩下的耗时工作推迟到下半部在更宽松的环境里完成。

两段的职责与约束如下：

1. **上半部（hardirq）**：运行在硬件中断上下文，对应驱动经 request_irq 注册的 handler。它在一个关闭（或屏蔽）本中断的环境里执行，通常不做耗时工作，也不能睡眠。上半部的耗时直接体现为其他中断的延迟，这是它必须短小的根本原因。
2. **下半部（bottom half）**：承载被推迟的工作。内核提供 softirq、tasklet 与 workqueue 三种机制，执行上下文与可执行的操作各不相同，按工作是否需要睡眠选择。
3. **判定边界**：不是所有设备都显式分两段。工作极短的中断（例如应答一个寄存器位）可以在上半部直接完成。分段的收益来自“响应及时”与“处理充分”两个目标之间的冲突强度。

依据：本地内核树 include/linux/interrupt.h 的 irqaction 定义（handler 与 thread_fn 并存）与 kernel/softirq.c。

**Q6: [learning] softirq 什么时候执行，为什么需要 ksoftirqd？**

softirq 不注册独立线程，而是“搭便车”在两个时机就地执行：硬中断退出路径 irq_exit，以及进程上下文重新开启下半部（local_bh_enable）时。就地执行有时间和轮次上限，超限后剩余工作交给每 CPU 一个的 ksoftirqd 内核线程，防止软中断长期霸占 CPU。具体机制如下：

1. **登记**：raise_softirq 把对应类型记入当前 CPU 的 pending 位图，不立即执行。
2. **触发**：两个执行点检查 pending 位图，非空则执行 softirq：

    1. __irq_exit_rcu 在退出硬中断且不在其他中断上下文时检查，非空调用 invoke_softirq。
    2. __local_bh_enable_ip 在重新开启下半部时做同样检查。

3. **就地执行**：__do_softirq 先清 pending 位图，然后开启本地硬中断，按位图依次调用各类型的 action。执行期间硬中断是开着的，新中断可以登记新的 pending。
4. **限额重启**：一轮结束后若又有 pending，且未超过 2 ms（MAX_SOFTIRQ_TIME）、未超过 10 轮（MAX_SOFTIRQ_RESTART）、当前任务不需要调度，就回到第 3 步再处理一轮。
5. **移交 ksoftirqd**：任一限额触顶仍有 pending，就唤醒本 CPU 的 ksoftirqd/n 线程（n 为 CPU 号）在进程上下文继续处理。ksoftirqd 是普通调度优先级的内核线程，与普通任务公平竞争 CPU。

设计动机：网络收包等高频场景下 softirq 可能源源不断，若无限就地重启，被中断的用户任务将永远得不到执行。限额加 ksoftirqd 把“软中断负载”变成一个可被调度器看见、可被抢占的实体。代价是移交后处理延迟上升，因此 /proc/softirqs 计数高而 ksoftirqd 占用 CPU 明显时，说明软中断负载已经超出就地处理的消化能力。

依据：本地内核树 kernel/softirq.c 的 MAX_SOFTIRQ_TIME、MAX_SOFTIRQ_RESTART、__do_softirq、__irq_exit_rcu、__local_bh_enable_ip 与 ksoftirqd 线程注册。

**Q7: [learning] softirq、tasklet 与 workqueue 三种延迟机制怎么选？**

选择取决于工作能否睡眠：需要睡眠（分配内存、拿互斥锁、做 I/O）就必须用 workqueue。不需要睡眠的短任务才考虑 softirq 或 tasklet。三者按执行上下文区分：

1. **softirq**：在最底层运行，同一类型可以在多个 CPU 上并发执行，因此处理函数必须使用 per-CPU 或加锁数据。内核自身使用固定的一组 softirq（本地树 include/linux/interrupt.h 定义 HI_SOFTIRQ=0 至 RCU_SOFTIRQ 共 10 类），驱动一般不新增 softirq，而是使用其上的机制。
2. **tasklet**：构建在 TASKLET_SOFTIRQ 之上，同一 tasklet 在任意时刻只在一个 CPU 上执行，串行性由机制保证，驱动因此不必自己加锁。它同样运行在中断上下文，不能睡眠。现代内核已不鼓励新增 tasklet，倾向用线程化中断或 workqueue。
3. **workqueue**：工作项在内核线程（进程上下文）中执行，可以睡眠、分配 GFP_KERNEL 内存、拿互斥锁并做阻塞 I/O。代价是调度延迟高于 softirq 一族，不适合纳秒级时效的场景。

选型规则按依赖关系排列：

1. 工作需要睡眠 → workqueue，没有别的选项。
2. 工作极短、无需睡眠、且对吞吐或时延敏感 → 优先考虑线程化中断的线程部分，其次 tasklet。
3. 需要跨 CPU 并发处理高频事件（如网络收包）→ 内核自用的 softirq，驱动层面通常不直接使用。

依据：本地内核树 include/linux/interrupt.h（softirq 枚举与 tasklet 声明）、kernel/workqueue.c（worker 进程上下文，may_sleep 路径经 might_sleep 断言）。

**Q8: [learning] 为什么中断上下文里不能睡眠？**

睡眠的本质是“当前执行流挂起，调度器选择其他任务运行”，而中断上下文不满足这个前提。级联关系如下：

1. **没有可挂起的进程身份**：hardirq 与 softirq 运行时，current 指向的是被中断打断的那个任务，中断处理本身不是独立可调度的实体。它若“睡下”，被换出的却是无辜的用户任务，唤醒时机也无人管理。
2. **调度器不可重入**：睡眠路径会调用调度器，而调度器自身的部分状态在 IRQ 路径上不安全。内核用 might_sleep() 这类断言在可抢占配置下直接报警（本地树 kernel/workqueue.c 的 worker 路径即含该断言）。
3. **内存分配受限**：GFP_KERNEL 允许在内存不足时回收页并等待，等待即睡眠，因此中断上下文只能用 GFP_ATOMIC——它绝不阻塞，代价是可能分配失败，调用方必须处理失败分支。
4. **锁语义收窄**：互斥锁（mutex）在拿不到时会睡眠，中断上下文只能用自旋锁。持自旋锁期间又禁止抢占，进一步约束了上半部能做的事。

由此得出驱动的通用纪律：上半部只摘数据、做标记，把一切可能睡眠的工作（分配缓冲、复制到用户、阻塞 I/O）交给 workqueue 或线程化中断的线程部分。

依据：本地内核树 include/linux/gfp.h 的 GFP_ATOMIC 语义、kernel/workqueue.c 的 might_sleep 断言。

**Q9: [learning] spin_lock、spin_lock_irq 与 spin_lock_irqsave 怎么选？**

选择取决于这把锁会不会在中断上下文里被再次获取：只在进程上下文使用的锁用 spin_lock 即可，硬中断 handler 也会拿的锁必须用关中断变体，否则同一 CPU 上会发生死锁。三个变体的语义与适用条件如下：

1. **spin_lock**：只关抢占，不关中断。持锁期间本 CPU 的硬中断可以打断执行流。若中断 handler 也来拿同一把锁，它会自旋等待一个永远无法释放的锁——持锁者被中断挂起，要等中断返回才能继续，而中断在等锁，两者互相卡死。因此它只适用于确定不会在中断上下文被获取的锁。
2. **spin_lock_irq**：拿锁前无条件关闭本 CPU 中断，解锁时无条件开启。它假定调用时中断本来就是开的。若调用处已经关着中断，解锁会把中断错误地打开，破坏外层的中断屏蔽假设。
3. **spin_lock_irqsave**：拿锁前把当前中断状态保存到 flags 并关中断，解锁时用 spin_unlock_irqrestore 恢复原状态。无论调用处中断是开是关都安全，是中断相关共享数据的默认选择。

两条补充规则：

1. 锁只与 softirq 或 tasklet 共享、不与硬中断共享时，用 spin_lock_bh 变体，只关下半部而不关硬中断，开销更小。
2. 关中断只需关本 CPU：其他 CPU 上的中断不会打断本 CPU 的持锁执行流，自旋锁本身负责跨 CPU 互斥，因此 irq 变体都是 local 操作。

依据：本地内核树 include/linux/spinlock.h 的变体定义、Documentation/locking/spinlocks.rst 的 Lesson 1 与 Lesson 3（同 CPU 死锁场景与 local 中断说明）。

**Q10: [learning] 线程化中断（request_threaded_irq）解决了什么问题？**

它把“必须快速返回的中断响应”与“可以调度的处理工作”合并到一个注册接口里：handler 仍运行在硬中断上下文负责快速检查与应答，thread_fn 则运行在一个专用的内核线程中，具备进程上下文的全部能力——可睡眠、可分配 GFP_KERNEL、可拿互斥锁。注册原型在本地树 include/linux/interrupt.h：request_threaded_irq(unsigned int irq, irq_handler_t handler, irq_handler_t thread_fn, ...)。

相对“request_irq 上半部 + 自己起 workqueue”的传统组合，它的收益与代价如下：

1. **收益**：处理工作成为可调度的任务，能参与优先级与 CPU 亲和性管理，对实时系统尤其重要——RT 路径甚至可以把全部中断强制线程化（force irqthreads）统一按线程调度。每中断一线程让“哪个设备的中断处理慢”在调度数据里直接可见。
2. **快速路径保留**：handler 返回 IRQ_WAKE_THREAD 时内核唤醒线程，返回 IRQ_HANDLED 时直接结束。检查失败的开销保持在上半部的量级。
3. **一次性语义**：thread_fn 执行期间内核默认持有该中断线（IRQF_ONESHOT 语义），避免处理未完成时同一中断反复进入。这消除了驱动手工 mask/unmask 的常见错误源。
4. **代价**：每个中断多一个线程的内存与调度开销。上下文切换使单次处理的绝对延迟略高于纯 softirq 路径，收益换来的是可调度性与睡眠能力。

选型判断：设备处理需要睡眠（多数 I2C/SPI 传感器、需要拿设备互斥锁的场景）选线程化中断。硬实时且处理极短的传统场景保留纯上半部加 tasklet/softirq。

依据：本地内核树 include/linux/interrupt.h 第 147 行起的 request_threaded_irq 原型与注释、kernel/irq/manage.c 的 IRQF_ONESHOT 处理。

**Q11: [learning] MSI 与 MSI-X 是什么，相对引脚中断有什么优势？**

MSI（Message Signaled Interrupt，消息信号中断）是设备向一个特定内存地址写入数据来触发中断的机制，不再依赖物理中断引脚。MSI 能力首次出现于 PCI 2.2，PCI 3.0 增强为支持逐中断屏蔽。MSI-X 同样引入于 PCI 3.0，支持更多中断向量且每个向量可独立配置地址与数据。设备可以同时具备两种能力，但同一时刻只能启用一种。

相对传统引脚中断的优势有三点：

1. **不共享**：引脚中断常因引脚复用被多个设备共享，内核必须逐个调用 handler 询问。MSI 向量专属于设备，不存在共享开销。
2. **保证数据先于中断到达**：引脚中断可能先于设备 DMA 写入的数据到达内存，handler 不得不读一次设备寄存器来强制排序。MSI 的中断写本身是一笔 PCI 写事务，不能越过前面的数据写，中断到达时数据必然已落内存，省去了这次读回。
3. **多向量分工**：引脚中断每个功能只有一根，驱动必须查设备才知道发生了什么事件。MSI-X 可以为每个收包队列、每个存储端口或错误条件分配独立向量，handler 直接按向量分工处理，也便于把不同向量绑到不同 CPU。

使用边界：内核需开启 CONFIG_PCI_MSI，且并非所有平台都正确支持 MSI，申请失败时设备回退到引脚中断。驱动经 pci_alloc_irq_vectors 申请向量，返回的 Linux 中断号直接用于 request_irq，编号映射由 irq_domain 层完成。

依据：本地内核树 Documentation/PCI/msi-howto.rst 的 What are MSIs 与 Why use MSIs 两节、include/linux/msi.h。

**Q12: [learning] 中断亲和性怎么设置，影响什么？**

中断亲和性决定一个中断由哪个或哪些 CPU 响应，设置入口是 /proc/irq/<中断号>/ 下的接口文件。它影响中断负载在 CPU 间的分布、缓存局部性，以及能否把中断从延迟敏感的 CPU 上移开。接口与规则如下：

1. **smp_affinity**：可读写，内容为十六进制 CPU 位掩码，如 4 表示只允许 CPU 2。写入经 write_irq_affinity 校验后生效。
2. **smp_affinity_list**：可读写，与 smp_affinity 等价，内容改为 CPU 列表写法，如 2-3，CPU 数多时更易读。
3. **effective_affinity**：只读，显示中断控制器实际生效的亲和性。请求的掩码可能被控制器收窄（例如只支持单目标），排查时应以它为准。
4. **default_smp_affinity**：/proc/irq/ 下的全局默认掩码，新注册中断的初始亲和性从这里继承。

写入限制：

1. 掩码必须至少包含一个在线 CPU，否则内核拒绝或回退到架构默认选择，避免把中断设成无处可去。
2. 托管中断（managed interrupt，内核自动分配亲和性的中断，典型如 PCI MSI-X 按队列自动绑核）不允许用户修改，写入返回 -EIO。判定逻辑是 irq_can_set_affinity_usr 检查 IRQD_AFFINITY_MANAGED 标志。
3. 单中断控制器可能不支持亲和性设置，此时接口写入同样失败。

实践上，手动绑核常用于把高频中断集中到指定 CPU 以隔离延迟敏感核，或配合 irqbalance 守护进程自动均衡。观察效果用 /proc/interrupts 各 CPU 列的计数变化验证。

依据：本地内核树 kernel/irq/proc.c 的接口创建与 write_irq_affinity、kernel/irq/manage.c 的 irq_can_set_affinity_usr。

**Q13: [learning] /proc/interrupts 与 /proc/softirqs 怎么读？增长模式能说明什么？**

两个文件分别回答“硬件中断打到了哪个 CPU”与“各类软中断被触发了多少次”，是定位中断风暴与负载不均的第一手证据。

读法与判读：

1. **/proc/interrupts**：每行一个中断源（中断号加名称），每个 CPU 一列计数。单列独大说明该中断的亲和性固定在某个 CPU 或设备流量集中。所有列同步增长的中断通常是广播型或定时器类。行尾名称（如 i2c、eth、mmc）对应驱动注册时的名字。
2. **/proc/softirqs**：每行一类 softirq（本地树共 10 类，与 include/linux/interrupt.h 枚举一致），每 CPU 一列。NET_RX 持续高增长对应高网络收包负载。TIMER 与 SCHED 的增长属于常态，需关注的是速率突变。
3. **增长模式判断**：中断计数以极高且稳定速率增长、同时 CPU 的 system 占比抬升，指向中断风暴——驱动可能在中断里没有正确清除硬件条件，导致同一中断被反复触发。此时先看 /proc/interrupts 定位中断源，再用 ftrace 的 irq 相关事件对齐时间线。
4. **边界**：计数是累计值且各 CPU 独立采样时刻略有差异，读数不能直接当速率用，需要两次采样做差并换算时间窗。/proc/interrupts 的存在与格式随内核配置变化，最小化内核可能裁剪部分条目。

依据：本地内核树 fs/proc/interrupts.c 与 fs/proc/softirqs.c 的展示逻辑、include/linux/interrupt.h 的 softirq_to_name。
