# VFS 与挂载

> 通用操作系统虚拟文件系统与挂载学习资料。主线：VFS 的统一接口与分派、vnode 与 inode 的概念辨析、挂载的目的与必要性、fstab 声明与 UUID 标识、挂载后路径查找的变化、bind mount、mount namespace 与 overlayfs。原 07 册更名并补规范格式；2026-10-06 按 kernel.org 与 AOSP fs_mgr 官方文档口径扩充 bind mount、mount namespace 与 overlayfs 三题；2026-10-08 增补挂载目的与必要性一题。Q 序列即结构，供 atlas 同源直读。

**Q1: [done] 文件系统实例是什么？为什么需要挂载才能按路径访问？**

文件系统实例是内核管理的一套具体文件系统。例如，ext4 是文件系统类型，某个分区上的 ext4 文件系统是具体实例。**挂载**将实例的根目录接入进程可见的目录树，使应用能从挂载点按路径访问其中的文件。

例如，把包含 `report.txt` 的分区挂载到 `/mnt/data`：

1. **挂载前**：可以通过块设备节点读取分区的原始字节，但不能通过 `/mnt/data/report.txt` 访问该分区中的文件。
2. **挂载后**：`/mnt/data` 指向该实例的根目录，`/mnt/data/report.txt` 因而指向其中的文件。tmpfs 等无需普通磁盘分区的文件系统，也需要挂载才能通过目录树访问。
3. **卸载后**：挂载从目录树移除，该路径不再指向被卸载实例中的文件。普通卸载通常要求挂载不再被占用，延迟卸载可先移除路径入口，再等待引用释放。

挂载会暂时遮蔽挂载点原有内容。例如，原目录中的 `old.txt` 没有被删除，卸载后会重新可见。同一路径指向什么还取决于进程的挂载命名空间；即使文件可见，访问仍需相应权限。







**Q2: [done] VFS 是什么，解决了什么问题？**

VFS（Virtual File System，虚拟文件系统）是内核中的文件系统抽象层。它的主要目的是**统一文件访问接口，并让不同文件系统接入同一目录树**：应用使用 open、read、write 等接口，内核再将操作交给对应的文件系统实现。

VFS 解决的核心问题是：ext4、tmpfs 和 procfs 等文件系统的存储方式与内部实现不同。如果应用需要分别适配每一种实现，程序就难以跨文件系统复用。VFS 定义通用对象和操作接口，让应用按同一方式访问，同时允许内核接入不同的文件系统。

1. **四类通用对象：**superblock 代表一个已挂载的文件系统实例；inode 代表一个文件对象的内存元数据与操作入口；dentry 代表路径中一个分量及其解析缓存；file 代表一次打开。四者共同支撑“路径到对象再到操作”的链路。
2. **分派机制：**每个具体文件系统注册自己的操作表（如何查目录项、如何读 inode、如何写数据）。VFS 的通用函数取对象的操作表调用，同一次 read 系统调用在 ext4 挂载点下落到 ext4 的代码，在 /proc 下落到 procfs 的代码。
3. **设备也走 VFS：**设备节点是特殊文件，open 与读写同样经 VFS 分派，块设备实现再把它们翻译成块请求。“一切皆文件”之所以成立，正是 VFS 把接口层统一了。
4. **边界：**VFS 定义接口契约，不定义磁盘格式；同一文件在不同文件系统下磁盘布局可以完全不同。VFS 对象（内存 inode、dentry）与磁盘上同名结构不是同一个东西。

依据：Linux 内核 VFS 层结构（内核 Documentation/filesystems）。







**Q3: [done] 通用 Linux 的 fstab 是什么，系统怎样使用它？**

fstab 是 file system table（文件系统表）的缩写。通用 Linux 使用 `/etc/fstab` 保存文件系统的挂载配置：每条配置说明一个文件系统从哪里来、挂载到哪个目录，以及如何挂载。这样，系统启动时就可以根据预先写好的配置安排挂载，不必每次都由用户手动指定。

例如，一台电脑有一个存放资料的分区，希望每次启动后都能从 `/data` 访问其中的文件。管理员可以在 `/etc/fstab` 中记录该分区和 `/data` 的对应关系。启动时，系统中的挂载工具读取这条记录，并尝试把该分区上的文件系统挂载到 `/data`。挂载成功后，用户才能通过 `/data` 访问该文件系统中的文件。

一条通用 Linux fstab 配置包含六个字段，按位置依次表示：

1. **文件系统来源**：指定要使用哪个设备或文件系统，可使用设备路径或 UUID（Universally Unique Identifier，通用唯一标识符）。
2. **挂载点**：指定文件系统接入目录树的位置，例如 `/data`。
3. **文件系统类型**：指定按哪种类型处理，例如 ext4。
4. **挂载选项**：指定挂载时采用的行为，例如是否只读。
5. **备份标志**：供传统 dump 备份工具判断是否处理该文件系统。
6. **检查顺序**：供启动时的文件系统检查程序决定是否检查及检查顺序。

本机 `/etc/fstab` 的完整内容如下。以 `#` 开头的行是注释，不会作为配置执行；其余三行分别配置根文件系统、EFI 系统分区和交换区：

```text
# /etc/fstab: static file system information.
#
# Use 'blkid' to print the universally unique identifier for a
# device; this may be used with UUID= as a more robust way to name devices
# that works even if disks are added and removed. See fstab(5).
#
# <file system> <mount point>   <type>  <options>       <dump>  <pass>
# / was on /dev/nvme1n1p4 during installation
UUID=06eb992a-c6e1-44b7-9c9a-0b42dcec1fd2 /               ext4    errors=remount-ro 0       1
# /boot/efi was on /dev/nvme0n1p1 during installation
UUID=D4A0-E9ED  /boot/efi       vfat    umask=0077      0       1
# swap was on /dev/nvme1n1p3 during installation
UUID=41325635-76dd-4a17-a97d-310bd31b54e6 none            swap    sw              0       0
```

本机配置中的三个实例分别是：

1. **根文件系统**：`UUID=06eb992a-c6e1-44b7-9c9a-0b42dcec1fd2` 标识 ext4 文件系统，本次观察位于 `/dev/nvme1n1p4`。`/` 是挂载点，`ext4` 是类型。`errors=remount-ro` 指定 ext4 检测到相关错误时转为只读；省略该选项时使用超级块中的错误处理策略。末尾 `0` 表示不由传统 dump 按此条目备份，`1` 表示根文件系统优先进行启动检查。
2. **EFI 系统分区**：`UUID=D4A0-E9ED` 标识 vfat 文件系统，本次观察位于 `/dev/nvme0n1p1`。`/boot/efi` 是挂载点，`vfat` 是类型。`umask=0077` 屏蔽组用户和其他用户的权限；省略该选项时，vfat 使用挂载进程的 umask。末尾 `0` 表示不按此条目供 dump 备份，`1` 是配置的检查顺序。
3. **交换区**：`UUID=41325635-76dd-4a17-a97d-310bd31b54e6` 标识交换空间，本次观察为 `/dev/nvme1n1p3`。`none` 表示没有普通目录挂载点，`swap` 标识交换空间，`sw` 是交换区选项字段。末尾两个 `0` 分别表示不按此条目供 dump 备份、不按此字段安排文件系统检查。

来源、挂载点、类型和选项四个位置字段用于确定目标及处理方式，不应省略。按本机 fstab 手册，末尾备份标志和检查顺序省略时均默认为 `0`；检查顺序为 `0` 时不按该字段安排检查。

根文件系统的 UUID 标识的是 ext4 文件系统，交换区的 UUID 标识交换空间；二者都不直接标识物理硬盘。`PARTUUID` 则标识分区表中的分区项。物理或虚拟块设备上的文件系统都可以有 UUID，复制文件系统可能产生重复 UUID。

“本次观察位于 `/dev/nvme1n1p4`”表示：查看本机当前状态时，发现该 UUID 对应的 ext4 文件系统存放在这个分区上，且已挂载到 `/`。fstab 记录的是文件系统 UUID；工具找到这个 UUID 后，才确定当前应访问哪个设备节点。

`/dev/nvme1n1p4` 是该分区的块设备节点：`nvme1` 是 Linux 分配的 NVMe 控制器名称，`n1` 是其第 1 个命名空间，`p4` 是该命名空间的第 4 个分区。设备名可能随系统识别顺序变化，因此这是本次查看到的对应关系，不是 UUID 永远对应同一路径的保证。

本次观察中 `/` 和 `/boot/efi` 已挂载，交换分区已启用。配置不保证挂载成功，实际结果取决于设备、选项和启动环境。Android 也使用 fstab，但字段和处理流程不同，不能直接套用通用 Linux 的六字段格式。







**Q4: [done] OverlayFS 是什么？如何合并目录，以及处理读写和删除？**

OverlayFS 是 Linux 的联合文件系统：它把一个或多个下层目录与可选的上层目录组合成一个合并视图，应用通过挂载点访问结果。它提供统一的路径视图，不取代存储设备或底层文件系统。

各目录的职责如下：

1. **lower**：提供原有内容，可以有多个下层。OverlayFS 不向 lower 写入。
2. **upper**：在可写覆盖层中保存新增、覆盖和隐藏下层内容所需的状态。
3. **work**：供内核处理覆盖层操作的工作目录。可写挂载时，workdir 须与 upperdir 位于同一文件系统，并按挂载要求准备为空目录。
4. **合并视图**：应用通过挂载点看到的结果，不是把各层完整复制成第三份数据。

**upper 与 work 的区别**：upper 保存合并视图使用的上层对象，work 供内核准备临时对象。先准备再发布，可以避免 upper 的正式路径过早出现未完成的副本。

例如，lower 中有 `config.txt`，应用要修改它。在使用 work 临时文件的一条 copy-up 路径中：

1. **准备**：内核在 work 创建临时文件，复制原文件的内容，并设置权限、所有者等必要属性，使副本保留原文件的信息。
2. **发布**：准备完成后，内核将临时文件重命名到 upper 的 `config.txt`。这是同一文件系统内的目录项操作，不再复制一遍文件内容。
3. **修改**：应用修改 upper 中的文件，合并视图显示上层结果，lower 原文件不变。被重命名的临时文件不再以原名称留在 work，但这不代表整个 work 目录始终为空。

work 与 upper 需要位于同一文件系统。实际实现也可能使用未命名临时文件；启用 metacopy 时，某些操作先复制元数据、稍后才复制数据。发布目录项不等于后续修改已保证断电后持久化。

合并视图中的操作按以下规则处理：

1. **读取**：同名普通文件通常优先显示 upper 中的对象；upper 没有对应条目时，再从 lower 查找。目录可以合并。只读挂载仍可读取已经存在的上层文件。
2. **修改**：需要修改下层对象时，OverlayFS 通常先通过 copy-up 在 upper 准备对应对象，再执行操作。写打开、修改权限或所有者都可能触发 copy-up，即使文件内容最终没有变化。
3. **新建**：新文件写入 upper，不修改 lower。
4. **删除文件**：删除只存在于 lower 的文件时，upper 中的 whiteout 标记让合并视图隐藏该下层同名条目，lower 中的原文件仍然存在。
5. **遮挡目录**：upper 目录被标记为 opaque 时，不再与对应的 lower 目录合并。仅检查 upper 中是否存在同名普通文件，不能判断下层内容最终是否可见。

常规 copy-up 会复制必要的目录、元数据和文件数据。启用 metacopy 时，某些仅元数据操作可以先复制元数据，待写数据时再复制内容；具体行为取决于内核版本和挂载选项，upper 中有对象不代表其数据必然全部位于 upper。

Android 支持该调试机制的设备可以在只读系统分区之上叠加可写 upper，从合并视图进行开发调试。upper 存储在哪里、是否跨重启保留，取决于设备配置和清理流程。不要在运行中的覆盖层背后直接修改 upper 或 lower 并假定结果可靠。



**Q5: [done] OverlayFS 中的upper重启后还会生效吗？如何恢复？**

**可能会。**如果通过 `adb remount` 建立了 OverlayFS，再用 `adb push` 替换系统 APK，测试版通常保存在 upper，原 APK 仍在 lower。upper 的后端未被清理且数据已持久化时，重启后文件可能保留；只有对应覆盖层重新挂载，上层文件才会再次遮蔽原 APK。

例如，向 `/system_ext/priv-app/Launcher/Launcher.apk` 推送了测试版，现在想恢复系统镜像中的版本。以下以支持 root 的 Android 13 调试设备为例；实际进程名、包名和路径应按设备替换。

1. **确认覆盖层是否生效**：

    1. 执行 `adb devices -l` 查看连接设备，`-l` 显示详细信息。多台设备连接时，每条 adb 命令使用 `-s 序列号` 指定目标，避免操作错误设备。
    2. 执行 `adb shell pidof 进程名` 获取 Launcher 的 PID，再执行 `adb shell cat /proc/PID/mountinfo`，在输出中找到 `/system_ext` 的挂载项。将 `PID` 换成实际数字；进程未运行或权限不足时无法用此方法确认它的视图。
    3. 挂载类型为 `overlay` 时，记录选项中的 `lowerdir`、`upperdir` 和 `workdir`。若是其他类型并且分区曾被直接重新挂载为可写，推送可能已改写底层文件，清理 OverlayFS 无法恢复，应按设备的镜像或升级流程处理。

2. **确认 upper 后端**：在同一份 mountinfo 中找到覆盖 upper 路径的最长匹配挂载点。例如 upper 位于 `/mnt/scratch/overlay/...`，就检查 `/mnt/scratch` 的来源。若来源是 `/dev/block/dm-0`，它只是运行时映射设备：还要结合设备支持的 dmctl 映射表、动态分区元数据或镜像文件映射追查。证据不足时只能记为“后端未确认”，不能凭 `dm-0` 判断数据在 `super` 还是 `/data`。

3. **确认 verity 和恢复条件**：verity 是读取受保护块时进行完整性校验的机制。`adb shell getprop ro.boot.verifiedbootstate` 显示启动验证状态，`adb shell getprop ro.boot.veritymode` 显示相关启动参数；两者都不能单独证明 system_ext 当前是否经过 dm-verity，仍需结合该分区的设备映射和设备实现判断。`adb enable-verity` 可能清理不止这个 APK 的其他调试覆盖，先确认并备份需要保留的内容。

4. **恢复并验证**：确认 lower 中有目标版本，且设备支持 AOSP 调试恢复流程后，依次执行 `adb root` 和 `adb enable-verity`，检查输出并按提示重启。重启后重新检查目标进程的挂载及系统路径 APK 的哈希，再用 `adb shell pm path 包名` 查看包管理器实际使用的路径。应用可能还有 `/data` 中的更新版本，不能只凭系统路径判断当前使用的是哪份 APK。

不要在覆盖层挂载期间直接修改背后的 upper 或 work，也不要在合并路径删除 APK 后就认定 lower 版本会出现：删除可能留下 whiteout，继续隐藏下层同名文件。work 是内核内部工作区，不是 APK 缓存；异常重启后的内部状态取决于实现。量产设备或厂商定制流程可能不支持上述 root 和恢复命令。

**Q6: [learning] vnode 和 inode 是同一个对象吗？**

这两个名称不表示所有操作系统中固定的一对不同对象。BSD 等系统常以 vnode 称呼 VFS 层的文件对象。Linux 使用 VFS inode 表示内存中的文件元数据与操作接口，并由具体文件系统提供其实现和持久化格式。它们在概念上都承担统一文件对象或元数据访问职责，但类型、缓存关系和持久化布局依操作系统而异。

因此，不能笼统说 vnode 是一个对象、inode 是另一个对象，也不能假定每次打开文件都会把磁盘 inode 完整复制成 vnode。讨论具体实现时应标出内核与文件系统。路径名、目录项缓存、内存中的 inode/vnode 和磁盘元数据也不是同一个概念。







**Q7: [learning] bind mount 与普通挂载有什么区别？它解决了什么问题？**

普通挂载把一个独立文件系统的根接到目录树。bind mount 则把“已有目录树中的某段子树”重新映射到另一个挂载点——两端是同一文件系统的同一份内容，不新建文件系统、不存在格式化对象，只是命名空间里多了一个入口视图。

1. **语义**：挂载点是子树的别名，经任一路径的修改都作用于同一数据。卸载别名不影响原路径。
2. **用途**：三类常见场景：

    1. 为容器/chroot 补齐 /proc、/dev 等入口。
    2. 把只读位置以只读标志重新暴露。
    3. Android 开发期的 adb remount 也用 bind/overlay 组合在只读分区上提供可写视图（平台细节归 `../../01-android/11-构建系统/01-产品配置.md` 相邻主题）。
3. **边界**：bind mount 的复制是挂载动作而非数据拷贝。移动（rename）挂载点下的内容与普通文件操作相同。









**Q8: [learning] mount namespace 是什么？它如何让不同进程看到不同的挂载布局？**

mount namespace 是内核提供的挂载视图隔离：每个命名空间持有独立的“挂载点集合”，进程关联到某个 namespace 后，它看到的目录树就由该集合决定。新建 namespace（clone/unshare 带 `CLONE_NEWNS`）会复制父视图，此后原视图与新视图各自 add mount / umount 互不可见。

1. **复制语义**：新 namespace 从父视图快照起步。此后一侧的新挂载不会出现在另一侧。
2. **传播关系**：视图间可配置挂载传播（private、shared、slave 等），shared 使挂载事件在多个 namespace 间广播，private 则完全隔离——容器运行时据此决定宿主新挂载是否渗入容器。
3. **用途**：容器与沙箱为每个实例构造独立挂载布局。Android 的应用隔离与多用户也在内核 mount namespace 之上叠加视图（平台侧实现归 `../../01-android/` 沙箱与存储专题）。
