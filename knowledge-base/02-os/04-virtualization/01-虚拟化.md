# 虚拟机与虚拟化

> 学习资料。围绕车机 Linux/Android 双系统，按“为什么需要隔离与资源仲裁 → CPU 怎样运行 → 设备怎样呈现 → 一次磁盘 I/O 怎样完成”组织。本文只讲可迁移的虚拟化原理。AVF（Android Virtualization Framework）的 Android 组件与接入见 [Android AVF 专题](../../01-android/09-平台服务/06-AVF虚拟化.md)。依据：QEMU《About QEMU》、Linux《KVM API》、OASIS《Virtio 1.2》、Android《AVF architecture》《Security》。题序即文档结构。

**Q1: [done] 虚拟机和虚拟机监控程序有什么区别，VMM 的两种类型如何划分？**

虚拟机（VM，Virtual Machine）是由虚拟 CPU、内存和设备组成的运行环境，可以在其中运行客体操作系统及应用。虚拟机监控程序（VMM，Virtual Machine Monitor）是创建和运行虚拟机的管理软件，负责协调虚拟资源、执行客体并处理或委托设备访问。虚拟机是客体使用的环境，VMM 是提供和管理这个环境的组件。

例如，一台 Windows 电脑安装 VirtualBox 后，在 VirtualBox 中创建一台分配了 2 个虚拟 CPU、4 GB 内存和虚拟磁盘的虚拟机，再在这台虚拟机里安装 Ubuntu。Ubuntu 看到的是这台虚拟机提供的资源。VirtualBox 是这里的 VMM，它负责创建、配置和运行虚拟机，并与 Windows 配合使用真实硬件。

按 VMM 与宿主操作系统的部署关系区分：

1. **第一类：**VMM 在硬件之上承载客体并参与资源管理，虚拟磁盘等设备可以由监控层或专门的服务域提供。例如一台电脑开机后直接启动 VMware ESXi，再由 ESXi 同时运行 Windows 和 Ubuntu 两台虚拟机。ESXi 负责为两台虚拟机分配硬件资源。Xen 也属于这一类，通常由特权域提供管理和设备服务。
2. **第二类：**宿主操作系统掌握真实设备驱动，VMM 借用宿主能力运行，Guest 的虚拟磁盘可映射为宿主上的文件，安装和桌面集成更方便。例如上面的 Windows 电脑先运行 Windows，再通过 VirtualBox 运行 Ubuntu 虚拟机。VMware Workstation 也是这一类。
3. **判断边界：**不能仅凭类别断言性能或迁移能力，实际表现取决于硬件虚拟化支持、设备直通、镜像格式和宿主资源竞争，要结合具体实现判断。

笔记本上常说的 Windows 和 Ubuntu 双系统通常是**交替启动**：开机时选择其中一个系统，选中的系统直接使用硬件。要换到另一个系统，需要重启并重新选择。这种情况没有同时运行的虚拟机，不属于上述两类 VMM。若先启动 Windows，再通过 VirtualBox 运行 Ubuntu，则属于第二类的例子。

**Q2: [done] hypervisor 是什么，与 VMM 有什么区别？**

hypervisor（虚拟机监控程序）是管理虚拟机运行的虚拟化层，负责让多个客体系统共享物理资源，并约束它们对 CPU、内存和设备的访问。它提供客体运行所需的隔离与仲裁机制，让每个客体看到分配给自己的虚拟机器。

它的主要职责包括：

1. **处理器运行：**安排虚拟 CPU 在物理 CPU 上执行。需要管理层处理的受控操作可触发退出，由 hypervisor 或其他负责的组件处理后恢复客体。
2. **内存隔离：**利用硬件地址转换限制客体可访问的物理内存。例如第二阶段地址转换将客体物理地址映射到获准的实际物理页，客体不能仅靠修改自己的页表访问其他客体的内存。
3. **设备访问：**协调设备的模拟、共享或直通。虚拟设备的具体后端可以在 hypervisor、宿主内核或用户态进程中，具体分工取决于实现。

hypervisor 和 VMM（Virtual Machine Monitor）在广义上常作为同义词，不能仅凭名称断定它们是两个独立组件。讨论某个具体实现时，人们有时用这两个词指代不同部分，区别在于该架构给各部分分配的职责。

以使用 KVM 加速的 QEMU 虚拟机为例，按职责区分：

1. **KVM，底层虚拟化组件：**位于 Linux 内核，利用处理器虚拟化能力运行客体 CPU，并参与建立客体内存映射和隔离。在这种讨论中，它常被称为 hypervisor。
2. **QEMU，用户态 VMM：**读取虚拟机配置，通过 KVM 接口创建虚拟机和虚拟 CPU，并提供虚拟磁盘等设备模型。客体访问需要 QEMU 处理的设备时，KVM 可将该事件交给 QEMU，处理后再继续运行客体。

例如客体读取虚拟磁盘时，KVM 负责支持客体 CPU 运行，QEMU 的设备模型接收请求并连接宿主存储。这里的区分适用于所述组合，其他 hypervisor 的设备模型可能内置在同一个系统中。

**Q3: [done] 车机为什么会同时运行 Linux 和 Android，怎样判断双系统是否采用虚拟化？**

采用虚拟化的动机通常是让两套需要独立内核的系统复用一套硬件，同时明确分配 CPU、内存和设备。例如产品可以让 Linux 承载一类设备服务、Android 承载交互界面，但具体分工取决于产品。看到两者并存只能说明有两个软件环境，必须再确认它们是否同时运行、是否共用内核与处理器资源，才能判断是否存在虚拟机。

按实际运行边界区分四种方案：

1. **交替启动：**一次只启动一套系统，切换要重启。两套镜像可共用设备，但没有同时运行的两个内核，也就不需要运行时仲裁器。
2. **处理器分区：**两个 SoC（System on a Chip）或固定划分的处理器核心分别运行 Linux、Android，通过网络或共享内存通信。各自控制分配给自己的资源，可以不使用虚拟化。同一颗 SoC 也可能这样部署。
3. **共享内核：**两套用户空间运行在同一内核上，用容器、命名空间等隔离进程和文件系统。它节省第二个内核及虚拟设备的成本，但一方需要不同内核、内核补丁或独立的内核故障边界时不适合。
4. **独立内核共享处理器资源：**Linux 与 Android 各有内核，并共享可调度的 CPU、内存或设备，由 hypervisor（虚拟机资源仲裁层）等组件隔离和仲裁。两者可能是并列客体，也可能一方是宿主、另一方是客体。仅凭“双系统”不能推断拓扑。

车机采用第四种方案时，收益是复用硬件并隔离不同系统的软件故障与权限边界。代价是必须定义显示、音频、存储、网络等设备由谁拥有，跨系统访问走共享、模拟还是直通，并处理调度与 I/O 延迟。排查前应从启动配置、内核/虚拟机日志、虚拟机监控程序和设备树或 PCI 枚举中核实实际拓扑。Android 宿主启动 Microdroid 的 AVF 场景也属于虚拟化，但不代表所有 Linux/Android 双系统车机都使用 AVF。

**Q4: [learning] 为什么两个独立内核不能直接共享硬件，hypervisor 与两类 VMM 怎样解决资源冲突？**

两个内核都按“自己管理整机”设计。如果它们能任意修改页表、处理中断或写设备寄存器，就可能访问彼此内存、重复配置同一设备并相互破坏。虚拟化在客体内核与共享硬件之间建立资源仲裁边界：给客体可运行的虚拟 CPU、可见的内存范围和受控设备接口。

先看一台虚拟机运行所需的三个动作：

1. **分配：**管理层给客体配置 vCPU、内存和设备。客体页表先把进程虚拟地址转换成客体物理地址，硬件的第二阶段转换再把它映射到获准的实际物理页。客体内核能改自己的页表，却不能因此把未分配给它的物理内存映射进来。
2. **运行与拦截：**硬件让客体内核以受限身份运行。允许的普通指令直接执行。需要更高权限或访问受控虚拟设备时发生 VM exit，由 hypervisor、宿主内核或用户态设备后端处理，再恢复客体。具体路径取决于平台和设备实现。
3. **仲裁：**调度器决定 vCPU 何时占用物理 CPU。设备后端完成 I/O 后，可通过受控的虚拟中断通知客体，或与客体约定共享内存队列。客体能看到“自己的设备”，不等于它独占物理设备。

第一类 VMM（Virtual Machine Monitor，虚拟机监控程序）直接承载客体并仲裁硬件。第二类运行在宿主操作系统上，复用宿主调度和 I/O 后端。这个分类只描述部署关系，不能推出第一类一定更快或更安全。Linux KVM 是混合形态的好例子：VMM 在用户态配置虚拟机，客体 CPU 运行依靠内核与硬件，设备仍可能由用户态处理。车机选型要逐项看调度、设备直通或模拟、内存隔离和故障域，而不是只看“第一类/第二类”标签。



**Q5: [learning] 为什么 QEMU 还需要 KVM 或 TCG，客体指令和设备访问分别怎样执行？**

QEMU 提供客体看到的**机器模型**，包括 CPU 型号、内存布局和设备。它还需要一种方式执行客体 CPU 指令。TCG（Tiny Code Generator）翻译指令，KVM（Kernel-based Virtual Machine）利用硬件虚拟化运行指令。二者是可选的 CPU 执行路径，不能代替 QEMU 的整机和设备模型。

两条路径的区别在于客体 CPU 如何前进：

1. **TCG：**QEMU 把客体指令块动态翻译为宿主指令再运行。它能支持不同指令集的客体，也适合没有虚拟化扩展的环境。指令翻译带来额外开销。
2. **KVM：**QEMU 创建 VM 和 vCPU，并让 vCPU 宿主线程经 KVM_RUN 进入客体。普通客体指令大多在处理器上直接执行。需要用户态处理的设备访问可触发 KVM_EXIT_MMIO 等退出，QEMU 模拟设备、提供结果，再让 vCPU 继续。部分退出可由内核处理，不应把每次中断或系统调用都算作返回 QEMU。
3. **客体系统调用：**客体应用调用自己的 Linux/Android 内核，通常仍在客体内完成。不是每次都转成宿主系统调用。这是“运行整个客体系统”和“翻译一个客体用户态程序”的根本区别。

QEMU 的**系统模拟**能启动完整客体内核。**用户态模拟**只运行客体程序并适配其系统调用，没有客体内核。跨指令集一般选 TCG。同架构、宿主内核及硬件支持时可用 KVM。实际车机也可能使用 crosvm 或其他 VMM，QEMU 只是解释这套分工的例子。依据：QEMU《About QEMU》与 Linux《KVM API》。



**Q6: [learning] 普通 KVM 已有虚拟机隔离，为什么还需要 pKVM？**

普通 KVM 主要防止**客体越界访问宿主或其他客体**，但宿主内核仍管理并通常可映射客体内存。若工作负载还要求“宿主被攻破后也不能读取客体秘密”，就需要 pKVM（protected KVM）把宿主排除在受保护客体私有内存的信任边界之外。这是 AVF 使用受保护虚拟机（pVM）的原因之一。

pKVM 的保护沿页面所有权建立：

1. **客体私有页：**Arm EL2 的 hypervisor 管理宿主与客体的 Stage-2 映射。页捐给 pVM 后，从宿主可访问映射中移除。宿主内核即使控制自己的页表，也不能仅靠重映射读出该页。
2. **设备 DMA：**仅限制 CPU 页表还不够，设备仍可能直接访问物理内存。平台还需 IOMMU（Input-Output Memory Management Unit）等机制约束 DMA，才能维持相同隔离目标。
3. **明确共享：**虚拟设备后端需要读取请求或写入结果时，客体须按协议共享所需页面或缓冲区。只开放通信数据，不能因此把所有私有页重新暴露给宿主。
4. **边界与成本：**宿主不能任意检查或换出私有页，调试、回收和某些 I/O 路径更复杂。宿主仍控制 vCPU 调度和设备供给，能够拒绝服务。存储镜像的真实性与持久状态还需验证启动、dm-verity、AuthFS 等相应机制。

pKVM 解决的是特定信任威胁，不是“比普通 KVM 性能更高”的开关。车机若主要需要 Linux/Android 互相隔离，还应先明确宿主是否可信、是否需要保护客体免受宿主读取，再决定是否需要受保护虚拟机。依据：Android《AVF architecture》《Security》。



**Q7: [learning] 为什么虚拟机需要模拟设备、virtio 或设备直通，三种方案怎样取舍？**

独立内核要访问存储或网卡，必须看到一种自己驱动能理解的**设备接口**。宿主有物理 UFS（Universal Flash Storage）驱动，不会自动变成客体的驱动。广义的全虚拟化让客体按普通硬件接口运行，半虚拟化则要求客体知道并使用专门的协作接口。现代系统可让 CPU 使用硬件辅助虚拟化，同时让 I/O 使用半虚拟化，因此这里比较的是设备方案。

按设备接口与所有权比较：

1. **模拟真实设备：**VMM 仿照某款控制器的寄存器、中断和命令，客体沿用已有驱动，例如 e1000 网卡。适合无法更换客体驱动的系统，但频繁访问寄存器可能使 vCPU 退出并等待软件模拟。
2. **半虚拟化设备：**客体预装 virtio 这类标准化虚拟设备的前端驱动，双方不再模仿真实控制器，而是通过共享队列批量提交请求。它减少控制路径的逐次仿真，适合能控制客体镜像的场景。仍要计算通知、拷贝、共享内存和宿主后端的成本。
3. **设备直通：**把物理设备或其可隔离的功能分给客体，客体使用对应物理驱动，减少软件设备模拟。代价是该设备通常不能由两套系统随意同时独占，还需要中断、DMA/IOMMU、复位与故障隔离方案。

这三种方案可以混用。车机可能让 Android 独占显示控制器，让两套系统通过 virtio 或共享内存访问网络，同时直通另一种设备。选型先问客体有哪些驱动、设备由谁拥有、是否要共享，再测吞吐和尾延迟。给 Android 安装 APK 不能补上缺失的内核驱动。



**Q8: [learning] 为什么要有 virtio 标准，前端、后端、队列和传输层怎样形成一个设备？**

如果每种 VMM 都自定义虚拟磁盘和网卡寄存器，客体就要为每个平台维护不同驱动。virtio（Virtual I/O）把**客体可见的设备契约**标准化：同一类前端驱动能与遵循规范的不同后端协作。规范解决互通，不规定后端必须使用哪种宿主文件或保证固定性能。

一个 virtio 设备由四层协作：

1. **设备类型：**virtio-blk 规定块读写、容量与能力。virtio-net 规定网络收发。客体的类型驱动把文件系统或网络栈请求转成这类设备的协议。
2. **公共机制：**设备提供特性位，驱动只接受自己支持的能力。virtqueue 以描述符指向请求缓冲区，传递“可处理”和“已完成”的状态。双方不能假定未协商功能存在。
3. **传输层：**virtio-pci、virtio-mmio 等给出设备发现、配置寄存器、队列地址和通知方式。它解决“接口从哪里进入”，不改变块设备的读写语义。
4. **宿主后端：**QEMU、crosvm 等 VMM 实现设备另一侧，把虚拟块请求接到镜像文件、宿主块设备或其他资源。

启动时也要形成契约：客体发现并复位设备，确认设备类型与状态，读取特性并选择共同支持的子集，设置 virtqueue，最后将设备置为可运行状态。这个顺序解释了为何“VMM 已提供磁盘”仍不足以让客体读盘：传输驱动和 virtio-blk 类型驱动必须存在，特性与队列也必须初始化成功。依据：OASIS《Virtio 1.2》设备初始化与特性协商章节。



**Q9: [learning] 为什么 virtio 设备还要借 PCI 或 MMIO，客体怎样从发现设备走到 /dev/vda？**

virtio 规定设备协议，但客体首先得知道“设备在哪里、如何读配置、怎样通知它”。PCI（Peripheral Component Interconnect）和 MMIO（Memory-Mapped I/O）提供两种不同的**传输入口**。之后还需匹配 virtio-blk 驱动，设备才会进入客体块层。

以 virtio-pci 块设备为例，发现链是：

1. **虚拟总线呈现：**VMM 在客体可见的 PCI 总线上创建设备。现代 virtio PCI 设备使用厂商 ID `0x1AF4`，块设备的现代设备 ID 为 `0x1042`。旧式兼容设备还有不同 ID，不能只按一个数字判断所有版本。
2. **传输驱动接管：**客体 PCI 枚举读取配置空间并找到设备，virtio_pci 根据能力结构定位公共配置、队列通知、中断状态和设备配置区域，然后注册一个 virtio 块类型设备。
3. **类型驱动接管：**virtio_blk 匹配块设备类型，协商特性并建立 virtqueue，再向客体块层注册磁盘。典型 Linux 客体的首块 virtio 磁盘可能出现为 `/dev/vda`，实际名称还取决于枚举顺序与设备节点管理。

virtio-mmio 不依赖虚拟 PCI 总线，适用于不少嵌入式机器模型。但 MMIO 本身没有 PCI 式通用枚举，平台需通过设备树、ACPI 等描述告知客体寄存器位置和中断。virtio_mmio 再完成传输层接管，后续仍由 virtio_blk 处理块协议。排查“镜像已挂给 VMM、客体却没有盘”时，依次核对设备是否呈现、传输驱动是否发现、类型驱动是否匹配、队列是否建立。依据：OASIS《Virtio 1.2》PCI 与 MMIO 传输章节。



**Q10: [learning] 为什么宿主的镜像文件能在客体中变成磁盘，一次块读取怎样映射到宿主存储？**

镜像文件只是宿主保存的数据，客体不能直接打开宿主文件描述符，也不能直接调用宿主 UFS 驱动。virtio-blk 在两侧建立协议映射：客体看到具有容量与扇区地址的块设备，宿主后端把相同扇区请求换算成镜像文件或块设备上的 I/O。选择块设备接口，是为了让客体自己管理分区和文件系统。若只需交换少量文件，可以另选文件共享接口。

以客体读取已挂载文件为例，路径依次是：

1. **准备设备：**VMM 提供盘体，设备配置空间报告容量，单位为 512 字节扇区。客体 virtio_blk 驱动完成发现与初始化，把设备注册到块层。文件系统随后才能挂载其中的分区。
2. **产生请求：**客体应用读文件，客体文件系统把文件偏移换成逻辑块，块层把它交给 virtio_blk。驱动生成读请求，指定 `type = VIRTIO_BLK_T_IN`、起始 `sector` 和接收数据的缓冲区。
3. **执行映射：**宿主后端读取请求，把扇区号按协议换算成字节偏移 `sector × 512`，再通过镜像格式和宿主存储栈找到实际数据。raw 镜像可直接按偏移访问。qcow2 还要经其格式映射。后端把结果写入获准的客体缓冲区。
4. **完成返回：**客体驱动收到完成状态后结束块请求，文件系统再把文件内容交给应用。宿主盘体可换实现，只要设备协议、容量与数据内容契约保持一致，客体基本读盘接口不变。

这解释了“客体必须有驱动”：宿主后端只接受 virtio 块协议，客体文件系统只提出通用块请求，中间的 virtio_blk 前端负责翻译和排队。受保护虚拟机还要求后端仅访问明确共享的请求缓冲区，不意味着宿主能读取全部客体私有内存。Android Microdroid 的系统和 payload 镜像是这一机制的应用实例，具体镜像组合归 Android 专题。



**Q11: [learning] virtqueue 为什么比逐寄存器仿真更合适，一次请求和完成怎样通过队列传递？**

逐次仿真真实设备寄存器，可能每访问一次就需要退出客体并让 VMM 解释语义。单有共享内存也不够，双方还须约定缓冲区地址、长度、读写方向、可用状态和完成状态。virtqueue 把这些约定组织成**可批量提交的请求队列**，通知只负责提醒后端“队列有新工作”。这减少控制路径开销，但仍有内存同步、通知和后端处理成本。

以 virtio-blk 的 split virtqueue 为例：

1. **描述缓冲区：**前端填写描述符链，分别指向读命令头、用于接收数据的缓冲区和状态字节。描述符包含地址、长度、方向及下一项索引。后端据此知道读什么、把结果写到哪里，而不需要模仿某款磁盘控制器的寄存器序列。
2. **发布请求：**前端先保证描述符内容对后端可见，再把链首索引放入 available 环并更新索引。必要的内存屏障防止后端先看到“请求可用”却读到未写好的描述符。若通知未被抑制，再通过传输层提醒后端。
3. **处理与完成：**后端取出请求，在宿主存储上执行 I/O，写入数据和状态，再把完成项发布到 used 环。前端收到通知或轮询到完成后检查状态、回收描述符，并结束上层块请求。通知和中断可被抑制或合并，因此一次 I/O 不必然对应一次 VM exit。
4. **布局版本：**split 将描述符表、available 环和 used 环分开。virtio 1.1 引入 packed，把可用与已用状态放在单个描述符环中。它改变队列布局与状态追踪，不改变 virtio-blk 的读写命令。双方须协商支持后才能启用 packed。

队列中的地址必须按相应虚拟化模型合法映射。普通客体由 VMM/宿主按其内存模型访问。pVM 的后端只能访问被明确共享的缓冲区。依据：OASIS《Virtio 1.2》split/packed virtqueue 与通知章节、Android《AVF architecture》。



**Q12: [learning] 为什么 virtio-blk 写成功仍可能掉电丢数据，FLUSH 怎样建立持久化边界？**

“写请求完成”与“数据已经稳定写入非易失介质”是两个不同承诺。writeback 模式下，后端可先把写入放进易失缓存并应答。掉电或宿主崩溃时缓存可能丢失。需要持久化时，客体必须通过文件系统同步、块层刷新、virtio 刷新和宿主存储栈形成完整链路。

按 OASIS Virtio 1.2 的块设备语义区分：

1. **能力与缓存模式：**设备宣告特性，驱动协商 VIRTIO_BLK_F_FLUSH 才能发送 VIRTIO_BLK_T_FLUSH。VIRTIO_BLK_F_CONFIG_WCE 允许协商后配置写缓存模式。不能从“virtio-blk”四个字推断设备默认使用 writeback 或 writethrough。
2. **写入与刷新：**在 writeback 情况下，已完成的写入可能尚未稳定。客体随后发送 FLUSH，后端必须在报告 FLUSH 完成前，按规范使此前相关写入稳定落到其持久化后端。仅有队列内存屏障或完成通知，不等于刷新宿主缓存。
3. **最终边界：**规范对持久化后端提出保证，但实际可靠性还取决于宿主镜像格式、文件系统、块设备和硬件供电。如果底层谎报刷新成功，virtio 协议本身无法补救。

因此车机的数据库、日志或更新状态出现断电丢失时，要沿“应用同步调用 → 客体文件系统与块层 → virtio 特性和缓存模式 → VMM 后端 → 宿主文件系统与物理存储”逐层查证。写调用返回、请求进入 virtqueue、后端收到数据和 FLUSH 完成都不是同一个时间点。依据：OASIS《Virtio 1.2》块设备缓存与 FLUSH 规则。



**Q13: [learning] QEMU（Quick Emulator）是什么，系统模拟和用户态模拟有什么区别？**

QEMU 是开源的机器模拟器与虚拟化工具。系统模拟提供一台由处理器、内存和设备组成的完整虚拟机器，用来启动客体操作系统。用户态模拟只在宿主上运行一个为其他架构编译的程序，只模拟该程序需要的指令，不提供完整的客体机器。两者对应不同的命令行程序：系统模拟是 qemu-system-<架构>，用户态模拟是 qemu-<架构>。

具体机制与边界如下：

1. **系统模拟：**面向完整操作系统，处理器、内存和设备都由 QEMU 的机器模型提供，客体可以与宿主架构不同。例如系统模拟可直接启动内核与初始内存文件系统。
2. **用户态模拟：**面向单个程序，把客体指令翻译成宿主指令执行，程序看到模拟的用户态环境，但没有客体内核。例如可在 x86 宿主上运行 AArch64 编译的程序，系统调用由用户态模拟适配到宿主内核。
3. **边界：**用户态模拟不需要客体系统镜像，也不能启动 Guest OS。要运行完整操作系统必须用系统模拟。



**Q14: [learning] QEMU 与 KVM（Kernel-based Virtual Machine）是什么关系，TCG 与硬件加速分别做什么？**

QEMU 不等同于 KVM。QEMU 提供机器模型和设备模拟，并决定客体 CPU 指令如何执行。KVM 是 Linux 内核提供的硬件虚拟化加速接口。系统模拟下，客体指令可以走 TCG（Tiny Code Generator）翻译执行，也可以走 KVM 直接在宿主处理器上运行。

具体机制与边界如下：

1. **TCG 翻译执行：**QEMU 把客体指令动态翻译成宿主指令，不依赖硬件虚拟化扩展，可跨架构，通常慢于硬件辅助路径。
2. **KVM 硬件辅助：**利用处理器虚拟化扩展直接执行客体代码，QEMU 仍负责虚拟机的设备模型与 I/O 模拟。
3. **边界：**能否使用 KVM 取决于宿主操作系统、处理器和 QEMU 构建。跨指令集的客体通常使用 TCG。



**Q15: [learning] pKVM（protected KVM）与普通 KVM 的本质差别是什么，为什么说信任模型把宿主内核排除在外？**

普通 KVM 下 guest 内存由宿主内核管理，宿主可以访问。pKVM 借助 ARM 的 EL2 与 Stage-2 页表强制 guest 内存只属于 guest，宿主内核即使被攻破也无法读写。宿主内核不再被信任访问私有页，但保护还依赖固件、硬件和 DMA 隔离等平台条件。

具体机制与边界如下：

1. **普通 KVM：**guest 是宿主内核管理的普通负载，宿主通常可以访问客体内存，适合可信环境下的资源复用。
2. **pKVM protected VM：**Stage-2 地址转换由 hypervisor 控制，受保护 guest 私有页面由 hypervisor 限制访问，私有页面须经明确授权才能共享。
3. **信任模型的变化：**被排除的是宿主而非 guest——宿主内核被排除在私有内存信任边界之外，保护仍依赖硬件、固件和 DMA 隔离，因此能承载内容对宿主也保密的工作负载。



**Q16: [learning] pKVM 的代价是什么，适合承载什么负载？**

代价在宿主侧：内存划归 guest 后，宿主的内存回收、内容级调试与探测都拿不到数据，对 protected guest 的管理能力受限。适合的是内容必须对宿主保密的负载。Android 的 AVF（Android Virtualization Framework）可使用 pKVM 作为 hypervisor、Crosvm 为 VMM、Microdroid 为最小 guest，正是用它保护这类场景。

具体机制与边界如下：

1. **管理受限：**宿主不能随意回收或检查 protected guest 的页面，调试与诊断手段相应减少。
2. **适用负载：**密钥处理、机密计算等需要防止宿主窥探的场景。
3. **Android 集成：**AVF 的整体架构与接入方式归 Android 虚拟化专题，这里只说明机制归属。



**Q17: [learning] 全虚拟化与半虚拟化分别是什么，理解模型上有什么区别？**

广义全虚拟化提供可运行未修改客体的环境，半虚拟化则要求客体配合虚拟化接口。全虚拟化把虚拟设备伪装成真实硬件，guest 不加修改、用真机驱动访问。半虚拟化与 guest 做协议约定，guest 安装专用前端驱动，按约定格式与后端协作。理解模型：全虚拟化靠欺骗换兼容，半虚拟化靠合作换效率。

具体机制与边界如下：

1. **全虚拟化：**hypervisor 按真实芯片设计“假硬件”，如模拟 Intel e1000 网卡，寄存器布局与中断行为同真机一致，具备对应驱动的 guest 可不修改运行。
2. **半虚拟化：**不照抄任何真实芯片，virtio（Virtual I/O）按规范定义新接口，前端驱动与宿主后端按协议交换数据。
3. **分界的实践范围：**CPU 虚拟化已由硬件扩展（Intel VT-x、AMD-V）直接加速，guest 同样无感知。这一二分主要用于 I/O 设备，混合形态是常态。



**Q18: [learning] 半虚拟化省掉了什么开销，为什么效率更高？**

省掉的是“每次设备访问都陷入 hypervisor 模拟寄存器”的开销。模拟设备的寄存器访问可能触发 VM exit，但具体次数取决于实现。virtio 把请求批量放进共享内存队列，可通过一次通知处理一批，通知可批量或抑制，降低控制路径的平均开销。

具体机制与边界如下：

1. **全虚拟化的开销来源：**一次磁盘读写可能产生多次受拦截的寄存器访问，具体次数取决于设备和实现。
2. **半虚拟化的批量设计：**virtqueue 是共享内存环，请求以描述符链批量入队，请求缓冲区经共享内存访问，通知仍可能涉及寄存器访问。
3. **前提：**省开销以 guest 安装前端驱动为条件。没有驱动的系统需要选择客体支持的其他设备接口。



**Q19: [learning] 半虚拟化对 guest 有什么要求，设备选型怎么判断？**

半虚拟化要求 guest 内安装对应前端驱动（virtio-blk、virtio-net 等），否则设备不可用。选型规则：guest 不可修改或缺少驱动时用全虚拟化兜底，可配驱动且追求性能时用半虚拟化。

具体机制与边界如下：

1. **驱动是前提：**老系统、闭源系统常缺少 virtio 前端驱动，可能需要使用模拟设备，这是全虚拟化设备仍然存在的原因。
2. **选型规则：**先看 guest 能否安装驱动，再看是否需要性能。具备驱动时可优先评估 virtio，模拟设备可作为兼容方案，最终应实测。



**Q20: [learning] virtio 是什么？**

virtio（Virtual I/O）是半虚拟化 I/O 的开放标准接口：它不照抄任何真实芯片，而是定义一族虚拟设备，guest 内使用规范规定的前端驱动，VMM（虚拟机监控程序，如 QEMU、crosvm）或外部服务提供后端，双方按统一协议经共享内存队列交换数据。规范由标准组织 OASIS（Organization for the Advancement of Structured Information Standards）以 Virtual I/O Device（VIRTIO）为名发布，目标是给虚拟环境提供简单、高效、标准、可扩展的虚拟设备机制，取代各平台自建的私有接口。

具体机制与边界如下：

1. **三层组成：**每类 virtio 设备都由三层拼合：

    1. **设备类型层：**规范为每类设备规定 virtqueue、特性位、配置空间与操作流程。virtio 1.2 定义网卡、块设备、控制台、GPU 等多种设备，例如 virtio-net（网卡）与 virtio-blk（块设备）。
    2. **公共机制层：**所有设备类型共用同一套基础——virtqueue 是两端共享的内存队列，负责批量搬运数据。特性位逐位协商能力。配置空间存放设备属性，部分属性可能变化。
    3. **传输层：**决定设备怎样被 guest 发现和访问，规范给出 PCI、MMIO（Memory-Mapped I/O）和 Channel I/O（IBM s390 大型机的 I/O 总线）三种，同一设备协议可跑在不同传输上。

2. **四条设计目标：**规范引言用四个性质刻画 virtio：

    1. **简单：**只用中断、DMA 这类常规总线机制，驱动作者眼中它就是一台普通设备，没有特殊的页翻转或写时复制机制。
    2. **高效：**数据走描述符环，队列布局旨在降低通信开销，缓存争用仍取决于布局和实现。
    3. **标准：**不假设任何虚拟化环境，只要求支持设备所挂的总线。
    4. **可扩展：**特性位由设备提供、驱动确认，双方只使用共同认可的子集，有助于不同版本的设备与驱动协商兼容能力。

3. **由来与标准化：**Rusty Russell 提出 virtio 并撰写早期规范草案，早期驱动随 Linux 2.6.24 发布，1.0 之前的接口在规范里统称 legacy interface。OASIS 接手后于 2016 年发布 1.0，2019 年发布 1.1（引入 packed virtqueue），2022 年发布 1.2。QEMU 与 crosvm 都可提供 virtio 设备，它已是虚拟化 I/O 的事实标准。

4. **边界：**规范只约定 guest 可见的设备接口，两件事不归它管：

    1. **不含后端实现：**同一 virtio-blk 的性能取决于后端 VMM 与宿主 I/O 路径，规范不作保证。
    2. **不免除前端驱动：**guest 必须安装对应前端驱动，否则设备不可用。



**Q21: [learning] virtio 虚拟磁盘（virtio-blk）是什么，为什么说它是协议约定出来的磁盘？**

virtio-blk 是按 virtio 规范实现的半虚拟化块设备：guest 侧前端驱动把它呈现为普通块设备（Linux 下首块通常是 `/dev/vda`），宿主侧后端把读写落到宿主文件或块设备。它不是对某种真实硬盘控制器的模拟——规范定义容量的表示、缓存行为和命令集合，设备提供具体容量，双方协商可选能力，不存在被照抄寄存器语义的“真实盘”。

具体机制与边界如下：

1. **是什么：**guest 看到一块标准块设备，文件系统与挂载照常工作。宿主侧由 VMM 后端承接真实 I/O。
2. **为什么说“协议约定”：**没有照抄任何真实芯片，容量由设备报告，命令集与缓存行为按规范和特性位协商，磁盘几何只是可选兼容项。
3. **行为边界：**宿主后端从镜像文件换成块设备时，只要容量、数据和协议行为保持一致，guest 无需改变基本块访问方式。代价是 guest 必须安装 virtio 前端驱动。



**Q22: [learning] virtio 磁盘在 guest 侧和宿主侧分别是什么形态？**

guest 侧，virtio_blk 前端驱动把设备注册为标准块设备，盘名通常以 vd 开头，SATA/SCSI 磁盘通常以 sd 开头。宿主侧，后端由 VMM 提供：QEMU 可通过 virtio-blk-pci 在 PCI 总线上挂设备，盘体可以是宿主文件（raw、qcow2）或宿主块设备。

具体机制与边界如下：

1. **guest 侧：**virtio_blk 驱动注册块设备，上层文件系统与挂载机制无感知。具体设备节点取决于设备枚举、分区和镜像布局。
2. **宿主侧：**QEMU 后端持有盘体镜像。Android AVF 的 VMM 是 Crosvm，系统盘与 payload 盘由它挂入。
3. **非 PCI 形态：**支持相应 MMIO 传输的 QEMU 机器上可用 virtio-blk-device，协议相同、传输不同。



**Q23: [learning] virtio 磁盘的容量、缓存等属性由谁决定？**

容量等配置由设备给出，可选能力由双方按特性位协商，不是照搬物理盘面参数。容量以 512 字节扇区计。flush、discard、缓存模式等能力对应特性位，如 VIRTIO_BLK_F_FLUSH、VIRTIO_BLK_F_DISCARD、VIRTIO_BLK_F_CONFIG_WCE。

具体机制与边界如下：

1. **配置空间：**virtio 设备向 guest 暴露一块属性区，容量等属性放在其中，部分配置可能变化。
2. **特性位协商：**能力支持与否由特性位逐位确认，guest 只使用双方都支持的子集。
3. **与模拟盘的差别：**不依赖柱面、磁头、扇区几何来寻址，规范仍提供可选的几何兼容字段，属性集由规范定义。



**Q24: [learning] virtqueue 是什么，guest 的一次读写请求怎么流转到宿主存储？**

virtqueue 是两端共享的内存队列。split 布局由描述符表、available 环、used 环组成。前端驱动把命令头与数据缓冲区挂成描述符链入队并通知后端，后端执行 I/O 后写入状态缓冲区，把完成项发布到 used 环，必要时通知 guest。请求缓冲区经共享内存访问，通知仍可能涉及寄存器访问。

具体机制与边界如下：

1. **组装请求：**驱动填命令头——type 字段区分读写（VIRTIO_BLK_T_IN/T_OUT），sector 字段给出以 512 字节为单位的起始偏移——再把命令头与数据缓冲区用 NEXT 标志串成描述符链。
2. **入队并通知：**描述符链首索引写入 available 环表示可处理，未抑制通知时再通知后端（PCI 上是一次 doorbell 寄存器写）。
3. **后端执行：**后端从 available 环取出请求，按命令头对宿主镜像文件或块设备发起实际读写。
4. **完成回收：**后端写入状态缓冲区并把完成项放入 used 环，必要时通知 guest。前端驱动取回结果、释放描述符，向上层完成请求。



**Q25: [learning] virtio 的缓存语义由什么决定，T_FLUSH 起什么作用？**

后端可配置为 writeback——写入进入宿主侧缓存即应答完成，此时应答不等于数据已落宿主存储。需要持久性保证时，guest 可在协商支持后发送 T_FLUSH，由后端按协议刷新此前相关写入。设备是否支持 flush、缓存模式能否运行中切换，都由特性位协商（VIRTIO_BLK_F_FLUSH、VIRTIO_BLK_F_CONFIG_WCE）。

具体机制与边界如下：

1. **writeback 的后果：**宿主崩溃可能丢失已经应答的写入。
2. **T_FLUSH 的作用：**guest 显式请求刷新，后端须在报告完成前使相关写入到达其持久化后端，实际可靠性还依赖底层正确实现刷新。
3. **能力来源：**是否支持 flush 与缓存模式切换由特性位协商，不能假设默认行为。



**Q26: [learning] split virtqueue 和 packed virtqueue 有什么区别？**

两者是 virtqueue 的两种布局。split 是描述符表、available 环、used 环各自独立的三段式。virtio 1.1 起新增 packed，把描述符与可用、已用状态放在同一描述符环中，并保留独立的事件抑制区域，可能改善缓存访问。双方按特性位协商能否使用 packed 布局，Linux 5.15 的 UAPI 头已包含两种布局的定义。

具体机制与边界如下：

1. **split：**三段各自独立，驱动与后端通过环下标间接引用描述符。
2. **packed：**使用单个描述符环和事件抑制区域，是 virtio 1.1 引入的替代布局，实际性能取决于实现和负载。
3. **选择方式：**由特性位协商，同一驱动可兼容两种布局。



**Q27: [learning] virtio-pci 是什么，guest 怎么通过它发现这块磁盘？**

virtio-pci 不是总线，而是 virtio 设备“乘坐”PCI 总线的传输层。QEMU 在机器模型的虚拟 PCI 总线上把 virtio-blk 做成标准 PCI 设备，guest 用 PCI 枚举机制找到它，再经两级驱动匹配注册磁盘，设备节点取决于枚举和设备管理。

具体机制与边界如下：

1. **QEMU 侧构造：**virtio-blk-pci 设备在 PCI 总线上实例化设备，盘体镜像由后端持有。总线由机型提供——pc 机型对应 i440FX，q35 机型对应其 PCIe 控制器。
2. **guest PCI 枚举：**内核从设备配置空间读到厂商 ID 0x1AF4（内核常量 REDHAT_QUMRANET）与设备 ID——现代布局从 0x1040 起按设备类型编号，块设备为 0x1042。
3. **virtio_pci 认领：**驱动通过 PCI 配置空间的能力结构定位 BAR 中的各段地址：common config 放特性协商与队列配置，notify 区是 doorbell，ISR 区放中断状态，device config 放磁盘容量等设备配置。
4. **virtio 总线匹配：**virtio_pci 注册一个 virtio 设备（块设备类型 ID 为 2），virtio 总线按类型匹配给 virtio_blk 驱动。初始化过程中协商特性并建立 virtqueue。
5. **块设备出现：**probe 完成向块层注册 gendisk，首块盘通常出现为 `/dev/vda`，此后读写走 virtqueue 数据通路。



**Q28: [learning] 为什么 virtio 借 PCI 总线呈现，没有 PCI 的环境用什么？**

借 PCI 是为了复用既有发现机制：枚举、BAR 内存映射、MSI-X 中断都是 PCI 栈自带的，virtio 不必发明新的设备发现协议。代价是机器模型通常需要提供虚拟 PCI 控制器。没有 PCI 的环境用 virtio-mmio——同一套协议直接挂在内存映射总线上，guest 换 virtio_mmio 传输驱动，块驱动与协议不变。

具体机制与边界如下：

1. **复用 PCI 栈：**发现、地址映射、中断都有现成机制，virtio 只定义设备本身。
2. **代价：**使用虚拟 PCI 的机器模型需要提供 PCI 控制器，机器模型更重。
3. **virtio-mmio：**QEMU 中支持 MMIO 的机器可使用 virtio-blk-device，平台还需通过设备树等方式描述设备，传输层替换不影响 virtio_blk 与协议。

virtio-pci 负责设备发现、配置和通知，virtqueue 负责传递请求及完成状态。
