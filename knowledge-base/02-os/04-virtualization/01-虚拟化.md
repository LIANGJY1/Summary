# 虚拟机与虚拟化

> 学习资料。围绕车机 Linux/Android 双系统，按“为什么需要隔离与资源仲裁 → CPU 怎样运行 → 设备怎样呈现 → 一次磁盘 I/O 怎样完成”组织。本文只讲可迁移的虚拟化原理。AVF（Android Virtualization Framework）的 Android 组件与接入见 [Android AVF 专题](../../01-android/09-平台服务/06-AVF虚拟化.md)。依据：QEMU《About QEMU》、Linux《KVM API》、OASIS《Virtio 1.2》、Android《AVF architecture》《Security》。题序即文档结构。

**Q1: [learning] 车机为什么会同时运行 Linux 和 Android，怎样判断双系统是否采用虚拟化？**

采用虚拟化的动机通常是让两套需要独立内核的系统复用一套硬件，同时明确分配 CPU、内存和设备。例如产品可以让 Linux 承载一类设备服务、Android 承载交互界面，但具体分工取决于产品。看到两者并存只能说明有两个软件环境，必须再确认它们是否同时运行、是否共用内核与处理器资源，才能判断是否存在虚拟机。

按实际运行边界区分四种方案：

1. **交替启动：**一次只启动一套系统，切换要重启。两套镜像可共用设备，但没有同时运行的两个内核，也就不需要运行时仲裁器。
2. **处理器分区：**两个 SoC（System on a Chip）或固定划分的处理器核心分别运行 Linux、Android，通过网络或共享内存通信。各自控制分配给自己的资源，可以不使用虚拟化。同一颗 SoC 也可能这样部署。
3. **共享内核：**两套用户空间运行在同一内核上，用容器、命名空间等隔离进程和文件系统。它节省第二个内核及虚拟设备的成本，但一方需要不同内核、内核补丁或独立的内核故障边界时不适合。
4. **独立内核共享处理器资源：**Linux 与 Android 各有内核，并共享可调度的 CPU、内存或设备，由 hypervisor（虚拟机资源仲裁层）等组件隔离和仲裁。两者可能是并列客体，也可能一方是宿主、另一方是客体。仅凭“双系统”不能推断拓扑。

车机采用第四种方案时，收益是复用硬件并隔离不同系统的软件故障与权限边界。代价是必须定义显示、音频、存储、网络等设备由谁拥有，跨系统访问走共享、模拟还是直通，并处理调度与 I/O 延迟。排查前应从启动配置、内核/虚拟机日志、虚拟机监控程序和设备树或 PCI 枚举中核实实际拓扑。Android 宿主启动 Microdroid 的 AVF 场景也属于虚拟化，但不代表所有 Linux/Android 双系统车机都使用 AVF。

**Q2: [learning] 为什么两个独立内核不能直接共享硬件，hypervisor 与两类 VMM 怎样解决资源冲突？**

两个内核都按“自己管理整机”设计。如果它们能任意修改页表、处理中断或写设备寄存器，就可能访问彼此内存、重复配置同一设备并相互破坏。虚拟化在客体内核与共享硬件之间建立资源仲裁边界：给客体可运行的虚拟 CPU、可见的内存范围和受控设备接口。

先看一台虚拟机运行所需的三个动作：

1. **分配：**管理层给客体配置 vCPU、内存和设备。客体页表先把进程虚拟地址转换成客体物理地址，硬件的第二阶段转换再把它映射到获准的实际物理页。客体内核能改自己的页表，却不能因此把未分配给它的物理内存映射进来。
2. **运行与拦截：**硬件让客体内核以受限身份运行。允许的普通指令直接执行。需要更高权限或访问受控虚拟设备时发生 VM exit，由 hypervisor、宿主内核或用户态设备后端处理，再恢复客体。具体路径取决于平台和设备实现。
3. **仲裁：**调度器决定 vCPU 何时占用物理 CPU。设备后端完成 I/O 后，可通过受控的虚拟中断通知客体，或与客体约定共享内存队列。客体能看到“自己的设备”，不等于它独占物理设备。

第一类 VMM（Virtual Machine Monitor，虚拟机监控程序）直接承载客体并仲裁硬件。第二类运行在宿主操作系统上，复用宿主调度和 I/O 后端。这个分类只描述部署关系，不能推出第一类一定更快或更安全。Linux KVM 是混合形态的好例子：VMM 在用户态配置虚拟机，客体 CPU 运行依靠内核与硬件，设备仍可能由用户态处理。车机选型要逐项看调度、设备直通或模拟、内存隔离和故障域，而不是只看“第一类/第二类”标签。

**Q3: [learning] 为什么 QEMU 还需要 KVM 或 TCG，客体指令和设备访问分别怎样执行？**

QEMU 提供客体看到的**机器模型**，包括 CPU 型号、内存布局和设备。它还需要一种方式执行客体 CPU 指令。TCG（Tiny Code Generator）翻译指令，KVM（Kernel-based Virtual Machine）利用硬件虚拟化运行指令。二者是可选的 CPU 执行路径，不能代替 QEMU 的整机和设备模型。

两条路径的区别在于客体 CPU 如何前进：

1. **TCG：**QEMU 把客体指令块动态翻译为宿主指令再运行。它能支持不同指令集的客体，也适合没有虚拟化扩展的环境。指令翻译带来额外开销。
2. **KVM：**QEMU 创建 VM 和 vCPU，并让 vCPU 宿主线程经 KVM_RUN 进入客体。普通客体指令大多在处理器上直接执行。需要用户态处理的设备访问可触发 KVM_EXIT_MMIO 等退出，QEMU 模拟设备、提供结果，再让 vCPU 继续。部分退出可由内核处理，不应把每次中断或系统调用都算作返回 QEMU。
3. **客体系统调用：**客体应用调用自己的 Linux/Android 内核，通常仍在客体内完成。不是每次都转成宿主系统调用。这是“运行整个客体系统”和“翻译一个客体用户态程序”的根本区别。

QEMU 的**系统模拟**能启动完整客体内核。**用户态模拟**只运行客体程序并适配其系统调用，没有客体内核。跨指令集一般选 TCG。同架构、宿主内核及硬件支持时可用 KVM。实际车机也可能使用 crosvm 或其他 VMM，QEMU 只是解释这套分工的例子。依据：QEMU《About QEMU》与 Linux《KVM API》。

**Q4: [learning] 普通 KVM 已有虚拟机隔离，为什么还需要 pKVM？**

普通 KVM 主要防止**客体越界访问宿主或其他客体**，但宿主内核仍管理并通常可映射客体内存。若工作负载还要求“宿主被攻破后也不能读取客体秘密”，就需要 pKVM（protected KVM）把宿主排除在受保护客体私有内存的信任边界之外。这是 AVF 使用受保护虚拟机（pVM）的原因之一。

pKVM 的保护沿页面所有权建立：

1. **客体私有页：**Arm EL2 的 hypervisor 管理宿主与客体的 Stage-2 映射。页捐给 pVM 后，从宿主可访问映射中移除。宿主内核即使控制自己的页表，也不能仅靠重映射读出该页。
2. **设备 DMA：**仅限制 CPU 页表还不够，设备仍可能直接访问物理内存。平台还需 IOMMU（Input-Output Memory Management Unit）等机制约束 DMA，才能维持相同隔离目标。
3. **明确共享：**虚拟设备后端需要读取请求或写入结果时，客体须按协议共享所需页面或缓冲区。只开放通信数据，不能因此把所有私有页重新暴露给宿主。
4. **边界与成本：**宿主不能任意检查或换出私有页，调试、回收和某些 I/O 路径更复杂。宿主仍控制 vCPU 调度和设备供给，能够拒绝服务。存储镜像的真实性与持久状态还需验证启动、dm-verity、AuthFS 等相应机制。

pKVM 解决的是特定信任威胁，不是“比普通 KVM 性能更高”的开关。车机若主要需要 Linux/Android 互相隔离，还应先明确宿主是否可信、是否需要保护客体免受宿主读取，再决定是否需要受保护虚拟机。依据：Android《AVF architecture》《Security》。

**Q5: [learning] 为什么虚拟机需要模拟设备、virtio 或设备直通，三种方案怎样取舍？**

独立内核要访问存储或网卡，必须看到一种自己驱动能理解的**设备接口**。宿主有物理 UFS（Universal Flash Storage）驱动，不会自动变成客体的驱动。广义的全虚拟化让客体按普通硬件接口运行，半虚拟化则要求客体知道并使用专门的协作接口。现代系统可让 CPU 使用硬件辅助虚拟化，同时让 I/O 使用半虚拟化，因此这里比较的是设备方案。

按设备接口与所有权比较：

1. **模拟真实设备：**VMM 仿照某款控制器的寄存器、中断和命令，客体沿用已有驱动，例如 e1000 网卡。适合无法更换客体驱动的系统，但频繁访问寄存器可能使 vCPU 退出并等待软件模拟。
2. **半虚拟化设备：**客体预装 virtio 这类标准化虚拟设备的前端驱动，双方不再模仿真实控制器，而是通过共享队列批量提交请求。它减少控制路径的逐次仿真，适合能控制客体镜像的场景。仍要计算通知、拷贝、共享内存和宿主后端的成本。
3. **设备直通：**把物理设备或其可隔离的功能分给客体，客体使用对应物理驱动，减少软件设备模拟。代价是该设备通常不能由两套系统随意同时独占，还需要中断、DMA/IOMMU、复位与故障隔离方案。

这三种方案可以混用。车机可能让 Android 独占显示控制器，让两套系统通过 virtio 或共享内存访问网络，同时直通另一种设备。选型先问客体有哪些驱动、设备由谁拥有、是否要共享，再测吞吐和尾延迟。给 Android 安装 APK 不能补上缺失的内核驱动。

**Q6: [learning] 为什么要有 virtio 标准，前端、后端、队列和传输层怎样形成一个设备？**

如果每种 VMM 都自定义虚拟磁盘和网卡寄存器，客体就要为每个平台维护不同驱动。virtio（Virtual I/O）把**客体可见的设备契约**标准化：同一类前端驱动能与遵循规范的不同后端协作。规范解决互通，不规定后端必须使用哪种宿主文件或保证固定性能。

一个 virtio 设备由四层协作：

1. **设备类型：**virtio-blk 规定块读写、容量与能力。virtio-net 规定网络收发。客体的类型驱动把文件系统或网络栈请求转成这类设备的协议。
2. **公共机制：**设备提供特性位，驱动只接受自己支持的能力。virtqueue 以描述符指向请求缓冲区，传递“可处理”和“已完成”的状态。双方不能假定未协商功能存在。
3. **传输层：**virtio-pci、virtio-mmio 等给出设备发现、配置寄存器、队列地址和通知方式。它解决“接口从哪里进入”，不改变块设备的读写语义。
4. **宿主后端：**QEMU、crosvm 等 VMM 实现设备另一侧，把虚拟块请求接到镜像文件、宿主块设备或其他资源。

启动时也要形成契约：客体发现并复位设备，确认设备类型与状态，读取特性并选择共同支持的子集，设置 virtqueue，最后将设备置为可运行状态。这个顺序解释了为何“VMM 已提供磁盘”仍不足以让客体读盘：传输驱动和 virtio-blk 类型驱动必须存在，特性与队列也必须初始化成功。依据：OASIS《Virtio 1.2》设备初始化与特性协商章节。

**Q7: [learning] 为什么 virtio 设备还要借 PCI 或 MMIO，客体怎样从发现设备走到 /dev/vda？**

virtio 规定设备协议，但客体首先得知道“设备在哪里、如何读配置、怎样通知它”。PCI（Peripheral Component Interconnect）和 MMIO（Memory-Mapped I/O）提供两种不同的**传输入口**。之后还需匹配 virtio-blk 驱动，设备才会进入客体块层。

以 virtio-pci 块设备为例，发现链是：

1. **虚拟总线呈现：**VMM 在客体可见的 PCI 总线上创建设备。现代 virtio PCI 设备使用厂商 ID `0x1AF4`，块设备的现代设备 ID 为 `0x1042`。旧式兼容设备还有不同 ID，不能只按一个数字判断所有版本。
2. **传输驱动接管：**客体 PCI 枚举读取配置空间并找到设备，virtio_pci 根据能力结构定位公共配置、队列通知、中断状态和设备配置区域，然后注册一个 virtio 块类型设备。
3. **类型驱动接管：**virtio_blk 匹配块设备类型，协商特性并建立 virtqueue，再向客体块层注册磁盘。典型 Linux 客体的首块 virtio 磁盘可能出现为 `/dev/vda`，实际名称还取决于枚举顺序与设备节点管理。

virtio-mmio 不依赖虚拟 PCI 总线，适用于不少嵌入式机器模型。但 MMIO 本身没有 PCI 式通用枚举，平台需通过设备树、ACPI 等描述告知客体寄存器位置和中断。virtio_mmio 再完成传输层接管，后续仍由 virtio_blk 处理块协议。排查“镜像已挂给 VMM、客体却没有盘”时，依次核对设备是否呈现、传输驱动是否发现、类型驱动是否匹配、队列是否建立。依据：OASIS《Virtio 1.2》PCI 与 MMIO 传输章节。

**Q8: [learning] 为什么宿主的镜像文件能在客体中变成磁盘，一次块读取怎样映射到宿主存储？**

镜像文件只是宿主保存的数据，客体不能直接打开宿主文件描述符，也不能直接调用宿主 UFS 驱动。virtio-blk 在两侧建立协议映射：客体看到具有容量与扇区地址的块设备，宿主后端把相同扇区请求换算成镜像文件或块设备上的 I/O。选择块设备接口，是为了让客体自己管理分区和文件系统。若只需交换少量文件，可以另选文件共享接口。

以客体读取已挂载文件为例，路径依次是：

1. **准备设备：**VMM 提供盘体，设备配置空间报告容量，单位为 512 字节扇区。客体 virtio_blk 驱动完成发现与初始化，把设备注册到块层。文件系统随后才能挂载其中的分区。
2. **产生请求：**客体应用读文件，客体文件系统把文件偏移换成逻辑块，块层把它交给 virtio_blk。驱动生成读请求，指定 `type = VIRTIO_BLK_T_IN`、起始 `sector` 和接收数据的缓冲区。
3. **执行映射：**宿主后端读取请求，把扇区号按协议换算成字节偏移 `sector × 512`，再通过镜像格式和宿主存储栈找到实际数据。raw 镜像可直接按偏移访问。qcow2 还要经其格式映射。后端把结果写入获准的客体缓冲区。
4. **完成返回：**客体驱动收到完成状态后结束块请求，文件系统再把文件内容交给应用。宿主盘体可换实现，只要设备协议、容量与数据内容契约保持一致，客体基本读盘接口不变。

这解释了“客体必须有驱动”：宿主后端只接受 virtio 块协议，客体文件系统只提出通用块请求，中间的 virtio_blk 前端负责翻译和排队。受保护虚拟机还要求后端仅访问明确共享的请求缓冲区，不意味着宿主能读取全部客体私有内存。Android Microdroid 的系统和 payload 镜像是这一机制的应用实例，具体镜像组合归 Android 专题。

**Q9: [learning] virtqueue 为什么比逐寄存器仿真更合适，一次请求和完成怎样通过队列传递？**

逐次仿真真实设备寄存器，可能每访问一次就需要退出客体并让 VMM 解释语义。单有共享内存也不够，双方还须约定缓冲区地址、长度、读写方向、可用状态和完成状态。virtqueue 把这些约定组织成**可批量提交的请求队列**，通知只负责提醒后端“队列有新工作”。这减少控制路径开销，但仍有内存同步、通知和后端处理成本。

以 virtio-blk 的 split virtqueue 为例：

1. **描述缓冲区：**前端填写描述符链，分别指向读命令头、用于接收数据的缓冲区和状态字节。描述符包含地址、长度、方向及下一项索引。后端据此知道读什么、把结果写到哪里，而不需要模仿某款磁盘控制器的寄存器序列。
2. **发布请求：**前端先保证描述符内容对后端可见，再把链首索引放入 available 环并更新索引。必要的内存屏障防止后端先看到“请求可用”却读到未写好的描述符。若通知未被抑制，再通过传输层提醒后端。
3. **处理与完成：**后端取出请求，在宿主存储上执行 I/O，写入数据和状态，再把完成项发布到 used 环。前端收到通知或轮询到完成后检查状态、回收描述符，并结束上层块请求。通知和中断可被抑制或合并，因此一次 I/O 不必然对应一次 VM exit。
4. **布局版本：**split 将描述符表、available 环和 used 环分开。virtio 1.1 引入 packed，把可用与已用状态放在单个描述符环中。它改变队列布局与状态追踪，不改变 virtio-blk 的读写命令。双方须协商支持后才能启用 packed。

队列中的地址必须按相应虚拟化模型合法映射。普通客体由 VMM/宿主按其内存模型访问。pVM 的后端只能访问被明确共享的缓冲区。依据：OASIS《Virtio 1.2》split/packed virtqueue 与通知章节、Android《AVF architecture》。

**Q10: [learning] 为什么 virtio-blk 写成功仍可能掉电丢数据，FLUSH 怎样建立持久化边界？**

“写请求完成”与“数据已经稳定写入非易失介质”是两个不同承诺。writeback 模式下，后端可先把写入放进易失缓存并应答。掉电或宿主崩溃时缓存可能丢失。需要持久化时，客体必须通过文件系统同步、块层刷新、virtio 刷新和宿主存储栈形成完整链路。

按 OASIS Virtio 1.2 的块设备语义区分：

1. **能力与缓存模式：**设备宣告特性，驱动协商 VIRTIO_BLK_F_FLUSH 才能发送 VIRTIO_BLK_T_FLUSH。VIRTIO_BLK_F_CONFIG_WCE 允许协商后配置写缓存模式。不能从“virtio-blk”四个字推断设备默认使用 writeback 或 writethrough。
2. **写入与刷新：**在 writeback 情况下，已完成的写入可能尚未稳定。客体随后发送 FLUSH，后端必须在报告 FLUSH 完成前，按规范使此前相关写入稳定落到其持久化后端。仅有队列内存屏障或完成通知，不等于刷新宿主缓存。
3. **最终边界：**规范对持久化后端提出保证，但实际可靠性还取决于宿主镜像格式、文件系统、块设备和硬件供电。如果底层谎报刷新成功，virtio 协议本身无法补救。

因此车机的数据库、日志或更新状态出现断电丢失时，要沿“应用同步调用 → 客体文件系统与块层 → virtio 特性和缓存模式 → VMM 后端 → 宿主文件系统与物理存储”逐层查证。写调用返回、请求进入 virtqueue、后端收到数据和 FLUSH 完成都不是同一个时间点。依据：OASIS《Virtio 1.2》块设备缓存与 FLUSH 规则。
