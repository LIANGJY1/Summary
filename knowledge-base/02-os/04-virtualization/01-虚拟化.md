# 虚拟机与虚拟化

> 学习资料。围绕车机 Linux/Android 双系统，按“为什么需要隔离与资源仲裁 → CPU 怎样运行 → 设备怎样呈现 → 一次磁盘 I/O 怎样完成”组织。本文只讲可迁移的虚拟化原理。AVF（Android Virtualization Framework）的 Android 组件与接入见 [Android AVF 专题](../../01-android/09-平台服务/06-AVF虚拟化.md)。依据：QEMU《About QEMU》、Linux《KVM API》、OASIS《Virtio 1.2》、Android《AVF architecture》《Security》。题序即文档结构。

**Q1: [done] 虚拟机和虚拟机监控程序有什么区别，VMM 的两种类型如何划分？**

虚拟机（VM，Virtual Machine）是由虚拟 CPU、内存和设备组成的运行环境，可以运行客体操作系统或其他程序。虚拟机监控程序（VMM，Virtual Machine Monitor）负责创建和管理虚拟机，并协调客体对硬件资源的使用。

按 VMM 与宿主操作系统的部署关系，常分为两类：

1. **第一类**：VMM 在硬件之上承载客体并参与资源管理，例如 VMware ESXi；Xen 通常由特权域提供设备等服务。
2. **第二类**：VMM 运行在宿主操作系统上，借用宿主的设备驱动和资源。例如，在 Windows 上使用 VirtualBox 运行 Ubuntu。

Windows 和 Ubuntu 双系统若通过重启交替启动，不属于虚拟机运行。VMM 类型只描述部署关系，不能单独决定性能或迁移能力。



**Q2: [done] hypervisor 是什么，与 VMM 有什么区别？**

hypervisor 是管理虚拟机运行的虚拟化层，负责协调客体对 CPU、内存和设备的访问。hypervisor 和 VMM（Virtual Machine Monitor）在广义上常作同义词；在具体实现中，也可能分别指承担不同职责的组件。

以 QEMU 和 KVM（Kernel-based Virtual Machine）组合为例：

1. **KVM**：Linux 内核中的虚拟化组件，利用硬件虚拟化运行客体，并参与内存隔离。
2. **QEMU**：用户态虚拟机管理程序，负责配置虚拟机，并提供虚拟设备模型；部分设备访问由它处理。

其他虚拟化系统的职责划分可能不同，不能仅凭名称判断组件边界。



**Q3: [done] 车机为什么会同时运行 Linux 和 Android，怎样判断双系统是否采用虚拟化？**

采用虚拟化的动机通常是让两套需要独立内核的系统复用一套硬件，同时明确分配 CPU、内存和设备。例如产品可以让 Linux 承载一类设备服务、Android 承载交互界面，但具体分工取决于产品。看到两者并存只能说明有两个软件环境，必须再确认它们是否同时运行、是否共用内核与处理器资源，才能判断是否存在虚拟机。

按实际运行边界区分四种方案：

1. **交替启动：**一次只启动一套系统，切换要重启。两套镜像可共用设备，但没有同时运行的两个内核，也就不需要运行时仲裁器。
2. **处理器分区：**两个 SoC（System on a Chip）或固定划分的处理器核心分别运行 Linux、Android，通过网络或共享内存通信。各自控制分配给自己的资源，可以不使用虚拟化。同一颗 SoC 也可能这样部署。
3. **共享内核：**两套用户空间运行在同一内核上，用容器、命名空间等隔离进程和文件系统。它节省第二个内核及虚拟设备的成本，但一方需要不同内核、内核补丁或独立的内核故障边界时不适合。
4. **独立内核共享处理器资源：**Linux 与 Android 各有内核，并共享可调度的 CPU、内存或设备，由 hypervisor（虚拟机资源仲裁层）等组件隔离和仲裁。两者可能是并列客体，也可能一方是宿主、另一方是客体。仅凭“双系统”不能推断拓扑。

车机采用第四种方案时，收益是复用硬件并隔离不同系统的软件故障与权限边界。代价是必须定义显示、音频、存储、网络等设备由谁拥有，跨系统访问走共享、模拟还是直通，并处理调度与 I/O 延迟。排查前应从启动配置、内核/虚拟机日志、虚拟机监控程序和设备树或 PCI 枚举中核实实际拓扑。Android 宿主启动 Microdroid 的 AVF 场景也属于虚拟化，但不代表所有 Linux/Android 双系统车机都使用 AVF。





**Q4: [done] 虚拟化中的 host、guest 与 virtio 前端、后端是什么关系？**

host（宿主侧）是为虚拟机提供资源和设备服务的一侧。guest（客体侧）是运行在虚拟机内的操作系统及应用。对于 virtio 设备，前端通常是 guest 内的设备驱动，后端实现虚拟设备行为，并连接实际资源或其他服务。

以虚拟输入设备为例，事件的传递关系如下：

1. **输入源：**物理触摸设备或其他输入源产生输入数据，具体来源取决于系统。
2. **设备后端：**host 侧组件处理输入，并按 virtio-input 协议向虚拟设备提供事件。后端可以位于虚拟机管理程序、宿主内核或独立进程中。
3. **virtqueue：**前后端通过共享内存中的队列交换缓冲区和完成状态，必要时通过传输层通知对方。
4. **guest 前端：**guest 内的 virtio-input 驱动接收事件并交给输入子系统，再补充接收缓冲区。

host 不一定是普通宿主操作系统，第一类 hypervisor 也可以提供运行环境。前端、后端是相对于接口的角色：在 guest 驱动与 virtio 设备的关系中，驱动是前端。在 vhost-user 控制协议中，QEMU 也可能称为前端，外部设备服务称为后端。依据：QEMU《Writing VirtIO backends for QEMU》《Vhost-user Protocol》。





**Q5: [done] virtio 是什么，它怎样让不同虚拟机实现复用设备驱动？**

virtio（Virtual I/O）是一族标准化的虚拟 I/O 设备接口。它规定 guest 驱动与设备之间的协议，让支持同一设备类型和协商能力的实现互通，而不要求照搬某个物理控制器。

一个设备由以下部分协作：

1. **设备类型：**virtio-blk 定义块设备操作，virtio-net 定义网络收发，virtio-input 定义输入事件。每种类型有自己的配置和队列用途。
2. **公共机制：**设备和驱动协商特性位，按协议初始化 virtqueue，再通过队列传递缓冲区和完成状态。双方只能使用已协商的可选能力。
3. **传输层：**virtio-pci、virtio-mmio 等负责设备发现、配置访问、队列配置与通知。它们不改变设备类型定义的基本操作语义。
4. **设备后端：**虚拟机管理程序、内核或独立服务实现设备侧行为，例如将块请求连接到镜像文件或宿主块设备。

以 guest 读取虚拟磁盘为例，host、guest 与 virtio 按以下步骤协作：

1. **host 提供设备：**设备后端提供 virtio-blk 虚拟磁盘，并将其连接到宿主文件或块设备。
2. **guest 提交请求：**guest 内的 virtio-blk 驱动将读取请求和数据缓冲区放入 virtqueue，必要时通知设备。
3. **host 处理请求：**设备后端按请求从宿主存储读取数据，写入 guest 提供的缓冲区，并发布完成状态。
4. **guest 接收结果：**设备在需要时通知 guest，guest 驱动取回结果并完成上层读取请求。

初始化时，驱动发现并复位设备、确认状态、协商特性、配置队列，最后使设备进入可运行状态。客体缺少传输驱动或对应类型驱动时，即使宿主已配置设备，客体也可能无法使用。virtio 统一的是协议，不保证特定后端性能。依据：OASIS《Virtual I/O Device 1.2》§3。





**Q6: [done] 为什么使用虚拟机运行操作系统或程序？**

虚拟机提供一套虚拟 CPU、内存和设备，让软件在一个独立的机器环境中运行。使用虚拟机是为了获得独立系统环境、隔离测试环境或兼容特定系统，不是运行程序的必要条件。

例如，在一台 Linux 电脑上测试 Windows 程序：

1. 创建虚拟机，为它配置虚拟 CPU、内存和磁盘。
2. 在虚拟机里启动 Windows。Windows 内核管理虚拟机中的程序和虚拟设备。
3. 在 Windows 中运行测试程序。测试环境可以独立启动、重启或删除；实际隔离效果仍取决于虚拟化实现和共享配置。

虚拟机也可以运行 Linux、Android 或裸机程序。启动 Android、Linux 等完整操作系统时，客体会运行自己的内核；直接运行裸机程序时，可以没有独立操作系统内核。虚拟机需要占用物理内存和处理器时间，也有设备虚拟化开销。



**Q7: [done] host 内核与 guest 内核怎样协作运行虚拟机？**

以 Linux 宿主使用 QEMU 和 KVM（Kernel-based Virtual Machine）运行 Linux 虚拟机为例，**guest 内核管理虚拟机内的程序和虚拟设备；host 内核管理宿主资源，并通过 KVM 和硬件虚拟化机制支持 guest 运行**。两者是独立运行的内核实例。

以 guest 应用读取虚拟磁盘中的文件为例：

1. **guest 内部：**应用发起文件读取，guest 内核的文件系统和虚拟磁盘驱动把它转换为设备请求。
2. **设备后端：**虚拟设备后端接收请求。例如，QEMU 可以将请求转换为对宿主磁盘镜像文件的读取；后端也可能由其他组件承担。
3. **host 内部：**宿主操作系统处理后端对宿主文件或设备的访问，再将数据返回给后端。
4. **返回 guest：**后端按虚拟设备协议提供结果，必要时通知 guest；guest 驱动完成请求，guest 内核再把文件内容交给应用。

同时，host 调度承载虚拟 CPU 的线程，硬件地址转换限制 guest 可访问的内存。guest 应用的系统调用通常先由 guest 内核处理，并非每次都交给 QEMU 或 host 内核。上述设备路径是 QEMU/KVM 的一种示例，不代表所有虚拟设备都经过同一个后端。



**Q8: [done] 操作系统容器是什么，它与虚拟机的内核有什么区别？**

普通 Linux 容器是运行在同一个 Linux 内核上的一组隔离进程。虚拟机则提供虚拟机器；如果其中运行 Linux、Android 等完整操作系统，该系统会启动自己的内核实例。

例如，一台 Linux 电脑上运行两个服务，可以有两种组织方式：

1. **使用两个容器：**服务 A 和 B 仍是这台 Linux 系统中的进程，共用同一个 Linux 内核。容器各自的文件、进程或网络视图可通过 namespace 隔离，CPU 和内存等资源可通过 cgroup 管理。
2. **使用两个虚拟机：**为每个虚拟机启动一套客体操作系统。两个系统各自有内核实例，再通过虚拟化层使用物理资源。

容器镜像通常提供程序及其依赖，不包含运行时独立启动的内核。容器如果运行在 Linux 虚拟机内，共享的是该虚拟机的 guest 内核。虚拟机也可以直接运行裸机程序，不一定启动完整操作系统。容器与虚拟机的具体隔离效果均取决于实现和配置。

**Q9: [learning] 两个独立内核共享硬件时，虚拟化怎样隔离并仲裁资源？**

两个独立内核都可能尝试管理 CPU、内存和设备。如果缺少仲裁，就可能修改对方内存或重复配置同一设备。虚拟化管理层通过处理器执行控制、地址转换和设备访问机制建立边界。

资源管理按以下顺序理解：

1. **配置：**管理层为每个客体配置虚拟 CPU、内存范围和设备。客体页表转换进程虚拟地址，第二阶段地址转换再将客体物理地址映射到允许访问的物理页。
2. **执行：**处理器在受控环境运行客体。需要管理层处理的访问可触发 VM exit，由 hypervisor、宿主内核或用户态设备后端处理，再恢复客体。并非所有客体系统调用或中断都会退出到用户态。
3. **调度与设备：**调度器决定虚拟 CPU 何时运行。设备可通过模拟、半虚拟化或直通提供。虚拟设备后端可使用队列交换数据，并在需要时通知客体。
4. **边界：**设备 DMA（Direct Memory Access，直接内存访问）也必须受约束。只限制 CPU 页表不足以隔离设备访问。实际隔离和调度能力取决于硬件及虚拟化实现。





**Q10: [learning] QEMU 的系统模拟与用户态模拟分别提供什么环境？**

QEMU（Quick Emulator）是机器模拟和虚拟化工具。系统模拟提供包含 CPU、内存和设备的虚拟机器，可启动完整客体操作系统。用户态模拟运行面向另一架构编译的程序，不提供客体内核。

两种模式的执行环境不同：

1. **系统模拟：**使用 `qemu-system-<架构>` 提供机器模型，客体内核和应用在该模型内运行。客体架构可以与宿主不同。
2. **用户态模拟：**使用 `qemu-<架构>` 运行单个客体程序，翻译其指令并适配系统调用，由宿主内核提供系统服务。例如可在支持的平台上运行 AArch64 编译的 Linux 程序。
3. **选择：**需要启动完整客体操作系统时使用系统模拟。只需运行一个兼容的跨架构程序时，可评估用户态模拟。用户态模拟不启动客体内核。

依据：QEMU《About QEMU》《Emulation》。





**Q11: [learning] QEMU、KVM 和 TCG 分别负责什么，客体指令怎样执行？**

QEMU 提供虚拟机器和设备模型，KVM（Kernel-based Virtual Machine）提供 Linux 内核中的硬件虚拟化接口，TCG（Tiny Code Generator）负责动态翻译客体指令。系统模拟可按支持情况选择 TCG 或 KVM 执行客体 CPU。

1. **TCG 路径：**QEMU 将客体指令动态翻译为宿主指令，适合跨指令集或没有硬件虚拟化扩展的环境。指令翻译有开销。
2. **KVM 路径：**QEMU 创建虚拟机和虚拟 CPU，通过 KVM 进入客体。多数普通客体指令由处理器直接执行。部分需用户态处理的设备访问导致退出，QEMU 处理后再恢复客体。
3. **设备边界：**使用 KVM 不会使 QEMU 的机器模型消失。设备可由 QEMU、内核或独立后端协作实现。客体系统调用通常由客体内核处理，不等于一次宿主系统调用。
4. **选择条件：**KVM 依赖宿主内核、处理器和客体架构的支持。跨指令集系统模拟通常使用 TCG。性能应按实际设备和负载测量。

依据：QEMU《System Emulation》、Linux《KVM API》。





**Q12: [learning] pKVM 与普通 KVM 的信任边界和使用成本有什么不同？**

普通 KVM 主要隔离客体之间及客体对宿主的访问，宿主内核通常仍能管理和访问客体内存。pKVM（protected KVM）为受保护虚拟机增加隔离目标：宿主内核不应读取或修改未共享的客体私有页。

该保护依赖页面所有权和平台配置：

1. **私有内存：**hypervisor 管理受保护客体的第二阶段地址映射，宿主不能仅靠修改自己的页表访问客体私有页。
2. **共享和 DMA：**虚拟设备后端需要访问的数据须按协议共享。还须使用适当的 DMA 隔离限制设备访问，单独限制 CPU 地址转换不够。
3. **可用性和持久数据：**宿主仍可影响调度与设备供给，因此能拒绝服务。持久化内容的完整性和真实性需要其他相应保护机制。
4. **代价：**宿主不能随意检查、回收私有页，调试和部分内存管理更复杂。适合需要保护客体内容免受宿主读取的负载，不能仅凭 pKVM 名称推断性能更高。

Android 虚拟化框架（AVF，Android Virtualization Framework）可使用 pKVM 运行受保护虚拟机。实际保证仍依赖硬件、固件和设备隔离。依据：Android《AVF architecture》《Security》。





**Q13: [learning] 虚拟机的模拟设备、半虚拟化设备和设备直通如何选择？**

三种方式的区别是客体使用什么设备接口，以及谁拥有实际硬件。选择时先确认 guest 驱动和设备共享需求，再评估隔离、性能与运维成本。

1. **模拟真实设备：**设备模型模拟真实控制器的寄存器与中断，guest 可使用兼容的现成驱动，例如模拟 e1000 网卡。兼容性较好，但受控寄存器访问可能带来退出和软件模拟开销。
2. **半虚拟化设备：**guest 使用 virtio 等专用驱动，双方按约定通过队列协作，不必逐次模拟某款真实控制器。它需要对应驱动，实际成本仍包含通知、内存同步和后端处理。
3. **设备直通：**将可隔离的物理设备或功能分配给 guest，由其使用相应物理驱动。通常需要考虑 DMA、IOMMU、中断、设备复位和故障隔离，也不能假设设备可同时由多个系统独占。

广义全虚拟化强调客体可不修改运行，半虚拟化要求客体配合专用接口。CPU 可用硬件辅助虚拟化，同时 I/O 使用 virtio。一次通知也可能处理多个请求，但批量大小、VM exit 次数和性能收益都取决于实现与负载。





**Q14: [learning] virtio-pci 与 virtio-mmio 怎样让 Linux 客体发现 virtio 块设备？**

virtio-pci 和 virtio-mmio 是 virtio 的两种传输方式：前者使用 PCI（Peripheral Component Interconnect）设备发现与配置机制，后者使用平台描述的 MMIO（Memory-Mapped I/O）寄存器。两者之后都需要 virtio-blk 类型驱动。

以 virtio-pci 块设备为例，发现与注册过程如下：

1. **呈现设备：**虚拟机管理程序在客体可见的 PCI 总线上创建设备。现代 virtio PCI 块设备的厂商 ID 为 `0x1AF4`、设备 ID 为 `0x1042`。旧式兼容设备可能使用不同 ID。
2. **传输层接管：**Linux PCI 枚举设备，virtio_pci 驱动根据 PCI 能力结构定位公共配置、队列通知、中断状态和设备配置区域，再注册 virtio 设备。
3. **类型驱动接管：**virtio_blk 匹配块设备类型，协商特性并设置 virtqueue，向块层注册磁盘。首块设备常见名称为 `/dev/vda`，实际节点取决于枚举顺序和设备管理。
4. **无 PCI 时：**virtio-mmio 的寄存器和中断通常由设备树或 ACPI 描述。virtio_mmio 完成传输层接管后，仍由 virtio_blk 处理块协议。

排查客体看不到磁盘时，依次检查设备是否呈现、传输驱动是否接管、类型驱动是否匹配以及队列是否初始化。依据：OASIS《Virtual I/O Device 1.2》§4.1、§4.2。





**Q15: [learning] split virtqueue 怎样传递 virtio-blk 请求和完成状态？**

virtqueue 是驱动与设备约定的缓冲区和完成状态队列。split virtqueue 将描述符表、available 环和 used 环分开。它支持批量发布请求，通知可按协议抑制或合并。

一次块读取按以下步骤流转：

1. **准备缓冲：**guest 驱动填写描述符链，指向命令头、接收数据的缓冲区和状态字节。命令头的 type 标识读取，sector 指定以 512 字节为单位的起始位置。描述符标明地址、长度、方向及后续关系。
2. **发布：**驱动先使描述符内容可见，再把链首索引发布到 available 环。通知未被抑制时，通过传输层提醒设备。
3. **处理：**设备后端读取请求，对镜像文件、块设备或其他存储后端发起 I/O，并把结果写入获准访问的客体缓冲区。
4. **完成：**设备写入状态并把完成项发布到 used 环，必要时通知驱动。驱动取回结果、回收描述符并完成上层请求。

双方必须遵守内存可见性和顺序要求，避免一方看到可用状态却读到尚未准备好的内容。队列减少逐次寄存器仿真的需求，但通知、内存同步、I/O 和调度仍有成本。一次请求不必然对应一次通知或 VM exit。受保护客体还须确保后端只能访问明确共享的缓冲区。依据：OASIS《Virtual I/O Device 1.2》§2.6、§5.2。





**Q16: [learning] split virtqueue 和 packed virtqueue 的布局有什么区别？**

split 和 packed 是 virtqueue 的两种布局，不是两种不同的 virtio-blk 读写协议。split 分开保存描述符表、available 环和 used 环。packed 将描述符与可用、已用状态放在同一描述符环中，并保留事件抑制区域。

1. **split：**驱动和设备通过各自的环发布索引，间接引用描述符。
2. **packed：**使用同一描述符环追踪可用与完成状态，处理方式与 split 不同。它在 virtio 1.1 引入。
3. **选择：**双方需要协商支持才能使用 packed。缓存访问和实际性能取决于实现与负载，不能只凭布局断言更快。

依据：OASIS《Virtual I/O Device 1.2》§2.6、§2.7。





**Q17: [learning] 宿主镜像文件怎样成为客体中的 virtio-blk 磁盘？**

virtio-blk 是标准化的虚拟块设备：客体驱动向块层提供设备接口，设备后端把块请求映射到宿主文件、块设备或其他存储。客体看到的是容量和扇区地址，不直接打开宿主的文件描述符。

1. **宿主侧：**虚拟机管理程序配置设备后端，例如 raw 或 qcow2 镜像。镜像文件是存储介质，格式及实际存储路径由后端处理。
2. **设备配置：**设备报告容量，单位为 512 字节扇区。缓存模式、flush 和 discard 等可选能力由设备特性和协商结果决定。
3. **客体侧：**virtio_blk 注册块设备后，客体可识别分区并挂载文件系统。应用读取文件时，客体文件系统将文件偏移转换成块请求，再由驱动提交。
4. **偏移映射：**后端将请求起始 sector 换算成 `sector × 512` 字节偏移。raw 可以按相应偏移访问。qcow2 还需经过镜像格式的映射。

换用另一种后端时，只有容量、数据内容和对客体承诺的协议行为保持一致，客体才可继续按原块设备接口访问。性能和可靠性仍取决于新的存储路径。依据：OASIS《Virtual I/O Device 1.2》§5.2。





**Q18: [learning] virtio-blk 的写入完成与 FLUSH 完成有什么区别？**

写入完成不一定代表数据已进入非易失存储。若设备使用 writeback 缓存，已完成的写入可能仍在易失缓存中。guest 需要持久化时，应经文件系统和块层发起相应刷新。

1. **能力协商：**设备是否支持 flush、缓存模式是否可配置，由相应特性和协商结果决定。不能仅凭 virtio-blk 推断默认缓存模式。
2. **写入完成：**设备按当前缓存语义返回写入状态。writeback 情况下，宿主崩溃可能使已应答但未稳定的数据丢失。
3. **FLUSH 完成：**在协商支持后，guest 可发送 VIRTIO_BLK_T_FLUSH。设备必须按规范使先前相关写入稳定到持久化后端后才报告完成。
4. **实际边界：**可靠性还依赖宿主镜像格式、文件系统、块设备和硬件正确执行刷新。共享队列中的内存屏障或完成通知不能代替持久化操作。

排查断电丢数据时，应沿应用同步调用 → guest 文件系统和块层 → virtio 缓存与刷新 → 宿主存储逐层核对。依据：OASIS《Virtual I/O Device 1.2》§5.2。





**Q19: [learning] virtio-input 事件包含什么，怎样从虚拟设备到达客体输入系统？**

virtio-input 是 virtio 输入设备，事件是设备与驱动间传递的一条输入记录。按 Virtio 1.2，记录包含 type（类型）、code（该类型下的代码）和 value（值），以小端格式传输。记录本身没有时间戳字段。

假设设备支持多点触摸，且已选中处于接触状态的槽位，下面是一组示意更新：

1. `EV_ABS / ABS_MT_POSITION_X / 500`：报告 X 坐标为 500。
2. `EV_ABS / ABS_MT_POSITION_Y / 300`：报告 Y 坐标为 300。
3. `EV_SYN / SYN_REPORT / 0`：结束这一组状态更新。

事件的传递步骤如下：

1. **接收缓冲区：**guest 驱动向 eventq 提供设备可写的缓冲区。设备将输入记录写入缓冲区并发布完成状态。
2. **客体处理：**驱动取回记录并重新提供缓冲区。Linux virtio_input 驱动将 type、code、value 交给 input core，evdev 再向用户态提供输入事件。
3. **Android 分发：**EventHub 和 InputReader 读取并处理输入，后续分发阶段才将对应事件交给应用。一个输入更新通常包含多条记录，不能将单条记录、一次队列通知与一个 MotionEvent 等同。
4. **反向状态和丢失：**statusq 可用于从驱动向设备反馈键盘指示灯等状态。若 eventq 缺少可用缓冲区，规范允许设备丢弃输入。是否发生丢失需结合实现和观测数据判断。

不能仅凭该记录得到 host 产生输入的时间。Linux 具体输入路径可在后续环节提供或换算时间戳，取时位置与时钟须按对应内核实现核实。依据：OASIS《Virtual I/O Device 1.2》§5.8、Linux virtio_input 驱动。
