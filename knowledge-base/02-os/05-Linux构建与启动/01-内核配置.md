# 内核配置选项

> Linux 内核配置规则、配置文件与早期启动所需选项。

**Q1: [learning] .config、Kconfig 和 defconfig 在内核构建中分别做什么？**

Kconfig 定义配置规则，defconfig 提供配置起点，`.config` 保存当前构建的配置结果。配置工具根据当前源码的规则解析并更新配置，构建系统再据此生成所需产物。

1. **Kconfig：**定义配置项的类型、依赖、提示和默认值。类型除 bool、tristate 外，还包括字符串、整数和十六进制数。
2. **defconfig：**为某架构或产品提供一组起始配置。未列出的符号由当前 Kconfig 规则决定，不能一概视为关闭。
3. **.config：**记录配置结果。就地构建时通常位于源码树根目录，使用独立输出目录时位于对应构建输出目录。它不只包含 y、m 和关闭状态，还可能包含字符串或数值。
4. **更新配置：**更换内核版本或手工修改后，配置工具可按当前规则重新计算结果。原有值能否保留取决于选项是否存在、类型和依赖是否满足。
5. **构建使用：**Kbuild 根据配置生成供构建系统和源码使用的配置文件，再参与条件编译。修改配置后仍需重新构建相关产物。

依据：Linux 内核文档 Kconfig Language、Kbuild。

**Q2: [learning] make olddefconfig 拿 Kconfig 逐项核对 .config，具体怎么比较？用最小实例走完全流程？**

核对不是两份文件的逐行文本比对：olddefconfig 背后的 conf 程序先读入全部 Kconfig 建立符号表——每个选项的类型、依赖、默认值和 select 关系——再把 .config 读作这些符号的“用户答案”，逐符号按规则算出最终值，最后写回规范化 .config。比较的单位是选项，不是行；真实内核符号表有数千选项，几行手改输入经同一套核对就会展开成数千行完整清单。

最小 Kconfig，五个选项覆盖全部规则形态（真实内核条目同构，只是字段更多，如 drivers/base/Kconfig 的 DEVTMPFS 为 bool 加提示词加帮助文本）：

```text
config SYS
	bool "system core"
	default y

config DEV
	bool "device support"
	depends on SYS

config NET
	bool "network"
	select LOG

config LOG
	bool "logging"

config EXTRA
	bool "extra"
	default y
```

手写 .config 四行作为用户答案：

```text
CONFIG_TYPO_OPTION=y
# CONFIG_SYS is not set
CONFIG_DEV=y
CONFIG_NET=y
```

olddefconfig 实测输出（规范化文件自带的头部注释行省略）：

```text
# CONFIG_SYS is not set
CONFIG_NET=y
CONFIG_LOG=y
CONFIG_EXTRA=y
```

四种分支逐一对照：

1. **Kconfig 有、.config 没有，按规则补：**EXTRA 输入无行，按默认值补 y。LOG 同样无行，却不是补默认值——它被 NET 的 select 强制拉成 y，说明“缺项”不一定落默认值，select 与依赖先参与计算。
2. **.config 有、Kconfig 没有，丢行：**CONFIG_TYPO_OPTION 在符号表里没有对应符号，整行被丢弃，这就是拼错选项名的兜底。
3. **两边都有且规则允许，保留用户值：**SYS 的用户值 n 压过它的默认 y（已填项一律保留，n 也不例外）；NET=y 同样保留。
4. **两边都有但规则否决，重算：**DEV 被用户写成 =y，但它 depends on SYS 而 SYS 为 n，依赖不满足：值被强制为 n，且该选项本轮不可见，连 not set 注释行都不写，整行从 .config 消失。“明明写了、跑完却找不到”就是这个原因。

写回之后是消费：再跑 syncconfig（make 构建时自动触发）把 .config 转成 include/generated/autoconf.h，实测只有开启项变成宏——`#define CONFIG_NET 1`、`#define CONFIG_EXTRA 1`、`#define CONFIG_LOG 1`；SYS 与 DEV 关闭，不产生任何宏，C 源码用 ifdef 做条件编译。至此 Kconfig 退场，构建只消费生成物。

相近命令的区别：

1. **oldconfig：**同一套核对，对缺项和新项逐个提问用户。
2. **olddefconfig：**同一套核对但不提问，缺项直接按默认值补，适合脚本与 CI。
3. **defconfig：**扔掉旧答案，从 defconfig 起点加默认值重新展开。
4. **都不跑：**make 构建时自动触发 syncconfig 做同样规范化，未规范的 .config 不会漏进构建；但手工跑 olddefconfig 能提前看到哪些行被改写，是改配置的验收动作。

依据：内核 5.15 scripts/kconfig 同源编译的 conf 对最小 Kconfig 的 olddefconfig 与 syncconfig 实测输出。

**Q3: [learning] 内核配置项的 y、m 和关闭分别表示什么？**

对于可表示功能开关的 Kconfig 项，y 通常表示内建，m 表示构建为可加载模块，n 表示关闭。并非所有选项都有三种状态，也不是所有配置项都是功能开关。

1. **bool：**只有开启或关闭，不能选模块。例如 Linux 5.15 中的 CONFIG_DEVTMPFS 是 bool。
2. **tristate：**在模块功能及依赖条件允许时，可选择内建或模块。关闭的 bool 和 tristate 项通常在 `.config` 中以 not set 注释表示。
3. **Kbuild 目标：**Makefile 中的 `obj-$(CONFIG_FOO) += foo.o` 按最终配置选择目标。值为 y 时展开成 obj-y，纳入内建目标，值为 m 时展开成 obj-m，生成可加载模块，关闭时不生成该目标。新增驱动需要把子目录 Kconfig 和 Makefile 接入上级树，再用配置选择目标。
4. **其他类型：**字符串、整数和十六进制项记录相应值，不能按 y/m/n 判断。
5. **依赖与默认值：**Kconfig 约束可选范围。删除一行不等于显式关闭，重新生成配置时可能采用默认值。手工修改后应按当前内核规则核对最终结果。
6. **启动时序：**早期必需功能可以内建。若做成模块，则模块文件及加载所需条件必须在使用前可用，例如放进 initramfs。只看配置为 m 不足以判断它是否能及时加载。

依据：Linux 内核文档 Kconfig Language、Linux Kernel Makefiles 及 Linux 5.15 的 `drivers/base/Kconfig`。

**Q4: [learning] 让自编内核在 QEMU 里用 virtio 虚拟磁盘启动，CONFIG_VIRTIO_PCI、CONFIG_VIRTIO_BLK、CONFIG_DEVTMPFS 各承担什么？缺一个会怎样？**

三个选项各守“发现设备 → 变成块盘 → 自动出节点”这条链路的一段。QEMU 用 -drive file=rootfs.ext4,if=virtio 挂盘（file 指定镜像，if=virtio 表示以 virtio-blk 设备接入）时，guest 内核至少前两项要 =y：PCI 驱动 select 带上 VIRTIO 总线核心，块驱动依赖这个核心才能编译。三个选项的分工：

1. **CONFIG_VIRTIO_PCI——发现与认领：**virtio 设备的 PCI 传输层驱动，guest 靠它从 PCI 总线上认领 QEMU 挂出的 virtio 设备。
2. **CONFIG_VIRTIO_BLK——变成块盘：**virtio-blk 块设备驱动，把认领到的设备变成块设备盘，Linux 命名 /dev/vda。
3. **CONFIG_DEVTMPFS——自动出节点：**让内核驱动核心自动维护 /dev 下的设备节点，盘注册后节点自动出现。

落到排障与配置，有四个要点：

1. **缺一个的现象：**

    1. 缺 CONFIG_VIRTIO_PCI：lspci 仍能看到 QEMU 挂的 virtio 设备，但没有任何驱动认领它，块盘不会出现。
    2. 缺 CONFIG_VIRTIO_BLK：传输层把设备接上 virtio 总线，但没有块驱动消费它，同样没有 /dev/vda，dmesg 里没有 virtio_blk 注册日志。
    3. 缺 CONFIG_DEVTMPFS：盘其实已经注册，但 /dev 下没有自动生成的节点，要手工 mknod 或靠用户态守护进程建节点。没有 devtmpfs 的内核上，所有设备节点（包括 /dev/console）都得在 initramfs 里预置。本实验内核虽编译了 devtmpfs，但挂载发生在 /init 运行后，而内核启动 /init 前就要打开 /dev/console，所以同样要预置。

2. **配置顺序的坑：**CONFIG_VIRTIO_BLK 的菜单项在 Device Drivers → Block devices 下，但一开始找不到它——它依赖 VIRTIO 总线核心，而这个核心没有提示文本，只有先到 Device Drivers → Virtio drivers 下把 CONFIG_VIRTIO_PCI 设为 =y（select 自动带上核心），块驱动选项才出现。
3. **devtmpfs 的两半：**CONFIG_DEVTMPFS 只是让内核“维护”节点数据。CONFIG_DEVTMPFS_MOUNT 才让内核在挂载根文件系统之后自动把 devtmpfs 挂到 /dev（行为可用内核参数 devtmpfs.mount=0|1 覆盖）。但它的 Kconfig 帮助文本明确写了不作用于 initramfs 启动——initramfs 场景必须由 /init 自己执行 mount -t devtmpfs devtmpfs /dev（-t 选择文件系统类型 devtmpfs，第一个 devtmpfs 是来源标识——这类伪文件系统没有磁盘设备，/dev 是挂载点）。CONFIG_DEVTMPFS 在 Device Drivers → Generic Driver Options 菜单下。
4. **=y 还是 =m：**自编最小内核建议三项全 =y，省去往 initramfs 放模块文件再加载的步骤。发行版内核把 virtio_blk 编成 =m 随 initramfs 携带，所以桌面系统也能直启云镜像。Android 的 Microdroid 同样把 virtio 驱动做成内核模块放在 vendor_boot 里随虚拟机携带。

“虚拟机里用虚拟盘”的配方是通用的：QEMU/KVM、Crosvm（Android 模拟器与 AVF 的 VMM）默认提供 virtio 设备，guest 内核按上面三项配好，宿主侧的一个镜像文件就成了 guest 里的启动盘或数据盘。

**Q5: [learning] 检查完内核配置后怎样启动编译，并定位缺失的主机工具？**

配置由 Kconfig 规范化，内核和模块由 Kbuild 生成。设置目标架构和工具链后，先确认 `.config`，再按主机资源选择并行度。构建失败时，先判断报错出自主机工具还是目标代码。

1. **配置与编译：**用 Q2 的方法检查配置。随后运行 `make -jN` 或目标构建入口。N 增大时会有更多并行作业，需要相应的内存和 CPU。过高可能导致进程被 OOM 杀死。
2. **主机工具：**flex、bison 用于构建配置解析工具。使用 menuconfig 时需要 ncurses 开发库。Ubuntu 的安装包可能叫 libncurses-dev，具体名称按发行版调整。
3. **对象与调试信息：**缺少 gelf.h 时检查 libelf 开发库。启用 BTF 时核对 pahole 与 DWARF/BTF 所需工具的版本。OpenSSL 等依赖也按分支和配置的实际需求安装。
4. **输出检查：**产物位置取决于目标架构和输出目录。x86 压缩内核通常是 `arch/x86/boot/bzImage`。检查本次输出目录和时间，避免误用上次构建的文件。

依据：Linux 内核文档 Minimal requirements to compile the Kernel、Kbuild 及 AAOS 13 x86_64 构建案例。

**Q6: [learning] 外部模块怎样使用目标内核的 Kbuild 编译？**

用目标内核已配置的构建树和工具链编译外部模块。模块源码目录包含 Kbuild 或 Makefile（例如 `obj-m += foo.o`），构建时交给内核自己的规则处理。

1. **入口：**`make -C <kernel-build-tree> M=<module-source-dir> modules`。-C 进入内核构建树，M 指向外部模块源码目录，modules 构建 .ko。
2. **生成物：**构建树应启用模块支持，并提供目标内核的配置和生成头文件。modules_prepare 可准备构建环境，但不会生成 Module.symvers。启用 CONFIG_MODVERSIONS 时，需要使用完整内核构建生成的符号版本数据。
3. **目标架构：**沿用目标构建的 ARCH 和工具链。用 GNU 交叉工具时，CROSS_COMPILE 给出工具前缀。用 LLVM=1 时，纯 LLVM 构建通常可省去该前缀，混用 GNU 工具时按目标构建规则设定。
4. **验证：**主机默认编译器可能生成错误架构的模块。目标架构、vermagic 和符号版本一致后，仍需在实际内核上验证加载与依赖。

依据：Linux 内核文档 Building External Modules 与 Building Linux with Clang/LLVM。
