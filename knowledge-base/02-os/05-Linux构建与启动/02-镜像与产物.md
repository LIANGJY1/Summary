# 镜像与内核镜像

> 镜像格式、文件系统镜像及内核构建产物。

## 第一章 镜像与归档

**Q1: [done] 镜像是什么？**

镜像是按特定格式保存某个系统、存储对象或运行状态的表示，供加载、恢复或分析。它可以由已有对象复制，也可以从文件和配置直接生成，不一定包含原对象的每个字节。

1. **磁盘或分区镜像：**表示可供块设备读取的内容。raw 可按块存放数据，qcow2 等格式还包含映射或快照元数据。
2. **系统或固件镜像：**按目标平台需要组织程序与数据，例如构建出的系统分区镜像或固件更新文件。
3. **内存转储：**记录进程或系统的部分运行状态，供故障分析，不保证包含所有内存。

能否直接使用取决于格式、目标和加载工具。镜像可以稀疏、压缩或只保存必要内容，不能仅凭名称推断是逐字节副本。

依据：QEMU《Disk Images》、Linux 内核《The /proc Filesystem》。

**Q2: [done] 归档是什么，与 tar、zip、gzip、cpio 有什么关系？**

归档把一个或多个文件及相关路径、元数据组织成可保存或传输的数据。压缩则减少数据体积，两者可以配合，也可以分别使用。

1. **tar 和 cpio：**归档格式及相应工具，用来组织文件条目。它们生成的归档可再用压缩工具压缩。
2. **zip：**同时提供文件归档和压缩能力，也可按格式支持的方式保存未压缩条目。
3. **gzip：**压缩数据流，不负责把目录中的多个文件组织成一个文件集合。常见的 `.tar.gz` 是先归档再压缩。

例如 Linux 的 initramfs 可使用内核支持的 cpio 归档，并按需压缩。内核将归档解包到初始 rootfs，不把归档本身作为文件系统挂载。

依据：Linux 内核《initramfs buffer format》。

**Q3: [learning] 镜像和归档有什么区别？**

镜像侧重按目标格式表示一个存储对象或系统，归档侧重组织文件条目及其元数据。两者都可以保存为文件，也都可能使用压缩或其他封装。

1. **访问方式：**文件系统镜像通常通过相应驱动和块设备接口挂载。tar、cpio 等归档通常由归档工具读取或解包。
2. **使用边界：**不是所有镜像都可直接挂载或写入，例如压缩、稀疏或只读镜像可能需要专用工具或转换。归档也不一定必须完整解包才能查看或提取条目。
3. **选择：**需要给虚拟机提供磁盘或生成系统分区时，按目标要求准备镜像。需要按文件打包和分发时，按文件及元数据需求选择归档。

**Q4: [learning] 磁盘镜像和分区镜像有什么区别？**

磁盘镜像表示整个磁盘的逻辑内容，分区镜像只表示某个分区或其文件系统的内容。两者的读取起点和恢复目标不同。

1. **磁盘镜像：**可包含分区表和多个分区，适合恢复整个磁盘布局。具体是否包含所有扇区取决于制作方法与镜像格式。
2. **分区镜像：**只覆盖一个分区的内容，通常不包含整个磁盘的分区表。目标分区需要适合该镜像的大小和格式。
3. **判断方式：**检查镜像内部布局和目标系统的加载要求，不能只凭 `.img` 扩展名判断是整盘还是单个分区。

**Q5: [learning] 磁盘镜像有哪些常见存储格式？**

磁盘镜像可保存为普通文件，也可由存储后端提供。格式决定虚拟磁盘如何映射到实际存储，不能只按扩展名判断。

1. **raw：**文件偏移直接对应虚拟磁盘偏移。宿主文件系统若支持稀疏文件，逻辑大小可以大于实际占用空间。
2. **qcow2：**用元数据组织虚拟磁盘数据，可支持按需分配和快照等特性，需要识别该格式的工具读取。
3. **Android sparse：**是 Android 使用的镜像表示格式，与宿主文件系统的稀疏文件不是同一概念。目标工具不支持该格式时需先转换。

镜像还可以被压缩或打包以便传输。使用前应确认格式、后端和目标工具是否匹配。

依据：QEMU《Disk Images》。

## 第二章 光盘、文件系统及其他镜像

**Q6: [done] ISO 镜像是什么，为什么有些可以启动安装程序？**

ISO 镜像通常是包含光盘文件系统内容的镜像文件，可以从已有光盘复制，也可以由文件树和构建工具生成。`.iso` 常用于分发系统安装介质，但扩展名本身不保证镜像可启动。

1. **内容组织：**镜像通常包含 ISO 9660 文件系统，某些镜像还包含其他文件系统或扩展。操作系统可在支持相应格式时挂载并读取文件。
2. **启动条件：**可启动镜像还需包含与目标固件和启动方式匹配的引导信息及程序。
3. **介质边界：**能从光盘启动不自动代表能直接写入 U 盘启动。是否支持 USB 启动取决于镜像布局和写入方式。

**Q7: [done] Ubuntu 安装镜像如何启动并安装系统？**

安装镜像先让设备启动安装环境，安装器再把系统部署到用户选择的目标磁盘。具体界面、文件系统和引导程序取决于发行版、版本与安装选项。

1. **制作启动介质：**使用支持该镜像的工具写入 U 盘。单纯把镜像文件复制到普通目录通常不足以建立启动介质。
2. **启动安装环境：**固件从所选介质加载兼容的引导程序，再加载内核和早期用户态环境。
3. **安装系统：**安装器按用户选择配置目标磁盘、部署系统文件并设置引导。完成后从目标磁盘重新启动。

**Q8: [done] ext4 system 镜像是什么，如何使用？**

ext4 system 镜像是包含 ext4 文件系统内容的镜像文件，可由构建工具直接生成，不要求先复制一块已有分区。能否直接挂载取决于镜像是否为内核可识别的原始文件系统格式。

1. **查看或挂载：**原始 ext4 镜像可交给支持 ext4 的工具读取，也可通过 loop 设备挂载。Android sparse 等封装格式需先使用相应工具处理。
2. **作为虚拟磁盘：**虚拟机可将镜像交给虚拟块设备，由客体内核识别并挂载其中的文件系统。
3. **Android 边界：**system 分区不一定使用 ext4，也可能使用 EROFS 等格式。应以设备构建配置和实际镜像为准。

依据：Android Open Source Project《EROFS》、QEMU《Disk Images》。

**Q9: [done] mkfs.ext4 全解析**

`mkfs.ext4` 在块设备或镜像文件上创建 ext4 文件系统，调用形式为 `mkfs.ext4 [选项] 设备 [块数]`。设备必须是已存在的分区、loop 设备或普通镜像文件。省略块数时文件系统使用整个设备。它是 e2fsprogs 里 mke2fs 的别名，`mke2fs -t ext4 设备` 与 `mkfs.ext4 设备` 等价，调用名只决定默认文件系统类型。

以 `mkfs.ext4 -d system_root -L system build/system.img 64M` 为例，命令行分四段：`-d system_root` 指定从哪个目录灌内容，`-L system` 写卷标，`build/system.img` 是输出文件，`64M` 是文件系统总容量。

1. **前置条件：**镜像文件要先建好再格式化，例如 `truncate -s 64M build/system.img` 生成空文件。目标不能处于已挂载状态。对真实分区执行会销毁原有数据，不可恢复。
2. **常用选项：**选项按职责分四类。

    1. `-d 目录`：把目录树连同文件内容和权限位一起写进新文件系统，制作 rootfs 或 system 镜像时直接灌入，不必先挂载再拷贝——`system/bin/init` 的可执行权限就是这样住进镜像的。省略时只得到空文件系统，内容需挂载后自行拷入。
    2. `-L 卷标`：把卷标写进超级块，`blkid`、`lsblk` 都能看到，挂载和 fstab 可按 `LABEL=system` 引用。省略时标签为空。
    3. `-b 块大小`：指定块大小，如 1024 或 4096，影响单文件大小上限和空间利用率。省略时由 mke2fs 按设备大小从 /etc/mke2fs.conf 取默认值，可用 `-n` 先查看将要使用的参数。
    4. `-O 特性` 与 `-n`：`-O` 启用或禁用文件系统特性，缺省按 mke2fs.conf 的特性集合创建。`-n` 不真正创建，只打印计算出的参数，用于确认布局后再执行。

3. **容量与块账：**mkfs 必须预先知道规划多大的地盘：把容量按块大小切成块，管理结构也按块记账，例如 64M 配 4096 字节块大小就是 16384 个块。ext4 还有与内容无关的固定开销——超级块、组描述符、inode 表和位图加起来通常一两 MB，日志（journal）也要数 MB，默认大小由实现按容量选择。因此镜像不要贴着内容大小建：一次留足开销和后续增长空间，比事后再 `truncate` 加 `resize2fs` 扩容省一道工序。
4. **创建后验证：**按顺序执行三步：

    1. `dumpe2fs -h 设备`：查看超级块中的块数、块大小、卷标、特性和 inode 数。
    2. `debugfs -R "ls -l /" 设备`：不挂载直接读目录内容。
    3. `mount -o loop`：确认无误后再挂载检查。

5. **平台边界：**选项行为按 e2fsprogs 1.46 核验，不同版本选项集略有差异，以 man mke2fs 为准。Android 构建中的 system.img 由构建系统封装的 mke2fs 生成，与手工命令行的等价路径不同，以对应源码和构建配置为准。

例如，从空文件造一个带卷标并灌入目录内容的镜像：

```console
$ truncate -s 64M build/system.img
$ mkfs.ext4 -d system_root -L system build/system.img 64M
$ dumpe2fs -h build/system.img | grep -E 'Block count|Block size|volume name'
```

`-d system_root` 连权限位一起灌入目录树，`-L system` 把卷标写进超级块，末尾的 `64M` 与块大小共同决定 `Block count`——4096 字节块下为 16384。`dumpe2fs` 输出中的块数、块大小与卷标和这笔账一致，即说明命令按预期执行。

**Q10: [learning] 固件和固件镜像是什么，为什么需要匹配设备？**

固件是为特定设备或硬件组件提供底层控制功能的软件。固件镜像按设备或更新工具要求组织程序及相关数据，用于加载、安装或更新固件。

1. **运行方式：**固件可能在设备上电时运行，也可能由宿主操作系统或驱动在设备初始化时加载。具体取决于硬件。
2. **镜像与格式：**镜像可能包括头部、版本、签名、多个组件或文件系统。`.bin` 只是常见文件名后缀，不能单凭它判断内部格式或适用设备。
3. **更新条件：**更新工具需识别目标设备、镜像格式和版本，并满足设备的校验要求。设备可能具备恢复或回退机制，具体能力取决于实现。

**Q11: [learning] core dump 是什么，能用来分析什么？**

core dump 是进程发生特定错误或收到特定信号时生成的诊断文件，可保存线程寄存器和部分进程内存，供调试器分析当时的运行状态。

1. **分析用途：**配合对应的程序、共享库与调试符号，可检查调用栈、寄存器和已保存内存中的数据。
2. **内容边界：**记录哪些映射由系统配置、过滤规则和大小限制等决定，不保证包含所有内存，也不保证所有变量都可恢复。
3. **生成条件：**系统设置、权限和资源限制可能禁止或限制生成 core dump。内核转储与用户进程转储的范围和生成方式也不同。

依据：Linux 内核《The /proc Filesystem》的 coredump_filter 说明。

## 第三章 内核构建产物

**Q12: [learning] vmlinux 和 objcopy 在内核构建中分别做什么？**

vmlinux 是内核链接生成的未压缩 ELF 文件。objcopy 是 GNU binutils 提供的对象文件转换工具，可在需要时提取或转换其中的段，供后续镜像打包使用。

1. **vmlinux：**包含内核代码及数据，常用于符号分析。符号和调试信息是否完整取决于构建配置及后续处理。
2. **objcopy：**可按选项选择段、转换输出格式或去除符号。转为裸二进制时，输出不再包含原 ELF 文件头和符号表。
3. **构建边界：**是否调用 objcopy、保留哪些段以及后续如何压缩和封装，取决于目标架构、内核版本与构建规则，不能把一种 x86 流程推广到所有架构。

**Q13: [learning] 自编 x86_64 内核得到的 bzImage 是什么？它和 vmlinux 是什么关系？**

bzImage 是 x86 内核编译的最终启动镜像（arch/x86/boot/bzImage），QEMU -kernel 加载的就是它。名字里的 bz = big zImage——比早期的 zImage 装得多，跟压缩算法无关。

它的结构像“三明治”：

1. **外层引导部分：**开头是一小段实模式代码加启动协议头（签名 HdrS），引导程序（BIOS 或 QEMU -kernel）照着它把镜像装进内存，并把启动参数、initramfs 地址递进去。
2. **压缩的内核本体：**完整内核 vmlinux 先被转成纯二进制、再压缩，塞在镜像里。
3. **解压代码：**引导交接后先跑这一小段，把压缩内核解到内存，然后跳进真正的内核入口。从这一刻起跑的就是解压后的 vmlinux 本体。

流水线一句话：vmlinux（编译原始件）→ objcopy 剥成裸二进制 → 压缩 → 加上引导和解压代码，装箱成 bzImage。vmlinux 带符号、用来调试。bzImage 用来引导。

三个边界：zImage 是它的“小容量前辈”，区别只在压缩载荷放的位置。arm64 的内核镜像叫 Image，不叫 bzImage。Android 的 boot.img 是打包容器，里面的内核在 x86 目标上就是 bzImage。

构建完用 file 一验：会被识别为 “Linux kernel x86 boot executable bzImage”，还带内核版本字符串。

**Q14: [learning] zImage 是什么？它和 bzImage 是什么关系？**

zImage 就是“压缩的内核启动镜像”这个名字——z = compressed。关键要分清三个语境：

1. **x86：**zImage 是被 bzImage 取代的历史格式。结构同源，区别只是压缩内核必须待在 1MB 以下的低内存，装不下大内核。bzImage 把载荷放到 1MB 以上，成了 x86 唯一格式。
2. **32 位 ARM：**zImage 是现役标准启动镜像（arch/arm/boot/zImage），U-Boot 用 bootz 加载的就是它。它跟 x86 的 zImage 只是同名，是两份独立实现。
3. **arm64：**没有 zImage——原生镜像叫 Image（未压缩），要减小体积就发布 Image.gz，解压交给引导程序。

判断规则：看到 zImage 先问架构——x86 是历史格式，32 位 ARM 是现役标准，arm64 没有。
