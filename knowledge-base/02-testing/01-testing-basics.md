# Testing Fundamentals

> 软件测试基础概念与通用实践。Q 序列即结构，供查阅与复习。

**Q1: 在新构建或关键改动后，冒烟测试覆盖什么，为什么不能替代完整回归测试？**

冒烟测试用少量核心路径快速判断版本是否适合继续测试；它的覆盖范围有限，不能替代完整回归测试。两者的区别在于覆盖范围：

1. **冒烟测试**：快速检查应用能否启动、关键页面能否打开、主要流程能否走通。
2. **完整回归测试**：按产品范围验证功能及其交互，确认改动没有破坏既有行为。

**Q2: 单元测试要隔离什么，怎样判断一个测试是否写在合适的层级？**

单元测试应快速、可重复地验证一个小范围行为，并把不属于该单元的外部依赖替换为可控边界；如果测试需要启动完整 Android 环境、网络或真实数据库，它通常已经越过纯 JVM 单元测试的边界。隔离不等于把所有对象都 Mock：被测逻辑及其简单值对象应保留真实实现，只有不可控或不属于当前责任的协作者才需要替身。

**Q3: JUnit 4 的测试生命周期与断言分别解决什么问题？**

JUnit 4 通过测试方法和生命周期注解定义执行单元：`@Test` 标记测试，`@Before`/`@After` 在每个测试前后运行，`@BeforeClass`/`@AfterClass` 在测试类级别运行，`@Ignore` 暂时跳过测试。断言负责检查结果是否符合预期；测试通过只说明当前断言覆盖的行为成立，不表示未检查的副作用也正确。

**Q4: Mock、Spy 和依赖注入各自适合解决什么问题？**

Mock 用预设行为替代协作者，Spy 默认调用真实对象并允许局部替换行为，依赖注入则让被测对象从外部接收协作者，便于测试提供可控实现。优先通过构造参数或明确的工厂接口注入依赖；`@InjectMocks` 等自动注入工具只是测试便利功能，不能弥补生产代码依赖边界不清的问题。

**Q5: 单元测试中的 Arrange、Act、Assert（Given、When、Then）怎样组织？**

先准备输入与依赖状态，再只执行一次被测行为，最后检查可观察结果与必要交互。每个测试应围绕一个行为条件组织；把多个无关场景塞进一个测试，或只验证 Mock 被调用而不检查行为结果，都会降低失败信息的定位价值。

**Q6: 什么时候用参数化测试，什么时候应拆成独立测试？**

当同一行为需要用多组输入验证同一个规则时，参数化测试可减少重复并让边界值形成清晰的数据表；当每组输入触发不同的业务路径、准备步骤或失败原因时，应拆成独立测试。参数化不应隐藏用例语义，数据行应能看出输入、预期与边界条件。

**Q7: Mockito 的 `when`、`verify` 和参数匹配器分别做什么？**

`when(...).thenReturn(...)` 为 Mock 配置输入到输出的行为，`verify(...)` 检查调用是否发生及其次数，参数匹配器则定义调用参数的匹配范围。一次调用中的参数应统一使用匹配器或具体值；不要只验证内部实现细节，优先验证对当前行为有意义的协作者交互。

**Q8: 什么时候用 ArgumentCaptor，什么时候用自定义 Matcher？**

当调用完成后要检查传入对象的多个字段或多次调用各自的参数时，使用 `ArgumentCaptor` 捕获参数并在 `verify` 后断言；当参数本身需要作为调用是否匹配的条件时，可用自定义 Matcher 表达谓词。Captor 通常更适合验证阶段，不宜拿来代替桩配置；Matcher 应保持无副作用，并提供能说明失败原因的匹配描述。

**Q9: Mockito 的 Answer 适合处理哪类桩行为？**

`Answer` 适合根据调用参数或调用状态动态生成返回值、触发受控副作用；固定返回值优先用 `thenReturn`，复杂对象断言优先用 ArgumentCaptor，复杂参数筛选优先用 Matcher。过度复杂的 Answer 会把测试变成另一段业务实现，应考虑引入可直接测试的真实逻辑。

**Q10: 静态方法 Mock 的作用域和清理边界是什么？**

Mockito 的静态 Mock 只在创建它的线程中生效，并在关闭后结束；应使用 `try-with-resources` 或等价的 `finally` 确保关闭。它不适合跨线程验证，也不应成为依赖全局静态状态的常规测试方案；能通过依赖注入隔离的代码，优先采用普通 Mock。
