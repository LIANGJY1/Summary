# Testing Fundamentals

> 软件测试基础概念与通用实践。Q 序列即结构，供查阅与复习。

**Q1: [learning] 在新构建或关键改动后，冒烟测试覆盖什么，为什么不能替代完整回归测试？**

冒烟测试用少量核心路径快速判断版本是否适合继续测试。它的覆盖范围有限，不能替代完整回归测试。两者的区别在于覆盖范围：

1. **冒烟测试**：快速检查应用能否启动、关键页面能否打开、主要流程能否走通。
2. **完整回归测试**：按产品范围验证功能及其交互，确认改动没有破坏既有行为。

**Q2: [learning] Android 单元测试应隔离哪些依赖，什么时候需要改用集成测试？**

单元测试应验证一个小范围行为，把不属于被测单元的外部协作者替换为可控实现。当结论依赖 Android 框架、数据库或网络栈本身时，应增加对应集成测试，而不是在单元测试里假装验证了真实平台行为。

1. **本地单元测试**：保留被测逻辑和值对象的真实实现，用 Fake 或 Mock 控制数据库、网络客户端、时钟等边界依赖。它适合快速验证分支、状态转换和错误处理。
2. **Android 环境测试**：当行为依赖真实 Context、生命周期、系统服务或平台实现时，在设备或模拟器上验证。Robolectric 一类环境可提供部分框架行为，但不能自动证明真实设备行为完全一致。
3. **集成测试**：当要验证数据库事务、网络协议、组件协作等多个真实部分之间的契约时，保留这些部分并隔离更外层依赖。测试范围变大后应接受更高运行成本，并让失败信息指向具体契约。

判断层级时看测试的结论依赖什么：如果换成可控协作者仍能证明被测逻辑正确，就留在单元层。如果必须依赖真实平台或多个组件的协作结果，就在更高层补测。隔离不是把所有对象都 Mock。

**Q3: [learning] JUnit 4 的 @Test、生命周期注解和断言各自负责什么？**

`@Test` 声明一个测试方法，生命周期注解准备和清理测试状态，断言检查可观察结果。三者分别定义执行入口、隔离条件和通过标准，不能用“测试方法运行过”代替断言。

1. **每个测试方法**：`@Before` 在测试前准备状态，`@After` 在测试后清理资源。每个测试都应能独立运行，不依赖其他测试留下的静态或共享状态。
2. **每个测试类**：`@BeforeClass` 和 `@AfterClass` 分别在该类测试开始前、结束后运行，适合昂贵且可安全共享的一次性资源。JUnit 4 要求这些方法为 `static`。
3. **执行与断言**：`@Test` 标出测试入口，断言应针对行为结果及必要的副作用。`@Ignore` 会跳过测试，不代表测试已通过。应说明跳过原因，并避免让它长期掩盖未覆盖路径。

测试通过只证明当前输入和断言覆盖的行为成立。若结果正确但重要副作用、状态变化或错误分支没有断言，测试仍不能支撑那些结论。

**Q4: [learning] Mock、Spy 和依赖注入分别解决什么问题，测试中怎样选择？**

依赖注入决定协作者如何交给被测对象，Mock 和 Spy 决定测试如何控制或观察某个协作者。三者不是互斥的替代方案。优先让生产代码通过构造参数或明确工厂接收依赖，再只替换测试边界上的协作者。

1. **Mock**：完全以预设行为替代协作者，适合控制外部返回值、异常或调用结果。若被测逻辑需要依赖真实协作者的行为，Mock 可能把待验证部分一起伪造掉。
2. **Spy**：以真实对象为基础，只对少数方法做替换或记录，适合难以替代且必须保留大部分真实行为的对象。真实方法可能产生副作用，因此要明确哪些调用会实际执行。
3. **依赖注入**：由构造参数、工厂或其他组装入口提供协作者，使测试可以传入 Fake 或 Mock。`@InjectMocks` 只简化测试装配，不能修复生产代码依赖隐藏、创建职责混乱的问题。

通常先使用真实值对象和简单 Fake。只有需要控制外部边界或验证有意义的协作契约时才用 Mock。不要为了让测试“可 Mock”而把每个内部对象都抽象成接口。

**Q5: [learning] 单元测试中的 Arrange、Act、Assert（Given、When、Then）怎样划分？**

Arrange 准备输入和依赖状态，Act 执行被测行为，Assert 检查结果。清晰分段能让失败定位到前提、行为还是预期。一个测试应围绕一个行为条件组织，但不要求机械地只写一条断言。

1. **Arrange / Given**：建立本题需要的输入、初始状态和协作者行为，避免包含与本场景无关的公共准备。
2. **Act / When**：调用被测入口并保存结果。若一个测试连续执行多个互不相关的动作，失败时很难看出哪个动作违反预期。
3. **Assert / Then**：检查对外可观察的结果、必要的状态变化，以及确实属于契约的协作者交互。只验证某个 Mock 被调用，无法证明返回结果和业务状态正确。

多个断言可以共同证明同一个行为契约。不同输入若代表不同失败原因或业务路径，应拆成独立测试，让每个失败名称和数据都能说明场景。

**Q6: [learning] 哪些输入适合放进参数化测试，哪些场景应拆成独立测试？**

当多组输入验证同一个行为规则、执行路径和断言结构时，使用参数化测试。当输入代表不同业务行为、准备条件或故障原因时，拆成独立测试。参数化减少重复的前提是每一组数据仍能清楚表达自己验证什么。

1. **适合参数化**：同一百分比函数对零值、边界值和普通值都应遵守同一舍入规则。每行给出输入与预期，失败报告能指出是哪组数据。
2. **适合拆分**：一种输入验证权限拒绝，另一种验证网络超时。两者的准备步骤、被测分支或诊断动作不同，合并后失败语义会变模糊。
3. **需要控制规模**：参数数量过多会形成难读的笛卡尔积。优先覆盖等价类、边界和能改变决策的条件，不把所有组合都塞进一个数据源。

**Q7: [learning] Mockito 的 when、verify 和参数匹配器分别怎样控制与验证调用？**

`when(...).thenReturn(...)` 为 Mock 配置响应，`verify(...)` 检查协作者交互，参数匹配器定义哪些参数算匹配。配置回答“被测代码调用时会发生什么”，验证回答“被测代码实际做了什么”。

1. **配置桩行为**：用 `when(mock.method(input)).thenReturn(value)` 控制依赖输出。若输入参数有业务意义，应指定该值，避免过宽匹配掩盖错误调用。
2. **验证交互**：用 `verify(mock, times(n))` 验证调用及次数。默认 `verify(mock)` 等价于期望调用一次。只验证交互中会影响功能契约的部分，避免把私有实现顺序锁死。
3. **匹配参数**：`any()`、`eq(value)` 等匹配器用于表达参数范围。一次方法调用的所有参数要么都用匹配器，要么都用具体值。混用时，具体值也要包成 `eq(value)`，否则 Mockito 会报错。

若参数本身是结果的一部分，最好直接断言返回值或状态。不要为了“验证得更多”而断言与外部行为无关的内部调用细节。

**Q8: [learning] Mockito 中何时用 ArgumentCaptor，何时用自定义 Matcher？**

调用之后要检查传入对象的内容时，用 `ArgumentCaptor` 捕获参数再断言。参数条件需要决定桩行为或验证是否匹配时，用 Matcher。两者区别在于“取出参数检查”与“用条件定义匹配”。

1. **Captor**：在 `verify` 阶段捕获一次或多次调用的参数，适合检查 DTO 多个字段、对象转换结果或调用顺序对应的参数。随后对捕获值做普通断言，失败信息通常更具体。
2. **自定义 Matcher**：当参数满足某个谓词才应匹配时使用，例如某对象的业务键等于预期值。Matcher 应无副作用，并提供有意义的描述，使失败报告说明哪个条件未满足。
3. **避免混用**：不要把 Captor 当成配置动态返回值的工具。桩行为需要随参数变化时使用 `Answer`。如果对象有稳定的值相等语义，优先直接比较对象或使用已有匹配器，避免写重复匹配代码。

**Q9: [learning] Mockito 的 Answer 适合配置什么样的桩行为？**

当 Mock 的响应必须根据本次调用参数或受控调用状态计算时，使用 `Answer`。固定响应应使用 `thenReturn`，否则测试会用一段自制逻辑重复实现生产行为。

1. **适用情形**：返回值要回显输入、依参数选择结果，或需要在调用时触发一个明确且可观察的副作用。
2. **更简单的替代**：固定返回值用 `thenReturn`，需要抛异常用 `thenThrow`。验证传入对象用 `ArgumentCaptor`，定义匹配条件用 Matcher。
3. **复杂度边界**：若 `Answer` 包含多层业务分支、状态机或复杂数据变换，应把逻辑提取到可直接测试的真实组件，再让 Mock 只提供边界响应。

**Q10: [learning] Mockito 静态方法 Mock 的作用域、线程限制和清理边界是什么？**

Mockito 的静态 Mock 是有作用域的测试替身，只对创建它的线程生效。测试结束时必须关闭，否则同一线程后续代码仍可能观察到被替换的行为。它适合短暂隔离遗留静态入口，不应作为新代码的默认依赖设计。

1. **作用域**：将 `MockedStatic` 放进 `try-with-resources`，或在 `finally` 中关闭，使替换行为只覆盖明确的一段测试代码。
2. **线程限制**：在其他线程执行的静态调用不会自动继承该 Mock。若被测逻辑把调用派发到线程池，测试需要控制执行器，不能假设静态 Mock 跨线程生效。
3. **设计边界**：静态 Mock 能隔离调用点，但会隐藏全局依赖。新代码若可改造，优先把时钟、文件系统或服务入口作为依赖注入。使用静态 Mock 前还要确认项目 Mockito 版本与 MockMaker 支持该能力。

**Q11: [learning] 测试金字塔的分层比例依据是什么？倒置的“冰淇淋筒”意味着什么？**

测试金字塔按成本与数量分层：底层单元测试数量最多、运行最快、失败时定位面最小；中间集成/组件测试验证模块协作；顶端端到端（End-to-End，E2E）与 UI 测试数量最少但最慢、最脆。比例依据是“反馈速度 × 定位精度 × 维护成本”的乘积——同样的覆盖置信度，把验证尽量压到低层，总成本最低。

1. **单元层**：毫秒级、可并行、无环境依赖，承担边界与分支的主要覆盖。
2. **集成层**：验证真实协作（数据库、IPC、网络栈），失败说明“各自对、合起来错”。
3. **E2E 层**：只验证关键用户路径；它的价值是置信度而非覆盖面，数量失控就是“冰淇淋筒”反模式——构建慢、随机失败多、定位要人工穿层。

**Q12: [learning] 回归测试为什么不能全量重跑？“测试选择”依据什么缩小范围？**

全量回归在代码库与用例规模增长后，运行时间会超过交付节奏能接受的上限，而其中绝大多数用例与本次改动无关。测试选择（test selection）依据改动影响面缩小执行集：按代码变更映射到对应的测试（覆盖率反推、调用链或依赖图分析、或按模块归属约定），只跑可能受影响的用例。

1. **映射手段**：粗粒度按模块/包归属；细粒度按行级覆盖反推“哪些用例执行过这段改动代码”；构建系统可用依赖图自动扩展到下游。
2. **代价与兜底**：选择算法有漏报风险（改了共享工具函数、下游用例未被映射到），因此关键合入仍保留周期性或合并前的全量兜底跑，选择策略本身也要用“漏掉的失败”回头校准。
3. **配套**：失败用例的“优先重试与隔离”（先跑上次失败的与改动相关的）在实践中收益最高——失败呈聚集性，历史失败是最好的风险信号。
