## 构造期配置与运行期 API 存在断层

**现象**：Android 车机项目，HCTabBar（车机 UI 组件库 UIComponent 1.3.2 AAR 中的自定义标签栏组件）。运行期调用属性 setter（`setItemMarginLevel1` 等），编译通过、运行无报错，界面纹丝不动；另见切分屏档位后列表选中态莫名回到第一项。手顺：进入页面 → 代码调 setter → 界面停留观察；javap 反编译 setter 方法体与字段消费点确认。

**原因**：构造期"先读 XML 属性再构建条目"，字段消费只发生在构建路径；条目建好之后再写字段，没有任何代码会重新消费它。且重建链路自带副作用契约：`updateAllitems()` 清空容器逐项重建 → 选中态重置为 0 → `setSelectIndex(0)` 以新状态回调监听器——监听器若在重建前已挂载，回调把组件的"新状态"写回业务要恢复的"旧状态"（如记住的用户选中页）。

```java
// HCTabBar.java（反编译，示意）
public void setItemMarginLevel1(int px) {
    this.itemHorizontalMarginLevel1 = px;   // setter 只写字段，到此为止
}
private void updateAllitems() {             // 字段的唯一消费点 = 私有重建方法
    // removeAllViews → 逐项创建 → setSelectIndex(0) → 触发监听回调
}
```

**误区**：直觉认为"属性调了就该生效"，排查偏向资源覆盖、调用时机、缓存——反编译前想不到组件内部没有运行期消费点；选中态漂移则只在数据层找原因（ViewModel 读写时序），想不到 UI 重建本身在写业务状态。

**解决方案**：运行期修改 = 写值 + 触发重建入口，两步缺一不可；重建后先恢复状态、再挂监听（或适配先于挂监听执行）。

**启示**：
- 组件设计：构建期消费的配置必须同时提供内建运行期 API（含静默恢复选项，区分程序化设置与用户触发），否则业务方只能各自反射（适用：自有组件设计期）
- 业务侧：前提是组件存在单一重建入口且 setter 无副作用；无重建入口的组件放弃运行期修改，改走布局变体

## 定制系统资源兜底回落不可信，锚资源探针验证

**现象**：车机/TV 定制系统项目：修改基准（`values/`）dimen 后，某些分屏/窗口档位不生效；或新增覆盖不生效——表现为"改了没反应"。手顺：改基准值 → 多设备逐档走查 → 读探针对比实际命中桶。（设备实测断言 + 探针机制佐证；根源未独立复现）

**原因**：标准 Android 行为是"限定桶未命中则回落 `values/`"，但定制系统可能不回落、或窗口宽度与桶映射假设不符，导致覆盖写了却命中基准（黑盒，未取证到系统源码级机制）。

```xml
<!-- 每个宽度桶的 dimens.xml 各放一条同名探针，值 = 桶宽 -->
<!-- values-w1920dp/dimens.xml -->
<dimen name="split_screen_resource_anchor">1920dp</dimen>
```

```java
// 运行时读取探针，即可断言当前窗口实际命中的资源桶
int bucket = getResources().getDimensionPixelSize(R.dimen.split_screen_resource_anchor);
```

**误区**：信任标准回落规则，把问题当业务 bug 排查；且缺一个"当前命中哪个桶"的观测手段，只能盲猜改哪个文件。

**解决方案**：跨档位资源逐桶显式定义，不依赖 `values/` 兜底——兜底失效时无害；"改了不生效"类问题先用探针定位实际命中桶再决定改哪里；探针值与预期不符说明设备窗口宽度和桶映射假设不一致，需重新映射桶。

**启示**：
- 多档位/多限定符资源不做兜底依赖；解析行为不可控的场景用锚资源探针把解析结果变成可观测（适用：定制系统/设备行为不可控，且资源按档位分化）

## ViewBinding 跨变体联合字段缺失为 null

**现象**：Android 车机多档位分屏项目（同一 layout 名在多个宽度桶各有副本）。编译期正常引用 Binding 字段，切窄档位后 NPE；同 id 在不同副本用不同控件类时，运行时 ClassCastException。手顺：宽档位进入页面 → 切窄档位触发布局重建 → 崩溃栈指向 Binding 字段；比对各档布局副本与生成的 `ActivityAppDetailBinding.java`。

**原因**：Binding 字段按各副本 id **并集**生成，类型取出现处的最强类型；仅存在于部分副本的节点，在缺失副本 inflate 后无对应视图，字段为 null。

```java
// 生成的 ActivityAppDetailBinding.java（车机项目）
public final Barrier barrierHeaderBottom;  // 基准副本有该 Barrier，窄分屏副本没有
binding.barrierHeaderBottom.setVisibility(...);  // 窄分屏下 NPE
// 同 id 不同控件类 → 字段类型降级为 View，按具体类型使用则 ClassCastException
```

**误区**：字段有编译期类型就当非空用（编译不报错）；以为删掉窄屏副本节点后代码会编译失败给出提示——实际编译期安静，问题只在缺失档位运行时暴露；类型降级后强转同样只在运行时炸。

**解决方案**：收编/合并布局副本的审计必须包含"仅单变体存在的节点 × 代码引用"检查（代码未引用的缺失节点无害）；收编第一步统一同 id 控件类；收编后核对生成的 Binding 字段类型未降级。

**启示**：
- 变体间节点集合差异视为破坏性变更：同步暴露等价运行期能力，或为跨档位引用补 null 守卫（适用：布局存在多宽度/朝向副本且节点集合不一致；单副本布局无此问题）
