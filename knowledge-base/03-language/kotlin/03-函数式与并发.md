## 第 8 章 函数式编程

**Q1: 编写高频高阶函数或需要 `reified` 类型参数时，`inline` 能解决什么问题，又会带来哪些限制？**

高阶函数接收 lambda 时，通常需要创建函数对象并进行间接调用。`inline` 允许编译器把函数体和可内联的 lambda 实参展开到调用处，以减少这部分开销。

```kotlin
inline fun repeatAction(times: Int, action: (Int) -> Unit) {
    for (index in 0 until times) {
        action(index)
    }
}

repeatAction(3) { index -> println(index) }
```

`inline` 不应简单理解为“强制复制后绝对零开销”：编译器仍根据后端和调用情况生成代码，标记为 `noinline` 的 lambda 参数也不会随函数体内联。它主要提供三类能力：

- 减少高频高阶函数的函数对象分配和间接调用。
- 允许可内联 lambda 使用非局部返回。
- 允许 `reified` 类型参数在函数体中访问实际类型信息。

```kotlin
inline fun <reified T> Any?.isType(): Boolean = this is T
```

普通泛型函数的类型参数在运行时通常不能直接用于 `is T`；内联后，编译器可以把调用处的实际类型代入函数体，因此 `reified` 必须与 `inline` 配合。

代价是调用处代码可能变大，公开 inline API 还受到可见性和二进制兼容性限制。通常只在以下情况使用：函数接收 lambda 且调用频繁，或确实需要非局部返回、`reified`。不接收可内联 lambda、也没有 `reified` 的函数通常没有必要添加 `inline`。

**Q2: 在 `forEach` 中只想跳过当前元素时，为什么裸 `return` 会退出外层函数，应该怎样表达局部返回？**

标准库 `forEach` 是 inline 函数。传入它的 lambda 被展开到调用处后，lambda 中未加标签的 `return` 可以直接返回最近的具名外层函数，这称为**非局部返回**。

```kotlin
fun printUntilZero(values: List<Int>) {
    values.forEach { value ->
        if (value == 0) return // 退出 printUntilZero
        println(value)
    }
}
```

如果只想跳过当前元素，应使用标签返回：

```kotlin
fun printNonZero(values: List<Int>) {
    values.forEach { value ->
        if (value == 0) return@forEach
        println(value)
    }
}
```

`return@forEach` 只结束本次 lambda 调用，效果接近普通循环中的 `continue`。如果控制流需要 `break`、多层跳转或复杂分支，普通 `for` 往往更直观：

```kotlin
for (value in values) {
    if (value == 0) break
    println(value)
}
```

非 inline 高阶函数中的 lambda 默认不能使用这种裸 `return`。如果 inline 函数把 lambda 保存在对象中或从其他执行上下文调用，也不能允许非局部返回，需要使用 `noinline` 或 `crossinline` 表达相应限制。

**Q3: 用 `runCatching { ... }.onFailure { ... }` 代替 try/catch 时，异常去哪了？这条链有什么边界？**

`runCatching` 执行代码块，把正常返回值包装为成功的 `Result`，把代码块抛出的 `Throwable` 包装为失败的 `Result`。`onFailure` 只观察失败结果并执行日志等动作，然后返回原来的 `Result`；它本身不会自动恢复或重新抛出其中的异常。

```kotlin
val raw = "x"
val result: Result<Int> = runCatching { raw.toInt() }
    .onFailure { e -> println("failed: ${e.message}") }

println(result.getOrNull()) // 打印 null
```

失败仍保存在 `result` 中。后续调用 `getOrThrow()` 会把它重新抛出，`getOrNull()` 会把失败映射成 `null`；如果 `onFailure` 的处理代码自己抛出异常，新异常也会直接向外传播。因此，“异常去哪了”取决于整条链最后如何消费 `Result`，不能只看到 `onFailure` 就断定异常已经处理完。

`runCatching` 捕获的是 `Throwable`。只想处理某类可恢复异常时，显式的 `try/catch` 更容易表达捕获范围。

**Q4: 在 `ids.forEach { id -> service.get(id)?.let { value -> handle(value) } }` 中，两个 lambda 和 `?.let` 分别怎样执行？**

外层 `forEach` 依次把集合元素传给 `id`；每一轮调用 `service.get(id)`。返回值非空时，安全调用 `?.` 才会执行 `let`，并把该值作为 `value` 传入内层 lambda；返回 `null` 时，本轮直接跳过 `handle`。

```kotlin
val namesById: Map<Int, String> = mapOf(1 to "Ada")

listOf(1, 2).forEach { id ->
    namesById[id]?.let { name ->
        println(name)
    }
}
// 只打印 Ada；id == 2 时查找结果为 null，内层 lambda 不执行
```

`id` 和 `value` 是两个不同 lambda 的参数。显式命名可以避免嵌套时两个 `it` 难以区分。`let` 会返回内层 lambda 最后一条表达式的结果；原代码没有接收这个结果，只利用“非空才执行”的条件效果。
