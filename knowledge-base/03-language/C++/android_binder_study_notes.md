# Android Binder 跨进程通信

> 本文聚焦 Android 用户空间与 Linux 内核的关系，以及 Binder 的接口、对象传递、缓冲区和线程协作。具体类名会随 Android 版本与 Java、Native 后端变化。涉及源码实现时应同时核对目标分支。

**Q1: Android 运行在 Linux 内核之上，为什么应用开发者常感觉它像另一个系统？**

Android 使用 Linux 内核提供进程、内存、调度、网络和驱动等基础能力，同时在用户空间提供自己的运行时、系统服务、图形栈、应用框架和 SDK。普通应用主要通过 Activity、Service、ContentProvider 等框架入口工作，进程创建与主线程消息循环由系统框架协作完成，因此开发者通常不直接编写 `fork()` 循环来启动应用。

这种体验差异不表示 Android 与 Linux 内核相互独立，也不表示应用完全接触不到内核能力。NDK、系统调用、设备节点和内核驱动仍构成用户空间与内核协作的边界，但普通应用通常受 API、权限和沙箱约束。

**Q2: 如果移除 Android 用户空间，只保留 Linux 内核，还能得到可用的 Android 或桌面 Linux 系统吗？**

不能。Linux 内核负责核心资源管理与硬件抽象，但不能单独提供 shell、C 库、init、服务管理、图形环境或 Android Framework。删除 Android 用户空间后，设备上只剩内核及可能保留的其他组件。它既不是完整 Android，也不会自动变成桌面 Linux。要运行常见用户程序，还需要与其 ABI 匹配的用户空间运行环境。

`ls` 和 `cd` 也不是内核自带功能：`ls` 是用户空间程序，`cd` 通常由 shell 内建实现。是否还能运行某个命令取决于对应可执行文件、动态链接器、库和配置是否仍存在。

**Q3: Java 的 SystemServer 如何通过 Binder 调用 Native 的 SurfaceFlinger？Binder 驱动是硬件吗？**

Binder 驱动是 Linux 内核中的软件驱动，不是硬件。跨语言调用通常由 Java Binder 框架、JNI/native Binder 库和内核 Binder 驱动共同完成。具体代理类、桥接类和调用路径依 Android 版本及服务接口而异，不能把所有请求概括为固定的一组 `BpBinder`、`BBinder` 对象。

Binder 设备以字符设备接口暴露给用户空间。进程通过打开相应设备节点、映射接收缓冲区并使用 `ioctl` 等机制与驱动交互。驱动负责对象引用、事务路由、缓冲区与线程唤醒等内核侧工作。它不会把两个进程的全部内存合并成共享内存。

**Q4: 应用如何取得应用服务或系统服务的 Binder 接口？**

应用服务通常通过 `bindService()` 建立绑定。连接成功时，服务端返回的 `IBinder` 到达 `ServiceConnection.onServiceConnected()`。客户端再依接口形式转换为本地接口或代理。绑定状态、导出属性、权限及进程配置都会影响连接能否建立。

系统服务一般通过公开的 Android API 取得。Framework 内部才会按服务名向 ServiceManager 查询 Binder。普通应用不应把隐藏的 `ServiceManager.getService()` 当作稳定公共 API。服务名、访问权限和可见性依系统版本及调用 UID 而定。

**Q5: AIDL 生成的 Stub 与 Proxy 如何把接口调用变成 Binder 事务？**

AIDL 描述接口与可传输类型，构建工具为所选语言后端生成接口适配代码。客户端代理把方法标识和参数写入 `Parcel` 并发起事务。服务端 Stub 解码事务、分派到实现方法，再按接口约定写回结果或异常。同步调用可以返回结果，`oneway` 调用则不等待远端方法的返回值。

生成代码并非必然是 Java 源码：Android 构建支持不同语言后端与版本演进。即使接口外观看起来像本地方法，调用也可能跨进程、阻塞、失败或触发远端异常，因此必须处理线程、生命周期、权限和进程死亡边界。

**Q6: 不使用 AIDL 时，手写 Binder IPC 需要承担哪些工作？**

调用方与服务端必须共同维护一份事务契约。手写实现通常需要分配事务码、按相同顺序编码和解码参数、处理返回值与异常，并约定接口版本及权限。字段类型或顺序不一致会造成解码错误或兼容性问题。

AIDL 的主要价值是从接口描述生成重复的编码、分派和代理样板代码，并降低契约两侧不一致的风险。它不能替开发者决定线程模型、权限策略、兼容性策略，也不能保证业务逻辑正确。

**Q7: AIDL 的 `oneway`、参数方向标记和 Binder 死亡通知分别影响什么？**

这几项分别控制事务等待方式、数据契约和远端对象失效通知，不能统称为性能开关：

1. **`oneway`：** 用于无返回值的异步事务。调用方提交请求后不等待服务端方法完成。它不保证远端必定处理，也不适合需要立即取得结果的接口。具体排队与线程行为应按目标 Android 版本确认。
2. **`in`、`out`、`inout`：** 描述 AIDL 参数的数据方向，并影响生成代码的读写约定。它们不是任意对象的零拷贝承诺。支持的类型、后端和版本会影响具体语义。
3. **`linkToDeath()`：** 注册 Binder 对象死亡通知，以便客户端在远端对象失效后清理状态或尝试重连。通知是异步生命周期信号，调用前后仍可能发生竞态，重新连接与请求重放策略需由客户端设计。

**Q8: Android `Messenger` 与直接使用 AIDL Binder 的差别是什么？**

`Messenger` 在 Binder 上封装基于 `Message` 的通信接口，并把处理交给服务端关联的 `Handler`。当 Handler 使用单个 Looper 时，消息按该队列规则串行处理，适合消息式、吞吐要求不高的交互。它不意味着 Binder 驱动本身只能串行处理事务。

直接 AIDL 可以定义更具体的方法与参数契约，服务端也可设计并发处理方式，但需要明确线程安全和调用阻塞。选择时看是否需要消息队列语义、接口粒度、吞吐量及并发控制，而不是只比较代码行数。

**Q9: Binder 服务注册与客户端查询的基本时序是什么？**

常见系统服务在启动后向 ServiceManager 注册 Binder，客户端再按服务名查询并取得代表远端对象的句柄或代理。随后客户端发起事务，驱动按 Binder 对象引用将事务交给目标进程。ServiceManager 提供服务名到 Binder 服务的查找入口，不负责转发服务的每次业务事务。

ServiceManager 本身由系统启动配置和 init 协作启动。不同 Android 版本的注册、访问控制与服务可见性机制有所变化。不要把 Binder 句柄号当成跨设备或跨进程稳定的服务地址，也不要把 ServiceManager 描述为一个保证服务始终存活的注册中心。

**Q10: Native Binder 与 Java Binder 怎样跨语言交互？**

Native 服务可使用 C++ Binder 接口，Java 服务可使用 Framework Binder 接口。跨语言场景由相应的 JNI/native 桥接层衔接。Java 代理对象与 native 引用之间存在映射关系，但具体类名和对象封装随 Android 版本及调用方向变化。

排查一次跨语言调用时，应沿公开接口、生成或手写代理、JNI 边界、native Binder 库、驱动事务和服务端实现逐层追踪。仅看到类名相似，不能据此断定两个对象是一一对应的同一个 C++ 实例。

**Q11: Binder 如何支持服务端回调客户端？**

Binder 事务由当前调用方向上的客户端发起，但 Binder 对象本身可以作为参数传递。客户端把实现好的回调 Binder 传给服务端后，服务端即可通过这个对象发起另一笔事务。在这笔事务中，原服务端成为调用方，原客户端执行回调。

这种模式常用于 AIDL 回调接口。双方仍需管理回调注册和注销、客户端进程死亡、并发调用、线程切换及重入。把 Binder 对象传过去不会自动保证回调必达或顺序符合业务预期。

**Q12: Binder 接收缓冲区的 `mmap` 如何减少事务数据复制？**

Binder 通常由接收方映射一段可供驱动写入并供接收进程读取的缓冲区。发送方数据仍需从发送进程复制到驱动管理的接收缓冲区。由于接收方用户地址映射到这段缓冲区，接收方可读取已写入的数据而不再把整笔事务复制到另一块用户缓冲区。因此常称典型 Binder 事务主体有一次用户态到内核管理缓冲区的复制，而不是“完全零拷贝”。

这不等于所有 Binder 负载都适合传大块数据。缓冲区有限，事务对象、文件描述符和特殊对象也有各自的处理。大数据通常应使用共享内存或文件描述符等专门机制，并明确双方生命周期与同步协议。具体分配与映射细节以目标内核 Binder 驱动实现为准。

**Q13: Binder 驱动如何接收事务、唤醒服务端线程并交付请求？**

用户态 Binder 库通过 `ioctl` 与驱动交换命令和缓冲区信息。常见读写入口是 `BINDER_WRITE_READ`：线程可提交写命令，也可读取驱动返回的工作。没有可处理工作时，线程可能在驱动的等待队列上睡眠。事务到达后，驱动根据目标 Binder 节点和线程池状态安排工作，并唤醒合适的等待线程。

被唤醒线程取出事务后，用户态 Binder 库解析驱动交付的数据，再由 Stub 分派到服务方法。进程和线程是否阻塞、由哪个线程处理以及能否并行，取决于同步或异步事务、Binder 线程池、调用链重入与版本实现。不能把一个固定的 `wait_event`/`wake_up` 源码序列当作所有版本的完整流程。
