# C++ 编译与链接工具链

**Q1: [learning] 用 `g++` 静态编译 `init.cpp` 时，命令中的编译选项分别控制什么？**

编译命令既选择 C++ 标准和诊断信息，也决定调试信息与链接方式；其中只有 `-static` 控制静态链接。

```bash
g++ -std=c++17 -Wall -Wextra -g -static src/init.cpp -o build/init-static
```

1. `g++`：C++ 编译器驱动，会协调编译和链接步骤；省略它就没有执行编译的命令。
2. `-std=c++17`：按 C++17 编译；显式指定可避免依赖编译器版本的默认标准，省略时使用该编译器的默认标准。
3. `-Wall -Wextra`：启用常见和额外的编译警告，帮助发现潜在问题；它们不改变链接方式，省略后仍会编译，但不会启用这两组警告。
4. `-g`：生成调试信息，方便调试器关联源码和变量；省略后通常没有这部分调试信息，除非其他构建选项另行加入。
5. `-static`：要求链接静态库，避免依赖运行时加载共享库；省略后由工具链默认链接策略决定，通常可能产生动态链接程序。静态库不可用时，链接仍会失败。
6. `src/init.cpp` 与 `-o build/init-static`：前者是输入源文件，后者指定输出路径；省略 `-o` 时会使用工具链默认输出名，`build/` 目录需预先存在。

编译器成功时通常不打印成功提示；应以命令退出状态为准，退出码 `0` 表示成功。仅看到命令提示符回来只能说明命令结束。

**Q2: [learning] 静态编译后，`file` 和 `ldd` 的输出说明了什么，能证明程序已可作为 initramfs 的 `/init` 启动吗？**

`file` 可检查 ELF 格式、目标架构和链接信息；`ldd`（List Dynamic Dependencies，列出动态依赖）用于查看动态库依赖。静态 ELF 上出现 `not a dynamic executable` 与静态链接相符，不是编译错误。

1. `file` 显示 `ELF 64-bit`、`x86-64` 时，说明产物面向 64 位 x86；显示 `statically linked` 表示文件被识别为静态链接，`with debug_info` 和 `not stripped` 表示保留了调试信息和符号。要放入 QEMU 前，仍须确认它与 QEMU 内核的架构一致。
2. `ldd` 显示 `not a dynamic executable` 时，表示它没有可供 `ldd` 列出的动态库依赖；这与 `file` 的静态链接结果相互印证。
3. 这些检查只说明编译产物的格式、架构和链接信息，不证明内核已经成功执行它。作为 `/init` 还要正确放入 initramfs，并能在目标内核和启动环境中运行；示例程序若打印后立即退出，也不能充当持续运行的 PID 1。

**Q3: [learning] 为什么同样使用 `-g` 编译，静态链接的 `build/init-static` 通常比动态链接的 `build/init` 大？**

静态链接会把程序需要的静态库实现放进可执行文件；动态链接的程序则记录共享库依赖，运行时再从系统加载库代码。`std::cout` 用到的 C++ 标准库及相关运行库会让静态产物变大，但链接器只纳入解决依赖所需的库成员，不会把整套 Linux 库全部复制进去。

`-g` 生成的调试信息会增加文件体积，`file` 的 `with debug_info` 会显示这一点；但这两次编译都使用了 `-g`，因此大小差异主要来自静态链接进来的库代码。`not stripped` 表示相关符号信息尚未剥除。
