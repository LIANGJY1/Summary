# JVM 运行时

> Java 虚拟机学习资料。区分 JVM 规范保证与 HotSpot 常见实现；题序即结构。

**Q1: [learning] JVM 规范中的运行时数据区如何按线程共享边界划分？**

JVM 规范描述的运行时数据区包括线程私有区和线程共享区：每个线程有自己的程序计数器与 Java 虚拟机栈；堆和方法区由线程共享。规范规定用途与可观察行为，不要求所有实现采用同一物理布局。

1. **线程私有**：程序计数器、Java 虚拟机栈，以及规范所述的本地方法栈。
2. **线程共享**：堆和方法区；运行时常量池属于方法区中的结构。

“堆里存对象、栈里存局部变量”是过度简化：局部变量表中可以保存基本值或对象引用，对象是否、何时被优化掉由实现决定。

程序计数器的用途可以落到执行模型上：解释器通过改变计数器的值选取下一条要执行的字节码指令，分支、循环、跳转、异常处理与线程切换后的恢复都依赖它，这也是它必须线程私有的原因。规范之外，实现还常使用未列入运行时数据区的堆外直接内存（如 NIO 的 `DirectByteBuffer`）：它受 HotSpot 的 `MaxDirectMemorySize` 这类实现参数约束，但不属于规范定义的数据区，排查内存问题时应与堆分开统计。

**Q2: HotSpot 的永久代和元空间为什么不能当作 JVM 规范固定区域？**

永久代、元空间是特定 HotSpot 版本的类元数据实现方式，不是 JVM 规范要求的运行时数据区名称。HotSpot 在 JDK 8 移除永久代并引入本地内存中的元空间，因此排查内存问题时必须记录具体 JDK 与 VM 实现。

方法区是规范层的抽象；不要把它等同于某个版本 HotSpot 的永久代或元空间。

**Q3: JVM 创建对象时，哪些步骤由规范定义，哪些布局细节依实现决定？**

字节码创建对象会触发类初始化检查、分配并初始化对象，再执行构造器；对象头、字段排列、指针压缩和访问定位等具体表示主要由虚拟机实现决定。不能把某一 HotSpot 版本的对象布局当成跨 JVM 保证。

HotSpot 常以对象头、实例字段区和对齐填充组织对象，但字段重排、压缩指针和锁状态等会受版本、架构与启动参数影响。

**Q4: Java 垃圾回收怎样判断对象可回收？引用计数为何不是唯一判据？**

常见追踪式收集器从 GC Roots 出发沿引用关系标记可达对象，未被可达集合覆盖的对象才可能回收。引用计数容易处理局部释放，但两个对象互相引用时计数仍非零，即使它们都无法从根访问。

是否立刻回收、采用何种算法和回收器由 JVM 实现决定；不可达不意味着终结器或清理回调会及时执行。

**Q5: 强、软、弱和虚引用分别表达什么保留意图？**

强引用在程序可达路径中保留对象；软、弱、虚引用提供不同程度的可回收关联，但回收时机并非精确调度接口。虚引用通常与引用队列配合观察对象将被回收的通知，不用于读取对象。

需要确定性释放文件、锁或连接时应使用显式关闭或结构化资源管理，不能依赖 GC 运行时机。

**Q6: 标记清除、复制和标记整理各自会付出什么成本？**

标记清除实现直接但可能留下碎片；复制收集把存活对象搬到另一空间，回收与分配简单但需要预留空间；标记整理将存活对象压紧，减少碎片但整理时要移动对象并更新引用。实际收集器常组合阶段或区域化策略。

Eden/老年代分代、对象晋升阈值和大对象分配策略是 HotSpot 收集器的实现策略，不是所有 JVM 必须采用的固定规则。

**Q7: CMS 为什么只应作为历史收集器理解？**

CMS 是 HotSpot 曾提供的并发标记清除收集器，目标是减少老年代收集停顿；它会留下碎片，并存在并发阶段与应用竞争 CPU、并发失败等代价。CMS 在 JDK 9 被弃用，并在 JDK 14 移除，现代 JDK 不能再按教程配置 CMS 参数。

GC 选择应依据实际 JDK 版本、延迟目标、吞吐量和观测数据；历史算法用于理解取舍，不能直接作为当前 JVM 配置建议。

**Q8: JDK、JRE 和 JVM 分别包含什么？**

JVM 定义并执行 Java 字节码运行时；传统 JRE 在 JVM 之上提供运行 Java 程序所需的类库与启动环境；JDK 再包含编译器等开发工具。开发时需要 JDK，运行程序需要兼容的 Java 运行时。

现代 JDK 发行版的打包方式与早期单独安装 JRE 的方式不同，不能把“JRE 一定是单独目录或独立安装包”当成现行发行规则。Android 使用 ART 执行应用字节码，不应把 JVM 发行版中的组件布局直接套到 Android。

**Q9: [learning] JVM 规范中的运行时数据区与 Java 内存模型有什么区别？**

运行时数据区描述虚拟机执行期间的内存区域及其线程共享边界，例如每线程的 PC 寄存器、Java 虚拟机栈，以及进程共享的堆和方法区；Java 内存模型（JMM）描述多线程之间共享变量的可见性、原子性与有序性规则。二者解决的问题不同，不能把“主内存/工作内存”当作 JVM 运行时区域的另一套物理内存划分。

JMM 把共享变量的访问抽象为两层：每个线程只操作自己工作内存中保存的变量副本，线程之间不直接读写对方的变量，值的传递必须经过主内存回写与刷新完成。这套抽象服务于可见性语义的定义，主内存/工作内存与堆、栈、方法区不是同一层次的划分。

程序计数器记录当前线程正在执行的虚拟机指令位置；虚拟机栈由该线程的方法调用帧组成。共享堆主要承载对象实例，但规范不要求每个逻辑区域都对应固定的操作系统内存映射。

**Q10: [learning] JVM 的主要组成部分怎样协作执行 Java 程序？**

典型 JVM 实现由类加载与链接、运行时数据区、执行引擎以及与本地代码交互的接口等部分协作：类加载器取得并准备类定义，运行时数据区承载执行状态，解释器或即时编译器执行字节码，垃圾回收器管理堆中对象。具体组件名称与实现会因虚拟机而异，JVM 规范不要求某个实现必须采用同一套内部模块划分。

现实中的常见实现是 HotSpot 与 Eclipse OpenJ9；毕昇、Corretto 等 JDK 发行版大多以 HotSpot 为内核打包。选择时应区分“规范语义”与“发行版提供的工具链、优化与支持”，不能把某个发行版的调优参数当成跨实现通则。

**Q11: Java 源文件从编译到 JVM 执行要经过什么过程？**

典型 Java 工具链先由 `javac` 把 `.java` 源码编译为 `.class` 字节码；运行时的类加载器取得类定义并完成链接与初始化，随后 JVM 解释执行字节码，或由即时编译器把热点代码编译为本机代码。操作系统再调度承载 JVM 的线程执行机器指令。

`.class` 文件中的字节码面向 JVM 规范，不等于平台机器码；类加载、解释与 JIT 的具体策略由 JVM 实现决定。Android 应用构建还会经历 DEX 与 ART 相关流程，不能直接把桌面 JVM 的运行链套用到 Android。

**Q12: [learning] 每运行一个 Java 程序就有一个 JVM 进程，Android 的 ART 也是按进程存在的吗？**

以 HotSpot 为代表的桌面 JVM 实现以独立进程形态交付：每运行一个 Java 程序，就启动一个承载该实现的进程实例，所以“JVM”无法作为一个固定窗口被打开，它随程序运行而创建。Android 的 ART 则不是独立进程，而是以运行库加执行引擎的形态嵌入每个应用进程：ART 的实现由一组 C/C++ 共享库（核心是 `libart.so`）构成，每个 App 进程都在自己的地址空间中加载它来执行字节码。

两者的差别源于交付形态不同，而不是执行语义不同：ART 执行 DEX 字节码，桌面 JVM 执行 `.class` 字节码，规范层的语义（类加载、运行时数据区语义、异常模型）在两边各有对应。讨论行为时先分清层次——问“规范怎么规定”查规范文档，问“以什么进程/库形态存在”看具体实现的部署方式。

**Q13: [learning] 为什么同一份 .class 字节码可以跨平台运行，也能运行 Kotlin、Groovy 等语言编译出的程序？**

因为 JVM 是一份只面向字节码的规范：`.class` 是它识别的输入格式，与源语言和操作系统无关。跨平台来自实现侧——各平台提供各自的 JVM 实现，同一份字节码分别由 Windows、Linux 上的实现翻译成本地指令，源码只需编译一次；语言无关来自输入侧——任何语言只要编译出合法的字节码（Kotlin、Groovy、Scala 等），JVM 不关心它由哪个编译器产生。

这条结论有两个边界。其一，规范屏蔽的是字节码之下的差异，性能与行为细节仍依实现，版本间收集器与编译策略的差异（如 CMS 的移除）就是例证。其二，Android 不在此链路上：ART 执行的是 DEX 字节码，桌面 `.class` 不能直接运行在 Android 上，构建时须经 d8/dx 转换，不能把“一次编译到处运行”直接延伸到 Android 场景。
