# 网络分层原理与地基机制

> 通用网络协议学习资料。边界：本文回答"分层模型、DNS/TLS/TCP/IP/NAT 等协议地基机制"；Android/车机网络实现与诊断归 [../01-android/07-network/](../01-android/07-network/)。Q 序列即结构，供 atlas 同源直读。

**Q1: [learning] TCP/IP 四层模型怎样分工？一个经 TCP 承载的 HTTPS 请求从车机发往服务器时如何封装与逐跳转发？**

TCP/IP 四层模型按通信职责拆分，从上到下依次为：

1. **应用层**定义业务协议并解释应用数据的含义。
2. **传输层**提供主机间进程交付，例如 TCP 或 UDP。
3. **网际层**负责 IP 寻址与跨网转发。
4. **链路层**负责当前链路到下一跳的帧交付。

以常见的 HTTP/1.1 或 HTTP/2 over TLS over TCP 为例，数据从上向下依次被封装为 HTTP 数据、TLS 记录、TCP 段、IP 包和链路帧，接收端逐层解封装。HTTP/3 则基于 QUIC/UDP，不能套用 TCP 段这一层次。实际以太网链路上，源与目的 MAC 属于当前这一跳，路由器转发时会重建下一跳链路帧。IP 源/目的地址通常端到端保留，但 NAT 等中间机制可以改写地址。

分层有助于把故障定位到具体职责：本机没有得到链路连接，先检查链路。有链路但跨网不可达，检查 IP 地址、路由与过滤。连接可达但请求失败，再检查传输连接、TLS 和应用协议。这个模型用于归纳协议职责，不表示每个真实协议栈都严格按教科书边界实现。

**Q2: [learning] DNS 的根、顶级、权威服务器各干什么？递归和迭代差在哪？**

典型解析由本地递归解析器代替客户端查询，逐级取得记录或下一步线索：

1. **根服务器**返回负责相应顶级域的服务器信息，例如 `.com` 的服务器。
2. **顶级域服务器**返回负责目标域名的权威服务器信息。
3. **权威服务器**返回目标域名的最终记录。

客户端向递归解析器提出“替我查到结果”是递归请求。递归解析器向根、顶级域和权威服务器逐级询问、每次取得下一步线索，是迭代查询。根和顶级域主要提供委派信息，日常排查通常先确认客户端配置、递归解析器缓存与权威记录。根或顶级域故障并非不可能，但一般属于更大范围的解析故障。

递归解析器会按记录的 TTL 缓存结果，因此权威记录更新后，客户端在缓存过期前仍可能得到旧值。排查应依次确认客户端实际使用的解析器、缓存答案与 TTL、权威服务器当前答案。若权威答案本身错误，应修正权威 DNS 配置，若只有递归答案过期，则需等待缓存失效或确认解析器刷新策略。DNS 层级划分是职责模型，具体缓存还可能存在于操作系统、应用或网络设备中。

**Q3: [learning] TLS 握手如何验证服务器并协商密钥？TLS 1.2 与 1.3 的往返次数和 0-RTT 有何差异？**

TLS 握手验证服务端身份、协商双方支持的密码参数，并建立后续保护记录层数据的会话密钥。完整 TLS 1.2 握手常需要两个网络往返：客户端发起协商，服务端返回选择结果和密钥交换材料，客户端再发送密钥交换与 Finished，服务端 Finished 后握手完成。TLS 1.3 将常规完整握手缩为一个往返：ClientHello 已携带密钥共享参数，服务端在 ServerHello 中选定参数并继续发送加密握手消息，客户端验证服务端证书与 Finished 后发送自己的 Finished。具体握手消息会随密码套件、客户端认证和恢复方式变化。

握手排查应区分两类失败：

1. **身份验证失败**：检查证书链信任、有效期、主机名及客户端本地时间。
2. **协商失败**：检查双方支持的协议版本、密码套件及密钥组。

会话恢复与完整握手不同：TLS 1.2 可借 session ID 或 session ticket 恢复会话，TLS 1.3 可使用预共享密钥恢复。TLS 1.3 的 0-RTT 还允许客户端在恢复时提前发送应用数据以减少等待，但早期数据可能被重放，服务端应只允许对重放无害的操作使用，不能用于不可安全重试的非幂等请求。握手失败要结合失败发生的消息阶段和告警原因定位，不能仅凭“连不上”推断为证书错误。

**Q4: [learning] TCP 三次握手和连接关闭时，ss 中的状态各表示什么？状态堆积能说明哪些问题？**

握手时主动连接方发送 SYN 后进入 `SYN_SENT`。被动监听方收到 SYN 并回复 SYN+ACK 后为 `SYN_RCVD`。主动方回复 ACK 后双方进入 `ESTABLISHED`。三次交换让双方分别确认本方发送方向和接收方向可用，并同步初始序列号。

关闭时每个传输方向独立结束，因此常见正常流程包含四个控制段：主动关闭方发 FIN 后进入 `FIN_WAIT_1`，收到对端 ACK 后进入 `FIN_WAIT_2`。被动方收到 FIN 后进入 `CLOSE_WAIT`，应用关闭本端后发 FIN 并进入 `LAST_ACK`。主动方收到 FIN 并确认后进入 `TIME_WAIT`，等待一段时间以处理重传报文并避免旧报文干扰新连接。经典模型以 2MSL 作为 TIME_WAIT 等待时长，具体系统的计时实现可能不同。若对端在 FIN 到达时已无数据待发，ACK 与 FIN 可合并在一个段中，所以抓包不保证总看到四个分离段。

解释 `ss` 状态应结合角色、持续时间和流量判断：

1. `SYN_SENT` 持续增长表示连接建立没有得到回应，可能涉及路由、过滤、对端不可达或服务无响应。
2. `SYN_RECV` 堆积可能与半开连接洪泛或返回路径异常有关。
3. 长期 `CLOSE_WAIT`表示本地应用已收到对端关闭，但本地套接字仍未关闭，应检查应用持有路径或有意保留连接的逻辑。
4. 大量 `TIME_WAIT`常见于主动短连接方，是否有问题取决于连接速率、端口资源和持续时间。

状态本身是线索，不足以单独确定根因。

**Q5: [learning] IP 包超过链路 MTU 时怎样分片？为什么应优先用路径 MTU 与传输层分段避免依赖分片？**

链路 MTU 限制单帧可承载的数据量。以太网常见 MTU 是 1500 字节，但隧道封装等会进一步降低路径 MTU。IPv4 包超过下一跳 MTU 且允许分片时，可由发送端或路由器拆成片段，目的端必须收齐全部片段才能重组原包。任一片丢失都会使整个 IP 数据报不可用。IPv6 路由器不会替发送端分片，过大的包由路径上的设备返回 Packet Too Big，发送端据此调整。

优先避免依赖分片，是因为分片会增加重组缓存和状态管理，任一片丢失都导致整包失败，且部分防火墙或 NAT 对非首片处理不一致。TCP 通常依据路径 MTU 与 TCP/IP 头部开销选择 MSS，把数据分成可发送的 TCP 段。UDP 应用需控制数据报大小，或自行设计分块与重传。路径 MTU 发现若被过滤 ICMP 错误报文，会形成 PMTU 黑洞，因此仍须验证探测路径。跨未知网络的隧道和私有协议应留出封装开销并设定可协商的报文上限，而不能把 IP 分片当作可靠兜底。

**Q6: [learning] NAT 到底改了包的什么？conntrack 在其中扮演什么角色？**

NAT 根据规则改写包中的网络层地址，有些类型还会改写传输层端口。连接跟踪（conntrack）保存原始流与转换后流的对应关系，使回包能够反向改写并送回内网端点。共享公网地址时，端口转换让多个内网连接复用同一地址。

在常见的状态型源 NAT 中，内网主动发起的流量会建立映射，外部主动发起连接则通常没有既有映射，需要端口映射、显式防火墙规则或穿透机制。映射会因空闲超时而老化，应用长时间静默时可能需要探活或重建。公网端口资源耗尽也会阻止新会话。应用层网关可能解析并改写其理解的协议载荷，因此会影响端到端加密与协议兼容。NAT 的行为取决于设备实现和规则，conntrack 表只能说明设备当前记录了什么，不能保证端到端服务可达。

**Q7: [learning] 打开 HTTPS 网页时，网络请求经历哪些阶段？各阶段的延迟应怎样定位？**

一次典型请求依次经历域名解析、TCP 建连、TLS 握手、HTTP 请求/响应和把响应交给浏览器或 WebView。每段可能被复用或跳过：DNS 可能命中缓存，已有连接可能复用而不重新握手，HTTP 缓存也可能直接满足请求。需要重新验证的缓存内容可通过条件请求让服务端返回 `304 Not Modified`，避免再次传输完整实体。因此应先根据实际网络记录确认发生了哪些阶段，再解释耗时。

按阶段分段定位：

1. **DNS**：确认客户端使用的解析器、缓存状态与查询耗时。
2. **TCP 建连**：检查往返时延、丢包和服务端监听状态。
3. **TLS 握手**：检查证书校验、密码参数协商与握手往返。
4. **首字节等待**：请求发出后到首字节之间的时间包含服务端处理及中间代理。
5. **响应下载**：结合响应大小、吞吐和拥塞判断。

浏览器/WebView 的解析和绘制属于渲染阶段，不能从网络计时直接推断。车载多 APN 环境还需确认 DNS 查询与 TCP 流量是否使用预期网络接口，否则相同 URL 可能走不同出口。

**Q8: [learning] 链路、IP、传输层和 TLS 的校验分别保护什么？为什么 TLS 之后仍可能需要应用层校验？**

这些校验针对不同范围和威胁：

1. **链路校验**：以太网帧尾部的 FCS 用 CRC 检测本链路传输中的偶发错误，检测失败的帧通常由接收接口丢弃。它不提供密码学防伪造能力。
2. **IP 头校验**：IPv4 首部校验和只检查 IPv4 首部，不覆盖负载。IPv6 没有 IP 首部校验和。
3. **TCP/UDP 校验和**：覆盖伪首部、传输层首部和数据，用于发现传输错误，不具备抗主动篡改的密码学强度。中间设备可能按改写后的包重新计算校验和。
4. **TLS 记录保护**：经过证书与握手验证后，AEAD 等机制保护 TLS 连接两端之间记录的机密性与完整性。它不证明业务数据本身正确，也不替代应用对操作权限、版本和业务约束的检查。

因此，链路与传输校验主要处理偶发错误，TLS 保护传输通道免受窃听和主动篡改。应用层仍可对关键对象做签名、哈希或业务约束校验，以验证数据来源、持久化完整性或语义一致性。应按威胁模型选校验，不能把 CRC 或 TCP 校验和当作身份认证。

**Q9: [learning] 计算机网络由哪些部分构成？它提供的两类基础能力是什么？**

计算机网络把能够独立运行的计算系统通过通信设备、链路和协议连接起来，由主机与转发设备、通信链路及约定数据交换方式的协议共同构成。网络提供两类基础能力：

1. **数据通信**：让分布在不同位置的系统交换数据。边缘系统运行应用并发起端到端通信，核心网络由链路和转发设备组成，为这些通信提供承载。
2. **资源共享**：使系统能够访问远端计算、存储、服务或数据资源。分布式处理是借助网络实现的应用协作方式，不应和网络自身提供的基础通信能力混为一谈。

**Q10: [learning] 网络常见分类按什么维度划分？局域网、专用网和分组交换能否互相替代？**

网络分类依观察属性不同而不同，一个网络可以同时拥有多个分类标签：

1. **覆盖范围**：个人区域网、局域网、城域网和广域网描述覆盖尺度。
2. **使用授权**：公用网和专用网描述谁可使用，因此一个网络可以既是局域网又是专用网。
3. **交换方式**：电路交换、报文交换和分组交换描述数据转发方式。
4. **拓扑结构**：总线、星形、环形和网状描述节点间连接形态。
5. **信道共享方式**：广播式与点到点描述节点如何共享或占用通信链路。

这些维度彼此独立，不能用“局域网”推断它采用哪种交换方式，也不能把“专用网”等同于某种物理拓扑。

**Q11: [learning] 网络协议、服务和接口分别描述什么，为什么网络需要分层？**

三个概念可按描述对象区分：

1. **协议**规定对等层实体如何交换数据，通常包含报文语法、字段语义和发送时序等规则。
2. **服务**描述某一层向相邻上层提供什么能力以及可观察到的行为。
3. **接口**是上层调用或访问该服务的边界。

分层把复杂通信拆成职责明确的部分，使每层能够通过稳定接口使用下层服务，并在不改变其他层实现的前提下演进。

OSI 参考模型强调服务、接口与协议的区分。实际互联网主要运行 TCP/IP 协议族。模型是理解职责的抽象，不保证每个协议都严格落在唯一一层，也不意味着实际实现必须和教科书分层一一对应。

**Q12: [learning] RFC 文档系列、正式标准和法定标准之间是什么关系？**

RFC 是 IETF 发布文档的编号系列，文档可记录协议规范、最佳实践、信息说明或实验性工作。RFC 编号不代表该文档已经成为互联网标准，也不自动意味着法律上的强制要求。应查文档状态、规范性用语和后续更新或废弃关系。IETF 的标准轨道文档可能按流程成为互联网标准，但“RFC”与“标准”不是同义词。

正式标准或法定标准强调由认可的标准组织依据正式程序形成规范。事实标准则主要因广泛部署而被实际采用。它们描述标准的形成和认可方式，与 RFC 文档系列并非互斥分类。判断一项规范的约束力时，应区分技术状态、组织认可和所在司法或合同环境的效力。

**Q13: [learning] 速率、带宽、吞吐量和时延怎样区分？**

这些指标描述不同对象，比较时必须写清单位、测量范围和统计口径：

1. **速率**是单位时间传送的比特数，通常以 bit/s 表示。
2. **带宽**在通信工程中指频率范围。网络语境常借指链路可承载的数据率，需根据上下文辨明。
3. **吞吐量**是实际单位时间成功通过某接口或路径的数据量，受链路能力、协议开销、拥塞和端系统处理能力影响。
4. **时延**是数据从一个观测点到另一个观测点所需时间，端到端时延通常包含发送、传播、排队和处理时延。

发送时延约等于数据长度除以发送速率。传播时延由链路长度与信号传播速度决定。提高链路速率会缩短发送时延，却不会自动缩短传播时延。评估性能时要注明测量位置、方向、负载与统计区间，不能把标称带宽当作实际吞吐量或端到端时延。

**Q14: [learning] MAC 地址是什么，在以太网通信中标识什么？**

MAC 地址是链路层网络接口使用的地址，用于本地链路帧的发送与接收。以太网帧包含源和目的 MAC 地址。它解决同一链路上的帧交付，不负责跨网段路由，跨网段转发要由 IP 层与下一跳链路地址协作完成。

不要把 MAC 地址理解成全球范围永久不变的设备身份：现代系统可能使用随机化地址，虚拟接口也有自己的链路层地址。地址的具体管理与分配规则取决于接口类型和系统策略。
