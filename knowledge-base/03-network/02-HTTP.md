# HTTP 缓存与传输

本册解释 HTTP 响应如何复用、HTTP/2 如何复用与限制流，以及 HTTP/3 使用 QUIC 后在传输层发生的变化。Android 客户端的配置与排查见 [应用网络约束](../01-android/09-network/04-应用网络约束.md)与[应用网络实践](../01-android/09-network/09-应用网络实践.md)。

**Q1: [learning] HTTP 缓存怎样判断新鲜度、验证响应和匹配变体？**

缓存先按请求方法和目标 URI 查找条目，再按 Vary 检查请求头是否匹配缓存的表示。新鲜响应通常可直接复用。陈旧响应可向源站发起条件请求，收到 304 时复用已有响应体，并按规则更新缓存字段。

1. **存储和共享。** 对响应使用 no-store 要求缓存不存储该次请求或响应。private 允许私有缓存按规则存储，限制 CDN（Content Delivery Network）和代理等共享缓存。它们不能替代传输加密、鉴权或账号隔离。
2. **新鲜度。** 响应的 no-cache 允许存储，但每次复用前须成功验证。max-age 优先于 Expires，s-maxage 优先规定共享缓存的新鲜期。当前年龄涉及 Date、Age、传输延迟及本地驻留时间。
3. **验证器。** 用 If-None-Match 发送缓存的 ETag，或用 If-Modified-Since 发送 Last-Modified，同时存在时遵循协议的求值顺序。304 传回元数据而无需再次发送内容，缓存会合并可更新的元数据。
4. **变体。** 服务端按 Accept-Encoding 返回不同表示时，发送 Vary: Accept-Encoding 供缓存匹配请求。语言或其他参与表示选择的请求头也应纳入变体。Vary: * 不能用现有请求头值判断是否匹配已有变体。

依据为 RFC 9110 与 RFC 9111。

**Q2: [learning] HTTP/2 怎样在同一连接复用多个请求，什么情况仍会阻塞？**

HTTP/2 把请求与响应编码为二进制帧。每个流有独立标识，不同流的帧可以在同一连接上交错发送。HPACK 用静态表与动态表压缩重复首部，HTTPS 通常通过 ALPN（Application-Layer Protocol Negotiation）协商 h2。

1. **减少应用层排队。** 一个慢响应等待服务端或暂时没有数据时，其他流仍可使用这条连接，多个请求也可共享握手成本。域名分片会增加解析与握手，跨域连接合并须满足路由与证书等来源校验。
2. **仍受 TCP 顺序约束。** TCP 只有一条有序字节流。缺失的 TCP 段未补齐时，接收方交付不了缺口后的数据，导致该连接上本可并行的多个流等待。多条 HTTP/1.1 连接可隔离这类等待，但需要更多握手和连接资源。
3. **按业务场景验证。** 高丢包时分别测试单条 HTTP/2 连接、多条连接或 HTTP/3，比较 P95/P99、失败率和连接成本，避免只根据协议名称推断弱网收益。

依据为 RFC 9113 与 RFC 7541。

**Q3: [learning] HTTP/2 为什么同时需要流级和连接级流量控制？**

HTTP/2 在每个方向同时为单个流和整条连接维护窗口。发送 DATA 帧时，两级窗口都必须有足够额度，接收端通过 WINDOW_UPDATE 补充对应窗口。

1. **流级窗口。** 将单个流的未消费数据限制在一条流的预算内。长时间不读完某个响应时，接收方可停止为它补充额度，给应用消费留出时间。
2. **连接级窗口。** 约束同方向上各流合计占用的接收资源。一条大响应可以消耗共享额度，也会与其他流争用 TCP 带宽和拥塞窗口。
3. **并发流上限。** SETTINGS_MAX_CONCURRENT_STREAMS 约束可同时存在的流数量，窗口限制可发送的数据量。调大其中一项无法解除另一项的限制。排查慢请求时同时核对流数量、两级窗口、客户端任务排队及业务端是否持续读取响应。

依据为 RFC 9113。

**Q4: [learning] HTTP/3 如何借助 QUIC 改变丢包、迁移与 0-RTT 行为？**

HTTP/3 使用 QUIC 在 UDP 上实现可靠传输与分流，并将 TLS 1.3 集成到握手。QUIC（RFC 9000）用连接 ID 标识连接，在条件允许时可以验证地址或端口变更后的新路径。

1. **丢包隔离。** 每条 QUIC 流独立交付，收到且不依赖缺失数据的流可以继续供应用读取。整个路径仍共享带宽及拥塞控制，QPACK 动态表等协议状态也可能让个别流等待。
2. **路径迁移。** 连接 ID 支持在 IP 或端口变化后关联既有连接。连接须支持迁移，新路径也须通过验证。若防火墙、代理或 VPN 阻断 UDP，客户端可回退至基于 TCP 的 HTTP。迁移不会缩短 DNS、服务端处理或应用读响应体的时间。
3. **早期数据。** 会话恢复满足条件时，0-RTT（Zero Round-Trip Time）允许在握手完成前发送部分请求，服务端仍可拒绝早期数据。早期数据可能跨连接被重放，有副作用的登录、下单、支付等操作须有服务端明确允许及可验证的重放防护，无法满足时等待握手完成。

依据为 RFC 9000、RFC 9001、RFC 9114 与 RFC 9204。
