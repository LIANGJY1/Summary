# 内存性能：增长归因、低内存影响与抖动诊断

> 学习资料（文章模式沉淀）。主线：先按内存域分离指标，再用对应工具把增长归因到持有者，并回答低内存、内存抖动与图形内存在性能上的影响与诊断方法。源文档：android-internals-wiki 第 10 章《内存性能》§10.1–§10.4；机制按本地 AAOS13 源码（Android 13）核对，与材料 Android 17 语境的差异已标注（libmemevents、MemoryLimiter、分代 CMC、TRIM_MEMORY_RUNNING_* 停投与 ProfilingTrigger 为 Android 14–17 能力）；getProcessMemoryInfo 自 Android Q 起仅返回调用 UID 进程并限频缓存已与官方文档核对。内存口径、lmkd 选择策略与 Freezer 的机制层见 [../memory/01-内存管理与压力治理.md](../05-memory/01-内存管理与压力治理.md)；低内存拖慢前台与 ANR 的联合取证见 [./03-ANR.md](./03-ANR.md)。Q 序列即结构，供 atlas 同源直读。

**Q1: Debug.MemoryInfo 的 App Summary 口径是什么？为什么 getProcessMemoryInfo() 不能高频调用？**

App Summary 是 dumpsys meminfo 的应用摘要口径：Debug.MemoryInfo.getMemoryStats() 返回 summary.java-heap、summary.native-heap、summary.graphics 等键（AAOS13 Debug.java 核对），getTotalPss() 包含按比例分摊的已换出页（SwapPss），getTotalUss() 由各域 Private Clean 与 Private Dirty 相加。getMemoryClass() 返回 MB 为单位的 ART 托管堆近似预算，与 PSS 之间没有可计算的使用率。

getProcessMemoryInfo() 只面向调试或进程管理 UI：官方文档明确 Android Q 起普通应用只返回调用 UID 进程的信息（其余为 0），且采样被显著限频——调用快于限频会返回上一次的数据；AAOS13 AMS 实现为按 MEMORY_INFO_THROTTLE_TIME 节流加缓存。因此它适合放在实验步骤边界或低频诊断任务中，不能放进每帧回调、紧循环或高频定时器；更短的采样周期未必产生新数据。

**Q2: heap dump 的 Shallow Size、Retained Size、GC Root path 各回答什么？怎样做一次可复现的泄漏检查？**

三个概念分工明确：Shallow Size 是对象自身在托管堆占用的字节（受对象头、对齐、压缩引用影响，不能按字段数硬算）；Retained Size 是该对象不可达后预计可一并回收的受支配对象总量；GC Root path 是对象通向 GC Root（活跃线程、JNI global reference、类对象等）的引用链。泄漏归因靠后两者，单看 Shallow 会把图片这类像素在 native 堆的对象严重低估。

可复现检查按序执行：固定初始页面与进程状态；执行同一生命周期动作多轮；等待异步任务与动画结束；采集 heap dump；查找应已销毁的 Activity、Fragment View、listener 或缓存条目；沿 GC Root path 找生命周期更长的持有者；修复后重复同一脚本比较实例数与保留图。单个实例存活不一定是泄漏，系统、输入法、动画可能短期持有；证据要同时满足"越过预期生命周期"与"稳定引用链"。缓存、积压与泄漏用释放动作后的回落区分：关闭页面或裁剪缓存后仍不降的，才是持有问题。

**Q3: heapprofd 能回答什么、不能回答什么？**

能回答 native 分配的来源：Android 10+ 起 heapprofd 以抽样方式跟踪 malloc/free、new/delete，用四个视图回答"采集窗口内已分配未释放的字节与次数"（Unreleased malloc size/count，分析泄漏用）和"窗口内全部分配的字节与次数"（Total，含已释放，分析 churn 用）；user build 只能分析 manifest 声明为 profileable 或 debuggable 的应用（Perfetto 官方文档口径；本地 AAOS13 树未含 perfetto 源码，此条按官方文档转写）。

不能回答的同样重要：无法回溯采集开始前的历史分配；默认看不到绕过默认分配器的直接 mmap、graphics buffer 与 GPU private allocation；采样间隔、缓冲溢出与符号化质量都会影响结果。以进程名启动时，已运行与后续启动的匹配进程都可进入采样，需要启动期证据应先启动 profiler 再启动应用。

**Q4: "Native Heap RSS 减 heapprofd unreleased 等于碎片"为什么不成立？**

因为三个数字的范围逐步扩大，不是同一口径的差值关系。heapprofd 记录的是采样到的 malloc/new 请求与 free；malloc_info 与 allocator 统计覆盖分配器管理的 arena、cache 与仍持有的页面；Native Heap RSS/PSS 是已驻留页，还受 page size、共享、swap 与采样时刻影响。

差值可能来自：未采样到的分配、采集开始前的历史分配、allocator cache、对齐与页内空洞、直接 mmap、统计分类差异、ZRAM 换出，以及两个工具没有同时采样——没有任何一项可以直接命名为"碎片"。判断碎片的正确路径是：先确认 live allocation（未释放分配）确实已下降，再看 allocator 统计与 smaps 匿名驻留页是否同步回落；RSS 滞后回落本身不能单独命名泄漏或碎片。

**Q5: Java OOM 的崩溃点栈为什么回答不了"内存被谁占用"？线上 Hprof 方案的关键环节是什么？**

OOM 栈只记录本次分配失败的位置（Bitmap、字符串构造、数组扩容），而此前的堆可能早被长期存活对象占满——失败点和占用者通常不是同一批对象。线上 Hprof 方案把分析对象从崩溃点转向持有关系：在 OOM 或高水位时采集 Hprof（用子进程减轻对交互线程的影响）；裁剪工具在 native 层移除字符串内容与 Bitmap 像素（该产品样本平均从 355 MB 降到 44 MB）；服务端重建引用图与支配树，按类聚合 Shallow/Retained/GC Root；混淆类名经 Retrace 还原后分派 owner。公开数字是该平台客户在特定周期的结果，不能推导任意 App 的收益。

修复服从引用语义：页面退出后仍被任务、监听器持有时取消任务、解除注册；数量符合业务但 Retained 过大时减少单对象负载或限制集合容量。不要把批量 Bitmap.recycle() 写成通用修复——API 26 起像素在 native 堆，生命周期正常的 Bitmap 交给 GC 与 NativeAllocationRegistry 管理，提前回收还可能让仍在绘制的调用方访问已释放像素。Android 17 的 ProfilingTrigger.TRIGGER_TYPE_OOM 可在 OOM 时申请 Java heap dump，AAOS13 没有该 API。

**Q6: 像 renderD128 映射增长这类 GPU 驱动侧 OOM，排查方法有什么可迁移的？**

可迁移的是方法而非结论。第一步按设备型号、SoC、GPU、OS、驱动与 ABI 聚类，确认问题只出现在少数组合——聚类结果本身就是证据。第二步监控 /proc/self/maps 或 smaps 中对应设备节点的映射，区分虚拟地址空间耗尽与物理驻留增长（32 位进程更容易被地址空间卡死）。第三步用稳定触发实验锁定入口：该案例中常规 mmap/mremap hook 无记录，反汇编发现 vendor 用户态库绕过 libc 直接调用 syscall（mmap2），只拦截 vendor 库与 gralloc 的 syscall 才抓到映射；调用栈指向 buffer pool 长期保留——阈值 50 时映射峰值约 1.25 GB，调到 20 约 530 MB、10 约 269 MB，修复交给厂商后受影响机型 OOM 崩溃率下降近 50%。

这些都是特定设备、驱动与复现工程的数据，不能外推；错误 hook 私有函数可能破坏正在使用的 GPU 资源。推进 64 位可缓解地址空间耗尽但不减少物理内存成本。材料按 Android 17 核对的 HWUI 规则（alpha 位于 (0,1) 且节点报告重叠绘制时提升为独立 layer）能解释 alpha 触发路径，但不能证明该 pool 行为延续到新版本。

**Q7: 低内存的性能损失为什么没有固定顺序？不同页面的回收成本差在哪？**

分配遇到压力后走哪条路径由页类型与设备配置决定，各路径消耗的资源不同：clean file page 直接丢弃，再访问时 refault 需重新读文件；dirty file page 先回写，付出写入延迟与存储竞争；匿名页换入 ZRAM，付出压缩与解压 CPU 及 swap-in 延迟；高阶连续页需求可能触发 compaction 后重试；线程自身可能同步进入 direct reclaim，直接占用它的执行时间。

两条常见误判要避开：direct reclaim 不一定产生存储 I/O（clean 页可丢弃、匿名页常见配置进 ZRAM），"回收等于读盘"不成立；主线程处于 D 状态也不等于在等回收，要用 direct reclaim 事件或内核调用栈证明它在等什么。分析时把 vmscan、block I/O、refault 与线程状态放在同一段 trace 里核对先后与因果。

**Q8: LowMemDetector 和 lmkd 都消费 PSI，它们的分工是什么？**

lmkd 在内存压力下选择并终止进程（选择策略与 oom_score_adj 见 [../memory/01-内存管理与压力治理.md](../05-memory/01-内存管理与压力治理.md)）；LowMemDetector 是 system_server 内的另一条路径，只做状态管理不杀进程：native 层注册三个 PSI monitor，Java 线程经 epoll 等等级变化，把压力等级提供给 ActivityManager 作为 memory factor 与进程统计调整的输入。AAOS13 LowMemDetector.cpp 的三个 monitor 为：LOW 用 PSI_SOME（1 秒窗口内 15 ms）、MEDIUM 用 PSI_FULL（30 ms）、HIGH 用 PSI_FULL（50 ms）——与材料按 Android 17 核对的数值一致。

两个消费者各持一个监听 fd 不表示 PSI 被重复计算；这些阈值是 framework 常量，OEM 分支可能不同，不能直接当作所有设备的性能阈值。

**Q9: lmkd kill 之后的性能损失怎么量化？**

cached process 被终止后内存立即可用，但用户再次进入该 App 时，warm/hot resume 变成 cold start：创建进程、加载代码与资源、初始化 Application 与 ContentProvider、恢复业务状态；代价取决于包体、I/O、编译状态和当时的系统压力，没有固定毫秒数可以概括。

评估关联五项证据：lmkd kill 的时间与原因；用户返回该 App 的时间间隔；温启动变冷启动的比例；冷启动的 CPU、I/O、首帧与状态恢复耗时；同一进程是否在短时间内反复启动退出——反复的终止与重启说明回收没有净收益，反而延长了压力窗口。App 侧用 ApplicationExitInfo 识别低内存退出（REASON_LOW_MEMORY；部分设备不支持精确报告，先查 isLowMemoryKillReportSupported()），不能只用末条内存曲线反推死因。

**Q10: 全局内存压力会直接改变前台应用的 GC 行为吗？**

公开机制上不会：ART GC 的频率由应用自身的分配速率、live set、堆目标、收集器与进程状态决定，没有"PSI 升高后前台切换到更重 GC"的规则。可能同时出现的现象要分别归因，判定分支是：GC slice 变密而 PSI、vmscan、kswapd 平稳，问题更可能来自应用 churn；PSI 与 direct reclaim 上升而 GC 不变，瓶颈在系统回收或 I/O；两组信号重叠时，再检查 CPU 竞争与分配线程调用栈。

两个相邻概念也要分开：kswapd、ZRAM、compaction 消耗 CPU 会挤压 GC 并发线程的调度时间；cached process 被 framework compact（压减驻留）或 freeze（暂停调度）属于进程驻留优化，不等同于 ART 的 Java heap GC。GC 与掉帧的重叠判定（暂停、等待、CPU 竞争四类时间）见 [../memory/01-内存管理与压力治理.md](../05-memory/01-内存管理与压力治理.md)。

**Q11: 低内存拖慢冷启动的证据链怎么建？以 682 ms 与 624 ms 的对比案例说明。**

先分线程状态再谈代码：两个样本主线程 Running 时间接近（低内存 682 ms、正常 624 ms），差距集中在不可中断睡眠——低内存样本的 Block I/O 唤醒前等待与普通不可中断睡眠合计约 750 ms，正常样本约 130 ms；单看总启动耗时很容易误归因到主线程代码。

完整链条四步：在 Perfetto 圈出启动区间，比较主线程 Running、Runnable、Sleeping 与 D 状态占比；展开 D 状态对应的内核调用栈，确认等待文件页、块设备还是文件系统锁；同一时间窗核对 kswapd0、回收 tracepoint、meminfo/vmstat、swap/ZRAM 与 PSI；核对 lmkd 与 ActivityManager 事件，确认进程是否反复被终止又重启。该案例支持"内存水位低、文件页回收活跃、启动缺页等待存储"的因果，但单次 trace 的同核现象不足以证明调度缺陷。原文调高 extra_free_kbytes 的历史建议不能直接迁移到新产品；修复验收以同场景 A/B 的 PSI、direct reclaim、kswapd CPU 与启动耗时为准，没有量化结果的案例不要补写修复收益。

**Q12: ZRAM、MGLRU 和回收事件观测有哪些设备与版本边界？**

ZRAM 评估要成对比较：pswpin/pswpout、ZRAM 占用与压缩效率，memory PSI、direct reclaim 与 kswapd 时间，swap-in 后的启动与切换延迟，压缩线程 CPU 与功耗，lmkd kill 与缓存进程存活；只提高压缩比可能增加 CPU，只加容量可能挤占未压缩内存。page-cluster 控制一次换入预读的相邻页数，16 KB 页设备上同一值覆盖更大字节范围；配置节点是否可用取决于内核，评估指标（mm_stat 口径）见 [../memory/01-内存管理与压力治理.md](../05-memory/01-内存管理与压力治理.md)。

MGLRU 用 generation 记录页面热度，是否启用要读 /sys/kernel/mm/lru_gen/enabled 并核对设备配置，评估看 refault、scan/steal、direct reclaim、PSI 与冷启动回访；generation 的 bitmask 随内核版本变化，不当作常量。回收事件观测的版本边界：材料按 Android 17 核对 lmkd 优先用 BPF 库 libmemevents 订阅回收事件、失败回退 vmstat，并已删除旧版 Perfetto 的 mm_events 常驻 probe；AAOS13 树的 system/memory/libmeminfo 中没有 libmemevents，lmkd 通过轮询 vmstat 获取回收状态——具体设备以镜像为准，不把某一版的观测设施写成平台通用结论。

**Q13: 内存抖动、泄漏、缓存增长在曲线上怎么区分？**

看同一脚本下曲线形态与释放动作后的回落，四类形态对应不同证据：抖动是分配速率高、GC 后大幅回落、基线稳定，查分配调用栈与 GC/慢帧重叠；泄漏是多轮 GC 后存活基线持续上升，查 heap dump、Retained Size 与 GC Root；缓存或对象池是上升到容量上限后封顶，核对容量、命中率与逐出记录；大对象突发是单次或少数分配拉高曲线，查分配大小、调用栈与业务事件。

两条克制规则：锯齿形只是线索，若每次 GC 后基线也在上升，要同时排查存活对象；分配很高但帧时间、CPU 和 GC 等待没有退化时，优化优先级可以后移。一次快照不能证明泄漏，一次 GC 也不能证明资源已释放；验证优化要用同一脚本、同设备、同构建复测分配、GC、帧时间与正确性。

**Q14: TLAB 让分配很快，为什么高频分配仍然会拖慢帧？**

TLAB（线程本地分配缓冲区）只优化分配动作本身：线程在私有缓冲区内推进指针、避免堆全局锁。之后的成本仍然存在：缓冲区用尽需要补充空间；每次分配增加标记、扫描与回收工作量；活对象越多收集器要处理的引用越多；大对象或突发分配容易离开最轻的分配路径；回收线程消耗 CPU 与内存带宽，与 UI 线程、RenderThread 竞争；可分配空间不足时，发起分配的线程要等待 GC 完成——这个等待往往比单次 GC 暂停更长。

从帧预算看：120 Hz 一帧约 8.33 ms，GC 暂停、分配等待或 CPU 竞争只要与已接近预算的帧重叠，就可能产生 missed frame。没有"某类 GC 固定耗时几毫秒"的跨设备常量，判定靠 trace 中分配、GC slice 与 FrameTimeline 的对齐，而不是暂停时长直方图。AAOS13 的收集器是并发复制 CC（支持分代），材料按 Android 17 核对的 CMC 及分代 CMC 在 AAOS13 源码中不存在，但这不改变"高频分配仍有后续成本"的结论。

**Q15: 常见的 Java 分配热点有哪些？各自怎么证实和修？**

证实一律用 allocation profile 的调用栈，不按代码外观猜。逐帧回调（onDraw、动画、触摸）里创建 Paint、Path、Rect、临时集合：把可复用的绘制状态移到 View 成员并在构造期创建，帧回调只更新字段。循环内创建集合、正则、格式化器或中间 DTO：容器移出循环并用 clear() 复用、给已知规模设置初始容量；复用前确认容器引用不会被异步任务或返回值保存，否则引入并发错误。字符串拼接 result += item 与日志参数求值：用 buildString 合并、在调用点判断日志级别或用接收 lambda 的延迟日志 API，确保禁用时不构造文本。

装箱与容器：已证实的热点可把 HashMap<Int, T> 换 SparseArray、密集数值计算换 IntArray/LongArray——SparseArray 用排序数组省去 key 装箱，但查找与插入特征和哈希表不同，按 benchmark 决定而不是按元素数量定统一切换点；Kotlin 的 @JvmInline value class 只在直接参数与局部变量路径避免包装，泛型、接口、可空场景仍会装箱。大 buffer 与图像：固定数量轮转、按目标尺寸解码、分块处理、遵守库的 buffer pool 所有权；API 26 起 Bitmap 像素在 native 堆，库管理的对象归还库的池，不要在未知调用方仍可能使用时提前 recycle()。

**Q16: Java/Kotlin 分配和 GC 在开发期与线上怎么观测？能复制 BinderInternal.GcWatcher 吗？**

开发期两条工具链：Android Studio 的 Java/Kotlin allocations 记录（提供 sampled 模式降低对高分配应用的影响），分析 churn 按窗口内累计次数与字节排序、分析泄漏按结束时仍存活的数量与引用排序——两个问题不用同一排序口径；Perfetto heapprofd 自 Android 12 起可指定 --heaps com.android.art 记录 Java 分配调用栈。注意 ART allocation profile 只记对象创建位置，不提供删除时间或引用图，存活关系仍需 heap dump；Total 包含已回收对象，不能当存活堆大小。

线上只保留经过开销评估的场景指标。不要复制 BinderInternal.GcWatcher（framework 隐藏 API，AAOS13 中仍靠 WeakReference 与 finalize 感知 GC）：finalization 的执行时间没有确定性，不能当每次 GC 的精确通知，更不能当线上 GC 计数器。System.gc() 只发出 GC 请求，不保证立即执行也不消除分配源，测试工具可用，产品代码靠修正分配速率与生命周期。

**Q17: Compose 的内存抖动怎么治理？remember、strong skipping、derivedStateOf 各解决什么？**

Compose 结构本身占内存，但更常见的 churn 来自重组期重复执行的构造代码与不稳定的参数身份。跨重组保存的对象用 remember(keys) 缓存，key 要精确描述失效时机：key 过频变化缓存反复失效，缺 key 会读到与新输入不匹配的旧对象；remember 延长对象在组合中的存活，不适合缓存无限增长的数据。

strong skipping（Kotlin 2.0.20 起默认启用）让参数未变的 restartable composable 可跳过，并编译器记忆捕获不稳定对象的 lambda；不要为跳过重组随意加 @Stable——它是一份行为契约，公开属性变化必须可感知，标注错误会让 UI 漏掉更新，应先用编译器报告核对稳定性推断。derivedStateOf 适合输入变化频率高、输出变化频率低的场景（如滚动位置持续变化、按钮只关心是否在顶部）；两个输入每次变化都要更新结果时直接计算更简单。计数器等状态用 mutableIntStateOf、mutableLongStateOf 等原始类型 API 减少 JVM 路径上的装箱。Compose 经 AndroidX 发布、不与 platform API 绑定，库版本边界不能推断为 Android 17 设备的专属运行时行为。

**Q18: 为什么图形内存没有一个统一数字？四类工具各回答什么、为什么不能相加？**

因为同一资源在不同工具里是不同视角，且互相重叠。dumpsys meminfo 给进程的 smaps 分类与 memtrack 补充归因；dumpsys gpu --gpumem 给驱动上报的 GPU 可寻址总量（全局与按 PID）；/proc/PID/fdinfo 与 /sys/kernel/dmabuf/buffers 描述 DMA-BUF 的持有与唯一实体；Perfetto android.gpu.memory 给随时间变化的 counter 序列。一张逻辑图片可能同时存在于软件像素、GPU 纹理缓存或 HARDWARE 位图中；一个 Java 对象可能没有独立底层分配，多个对象也可能共享同一 DMA-BUF。

不能相加的原因：同一 DMA-BUF 被多个进程和 GPU 引用时，各进程 GPU 总量之和可能大于唯一物理容量；memtrack 按 PSS 规则分摊共享并排除类型间重叠，与 gpu_mem_total 的目标不同。排查图形内存增长时，先为数字写清四项限定——采集接口、设备与系统 build、被归因的进程、资源是否共享；离开限定，"Graphics = 120 MB"既说不出物理内存有多少，也证明不了泄漏。

**Q19: dumpsys meminfo 的 Graphics 摘要由什么组成？Graphics 为 0 说明没有 GPU 内存吗？**

App Summary 的 Graphics 是三项 private memory 相加（AAOS13 Debug.MemoryInfo 的 summary.graphics 口径核对）：Gfx dev（smaps 识别的图形设备映射）、EGL mtrack（memtrack GRAPHICS 中尚未被 smaps 统计的部分）、GL mtrack（memtrack GL 中未统计的部分）。详细表中还可能出现 Other mtrack（来自 memtrack 的 MULTIMEDIA、CAMERA、OTHER 分类），它不属于 App Summary 的 Graphics 项。

memtrack 是厂商 HAL 提供的设备内存记账接口，通过 SMAPS_UNACCOUNTED 标志只报告 smaps 没有计入的部分，避免重复记账；接口契约按材料与官方口径转写（本地 AAOS13 树未包含 memtrack 接口目录）。由此得到判断规则：HAL 缺项或不支持某类型时对应行为 0 或缺失——Graphics 为 0 不能断言进程没有 GPU 资源；Graphics 上升也不能只从 Java heap dump 找 owner，Surface、TextureView、ImageReader、MediaCodec、Camera 与 Vulkan 的 buffer 生命周期各自独立。

**Q20: dumpsys gpu --gpumem 和 Perfetto 的 android.gpu.memory 怎么配合使用？**

它们是同一条数据链的两段。GPU 驱动在分配、释放、导入、取消导入改变 GPU 可寻址总量时发出 gpu_mem/gpu_mem_total tracepoint（pid = 0 表示全局总量，正 PID 表示进程总量）；GpuService 把 BPF 程序挂到该 tracepoint，维护以 (gpu_id, pid) 为键的 BPF map（AAOS13 的 GpuMem.cpp 与 GpuMemTracer.h 核对，数据源名 android.gpu.memory）；dumpsys gpu --gpumem 读取此刻的 map 快照，GpuMemTracer 在 trace 启动时遍历 map 写入初始值，持续变化来自 ftrace 事件。

因此 Perfetto 配置要同时开两路：android.gpu.memory 提供启动基线，gpu_mem/gpu_mem_total 提供增量——只开 ftrace 会缺采集前已存在且未变化的资源，只开 android.gpu.memory 只有一份快照。解读边界：gpu_memory 是驱动上报的地址空间总量，不是 PSS；驱动没实现 tracepoint、BPF 未加载或 map 初始化失败时输出为空，0 不是有效测量。该命令适合回答"增长集中在哪个 PID"，没有分配标识、格式与调用栈，定位创建点还要靠应用资源注册表、AGI 或厂商工具。

**Q21: 进程 fd、sysfs、debugfs 三个 DMA-BUF 入口怎么分工？进程 fd 大小总和能当系统物理占用吗？**

三个入口按范围分工。/proc/PID/fdinfo/FD 回答"该进程还持有哪些共享 buffer"：DMA-BUF fd 额外输出 size（容量）、count（该 dma-buf file 的引用计数）、exp_name（导出方驱动）。/sys/kernel/dmabuf/buffers/<inode> 在开启 CONFIG_DMABUF_SYSFS_STATS 的内核上回答"系统里有哪些唯一 buffer"（size 与 exporter_name），适合按 inode 去重、按 exporter 聚合。/sys/kernel/debug/dma_buf/bufinfo 是已 root 且挂载 debugfs 的实验室设备上的完整快照，格式不承诺稳定，不做生产接口。

进程 fd 的 size 总和不能当系统物理占用：被多进程 import 的同一 buffer 会在每个持有者处重复计入，fd 视图只证明持有关系；sysfs 也不保存创建调用栈，把 inode 与 fd 对上只能确认当前引用，不能证明最初由谁创建。权限受 SELinux 与 /proc 可见性限制，user build 可能读不到；Linux 没有通用的 /proc/PID/dmabuf 文件，设备私有节点不写成平台保证。

**Q22: 图形内存"泄漏"为什么先要排除三类延迟释放？**

图形资源从逻辑释放到物理回收常有三段延迟：GPU command 未完成时，driver 要等 fence signal 后才回收 backing memory；BufferQueue 的 producer、consumer 或 SurfaceFlinger 仍持有 slot；图片库、HWUI 或图形 API 保留高水位缓存，复用后不再增长。所以判据是形态：预热后数值稳定不涨，通常符合有上限缓存；每轮相同操作后基线持续上移，更像持有者引用或资源销毁不完整；退出页面后短时不降，要把 fence 与 queue drain 的时间放进采样窗口。一次 System.gc() 不能证明图形资源应立即归零。

资源关闭责任按 API 界定：ImageReader.acquire 得到的每个 Image 要及时 close（未关闭会占用 maxImages 配额和对应 buffer）；Surface、SurfaceTexture、MediaCodec、camera session 按生命周期关闭，Surface 销毁后 buffer 仍可能由 consumer 或 fence 短暂持有。OpenGL ES 资源要在属于相应 share group 的 context 中调用匹配的 delete API，删除后 driver 仍可等引用它的命令完成再释放；Vulkan 要区分 object 与 bound memory——销毁 VkImage 不会隐式替代 vkFreeMemory，suballocation 要交还应用 allocator，不要用 vkDeviceWaitIdle 当生产修复。

**Q23: SurfaceView 和 TextureView 谁更省内存？BufferQueue 的 buffer 数是固定的吗？**

两者都不能给固定排序。SurfaceView 由独立 Surface layer 提供内容，系统有机会直接交给 Hardware Composer 合成，但自己也有 BufferQueue；TextureView 把 SurfaceTexture 内容作为 View 层级的一部分由 HWUI 采样，支持普通 View 的 alpha、旋转与裁剪，但增加采样与合成工作，所在应用窗口也要 window buffers。总量由分辨率、格式、queue 深度、overlay 资格与内容路径共同决定，相机与视频页应同机实测进程 GPU counter、DMA-BUF inode 与帧时间再选。

BufferQueue 也没有通用"三缓冲"结论：可用 slot 与同时分配的 buffer 数由 max dequeued（生产者最多取出的槽位）、min undequeued（必须留在队列的最少槽位）、max acquired（消费者最多持有的槽位）、异步模式与 producer 行为共同决定。每个 buffer 的 payload 可用 width × height × bytesPerPixel 粗估，真实 allocation 还要看 stride、plane、格式、压缩与对齐——16 KB 内核页会提高小分配尾部向上取整的最大额外字节，但不能推导统一的"图形内存增加百分比"，4 KB 与 16 KB 的差异要用同 workload 实测。
