# 显示与窗口链路

> 学习资料（文章模式沉淀）。主线：从应用窗口到屏幕的渲染主线，WMS 的窗口、输入分工与 relayout 条件。源文档：android-internals-wiki §1.19《Android 显示架构与 WindowManager》；机制按本地 AAOS13 源码（Android 13）核对，与材料 Android 17 语境的差异已标注：SurfaceFlinger FrontEnd 帧快照（RequestedLayerState/LayerSnapshotBuilder）是 Android 14+ 形态、13 仍是经典 Layer 树，其余主线（五类 Choreographer 回调、AutoSingleLayer latch、presentOrValidate、WMS 线程分工）在 13 已存在。Vsync 与多屏细节见 [../framework/Android显示系统/Vsync流程.md](../../others/framework/Android显示系统/Vsync流程.md) 与 [../framework/Android显示系统/多屏.md](../../others/framework/Android显示系统/多屏.md)；system_server 服务宿主背景见 [08-SystemServer.md](./08-SystemServer.md)。原 Q7–Q12 音频链路部分已于 2026-09-28 移至 [../13-audio/](../13-audio/)（延迟与应用实践在 03 册、蓝牙延迟在 04 册）。Q 序列即结构，供 atlas 同源直读。

**Q1: 一次标准硬件加速窗口从 VSync 到上屏经过哪些环节？"syncAndDrawFrame() 已返回"能证明 GPU 画完了吗？**

主线是 VSync 调度 → Choreographer → ViewRootImpl/HWUI → RenderThread/GPU → BLAST → SurfaceFlinger → HWC → 显示屏。Choreographer 在主线程按 INPUT → ANIMATION → INSETS_ANIMATION → TRAVERSAL → COMMIT 的回调顺序组织一帧（AAOS13 源码核对，回调类型常量 0–4 即此顺序）；硬件加速路径中 View.draw 主要更新 RenderNode/DisplayList 绘制指令，真正的像素工作在 RenderThread 与 GPU 完成。`syncAndDrawFrame()` 返回只表示主线程与 RenderThread 的同步阶段完成，GPU 可能仍在执行。由此得到三个不能互换的时间点：queueBuffer（生产者交回 buffer，GPU 写入可能未完成）、latch（SurfaceFlinger 采纳该 layer 的新 buffer）、present（提交到显示设备）——把它们合并成一个"渲染完成时间"会直接误导排查方向。

**Q2: acquire fence、release fence、present fence 分别回答什么问题？queueBuffer 传输的是整帧像素吗？**

acquire fence 由生产者指向消费者、逐 buffer 一份，回答"生产者何时写完、消费者何时可以读取"；release fence 由 SurfaceFlinger/消费者指回生产者、逐 layer 每帧一份，回答"旧 buffer 何时可以安全复用"；present fence 由 HWC 指向 SurfaceFlinger、逐显示屏每帧一份，回答"本轮显示提交何时越过系统显示边界"。三者方向和责任对象不同，不能互相替代。queueBuffer 不复制像素：传的是缓冲槽、buffer 句柄、裁剪区域、变换、dataspace、时间戳与同步 fence；消费端（RenderEngine 或 HWC）读取内容时必须遵守 acquire fence。present fence 也不包含面板扫描、像素响应与人眼感知时间，定位端到端显示延迟时系统轨迹只能回答到系统显示边界，光学延迟要靠显示驱动或外部测量。

**Q3: WMS.addWindow 返回成功后窗口就可见了吗？应用收到 BadTokenException 应该先查什么？**

不可见。`addWindow()` 只把逻辑窗口加入系统：校验 display、token、类型与权限后创建 WindowState 和 input channel，但方法内不做 layout；窗口必须随后经 relayout 让 WMS 计算几何与 Surface 才会显示，所以 addWindow 成功与首帧可见是两个时间点。BadTokenException 对应的失败发生在 Layer 创建之前：应用窗口必须对应有效 ActivityRecord（ADD_BAD_APP_TOKEN）、子窗口必须指向合法父 WindowState、同一 IWindow 不能重复添加（AAOS13 源码核对 addWindow 的失败码分支），因此应核对 window type、Context/token 来源、Activity 生命周期与目标 display，而不是先查 SurfaceFlinger。这也界定了 WMS 的职责：它维护窗口/任务层级、焦点与可见性，并经 SurfaceControl.Transaction 把状态写给合成与输入系统，但不绘制应用 View、不逐个消费触摸事件。

**Q4: WMS 的 android.display、android.anim、android.anim.lf 三条线程怎么分工？"线程分开了"为什么仍可能互相拖慢？**

android.display（DisplayThread）跑 WMS 的 H 消息与一般异步状态处理；android.anim（AnimationThread）跑 surface placement、layout 与影响动画时序的任务；android.anim.lf（SurfaceAnimationThread）跑 SurfaceAnimationRunner 的逐帧动画计算，设计目标是不持有 WMS 全局锁（AAOS13 源码核对三个线程名，均以 THREAD_PRIORITY_DISPLAY 档位创建）。但共享瓶颈仍在：WMS 与 ATMS 共享 WindowManagerGlobalLock，addWindow、relayoutWindow、容器 reparent、焦点变化都在锁内修改状态，surface placement 仍要读写该锁保护的窗口树——持锁者执行过长会让动画线程在锁上等待。排查 system_server 窗口卡顿要区分：等 mGlobalLock、持锁执行过长、动画线程已收到 traversal 但在等锁、或时间实际耗在应用绘制与 SurfaceFlinger；"WMS 很忙"本身不构成解释。

**Q5: ViewRootImpl.performTraversals 是每帧都跨进程调用 WMS 的 relayout 吗？命中哪些条件才会 relayout？**

不是。`scheduleTraversals()` 只在应用进程内向 Choreographer 投递 traversal；跨进程的 relayout 只在 `performTraversals()` 内条件命中时调用（AAOS13 源码核对 mForceNextWindowRelayout 参与同一判断）。13 与 17 一致的五类条件：mFirst（首帧需初始 SurfaceControl、frames 与 insets）、windowShouldResize（requestLayout 后测量结果改变窗口尺寸）、viewVisibilityChanged（可见性翻转或需要新 Surface）、params != null（setLayoutParams、system UI visibility 等窗口属性变化）、mForceNextWindowRelayout（WMS 经 resized() 等回调强制下一轮 relayout）。因此 invalidate() 引起的纯重绘不会进 WMS，requestLayout() 也只有命中上述条件才跨进程；Insets 变化先走独立的 dispatchApplyInsets 通道并可能间接引发上述条件，但它本身不是这段判断的独立布尔条件。异步 relayout 用于无需同步取回结果的场景；同步路径返回 frame 与 sync id，供 BLAST 同步按帧号对齐。

**Q6: 点击无响应时，WMS、InputFlinger 和应用各自可能的责任段是什么？**

输入事件先由 native InputFlinger 处理：InputReader 读取并规范化设备事件，InputDispatcher 按输入窗口快照选择目标并投递。WMS 不遍历触摸事件，而是经 DisplayContent 的 InputMonitor 把每个窗口的 input token/channel、touchable region、transform、focusable 与当前焦点窗口写进 `SurfaceControl.Transaction.setInputWindowInfo()`，与 layer 状态同一批提交（AAOS13 源码核对 InputMonitor）。输入延迟因此拆成三段：快照过期（窗口移动或转场后 input info 未更新，查 WMS/InputMonitor 的提交与快照发布时序）、队列等待（目标正确但 dispatcher 或线程调度延迟）、应用处理慢（事件已到但主线程被锁、I/O 或重计算占用）。InputDispatcher 判定无焦点或窗口无响应时，经 InputManagerCallback 回到 WMS，由 AnrController 通知 ActivityManager 产生 ANR；ANR 超时受目标窗口与应用状态影响，不应硬编码成单一的"5 秒"结论。
