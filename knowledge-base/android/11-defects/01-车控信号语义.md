# 车控信号语义：超时显示、双编码与值域换算

> 学习资料（文章模式沉淀）。主线：车控 CAN 信号在显示侧与下发侧各有一套语义规则——超时表示未知而非清零、状态域与命令域双编码不得混用、内部哨兵必须避开协议值域、UI 值与协议值要显式换算、独立 CAN 帧到达有时差、多信号合成状态需要仲裁者、下发必须有反馈闭环与值域校验。源文档：`Summary/project/yadi/git提交与缺陷分析` 00_主报告 §5 模式二/三、EnergyManagement.md、Launcher.md 及逐commit详析深案例（缺陷单号 SIR-xxxx 为溯源锚点）。Q 序列即结构，供 atlas 同源直读。2026-09-26 修订：补代码级讲解与深案例覆盖。

**Q1: 车控信号超时丢失时，为什么不能把 UI 显示值清零，正确做法是什么？（SIR-1486）**

信号超时的语义是"当前值未知"，而 0 在显示层是有业务含义的有效数据点；正确做法是冻结最后一次收到的值（或按信号语义显示占位符），等信号恢复后再用真实数据刷新，不能在超时分支执行 set 0 或重置默认值。

某车机项目 SIR-1486 案例：能量柱显示 30% 电量时停发电量信号，能量柱直接清空、底部光效熄灭。修复 diff 删掉的正是超时分支里的两行清零调用：

```diff
         if (lost) {
-            binding.energyBarSeekBar.setBatterySoc(0);
-            updateEnergyBarBottomGlow(0);
+            // 信号超时丢失时，保持能量柱之前的值不变，不设置为0
         } else {
             refreshSocFromFramework("socPercentTimeoutRecovered");
         }
```

删除后超时分支不触碰显示状态，能量柱保持最后一次收到的 30%，恢复分支再由框架缓存刷新。机制上，"数据丢失"和"数据为零"是两种事实：用户看到 0% 会理解为车辆没电，看到 30% 冻结只表示"此刻没有新数据"，两者的用户判断完全不同。

边界：冻结策略有固有取舍——整车真实掉电且长时间停发信号时，界面会一直显示旧值，可能掩盖真实异常，这需要产品侧接受。同时恢复分支不能相信被污染过的本地缓存，应重读数据源刷新；某车机项目 SIR-326 案例中，超时清零后没有恢复分支，渲染端永久停在"未连接"。

**Q2: 信号超时导致控件置灰时，为什么不应顺带把控件的值重置为默认值？（SIR-1494）**

可用性与取值是控件的两个正交状态：置灰表达"不可操作"，重置数值属于明确的业务事件（如恢复出厂）；把重置塞进禁用分支，等于在信号丢失瞬间替换掉用户的设置。

某车机项目 SIR-1494 案例：慢充功率 seekbar 在信号超时不可用时执行 `setProgress` 拉回默认 2.0kW 档，用户设置的 0.9kW 被替换。看修复前后禁用分支的差异：

```diff
     private void updateSlowChargeSeekBarEnabledState() {
         boolean enabled = isSlowChargeSeekBarEnabledBySignals();
-        if (!enabled) {
-            binding.seekbarRangeMode.setProgress(SLOW_CHARGE_POWER_DEFAULT_TENTHS - SLOW_CHARGE_POWER_MIN_TENTHS);
-        }
+        // 信号超时时保持当前值不变，只改变视觉状态（置灰）
         binding.seekbarRangeMode.setEnabled(true);
         binding.seekbarRangeMode.setFocusable(enabled);
```

删除重置调用后，超时只改视觉与交互态（`setFocusable(false)`、置灰），进度条数值保持最后收到的 0.9kW；信号恢复后可用性判断重新为真，不需要恢复动作。

边界：若产品语义是"信号丢失后旧设置不可信、应回默认"，冻结旧值只是延后问题——这类语义冲突要在需求层面确认，不能靠代码顺手决定。超时分支顺手 set 0 或 set 默认值在同模块反复出现（同期的 SIR-1486 同构），规范应固定为"超时冻结显示，恢复后刷新"，修复时用注释说明"什么都不做"的意图，防止后人补回清零。

**Q3: 充电状态信号超时后界面显示"充电枪已连接"而不是"充电异常"，问题出在哪、如何统一超时的状态语义？（SIR-1490）**

问题出在超时分支调用渲染函数时把异常标志传成了 false：信号超时本质是异常工况，却在调用点被声明为非异常；修复是把该参数改为 true，让状态机走异常分支。

某车机项目 SIR-1490 案例：六参方法 `updateChargeStateUi(boolean isCharging, boolean isStopped, boolean isCompleted, boolean isUserStoppedCompleted, boolean isAbnormal, String source)` 用 5 个连续布尔表达互斥状态，超时分支把第 5 个异常标志也传成 false，所有正常态标志与异常标志全为 false，落入 else 分支渲染默认标题"充电枪已连接"。整条修复就是翻转这一个实参：

```diff
-            updateChargeStateUi(false, false, false, false, false, "chargingStateTimeoutLost");
+            updateChargeStateUi(false, false, false, false, true, "chargingStateTimeoutLost");
```

`isAbnormal` 为 true 后方法走异常分支，标题显示"充电异常"并展示告警图标，与"信号丢失即异常"的产品语义一致。

机制与边界：同一模块里有的超时映射为异常态、有的超时显示默认态，说明"信号超时映射为异常"没有统一约定，应作为规范在各超时分支一致执行。连续布尔参数传错位是高发事故，互斥状态应改用枚举或密封类参数；排查这类问题的第一步是核对调用点实参与参数名的语义对应，看到一串 false 应立即逐位对参数名。

**Q4: 信号丢失后的显示策略有冻结旧值、占位符"--"、异常态三种，面对具体信号应如何选择？**

选择依据是信号丢失在业务上的含义：数据量仍在演进、丢失只代表暂时没有新值时冻结旧值；连接或会话语义已经结束时清理为占位符；丢失本身构成异常工况时映射为异常态。

三种策略各有一个真实案例作证据。某车机项目 SIR-1486 案例中电量信号超时冻结能量柱旧值，因为 SOC 数据持续有效、丢失不代表没电；SIR-1490 案例中充电状态信号超时直接映射为"充电异常"标题。SIR-1491 案例则选择占位符：充电枪连接信号丢失被定性为"充电会话结束"，断开分支在隐藏按钮之外补上四个数值控件的占位清理——只隐藏按钮而不清数据，会留下"枪已断开但数值还在"的僵尸状态：

```diff
         if (!connected) {
             binding.btnStopCharging.setVisibility(View.GONE);
             binding.tvChargeEnergyInfo.setVisibility(View.GONE);
+            // 清除充电信息显示（剩余时间、充电功率、充电电流、充电电压）
+            binding.tvMileageDebugRemainingTimeValue.setText(R.string.mileage_debug_remaining_time_value);
+            binding.tvMileageDebugChargeCurrentValue.setText(R.string.mileage_debug_charge_current_value);
+            binding.tvMileageDebugChargeVoltageValue.setText(R.string.mileage_debug_charge_voltage_value);
+            binding.tvMileageDebugChargePowerValue.setText(R.string.mileage_debug_charge_power_value);
             updateMileageDebugPanelPosition(false);
         }
```

真实 diff 还同步复位了剩余时间的单位与横杠控件可见性；剩余时间、充电功率、充电电流、充电电压四类数值统一指向无数据占位资源。

边界：断开分支的清理清单要对照布局控件树逐项核对，漏一个控件就是一条缺陷；占位符统一用"--"而不是空串或 0，模块内才能形成一致的无数据语义；三种策略的选择应由产品语义决定并写成规范，而不是由每个开发者现场决定。

**Q5: "无数据"与"数据为 0"为什么必须用不同的值表达？重置操作后为什么不应立刻回读信号？（SIR-1513）**

0 是合法测量值，用它兼任"无数据"必然错显；应选值域外的哨兵（如 -1）或等价语义，并在显示层格式化前先判哨兵。重置后立刻回读外设拿到的是旧周期数据，会把刚清掉的值又灌回 UI。

某车机项目 SIR-1513 案例：小计里程重置后平均电耗显示 0.0 而非"--"。两处配合失误——重置把缓存设为 `0f`，格式化得 "0.0"；重置回调里 `postDelayed` 500ms 后回读 CAN，车端静止读回 0.0，即使先置成无数据标记也会被覆盖。修复三步闭环的关键 diff：

```diff
     private fun applyTripEavCnsUI() {
-        val avgConsumption = if (mCachedSubtotalTripMileage <= 0f) {
-            getSpannableString("0.0", "kwh")
-        } else {
-            getSpannableString(String.format("%.1f", mCachedTripEavCns), "kwh")
-        }
+        val displayValue = if (mCachedTripEavCns < 0f) "--" else String.format("%.1f", mCachedTripEavCns)
```

```diff
-        mCachedTripEavCns = 0f
+        mCachedTripEavCns = -1f          // -1f 作为"无数据"哨兵
```

`-1f` 在电耗域上不可能出现（电耗不会为负），显示层先判负值输出"--"；删掉重置后的回读后哨兵不会被旧周期数据冲掉，"--"保持到真实行驶数据到来。

边界：哨兵约定必须全链路一致——若有读取路径不判断哨兵直接格式化，仍会显示异常，该项目把所有显示收敛到同一个入口函数来控制风险。旧逻辑还把"里程为 0（无数据）"直接翻译成"电耗 0.0"，语义映射本身就写反了，说明显示层是最后一道语义防线，格式化前的判断不能省。该单经两次提交才收敛：第一版把本地缓存清零并做"立即刷新 + 500ms 回读"两段式更新，解决了不及时问题但电耗仍显示 0.0，哨兵与删回读是第二版方案。

**Q6: 为信号设计"超时丢失"内部标记时，为什么哨兵值不能落入协议真实值域？（SIR-1493）**

数值型信号的小值（0、1、-1）极易与协议合法取值撞车，撞车后合法数据会被当成超时处理；超时应由信号管理层的 lost 回调表达，而不是在业务值里猜。

某车机项目 SIR-1493 案例：代码自造哨兵 `OBC_SLOW_CHARG_CAP_SET_FEED_TIMEOUT_LOST = 0x01`，而慢充功率反馈信号的单位是 0.1kW，合法的 0.1kW 对应的 CAN 值恰好就是 1——设置 0.1kW 永远被判超时，滑条被重置为默认 2.0kW。修复把整套"值等于 1 即超时"的判断连根删除：

```diff
     private void handleObcSlowChargCapSetFeedChanged(int slowChargCapSetFeed, String source) {
-        boolean lost = (slowChargCapSetFeed == OBC_SLOW_CHARG_CAP_SET_FEED_TIMEOUT_LOST);
-        if (mObcSlowChargCapSetFeedTimeoutLost != lost) {
-            mObcSlowChargCapSetFeedTimeoutLost = lost;
-            updateSlowChargeSeekBarEnabledState();
-        }
-        if (lost) {
-            binding.seekbarRangeMode.setProgress(SLOW_CHARGE_POWER_DEFAULT_TENTHS - SLOW_CHARGE_POWER_MIN_TENTHS);
-            updateSlowChargePowerUi(binding.seekbarRangeMode);
-            return;
-        }
+        LogUtils.d(TAG, "[OBC_SLOWCHARGCAPSETFEED] value=" + slowChargCapSetFeed + ", source=" + source);
```

删除后反馈值 1 作为正常数据刷新 UI，不再重置滑条。同一哨兵判断在三个函数里复制粘贴，修复要删三处，超时检测应收敛到框架层统一实现。

边界：设计协议解析前先列出信号完整值域再定哨兵，单位换算型信号（0.1kW 粒度）的小值尤其危险；若协议本身用特定值表示无效（如全 1 位），要确认哨兵在该业务值域之外。删除误判逻辑后超时感知能力会弱化，需确认其它超时监听已覆盖该场景——删防御代码时要核对兜底仍然存在。

**Q7: 状态回读值与命令常量比较导致置灰逻辑恒假，这种"状态域/命令域双编码"错误如何发生与防范？（SIR-7500）**

CAN 车控信号常同时存在两套开关编码——状态域 0=关/1=开、命令域 1=关/2=开；回读状态是状态域值，拿它与命令域常量比较，条件永远不成立，互斥逻辑静默失效。

某车机项目 SIR-7500 案例：湿滑模式开启时驾驶模式应置灰，代码写 `slipModeSwitchSetting.value == SWITCH_CMD_ON`，而回读的状态值是 1（对应 `SWITCH_ON`），命令域的"开"是 2，比较恒假，置灰分支形同虚设，用户仍可切换驾驶模式。修复只换一个常量：

```kotlin
-                if (isDrivingModeEnabled && settingVehicleService.slipModeSwitchSetting.value == CanSignalConstants.SWITCH_CMD_ON) {
+                if (isDrivingModeEnabled && settingVehicleService.slipModeSwitchSetting.value == CanSignalConstants.SWITCH_ON) {
                     isDrivingModeEnabled = false
                 }
```

状态值（1）对状态值（1）比较后互斥分支真正生效，`isDrivingModeEnabled=false` 驱动 `setGrayState` 置灰，一个常量恢复整条互斥规则。

防范：常量命名携带域语义（`CMD` 前缀表示下发命令值），代码评审把"比较方向 + 常量语义"作为固定检查项。这类错误不崩溃、只让功能静默失效，常规异常测试抓不到，给关键互斥结果（如 `isDrivingModeEnabled`）加日志能显著缩短定位链路；若车端某协议版本的回读值确实使用命令编码，必须按收发方向区分，不能一刀切。

**Q8: 多档位 CAN 协议存在"请求值=反馈值+1"偏移和"0 为 NoAction"怪癖时，换算规则应如何固化？**

换算规则必须先于业务代码显式化为命名常量并在所有比较点写明换算：状态域与命令域分立（状态 0=关/1=开，命令 1=关/2=开/0=NoAction）、档位请求等于反馈加一；0 在带 NoAction 语义的协议里是"不发"，不是"关"。

某车机项目一次驾驶与主动安全信号收口提交（无单号）案例中，回弹判断与关闭下发两处改动最具代表性。回弹判断的值域错位：

```diff
// VehicleControlFragment.kt
-                if (getState() != getTemp()) {
+                // 反馈(0..3)与下发(1..4)值域不同，反馈+1==下发才表示已达期望档位
+                if (getState() + 1 != getTemp()) {
```

旧判断 `temp == feedback` 因值域错位永远不等，1 秒后必回滚。关闭下发则踩中 NoAction 语义：

```diff
// DrivingFragment.kt
-        settingVehicleService.sendVehicleProperty(CarPropertyIds.CCU_SETSEATHEATSWREQ, 0)
+        // 加热档位信号为 CCU 新协议：关闭需下发 SWITCH_CMD_OFF(1)，0 为 No Action 不生效
+        settingVehicleService.sendVehicleProperty(CarPropertyIds.CCU_SETSEATHEATSWREQ, CanSignalConstants.SWITCH_CMD_OFF)
```

常量体系同步收敛为"两域四值"——状态域 `SWITCH_ON=1`/`SWITCH_OFF=0`、命令域 `SWITCH_CMD_ON=2`/`SWITCH_CMD_OFF=1`，删除语义混乱的旧常量。

边界：这类值域规范要在接入 CAN 前先定义——该项目常量体系经过三版演进才收口，期间产生了多处真 bug；每个比较点写 `+1` 时必须配注释，否则下一个维护者会把它当 bug 改回去；评审时见到字面量 0 下发要条件反射式质疑其语义。

**Q9: 车速有效性这类"0=有效、1=无效"的反直觉协议值，如何在多个消费模块间保持语义一致？（SIR-7180）**

反直觉枚举极易写反，最好的防线是在信号服务层把原始值收敛成语义化布尔（如 `speedValid`），消费方不再各自比较原始值；修复存量代码时先全局搜索信号 ID，对照仓库内的正确示范。

某车机项目 SIR-7180 案例：车速有效性信号 `PCU_VEHICLE_SPEED_VALID` 的协议语义是 0x0=有效、0x1=无效，车灯页却写成 `vehicleSpeedValid == 1` 才置灰，把"无效"当"有效"，真实车速有效（值 0）时置灰条件恒假，车外灯 OFF 档未按需求置灰。修复只翻转比较的一侧：

```diff
// application/Setting/src/main/java/com/yadea/setting/ui/fragment/LightFragment.kt
     val vehicleSpeedValid = settingVehicleService.getAnyProperty(CarPropertyIds.PCU_VEHICLE_SPEED_VALID)
-        val shouldShow = (vehicleSpeedValid == 1) && (speed >= 10f)
+        val shouldShow = (vehicleSpeedValid == 0) && (speed >= 10f)
```

`== 0` 与协议"0=有效"对齐后，车速有效且 ≥10km/h 时 `shouldShow` 为真：副标题显示、`setItemSelectable(0, false)` 将 OFF 档置灰，一行改动同时修好"车速过高"副标题不显示与 OFF 档未置灰两个现象。

边界：修复后方法头注释仍写着旧语义会误导后人，注释必须与代码同步；`getAnyProperty` 返回 null 时与 0 比较为 false，恰好落在安全侧但属隐式依赖，应显式判空。同一信号被多个模块消费时语义不一致是常态风险，任何一处有依据的正确实现（如本项目数字钥匙服务中的注释与判定）都可作为全仓库对齐的基准。

**Q10: UI 内部值与协议单位不一致时（如滑条 0.1kW 档位、协议单位 W），下发链路会出什么错？换算应放在哪里？（SIR-5734）**

缺一层显式换算时数值偏差一个数量级倍数——滑条值 33 被当作 33W 下发而实际应发 3300W；换算必须显式为命名常量并放在发送点之前，信号收发函数的入参强制使用协议单位。

某车机项目 SIR-5734 案例：慢充功率 UI 显示 0~3.3kW，seekbar 整数值 0~33（0.1kW 档位），下发代码把 seekbar 值原样发给单位为 W 的协议，用户拖到 3.3kW 只发出 33，CCU 按 33W 解释，偏差 100 倍；修复新增常量 `WATTS_PER_TENTH_KW = 100`，下发前完成 0.1kW 到 W 的换算——拖到 0 下发 0、0.1 下发 100、1 下发 1000、3.3 下发 3300。换算收口在发送函数内部，参数名同步带上单位：

```diff
+        int valueWatts = valueTenthsKw * WATTS_PER_TENTH_KW;
         boolean result = vehicleService.sendVehicleProperty(
-                CarPropertyIds.ENERGY_EEM_CHARGING_POWER_ADJUSTMENT_RANGE_SETTING, value);
```

**Q11: 协议值回读显示时，为什么必须先换算再钳位？（SIR-5973）**

钳位会把量纲错误的值"修正"进合法区间，掩盖换算缺失；正确顺序是先按单位归一化，再做范围钳位。

某车机项目 SIR-5973 案例：反馈信号以 W 为单位上报，UI 以 0.1kW 档位为刻度，原代码把原始值直接钳进 0~33 档，30W 被当作 30 个档位显示为 3.0kW，放大 100 倍；修复新增 `wattsToTenthsKw()` 换算（除以 100 四舍五入），30W 归一化为 0 档显示 0.0kW、100W 归一化为 1 档显示 0.1kW，反馈回调与读取两条路径都插入同一转换：

```diff

         int clampedActual = Math.max(SLOW_CHARGE_POWER_MIN_TENTHS,
-                Math.min(SLOW_CHARGE_POWER_MAX_TENTHS, slowChargCapSetFeed));
+                Math.min(SLOW_CHARGE_POWER_MAX_TENTHS, normalizedActual));
     // …（节选自真实 diff，下为新增的换算函数）
+    private int wattsToTenthsKw(int watts) {
+        return Math.round(watts / (float) WATTS_PER_TENTH_KW);
+    }
```

归一化之后钳位退回普通的范围保护职责，量纲修正不再依赖它。

边界与做法：30 被钳进 0~33 看起来"合法"，正是钳位掩盖量纲错误的原因，"先归一化再钳位"应固定为顺序；同一转换出现在多个调用点时立即抽成公共函数，避免两条路径换算漂移。W、0.1kW、0.5A 等多单位体系共存是车控域常态，缺换算这类错误在其中的出现频率很高。

**Q12: 车控信号收发点的联调日志应该怎么设计，才能让单位或精度错误一眼可查？**

**Q13: 超时恢复信号与业务数据信号是两个独立 CAN 帧时，恢复分支为什么不应主动读取关联缓存？（SIR-2084）**

**Q14: 处理"超时置位"类信号时，为什么恢复分支必须重读数据源？单向状态机缺陷如何避免？（SIR-326）**

**Q15: 两个关联信号各自驱动对方的状态位时会产生什么问题？合成状态的仲裁应怎么设计？（SIR-4569）**

**Q19: 对接"设置类"车控信号时，为什么每个下发（Set）信号必须配套注册反馈（Feed）监听？（SIR-8578）**

只对接下发、漏掉反馈监听时，一切非本页操作产生的状态变化（车端修改、其他入口下发）都不会刷新 UI，界面与真实状态脱节；标准结构是"反馈回调 + 页面恢复时读一次 + 统一入口校验"三条路径互补。

某车机项目 SIR-8578 案例：SOC 充电上限只有拖动后的反馈校验作为唯一刷新来源，从未注册 `BMS_SOCThrdSetFeed` 监听，外部信号改了上限后主页的百分比、滑条、提示文案全部不刷新；修复注册反馈监听、`onResume` 主动读一次兜底（兜住监听注册前与页面恢复期间的错位），并把回调、校验、读值收敛到同一个带越界过滤与生命周期守卫的入口函数：

```java
// application/EnergyManagement/src/main/java/com/android/yadea/energymanagement/view/ui/MainActivity.java（节选自真实 diff）
```

**Q20: 同一驾驶模式的下发编码是经济=2、反馈编码是经济=1，两个方向编码不同时，常量应如何组织？（无单号提交）**

为下发与反馈各建一套带方向前缀的常量（`REQ_`/`STS_`），映射函数各自只引用本方向常量——让"拿反馈值当下发值"在编译期不可表达，而不是靠开发者记忆。

某车机项目"修改驾驶模式下发和反馈信号"提交（无单号）前的代码正是反面形态：驾驶模式共用一组常量，而下发与反馈是两套物理编码（下发：经济=2/舒适=1/运动=3；反馈：舒适=0/经济=1/运动=2），混用必错一个方向。修复把常量区一分为二：

```kotlin
// application/Setting/src/main/java/com/yadea/setting/ui/fragment/DrivingFragment.kt
-        private const val DRIVE_MODE_ECO = 1   // 旧：两个方向共用一组常量
+        // 驾驶模式外发信号值：经济=2, 舒适=1, 运动=3
+        private const val DRIVE_MODE_REQ_ECO = 2
+        private const val DRIVE_MODE_REQ_COMFORT = 1
+        private const val DRIVE_MODE_REQ_SPORT = 3
+        // 驾驶模式反馈信号值：舒适=0, 经济=1, 运动=2
+        private const val DRIVE_MODE_STS_COMFORT = 0
+        private const val DRIVE_MODE_STS_ECO = 1
+        private const val DRIVE_MODE_STS_SPORT = 2
```

之后 UI 位置到下发值走 `getDriveModeValue()`（只用 REQ 常量），反馈值到 UI 位置走 `getDriveModeUiIndex()`（只用 STS 常量），图标映射同步改用 STS。方向被命名空间隔开后，SIR-7500 那类"回读状态值与命令域常量比较"的静默失效从源头被排除。

边界：两套常量的注释必须写明方向与完整值域并随代码同步更新（该提交连 KDoc 一起改），否则后人仍会按旧注释取值；反馈映射的 else 分支应落到无效值常量而不是默认选中某档，异常反馈才不会误选模式。

**Q21: CAN 协议改版把座椅加热档位值域从 0~3 整体平移到 1~4 时，代码要同步修改哪些点，漏改一处会怎样？（无单号提交）**

下发映射、回显判断、图标映射、循环切换四处必须同步平移，漏任何一处都会出现"下发对了但图标错一格"或"回弹判断永远不等"的错位；最稳妥是把档位与图标的对应关系抽成映射表单点维护。

某车机项目"根据最新 CAN 统一修改外发信号值"提交（无单号）中，座椅加热循环切换的值域平移如下：

```kotlin
// application/Setting/src/main/java/com/yadea/setting/ui/fragment/VehicleControlFragment.kt
             val value = when (currentState) {
-                0 -> 3
+                1 -> 4
+                4 -> 3
                 3 -> 2
                 2 -> 1
-                else -> 0
+                else -> -1
             }
```

值域整体 +1 后循环切换在旧值域 0~3 与新值域 1~4 间重排，else 分支从 0 改为 -1 表示异常态——0 在新值域是合法的"关闭"，不能再当兜底。同一提交里坡道驻车的开/关下发也因协议改版从通用常量改为逐信号字面量：`if (isChecked) 2 else 1` 替换了 `CanSignalConstants.SWITCH_ON/OFF`（该信号协议为 2=开/1=关）。

边界：同一批开关在不同信号上开/关编码并不一致（坡道类 2=开/1=关、迎宾类 1=开/2=关），通用 `SWITCH_ON/OFF` 常量在协议改版时反而成为阻碍，对外发信号应显式写出该信号的枚举值并注释含义；值域平移是高危改动，评审按"下发、回显、图标、循环"四点清单逐项核对；信号职责移交（如座椅记忆结束信号改由 MCU 下发）后，注释掉的下发死代码应尽快删除并写入联调记录。

**Q22: 3D 车模点击乐观推进把手加热档位、1 秒后延迟反馈兜底刷新时，为什么连点两次会停在 1 档？修复要做对哪两件事？（SIR-3241）**

根因是两个刷新驱动源都不信任事实源：一次物理点击会重复上报（日志实测间隔约 386ms），每次上报都被当成新点击推进一档；1 秒延迟兜底任务又可能用旧请求的结果覆盖车端真实回调刚更新的档位。修复两件事：600ms 防抖挡掉重复上报；车端真实回调到达时撤销未执行的兜底任务。

某车机项目 SIR-3241 案例：先拉日志量化出重复上报 386ms、兜底延迟 1000ms 两个参数，再在车端 `CCU_SETHANDLEHEATSWREQ` 回调里先撤销兜底再刷新：

```diff
// application/Launcher/src/main/java/com/yadea/launcher/control/KanziSignalMapping.java
         signalHandlers.put(CarPropertyIds.CCU_SETHANDLEHEATSWREQ, event -> {
             mHandleHeatLevel = (int) event.getValue();
+            if (mHandleHeatFeedbackRunnable != null) {
+                mHandler.removeCallbacks(mHandleHeatFeedbackRunnable);
+                mHandleHeatFeedbackRunnable = null;
+            }
             updateHandlebarStateToKanzi();
         });
```

点击路径同时加 `HANDLEBAR_CLICK_DEBOUNCE_MS = 600L` 的时间戳防抖，600ms 内的重复上报直接忽略。防抖关掉多推档位、撤销兜底关掉旧结果回滚，UI 只剩"车端真实回调"这一个事实源驱动。

边界：防抖窗口必须落在"重复噪声间隔 < 防抖 < 人类双击间隔"区间（386ms < 600ms），参数从日志量化得出而不是拍脑袋；兜底任务被撤销后，真实回调若迟迟不到，UI 将停在点击后的乐观值直到回调到来，这是乐观更新换取响应的固有代价；同类的座椅加热按钮存在同样的重复上报问题，需按同思路排查。

**Q23: 车控信号值下发给 3D 车模后一直显示 0.0，数据源与换算都查不出问题时，下一步应检查什么？（SIR-6771）**

检查写入通道的值类型与渲染端属性类型是否匹配：float 值经 `String.valueOf` 装进字符串通道后，Kanzi 侧 float 类型属性的写入静默失败，渲染端永远显示默认值 0.0。

某车机项目 SIR-6771 案例：Java 侧充电里程是 float，下发却按字符串传递，车模一直显示 0.0；修复只改装箱类型：

```diff
// application/Launcher/src/main/java/com/yadea/launcher/control/KanziSignalMapping.java
-        kanziManager.setValue("", KanziType.CarModel.CHARGING_MILEAGE, String.valueOf(kanziValue));
+        kanziManager.setValue("", KanziType.CarModel.CHARGING_MILEAGE, Float.valueOf(kanziValue));
```

`setValue` 按值的类型路由到远端属性，`Float` 装箱与 float 属性匹配后写入生效，车模显示真实里程。

边界：这类通道对类型不匹配不报错、只写失败，错误被推迟到渲染端表现为"一直显示默认值"——遇到该症状应先验证通道类型与写入路径，再怀疑数据源；跨端同名字段的类型要逐一核对，同模块其他 `CHARGING_*` 信号若也存在 String/Float 混传需同类排查，映射层可加类型断言或日志提前暴露。

**Q24: SOC 超限提示条件写成 `currentSoc >= presetSoc` 时，什么场景会误弹"已超出"提示？如何避免这类边界比较错误？（SIR-1492）**

当前电量恰好等于设定上限时会误弹：业务语义"超出"是严格大于，`>=` 把"等于上限"也判为超限。写条件前先明确"相等"归属哪个业务分支，再把提示文案与比较符放在一起对照，是避免此类错误最直接的方法。

某车机项目 SIR-1492 案例：用户把充电上限设为与当前电量相同（如电量 80%、上限 80%）后插枪，弹窗条件命中，误提示"当前剩余电量已超出设定电量"；修复只收紧一个比较符：

```diff
// application/EnergyManagement/src/main/java/com/android/yadea/energymanagement/view/ui/MainActivity.java
-        if (currentSoc >= presetSoc) {
+        if (currentSoc > presetSoc) {
             ToastUtils.showCenterToast(this, getString(R.string.soc_exceeds_charge_limit),
     // …（节选自真实 diff，后续实参省略）
```

等于上限不再命中分支后，只有真实超出才弹窗，行为与文案"已超出"一致。

边界：电量恰等于上限时车端不会继续充电，这一产品语义需另行确认（本单按 UI 需求以不弹提示为准）；`>=` 与 `>` 的取舍是弹窗、告警类逻辑最高频的缺陷源，评审时把字符串文案当测试用例读——文案说"超出"而条件允许相等，矛盾立即暴露。
