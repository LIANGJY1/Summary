# 崩溃防护与偶现排查：缺陷形态与排查方法

> 学习资料（文章模式沉淀）。主线：偶现问题先怀疑时序的排查法、崩溃类根因形态（并发修改异常、Fragment 生命周期回调、重复注册、主线程 Binder ANR）、A 级缺陷规律（偶现 A 级多为并发与状态机、必现 A 级多为多系统联调与启动时序）以及日志量化定位、防御叠加死锁排查、压力复现手段等方法。源文档：`Summary/project/yadi/git提交与缺陷分析` 下 00_主报告 §4、§5 模式四、SystemUI.md、BTPhone.md 及逐commit详析深案例（缺陷单号 SIR-xxxx 为溯源锚点）。ANR 超时契约与输入分发计时等平台机制见 [../07-performance/03-ANR.md](../07-performance/03-ANR.md)；异步时序的设计侧修复范式见 [02-主线程与异步时序.md](./02-主线程与异步时序.md)，本文专注排查方法与崩溃形态。Q 序列即结构，供 atlas 同源直读。2026-09-26 修订：补代码级讲解与深案例覆盖。

**Q1: 排查偶现缺陷时为什么应先怀疑时序，而不是功能逻辑？**

偶现的本质是竞态窗口：缺陷只在"两个事件以特定顺序交叠"时出现，功能逻辑错误则是确定性必现。该项目 761 条缺陷修复中必现占 79.2%，常规冒烟即可发现；23 个偶现缺陷（4.2%）几乎全部落在回调、延迟任务、生命周期、跨进程竞态四类时序问题上——例如热点状态广播与连接数量回调的顺序竞态（SIR-8259）、旧任务的延迟删除事件覆盖新状态（SIR-6613）、Fragment 销毁后迟到回调（SIR-2886）、开关机压测下的回调重复注册（SIR-2138）。

因此偶现问题的排查切入点是重建事件到达顺序：从日志提取"信号 A 何时到、状态机何时迁移、旧值何时 post"，而不是反复读业务分支。修复方向也由此确定——为事件加身份校验、去重或守卫，而不是改判断条件。

**Q2: 该项目 11 个 A 级缺陷呈现什么规律？对排查有什么指导意义？**

规律是"偶现 A 级 = 并发/状态机，必现 A 级 = 多系统联调或启动时序"。偶现 A 级全部是竞态与状态机问题：通话状态切换的并发修改异常（SIR-2104）、回调重复注册（SIR-2138）、Fragment 销毁后同步回调（SIR-2886）、主线程同步 Binder 写属性 ANR（SIR-5983）、下拉取消分支未复位（SIR-6044）。必现 A 级则集中在跨系统与启动链路：dsp 阻塞加音频通路串扰（SIR-2463）、回调覆盖写丢属性组加渲染看门狗（SIR-7936/7938）、单例初始化块在用户存储就绪前落盘导致卡开机（SIR-8227）、流程弹窗缺关闭路径加状态机提前 return 的盲区（SIR-6185）。

指导意义有两点：偶现 A 级优先从崩溃栈与竞态窗口入手，把复现压力放在并发与时序上；必现 A 级要先确认问题边界在哪个系统（dsp/HAL/存储时序），避免在应用层反复试错。另有单据教训：SIR-7151 的主单提交只加了日志，真实修复在另一提交——复盘时要以 diff 为准核对修复与单据的对应关系。

**Q3: 偶现 A 级缺陷为什么常藏在"取消"这类非主流分支上？（SIR-6044）**

因为取消分支没有独立的验收路径，手势与动画的开发者天然先写完整路径，取消路径只在与用户操作交叠时才暴露。SIR-6044（偶现，A 级）中下拉关闭车辆设置页的手势控件，拖动回调持续修改视图的 Y 平移与透明度，未达关闭阈值时手势取消回调是空实现——视图永远停在最后一次拖动的中间值，页面"卡"在半透明的驻车界面残像上，内部状态变量也未归零，下次进入页面直接呈现残像。偶现正是因为只有"下拉后取消"这一条路径触发。

修复只有三行，全部落在取消回调里：

```diff
--- component/CommonTools 的 LapseTouchLayout.kt（取消分支的完整修复，节选自真实 diff）
     override fun onExitCancel() {
+        this.translationY = 0f
+        this.alpha = 1f
+        currentTranslationY = 0f
     }
```

观察取消回调的修复内容：三个赋值把视觉属性（`translationY`、`alpha`）与内部状态（`currentTranslationY`）一起归零，视图立即离开中间态，下次拖动也从正确基准开始——这就是"`onDragging` 改了哪些属性，取消回调就复位哪些"的最小实现。方法论两条：手势/动画控件必须成对处理进入与取消；排查时覆盖手势的所有出口（完成、取消、抬起、事件取消），偶现加 A 级的组合优先怀疑非主流路径。

**Q4: 反复开关机压测为什么能暴露回调重复注册类问题？治本位置在哪？（SIR-2138）**

压测让连接反复断建，注册泄漏被叠加放大到必然崩溃。SIR-2138（偶现，A 级）中业务进程内创建了多个 CarServiceManager 实例，每个实例初始化时各自调用 `Car.createCar` 并挂生命周期监听——连接成功后每个实例都触发服务接入，底层属性回调被重复注册，同一条 P 档信号从 N 条注册通道各回调一次，"P 档回 Home"逻辑被重复执行，开关机压测下最终压垮进程。

治本位置在注册端而非各业务端：把连接管理收敛为进程级单例，业务侧改为向单例注册监听，属性回调自然只挂一次。收敛后的连接单例核心结构：

```kotlin
// component/Carlib 的 CarConnectionManager.kt（进程级连接单例，节选自真实 diff）
object CarConnectionManager {
    @Synchronized fun init(context: Context) {
        if (mCar != null || mIsInitializing) return   // 已创建或在创建中，多次调用仅第一次生效
        mIsInitializing = true
        mCar = Car.createCar(context, mHandler, CONNECTION_TIMEOUT_MS, mCarServiceLifecycleListener)
    }
    fun registerListener(listener: CarServiceLifecycleListener) {
        if (mListeners.add(listener)) listener.onLifecycleChanged(mIsConnected)   // 注册即回放当前连接状态
    }
}
// …（节选自真实 diff）
```

`@Synchronized` 加"已创建或在创建中"双守卫保证 `Car.createCar` 每进程只执行一次，`PropertyManager.onServiceConnected` 随之只跑一次，回调不再重复挂载；`registerListener` 在登记成功时立即回放当前连接状态，后注册者不会错过已就绪事件。配套细节：删除各实例自带的重试逻辑，改用 createCar 自带的重连。方法结论：压测是暴露连接泄漏与重复注册的最佳手段，偶现 A 级优先跑压力场景复现。

**Q5: 偶现 A 级崩溃的崩溃栈应该按什么路径分析？（SIR-2104）**

从崩溃栈的集合操作点入手，依次确认共享线程模型与竞态窗口，让"偶现"变成可陈述的交叠条件。SIR-2104（A 级）的分析链条：崩溃发生在通话状态由活跃转断开、系统按来电号码查联系人的路径上，栈顶是 `ConcurrentModificationException`；顺藤确认共享集合——蓝牙 PBAP 同步线程在写入/合并联系人号码列表，通话回调线程同时在遍历查询；再解释偶现——只有"同步进行中 + 恰好来电触发号码查询"同时发生才崩，两个条件交叠即竞态窗口。

修复组合拳对应三处改动，可直接从 diff 读出三层防线：

```diff
--- ContactRepository.java（共享集合与跨线程标志的修复，节选自真实 diff）
-    private static boolean isContactLoading = true;
+    private static volatile boolean isContactLoading = true;
-    private List<BluetoothPbapContact> mPbapContacts = new ArrayList<>();
+    private List<BluetoothPbapContact> mPbapContacts = new CopyOnWriteArrayList<>();
+    List<String> numbersSnapshot;
+    try {
+        numbersSnapshot = new ArrayList<>(pbapContact.getmNumber());   // 遍历前先做快照
+    } catch (Exception e) { continue; }   // 快照失败跳过该联系人
```

`CopyOnWriteArrayList` 让迭代器基于快照，"遍历 vs 写入"不再共享同一份修改计数，CME 从结构上不可能发生；遍历前的快照拷贝外包 try-catch，兜住快照瞬间的极端竞争，按"跳过该条"降级而非整体崩溃；`volatile` 补齐同步标志的跨线程可见性——三层各挡一类竞态。排查纪律：偶现 A 级崩溃优先看崩溃栈里的集合与生命周期操作点，而不是先怀疑业务判断；"部分失败优于整体崩溃"的容错取向适合稳定性敏感模块。

**Q6: "点击无反应 + 应用进程异常"的组合应该先查什么？（SIR-5983）**

先查 ANR：应用被系统判定无响应杀死后，所有入口点击自然全部无反应，表象像崩溃或死机。SIR-5983（A 级）中自动化运行时主线程同步调用车辆属性写 Binder，远端 CarProperty 服务迟迟不返回，输入超时即 ANR，进程死亡后 dock 栏与列表点击全部失效，其他应用正常——"单应用假死 + 进程消失"是特征组合。排查入口是 `/data/anr/` 下的主线程堆栈，找同步 Binder 调用点。挂单修复把全部属性写从调用线程剥离到专用串行线程：

```kotlin
// SendPropertyManager.kt：新增专用写线程，setIntProperty 改为入队（节选自真实 diff）
+    private val writeHandlerDelegate = lazy {
+        HandlerThread("CarPropertyWrite").let { it.start(); Handler(it.looper) }
+    }
+    private val writeHandler by writeHandlerDelegate
     fun setIntProperty(vehiclePropertyId: Int, area: Int, value: Any): Boolean {
-        return (value as? Int)?.let { carPropertyManager?.setIntProperty(...) != null } ?: false
+        return enqueueWrite("int", vehiclePropertyId, area, value) { manager ->
+            manager.setIntProperty(vehiclePropertyId, area, value)   // 真正的 Binder 写在专用线程执行
+        }
```

观察入队改造：各类型的属性写统一 post 到 `CarPropertyWrite` 串行线程，远端再慢也只阻塞该线程，串行同时保住了下发顺序，ANR 崩溃链被切断；返回值语义随之变为"是否成功入队"，依赖写结果做 UI 假设的调用方需同步跟进。

同类问题的另一个伪装形态是"偶发整机像卡死"：SIR-5994 中上电后 dock 栏变灰、点击无响应但进程未死，根因同样是主线程被 `Car.createCar` 同步 Binder 挂起。因此偶发"像卡死"优先查主线程阻塞（binder 耗时、锁竞争），而不是渲染逻辑；修复范式（专用线程、串行队列、代数守卫）见 [02-主线程与异步时序.md](./02-主线程与异步时序.md)。

**Q7: monkey 测试暴露的崩溃与 ANR 有哪些典型形态？（SIR-8541、SIR-6008）**

monkey 暴露两类问题：事件序列异常导致的崩溃，与主线程耗时导致的 ANR。SIR-8541 中手势监听的 onFling 回调收到空 MotionEvent——事件流被随机打乱后，fling 可能没有配对的按下事件；修复是传入事件前先校验有无 Down 事件，属于"事件序列完整性校验"防御。SIR-6008 中日志多处 ANR，根因是蓝牙状态广播在主线程处理且同步执行秒级的换设备数据清理（数据库加跨进程）；修复把清理投入单线程 executor 后台执行，并补两个配套：闭包捕获的变量先存快照（旧设备 MAC），状态标志改 `volatile`。

方法论：monkey 测试是暴露这类问题最高效的手段，因为它以远超人工的频率制造异常事件序列与状态切换；接入 monkey 后要主动扫日志中的 ANR 与 crash 关键字，而不是只看应用是否存活。

**Q8: Fragment 生命周期类崩溃有哪些形态？排查清单是什么？**

三类高频形态对应三个检查点，共同点是"销毁后仍有事件到达"：

1. **迟到事件触达已销毁视图**：SIR-2886（A 级）中同步未完成时切 tab，ViewPager 销毁 fragment，RxBus 迟到的进度事件继续操作已置空的 binding 而崩溃。检查点：每个异步回调触达视图前必须有 `isAdded()` 与 `binding == null` 守卫，包括 `postDelayed` 内部；
2. **残留消息访问已销毁生命周期对象**：SIR-8545 中昼夜切换重建视图，handler 队列残留的初始化消息引用已失效的 viewLifecycleOwner 崩溃，且初始化标志未复位导致 dock 栏不再恢复。检查点：onDestroyView 清空 handler 消息、消息体判活生命周期对象、初始化标志可复位；
3. **延迟初始化留下空指针窗口**：SIR-5896 中核心数据成员的初始化被包进 UI 延迟任务，构造完成到任务执行前被访问即 NPE。检查点：纯创建型、无视图依赖的初始化留在构造期，只把观察注册等需要视图就绪的工作延迟。

守卫的标准形态（SIR-2886 的实际修复）：

```diff
--- ContactsFragment.java（RxBus 进度事件入口，节选自真实 diff）
                 Integer progress = (Integer) event.getData();
                 if (progress != null) {
+                    if (!isAdded() || binding == null) {
+                        return;   // 已脱附或视图已销毁，迟到事件直接丢弃
+                    }
                     updateSyncProgress(progress);
                 }
```

两个条件把"fragment 还附着且视图还在"变成触碰视图的前置校验，销毁后的迟到事件在访问任何视图成员前被丢弃；同一守卫必须复制到 `postDelayed` 的延迟回调内部，否则延迟执行窗口仍然裸露。

排查"杀进程后立即重进""快速切换后崩溃"类问题时按此清单过一遍；这类路径是延迟初始化与生命周期竞态的天然触发器。

**Q9: 系统服务的"占位/幽灵"状态如何污染应用状态机？（SIR-5769）**

系统服务会制造不对应真实业务的占位对象，应用若不按状态做生命周期清理，占位对象会被误判为第二条通话，进而触发错误分支。SIR-5769 中 telecom 产生 `SELECT_PHONE_ACCOUNT` 占位通话且无人清理，状态机用"是否存在第二条通话"的位置语义判断三方来电，占位通话被误判，三方分支又假定"活跃通话 + 振铃通话"都存在，取到 null 直接解引用崩溃，同时来电框已先被移除而不显示——一个根因同时产出崩溃与黑屏两个症状。

防御要点四条：通话集合按状态做生命周期清理（新外呼建立时移除被取代的占位对象）；"多方通话"判定用状态组合（活跃/保持 + 振铃）而非位置语义；UI 渲染先取数判空、再动视图，顺序颠倒会把崩溃放大成黑屏；回调入口校验对象身份，屏蔽已清理对象的迟到期事件。排查车载蓝牙电话类"幽灵状态"时，先列系统服务会产生的全部占位/中间态。

**Q10: 长驻进程的信号订阅"静默失效"如何排查与兜底？（SIR-5446）**

静默失效的特征是框架不派发断连回调，订阅永久失效且无日志——症状是档位等信号收不到更新（偶发无法进 D 档），而进程一切"正常"。排查上先确认回调链路是否存活，再查异步初始化的过期回填：SIR-5446 中异步获取 manager 期间若断连，过期回调还会把连接标志错误置回。

兜底是"看门狗 + 代际令牌 + 重连补注册"三件套：周期巡检"未连接且未在重连"的静默断连状态，连续多次即强制重连；异步初始化结果带代际令牌，不匹配即丢弃，防过期回调回填；重连成功后按注册表补注册全部属性回调，恢复订阅。要诚实标注修复边界：该缺陷偶现（低于 10%）且缺陷库注明 HAL 层疑点未排除，此修复属规避加兜底而非确定性根治，若再复现需向 HAL 层继续追查——偶现问题的修复不等于根因闭合，排查结论要写明证据边界。

**Q11: 上下电、睡眠唤醒场景的初始化时序竞态如何排查？（SIR-6170）**

这类场景会重走初始化链路，"服务未就绪时发出的查询直接丢失"是高发模式。SIR-6170 中应用启动时向 L2A 查询 HUD 信号初值，此刻 L2A 尚未连接，查询丢失，UI 停留在默认高亮态；项目已有"连接建立后补查"的补偿机制，但补偿清单漏了 HUD 总开关一项，导致自动亮度与亮度条被刷新、总开关仍是错的——补偿清单与初始化清单不对齐，漏一项就出一个必现 UI 状态 bug。

排查步骤：列出初始化查询清单，确认服务未就绪时每项查询的失败行为；确认补偿机制的触发条件（本项目是连接状态跳变）与补查清单是否全覆盖；跳变检测的边界也要核对——若服务在应用启动前已连接则无跳变，仍依赖启动查询路径。测试策略：上下电、睡眠唤醒是启动时序竞态高发区，要作为专门用例覆盖，不能只测冷启动。

**Q12: 状态机如何对"带着历史脏状态到达的新事件"自愈？（SIR-5468）**

在状态入口处识别脏状态并强制迁移，而不是假定每次事件都从干净状态开始。SIR-5468 中历史缺陷留下的三方通话残留状态无法退出，之后单路来电到达时状态机无法处理；修复除了切断脏状态的来源（乐观移除改为确认后移除），还在状态机补了两类自愈：三方残留态收到单路振铃新来电时强制回迁移到来电态；主通话对象为空时兜底迁移到空闲态。

这条原则与"防御留退出通道"互补：防御机制防止脏状态产生，自愈路径负责消化已经产生的脏状态。排查状态机类偶现时，先画出全部状态的迁移表，再检查每个状态下收到"不该出现的事件"时的行为——异常组合要么被屏蔽、要么有确定的迁移目标，不能悬空。

**Q13: 日志量化定位"双驱动回滚"类缺陷的方法是什么？（SIR-3241）**

先用日志量化出互相冲突的驱动源及其时序参数，修复参数直接从数据得出。SIR-3241 中把手加热连点两次显示停在 1 档：日志显示一次物理点击附近存在约 386ms 间隔的重复上报，每次都推进一档；还存在 1000ms 的延迟反馈任务，会用旧请求结果刷新 UI，把车端真实回调刚更新的档位回滚——两股驱动都不信任唯一事实源。两处修复可直接从 diff 读出：

```diff
--- KanziSignalMapping.java（两股驱动源各自的收敛，节选自真实 diff）
+    private static final long HANDLEBAR_CLICK_DEBOUNCE_MS = 600L;
@@ 车端真实回调到达

+            if (mHandleHeatFeedbackRunnable != null) {
+                mHandler.removeCallbacks(mHandleHeatFeedbackRunnable);   // 撤销未执行的延迟反馈
+            }
@@ 点击入口
```

防抖 600ms 落在"重复噪声 386ms < 防抖 < 人类双击间隔"之间，把重复上报挡在档位推进之前；真实回调到达即撤销延迟反馈任务，UI 只剩车端回调一个事实源——防抖窗口与撤销时机全部来自日志量化，不是拍脑袋。

**Q14: "状态横跳/回退"类偶现显示错乱，排查路径是什么？（SIR-5737、SIR-8259）**

症状到根因的路径是：先识别"双真值源互相触发"或"多事件源竞态"，再画环找引用旧状态的那一环。SIR-5737 的横跳是双真值源：开关回调里反查管理器缓存（仍为旧值），走错分支后又触发状态回调翻回，两个源互相拉扯——排查方法是画出"UI 状态 → 指令 → 系统回调 → UI 状态"的环，找到环上用滞后缓存做分支判断的那一环，改为以回调参数为准。SIR-8259 的错乱是多事件源：热点状态广播与连接数量回调共同决定同一 UI 状态，其中一处读的是异步迁移窗口内不可靠的实时查询——排查方法是画出事件到达顺序图，找出读非确定性状态的路径。

两条路径的公共纪律：不要在症状层面打补丁（如动画上加延时遮罩），要定位到"谁引用了过期状态"；修复后用原时序复现步骤回归验证。设计侧的对应规则（回调参数优先、唯一权威来源）见 [02-主线程与异步时序.md](./02-主线程与异步时序.md)。

**Q15: "卡在 Loading/正在同步"类偶现，排查清单是什么？（SIR-4087、SIR-6525）**

按"谁该把状态置回终态"逐层核对，每层都有真实案例支撑：

1. **请求是否被防抖吞掉**：SIR-6525 中跨进程入口的 500ms 时间窗防抖把用户"重新获取"的真实请求静默丢弃；
2. **空数据是否被当作"同步中"吞掉**：SIR-4087 中空收藏是合法终态，却被"同步中收到空数据继续等"的分支保持 Loading；
3. **超时兜底是否被公共路径无条件取消**：SIR-6525 中空数据也会走的数据路径末尾无条件取消超时，兜底被变相拆除；
4. **超时重试是否构成自我循环**：SIR-4087 中超时后重置状态并重新发起同步，形成"同步、超时、重置、再同步"死循环；
5. **状态位是否串写**：SIR-4087 中收藏下载失败误写联系人状态位，下游全部判断失真；
6. **布尔方法名与实现是否相反**：SIR-4087 中 `isPbapAuthorized` 实际返回"未授权"，双重否定是定时炸弹，review 零容忍。

排查顺序建议从 1、3 开始（防御类，最隐蔽），再到 2、4、5（状态机类）。修复纪律见 Q16。

**Q16: 为什么防御机制叠加造成的死锁比没有防御更难查？如何系统性排查？**

因为每个防御单独评审都合理，组合后互相拆台：拆掉兜底的、吞掉重试的、续命窗口的各自隐藏在"防御性代码"的外衣下，日志里表现为"什么都没发生"。该项目的三连案例：SIR-6525 中防抖吞掉新请求、空数据路径取消超时兜底，两者叠加成无出口死锁；SIR-4087 中超时重试循环自我续命；SIR-4602 中一次性标志无复位路径导致每通电话复现弹窗。

系统性排查法：把所有防御机制（防抖、守卫、超时、重试、标志位、缓存）列成清单，画它们之间的交互图，对每个 cancel/reset/retry 路径追问"到达终态吗"——SIR-6525 的修复就是把超时取消收敛到每个终态分支，保证兜底必然可达。评审纪律：每新增一个防御都要回答"它会不会挡住正常路径、会不会拆掉已有兜底"；修 A 问题引入的防御造成 B 问题时，说明补丁缺乏回归视角。

**Q17: 偶现问题有哪些可用的复现手段？各对应什么 bug 类型？**

按缺陷类型选择压力手段，目标是用可控频率制造竞态窗口：

1. **反复开关机/上下电压测**：暴露连接泄漏、重复注册、启动时序类问题（SIR-2138 压测复现回调重复注册）；
2. **monkey 测试**：暴露异常事件序列崩溃与主线程耗时 ANR（SIR-8541、SIR-6008）；
3. **快速连点**：暴露任务栈抖动与事件覆盖类问题（SIR-6613 快速连点 AppList 触发旧任务延迟删除事件覆盖新前台）；
4. **昼夜模式快速切换**：暴露视图重建与 Handler 生命周期问题（SIR-8545）；
5. **杀进程后立即重进**：暴露延迟初始化空指针窗口（SIR-5896）；
6. **上下电/睡眠唤醒循环**：暴露服务慢启动丢初始化查询（SIR-6170）。

配套策略：对高频入口加输入侧防抖、对事件处理加幂等与身份校验（SIR-6613 的双管齐下），让"偶现才修"变成"结构性免疫"。复现手段的选择依据是缺陷的竞态窗口在哪个维度——连接生命周期、输入频率、视图重建还是服务就绪时序。
