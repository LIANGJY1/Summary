# 主线程与异步时序：缺陷模式与修复范式

> 学习资料（文章模式沉淀）。主线：主线程同步 Binder 的病灶形态与四种修复范式（缓存直读加异步补拉、专用线程池加代数守卫、专用串行 HandlerThread、IO 线程加旧值先显），以及延迟任务可取消、Fragment 迟到回调失效、并发容器选型、回调禁反查滞后缓存、防抖不吞真实请求、防御机制留退出通道、乐观更新可被事实源撤销、长驻订阅自愈三件套、终态事件直达快路径等异步时序防回归规则。源文档：`Summary/project/yadi/git提交与缺陷分析` 下 00_主报告 §5 模式四、SystemUI.md、BTPhone.md 及逐commit详析深案例（缺陷单号 SIR-xxxx 为溯源锚点，代码均节选自真实 diff）。ANR 超时契约与 InputDispatcher 计时等平台机制见 [../07-performance/03-ANR.md](../07-performance/03-ANR.md)，本文只写项目缺陷模式与修复范式视角；偶现问题的排查方法与崩溃形态见 [07-崩溃防护与偶现排查.md](./07-崩溃防护与偶现排查.md)。2026-09-26 修订：补代码级讲解与深案例覆盖。Q 序列即结构，供 atlas 同源直读。

**Q1: 车载应用在主线程调用 getProperty、Car.createCar 这类车服接口，为什么是本仓库最大性能病灶？症状有哪几种形态？**

这些接口底层都是同步 Binder 调用，远端 CarService 未就绪或繁忙时调用线程会被长时间挂起；调用发生在主线程，等于把系统服务的可用性风险直接转嫁给 UI 流畅性。开机、上电、服务重启窗口风险最高，因为此时车服务最可能未就绪。

病灶在代码上的形态：修复前的 Carlib 读属性入口对调用线程不做任何分流，主线程调用即同步 Binder（节选自 SIR-5459 真实 diff）：

```kotlin
// 修复前：CarServiceManager.kt 的读属性入口（节选自真实 diff）
fun getProperty(propertyId: Int, area: Int = CarConstants.UNUSED): CarPropertyValue<*>? {
    return PropertyManager.getProperty(propertyId, area)
}
```

`PropertyManager.getProperty` 内部是同步 Binder 往返，调用线程是谁，阻塞就落在谁身上——这正是 Q2 到 Q5 四种范式都要先把"调用线程"与"Binder 阻塞"解耦的原因。

症状有三种典型形态，严重度递增：点击后页面冻结数秒（SIR-6629 中 getCarLinkAppList 逐个查询应用详情耗时秒级）；整机"像卡死"但未崩溃（SIR-5994 中上电后 dock 栏变灰、点击无响应）；输入超时触发 ANR 被系统杀死，之后该应用所有入口点击都无反应（SIR-5983，A 级）。排查"偶发整机像卡死"应优先查主线程阻塞（binder 耗时、锁竞争），而不是渲染逻辑。

需要按同步 Binder 对待的调用不止读属性：`Car.createCar`、`getCarManager`、`getProperty` 系列读属性、`setIntProperty` 系列写属性、`registerCallback`/`unregisterCallback` 属性注册注销，以及返回大列表的阻塞 IPC（如 getAllContacts）全部在列，任何一处出现在主线程都是同类隐患。

**Q2: 对 getProperty 这类高频属性读取，"事件缓存直读 + 异步补拉"的修复范式怎样设计？（SIR-5459）**

核心是让主线程的属性读取永远不碰同步 Binder：命中缓存直接返回最近一次回调的值，未命中立即返回默认值并转后台线程补拉。SIR-5459 中开机阶段 CarService 尚在初始化，主线程直读 `getProperty` 被挂起导致 Launcher 整体 ANR 黑屏，修复分三层：

1. **缓存维护**：`onChangeEvent` 回调里顺手把值写入 `propertyCache`（ConcurrentHashMap），断连时清空，保证缓存来自事件流而非主动查询；
2. **线程分流**：`getProperty` 内用 `isMainThread()` 判断，主线程走 `getCachedProperty`，子线程仍走阻塞读；
3. **异步补拉**：主线程未命中时 `requestCacheRefresh` 用 `pendingCacheReads.putIfAbsent` 去重、按重试间隔节流，投递到专用 `HandlerThread` 执行阻塞读后回填。

线程分流的真实落点（节选自真实 diff）：

```diff
// CarServiceManager.kt：主线程走缓存，子线程保留阻塞读语义
     fun getProperty(propertyId: Int, area: Int = CarConstants.UNUSED): CarPropertyValue<*>? {
-        return PropertyManager.getProperty(propertyId, area)
+        return if (isMainThread()) {
+            getCachedProperty(propertyId, area)
+        } else {
+            getPropertyBlocking(propertyId, area)
+        }
     }
```

异步补拉入口的去重与节流同样来自该提交（节选自真实 diff）：

```diff

+        if (!isMainThread() || released || !CarConnectionManager.isConnected()) return
+        if (pendingCacheReads.putIfAbsent(key, true) != null) return
+        // …（节选自真实 diff：按重试间隔节流后投递）
+        PROPERTY_READ_HANDLER.post { ... getPropertyBlocking(propertyId, area) ... }
+    }
```

`putIfAbsent` 保证同一属性同时只有一个补拉在途，节流防止开机阶段高频重试压垮尚未就绪的远端；主线程从此与 Binder 阻塞解耦。配套改动是把启动期的关键读取（如 VIN 码）改为 `getPropertyAsync` 回调式 API。该范式的副作用必须写进契约：主线程首读可能拿到缓存未热时的"暂态默认值"，业务要容忍异步补齐；缓存一致性依赖 `onChangeEvent` 持续派发，需与断连看门狗互补。

**Q3: Car.createCar 与 getCarManager 这类连接级初始化，为什么用"专用线程池 + 代数守卫"修复？（SIR-5994）**

因为初始化异步化后，"完成"变成了时序不确定事件，必须同时建模回调时序、过期结果丢弃与失败重试。SIR-5994 中上电阶段主线程同步执行 `Car.createCar` 与 `getCarManager` 被长时间挂起，SystemUI 表现为 dock 栏变灰、整机无响应。修复的关键设计：

- `createCar` 移入专用单线程 executor 执行（`createCarAsync`），生命周期事件等 createCar 返回后再派发回主线程，注释明确"避免回调内的 getCarManager 抢占 Car 内部锁"；
- 应用侧新增 `initializeCarFeaturesAsync`：Car manager 的获取放在后台线程，仅把 UI 对象初始化 post 回主线程；
- 用代数计数（generation）丢弃断连/重连后过期的初始化结果，配合在途标志与看门狗重连。

createCar 异步化的落点（节选自真实 diff）：

```diff
// CarConnectionManager.kt：同步调用整体挪进专用单线程 executor
+    private fun createCarAsync(context: Context, successLogPrefix: String) {
+        mConnectionExecutor.execute {
+            try {
+                Car.createCar(context, mHandler, CONNECTION_TIMEOUT_MS, mCarServiceLifecycleListener)
+            } catch (e: Exception) {
+                Logcat.e(TAG, "createCar failed", e)
+            }
+        }
+    }
```

远端再慢也只阻塞 `mConnectionExecutor` 这一条线程，主线程照常渲染与响应输入；应用侧 `SystemUIApplication` 用 `mCarFeatureGeneration` 校验，断连/重连后旧代数的初始化结果 post 回主线程前即被丢弃，不会覆盖新连接的状态。这条范式的代价是复杂度显著上升：所有依赖 Car 就绪顺序的逻辑都要显式建模，不是简单 post 了事。

**Q4: 写车辆属性为什么要用专用串行 HandlerThread，而不是普通线程池？（SIR-5983）**

因为写操作除了"离开主线程"还必须保住下发顺序，只有串行队列能同时满足两点。SIR-5983（A 级）中业务在主线程点击事件里调 `setIntProperty` 等同步 Binder 写，远端 CarProperty 服务迟迟不返回导致 Input ANR。修复要点：

1. 新建 `HandlerThread` 专用写线程，所有类型的属性写统一经 `enqueueWrite` 投递，主线程只做入队；
2. 串行执行保住业务侧信号下发顺序不变，这是线程池无法承诺的；
3. 返回值语义从"写成功"改为"入队成功"，依赖返回值做 UI 假设的调用方必须跟进改写；
4. 带队列延迟与执行时长观测日志，加 500ms 慢写告警，让"远端卡死"可见。

写线程的建立与写入口的改造（节选自真实 diff）：

```diff
// SendPropertyManager.kt：属性写统一入队到专用串行 HandlerThread
+    private val writeHandlerDelegate = lazy {
+        HandlerThread("CarPropertyWrite").let { thread ->
+            thread.start()
+            Handler(thread.looper)
+        }
+    }
     fun setIntProperty(vehiclePropertyId: Int, area: Int, value: Any): Boolean {
-        return (value as? Int)?.let { intValue ->
-            carPropertyManager?.setIntProperty(vehiclePropertyId, area, intValue) != null
-        } ?: false
+        val intValue = value as? Int ?: return rejectInvalidValue("int", vehiclePropertyId, value)
+        return enqueueWrite("int", vehiclePropertyId, area, intValue.toHexString()) { manager ->
+            manager.setIntProperty(vehiclePropertyId, area, intValue)
+        }
     }
```

`enqueueWrite` 内部经 `writeHandler.post` 投递，调用方拿到的是"入队成功"而非"写成功"。配套细节同样关键：回滚超时任务先于写入建立（否则回调先到无法清理）、manager 失效时拒绝入队、注销时释放未完成的回滚任务。隐患是慢写会积压串行队列，靠告警日志观测。

**Q5: "runOnUiThread { 慢调用 }"错在哪？列表类加载的正确范式是什么？（SIR-6629）**

把慢调用包进主线程块不会让它变快，只会把耗时摊到帧渲染上——主线程只该做 UI 赋值。SIR-6629 中连接 CarLink 后点击应用列表冻结约 3 秒，两处调用都在主线程：Fragment 直接同步取数，更典型的一处是用 `ThreadUtils.runOnUiThread { ... getCarLinkAppList() ... }` 把同步 Binder 整个裹进了主线程。

修复后的取数链路（节选自真实 diff）：

```kotlin
// DeviceConnectManager.kt：查询移到 IO 线程，主线程只做 UI 通知
// 修复前：ThreadUtils.runOnUiThread { ... getCarLinkAppList() ... } 把同步 Binder 裹进主线程
ThreadUtils.getIoPool().execute {
    val appInfoList = getCarLinkAppList()
    ThreadUtils.runOnUiThread {
        synchronized(mListener) {
            for (callback in mListener) {
                callback.onDeviceAppListLoaded(CARLINK, appInfoList)
            }
        }
    }
}
```

Fragment 入口同步改为 `viewLifecycleOwner.lifecycleScope.launch(Dispatchers.IO)` 取数、`withContext(Dispatchers.Main)` 回主线程刷新。正确范式是"IO 线程 + 旧值先显"：进入页面前先展示 `@Volatile` 缓存的旧列表让首帧立即可见，后台拉到新数据后二次刷新；缓存只在查询成功后更新、连接断开时清空；异步期间先隐藏引导页避免闪现。这条范式适用于一次性的列表/详情加载，与高频属性读的"缓存直读 + 异步补拉"范式适用条件不同：后者要求回调持续派发以维持缓存热度，前者只要求有旧值可先显。

**Q6: 同一仓库并存的四种主线程 Binder 修复范式，分别适用于什么场景？如何选择？**

选择依据是读还是写、要不要保顺序、结果是否过期敏感、有没有旧值可以先显：

- **事件缓存直读 + 异步补拉**：适合回调持续派发的高频属性读，主线程要"立即有值"，容忍暂态默认值（SIR-5459）；
- **专用线程池 + 代数守卫**：适合连接级初始化（createCar/getCarManager），结果与连接代数绑定，过期结果必须丢弃（SIR-5994）；
- **专用串行 HandlerThread**：适合写操作与有顺序要求的下发，串行队列保序，返回值语义变为入队（SIR-5983）；
- **IO 线程 + 旧值先显**：适合一次性的列表/详情加载，有缓存旧值可先显、用户可容忍先旧后新（SIR-6629）。

四者共同点是主线程永不等待 Binder；差异在结果的一致性要求与是否需要顺序保证，按上述四问对号入座即可。

**Q7: 把同步 Binder 调用异步化，除了"挪线程"还必须连带处理哪些事？**

异步化不是简单 post：原同步调用的语义依赖（返回值、顺序、超时、时序）都会在新形态下变成新的 bug 源。项目深案例归纳出必须逐项审视的清单：

1. **返回值语义**：写属性从"写成功"变"入队成功"，调用方对返回值的假设要改写（SIR-5983）；
2. **顺序性保证**：要求按序下发的场景用串行队列而非并发池（SIR-5983）；
3. **超时/回滚任务的建立顺序**：pending 超时任务先建、异步写后投，避免回调先到无处清理（SIR-5983）；
4. **过期结果丢弃**：连接断建、页面销毁后用代数计数丢弃过期初始化（SIR-5994、SIR-5446）；
5. **失败重试**：静默断连需要看门狗兜底（SIR-5446）；
6. **闭包变量快照与可见性**：后台化后闭包捕获的变量要先存局部快照，跨线程状态标志加 `volatile`（SIR-6008）；
7. **回调线程契约**：异步注册完成后仍要按原契约把首次回调 post 回主线程，避免引入新线程问题（SIR-6325）。

**Q8: BroadcastReceiver.onReceive 里处理耗时清理为什么会 ANR？后台化时要补哪两个配套？（SIR-6008）**

`onReceive` 默认在主线程且有时限，任何数据库或跨进程操作都可能超限。SIR-6008 的 monkey 测试多处 ANR 正是蓝牙状态广播的主线程路径上同步执行换设备清理——该清理涉及联系人/通话记录数据库与跨进程调用，秒级耗时。

修复是把清理任务投入单线程 executor 后台执行，闭包捕获的旧设备 MAC 先存快照再入队（节选自真实 diff）：

```diff
// BluetoothManager.java：秒级清理入队单线程 executor，旧设备 MAC 先存局部快照
+    private final ExecutorService dataClearExecutor = Executors.newSingleThreadExecutor();
+    // …（节选自真实 diff：换设备连接检测分支内）
-                            DataClearUtil.clearDeviceData(appContext, previousConnectedMac);
+                            final String oldDeviceMac = previousConnectedMac;
+                            dataClearExecutor.execute(() -> {
+                                try {
+                                    boolean success = DataClearUtil.clearDeviceData(appContext, oldDeviceMac);
+                                    Log.i(TAG, "Old device data cleanup completed, mac=" + oldDeviceMac + ", success=" + success);
+                                } catch (RuntimeException e) {
+                                    Log.e(TAG, "Old device data cleanup failed, mac=" + oldDeviceMac, e);
+                                }
+                            });
```

`onReceive` 快速返回，ANR 触发条件消失。但后台化必须补两个配套，否则修完 ANR 换来竞态：一是闭包捕获的变量先存快照（如上先保存旧设备 MAC 局部变量，避免异步执行时读到已被更新的值）；二是配套的状态标志改 `volatile`（`isClearing`），保证跨线程可见。另一个经验：首次连接场景广播里已携带确定的状态与设备，直接使用比再走一次 Profile 查询更快也更不易漏。

**Q9: "数据量小时没事"的同步代码，怎样在五千联系人规模下变成 ANR？（SIR-983）**

凡循环里做去重、分组、逐项展开的代码，数据量放大后就是主线程重活；再叠加阻塞 IPC，输入调度稍慢即过 ANR 阈值。SIR-983 中三处主线程重活叠加：全量联系人去重比较、下载完成后主线程直调阻塞式 Binder IPC 拉全量大列表、主线程一次性把五千联系人转换成上万个列表项（按字母分组、每个号码展开一条记录）。

修复用最小侵入模板逐处异步化，以去重一处为例（节选自真实 diff）：

```java
// ContactsRepository.java：重活移到 IO 线程，主线程只收结果提交 UI
io.reactivex.Single.fromCallable(() -> {
            List<BluetoothPbapContact> deduplicatedContacts = deduplicateContacts(contacts);
            return deduplicatedContacts;
        }).subscribeOn(io.reactivex.schedulers.Schedulers.io())
        .observeOn(io.reactivex.android.schedulers.AndroidSchedulers.mainThread())
        .subscribe(deduplicatedContacts -> {
            this.mPbapContacts = deduplicatedContacts;
            refreshContactsUI();
        }, error -> LogUtils.e(TAG, "syncContactData deduplication failed: " + ...));
```

主线程只保留 `notifyDataSetChanged`、`postValue` 这类轻量 UI 提交。要点是把阻塞式 Binder IPC 与磁盘 IO 同级看待——返回大 Parcel 的跨进程调用在主线程同样是 ANR 高发点。该模板的隐患也要记住：订阅的 Disposable 未做生命周期管理、并发同步无串行化保护，会留下旧结果覆盖新结果的窗口。

**Q10: 除了 getProperty，属性注册（registerCallback）与 getCarManager 为什么也禁止主线程调用？（SIR-6325）**

它们同样是潜在阻塞的同步 Binder 调用，批量执行时阻塞还会叠加。SIR-6325 中下拉通知中心触发大量属性注册：Car 就绪回调在主线程调 `getCarManager`，注册注销又在主线程逐个执行 `registerCallback`，主线程被阻塞出现 ANR。修复是把 CarManager 获取与属性注册/注销全部移出主线程——Carlib 层提供 `getCarManagerAsync`（投递到与补拉共用的 `PROPERTY_READ_HANDLER`），注册走单线程串行 executor（节选自真实 diff）：

```diff
// PropertyManager.kt：注册移入串行后台线程，逐项 catch，回调按原契约切回主线程
+    private val propertyOperationExecutor = Executors.newSingleThreadExecutor { Thread(it, "CarPropertyOperation") }
         ids.forEach { propertyId ->
+            propertyOperationExecutor.execute {
+                // …（节选自真实 diff：try/catch 包裹单属性 registerCallback，失败不中断整批）
+                if (immediateCallback) { mHandler.post { callback.onChangeEvent(property) } }
+            }
```

批量注册逐项 try/catch，避免单属性异常拖垮整批；`immediateCallback` 场景把首次回调 post 回主线程，保持业务回调线程语义。

该案例还有一个独立的时序教训：`dispatchPageVisible` 对"目标页本就可见"的分支直接跳过 `onPageVisible`，吃掉了"页面保持可见期间状态发生变化"的场景（授权发生在通知中心可见期间，查询不重跑）。可见性回调应当幂等可重入，去重只能用于真正幂等的渲染。

**Q11: "乐观更新 + 延迟反馈兜底"与真实回调并存时，延迟任务必须怎么处理？（SIR-3241、SIR-8205）**

延迟任务必须可取消：真实事实源到达时要撤销未执行的兜底任务；无法取消时，任务执行前必须校验触发条件仍然成立。两个案例分别是这两道防线的证据。

**Q23: 一次性提示、一次性标志的生命周期管理原则是什么？（SIR-4602）**

消费即复位：标志位置 true 的同时就要写好所有 false 路径（用户确认、取消、业务结束、断连）。SIR-4602 中"流转"提示标志置 true 后没有任何复位路径，之后每通电话都命中"标志已设置"分支重复弹窗；配套的时间戳窗口也有同样的粘滞——窗口判定命中后连接时间戳不清零，且每次蓝牙状态回调都刷新时间戳，窗口被不断续期，后续通话持续误命中。

用户确认路径的消费方法（节选自真实 diff）：

```java
// FloatCallWindowPresenter.java：确认后一次性清空全部标志与时间戳

+        mHasActiveCallBeforeBluetoothConnect = false;
+        mCallStartedDuringBluetoothDisconnected = false;
+        mLastBluetoothConnectTime = 0L;
+        Constants.setCirculation(false);
+    }
```

配套时间窗口判定命中后立即消费时间戳（置 0），窗口只允许第一通电话命中，防后续事件搭车；时间戳只在真实连接沿记录、断开即清零，重复状态回调不再续期窗口，窗口本身从 10s 收紧到 5s。设计层面的判断：布尔标志加时间戳双条件容易互相续命，收敛为单一状态机可根治此类粘滞。

**Q24: 依赖外部服务初始化的 UI 状态，如何应对"服务慢启动丢查询"的时序竞态？（SIR-6170）**

建立"连接建立后重查全量状态"的补偿路径，且补偿清单必须与初始化查询清单对齐。SIR-6170 中 SystemUI 启动时向 L2A 查询 HUD 信号初值，但此刻 L2A 尚未连接，查询请求丢失，UI 停留在默认高亮态；已有的补偿机制（检测到连接由断变通时补查）清单里漏了 HUD 总开关，导致自动亮度与亮度条被刷新、总开关仍是错的——补偿清单漏一项就出一个必现 UI 状态 bug。

**Q25: 长驻进程对车服属性的订阅为什么会"静默失效"？订阅链路异步初始化必须配哪三件套？（SIR-5446）**

因为框架可能不派发断连回调——Carlib 只建一次 Car 连接，ready=false 不来时订阅永久失效且无日志，进程看似正常、档位等信号再也不来，SIR-5446 中表现为 SystemUI 偶发无法进 D 档。三件套分工：看门狗负责"发现失效"，代际令牌负责"丢弃过期初始化"，重连补注册负责"恢复订阅"。

异步获取 manager 的窗口本身也是竞态源：期间若断连，过期的初始化结果仍会把连接状态错误置回。初始化结果因此必须携带代际令牌（节选自真实 diff）：

```diff
// PropertyManager.kt：异步初始化结果带代际令牌，过期回填被丢弃（节选自真实 diff）
+        val generation = ++connectionGeneration
         Thread{
+            val manager = try {
+                car.getCarManager(Car.PROPERTY_SERVICE) as CarPropertyManager
+            } catch (e: Exception) { null }
             mHandler.post {
+                if (generation != connectionGeneration) { return@post }
+                carPropertyManager = manager
+                if (manager == null) {
+                    CarConnectionManager.requestReconnect()
+                    return@post
+                }
+                reregisterAllCallbacks()
```

代际不匹配的回填在 post 回主线程前即被丢弃；manager 获取失败则触发重连；重连成功后 `reregisterAllCallbacks()` 按注册表补注册全部属性回调，恢复档位订阅。看门狗是 20s 周期巡检："未连接且未在重连"的静默断连连续 3 次即 `forceReconnect()`，专治无回调可等的场景。同一思想在本仓库有两层落地：连接级初始化用代数计数丢弃过期 UI 初始化结果，订阅链路用代际令牌丢弃过期连接初始化——评审任何异步初始化时都应默认检查代际保护。边界：该缺陷偶现且 HAL 层疑点未排除，此修复属规避加兜底而非确定性根治；巡检间隔要远小于业务可容忍的信号中断时长。

**Q26: 蓝牙来电挂断后浮窗 1.56s 才消失，时延预算被异步链路的哪几段吃掉？终态事件该怎么走？（SIR-2617）**

终态事件混在通用状态机的重处理链路里，被多段排队与无效更新层层延迟；终态（挂断/断开）应走直达快路径，并让视图"先不可见、再清理"。SIR-2617 中挂断后浮窗平均 1.56s 才消失（产品标准 0.5s），三段叠加吃掉预算：状态变化处理先 `postDelayed(..., 0)` 排队、`updateOngoingCallView` 未过滤 DISCONNECTED 仍做"通话中"视图更新、`showEmptyUI` 把 `setVisibility(GONE)` 排在清理链最后。

修复为断开事件增加直达快路径，在处理现场直接驱动清理（节选自真实 diff）：

```diff
// FloatCallWindowPresenter.java：断开事件绕过状态机排队直达 showEmptyUI
+        InCallServiceImpl.SDisconnectCallback = () -> {
+            LogUtils.d(TAG, "SDisconnectCallback onDisconnect()");
+            if (getView() == null) return;
+            getView().showEmptyUI();
+        };
```

`updateOngoingCallView` 过滤 DISCONNECTED 后不再做无谓更新；`showEmptyUI` 把"不可见"提到第一步、HUD 配套视图移除放最后——用户立刻看不到浮窗，耗时收尾在不可见后完成；`postDelayed(..., 0)` 一并移除。方法结论：性能时延指标要测端到端链路，通用链路上的每一跳（postDelayed、无关刷新、清理顺序）都在吃预算；终态事件值得一条直达快路径，不与中间态共用重处理链路。边界：快路径的静态回调持有 Presenter lambda，不置空可能引用泄漏，且依赖 `InCallServiceImpl` 与 Presenter 的生命周期顺序。
