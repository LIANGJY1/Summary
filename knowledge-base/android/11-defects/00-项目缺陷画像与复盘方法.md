# 项目缺陷画像与复盘方法：从 85 天提交流读出质量结构

> 学习资料（文章模式沉淀）。主线：某车机项目 85 天窗口的 1010 条提交复盘显示，缺陷分布有稳定的权重结构（UI 还原 34.7% 居首，信号、状态缓存、蓝牙、异步时序依次随后），A 级缺陷沿"偶现=并发/状态机、必现=多系统联调/启动时序"两条规律线分布，而"缺陷库根因填充率 98.7% 对提交自带完整 why/how 仅 27.9%"的对照决定了复盘必须双源取数、以 diff 为准。源文档：`Summary/project/yadi/git提交与缺陷分析/00_主报告_Git提交与缺陷复盘.md`（数据截至 2026-09-18）、`附录_Feature与其他提交.md` 及 `逐commit详析/` 流程类深案例。Q 序列即结构，供 atlas 同源直读。六大根因模式的技术细节由同目录分册承载：[./01-车控信号语义.md](./01-车控信号语义.md)、[./02-主线程与异步时序.md](./02-主线程与异步时序.md)、[./03-蓝牙机制.md](./03-蓝牙机制.md)、[./04-Kanzi双端状态同步.md](./04-Kanzi双端状态同步.md)、[./07-崩溃防护与偶现排查.md](./07-崩溃防护与偶现排查.md)。2026-09-26 修订：补代码级讲解与深案例覆盖。

**Q1: 某车机项目 85 天开发窗口的提交流呈现什么样的缺陷画像，为什么说它处于"功能开发在前、提测放量在后"的密集修复期？**

画像的三个核心数字：非 merge 提交 1010 条中缺陷修复 761 条（75.3%）、功能开发 241 条（23.9%）、其他 8 条；修复共涉及 543 个去重缺陷单；月度修复量从 6 月的 34 条一路爬升到 9 月上半月的 319 条（7 月 189、8 月 219）。

"功能开发在前、提测放量在后"正是从这条月度曲线读出来的：功能提交带着需求单号从 6 月底开始入库，修复量却逐月放大、在 9 月上半月达到峰值——缺陷流入滞后于功能合入约一个月，是提测批量展开后的必然结果。修复占非 merge 提交的四分之三，说明这段时间仓库的主旋律不是加功能而是还债。

判断规则：看两个量即可给项目定位——月度修复量是否持续爬升、修复占非 merge 提交比例是否超过七成。两者同时成立时，质量投入应向修复吞吐与回归矩阵倾斜，而不是继续堆功能排期。

**Q2: 被修复缺陷中必现占 79.2%、已闭环占 89.5%，这两个比例分别说明测试与修复流程处于什么状态？**

口径为某车机项目 85 天窗口的 543 个被修复缺陷单。必现（复现率 80%~100%）430 个、占 79.2%，偶现（低于 10%）只有 23 个、占 4.2%——绝大多数问题常规冒烟即可发现，短板不在"测不出"，而在"流入量大"。闭环 486 个、占 89.5%，说明修复吞吐跟得上缺陷流入，流程处理能力健康。

两个比例合起来还给出一个提示：闭环率高是"处理能力"指标而不是"质量好"指标，真正决定产品体验的是未闭环的 10% 和占 4.2% 的偶现缺陷。偶现数量虽少，却是 A 级的主力形态之一——11 个 A 级中有 5 个是偶现或低概率，它们靠加用例兜不住，必须靠机制分析。

收束：必现问题用提测矩阵兜底即可，偶现问题要单独走"并发/时序专项分析"的处置路径，两条线不能混用同一套方法。

**Q3: 根因分布中"UI 还原与主题适配"以 34.7% 高居第一，这个权重对车机项目意味着什么？**

761 条修复中 264 条（34.7%）归类为 UI 还原与主题适配，是第二名"信号与协议"（88 条）的三倍。子形态包括颜色字号字重间距与设计稿偏差、深色资源缺失或用错、设计稿版本混淆、动态资源名绕过深色资源限定符、多模块同名资源遮蔽等。

这个权重说明车机 UI 有结构性难度：界面面积大、日夜双主题、多屏多分辨率矩阵，任何一个新增颜色漏配深色值就是一条缺陷。因此 UI 还原不是"低技术含量的杂活"，而是第一缺陷源；它主要是资源覆盖完整性问题而不是手艺问题，用制度兜底比靠个人细心有效。

投入含义：UI 提测必须跑"日夜×分辨率"矩阵；评审把"新增颜色是否配深色值、动态资源名是否改为静态引用"作为固定检查项。收束规则：凡项目带双主题与多屏矩阵，UI 还原大概率就是根因第一大类，资源规范先行是性价比最高的预防。

**Q4: 信号与协议 11.6%、状态管理与缓存 10.1%、蓝牙机制 9.6%、异步时序与竞态 7.5%，这四类权重如何转化为评审与测试的重点排序？**

口径为某车机项目 761 条修复的互斥归类：这四类合计约 38.8%（559 条），加上 UI 还原后前五类覆盖全部修复的七成以上——权重本身就是"代码改动最容易出错的机制域"排序。各类错误有不同的可观察特征，对应不同的评审抓手。

按权重排序的抓手：

- **信号与协议（11.6%）**：错误多为静默失效，评审重点放在值域换算、超时语义与状态域/命令域区分。
- **状态管理与缓存（10.1%）**：错误表现为残留与滞后，评审重点放在重置路径是否成对清理、缓存是否滞后于事实源。
- **蓝牙机制（9.6%）**：错误集中在连接状态机与跨进程协作，评审重点放在状态互斥与跨进程单例。
- **异步时序与竞态（7.5%）**：错误只在特定时序暴露，评审重点放在回调生命周期、延迟任务可取消性与主线程阻塞。

反向加权一条：占比 7.5% 的异步时序却是偶现 A 级的主要来源，评审权重不能只按占比线性分配——低频高害类别要额外加权。这四类的技术细节由同目录 02、03 册承载，此处只取权重与抓手。

**Q5: 根因统计中"其他（描述过短）"占 10.1%，这个类别对整套分布数字构成什么口径约束？**

某车机项目口径下 77 条修复（10.1%）因提交消息与缺陷库描述都过短而无法可靠归类，被单列为"其他"。这个桶的存在给所有分布数字加了两个约束。

约束一：各类占比只对"可归类部分"成立，绝对值应理解为量级而非精确份额——若这 77 条里多数实为 UI 问题，UI 的 34.7% 就被低估了。约束二：它本身是流程信号，"描述过短"与"提交自带完整 why/how 仅 27.9%"是同一件事的两面——信息在源头就没被记录，统计自然归不了类。

使用规则：用这类分布做决策时看排序与相对差距，不抠绝对值；治理方向不是修正统计方法，而是把描述质量提上来让"其他"桶收缩。收束：读任何根因分布报告，先看"无法归类"的桶有多大，再读各类占比。

**Q6: 11 个 A 级缺陷全部落在哪两条规律线上？这条规律如何用于排查与排期？**

口径：某车机项目 85 天窗口 543 个缺陷单中 A 级 11 个（2.0%），复盘发现它们全部与"偶现+并发/状态机"或"必现+多系统联调/启动时序"相关，其中 5 个是偶现或低概率、6 个必现。

偶现侧的证据：通话状态切换的并发修改异常、多实例重复注册回调、主线程同步 Binder 阻塞、Fragment 销毁后回调继续刷新、界面退出未重置坐标——全是并发路径与状态残留缺陷，靠堆测试用例几乎抓不住。必现侧的证据：系统级音频通路阻塞（dsp/HAL 层）、流程弹窗缺关闭路径叠加状态机提前 return 的盲区、组合状态覆盖写丢失属性组、单例初始化早于存储就绪导致卡开机——冒烟必现，但定位要跨系统。

用途：偶现 A 级的排查从并发路径与状态机审查切入，而不是从"加日志等复现"切入；必现 A 级在联调排期里把启动时序与跨系统状态恢复列为独立验收项，不等联调暴露。收束：A 级占金字塔尖 2% 但条条卡死或卡开机，两条规律线是给"最贵的缺陷"划定的检索范围。

**Q7: 追溯性损耗有哪些形态？它们如何把"提交↔缺陷"的自动关联压到 75.4%？**

口径：某车机项目 85 天窗口 761 条修复提交，能精确关联到缺陷库的只有 574 条（75.4%）。损耗分六种形态：

- **无单号与占位**：85 条完全无可关联单号，其中大量是 `SIR-XXXX` 式占位，aar 更新、分支同步、日志调试类也在其中。
- **库外单号**：102 条引用的单号不在缺陷库导出内，旧工单系统单号约 60、跨域单号约 30、个别笔误。
- **类型错标**：feature 与 bugfix 互相标错 40+ 例。
- **重复提交对**：同一 diff 以两个单号先后入库，且单号交叉错标。
- **Change-Id 串号**：一个 Change-Id 挂多个单号。
- **搭车修改**：提交内容与单号声明的范围不符，如日志提交夹带真修复。

危害机制是同构的：每种形态都让"从缺陷单反查代码"或"从提交反查缺陷"至少断一个方向——游离提交无人认领，重复提交让修复计数虚高，错标把修复归给错误的问题。收束：自动关联的覆盖率上限由提交纪律决定，工具只能在已有信息里做匹配，补不出没写的信息。

**Q8: "缺陷库根因填充率 98.7%、提交自带完整 why/how 仅 27.9%"这组对照说明了什么，复盘应如何据此取数？**

口径：某车机项目 543 个被引用缺陷单中 536 个填有根因分析（98.7%）；761 条修复提交中仅 212 条消息自带完整 [why] 与 [how]（27.9%）。对照说明：缺陷单有单据流程强制，根因字段质量高；提交消息是自由文本、无强制，只对约四分之一提交可靠。

据此的取数策略：单号把两源接起来后，缺陷的现象、等级、频次、库方根因取缺陷库，实际改动与修法取 git diff，提交消息只当检索键与补充说明。两者冲突时以 diff 为准——某项目就有 A 级单的主单提交只含日志、真实修复在邻提交的实例，若信提交消息会把日志当修复经验沉淀。

深一层：98.7% 这个数也是复盘能自动化的前提——库端字段填充到位，批量解析与关联才有意义。收束判断：评估一个项目的可复盘性，先看缺陷库根因填充率与提交 [why] 完整率这两个数，前者决定库侧可信度，后者决定提交侧可信度。

**Q9: "提交↔缺陷库自动关联 + 逐 commit 精读"这套复盘方法是怎么运转的？**

方法分两个支柱。支柱一是自动关联：解析提交消息中的单号前缀（智能化域 `SIR-`、整车域 `VIR-`、旧工单 `YD-`），与缺陷库导出精确匹配，批量拿到每笔修复对应的等级、频次、状态与库方根因；某车机项目覆盖 574/761（75.4%），其余为追溯性损耗。支柱二是逐 commit 精读：对全部非 merge 提交逐条读 diff，每条产出固定五段——问题、根因分析（双源互证）、关键代码摘录、为什么能修复、复盘经验；该项目 85 天窗口产出 1010 篇、覆盖 1010/1010。

运转要点有三：特殊提交（aar 更新、分支同步、纯资源、建库）标注类型后不强行套"问题→根因"模板；描述与 diff 不符处逐条注明"以 diff 为准"；功能提交与修复提交分开统计、分别产出附录。

产出分三层：画像统计（分类计数与占比）、模式归纳（跨案例提炼的系统性规律，如"内部哨兵不得落入协议值域"）、深案例库（逐条可检索的坑与修法）。收束：这套方法的成本在精读环节，产出的是组织资产——后续同类问题可直接检索前科，不必重新踩坑。

**Q10: 逐 commit 精读为什么必须读 diff，而不能只汇总提交消息和缺陷库描述？**

因为提交消息与实际改动的失真是常态而非例外，只信消息会把错误经验写进知识库。某车机项目 85 天窗口内的三类实证：一笔 A 级必现单挂名的主单提交只含日志调整与死代码清理，真实机制修复在 17 分钟前的邻提交里；同一 diff 以两个单号先后入库且单号交叉错标，只看标题会把一次修复当两次；还有标题写 UI 适配、diff 却完全是另一套改动的串单提交。

所以精读的单位是 diff，单号只是检索键。处理规则：现象与复现信息取缺陷库（测试的描述通常更完整），根因与修法从 diff 推导，冲突时以 diff 为准并在产物中显式注明冲突点，不静默择一。

收束：任何"按提交消息统计"的复盘都应预留 patch 抽查——提交消息可以随手复制，diff 不能，这就是以 diff 为准的底层原因。

**Q11: 复盘统计时，重复提交对、类型错标与不适用模板的特殊提交应如何处理，才能不污染结论？**

处理原则按三类分别定，共同点是先定性、再入统计，而不是让元数据直接决定归类。

- **重复提交对**：用 patch 内容比对（等价于 patch-id）判定，同一 patch 只计一次修复；单号归属按 diff 内容归因，不看提交标题。
- **类型错标**：按标题与 diff 综合定性——feature 前缀但 diff 是修复的，计入修复并标注错标，不让标签决定归类；反向的 feature 提交挂需求单号混入修复批次会稀释缺陷统计，分析流水线应先按提交消息前缀（[feature]/[bugfix]）分流再入统计。
- **特殊提交**：aar 更新、分支同步、纯资源、建库类不强行套"问题→根因"模板，标注类型后排除出缺陷样本；某项目口径即 1010 条 = 761 修复 + 241 功能 + 8 其他，功能与其他另出附录。

收束：口径要显式写进报告（互斥归类、供量级参考），让读者知道每个数字怎么来的——口径不透明的统计比没有统计更危险。

**Q12: 同一单号被六个提交引用、另有单号被引用三四次，这类"多次返工单"应该如何解读？**

某车机项目口径：被引用最多的一单挂了 6 个提交，时间跨度半个多月、跨两个模块，其中多数是功能提交、少数是联调修复——说明该单是需求/联调性质，"引用次数"不等于"缺陷返工次数"；另有若干真实缺陷单各被修复 3 到 4 次。

解读分三种情况：

- **需求/联调单多次被引用**：单号颗粒度大于提交颗粒度，统计缺陷前先看单据性质，不能拿引用次数当返工次数。
- **真实缺陷单多次修复**：每次返工对应一次"第一次没打中真因"，这是根因分析质量的直接信号，应优先复盘——尤其当修复在相邻位置反复试探时。
- **单号性质不明**：需求单与缺陷单共用同一前缀时，前缀不足以判定性质，必须回到单据内容。

收束：单号是连接两源的钥匙，但钥匙不保证开到的都是同一扇门——以单据内容定性，以 diff 定修复。

**Q13: 修复的模块分布（车控设置应用 259 条居首）对新人上手与回归测试排布有什么指导意义？**

分布口径：某车机项目 85 天窗口 761 条修复中，车控车设应用 259 条、SystemUI 128、蓝牙电话 112、能量中心 82、Launcher 77、蓝牙音乐 45，前六个模块合计约 92%。缺陷密度与模块的信号交互面和状态复杂度正相关，车控设置类应用是绝对的质量重心。

三个用法：

- **新人上手**：先读跨模块的模式归纳建立复杂度地图，再按目标模块查深案例库——高频模块的每个功能点几乎都有前人踩坑记录。
- **回归排布**：测试资源按模块分布加权，质量重心模块优先跑日夜与信号矩阵，而不是各模块平均用力。
- **风险预估**：改动落在高密度模块时，评审与回归强度相应提高。

收束：模块分布是排人力、排测试、估风险的基数数据，一次复盘统计即可获得，性价比极高。

**Q14: 把"自动关联+逐 commit 精读"的复盘方法迁移到其他项目，哪些前提必须满足？**

四个前提：

- **单号体系可解析**：提交消息带稳定前缀的单号，缺陷库可导出且根因字段填充率足够——填充率不足时，根因分布会退化为提交消息文本分类，结论质量骤降。
- **提交消息有最低结构**：至少单号与类型标签两个解析锚点；某车机项目 [what][why][how] 模板执行率虽仅 27.9%，但单号锚点撑起了 75.4% 的关联率。
- **精读预算**：逐 commit 读 diff 是人力密集步骤，可按"先 bugfix 后 feature、先 A/B 级后 C/D 级"分批，或只精读高频模块。
- **口径透明**：互斥归类规则、特殊提交处理、冲突以 diff 为准，都要显式写明。

落地路径：先跑小样本（一个模块一至两周的提交）校准归类口径与产出模板质量，再放量到全量。收束：这套方法的本质是把个人经验转成组织可检索资产，前提齐备时，一个季度就能沉淀上千条带代码证据的案例。

**Q15: 同一 diff 以两个缺陷单号先后入库且单号交叉错标，这种"交叉串单"是怎么形成的？对修复计数和归因各有什么影响？**

多数形成于暂存区复用——一次全量 `git add -A` 把多个工单的改动带进同一提交，或本地分支 cherry-pick/合并后未去重，同一份 patch 被打上不同单号重复入库；影响是修复计数虚高（一次修复被统计两次）和归因错位（挂着 A 单标签的提交实际内容是 B 单的修复）。

某车机项目实例：同一天同模块 4 个 UI 提交两两成对重复、单号交叉错标——A 单（字体遮挡）的真实修复正确入库一次，又被错标 A 单把 B 单（按钮文案与底色）的修复重复提交一次；B 单同样一正一错，每个单号各挂着一笔自己内容之外的提交。判定用 patch 内容比对（排除提交信息）：

```bash
diff <(git show 5b443500 --format=) <(git show b6771acc --format=)   # 输出为空即同一 patch
```

两笔提交的 patch 完全一致、仅单号与标题不同，即可判定为重复对——修复计数按 patch 去重只计一次，单号归属按 diff 内容归因而非提交标题。Git 对内容完全相同的重复提交按"无变化"处理，代码不会因此回退，但缺陷库与提交历史的映射出现一对多混乱。

边界：patch 比对必须排除提交信息（`--format=` 置空），否则任何两笔都不相等；含二进制文件（图片、aar）的提交 patch-id 不稳定，需辅以改动文件清单比对；重复不一定是相邻提交，cherry-pick 到其他分支的重复要在全量提交范围内查重。

**Q16: 要在提交流水线上预防单号占位、类型错标与重复提交对，有哪些可落地的卡点？分别拦截什么损耗形态？**

三层卡点各管一段——pre-commit 校验提交消息格式（类型枚举、真实单号、模块白名单），CI 用 patch-id 对全量历史查重，MR 评审要求单号与 diff 范围 1:1 核对；分别对应入库前、入库时、合并前三个拦截点。

某车机项目 85 天窗口的损耗形态可逐条映射到卡点：85 条无单号提交中大量 `SIR-XXXX` 式占位，单号格式校验直接拒绝 XXXX 占位；40 多例 feature/bugfix 互标，类型枚举校验兜住；同一 diff 两个单号入库，CI patch-id 查重兜住；日志提交夹带真修复的搭车修改，靠 MR 评审核对"单号声明的范围 vs 实际改动文件"兜住。配套个人习惯：一个提交只 stage 一个工单的改动，多工单并行时用 `git add -p` 按工单拆分，不用全量 `git add -A`。

边界：卡点只能拦截格式可校验的损耗；描述空洞（why/how 缺失）、库外旧单号这类语义层问题机器判不了，仍靠评审与描述质量指标（如 [why] 完整率）兜底；pre-commit 钩子可被 `--no-verify` 绕过，关键校验须在服务端再执行一遍。

**Q17: 缺陷单挂名的主提交 diff 与缺陷描述明显不符时，如何找回真实的功能修复提交？**

沿"同作者、同模块、时间邻近、提交消息描述相似"四个条件在邻提交中回溯——配套提交通常与主单在几分钟到几小时内先后入库；找到后在复盘产物中显式标注两笔提交的关联，把修复经验记在含功能改动的那一笔名下。
