# 提交治理与防回归：让每笔提交可追溯、可复盘

> 学习资料（文章模式沉淀）。主线：某车机项目 85 天窗口 761 条修复提交的复盘显示，占位单号、类型错标、重复提交对、搭车修改、复制模板带出逻辑反转等提交纪律问题会系统性削弱缺陷追溯与回归精度，治理应在 pre-commit 校验、CI 查重与 MR 核对三层设卡。源文档：`Summary/project/yadi/git提交与缺陷分析/00_主报告_Git提交与缺陷复盘.md`（数据截至 2026-09-18）、`附录_Feature与其他提交.md` 及 `逐commit详析/` 流程类深案例。Q 序列即结构，供 atlas 同源直读。2026-09-26 修订：补代码级讲解与深案例覆盖。

**Q1: 提交消息的 [what][why][how] 模板为什么值得强制执行？某车机项目"自带完整 why/how 的修复提交仅 27.9%"损失了什么？**

模板的价值不在格式，而在把"现象、根因、修法"留在离代码最近的地方：评审者不查缺陷单即可理解一笔提交的意图，之后的考古者不必反推，自动化复盘工具能靠结构化字段做分类与关联。某车机项目 85 天窗口：761 条修复提交中仅 212 条（27.9%）自带完整 [why] 与 [how]。

执行率低的损失有三层：

- **追溯断链**：没有 why 的提交在作者离开后成为无主资产，无人能解释它为什么改。
- **统计退化**：根因归类只能依赖缺陷库单侧，提交侧信息归不了类，"描述过短"的桶因此膨胀。
- **误读风险**："修改 XX 逻辑"式的消息可以指任何改动，读 diff 的人只能靠猜重建动机。

同一项目缺陷库根因填充率却有 98.7%，说明差距不在人而在有无流程强制。收束：模板执行率决定项目可复盘性的上限，而执行率靠自觉守不住，pre-commit 校验是最低成本的强制手段。

**Q2: 提交消息里的 [why] 写到什么程度才合格？把标题原样复制进 [what][why][how] 三个字段为什么等于没写？**

[why] 的合格标准是给出机制层面的原因——至少能回答"当时的代码为什么在该场景下会出错"，而不是重复做了什么。把同一句话复制进三个字段（某车机项目真实提交：[what][why][how] 三个字段都是"能量回收 toast 修改"的复制），三个字段零信息增量，等于没有模板。

合格写法包含两层：触发条件（什么场景、什么输入、什么时序）与错误机制（代码为什么在该条件下出错）；[how] 写改动路径与关键决策。两个字段合起来，应能让没参与该修复的人不看 diff 也能复述问题与修法。

自检方法是删除测试：把三个字段当独立段落，逐个问"删掉它信息是否仍完整"，复制的字段必然过不了这个测试。收束：[why] 不是格式义务，是修复者与未来读者之间唯一的同步通道。

**Q3: 提交消息的 [影响等级] 与 [测试范围] 字段照抄标题时，回归范围声明如何失效？这两个字段应如何填？**

这两个字段是回归范围与风险评估的声明位。照抄标题后（某车机项目实例：某 toast 修复的 [测试范围] 字段就是标题的截断复制），测试无法从提交消息得出要回归什么，回归范围与实际 diff 脱节——夹带的改动、波及的相邻模块都不会进入回归清单。

填法：[影响等级] 按改动传播面定，纯资源改动、单模块逻辑、跨模块或跨进程分别对应不同档位；[测试范围] 写可执行的验收动作——页面、场景、需要覆盖的矩阵维度（如日夜、分辨率、连接状态）。判断标准是测试拿到字段能直接排用例，不需要再读 diff。

收束：评审把"测试范围是否覆盖 diff 触及的模块"作为机械检查项，字段与 diff 对不上的提交退回。

**Q4: SIR-XXXX 式占位单号是怎么产生的？它对缺陷追溯造成什么破坏？如何用工具拦截？**

某车机项目口径：85 条修复提交完全无可关联单号，其中大量使用 `SIR-XXXX`/`SIR-XXX` 式占位。占位的成因有三类：

- **修复先于提单**：缺陷单还没建，代码先提交了。
- **调试类提交不提单**：日志调整类改动被认为"不值一提单"。
- **复制忘改**：复制上一条提交消息后忘了换单号。

破坏在于该笔修复成为游离提交：从缺陷单反查代码时它不存在，从提交反查缺陷时它无处可归——复盘统计漏计、同区域后续改动时无人能发现这里有前科、回归时无人知道要覆盖它。某项目中 aar 更新、分支同步、日志调试类提交也在"无单号"之列，这类确实可以无单号，但必须与"漏填"区分开。

拦截的最小实现是一个 commit-msg 正则校验：

```bash
# commit-msg hook（示例）：单号必须为"库内前缀+数字"，占位与漏填一律拒绝
if ! grep -qE 'SIR-[0-9]{4,}' "$1" && ! grep -qE '\[(build|sync|log)\]' "$1"; then
    echo "commit blocked: 缺少合法缺陷单号，SIR-XXXX 占位视为漏填" >&2
    exit 1
fi
```

正则要求真实数字单号，`SIR-XXXX` 不含数字自然不匹配即拒绝；豁免标签让打包修复、分支同步这类确实无单号的提交显式声明身份，而不是混在漏填里。

收束：占位单号是"知道该填但不想填"的产物，工具拦截比规范呼吁有效。

**Q5: 提交引用缺陷库外部的单号（旧工单号、跨域单号），为什么会让复盘口径失真？单号域应如何约束？**

某车机项目 102 条修复提交引用的单号不在缺陷库导出内：已弃用的旧工单系统单号约 60 条、跨域单号约 30 条、个别笔误。失真有两种机制：库外单号匹配不到库内单据，这部分修复的等级、频次、根因全部缺失，统计出现"有修复、无缺陷"的空洞；更隐蔽的是笔误单号会命中一个不相关的真实单据，把别人的缺陷挂上不相关的修复，双向污染。

约束做法：单号域收敛到当前缺陷库的一个前缀；历史工单号只允许出现在正文说明段，不允许占据单号字段；MR 核对时验证单号在库内存在且性质与类型标签一致。

边界：跨域协作（如整车域单号）确实存在时，做法不是禁止而是登记映射——维护跨域单号与库内单据的对照，让库外单号显式可解释。收束：单号是自动关联的唯一钥匙，钥匙域不收敛，关联率就有天花板。

**Q6: 类型 mistag（feature/bugfix 互相标错，某项目 40+ 例）因何发生？它如何同时污染统计与回归范围？**

成因主线是联调期：修复发生在需求联调过程中，开发者顺手挂上需求的 [feature] 前缀提交而不单独提缺陷单（某车机项目一批联调修复全部以 feature 前缀入库）；反向的 bugfix 标错多来自复制消息模板没改类型段。某项目口径 40+ 例。

两类污染：

- **污染统计**：feature 被计入修复样本则根因分布虚高、功能数量虚低；bugfix 被计入功能则缺陷闭环被低估。
- **污染回归**：类型标签是回归范围的第一提示，feature 标签会让测试低估风险面——同一单号下既有需求提交又有联调修复时，按 feature 回归就漏掉了修复部分。

防法分两层：pre-commit 校验类型标签属于合法枚举只解决"乱写"；另一半是核对"类型与单号性质一致"（缺陷单挂 bugfix、需求单挂 feature），放在 MR 核对清单人工执行。收束：mistag 单笔看是小事，批量看会让整个根因分布失真。

**Q7: 模块段拼写出现同一模块的多种变体，说明缺什么约束？模块段应如何治理？**

某车机项目同一模块名在提交消息里存在三种拼写变体（正确名加两种笔误形态）。这不是手误问题而是约束问题：模块段没有白名单时，每个提交现场拼写，"按模块聚合修复量"的统计会被拆成多个假模块，模块分布、按模块检索深案例全部失真。

治理：pre-commit 校验模块段必须命中仓库目录名白名单——模块目录本身就是天然白名单，维护成本接近零；白名单变更随目录变更走代码评审。

收束：凡是"按某字段聚合统计"的数据，字段取值必须先收敛——模块段、类型段、单号前缀三者同理。

**Q8: 同一份 diff 被以两个不同单号先后提交（重复提交对），是什么工作流造成的？如何识别与预防？**

成因有两类：全量暂存——`git add -A` 把工作区中多个单的改动一起带入，先后以不同单号提交了重叠甚至相同的内容；本地分支 cherry-pick 或合并后未去重，同一修复重复入库。某车机项目实例：同一天同一作者的四个 UI 修复提交两两成对重复，diff 逐字节一致、仅提交消息不同。

识别用补丁内容比对，两条等价命令：

```bash
# 直接比对两笔提交的补丁（--format= 去掉提交消息，只留 diff）
diff <(git show 5b443500 --format=) <(git show b6771acc --format=)   # 输出为空即同一份改动
git show 5b443500 --format= | git patch-id --stable                  # 计算补丁指纹，供 CI 批量查重
```

该项目实例中，这两笔提交相隔 40 分钟、标题分别挂两个不同工单，diff 却逐字节一致（同一处按钮底色与"连接中…"文案改动），构成典型重复提交对。预防三层：

- **按单拆分暂存**：一次提交只 stage 一个单的改动，多单改动用 `git add -p` 按块挑选。
- **提交前核对暂存**：`git diff --cached` 确认暂存内容与单号声明一致。
- **CI patch-id 查重**：对近期合入提交计算 patch 指纹，重复即告警。

收束：重复提交本身通常不产生代码回退（Git 对相同改动幂等），但它让缺陷与提交的映射一对多失真，复盘统计被重复计数。

**Q9: 单号交叉错标（两个单的修复互相贴错标签）对缺陷库与代码历史的映射伤害有多大？复盘时应如何归因？**

某车机项目实例的完整链条：甲单的真实修复正确入库一次，又被以甲单号重复提交了一次乙单的内容；乙单同样被重复提交并错标为甲单——四个提交两两重复、单号交叉。伤害：从甲单号反查命中三笔提交，一笔真修复、两笔不相关内容，缺陷与代码的映射一对多失真；统计上同一修复计两次，模块修复量虚高。

归因原则：以 diff 内容归因而非提交标题——逐笔判断实际改了什么，再把它归给真正被修复的单。某项目的复盘正是靠 `git show` 逐字节比对才把四个提交还原成两次修复。

预防是最便宜的一步：评审时做"标题与 diff 互证"——该项目实例 `b6771acc` 的标题写"字体被挡住"，diff 却与 40 分钟前 `5b443500` 的按钮底色、文案改动逐字节一致，一眼可拦。收束：交叉错标几乎总是全量暂存提交的伴生品，治好暂存纪律，错标随之消失。

**Q10: Change-Id 串号（一个 Change-Id 挂多个单号）如何发生？为什么合入前必须核对单号与 Change-Id 的一一对应？**

Change-Id 的设计意图是让一个逻辑变更在多次评审、rebase、cherry-pick 之间保持稳定身份；串号通常来自复制上一条提交消息时连 Change-Id 一起复制，或 rebase/cherry-pick 时保留了旧值。

危害在于身份失效：按 Change-Id 聚合提交历史时，会得到内容无关的多笔提交挂在同一身份下——评审历史、单号历史、patch 集合三者对不上；任何"按 Change-Id 追一个变更全过程"的检索（定位引入点、界定回滚范围）都会被串号误导。

核对动作：MR 模板列入"一笔提交一个单号一个 Change-Id"检查，发现复用即退回，让作者重新生成。收束：单号声明"这是哪个问题的修复"，Change-Id 声明"这是哪次逻辑变更"，两个身份一一对应，追溯链才闭合。

**Q11: 搭车修改（一笔提交夹带与单号无关的改动）为什么必须拆分？如何用机械检查拦住它？**

某车机项目实例：弹窗修复夹带通话逻辑改动、日志提交夹带真实功能修复。危害链：单号声明的是 A 问题，测试按 A 回归，夹带的 B 改动无人回归——B 区域引入新缺陷时既无法归因也无人怀疑；复盘时夹带改动还会污染 A 单的根因分析，读 diff 的人会把无关 hunk 当成 A 的修法。

拆分规则：一笔提交一个意图；提交时发现顺手改了别的，把无关改动单独提单、单独提交——有缺陷单挂缺陷单，是顺手优化就写明并走对应评审。

机械检查："diff 触及的模块集合 ⊆ 单号与模块段声明的范围"，超出即告警或人工复核。收束：搭车省下的五分钟，由回归遗漏与复盘考古加倍偿还；单号的价值就在于它划定了回归与追责的边界。

**Q12: 一笔 A 级必现缺陷的主单提交只含日志调整、真实修复在 17 分钟前的邻提交——这种"单号挂错主角"如何发现与防范？**

某车机项目实例（SIR-7151，蓝牙音乐无法播放，A 级必现）：挂该单号的提交 diff 仅两处日志调整与死代码清理，不含任何播放链路功能改动；真正的机制修复（音源标志判定收敛、移除两处误覆盖）在 17 分钟前挂邻单号的提交里，两单描述同根同源。挂单提交的全部实质改动如下，可与"修复一个 A 级功能"的预期直接对照：

```diff
--- BluetoothPlayerService.kt（挂 A 级单号提交的全部实质改动，节选自真实 diff）
-            if (commandID != "dsi_lux") {
-//                LogUtils.d(TAG, "onCommState: commandID = $commandID; value = $value")
-            }
             if (commandID == "Meter_Form") {
+                LogUtils.d(TAG, "onCommState: commandID = $commandID; value = $value")
```

删除的是"if 包一行注释"的死代码块，新增的是一条日志——没有任何播放链路改动，与单号声明的 A 级修复直接矛盾，这一眼矛盾正是核对入口。

发现方法：A 级（或任何关键标记）的单合入时核对"提交 diff 是否与单号描述的问题匹配"——日志提交不可能是 A 级功能修复，这个矛盾检查零成本；复盘时沿同作者、同模块、相邻时间的提交回溯真实修复点，该项目正是用这方法定位到邻提交。

防范：一单多提交是合法形态，但每笔提交的消息要说明本笔承担的角色（修复、配套日志、清理），让"功能修复合入 A、日志清理单独成 B"从消息上可分辨。收束：以 diff 为准的复盘原则是这类失真的最后防线；单号加等级的组合会误导，diff 不会。

**Q13: 提交消息、缺陷库描述、代码 diff 三者不一致时，复盘应以哪个为准？为什么？**

以 diff 为准。三者中只有 diff 是确定发生的事实：提交消息是作者的事后声明（可以复制粘贴、可以占位、可以忘改），缺陷库描述经多人转手（测试描述现象、开发填根因，可能滞后于最终修法），而 diff 是版本控制系统记录的改动本体。

某车机项目的全量逐 commit 精读即采用"diff 与缺陷库描述不符处逐条注明'以 diff 为准'"的口径，1010 条中这类冲突并不罕见——A 级单挂日志提交、库方根因与实际修法对不上都有实例。

操作规则：现象描述取缺陷库（测试的复现信息通常更完整），根因与修法取 diff 分析；两者冲突时在产物中显式标注冲突点，而不是静默择一。收束：静默择一会让错误结论伪装成确认过的事实，显式标注冲突才能让读者自行裁决。

**Q14: 复制既有"pending 暂存+回显比对"模板时，条件判断的逻辑反转 bug 为什么会跟着一起复制过去？正确的复制姿势是什么？**

复制绕过了"为新场景重新推导每个分支"的过程：原模板的条件是围绕原场景真值写的，复制者往往只改变量名不改判断方向；条件写反通常照常编译、照常运行，只在特定回显路径上表现为误弹提示或漏弹，常规测试抓不住。某车机项目实例：开关"pending 暂存+回显比对"模板落地时，失败提示的条件整体写反（回显等于暂存时弹"切换失败"，实际应不匹配才弹），下一个提交才修正。两笔提交的条件差异只有取反号：

```diff
--- DrivingFragment.kt（模板落地时写反的条件与下一笔的修正，节选自真实 diff）
-            if (isStateMatched) {                     // e2ee6731：回显等于暂存却弹"切换失败"
-                showToast(R.string.slip_mode_switch_open_fail_tip)
-            }
+            if (!isStateMatched) {                    // 11d164b8：仅不匹配才进入失败提示
+                showToast(R.string.slip_mode_switch_open_fail_tip)
+            }
```

写反时"成功回显弹失败提示、真失败反而静默"，且编译运行都正常——这正是它穿透常规测试的原因。

正确姿势：复制后列出输入组合真值表（本例为匹配/不匹配 × 暂存有值/无值四格），逐格核对预期行为与代码行为；有条件就用单测钉住各分支，没有单测就评审时逐分支走读，而不是只确认"长得跟模板一样"。

收束：模板是加速器也是错误放大器——它复制的不只是结构，还有结构里的语义，语义核对不能省。

**Q15: "pending 暂存+回显"模板从落地到收敛经历三个提交，这段收敛史说明这类机制的验收标准是什么？**

收敛史（某车机项目，同一模块连续三笔提交）：第一笔引入模板并带出失败提示条件反转；第二笔修正条件方向；第三笔修复页面重新可见时 LiveData 重派发旧值、与残留 pending 不匹配而误弹"切换失败"toast 的问题——把"取消回弹/弹失败提示"收敛为单出口结构，并在 onStart 统一清空全部 pending。第三笔补的"生命周期清空"防线：

```kotlin
// DrivingFragment.kt（收敛提交新增的 onStart 防线，节选自真实 diff）
+    override fun onStart() {
+        super.onStart()
+        // 界面重新可见时清空待确认状态，避免 LiveData 重新派发旧值导致误弹 toast
+        drivingModeStateTemp = INVALID_STATE_VALUE
+        slipModePendingState = null
+        extremeRangePendingState = null
+    }
```

LiveData 重派发最后一次值是 Android 既有行为，页面重建后残留的 pending 必然撞上重派发；onStart 统一清空让每轮回显判定从干净状态开始。

这段收敛史说明验收标准至少有三条：

- **单次回显消费**：pending 必须在单次回显中被消费，消费后立即置无效值，否则重派发会造成二次判定。
- **生命周期清空**：LiveData 重派发最后一次值是 Android 的既有行为而非异常，页面重建后残留的 pending 必然撞上它。
- **单出口三态穷尽**：成功、失败、暂存为空三态互斥且穷尽，比对结构收敛到一条判断链。

边界：onStart 清空 pending 意味着"切走页面瞬间发出的指令"的回显不再比对，属于用体验换正确性的取舍，评审时要显式确认。收束：复制这类模板时，把三条不变量当检查单逐条过。

**Q16: 把另一分支的适配方案 cherry-pick 到主干，为什么可能在几小时内被整体回退？跨分支搬运前应确认什么？**

某车机项目实例：账号中心"摘除 uiMode 的 configChanges + 颜色令牌化"的换肤方案（cherry-pick 自另一分支），合入主干 5 小时后被同作者以逐行互逆的提交回退，78 行改动一一对应、符号相反。这对提交的核心 hunk 方向完全相反：

```diff
--- AndroidManifest.xml（正向提交摘除 uiMode，回退提交逐字符还原，节选自真实 diff）
-            android:configChanges="screenLayout|screenSize|smallestScreenSize|orientation|uiMode|locale|layoutDirection|touchscreen"
+            android:configChanges="screenLayout|screenSize|smallestScreenSize|orientation|locale|layoutDirection|touchscreen"
```

`uiMode` 一旦摘除，昼夜切换就从"应用自己处理配置变化"变为"系统重建 Activity"——方案成立的前提随分支上的组件形态而异，不随 diff 一起迁移。

原因在方案的前提不随代码迁移：configChanges 组合是每个应用自己声明的生命周期契约，摘掉 uiMode 后昼夜切换触发 Activity 重建，该应用的登录表单与第三方拉起的弹窗可能丢状态或闪屏；且该适配可能本属另一车型分支，被误搬入主干。回退本身是干净的（逐行互逆保证行为等价），但成本已经发生。

搬运前确认三件事：

- **组件形态一致**：目标分支上该组件的 manifest 声明与生命周期契约和源分支相同。
- **前提在目标分支成立**：方案依赖的条件（状态可重建、无外部拉起场景）逐项核对。
- **标注搬运来源**：提交消息注明出处分支，出问题时能快速定位回退对象。

收束：cherry-pick 复制的是 diff，不是 diff 成立的条件。

**Q17: 回退提交不用 Revert 字样、沿用原提交的同名标题，为什么是追溯败笔？回退提交的规范做法是什么？**

同一案例中，回退提交与 5 小时前的正向提交同名同作者、方向完全相反，标题却仍是"黑夜模式适配"——不逐行比对 diff 就无法识别这是回退，日志考古成本翻倍，统计还会把它当又一次"适配"计入工作量。

规范做法：优先用 `git revert` 生成回退提交，自动保留原提交引用与互逆关系；手写回退时标题注明"回退 <原提交>"，正文写明回退原因；类型标签与被回退对象保持一致。回退是合法操作，隐瞒回退身份不是。

收束：判断提交消息好坏的一个硬标准是"三年后只读日志能否还原发生了什么"——反向同名提交过不了这个标准。

**Q18: pre-commit 与 CI、MR 三层各应设置哪些防回归检查，把提交纪律变成卡点？**

pre-commit 层三项校验，commit-msg hook 正则即可实现，把发现问题从"复盘时"提前到"提交时"：

- **类型枚举校验**：类型标签必须属于固定枚举，杜绝自造变体与漏写。
- **单号格式校验**：单号必须匹配"库内前缀+数字"的正则，显式禁止 XXXX 式占位；无单号提交必须走固定豁免标签。
- **模块白名单校验**：模块段必须命中仓库目录名清单，杜绝同模块多种拼写。

CI 层两项自动检查：patch-id 查重拦截重复提交对与未去重的 cherry-pick；单号存在性校验确认单号在缺陷库可查、且单据性质与类型标签一致（缺陷单挂 bugfix、需求单挂 feature）。

MR 核对清单四项（模板化人工执行）：单号与提交一一对应，复用 Change-Id 或串号即退回；diff 触及模块与单号、模块段声明一致，拦搭车修改；[测试范围] 覆盖 diff 触及的模块，拦回归范围失真；回退提交注明对象与原因。

边界：本机 hook 可被 `--no-verify` 绕过且不覆盖所有环境，pre-commit 必须配合服务端 CI 复检才闭环。这套清单的每一项都对应某车机项目 85 天窗口实测过的失真形态：占位单号 85 条、库外单号 102 条、类型错标 40+ 例、重复提交对、Change-Id 串号、搭车修改。治理的回报不止于规范本身——提交侧数据质量上来后，"提交与缺陷库自动关联+逐 commit 精读"的复盘才能自动化运转，缺陷库 98.7% 的根因填充率已经证明这五分钟值得花。

**Q19: 一个需求单号被六笔互不相关的提交共用（"口袋单"），从单反查提交时会发生什么？应如何治理？（SIR-3401）**

单号失去"这笔改动为哪个问题而做"的区分度：从该单反查得到一串互不相关的改动——某车机项目同一需求单号在 85 天窗口被六笔提交引用，内容横跨锁屏信号联调、歌词页面功能、密码错误推送对接、丢失模式 UI 更新、主交互状态机需求逻辑，每笔改动都无法被单号描述圈定回归范围；引用次数多还会被复盘误读成"返工最多"的缺陷单。

治理三条：

- **按子任务拆单**：需求包含多个可独立交付的子项时，每个子项有自己的单号，一笔提交引用最能描述其内容的那个。
- **消息写明子需求**：确需多笔提交共同交付一个需求时，每笔提交消息注明本笔承担的子项，让"从单反查"至少能按描述分拣。
- **复盘先归因再计数**：解读"同一单号多次引用"时先区分需求迭代、真返工与口袋单，不能默认按返工次数计入质量损失。

收束：单号是回归与追溯的最小分配单元，一个意图一个单号；"引用次数多"是核查信号，不是统计结论。

**Q20: 跨系统需求在依赖方（如 Linux 仪表侧）尚未就绪时，如何把应用侧改动安全合入主干并保留整体回退能力？（SIR-3401 的特性开关做法）**

把新行为整体包进一个临时特性开关，默认关闭合入主干，依赖方就绪后再打开；开关必须写明删除条件。某车机项目的跨系统主交互适配即以此方式交付，多个新逻辑挂在同一标志下，回退成本一行代码而不是一次提交回滚：

```kotlin
--- DataContext.kt（临时特性标志的声明与注释，节选自真实 diff）
+    var linuxDockAdaptationEnabled: Boolean = false,
+    // Linux 仪表侧适配总开关（临时特性标志，默认关）…对接稳定后删除此标志即为永久启用
```

观察标志的声明：默认关保证"合入即安全"，主干随时携带这套逻辑而不激活；注释直接写明删除条件，把"临时"变成可核查的承诺。

边界两条：开关只覆盖被包裹的逻辑，未纳入开关的行为（该需求中 G6/G7 两项）不享受整体回退能力，需单独评审；"稳定后删除"是承诺，遗忘即长期双路径维护负担，应把删除项挂进需求闭环清单。收束：特性开关是"提交可回退性"在需求维度的延伸——回退粒度从提交级细化到特性级，代价是多一条需要生命周期管理的配置。
