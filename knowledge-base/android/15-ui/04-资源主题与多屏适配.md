# 资源、主题与多屏适配

> 学习资料（文章模式沉淀）。主线：资源限定符的选择与顺序规则、默认资源兜底与版本限定符、深色模式的三个处理面、动态取色与车机品牌主题的取舍、主题属性作用域与叠加、运行时资源叠加（RRO）与车机定制契约、dp/sp/fontScale 与无障碍字号、资源限定符不等于窗口尺寸、车机多屏下的 Configuration 分歧、多语言与 RTL、多变体布局与 ViewBinding 字段缺失、运行期 Configuration 变更纪律、生效变体的探针方法。规则按官方文档与 AOSP 约定口径（2026-09 检索），车机项目里"定制系统改过资源后兜底不可信""ViewBinding 跨变体联合字段缺失"两条真实踩坑已在 [../../android-ui.md](../../android-ui.md) 就地记录，本文只给机制侧解释。Q 序列即结构，供 atlas 同源直读。

**Q1: 资源限定符按什么规则选？顺序写错为什么会静默失效？**

限定符的匹配不是"越具体越优先"的自由排序，而是一张官方文档给定的固定优先级表：先按地区与语言、再按布局方向、再按最小宽度与可用尺寸、再按可用高度、再按屏幕宽高类别、再按屏幕长宽比、再按方向、再按 UI 模式（夜间）、再按密度、最后是平台版本。多限定符目录必须按这张表的顺序书写，顺序错误时资源系统不会报错，而是把该目录当成无法识别的限定符序列，于是永远匹配不上。

例：`drawable-night-hdpi` 有效，`drawable-hdpi-night` 无效。判断办法是先回文档查优先级表，再对照目录名逐位检查，不要靠记忆。

**Q2: 找不到匹配的限定符变体时回落到哪里？为什么必须保留无限定符的默认资源？**

回落到同类型资源的默认目录（不含任何配置限定符的那一份），不是"找最接近的一个"。官方文档明确警告：如果一个资源只提供了带限定符的变体而没有默认变体，当设备配置不匹配时会得到 `Resources.NotFoundException`，典型案例是字符串只放在 `values-en` 而默认语言目录缺这一条，用户切回默认语言就崩（官方文档口径）。

因此每新增一种限定符，都要检查该类型资源是否仍有一份默认版本；清单式做法是新增限定符后跑一次"最低 minSdk + 最高 minSdk"两端的构建或冒烟。

**Q3: 为什么有些新限定符在老设备上"配了等于没配"？**

因为使用新限定符等于隐式加上该限定符引入时的平台版本限定符，老系统既不识别这个限定符也不匹配对应版本，于是只能落到默认目录。也就是说 `values-w600dp` 在 API 13 之前等价于"带 v13 版本限定符"，老设备必然取默认资源。这条规则是兼容策略的一部分，但也意味着"资源没生效"的第一嫌疑是"目标设备版本低于该限定符的引入版本"。

**Q4: 支持深色模式要处理哪三件事？它们之间是什么关系？**

三件事各管一段，缺一不可：

- **资源层**：把颜色、位图、主题属性等在夜间不同的值放到 `values-night` 与 `values-night` 的 drawable 等变体里（该限定符自 API 8 提供）。
- **读取层**：通过 `Configuration.uiMode` 与 `UI_MODE_NIGHT_YES`/`NO` 位掩码判断当前是否夜间（`Configuration.isNightModeActive()` 是同一判断的便捷封装），或用 `UiModeManager` 做应用级覆盖。
- **主题层**：主题本身要随模式切换（`Theme.Material*` 家族已具备），自定义主题则必须显式提供夜间版本，否则夜间只是"文字变白、背景还是白的"。

三者关系是：UI 模式变化是一次 Configuration 变化，默认会触发组件重建，所以运行期切换看起来"整页闪一下"；若在清单里声明了 `configChanges` 并自行处理，就必须自己重新解析受影响资源并刷新界面（官方文档口径）。

**Q5: "系统已经是深色模式，应用却没变深"怎么定位？先排除哪些误判？**

按发生位置分三层，逐一排除：

- **应用资源层**：确认是否存在夜间变体、限定符顺序是否正确、是否被"默认目录已有一份同类型资源"命中（Q2）。
- **系统主题层**：车机与定制系统常把应用主题强制替换为厂商主题（组件 overlay 或主题应用），此时应用自己的夜间资源可能根本没被使用。
- **定制框架层**：厂商可能改写了资源回退逻辑或主题应用顺序，"存在默认资源"不再等于"一定回落到它"。这种情况下不要靠推理，用探针实测：打印当前 `Configuration.uiMode`、`density`、`fontScale`，并在运行时反查某个已知 id 实际落到了哪个资源文件，据此建立事实基础（对应 [../../android-ui.md](../../android-ui.md) 里的资源探针条目）。

**Q6: 动态取色在车机上为什么常常不用？**

动态取色是 Android 12 起面向手机壁纸主题的机制：应用可从系统取色板生成自己的调色板（官方文档口径）。车机与工业场景通常有强制品牌规范——仪表与中控的配色属于法规与品牌的一部分，还涉及日夜模式的对比度要求；而车机壁纸往往不存在或与品牌色无关。此时跟随壁纸会让同一套界面在不同机器上呈现不同主色，破坏可识别性与一致性。

判断规则：品牌色是硬约束时用固定主题，关掉动态取色；只有当车机确实以壁纸配色为卖点、且已验证对比度可达标时才启用。

**Q7: 主题属性 `?attr` 与 `?android:attr` 的作用域有什么差别？**

`?android:attr/...` 取的是平台定义的属性，`?attr/...` 取的是当前应用或组件库自己定义的属性。前者在使用平台控件、引用平台内置主题属性时必要，后者用于组件库主题。当属性名在两处同名但含义不同（例如颜色与维度同时自定义），写错前缀会得到"能编译但取到别的值"的结果，且不易察觉。

配套纪律是主题继承：一个应用主题应继承一个基础主题再覆盖差异项，而不是复制粘贴整套属性；属性一旦成为对外契约（被 overlay 覆盖、被第三方应用引用），改名等于破坏兼容，这与 SDK 设计是同一类问题（[../../sdk-design.md](../../sdk-design.md) 讨论这类契约）。

**Q8: 运行时资源叠加（RRO）与编译期 overlay 有什么区别？车机的定制契约是什么形态？**

- **编译期 overlay**：在构建系统镜像时把 overlay 目录的资源合并进目标包，产物是固定的镜像，适合系统与供应商在同一份源码树上协同。
- **运行时 RRO**：目标包与 overlay 包在设备上分别安装，由资源管理子系统按策略在运行时替换资源，可按目标包、按属性、按屏幕状态等维度限定生效范围，且能覆盖运行时才存在的包。

车机 Car UI 库的官方做法是把"哪些资源可被定制"当作对外 API 来管理，生成定制的资源契约，并对定制失败提供专门的排障指引（source.android.com 文档口径）。工程含义是：定制点要少而明确，每个可覆盖资源都要考虑"被覆盖后应用是否仍能正常渲染"，因为覆盖发生在运行时、不会在编译期暴露错误。

**Q9: dp、sp、px 与 fontScale 怎么用？无障碍大字号为什么容易让布局溢出？**

长度用 dp、字号用 sp、绝不用 px 写死尺寸（官方文档口径）。`sp` 会跟随系统字体缩放 `Configuration.fontScale`，`dp` 不跟随。后果是：用户把字号调大时，文字尺寸放大而容器尺寸按 dp 不变，固定高度容器先溢出，多行文本再让高度继续增长；一张写死 dp 高度的图与一列文字同时出现时，两者永远不会同比例缩放。

正确做法是让容器高度由内容决定（用 wrap 语义加最小高度），而不是给文本容器写死高度；在需要严格适配的场景提供可选的大字号布局变体，并把"最大字号下不破版"作为验收项——这是可访问性的硬要求，不是体验优化。

**Q10: 资源限定符反映的是设备配置，不是窗口尺寸，这带来什么后果？**

资源变体的选择依据是 Configuration，而 Configuration 描述的是设备/显示的属性。在可调整大小的窗口（分屏、自由窗口、折叠屏展开）里，同一台设备同一时刻可以存在多个尺寸的窗口，而 Configuration 不随之变化；这意味着按 `sw600dp` 之类最小宽度限定符切换布局，在自由窗口下可能"选错了变体"。

工程结论有两条：资源层只处理设备级差异，窗口级差异用运行时判断（取本次布局拿到的可用宽度，或用按窗口分档的方案自行判定）；适配决策不要绑死在 Configuration 上（多窗口下的窗口几何见 [01-窗口系统与WMS.md](./01-窗口系统与WMS.md) Q12）。

**Q11: 车机多屏下，同一应用在不同显示上的资源与尺寸分歧体现在哪？**

车机上同一应用可能被创建到多个显示（不同座位区的屏幕），这些显示在分辨率、密度、尺寸类别上可以完全不同；Activity 的 Configuration 是按显示来定的（02 册 Q13）。常见后果有三个：

- 只提供一套横屏布局的应用在窄屏座位区显示上被拉伸或截断。
- 用 `DisplayMetrics` 里的全局默认值而非当前显示值计算尺寸，导致位置偏移。
- 深浅色与字号按"系统设置"统一取值，无法按屏区分。

对策是按"显示"而非"设备"取度量：布局参数从本次 relayout 的窗口尺寸来（01 册 Q12），密度与 Configuration 从当前 Activity 的上下文取，必要时按显示 id 显式查询并为不同屏幕准备独立资源变体。

**Q12: 多语言与 RTL 的正确做法是什么？只翻译一半会出什么问题？**

- 位置语义用 `start`/`end` 而不是 `left`/`right`，并在清单里声明支持 RTL，布局方向变化时框架会镜像。
- 需要非镜像的资源用 `-ldrtl`/`-landrtl` 限定符提供"RTL 且指定语言方向"的变体；注意 `ar` 这类语言限定符优先级更高，会压过 `ldrtl`。
- 文案不要硬编码进布局，长文案容器要能换行并考虑截断策略。

只翻译一部分的后果不是"显示英文"，而是资源找不到默认版本直接抛异常（Q2）；只翻译一半且恰好有默认版本，则会出现"有的页面中文、有的页面回落到英文或直接缺字符串"的混合体验，验收时必须按"每种语言下每个界面都跑一遍"来覆盖。

**Q13: 多套 layout 变体共存时，ViewBinding 生成的字段为什么可能是 null？**

ViewBinding 按"所有变体的字段并集"生成绑定类：某个控件只在部分变体里出现时，它在生成类中对应字段就是可空类型。运行时选中的变体不含该控件，字段就为 null；直接访问会空指针。

处置方式是把它当成契约对待：要么让所有变体保持同一控件骨架（只是约束不同），把差异放到约束与资源上；要么在代码里显式判空并给出兜底。这条坑的具体排查路径见 [../../android-ui.md](../../android-ui.md) 的对应条目。

**Q14: 运行期 Configuration 变更应该自处理还是让系统重建？边界在哪？**

原则是：能用布局/资源重载解决的用重建，避免自己维护两套状态；只有当重建代价明确不可接受、且状态保存恢复已有成熟方案时才声明 `android:configChanges`。声明时要注意它只覆盖你列出的变化位，未列出的项仍会触发重建，于是会出现"我处理了横竖屏但深色模式切换仍然重建"的困惑。

此外，手工调用 `Resources.updateConfiguration` 之类的接口去"改配置"是受限且不受支持的路径（官方文档口径）：它只影响本进程、资源匹配结果可能与系统不一致、并且不解决窗口几何问题。需要"模拟某配置"用于验证时，应用内提供显式的预览开关并只改自身绘制逻辑，比改全局配置更可控。

**Q15: 怎么确认当前实际生效的是哪一个资源变体？**

按"配置 → 取值 → 文件"三层实测，别靠猜：

- **配置层**：打印 `Configuration.uiMode`、`density`、`fontScale`、`screenLayout`、当前显示 id 与其 `DisplayMetrics`，确认输入符合预期。
- **取值层**：对关键资源用 `getString`/`getDrawable` 取值并打印关键属性（颜色值、尺寸值），判断是否拿到了夜间/大屏应有的那份。
- **文件层**：用调试手段反查某个 id 实际落在哪个资源文件/条目，确认命中的是变体还是默认项（思路与 [../../android-ui.md](../../android-ui.md) 的资源探针一致）。

这套流程的价值在于把"看起来没生效"变成"输入配置不对 / 取值不对 / 命中了被定制改写的项"三种可区分的结论，而不是继续在布局文件里找。
