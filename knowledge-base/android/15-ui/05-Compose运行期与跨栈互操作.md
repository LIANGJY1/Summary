# Compose 运行期与跨栈互操作

> 学习资料（文章模式沉淀）。主线：组合/布局/绘制三阶段与"读状态即订阅"、组合期写状态的无限重组、`remember` 与 `rememberSaveable` 的持有边界、`derivedStateOf` 与延迟读取、稳定性推断与 strong skipping、列表键与重组范围、`LaunchedEffect`/`SideEffect`/`DisposableEffect` 分工、`ComposeView` 嵌入与组合策略、`AndroidView` 的代价、自定义宿主与帧时钟、重组与掉帧的归因工具、View 迁移的高频坑。Compose 属 AndroidX、不在 AOSP 源码树内，本册结论按官方文档与 AndroidX 源码口径（2026-09 检索）；渲染侧的帧调度与掉帧度量见 [../02-rendering/01-渲染管线与VSync调度.md](../02-rendering/01-渲染管线与VSync调度.md)，View 侧绘制机制见 [03-View测量布局与绘制.md](./03-View测量布局与绘制.md)，应用实践见 ../09-app-practice/07-渲染实战-Compose进阶.md。Q 序列即结构，供 atlas 同源直读。

**Q1: Compose 的三阶段是什么？"读状态就触发重组"具体是怎么工作的？**

三个阶段依次是组合（把 composable 函数执行成一棵节点树）、布局（测量并定位）、绘制（发出绘制命令）。重组指的是状态变化后**重新执行 composable 函数**以更新组合结果，它只发生在组合阶段。

机制是快照与订阅：状态对象写入时记下全局快照，组合执行期间被读取的状态被记录为"本次组合的依赖"；写入发生后，运行时把依赖集合中包含该状态的组合范围标脏，排进下一次重组调度（官方文档口径）。这条设计的后果是——重组范围由"谁读了状态"决定，而不是由"谁调用了谁"决定，因此把状态读尽量推迟到后面的阶段能直接缩小重组面。

**Q2: 为什么在 composable 函数体里直接写状态会导致无限重组？**

因为写入会把本次组合标脏，而标脏的下一次重组又会执行同一段代码再次写入，于是永远排不到一个"不再需要重组"的稳定态，表现为持续掉帧（官方文档把这类写法列为常见陷阱）。

正确做法是分清两类写：事件响应里的写（点击回调里改状态）发生在组合之外，是正确的；组合期间需要"同步派生"的写应当移出组合，或改为在下一帧/副作用里执行。判断标准是问"这次写入是否是因为组合读了某个状态而被迫发生"，是则说明它是派生逻辑，应该改写成派生而非写入。

**Q3: `remember` 和 `rememberSaveable` 的差别在哪里？**

`remember` 把值存在组合里，只跨重组有效，**不跨配置变更与进程重建**：屏幕旋转后拿到的是全新组合，之前记住的值消失。`rememberSaveable` 会把值按可保存形式写入实例状态，因此能跨配置变更恢复。

选型规则是"这个值是纯派生/缓存，还是用户可感知的界面状态"：缓存、对象引用、监听器用 `remember`；滚动位置、展开状态、输入内容这类"用户操作痕迹"用 `rememberSaveable`。可保存类型有限（基本类型、Bundle 可装类型等），不可保存对象只能走 `remember`，这也是为什么自定义类型要用注册自定义 Saver 的写法。

**Q4: `derivedStateOf` 解决什么问题？默认不带 policy 会有什么坑？**

它解决"依赖变化频繁但真正关心的派生结果很少变"的场景：官方例子是列表滚动中只有首屏可见项进入视野这一结果才需要触发重组，若直接读滚动偏移则每一帧都会重组；用 `derivedStateOf` 包一层后，只有派生结果本身变化时才触发更新（官方文档口径）。

坑在默认值：不传 `SnapshotMutationPolicy` 的派生状态在**每次依赖变化**时都会通知更新，等于把过滤降级成了"每次依赖变化但按派生结果比较"——当派生结果本身类型不稳定（每次生成新对象）时，等于没过滤。解法是传一个基于结构相等的 mutation policy，使结果相等时不通知。另外派生状态本身不该在组合期被频繁读取，否则订阅关系会被建立到错误的范围。

**Q5: 稳定性是怎么推断的？不稳定参数会带来什么后果？**

编译器按类型推断稳定性：不可变类型（含不可变属性的数据类、被标注为稳定的类）与基本类型、`val` 声明的集合字面量等被视为稳定；可变容器、可变数据类、外部未知类型被视为不稳定（官方文档口径）。后果是：一个 composable 只有在所有参数都是稳定值时才会被标记为可跳过（skippable）；参数里有不稳定类型时，任何一次状态变化都可能让整段函数重跑，并把重组范围向上扩散到调用者。

修复方向是让类型真正稳定——把可变字段改为不可变、用不可变集合、把值类型标为稳定注解，而不是靠包一层 `remember` 掩盖。

**Q6: strong skipping 是什么？它默认开启了吗？**

它是 Compose 编译器的一个模式，改变两件事：不稳定参数的 composable 也变为可跳过；捕获了不稳定变量的 lambda 会被记忆化（官方文档与 AndroidX 设计文档口径）。它引入于 Compose 编译器 1.5.4，并在 Kotlin 2.0.20 起默认启用。比较规则也随之分岔：不稳定参数用实例相等（`===`）比较，稳定参数仍用 `equals`。

需要知道的边界：它放宽的是跳过条件，不是让不稳定的类型变稳定；编译器仍会把 restartable 函数标记为可跳过，non-restartable 函数不受影响；lambda 在强跳过下会被自动记忆，因此"每次重组都新建 lambda 导致重组"这类问题会自动缓解，但不能替代稳定性治理。

**Q7: 怎么把状态读取推迟到布局或绘制阶段？**

做法是把读取包进只在布局/绘制阶段执行的 lambda 型 modifier 或 effect，使状态订阅发生在后段阶段。官方文档给出的收益是：这样状态变化时可以跳过组合阶段，直接从布局阶段开始；代价是可读性和调试难度上升（官方文档口径）。

判断是否值得的标准是看 trace：只有当重组本身占了显著耗时、且被读状态确实高频变化时才推迟读取；否则优先用 `derivedStateOf` 与稳定键解决，收益更直接。

**Q8: 懒加载列表里的 `key` 参数解决什么问题？**

它给每个列表项一个稳定身份，让 Compose 在数据增删、顺序变化或复用位置时能对上号：没有稳定键时，运行时按位置匹配，插入或删除会让后续项的数据"错位"到别的位置（表现为状态跑到别的行、动画错乱），并且容易在重组时丢掉复用收益。官方性能建议是给懒布局提供稳定键（官方文档口径）。

实践要求是键必须唯一且稳定：拿数据库主键或业务唯一 id，不要拿数组下标——下标在删除时必然复用，等于没有键。

**Q9: `LaunchedEffect`、`SideEffect`、`DisposableEffect` 各自在什么时机执行？常见误用是什么？**

- `LaunchedEffect` 在组合后启动协程，键变化时取消上一个并重启。
- `SideEffect` 在每次成功重组后运行，用于把非 Compose 状态同步到外部世界。
- `DisposableEffect` 在组合后建立资源并在离开组合时清理，用于注册/反注册。

常见误用有三类：把"点击事件"写成 `LaunchedEffect`（事件不是副作用，应该在回调里处理）；把 `LaunchedEffect` 的键写成每帧都变的值，导致协程被反复取消重启；用 `DisposableEffect` 持有"启动一次即可"的资源，导致重建时被清空。

**Q10: 用 `ComposeView` 嵌入既有 View 体系时，组合策略为什么重要？**

`ComposeView` 持有一个组合，需要明确的销毁时机，否则组合会随宿主一起泄漏、或在宿主暂时不可见时保留过期的状态。这就是 `ViewCompositionStrategy` 存在的原因，官方提供多种策略：在视图从窗口移除时释放、在离开 ViewTree 生命周期所有者时释放、或在进入对象池时释放（官方文档口径）。

选型规则：宿主是普通 Activity/Fragment 里的一个 View，用随 ViewTree 生命周期释放的策略最贴近直觉；宿主是可复用容器（列表项、Tab 页面、ComposeView 复用池），要用"从窗口分离即释放"或"归还对象池即释放"，否则会出现切走再切回状态莫名重置或内存涨高。

**Q11: `AndroidView` 承载 View 的代价在哪里？**

代价有三项：它把一个独立的测量布局绘制子树接进 Compose 的树里，等于多一层桥接；`update` 块会在参数变化时被调用，块里做重活就会拖慢 Compose 的重组与布局；而每次真正变化都要通过桥接把状态同步进 View，绕开了 Compose 的跳过优化（官方文档口径）。

使用纪律是"把它当成不可优化的边界"：View 只做它擅长的那部分（复杂自绘、成熟第三方控件），不要在 `update` 里重建整个 View，也不要把高频变化的参数灌进去。

**Q12: 自定义 Compose 宿主时，Recomposer 与帧时钟是什么关系？**

宿主需要显式提供 `Recomposer` 与帧时钟，两者要成对设置，否则要么不重组、要么在错误时机重组。官方做法是把帧时钟接到平台的帧回调上，使重组调度与 VSync 对齐（官方文档口径）。

这正是"自定义宿主里动画和重组不同步"问题的根因：重组没挂到帧时钟上就会在消息循环的随机时机执行，布局在下一帧才生效，于是看到"点了没反应、过一会儿才跳"的现象。跨栈宿主还要保证 Composition 与宿主的生命周期绑定（Q10）。

**Q13: 排查 Compose 掉帧按什么顺序做？**

先归因到"重组慢 / 布局慢 / 绘制慢"，再处理：

- **工具**：用 Layout Inspector 查看重组次数与哪些 composable 在重组；用 trace 事件（AndroidX 提供的 trace 事件 API，官方在性能文档中给出用法）把自定义慢逻辑包起来看耗时；用帧时间线/帧指标判断是否真的超过帧预算（度量口径见 ../07-performance/01-流畅性.md）。
- **归因顺序**：重组次数异常高 → 查不稳定参数与延迟读取；单次重组耗时高 → 查组合期重活与昂贵的列表筛选排序；布局慢 → 查测量复杂度与深嵌套；绘制慢 → 查绘制期分配与大面积渐变模糊。
- **不要先做的事**：不要一上来就加缓存层或换渲染后端，先确认瓶颈阶段，否则优化落不到点上。

**Q14: View 迁移到 Compose 有哪些高频坑？**

- **主题与类型体系不同**：View 主题属性与 Material 主题不是一一对应，迁移后颜色、字号可能整体偏移，需要逐屏比对而不是逐控件替换。
- **状态归属**：迁移前状态常挂在 View 上，迁移后若不放进状态对象，切走再回来会丢；`remember` 挡不住进程重建（Q3）。
- **生命周期不对称**：View 的回调（绘制、可见性）与 composable 的生命周期不是一一对应，依赖 `OnDrawListener` 之类的逻辑迁过去往往要重新设计。
- **返回键与焦点**：View 体系里靠 `onBackPressed` 与焦点顺序处理的交互，迁到 Compose 需要显式的返回处理与焦点修饰符，缺了就表现为"返回没反应"或"键盘焦点乱跳"。
- **嵌回 View 的位置**：`AndroidView` 内部不要再反向调 Compose 状态，容易形成双向更新环。

**Q15: 同一页面同时存在 View 与 Compose 时，布局与状态各要注意什么？**

布局侧只有一条纪律：两者都要参与同一套尺寸约束，不要一个用固定 dp、一个用自适应，否则任何一侧的尺寸错误都会被另一侧放大。状态侧的方向是单向的——选定一个状态持有方，View 侧通过 `AndroidView` 的 `update` 接收状态、Compose 侧通过回调接收事件，不要让两个体系各自持有一份真值。

还有一个版本相关的注意点：Compose 侧走的是 AndroidX 的渲染实现与管线，跨栈页面的帧预算受两套系统的录制与渲染影响，混用页面掉帧时要按阶段分别归因，不要默认"卡在 Compose"或"卡在 View"。
