# 网络排查工具与实践

> 学习资料（文章模式沉淀）。主线：Android 上抓包的权限边界与部署形态、tcpdump `-i any` 的 SLL 语义与过滤器写法、ip/ss 工具族、无 root 场景的取证替代、Perfetto/ftrace 网络轨迹、ICMP 工具的正确读法、DNS 诊断替代。通用 Linux 机制与社区经验口径为主（2026-09 检索），工具在 AOSP 的存在性按官方口径标注；车机多 APN 的验证脚本结构见 [02-车机多APN与虚拟网卡.md](./02-车机多APN与虚拟网卡.md)。Q 序列即结构，供 atlas 同源直读。

**Q1: Android 上抓包需要什么权限？user 版设备为什么抓不了？**

tcpdump 经 libpcap 打开 `AF_PACKET` 旁路监听，需要 **root 或 CAP_NET_RAW**；Android 上还有第二道闸——SELinux：user 版设备既拿不到 su 也过不了策略，shell 域执行抓包直接被拒（avc denied 可 `dmesg | grep avc` 看到，社区实战口径）。可行形态：userdebug/eng 版 `adb root` 后把 tcpdump 推到 `/data/local/tmp` 运行；user 版替代——代理抓包（设备设代理，PC 上 mitmproxy/Charles，HTTPS 要装证书）、VPN 型抓包应用（本机建 tun 收包）、或应用内自带诊断埋点。车机交付含义：量产 user 版留不了 tcpdump，现场取证能力必须在研发期以"日志/指标埋点"形式内置（02 册验证脚本要做成分级版本）。

**Q2: tcpdump -i any 抓出来的包为什么没有以太网头？过滤器怎么写才不吃亏？**

`-i any` 用 Linux cooked capture（SLL）封装替代真实链路头，`-e` 打出的是 SLL 元信息而非 MAC 帧——所以按 ether 字段过滤会失效，按 `ip`/`port` 等 L3 以上字段过滤不受影响（02 册验证脚本全部用 L3/L4 过滤器即此原因）。两个实用写法：抓 VLAN 流量要在过滤器里显式加 `vlan`（含 VLAN 的包偏移变了，裸 `udp port 53` 会漏）；隧道场景（VPN/ GRE）外层内层两层头，想看业务包要按内层地址过滤或先在外层收再解码。输出加 `-nn`（不做名字解析）、`-l`（行缓冲配管道实时处理）、`-w` 存 pcap 供 Wireshark 离线分析。

**Q3: ip/ss 工具族在车机上分别看什么？**

三件分工：`ip addr/link`（接口状态、地址、veth 对两端）、`ip route show table all` + `ip rule`（Android 每网络一个表，策略路由必须连表带规则一起看——01 册口径）、`ip neigh`（邻居/ARP 表，二层可达性）。`ss -tunap` 看套接字状态与归属进程（`-p` 看进程名需要 root/同 uid），重点列子状态：`ESTAB` 但对端已失联、`CLOSE-WAIT` 堆积（应用没关连接）、`SYN-SENT` 卡住（路由/防火墙丢 SYN）。这些命令在 toybox/iproute2 里车机普遍可用，是 02 册五段定位法的执行层。

**Q4: 拿不到 root 的量产车机，网络问题怎么取证？**

降级三板斧：**应用内埋点**——请求级记录 DNS/TCP/TLS/首字节分段耗时与失败原因（04 册网络库实践口径），配合系统回调日志（NetworkCallback 的 available/lost/capabilities 序列）；**代理取证**——研发期在实验室把设备指到代理（mitmproxy），HTTPS 装证书后可看全明文（注意 NSC 的 pinning 会挡住，临时用 debug-overrides，见 04 册证书题）；**VPN 型抓包应用**——本机 tun 抓本机流量，不需要 root，但抓不到整机其他 uid 与内核态细节。量产现场优先信第一类：埋点是唯一"随版本发布、随车辆在线"的取证通道。

**Q5: Perfetto/ftrace 能看到哪些网络轨迹？**

ftrace 事件里有网络相关探针：TCP 重传、连接状态迁移、网卡收发队列等事件可在 Perfetto 时间轴上与 CPU/调度轨对照，定位"请求卡在哪一段"——是没发包（应用线程没跑）、发了没回（对端/链路）还是回包没被处理（线程阻塞）。配合 atrace 的应用自定义 trace 段把"发起请求"与"收到响应"圈出来，端到端延迟一轴可见（Perfetto 官方文档口径）。注意它替代不了 tcpdump：ftrace 看行为不讲内容，要看包内容仍要抓包；两者同一时间窗采集可以互相印证。

**Q6: ping/traceroute 的结果怎么读才不会误判？**

三个常见误读：ICMP 被限速或禁 ICMP 的路径上，ping 不通不等于业务不通——以业务端口探测为准（`ping -I <网卡> <域名>` 是绑定探测，02 册；端口级用 `nc`/应用自身）；traceroute 的中间跳星号可能是设备不回 ICMP TTL 超时，只有最后一跳的结论可信；路径不对称（去程回程不同路由）让中间跳延迟解读失真。车机多 APN 环境必须带 `-I`（或等价绑定）跑，否则 ICMP 走默认网卡，测的不是目标链路——02 册验证脚本把解析、ICMP、出口三件事绑在同一路径上就是为了这个。

**Q7: 车机上没有 dig/nslookup，DNS 问题怎么查？**

三层替代：应用侧 `InetAddress.getAllByName()` 直接验证"框架解析出什么"（注意它有 JVM 层缓存，验证前考虑清缓存或换进程）；系统侧看配置——`dumpsys connectivity` 里该网络的 DNS 服务器列表、Private DNS 模式（01 册解析链口径）；链路侧抓包——`tcpdump 'udp port 53 or tcp port 53 or tcp port 853'` 看实际查询发往哪台服务器、从哪个接口发出（DoT 走 853，密文看不到内容但看得见对象）。三件对齐后，"解析错"能定位到配置、链路或缓存三层之一。

**Q8: 车机网络的弱网/异常场景怎么在台架上造出来？**

用 netem（内核 tc qdisc，userdebug/root 可用）在出口网卡上注入损伤：`netem delay/loss/duplicate/reorder/corrupt` 分别造延迟、丢包、重复、乱序、比特错，`rate` 限带宽，`-HISTGRAM` 类分布可造抖动（通用 Linux 机制；注意 netem 挂在 egress，双向损伤要在两端或 ifb 回环造）。测试矩阵至少覆盖六场景：好网基线、高丢包（1%/5%/20%）、高延迟与抖动（弱信号蜂窝）、窄带宽（2G/边缘速率）、**切换抖动**（两网来回横跳，`ip link` up/down 脚本化）、**无网与假网**（断链、以及"有链路无外网"的认证门户态）。三个补充：v6-only/CLAT 场景单独列一档（02 册 Q13 的 UDP 分片坑只有 v6-only 才暴露）；真实弱网样本用 pcap 录制回放比人造参数更可信；全部脚本化进 CI，台架每轮跑一次六场景矩阵，网络回归不靠人肉。

**Q9: radio log、tcpdump、应用埋点三个时间轴对不齐，怎么对齐？**

三源时间戳来源不同是根因：logcat 用墙钟（可被 NTP 跳变、带时区），tcpdump 默认也用墙钟微秒精度，应用埋点常用 `SystemClock.elapsedRealtime()`（单调但不含绝对时刻）。对齐方法：选一个**双源共同可见的锚点事件**（如一次 DNS 查询在 tcpdump 与应用埋点里都出现），计算两源在该事件上的偏移量，把其余事件按偏移平移对齐；跨时钟跳变（校时发生）的事件分段各自对齐，不要跨段直连。预防性的采集纪律：埋点同时记录墙钟与 elapsedRealtime 两个时间（对齐用相对、展示用绝对）；采集脚本在开始时同步记录两个钟的读数。多源对齐是多 APN 链路定位（02 册五段法）能落地的前提——各段证据不在同一时间轴上，"分段取证"就退化成"各段猜谜"。

**Q10: 带宽怎么实测？iperf3 的用法与测速陷阱有哪些？**

iperf3 是双端工具：对端起 `iperf3 -s`，本端 `iperf3 -c <对端> -t 30` 测 TCP 吞吐，`-u -b <带宽>` 测 UDP 吞吐并报告丢包与抖动；TCP 单流可能受单连接窗口限制，`-P` 多流才能逼近链路上限（工具通用口径）。四个陷阱：测的是全链路最小段——中间任何一段（热点、NAT、modem）是瓶颈时结果只反映瓶颈段；多客户端共享热点/链路时互相分抢，测速值随并发漂移；本机 CPU 或接口本身是瓶颈的车机（低端模组）先排除端侧瓶颈；测速流量会与真实业务互相挤占——台架上在 netem 矩阵（本册 Q8）之外单独跑基线，量产现场不做压测。结论用法：iperf3 得到的是"当前链路段的可用吞吐"，用于基线对比与硬件验收，不能当作用户真实体验速率对外承诺。
