# 网络分层原理与地基机制

> 学习资料（文章模式沉淀）。主线：把 01–09 册用到的机制下沉到地基——分层模型与一个包的旅行、DNS 层级与递归、TLS 握手逐步、TCP 握手挥手与状态机、IP 分片、NAT 原理、全链路走读、分层校验。全部为通用网络机制（RFC 与教科书口径），不依赖特定 Android 版本；章节内各册的 Android 落点随题互链。Q 序列即结构，供 atlas 同源直读。

**Q1: 网络分层到底怎么分工？一个包从车机到服务器经历了什么？**

分层是责任划分：链路层负责"同一段线路上送到下一跳"（MAC 寻址、错帧检测），网络层负责"跨网段寻址与路由"（IP、逐跳转发），传输层负责"端到端的进程间可靠或不可靠交付"（TCP/UDP、端口），应用层负责业务语义（HTTP/MQTT/私有协议）。一次 HTTPS 请求的封装顺序自上而下：应用数据 → 加 TCP 头（源/目的端口）→ 加 IP 头（源/目的地址）→ 加以太网帧头尾（源/目的 MAC），每过一层加一层头，对端逐层剥离（通用分层模型口径）。实践意义：排查时按层归因——不通先问"哪一层断"（Q16 的三层口诀），改协议先问"动了哪层的头"。

**Q2: DNS 的根、顶级、权威服务器各干什么？递归和迭代差在哪？**

解析链条：客户端 → 本地递归解析器（运营商/公共 DNS）→ 根服务器（告知 `.com` 由哪些 TLD 服务器负责）→ TLD 服务器（告知该域名由哪台权威服务器负责）→ 权威服务器（给出最终记录）。递归与迭代的区别：客户端到递归解析器是**递归**（"你帮我查到底"），递归解析器到根/TLD/权威是**迭代**（"你告诉我下一该问谁"）——递归解析器替客户端跑完全程并缓存（DNS 协议通识口径）。层级结论的排查映射：权威记录错了改 DNS 服务商配置；递归缓存了旧值要等 TTL 或换解析器（04 册 HTTPDNS 即绕过这段公共递归链）；根与 TLD 层在车机场景几乎从不背锅。

**Q3: TLS 握手到底交换了什么？1.2 与 1.3 差在哪？**

TLS 握手要达成两件事：验证对端身份（证书链校验，04 册 Q10 的对象）与协商出会话密钥。TLS 1.2 需要两个往返：第一轮协商套件与交换参数（ECDHE 产生共享密钥），第二轮双方各发握手完成；TLS 1.3 压缩到一个往返——ClientHello 直接带上密钥共享参数，服务器一次返回证书与完成消息，应用数据可随第三个飞行包立即发出（RFC 8446 机制口径）。会话恢复：1.2 用 session ID/ticket 复用此前密钥材料，1.3 提供 0-RTT 但带重放风险（08 册 Q12）。排查映射：握手类失败在"第几个往返"定位——证书错误发生在收到 Certificate 之后（链/时间/域名问题，Q3 归 08 册），密钥协商失败则是套件不兼容（老设备与强策略服务端互斥）。

**Q4: TCP 的三次握手与四次挥手各对应 `ss` 里的什么状态？**

握手：客户端发 SYN 进入 `SYN_SENT`，服务端回 SYN+ACK 进入 `SYN_RCVD`，客户端回 ACK 后双方 `ESTABLISHED`——三次的原因是双方都要确认"自己的发送与接收能力"被对端确认。挥手：主动方发 FIN 进入 `FIN_WAIT`，对端回 ACK 再发自己的 FIN（`LAST_ACK`），主动方回 ACK 后进入 `TIME_WAIT` 停留 2MSL（Q15）——四次的原因是关闭是两个方向独立的事，被动方可能还有数据要发（通用 TCP 机制口径）。`ss` 排查映射：大量 `SYN_SENT` 卡住是路由/防火墙丢 SYN；`SYN_RCVD` 堆积是被 SYN 洪泛或回包不通；`CLOSE_WAIT` 堆积永远是应用没调 close；`TIME_WAIT` 是主动关闭方的正常残留（Q15 治理）。

**Q5: IP 分片是怎么发生的？为什么工程上一律避免？**

链路层有 MTU 上限（以太网 1500），IP 包超过时由发送端或中间路由器分片，各片独立传输、由接收端重组——任何一个分片丢失，整个 IP 包报废（通用 IP 机制口径；UDP 无重传时表现为整包丢失，见 09 册 Q14）。工程上避免分片的原因：分片重组是性能与安全双包袱（重组缓存攻击面、丢包放大、部分中间设备丢弃非首片），所以 TCP 依据 MSS 主动分段避让，UDP 靠应用控制包尺寸；带 DF 位（不分片）的路径靠 PMTUD 探测最小 MTU（03 册 Q10 的 MTU 黑洞即 PMTUD 失效场景）。设计纪律：承载未知网络的协议（隧道、VPN、跨公网私有协议）按保守 MTU 设计报文上限，而不是指望分片兜底。

**Q6: NAT 到底改了包的什么？conntrack 在其中扮演什么角色？**

NAT 的本质是改写地址/端口并记账：出向包把内网源地址:端口替换为公网地址:新端口，在 conntrack 表里记录"(内网源:端口 ↔ 公网:端口) 会话"，回包按表反向改写送到内网主机（通用 NAT 机制口径；02 册 SNAT 拓扑即此）。推论四条：NAT 只对"由内发起"的会话天然友好，外部主动进来没有表项可查（需要端口映射/打洞，车机远程访问的难点）；会话是状态——长期无流量表项老化，连接静默失效（05 册 Q9 心跳对齐 NAT 超时）；ALG 会深改已知协议的载荷（02 册 Q18 的破坏面）；多设备共享出口靠端口区分，端口耗尽即新会话失败。

**Q7: 从"打开一个网页"到渲染，全链路要经过哪些步骤？**

全链路走读（串联本章节）：输入 URL → **DNS 解析**（Q2 层级链，可能经 HTTPDNS 绕劫持）→ **TCP 三次握手**（Q4，慢启动随后爬坡 Q5 拥塞）→ **TLS 握手**（Q3，1.3 一个往返；失败族见 08 册 Q3）→ **HTTP 请求与响应**（缓存命中则止步于条件请求 304，08 册 Q14）→ **浏览器/WebView 解析渲染**（渲染细节属渲染域）。每一步的延迟都可归段：解析慢查 DNS 链，握手慢查 RTT 与丢包，首字节慢查服务端——这与 01 册 Q8 的 dumpsys 分工、06 册 Q9 的时间轴对齐组合成完整的端到端取证方法。车机差异点：多 APN 环境下"DNS 从哪出、TCP 从哪个接口走"要先按 02 册绑定机制确认，链路走读才有意义。

**Q8: 每一层都有校验，它们各防什么？为什么 TLS 之后还要应用层校验？**

分层校验各管一段：以太网帧 CRC 防线缆位翻转（链路层，错帧在网卡即丢弃）；IP 头校验和只护 IP 头自身；TCP/UDP 校验和护"头部+数据"的伪首部校验，但算法强度弱且可被中间设备重算——**传输层校验不防恶意篡改**（通用机制口径）。TLS 的 AEAD 加密认证同时保证机密与完整性，覆盖"离开本机到对端解密"的全程——这是唯一能对抗主动篡改的层。因此结论分层：随机误码靠链路/传输校验自然处理；中间设备改写（02 册 Q18 ALG、劫持注入）必须靠 TLS 或应用层签名（07 册 Q2）；业务关键数据的最终一致性校验（哈希对账）永远值得做在应用层——每层校验只对该层的威胁模型负责。
