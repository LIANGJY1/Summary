# 稳定性治理：资源泄漏与进程恢复

> 学习资料（文章模式沉淀）。主线：把"内存不足"拆成 Java 堆、Native、线程、地址空间与 FD 的独立失败路径，先分类再选工具，并按独立进程边界处理 WebView renderer 的退出与恢复。源文档：android-internals-wiki §20.5《OOM、进程资源治理与 WebView Renderer 恢复》、§20.6《Native 内存泄漏的线上分层监控》、§20.7《FD 耗尽监控与故障排查》；可本地核对的机制按 AAOS13 源码（Android 13）核对并标注版本差异（MemoryLimiter、mallopt 的 M_PURGE_ALL/M_PURGE_FAST、ProfilingManager 的 heap profile 为 Android 14–17 能力，AAOS13 无或不同），工程实践按材料口径转写、不确定处已弱化；WebView renderer 终止处理契约（不复用旧实例、新建实例、返回 true）已与官方文档核对（官方页面 2026-08-13 更新）。lmkd、整理回调与 MemoryLimiter 的机制层见 [../memory/01-内存管理与压力治理.md](../05-memory/01-内存管理与压力治理.md)；ANR 机制层见 [../performance/03-ANR.md](../07-performance/03-ANR.md)。Q 序列即结构，供 atlas 同源直读。

**Q1: 一条"内存不足"告警可能来自哪几类资源失败？哪些会抛出 Java `OutOfMemoryError`？**

"内存不足"不是单一故障：至少要区分 Java 堆 OOME、Native 分配失败、线程创建失败、FD 耗尽、虚拟地址空间耗尽与 LMK 六类；只有部分路径会抛 `OutOfMemoryError`——LMKD 终止进程直接以 SIGKILL 结束、没有任何 Java 异常，FD 耗尽通常返回 `EMFILE` 也不经过 ART。

分类与证据对应：

1. **ART Java 堆分配失败**：OOME 文本、Java 栈、heap dump 与 GC/heap 指标；
2. **由 native 层提供存储的 Java API 失败**：Bitmap 分配、特定 JNI 错误；证据是 Java 栈、native 分配栈与 PSS/RSS，是否抛 OOME 由 API 决定；
3. **线程创建失败**：ART 抛出带 `pthread_create` 信息的 OOME，证据还有线程数与进程限制；
4. **普通 native 分配失败**：`malloc`/`mmap` 返回空指针或 `ENOMEM`，调用方未检查就表现为 SIGSEGV，主动 `abort()` 表现为 SIGABRT；
5. **FD 耗尽**：`EMFILE`、socket/pipe 创建失败，或把高编号 FD 交给 `select()` 触发 FORTIFY abort；证据是 `/proc/self/fd` 与 rlimit；
6. **LMK**：进程被系统终止，证据是 `ApplicationExitInfo`（API 30+）与系统内存状态。

这张分类决定工具选择：heap dump 看不到所有 native 映射，heapprofd 看不到 Java 对象引用，LMKD 结束进程后崩溃 SDK 没有机会执行收尾代码。反例：`OutOfMemoryError` 不能只凭异常类型判定"内存泄漏"，`REASON_LOW_MEMORY` 也不能单独证明应用存在泄漏。

**Q2: ART 抛出 Java 堆 `OutOfMemoryError` 时错误文本能读出什么？为什么不能只凭文本断定泄漏？**

AAOS13 的 `Heap::ThrowOutOfMemoryError()` 生成的文本形如 `Failed to allocate a 48 byte allocation with 3610680 free bytes and 3526KB until OOM, target footprint 536870912, growth limit 536870912; giving up on allocation because <1% of heap free after GC.`——它描述的是失败那一刻的堆状态，请求很小仍失败通常说明堆已贴近限制或碎片化（AAOS13 `heap.cc` 核对）。

各字段含义与边界：

1. **allocation size**：本次请求大小；一次超大请求要先检查输入尺寸与宽高乘法溢出；
2. **free bytes**：ART 统计的堆空闲总量，它大于请求值也不能单独证明分配可成功——目标堆区是否有足够大的连续块、分配后能否保留最小空闲比例都参与判断；
3. **until OOM**：到 OOME 还可增长的剩余空间；
4. **target footprint**：GC 用来调节堆增长的目标值，不是硬上限；
5. **growth limit**：应用堆增长上限，由 `dalvik.vm.heapgrowthlimit` 等设备属性配置；
6. **`<1% of heap free after GC`**：GC 后无法保留 `kMinFreeHeapAfterGcForAlloc`（0.01）要求的最小空闲比例，描述的是比例限制，不能仅凭这句断定引用泄漏。

抛出机制上还有一个兜底：AAOS13 的 `Thread::ThrowOutOfMemoryError()` 先尝试构造带文本的 OOME，若构造时再次耗尽内存，线程改用 Runtime 启动期预分配的 OOME 对象（`thread.cc` 核对）——保证异常状态可设置，但没有完整文本与栈。因此监控平台只能提取 allocation size、growth limit 等已知字段做辅助分组，原始文本和栈必须保留；判断泄漏要比较同一场景、同一 GC 状态下对象数量与 retained size，错误文本替代不了 heap dump 的引用关系。

**Q3: `android:largeHeap="true"` 能解决 OOM 吗？它的真实作用与边界是什么？**

不能。`largeHeap` 只让 AAOS13 的 `ActivityThread` 调用 `VMRuntime.clearGrowthLimit()`，把应用 Java 堆的增长上限放宽到设备配置的大堆档；它不增加设备物理内存，也不会消除 native、图形缓冲、线程栈与其他进程的内存压力（AAOS13 `ActivityThread.java` 核对）。

边界：设备通过 `dalvik.vm.heapgrowthlimit`、`dalvik.vm.heapsize` 等属性配置堆档位，没有固定的 512 MB 保证；更大的堆会容纳更多存活对象，让系统更早承受内存竞争，通常只是推迟故障并增加 GC 成本。它适合的对象是少数确有大内存工作集、且已在低内存设备、后台切换与进程重建上有测试数据的产品；泄漏、无界缓存和错误尺寸的分配不能靠它处理。通过反射改 ART 私有字段或动态"扩堆"的做法依赖内部实现、可能破坏 GC 假设，不应进入生产方案；`Runtime.maxMemory()` 与 `getMemoryClass()`/`getLargeMemoryClass()` 的值都取决于设备与运行时配置，也不代表进程总内存上限。

**Q4: 哪些 native 失败会转换成 Java `OutOfMemoryError`？普通 `malloc` 失败为什么不是 OOME？**

Android 有明确的转换点：`Unsafe.allocateMemory()` 的 `malloc` 返回空指针后抛出消息为 "native alloc" 的 OOME（AAOS13 `jdk_internal_misc_Unsafe.cc` 核对）；Bitmap 像素由 `allocateHeapBitmap()` 用 `calloc` 分配，失败后经 JNI 入口 `doThrowOOME()` 抛出 OOME（AAOS13 `libs/hwui` 核对）；部分 JNI API（如超长 `NewStringUTF`）在无法分配时也会抛 OOME。

普通 `malloc/calloc/realloc/mmap` 失败则是调用方契约：失败返回 `nullptr` 或 `errno`，由调用方决定处理方式——忽略空指针会在后续访问时表现为 SIGSEGV，主动 `abort()` 表现为 SIGABRT，只有显式调用 JNI/ART 异常接口才会变成 Java OOME。因此"没有 OOM 异常"不等于"没有内存问题"，tombstone 与 `ApplicationExitInfo` 都要纳入排查。

Bitmap 的版本边界：Android 8.0 起普通 Bitmap 像素由 native 堆持有（官方文档口径），`Bitmap.Config.HARDWARE` 使用 GraphicBuffer/AHardwareBuffer——两者都增加进程或系统内存压力，但归属与采集方式不同；Java heap dump 里体积很小的 Bitmap 包装对象不代表全部像素或图形缓冲成本。

**Q5: `pthread_create` 失败抛出的 `OutOfMemoryError` 应该怎样解读？线程数治理从哪里入手？**

AAOS13 的 `Thread::CreateNativeThread()` 失败后有两条错误文本："Could not allocate JNI Env" 说明失败发生在 pthread 启动前的 JNI 环境分配；"pthread_create (N stack) failed: <errno>" 要继续看 `strerror()` 给出的原因（AAOS13 `thread.cc` 核对）。Bionic 在栈/TLS 映射失败时返回 `EAGAIN`（AAOS13 `pthread_create.cpp` 核对），含义是当前资源不足、稍后可能成功；内核 `clone` 还可能因 task 数量或 `RLIMIT_NPROC` 返回同样的错误——诊断必须保留原始 errno，不能把所有 `EAGAIN` 记成同一原因。

每条 Java 平台线程都对应一个 native 线程，占用线程栈映射、guard 区、ART `Thread`、JNI 环境与内核 task；协程或排队任务的数量不能换算成操作系统线程数。栈大小由 ART 的 `FixStackSize()` 与线程请求共同决定，不存在"每线程固定 1 MB"的跨设备结论。

治理动作：自有任务使用队列长度受限的 executor 与统一调度入口，记录池大小、执行中、排队、拒绝与取消次数；审计 SDK、WebView、媒体与网络库的线程池——多个库各自"合理"的池相加仍可能过量；`Dispatchers.IO` 不是全应用线程总额控制器，多个 `limitedParallelism` 也要共享一份产品级预算。监控读取 `/proc/self/status` 的 `Threads` 与 `/proc/self/task`（两者是采样值），阈值来自设备与场景基线而非固定 400/500；线程数超阈值时不要立即调用 `Thread.getAllStackTraces()`（会创建大量对象），用平时保留的线程名与责任模块记录定位。线程数下降也要确认任务仍能完成——把线程改成一个无界队列，只是把资源 OOM 换成排队延迟或 ANR。

**Q6: `mmap` 返回 `ENOMEM` 时，为什么"内存用完"只是原因之一？32 位与 64 位进程分别怎么排查？**

`ENOMEM` 覆盖多类失败：32 位进程地址空间窄，`.so`、Java 堆、native 堆、线程栈与映射互相挤压；64 位进程也可能因无界映射、VMA 数量上限或超大连续请求失败。总剩余地址空间足够，不代表存在满足本次请求的连续区间；"32 位用户空间固定 3 GB、内核占 1 GB"也不能作为跨设备结论——内核配置、ASLR、保留区与进程映射共同决定可用范围。

排查顺序：保存进程位数（用 `Process.is64Bit()` 记录，不要只看设备 CPU）、失败 errno、请求长度与调用栈；对比同设备同场景健康样本的 `VmSize`/`VmPeak` 与 maps 区间数量；按映射名称、权限与责任模块聚合，区分持续增长与单次巨型请求；32 位进程额外检查最大空洞与碎片；64 位进程先识别 Runtime 保留区——较大的保留区可以是正常实现，证据要回到失败栈与映射增长。

治理方向：能迁移时提供完整 64 位 ABI，并验证指针变大带来的 native 增量与第三方 `.so` 兼容；限制线程、映射与内存映射文件的数量与生命周期，及时 `munmap()` 或释放所有者；大对象分块、流式处理或设置尺寸上限，避免要求巨型连续区域；`mallopt(M_PURGE, 0)` 只能归还可清理的空闲物理页，不能释放保留地址区间、更不能修复映射泄漏；拆进程能获得独立地址空间，但会复制 Runtime、`.so`、线程与缓存，只有隔离边界和测量数据同时成立时才采用。

**Q7: OOM 前的降级应该怎么做？为什么不能指望 `UncaughtExceptionHandler` 里的抢救？**

降级与观测必须在资源接近预算时由明确的 owner 完成；OOME 交给 `UncaughtExceptionHandler` 后，当前线程连创建异常对象都可能失败，此时只应保留最小记录并沿默认处理路径结束进程。

按风险排序的降级动作：

1. 对图片、页面模型、预取、媒体缓冲和离线队列设置硬上限与缓存淘汰规则，不等待系统回调才控制；
2. 页面退出、UI 隐藏或任务取消时释放资源所有者，`close()` 与取消路径都要测试；
3. 内存持续上升时停止非必要预取、降低图片目标尺寸、缩小并发，保留用户当前操作所需数据；
4. 后台阶段释放可快速重建的 UI 缓存，避免同步序列化阻塞主线程；
5. 重任务保存阶段性进度并允许安全重试，让进程被系统结束后能够恢复，而不是依赖 OOM 处理器抢救。

版本边界：API 34 起常规只投递 `TRIM_MEMORY_UI_HIDDEN` 与 `TRIM_MEMORY_BACKGROUND` 两个整理级别（旧的 `RUNNING_*`、`MODERATE`、`COMPLETE` 不再送达，材料按 Android 17 核对），面向新系统的代码聚焦这两级；回调在主线程执行，只做快速的引用释放。预算管理要同时覆盖 Java live heap、native malloc、进程物理成本、图形/媒体、线程、FD 与虚拟地址空间，采样点用"场景完成条件满足 + 短暂稳定窗口"而不是启动后固定等待若干秒；模块预算之和不能直接等于进程预算，Runtime、共享库与共享对象需要单独余量。在局部边界捕获 OOME 只适用于输入尺寸已知、无共享状态写到一半、能返回低规格结果的操作；`sigsetjmp`/`siglongjmp` 不能处理 Java 堆 OOME，跳回会绕过析构与锁释放，不是 OOM 降级方案。

**Q8: `onRenderProcessGone()` 的契约是什么？`didCrash()` 返回 false 能断定页面 OOM 吗？**

Android 8（API 26）起，`WebViewClient.onRenderProcessGone(view, detail)` 是 WebView renderer（承载 Blink、JavaScript 与绘制的独立渲染进程）退出后的入口。契约要点：多个 WebView 可能关联同一个 renderer，每个受影响实例都会收到回调；当前回调只负责清理参数中的 `view`，不能假设其他实例已失效；返回 `false` 时，renderer 崩溃宿主随之崩溃、renderer 被系统结束宿主也被结束；返回 `true` 表示应用已处理并继续运行。官方指南进一步要求：旧实例不可复用——从视图树移除、清理引用并调用 `destroy()`，需要网页内容就新建实例并返回 true；任何使用该 renderer 的 WebView 未返回 true，WebView 会按退出原因 kill 或 crash 应用。

`didCrash()` 只做二分类：`true` 表示 renderer 被观察到崩溃；`false` 表示被系统结束，AOSP 注释说明最常见背景是低内存——但不能单凭 `false` 断言"页面 OOM"：应用在 API 29+ 可能主动调用 `WebViewRenderProcess.terminate()`，provider 更新通常结束整个应用进程，还要补设备内存档位与系统内存压力证据。`rendererPriorityAtExit()` 返回退出时的最终 renderer 优先级（多个 WebView 共享时取关联实例请求值的最大值），适合描述现场，不能反推是哪个 WebView 提高了优先级。`RenderProcessGoneDetail` 不提供 renderer PID、页面内存或调用栈，公开 API 没有精确的 renderer 内存读数，不能用宿主进程 PSS 冒充。

**Q9: renderer 退出后的恢复流程为什么不能只做"新建一个 WebView"？卡死与低内存策略怎么配？**

恢复是一段有先后顺序的状态迁移：销毁旧实例 → 展示恢复 UI → 延后重建 → `onPageCommitVisible()` 视觉提交 → H5 业务握手完成才算用户恢复；旧 `WebView` 上的 `reload()`、`goBack()`、`evaluateJavascript()` 与 JS Bridge 调用都救不回它。`onPageFinished()` 不能保证用户看到可操作内容，"新 WebView 已创建"更不算恢复成功。

实现约束：

1. **延后重建**：把恢复任务经 `container.post` 放入主线程队列，等回调返回后再执行，并检查 Activity 是否正在结束或已销毁，避免回调未退出就开始创建新实例；
2. **自动恢复上限**：自动重载次数写入 `onSaveInstanceState`，防止旋转等配置变更把计数清零；被系统结束的页面只给一次自动恢复机会，崩溃页（可能稳定复现 Chromium 或页面内容问题）不自动重载；
3. **可重放判断**：资讯、帮助等幂等页面可自动恢复；支付提交、表单编辑、一次性 URL 应跳转服务端状态查询或原生错误页，checkpoint 只保存去敏后的业务路由，不序列化 POST 数据与浏览历史；
4. **共享 renderer**：同一次退出会逐个触发回调，每个回调只销毁参数中的 view 并返回 true，容器再统一决定错误页，不能在第一个回调里假设其余 WebView 已失效。

卡死与低内存策略：API 29 起 `WebViewRenderProcessClient.onRenderProcessUnresponsive()` 提示 renderer 无法及时处理输入或导航（相邻回调最短间隔 5 秒，AAOS13 javadoc 核对），它不等于应用 ANR 也不强制要求终止；只有产品允许用户放弃页面且所有共享 WebView 都实现终止处理时，才在写入短时预期终止 token、切断新注入后调用 `renderer.terminate()`，再等 `onRenderProcessGone()` 清理。`setRendererPriorityPolicy()` 的三档（IMPORTANT/BOUND/WAIVED）只影响内存紧张时 renderer 被选为回收对象的可能性，不限制它的内存用量；共享 renderer 的最终优先级取最大值，只有容器能处理全部关联实例的 gone 回调时才适合降低优先级。

**Q10: 线上监控"Native Heap"时，为什么单一曲线会自相矛盾？要同时保留哪些维度？**

因为"Native Heap"混着回答不同问题的指标：allocator live bytes（分配器认为在用的字节）、mapped/retained（向内核映射与保留的页）、RSS（当前驻留物理页）、PSS（按共享比例分摊）、VMA 分类（增长落在哪类映射）、采样分配栈（heapprofd）与业务 owner counters。线上监控必须同时回答两个问题——"哪类内存在增长"和"增长是否脱离业务生命周期"，单个数值无法完成。

三个常见误判：

1. **RSS 上升不等于泄漏**：新触达的代码页、文件页、线程栈和 allocator 保留页都会抬高 RSS；
2. **`uordblks` 回落而 RSS 不回落，不等于 `free()` 失效**：Scudo 可以保留已释放页供后续复用，是否归还内核受尺寸、碎片与 release 策略影响；
3. **malloc 统计平稳不等于 Native 资源平稳**：`mmap(MAP_ANONYMOUS)` 自研内存池、GraphicBuffer、AHardwareBuffer 与 dma-buf 可能完全绕过 malloc。

采样时每个维度要绑定场景与时间点；比较点必须具有相近的页面、网络、播放与前后台状态，"启动后 1 分钟/1 小时"的固定时刻只适合连续使用场景。

**Q11: `mallinfo` 为什么只能当趋势计数器？bionic 的 `mallinfo2` 与 glibc 有什么不同？**

`mallinfo` 是 allocator 自己的统计，不是进程 RSS/PSS，也不是泄漏证明：AAOS13 的 `Debug.getNativeHeapAllocatedSize()` 直接返回 `mallinfo().uordblks`，`getNativeHeapSize()`/`getNativeHeapFreeSize()` 分别取 `usmblks`/`fordblks`（AAOS13 `android_os_Debug.cpp` 核对）；Scudo 把 `uordblks` 填为已分配字节、`fordblks` 为空闲字节、`hblkhd` 为映射字节。bionic 头文件明确把 `mallinfo()` 标为 inherently unreliable，建议需要更多信息时用 `malloc_info()`；在 allocator 与配置一致的前提下，这些计数器仍适合按秒级或分钟级观察趋势。

版本与可观测边界：bionic 的 `struct mallinfo` 字段已是 `size_t`，`mallinfo2()` 经 `__RENAME(mallinfo)` 指向同一个符号、布局相同（AAOS13 `malloc.h` 核对）——不要把 glibc 历史上 mallinfo 的窄整数与版本规则套到 bionic。sanitizer 与 hook 会改变可观测结果：heapprofd、GWP-ASan 生效时统计由当前 malloc dispatch 路径提供，HWASan 路径的 `malloc_info()` 会返回 -1 并置 `errno` 为 `ENOTSUP`——采集端要允许"无数据"、不要把 0 当作没有分配、灰度对比时保持构建类型与 allocator 配置一致。`malloc_info()` 输出的 XML（如 `scudo-1` 结构）不是稳定业务协议，且实现会暂停 allocator 并遍历 chunks，不能进信号处理器或高频心跳，只适合低内存告警后执行一次并把解析器按 allocator/version 分派。

**Q12: PLT hook 拦截 `malloc/free` 做内存账本，为什么容易得到错误结论？**

PLT/GOT hook 只改写选定 ELF 的导入跳转，覆盖范围达不到进程级 allocator 替换，Android 平台也不承诺其为稳定 API；若目标是维护"仍存活的分配"，只拦 `malloc/free` 的账本必然失真。

要覆盖的入口与难点：

1. **分配族**：`malloc`、`calloc`、`realloc`、`posix_memalign`、`aligned_alloc`、`memalign`，以及 C++ `new/delete` 及数组和 aligned 变体；漏掉对齐分配或 sized delete 会直接记账错乱；
2. **realloc 语义**：输入 `nullptr` 等价于分配；失败返回 `nullptr` 时旧分配仍有效；成功时地址可能不变也可能搬迁——三处写错任何一处都会破坏账本；
3. **地址复用与乱序**：地址释放后会被复用，异步消费还会乱序，账本键不能只用裸指针，要带单调时间、分配序号、线程 ID、尺寸与 Build ID 区分同一地址的不同分配周期；
4. **动态库加载卸载**：未注册的模块与卸载后的模块都会漏账。

hook 自身要比被观测代码更克制：TLS 重入标记防止代理函数内再次分配、预分配有界 ring buffer、原子写入固定长度事件、只记返回地址或少量原始 PC、独立消费者线程、离线按 Build ID 符号化、缓冲满则丢弃并计数；还要有远程关闭、时限与崩溃熔断。采样上，固定"每 1000 次取 1"偏向高频小对象——一次 64 MiB 分配与一次 32 B 分配入样概率相同；做字节归因应按尺寸分层或按字节加权随机采样，服务端用每条记录的采样概率反推总体规模。

**Q13: heapprofd 能提供什么、看不到什么？AAOS13 与 Android 15+ 的接入条件有何不同？**

heapprofd 是 Perfetto 的 Native 堆采样器，经 bionic 的 `MallocDispatch` 接入（与修改各 ELF PLT 的第三方 hook 是不同路径），能提供采样分配与释放的调用栈、分配大小与线程时间信息、按栈聚合的 allocated/freed/unreleased 视图，并与 Perfetto trace 时间线关联。

边界：profile 开始前已存在的分配无法补回原始栈；采样可能漏掉小对象，结果要按采样权重解释；直接 `mmap`、自研 arena 内部切分、GPU 与 AHardwareBuffer 等不经过 malloc 的分配不可见；`unreleased` 只表示采样窗口内尚未匹配到 free，不等同于从业务根不可达的泄漏；它也没有 Java 对象到 Native 资源的所有权引用图。

版本边界：Android 10 起可用；Android 10–14 上能否采集取决于应用是否声明 `profileable`、是否 debuggable 构建或由 shell 发起；Android 15（API 35）起普通应用可经 `ProfilingManager` 请求受系统管理的 heap profile——AAOS13 没有 `ProfilingManager`，线上要在受控灰度、异常趋势或 MemoryLimiter anomaly 命中后开短窗口，不持续高频采集（CPU、内存、trace 存储与隐私都有成本）。

**Q14: `mallopt` 的 purge 能不能修复泄漏？Scudo、GWP-ASan、HWASan、MTE 各自查什么？**

不能。`mallopt` 的 purge 只是把 allocator 中已经空闲、可归还的页交回内核：`M_DECAY_TIME`（API 27）调整空闲页归还时间策略、`M_PURGE`（API 28）主动请求归还，两者 AAOS13 已有；`M_PURGE_ALL`（API 34）与 `M_PURGE_FAST`（API 37）是后续版本新增（AAOS13 `malloc.h` 仅含前两者）。仍被引用的泄漏块不会因 purge 消失，碎片也可能让部分页无法释放；若每次 purge 后 RSS 暂时下降又持续上升，应继续查对象生命周期，不要把周期性 purge 包装成修复。Scudo 的环境变量选项适合可控 native 进程与测试构建，由 Zygote 启动的普通应用不应把它当线上开关。

工具分工：

1. **Scudo**：Android 11 起大多数 native 分配使用的 hardened allocator，提供安全加固与统计，不给业务所有权，不自动定位泄漏；
2. **GWP-ASan**：生产环境低概率抽样，捕获被采中对象的堆 UAF 与越界并写入崩溃报告，不负责普通泄漏；
3. **HWASan**：自动化测试与内部试用，高覆盖 UAF/越界/栈错误，开销高不适合线上；NDK 支持可追溯到 NDK r21/API 29，不是"Android 14 才出现"；
4. **MTE**：依赖 Arm 硬件标签能力的 64 位设备，用于发现或缓解内存破坏，不提供泄漏引用图；
5. **ASan**：官方已标记被其他工具取代，只用于无法用 HWASan 的遗留测试场景。

判定规则：这些工具命中的是内存安全错误，应按崩溃证据修复；只有稳定增长、未释放栈与业务生命周期互相吻合时，才把结论写成泄漏。

**Q15: 自研 arena、图形与媒体内存为什么必须"另建账"？这类增长怎么定位？**

游戏引擎、数据库、媒体栈常用 `mmap(MAP_ANONYMOUS)` 直接创建匿名映射再由内部 arena 切分：heapprofd 与 malloc hook 最多看到外层申请，外层直接走 mmap 时两者都看不到；GraphicBuffer、AHardwareBuffer、dma-buf 与驱动内存也都不在 malloc 统计内。所以这类资源要在所有者一侧记录：`mmap/munmap` 的地址、长度与用途，arena 的 committed/used/free 与历史峰值，缓存条目数与逐出原因，以及便于 `smaps` 分类的 VMA 命名。

定位方法：先确认哪一类在增长——allocator live bytes、graphics/dmabuf 还是匿名映射；媒体案例中按 owner 检查 `MediaCodec`、`Image`、`ImageReader` 是否按生命周期 `close()/release()`，队列中 outstanding buffer 是否持续增加，stop/release 后是否回到可复用基线；若 heapprofd 平稳而 dmabuf 上升，应转向 buffer queue、fence 与组件释放路径，继续加大 malloc 采样率不会增加有效证据。反例约束：不要在进程中无差别 hook 所有 `mmap` 后就把结果称为业务泄漏——运行时、linker、线程栈、JIT 与文件映射都在用 mmap，必须结合映射标志、fd、VMA 名称与 owner 事件分类。

**Q16: 线上 Native 内存监控的 L0–L3 分层怎么落地？判定"泄漏"的最终依据是什么？**

L0–L3 表示采集成本与证据深度递增，不是事故等级：L0 常驻低成本指标（`uordblks`、RSS、Java committed、线程数、图片/媒体/arena 的 owner counters）；L1 异常确认（连续窗口斜率异常或回落不足时，追加 `smaps_rollup`、`malloc_info()` 附件并记录历史退出原因）；L2 调用栈定位（按设备与版本灰度开 heapprofd 短窗口、受控模块 hook、owner allocation events，并保留 Build ID 符号化）；L3 回到测试环境复现（HWASan、MTE、GWP-ASan 与循环场景的稳态差值）。

落地细节：`smaps_rollup` 只有总览且包含 Java 堆，不能命名成 "PSS-Native"，也不要放进每帧等高频路径（内核仍需遍历页表）；现代 allocator 的区域是 `[anon:scudo:*]` 这类命名匿名映射，只累计传统 `[heap]` 会漏掉大部分；解析器保留原始 VMA 名称，无法识别的归入 other 类，不静默丢弃。版本边界：Android 17 起部分设备启用 MemoryLimiter，进程因匿名内存与 swap 超限被终止时，`ApplicationExitInfo` 表现为 `REASON_OTHER` 且描述含 `MemoryLimiter:AnonSwap`——AAOS13 没有这条路径，命中它只能说明系统因约束结束进程，不能证明 malloc 泄漏。

最终判定依据：工具命中的是内存安全错误时按崩溃证据修复；只有"稳定增长 + 未释放调用栈 + 与业务生命周期吻合"三者同时成立，才把结论写成泄漏。诊断开始与结束都要记录边界，避免把窗口外的存量解释成窗口内泄漏。

**Q17: FD 监控要区分哪些维度？为什么 `/proc/self/fd` 只能算近似快照？**

FD 是进程描述符表中的整数索引，监控要同时区分六个维度：当前打开数量、FD 编号本身（是否达到 `FD_SETSIZE`）、符号链接指向的对象类型、创建代次（generation）、负责关闭的所有者，以及 `dup` 复制后新旧描述符各自的生命周期。编号会复用：关闭后内核通常分配最小空闲编号，double-close 的第二次关闭可能关掉别的线程刚创建的对象，所以只记"编号 123 曾由谁打开"不够，要用 `fd + generation` 区分旧的 123 和新的 123。

`/proc/self/fd` 只是近似快照的原因：枚举目录本身要短暂打开一个目录 FD，采样期间其他线程仍可能打开或关闭 FD，`readlink()` 失败可能只是资源恰好被关闭，不能直接记成泄漏。`/proc/self/status` 的 `FDSize` 是已分配的描述符槽位数，不是当前打开数量。落地做法：常规样本只计数（跳过非数字目录项，不为"精确值"固定减 1），阈值触发时才读取各条符号链接归类为 `socket:`、`pipe:`、`anon_inode:`、文件与设备，并对私有路径归一化、去掉文件名与用户信息；结果保留 `complete` 与 `skipped` 字段，缺少条目的快照不能解释为资源已恢复。

**Q18: `RLIMIT_NOFILE` 与 `FD_SETSIZE` 是两条什么边界？"打开 FD 超过 1024 就会崩溃"错在哪里？**

两者是独立边界：`RLIMIT_NOFILE` 约束进程可打开的 FD 数量，超出 soft limit 时新分配通常返回 `EMFILE`（系统级打开文件表压力则返回 `ENFILE`）；`FD_SETSIZE` 是 `select()` 所用 `fd_set` 位集合的表示边界，AAOS13 bionic 的 `sys/select.h` 将其定义为 1024。

"超过 1024 就会崩"的错误在于混淆了两个条件：FORTIFY 触发条件是"被交给 `FD_SET` 的编号 ≥ 1024"，与打开总数无关——进程打开数量很少，也可能经 `dup2` 得到高编号 FD；AAOS13 的 `__check_fd_set()` 在 fd 越界时触发 `__fortify_fatal`（日志形如 `FORTIFY: FD_SET: file descriptor <n> >= FD_SETSIZE 1024`）并中止进程。反向结论也成立：泄漏使新 FD 编号持续升高时，旧库调用 `FD_SET` 的风险随之增加。修复是两个独立任务——定位把高编号传给 `select()` 的库（新代码应改用 `poll` 或 `epoll`），以及治理 FD 增长源；看到 tombstone 中的该日志，先查 select 调用方，再查编号为何升高。

**Q19: fdsan 与 fdtrack 分别解决什么问题？为什么都不能当线上采集 SDK？**

fdsan（file descriptor sanitizer）用 owner tag 发现重复关闭、关闭后使用与错误所有者关闭：Android 11 起默认在检测到所有权错误时中止进程（AAOS13 `fdsan.cpp` 的默认级别为 `ANDROID_FDSAN_ERROR_LEVEL_FATAL`，核对一致）。fdtrack 是平台内部的 FD 创建栈追踪：bionic 内部 hook 接收创建与关闭事件，`libfdtrack` 用 unwindstack 保存最多 32 帧创建栈（AAOS13 `fdtrack.cpp` 的 `kStackDepth = 32` 核对），适合系统镜像、可调试构建与短时诊断。

不能当线上 SDK 的原因与对策：fdsan 只检查参与标签协议的 FD，不负责统计泄漏数量，遇到 `fdsan: attempted to close file descriptor ...` 的 tombstone 应修正所有权与关闭协议，不要通过降低错误级别隐藏问题；`libfdtrack.so` 与其内部 hook 符号属于平台内部接口，不保证跨版本稳定。线上方案应使用经过验证、开销有上限的自有诊断组件，或采用低频 `/proc` 快照并在资源封装层记录所有者。

**Q20: 做 FD 事件采集（Hook）时，事件表为什么必须带 generation？实现上要处理哪些坑？**

因为 FD 编号会复用：`dup2()`/`dup3()` 成功覆盖目标编号时，新对象继承旧编号，若不先结束旧记录再以递增 generation 建立新记录，账本会把两次不同生命周期的事件混在一起。事件表以 `fd + generation` 为本地键，每条事件至少包含操作、结果、类型、单调时间、线程 ID、来源 ID，以及按采样规则选取的调用栈。

创建入口的完整性：FD 创建不止 `open()`——`socket/socketpair/accept/accept4`、`pipe/pipe2`、eventfd、epoll、inotify、timerfd、memfd、`dup/dup2/dup3` 与 `fcntl(F_DUPFD*)` 都会产生描述符；只拦 `open()` 与 `close()` 必然账目不齐，漏掉 `dup` 或 `accept` 会让创建与关闭记录对不上。

实现约束：thread-local 标志防重入（展开调用栈或写日志时不能再打开 FD）；固定容量与淘汰规则，避免诊断表自身无限增长；只在系统调用成功后更新状态；记录未拦截 API、直接 syscall 与 hook 加载顺序造成的盲区；定期用 `/proc/self/fd` 交叉核对，无法匹配的条目标成 `unknown` 而不是声称完整。这类 Hook 属于长期挂在 libc 路径上的高权重手段，只在受控版本、受限时长内启用，并与同一进程内其他 Native Hook 验证兼容性。

**Q21: 跨 JNI 边界的 FD 所有权协议要写清哪些内容？为什么不能按 readlink 目标决定 close？**

所有权比"崩溃前关几个 FD"更重要：每条成功创建路径都应有且只有一次关闭。Java/Kotlin 侧优先用 `use{}` 与 try-with-resources，Native 侧用 RAII wrapper 把关闭绑定到对象析构；`use{}`/RAII 要覆盖成功、异常、取消与超时全部路径。

跨 JNI 边界的接口文档至少写清：参数是 borrowed（调用方仍持有，接收方不能关闭）还是 transferred（所有权转给接收方）；哪一方负责 `close()`；`dup()` 之后新描述符归谁；`detachFd()` 取出原始 int 后 Java 封装对象不再负责关闭什么；异常与取消路径如何关闭；callback 超时、页面销毁与进程切换时怎样释放。

不能按 readlink 目标决定 close 的原因：符号链接目标只说明对象类型，说明不了所有者——关闭 Binder、Looper、数据库或其他线程正在使用的 FD 会造成关闭后使用与数据损坏；同理，线程也不能因为名称陌生就强制 `interrupt`/`stop`。修复的终点永远是创建模块和明确的生命周期所有者。

**Q22: FD 证据与 OOM、ANR、Native Crash 的关系是什么？哪些推论是越界？**

FD 监控提供的是故障前的趋势、构成与所有权证据，它不能替代 tombstone、ANR trace 或 `ApplicationExitInfo` 的判定，常见越界推论要逐条排除：

1. **`OutOfMemoryError: pthread_create` 不证明 Java 堆满**：要看 task 趋势、栈大小与 `VmSize`，属于线程资源失败；
2. **`EMFILE` 失败的那次 `open` 不一定是泄漏点**：它只是第一个撞上 soft limit 的调用，泄漏源要看类型分布与增长来源；
3. **`ENFILE` 不能推出当前 App 单独泄漏**：它是系统级文件表压力；
4. **fdsan abort 不代表数量到上限**：它指向的是所有权错误（重复关闭、错误所有者），与打开数无关；
5. **`FD_SET` FORTIFY abort 不代表打开数超过 1024**：编号达到 1024 即可触发；
6. **Binder 线程全在等待不靠加线程解决**：常由同步事务阻塞或调用环造成，线程数只是伴随现象；
7. **`anon_inode:[eventpoll]` 持续增长不一定是泄漏**：Looper/HandlerThread 会正常持有 epoll/eventfd，只有随页面或模块反复销毁而持续增长才构成泄漏证据。

排查顺序因此是：先看 FD 总量、类型分布与最大编号的趋势，再定位持续增长的类别与创建方，最后回到创建模块与生命周期所有者修复。

**Q23: FD 接近上限时应采取什么动作？fatal handler 里为什么只能写预生成摘要？**

资源接近上限时，动作按影响范围控制：对新任务施加背压（限速、排队或拒绝），停止可选预热、调试日志、长连接或并发下载；由对应页面或模块执行自己的 `close()`/`shutdown()`/`quitSafely()`；停止隔离进程中的可选功能并在满足条件后重建进程。反例：不要强制关闭任意 FD、停止未知线程、清除用户数据，也不要把主动终止主进程当日常恢复方案——SafeMode 只能跳过边界明确的可选模块。

fatal handler 只能写最小证据的原因：资源接近耗尽时，创建线程、分配大数组、枚举全部调用栈或打开新文件都可能失败——此时调用 `Thread.getAllStackTraces()`、遍历每个 `fdinfo` 或启动上传，都会把诊断变成新的故障。稳妥流程是：平时把低成本趋势写入固定容量环形缓冲；阈值触发时预生成有大小上限的 FD 摘要；崩溃现场只写摘要 ID 与少量计数；下一次启动用 `ApplicationExitInfo` 与 tombstone 核对后再后台上传。触发条件按进程基线组合绝对值、占 soft limit 的比例、增长速度、持续时间与同设备分位数——主进程、WebView 进程、播放器与 isolated process 的基线不同，共用固定阈值会掩盖角色差异。隐私上路径归一化为目录类别、线程名去掉动态 ID、socket 只留协议与 endpoint ID、调用栈按 build ID 表示；低熵字符串（短文件名、手机号类）即使散列也可能被字典猜出，能用枚举类别就不要上传原值的 hash。

**Q24: Java 堆看起来健康、Native 内存却持续上涨，logcat 偶见 "BinderProxy leak?"——这是什么泄漏？怎么确认与避免？**

BinderProxy 是指向远端 Binder 对象的 Java 代理，它的主要内存在 native 侧：大量未释放的远端代理不体现在 Java 堆统计里，表现为"Java 堆正常、Native Heap 涨"——排查要归入 Native 内存账本（见 Q10/Q15 的分层），而不是 Java 引用链分析。

1. **确认**：logcat 搜 "BinderProxy leak?" / "JavaBinder"；调试构建可对比 BinderProxy 实例计数随业务操作的增长曲线（AOSP 有 instance-count 追踪点）；
2. **常见根因**：`linkToDeath()` 注册后不 `unlinkToDeath()`（DeathRecipient 持有代理）、监听器/回调注册表只加不减、长生命周期对象缓存了短生命周期进程的代理；
3. **避免**：死亡通知与监听器成对注册/注销；对端进程退出语义下主动清空代理集合；把"远端服务句柄"的所有权写进模块边界协议——与 Q21 的跨 JNI FD 所有权同构，远端句柄也是必须显式归还的资源。

**Q25: LeakCanary 报 Handler 持有 Activity、应用主线程"只处理异步消息"式卡死——Handler 体系有哪些经典泄漏与卡死模式？**

Handler 体系的泄漏与卡死都源于"消息队列持有 Handler、Handler 持有外层对象"这条引用链，再加上同步屏障的配对纪律。

1. **Activity 泄漏**：非静态内部 Handler 隐式持有外层 Activity；`postDelayed` 的 Message 在队列存活期间形成 Message→Handler→Activity 链，让 Activity 无法回收——改成静态 Handler + `WeakReference<Activity>`，并在 `onDestroy()` 调 `removeCallbacksAndMessages(null)`（注意 `removeCallbacks(null)` 只清 Runnable、不清 Message）；
2. **同步屏障泄漏**：`postSyncBarrier(token)` 之后队列里所有同步消息被无限挂起（只有异步消息能执行），异常路径漏掉 `removeSyncBarrier(token)` 就表现为整机级卡死——Choreographer/ViewRootImpl 是历史上最高发的区域；业务代码除非明确需要，不要直接操作屏障；
3. **退出纪律**：`quit()` 立即丢弃队列中全部消息；`quitSafely()`（API 18+）处理完已到期消息后退出、丢弃未到期消息；退出后 `post` 返回 false，调用方要处理发送失败而不是假设永远成功；
4. **IdleHandler**：`queueIdle()` 返回 true 会被持续回调，且"队列空闲"不等于"没有 delayed 消息"——不要在里面做依赖完整队列状态的事（启动期专项见 05-启动优化.md Q10）。
