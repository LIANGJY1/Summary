# 启动优化：应用侧启动治理

**Q1: 启动监控为什么不能只上报 `Application.onCreate()` 的出入口耗时，为更早拿到时间点新增自动初始化 Provider 错在哪？**

只埋 `Application.onCreate()` 会漏掉系统收到启动请求、进程创建、`bindApplication`、Provider 安装与首帧渲染这几段，也无法表达首屏核心内容何时可用；而为了"更早"新增自动初始化 Provider，等于把监控 SDK 自己的类加载与初始化放进每一次冷启动的关键路径——Provider 在 `Application.onCreate()` 之前安装（该时序已按 AAOS13 源码核对，见 [../performance/02-响应速度.md](../07-performance/02-响应速度.md)）。正确做法是固定一份测量契约并分层埋点：已有最早轻量入口或 `Application.attachBaseContext()` 记 `process_observed`（只说明 App 代码能看到进程，不含 fork 精确时间）；`onCreate()` 出入口只解释 Application 阶段；首屏状态机记 `content_ready`；`reportFullyDrawn()` 调用处记 `fully_drawn_reported`。已有 Provider 即使承担最早入口，也应只保存一个时间戳与必要身份，序列化、压缩、网络发送与扩展设备信息延后到首帧后；采集器本身不能在首帧前建大线程池、扫描完整设备信息或同步写日志。边界：`onResume`、`OnPreDrawListener` 与 `Choreographer.FrameCallback` 都只是自定义近似点，事件名要写成 `pre_draw`、`frame_callback`，不能冒充平台 TTID，因为它们都不能证明 SurfaceFlinger 已完成显示。

**Q2: `ApplicationStartInfo` 提供哪些系统侧启动信息，Android 13 设备上能用吗，读取时间戳有哪些陷阱？**

`ApplicationStartInfo` 是 Android 15（API 35）引入的系统启动记录，AAOS13（Android 13）上不存在该 API（本地核对 frameworks/base 无此类、system_server 无 `AppStartInfoTracker`），Android 10–14 仍需自建埋点。它提供启动原因 `getReason()`、启动类型 `getStartType()`（cold/warm/hot）、启动状态 `getStartupState()`、进程名/PID/UID，以及 launch、fork、bindApplication、`Application.onCreate`、first frame、fully drawn 等单调时间戳；Android 16（API 36）增加 `getStartComponent()` 区分组件类型，API 35 上调用它必须先查版本。读取陷阱按 Android 17 行为核对转写：历史列表 `getHistoricalProcessStartReasons()` 混有同应用其他进程与未完成记录，先按 PID 与进程名过滤再按 `LAUNCH` 取最新，不能无条件取第 0 项；时间戳 Map 的 key 可能缺失，不能把"未写入"当 0，也不能按常量编号排序——只有起止节点都存在且终点不早于起点，区间才有效；平台没有 `FULLY_DRAWN` 状态，fully drawn 只是依赖应用调用 `reportFullyDrawn()` 的可选时间戳，首帧完成监听在 `FIRST_FRAME` 时回调、回调快照通常没有 `FULLY_DRAWN`，需要 TTFD 时应在上报后重新查询新副本；API 36 及以下 Service 启动的 `LAUNCH` 时间戳可能不准确（官方标注）。可用 21–30 的保留 key 经 `addStartInfoTimestamp()` 写业务时间点，兼容不同版本实现的做法是每个 key 首帧前只写一次、回读缺失就按缺失处理。

**Q3: 启动各阶段耗时为什么要用单调时钟相减，`uptimeNanos`、`elapsedRealtimeNanos`、`nanoTime`、`currentTimeMillis` 各适合什么？**

启动耗时要靠"终点减起点"，时钟必须只向前推进、不受用户改时、网络校时和时区影响，`System.currentTimeMillis()` 这类墙钟只适合记录事件发生的对齐时间（发布、灰度），相减得到的"耗时"可能被校时污染。各时钟的分工：`SystemClock.uptimeNanos()` 不计深度休眠，适合进程内 CPU/主线程工作区间，平台启动记录（Android 15+）的各节点也用它，因此自定义点经 `addStartInfoTimestamp()` 写入时必须用同一时基；`SystemClock.elapsedRealtimeNanos()` 计入深度休眠、以开机为基准，适合同一台设备本次启动会话内的阶段耗时；`System.nanoTime()` 只保证用于计算同一运行环境内的时间差，不能依赖其绝对起点。边界：不要把自有 `elapsedRealtimeNanos` 与平台记录里的 `uptimeNanos` 节点相减；一个事件可同时存墙钟（对齐发布）与单调耗时（阶段计算），服务端不跨设备相减单调时钟。

**Q4: 线上启动分位数应该怎么聚合，"TTFD 变好但完成率下降"说明什么？**

启动耗时呈右偏长尾，均值会被极慢样本拉高、也会被大量热启动稀释；分位数必须从同一 cohort（冷/温/热、入口、安装状态、版本、设备档位一致的样本组）的原始数据或可合并分布摘要计算，不能先算每台设备或每天的分位数再平均——平均分位数不是全量分位数。样本至少按冷/温/热、首屏路由与入口、首装/升级/普通启动、版本与实验组、Android 版本与设备档位、主/远程进程分组，Profile 编译状态可靠可得时单独分组。"TTFD 数值变好但完成率下降"是幸存者偏差：启动期间退出、崩溃、ANR、进程被杀或长期 loading 的会话没有 TTFD，排除后曲线"变好"，慢到无法完成的会话恰恰被隐藏，所以每个窗口要同时展示请求会话数、TTID/TTFD 有效样本数与完成率、超时数、首屏前崩溃与退出。回归门禁应同时满足：同 cohort 样本量达标、P90 绝对增量超产品预算、相对增量超历史噪声带、置信区间不跨"无影响"边界、连续两个窗口成立；慢样本高采样的诊断数据不能与告警数据直接混算分位数，合并须按采样概率加权。Play Vitals 的 excessive 启动阈值（冷 5 秒、温 2 秒、热 1.5 秒，官方口径转写）是外部告警边界，内部预算应按入口与设备档位设得更严格。线下对照用 Macrobenchmark 固定 `CompilationMode` 与启动模式（工具细节见 [../performance/02-响应速度.md](../07-performance/02-响应速度.md)）。

**Q5: 启动优化为什么先删任务再谈编排框架，任务按什么阶段分级？**

启动框架不能把不必要的工作变便宜，拿到初始化清单先逐项回答：当前进程需要吗、当前入口需要吗、首帧前必须完成吗、TTFD 前必须完成吗、失败时能否显示降级界面、能否在功能首用或空闲阶段再初始化。按完成边界分四阶段：`PRE_APP`（`Application.onCreate()` 之前，由 Provider 组件生命周期强制，不应作为追求"更早"的优化手段——放进去的重活直接进入更早的主线程关键路径）；`PRE_FIRST_FRAME`（TTID 前，首屏渲染不可缺少的同步状态）；`PRE_FULLY_DRAWN`（TTFD 前，首要操作所需的数据与能力）；`DEFERRED`（页面可用后，二级功能、预取、非必要 SDK）。"从主线程移到后台"只消除主线程直接执行时间，后台任务占满性能核、触发缺页或争用同一数据库时 TTID/TTFD 仍会变差；"首帧后执行"只改开始时机、不减工作总量；"首次使用"把成本移到用户第一次点击；"按需交付"改的是包里有没有代码。边界：长期轮询、常驻连接与周期任务属于运行期调度，启动任务只负责把它们配置到约定状态，不能让任务图一直保持未完成。

**Q6: 启动任务图的节点为什么必须把"异步完成"建模成一等状态，"SDK init 已提交"与"SDK 已就绪"差在哪？**

后继任务只能在前驱产生最终结果后就绪，所以节点必须声明 id、进程、phase、依赖、执行上下文、任务逻辑与完成信号，且完成要带结果——`Success`、`Degraded`（含备用值）、`Failed` 三态，"已提交异步工作"不是完成。用 `suspend` 函数表达逻辑完成点：函数挂起时不占住调用线程，只有结果产生才算结束；SDK 的 `startAsync()` 返回只说明请求已提交，依赖它的后继不能据此运行。App Startup 的 `create()` 必须同步返回可用实例，内部若只提交异步任务，依赖顺序对逻辑就绪没有保证。框架也可以用 Guava `ListenableFuture`、Java `CompletionStage` 或带完成回调的接口实现同一契约。边界：等待异步结果时应在生产者与消费者两端记录可关联的 async trace（并控制关联 ID 数量），否则 trace 里"切片结束"只代表提交，无法定位真正的初始化完成时刻。

**Q7: 构建启动任务图时必须拒绝哪些无效输入，DFS 与 Kahn 检测环各怎么做？**

任何任务执行前，构图校验器应拒绝：重复 ID 与不存在的依赖；自依赖与环；被禁用的节点仍被硬依赖；Main 任务阻塞等待后台 worker、而该 worker 又要回 Main 才能完成；当前进程不允许的节点；阶段倒挂（如首帧任务硬依赖 `DEFERRED` 任务）；多个节点写同一非线程安全状态却没有顺序约束。环检测两条等价路径：DFS 把当前递归路径中的节点标为 `GRAY`，再次遇到 `GRAY` 节点即存在环，并可直接输出环路径；Kahn 拓扑排序反复移除入度为 0 的节点，处理结束后仍有剩余节点即存在环。错误信息必须输出完整环路径（如 `A → B → C → A`），方便配置与模块负责人定位。边界：任务图可以有多个互不依赖的根节点，不要求整张图只有一个连通分量；条件任务应在构图时移除节点并重新检查所有后继，而不是留到执行阶段才跳过。

**Q8: 启动任务的超时与失败语义怎么定义，"A 超时就当作完成"会破坏什么？**

超时通常只让等待方停止等待，底层网络、Binder、文件 I/O 或供应商线程可能继续运行；`Future.cancel(true)` 与线程 interrupt 只是协作取消信号，任务代码需要主动检查取消状态或调用底层取消 API。把硬依赖的超时映射成"完成"会破坏语义——正确做法是映射成 `Degraded` 或 `Failed`，再由后继的契约决定能否继续。失败策略至少四种：`FAIL_GRAPH` 终止依赖该结果的关键路径并展示可恢复错误；`USE_FALLBACK` 产出类型一致的本地或默认备用结果；`SKIP_DEPENDENTS` 跳过所有无法满足硬依赖的后继；`CONTINUE_SOFT` 仅软依赖继续并记录能力缺失。框架要保存原始异常、任务 ID、进程、线程与已运行时长；捕获 `Throwable` 后无条件继续会掩盖 `OutOfMemoryError` 等进程级风险，也会让后继在半初始化状态运行。反例：为每个任务新建线程再用 `CountDownLatch.await(timeout)` 包住，只会让 executor 工作线程空等另一线程、无法停止被包裹任务，还放大线程数与栈内存。

**Q9: Jetpack App Startup 1.2.0 的执行模型是什么，动态特性模块与多进程场景各有哪些坑？**

App Startup 1.2.0 用一个 `InitializationProvider` 发现 Manifest `<meta-data>`（value 为 `androidx.startup`）声明的 `Initializer`：反射按类名加载、深度优先初始化 `dependencies()`、用 `initializing` 集合检测环、调用 `create()` 并缓存结果、为发现与初始化加 Trace；全部发生在 Provider 安装阶段的主线程，不支持优先级、超时、取消与异步结果。三个关键边界：其一，动态特性模块——metadata 指向尚未安装模块中的类时 `Class.forName()` 抛异常并被包装成 `StartupException`，进程可能在 `Application.onCreate()` 之前终止，可选模块的桥接 initializer 应留在基础模块或等模块安装后手动初始化；其二，多进程——`AppInitializer` 是进程内单例，Provider 归属由最终 Manifest 的 `android:process` 决定，默认 Provider 不会因为应用有多个子进程就各执行一次，跨进程完成关系要用 Binder、Provider 或持久状态显式传递；其三，手动初始化——在最终合并 Manifest 中对对应 `<meta-data>` 用 `tools:node="remove"`（Merger 按 `android:name` 匹配，只从自己源码删一行不能证明已移除），需要时调 `AppInitializer.initializeComponent()`，注意关闭一个组件的自动初始化也会关闭由它带入的依赖。metadata 与集合遍历顺序不是契约，有先后要求必须写进 `dependencies()`。

**Q10: `MessageQueue.IdleHandler` 的 `queueIdle()` 在什么条件下被调用，为什么不能当"设备空闲"信号？**

`IdleHandler` 在所属 Looper 没有可立即分发的消息、准备进入等待时收到 `queueIdle()`——即使队列里仍有未来时间点才到期的消息也可能被调用；返回 `true` 表示以后每次进入 idle 仍可调用，`false` 表示用后移除。它只说明主线程消息队列暂时无事可做，不代表 CPU 或 GPU 利用率低、下一次输入或 VSync 很远、系统给了固定执行预算，也不说明设备适合预解压或构建大对象。正确用法是只做有界检查或向调度器发一次信号（返回 `false` 避免重复触发），由调度器再核对首帧状态、页面可见性、任务 deadline 与资源冲突；禁止在 `queueIdle()` 里读数据库或文件、解析大 JSON、创建大量对象、返回 `true` 轮询业务状态，也不要让每个 SDK 各自注册。版本边界：Android 17 引入并发消息队列 DeliQueue，`targetSdkVersion >= 37` 默认启用，IdleHandler 的外部语义与 legacy 保持一致；AAOS13 仍是经典单 monitor 锁的 `MessageQueue` 实现（本地核对无 `CombinedDeliMessageQueue`），两条路径下"队列将要等待"的语义相同。

**Q11: "首帧已提交"为什么不能靠 `view.post()` 或 `onResume` 判断，`registerFrameCommitCallback()` 有哪些边界？**

`view.post()` 只表示 Runnable 进入了主线程消息队列，执行位置受队列已有消息、同步屏障与 traversal 调度影响；`onResume` 不等于首帧，`OnPreDrawListener` 发生在即将绘制之前，`Choreographer.FrameCallback` 只是帧调度回调，三者都不能证明该帧已提交或显示。API 29+ 的硬件渲染窗口可用 `ViewTreeObserver.registerFrameCommitCallback()` 观察"当前渲染内容已提交到 swap chain（等待显示的图形缓冲队列）"，用它打开调度门、不在回调里执行初始化。边界：回调只针对注册后参与提交的帧，注册太晚只能观察后续帧；提交到 swap chain 不等于像素已经显示；软件渲染时不会回调，允许软件渲染的应用要提供独立的保守触发或把任务改成首次使用执行，且该信号只用于性能调度、不作为业务正确性的唯一条件。首帧后队列要限流：控制同时运行的 CPU 任务数、I/O 是否访问同一文件或数据库、主线程回调分散到多个帧，jank、thermal 或低电量时暂停非必要预热；从 TTID 前移走的任务可能延长 TTFD，只有 TTFD 必需项才进入完成条件。需要跨进程存活的预热交给 WorkManager，它的调度时机不是精确的"首帧后 500 ms"。

**Q12: 启动线程池为什么"按核数创建 + 无界队列"常常无效，`CallerRunsPolicy` 会把什么搬回主线程？**

`ThreadPoolExecutor` 在核心线程都忙时先调用 `workQueue.offer()` 入队，只有入队失败才创建非核心线程，最后才执行拒绝策略——所以配无界 `LinkedBlockingQueue` 时线程数停在核心线程数，`maximumPoolSize` 不参与扩容且积压无上界，调大它没有效果。有界队列的拒绝策略必须绑定任务契约：`CallerRunsPolicy` 让提交线程直接执行被拒任务，提交者是 Main 时后台重活直接回到启动关键路径，主线程提交禁止使用；关键任务被拒应记录并走明确降级，遥测类任务可丢弃但要记录丢弃原因。并发度也不该固化成 `availableProcessors()`：它不表达大小核、调频、温度与 RenderThread 竞争，首帧期间占满所有核心可能让 Main 与 RenderThread 更慢；阻塞线程不占 CPU 但占栈与调度结构，I/O 并发应按数据库、连接池、Binder 与服务端配额设上限，同池同步等待子任务会造成永久饥饿。优先级方面 `Process.setThreadPriority()` 对应 Linux nice 值（AAOS13 核对：`THREAD_PRIORITY_BACKGROUND = 10`、`FOREGROUND = -2`、`DEFAULT = 0`，数值越小权重越高），由 `java.lang.Thread` 创建的子线程不继承它，线程工厂应显式命名并让每个 worker 在自己入口设置；不要把业务线程硬绑大核。反例参考：`AsyncTask` 的 `THREAD_POOL_EXECUTOR`（AAOS13 核对：core 1、max 20、`SynchronousQueue`、拒绝后转 5 线程串行兜底）是遗留实现，不是应用线程池模板。

**Q13: 多进程应用为什么必须逐进程建初始化清单，在 `Application.onCreate()` 里按进程名分支漏掉了什么？**

Provider 归属由最终 Manifest 的 `android:process` 决定：默认 Provider 只随默认进程安装，声明 `:worker` 的 Provider 只在对应进程创建；每个进程有独立的堆、静态字段、ClassLoader 与 App Startup 单例，一个进程不能依赖另一个进程的静态 `initialized` 布尔值。在 `Application.onCreate()` 里按 `Application.getProcessName()`（API 28+）分支只能约束分支之后的工作——分配给该进程的自动初始化 Provider 已在此前执行，无法撤销；类第一次加载触发的静态初始化同样拦不住，所以进程选择应在 Manifest 或构图阶段完成，而不是在 initializer 里先加载全量模块再 `if` 跳过。进程启动没有"只创建进程、暂不运行组件"的通用接口：启动 Activity、`startService()`、`bindService()`、访问远程 Provider、接收广播都可能触发进程创建。拉起时机按用户路径分档：首屏前（缩小协议与初始化集、异步协议 + deadline + 降级）、首帧后（低端机上仍会与主进程竞争 CPU/存储/内存，预热实验要同时比较命中率、TTID/TTFD、全应用 PSS 与失败率）、临近入口（明确产品信号、过期取消）、系统调度（WorkManager/JobScheduler）。普通私有远程进程沿用应用 UID 与权限，`isolatedProcess` 用隔离 UID、没有自身权限，两者的权限假设要分别验证。

**Q14: ContentProvider 自动初始化的成本从哪里来，"Provider 数量少"能直接换算成启动快吗？**

Provider 的成本不只是 `onCreate()`。AAOS13 的链路（已按源码核对）：`handleBindApplication()` 先创建 Application，再 `installContentProviders()` 对每个 Provider 经 `AppComponentFactory.instantiateProvider()` 实例化、`ContentProvider.attachInfo()` 读取权限/authorities/exported 并落到字段、在主线程调用 `onCreate()`，最后把本批 holder 汇总后一次调用 `publishContentProviders()` 发布给 system_server——是批量一次发布，不是每个 Provider 单独一次 Binder 调用。成本分四层看：组件固定成本（类加载、构造、`attachInfo`、authority 注册）、`onCreate()` 负载（文件、数据库、反射、SDK 初始化、native 库加载）、资源竞争（它创建的后台线程与首帧争 CPU/I/O/锁）、进程成本（远端 Provider 触发承载进程启动与发布）。常见误判：`onCreate()` 很快不代表它创建的后台线程不会与首帧争资源；删除一个 Provider 后 TTID 下降，也可能是其业务初始化一起被删；看到 Provider 类不代表全部成本归属框架。Provider 数量只能作审计入口，不能换算毫秒；测量要用自有 Provider 的稳定 trace 切片、第三方 Provider 的合并 Manifest + Perfetto 组合证据，以及唯一差异为是否保留自动入口的 release A/B。

**Q15: `android:initOrder` 和 Manifest 书写顺序能表达依赖吗，边界在哪？**

`android:initOrder` 只能在同一进程内声明 Provider 的相对实例化顺序（数值高的先初始化），Manifest 中元素的书写顺序不是依赖契约。它只能表达静态先后，不能让 `onCreate()` 异步、不能表达完成结果/失败/降级、不能解决跨进程依赖、也不能缩短各 Provider 自身的工作——所以它适合"谁先装配"这类弱约束，需要完整任务依赖时应改用 App Startup 的同步依赖图或显式任务框架。改动顺序前先核对合并结果：源码 Manifest 不是安装包里的最终结果，依赖库、build type、product flavor 与 placeholder 都可能改变组件，AGP 的合并决策报告在模块 `build/outputs/logs/manifest-merger-<variant>-report.txt`，要按准备发布的每个构建变体检查，不能只看 debug。

**Q16: 首帧前同步访问远程 Provider 或同步等待 Binder 会发生什么，`MODE_MULTI_PROCESS` 和 `Application.onTerminate()` 为什么不可依赖？**

主进程通过 `ContentResolver` 同步访问远端 authority 时，`ActivityThread` 会向 system_server 请求 Provider 并等待承载进程完成发布，等待方若是主线程，进程创建、Provider 安装、`Application.onCreate()` 的全部时间都进入 UI 关键路径；`bindService()` 后又同步等待连接结果同理——远端进程并不会让同步访问自动变快。跨进程能力应建模为状态机（Disconnected/Connecting/Ready/Failed，处理 `onServiceDisconnected`/`onBindingDied`/`onNullBinding`/`binderDied` 的不同语义），业务协程异步等待 ready，主线程禁止 `CountDownLatch`、自旋或无限期同步调用。超时边界：`withTimeout` 只让调用方协程停止等待，不能中断已进入内核的同步 Binder 事务，需要硬时限的耗时协议要改成异步请求 + 请求 ID + 显式 `cancel` + 服务端可重试。两个历史 API 不可依赖：`Context.MODE_MULTI_PROCESS` 自 API 23 废弃，不能可靠协调跨进程 `SharedPreferences`（各进程独立缓存、无冲突合并规则），跨进程状态要有唯一写入者与一致性协议；`Application.onTerminate()` 在量产设备结束进程时不会被调用，恢复要靠 Binder 死亡监听、持久化状态与幂等请求。另外 `android:multiprocess="true"` 允许系统在调用方同 UID 进程本地创建 Provider 实例（AAOS13 核对：`ContentProviderRecord.canRunHere()` 同时检查 multiprocess 与 UID），省部分 Binder 但复制对象/缓存/连接，不是通用启动优化。

**Q17: Baseline Profile、Startup Profile、Cloud Profile 与本地运行时 profile 各由谁生产、被谁消费？**

四类 profile 的生产者与消费方不同，验证方法不能互换：Baseline Profile 由应用/库作者在 CI 生成，随 APK/AAB 交付给 ART 做 AOT 编译（Android 7/API 24+），可覆盖 Day-0（新装、升级后的首次使用）；Startup Profile 是其中的启动子集，但消费方是构建期的 D8/R8，用于调整 DEX 布局，不产生另一套 ART 编译状态；Cloud Profile 由 Google Play 聚合真实用户数据后分发（API 28+，需要足够样本与聚合时间，官方口径为数小时到数天），补充 Baseline 未覆盖的热路径；本地运行时 profile 由设备上的 ART/JIT 随使用积累，指导该设备后续的 `speed-profile` 编译。库可以随 AAR 贡献 Baseline Profile（构建时合并、按 release 混淆结果重写），但不能替宿主贡献 Startup Profile——库不知道宿主的启动入口与主 DEX 容量。因此两类规则可来自同一生成脚本（启动场景设 `includeInStartupProfile = true`，滚动、详情等非启动 CUJ 保持 `false`，否则扩大启动 DEX 布局范围），但 Baseline 的验证看设备编译状态与启动基准，Startup 的验证看构建产物 DEX 布局。工具链版本按材料口径固定并记录（2026-08 官方推荐组合 AGP 8.0.0、Macrobenchmark 1.4.1、ProfileInstaller 1.4.1；Startup Profile 建议 AGP 8.2+），升级任一项后需重新生成与测量。

**Q18: 请求了 `speed-profile` 就一定得到 speed-profile 产物吗，怎么确认设备实际编译状态？**

不一定。`speed-profile` 表示"只 AOT 编译有效 profile 选中的方法"，不代表整个应用已 AOT；找不到有效 profile 时，实际 filter 会退为 `verify`，所以排查必须同时记录 requested filter（请求值）与 actual filter（实际值）。Android 13 用 `dumpsys package dexopt` 查看（本地核对 PMS 侧存在 `dumpDexoptState`），输出里 `status=speed-profile` 表示存在 profile 指导的编译产物，`reason=install-dm`/`bg-dexopt`/`cmdline` 说明触发原因；Android 14+ 首选 `pm art dump`（AAOS13 的 `pm` 无 `art` 子命令，本地核对）。验证外部 profile 能否被接受：先 `pm art clear-app-profiles`（14+ 命令；13 用对应 `cmd package` 能力）清本地采集的 profile，再 `pm compile -m speed-profile -f -v`，输出 `actualCompilerFilter=speed-profile` 说明找到有效 profile，`=verify` 说明没有（文件名错误、格式错误或 DEX checksum 不匹配）。版本差异：Android 13 的安装期 dexopt 仍由 PMS 经 installd 执行（本地核对 `frameworks/native/cmds/installd/dexopt.cpp`），PackageManager → ART Service → artd → dex2oat 的链路自 Android 14 起。边界：Play 的 Baseline Profile 编译可能发生在后台设备更新，安装命令返回不代表已完成；`pm compile --reset` 与"卸载重装"不等价，实验记录要写清用了哪条命令。

**Q19: `.dm` 文件是什么、不等同于什么，ART 接受一个外部 profile 要满足什么条件？**

`.dm` 是 Dex Metadata 容器，与某个 APK 一一对应的 ZIP 文件，可以携带 profile、VDEX 与配置——它不等同于 Cloud Profile，是否来自 Play、包含什么要结合安装来源与文件内容判断。ART 接受它要过三道关：文件名与 APK 配对（`base.apk` 配同目录 `base.dm`，split APK 各自对应，base 的 `.dm` 不能替代 split 的）；能作为 ZIP 归档打开；profile 格式正确且 DEX checksum 与当前 APK 匹配，否则拒绝。安装期与后续 dexopt 是两个时机：`PackageManager.INSTALL_IGNORE_DEXOPT_PROFILE` 只让安装期忽略 `.dm` 与 APK 内嵌 profile，之后后台 dexopt 或 `pm compile` 仍可使用 profile——profile 缺失通常只损失优化，不改变代码语义。版本差异：Android 13 的安装期 profile 消费在 PMS/installd 链路；从 Android 14 起 ART Service 统一选择 profile 与 filter。边界：APK 内嵌 Baseline Profile、相邻的 `<apk-name>.prof` 与 `.dm` 都属于 ART 可选的外部输入，`actualCompilerFilter` 区分不了来源，要区分必须控制安装产物；"设备能消费外部 profile"与"这个 `.dm` 是否来自 Play"是两个问题。

**Q20: Startup Profile 的 DEX layout 收益怎么验证，"多了一个 classes.dex"是回归吗？**

Startup Profile 在构建期被 R8/D8 消费，APK/AAB 中没有供 ART 使用的独立 `startup.prof`，验证必须沿构建产物逐层走：AGP 8.8+ 检查 AAB 的 `r8.json` 构建元数据中至少一个 DEX 带 `"startup": true`，并把其中 checksum 与包内对应 DEX 的 SHA-256 对齐——不一致说明 R8 之后有加固、插桩或重打包悄悄改写了 DEX，要先修复链路再谈收益；用 APK Analyzer 确认主要启动类实际位于哪个 DEX；再用同编译模式 Macrobenchmark 比较 TTID/TTFD 与缺页。单 DEX 应用因布局优化变成两个 DEX 不一定是回归：构建工具可能把启动代码集中到主 DEX、把非启动代码移到后续 DEX，判断依据是启动类分布、R8 诊断与测量结果。两个边界：规则过宽会让非首屏 CUJ 挤占主 DEX 容量、必要启动代码反而溢出，应缩小到初始显示路径；A/B 必须单变量——只改变是否提供 Startup Profile，Baseline Profile、R8 规则、签名、安装步骤与设备端 `CompilationMode` 保持一致，否则 ART 编译与 DEX 布局的贡献无法区分。杀进程冷启动不代表 page cache 冷态，首轮结果不能直接解释成稳定的 DEX I/O 收益。

**Q21: 用户点击图标后看到的"启动画面"有哪些可能的实现，热启动会显示 Splash 吗？**

启动期间用户先看到的通常是系统创建的 starting surface，不一定是带品牌图标的 Splash。system_server 的 `ActivityRecord` 检查显示状态、主窗口是否已绘制、有无可用且兼容的 TaskSnapshot、任务与进程状态和主题，决定是否创建与类型，再交 WM Shell 绘制。可选类型包括 Splash Screen、纯色 Splash、legacy Splash（沿用旧主题行为）、TaskSnapshot（任务上次可见界面的快照）、windowless（直接挂到任务表面的实现）与 none；AAOS13 已有 `STARTING_WINDOW_TYPE_SPLASH_SCREEN`/`SOLID_COLOR_SPLASH_SCREEN`/`LEGACY_SPLASH_SCREEN`/`SNAPSHOT`/`NONE` 常量（本地核对），windowless 为后续版本新增。选择依据启动条件：TaskSnapshot 常用于已有任务切回且快照兼容，Splash 常见于冷启动、新任务与 warm start；hot start（进程与目标 Activity 都在、只需带回前台）不会重复显示 Splash。两个边界：Splash 由系统在 App 首帧前创建，App 不需要自己 inflate 一张启动页；App 主题只是输入之一，最终类型受任务、进程、snapshot 与系统策略影响，所以"点击后看见一张图"不能推断走了哪条路径，解释 Perfetto 前先确认启动类型与 starting window 类型。

**Q22: AndroidX core-splashscreen 在不同系统版本上的能力边界是什么，starting theme 各属性控制什么？**

`androidx.core:core-splashscreen`（材料口径：1.2.0 为当前稳定版，`minSdk` 21）按系统分三档实现：API 21～22 只有 AndroidX 兼容主题、启动早期没有兼容 Splash 图标；API 23～30 模拟 Android 12 行为、支持静态图标但不支持图标 AVD 动画；API 31+ 委托平台 SplashScreen API，含系统 Splash、图标动画与平台退出交接，因此测试至少覆盖 21/22、23～30、31 与目标 API，不能只在 Android 17 模拟器验收。starting theme 要点：`windowSplashScreenBackground` 用单一不透明颜色并在 `values-night` 提供对应资源；图标按 adaptive icon 安全区域裁剪、四周留余量；`windowSplashScreenAnimationDuration` 只描述图标动画时长、不控制 Splash 停留多久（材料口径：API 33 起平台直接从 AVD 推断时长）；`postSplashScreenTheme` 指向正常主题，与手动 `setTheme()` 只能保留一套切换责任；底部品牌图官方设计规范不建议使用。所有可能直接成为起始 Activity 的外部入口（launcher、deep link、通知冷启动）都要配 starting theme 并在 `super.onCreate()` 前调用 `installSplashScreen()`，只验证桌面图标会漏掉其余路径。

**Q23: 自定义 Splash 退出动画必须做什么收尾，旧 `windowBackground` 与专用 SplashActivity 在 Android 12+ 的问题是什么？**

注册 `setOnExitAnimationListener` 后回调在 UI 线程执行，动画结束的所有路径——正常结束、取消、Activity 销毁、系统动画缩放关闭导致立即结束——都必须调用 `provider.remove()`，否则 Splash View 持续覆盖应用；参数是 `SplashScreenViewProvider`，与 `ContentProvider` 无关。退出动画只改变画面交接：内容首帧必须已在 Splash 下方稳定，动画结束不等于内容可用，主线程仍有长任务时动画结束后照样掉帧；时长用设备实测决定，低端机、动画缩放关闭与"减少动态效果"的无障碍偏好下要有合理行为。迁移两个旧方案：Android 11 及更早放在启动主题 `windowBackground` 里的 layer-list，在 Android 12+ 冷/温启动会被系统 Splash 替换、外观不再等同，应把颜色与图标转成 `Theme.SplashScreen` 属性、设置 `postSplashScreenTheme` 并删除两套启动视觉；专用 SplashActivity 在 Android 12+ 会出现"系统 Splash + 自身页面"两段画面，还多一轮生命周期与跳转，路由应放进单 Activity 或直接启动目标 Activity（迁移期允许"保持 Splash、立即跳转并结束自己"，但路由必须同步、快速、无网络等待）。交接内容时优先显示有边界的本地缓存再异步刷新，骨架屏要贴近最终结构避免 layout shift；starting surface 首见时间、TTID、TTFD 是三个不同时点，Splash 显示得早不会自动缩短 TTID。

**Q24: Privacy Sandbox 的 SDK Runtime 现在还能用于新项目吗，Android 13 设备上是什么状态？**

不能。Google 已决定让 Topics、Protected Audience、Attribution Reporting 与 SDK Runtime 四项技术退场（材料口径：2025-10-17 公告，官方状态页列为 Deprecate and remove）；Android 17（API 37）的公开 API 文档把 `SdkSandboxManager`、`SandboxedSdkProvider`、`SandboxedSdk` 标记为 deprecated 并说明 SDK sandbox 不再受支持，Topics/Ad Selection/Measurement 各 manager 也已废弃或处于 soft removal（先废弃、随后分阶段拒绝调用）。版本边界：Android 13（API 33）引入 `SdkSandboxManager` 与状态查询、但平台 `loadSdk()` 尚未加入；Android 14–16 是平台 `loadSdk()` 的历史支持区间，设备状态与 Ad Services 扩展版本仍影响可用性；AndroidX `privacysandbox-sdkruntime` 预发布版已 deprecated 且停止更新。该模块源码不在 AAOS13 本地树（packages/modules 为空，本地核对），上述 API 状态按材料口径转写。判断规则：API 符号能编译不代表设备能力可用，`SDK_INT >= 34` 不能作为接入判断；遗留 Android 14–16 产品只做维护、检查能力并准备失败降级；Android 17 新项目按普通嵌入式 SDK 治理，旧的 `getTopics()`、`selectAds()`、`loadSdk()` 不进入新代码。

**Q25: SDK Runtime 退场后广告 SDK 的启动治理应该怎么做，"异步 init"返回后能假设什么？**

广告 SDK 回到宿主进程 AAR 形态后，治理从最终 merged manifest 入手：SDK 的 Provider/App Startup initializer 属于哪个进程、能否按供应方支持方式关闭自动初始化（Provider 在 `Application.onCreate()` 之前执行，进程分支和延迟开关来不及阻止它）、authority 是否冲突、升级后的 Manifest diff 是否新增组件。`Application.onCreate()` 只注册轻量网关并读取本地功能开关，不等待 SDK ready；页面并发 init 由网关状态机（Idle/Initializing/Ready/Failed）合并成一次会话任务，失败保存为调用方可读取的结果，重试按错误类型与退避间隔由网关控制，不能多个页面各自循环触发。阶段拆分：Provider 只留 SDK 强制且无法关闭的最小工作；首帧前只做"页面是否保留广告容器"的本地决策；初始化与首请求放到首帧后或临近广告入口，低端设备上"首帧后"仍可能与首屏动画争 CPU，要用实验确认首个广告可用率与启动体验的取舍。两个边界：SDK 文档说"异步初始化"也要在 trace 中验证——异步 API 可能在返回前同步执行类加载、读取 Preferences、创建线程，完成回调也可能回主线程；init 超时只是调用方停止等待，后台初始化未必取消，失败后的备用路径不能比正常路径更重（如回主线程同步初始化旧 SDK），否则少量错误样本会集中到 P99 与 ANR。首屏广告要产品先定默认行为：跳过、固定占位、短 deadline 或独立可取消加载页，并把广告等待计入 TTFD/业务 ready。

**Q26: 并发 GC 时代 GC 还会拖慢启动吗，`HeapTaskDaemon` 在 Perfetto 里 Running 就等于在 GC 吗？**

会，路径有三：并发收集器仍有需要挂起 mutator 的短暂停顿，落在主线程关键路径上直接增加 TTID/TTFD；分配失败或为完成分配而触发的 GC（`heap.cc` 用 `kGcCauseForAlloc` 标记，AAOS13 核对该常量存在）会让分配线程等待；`HeapTaskDaemon` 执行标记、扫描、复制时消耗 CPU、内存带宽与 cache，主线程即使没被挂起也可能 Runnable 变长。观测上不要把 `HeapTaskDaemon` 的 Running 时间都记为 GC——它还执行 collector transition（前后台回收策略切换）、heap trim（归还空闲页）与启动完成清理，这些 slice 不计入 GC 的 CPU 时间；正确顺序是先在 App 进程找到该线程，区分 concurrent/blocking GC、trim 与其他 heap task slice，再看主线程在同一窗口是 Running、Runnable 还是卡在 GC wait slice，最后对照 TTID/TTFD——首帧之后的 GC 不能解释 TTID 变慢，长时间 Runnable 更支持 CPU 竞争，明确的 GC wait slice 才证明线程在等回收完成。Logcat 的 ART GC 行默认只记录符合条件的显式或慢 GC，没有日志不等于没发生 GC。堆结构、GC 分类与 lmkd 机制见 [../memory/01-内存管理与压力治理.md](../05-memory/01-内存管理与压力治理.md)。

**Q27: 应用进程 fork 后 ART 对启动期堆做了什么，这等于"关闭了两秒 GC"吗？**

不等于。按 AAOS13 源码核对（`art/runtime/gc/heap.cc` 的 `Heap::PostForkChildAction()`，材料描述的 Android 17 行为在 13 已同构存在）：进程 fork 后若非低内存设备，先把 `target_footprint_` 抬到 `growth_limit_` 并重设并发 GC 启动阈值，减少启动期 GC；2 秒（`kPostForkMaxHeapDurationMS = 2000`）后若期间没有发生过 GC 且无 collector 在运行，把目标降到 `max(growth_limit/4, initial_heap_size)`；若该值仍高于初始堆，再过 8 秒（fork 后约 10 秒）降到 `initial_heap_size`。随后安排 `TriggerPostForkCCGcTask`：目标时间为最后一次调整后再加 8 秒，加上按 UID 生成的 0–19,999 ms 确定性抖动（进程间错峰），执行时若 GC 计数仍与 fork 后相同，才以 `kGcCauseBackground` 请求一次并发 GC 回收启动垃圾。两个关键边界：这期间 collector 并未关闭——启动分配触及阈值、显式 GC 请求、native allocation 压力或进程状态变化仍会触发回收，放宽的只是堆目标；该策略只对新 fork 进程，温/热启动复用进程不会重新执行，多进程应用的每个新进程有独立的堆与 post-fork 状态。启动完成清理在 AAOS13 由 `Runtime::NotifyStartupCompletedTask`（`VMRuntime.notifyStartupCompleted` 触发）负责释放 app image 元数据，Android 17 对应类名为 `StartupCompletedTask`——都是 runtime 自身触发，不是第三方应用的 GC 开关。

**Q28: 哪些"GC 抑制"手段不可用于生产应用，启动期分配治理的正确顺序是什么？**

三类方案不可用：hook `libart.so`（替换 `ConcurrentGCTask` 的 vtable 条目或 inline hook）直接改系统运行时内部 ABI，受只读映射、RELRO、CFI 等加固保护，ART 可经 Mainline 独立更新，在 `Run()` 中 sleep 还会连 trim、transition 一起延迟，失败后果是随机崩溃、堆破坏或 OOM；反射调用 `VMRuntime` 的 `requestConcurrentGC()`、`setTargetHeapUtilization()`、`notifyStartupCompleted()`——它们是 hidden 或 module-only API 且受 non-SDK 接口限制，而 `registerSensitiveThread()` 只是给线程设 JIT sensitive 标记（AAOS13 核对：`handleBindApplication()` 第一行即为 UI 线程调用它），没有"优先分配"或"减少 GC"的语义；无证据地在首帧后主动 `System.gc()`——显式请求可能引入暂停与带宽竞争，只有 trace 与对照实验证明无交互窗口的请求能改善后续关键路径才可评估。正确顺序：先用 Perfetto 证明 GC 与启动关键路径重叠并确认 cause 与 collector；再用 Allocation Recording（要求 debuggable 构建，采集期间耗时不作基准）按分配字节与次数定位调用栈，区分短命对象、存活对象（live set）与大对象；然后治理——把与首帧无关的对象图延后并错峰、降低瞬时分配率（重复解析、大集合 map/filter 链、字符串与日志、未预估容量扩容）、给启动期缓存设容量与逐出边界。边界：把工作移到后台线程不降低 GC 压力，进程内 heap 由线程共享；对象池只适合已测出高频构造且重置可控的对象，随意池化反而扩大 live set。

**Q29: `@HiltAndroidApp` 的 component 什么时候创建，ContentProvider 与 ViewModel 场景的注入时机差在哪？**

`@HiltAndroidApp` 生成的应用基类在 `onCreate()` 中先执行 `hiltInternalInject()`（创建 `SingletonComponent` 并给 Application 做成员注入），用户 Application 覆盖 `onCreate()` 时必须先调用 `super.onCreate()`，注入字段只能在 `super` 返回后使用；`SingletonComponent` 按第一次访问创建（生成代码用 volatile 双检锁），标准 Hilt 应用的这次访问就发生在 `super.onCreate()` 的注入阶段。component 构造只建立 provider、module 与 scope 关系，不把图中所有业务对象创建一遍。两个入口的时机差：Android `ContentProvider` 安装在 `Application.onCreate()` 之前（AAOS13 核对），Hilt 不支持给 `ContentProvider` 加 `@AndroidEntryPoint`，若必须访问 binding 要声明显式 `@EntryPoint`——它只解决访问方式，且会把 component 创建提前到 Provider 阶段，所以非必要 Provider 应移除或延迟，必须保留的只读轻量 binding；`@HiltViewModel` 不会随进程无条件创建，首次 `ViewModelProvider`/`hiltViewModel()` 请求时才建立 `ViewModelComponent` 并解析构造参数，它是否属于启动成本取决于首屏何时请求——把重工作从 Activity 字段移进 ViewModel 构造函数只是换位置。Hilt Gradle 插件默认启用 `fastInit`（减少 component 初始化需加载的类），但不会让重对象自动延迟。

**Q30: `@Singleton`、直接注入、`Lazy<T>`、`Provider<T>` 的构造时机差在哪，"图里有 2000 个 binding"等于启动创建了 2000 个对象吗？**

不等。`@Singleton` 只规定同一 `SingletonComponent` 内共享一个实例（Dagger 用 `DoubleCheck` 包装：第一次 `get()` 计算并缓存），component 创建时没被请求就不会提前构造——它不是 eager。时机差异：`@Inject lateinit var` 与构造参数注入在宿主被注入/构造时就拉起递归依赖，`@Inject lateinit var` 不具备"第一次业务使用时再注入"的语义；`dagger.Lazy<T>` 第一次 `get()` 时创建并由该 wrapper 缓存（分别注入的两个 `Lazy` 各自独立）；`Provider<T>` 每次 `get()` 请求（unscoped binding 每次新建，scoped 返回缓存）。因此判断启动成本要看 Application 直接注入字段、Provider 阶段访问的 binding、首屏 ViewModel 及其递归依赖，而不是图的总大小。边界：若启动路径仍在首帧前调用 `Lazy.get()`，延迟形同虚设；`@Provides` 方法体是重活常见藏身处（网络栈构建、证书读取、数据库打开、native 库加载、线程池创建），适合 `@Binds` 的接口映射不要写成 `@Provides`；`@Reusable` 允许复用但不保证对象身份相同。

**Q31: Koin 的启动成本分哪两段，`createdAtStart`、`lazyModules` 与 KSP 迁移各要注意什么？**

Koin 经典 DSL 的启动成本分两段：`startKoin { modules(...) }` 创建 `KoinApplication`、注册 `GlobalContext` 并载入 module definitions（运行时注册表，按类型/qualifier/scope 查找，不是每次都走 Java 反射）；第一次 `get()` 解析 definition 并执行构造 lambda，是否缓存由 `single`/`factory`/scope 决定。要点：`createdAtStart = true` 标记 eager singleton，标准 `startKoin` 在注册完后自动 `createEagerInstances()` 统一创建——优化先删没有业务必要的 `createdAtStart`；`lazyModules()` 用协程后台载入 module（Koin 4.2 起多个 module 各用一个协程并行，默认 `Dispatchers.Default`），`waitAllStartJobs()` 会阻塞等待、主线程调用会把成本放回启动路径（应使用挂起的 `awaitAllStartJobs()`），且同步 module 依赖尚未载入的 lazy module 时 Koin 目前不自动校验，只适合延迟依赖边界清晰、首屏不访问的 feature；release 不要显式启用 DEBUG/INFO 级 `AndroidLogger`（默认 `EmptyLogger`）。KSP/kapt 属于构建期优化：KSP 直接分析 Kotlin symbol，收益体现在 clean/incremental 构建时间（官方口径"最高约两倍"描述 symbol processing），在 DI 图、编译选项与发布产物等价前不能换算成冷启动收益；每个 module 移除全部 kapt processor 后再比较构建时间，并用 release Macrobenchmark 验收。框架名称不决定结果：小型手写 `ServiceLocator` 也可能在静态初始化中 eager 创建全部服务。

**Q32: Compose 的 `setContent` 到首帧经过哪些阶段，初始组合会执行哪些 composable？**

`ComponentActivity.setContent` 创建 `ComposeView` 作为公开宿主（内部组合创建时才创建/复用 `AndroidComposeView`），View 尚未 attach 时只保存 content，初始组合在 attach 或显式 `createComposition()` 时创建；窗口级 `Recomposer` 受 Lifecycle 驱动（STARTED 后 frame clock 提供帧、`ON_STOP` 暂停、`ON_DESTROY` 取消）。初始组合执行"本轮会进入"的内容：没有上一轮结果可复用，进入的 group 都要执行，已进入 group 里的 `remember { ... }` calculation 也执行一次；条件分支未选中的内容不执行；Lazy layout 尚未被请求的 item 不会因为数据集合存在就全部执行——所以首帧成本没有"层数 × 数量"公式，它等于被进入的 composable 工作量、创建的布局/modifier/semantics 节点、业务计算，再加上应用变更、测量、布局与绘制的总和。组合完成后 `AndroidComposeView` 仍是 `ViewRootImpl` 管理的 View 子树，还要经过 `onMeasure`/`onLayout`/draw、HWUI 与 RenderThread、SurfaceFlinger 合成才上屏——组合只是首帧中的一段，trace 显示组合很短而 I/O、文本测量或渲染很长时，删 composable 层级不解决问题。首屏 ready 用 `ReportDrawnWhen` 注册到 `FullyDrawnReporter`，合法空态也要能进入 Ready，否则 TTFD 永久缺失。

**Q33: Compose 自带的 Baseline Profile 覆盖什么，为什么 `Class.forName()` 预热不是替代品？**

Compose 随应用发布、不在 platform boot image 中，其发布物附带的 Baseline Profile 只覆盖 Compose 库代码，应用合并这些 library profile 后 ART 可提前编译库的规则路径，但不会自动覆盖应用自己的 composable、ViewModel、导航与数据准备路径；`androidx.compose:compose-bom` 只是版本清单，不含实现代码也不是 profile 载体。所以应用仍要用 `BaselineProfileRule` 采集桌面启动、通知、deep link 等主要入口并让测试走到首屏可交互，Startup Profile 反映相同入口且只能由应用自己的启动测试贡献（库不能替宿主贡献；构建期 DEX 布局的 AGP 版本要求见 Q20）。`Class.forName()` 预热 Compose 类是反模式：它把类加载移到更早的主线程路径、扩大每次启动的必做集合，既不能替代 AOT 编译，也不能保证启动代码在 DEX 中相邻存放。Profile 只改变编译状态与布局，数据库查询、网络等待与图片解码照旧存在；收益必须用目标产物与设备测量，不要写"提升 10%～30%"这类固定承诺。

**Q34: `Column`、Lazy layout 与 `SubcomposeLayout` 怎么选，什么模式会让"首帧后立刻再来一帧"？**

选择依据内容规模：固定且数量少的内容用 `Column`/`Row`；数量大或未知时用 Lazy layout，避免一次组合并布局所有 item。Lazy 首屏注意：item 在异步内容到达前不要是 0 像素，否则一次 measure 会误判 viewport 能容纳大量 item、造成无效组合；为可重排数据提供稳定 `key`；异构列表提供合适 `contentType` 帮助复用组合结果；不要把大量元素塞进同一个 `item { ... }`（它们仍会作为一个单元一起组合和测量）；小型固定按钮组不应只为"懒加载"换成 `LazyRow`。`SubcomposeLayout` 只用于子内容依赖父布局约束的场景（`LazyColumn`、`BoxWithConstraints` 是官方例举），普通 `Box` 即使用 `Modifier.align` 走的仍是常规 `Layout`；默认选它会把一部分组合移进布局阶段，常增加当前帧总成本。"首帧后立刻再来一帧"来自阶段反馈：`onSizeChanged()`/`onGloballyPositioned()` 得到尺寸写入 `MutableState`，又在同一布局关系中把它读成 `padding`、`height` 或子节点位置——能在同一次测量中求解的父子关系应使用现有布局组件或自定义 `Layout`，自适应页面从当前 constraints 派生结构。边界：重组优化（稳定类型、Strong Skipping、延后状态读取）主要减少后续重复工作，不能免除首屏第一次必须进入的内容；`remember` 只缓存后续复用，它的 calculation 在初始组合中仍要执行。
