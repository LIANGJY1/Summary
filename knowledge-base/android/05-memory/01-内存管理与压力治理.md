# Android 内存管理与压力治理

> 学习资料（文章模式沉淀）。主线：进程内存口径与内核页管理、ART 堆与 GC 调度、lmkd/缓存进程冻结器/MemoryLimiter 的压力治理分层、App 内存优化诊断、16 KB Page Size 的兼容与性能。源文档：android-internals-wiki §4.1《Android 与 Linux 内存管理全景》、§4.2《ART Heap、GC 与后台维护调度》、§4.3《lmkd、Cached App Freezer 与内存压力治理》、§4.4《App 内存优化与诊断》、§4.5《16 KB Page Size 与 Android 性能》；机制按本地 AAOS13 源码（Android 13）核对，与材料 Android 17 语境的差异（如 MemoryLimiter/PMGD、分代 CMC、整理级别收窄）已标注；16 KB Page Size 的 Play 要求已与官方文档核对。ART 的角色与演进总览见 [../architecture/05-Art.md](../01-architecture/05-Art.md)；输入延迟与内存压力的关联见 [../input/01-输入系统.md](../03-input/01-输入系统.md)。Q 序列即结构，供 atlas 同源直读。

**Q1: Android 进程的"内存"由哪些域组成？为什么"Java 堆没满，所以不会 OOM"不成立？**

同一进程的内存至少包括：ART 托管堆（Java/Kotlin 对象）、原生堆（`malloc/new`、JNI）、匿名映射（`mmap`、线程栈、JIT 区域）、文件映射与页缓存（dex/oat/so、资源）、图形与共享缓冲区（Gralloc、DMA-BUF、`AHardwareBuffer`）、内核内存（slab、页表、驱动）以及 zram 压缩交换空间。最终都以内核的页、匿名内存、文件页和 swap 形式存在。

"Java 堆没满"不成立的原因：进程还包括原生内存、线程栈、代码映射、图形内存与共享内存，任何一处失败都会表现为分配失败或被系统回收；ART 自身也可能因连续空间不足、堆增长策略或分配请求无法满足抛出 `OutOfMemoryError`。Java 堆转储（HPROF）看不到原生内存、图形内存、页缓存和内核分配，只抓 HPROF 会漏掉大半现场。

`ActivityManager.getMemoryClass()` 返回的是按 `dalvik.vm.heapgrowthlimit` 给出的托管堆近似容量（MiB），`largeHeap` 对应的也是设备配置的堆等级——它们都不是进程总内存上限，不覆盖原生、图形与共享内存。

**Q2: VSS/RSS/PSS/USS 各回答什么问题？为什么"PSS 连续上升"不等于泄漏？**

四个口径回答不同问题：

1. **VSS**：进程虚拟地址空间中所有映射的总大小，看地址空间是否异常、是否存在超大预留；大量页面可能从未驻留，不能当作物理占用；
2. **RSS**：当前驻留 RAM 的页面总量，看进程此刻的驻留规模；共享页在每个映射进程中重复计数，多进程相加会重复；
3. **PSS**：驻留共享页按映射者数量分摊后求和，用于多进程间较公平的内存归因；
4. **USS/Private**：只归入该进程的私有页面（约等于 `Private_Clean + Private_Dirty`）。

同一时刻同一进程通常满足 `VSS ≥ RSS ≥ PSS ≥ USS`，但工具是否计入 `SwapPss`、设备与 memtrack 实现会改变展示口径，不能替代字段定义。

PSS 上升不等于泄漏：共享映射者退出会让剩余进程的 PSS 上升而对象没变；预热、JIT、图片缓存、页面回收与交换活动也会改变 PSS。判断泄漏应在可重复的业务阶段采样，同时观察 RSS、PSS、私有脏页、`SwapPss` 的趋势与具体组成（Java 对象、原生分配、DMA-BUF），并结合共享进程的启动退出时间点；"PSS 连续上升"只是继续调查的信号。USS 也不能精确预测进程退出后 `MemAvailable` 的增量——共享页会重新分摊，私有脏页需要回收，fd 关联的内核对象各有生命周期。

**Q3: `MemFree` 很小说明系统异常吗？判断压力应看哪些指标？**

`MemFree` 小通常正常：Linux 会利用空闲页做文件页缓存，干净页随时可回收。判断系统余量应看 `MemAvailable`（估算在不发生交换的前提下可供新应用使用的内存）；判断压力是否已经影响任务运行，还要看内存 PSI（pressure stall information）——`/proc/pressure/memory` 中 `some` 表示至少有一个任务因等待内存停顿，`full` 表示所有非空闲任务同时停顿。短时尖峰与持续高压含义不同，应把 PSI 与 `vmstat`、页面回收、业务卡顿和进程退出记录放在同一时间线。

zram 相关指标要分开读：`SwapTotal` 是配置容量、`SwapFree` 是未使用容量、`SwapCached` 是已换回但仍在交换空间保留副本的页面，三者不能相加当 zram 占用；评估 zram 应看 `/sys/block/zram0/mm_stat` 的 `orig_data_size`（未压缩数据）、`compr_data_size`（压缩数据）与 `mem_used_total`（含碎片和元数据的实际 RAM 成本）。zram 使用高只说明匿名页进入了压缩交换，是否陷入抖动要看 PSI、换入换出与压缩 CPU 开销，`SwapTotal - SwapFree` 给不出这些结论。

**Q4: 内存分配为什么会进入内核慢路径？判断"直接回收拖慢了线程"的证据如何取？**

大多数 `malloc`、文件映射访问走快速路径；空闲页不足、目标内存区域（zone）不满足水位、需要高阶连续页或页面已换出时进入慢路径，可能包含缺页处理、页面回收、swap I/O 与内存规整（compaction）。zone 水位的语义是：空闲页低于 low 唤醒 `kswapd` 后台回收，低于 min 时允许阻塞的分配可能进入直接回收（direct reclaim）——但"低于 min 一定直接回收"过于绝对，GFP 标志、order、memcg 限制都会改变分支。

直接回收在发起分配的应用线程上下文中执行，会直接延长该线程。可靠证据不是线程处于 D 状态（不可中断睡眠来源很多），而是：

1. ftrace 跟踪点：`vmscan/mm_vmscan_direct_reclaim_begin/end`、`mm_vmscan_kswapd_wake/sleep`、`compaction/mm_compaction_*`；
2. `/proc/vmstat` 的 `pgscan_*`、`pgsteal_*`、`allocstall_*`、`pswpin/pswpout` 前后做差；
3. 内存 PSI 的持续停顿与内核调用栈。

内存规整（迁移可移动页形成连续空闲块）与数据压缩不同，zram 才涉及压缩；两者可能出现在同一时间窗但不能用同一套"碎片率"衡量。

**Q5: DMA-BUF 的内存占用如何核算？ION 与 DMA-BUF Heaps 的版本边界是什么？**

DMA-BUF 是跨设备、跨驱动、跨进程共享缓冲区的框架：导出方驱动创建 `dma_buf`，其他驱动以附件方式导入，用户空间只持有一个 fd。同一缓冲区可被应用、SurfaceFlinger、GPU 和 HWC 同时引用，把完整大小计入每个持有者会重复计算；只看进程 `smaps` 也会漏掉未映射到该进程但由 fd 或驱动持有的缓冲区。Linux 内核在 `CONFIG_DMABUF_SYSFS_STATS` 开启时提供 `/sys/kernel/dmabuf/buffers/<inode>/size` 等统计；Perfetto `linux.process_stats` 的 `record_process_dmabuf_rss` 读到的仍是"引用规模"，不能当作该进程独占的物理内存。

版本边界：Android 12 的 GKI 2.0 起 DMA-BUF Heaps 替换 ION，`/dev/dma_heap/<heap_name>`（如 `system`、`default_cma_region`）成为新设备的分配接口；升级设备仍可能经 `libdmabufheap` 兼容映射访问旧 ION。"每个 DMA-BUF 都是物理连续内存"不成立——system heap 虚拟连续，CMA heap 才物理连续，有 IOMMU 的设备通常能让硬件访问离散页。

**Q6: MemoryLimiter 与 PMGD 是什么机制？在 Android 13 设备上存在吗？**

两者都是材料按 Android 17 核对的新机制，AAOS13（Android 13）源码中不存在（`services/core/java/com/android/server/am/` 下无对应文件）：

- **MemoryLimiter**：`system_server` 内按进程状态映射配额、通过 JNI 写入进程 cgroup v2 的 `memory.high` 与 `memory.swap.max`，监听 `memory.events` 的 `high` 计数进入红区轮询，联合指标 `anon + shmem + swap` 越界后解除限制、可选采集 30 秒剖析再终止进程；应用侧识别方式是 `ApplicationExitInfo` 的 `REASON_OTHER` 加 description 含 `MemoryLimiter:AnonSwap`。只在部分设备启用（vendor 配置 `memory-limiter-config.xml` 匹配 `MemTotal` 才生效）。
- **PMGD（Process Memory Guardian Daemon）**：由 `/vendor/etc/pmgd/config.json` 点名目标进程（可以是 `system_server`），设置 `memory.high` 与 `anon_limit_in_mb` 硬边界，用 inotify 监听 `memory.events` 决定终止。

因此"Android 17 应用都有固定内存上限"不是通用结论，阈值以目标设备镜像与 `am memory-limiter status` 为准；在 Android 13 设备上排查进程消失时不存在这条路径。

**Q7: ART 堆由哪些 space 组成？Android 13 与 Android 17 的主移动空间实现有何差异？**

ART `Heap` 管理五类空间，差别在"对象从哪来、GC 能否回收、能否移动"：

1. **Boot Image Space**：启动镜像中预生成的类与对象，GC 免疫、不可移动，跨进程共享；
2. **Zygote Space**：Zygote fork 前保留的对象，应用进程中不回收不移动，写入触发 COW；
3. **主移动空间**：应用大多数普通对象，可回收可移动；
4. **Non-moving Space**：`Class`、`ArtMethod` 等要求地址稳定的对象（Android 17 用 `DlMallocSpace`，默认容量 64 MiB）；
5. **Large Object Space**：达到阈值的基本类型数组或 `String`，不可移动，实现为 `FreeListSpace` 或 `LargeObjectMapSpace`。

主移动空间的实现随收集器而定：并发复制收集器 CC 用 `RegionSpace`（region 固定 256 KiB），并发标记规整 CMC 用连续的 `BumpPointerSpace`。版本边界：按 AAOS13 源码核对（`art/runtime/gc/collector/` 无 `mark_compact.cc`），Android 13 只有 CC 路径，默认启用并支持分代 CC；CMC 是 Android 17 的收集器（官方发布说明称分代 CMC 自 Android 16 QPR2 引入），能否启用取决于 userfaultfd 等内核能力与运行时配置，不能按 Android 版本号推断某台设备在用哪条路径。

**Q8: 小对象分配的快路径与慢路径分别是什么？"TLAB 用尽就去拿堆全局锁"准确吗？**

快路径是线程局部分配缓冲区（TLAB）内的递增指针分配：线程在自己的缓冲区内推进指针，主要工作近似"记录位置、对齐大小"，无需任何锁。按 AAOS13 源码核对（`art/runtime/gc/heap.h`、`region_space.h`），三个常量分属不同层次：默认 TLAB 32 KiB、部分 TLAB（partial TLAB）参考值 16 KiB、RegionSpace 单个 region 256 KiB——region 可承载 TLAB，三者不是同一概念。

TLAB 用尽的补充路径有多个分支：尾部仍有空间可先扩展；`RegionSpace::AllocNewTlab()` 持 region 锁后先尝试复用足够大的部分 TLAB，再寻找或建立 region——不是笼统的"拿堆全局锁并 mmap"。另外 TLAB 不是所有收集器的唯一快路径，Mark-Sweep/CMS 系列可用 RosAlloc 按尺寸档位使用线程本地 run，只有共享 run 才需要档位锁。

慢路径由 `Heap::AllocateInternalWithGc()` 接管：先等待正在运行的 GC 完成（等待本身可能构成明显卡顿），重试失败后按 `next_gc_type_` 执行阻塞式 GC，再失败做全堆回收并清除软引用，仍失败才抛 `OutOfMemoryError`。分配线程等待整轮 GC 的时间可能远大于单次 GC 暂停，只看暂停直方图解释不了主线程的长空档。

**Q9: 进入大对象空间（LOS）的条件是什么？"12 KiB 阈值"怎么理解？**

大小只是第一个条件。`Heap::ShouldAllocLargeObject()` 要求对象同时满足 `byte_count >= large_object_threshold_` 且类型是基本类型数组（primitive array）或 `String`；普通对象数组、业务实体不会仅因"大"就进 LOS。图片像素也可能在原生内存或 GPU 内存，看到 Bitmap 应先确认像素存储位置。

阈值本身有版本差异：按 AAOS13 源码核对（`art/runtime/gc/heap.h`），Android 13 的定义是 `kMinLargeObjectThreshold = 3 * kPageSize`，在 4 KiB 页设备上等于 12 KiB；材料按 Android 17 核对该值已固定为 12 KiB、不随 16 KiB 基础页放大。分析具体设备时回到对应源码标签的 `heap.h`。

LOS 有两个排查要点：其一，`AllocObjectWithAllocator()` 在 LOS 分配失败后会清除本轮 LOS OOM 异常再尝试普通空间，所以不能只凭对象大小和最后一条 OOM 日志断定失败发生在 LOS；其二，频繁创建大 `byte[]`、`char[]`/`String` 会增加 LOS 分配、扫描和页面映射压力，但每次 LOS 分配是否触发阻塞 GC 取决于当时的堆空间，不能描述为同步 GC。

**Q10: 一次 GC 有哪三种分类？`System.gc()` 是"强制全堆 GC"吗？**

三种分类维度不同，混用会造成误判：

1. **收集器（collector）**：用哪套算法，如 CC（并发复制）、CMC（并发标记规整，Android 17）、CMS（并发标记清除）；
2. **GC 类型（GcType）**：收集多大范围，`Sticky`/`Partial`/`Full`；分代收集器中 sticky 对应年轻代回收；
3. **GC 原因（GcCause）**：为什么触发，如 `Alloc`（分配失败）、`Background`（提前异步回收）、`Explicit`（显式请求）、`NativeAlloc`（ART 登记的原生内存超水位）、`CollectorTransition`、`HeapTrim`。

`NativeAlloc` 说明"可随 Java 对象释放的原生内存"会计入 GC 触发：`RegisterNativeAllocation()` 独立记账，ART 将 Java 堆与登记的原生压力加权比较；但 GPU 缓冲区、驱动映射、第三方库分配不在其中，仍需 `heapprofd`、memtrack 等工具。

`System.gc()` 不是强制全堆 GC：它发出 `Explicit` 原因的请求，具体范围由当前收集器与 GC 方案决定，运行时还支持 `-XX:+DisableExplicitGC`。显式 GC 无法回收仍可达的对象、不能修复引用与生命周期，业务代码通常没有信息替 ART 决定回收时机。

**Q11: 分代回收如何工作？Android 13 与 Android 17 的分代实现有何不同？**

分代回收的核心是：多数临时对象很快死亡，让常见回收优先处理较新对象，并用写屏障记录老对象可能指向新对象的区域，缩小单轮扫描范围。

按 AAOS13 源码核对（`art/runtime/gc/heap.h` 的 `use_generational_cc_`），Android 13 的分代实现是**分代 CC**：年轻代 CC 优先回收新分配对象，ART 比较最近年轻代回收与更大范围回收的估算吞吐，决定下一次继续年轻代还是扩大范围——没有固定的"每 N 次 young 执行一次 full"。跨代引用靠写屏障与卡表：引用字段写入时 `MarkCard()` 标记的是持有者对象所在的卡表项（一项覆盖 1024 字节地址范围），不是新值对象；脏卡只表示该范围发生过引用写入，是保守候选，GC 仍需扫描对象字段确认。

Android 17 的分代实现演进为**分代 CMC**：在 `BumpPointerSpace` 中维护 young/mid/old 三个逻辑代际边界，年轻代回收同时处理 young 与 mid，对象需连续存活两轮 GC 才晋升 old（`YoungMarkCompact` 只是主收集器进入年轻代模式的轻量包装）。这是 Android 16 QPR2 起发布、材料按 Android 17 核对的边界，Android 13 不存在该路径。

**Q12: Perfetto 里 GC 时间片与掉帧帧重叠，能判定 GC 导致掉帧吗？**

不能直接判定，重叠只是调查入口。并发 GC 的大部分工作可与应用线程同时运行，掉帧可能来自暂停、等待 GC、CPU 抢占、内存带宽竞争，也可能只是时间重合。需要分开四类时间：mutator pause（应用线程被暂停多久）、GC 墙钟时长、GC 实际运行时长、GC 可运行等待时长——墙钟长不代表全程暂停；运行时间高说明 GC 耗 CPU，可运行等待高说明 GC 线程自己也受调度竞争影响。

Perfetto 上可区分两类事件：GC 运行的时间片名形如 `"<cause> <collector> GC"`（如 `Background concurrent copying GC`）；等待 GC 的时间片是 `GC: Wait For Completion <cause>`，后者表示当前线程正在等另一次 GC 完成，是解释分配卡顿的更直接证据。可用 Perfetto 标准库 `android.garbage_collection` 汇总次数与时长，再与 `actual_frame_timeline_slice` 的 jank 帧做时间交集查询。

阈值判断必须带设备与负载条件：120 Hz 帧预算约 8.33 ms，但一段 2 ms 暂停是否造成掉帧取决于它落在帧的哪个位置及同帧其他工作。固定"3 ms 黄金线""暂停超过 5 ms 异常"缺少跨设备依据，回归判断用同一场景前后差异。

**Q13: `HeapTaskDaemon` 是什么？进程被冻结期间，ART 的维护任务会怎样？**

`HeapTaskDaemon` 是 libcore `Daemons` 创建的 Java 守护线程，它调用 `VMRuntime` 的隐藏接口进入原生层 `TaskProcessor` 主循环。`TaskProcessor` 用按目标时间排序的 `std::multiset` 维护 `HeapTask` 队列（按 AAOS13 源码核对，`art/runtime/gc/task_processor.cc` 存在），到期任务串行执行、用后自毁。GC 请求、堆裁剪、启动期清理、方法追踪停止都走这套机制；任务到期只表示获得执行机会，是否真的执行 GC 还取决于各任务自己的守卫条件（如 GC 序号、待处理指针）。

关键常量：GC 完成后 `RequestTrim()` 安排 `HeapTrimTask`，按 AAOS13 源码核对延时为 `kHeapTrimWait = 5000 ms`；重复 trim 请求直接忽略。ART 的 Heap Trim 负责把分配器可归还页面、JNI 引用表、arena 映射交还内核，它不是"完整 GC 加堆规整"。

冻结期间 `HeapTaskDaemon` 拿不到 CPU，但墙钟继续前进，队列里任务的目标时间可能已过去；解冻后多个逾期任务被同一线程串行取出执行，是否触发 GC 仍由各自守卫条件决定。所以看到解冻后连续的 ART 工作，应逐项核对任务条件，不能直接归因于"冻结期间积累了多轮 GC"——积累的是已到期的队列项，不是已执行的回收。这套队列是 ART 内部设施，应用没有受支持的 API 去启动、停止或改写它。

**Q14: `onTrimMemory()` 会触发 GC 或内核回收吗？Android 13 与 Android 14+ 的回调级别有什么差异？**

`onTrimMemory()` 只是系统发给应用的异步状态信号：它不调用 `VMRuntime`、不触发 ART GC、堆规整、内核直接回收或 `kswapd`。应用断开强引用后对象只是变为可回收，GC 时机仍由 ART 按分配压力与堆目标决定；GC 完成后的 `HeapTrimTask` 归页是另一条异步链。分发路径上，回调经 oneway Binder 到达应用，`ActivityThread.scheduleTrimMemory()` 优先投递到主线程 `Choreographer.CALLBACK_COMMIT` 阶段（按 AAOS13 源码核对，`ActivityThread.java` 中 `choreographer.postCallback(Choreographer.CALLBACK_COMMIT, r, null)`），以降低打断当前帧的概率，但回调仍在主线程执行，应只做快速、可重建的资源缩减。

级别有明确版本边界：

1. **Android 13**：仍发送完整档位。按 AAOS13 源码核对，`ComponentCallbacks2` 的 5/10/15/20/40/60/80 七个级别都未弃用，`AppProfiler` 仍按 COMPLETE→MODERATE→BACKGROUND 阶梯向缓存进程发送；
2. **API 34+（材料按 Android 17 核对）**：常规只投递 `TRIM_MEMORY_UI_HIDDEN(20)`（由 `AppProfiler` 按进程状态与 `pendingUiClean` 发送）与 `TRIM_MEMORY_BACKGROUND(40)`（由 `CachedAppOptimizer` 在安排冻结前发送），旧五个级别不再送达并标记 `@Deprecated`。

`UI_HIDDEN` 不等于内存压力，只说明 UI 不可见；`BACKGROUND` 也不预告进程死亡——lmkd 与 MemoryLimiter 都不发整理回调，系统可以直接终止缓存进程，关键状态必须按正常生命周期持久化。比较级别时用 `>=` 以兼容未来插入的中间值。

**Q15: lmkd 与内核 OOM Killer 的分工是什么？lmkd 如何拿到进程优先级？**

内核 OOM Killer 在内存分配已难以继续时才由内核选择目标；lmkd（low memory killer daemon）是用户空间守护进程，监控 PSI 等压力信号，可以在内核 OOM 之前、结合应用重要性更早地终止对用户影响较小的进程。两者工作在同一压力环境中但没有严格先后顺序。

进程优先级的数据流是：OomAdjuster 根据组件状态与依赖关系计算每个进程的 `oom_score_adj` → `ProcessList` 经本地 `SOCK_SEQPACKET` 控制套接字把 PID、UID、adj 发给 lmkd（`LMK_PROCPRIO` 单发、`LMK_PROCS_PRIO` 每包最多 3 条批量、`LMK_TARGET` 下发最多 6 组 minfree/adj）→ lmkd 把 adj 写入 `/proc/<pid>/oom_score_adj` 并维护自己的候选链表。按 AAOS13 源码核对，6 档 `mOomAdj` 为 `FOREGROUND(0)/VISIBLE(100)/PERCEPTIBLE(200)/PERCEPTIBLE_LOW(250)/CACHED_MIN(900)/LMK_FIRST(950)`，配合低/高档 minfree 基线（12288–49152 KB 与 73728–184320 KB）。

手工写 `/proc/<pid>/oom_score_adj` 只改内核值，未必同步 lmkd 候选链表，AMS 下一轮调整还会覆盖。

**Q16: `oom_score_adj` 的主要档位有哪些？为什么"进程有 Service 就不会被杀"不可靠？**

取值范围 -1000 到 1000，数值越大越容易成为终止候选。按 AAOS13 源码核对（`ProcessList.java`），主要档位为：`SYSTEM_ADJ(-900)`、`PERSISTENT_PROC_ADJ(-800)`、`FOREGROUND_APP_ADJ(0)`、`VISIBLE_APP_ADJ(100)`、`PERCEPTIBLE_APP_ADJ(200)`、`SERVICE_ADJ(500)`、`HOME_APP_ADJ(600)`、`PREVIOUS_APP_ADJ(700)`、`SERVICE_B_ADJ(800)`、缓存进程 `900–999`（其中 950 为 LMK 优先边界）。

"有 Service 就不会被杀"不可靠，因为 adj 不是组件枚举而是 OomAdjuster 对整张依赖图计算的结果：前台客户端绑定后台服务可提高服务端保护，前台进程使用的 ContentProvider 所在进程也会受益，前台服务类型、最近顶层状态宽限、可见 Activity 层次都影响结果；缓存进程与前一个应用在特性开关下还有更细的阶梯值。排查时要读取目标时刻的实际 adj，不能从"它有一个 Service"反推。

`UNKNOWN_ADJ(1001)` 是框架内部未决值，超出可写入内核的范围。lmkd 普通低水位分支的默认门槛是 `PREVIOUS_APP_ADJ + 1`（701）且被限制不低于 201，但发生严重停顿时门槛可降到 0，前台层进程也会进入候选。

**Q17: lmkd 的 PSI 新策略默认阈值是什么？PSI 唤醒后还会检查什么？**

PSI 触发器形式是"某时间窗口内累计停顿多久"。按 AAOS13 源码核对（`system/memory/lmkd/lmkd.cpp`），静态初始化三档为 `some 70 ms / some 100 ms / full 70 ms`；运行时新策略会覆盖：LOW 档设 0 不注册，MEDIUM 取 `ro.lmk.psi_partial_stall_ms`（默认定义 `DEF_PARTIAL_STALL = 70`，低内存设备 200 ms），CRITICAL 取 `ro.lmk.psi_complete_stall_ms`（`DEF_COMPLETE_STALL = 700`），默认窗口 1000 ms。`use_new_strategy` 的默认条件是 `low_ram_device || !use_minfree_levels`（本地源码与材料一致）。因此只摘录静态数组会得到错误的运行时阈值，要追到 `init_psi_monitors()`。

PSI 触发只负责唤醒 lmkd，之后还要读取并比较：`/proc/vmstat` 的工作集 refault、直接回收与 `kswapd` 统计（启动完成后还会尝试注册 BPF 内存事件获得更及时的状态）；`/proc/meminfo` 的空闲页、文件页、swap；按 zoneinfo 计算的水位；文件页 refault 相对页缓存的增长率（缓存抖动 thrashing）；上一个终止动作是否结束、水位是否恢复。终止原因按固定顺序检查（厂商事件、终止后仍低水位、严重 PSI、swap 不足、缓存抖动、直接回收、普通低水位），前序命中后后续条件不会覆盖。

lmkd 通过 `libpsi` 打开全局 `/proc/pressure/memory`，不遍历每个应用的 `memory.pressure`，不能推断"按哪个应用控制组 PSI 最高选目标"。

**Q18: lmkd 选定候选后如何终止进程？有哪些保护与加速机制？**

`find_and_kill_process()` 从 `oom_score_adj = 1000` 逐档向门槛递减：默认取该档链表尾部（保护程度最低的方向）；`ro.lmk.kill_heaviest_task=true` 时选该档内存占用最多者；门槛降到 `PERCEPTIBLE_APP_ADJ` 或更低时强制选最重目标，尽量减少被终止的高价值进程数量。一次调用只处理一个目标，但一个压力周期可继续多轮。

终止前的保护：再读 `/proc/<pid>/status` 确认进程仍存在、校验 TGID 降低 PID 复用误杀风险、读取 RSS/匿名页/swap 与可用 DMA-BUF 占用、调用厂商释放内存钩子（足够则跳过终止）。终止与回收由 Reaper 异步执行：优先写 cgroup 终止接口，否则 `pidfd_send_signal(SIGKILL)`；随后 Reaper 线程调用 `process_mrelease()` 促使内核在退出清理完成前提前回收匿名页与页表，并把自身放入前台 cpuset、提高优先级。

按 AAOS13 源码核对，lmkd 为事件处理设 2 秒看门狗（`WATCHDOG_TIMEOUT_SEC = 2`）：超时后由独立线程从 adj 1000 向 0 搜索候选同步终止一个进程，这条紧急路径不重走完整 PSI/水位判断，日志 `lmkd watchdog timed out!` 应与常规压力终止分开统计。终止后 `ProcessList` 收到通知，把退出记录标为 `ApplicationExitInfo.REASON_LOW_MEMORY`。

**Q19: 进程"消失"有哪几类原因？如何用证据区分？**

四类故障都可能表现为"进程没了"，证据来源不同：

1. **用户空间 lmkd（LMK）**：系统整体压力下按 adj 终止，证据是 `lowmemorykiller` 日志、Perfetto `android.memory.lmk` 事件、`REASON_LOW_MEMORY`；
2. **内核 OOM Killer**：内核无法满足分配时选择目标，证据是内核日志，Framework 侧记录 `REASON_LOW_MEMORY` 加子原因 `OOM_KILL`；
3. **进程内 OOM**：Java `OutOfMemoryError`、原生崩溃 tombstone 或 abort 记录；
4. **MemoryLimiter（仅 Android 17、部分设备）**：单进程超配额，`REASON_OTHER` 加 description 含 `MemoryLimiter:AnonSwap`。

排查顺序：先用 `ApplicationExitInfo`（`getHistoricalProcessExitReasons()`）与日志确定退出时间与类型，再看终止前是否存在 PSI、低水位、swap 不足或缓存抖动，然后核对目标进程当时的 adj 与内存构成，最后确认用户返回后是否产生新进程与启动代价。`REASON_LOW_MEMORY` 需结合子原因区分系统 LMK 与内核 OOM；Java `OutOfMemoryError` 不能归因于 lmkd。注意部分设备不支持精确报告低内存终止，可能显示为 `REASON_SIGNALED` + SIGKILL，可先查 `ActivityManager.isLowMemoryKillReportSupported()`。

**Q20: Cached App Freezer 的冻结流程与资格判断是什么？冻结期间进程内的 GC 会运行吗？**

缓存应用冻结器（Cached App Freezer）通过 cgroup freezer 暂停已进入缓存状态进程的线程调度。资格判断以 OOM 调整为输入：缓存进程区间是 `CACHED_APP_MIN_ADJ(900)` 到 `999`，`ActivityManagerConstants.DEFAULT_FREEZER_CUTOFF_ADJ` 默认取 900；但 adj 达标只是候选——进程若仍有需要 CPU 时间的职责（前台/顶部组件、正在执行的 Service、前台服务、广播等），不会被冻结。Android 14+ 的公开行为是进入缓存约 10 秒后冻结（源码用防抖超时控制，设备可调），生命周期事件到来立即解冻。

冻结动作的顺序（按 AAOS13 源码核对 `CachedAppOptimizer.java`）：先 `freezeBinder(pid, true)` 冻结 Binder 接口并处理未完成事务，再 `setProcessFrozen()` 写入冻结 cgroup——先 Binder 后 cgroup 让 system_server 能在停止调度前处理 Binder 状态。解冻时先解 Binder 再解 cgroup；若冻结期间收到同步 Binder 事务，服务端进程会以 `ApplicationExitInfo.REASON_FREEZER` 终止。

冻结期间所有线程（包括 ART GC 守护线程）都无法获得 CPU，应用不能分配对象、不能推进并发 GC、不能执行 `onTrimMemory()`。"冻结区间内发生 GC"通常是观测口径问题：GC 区段在冻结前已开始、解冻后补做，或看到的是系统从进程外部执行的内存优化。固定频率的后台任务在冻结期间会错过周期、恢复时密集执行，需要可靠后台工作应使用系统调度 API。

**Q21: 冻结后 RSS 下降了，是谁做的？"应用页面回收"与 ART GC、内核规整有什么区别？**

冻结后 `dumpsys meminfo` 中 RSS 下降可能来自进程外部的动作，而不是 ART 在冻结区间执行了 GC。三个同名概念分属三层：

1. **ART 压缩式 GC**：应用进程内的 ART 移动受管理堆中的 Java 对象；
2. **应用页面回收（app compaction）**：`CachedAppOptimizer` 在冻结成功后按 `CompactProfile`（`SOME` 偏文件页、`ANON` 偏匿名页、`FULL` 两者）对目标进程执行；按 AAOS13 源码核对，JNI 层用 `process_madvise()` 分批提交（文件页常用 `MADV_COLD`、匿名页常用 `MADV_PAGEOUT`）；
3. **Linux 物理页规整**：内核迁移物理页形成连续空闲块，目标是伙伴系统的高阶分配。

Android 17 还引入 MMD 协作：冻结后可安排按进程 ZRAM 写回，Activity 激活解冻时可预取先前写回的页面。这些都改变 RSS 或匿名页位置，但执行者都不在应用进程内，且受开关与设备配置约束。

诊断口径上：冻结器的 ATrace 事件是瞬时事件，`dur` 不能当冻结时长，应按 PID 配对 `Freeze`/`Unfreeze` 并用 `cgroup.events:frozen` 确认；一次 `FULL` 请求不能证明原生层最终执行了 `MADV_PAGEOUT`。`lmkd → CachedAppOptimizer → freeze` 这类串联画法是错的，冻结器与 lmkd 是两条独立路径。

**Q22: App 内存优化的推进顺序是什么？为什么不能一上来就上对象池？**

按"减少分配 → 缩短持有时间 → 消除泄漏 → 监控和回归"推进，这是排查顺序而非并列技巧，且每一步都要先用分配记录或性能轨迹证明热点再动手：

1. **减少无效分配**：优先检查 `onDraw()`/动画/触摸回调、列表绑定、循环装箱与复制、先解码原图再缩放的链路；把偶发小对象改成成员变量可能延长存活，"零分配"地长期保留大缓冲区反而抬高常驻内存；
2. **缩短持有时间**：页面销毁取消任务与回调、缓存设上限并缩容、`Closeable` 与游标明确关闭、Fragment 在 `onDestroyView()` 清 View Binding；
3. **消除泄漏**：从 GC Root 到不再需要的对象仍有强引用；修复靠生命周期所有权，弱引用只能改强度、不能取消工作或关闭资源；
4. **监控回归**：LeakCanary/堆转储查引用链，Perfetto/heapprofd/`dumpsys meminfo` 看趋势，线上关注退出原因与低内存终止率。

对象池不是首选：池中对象保持可达会抬高存活集，可能把短时峰值变成长驻内存，还要付出加锁与状态清理成本；短小对象经 TLAB 分配成本很低。Android 的 `Message.obtain()`、`MotionEvent.obtain()` 有明确获取/归还合约，业务自建池只在分配剖析证明热点、所有权清晰、容量有界时才值得引入。每次优化保留可复现场景与前后数据，单次快照不作结论。

**Q23: Bitmap 内存有哪些关键口径与手段？`recycle()` 该不该手动调？**

关键口径先立住：解码后内存由宽、高、像素格式与行跨度决定，与压缩文件大小无关（1080×1920 的 `ARGB_8888` 约为 7.91 MiB）；Android 8.0（API 26）起像素数据在原生堆，经 `NativeAllocationRegistry` 把原生分配压力反馈给运行时，仍会增加物理内存压力、分配失败仍可能表现为 OOME，只盯 `Runtime.maxMemory()` 会漏掉这部分。

手段按层次选择：

1. **解码阶段降采样**：`inSampleSize` 平台规则是小于等于 1 按 1、最终取 2 的幂、值为 n 时像素数约为 1/n²；应先读边界再计算，避免把尺寸刚好的图再放大；
2. **像素复用**：`inBitmap` 要求候选 Bitmap 可变且非 `HARDWARE`（API 19+ 解码字节不超过候选 `getAllocationByteCount()`），不满足抛 `IllegalArgumentException`，必须使用 `decode*()` 返回值而不是假设返回传入对象；成熟图片库已实现完整候选筛选，业务无需重复造池；
3. **格式选择**：`RGB_565` 减半但可能色带，`HARDWARE` 由图形后端管理、CPU 像素访问会失败，且设备通常用统一物理内存，"不占 RAM"是误导；
4. **`recycle()` 是所有权操作**：立即释放像素，前提是能证明此后无 View、Drawable、图片库或后台任务使用；现代应用优先靠清晰所有权与 GC 管理生命周期，库管理的 Bitmap 不由业务手动回收。

**Q24: 16 KB Page Size 对应用意味着什么？Android 13 设备需要关心吗？**

16 KB 基础页从 Android 15（API 35）起进入 AOSP 设备兼容范围，Android 13 仍是 4 KiB 页（按 AAOS13 源码核对，bionic linker 无 16 KiB 兼容代码），但含原生代码的应用现在就要为未来设备适配。

兼容性有两道独立门槛，修好一道另一道仍可能失败：

1. **ELF 可加载段对齐**：每个 `.so` 的 `PT_LOAD` 段要能按 16 KiB 边界映射（`llvm-objdump -p` 检查 `align` 至少 2**14）；
2. **APK 内未压缩 `.so` 的 ZIP 对齐**：文件起始偏移要 16 KiB 对齐（`zipalign -c -P 16 4`；AAB 用 bundletool 检查 `PAGE_ALIGNMENT_16K`）。

工具链基线：AGP 8.5.1+、Build Tools 35+、NDK r28+（默认生成兼容 ELF）；NDK r27 及以下需链接参数 `-Wl,-z,max-page-size=16384` 与 `-Wl,-z,common-page-size=16384`。纯 Java/Kotlin 且依赖无原生代码通常免改，仍应在 16 KiB 环境测试——SDK 常经 AAR 带入 `.so`。源码中写死的 `4096`（页对齐位运算、`mprotect` 地址、页数换算）都要改为运行时 `sysconf(_SC_PAGESIZE)` 查询。已与官方文档核对的 Play 要求：目标版本为 Android 15（API 35）及以上的应用必须支持 64 位设备的 16 KB 页，自 2027 年 2 月 1 日起不满足的应用更新无法发布。

性能收益必须测量：16 KiB 页让同样数量 TLB 条目覆盖四倍地址、顺序访问缺页更少，但小映射多、对齐边界多的应用内存可能略增；官方初期 Pixel 测试（内存压力下启动平均缩短 3.16%、系统启动约 8%）是设备级均值，不能推导单个应用的预期收益。Android 17 的 bionic 兼容模式（`bionic.linker.16kb.app_compat.enabled`，含 `fatal` 验证值）只为旧 ELF 争取迁移时间，发布产物应在不依赖兼容路径的前提下完整验证。
