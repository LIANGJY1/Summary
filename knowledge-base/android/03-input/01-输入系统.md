**Q1: 一次点击"没有反应"，输入事件从硬件到 View 树要经过哪些阶段，排查时按什么顺序分段定位？**

事件主链路是：内核 input core/evdev（`/dev/input/eventX`）→ `EventHub`（epoll + inotify）→ `InputReader`（mapper 生成 `NotifyArgs`）→ 监听链 → `InputDispatcher`（目标选择与队列）→ `InputChannel`（AF_UNIX SOCK_SEQPACKET 套接字）→ 应用 `NativeInputEventReceiver` → `ViewRootImpl` 的 `InputStage` → View/ViewGroup。"没有反应"可能停在链路上任何一段，且帧率正常不能证明输入及时到达。

排查按"事件是否存在"逐级缩小，顺序为：

1. `getevent -lt`：确认 evdev 节点是否产生事件及时间戳，排除触控固件与驱动；
2. `dumpsys input`：确认设备启用、视口、焦点窗口与连接状态；
3. 输入系统跟踪：确认 `RawEvent`、`NotifyMotionArgs`/`NotifyKeyArgs` 是否出现；
4. `InputDispatcher` 丢弃与超时日志：确认是否因过期、策略、安全校验或无目标被丢；
5. 应用侧 `deliverInputEvent` 与主线程状态：确认事件已到达但消费被阻塞。

`InputReader` 与 `InputDispatcher` 是 `system_server` 中的原生线程（`libinputflinger` 库，不是独立进程）。`adb shell input tap` 走系统注入路径，可以绕过真实硬件与 evdev，注入成功只能说明注入点之后的链路可用。按 AAOS13 源码（`frameworks/native/services/inputflinger/InputManager.cpp`）核对，Android 13 的监听链是 `InputReader → UnwantedInteractionBlocker → InputClassifier → InputDispatcher`；Android 14 起分类组件改为 `InputProcessor`，Android 17 链上还增加了 `PointerChoreographer`、Rust 桥接的 `InputFilter` 等阶段，分析具体设备时按对应标签确认。

**Q2: `MotionEvent.getEventTime()` 代表什么时间？为什么"eventTime 到回调结束"不等于端到端触摸延迟？**

`getEventTime()` 接近设备产生事件的时刻（内核事件时间 `eventTime`），它既不是应用收到事件的时间，更不是画面显示的时间。用"eventTime 到业务回调结束"测出的只是"输入到应用处理"这一段，端到端的触摸到显示（touch-to-photon）还要包含应用渲染、缓冲区提交、SurfaceFlinger 合成与面板呈现。

一次事件在源码里有五个可测时间戳：

1. `eventTime`：设备产生事件的时间；
2. `readTime`：`EventHub` 从 evdev 读取的时间（`RawEvent` 同时保存两者）；
3. `deliveryTime`：`InputDispatcher` 成功向目标连接发布的时间；
4. `consumeTime`：应用从 `InputChannel` 读到消息的时间；
5. `finishTime`：应用回报处理完成、`FINISHED` 回到分发器的时间。

`readTime - eventTime` 大说明事件在驱动排队、线程唤醒或调度上停留；`deliveryTime - readTime` 覆盖映射器、监听链与目标选择；`consumeTime - deliveryTime` 覆盖套接字与应用 Looper；`finishTime - consumeTime` 覆盖批处理、`InputStage`、IME 与 View 处理。业务回调结束也不代表画面已上屏，`finishInputEvent()` 只表示应用结束了这枚事件的分发责任。因此测量口径必须先声明起止点，再做分段归因。

**Q3: 窗口输入事件为什么走 AF_UNIX SOCK_SEQPACKET 套接字而不是 Binder？Binder 在输入路径里还承担什么？**

高频事件的数据面用 `socketpair(AF_UNIX, SOCK_SEQPACKET)` 套接字传输：报文语义保证一条 `InputMessage` 原子收发、保留消息边界，非阻塞写入在缓冲区满时返回 `WOULD_BLOCK`，天然形成对应用消费速度的反压。按 AAOS13 源码核对（`frameworks/native/libs/input/InputTransport.cpp` 中 `socketpair(AF_UNIX, SOCK_SEQPACKET, 0, sockets)`），两端设为非阻塞并共享 Binder 令牌。

"输入事件不走 Binder"需要加限定：Binder 仍承担控制面，包括通道创建/移除、把客户端 fd 与令牌经 Parcel 传给目标进程、焦点与窗口策略回调、ANR 通知等。Binder 也支持 oneway 异步调用，不能用"Binder 只有同步模型"解释这个架构选择。

套接字里也不只有按键和动作消息：`FOCUS`、`POINTER_CAPTURE`、`DRAG`、`TOUCH_MODE`、应用返回的 `FINISHED` 等都走同一协议。窗口创建时的主路径是 `WindowState.openInputChannel()` → `InputManagerService.createInputChannel()` → `InputDispatcher::createInputChannel()` → `openInputChannelPair()`，服务端点包装成 `Connection`，客户端点作为可跨进程传递的 `InputChannel` 返回。

**Q4: InputDispatcher 中一条事件的 iq/oq/wq 三段队列如何迁移？`wq=1` 是否说明应用即将 ANR？**

一条事件的典型迁移是 `inbound → pending → outbound → publish → wait → FINISHED → remove`：监听链交付的事件先进入全局输入队列（`iq`），选定目标连接后包装成 `DispatchEntry` 进入该连接的输出队列（`oq:<channel>`），经 `InputPublisher` 写入通道成功后转入等待队列（`wq:<channel>`），收到序列号匹配的 `FINISHED` 才移除。三者在 Perfetto 中是 `ATRACE_INT` 计数器轨道，不是执行片段。

`wq=1` 只说明有一个已发布事件尚未完成，短暂非零是正常状态。判断是否指向 ANR 要同时看：最早分发项的 `deliveryTime` 与 `timeoutTime`、连接是否仍标记为可响应、应用是否已消费（`consumeTime`）、主线程处于 Running/Runnable/Sleeping、IME 与套接字回写是否在等待。只有事件年龄接近超时阈值、队列持续增长或连接被标记无响应时，才构成 ANR 证据。

反压的触发点是套接字实际不可写：`startDispatchCycleLocked()` 写入返回 `WOULD_BLOCK` 时，若 `waitQueue` 已有未完成事件则保留 `outboundQueue` 队首等待应用消费；若 `waitQueue` 为空却不可写，则视为异常并终止该连接的分发周期。排查堆积时分段看：`iq` 堆积查 dispatcher 线程调度与策略，`oq` 堆积查通道可写性与前序完成反馈，`wq` 堆积查应用主线程、`InputStage` 与 IME。

**Q5: 输入 ANR 的 5 秒从哪个时刻开始计时？哪些配置会改变它？"无焦点窗口 ANR"又是什么？**

连接型输入 ANR 的计时起点是 `InputDispatcher` 成功发布事件、设置 `deliveryTime` 的时刻，而不是硬件 `eventTime`，也不包含事件进入全局队列之前的延迟。默认基值是 AIDL 常量 `UNMULTIPLIED_DEFAULT_DISPATCHING_TIMEOUT_MILLIS = 5000`，再乘以读取 `ro.hw_timeout_multiplier` 的 `HwTimeoutMultiplier()`（默认 1）。按 AAOS13 源码核对，`InputDispatcher.cpp` 使用该常量与倍率组合。

改变实际超时的因素有三类：窗口可通过 `WindowInfo.dispatchingTimeout` 提供覆盖值；焦点应用有自己的分发超时；输入监视器使用 dispatcher 的监视器超时。因此"所有按键和触摸都固定等 5 秒"不准确，具体事件的 `timeoutTime` 以发布时读取的配置为准，之后即使超时配置改变也不追溯已发送的分发项。事件发布后应用迟迟不消费、异步 IME 未返回、View 处理阻塞或 `FINISHED` 回传受阻，都会占用这段超时。

无焦点窗口 ANR 是另一类：某显示器上有焦点应用、没有焦点窗口、且来了需要焦点目标的事件时，分发器保留待处理事件并按焦点应用的超时等待窗口出现；触摸其他应用改变焦点会取消等待。它不表示 `onResume` 变慢就必然 ANR。超时到期后分发器先把连接标为 `responsive=false` 并合成取消事件，新的目标选择会跳过该连接；客户端恢复传回 `FINISHED` 且剩余条目未过期时，连接才被标记恢复。

**Q6: 过期事件（stale event）的判定阈值是什么？它与 ANR 检查、事件丢弃是什么关系？**

过期判定的默认式是 `currentTime - eventTime >= 10s × HwTimeoutMultiplier()`（按 AAOS13 源码核对为 `STALE_EVENT_TIMEOUT = 10s × 倍率`）。它是系统保护阈值而非交互体验目标，厂商可修改。判定只作用于尚未分发的事件：已发布并进入 `waitQueue` 的事件不再回到过期判定，改由 `AnrTracker` 按 `timeoutTime` 检查——所以"只有过期"说明事件在注入或队列中停留过久，"只有 ANR"说明事件已投递但应用没按时确认，两者阶段不同。

丢弃原因有优先级顺序：`POLICY`、`DISABLED` 先判，仍为 `NOT_DROPPED` 才检查过期（`STALE`），按键与非指针动作随后才可能命中 `BLOCKED`。对进行中的指针手势，为维持 `DOWN—MOVE—UP/CANCEL` 状态一致，过期也允许继续分发。丢弃后 `dropInboundEventLocked()` 还会按已分发状态合成取消事件，因此"原事件未投递"与"应用收到 CANCEL"可以同时发生，`CANCEL` 用于清理旧状态。

按键和动作事件使用单调时钟域，`SensorEntry` 使用启动时钟；注入端或驱动用错时钟基准会制造大量虚假过期事件。历史资料中的 `APP_SWITCH` 丢弃原因在 Android 13/17 的枚举中都已不存在，分析旧日志必须对照相应发布标签。

**Q7: "点到谁就永远给谁"成立吗？`DOWN` 之后哪些情况会改变触摸目标并产生 `ACTION_CANCEL`？**

只能作为粗略描述。初次 `DOWN` 执行窗口命中测试并建立触摸状态，后续 `MOVE`/`UP` 通常延续已有目标、不在每个采样点重新选窗；但过程中多种情况会改变目标或终止原手势：

- 父容器在应用内拦截（`onInterceptTouchEvent()` 返回 true），原子 View 收到 `ACTION_CANCEL`；
- 系统手势监视器通过 `pilferPointers()` 抢占指针，原目标被分发器合成 `CANCEL`；
- 触摸拆分把不同触点 ID 分给不同目标；窗口消失、变得不可触摸或连接断开；
- 安全策略（窗口被遮挡、`DROP_INPUT` 类 `InputConfig`、UID 与令牌不匹配）要求丢弃；
- 子 View 被移除、窗口失焦或系统取消手势时清理 `TouchTarget`。

因此分析手势问题要同时看 `DOWN` 的命中结果、后续拦截决策、触点 ID 与 `CANCEL`，不能只看最终 `onTouchEvent()` 返回值。按键按焦点窗口分发（无屏幕坐标），指针动作按触摸状态分发，触摸目标不一定与键盘焦点相同。

**Q8: `InputFilter`、`InputMonitor`（监视窗口）、无障碍按键过滤三类旁路拦截的权限边界分别是什么？普通应用能注册吗？**

三类旁路能力作用不同，权限都在系统侧：

- **`InputFilter`（全局过滤器）**：隐藏系统接口，由 WMS/IMS 经 `WindowManagerInternal.setInputFilter()` 安装（按 AAOS13 源码核对，`InputManagerService.setInputFilter()` 保存过滤器并只向原生同步启用状态），可拦截原事件后决定放行、消费或经 `sendInputEvent()` 发替代事件，典型实现是 `AccessibilityInputFilter`。普通应用没有入口。
- **`InputMonitor`（监视窗口）**：`InputManagerService.monitorGestureInput()` 创建手势监视通道与 spy window，调用方必须持有 `android.permission.MONITOR_INPUT`（按 AAOS13 源码核对，平台清单声明于 `AndroidManifest.xml`，保护级别为 `signature|recents`）。监控阶段只读副本；接管需另调 `pilferPointers()`，且不能注入替代事件。SystemUI 的边缘返回手势即此模式。
- **无障碍按键过滤**：需服务配置声明 `canRequestFilterKeyEvents` 能力并在运行时置 `FLAG_REQUEST_FILTER_KEY_EVENTS`；`onKeyEvent()` 收到副本，返回 true 表示消费。判定发生在 `AccessibilityManagerService`/`KeyEventDispatcher` 与服务进程一侧的异步等待，材料按 Android 17 核对的等待上限为 500 ms，不是 `InputDispatcher` 同步等待远端 Binder。

版本边界：Android 17 的 `InputFilter` 是 C++ 包装层加 Rust 实现的辅助功能过滤器（防重复键、慢速键、粘滞键），`EventHub`/`InputReader`/`InputDispatcher` 仍是 C++；AAOS13 源码中不存在这套 Rust 过滤器，"InputFlinger 已用 Rust 重写"的说法不成立。无障碍触摸另有 API 34 起的 `setMotionEventSources()` 通用运动事件来源监听，与触摸探索的 `FLAG_SEND_MOTION_EVENTS` 不是同一开关。

**Q9: `Instrumentation`、`UiAutomation`、`adb shell input`、无障碍 `dispatchGesture()` 四类注入入口有什么差异？应用能用 source 判断事件是注入的吗？**

四类入口都最终经系统注入，但身份、目标与过滤器关系不同：

1. **`Instrumentation.sendPointerSync()`**：标准注入，目标 UID 固定为 `Process.myUid()`，只能命中测试目标自身拥有的窗口；使用 `WAIT_FOR_FINISH` 只等到 `FINISHED`，不保证界面已绘制；
2. **`UiAutomation.injectInputEvent()`**：经受信任的 `UiAutomationConnection` 标准注入，可跨应用窗口，按 `sync` 参数选择 `WAIT_FOR_FINISH` 或 `ASYNC`；
3. **`adb shell input`**：`InputShellCommand` 以 shell 身份走标准注入，目标是 shell 权限允许的范围；
4. **`AccessibilityService.dispatchGesture()`**：不使用 `INJECT_EVENTS` 通用入口，而在无障碍变换链内由 `MotionEventInjector` 生成事件（需 `canPerformGestures` 声明），可指定 `displayId`。

标准注入入口最终都经过 `InputManagerService` 的权限检查（`INJECT_EVENTS`，并按需检查 Instrumentation 来源 UID），不满足抛 `SecurityException`。普通注入事件绕过全局 `InputFilter`，只有专用测试入口或无障碍链内生成的事件才进入过滤器。

不能用 `MotionEvent.isFromSource()` 或公开 flags 判断注入：`source` 只描述设备类别；`InputEvent` 基类没有统一的 `getFlags()`，`FLAG_IS_ACCESSIBILITY_EVENT` 在材料核对的 Android 17 中仍是 `@TestApi @hide`。普通应用没有受支持的通用注入检测 API。

**Q10: 触摸采样率 240 Hz 与屏幕刷新率 120 Hz 是什么关系？高采样率的价值由什么决定？**

两者是彼此独立的频率：采样率是触控硬件每秒检测位置的次数，决定坐标的时间密度；刷新率是屏幕每秒更新画面的次数，限定显示更新机会。240 Hz 触控配 120 Hz 显示，理想情况下每个显示周期约有两个触控样本；相位也未必对齐，且控制器可能动态调整报告率，样本数只是频率比而非保证。

高采样率的价值取决于下游怎么消费：多出的样本常被合并进同一个 `MotionEvent` 的历史记录，列表滚动只读当前坐标时收益有限；笔迹拟合、速度估计、轨迹预测和高帧率场景更能利用密集样本。显示帧数仍受渲染能力与刷新率限制，提高采样率不能直接推导端到端延迟缩短——事件能否进入最近一帧，取决于到达时刻与整条处理路径。验证设备实际采样节奏应从驱动事件时间或结构化输入跟踪统计相邻样本间隔，而不是只看规格表。

**Q11: 应用收到的 `MotionEvent` 为什么会包含历史样本？批处理在 Perfetto 上如何识别？**

当触摸采样率高于渲染帧率时，一个 VSYNC 周期内可能到达多个 `ACTION_MOVE` 样本。批处理（batching）让应用侧 `InputConsumer` 把设备、来源、动作、显示设备与指针属性都兼容的样本合成一次交付：第一条样本初始化 `MotionEvent`，后续样本经 `addSample()` 加入历史。它合并交付但不删除坐标——当前坐标用 `getX()/getY()` 读，较早样本用 `getHistorySize()` 和 `getHistorical*()` 读。

按时间顺序消费历史样本的最小写法：

```java
for (int h = 0; h < event.getHistorySize(); h++) {
    float x = event.getHistoricalX(0, h);
    float y = event.getHistoricalY(0, h);
    // 处理批内历史样本
}
float latestX = event.getX();
```

Perfetto 上的表现是：一个批只出现一次 Java `deliverInputEvent`；原生区段 `dispatchInputEvent MotionEvent ... historySize=N` 直接给出历史样本数。不要把一个事件里的 N 个历史点误判为 N 次 View 分发，也不要用"采样点数量 × View 树深度"估算开销。通道已收到消息也不代表 Java 立刻逐条执行 `dispatchTouchEvent()`，靠近下一帧输入回调才消费是设计行为。

**Q12: 触摸重采样（resampling）以什么时间为目标？有哪些边界条件？**

重采样发生在目标应用进程内（不在 `InputReader` 或 `InputDispatcher`）：当 `InputConsumer` 使用有效的 `frameTimeNanos` 消费一批事件、且厂商未关闭 `ro.input.resampling` 时，以 `frameTimeNanos - 5 ms` 为目标时间，在真实样本间线性插值，或按最近两个样本做受限外推，让 `MOVE` 坐标更接近帧时序。

按 AAOS13 源码核对（`frameworks/native/libs/input/InputTransport.cpp`），相关常量为：`RESAMPLE_LATENCY = 5 ms`（目标相位偏移）、插值要求两点间隔至少 2 ms、外推要求间隔在 2–20 ms 之间、外推最远到 `currentTime + min(delta/2, 8 ms)`，仅对指针来源的 `ACTION_MOVE` 执行，并要求触点 ID、工具类型与显示器一致。这 5 ms 是给插值预留后续样本的相位偏移，不能写成"系统额外等待 5 ms"，也不能计入触摸到显示耗时。

版本边界：API 35 起可用 `MotionEvent.PointerCoords.isResampled()` 判断坐标是否由重采样生成；重采样坐标会作为批内新样本加入，事件中至少保留一个真实样本。Android 17 把批处理与重采样拆到 `InputConsumer.cpp`/`Resampler.cpp`，但常规 `ViewRootImpl` 路径的实际调用链仍以对应源码标签为准。急转弯、速度突变和稀疏样本仍可能产生偏差，评估时要同时比较真实样本、重采样标记与最终笔迹。

**Q13: `requestUnbufferedDispatch` 与前缓冲渲染分别解决什么问题？轨迹预测（MotionPredictor）的可用边界是什么？**

两者作用于不同阶段，可组合但不能互相替代：

- **无缓冲分发**：`View.requestUnbufferedDispatch(event)` 让当前序列（到 `ACTION_UP` 前）的真实样本经 `consumeBatchedInputEvents(-1)` 立即送达，缩短 `MOVE` 进入应用前的等待；代价是事件更早逐个到达、CPU 与回调压力增加，官方文档提示它不适合多数应用，随意启用可能造成滚动抖动并失去系统重采样收益；
- **前缓冲渲染**：Jetpack 低延迟图形（`GLFrontBufferedRenderer`、`CanvasFrontBufferedRenderer`、`LowLatencyCanvasView`）把短生命周期增量内容画到专用前缓冲图层，缩短笔迹从提交到可见的路径，代价是可能出现撕裂。

前缓冲适合签名、白板、手写笔迹这类增量区域小、预测段可被真实样本修正的场景；整屏列表滚动与普通按钮反馈不适合。手写的完整流程是：读真实样本与历史点，必要时无缓冲分发，`MotionPredictor` 只产生短时间窗的临时预测点画在前缓冲层，真实样本到达后修正，抬笔经 `commit()` 提交多缓冲层。

版本边界：`android.view.MotionPredictor` 自 API 34 加入；材料按 Android 17 核对，设备资源 `config_enableMotionPrediction` 的 AOSP 基础值为 `false`，原生层只接受手写笔来源，`predict()` 可能因噪声下限等返回 `null`，且没有定义 `FLAG_PREDICTED`，应用需分层管理真实与预测笔迹。API 可用不表示设备默认开启。

**Q14: Choreographer 一帧内输入回调排在什么位置？缓冲与无缓冲的消费分支如何选择？**

`Choreographer.doFrame()` 的回调顺序固定为 `CALLBACK_INPUT`(0) → `CALLBACK_ANIMATION`(1) → `CALLBACK_INSETS_ANIMATION`(2) → `CALLBACK_TRAVERSAL`(3) → `CALLBACK_COMMIT`(4)（按 AAOS13 源码核对，`Choreographer.java` 常量定义）。输入排最前，保证同帧的动画与遍历基于最新输入状态；`COMMIT` 在遍历之后负责帧末工作与时间基准修正，不负责测量布局绘制。

连续 `MOVE` 默认走缓冲路径：`WindowInputEventReceiver.onBatchedInputEventPending()` 检查 `mUnbufferedInputDispatch` 与来源，未请求无缓冲时调用 `scheduleConsumeBatchedInput()`，让事件在接近下一帧的输入回调中消费，以减少 Looper 唤醒和 View 分发次数并保留重采样机会；当前序列请求无缓冲时改走 `consumeBatchedInputEvents(-1)` 立即取走全部待处理样本。普通滚动应保留缓冲路径；笔迹等确认归属的场景才对已 attach 的 View 请求无缓冲，且只影响当前手势序列。

**Q15: 边缘返回手势如何做到"先并行观察、条件成立再接管"？应用分别会看到什么？**

SystemUI 通过 `monitorGestureInput()` 建立名为 edge-swipe 的手势监视通道（spy window），与应用并行收到同一条指针事件流。`ACTION_DOWN` 后按顺序判定：导航模式与 SystemUI 状态、底部手势区与画中画等排除区、应用申请的排除区、左右边缘宽度；资格成立后比较横向与纵向位移——纵向先超过 `mTouchSlop`、停留超时或第二根手指落下会取消候选；横向占优并越过阈值后进入接管。

接管即 `pilferPointers()`（按 AAOS13 源码核对，`InputDispatcher.cpp` 提供 `pilferPointers(const sp<IBinder>&)`）：分发器把当前指针从原目标移走，并给原窗口合成 `ACTION_CANCEL`，后续事件流由监视器持有。旧式路径（无返回动画可用时）提交后注入 `KEYCODE_BACK` 的按下与抬起；有动画路径则把事件交给 WM Shell 的 `BackAnimationController`，由系统解析返回目标并驱动预览。因此"应用触摸流以 CANCEL 中断"未必是应用问题，可检查是否有系统监视窗口抢占了指针。

性能敏感点：阈值判定涉及排除区、状态标志与可选 ML 分类，不适合同步 I/O；材料按 Android 17 核对 `gestures.back_timeout` 的 AOSP 默认值为 250 ms 且长按取消取其与 ViewConfiguration 的较小值，旧口径"400–500 ms"不适用。

**Q16: Predictive Back 的回调接口有哪几层？`android:enableOnBackInvokedCallback` 在不同版本语义有何差异？**

回调分三层（已与官方文档核对）：

- **平台提交回调 `OnBackInvokedCallback`**（API 33）：只有 `onBackInvoked()`，提交后通知，没有进度方法；
- **平台进度回调 `OnBackAnimationCallback`**（API 34）：`onBackStarted()`/`onBackProgressed()`/`onBackCancelled()`/`onBackInvoked()`，可接收开始、进度、取消与提交；
- **AndroidX 兼容层 `OnBackPressedCallback`**：`handleOnBackPressed()` 一直可用，进度方法自 activity 1.8.0 增加，且只有框架 API 34+ 才由系统驱动。

清单属性语义随版本变化：Android 13/14 用于显式加入新模型（开发者选项测试动画）；Android 15 移除开发者开关，已加入的应用显示返回主屏、跨任务、跨 Activity 三类系统动画；Android 16 起对目标版本为 36+ 的应用默认启用，仍可设 `false` 临时退出，且启用后旧 `onBackPressed()` 不再调用、`KEYCODE_BACK` 不再分发给应用。API 36 新增 `PRIORITY_SYSTEM_NAVIGATION_OBSERVER` 观察者回调（值为 -2，只观察不消费），API 37 起允许注册多个。

应用侧判断路径时不能把所有返回手势当成 `KEYCODE_BACK`：提前分发分支经 WM Shell 解析 `BackNavigationInfo`，只有找不到有效返回信息等兜底条件才注入返回键。

**Q17: 预测性返回为什么要求"进度阶段只做可撤销的视觉更新"？提交边界是什么？**

因为手势随时可能被取消。`onBackStarted()`/`onBackProgressed()` 属于预提交阶段，只应保存起始状态并更新 `translationX`、alpha、缩放等可撤销属性；`onBackCancelled()` 把视觉状态恢复到起点；只有 `onBackInvoked()`（已提交）才执行 `finish()`、`popBackStack()`、隐藏 IME 等导航状态变更。若在进度阶段就改变导航栈，取消手势时很难恢复一致。

系统动画同样遵守这一边界：WM Shell 在手势阶段只对 `RemoteAnimationTarget` 的 leash（`SurfaceControl` 动画控制柄）做逐帧变换，提交后才触发真实回调并接入正式窗口转场。`BackNavigationInfo` 类型（`TYPE_CALLBACK`、`TYPE_CROSS_ACTIVITY`、`TYPE_CROSS_TASK`、`TYPE_RETURN_TO_HOME` 等）与 `isPrepareRemoteAnimation()` 决定谁驱动进度：应用回调获胜时不并跑跨 Activity 系统动画。

性能上进度回调每帧都可能执行，应避免在其中做 I/O、同步 Binder 或创建大量对象；掉帧时要同时检查当前应用、目标窗口、WM Shell 与 SurfaceFlinger，不能只看当前 Activity 的 RenderThread。跨 Activity/跨任务预览通常要求目标已有进程和窗口，系统不会为预览强行冷启动已死亡进程，此时回退到普通回调属安全行为。

**Q18: `setSystemGestureExclusionRects` 申请的排除区一定生效吗？限制是什么？**

不保证。应用上报的矩形要经过两道裁剪：与窗口可触摸区域相交，并受每侧纵向高度预算限制。按 AAOS13 源码核对（`DisplayContent.java` 的 `mSystemGestureExclusionLimit`，源自 `WindowManagerConstants`），该值至少 200 dp，限制的是左右边缘各自可排除的纵向总高度，不限制横向宽度；超出预算的部分被裁掉，SystemUI 通过 `ISystemGestureExclusionListener` 收到的是限制后的区域。

区域分两层：`WindowInsets.Type.systemGestures()` 描述系统手势优先区，应用可在非强制部分有限排除；`mandatorySystemGestures()` 是 `setSystemGestureExclusionRects()` 无法覆盖的子集，底部主屏与快速切换手势不能像侧边返回一样退出。触点只命中未受限区域时，说明申请过但未获配额，系统仍识别返回并记为被拒绝的排除。

坐标以 View 布局后的局部坐标为准，View 移动或尺寸变化后要重新上报。排查"同一条边有些位置有效、有些仍触发返回"时，应结合 `dumpsys window` 的最终获批区域与 Perfetto 中指针流是否被抢占，不能只看应用传入的列表。

**Q19: `VelocityTracker` 有哪些容易出错的使用细节？默认拟合策略是什么？**

常见错误集中在三处：

1. **时机**：`addMovement()` 只负责收样（`ACTION_DOWN` 起），`computeCurrentVelocity()` 才生成可查询的速度；源码注释称其相对昂贵，简单 Fling 在 `ACTION_UP` 计算即可，拖动中需要按速度切状态时应限定触发条件；
2. **取值键**：`getXVelocity(id)`/`getYVelocity(id)` 的参数是稳定的指针 ID，不是随指针增减变化的位置索引；
3. **生命周期**：`obtain()`/`recycle()` 成对调用，`ACTION_CANCEL` 也要回收；一个实例可同时记录多个指针 ID，"多指需要多个 Tracker"是误解。

底层实现在原生 `VelocityTracker.cpp`。按 AAOS13 源码核对，`DEFAULT_STRATEGY = LSQ2`（对近期位置与时间样本做二阶最小二乘拟合），是全局默认策略；Android 14 起才引入轴级策略表（X/Y 用 `LSQ2`、`AXIS_SCROLL` 用 `IMPULSE`），且禁止差分轴套用位置轴策略——跟踪滚轮/旋钮时不能直接复用触摸屏结论。原生收样还会跳过标记为重采样的样本（避免按预测坐标拟合速度），同一指针超过 40 ms 无新样本时按"已停下"重建状态。AOSP 没有承诺固定耗时，测量开销应在受控构建中加自定义 trace 区段并结合分配分析。

**Q20: TouchSlop 与 Fling 速度阈值应该怎么取值？硬编码源码常量有什么问题？**

两者都必须运行时从 `ViewConfiguration` 获取，不能用源码后备常量：

- **TouchSlop**：`TOUCH_SLOP = 8` 只是给没有 `Context` 的旧代码兜底的 dp 后备值（按 AAOS13 源码核对，`ViewConfiguration.java`）；正常路径是 `ViewConfiguration.get(context).getScaledTouchSlop()`，框架从 `config_viewConfigurationTouchSlop` 资源读取像素值，设备可用资源覆盖校准。判定是否开始拖动通常用从 `DOWN` 起的总位移，而不是相邻 `MOVE` 的增量，否则许多小增量永远越不过阈值；
- **Fling 速度**：50 dp/s 与 8000 dp/s 同样是后备常量，运行时取 `getScaledMinimumFlingVelocity()`/`getScaledMaximumFlingVelocity()`（像素每秒），并把 `computeCurrentVelocity(1000, max)` 的限幅参数与比较阈值保持同一单位。Android 14 起还有按输入设备、轴、source 的变体，设备或轴组合无效时最小值返回 `Integer.MAX_VALUE`、最大值返回 `Integer.MIN_VALUE` 表示不支持。

TouchSlop 过大拖动启动显得迟钝，过小会把抖动误判为拖动；调整自定义控件时阈值来源应可随设备配置变化，业务代码不复制数字。

**Q21: `GestureDetector` 的 `onDown` 返回值为什么重要？长按与双击有哪些机制细节？**

`onDown()` 决定控件是否从 `DOWN` 起接受整个触摸序列：等到 `MOVE` 才返回 true，常导致后续事件没有按预期交给识别器。`GestureDetector` 是事件序列驱动的状态机，`DOWN` 时安排 `SHOW_PRESS`、`LONG_PRESS` 消息并调用 `onDown()`，位移超过 TouchSlop 取消点击/长按候选并转 `onScroll()`。

长按：`DEFAULT_LONG_PRESS_TIMEOUT = 400` 是平台默认值（按 AAOS13 源码核对），运行时经 `getLongPressTimeout()` 读取 `Settings.Secure.LONG_PRESS_TIMEOUT`，所以"所有设备固定 400 ms"不准确；移动越过 TouchSlop、额外指针按下或 `CANCEL` 都会取消长按。长按等待用消息调度、不占主线程，性能问题通常出在 `onLongPress()` 回调本身。输入分类也会参与：`CLASSIFICATION_AMBIGUOUS_GESTURE` 按配置倍率放大 slop 并延后长按，`CLASSIFICATION_DEEP_PRESS` 可立即触发，应用不应根据压力值再造一套冲突规则。

双击：启用 `OnDoubleTapListener` 后要区分 `onSingleTapUp()`（立即回调，适合即时反馈）与 `onSingleTapConfirmed()`（等待双击时间窗后确认）；第二次 `DOWN` 需同时满足时间在 `doubleTapMinTime` 到 `doubleTapTimeout` 之间、距离在双击容差内、首次点击未滑出区域才判定为双击。这些阈值来自运行时配置，业务不应自行复制框架后备的 40 ms/300 ms。

**Q22: 父子容器的手势冲突如何仲裁？`requestDisallowInterceptTouchEvent` 有什么边界？**

View 分发没有通用的"谁先超过 TouchSlop 谁获胜"规则：`ACTION_DOWN` 时 `ViewGroup` 命中子 View 并记录为 `TouchTarget`，后续事件沿目标链分发；父容器在每次分发中仍可调用 `onInterceptTouchEvent()`，一旦由"不拦截"变为"拦截"，原子 View 收到 `ACTION_CANCEL`，之后事件交给父容器。诊断冲突要把同一序列的 `DOWN → MOVE → CANCEL/UP` 连起来看。

子 View 调用 `parent.requestDisallowInterceptTouchEvent(true)` 后，`ViewGroup` 置 `FLAG_DISALLOW_INTERCEPT` 并逐级传给祖先，祖先跳过 `onInterceptTouchEvent()`；新的 `DOWN`、手势结束或取消会在 `resetTouchState()` 中清除标志。它的边界是：只约束祖先 View 的拦截，不绕过系统导航手势、窗口级输入策略或应用外的输入消费者；也不解决方向判断本身。应在手势所有权变化时调用一次，而不是每个 `MOVE` 重复调用。

需要父子协作分摊滚动距离时优先使用嵌套滚动协议：子 View `startNestedScroll()`，消费前 `dispatchNestedPreScroll()` 让父级先取走一部分，消费后 `dispatchNestedScroll()` 上报余量，结束时 `stopNestedScroll()`。嵌套回调本身不天然昂贵，只有性能跟踪显示父级回调或反复布局占主线程时才视为问题。横纵方向冲突的典型做法是父容器从 `DOWN` 保存坐标，位移超过 slop 且水平占优再拦截，并正确处理 `ACTION_CANCEL` 的清理。

**Q23: `showSoftInput()` 返回 true 意味着什么？应用如何可靠确认软键盘可见？**

返回 true 只表示请求通过了前置条件、进入后续处理，不表示输入法已经显示。前置条件包括：目标 View 是当前服务目标（served view）、View 自身有焦点、所在窗口有窗口焦点。带 `ResultReceiver` 的重载在 API 36 已弃用，因为回调同样不能可靠代表屏幕最终状态；Android 16 起 `SHOW_IMPLICIT`、`SHOW_FORCED`、`HIDE_IMPLICIT_ONLY`、`HIDE_NOT_ALWAYS` 不再影响平台处理，Android 17 应传 0 或直接用 `WindowInsetsController.show()/hide()`。

可靠确认用 Insets：监听 `insets.isVisible(WindowInsets.Type.ime())` 与 `getInsets(Type.ime()).bottom`。Insets 监听器可能在布局与动画期间多次回调，处理前应比较新旧值避免重复触发。Activity 刚创建时 View 焦点与窗口焦点可能尚未同时成立，必须用 `InputMethodManager` 时，等 `onWindowFocusChanged(true)` 后再请求（可 `post` 让服务目标状态先完成更新）。

**Q24: 软键盘显示慢，系统侧的完整链路和等待点是什么？3 秒重连阈值说明什么？**

显示链路以 Insets 为主线：应用 `WindowInsetsController.show(ime)` → `InsetsController` 更新请求可见类型并经 `IWindowSession` 上报 → WMS 更新窗口状态，`ImeInsetsSourceProvider` 通知 IMMS → IMMS `showCurrentInputLocked()` 检查就绪条件后调用 `IInputMethod.showSoftInput()` → IME `onShowInputRequested()` 接受后 `showWindow()` → WMS 等输入法 Surface 绘制并下发带 leash 的控制对象 → 应用 `InsetsController` 启动动画。把现代路径概括成"应用直接 Binder 调 IMMS"会漏掉 WMS 状态机。

等待点主要在：IMMS 只有在 `mCurIme`（输入法接口）、当前客户端、当前会话 `mCurSession` 同时存在时才直接发请求，条件不足进入 `PHASE_SERVER_WAIT_IME` 等绑定或会话；IME 接受后还要等 Surface 与 leash，控制对象未到达时客户端把 IME Insets 当不可见。按 AAOS13 源码核对，`InputMethodBindingController.TIME_TO_RECONNECT = 3000`（毫秒）是"绑定长期没连上"的恢复阈值，不能当正常冷启动预算，触发重连的样本应列为异常。

定位工具用 ImeTracker：同一请求跨客户端、system_server、IME 记录阶段令牌，停在 `CLIENT_VIEW_SERVED` 之前查焦点与调用时机，停在 `SERVER_WAIT_IME` 查进程启动/绑定/崩溃，到了 `IME_SHOW_WINDOW` 还拿不到控制对象查 Surface 与 leash 条件；配合 `dumpsys input_method` 的 `mSoftInputShowHideHistory` 与绑定状态交叉验证。

**Q25: 物理键盘按键从硬件到应用经过哪些阶段？按键重复（key repeat）由谁合成？**

路径是：`KeyboardInputMapper` 用扫描码和 HID 用法码查按键字符映射（KCM）与按键布局得到 `keyCode`、`metaState` 与策略标志，生成 `NotifyKeyArgs` → `InputDispatcher` 入队前调用策略 `interceptKeyBeforeQueueing()`（电源、音量、Home 等系统按键可能在此结束；按 AAOS13 源码核对，`InputDispatcher.cpp` 在 `notifyKey` 路径调用该钩子）→ 目标选择用焦点窗口（事件带有效 displayId 用之，否则用焦点显示设备）→ 分发前还可经 `interceptKeyBeforeDispatching()` 延迟或消费 → 应用侧依次过 `NativePreImeInputStage`、`ViewPreImeInputStage`、`ImeInputStage`（IME 可异步处理，返回未处理才继续）、`ViewPostImeInputStage` 等阶段。IME 不是"View 未消费后的兜底"：硬件按键可先交给 IME，软键盘输入又常经 `InputConnection.commitText()` 直接送文本，不保证对应一串 `KeyEvent`。

按键重复由 `InputDispatcher` 合成：`EventHub` 打开设备时尝试用 `EVIOCSREP` 关闭内核重复，mapper 忽略 `EV_KEY value==2`；分发器保存最近可重复的 key-down，在入站队列为空时按配置合成。按 AAOS13 源码核对（`InputDispatcherConfiguration.h`），默认首次等待 500 ms、后续间隔 50 ms，第一条重复事件 `repeatCount` 为 1 并带 `FLAG_LONG_PRESS`。应用应读取 `repeatCount` 区分首次按下与重复，只在 `repeatCount == 0` 做一次性初始化；长按驱动连续移动时保持幂等，否则 50 ms 间隔很快积压主线程。

**Q26: 鼠标、触控板与触摸屏的事件语义有什么区别？指针捕获有哪些模式？**

三类设备的映射器与事件语义不能互换（映射器由 `InputDevice::createMappers()` 按设备类别创建）：

- **鼠标**：`CursorInputMapper` 处理相对位移，先经速度曲线更新系统光标，再生成带屏幕坐标的 `SOURCE_MOUSE` 事件（未按键是 `ACTION_HOVER_MOVE`，滚轮是 `ACTION_SCROLL` + `AXIS_VSCROLL/HSCROLL`）；
- **触控板**：`TouchpadInputMapper` 先经手势识别库解释，普通模式下应用收到的是鼠标或已分类手势事件，不能反推"硬件只报了一个相对坐标"；
- **触摸屏**：`MultiTouchInputMapper` 直接产出 `SOURCE_TOUCHSCREEN` 的多点 `MotionEvent`。

source 描述分发语义：`SOURCE_MOUSE` 属于 `SOURCE_CLASS_POINTER`（坐标即指针位置），`SOURCE_MOUSE_RELATIVE` 属于 `SOURCE_CLASS_TRACKBALL`（指针捕获期间的相对移动），`SOURCE_TOUCHPAD` 属于 `SOURCE_CLASS_POSITION`（原始触点），判断输入类型要同时看设备能力、source、action 与轴值。

指针捕获要求 View 层级有窗口焦点，窗口失焦或焦点显示设备改变时被强制释放；鼠标捕获后切到 `SOURCE_MOUSE_RELATIVE`、关闭加速并隐藏光标。版本边界：材料按 Android 17（API 37）核对，触控板有 `POINTER_CAPTURE_MODE_RELATIVE` 与 `POINTER_CAPTURE_MODE_ABSOLUTE` 两种模式，绝对模式跳过手势识别库、以 `SOURCE_TOUCHPAD` 上报触控板坐标空间的多点数据，且无参 `requestPointerCapture()` 的默认行为受平台功能标志控制、语义敏感代码应显式传参——AAOS13 源码中不存在这套双模式 API。
