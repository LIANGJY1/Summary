# 运行时分区与挂载

> 学习资料（文章模式沉淀）。边界：本文回答设备分区的职责、动态分区与 `super` 的容量关系、Virtual A/B 的 OTA 数据路径，system-as-root 根布局，以及启动时逻辑分区和 `/data` 的挂载职责、系统分区内的目录约定（/system/etc）。镜像如何构建、打包与刷写归 [../11-构建系统/04-系统镜像.md](../11-构建系统/04-系统镜像.md)。具体分区名与布局随设备、启动模式和 Android 版本变化，最终以设备 fstab、分区表与构建配置为准。Q 序列即结构，供 atlas 同源直读。

**Q1: [done] Android 分区是什么，如何理解？**

Android 分区是设备存储中为特定用途划出的存储区域或逻辑存储空间，用来组织启动文件、系统软件和用户数据等内容。一个设备有多个分区，可以让不同内容分别管理、更新和保护。

从存储到文件访问，可以分为以下几层：

1. **存储设备**：例如车机中的闪存设备，提供实际的持久化存储容量。
2. **分区**：在存储空间上划出不同用途的区域。例如，boot 用于启动相关内容，userdata 通常用于用户和应用数据。
3. **文件系统或镜像内容**：某些分区包含文件系统，由它组织目录和文件；另一些分区保存启动镜像等数据，不一定以普通目录方式访问。
4. **挂载点**：当分区中的文件系统需要按路径访问时，系统将它接入目录树。例如，userdata 上的文件系统通常挂载到 `/data`。`/data` 是目录入口，不是分区本身。

Android 的分区还可以按组织方式区分：

1. **物理分区**：由存储设备的分区表描述，例如部分设备上的 userdata 和 super。
2. **逻辑分区**：在动态分区方案中，由 super 中的元数据描述其占用的空间，例如 system 和 vendor。系统建立映射后，将它们作为块设备使用。

可以把存储设备想成一个柜子，分区是按用途划出的空间，文件系统负责组织空间里的文件，挂载点则是访问这些文件的入口。实际分区名称、大小和布局取决于设备、Android 版本及构建配置，不能仅凭目录名称判断它一定对应独立物理分区。









**Q2: [done] Android 常见分区各有什么作用？**

Android 将启动、系统软件、厂商适配和用户数据组织到不同分区。分区名称和是否存在取决于设备配置、首次发布时的 Android 版本及升级方案，不能假定每台设备都有以下所有分区。

启动、验证和恢复相关的分区包括：

1. **boot**：保存启动内核。采用通用内核映像（GKI，Generic Kernel Image）的 Android 12 及更早版本设备通常还在此包含通用 ramdisk；随 Android 13 及更高版本发布的设备将通用 ramdisk 放入 init_boot。升级设备可能保留旧布局。
2. **init_boot**：在适用设备上保存通用 ramdisk，提供启动早期用户空间所需内容。
3. **vendor_boot**：保存厂商启动相关内容，例如 vendor ramdisk；具体组成取决于设备和启动镜像版本。
4. **dtbo**：保存设备树覆盖内容，供启动时描述或调整设备硬件配置。
5. **vbmeta**：保存 Android Verified Boot（AVB，Android 验证启动）使用的验证元数据，参与检查镜像及分区内容的可信性。
6. **recovery**：提供恢复环境所需的镜像。支持无缝更新的设备可以把恢复环境放在 boot 或 init_boot 相关的 ramdisk 中，因此不一定有独立 recovery 分区。
7. **misc**：保存供启动及恢复流程使用的少量控制信息，例如恢复启动命令。

系统和硬件适配相关的分区包括：

1. **system**：保存 Android 系统镜像中的框架及通用系统组件。
2. **system_ext**：保存扩展通用 system 镜像的系统资源和专有模块。
3. **product**：保存面向具体产品的系统内容。
4. **vendor**：保存芯片或设备厂商提供的硬件相关实现，例如部分 HAL 实现及配置。
5. **odm**：保存设备设计厂商对板级支持包的定制内容，是可选分区。
6. **vendor_dlkm 和 odm_dlkm**：分别用于保存供应商和设备设计厂商的内核模块，使这些模块可以与相应的 vendor 或 odm 内容分别组织和更新。
7. **super**：在动态分区设备上作为物理容器，以元数据管理 system、vendor 等逻辑分区及其占用空间；它不是应用直接访问的目录。

数据及特定硬件功能相关的分区包括：

1. **userdata**：通常挂载到 `/data`，保存用户安装的应用及用户和应用数据。
2. **metadata**：在使用元数据加密等功能的设备上保存相关密钥材料或元数据；它与 userdata 是不同分区，具体用途取决于设备实现。
3. **cache**：保存临时数据；使用无缝更新的设备可能没有独立 cache 分区。
4. **radio**：在需要独立存储无线装置软件的设备上保存相应映像，并非所有设备都有。
5. **tos**：在使用 Trusty 可信执行环境的设备上保存相应系统映像。
6. **pvmfw**：在支持受保护虚拟机的设备上保存其启动固件。

分区职责不等于固定物理布局。例如 system 可以是 super 中的逻辑分区，而 `/data` 是文件系统挂载点；判断实际设备时应查看分区表、动态分区元数据和挂载状态。







**Q3: [done] Android 的动态分区是什么？**

动态分区是 Android 的一种分区管理方式：在 `super` 物理分区中划分 system、vendor 等**逻辑分区**，并用元数据记录它们占用的空间。系统可以在允许的容量范围内调整这些逻辑分区，而不必重新划分物理分区表。

可以把 `super` 想成一个总容量固定的储物柜，逻辑分区是其中按需分配的空间：

1. **固定分区时**：system 和 vendor 各占预先划定的物理区域。升级后如果 system 空间不够，即使 vendor 留有空闲，也不能直接跨越物理分区边界使用。
2. **动态分区时**：system 和 vendor 的空间由 `super` 中的元数据管理。OTA 更新可以根据需要调整逻辑分区的空间分配，但仍受 `super` 总容量、分区组和更新过程所需空间限制。
3. **启动时**：系统读取元数据并建立逻辑分区到实际存储区域的映射，随后才能把其中的文件系统挂载到对应路径。

“动态”指逻辑分区的空间分配可以调整，不表示物理存储容量会自动增加，也不表示所有分区都位于 `super` 中。具体布局取决于设备和 Android 版本。







**Q4: [done] Android /system/etc 目录是什么？**

/system/etc 是 Android 系统分区的配置文件目录，承担 Unix 传统中 /etc 的角色：init 的 rc 文件、权限 XML、音频策略等出厂配置都在这里。根目录被分区挂载点占满，Android 没有独立的 /etc，配置就随系统分区放在这里。

1. **/etc 的传统：**早期 Unix 把不便归类的文件放进 /etc，逐渐演变成配置文件的约定位置，fstab、hosts 等都在这里。程序按固定路径找配置，管理员按固定路径放配置，不必各自发明路径。
2. **Android 为什么没有独立 /etc：**根目录被 `/system`、`/vendor`、`/data` 等分区挂载点占满，只读与可写内容按分区组织。早期版本还用 `/etc` 到 `/system/etc` 的软链接兼容旧习惯。
3. **路径是契约：**init 的代码按写死的路径读配置——init.rc 在 `/system/etc/init/hw/init.rc`，各服务的 rc 文件在 `/system/etc/init/` 下。配置放别处 init 读不到，放置位置不是可选建议。
4. **暂存目录到运行时的映射：**制作镜像时，暂存目录（如 system_root）里那一层 `system/` 就是运行时挂载到 `/system` 的目录树，暂存区的 `system_root/system/etc/init.rc` 打包开机后就是 `/system/etc/init.rc`。镜像树整体复刻真机布局。

























**Q5: [done] Android 的 super 是什么，解决了什么问题？**

`super` 是 Android 动态分区方案中的物理分区，用来容纳和管理 system、vendor 等逻辑分区。它让这些分区在同一个容器内分配空间，便于系统升级时调整各自的容量。

1. **解决的问题**：传统固定分区各有物理边界。system 升级后空间不足时，即使 vendor 有空闲，也不能直接使用其预留空间。
2. **工作方式**：`super` 中的元数据记录逻辑分区及其占用的存储区域。启动时，Android 根据元数据建立各逻辑分区的块设备映射，再分别挂载其中的文件系统。
3. **调整与限制**：OTA 可以在允许范围内调整逻辑分区的空间，不必重新划分物理分区表。但 `super` 总容量有限，调整还需满足分区组和升级过程的空间要求。

`super` 是容器，不是 system 文件系统，也不是应用直接访问的目录；userdata 等分区不一定位于其中。

















**Q6: [done] Android 的 super 为什么通常不包含 userdata？**

在常见的 Android 动态分区布局中，`super` 容纳 system、vendor 等系统逻辑分区，`userdata` 通常是独立分区。`/data` 是 userdata 上文件系统的挂载点，不是分区名。

典型关系如下，具体设备布局可能不同：

```text
存储设备
├── super 物理分区
│   ├── system 逻辑分区
│   ├── vendor 逻辑分区
│   └── product 等逻辑分区
└── userdata 分区
    └── 文件系统挂载到 /data
```

两者分工不同：

1. **super**：管理系统镜像使用的逻辑分区，便于 OTA 在容量和分区组限制内调整它们的空间。
2. **userdata**：保存应用和用户持续读写的数据，通常希望系统升级后仍保留。它的使用方式和生命周期与系统镜像不同。

Android 官方建议避免将 userdata 等永久可写分区放入 super，但具体布局仍需查看设备配置。Virtual A/B 更新可能使用 `/data` 空间保存快照，这不意味着 userdata 属于 super；调试用 scratch 也可能使用受支持的逻辑分区或数据分区上的后备镜像文件。





**Q7: [done] Android 的 scratch 是什么，怎样为 OverlayFS 提供可写空间？**

scratch 是 Android 在部分设备上为调试性 OverlayFS 准备的可写工作空间。它解决的问题是：系统分区可能使用只读文件系统，开发时需要临时替换文件，却不能直接向原分区写入。scratch 提供另外一处存储，OverlayFS 再把这处修改与原系统文件合并，让程序仍通过原路径访问。

以开发者替换 `/system_ext/priv-app/Launcher/Launcher.apk` 为例，先理解涉及的几层：

1. **原始系统文件**：只读 system_ext 中的 APK 是 OverlayFS 的 lower（下层）内容。它来自原系统分区，本身不会因上层覆盖而改变。
2. **scratch 后端**：后端是提供存储空间的实际对象和映射链路，例如受设备配置支持的逻辑分区或镜像文件。它提供可读写的块设备；“后端”回答的是数据最终存在哪里、通过什么设备访问。
3. **scratch 文件系统**：系统在后端块设备上准备可写文件系统，并将其挂载到 `/mnt/scratch`。挂载点是访问入口，不是存储设备本身；文件系统负责管理其中的目录和文件。
4. **upper 和 work**：系统为 system_ext 在 scratch 中准备 OverlayFS 目录。upper 保存新增或替换后的文件，work 供 OverlayFS 内部准备对象；可写覆盖层要求二者位于同一文件系统。
5. **合并视图**：OverlayFS 将原 system_ext 作为 lower、scratch 中相应目录作为 upper，合并后仍从 `/system_ext` 提供访问。推送的新 APK 写入 upper 后，同路径的上层文件通常遮蔽 lower 中的原 APK。

例如，假设设备使用 `super` 中的 scratch 逻辑分区作为后端：系统将分配的空间映射为块设备，在其上使用文件系统并挂载到 `/mnt/scratch`；upper 中的替换 APK 最终保存在这套后端空间中。

判断实际设备时需要区分：

1. **后端位置**：Android 13 也可能在符合条件时使用 `/data` 上的后备镜像文件。应查看目标设备的映射和配置，不能仅凭 `/dev/block/dm-0` 推断最终物理位置。
2. **“scratch 文件”**：可能指工作空间中的 APK、目录或覆盖层标记，也可能指后端镜像文件，需结合具体路径判断。
3. **重启后的状态**：持久化后端未被清理时，内容可能保留；只有覆盖层重新挂载并使用该 upper 时，它才可能再次遮蔽 lower。

实际后端、启用和清理条件取决于设备配置；有些设备使用其他覆盖层存储位置，或直接重新挂载而不使用 scratch。上述 APK 路径只是示例，不能证明目标设备存在该文件。



















**Q8: [done] adb remount 的原理是什么？**

adb remount 请求设备端为可调试系统分区准备可写访问，具体可能是直接重新挂载，也可能在只读文件系统上建立 OverlayFS。它不把 EROFS 本身变为可写格式。

Android 13 的 fs_mgr 会检查可重挂载分区和 verity，条件允许时准备覆盖层；某些状态更改需要重启后生效。是否支持取决于构建、权限、内核和设备配置，必须检查命令结果与实际挂载。





**Q9: [done] /dev/block/dm-0 /mnt/scratch f2fs rw 如何解析？**

这行表示当时把设备映射节点 dm-0 提供的 F2FS 文件系统以读写方式挂载到 /mnt/scratch。dm-0 是运行时 device-mapper 编号，不是稳定的物理设备身份；仅凭这一行不能判断其最终后端是否在 super 或数据分区。





**Q10: [done] Android 的 verity 是什么，为什么启用后可能清理 OverlayFS？**

Android 中讨论分区校验时，verity 通常指 **dm-verity**。其中 dm 指 device-mapper（设备映射器），是 Linux 提供的虚拟块设备框架；verity 表示完整性验证。dm-verity 是建立在 device-mapper 上的块设备校验机制，在读取受保护分区的数据时检查其是否与可信的校验信息一致，帮助发现系统分区被篡改或数据损坏。

它的工作过程可以这样理解：

1. **建立校验信息**：制作受保护的分区镜像时，为数据块生成哈希树，并将可信的根哈希纳入 Android Verified Boot（AVB，Android 验证启动）的验证链。
2. **读取时校验**：设备启动后，系统通过 dm-verity 映射访问受保护的块设备。读取数据块时，内核根据哈希树验证数据；校验失败时如何处理取决于设备配置和错误处理模式。
3. **保护范围**：dm-verity 检查的是受保护的块设备内容，不是检查所有文件，也不等于把 userdata 上的应用私有数据都纳入同一套校验。

例如，车机从 system_ext 读取出厂 Launcher APK 时，如果该分区受 dm-verity 保护，APK 所在数据块会在读取过程中接受校验。若数据块与可信校验信息不符，系统可能报告或处理校验错误，具体表现取决于设备的错误处理模式。verity 校验块内容，并不单独判断 APK 的业务逻辑是否正确。

项目中常见两种使用场景：

1. **正式系统**：通过验证启动链和受保护分区的完整性检查，降低系统镜像被持久篡改或损坏后仍被当作可信内容使用的风险。
2. **开发调试**：受支持的 userdebug 或 eng 设备可以按平台流程调整 verity 状态，再通过 adb remount 准备可写视图并推送测试文件。Android 13 的 AOSP 调试流程可能使用 OverlayFS；具体权限、是否需要重启和是否支持由设备配置决定。

例如，调试时通过 `adb push` 替换 Launcher，测试 APK 可能保存在 OverlayFS 的 upper，并遮蔽 lower 中的原 APK。Android 13 AOSP 的恢复过程如下：

1. **启用校验**：在支持的 AVB 调试设备上，`adb enable-verity` 请求设备端按当前 slot 设置 verity 状态。
2. **清理覆盖**：状态改变后，Android 调试流程主动调用 OverlayFS teardown，清理上层覆盖，并可能按后端和设备状态删除 scratch 后备镜像或逻辑分区。**这不是 dm-verity 校验数据时自动删除 upper。**
3. **重启验证**：按设备提示重启后，检查目标进程的挂载、系统路径 APK 的哈希和包管理器使用的路径。清理后可见的是当前 lower 镜像中的版本，不一定是最初出厂版本；`/data` 中的应用更新也可能影响最终使用的 APK。

清理可能影响其他调试覆盖，应先备份需要保留的内容。不能只凭命令执行就认定清理成功：本地 Android 13 的 AVB 分支在 verity 已启用时会提前返回，清理也可能失败。若此前直接改写了底层分区，清理 OverlayFS 不能还原该文件。具体行为取决于构建、权限和厂商实现。

verity 状态、bootloader 锁定状态、Verified Boot 启动颜色及挂载的只读或可写标志彼此相关，但不是同一概念。排查时应结合启动信息、实际设备映射和命令输出判断，不能只凭一个属性或 `ro` 标志推断分区当前是否经过 dm-verity。





**Q11: [done] U 盘系统升级后为什么可能再次看到旧文件？**

升级可能更新系统镜像中的 lower，而独立的持久化 upper 未清理；如果之后再次挂载覆盖层，upper 的同路径旧文件可能遮蔽新 lower。U 盘只是升级包的载体，实际写入和擦除范围由升级方案决定。

这只是有条件的机制：必须证明 upper 中确有旧文件、它与当前目标路径对应且覆盖层生效，才能把旧文件来源归因于该路径。升级成功与合并路径显示旧内容可以同时成立。

**Q12: [done] 如何确认升级前后的 upper 是否是同一持久化对象？**

需要建立跨时间的设备和文件证据链，不能只比较 /mnt/scratch 路径或 dm 编号。记录每次启动的 boot ID、slot、mountinfo、设备映射和动态分区信息，再比较 upper 文件清单与哈希；任一后端重建、路径变化或采集权限不足都可能改变判断。

**Q13: [learning] 为什么 A/B 切槽和 OverlayFS 的 upper 生命周期要分别验证？**

A/B 更新管理目标槽位、启动与回退；OverlayFS 管理挂载和上下层文件。切换槽位本身不能证明 upper 一定保留或清除。要判断旧内容是否影响新槽位，需要分别核对新 lower、后端是否仍为原对象、upper 条目及新启动后的挂载关系。

**Q14: [learning] Android 启动时谁把 super 里的逻辑分区映射并挂载？bootloader 会挂载 super 或 /data 吗？**

bootloader 负责加载启动所需的物理镜像并启动内核，不负责解析 Android 的 `super` 元数据或挂载 `/data`。启动后由 first-stage init 根据 ramdisk 中的 fstab、动态分区元数据和设备功能创建逻辑 block device 并挂载指定系统分区。`/data` 则在后续 init 阶段完成密钥准备后挂载。

1. **bootloader 阶段：**bootloader 根据设备启动配置读取 boot chain 所需物理分区，例如 boot、vendor_boot、init_boot、dtbo 和 vbmeta，并将内核与 ramdisk 交给内核启动。具体组合取决于 Android 发布版本、GKI、A/B 与 recovery 布局。
2. **first-stage init：**init 从 ramdisk 启动并读取设备 fstab。对标记为 first-stage mount 的条目，它解析 `super` 元数据、创建逻辑分区映射设备，再挂载 system、vendor 等早期所需分区。fstab 中的分区类型和 first-stage 标记决定实际挂载集合，不能假设所有动态分区都会在同一时刻挂载。
3. **Virtual A/B 特例：**启用压缩快照的设备可能需要 first-stage init 在挂载系统分区前启动 ramdisk 中的 `snapuserd`，让逻辑设备读取经过 snapshot 映射的数据。切换到系统分区并加载 SELinux policy 时，init 还需按版本定义的时序重新启动或切换 snapuserd 上下文，避免 snapshot I/O 中断。
4. `/data` 阶段：init 在挂载 `/data` 前要按设备配置完成 metadata encryption 的密钥准备。常见 fstab/init 流程会在 late-fs 阶段等待 KeyMint/Keymaster 等依赖，再通过 `mount_all` 处理 `/data` 条目。阶段名称、等待服务和 fstab 标记随设备实现变化，因此具体顺序要检查产品 init rc 与 fstab。
5. **文件系统安全层：**只读系统分区通常可在 block device 上叠加 dm-verity 校验。`/data` 可配置 dm-default-key 等 metadata encryption 机制。Android 9 的 system-as-root 布局把 root 文件系统并入 `system.img`，由内核将 `system` 挂载为根文件系统。Android 10 起，逻辑 `system` 分区不能再由内核直接挂载，系统分区映射和早期挂载由 ramdisk 中的 first-stage init 处理。升级设备会保留其原有启动布局，不能只按运行的 Android 版本推断分区形态。



























**Q15: [learning] android 中的 system-as-root 怎么理解？**

system-as-root（SAR）指根文件系统就是 system 分区本身：挂载后 system 镜像根部的内容直接出现在 `/` 下。init 二进制在镜像里位于 `system/bin/init`，成为根之后它在设备上的路径就是 `/system/bin/init`。构建时由 rootdir 模块（`system/core/rootdir`）在镜像根部创建指向它的符号链接，于是挂载后 `/init` 指向 `/system/bin/init`。内核启动第一个用户态进程的入口就是根下的 `/init`，保留这条路径使内核、既有工具和脚本都无需改动。该布局 Android 9 引入，Android 10 起成为新发布设备的要求。ramdisk 仍然存在，但只负责 first-stage 启动，不再提供根文件系统。

1. **和旧布局比：**旧布局由 ramdisk 提供初始根文件系统，`/init` 是 ramdisk 内的实体文件，system 作为普通分区挂载到 `/system`。SAR 下 system 同时承担根，init 再把根绑定到 `/system` 路径，按 `/system` 开头的旧访问方式继续可用。
2. **为什么 Android 10 起必须采用：**动态分区下 system 是 `super` 内的逻辑分区，内核只挂载物理块设备，无法把它挂为根。必须由 ramdisk 中的 first-stage init 解析 `super` 元数据、创建设备映射后再挂载。根从 ramdisk 换成 system，与 first-stage init 承担根挂载是同一变化的两面。
3. **怎么确认：**`ls -l /init` 第一列为 `l`，输出形如 `init -> /system/bin/init`——符号链接是一种内容为路径的特殊文件，访问它等于访问目标文件。`findmnt /` 应显示根来自 system 逻辑分区。两者同时成立即可判定设备采用 SAR。
4. **注意：**升级设备保留原有启动布局，非 SAR 设备上 `/init` 是实体文件。recovery 的根布局可能与正常启动不同。判断以设备 fstab 和分区表为准，不按 Android 版本反推。



























**Q16: [learning] Android 动态分区怎样把 system、vendor 等逻辑分区放进 super？它解决了什么容量问题？**

Android 10 引入动态分区后，设备可将 `system`、`vendor`、`product`、`odm` 等分区实现为 `super` 内的逻辑分区。OTA 可调整逻辑分区容量，而无需为每个只读分区在出厂物理分区表中永久预留增长空间。

1. **物理与逻辑关系：**`super` 本身是物理分区。逻辑分区由 `super` 中的 extents 和分区组元数据描述，设备映射出 block device 后再挂载文件系统。逻辑分区不是一块独立的物理闪存区域。
2. **容量调整：**旧式固定布局需要给每个分区单独预留空间，某个分区增长时，即使别处有空余也可能受分区边界限制。动态布局在 `super` 的可用空间范围内调整分区大小，设备仍必须满足总容量、分区组和 OTA 峰值空间约束。
3. **OTA 配合：**OTA 可更新分区组元数据并重设逻辑分区大小。采用 Virtual A/B 的设备还会在 `/data` 保存写时复制快照，快照空间需求和 `super` 的逻辑分区容量是两项不同的约束。
4. **查看布局：**设备上可用 `adb shell lpdump` 读取 `super` 元数据，检查逻辑分区、分区组和容量分配。它展示设备当前的分区元数据，不代替构建配置或 OTA 包内容分析。



























**Q17: [learning] Virtual A/B 与双份静态 A/B 分区有什么区别？OTA 快照写在哪里，何时回滚或合并？**

Virtual A/B 保留 A/B 更新的 slot 切换能力，但不在 `super` 内完整复制一套动态系统分区。OTA 将新数据写入 `/data` 上的写时复制快照，设备重启后通过快照映射读取新旧数据，确认新系统启动成功后再把快照合并回基础分区。

1. **存储布局：**bootloader 直接读取的关键物理分区仍按 A/B slot 更新。动态系统分区通过 `/data` 上的 COW snapshot 提供新版本块，不为每个动态分区在 `super` 中再保留完整 B 副本，因此比双份静态 A/B 少占常驻空间。
2. **安装与运行：**`update_engine` 编排下载、写入快照和 slot 切换。安装过程中快照写入 `/data`，设备仍可运行旧系统。重启后 device-mapper、`dm-user` 与 `snapuserd` 等组件按 Android 版本提供快照读取与合并路径。
3. **确认与回退：**新 slot 启动成功并标记为成功后，系统把快照合并回基础动态分区。若新系统启动失败，boot control 与更新状态可让设备回退到旧 slot 并放弃未完成的新版本更新。合并过程可跨重启继续，不能把普通启动失败与快照已合并完成混为一谈。
4. **版本和空间：**Virtual A/B 自 Android 11 起是 GMS 新发布设备要求。Android 12 支持压缩快照。Android 13 起，新发布设备的压缩快照与 userspace merge 默认使用 `snapuserd` 流程。存量设备升级时还受原有分区布局和配置约束。`/data` 必须容纳 OTA 的临时快照。空间不足会阻止更新或要求释放空间。
