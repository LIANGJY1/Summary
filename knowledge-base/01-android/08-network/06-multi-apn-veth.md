# 车机多 APN 与虚拟网卡

> 学习资料（文章模式沉淀）。主线：蜂窝多 APN 在 Android 内核/框架层的形态、veth 虚拟网卡 + 网关 + SNAT 的业务隔离拓扑、应用按业务绑定网卡、多 APN 的 DNS 分流与验证方法、双公网链路切换、TBOX 两种组网形态。拓扑实例来自某车机项目的多 APN 设计文档（2026-09，V1.0）——**内网 IP、私网域名、DNS 地址已按脱敏约定改写**，接口名保留通用结构（物理蜂窝网卡 / veth 虚拟网卡）；Telephony data 层类名按本地 AAOS13 源码核对（DataNetworkController/DataNetwork/DataProfileManager），veth/NAT 为通用 Linux 机制，项目私有绑定实现未核对。车联网总纲与 SOME/IP 见知识库 `网络/` 目录。Q 序列即结构，供 atlas 同源直读。

**Q1: Android 里多个 APN 在底层长什么样？框架怎么管理？**

每个成功的 PDN 激活对应内核里一张蜂窝数据网卡（标准命名 `rmnet_dataX`，每个 APN 一张）；Android 12 起 telephony data 栈重写为 DataNetworkController/DataNetwork/DataProfileManager（本地 AAOS13 源码文件核对），把每个 APN 配置（DataProfile）建模成一条 DataNetwork，各自有独立的 Network、路由表与能力。多 APN 的价值是业务隔离：默认公网、IMS、车厂私网（TSP）各走各的 PDN，互不抢带宽也互不可达。社区上的双卡双通（TBOX 场景）进一步把两张公网网卡做成主备双路由（`ip route` 按 metric 配优先级，主路由失效自动切换，CSDN TBOX 方案口径）。

**Q2: "虚拟网卡→物理蜂窝网卡"的隔离拓扑怎么读？为什么要引入 veth？**

项目内的三段式拓扑（脱敏后）：应用绑定 veth 虚拟网卡（固定内网地址，如 192.168.1.10）→ 流量到同 veth 对上的虚拟网关（192.168.1.1）→ 网关做转发与源地址转换（SNAT）→ 从物理蜂窝网卡（IP 随拨号变化）发往对应 APN。引入 veth 的动机：蜂窝侧 IP 拨号可变、应用无法预知，把"业务绑定面"固定在 veth 侧（地址、网关恒定），把"变化面"收敛到网关的转换规则里；同时不同 APN 的私网/公网在 L3 隔离，业务互访被拓扑禁止。每个 APN 一套 veth 对 + 网关 + 转换规则，是车机多路数据隔离的常见设计。

**Q3: 应用怎么把流量绑定到指定网卡？Java 层 Network 绑定与内核 SO_BINDTODEVICE 是两套什么机制？**

两套机制，别混：一是 **Android Network 绑定**——`ConnectivityManager.bindProcessToNetwork()` 或 `Network.bindSocket()`，作用于框架登记的 netId，适合绑 Wi-Fi/蜂窝这类"框架可见网络"；二是 **内核接口绑定**——`SO_BINDTODEVICE` 套接字选项或 `ip rule`/路由策略，直接按接口名（veth、rmnet）收口，veth 这类框架不当作 Network 的链路只能走这套。项目文档要求"应用绑定对应虚拟网卡"，具体落在哪套由项目实现决定（未核对），判断方法：能 `bindProcessToNetwork` 拿到该网卡的 Network 就是前者，只能写套接字选项就是后者。绑定错了的表象一致：包从默认网卡发出、私网不可达。

**Q4: veth + SNAT 的数据路径里，SNAT 解决什么？为什么虚拟网关地址固定、物理地址可变？**

SNAT 把内网源地址（veth 侧 192.168.x.10）改写成物理网卡地址（拨号所得，如 10.x.x.x）再发出，回包按转换表改回——没有它，对端回包找不到 192.168.x.10 这个私网源。"网关固定、物理可变"正是分层目的：应用与防火墙规则面向恒定的 veth 网段写死；拨号变化只影响网关侧的转换规则与出接口地址，业务零感知。排查连通性时按链路分段取证：veth 上有包 → 物理网卡上有包且源地址已转换 → 对端可达，断在哪段查哪段（绑定/路由、转换规则、运营商）。

**Q5: 多 APN 下 DNS 为什么会"串"？私网域名的解析怎么保证走私网 DNS？**

每个 APN 有独立 DNS 视图：私网 APN 的 DNS 只解析私网域名（返回私网地址），公网 DNS 不认识私网域名——解析请求走错 DNS 的两种症状是"解析失败"或"拿到不该有的地址"。保证方法是：解析必须从绑定网卡的接口发出并命中该 APN 下发的 DNS 服务器（框架 resolver 按绑定网络选 DNS，02 册框架篇机制）。验证三板斧（项目验证脚本的结构化提炼）：

1. **抓解析**：`tcpdump -i any -nn 'udp port 53 or tcp port 53'`，确认 53 端口查询的实际目的服务器；
2. **绑定探测**：`ping -I <虚拟网卡> <域名>`，让 ICMP 与解析都走指定路径；
3. **自动判定**：从 ping 输出提取解析 IP，按私网段（10/8、172.16/12、192.168/16）分类输出 PRIVATE/PUBLIC/FAILED，再分别 grep 虚拟网卡与物理网卡上的 ICMP 记录，三段证据（解析正确、虚拟网卡有流量、物理网卡有流量）齐了才算链路确认。

**Q6: "解析成功但业务不通"在多 APN 环境怎么定位？**

按五段二分（结合项目验证经验）：解析结果对不对（私网域名应得私网 IP，错则 DNS 走串）；绑定是否生效（`ping -I` 指定网卡通不通，不通则查 SO_BINDTODEVICE/ip rule 是否落到 veth）；veth→网关是否转发（抓包看虚拟网关侧）；网关→物理网卡是否做转换（对比两段源地址）；物理网卡→对端是否可达（抓 ICMP 回包，不通查路由与运营商侧）。每段只回答一个问题，别把五段混在一个"ping 不通"里猜。

**Q7: 双公网链路（双卡双通）怎么做无缝切换？**

两张公网网卡各配路由并按 metric 定主备（CSDN TBOX 双卡双通方案口径）：主路由在表内 metric 更小，链路检测（网关可达性/信号）失败时切到次路由，业务侧靠连接重试扛住切换间隙；要求"视频不中断"还要应用层做快速失败与断点续传。与多 APN 私网隔离是两个维度：双公网解决"出口冗余"，多 APN 解决"业务隔离"，车机整机常常两者叠加——公网主备 + 私网专链。

**Q8: 车机上网有哪两种形态？本项目属于哪种？**

两种形态（绿盟 TBOX 分析口径）：**独立 TBOX**——TBOX 内置模组拨号，经 USB 网络共享（RNDIS/ECM）给车机，车机侧看到的是一张 USB 网卡，NAT 做在 TBOX；**车机内置模组**——模组挂在车机 SoC 上，PDN 网卡（rmnet/厂商命名）直接出现在车机内核，多 APN 隔离在车机本地完成。本项目属后者：物理蜂窝网卡（项目内 sipa_eth* 命名）与 veth 都在车机内核里，转换与隔离规则在车机本地可查可改——这也是验证脚本能在一台设备上看到全链路的原因。

**Q9: 多 APN 私网隔离的安全设计要点是什么？**

私网 APN 的价值是业务只可达车厂服务端，安全设计围绕"不放大可达范围"：转换/转发规则只放行业务需要的端口与目标网段（iptables 转发白名单，不做全网段 MASQUERADE）；私网 DNS 只部署私网解析，避免私网域名泄露到公网 DNS；公网与私网链路禁止互通转发（两张 veth 之间无规则即不可达）；日志与抓包记录转换前后地址便于审计。文档层面的对应纪律：内网地址、私网域名、DNS 地址写在内网文档并脱敏流转（本项目文档即按此处理），机制知识才进公共知识库。

**Q10: 排查这类多网卡车机网络，随身工具箱有哪些？**

五件套：`ip addr`/`ip link`（确认 veth 对与物理网卡状态、地址）；`ip route show table all` + `ip rule`（按表+规则看策略路由，别只看主表）；`iptables -t nat -L`（转换规则，确认 SNAT 目标接口与网段）；`tcpdump -i any`（全接口抓包，按 53/ICMP/业务端口过滤，对比虚拟/物理两段）；`dumpsys connectivity` + `dumpsys telephony.registry`（框架侧网络与数据状态）。工具链全部可在设备 shell 执行，是车机现场排查的标准组合。

**Q11: 多 APN 的配置从哪里下发？OEM 定制走哪条链？**

配置链三层（01 册框架 + 04 册类型为基）：平台全量 APN 表（TelephonyProvider 的 apns-conf）按运营商匹配出候选 → CarrierConfig 按运营商覆写参数 → OEM 用 overlay/私有配置注入车厂专用 APN（私网 TSP 这类）。每个 APN 在框架内成为 DataProfile，由 DataProfileManager 管理并按需驱动 DataNetwork 激活（本地 AAOS13 类名核对）。定制多 APN 时的常见坑：APN type 该用 default（要出 Internet 语义）还是专用类型决定框架是否给它独立 Network；认证协议（PAP/CHAP）与 IP 版本要和运营商侧一致，错一个整条 PDN 起不来。排错从配置侧开始：先确认 DataProfile 的参数与下发来源，再查内核网卡。

**Q12: 车机流量怎么管"用量与超限"？流量策略在哪一层生效？**

框架的流量策略由 NetworkPolicyManager 管：按订阅/网络设置警戒线与限额（限额后可整体降速或禁用），Data Saver 控制后台应用访问，统计来自 netstats（按 uid 归因，官方机制口径）。车机的特殊性：私网 APN 常是按年签约的定量卡、公网卡计费——策略要按"每 APN 订阅"分别设额，热点（04 册共享场景）消费公网卡时尤其要接配额告警。排查"莫名断网/降速"先查策略层：`dumpsys netpolicy` 与数据用量统计，确认是策略触顶而不是链路故障。

**Q13: 蜂窝走向 IPv6-only，车机的 v4 私网服务怎么办？CLAT 是什么？**

运营商逐步关闭 LTE/NR 的 v4 承载，蜂窝只发 IPv6 前缀（v6-only + NAT64/DNS64 网关）。Android 的兜底是 CLAT（clatd，Android 6.0 起内置，RFC 6877 的 464XLAT 终端侧，高通平台由 modem 硬件加速）：系统发现 NAT64 前缀（对 `ipv4only.arpa` 做 DNS64 查询，RFC 7050）后在本地起 192.0.0.4 虚拟接口，把应用的 v4 包就地转成 v6 发出——v4-only 应用无感（社区与 RFC 口径；clat 实现不在本地部分同步树）。三个坑：纯 DNS64 环境（无 CLAT）下**硬编码 IPv4 字面量**的应用必死，v4 私网地址更不可能被 DNS64 合成——车厂私网若仍是 v4 专网，必须要求运营商给专网 APN 保留 v4 PDP 或自做转换；CLAT 下 UDP 大包受 MTU/分片影响，症状是 TCP 正常 UDP 丢（社区实测口径）；NAT 规则与安全策略按 v4 写的要重审 v6 语义。验证：v6-only 卡上分别 ping v4 公网与 v4 私网，抓包看是否出现 v6 封装。

**Q14: OTA/地图包这类大文件下载，网络策略怎么设计才不踩坑？**

四条：**APN 选择**——默认公网卡承载大下载，私网专卡只给业务（02 册隔离原则），计费敏感时用专用下载卡或限定 Wi-Fi 上游（Connectivity 侧按 transport+计费位过滤 NetworkRequest）；**可恢复性**——分块断点续传 + 服务端幂等（Range/分片校验），按"网络切换、熄屏、车速"三类事件预期中断，续传逻辑是常态路径而不是兜底；**时机与配额**——结合 04 册计费策略挑窗口（停车充电+Wi-Fi/不限量卡），配额联动多路径预算（05 册 Q8 的多路径仅用于"愿意花流量换时间"的场景）；**并发控制**——限制并发连接数避免占满 PDN（私网业务同卡共存时尤其重要），下载进程与业务进程分 uid 便于 netstats 归因与策略隔离。

**Q15: 车云 MQTT 通道（TSP/EMQX 类）怎么设计才能在弱网与休眠下不丢指令？**

五个机制各答一个问题（EMQ 官方 TSP 建设系列与实践口径）：

- **会话一致**：ClientID 用 VIN 等唯一标识，`CleanSession=false` 持久会话——休眠/穿隧道掉线重连后，离线期间的下行指令由 Broker 补投。
- **QoS 分级**：车控下行用 QoS1（至少一次）并配指令 ID 幂等去重（至少一次会变成可能重复）；高频遥测按业务权衡 QoS0/1，全量 QoS2 的开销与阻塞不值得。
- **离线判定**：连接时注册遗嘱消息（LWT，如车辆状态 Topic），异常掉线由 Broker 代发，平台据此判上下线——比"心跳超时"更及时且对所有订阅方一致。
- **重连纪律**：指数退避 + 抖动，防止整片车辆同时唤醒造成重连风暴压垮接入层；重连成功后先补订阅再恢复业务。
- **KeepAlive 与休眠对齐**：保活周期与车辆电源策略（05 册电源状态题）和蜂窝 NAT 老化双重对齐——座舱深睡后连接由常供电域（TBOX）维持，座舱醒来补收，而不是让座舱连接硬扛休眠。

安全叠加（TLS + 客户端证书、指令签名防重放）见 07 册，属于同一通道的另一个维度。

**Q16: APN 激活失败怎么按错误码排查？**

框架上报的 `DataFailCause` 与 3GPP NAS 标准原因码对齐（TS 24.301 系，官方口径；实现类不在本地部分同步树），常见码到排查动作的映射：

- **认证失败类**：`AUTH_FAILED`（PAP/CHAP 用户名密码错误）——核对 APN 配置的认证协议与凭据，运营商侧与配置侧不一致是首因；
- **签约/策略类**：`OPERATOR_DETERMINED_BARRING`（运营商禁止该 APN）——查卡签约与 APN 开通状态，换测试卡常踩；`ACTIVATION_REJECT_GGSN/NETWORK`——核心网侧拒绝，查专用 APN 是否对本 IMSI 放行；
- **配置类**：`MISSING_OR_UNKNOWN_APN`——DataProfile 没下发或名字不匹配（11 册配置链）；`IP_VERSION_MISMATCH`——IP 版本协商（v4/v4v6）与签约不符；
- **环境类**：`SIGNAL_LOST`、`REGULAR_DEACTIVATION`——射频或网络侧重激活，通常自动恢复。

排查入口：`dumpsys telephony.registry` 与 telephony 数据日志看最后一次 fail cause，按上表映射到配置/签约/环境三层，再进本册五段定位法。

**Q17: 多业务要二层隔离时，VLAN 子接口在 Android 侧怎么落地？**

交换机侧把不同业务划进不同 VLAN（05 册架构口径）后，车机侧对应做法是在物理口上建 VLAN 子接口：`ip link add link eth0 name eth0.100 type vlan id 100`（802.1Q，通用 Linux 机制），每个子接口有独立地址、独立路由表，可分别被业务绑定或注册成独立链路——由此实现"同一根网线/网口上多业务二层隔离"。三个注意：VLAN 子接口 MTU 比物理口小 4 字节（802.1Q 标签占用，大包链路要一并核 MTU）；组播/广播不跨 VLAN，服务发现只在同 VLAN 内可见；与 02 册 Q8 的网段规划联动——每个 VLAN 配一个不重叠网段，热点/veth/专网各自独立。OEM 通常在 init 或网络服务脚本里固化这些子接口，现场排查先 `ip -d link` 确认子接口与 VLAN id 与设计文档一致。

**Q18: 连接正常但业务数据"莫名其妙被改"——NAT/ALG 会破坏私有协议吗？**

会。NAT 设备常内置 ALG（应用层网关）：它识别 FTP/SIP 等已知协议的载荷，改写其中内嵌的 IP/端口使 NAT 后的服务可达（通用 NAT 机制口径）。对私有协议的威胁：ALG 按已知协议的特征扫描载荷，二进制协议里恰好出现与触发模式匹配的字节序列时，**载荷会被误改写**——私有报文里内嵌的地址/端口字段被替换成网关地址，业务对端拿到错误数据；症状精确表现为"连接正常、内容错乱"且只有经过 NAT 的链路出现。对策：载荷加密（TLS 或私有加密使 ALG 无法识别与改写，最彻底）；关闭网关侧 ALG（自管网关可控，运营商侧不可控）；协议设计避免内嵌裸的传输地址端口。定位：明文私有协议 + NAT 链路 + "内容被改"三要素同现，抓包对比进出 NAT 前后载荷即可实锤。

**Q19: 手机想直连家里的车机（两端都在 NAT 后），怎么打洞？**

两端都无公网地址时靠 UDP 打洞：先经 STUN 服务器各自探测"自己在公网上呈现的地址:端口"，双方通过信令交换该映射，然后同时向对方映射地址发包——各自 NAT 上的出站映射被对方流量"钉住"，即建立直连（STUN/打洞通用机制口径）。失败条件与退路：对称型 NAT（每连一个目标换一个映射）打洞必败、企业防火墙拦 UDP——退路是 TURN 式中继，流量经中转服务器转发。车机的现实设计：常态远程访问不走打洞——车侧主动维持到平台的持久连接（MQTT 持久会话通道），手机经平台中转下发指令，链路永远可达且过平台鉴权；真正的直连（远程桌面、大带宽调试）才值得打洞，且要用"平台信令 + STUN/TURN 降级"的完整方案，配合 03 册 VPN 做加密。诊断打洞失败先分类：STUN 拿不到映射（UDP 被拦）、映射拿到了但洞打不通（对称 NAT/严格防火墙）、洞通了但应用层没通（02 册五段法继续）。
