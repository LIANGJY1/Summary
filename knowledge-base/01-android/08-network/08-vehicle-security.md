# 车机网络安全

> 学习资料（文章模式沉淀）。主线：车机网络攻击面盘点、远程指令通道的防重放与完整性、传输安全基线、固件/配置下发校验、量产调试接口治理、检测与响应。内容为行业实践与官方规范口径的沉淀（2026-09 检索），机制与通道细节分别见 [06-multi-apn-veth.md](06-multi-apn-veth.md)、[05-vpn.md](05-vpn.md)、[07-vehicle-network.md](07-vehicle-network.md)。Q 序列即结构，供 atlas 同源直读。

**Q1: 车机的网络攻击面有哪些？按通道怎么盘点？**

三类通道分开盘点：**远程**——蜂窝 APN 上的服务端通道（消息/MQTT、OTA、远程诊断隧道），攻击者是"平台到车"链路上的任何人，靠传输加密与双向认证收敛；**近场**——Wi-Fi 热点与 STA、蓝牙、USB 口、诊断口（OBD/UDS），攻击者是贴身接触者，靠配对鉴权、端口最小化与量产关闭收敛；**供应链**——第三方 SDK、预装应用、更新包本身，靠准入审核与签名校验收敛。盘点的产出是一张"通道 × 认证 × 加密 × 关闭状态"清单：每条通道四项都有答案才算受控，缺项即攻击面。

**Q2: 远程控车指令走了 TLS，为什么还要应用层签名与防重放？**

TLS 保护的是"通道"，防不了三类风险：车端无法确认指令的原始发起方业务身份（平台内被冒用）、抓包重放（截获的合法密文换个时间再发仍然有效）、平台侧密钥体系被拖库后的伪造。应用层对策三条：**完整性签名**——指令携带业务签名（HMAC 或非对称签名），车端用独立密钥验签；**防重放**——时间窗 + 单调计数器/nonce，超出窗口或重复序号直接拒绝；**幂等**——指令带唯一 ID，网络重传导致的重复执行被去重（控车指令重放是物理后果，不是数据问题）。三条都在业务协议层实现，与 TLS 是纵深关系而非替代关系。

**Q3: 传输安全基线是什么？"私网 APN"为什么也要加密？**

基线：全链路 TLS 1.2 起步、优先 1.3；禁用 SSLv3/TLS1.0/1.1 与过时套件；车端校验服务端证书（含域名与有效期），平台侧用客户端证书/Token 双向认证车机身份。私网也必须加密的原因：APN 隔离防的是"外部互联网不可达"，不防"私网内横向"——私网内的诊断平台、测试设备、被攻陷的其他车辆都在同一可达域，明文 MQTT/HTTP 在私网内同样是明文。落点检查：消息通道（MQTT over TLS）、OTA、诊断隧道、日志上传四类通道逐一核对加密与认证，"测试环境先明文后补"的债务会直接带进量产。

**Q4: 固件与配置下发的校验怎么做？怎么防降级？**

三件套：**签名验签**——更新包/配置由平台私钥签名，车端内置公钥验签，验签失败不落地；**版本单调（anti-rollback）**——安全版本号只升不降，防攻击者用旧版合法签名包把车"降级"出漏洞（回滚计数器由硬件/可信存储保障，通用安全设计口径）；**分阶段灰度**——签名合法不代表内容无缺陷，按车队批次灰度并保留回退版本。机制上与 Android A/B 无缝升级配合：下载验签在后台完成，切换在重启时原子生效，失败自动回退（Android 升级机制口径）。配置类下发同理：签名 + 单调版本 + 白名单 schema 校验，防止配置注入。

**Q5: 量产车机上哪些调试接口必须治理？**

按暴露面收口：**adb**——量产默认关闭或仅授权模式（用户显式开启），build 参数不带 root；**诊断口**——OBD/UDS 会话进入安全访问要鉴权，刷写与控车类服务量产限权或关闭；**隐藏入口**——工厂测试模式、后门 shell、临时 telnet/ssh 全部移除，不留"忘了关"；**服务面**——`netstat`/`ss` 审计监听端口，绑定 127.0.0.1 而不是 0.0.0.0，无用的服务不启动；**SELinux**——保持 enforcing，新增服务写独立 domain 而不是放宽容器。验收方式：以攻击者视角从每条通道（蜂窝、Wi-Fi、蓝牙、USB、诊断口）各做一次"能看到什么、能登录什么、能刷什么"的实测，遗留项清单进版本发布门禁。

**Q6: 网络入侵的检测与响应在车端怎么落地？**

三层：**基线**——每条通道记录正常流量画像（对端、端口、频次、时段），车端轻量规则可发现离谱偏差（本不该有入站连接的网卡出现扫描、深夜巨量上行）；**上报**——异常事件经运维通道（05 册远程运维三件套）带上时间戳与证据摘要上报平台，时间戳可信度依赖时间同步层；**响应**——事件分级（提示/限权/断链），高危动作（断开某通道、进入安全模式）需要平台下发或本地策略授权，避免误报直接断动力相关链路。设计边界：车端检测做"轻量异常发现与取证"，深度分析在平台侧——车端算力与误报代价都不支持复杂模型本地闭环。

**Q7: 车端的信任锚（根证书）体系怎么管理？**

按"分域 + 轮换 + 吊销"管理。**分域**：消息通道、OTA、诊断、EAP 接入各自独立的私有根 CA，互不交叉授权——一个域的根泄露不波及他域；公共 CA（系统信任库）只用于公网服务，私有域一律进各自信任锚（应用级 NSC 或平台级配置，04 册 NSC 口径）。**轮换**：根/中间证书都有到期日，建立证书台账与到期监控（04 册 Q10/Q13 的 pinning 与 EAP 证书都挂在这个台账上），到期前经 OTA 通道完成新锚下发；车端预置"下一任"锚实现平滑过渡。**吊销**：CRL/OCSP 在弱网下不可靠，车机常用折中是"短有效期 + 定期重签"或平台侧吊销名单随消息通道下发；离线期间的吊销延迟要在威胁模型里显式接受。红线：私有根私钥永不落车端、最好离线保存；车端只持有公钥与中间证书链。

**Q8: 近场三通道（Wi-Fi 热点、蓝牙、USB）各自的加固清单是什么？**

- **Wi-Fi 热点**：WPA2/WPA3 加密必开（开放热点只允许在受控演示场景）；开启客户端隔离防乘员设备互访（05 册隔离语义）；限定最大客户端数与频段；管理界面不暴露到热点侧。
- **蓝牙**：配对模式选数字比较类而非 Just Works（防中间人）；关闭"始终可发现/可配对"；关键 Profile 的数据走加密链路；不用的 Profile 服务关闭。
- **USB**：host 模式按 accessory 白名单过滤设备（防恶意 USB 外设——USB 攻击可模拟键盘/网络设备）；量产关闭 ADB 与 MTP 默认开启；USB 网络共享（RNDIS/NCM）只在实际需要时启用。
- 共同纪律：每条通道定义"无连接、有连接无配对、已配对"三态的权限差，默认态最小；状态与异常计入 Q6 的检测基线。
