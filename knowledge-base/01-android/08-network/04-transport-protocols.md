# 传输细节与协议设计

> 学习资料（文章模式沉淀）。主线：TCP 字节流的协议定界（粘包/拆包）、Nagle 与延迟 ACK 的组合延迟、TCP keepalive 参数真相、证书链不完整事故、拥塞控制的应用层启示、字节序与协议版本兼容、车云通道选型、热点网段冲突、TCP 半开假在线、DNS 劫持防御。通用传输层机制与社区经验口径沉淀（2026-09 检索），车云上下文衔接 [06-multi-apn-veth.md](06-multi-apn-veth.md)。Q 序列即结构，供 atlas 同源直读。

**Q1: TCP 是字节流没有消息边界，车云二进制协议怎么定界？**

TCP 只保证字节顺序不保证"一次发送=一次接收"——一次 send 可能被拆成多段到达（拆包），多次 send 也可能被合并送达（粘包），消息边界必须应用层自己定义。三种定界方案（传输层解析文章口径）：**固定长度头+变长体**——头里带魔数、版本、Body 长度、校验，接收方先读定长头再按长度读体，是最通用方案（Netty 的 LengthFieldBasedFrameDecoder 即此模式）；**TLV**（Type-Length-Value）——字段级自描述，扩展信号字段不动协议骨架，车联网上报常用；**分隔符**——只适合纯文本，二进制载荷可能出现任意字节（含分隔符本身）导致误切分，二进制协议不推荐。工程增强：帧头魔数用于错位后重新同步，校验和（CRC）用于防位翻转，版本号用于灰度兼容。

**Q2: 车控指令偶尔"一顿一顿"延迟 40ms，跟 Nagle 算法有什么关系？**

Nagle 算法为减少小包，会攒住未满 MSS 的小包，直到收到前一个包的 ACK 才发下一个；对端 TCP 还有延迟确认（Linux 默认约 40ms 才回 ACK）——两者叠加形成"发送方等 ACK、接收方等数据"的互等，交互式流量表现为固定节奏的卡顿（社区实测案例：未开 TCP_NODELAY 的音频流服务端收帧忽快忽慢）。对策：交互式/小包低延迟连接（车控指令、实时音频、RPC）设置 `TCP_NODELAY` 禁用 Nagle，让小包立即发出；吞吐型大流量传输保持默认即可。注意禁 Nagle 只影响发送节奏，不解决带宽与拥塞问题；带外确认：抓包看小包是否按发送节奏到达，是验证 NODELAY 生效的直接证据。

**Q3: TCP 自带的 keepalive 能用来做连接存活检测吗？**

能用但默认形同虚设：内核 TCP keepalive 三参数默认 `tcp_keepalive_time=7200s / intvl=75s / probes=9`——空闲两小时后才开始探测，对业务毫无意义（内核参数文档口径）。Android 上的正确姿势是两层：系统层用 `SocketKeepalive`（蜂窝/Wi-Fi 下把心跳卸载到内核/ modem，省电且周期可配，04 册已述）；应用层仍需自己的心跳（带业务语义、能触发重连与状态恢复），因为 keepalive 只证明"TCP 通"，不证明"应用可用"。两者是互补关系：系统 keepalive 防静默死链占资源，应用心跳做业务级健康与恢复（02 册 Q15 的 MQTT keepalive 与 LWT 即应用层实例）。

**Q4: "PC 浏览器 HTTPS 正常、车机/App 握手失败"——证书链不完整事故怎么定位？**

最常见根因是服务器只部署了域名证书、漏发中间证书链（阿里云小程序握手失败案例与 TopSSL 排查文章口径）：完整信任链需要"站点证书 → 中间 CA → 根 CA"，服务器必须把中间证书一并发送；桌面浏览器有中间证书缓存并能通过 AIA（Authority Information Access）在线补齐，多数移动客户端不具备补齐能力，直接握手失败——所以"电脑正常、车机不行"恰恰指向链不完整而不是网络问题。定位：SSL Labs/myssl.cn 检测工具报 "Chain issues: Incomplete"，或 `openssl s_client -connect host:443` 看返回链；修复是把 fullchain（站点+中间证书拼接）部署上服务器。车机交付检查单里应加入"全证书链检测"，避免新业务域名带着这条病上线。

**Q5: Linux/Android 的 TCP 拥塞控制是什么？应用层能利用什么结论？**

内核默认拥塞控制多为 cubic（丢包驱动），新内核支持 BBR（基于带宽与 RTT 估计，弱网长肥管道下更稳，通用 Linux 机制口径；切换算法需 sysctl 权限，应用不可调）。应用层可利用的结论三条：慢启动期吞吐爬坡——长连接复用比每次新建快，首包后不要立刻打满；丢包会被 cubic 解释为拥塞并塌缩窗口——弱网下应用层主动限速（04 册下载策略）比"能发多快发多快"总吞吐更高；QUIC 在应用层自带拥塞控制（04 册 Q9），绕开内核算法限制——这就是弱网优化选 QUIC 的底层原因之一。诊断勿把"限速导致丢包"误判为网络故障：应用自限速、运营商 QoS、拥塞丢包三者的抓包特征不同（重传模式与窗口轨迹）。

**Q6: 自定义二进制协议的字节序与版本兼容怎么设计？**

字节序统一用网络序（大端），编解码集中在协议层一处完成，业务层永不手写字节操作——大小端问题是跨厂商联调最高频的协议 bug 源。版本兼容纪律：帧头带版本号，新增字段只增不改不改语义（TLV 天然支持未知字段跳过——不认识的 Type 按 Length 跳过继续解析，这是 TLV 相对紧凑结构的最大工程优势）；删除字段先废弃后移除；枚举值只增不减。升级策略：版本协商在握手阶段完成（双方取交集），低版本对端不识别的新字段靠"跳过未知"消化。这些纪律与 02 册的通道设计（绑定、重连、幂等）组合，才是完整的车云协议设计。

**Q7: 车云通道怎么选型——MQTT、HTTP(S)、私有 TCP/QUIC 各适合什么？**

按业务特征选通道（综合本章节各册）：**MQTT（02 册 Q15）**——双向指令与状态遥测，持久会话+遗嘱+QoS 解决弱网不丢指令，是 TSP 消息通道默认解；**HTTPS**——大文件（OTA/地图，02 册 Q14）、低频配置拉取、生态兼容性要求高的接口，请求-响应模型简单、CDN/网关生态成熟；**私有 TCP/QUIC**——极致延迟或特殊传输语义（实时音视频流、高频信号流）才值得自建，代价是协议维护、断线恢复、安全全部自己做。常见反模式：用 HTTP 轮询模拟推送（延迟与耗电双输）；用 MQTT 传大文件（Broker 存储与重传成本失控）。多通道共存是常态：一条 MQTT 指令通道 + HTTPS 文件通道 + 可选实时流通道，按业务分流到对应 APN（02 册拓扑）。

**Q8: 车机开热点后"部分网站打不开"，为什么可能是网段冲突？**

Android 热点默认网段是 192.168.43.0/24（工业设备案例中手机热点 192.168.43.x 同段冲突的定位方法可直接迁移）：当热点网段与车机侧其他内网（TBOX 专网、诊断网段、上游路由器 LAN）相同或重叠时，路由表出现同目的不同接口的歧义，流量被路由进错误链路形成黑洞——症状是"热点客户端能连上、部分目标不通"，且随上游环境变化时好时坏（工业案例口径：Ping 不通但独立通道正常）。设计期对策：车内各网段统一规划互不重叠（热点、veth、专网各占独立 /24），并对已知常见网段（192.168.0/43/1.x）避让；运行期检测：冲突时从热点客户端 traceroute，第一跳之后的路径走向即可暴露歧义。修改默认热点网段在 framework/tethering 配置层完成（OEM 可定制）。

**Q9: "连接还在但对方已经没了"——TCP 半开连接怎么发现与处理？**

半开（half-open）指一端已崩溃/重启/链路静默丢失，另一端的 TCP 状态仍是 ESTABLISHED：此时不发数据永远不知道对端已死，一旦发送，重传若干次后才报错——期间应用表现为"假在线"（连接对象健在、任何请求无响应）。发现手段两层：内核 TCP keepalive（Q3，默认参数必须调短或用 SocketKeepalive）负责"协议层活着"；应用层心跳负责"业务层活着"并驱动恢复（超时未收到心跳响应即主动断开重连，02 册 MQTT 通道的 KeepAlive+LWT 组合是标准实现）。残余风险：重连幂等——半开期间服务端可能仍认为旧会话有效，重连协议要带会话令牌或让服务端以新连接顶掉旧连接，避免双活会话互相干扰。

**Q10: DNS 劫持有哪些形态？HTTPDNS 为什么能防，怎么防得彻底？**

运营商/链路 DNS 劫持的常见形态（社区攻防实践口径）：解析结果替换（域名指向广告页或错误 IP）、TTL 篡改（长期缓存错误结果）、对不存在域名返回广告 IP（NXDOMAIN 重定向）。HTTPDNS 的防御原理是绕过链路 DNS：应用经 HTTPS 直接向 HTTPDNS 服务查询解析结果，解析路径不走运营商递归，天然避开劫持点（腾讯云/阿里云实践口径）。防彻底还要补三件事：结果校验（对解析 IP 做服务侧校验或 HTTPS 域名校验兜底，防止 HTTPDNS 通道本身被污染）、降级路径（HTTPDNS 不可用时回退系统 DNS，但要保留劫持检测）、与证书校验联动（HTTPS 的域名校验使"连上假 IP"也无法完成握手，是最后一道防线）。车机注意：私网域名走私网 DNS（02 册 Q5），公网 HTTPDNS 不解析私网名——两套解析体系按域名域分流，不能混用。

**Q11: HTTP/2 的多路复用与队头阻塞——什么场景该用、什么场景反而不划算？**

HTTP/2 在单条 TCP 连接上用流（stream）多路复用多个请求，消除了 H1.1 的"一条连接一次一个请求"排队；但流之下仍是同一条 TCP——**任何一个包丢失，TCP 层重传会阻塞所有流**（传输层队头阻塞，协议机制口径）。取舍结论：网络质量好时 H2 单连接效率高（头部压缩、少握手）；高丢包弱网下单条 H2 连接反而比"多条 H1.1 连接"更脆——丢一个包全体请求受阻。另一个细节是连接合并（coalescing）：同证书多域名可能共用一条连接，服务端证书必须覆盖所有域名。HTTP/3（QUIC，04 册 Q9）把流做进传输层，流间独立重传，从根上解决该问题。工程建议：接口层允许在 H2 与 H3/多连接间切换配置，用弱网矩阵（06 册 Q8）实测各自的 P95 再定。

**Q12: 业务拆成多条连接后，消息乱序怎么设计保序？**

车云常见形态是指令与遥测各走独立通道（甚至不同 APN），同一业务对象的事件会乱序到达——"状态变更回执"可能晚于下一条指令的回执到达。设计三件：**业务序列号**——按业务对象（车辆/会话）维护单调序号随消息下发，接收端按序号重组与去重，不依赖到达顺序；**连接亲和**——同一业务键的消息固定走同一连接/通道，天然串行（代价是通道故障时该业务全停，按业务重要性取舍）；**版本/时间裁决**——跨通道的最终状态以业务时间戳或版本号高者为准，到达顺序只影响延迟不影响正确性。反模式：按"谁先到谁生效"处理带因果的消息（如"解绑"先于"绑定"到达），业务状态机直接错乱——保序是协议设计职责，不能指望网络替你保序。

**Q13: 对端一直不 read 数据，本端的 send 会怎样？TCP 流量控制怎么工作？**

TCP 用滑动窗口做流量控制：接收方在每个 ACK 里通告自己的剩余接收缓冲（rwnd），发送方未确认在途数据不能超过该窗口——对端应用不 read，接收缓冲逐渐占满，rwnd 通告到 0，发送方 `send()` 就会阻塞（或非阻塞返回 EAGAIN），直到对端恢复读取、窗口重新打开（通用 TCP 机制口径）。两层推论：**阻塞与假死**——"发得慢"不是网络问题而是对端消费不动，诊断看两端缓冲与窗口（`ss -tm` 可见），修复在对端的消费速度而非本端重试；**超时风险**——窗口长期为 0 时 TCP 有探测机制（零窗口探针），但应用层的写超时（SO_SNDTIMEO/非阻塞+select）要自己设，否则业务线程可能无限期挂起。UDP 对照：接收缓冲满时新到的包直接丢弃、不阻塞发送方——这就是高频遥测选 UDP 的机制根源。

**Q14: 高频小信号上报选 UDP 还是 TCP/MQTT？UDP 的坑在哪？**

UDP 适合的判据：容忍偶发丢失（下一帧信号很快覆盖）、追求低延迟（无握手无重传排队）、发送频率高到 TCP 状态维护不划算——车机高频信号流是典型；UDP 无连接也无队头阻塞，一包丢失不拖累后续包（与 TCP 的排队阻塞形成对照）。必须自建的三件事：**序列号**用于去重与乱序排序；**丢包容忍策略**（信号类丢一帧无碍，累计类要用周期快照代替增量）；**MTU 约束**——UDP 超过路径 MTU 会触发 IP 分片，任一分片丢失则整包报废，等于把丢包率放大数倍，单包应控制在安全尺寸内（通用 UDP 工程口径）。反例：不可丢的指令、需要会话与安全的业务不要用裸 UDP——自建可靠层等于重写半个 TCP；这类需求回到 MQTT/TCP 通道（02 册 Q15）。选型一句话：信号流用 UDP+序列号+快照，指令与事务用可靠通道，按报文语义分流而不是全局一刀切。

**Q15: 车机大量短连接后"新连接建不出来"——TIME_WAIT 累积是怎么回事？**

主动关闭连接的一方会进入 TIME_WAIT 状态并停留约 1–4 分钟（2MSL，通用 TCP 机制口径），期间占用本地四元组（源 IP+源端口+对端+端口）。车机上典型的触发形态：某些模块用"每条请求新建连接、用完即关"的模式高频访问服务器，短连接把临时端口与 TIME_WAIT 槽位消耗殆尽，症状是新建连接失败（EADDRNOTAVAIL）或大量连接堆在 TIME_WAIT。治理按优先级：**长连接复用**是根治（连接池/单一 MQTT 通道，02 册 Q15），短连接场景开启端口复用参数（`tcp_tw_reuse`，需系统层权限，且仅对出向连接有效）；同时检查是否真的需要逐条新建——HTTP 的 keep-alive 已是标配。定位：`ss -s` 与 `ss -tan state time-wait | wc -l` 看规模，按对端统计是谁在制造短连接。

**Q16: "网关 ping 不通但配好 IP 了"——二层（ARP）排查怎么做？**

IP 配置正确不代表二层可达：ARP 表里网关条目异常（STALE/FAILED/被别的设备冒用 IP）会让流量卡在"找不到网关 MAC"，表现与断网无异（通用 Linux 机制口径）。排查三板斧：`ip neigh` 看网关条目状态——FAILED 表示 ARP 请求无应答，REACHABLE 才是健康；`ip neigh flush` 清掉可疑条目后重新触发流量观察学习过程；抓 ARP 包（`tcpdump arp`）确认请求与应答是否成对、应答 MAC 是否正确。车机特有场景：网关切换/重复 IP（02 册网段冲突）都会让 ARP 学习到错误表项；热插拔上游设备后"旧网关 MAC 失效"也是同类。三层定位口诀：ARP 不通查二层（线、隔离、IP 冲突），ARP 通而 IP 不通查路由，路由通而业务不通查应用——这条口诀是 02 册五段定位法的二层前置段，车辆链路问题先过这一层再进入 IP 层取证。
