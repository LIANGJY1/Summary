# 应用网络编程与系统约束

> 学习资料（文章模式沉淀）。主线：系统省电约束（Doze/App Standby）对网络的影响、作业调度的网络约束编程、HTTPS 校验失败的分类诊断、IPv6 双栈 socket 坑、车机 eSIM 与 profile 下载、应用层连接竞速。`PowerManager.isDeviceIdleMode` 与 DownloadManager 按本地 AAOS13 源码核对，其余按官方文档与社区经验口径随题标注（2026-09 检索）。系统侧语义见 [01-network-framework.md](./01-network-framework.md)，承载层见 [02-cellular-wireless.md](./02-cellular-wireless.md)。Q 序列即结构，供 atlas 同源直读。

**Q1: [learning] Doze/App Standby 对网络做了什么？"设备息屏后长连接断了"该怎么归因？**

重 Doze（设备静止、灭屏、不用电池一段时间后进入）下应用的网络访问被整体挂起，只在系统安排的维护窗口恢复；轻 Doze（仅灭屏+电池供电触发）约束更松但同样影响后台联网；App Standby 按应用使用度限制其作业与网络（官方文档口径；`PowerManager.isDeviceIdleMode()` 与 idle 态广播本地源码核对）。归因顺序：先看时间规律——灭屏固定时长后断、维护窗口批量恢复，是 Doze 特征；再看前台服务与电池优化白名单状态；最后看厂商限制（OEM 册口径）。对策：真正需要持续联网的任务用前台服务并接受版本间收紧，数据同步类交给 WorkManager 约束调度（系统保证约束满足时的执行窗口），不要用"闹钟唤醒自己重连"硬扛 Doze。

**Q2: [learning] 同步/下载任务的网络时机为什么应该交给 WorkManager 而不是自己判断？**

WorkManager/JobScheduler 把网络作为**约束**声明（`setRequiredNetworkType(CONNECTED/UNMETERED/NOT_ROAMING)`，JobInfo 官方口径），由系统在"约束满足 + 窗口允许"时执行——系统保证执行时网络条件成立，且天然兼容 Doze 的维护窗口与批次调度。自己判断的典型错误：应用自查 `isActiveNetworkMetered()` 后自行重试，既浪费电又在 Doze 里根本拿不到执行权。车机映射：地图包/内容预取设 UNMETERED（01 册计费适配口径）交给系统排队；控车类时效任务不走作业调度（走自己的长连接通道，02 册 Q15）。注意 JobScheduler 的网络约束不感知 veth 这类非框架链路（02 册绑定机制），专网下载要自行拉起。

**Q3: [learning] 线上 HTTPS 校验失败怎么分类诊断？车机有什么特有的坑？**

按错误族分类，各有固定病因（通用 TLS 机制 + 社区排查口径）：`Trust anchor not found`——证书链不被信任（自签/私有 CA 未进信任配置，04 册 NSC 口径）；`Hostname mismatch`——证书域名与访问名不符（HTTPDNS/IP 直连未做域名校验回填）；`certificate expired / not yet valid`——服务端证书过期，或**设备时钟错误**：车机断网断电后 RTC 漂移，系统时间回到证书生效期之前，所有证书都"未生效"。车机特有结论：时钟漂移会伪装成证书故障，诊断先核对设备时间（05 册时间同步层），TLS 失败率突增与时钟异常同现时先修时钟再查证书。

**Q4: [learning] IPv6 双栈下 socket 编程有哪些坑？**

四个常见坑（通用机制 + 社区口径）：解析优先序——`getaddrinfo` 返回 v6 优先，应用拿第一个地址直连，v6 不通就卡满超时，应实现连接竞速（多地址并行试探、先到先用）而非取首项；v4-mapped 地址——双栈 socket 上的 `::ffff:x.x.x.x` 是 v4 的映射形式，日志与按前缀过滤的逻辑要识别；scope id——链路本地地址（fe80::）必须带接口 scope，跨接口直连失败；**字面量 IP 直连**——写死 v4 地址在 v6-only/CLAT 环境（02 册 Q13）必死，v6 字面量没带 scope 同样失败。车机多网卡下再加一条：同一主机名在不同网络解析结果不同，socket 创建、连接、绑定要在同一网络语义内完成（01 册 Q3）。

**Q5: [learning] 车机的 eSIM（下载式 SIM）在 Android 侧怎么工作？联网扮演什么角色？**

eSIM 的 profile 不再是写死的卡，而是经 LPA（本地档案助手）从 SM-DP+ 服务器安全下载安装：车机出厂预置一个引导 profile（仅够联网），入网后按需下载目标运营商 profile 并切换（官方 eSIM/UICC 口径；euicc API 不在本地部分同步树）。网络侧的耦合点：下载 profile 本身要外网可达（通常走公网 APN）、下载中断可重试、切换瞬间数据短暂中断（04 册 DDS 切换同理）；车厂级玩法是"全球车型一套硬件、按销售地远程切运营商 profile"，省掉插卡与库存。排查 eSIM 上不了网先分三层：引导 profile 还在不在、LPA 下载通道是否被策略拦、目标 profile 激活状态。

**Q6: [learning] 应用层连接竞速（Happy Eyeballs 思想）怎么落地？**

核心是"并行试探、先到先得、输了即弃"（RFC 8305/8304 思想，官方与社区口径）：对同一主机拿到多个候选地址（v6/v4、多 A 记录）后，不必串行逐个超时重试，而是错开小延迟（约 250 ms）并发发起连接，最先完成 TLS 握手者胜出，其余取消。落地要点：竞速在"建连+握手"阶段做，请求体只在胜者上发送（避免重复提交）；取消输家要彻底（连池不回收会泄漏）；胜者地址短期记忆可加速后续请求，但要尊重 DNS TTL 与网络切换事件（04 册 Q8）。车机弱网收益明显——IPv6 部署不均、蜂窝高丢包环境下，竞速把"串行超时叠加"变成"取最快路径"。

**Q7: [learning] 应用的网络指标监控应该埋哪些点才算体系？**

按请求生命周期分五段埋点并成对上报（与 06 册取证工具互补，监控看趋势、工具看细节）：**DNS**（解析耗时、命中缓存/HTTPDNS、失败码）、**TCP**（建连耗时、重连次数）、**TLS**（握手耗时、失败分类——Q3 的错误族）、**首字节**（TTFB，含服务端排队因素）、**完成**（总时长、字节数、结果码）；每条附带网络上下文（网络类型、计费态、是否 VPN、绑定网络 id、信号代际）与系统事件（切换、Doze 进出），没有上下文的耗时数据无法归因。聚合口径按"分位数+失败分类"而非平均值；车机附加维度：APN 通道、隧道（VPN）内外、电源状态（05 册 Q12）——同一 URL 在不同通道/电源态下的表现要能拆开比较。

**Q8: [learning] HTTP 客户端的重试与幂等，系统化设计怎么做？**

四个决策点：**能不能重试**——连接超时/连接被重置可重试；HTTP 5xx 视接口幂等性；4xx（除 408/429）重试无意义；已确认服务端处理成功的错误不重试。**怎么重试**——指数退避加随机抖动（防惊群），设单请求重试上限与全局并发重试预算，连续失败进入熔断（半开探测恢复），避免弱网下"越弱越猛重试"；**幂等保障**——写操作携带幂等键（客户端生成唯一请求 ID），服务端据此去重，使"至少一次"重试安全——没有幂等键的写请求只允许在"确认未发出"（连接从未建立）时重试；**与其他层协同**——本层管 HTTP 客户端语义，清池重连（04 册 Q8）与长连接重连纪律（02 册 Q15）各自独立，叠加重试时要防"上层重试 × 下层重连"的乘法风暴，总重试预算按端到端封顶。

**Q9: [learning] 为什么在主线程发网络请求会抛 NetworkOnMainThreadException？"release 版不抛"是真的吗？**

会抛，且与构建类型无关：libcore 的 `BlockGuardOs` 代理层在检测到主线程发起网络相关系统调用时直接抛 `NetworkOnMainThreadException`（BlockGuardOs.java 本地核对）——这是运行时默认行为，不是只在 StrictMode 开启或 debug 版才生效；StrictMode 的 penalty 是额外的告警/崩溃策略，与该异常是两套机制。系统这么做的原因：主线程网络动辄数百毫秒到秒级，直接造成掉帧与 ANR，平台用强异常把这个错误在开发期暴露。正确姿势：所有网络 I/O 进工作线程/协程 IO 调度器；框架回调类（NetworkCallback）已在系统线程，回调里只做状态分发。误读澄清：偶发"没抛"通常是走了内部已切线程的封装（如部分图片/推送 SDK），不代表主线程网络合法。

**Q10: [learning] INTERNET 与 ACCESS_NETWORK_STATE 两个权限到底各管什么？**

两个都是 normal 级（安装即授），但管的层面完全不同（官方权限文档口径，强制点在框架/netd 侧、实现不在本地部分同步树）：`INTERNET` 管"能不能发包"——没有它，系统的网络访问许可机制会隔离该应用的套接字，表现为所有请求失败，与目标网络状态无关；`ACCESS_NETWORK_STATE` 管"能不能查"——没有它不能使用 ConnectivityManager 查询网络状态、注册 NetworkCallback，但已建立的行为不受影响。典型事故形态：三方 SDK 只要求宿主声明 ACCESS_NETWORK_STATE，宿主漏声明 INTERNET，于是"SDK 初始化正常、所有请求失败"；反过来漏 NETWORK_STATE 则是"能上网但查不到状态"。发布前用 `dumpsys package` 核对合并后的权限清单（多个 manifest 合并容易漏）。

**Q11: [learning] TrafficStats 能统计什么？车机上"按业务分账"怎么实现？**

TrafficStats 提供应用侧流量读数（官方 API 口径，类不在本地部分同步树）：进程累计收发字节数（自开机累计）、按 uid 查询接口级用量，并支持**线程级标签**——`setThreadStatsTag()` 给当前线程后续 socket 打 tag、`setThreadStatsUid()` 以指定 uid 名义记账（系统服务为别的账号归因时用），与 05 册 Q7 的内核 eBPF 系统侧统计是同一数据的不同视图。车机"按业务分账"的做法：不同业务（地图、语音、下载）分进程或分 tag，使 netstats/TrafficStats 能按业务拆分用量；异常发现靠业务基线对比（某 tag 流量暴涨即告警）。限制：读数是累计值要自己做差量、统计不区分隧道内外（VPN 场景口径）、跨重启累计值清零需要落库快照。

**Q12: [learning] TLS 1.3 的 0-RTT 为什么有重放风险？车控场景怎么处理？**

TLS 1.3 允许会话恢复时在第一个飞行包里就携带应用数据（0-RTT early data）：这份数据用恢复密钥加密，但没有服务器新鲜随机数参与，**攻击者可以把录制的 0-RTT 数据原样重放**，服务器无法凭协议区分重放（RFC 8446 明示 0-RTT 不防重放，官方规范口径）。因此 0-RTT 只能承载幂等请求（GET、幂等上报），写操作与控车指令必须禁用 0-RTT 或等完整握手后再发。落地检查：各客户端库对 0-RTT 的默认行为与开关不同（Cronet/OkHttp 各自配置，官方文档口径），车控类通道在协议评审时把"禁用 0-RTT"列为条目，配合 07 册 Q2 的应用层防重放形成纵深——TLS 层防窃听、应用层防重放。

**Q13: [learning] 自研连接池的池 key 应该包含什么？少了哪一项就会跨网复用失败？**

池 key 决定"哪些连接可以互相复用"，最少要含四个维度：目标（scheme+host+port）、代理配置（有无代理是不同的连接语义）、**所在网络**（网络 id 或绑定标识——key 不含网络，网络切换后旧连接被跨网复用必然失败，这是"网络切换后清空连接池"要解决问题的另一面：key 设计对了可精准淘汰而不是整池清空）、身份（分应用代理或不同账号凭证时需隔离）。并发约束与 key 配套：单 key 设连接数上限防对单一主机打满，池总量设上限防内存失控；TLS 会话票据随连接存储，跨 key 复用会话恢复失效即退化为全握手。与框架能力的边界：只用框架网络库时这些由库内池管理，自研长连接/自建传输时 key 设计才落到自己头上——按此四维清单审一遍现有连接管理代码，是常见的存量问题入口。

**Q14: [learning] HTTP 缓存与条件请求怎么用？车机上省流量的正确姿势是什么？**

两层机制：新鲜度——服务端用 `Cache-Control: max-age` 声明可缓存时长，期内客户端直接用本地副本不发请求；条件请求——缓存过期后带 `If-None-Match`（ETag）或 `If-Modified-Since` 重验，资源未变服务端回 304 空体，省的是响应体流量（HTTP 语义，官方文档口径）。落地：OkHttp 配置 Cache 目录即自动实现条件请求与存储；静态资源（配置、包索引、素材清单）是最该缓存的对象。纪律三条：敏感数据响应带 `no-store` 防落盘；接口别滥用 no-cache（它要求每次重验而不是不缓存，语义常被误解）；URL 是缓存键——同一资源不同 URL（多一个无意义参数）是两份缓存，多端 URL 拼接要稳定。车机价值：计费网络下（配合计费网络适配与连接池治理）缓存命中就是真金白银的流量节约，静态清单类接口全走条件请求是低成本高收益的标准动作。
