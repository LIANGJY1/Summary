# 内存实践：堆预算、泄漏治理、Native 排查与线上监控

> 学习资料（文章模式沉淀）。主线：应用侧内存实践——堆预算与 GC 友好编码、内存泄漏治理、Native 与虚拟内存排查、Bitmap 优化、大内存与多进程策略、端侧推理内存管理与线上监控的落地判断。源文档：android-internals-wiki 第 23 章《内存实践》§23.1–§23.7；可本地核对的机制按 AAOS13 源码（Android 13）核对并标注版本差异（MemoryLimiter、ProfilingManager 触发器、`Debug.getRss()`、16 KiB 页要求为 Android 14–17 能力，AAOS13 无或不同），工程实践按材料口径转写、不确定处已弱化；Compose、OkHttp、KOOM 等独立发布组件按材料口径转写并标注组件版本，Play 内存门槛（2027-02 起）按材料口径转写，材料声明已与官方公告核对、本次网络不可用未重复核对。GC、lmkd、冻结与 MemoryLimiter 的机制层见 [../memory/01-内存管理与压力治理.md](../05-memory/01-内存管理与压力治理.md)；OOM 分类与 Native、FD 监控视角见 [./02-稳定性治理-资源泄漏.md](./02-稳定性治理-资源泄漏.md)。Q 序列即结构，供 atlas 同源直读。

**Q1: 只看 `Runtime.maxMemory()` 和一次堆曲线就判断 Java 堆健康，为什么不可靠？应该比较哪些信号？**

堆曲线回落只说明对象具备被回收的条件，不代表页面达到了性能目标；`maxMemory()` 只描述 Java 堆上限，不覆盖原生内存、图形内存与线程栈。判断堆压力要在同一场景下比较分配速度、峰值、页面退出后的存活对象和 GC 行为，而不是读一次数值。

前提：Android 为每个应用进程设置 Java 堆增长限制，无法在限制内完成分配会抛出 `OutOfMemoryError`。按 AAOS13 源码核对（`ActivityThread.handleBindApplication()`），声明 `largeHeap` 时调用 `VMRuntime.clearGrowthLimit()`，否则 `clampGrowthLimit()`，它只改变堆限制，不改变物理内存。曲线没有立即回落，也可能是 ART 保留可复用堆空间（HeapTrim 归还页面前的暂存），不是对象仍被引用。

可用的三组数：`Runtime.maxMemory()` 是制定缓存预算的输入之一，不能乘固定比例得出通用预算；`totalMemory() - freeMemory()` 是 ART 堆已用近似值，适合在同一构建、同一设备上观察趋势；heap dump 观察快照时刻的存活对象与引用链，allocation recording 观察目标窗口内的分配次数、大小与调用栈。后两者采集有成本，应放在可控诊断流程中。

边界：趋势信号不知道对象是否可回收，单次超阈值不能证明泄漏；单次快照也解释不了抖动。生产采样要限制频率、合并连续事件并记录场景。

**Q2: `LruCache` 的 `sizeOf` 计量和 `trimToSize` 行为有哪些边界？Android 14 之后应响应哪些 `onTrimMemory` 等级？**

`LruCache` 按 `sizeOf` 返回值累计条目大小、超限后调用 `trimToSize` 淘汰最旧条目（按 AAOS13 `LruCache.java` 核对）；`sizeOf` 没覆盖的开销（键字符串、条目对象头）会让真实占用大于 `maxBytes`，而 `trimToSize` 只收缩当前条目、不会永久修改构造时传入的最大容量，后续写入仍会重新增长。Android 14（API 34）起应聚焦 `TRIM_MEMORY_UI_HIDDEN` 与 `TRIM_MEMORY_BACKGROUND` 两个等级。

缓存内容按真实成本计量：缓存字节数组时重写 `sizeOf` 返回 `value.size`；字符串、图片引用与解析对象需要各自的计量口径。收到 `UI_HIDDEN`（界面已不可见）与 `BACKGROUND`（进入后台 LRU）后按业务策略分别收缩到不同目标字节数，比较用 `>=` 以兼容未来插入的中间等级，重复调用要幂等。

版本边界：Android 13 仍发送完整档位；按材料核对（Android 17 语境），`TRIM_MEMORY_RUNNING_*`、`TRIM_MEMORY_MODERATE`、`TRIM_MEMORY_COMPLETE` 自 API 34 起不再投递、`onLowMemory()` 不再调用并于 API 35 弃用，兼容旧系统可保留旧等级处理。

反例：不要在回调里调用 `System.gc()`——释放引用只是让对象可回收，GC 时机仍由 ART 决定；也不要释放播放、导航等仍在使用的资源，收缩过多会导致回前台重新加载。

**Q3: 大 JSON 响应、一次性读大文件把堆峰值顶上去时，按什么顺序处理？`Sequence` 一定更省内存吗？**

先让数据不一次性进内存（分页、分块、流式），再消除中间态复制，最后才考虑更换容器；`Sequence` 的收益主要来自 `take(limit)` 限制结果数量和避免完整中间列表，源数据已经完整驻留或集合很小时它还会额外创建包装对象，未必更省。

排查顺序按因果推进：输入能否分页或流式（列表接口、文件读取、日志解析）；JSON 字符串、DTO、领域模型、UI 模型的多层复制能否在边界处直接转换；日志、埋点的字符串构造是否设置长度上限并在超限后截断或落盘；数组容量是否按需传入。GC 能回收不可达对象，但不能替业务决定哪些数据不该一次性加载。

集合选择依据元素数量、键类型、访问模式、写入频率和生命周期：整数键场景用 `SparseArray` 家族可避免 `HashMap<Int, ...>` 的装箱，但要用 CPU 与内存测量验证，不要写固定的元素数量分界线。

结果验证：用分配记录同时比较分配字节数、对象数和 CPU 时间；`yield()` 分批只把分配峰值分散到多个调度片段，不减少总分配量，最终结果仍全量驻留时稳定占用不会下降。

**Q4: 什么对象适合池化？为什么把短命小对象池化反而可能增加老年代压力？**

对象池只适合同时满足三个条件的对象：创建频繁、初始化成本高、状态可完整重置。ART 对短命小对象提供低开销的线程本地分配路径，强行池化把短命对象变成长命对象——存活集被抬高、这些对象可能晋升进老年代，字段未清空时还会把上一使用者的残留数据带进下一次复用。

机制上，分代回收优先处理新对象，池中对象长期可达使 GC 无法回收；池本身还要付出同步与重置成本。普通 `data class`、生命周期复杂的对象、持有 `Context`、`View` 或回调的对象不应入池。

做法：只有分配热点造成可观测的 GC 或 CPU 压力时才评估池化，用分配记录与基准同时比较分配、GC、稳定占用与帧表现。平台自带的 `Message.obtain()` 等池有明确的获取与归还合约，业务自建池需要提供同等契约。

边界：移出高频回调（复用 `Paint`、格式化器）通常已足够；把所有临时对象改成成员会延长生命周期，可能增加长命对象数量，不是通用优化。

**Q5: 内存抖动在 Perfetto 和分配记录里长什么样？为什么一次堆转储定位不了抖动？**

抖动表现为四组现象：堆曲线锯齿（快速上升、GC 后下降）、GC 事件密集且 `HeapTaskDaemon` 活跃、慢帧集中在滑动动画等交互窗口、线程进入分配慢路径或等待 GC。堆转储只反映采集时刻的存活对象，抖动的临时对象可能已被回收，必须用时间序列上的分配记录定位。

检测按"现象确认 → 分配归因 → 修复 → 回归防护"推进：先在同一份跟踪中确认 Frame Timeline 的 missed/slow frame、GC 事件与分配速率三组信号；找到分配栈后按调用频率、单次字节数与存活时间分层——每帧调用的高频小对象累计字节可能超过低频大对象。

修复动作四类：把 `Paint`、`RectF`、格式化器移出 `onDraw()`、`onBindViewHolder()` 等高频回调（持有 View 或 Context 的对象不能无条件提升为全局成员）；合并数据转换的中间态；高频整数键换 `SparseIntArray` 等基本类型容器；大批量处理分块执行。分配记录要求 debuggable 或 profileable 构建，Perfetto 自 Android 12 起支持 ART 分配画像。

边界：GC 与慢帧时间重叠只是相关性——还要检查线程状态（`Running` 看调用栈、`Runnable` 才更支持调度竞争），并以修改后同场景对照数据确认因果；Android 13 起启动后还可能看到一次带 UID 偏移调度的后台 GC，不能归因给某个页面的临时对象。

**Q6: Compose 页面退出后 Composition 仍存活、或重组阶段反复分配，分别怎么定位与处理？**

前者沿 heap dump 的 dominator 查找生命周期更长的持有者（Fragment View、Navigation destination、长生命周期 ViewModel、未管理的协程），并让 Composition 跟随正确宿主销毁；后者用分配记录定位可组合函数体内的集合加工与高频状态更新，用 `remember`、原始类型状态 API、`derivedStateOf` 和稳定 Lazy key 治理。

存活对象持续增加的处理：Fragment 中用 `setViewCompositionStrategy(DisposeOnViewTreeLifecycleDestroyed)` 让 Composition 随 View 生命周期销毁（官方 Compose-in-Views 文档口径）；`AndroidView` 在 Lazy 容器中复用要提供非空 `onReset` 才启用复用、`onRelease` 在不再复用时释放；页面退出后仍存在一份 Composition 不一定是异常——Navigation 可能按设计保留目的地状态，实例数随进入次数持续增加或旧 Fragment View 已销毁仍支配 Composition 才指向泄漏。

短命分配的处理：排序、映射、格式化等加工用 `remember(contacts, comparator)` 缓存或移到 ViewModel；高频计数用 `mutableIntStateOf` 等原始类型状态 API 避免装箱；滚动位置这类"高频输入、低频结果变化"用 `derivedStateOf`（Compose Runtime 1.11.4 存在未 `remember` 的 forward-write 保留问题、1.12.0 修复，升级后仍应 `remember`）；Lazy 列表提供稳定唯一 key 保持列表项身份；Strong Skipping（Kotlin 2.0.20+ 默认启用）自动缓存可组合函数内 Lambda，但不稳定参数按引用相等比较，每次构造新集合或新模型仍会失去跳过机会。

边界：slot storage、`RecomposeScopeImpl`、Snapshot 状态记录是正常运行时结构，heap dump 中出现类名本身不证明泄漏；Compose Compiler 报告不提供运行时分配数量，需与分配记录配合。

**Q7: 页面销毁后 heap dump 里对象仍可达，能直接下"内存泄漏"结论吗？**

不能。对象经过观察窗口仍未回收只能记为 retained object（已保留对象）；泄漏还要求对象已越过应有的业务生命周期，且被一条不必要的强引用路径保留。两者之间隔着 GC 时机、环境持有和复现确认。

retained 不等于泄漏的原因：GC 可能尚未发生；测试框架、调试器或系统组件可能暂时持有；异步任务可能仍在合法完成阶段；厂商修改过的系统框架可能存在已知泄漏。可靠结论需要把生命周期结束事件（`onDestroy()`、`onDestroyView()`、`onCleared()`）、GC Root 强引用路径、持有者语义和重复复现放在一起。

判断 Root 路径时注意：ART 从 GC Root 出发遍历引用图，对象可达只是"能不能回收"的答案；静态字段位于"类对象 → static field → 业务对象"的路径上，把每个 static 字段称作独立 GC Root 会漏掉类对象这一层，也容易把合法进程级状态误判成泄漏——单例、进程级缓存和当前显示的 Activity 都有 Root 路径。

排查入口先分区再选工具：Java 对象持续增长看 heap dump 与 retained size；原生堆增长看 heapprofd 分配栈；线程数增长看 `/proc/<pid>/task`；图形内存看 `dumpsys meminfo` 分类——不同分区不能共用一个"泄漏"结论。

**Q8: 监听器、回调和协程为什么必须在同一生命周期内注册与注销？**

常见泄漏链是"进程级单例 → 监听器集合 → Activity/Fragment/View"：注册方、注销方与资源生命周期终点不一致时，页面对象经由外部持有者长期可达。协程同理——scope 决定协程的父子关系与取消边界，队列或作用域比被捕获对象活得久就会形成保留。

货拉拉司机端公开复盘的首页弹窗案例展示了完整证据链：Dialog 初始化时向常驻 MainActivity 的 `LifecycleRegistry` 注册生命周期观察者，`dismiss` 时没有移除；heap dump 显示 `SolverVariable[]`、`ArrayRow` 等布局对象随弹窗展示次数累积，引用链从弹窗 `mView` 经 `mObserverMap` 到 MainActivity；修复后用同一事件序列复测，观察者与旧 Dialog/View 不再累积。

对应做法：监听器用 `DefaultLifecycleObserver` 在 `onStart`/`onStop` 对称注册注销，后台继续采集时把所有者提升为 Service 而不是省略注销；延迟消息在 `onDestroyView()` 中 `removeCallbacks`；协程用 `viewLifecycleOwner.lifecycleScope` 加 `repeatOnLifecycle(STARTED)`，Fragment 在返回栈上而 View 已销毁时不会继续持有旧 View 树；Compose 的外部订阅放进 `DisposableEffect` 的 `onDispose`；`observeForever()` 不受 Lifecycle 管理，必须保存同一 observer 并 `removeObserver()`。

边界：问题不在"匿名类"这个语法形式，而在任务队列是否比被捕获对象活得更久；页面任务不要放进 `GlobalScope`；`callbackFlow` 要在 `awaitClose` 中移除 listener。

**Q9: Context 引用、JNI global reference 和带 `close()` 协议的资源分别怎么避免泄漏？**

三类资源的共同修复点是所有权：进程级对象只保存 `applicationContext`；每条 `NewGlobalRef()` 都要有明确持有者并在终点 `DeleteGlobalRef()`；`Cursor`、`ParcelFileDescriptor`、`MediaCodec`、`Image`、`Surface` 等带关闭协议的对象通过 `use` 或 try-with-resources 在业务终点显式释放，finalizer 与 Cleaner 只是延迟兜底。

Context 的选择依据用途：仓库这类与进程同寿命的对象保存 `applicationContext`；主题、窗口、权限交互和 Activity Result 仍需要 Activity Context，此时让引用跟随页面生命周期释放，而不是全部换成 Application。

JNI 引用区分三种：local reference 只在当前原生方法调用内有效，不能保存到调用结束以后；global reference 让 Java 对象跨调用持续可达，必须配对删除；weak global 用于不阻止回收的观察。Java wrapper 可能很小，背后却连接着原生分配、图形缓冲或内核对象——泄漏根常常在 Java 引用链而非原生层。

Fragment view 相关的 binding、Adapter callback、Animator、ComposeView 对象是典型短生命周期引用：Fragment 本体可留在返回栈而 View 已销毁，应在 `onDestroyView()` 释放。反例：只清空页面字段、不注销外部 listener 修不好泄漏；`mFragmentManager == null` 之类的框架内部字段不是泄漏判断契约。

**Q10: 用 heap dump 分析泄漏时 retained size、dominator 和 shortest path 怎么配合？修复点通常在哪里？**

分析顺序是：找到按业务应已销毁的对象实例 → 查看它到 GC Root 的 shortest path（最短强引用路径）→ 在路径上找第一个不应继续持有的引用 → 判断该引用属于应用、第三方库还是框架 → 修改所有权后重复同一场景。retained size 描述"该对象不可达后可随之释放的支配集合大小"，修复点往往在路径上更靠近 Root 的字段或容器，而不是 retained size 最大的节点。

dominator（支配对象）指到达某组对象的所有路径都必须经过它，工具用它计算 retained size；retained size 很大不代表当前节点是缺陷位置。LeakCanary 报告中 `~~~` 标出的是分析器认为可疑的引用边，对象仍可能存在其他到 Root 的路径，修复后必须重新抓取验证。

操作边界：heap dump 会暂停或扰动目标进程并暂时增加内存占用，性能数据不能用 dump 期间的结果代替；文件可能包含账号、页面文本与业务对象，采集、保存、上传要遵守调试数据访问控制；`am dumpheap` 适合 debuggable 进程，全量 HPROF 不应作为生产常规定时监控。

**Q11: LeakCanary 的工作流程是什么？"Library Leak" 和 leak signature 应该怎么对待？**

LeakCanary 的检测链路是：`ObjectWatcher` 用弱引用观察已越过生命周期的对象 → 等待并触发 GC 后仍存在则标记 retained → retained 达到配置条件后生成 HPROF → Shark 分析对象图并计算 leak trace → 相同可疑路径按 signature 归组。它回答的是开发期"谁保留了这个对象"，不替代生产监控。

Library Leak 表示路径匹配已知库或框架模式，不等于可以忽略：应核对依赖版本和上游修复，评估发生频率与 retained bytes；应用侧无法消除时，仍要记录受影响版本、规避方案和验收条件。signature 适合统计同类缺陷，但修复前要确认被标对象业务上确实无用、可疑引用是否由测试环境引入、同一 signature 能否稳定复现。

使用边界：依赖通常只加入 debug variant，避免把分析界面和自动 dump 带进生产包；默认观察范围覆盖 Activity、Fragment、Fragment view、ViewModel，业务自定义对象可交给 `AppWatcher.objectWatcher.watch()`；默认阈值随版本变化，以当前依赖文档为准。

生产环境替代：KOOM 提供 Java（fork/COW dump）、Native、Thread 三类监控模块，接入前固定版本并覆盖目标 Android 版本、ABI 与厂商设备；自建方案不要用周期性 `System.gc()` 加弱引用宣布泄漏——低成本趋势信号只能筛选样本，泄漏结论要由 heap/native profile 支持。

**Q12: `dumpsys meminfo` 的 Native Heap 增长可能来自哪几类映射？AAOS13 按什么规则归类？**

至少四类：分配器堆（`malloc`/`new`，含第三方 `.so` 与图片解码）、匿名 `mmap` 区域（分配器 arena 或业务映射）、`.so`/ELF 映射（代码段、可写数据、重定位页）、图形与硬件缓冲（Bitmap 像素、纹理、`dma-buf`）。AAOS13 的 `frameworks/base/core/jni/android_os_Debug.cpp` 按 VMA 名称归类：`[heap]`、`[anon:libc_malloc]`、`[anon:scudo:*]`、`[anon:GWP-ASan*]` 归 Native Heap，`.so`/`.jar`/`.apk`/`.odex`/`.dex` 归共享库与代码分类，`[stack]` 与 `[anon:stack_and_tls:*]` 归 Stack。

版本差异：材料按 Android 17 核对时，该分类逻辑位于 libmeminfo 的 `androidprocheaps.cpp`；AAOS13 树没有该文件，分类仍在 `android_os_Debug.cpp` 内完成，命名规则一致。Graphics 数值另来自 memtrack 接口，不能推断所有 `dma-buf` 都按名称归入某个分类。

读取路径也有两条：分类依赖每个 VMA 的名称，必须读逐 VMA 的 `smaps`；PSS/RSS 聚合值可读 `smaps_rollup`，它没有 VMA 名称、不能替代分类路径。量产设备上 `smaps` 可能受 UID 与 SELinux 限制，权限失败要记为观测缺口。

诊断含义：原生堆增长看 heapprofd 分配栈；`.so` 看装载范围与脏页；图形缓冲看 memtrack 与业务资源计数；匿名 `mmap` 追踪 VMA 命名与调用方。把它们合成一个"原生内存"数字会丢失定位所需的信息。

**Q13: heapprofd 的启动机制和采样结果怎么解读？"采样间隔 4096"意味着每个分配都被记录吗？**

不是。heapprofd 对小于 `sampling_interval_bytes` 的分配按字节推进做概率采样，含义是长期期望每 N 字节产生一个样本；单次分配大于或等于间隔时绕过概率路径、记录原始大小。因此不能用"采样覆盖率"换算某个对象被记录的固定次数，也不能给出跨设备固定的 CPU 开销百分比。

启动机制（材料按 Android 17 核对；A13 树不含 external/perfetto，机制口径转写；heapprofd 自 Android 10 可用为公开事实）：服务声明为 disabled，`persist.heapprofd.enable=1` 或 `traced.lazy.heapprofd=1` 时 init 才启动；目标进程内通过 Bionic 的 `MallocDispatch` 拦截 `malloc`/`free` 等入口，不依赖 `LD_PRELOAD`；user 构建只能分析满足权限规则的 debuggable 或 profileable 应用。

解读方法：分析泄漏时比较多个时间点仍存活的分配及其调用栈（火焰图按调用栈层级汇总）；分析频繁申请释放时观察累计分配量与频率。间隔越小小分配细节越多、事件量与运行开销越高，先在目标设备测开销再定复现窗口。

边界：heapprofd 与 Java HPROF 是两条独立管线——材料按 Android 17 源码核对，native 用 `__SIGRTMIN + 4`、Java 用 `__SIGRTMIN + 6`，数据源、信号与权限路径都不同；一种转储命令能运行不能推出另一种数据源可用。

**Q14: `.so` 库的内存要从哪三个维度拆开？各看什么指标、做什么动作？**

三个维度是装载成本、运行时分配、可写脏页，分别对应"少装、晚装、按需装"、统一大块分配入口并归因调用栈、减少启动期对共享映射的写入。

装载成本：`.so` 加载后代码段、只读数据与重定位页进入地址空间，只看 APK 体积判断不了运行时内存，要看 `maps`/`smaps` 中该 `.so` 的 RSS、PSS 与 Private Dirty。合并小型原生模块只在 `dlopen` 数量或重复元数据被测量证实时评估；清理未使用 ABI 主要减少安装包体积，只有文件原本会被映射时才影响运行时。

运行时分配：第三方 `.so` 分配异常时单靠 `dumpsys meminfo` 只能看到原生堆变大，用 heapprofd 或 malloc 拦截把分配归到调用栈，符号完整时可还原到函数名；对可控的原生大对象（模型缓冲、帧缓冲、解码池）建立统一分配入口，记录大小、用途、生命周期与调用位置，生产只上报聚合数据。

可写脏页：只读页可跨进程共享，一旦被当前进程写脏就变成私有成本；同一 `.so` 的 `Private Dirty` 远高于同类模块时，检查启动期大表初始化、懒加载缓存写入和重定位后的可写段。

边界：第三方 `.so` 报告至少保存 SDK 版本、Build ID、ABI、输入与并发、设备页大小；缺少 Build ID 时同名 `.so` 可能来自不同二进制，聚合调用栈没有可比性。

**Q15: `maps` 里的 `[anon:libwebview reservation]` 是什么？64 位进程为什么常见约 1 GiB 的 VSS 增量？**

这是 WebView 加载器为 provider 原生库预留的地址空间：按 AAOS13 源码核对（`WebViewLibraryLoader.reserveAddressSpaceInZygote()`），64 位进程预留 1 GiB、32 位 ARM 130 MiB、其他 32 位 190 MiB，以 `PROT_NONE` 匿名映射创建，`maps` 中名称为 `[anon:libwebview reservation]`。

机制：预留先占用一段禁止访问的虚拟地址，加载器随后把预留地址与大小交给 `android_dlopen_ext()`，在这段固定预留中加载 WebView provider 原生库和共享 RELRO 数据。未访问的 `PROT_NONE` 页不按预留大小消耗 RSS，所以它推高 VSS 而不是 RSS——64 位进程看到 1 GiB VSS 增量不能写成"WebView 已消耗 1 GiB RAM"。

应用不能 `munmap` 这段预留：加载器的全局状态没有同步清零，该地址还可能被其他映射占用，稍后任何 WebView 初始化（广告、登录、支付、SDK、系统组件都可能触发）都可能失败或破坏进程地址空间。安全策略只有两类：不使用 WebView 时接受从 Zygote 继承的预留计入 VSS；需要隔离时把 WebView 放入受控进程并测量总 PSS、启动时延与 Binder 代价。

边界：表中常量解释的是 A13/A17 固定标签源码，其他系统版本按对应标签核对；把 WebView Activity 放入子进程不会移除主进程继承的预留，收益只来自已提交页与故障边界的隔离。

**Q16: 对 ART 的 `dalvik-*` 空间做 `munmap`、长期持有 JNI 临界区指针，这些"压内存"手段为什么不成立？**

不成立。ART 的堆空间、card table、对象位图与引用关系构成一致状态，对任一 `dalvik-*` 区域 `munmap` 会破坏分配计数与 GC 根集合；`GetPrimitiveArrayCritical()` 取得的指针必须在 `ReleasePrimitiveArrayCritical()` 前尽快释放，长期持有可能延迟或限制 GC，增加分配等待与线程停顿。

HSC（Homogeneous Space Compact，同构空间压缩）的边界说明为什么"干预运行时空间"不可靠：它把主分配空间的存活对象复制到备用空间整理碎片，但受回收器与空间布局约束——材料按 Android 17 核对要求同时存在备用主空间且前台收集器为 CMS，当前收集器本身移动对象时会拒绝执行；A13 默认收集器为 CC，应用更不应假设该路径存在，也不能推出"每个应用都有两块固定 512 MiB MainSpace"。ART 按回收器、堆上限、设备配置与进程类型建立不同空间，RegionSpace、zygote space、LOS、image space 各有用途。

JNI 临界区的约束：ART 可能返回指向数组的直接指针或副本，两种路径都要求临界区尽快结束，期间不能长时间阻塞或任意调用 JNI；"禁用 moving GC 后释放备用 Space"不是安全方案。

应用侧能控制的只有对象生命周期与分配形态：取消不需要的任务与回调、给缓存设容量、释放 Bitmap 与媒体缓冲、用 heap dump 与 heapprofd 找长期持有者。

**Q17: Bitmap 记账该用 `getByteCount` 还是 `getAllocationByteCount`？解码前怎么避免按原始尺寸分配像素？**

排查占用优先记录 `getAllocationByteCount()`（底层分配区大小）；当 Bitmap 被 `inBitmap` 复用或 `reconfigure()` 调整后它可能大于 `getByteCount()`（当前像素所需最小字节数），只记后者会低估复用池里的大块分配。解码前用 `inJustDecodeBounds = true` 先取 `outWidth`/`outHeight`/`outMimeType`（返回 null、不分配像素），算出 `inSampleSize` 后第二次调用才真正分配。

预算估算式为 `bytes ≈ width × height × bytesPerPixel`：`ARGB_8888` 每像素 4 字节、`RGB_565` 2 字节、`ALPHA_8` 1 字节、`RGBA_F16` 8 字节、API 33 起 `RGBA_1010102` 4 字节；该式不含行对齐填充，只适合预算。`inSampleSize` 非 2 的幂会向下取到最近的 2 的幂，值为 n 时像素数约为 1/n²；显示阶段的缩放不能替代解码阶段的像素数控制。API 28 及以上可用 `ImageDecoder` 在 `OnHeaderDecodedListener` 中 `setTargetSampleSize()`/`setTargetSize()` 一次完成。

`inPreferredConfig` 是解码器尽量满足的请求而非结果，实际配置要读 `bitmap.config` 与 `allocationByteCount`；照片与透明图优先 `ARGB_8888`，无 alpha 的低质量缩略图可评估 `RGB_565`（接受色带风险）。

**Q18: Android 8.0 之后 Bitmap 像素存在哪？原生堆上升时怎么区分 Bitmap 分配与 JNI 泄漏？**

普通软件 Bitmap 的像素自 Android 8.0 起位于原生堆（历史：2.3.3 及更早原生、3.0–7.1 随对象在 Java 堆、8.0 起回到原生），`Config.HARDWARE` 的像素在图形缓冲区。原生堆上升时先按分配调用栈区分 Bitmap 解码与 JNI/`.so` 分配，不能直接归因于 JNI 泄漏。

记账机制（按 AAOS13 `Bitmap.java` 核对）：Java 对象经 `mNativePtr` 指向原生 Bitmap，`NativeAllocationRegistry` 用两个登记器——一个以空操作释放函数登记像素大小做分配记账，另一个登记原生对象与释放函数；`recycle()` 释放像素后运行清理任务更新 ART 记账。

两个工程结论：其一，Bitmap 对象仍受 Java 可达性影响，Activity、Adapter、缓存或回调持有 Java 对象时原生像素同样被保留——图片泄漏的根常在 Java 引用链；其二，Java heap dump 中 Bitmap 包装对象很小，图形缓冲大小不能靠 HPROF 判断，要看 `dumpsys meminfo` 的 Graphics 与原生堆分类。

`recycle()` 只用于明确失效后的提前释放，被回收后再绘制会抛 "Canvas: trying to use a recycled bitmap"；更稳的策略是让图片请求跟随页面生命周期取消、缓存有上限、不可见页面及时释放强引用。

**Q19: Hardware Bitmap 什么时候必须避开？判断依据是什么？**

四类场景必须避开：需要 `Canvas` 软件绘制（截图合成、离屏处理、分享图）、需要读取或修改像素（滤镜、取色、涂鸦）、需要进入 `inBitmap` 复用池、目标 View 可能跑在软件渲染路径或业务显式创建软件 `Canvas`。判断依据是平台行为：按 AAOS13 源码核对，`BaseCanvas` 的软件绘制路径遇到 `Config.HARDWARE` 抛出 "Software rendering doesn't support hardware bitmaps"，`BitmapFactory.Options.validate()` 拒绝硬件 Bitmap 作为 `inBitmap`（源码注释明确 "Bitmaps with Config.HARDWARE are always immutable"），因此它也不能与 `inMutable = true` 同时要求。

适用场景是只展示、不修改、由硬件加速管线绘制的图片，例如详情页大图与列表封面。`ImageDecoder` 默认"通常"创建 `HARDWARE`——保留"通常"是因为 `ALLOCATOR_DEFAULT` 可能为小图或 mutable 等条件切换到软件分配。

图片库策略按用途区分：展示型优先允许 Hardware，编辑型强制软件；列表页按设备内存、圆角或变换需求与占位图策略决定，全局开关不能只依据"硬件更省内存"。

边界："像素不在 Java 或原生堆"不等于没有成本——Java 包装对象与原生元数据仍存在，图形缓冲计入 Graphics/memtrack 统计。

**Q20: 统一解码入口的大图监控应该记录什么？为什么验收要比较峰值而不是平均值？**

统一入口记录：原图尺寸、目标 View 尺寸、解码后尺寸、像素配置、`allocationByteCount`、页面名与调用栈摘要。这组字段直接回答两个问题——是否解码了远大于显示尺寸的图片，是否有页面退出后仍保留大图。验收必须覆盖解码与变换峰值：OOM 由瞬时峰值触发，只比较操作结束后的平均值会漏掉它。

货拉拉公开复盘的图片发送案例是典型：发送前后原生内存突增，根因是旋转逻辑先完整解码原图、再做缩放与方向变换，峰值阶段同时持有原图像素与中间结果；正确做法是在第一次像素分配之前限制尺寸——先读边界与 EXIF 方向，按上传或展示目标计算采样尺寸，再解码、旋转或裁剪。

阈值按屏幕、业务类型、同时在内存中的图片数量和设备可用内存分组制定，字节与维度比都做成可配置策略并通过目标设备峰值与滚动测试确定——同一张图在单图详情页可接受，进入多列列表可能让并发像素预算失控。

隐私与边界：只上报超过阈值的记录，用不含用户数据的类别标识，不上传真实 URL、文件名或图片内容；页面退出后同一场景的大图仍可达时按引用链方法处理，对象已释放但原生峰值过高时查解码尺寸、缓存上限与并发。

**Q21: 把模块拆到独立进程能减少应用内存吗？为什么 RSS 不能相加？**

拆进程改变内存归属与故障边界，但每个进程都有独立的 ART 运行时、类加载器、线程、Binder 线程池与业务缓存，应用总 PSS 往往上升；RSS 在每个进程中完整计入共享页，直接相加会重复计算，评估总成本必须用 PSS（共享页按参与进程数分摊）。

共享与私有的分界：`.so`、`.dex` 与框架的只读代码页可共享；被写脏的页、Java 对象、线程栈和多数原生分配不共享。适合拆分的模块特征：峰值高且生命周期清楚（任务完成后可转为缓存进程）、需要隔离崩溃（原生或 WebView 异常不拖垮主进程）、跨进程输入输出能表示为句柄或小对象、启动开销可测量、被回收后可恢复。不适合的：高频小调用、强共享内存状态、需要大量 Java 对象跨进程传输的模块——内存问题会换成 Binder、序列化与一致性问题。

结果判断：主进程单项下降不能证明方案节省了整机内存，要把所有进程 PSS 相加，并检查子进程反复冷启动、Binder 载荷与 LMKD 回收后的恢复体验。

边界：不应把主动终止子进程当常规资源释放接口——进程寿命由系统按组件活跃度决定，任务完成时应停止 Service、解除绑定并保存结果；大数据载荷用 `SharedMemory`、文件描述符或流式接口传递并明确关闭时机。

**Q22: `android:largeHeap` 的作用范围和设备档位是什么关系？开启前要确认什么？**

`largeHeap` 把应用 Java 堆增长限制放宽到设备的大堆档（按 AAOS13 源码核对，`ActivityThread` 检测 `FLAG_LARGE_HEAP` 后调用 `clearGrowthLimit()`），作用于应用创建的所有进程；设备的大堆档（`largeMemoryClass`）可能与普通档相同，开启不保证增加固定容量。档位读取：`getMemoryClass()` 读 `dalvik.vm.heapgrowthlimit`，`getLargeMemoryClass()` 读 `dalvik.vm.heapsize`。

官方边界（按材料与官方文档口径）：同一进程采用第一个载入应用的设置；共享 UID 并共用进程的多个应用必须保持设置一致，多进程应用的统计不能只看单个组件。

开启条件三者同时满足：峰值来自短时 Java 对象且缓存、Bitmap、流式处理已经优化（主要增长来自原生、图形或线程栈时无效）；高内存操作有明确起止（大图编辑、离线地图、批量导入）；应用能按设备状态降低资源规格。代价：存活集变大 GC 成本增加、PSS 上升后更易被系统回收、泄漏从"快速 OOM"变成"运行更久后被杀"。

验收：同设备同输入比较 Java 堆存活量、分配速率、GC、PSS 与退出原因；OOM 消失只说明没有在原上限处失败，系统内存压力仍可能上升。

**Q23: 32 位应用迁移 64 位要检查什么？迁移能解决所有内存问题吗？**

迁移扩大单进程可用虚拟地址范围，缓解 32 位进程因连续空洞不足导致的 `mmap`、动态链接或 `pthread_create` 失败；但它不增加设备物理内存，也不改变堆上限与系统限制，指针变大还可能增加部分原生对象与容器体积。检查按五步做：

1. 安装包：用 APK Analyzer 核对 ABI，`armeabi-v7a` 对应 `arm64-v8a`、`x86` 对应 `x86_64`，每个受支持的 64 位环境都不能缺少 64 位 `.so`；
2. 运行时：用 `Process.is64Bit()` 确认当前进程位数——`Build.SUPPORTED_ABIS` 只表示设备支持的 ABI 优先顺序，不能证明进程已以 64 位运行；
3. 代码：排查指针截断（JNI 不把指针存入 `int`/`jint`，用 `uintptr_t`/`intptr_t`）、结构体布局、序列化格式、汇编与编译参数，覆盖第三方 SDK、插件、热修复与符号文件；
4. 性能：同一设备对比启动耗时、PSS、原生堆、图形内存、线程数、缺页与崩溃率；
5. 设备：至少覆盖 64 位进程、仍受支持的 32 位设备与仅支持 64 位的环境——最后者能直接暴露遗漏的 32 位专用依赖。

边界：二进制大小、冷启动 I/O 与指令缓存命中率也可能变化；迁移后仍要处理原生堆增长与泄漏，虚拟地址不再是瓶颈不代表物理内存充裕。

**Q24: 端侧推理的内存为什么必须分阶段采样？一次"加载完成"的快照会漏掉什么？**

模型权重、KV 缓存、临时张量、编译与后端资源、输入输出、应用基线六类内存在不同阶段形成峰值：加载完成只反映权重文件映射，prefill 的临时工作区、delegate 初始化的编译产物、稳定 decode 的 KV 增长和取消后的回落都不在一张快照里；模型能加载也不等于长上下文与并发会话稳定。

至少采样的阶段：未加载模型、模型文件打开、运行时与 delegate 初始化完成、首次运行、prefill 峰值、稳定 decode、取消生成、关闭会话、关闭模型。逐阶段对比后才能回答峰值来自哪一类，再决定限制上下文、关闭闲置会话、换量化变体或更换后端。

权重与 KV 的口径：权重理论下限为 `P × b ÷ 8`，但不含量化 scale、zero-point、词表、对齐填充与运行时重排副本，"4-bit 文件 1 GiB 所以运行内存 1 GiB"不成立；KV 缓存按层数、KV 头数、头维度、缓存 token 数与元素类型计算，随输入长度和并发增长。

边界：量化选择还要看算子是否被后端支持、是否触发 CPU 回退——强量化模型回退 CPU 后内存与时延可能更差；MediaPipe LLM Inference 已进入维护模式，新项目按材料评估 LiteRT-LM。

**Q25: 权重用只读 `mmap` 加载后 RSS 远小于文件大小，这说明什么？可以一直依赖吗？**

说明多数文件页尚未缺页或已被内核回收——VSS 先增加、RSS/PSS 随缺页和回收变化，文件页可被内核回收也可能经页缓存与其他进程共享。但这不是零成本承诺：delegate 可能为了对齐、布局转换、量化解码或设备私有格式再分配一份缓冲区，长上下文与并发会话会把缺页、副本与工作区叠加成第二次峰值。

分别观察五组增量：模型文件映射的 VSS 与 RSS/PSS、native heap 与匿名映射、图形与 memtrack 能看到的设备缓冲、delegate 初始化前后、第一次推理前后。把文件大小、native heap 与 GPU 缓冲直接相加可能重复计算同一物理页，跨域比较优先用进程 PSS 并保留各分类作归因线索。

边界：能否共享取决于是否发生解压、反量化、重排到私有缓冲，以及驱动是否为每个会话复制设备侧权重；16 KiB 页设备会改变映射与分配器的页面粒度（自研加载器不写死 4096 字节对齐，文件 `mmap()` offset 遵守运行时页大小）。

做法：为每个模型变体建立设备档案记录这些增量；模型加载、delegate 初始化与首次编译不放在主线程，Perfetto 中区分计算 slice、缺页、大块 `memcpy` 与后端返回码。

**Q26: 用 `availMem` 或"模型文件 × 1.5"判断设备能不能跑模型为什么不成立？应该用什么代替？**

`ActivityManager.MemoryInfo` 的三个字段都不是应用额度：`availMem` 是系统层面可用内存估算（源码注释明确不能当绝对值）、`threshold` 是系统开始清理后台进程的参考阈值、`lowMemory` 是全设备当前状态；固定公式忽略了应用基线、KV 缓存、后端副本、进程优先级和并发工作集。可用预算只能来自目标设备上每个模型变体的实测档案。

档案至少包含：模型与量化格式的不可变版本；运行时、delegate 与驱动版本；ABI、Android 版本、页大小、SoC 与 RAM 档位；后端与回退结果；上下文上限、并发会话数与输入模态；各阶段 PSS、RSS、`VmHWM`、native heap 与可见图形数据；冷/热加载、取消、释放与重载结果；失败现场。

降级项必须独立配置而不是只有"完整模型"和"拒绝运行"两档：模型（更小或更强量化）、上下文（token 总上限）、会话（并发与闲置关闭）、模态（输入尺寸）、后端（GPU/CPU 回退）、预热（后台预载）各自可选并分别验证，因为每个组合的内存与时延都不同。

边界：Memory Advice API 已结束 beta 并被官方弃用，新推理管线不应只依赖它；同一 RAM 档的两台设备也可能因驱动是否复制权重、NPU 编译策略不同而结果不同。普通应用没有公共 API 为自己设置 `memory.high` 或 OOM-adj，不应绕过系统策略。

**Q27: 切换模型时"先加载新的再释放旧的"有什么代价？推理资源的正确释放顺序是什么？**

该策略降低切换失败风险，却制造双模型驻留峰值；内存紧张设备应改为：保存可重建的会话文本与业务状态 → 停止旧会话 → 关闭旧模型并记录释放后的资源数量与内存快照 → 加载目标变体 → 失败时进入更小变体或云端路径。产品若要求无缝切换，双模型窗口必须作为独立场景计入预算。

释放顺序遵守运行时所有权（一个资源管理器统一负责模型、delegate、会话与缓冲）：停止接收新请求 → 请求取消正在生成的任务 → 等待回调和后端工作结束 → 关闭会话释放 KV 缓存 → 关闭 I/O、图像、音频与共享缓冲 → 关闭模型、delegate 与运行时 → 清理专属分词器和业务缓存。不能在异步回调仍可能访问对象时直接关闭 native handle；实现 `AutoCloseable` 时用 try-with-resources 或 `use`。

回落判断：分配器、驱动缓存与文件页可能让数值延迟回落，"旧资源已关闭"不能只由单个 RSS 数字判断，要结合资源对象计数与多轮加载/关闭直到进入稳定区间。

会话策略：能快速从文本重建时，关闭会话比长期保存 KV 稳妥；状态导出/导入是引擎能力，会话状态可能含用户敏感内容，持久化需要加密、失效与删除规则；预热模型与预热会话分开配置。

**Q28: 推理各阶段采样应读哪些字段？`VmRSS` 与 `VmHWM` 能互相替代吗？**

不能。`VmRSS` 是当前驻留值，`VmHWM` 是进程生命周期内 RSS 的最高水位且不能重置——推理前后各读一次 RSS 取差值无法证明区间峰值。低频采样读取 `/proc/self/status` 的 `VmSize`、`VmRSS`、`VmHWM`、`RssAnon`、`RssFile`、`RssShmem`、`VmSwap` 与 `Threads`（内存字段单位 KiB）。

差值陷阱与对策：峰值可能出现在两次采样之间；要比较单阶段峰值时，在独立测试进程中运行场景，或用足够频率的 RSS/PSS 采样配合 Perfetto 时间线。`VmHWM` 适合回答"这一轮最高到过多少"，不能回答"此刻多少"。

版本边界：AAOS13 没有 `Debug.getRss()`（API 35 起）；材料按 Android 17 核对其 JNI 实现会在 memtrack 可用时并入 graphics/GL/other 三类未计入 `/proc` 映射的图形内存——API 35 前后的 RSS 来源要分别标记，不能拼进同一条比较基线。GPU 侧 `Debug.getGpuTotalUsageKb()` 等是 `@hide` 系统接口，普通应用用 `dumpsys meminfo` 的 Graphics/GL/DMA 分类与 Perfetto 计数器。

频率：在阶段边界或异常触发时采样，不在每生成一个 token 时调用；同一场景保留工具版本与 build fingerprint，避免横向比较厂商字段。

**Q29: 线上内存监控的 PSS、RSS、Java Heap 与 native allocator 指标各能回答什么？`getProcessMemoryInfo()` 有什么限制？**

四个指标各管一层：PSS 回答按共享者分摊后的系统内存占用（`ActivityManager.getProcessMemoryInfo()`、`Debug.getPss()`）；RSS 回答当前驻留页总量；`Runtime.totalMemory() - freeMemory()` 与 `maxMemory()` 回答 ART 堆近似用量与上限；`Debug.getNativeHeapAllocatedSize()` 回答分配器已分配字节（按 AAOS13 源码核对，实现直接返回 `mallinfo().uordblks`）。任何一项都不能代表进程全部内存——`getNativeHeapAllocatedSize()` 不含 `mmap`、线程栈、共享库与 Graphics。

限制：Android 10（API 29）起普通应用经 `getProcessMemoryInfo()` 只能取得调用方 UID 下进程的信息，其他 PID 条目为零；平台限制采样频率，调用过密可能收到上一次结果——采样请求时间不等于底层数据更新时间，不能靠高频调用制造高分辨率曲线。

单位与来源：`Debug.MemoryInfo` 的 PSS 字段是 kB，`Runtime` 与 native allocator 返回字节，入库前统一；`pss`/`rss` 为空表示本次未取得有效值，不能按零上报。`Debug.getMemoryInfo()` 直接读当前进程但可能拿不到 graphics 等受保护分配，需要完整分类时用 `getProcessMemoryInfo()`。

事件包还要带：应用版本、Android 版本、ABI、RAM 档、前后台状态、页面类别、采样原因、策略版本与每个指标的来源——RSS 来源（API 35 前后实现不同）也要标记。

**Q30: 线上内存告警为什么不能用跨设备固定百分比？告警要组合哪些信号才有排查价值？**

Java 堆上限、设备 RAM、页面资源、ABI、WebView 版本与厂商内存策略都会改变正常分布，一个固定比例同时产生漏报与误报。阈值应来自按版本（灰度对比上一稳定版）、设备（RAM 档、low-RAM 标记、ABI）、进程（主进程、任务进程、推送进程、WebView 宿主）、场景（冷启动稳定点、页面停留、任务峰值、退出回落）和状态（前台、后台、缓存）分组的同类样本。

统计纪律：比较基线保留完整分布、样本数与缺失率（应采样但未得到有效数据的占比）——只比较成功样本会把限流或采集失败误判成改善；均值掩盖长尾，用 P95/P99 描述慢请求，样本构成变化时不能直接发布判断。

告警按"现象 → 组合信号 → 方向"组织：Java Heap 接近上限看使用比例加分配回收趋势加退出回落；RSS/PSS 上涨而 Java 堆平稳看 native allocator、Graphics、线程数与 FD；资源释放后不回落看同场景多次采样与生命周期边界。方向只用于选择下一项证据，不能直接当根因。

事件按用途拆分命名：基线回归、Java 堆压力、原生或映射增长、系统内存压力、采集请求、采集结果、历史退出记录——不同事件进入版本比较、资源降级、重启后取证或敏感文件治理等不同流程。

**Q31: Android 15/17 的 `ProfilingManager` 与 OOM/anomaly 触发器是什么？Android 13 应用能用吗？产物怎么治理？**

`ProfilingManager` 自 Android 15（API 35）加入平台，可请求 Java heap dump、heap profile、stack sampling 与 system trace；Android 17（API 37）新增 `TRIGGER_TYPE_OOM`（抛出 `OutOfMemoryError` 时采集 Java heap dump，要求自定义 `UncaughtExceptionHandler` 在处理结束后转交默认处理器，否则触发器不生效）与 `TRIGGER_TYPE_ANOMALY`（系统识别异常资源行为时按异常类型返回产物，MemoryLimiter 命中时可取 heap dump）。Android 13 平台没有这套 API（本地核对 AAOS13 无 `ProfilingManager`），线上只能使用自建低频信号与受控工具。

交付与限流机制：结果只经 `registerForAllProfilingResults()` 注册的全局监听器交付，应用应在稳定进程入口尽早注册，采集时进程已退出的会在下次启动注册后交付；`unregisterForAllProfilingResults()` 只停止交付、不删除触发器，还要 `removeProfilingTriggersByType()` 或 `clearProfilingTriggers()`；系统 rate limiter 与随机采样约束下不保证每次事件都有产物，`setRateLimitingPeriodHours()` 与系统限流叠加。

产物治理：heap dump 含对象字符串、请求响应、缓存键与文件路径，采集资格（版本、场景、磁盘、配额）、最小化、加密传输、访问审计、保留期限与远程关闭要作为同一工程能力设计；收到路径后不在回调线程同步上传，先核对文件、策略与设备条件。

A13 可用的系统侧证据：`ApplicationExitInfo`（API 30 起）读退出原因与最近 PSS/RSS 采样，`Debug.dumpHprofData()` 与 `setWatchHeapLimit()` 用于 debuggable/userdebug 受控诊断——后者不是生产监控接口。

**Q32: 同样是"内存上涨"，弹窗泄漏、相机帧分配与图片解码三条曲线为什么结论完全不同？**

上涨只是现象，证据决定结论：首页弹窗案例指向生命周期持有（Lifecycle observer 未注销、旧 Dialog 与布局对象随展示次数累积、引用链到达常驻 Activity）；相机帧录制案例指向高频短命数组分配（`byte[]` 占比高、频繁 GC，创建释放与复用不足）；图片发送案例指向解码峰值（第一次像素分配前没有尺寸约束，旋转变换同时持有原图与中间结果）。治理动作分别是注销观察者、移出高频路径并复用缓冲、解码前限尺寸——三者不可互换。

一条完整案例的证据链模板：用户场景 → 可重复动作 → 按同一统计定义采集的前后快照 → 引用链或分配栈 → 资源所有权缺陷 → 最小修改 → 同场景复测 → 线上结果。只有快照相关性时结论仍是待验证假设；被排除的假设也要记录，避免下次面对相同曲线重新猜测。

验收分层：目标对象数量回到预期、同一 leak signature 不再出现、同轮次 retained size 或增长斜率下降、页面行为与缓存命中未被破坏、OOM/LMK 指标按版本与设备分层改善。

反例：只上传 OOM stack trace——内存耗尽后异常可能出现在任意后续分配点，stack trace 常常不是增长源；单一曲线或模块名都不能直接映射结论。
