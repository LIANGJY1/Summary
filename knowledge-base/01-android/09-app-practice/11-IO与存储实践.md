# I/O 与存储实践：文件、数据库、缓存、媒体与网络

> 学习资料（文章模式沉淀）。主线：应用侧 I/O 实践——文件与键值存储、SQLite/Room 与序列化、缓存与离线优先、MediaStore 与 Photo Picker、移动网络连接与容灾、HTTP/2/HTTP/3 与 gRPC/ECH 的选型和排查方法。源文档：android-internals-wiki 第 24 章《I/O 与网络优化》§24.1–§24.6；可本地核对的机制按 AAOS13 源码（Android 13）核对并标注版本差异（Photo Picker 扩展能力、DocumentsContract 回收站与同步状态、`HttpEngine`、ECH 为 Android 14–17 能力，AAOS13 无或不同），工程实践按材料口径转写、不确定处已弱化；SQLite WAL 默认参数（连接池 4、WAL 同步 NORMAL、自动 checkpoint 100 页）已按 AAOS13 `config.xml` 核对，OkHttp 5.4.0、Room 3、MMKV 等独立发布组件按材料口径转写并标注组件版本。存储架构、FUSE 与 SharedPreferences/DataStore 的机制层见 [../storage/01-存储与IO.md](../04-storage/01-存储与IO.md)；缓存与内存预算的应用侧实践见 [./10-内存实践.md](./10-内存实践.md)。Q 序列即结构，供 atlas 同源直读。

**Q1: StrictMode 在开发期检测主线程 I/O 的能力边界是什么？I/O 切到工作线程后就安全了吗？**

不安全。StrictMode 的 `detectDiskReads()`/`detectDiskWrites()` 只能发现调用线程上的磁盘违规（按 AAOS13 源码核对，`detectAll()` 会启用磁盘读写与网络检测）；它检测不到工作线程的 I/O 占满存储队列、持有主线程需要的锁、或主线程等待结果这类间接影响。策略只报告受该线程策略约束的调用。

框架会在明确知道线程可能等待磁盘的位置主动触发检测：按 AAOS13 源码核对，`SharedPreferencesImpl.awaitLoadedLocked()` 在等待 XML 加载前调用 `BlockGuard.getThreadPolicy().onReadFromDisk()`，因此主线程首次读 SP 会被 StrictMode 点名。

配置上，调试构建用 `penaltyLog()` 记录违规而不结束进程，适合开发期持续启用；不要把改变用户流程的惩罚（如崩溃）带入发布构建，生产环境只做采样记录。

补充观测：首帧、点击与页面切换要结合 Perfetto 的线程状态与自定义 trace 区间判断——I/O 等待不一定表现为 CPU 热点，线程可能停在可中断睡眠或不可中断睡眠。

**Q2: MMKV 用 mmap 追加写，为什么"写入返回即已持久化、延迟稳定"不成立？**

mmap 把小写入变成映射页修改，减少传统 `read()`/`write()` 路径的部分复制，但首次访问仍可能触发缺页、脏页仍要回写存储、初始化仍要校验并解析文件；API 返回与数据到达持久化介质不是同一件事。需要断电或进程异常下的明确持久性时，应核对所用 MMKV 版本的同步接口、返回值与恢复策略，并做故障注入验证。

设计要点（Tencent MMKV 设计文档口径）：值使用 Protocol Buffers 二进制编码，更新采用追加写、同名键以末次值为准，空间不足时整理有效数据或扩容，并用 CRC 检测文件损坏。

适合的位置：高频读取的开关、实验参数、轻量运行态标记（读路径短，避免 SP XML 首次解析拖住启动）；对启动延迟敏感的小配置（控制键数量与文件大小并实测首次缺页）；显式启用多进程模式的小型共享状态。

不适合的位置：大 JSON、图片、二进制包（文件膨胀与内存映射增加页缓存与地址空间压力）；需要范围查询、排序、分页的数据；要求事务与失败恢复语义的交易数据。与 DataStore 的选择基于访问行为和一致性要求，并用本应用的冷启动、尾延迟、内存与异常恢复测试决定，不引用库作者的一次基准结果。

**Q3: `AtomicFile` 保护什么、不保护什么？多个写者并发写同一文件怎么办？**

`AtomicFile` 保证"读者只会看到旧版本或完整的新版本"：按 AAOS13 源码核对，`startWrite()` 把新内容写进 `.new` 文件，`finishWrite()` 对流执行 `FileUtils.sync()` 后用 rename 原子替换目标文件，`failWrite()` 删除半成品；它不提供文件锁，源码注释要求调用方为所有并发访问建立互斥条件。

单进程做法：把写入收敛到一个 `Mutex` 互斥边界内，工作线程执行 I/O；若读取可能与写入协议并发，读取也走同一互斥边界。多个实例或多个进程仍可能互相覆盖——把写入集中到单进程 Service 或 ContentProvider，或改用具备跨进程事务语义的数据库。

持久性边界：`finishWrite()` 返回 `void`，内部同步或 rename 失败主要写日志，不能向业务提供丰富的失败信息；支付、订单等需要确认提交的状态不能只依赖这类封装，应在工作线程等待明确结果并把失败反馈给上层。

配套规则：普通 `write()` 返回时数据通常只到了内核页缓存；可重建的日志与埋点可合并写入与同步以减少频繁 `fsync()`，不可丢状态必须等待明确提交结果——合并同步的前提是业务接受对应时间窗的数据丢失。

**Q4: `content://` URI 和文件路径的本质区别是什么？跨重启继续访问选中的文档要做什么？**

URI 是 Provider 授权的访问入口而非路径：`DocumentsContract.Document.COLUMN_DOCUMENT_ID` 由 Provider 自行定义，客户端只能把它当不透明标识交回同一个 `authority`——不能从 URI 字符串截取存储路径、用显示名拼子文档 URI、假定重命名后 URI 不变，也不能用 `File(uri.path)` 打开 `content://` URI。

授权语义：`ACTION_OPEN_DOCUMENT` 授权单个文档、`ACTION_CREATE_DOCUMENT` 指定新文档位置、`ACTION_OPEN_DOCUMENT_TREE` 授权目录树；URI grant 是系统赋予调用应用的读写能力，不等同传统文件权限。从 Android 11 起，树授权不能选择内部存储卷根、Download 根、`Android/data` 与 `Android/obb`——选择器界面展示某位置与应用能否取得授权是两件事。

跨重启使用：选择器通过结果 Intent 临时授权，需在设备重启后或交给 WorkManager 继续访问时，在收到结果后调用 `takePersistableUriPermission()` 持久化结果 Intent 中已有的读写标志，不额外申请未授予的权限；该调用只管理授权生命周期，不加快读取，也不应放进循环。

失效处理：文档被删除、移动或 Provider 撤销授权后持久化记录仍可能失效——任务开始前检查访问结果、处理 `SecurityException` 与 `FileNotFoundException`、提供重新选择入口；长期不用的授权用 `releasePersistableUriPermission()` 释放。

**Q5: `DocumentFile.listFiles()` 之后的属性读取为什么是 N+1？大目录应该怎么查？**

`listFiles()` 本身只发起一次子项查询（只读取 `COLUMN_DOCUMENT_ID`，Java 层没有逐项调用 `query()`），但 `getName()`、`getType()`、`lastModified()`、`length()`、`exists()` 每次调用各自查询一两个字段——N 个子项就是一次列表查询加 N 次属性查询。少量低频交互可接受，文件管理器或大目录扫描应在一次子项查询中取齐全部所需字段。

一次投影查询的做法：用 `DocumentsContract.buildChildDocumentsUriUsingTree()` 构造子项集合 URI，`resolver.query()` 传入投影数组（ID、显示名、MIME 类型、大小、修改时间、`COLUMN_FLAGS`）与 `CancellationSignal`，在工作线程遍历并用 `use` 关闭 Cursor；查询授权根目录时父 ID 取 `DocumentsContract.getTreeDocumentId(treeUri)`。

相关陷阱：`findFile(name)` 先 `listFiles()` 再逐项 `getName()`，循环查找多个名称会反复枚举——批量查找先构建一次名称索引并定义重复名规则（Provider 不保证显示名唯一）；`canWrite()` 在文档可删除或目录可创建子项时也可能返回 `true`，判断能否改写内容要查 `COLUMN_FLAGS` 的 `FLAG_SUPPORTS_WRITE`，创建、删除、重命名等各有标志位。

分页边界：`QUERY_ARG_LIMIT`/`QUERY_ARG_OFFSET` 是可选能力，用 Cursor extras 的 `EXTRA_HONORED_ARGS` 确认已接受；Provider 不支持分页时，客户端分批遍历只降低自身峰值内存，无法减少 Provider 生成整个结果集的成本。

**Q6: `ContentResolver` 打开大文件时 Binder 传了什么？管道描述符和普通文件描述符有什么行为差异？**

`openFileDescriptor()` 经 Binder 调用 Provider 的 `openFile()`，传输 URI、打开模式、授权信息与文件描述符（控制阶段）；对普通文件，随后的内容读写直接通过文件描述符进行，不会逐块放进 Binder 事务（数据传输阶段）。大文件复制缓慢时应分段测量——打开前的 Provider 启动、鉴权与按需下载、打开到首字节、持续吞吐、刷新关闭与远端提交——不能只归因于 Binder 缓冲区。

管道与套接字对的差异：`"r"`/`"w"` 模式可能得到 Provider 边生成边发送的管道描述符，只能顺序访问、不能随意 seek；`"rw"` 表示需要可读写可定位，Provider 仍可拒绝；是否截断原内容由 Provider 决定。代码不能假定所有 URI 都支持 `FileChannel.position()`、`size()`、`map()` 或 `transferTo()`。

复制优先级：同一 Provider 内源文档声明 `FLAG_SUPPORTS_COPY` 时优先用 `DocumentsContract.copyDocument()`，Provider 可能在存储或云服务端完成复制；跨 Provider 或未声明复制能力时才由应用流式传输，循环中主动检查取消状态（描述符返回后 `CancellationSignal` 不会自动中断普通流读取）。复制失败可能留下部分目标内容——两个 Provider 之间没有原子性保证，应用要记录任务状态并清理未完成目标。

`transferTo()` 只在两个描述符确认对应本机可随机访问的普通文件时基准测试；它不适用管道、转码流与云 Provider，也不能直接套用于带起始偏移的 `AssetFileDescriptor`。

**Q7: WAL 给 SQLite 带来什么并发能力？`synchronous=NORMAL` 改变了什么持久性边界？**

WAL 把新页追加到 `-wal` 文件：读事务记录自己的 end mark，用主库与该位置之前的 WAL frame 组成一致快照，写者可以在读者读旧快照时继续追加——提供读写并发；但两种日志模式都只有一个活跃写者，WAL 不提供并行写入。Android 官方性能文档建议除使用 `ATTACH DATABASE` 的场景外启用 WAL，并在 WAL 下使用 `synchronous=NORMAL`。

持久性边界：NORMAL 下应用进程崩溃后事务仍可恢复，但设备断电或内核崩溃可能回滚已经返回成功的事务——订单、支付或跨库依赖不能只按吞吐量选择同步级别。

生效参数（按 AAOS13 `config.xml` 核对，与材料 Android 17 口径一致）：`db_wal_sync_mode` 为 NORMAL、`db_wal_autocheckpoint` 为 100 页、WAL 连接池 `db_connection_pool_size` 为 4；这些是 AOSP 资源默认值，厂商、系统属性与应用显式配置都可覆盖。100 页不能按 4 KiB 内存页换算，应查该数据库的 `PRAGMA page_size`。

应用侧检查项：在目标设备读实际生效的日志/同步模式，不把 Builder 选项当运行结果；使用 `ATTACH DATABASE` 时重新评估 WAL；不在主线程首次打开数据库（模式校验、Migration、预置库复制都可能发生）。

**Q8: `-wal` 文件持续增长是什么原因？调小自动 checkpoint 阈值为什么没用？**

checkpoint 把已提交的 WAL frame 写回主库，`PASSIVE` checkpoint 只能推进到活跃读事务允许的位置——持有较老 end mark 的长读事务会让它提前停止，而后续写入仍继续追加，`-wal` 因此持续增长。调小自动 checkpoint 阈值不能结束这些读事务，正确方向是找到未结束的读事务和生命周期过长的 Cursor。

观测方法：读取 `PRAGMA journal_mode`、`PRAGMA page_size`、`PRAGMA wal_autocheckpoint`；执行 `PRAGMA wal_checkpoint(PASSIVE)` 后看返回的 busy 状态、WAL frame 数与已写回主库的 frame 数——后两者长期拉开时，关联长读事务、写入批次与 checkpoint 时机。

锁语义：普通 checkpoint 使用 WAL 共享内存中的写锁、checkpoint 锁与读标记协调，不能概括为"先取得主数据库 EXCLUSIVE 锁"；切换日志模式、恢复与带截断语义的操作另有锁边界。

配套实践：大事务后观察 `-wal` 增长、读事务持续时间与 checkpoint 耗时；连接池等待出现时先查长事务、慢查询与未关闭资源，再考虑调整池大小——增加连接数不改变写串行化。

**Q9: 列表查询慢时 CursorWindow 扮演什么角色？单行过宽和 `TransactionTooLargeException` 是一回事吗？**

不是一回事。CursorWindow 分批承载查询结果，游标移动到现有窗口以外的行会触发重新填充——framework 驱动下大结果集表现为多轮 SQL 步进与窗口重填；投影列越多、结果中大字符串或 BLOB 越多，窗口越容易装满。单行放不进窗口时减少总行数没有帮助，要缩小该行与投影列集合。而 `TransactionTooLargeException` 来自 Binder 事务缓冲：跨进程返回 Cursor 时，`CursorWindow::writeToParcel()` 为 ashmem 窗口传递文件描述符副本、无 ashmem 时按已用容量写 Parcel，三者是不同失败，不能都归因"2 MB Binder 限制"。

按 AAOS13 `config.xml` 核对，窗口默认 `config_cursorWindowSize` 为 2048（KiB）；OEM 覆盖与显式构造可改变容量。滚动时不断跨边界应在 trace 中统计 refill 次数，优先减少结果宽度与改进分页，而不是盲目放大窗口。

查询四条规则：明确列出投影、不传 `null` 读全部列；筛选条件用 `?` 占位符与 `selectionArgs`、不拼接用户输入；在工作线程遍历并用 `use` 及时关闭；可取消的界面查询传入 `CancellationSignal`。

边界：Provider 是否利用数据库索引取决于该 `authority` 的公开契约——MediaStore 的列与查询策略不能套到任意云盘 Provider。

**Q10: "按会话过滤 + 按时间倒序"的消息查询该建什么索引？`EXPLAIN QUERY PLAN` 出现 SCAN 一定错吗？**

建 `(conversation_id, sent_at)` 复合索引：等值过滤列放在索引前缀、排序列在后，SQLite 可以反向扫描 B-tree，因此同一索引也能服务 `sent_at DESC` 的排序。两个互不相关的单列索引通常不能同时完成过滤与排序。SCAN 不一定错——小表扫描、覆盖索引扫描或统计信息变化都可能使扫描成为合理选择，应同时检查扫描对象、是否出现临时 B-tree、返回行数与实际耗时。

每个索引都占空间并增加插入、更新、删除成本，用生产环境 SQL 采样与 `EXPLAIN QUERY PLAN` 反查确认确有使用，清理无效索引。EQP 输出格式不是稳定接口（SQLite 明确不保证跨版本一致），CI 断言不要绑定完整文本，只对明显的计划退化与耗时变化报警。

配套做法：列表页用 DTO 投影只读渲染所需列、详情页再读全文；加 `LIMIT` 控制行数；过滤、排序、计数、去重交给 SQL，不把大量行搬到 Kotlin 后处理。

分布边界：空库或均匀小样本不能代表线上偏斜分布，验证用接近真实分布的本地数据库。

**Q11: Room 遇到大表迁移该怎么设计？`fallbackToDestructiveMigration` 什么时候能用？**

大表转换让新旧结构共存一段时间：版本 N 先增加可空的新列或新表，新代码兼容两种表示并维护双写，后台任务按稳定主键分批回填并记录进度位置，进程被终止后从已确认位置继续；监控确认所有受支持版本回填完成后，后续版本才加非空约束、停止写旧表示并删除旧列。回填期间的读取必须能识别"新表示尚未生成"，不能把空值当业务结果。

迁移设计分三层：数据库结构改动（SQL 与导出的目标结构一致）、数据转换（短事务能完成的小转换随 `Migration` 执行，大表用回填）、发布策略（只有明确可重建的数据允许破坏性重建）。`exportSchema = true` 并把结构 JSON 提交版本库，`MigrationTestHelper` 从每个受支持历史版本走完升级路径并验证业务数据——缺少路径时 Room 在打开阶段抛异常。

`fallbackToDestructiveMigration()` 只适合产品确认可以重建的数据（如纯缓存库），并记录触发版本与重建成本；用户草稿、离线内容、支付状态和消息记录不能使用。它删库重建，与 `fallbackToDestructiveMigrationOnDowngrade()` 一样只覆盖明确允许丢失的场景。

性能边界：建索引与重建表都可能扫描或重写大量数据，让工作线程负责首次打开只避免主线程执行迁移、不消除 I/O；无法在可接受启动时间内完成的大迁移必须走分阶段版本加可恢复回填。

**Q12: 新 Kotlin 模块选 JSON 库为什么先对齐语义再比速度？Gson 的问题出在哪？**

同一份 JSON 在不同库中未必得到相同对象：未知字段（忽略、报警还是拒绝）、缺失与 `null`（是否用默认值）、数字（范围与字符串数字）、枚举（未知值）、多态（判别字段）、字段名注解是否对应——这些行为不一致时，耗时差异混入了语义差异，速度对比无效。基准前先固定语义规则并验证两库解码结果相等。

Gson 的边界：截至材料口径它处于维护模式、以 Java 为主要目标，不支持 Kotlin 非空类型与默认参数语义，并在运行时反射任意模型字段，这种开放式反射难以与 R8 缩减、优化、混淆配合，官方不再推荐用于 Android 的新 JSON 处理。存量项目不必立即重写，但要限制允许反射的模型、用 `@SerializedName` 固定字段名、用经 R8 的发布包验证字段与泛型适配器，按路径渐进迁移。

候选方案：Moshi 支持 KSP 编译期生成适配器（`@JsonClass(generateAdapter = true)`），减少运行时反射并让 R8 规则更可审计；`kotlinx.serialization` 由编译器插件为 `@Serializable` 类型生成序列化器，适合受控的 Kotlin 与 KMP 模型（材料口径：仅 JSON 格式稳定，CBOR、protobuf 等为实验 API）。迁移时逐项验证空值、默认值、枚举、时间格式与自定义适配器。

基准方法：Jetpack Microbenchmark 固定输入样本与发布配置，结果校验放在计时循环外、用 `BlackHole.consume()` 防止代码被删除；首次类加载与完整用户路径交给 Macrobenchmark 与 Perfetto。

**Q13: OkHttp 什么时候自动解压 gzip？手动设置 `Accept-Encoding` 之后行为怎么变？**

默认 `BridgeInterceptor` 只在请求没有显式设置 `Accept-Encoding`、且没有 `Range` 时添加 `Accept-Encoding: gzip`，并在响应包含 `Content-Encoding: gzip`、语义允许携带响应体时流式解压，解压后移除 `Content-Encoding` 与 `Content-Length`、长度标为未知。一旦调用方手动设置 `Accept-Encoding`，透明解压不再发生，业务要自行解码；要关闭压缩可显式发送 `Accept-Encoding: identity`。

OkHttp 5.4.0 的扩展行为（按材料核对）：通用 `CompressionInterceptor` 把注册算法组成请求头并按完整的 `Content-Encoding` 值匹配，不逐层解码 `gzip, br` 这类多层编码；`okhttp-brotli` 的 `BrotliInterceptor` 注册 Brotli 与 Gzip、声明 `Accept-Encoding: br, gzip`，并接管响应解压、替代 BridgeInterceptor 的默认 gzip 路径。

服务端配合：按 `Accept-Encoding` 返回不同表示时必须发送 `Vary: Accept-Encoding`，共享缓存据此分别保存变体，避免把 gzip 响应发给不支持的客户端。

测量与防护：分别记录编码前数据大小、网络传输字节、解码后大小与编解码耗时——透明解压让应用层长度与线上传输长度不同，两者不能混用；客户端要限制解码后数据量、集合元素数与解析深度，防御压缩炸弹（传输体积很小、解压后急剧膨胀的输入）。

**Q14: `no-cache`、`no-store`、`private`、`s-maxage` 分别控制什么？304 验证怎么工作？**

四个指令回答不同问题：`no-cache` 允许存储但每次复用前必须向源站验证（表达"先验证"，不是"不要存储"）；`no-store` 要求不存储请求或响应、也不用于满足后续请求（且不能替代传输加密与访问控制）；`private` 限制 CDN、代理等共享缓存存储，不禁止私有缓存存储；`s-maxage` 只为共享缓存指定新鲜期——OkHttp 的磁盘缓存是私有缓存，会解析该值但不按它决定复用时间。

新鲜度与验证分开：`max-age` 存在时优先于 `Expires`；当前年龄要结合 `Date`、`Age` 与本地驻留时间计算，不能只比较设备时钟与下载时间。验证器没有固定高低：`ETag` 配 `If-None-Match`、`Last-Modified` 配 `If-Modified-Since`，服务端返回 304 表示内容未变，客户端保留本地响应体只更新可合并的元数据；两者按服务端数据模型选择。

`Vary` 语义：它声明哪些请求头共同决定缓存变体；OkHttp 把这些头的名称与值写入缓存元数据并在复用前逐项比较，`Vary: *` 表示任何请求都不能直接匹配、响应不进入缓存。自建缓存键只含 URL 而遗漏语言、编码或账号范围时，会复用错误的变体。

OkHttp 5.4.0 实现边界（按材料核对）：磁盘缓存只写 GET 响应、不缓存 206；`only-if-cached` 找不到条目时生成 504（不是源站错误）；条件命中同时计入 `networkCount` 与 `hitCount`。账号隔离不能只靠 `private`——同一应用的多账号要用账号级缓存目录或把账号纳入缓存键，敏感一次性数据由服务端返回 `no-store`。

**Q15: 内存缓存、磁盘缓存、HTTP 缓存与权威数据源各负责什么？`cacheDir` 为什么不能当权威数据源？**

四层的淘汰语义不同：内存缓存（`LruCache`、图片库内存层）服务进程内重复访问，按容量与最近访问淘汰，占用堆并可能增加 GC；可删除磁盘文件（`cacheDir`、图片库磁盘层）允许应用重启后复用可再生数据，按配额与修改时间淘汰，系统或用户可随时删除；HTTP 缓存按协议的新鲜度与验证器复用响应；权威数据源（Room、DataStore、持久文件）保存用户可见数据与同步状态，按业务版本、账号、租户淘汰。

`cacheDir` 不能当权威数据源的原因：系统回收存储空间时按 `lastModified()` 从较旧文件开始处理，应用升级、卷状态变化也会让内容缺失——读路径必须允许"文件不存在"并回源。需要跨升级、跨重启可靠恢复的数据放在持久数据源，界面从权威数据源读取，而不是直接读 HTTP 缓存或缓存目录。

失效与一致性：写操作成功后按资源关系让受影响条目失效（头像更新会影响用户详情、会话列表等多个条目）——依赖不可枚举时提升账号或资源版本让旧缓存整体失效；同键过期时的并发刷新合并为一次实际刷新（single-flight，互斥范围限制在同一键）；磁盘内容先写临时文件、校验后原子重命名替换，损坏条目按可恢复未命中处理并回源。

陈旧展示：界面状态区分"旧数据加刷新中""旧数据加刷新失败""无数据"；`lastSyncedAt` 只记录最近一次成功同步，失败尝试不改写它。

**Q16: `cacheDir` 里的文件会被系统怎么清理？墓碑和分组行为是什么？**

系统需要回收存储空间时，按文件 `lastModified()` 从较旧文件开始清理缓存目录；应用应把用量控制在 `StorageManager.getCacheQuotaBytes()` 返回的动态配额内（该值随设备状态变化），访问自己的内部缓存目录无需额外权限。`externalCacheDir` 可能不可用，使用前检查返回值与卷状态。

两个可选行为（API 26 起，只能设置在目录上并递归生效）：`setCacheBehaviorTombstone()` 让被系统自动清理的文件截断为零字节而非移除目录项——零长度"墓碑"帮助应用区分"曾经存在但已被清理"与"从未创建"；`setCacheBehaviorGroup()` 让整组目录以组内最新修改时间参与清理决策，整体保留或整体删除。两者都只影响系统自动清理：用户主动清除缓存时墓碑被忽略，分组也不提供持久性保证。

路径边界：设备采用可迁移存储后绝对路径可能变化，应用只应持久化相对路径。

OkHttp `Cache` 的目录契约：缓存目录必须独占——`Cache.delete()` 会删除目录中全部内容，不能与应用其他文件混放，同一目录也不能交给多个 `Cache` 实例；一个实例可由多个共享的 OkHttpClient 使用，应用共享长生命周期客户端，缓存读写失败时退回网络或权威数据源并记录错误。

**Q17: 离线优先的写操作为什么同时需要幂等键和服务端版本？本地变更和 Outbox 为什么必须同事务？**

两个字段识别不同故障：幂等键识别"同一操作被重发"——服务端收到相同键时返回已有结果、不重复产生副作用，防止"服务端已成功、本地未确认时进程终止"导致的重复执行；`expectedServerVersion` 识别"操作基于旧数据"——服务端原子地检查版本并执行写入，防止旧副本覆盖新数据。前者靠重试复用同一键、用户发起新操作时生成新键，后者靠本地保存最近确认版本并随写请求携带。

同事务的原因：本地可见变更（如收藏状态）与 Outbox 插入在同一个 Room 事务中提交或回滚，保证"用户已经看到的效果"与"待发送记录"一起存在——进程在事务提交后终止时，Outbox 记录仍在，重启后能继续同步；如果两步分开，会出现已显示成功却没有任何待发送记录的状态。服务端版本读取也应放入同一事务。

Outbox 的关键状态：`localOperationId`（唯一索引）、`status`（PENDING / WAITING_FOR_AUTH / CONFLICT / PERMANENT_FAILURE）、`attemptCount` 与 `nextAttemptAtMillis`、错误分类；HTTP 语义上 412 Precondition Failed 是版本不匹配、409 Conflict 是业务冲突，二者分开处理；429 读取合法的 `Retry-After`，401 或登录失效转为等待身份恢复而不做无限退避，数据校验失败标记永久失败。

事务与调度边界：网络请求不能包进 Room 事务——发送前用短事务认领可发送记录，响应回来再用短事务更新实体与状态；调度调用位于事务之后，进程恰好在提交后、安排 WorkManager 前终止时，启动或登录恢复入口必须重新安排唯一工作，服务端幂等始终不可省略。

**Q18: 大图库列表为什么不能用不断增长的 OFFSET 翻页？应该用什么锚点？**

`OFFSET` 表示先跳过多少行：较早页面发生插入或删除后，按行数跳过会造成重复或遗漏，MediaProvider 仍可能扫描被跳过的行。正确做法是保存上一页末尾的"排序值 + `_ID`"作为锚点，下一页用条件查询从该位置继续——`DATE_ADDED` 相同的记录用 `_ID DESC` 区分。

查询配合：一次只取当前页所需列（`_ID`、时间、MIME 类型、宽高、时长、`GENERATION_MODIFIED`），详情页再读 EXIF 或打开文件；用 Bundle 的 `QUERY_ARG_SQL_SORT_ORDER`、`QUERY_ARG_SQL_SELECTION`（占位符加参数数组）与 `QUERY_ARG_LIMIT` 传参，并传入 `CancellationSignal`——筛选条件变化、界面销毁或新查询取代旧查询时调用 `signal.cancel()`。

稳定性边界：`_ID` 不保证永久稳定，MediaStore 的 version 变化后应废弃旧页位置并重新查询；分页与排序是否被支持取决于 Provider，客户端要检查 `Cursor` extras 确认。

结果处理：查询返回后把列表所需字段复制到小型数据对象再关闭 Cursor，避免界面长期占用 MediaProvider 查询资源；只查所需列同时降低 CursorWindow 填充与对象构造成本。

**Q19: MediaStore 的 version 与 generation 怎么配合做增量同步？删除记录怎么补偿？**

两层协议：`getVersion(context, volume)` 返回不能解析内部格式的版本字符串，媒体库发生重大变化时改变——此时旧 generation 失去比较意义，应用必须全量重新分页读取当前可见数据；version 未变时 `getGeneration(context, volume)` 单调递增，用每行的 `GENERATION_ADDED`（加入索引时的值）与 `GENERATION_MODIFIED`（最近元数据变化时的值）过滤上次检查点之后的增量。

检查点协议：查询前校验 version 未变，取本轮 `endGeneration`，把增量限制在"检查点之后、endGeneration 之前"；处理并持久化所有行后再次读取 version——前后相同才把 endGeneration 写入检查点，查询期间发生且大于 endGeneration 的变化留给下一轮。generation 比 `DATE_ADDED`/`DATE_MODIFIED` 可靠（不受 `setLastModified()` 与时钟影响），但只描述索引变化，元数据变化不表示文件字节变化，不能替代内容哈希。

删除补偿：Android 13 的公开 API 没有删除记录查询——原始媒体行删除后，增量查询不会返回替代的删除标记；可靠同步需要两条路径，generation 增量处理新增和修改，再定期分页查询该卷当前可见的 `_ID` 集合与本地记录逐项比较，补偿进程停止期间遗漏的删除。比较前确认卷仍挂载、权限未收窄——权限造成的"不可见"不能记为用户删除。

版本扩展：`queryDeletedFiles()` 属于 API 37.1 / S Extension 23（材料口径，AAOS13 无此 API），返回外部卷的删除记录，内部卷与已移除卷不返回；支持时把删除查询并入增量阶段，不支持时继续 `_ID` 对账。`ContentObserver` 只负责唤醒重新查询——合并短时间重复通知、后台转成 generation 检查，回调的合并、顺序与详细程度不构成持久同步协议。

**Q20: 向共享存储写媒体时 `IS_PENDING` 是干什么的？`DATA` 列为什么不能用于创建或移动？**

`IS_PENDING=1` 表示记录尚未发布：其他应用通常看不到未完成媒体，调用方也不必等媒体扫描发现自己刚写入的文件；内容写完后再清除标记发布，保证其他应用看到记录时文件已经完整。失败分支要删除调用方刚创建的待发布记录，避免留下长期不可见的半成品——清理本身也可能失败，应记录待清理的 Uri 且不让清理异常覆盖原始写入异常；整段操作在负责阻塞 I/O 的后台调度器执行。

`DATA` 是旧式绝对路径列：可用于打开当前已存在且有权访问的媒体，但路径可能因移动、卸载卷或权限变化失效；创建和移动媒体必须用 `DISPLAY_NAME` 与 `RELATIVE_PATH`，不能写 `DATA`。Photo Picker 或云媒体返回的 Uri 不保证对应本地路径，也不应从 `DATA` 拼装路径。

批量用户请求的边界：`createWriteRequest()`、`createFavoriteRequest()`、`createTrashRequest()`、`createDeleteRequest()`（Android 11 / API 30 起）生成封装系统操作的 `PendingIntent` 并显示系统确认界面；每个 Uri 必须是 MediaStore `authority`（`media`）下带 `_ID` 的具体媒体项，不能传集合 Uri。收藏、回收站、删除在系统返回结果前已执行完成，`createWriteRequest()` 的成功只代表用户授予写权限、应用随后仍要执行写入；该写权限与发起请求的 Activity 生命周期绑定、不能持久化或按前缀授权。按材料核对（Android 17），targetSdk 36 及以上每次请求最多 2000 个 Uri、超出抛 `IllegalArgumentException`——AAOS13 无此上限，跨版本实现按 2000 分组即可统一处理；用户取消时不能修改本地媒体状态。

**Q21: 媒体网格的缩略图该怎么加载？缓存键要包含什么？**

Android 10 起用 `ContentResolver.loadThumbnail(uri, size, signal)`（按 AAOS13 `ContentResolver.java` 核对存在），内容提供方可以复用已有缩略图并按目标尺寸返回 `Bitmap`，避免读取原图再缩小带来的文件读取量、解码时间与内存峰值。调用内部仍可能发生 Binder、文件读取与解码，应在限制并发数的工作线程执行并支持取消；官方约定加载失败或 `signal.cancel()` 都可能抛 `IOException`，调用方要把用户取消与真实读取失败分开统计。

缓存键至少包含：媒体 `Uri`；`GENERATION_MODIFIED` 或应用能验证的内容版本；目标物理像素宽高；裁剪、旋转、色彩与 HDR/SDR 处理参数。同一 `Uri` 的小网格图和详情预览不能共用无尺寸缓存键；generation 改变只失效对应媒体的派生图，version 改变要重新校验整个缓存索引。

并发边界：查询、缩略图、上传与转码不宜共享一个可无限增加任务的执行器——缩略图同时消耗 Binder、磁盘、CPU 与图形内存，并发数按首屏时间、滚动丢帧、内存峰值与设备温度测量确定，固定套用 CPU 核数公式可能在低内存设备同时产生过多 `Bitmap`。

替代 API 的位置：`ThumbnailUtils` 适合合法持有 `File` 的旧路径代码；`MediaMetadataRetriever` 提取视频指定帧的成本高，不适合网格并发提取大量帧。

**Q22: Photo Picker 返回的 HDR 视频什么时候会被转成 SDR？应用怎么声明能力、怎么处理授权？**

HDR 转 SDR 不会自动发生：Android 13 及以上通过 AndroidX `PickVisualMediaRequest` 的 `setMediaCapabilitiesForTranscoding()` 显式声明（AndroidX Activity 1.11.0 及以上），列出的 HDR 类型表示应用支持、未列出的视为不支持，发生转换时 Picker 返回转码结果 Uri；该路径只处理不超过 1 分钟的视频，超过限制或平台未执行转换时应用可能拿到原内容，上传前要验证视频轨道的色彩信息。`MediaProvider` 兼容转码是另一条入口：打开媒体时传 `ApplicationMediaCapabilities`（Android 12 起），本机播放与缩略图生成不应触发，标准来源限 OEM 相机写入 `DCIM/Camera/` 的本机视频，标准实现限 1 分钟、连续 10 个会话、累计 3 分钟（AOSP 文档口径）。

能力声明的方向：声明过窄会增加转码、过宽会收到自身无法处理的源格式；完全不声明时平台按"支持所有格式"处理、兼容转码默认关闭——依赖转换的路径必须显式声明不支持的格式。调用级声明优先于应用资源级声明，适合"本机播放支持 HDR、上传只接受 SDR"的差异路径。

授权处理：Picker 返回只读 Uri，默认授权持续到设备重启或应用停止；跨重启或后台任务在收到 Uri 后调用 `takePersistableUriPermission()` 持久化逐项读取授权（官方口径：平台允许每应用最多 5000 个持久媒体授权，继续新增时移除最早授权），草稿删除与账号退出时 `releasePersistableUriPermission()`。不能把返回 Uri 转换成本地路径——云媒体与系统转码结果都不保证存在可依赖的文件路径。

回退边界：AndroidX 在设备不支持 Picker 时回退到 SAF 的 `ACTION_OPEN_DOCUMENT`，会忽略多选最大数量，回调后仍需数量校验；多选上限可经 `MediaStore.getPickImagesMaxLimit()` 读取（API 34 起，材料按 Android 17 核对上限 100）。

**Q23: `NET_CAPABILITY_INTERNET`、`VALIDATED`、`NOT_METERED` 各证明什么？在 `onCapabilitiesChanged` 回调里重新查询有什么风险？**

三个能力都只回答自己的问题：`INTERNET` 表示网络被配置为访问一般互联网，不证明当前可达；`VALIDATED` 表示系统最近一次验证一般互联网成功，不证明业务端点此刻可达；`NOT_METERED` 表示网络不按流量计费——大传输应看它，而不是用 Wi-Fi 或蜂窝等传输类型代替计费判断。

回调竞态：`getNetworkCapabilities()` 返回调用瞬间的快照、可能立即过时；在 `onCapabilitiesChanged()` 回调内重新同步查询 capabilities 或 `getLinkProperties()`，拿到的可能已是更新后的状态、与当前回调不再对应。正确做法是使用回调传入的对象；Android 8.0 起 `onAvailable()` 后会按序收到 `onCapabilitiesChanged()`，状态发布放在能力回调之后。

用途边界：`VALIDATED` 适合提示离线状态、延迟非紧急公网同步和标记监控数据，不适合作为每个 API 请求的前置条件——系统验证可能刚失效而业务端点仍可达，captive portal、企业专网可能没有验证但局域网端点可达。

网络身份：默认网络从 Wi-Fi 切到蜂窝时新旧 `Network` 对象身份不同，接入点重连也可能得到新 Network——HTTPDNS 缓存与按网络绑定的套接字要保留 Network 身份，不能只存"Wi-Fi/蜂窝"字符串。注册需要 `ACCESS_NETWORK_STATE`，不再观察时 `unregisterNetworkCallback()`；回调投递到并发执行器时状态要加同步。

**Q24: OkHttp 怎么判断连接可复用？响应体不关闭会怎样？**

复用资格由 `Address`（URL 协议方案、主机、端口、DNS、代理、套接字工厂、TLS 配置、主机名校验器、证书固定器等静态配置）与 `Route`（代理、候选 IP 等本次连接选择）共同决定；跨主机的 HTTP/2 连接合并还要求直连路径、IP、证书覆盖、主机名校验与证书固定规则同时满足——两个域名解析到同一 IP 不一定共享连接，证书覆盖多域名也不保证合并。

连接池语义：默认构造参数限制的是保留多少条空闲连接，不限制正在使用的连接总数，也不等于域名数量；HTTP/2 在一条连接上并发多个逻辑流，HTTP/1.1 通常在连接空闲后复用。默认值是库的调优选择，客户端升级后可能变化。

响应体未关闭的后果：它持续占用套接字与 HTTP/2 逻辑流，连接池即使配置正确也无法复用；同步调用用 `use` 确保成功、异常、提前返回都关闭，流式下载不能先 `string()` 但消费结束、取消或异常时同样要关闭。

客户端组织：应用内共享一个基准 `OkHttpClient`，需要差异时用 `newBuilder()` 派生——它继承配置并共享连接池等资源，直接新建 Builder 会创建独立资源；EventListener 观测时注意连接池命中时 DNS 与建连事件缺席、重定向与认证会让同一组事件出现多次，要以一次逻辑 `Call` 为父级给事件编号。

**Q25: 接入 HTTPDNS 后哪些安全检查不变？缓存键和回退策略怎么定？**

自定义 `Dns` 只返回地址：HTTPS URL 仍按原主机名执行 SNI、主机名校验、证书/公钥固定与 Cookie 域规则——不能用换 IP 换取省略校验。缓存键至少包含主机名与 Android `Network` 身份：默认网络变化后旧网络的结果不能直接继承，切换 Wi-Fi/蜂窝要重新解析。

TTL 与多地址：TTL 使用 HTTPDNS 响应或服务协议给出的值，不存在"统一取某个百分比"的通用规则；进程内有效期用 `elapsedRealtime()` 判断，避免用户修改系统时间后错误延长。缓存要保留 IPv4、IPv6 与多个候选地址——OkHttp 5.4.0 默认启用 Fast Fallback（Happy Eyeballs），并行错峰尝试候选连接，只存一个地址会丢失该恢复能力。

递归与引导：HTTPDNS 查询若复用正在实现自定义 `Dns` 的业务客户端，HTTPDNS 服务自身的域名会重新进入自定义解析器形成递归，还可能在受限执行资源上线程互等——解析路径不能依赖自身，HTTPDNS 查询要用独立的引导解析策略，缓存写入端直接解析数值 IP。

回退是产品策略：严格隐私模式若承诺只用指定解析服务，静默转向系统 DNS 会违反承诺；允许回退时记录原因，客户端绑定指定 `Network` 时回退解析也用该网络的 `getAllByName()`。自定义解析会绕开系统为 Private DNS、企业 VPN 与分流 DNS 提供的语义，企业内网与本地域名要实机验证。失败分类：查询失败、返回空地址、地址连接失败与 TLS 校验失败是不同事件，前两类属于解析与缓存策略，TLS 失败不能通过关闭校验"兼容"。

**Q26: 弱网下统一延长超时、增加重试为什么不行？OkHttp 各超时参数覆盖哪一段？**

一次请求显示"慢"，内部可能经历 Dispatcher 排队、DNS、多地址竞速、TCP 建连、TLS 握手、服务端等待与响应体读取；未定位失败阶段就统一延长超时或增加重试，会让失败请求占用更多连接、线程、电量与用户等待时间，还可能把局部故障变成更长等待。分段处理：排队阶段调整业务优先级与隔离大传输；DNS 阶段检查目标网络与候选地址；TCP 阶段保留多地址与 Fast Fallback；TLS 阶段查证书链与固定规则；写入与响应阶段检查体积、取消与幂等。

超时分工：`connectTimeout` 约束套接字建连阶段，`readTimeout`/`writeTimeout` 约束对应读写操作，`callTimeout` 覆盖整次逻辑调用（含 DNS、连接、写入、服务端处理与读取）。增大读超时修复不了 DNS 或排队；只设阶段超时也限制不了重定向与重试累积后的总等待。

参数来源：同一接口在不同网络类别下的耗时分位数、用户交互截止时间与服务端 SLO；流式下载与短 API 的读取模型不同，不共享一组机械常数。

观测边界：EventListener 的事件可能缺席（连接池命中时 DNS 与建连事件不出现）或重复（重定向、认证、连接路径重试）；TTFB 是请求发出到响应首部的等待，不等于解析响应头耗时。验收时平均耗时下降而 P99、重试次数或后台字节上升，不能判定优化有效。

**Q27: OkHttp 的 `retryOnConnectionFailure` 和业务重试有什么区别？POST 失败后能直接重发吗？**

不能直接重发。`retryOnConnectionFailure`（默认开启）只做传输恢复：从失效的池连接或可替代连接路径的故障中恢复，不代表应用可以重新提交任意业务操作；非幂等方法不能仅凭"尚未收到响应"推断服务端没有执行——支付、下单、发消息等 POST 需要服务端幂等键、状态查询或事务协议。

HTTP 语义边界：RFC 9110 把 GET、HEAD 等安全方法以及 PUT、DELETE 定义为幂等方法；幂等描述重复相同请求的预期服务端效果，不保证响应相同，也不能修复违反规范的服务端实现。

请求体能力：一次性请求体无法可靠重放——自定义流式 `RequestBody` 若只能写一次，应实现 `isOneShot()` 明确告知客户端不能重新生成；请求体压缩或包装可能改变可重放性，重试前要确认暂存文件路径、长度与内容未变。

服务端提示与计数：`Retry-After` 表达服务端期望的等待（503 语义见 RFC 9110、429 见 RFC 6585），客户端还要服从用户取消与 `callTimeout`；一次 `Call` 内部的传输恢复加应用层重试会让实际尝试次数高于表面计数，重试间隔按指数退避加随机偏移，起始间隔、上限与次数来自业务恢复目标与服务端容量——不存在对所有接口都安全的一组毫秒值。

**Q28: HTTP/2 多路复用解决了什么、没解决什么？**

解决了连接数量与应用层队头等待：HTTP/2 把消息编码为二进制帧并归入逻辑流，多个流在同一连接交错传输，HPACK 用动态表压缩重复首部；HTTPS 下通常经 ALPN 协商 `h2`。未解决传输层队头阻塞：它仍运行在单个 TCP 有序字节流上，丢包会阻塞同一连接所有流的数据交付。

并发上限来自多处取最小值：服务端 `SETTINGS_MAX_CONCURRENT_STREAMS`、客户端 Dispatcher 并发、连接级与流级 HTTP/2 流量窗口、服务端容量与设备资源。流量控制是连接级与流级并存：消费方长时间不读响应体会形成流级背压，并可能影响连接级窗口；大响应体会争用同一连接的带宽与拥塞窗口——大文件与短 API 是否同客户端/Dispatcher，按排队与 P95/P99 尾延迟决定。

连接复用仍受 `Address`/`Route`/证书与连接健康约束："域名分片"可能增加 DNS、TCP 与 TLS 成本并阻止符合条件的连接合并，HTTP/2 时代通常应减少域名分散。

OkHttp 边界（按材料核对 5.4.0）：服务器推送是协议能力而非应用能力——`Http2Connection.Builder` 默认使用内部 `PushObserver.CANCEL`，`OkHttpClient.Builder` 没有开放的推送配置入口，方案应改用聚合接口、可取消预取与标准 HTTP 缓存；单个响应首部总量限制 256 KiB。

**Q29: HTTP/3/QUIC 相对 HTTP/2 改变了什么？0-RTT 为什么不能随便用？**

QUIC 在 UDP 上实现可靠传输、拥塞控制、TLS 1.3 集成、流复用与连接 ID 标识：单条流丢包需要重传时，其他不依赖该数据的流可以继续交付（消除 HTTP/2 的传输层队头阻塞）；连接用连接 ID 标识，IP 或端口变化后可验证新路径并迁移连接；已建立会话状态满足条件时可恢复握手。

没有改变的部分：DNS、服务端处理与应用读取时间不缩短；QUIC 拥塞控制通常作用于连接路径，某条流占满带宽仍影响其他流；UDP 被企业网络、代理、VPN 或热点阻断时要保留基于 TCP 的 HTTP/2 回退（RFC 9114 允许改用基于 TCP 的 HTTP）。服务端要通过 Alt-Svc 或 QUIC hint 声明能力，`setEnableQuic(true)` 只允许引擎选择、不会让缺少服务端配置的域名自动使用 HTTP/3。

连接迁移的边界：前提是连接为 QUIC 且服务端支持迁移（Android 17 `ConnectionMigrationOptions` 源码口径）；NAT、企业代理、VPN、防火墙与负载均衡可能阻止，迁移期间请求可能超时——业务仍要恢复策略；该选项在 AOSP 标注为实验 API，A13 无平台 `HttpEngine`，Android 13 设备使用 HTTP/3 需外部 Cronet。

0-RTT：恢复会话时可在握手完成前发送早期数据、省一个往返，但缺少跨连接防重放保证——攻击者可能重放捕获的数据，登录、支付、下单等产生一次性副作用的写请求不能仅凭"使用 HTTPS"进入 0-RTT；服务端也可拒绝早期数据，指标要区分最终协议与业务总耗时，不把"启用 QUIC"记成"命中 0-RTT"。

**Q30: gRPC 的 `Channel` 是什么？deadline 和 wait-for-ready 应该怎么设置？**

`Channel` 是到一个逻辑目标的通信通道：内部可持有零条、一条或多条实际连接，并参与名称解析与客户端负载均衡，不等同于一条套接字连接。官方性能建议要求复用 `Channel` 与生成的 stub——复用边界按逻辑目标、TLS、代理、名称解析与服务配置决定；用户令牌经每次调用的调用凭据或元数据提供，不因账号切换重建 Channel，也不把旧令牌固化在长生命周期拦截器中。

deadline：gRPC 默认不设置调用截止时间，客户端可能无限等待——每个方法按用户交互期限、网络耗时分布与服务端处理预算显式设置；上游取消、页面销毁与后台任务停止也要传播到 RPC。

wait-for-ready：通道暂时不可用时把调用留在队列中，待连接恢复后再发送；默认模式会更早返回失败。它只适合允许短暂等待连接恢复的调用，且 deadline 仍然生效——不能绕过用户取消或无限延长启动等待。

流式与资源：流式 RPC 断线后未完成的逻辑流会失败，消息序号、游标、确认、去重与补发属于应用协议；一次写入只表示消息交给 gRPC、不代表字节已到网络，发送快于接收时框架等待或缓存——应用队列必须有界并保证两端持续读取。监控要记录 gRPC 状态码、服务名、方法名、deadline、取消与每次尝试，HTTP 200 不足以表示结果。

**Q31: gRPC 返回 `UNAVAILABLE` 就可以直接重试吗？收到响应首部之后呢？**

`UNAVAILABLE` 不自动表示业务操作可重复：查询或幂等操作可以在总 deadline 内受控重试，写操作需要幂等键、版本条件或查询确认，不能只按状态码重发。两类重试机制要区分：透明重试在确认调用没有进入服务端应用逻辑时，恢复少量因并发事件先后顺序不确定产生的底层故障；更广泛的重试通过 Service Config 按方法设置尝试上限、逐次延长的等待、可重试状态码与重试总量限制。

收到响应首部之后：gRPC 重试机制把该 RPC 视为已提交，不再按同一策略重试——因此"未收到首部"与"已收到首部"的失败要分开处理，监控同时记录逻辑 RPC 与每次尝试，避免把内部重试时间全归为一次服务端延迟。

保活与长流：保活探测用 HTTP/2 `PING` 检查空闲连接，客户端间隔不应远低于一分钟、无调用时避免启用，服务端可用 `GOAWAY` 与 `too_many_pings` 拒绝过密探测；移动端还要考虑蜂窝无线电唤醒、Doze 与后台限制，低频通知更适合系统共享推送通道。长生命周期逻辑流启动后通常不能重新参与客户端负载均衡，服务端滚动发布或节点故障都会中断它——固定保持一条永久流不是高可用方案。

回退边界：gRPC 到 REST 是两套接口契约而非协议自动回退，双路径必须共享鉴权、幂等、字段与错误映射规则；多数业务更适合在当前 RPC 上恢复或显示错误。

**Q32: Android 17 的 ECH 生效链路是什么？"发送了 GREASE"能算 ECH 成功吗？**

不能。`enabled` 模式下没有可用 ECH 配置时，客户端发送的是 ECH GREASE——内容随机的兼容性测试扩展，用于检查网络中间设备能否容忍 ECH 格式，它不加密真实 SNI，诊断事件要区分"ECH 被接受、GREASE、策略禁用、没有配置、配置失配与其他 TLS 错误"。

生效需要四层同时满足：网络安全配置的 `domainEncryption` 策略（targetSdk 37 时默认 `enabled`，正式 XML 只接受 `enabled` 与 `disabled`，`OPPORTUNISTIC` 只是 API 常量不能写进 XML）；DNS 的 HTTPS 资源记录携带 `ech` 配置；网络库完成接入——经 `NetworkSecurityPolicy.getDomainEncryptionMode()` 读策略、`DnsResolver` 并发查询 A/AAAA/HTTPS 记录得 `HttpsEndpoint`、`HttpsRecord.getEchConfigList()` 解析配置（无效抛 `InvalidEchDataException`）、握手开始前调用 `SSLSockets`/`SSLEngines.setEchConfigList()`；服务端支持 RFC 9849 并发布配置。

失配处理：`EchConfigMismatchException` 要求先取 `getPublicHostname()`，用主机名校验器确认证书对该公开名称有效（为 `null` 时必须忽略重试配置），`getRetryConfigList()` 非空后才可新建连接重试——不能跳过校验直接重试。证书与 CT 失败是独立校验阶段，禁用 ECH 不会修复证书错误。

保护与版本边界：目标 IP 仍可见、外层 ClientHello 保留公开名称、明文 DNS 查询仍可能泄露、流量时序可分析——ECH 不替代加密 DNS 与证书验证。AAOS13 没有这套 API（本地核对无 HTTPS 记录查询与 `domainEncryption` 配置）；官方文档把 HttpEngine、WebView、OkHttp 列为示例，但 ECH 只在网络库实际集成了支持时生效，上线记录要包含网络库与 WebView 的具体版本。
