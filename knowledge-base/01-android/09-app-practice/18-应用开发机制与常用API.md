# 应用开发机制与常用 API

> 面向 Android 应用开发的若干独立主题：集合与 View 元数据、对象传输、网络接口抽象。Q 序列即结构。

**Q1: 小规模整数键映射为什么可以考虑 `SparseArray`，它的主要取舍是什么？**

`SparseArray` 以有序 `int[]` 保存键、以并行 `Object[]` 保存值，避免 `HashMap<Integer, …>` 的键装箱和哈希节点开销，适合条目较少且键为整数的场景。它用二分查找定位，查询为 O(log n)，但插入和删除可能需要移动数组元素，不能把它当成任意规模下比哈希表更快的通用替代品。

Android 实现会用删除标记延迟压缩数组；值本身允许为 null，因此内部需要能区分“合法 null 值”和“已删除槽位”的标记。选择时看条目规模、读写比例与内存开销，而不是只比较渐进复杂度。

**Q2: `View.setTag()` 和 keyed tag 适合存什么，如何避免资源键错误与引用泄漏？**

无键 `setTag(Object)` 适合给 View 绑定一个简单关联对象；多个独立元数据可使用 `setTag(int, Object)`，键必须是项目 `ids.xml` 中声明的资源 ID。keyed tag 由 View 内部管理，不需要在 Activity 里另建 `Map<View, …>`。

Tag 与 View 一起持有对象引用，所以只存生命周期不长于该 View 的轻量数据；若对象持有 Activity、Context、监听器或大对象图，View 被意外长期持有时会连带泄漏。不要用硬编码整数代替资源 ID，也不要把 Tag 当通用业务仓库。

**Q3: Java 对象在 Android 进程间传递时，`Parcelable` 与 `Serializable` 应怎样选择？**

Android 组件间通过 Intent 或 Binder 传输对象时，优先使用符合平台契约的 `Parcelable`；`Serializable` 更简单但通常有更高的反射与编码开销。两者都要控制载荷大小：Binder 事务缓冲区有限，大对象应传 URI、数据库键或文件描述符等间接引用。

`Parcelable` 的写入顺序必须与读取顺序一致，嵌套对象与文件描述符也要遵守相应契约；自定义 `Serializable` 类型要考虑版本演进和 `serialVersionUID`。序列化格式不应被当成长期稳定的持久化协议，存储格式需要明确的版本与兼容策略。

Parcelable 通常更适合 Android 进程间传递，是因为它让类型按字段顺序直接读写 Parcel，避免 Java 原生序列化的通用对象图编码与反射成本；实际成本仍取决于载荷结构和读写实现，选择它不代表可以传送无限大的对象。

**Q4: Retrofit 怎样把带注解的 Java 接口变成 HTTP 请求？**

Retrofit 解析接口方法及其注解，把路径、HTTP 方法、查询参数、请求体和响应类型转换成请求描述，再通过动态代理创建接口实现，并把请求交给底层 HTTP 客户端（常见为 OkHttp）执行。接口因此描述服务器契约，不是实际网络实现。

`@GET`、`@POST`、`@Query`、`@Path`、`@Body` 等注解定义请求形状；返回类型与 converter、call adapter 共同决定响应如何解码及以何种调用形式交付。同步 `execute()` 不应在主线程调用；异步 `enqueue()` 的回调线程取决于配置的 call adapter，Android 默认适配通常把回调投递到主线程。具体 API 和行为应以项目使用的 Retrofit 版本及 adapter 配置为准。

**Q5: Retrofit 的接口方法如何表达查询参数与表单请求，为什么不应在 UI 回调里直接拼完整 URL？**

接口方法用注解表达固定路径与参数位置：`@Path` 替换路径段，`@Query` 添加查询参数，`@QueryMap` 批量添加查询参数，表单字段需配合 `@FormUrlEncoded` 与 `@Field`。把这些规则放在接口契约中可统一编码、转义和测试，也避免 UI 层承担 URL 拼接细节。

接口路径通常是相对 Retrofit 配置的 base URL；接口返回的数据模型应与真实响应结构匹配。认证、错误响应、超时、取消和重试仍需在客户端策略中明确处理，不能因为请求已封装就假设网络调用必然成功。

**Q6: Android 通知渠道解决什么问题，应用能否绕过用户设置强制提高通知重要性？**

面向 Android 8.0（API 26）及以上的应用，通知应先归入通知渠道；渠道把一类通知的名称、用途和重要性暴露给用户，由用户控制提醒方式。应用可在首次使用时创建渠道并为每条通知指定渠道 ID，但渠道创建后的重要性等用户可见设置由系统和用户管理，应用不能靠重复创建同 ID 渠道重置用户选择。

应用仍须在每条通知中提供合理的小图标、内容和点击行为，并按平台版本处理通知运行时权限与前台服务要求。渠道用于分类和用户控制，不是通知必然展示或绕过勿扰、权限及系统策略的保证。

**Q7: Android SharedPreferences 适合保存什么数据，如何读取一个键值？**

SharedPreferences 适合保存少量、简单的键值设置，例如用户偏好和轻量配置；它提供字符串、布尔值、整数、长整数、浮点数和字符串集合等类型读取接口。读取时要使用与写入值匹配的类型，并提供合理默认值；它不适合保存大列表、复杂对象、密钥或需要关系查询的数据。

通过 `Context.getSharedPreferences(name, MODE_PRIVATE)` 获取命名文件对应的实例，再调用 `getString()`、`getBoolean()` 等方法按键读取。缓存与加载行为的线程边界见 [存储与 I/O](../04-storage/01-存储与IO.md)；多进程应用不能把多个进程各自缓存的 SP 当成一致性存储。

**Q8: SharedPreferences 如何写入数据并监听键值变化？**

调用 `edit()` 获取 Editor，使用 `putXxx()` 修改键值，再调用 `apply()` 或 `commit()` 提交。`apply()` 立即更新内存并异步安排持久化，不返回磁盘成功状态；`commit()` 等待写盘并返回成功与否，因此不应在主线程对可能耗时的写入使用 `commit()`。

`registerOnSharedPreferenceChangeListener()` 可监听键值变化，使用完应调用对应注销方法。监听器生命周期应由持有它的页面或组件管理，避免长期注册后继续引用已结束对象。

**Q9: Parcelable 对象如何通过 Parcel 写入并恢复？**

实现 Parcelable 时，`writeToParcel()` 按固定顺序写出字段，`CREATOR` 在构造对象时按完全相同的顺序读取；顺序或类型不匹配会造成字段错乱或反序列化失败。`describeContents()` 通常返回 0，包含文件描述符时需正确报告相应标记。

`Parcel` 是 Binder/组件传递使用的暂存序列化容器，不是供应用长期保存的稳定文件格式；它的内部编码不应跨版本或跨平台当成持久化协议。
