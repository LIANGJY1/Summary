**Q1: Android Vitals 与内部 APM 是两套什么口径的数据？为什么内部 crash-free 率和 Play 的 user-perceived crash rate 不能放在同一张图上直接比较？**

Vitals 是 Google Play 对线上技术质量的外部观测：只统计从 Play 安装、设备通过认证、允许共享使用情况与诊断数据且达到隐私展示门槛的用户；内部 APM 统计所有接入并成功上报的渠道与包。Vitals 的分母是 28 天窗口内用户加权的 DAU（一天一台设备上的一名用户）或按日聚合的 user session（太平洋时间午夜起 24 小时内的全部使用活动），内部 APM 的分母是团队自定义的 user、device、session、launch 等口径。两者没有事件级关联键，重复崩溃、后台事件和渠道范围的处理也不同。

直接相减或比较大小会产生三类误判：低流量版本或小设备分组可能没有可见数据，"没有数据"不是"零问题"；Vitals 排除未认证设备和非 Play 渠道（国内渠道、企业分发、预装、旁加载必须由其他观测系统覆盖）；分母不同（DAU 与会话）让两个百分比没有共同的比较基准。正确做法是分别判断各自趋势，再按版本、时间桶、设备维度和错误聚类验证两边是否指向同一变更。时效也不同：Vitals 每日更新、受聚合与隐私门槛影响，内部 APM 可做到分钟级但受采样与上传成功率影响。

**Q2: 2026 年 Play 的 core vitals 有哪些指标、阈值是多少？整体阈值与机型阈值分别约束什么范围？**

core vitals 指影响 Play 可见性的指标，Play 每天按最近 28 天的用户加权结果检查，突增时可能提前采取措施。2026 年口径如下：

- **user-perceived crash rate**：整体阈值 ≥ 1.09%（文档用 "at least"，达到即算 bad behavior）；机型阈值手机 ≥ 8%、手表 ≥ 4%；
- **user-perceived ANR rate**：整体阈值 ≥ 0.47%；机型阈值手机 ≥ 8%、手表 ≥ 5%；
- **excessive partial wake locks**：超过 5%（文档用 "more than"），无机型阈值；规则是应用在后台或运行前台服务期间持有的 partial wake lock 在 24 小时内累计达到 2 小时即判 excessive（音频、定位、用户发起的 JobScheduler 任务等有豁免），28 天内 excessive 会话占比超 5% 可能影响可见性——该政策自 2026 年 3 月 1 日起进入可见性约束阶段，旧资料的"3 小时""仍处 beta"已过时；
- **excessive battery usage**：目前只对有足够数据的表盘应用提供（电量消耗超过 4.44%/hour 计入），不扩展到所有 Wear OS 应用。

整体越线可能影响所有设备上的可见性，机型越线主要影响对应设备并可能在详情页显示警告。两点边界：官方文档对可见性影响使用 "may"/"likely"，不能改写成每次越线立即降权的确定承诺；内部暂停阈值可以比官方更严格，但字段名必须标明属于团队规则，不能写成 Play 官方阈值。崩溃/ANR 持续超 7 天的新出现问题会被标记为 emerging issues 并给最长 21 天处理——这不改变 28 天统计定义，也不是继续放量的宽限承诺。

**Q3: Vitals 的 user-perceived crash/ANR 与自建 Crash SDK 的口径差在哪？用 Play 聚合数据定位一个崩溃时，三层证据怎么配合？**

user-perceived crash 只统计用户主动使用应用（显示 Activity 或执行前台服务）时发生至少一次崩溃的受影响用户；user-perceived ANR 当前只计 `Input dispatching timed out` 类型。自建 SDK 通过 watchdog、主线程消息耗时或系统 trace 能识别更多卡死，是否标为前台取决于 SDK 自己的进程状态实现；"至少一次"的分子不随多次崩溃增加，观察循环失败要看 multiple crash/ANR rate（一天内至少两次的受影响用户）。Wear OS 有一条例外：官方文档把手表的前台和后台崩溃都纳入 user-perceived 口径，手机结论不能直接复用。

三层证据各管一段：Play 层确定影响面（`versionCode`、`deviceModel`、`apiLevel`、地区、错误聚类），系统层用 `ApplicationExitInfo`（Android 11+）确认退出原因与可用 trace，应用层补用户路径、页面、实验桶、feature flag 和最近变更。三层通常没有可跨系统使用的事件 ID，只能按版本、时间桶、设备维度、进程名和 top frame 建立弱关联——弱关联只筛出候选事件，还要打开少量原始证据验证；两个聚合数字相近不能证明来自同一批事件，Play 的聚类 ID 也不应写进内部事件主键。ANR 不能只看一张堆栈：输入超时只说明输入没有按时处理，根因可能发生在主线程同步 Binder、磁盘 I/O、锁竞争、类初始化或 CPU 密集计算中，要回到 ANR trace、Perfetto 和相邻线程状态判断。

**Q4: Play 的 slow startup、frozen frame、user-perceived LMK 各自的统计边界是什么？为什么"这一帧超过 700 ms"推不出 ANR，"LMK 高于 1%"不能写进发版门禁？**

slow startup 按 TTID（首帧显示耗时）统计，cold ≥ 5 s、warm ≥ 2 s、hot ≥ 1.5 s 计为 excessive——固定秒数识别不了从 1.8 s 退化到 2.4 s 这类未过线的回归，灰度暂停规则仍要比较同启动类型、同设备档的分布，`reportFullyDrawn()` 也不能代替 TTID。slow/frozen rendering 只覆盖 View/UI Toolkit 路径（frozen frame 阈值 700 ms），直接使用 Vulkan/OpenGL/游戏引擎渲染时间的应用可能不在该报表中。user-perceived LMK 统计 28 天内至少经历一次可感知低内存终止（如 Activity 正在显示或前台服务运行时被杀）的 DAU，`ApplicationExitInfo.REASON_LOW_MEMORY` 只是诊断起点，设备整体压力、swap 和应用内存峰值共同参与决策，不能把每次都归咎单一对象泄漏。

两个推论都不能成立的原因在于判定条件不同：frozen frame 超过 700 ms 只说明产生了明显停顿，是否形成 ANR 取决于系统超时条件（输入/广播/服务等各有超时契约），渲染归因应以 FrameTimeline 和线程调度证据为准；LMK 页面把高于 1% 称为需要立即处理的警戒信号，但 Android Vitals 总览没有把 user-perceived LMK 列为 core vital、也没有为它声明商店可见性阈值，所以发版规则里它只能标成内部警戒线。游戏另有 Slow Sessions（仅游戏、运行满一分钟后统计，超过 25% 帧的相邻呈现间隔不低于 50 ms 即 20 FPS slow session），反映用户看到的出帧节奏，不等同于 CPU 单阶段耗时。

**Q5: 用 Play Developer Reporting API 把 Vitals 数据入仓时，哪些口径错误会让曲线"看似完整"却不可信？**

五类高频错误：不读 freshness 就拉数——每个 metric set 提供各粒度最新可用数据点，定时任务应先读 freshness、只在数据推进后拉新增区间，并记录服务端 freshness 与抓取时间；时区混用——`timelineSpec` 的 DAILY 只支持 `America/Los_Angeles`、HOURLY 只支持 UTC，与 Console 窗口和内部看板时区都可能不同；对聚合值二次汇总——`distinctUsers` 是按数量级取整的近似值，官方明确警告不要跨维度行相加，需要整体值时应发起不带 breakdown 的独立查询；7 天/28 天字段是按每日 `distinctUsers` 加权的 rolling rate，服务端已让大流量日期占更高权重，再对日值做简单平均是错的；rate 与 `errorReportCount` 是两种量纲（受影响用户比例与错误报告条数），不能用同一条公式合并。

分页时除 `pageToken` 外必须保持原查询参数不变，否则可能拼出看似连续的假曲线。2026 年稳定性与性能 rate 的主要入口是 `v1beta1`（`vitals.crashrate`、`vitals.anrrate`、`vitals.lmkrate`、`vitals.slowstartrate`、`vitals.slowrenderingrate`、`vitals.excessivewakeuprate`、`vitals.stuckbackgroundwakelockrate`），错误报告计数仍是 `v1alpha1`；metric set 名称与字段应按官方 schema 保存。注意 `stuckBgWakelockRate`（后台持有超 1 小时的用户率）与 core vital 的 excessive partial wake locks（24 小时累计 2 小时、28 天影响 5% 会话）定义不同，仓库可以同时保存两者，但告警字段必须带上具体定义。发版决策上：Play 未越线而内部指标恶化时按内部灰度规则处理，Play 升高而内部无变化时先查分母、渠道、同意范围和上报成功率，不能按"无复现"关闭问题。

**Q6: 一次"打开页面卡住"要建哪些存储观测事件？为什么 wall time 与 CPU time 必须分开记录、事件必须带 scope？**

按失败层次分类建事件，单一的 `storage_slow` 无法判断该检查哪一层：文件调用事件（操作类别、路径类别、线程、wall time、CPU time、字节数、调用点、场景）区分调用方耗时与疑似 I/O 等待；不良形态事件捕获主线程访问、细碎调用、重复读取和大目录遍历；SQLite 执行慢事件（scope、SQL 指纹、事务状态、driver）区分查询本身、排队与连接等待；再加 SQLite 错误、空间快照、文件校验失败和资源未关闭信号。

wall time 是自然经过时间，CPU time 是线程实际占用处理器的时间：前者长而后者短指向调度、锁或 I/O 等待，两者都高更像应用代码计算——这只用于选择下一步证据，不能凭两个时长直接认定内核 I/O。scope 决定同一字段能解释什么：围绕 DAO 方法计时得到调用端到端时长（含协程调度与连接等待），driver 执行边界更接近 SQLite 操作，native `read()`/`write()` Hook 看到的是系统调用（覆盖不了页缓存回写）；字段里只写 `duration` 会让后台把不同 scope 的数据错误合并。路径、SQL 和文件内容可能含用户数据，默认只采集稳定类别、受控指纹和应用调用点，原始证据走受限诊断流程。

**Q7: 线上 I/O 采集为什么优先公开 API 回调而不是 Native Hook？直接 Hook libc 的 read/write 要逐项验证什么？**

采集路径同时决定覆盖面和升级风险，优先级从低风险到高风险：应用封装或库提供的回调（生产长期主路径，看不到绕过封装的三方调用）、编译期插桩（自有字节码的文件入口与 DAO 调用，看不到 native、反射和系统内部 I/O）、StrictMode/BlockGuard（libcore OS 层的线程磁盘读写与泄漏信号，不测设备耗时，三方 native 不覆盖）、Native Hook（覆盖面最广、风险最高，只对少量用户专项灰度启用）。adb 加 Perfetto 属实验室手段，能看到调度、频率、database atrace 与设备允许的 ftrace 事件。

Hook 属于未获平台兼容性保证的手段，即使某一版能拦截 `open`/`read`/`write`/`close`，也要逐项验证：已加载与延迟加载的共享库是否都进入 Hook；32/64 位 ABI、Android 版本与厂商链接器行为是否一致；`pread`/`pwrite`、`readv`/`writev`、`mmap`、`sendfile` 和直接 syscall 是否在覆盖清单；Hook 内部是否有递归保护（采集与上报自身的 I/O 不得再次触发）；路径与 fd 生命周期采集是否线程安全、失败能否回退原函数；远程关闭是否在 Hook 初始化前可用。事件必须带 `collector` 和 `coverage_version`，否则无法区分业务回归与采集器升级造成的数量变化。

**Q8: StrictMode 能证明"主线程发生了磁盘操作"吗？能测出这次 I/O 花了多久吗？为什么不能反射替换 CloseGuard 的 reporter 做长期监控？**

StrictMode 能证明触发、不能测时长。AAOS13 源码核对：`BlockGuardOs` 在 `open`、`read`、`write`、`fsync`、`stat`、`rename` 等 libcore OS 操作前调用线程策略的 `onReadFromDisk()`/`onWriteToDisk()`，所以 StrictMode 回答的是"这个受监控线程是否触发了磁盘操作"，它不测量存储设备完成一次请求的时间；调用发生时数据可能已在页缓存，耗时也可能短于一次帧预算，主线程告警要关联 FrameTimeline 和用户操作后再定优先级。两个使用边界：`setThreadPolicy()` 只作用于调用它的线程，只在主线程安装不能声称覆盖全部工作线程；`detectUnbufferedIo()` 从 API 26 提供、`detectLeakedSqlLiteObjects()` 从 API 9 提供（AAOS13 均已核对存在），适合 debug、自动化测试与内测包，生产开启要先评估成本。

`CloseGuard.setReporter()` 在 AAOS13 仍标记为 `@hide`（已核对），普通应用没有稳定的公开调用契约；反射替换 reporter 会同时引入 non-SDK 限制和版本兼容风险。长期监控应使用公开的 StrictMode VM policy（`detectLeakedSqlLiteObjects()`、`detectLeakedClosableObjects()` 等）并限制在测试与受控诊断场景。

**Q9: 一个 DAO 方法耗时 300 ms，怎么分层定位慢在 SQL 本身、连接等待还是结果映射？验证查询计划时要注意什么？**

按计时 scope 分层，一层排除一类原因：DAO 端到端时长回答"用户路径中等待多久"，包含排队、协程调度和结果映射；transaction scope（`begin` 到 commit/rollback 返回）暴露锁持有窗口与批量写范围；driver statement scope（prepare/step 到完成）最接近 SQL 执行与取数成本；exception/recovery scope 记录错误类别与恢复结果。若 DAO 层高而 driver 层低，慢在调度或结果映射，不在 SQL 计划。

`RoomDatabase.QueryCallback#onQuery()` 只在查询执行时提供 SQL 与绑定参数，没有开始和结束时间——在回调的 Executor 里计时只会得到处理回调本身的时间；官方提示它有额外成本，应按需启用并采样，参数只记类型、SQL 先归一化删除敏感字面量再算指纹。确认 SQL 本身慢后，用 `EXPLAIN QUERY PLAN` 在同一 SQLite 实现上验证计划：`SCAN` 表示扫描，`SEARCH ... USING INDEX` 表示用了索引，`USE TEMP B-TREE` 说明排序或去重可能要临时结构。计划节点不是自动修复指令：小表扫描可能合理，索引增加写入与空间成本，复合索引列顺序要结合过滤、排序和选择性判断。官方建议用目标设备的 `adb shell sqlite3`（不同版本 SQLite revision 不同）；使用 `BundledSQLiteDriver` 时应用携带自己的 SQLite 实现，设备自带 sqlite3 与它可能不同，应用同一 driver 和 schema 的测试工具执行。

**Q10: Android 框架内部的 SQLite 诊断信息（OperationLog、语句缓存统计、慢查询开关）能搬进普通 App 吗？AAOS13 与 Android 17 有什么差异？**

不能——这些诊断都是框架私有或 `@hide`，普通 App 没有对应采集接口。AAOS13 源码核对：`SQLiteConnection.OperationLog` 保留 `MAX_RECENT_OPERATIONS = 20` 条最近操作，只服务于 framework 调试与 dump；材料核对的"严格超过 2 秒的操作记入长操作"（`LONG_OPERATION_THRESHOLD_MS = 2_000`）是 Android 17 的实现，AAOS13 树中不存在该常量，2 秒也不应复制成业务慢查询门槛。`SQLiteConnectionPool#getStatementCacheMissRate()` 在 Android 17 带 `@hide`（AAOS13 树中未见该方法）。

公开侧的边界：每连接 prepared statement cache 默认 25、`setMaxSqlCacheSize()` 公开上限 100（AAOS13 已核对 `SQLiteDatabaseConfiguration` 默认 25 与 `MAX_SQL_CACHE_SIZE = 100`），没有内存与命中率证据时不应把缓存调到上限；`setIdleConnectionTimeout()` 已废弃，文档警告重建连接会清除 per-connection PRAGMA 且系统没有恢复回调；`setLookasideConfig(0, 0)` 只是请求禁用 lookaside，系统可能按设备选择不同值。开发设备可用 `adb shell dumpsys meminfo <package>` 查看缓存命中统计，普通应用没有免权限的生产 API；`SQLiteDebug.shouldLogSlowQuery()` 读取带 UID 后缀的系统属性、受日志标签控制，是隐藏调试开关，不能当动态下发阈值方案。结论：线上用自己 driver 层或回调采集，framework 细节只用于理解平台行为。

**Q11: SQLite 报错按 message 搜 "corrupt" 为什么不可靠？发现损坏后的恢复策略要区分什么？远程清理要满足什么条件？**

错误分类要看主错误码与扩展错误码，异常 message 只是文本：`busy`/`locked` 说明并发或锁状态，`full` 说明写入空间不足，`IOERR` 指向 I/O 路径，`CORRUPT`/`NOTADB` 才接近数据库内容或格式问题——按 message 搜 "corrupt" 会把不同性质的错误合并到同一处理路径。事件至少记录数据库别名、driver 与库版本、异常类、主/扩展错误码（driver 提供时）、事务状态、WAL/SHM 文件是否存在及大小、剩余空间、恢复动作与结果；message 可能带 SQL 或路径，进日志前要脱敏。

`PRAGMA integrity_check` 会读取大量页面，不适合在前台或每次启动执行，应放在维护窗口、数据库副本或用户明确发起的诊断流程中并记录检查覆盖。恢复策略按数据性质分三类处理：可再生缓存直接删除重建；可从服务器重建的数据走重新同步；唯一用户数据必须先尝试导出保存——默认删除数据库会让"恢复成功"掩盖数据丢失。应用私有可替换文件用 `AtomicFile` 或"先写临时文件、成功后 rename 替换"的协议；数据库文件交给 SQLite 的事务与 journal/WAL 机制，不自行拼装或远程删除 `.db`、`-wal`、`-shm` 文件。远程清理是破坏性能力，需要固定 allowlist、规则版本、dry-run 先行、幂等执行和远程关闭开关；未知文件、唯一用户数据、打开中的数据库文件都不能按"疑似缓存"处理。

**Q12: 网络质量监控为什么要同时保留客户端、接入层、系统网络状态三层观察？接入层没有这条请求记录时能丢弃客户端样本吗？**

三层各回答一个不同的问题：客户端样本回答用户当时的经历（阶段耗时、失败异常、路由尝试、页面场景），盲区是上报通道自身受故障影响、采样和延迟上传会改变可见分布；接入层日志回答请求是否到达入口、入口流量与状态码分布，看不到 DNS 失败、建连失败和被代理/VPN 拦截的请求；系统网络状态（`NetworkCapabilities` 等）解释默认网络、VPN、计费与门户验证，拿不到驱动、基站和运营商内部路由。

对账时按 `trace_id`（业务请求路径）、`request_id`（网络库一次逻辑调用）、`attempt_id`（一次路由或连接尝试）分成三个集合：两侧都有记录的可比较端到端耗时与服务端耗时；只有客户端记录的用于分析入口前失败（DNS、运营商、CDN、证书、网络切换）；只有接入层记录的提示客户端采样、ID 注入或上报丢失。DNS、connect、TLS 阶段失败的 attempt 不会到达服务器，服务端自然没有同名 ID——这些记录必须保留，并保存候选地址数量、脱敏后的 peer 分组、库级错误枚举、TLS 错误类别、代理/VPN 标记等受控证据；原始 DNS 列表、完整 IP、完整 URL 和查询参数不应作为通用遥测字段。重定向和重试还要按 `exchange_id` 区分，避免把多次响应的字节数和耗时相加后当成一次请求。

**Q13: OkHttp EventListener 和 Cronet Metrics 的阶段事件为什么不能假设序列固定？连接复用时"阶段为空"为什么不能记成 0 ms？**

事件序列由库的重试、回退和复用策略决定：OkHttp 的 Fast Fallback 会交错尝试多个地址，同一个 `Call` 中 connect 系列事件和 `connectionAcquired` 都可能出现多次；重定向与认证质询产生新的 exchange；连接复用时 DNS、connect、TLS 事件完全缺席。Cronet 的 `RequestFinishedInfo.Metrics` 对没有发生或无法取得的阶段返回 `null`，复用 socket 时 DNS/connect/SSL 均为空；反过来"存在 DNS 事件"也不能等价于"访问了远端 DNS"——DNS 命中本地缓存但未复用 socket 时 Cronet 仍可给出 DNS 时间戳。因此每个阶段要同时记录 observed、not_observed 或 unsupported：复用是"阶段未发生"，记成 0 ms 会把缓存连接伪装成瞬时建连。

版本边界：OkHttp 与 Cronet 都独立于 Android 平台版本发布，不能从平台 API level 推导事件语义；材料口径（2026-08）OkHttp release 为 5.4.0，`cronet-api:500.0.1` 虽被标为 release 但其 POM 说明这是指向 `org.chromium.net:cronet` 的废弃过渡空工件——事件必须记录网络库、库版本、provider、引擎版本和 `negotiated_protocol`。QUIC/HTTP/3 下 `connect_ms` 不能固定解释为 TCP 三次握手，`secure_handshake_ms` 也不一定是 TLS；字节字段同样要分清来源：`Metrics#getReceivedByteCount()` 是当前请求的传输层接收字节（不含之前的重定向），`UrlResponseInfo#getReceivedByteCount()` 从请求开始累计并包含重定向，两者不能混入同一指标序列。

**Q14: TrafficStats 的字节数为什么必须按相邻差值使用？`registerDefaultNetworkCallback()` 之后应该在哪一步读网络属性？**

`TrafficStats` 提供的是自开机以来所有网络接口上网络层流量的累计计数器（含 TCP 与 UDP），设备重启后归零；`getUidRxBytes()`/`getUidTxBytes()` 聚合同一 UID 下的所有进程，Android 7.0 起查询其他 UID 返回 `UNSUPPORTED`，设备不支持某项统计时也返回 `UNSUPPORTED`（数值为 -1，不是有效字节数），`getTotal*` 系列是整机口径。看板必须保存 `boot_id`（或等价的开机标记）、采集时间和前后差值；发现计数变小、启动标记变化或任一端为 `UNSUPPORTED` 时丢弃该区间差值。`tagSocket()` 只能给 socket 计账加标签，不产生 DNS、握手和首包时间，不能替代网络库的逐请求事件。

网络状态要按样本发生时记录：Android 8.0 及以上在 `onAvailable()` 之后才会回调 `onCapabilitiesChanged()` 和 `onLinkPropertiesChanged()`，在 `onAvailable()` 里同步查询新网络属性会遇到时序竞争；回调运行在 `ConnectivityManager` 专用线程，里面只应更新创建后不再修改的内存快照，耗时计算与上传放到工作线程，用完注销。语义边界：`NET_CAPABILITY_INTERNET` 表示被配置为可访问互联网、不代表已连通；`NET_CAPABILITY_VALIDATED` 表示系统探测到公共互联网，仍不保证业务域名可达；`CAPTIVE_PORTAL=true` 且非 `VALIDATED` 是门户登录的重要旁证。transport 是集合：VPN 可以同时带 VPN、Wi-Fi 与蜂窝承载，数据模型要保存集合而不是单值枚举。`onLost()` 只说明这张网络不再是默认网络，未必已断开；显式绑定其他 `Network` 的请求要用该请求选中的快照。`Network` 对象仅在连接存续期内有效，重连后是新对象，只能端侧短期关联。

**Q15: 功耗分析常把哪四类不同性质的数据混为一谈？Battery Historian 能回答其中哪个、不能回答哪个？**

四类数据要分开：状态与事件时间线（Batterystats 历史、system trace、应用 Trace）回答"某段时间发生了什么、哪些行为重叠"；本 UID 资源计数（`SystemHealthManager.takeMyUidSnapshot()` 的 HealthStats、应用埋点）回答 CPU 时间、网络字节、WakeLock 与 Job 时长怎样变化；系统归因估算（`BatteryUsageStats`、设置页、bugreport）回答系统怎样把组件能耗估算到 UID——数值仍受设备功耗模型限制（AAOS13 的归因走 `*PowerCalculator`，Android 17 才是 `PowerAttributor`/processor 管线，差异见功耗机制文档）；设备级能量（ODPM 电源轨、外置功耗仪）回答实验窗口内整机或子系统的能量差。

Battery Historian 只是把 bugreport 中的 Batterystats 等记录转成可交互时间线的离线工具（官方已标注不再积极维护），它属于第一类：能帮助回答"电量下降时屏幕、CPU、Job、网络、定位和 WakeLock 处于什么状态"，不能直接证明某个事件消耗了多少能量。能量与功率也要分开：能量是窗口内累计消耗，平均功率等于能量增量除以时间增量；电池百分比经过量化与系统估算，短窗口内没有下降不能推导为"零消耗"。

**Q16: API 35 的 `PowerMonitor` 读数为什么"单次累计值没有场景意义"？AAOS13 上能用吗？**

AAOS13 不可用：`SystemHealthManager` 的 `getSupportedPowerMonitors()` 与 `getPowerMonitorReadings()` 从 API 35 起公开（AAOS13 源码核对不存在这两个方法），Android 13 及更早版本没有这条公开路径。可用平台上也要按正确语义使用：`PowerMonitorReadings` 返回自开机以来的累计能量（单位微瓦秒，包含电池供电与插电阶段），重启后不连续——单次读数没有场景意义，正确用法是同一组 `PowerMonitor` 在场景前后各读一次，按各自 `timestamp`（来自 `SystemClock.elapsedRealtime()`）计算非负增量；跨重启、计数回退或 `ENERGY_UNAVAILABLE` 的样本应丢弃。

三条使用边界：支持列表可能为空，电源监视器的名称与含义依设备而变，名称相同也不代表不同 OEM 的计量范围等价；普通 App 读数可能被缓存并加入与调用 UID 相关的随机噪声，高频读取得不到仪器精度，也不应尝试反推去噪；电源轨是设备级数据，App 只能在受控实验中用 Trace 时间窗做相关分析，不能把电源轨增量直接记为当前 App 的能耗。硬件通道名称可能暴露机型与硬件组合，生产上报要先评估设备指纹风险，并对采样频率和保留期设限。

**Q17: 普通 App 在 Android 13/17 上还能从系统读到哪些功耗相关数据？哪些路径走不通？**

公开可用的有两层。本 UID 层：API 24 起 `SystemHealthManager.takeMyUidSnapshot()` 返回本 UID 的 `HealthStats`（用户态/内核态 CPU 时间、Wi-Fi 与移动网络字节、WakeLock、Job、Sync、传感器、前后台状态等键），它是资源代理指标而不是能量测量；读取前必须用对应的 `has…()` 检查键是否存在，共享 UID 会把多个包的统计记到同一身份，系统代持的 WakeLock 和库内部调度也会影响解释。电池状态层：`BatteryManager` 公开电量、充电状态、瞬时/平均电流、charge counter（微安时）和 energy counter（纳瓦时）等属性，描述整块电池或燃料计状态、不提供 App 归因；设备可以不支持某个属性——`getIntProperty()` 对 targetSdkVersion 为 Android 9 及以上的应用返回 `Integer.MIN_VALUE`（更旧目标返回 0），`getLongProperty()` 返回 `Long.MIN_VALUE`，API 35 新增的 `getStringProperty()` 返回 `null`。

走不通的路径：`BatteryStatsManager#getBatteryUsageStats()`、`BatteryUsageStatsQuery` 和按 UID 获取 `BatteryConsumer` 的路径都带 `@hide`，且受 `BATTERY_STATS` 权限保护（Android 17 清单声明为 `signature|privileged|development`，AAOS13 同样不是普通应用可得）；`SystemHealthManager` 也没有 `getBatteryUsageStats()`、`registerBatteryStateCallback()` 或 `getCurrentPowerStats()`。普通 App 不能复制系统设置或 system_server 的调用代码获取全设备 `BatteryUsageStats`——这类信息应通过 adb、bugreport、平台测试组件或 OEM 授权的系统应用获取。

**Q18: 验证一个"后台同步更省电"的改动，为什么"功率降低了"或"时间线更安静了"都不算结论？网络功耗的固定排名（Wi-Fi 低、5G 高）为什么不可用？**

功耗优化必须同时观察"完成了多少工作"和"付出了多少能量"：只降低功率可能让任务执行更久、总能量反而增加，只缩短耗时也可能抬高峰值功率和温度。每次实验至少保留五组数据：场景产出（完成的同步数、请求量）、性能（耗时、CPU 时间、字节）、能量（整机或所选 `PowerMonitor` 的增量）、环境（温度、亮度、网络、充电状态、版本）和正确性（失败率、数据时效）。A/B 在等价条件下交替运行基准与候选实现（同设备、同场景、相近初始状态，并保留不执行待测场景的空闲基线），结论只填测量得到的分布、样本条件和不确定性，不预写固定百分比或"续航增加几小时"；某次 Historian 时间线更安静，也需要多轮实验与能量增量支持。

网络功耗的固定排序不成立，因为信号质量、频段、基带状态机、扫描、连接建立、传输时长、数据量、硬件代际和共享芯片都会改变结果：5G 不统一解释为更耗电，弱信号或频繁扫描的 Wi-Fi 同样可能很贵。`TrafficStats` 或 HealthStats 的字节数只表示活动量，能量还取决于传输时间和无线状态，"每 MB 固定耗电"不能跨网络和设备复用。优化假设要逐项验证：合并可延期请求可减少 radio 活跃次数但增加等待与单次失败影响；连接复用减少握手成本而频繁主动断开可能增加 radio 状态切换；预取可能下载用户永远不用的数据；WorkManager 的网络约束只适合可延期任务，交互请求仍按用户时效执行。

**Q19: 字节码插桩能改什么、不能改什么？"无业务手写埋点"为什么仍不等于零侵入？**

字节码插桩在源码编译成 JVM `.class` 之后、生成 DEX 之前自动检查或改写指令，只能处理进入当前 App 构建流程的 class；不能修改 Android framework、ART 或任意第三方库的内部实现——普通 App 的 AGP 插桩改不了设备 boot classpath 上的 `Choreographer`、`ActivityThread`、`Looper`，运行时反射或 ART hook 受隐藏 API、版本差异和完整性策略影响，不应作为常规生产方案。帧与主线程监控应优先 JankStats、`FrameMetrics`、Macrobenchmark 与 Perfetto。

可维护的插桩方案分四层，每层有典型错误：选择规则决定哪些 variant、class、method 需要处理（release 无条件全量插桩、误改生成代码是常见错误）；字节码变换要保证控制流、操作数栈和 frame 合法（只处理正常 `return`、异常路径没有清理）；运行时桥接负责采样、限流、隐私处理并写入 Trace/APM（在热路径分配对象、同步 I/O 或递归调用）；验证发布要校验 class、D8/R8 产物与运行时成本（只看编译成功、不检查优化后产物）。"无手写埋点"仍有侵入：每条注入指令都改变 class、构建时间和运行路径，是否启用、覆盖哪些方法以及容许多少成本，都应由当前工程的测量结果决定。

**Q20: Transform API 已经怎样了？用 AGP Instrumentation API 注册 `AsmClassVisitorFactory` 要遵守哪些约束？**

旧的 `Transform` API 在 AGP 7.2 废弃、AGP 8.0 移除，且没有覆盖所有旧用法的单一替代：逐 class 变换用 `variant.instrumentation.transformClassesWith()`；读取或变换整组 class 用 `variant.artifacts.forScope()` 与 `ScopedArtifact.CLASSES`；在编译后生成新 class 且还要读已编译 class 时用 `ScopedArtifact.POST_COMPILATION_CLASSES`（AGP 9.3.1 才加入且标 `@Incubating`，材料口径——构建侧版本不在本地源码树）。ASM 库本身也有 Core API（visitor 流式回调，适合入口/出口/调用点替换等局部操作）与 Tree API（读入 `ClassNode` 便于多次遍历与控制流分析，内存成本更高）的选择；需要全程序调用图时逐 class 信息不足，应走 Scoped Artifacts 独立 task。

注册 factory 的硬约束：`isInstrumentable()` 与 `createClassVisitor()` 可能被异步、并发调用，factory 不能用可变全局集合统计结果或读写共享文件；所有配置必须声明为 Gradle `Property` 系输入，回调里临时读取未声明的文件会破坏 up-to-date 判断与 build cache 命中；ASM API 版本应取 `instrumentationContext.apiVersion`，不要把上游最新版（材料口径 2026-08 为 9.10.1）写死进 visitor。范围控制：`InstrumentationScope` 默认 `PROJECT`（自有代码），`ALL` 会处理传递依赖、可能重复插桩已插桩库并扩大兼容面；Android library 只能对本项目 class 注册。给既有方法增加控制流时用 `FramesComputationMode.COMPUTE_FRAMES_FOR_INSTRUMENTED_METHODS` 让 AGP 重算 frame，只加注解可用成本更低的 `COPY_FRAMES`，`COMPUTE_FRAMES_FOR_ALL_CLASSES` 触发非增量全类计算应避免。

**Q21: 给方法插 `Trace.beginSection()/endSection()` 时，为什么只检查 RETURN 和 ATHROW 两条退出路径不够？section 名称与协程有什么限制？**

`RETURN` 和 `ATHROW` 只覆盖显式出现在当前方法字节码中的退出指令：`repository.load()` 抛出的异常会沿调用栈传播，当前方法没有自己的 `ATHROW`，却在 `INVOKEVIRTUAL` 调用指令处退出——只看退出 opcode 时 `beginSection()` 无法配对，后续同线程的嵌套 section 全部错位。稳妥做法是给原方法体加 catch-all handler，语义等价 `try/finally`：正常返回前调用 `endSection()`，异常路径由 handler 调用后原样重抛；ASM 的 `AdviceAdapter` 已处理"构造方法必须等父类构造完成"的限制。注册了新增控制流后必须选择能重算 frame 的 `FramesComputationMode`，并用包含多 return、显式 throw、被调用方法抛异常、try/catch/finally 的 fixture 验证正常与异常路径 begin/end 数量相等。

平台契约（AAOS13 已核对）：`android.os.Trace` 的同步 section 必须在同一线程成对并正确嵌套，名称上限 127 个 UTF-16 code unit（`MAX_SECTION_NAME_LEN = 127`；AAOS13 的 Java Trace 走 libcutils trace_marker 单路径，Android 15+ 才有 TrackEvent 路径可选）。tag 应在构建期生成固定值、替换竖线/换行/空字符并处理截断时的 UTF-16 代理对，且不包含业务参数、URL 或账号。`Trace.isEnabled()` 从 API 29 提供：固定字符串的 `beginSection()` 可以直接调用（平台内部会检查 tracing 状态），只有运行时构造临时对象或格式化字符串时才值得先检查。Kotlin 协程是结构性例外：suspend 函数的主要执行逻辑位于生成的 `ContinuationImpl.invokeSuspend()` 状态机，一次源码调用可能跨线程恢复多次，同步 section 无法表达跨线程生命周期——需要异步 trace 或支持关联信息传播的 API；Compose 则用官方 `runtime-tracing` 而不是基于生成方法名的 ASM 规则。

**Q22: 插桩产物进入 R8 之后，为什么必须在 minified release 上验证 trace？"注入直接调用"和"反射桥接"对 keep 规则的要求差在哪？**

AGP Instrumentation 产生的 class 会继续进入 D8/R8，R8 的内联、合并、删除和 outlining（把重复指令抽成共享方法的优化）都会改变发布产物中的执行形态，只检查未优化 class 不能证明线上 trace 正确。keep 要求分三类：注入的是直接方法调用时，R8 能从调用图找到桥接类，通常无需为整包加 `-keep`；桥接类通过反射或 JNI 按名称查找时，R8 无法从调用图推导目标，需要精确 keep 规则；监控要求与源码方法一一对应时，必须接受发布产物形态变化并直接在 minified release 上验证。不要为保留 trace 结构对整包禁用优化，正确顺序是缩小插桩范围、确认关键方法在 release 中的形态、再为少量边界设规则。

完整验证链有四步：class 级 fixture 测试（`CheckClassAdapter` 不报 verifier 问题、隔离 ClassLoader 可加载执行、原返回值与异常 cause/suppressed 不变、重复经过插件不二次注入——`ClassWriter.COMPUTE_FRAMES` 能修 frame 但证明不了业务语义）；Gradle 集成测试（clean/incremental、configuration cache、build cache、多 variant 多模块）；minified release 产物检查（APK/DEX 大小、R8 `mapping.txt`/seeds/usage 归档、目标调用存在、排除类未被修改）；代表设备上采集 Perfetto 检查 section 嵌套与 R8 后名称。若 trace tag 保存插桩前类名会暴露内部命名，可改用稳定 method ID 加受控映射，与崩溃栈还原用的 `mapping.txt` 分开保存授权。成本门禁用本工程启用/禁用插桩的 A/B 实测建立，不用文章固定百分比。

**Q23: 在量产 user build 上，谁有权对一个应用做 native heap 采样？普通 App 想在线上采自己的堆 profile 应走哪条路？**

权限主体按"会话发起者 + 目标应用属性"判定（材料按 Android 17 的 `CanProfileAndroid()` 核对；heapprofd 自 Android 10 引入，本地 AAOS13 树无 `external/perfetto`，但 bionic 侧已核对）：shell 或未指定发起者要求目标声明 `profileable_from_shell`（`<profileable android:shell="true" />`）或 `debuggable`；trusted-system 发起者（`traced` 赋予受信系统会话的身份，普通 App 写进自己的配置也不会获得）只要求 `profileable` 或 `debuggable`。user build 上平台 UID（小于 `AID_APP_START`）只允许 trusted-system 发起，isolated process 判定有意从严；installer 过滤（`target_installed_by`）只会缩小候选集合、不会授予权限。AAOS13 已核对 bionic 的 `malloc_heapprofd.cpp`：安装是多步流程，且已有不兼容 malloc hook（如 GWP-ASan/malloc debug 占用 dispatch）时 heapprofd 会拒绝安装。

普通 App 的线上路径是 Android 15+ 的 `ProfilingManager` 请求自己的 heap profile：系统核对 Binder 调用 UID 与包名、配置目标固定为调用方包名、受单应用与全系统限流，请求被接受只表示开始尝试、不保证生成结果文件（`ERROR_FAILED_RATE_LIMIT_PROCESS`/`_SYSTEM`/`_INVALID_REQUEST` 等错误码要分别记录）；`:remote` 等次要进程不会自动加入。AAOS13（Android 13）没有 `ProfilingManager`。QA 复现走另一条路：release APK 声明 `android:shell="true"` 后在 user build 上由 shell 侧 Perfetto/`tools/heap_profile` 采集——它依赖本地调试通道，不代表 App 能在用户手机上自行启动系统采集。

**Q24: 用 heapprofd 判断 native 泄漏，为什么第一个 dump 不能当基线？哪些"看起来在涨"其实不是 malloc 泄漏？**

heapprofd 只记录采集窗口内经过受支持分配器（默认 heap 为 `libc.malloc`，覆盖 Bionic 的 malloc/free 与 C++ new/delete 路径）抽样到的分配与释放，不扫描完整堆快照——attach 之前已存在的分配没有历史事件，第一个 dump 无法代表完整 native heap。判断泄漏至少需要：两个以上连续 dump（`continuous_dump_config` 周期输出）、可重复的操作序列，以及场景结束后观察是否回落的稳定窗口；用 `heap_profile_allocation` 表按 callsite 汇总正样本（分配）与负样本（释放）得到净存活字节，相同调用栈跨 dump 增长、场景退出后不回落且多轮复现一致，才构成较强线索。

三类常见误判：一是分配器缓存仍保留页面——应用已 free 但分配器保留 arena/page，存活分配估算已回落而 RSS 不变；二是增长来自 mmap 或图形内存——heapprofd 默认不看 `mmap`/`munmap` 直接建立的映射，DMA-BUF 与 GPU 内存也没有分配器调用栈语义，PSS 上升而 heapprofd 平稳时应转查匿名映射、memtrack、`dmabuf_dump`；三是 Java 引用保住 native 对象——heap profile 不提供引用关系，需要 Java heap dump 补充。参数边界：`sampling_interval_bytes` 是平均每 N 字节取一个样本（1 表示逐次），增大降低开销但漏掉小分配；`block_client` 在 buffer 满时让目标进程等待，线上测量通常关闭以免阻塞高频分配线程；daemon 的 memory/CPU guardrail 每 30 秒检查一次、命中后直接关闭对应 data source，且 `max_heapprofd_memory_kb` 限制的是 heapprofd 自身而非目标 App。

**Q25: 普通应用为什么读不了 `/proc/stat` 和 `/proc/loadavg`？"CPU 使用率"的核等价口径与整机占比口径差在哪？**

AAOS13 源码核对两层限制：`system/sepolicy/private/app_neverallows.te` 用 neverallow 禁止所有 untrusted_app 域读取 `proc_stat`、`proc_loadavg` 等节点——neverallow 在策略编译期强制检查，降低 `targetSdk` 也无法恢复，且 `untrusted_app_all.te` 对读取失败做了 `dontaudit`（只抑制审计日志、不授权，应用侧失败时未必有醒目 denial）；first-stage init 以 `hidepid=2,gid=AID_READPROC` 挂载 procfs（AAOS13 `first_stage_init.cpp` 已核对），其他 UID 的进程目录被隐藏。普通应用稳定可依赖的是 `Process.getElapsedCpuTime()`（AAOS13 已核对）加 `/proc/self/stat` 与自身 `task` 节点。

两种百分比口径不要混用：核等价利用率 = Δ进程 CPU / Δwall × 100%，100% 表示约占用一个核、多线程可超 100%，不需要 `/proc/stat`；整机容量占比 = Δ进程 / Δ全机累计 CPU，需要全局计数，普通应用在 AOSP 上算不了。把核等价除以 CPU 数必须先定义分母（物理核、在线核、cpuset 允许的核或按调度容量加权），移动设备有热插拔与大小核，简单除以 `Runtime.availableProcessors()` 只是近似。分母还应区分设备醒着（`uptimeMillis()`，深度睡眠时停走）与完整窗口（`elapsedRealtime()`，含睡眠）。解析 `/proc/self/stat` 有一个必踩的坑：`comm` 字段被括号包围且可含空格和右括号，按空格切整行会错位，必须先找最后一个 `)`：

```kotlin
val line = File("/proc/self/stat").readText()
val tail = line.substring(line.lastIndexOf(')') + 1).trim().split(Regex("\\s+"))
// tail[0] 对应字段 3（state）；utime/stime/starttime 分别为 tail[11]、tail[12]、tail[19]
```

计数回退、`starttime` 变化（PID 复用）或读取失败都要丢弃本轮差值，不能拿 -1 继续算。

**Q26: `ProcessCpuTracker` 是什么、谁能用？自建采样器从它身上要避开哪些坑？**

`ProcessCpuTracker` 位于 `com.android.internal.os`，是 Android 框架内部的全进程 CPU 采样类（AAOS13 已核对存在），不属于 SDK API。AAOS13 的 `AppProfiler` 在 `system_server` 内持有它：一次 `update()` 会读 `/proc/stat`、用 `Process.getPids("/proc", ...)` 枚举全部可见进程、对每个 PID 读 `/proc/<pid>/stat` 计算增量（含 `rel_minfaults`/`rel_majfaults` 缺页增量），可选扫描线程目录并读取 `/proc/loadavg`；结果用于 ANR 诊断输出、进程 CPU 统计与 BatteryStats 归因。普通应用同时受两层约束：类本身是隐藏 API、反射调用没有兼容性保证；即使调用成功，SELinux 与 procfs 挂载权限也不会随之绕过——第三方 APM 应使用公开 API 采集自身进程，系统级诊断交给 Perfetto、bugreport 或受控平台服务。

自建采样器要避开它已暴露的三个坑：其一，AAOS13 源码中累计回退检查写成 `if (true || ...)`，该分支实际总会接受读数——自建采样器遇到负差值必须丢弃样本，不能照抄这个行为；其二，同一个类内部就存在不同的百分比定义（`getTotalCpuPercent()` 的忙时间不含 iowait 和 softirq，而 proto 输出的总时间包含），使用内部数据时应直接选取需要的增量字段并在指标协议里写明公式；其三，全 PID 扫描是长操作，它每轮仍要枚举 `/proc`，框架源码注释还要求调用方避免在关键锁路径上持有其锁——应用侧常态只采自身进程累计 CPU，异常窗口再临时加线程维度，且不在主线程读取 procfs（StrictMode 会把这类文件 API 归入 disk read）。

**Q27: minor fault 和 major fault 的计数边界在哪？为什么不能用 Δfaults × 4 KB 估算分配字节？**

minor fault 指内核成功完成、最终不带 `VM_FAULT_MAJOR` 且处理过程中没有 retry 的缺页，常见来源是匿名页按需分配、写时复制（COW）和"页缓存已有数据、只需建立 PTE"；major fault 指成功完成但带 `VM_FAULT_MAJOR` 或发生过 retry 的缺页，对应文件页读入与 zRAM/后备存储的 swap-in。计数时机有三处差异（材料按 Android 17 与 6.18 内核核对，本地 AAOS13 树无内核目录）：Simpleperf 的 `page-faults` 在 arm64 校验 VMA 之前计数，包含后来失败的访问；`min_flt`/`maj_flt` 在 `handle_mm_fault()` 成功返回后才记账，`VM_FAULT_ERROR`（最终 SIGSEGV/SIGBUS 的失败访问）不进入任何 fault 计数——所以 `page-faults` 与 minor+major 之和出现差值是有源码依据的，排查时同时检查失败访问、统计区间和工具权限。

换算陷阱有四个：Android 15 起存在 16 KB 页设备，页大小必须运行时查询（`Os.sysconf(OsConstants._SC_PAGE_SIZE)` 或原生 `getpagesize()`），4 KB 只是旧默认；minor fault 还包含 COW 与页缓存映射，同一虚拟区域被回收后再次访问会再 fault；分配器复用已驻留的堆页时，发生分配却没有新增 fault；readahead 和大 folio 让一次 major fault 与一页 I/O 失去一一对应。fault 计数是同步异常的次数，不等于阻塞时间；major 增长只有与关键线程等待存储在同一时间段出现，才支持"I/O 影响关键路径"的判断。改进手段按原因选：冷启动文件页查 Baseline Profile 覆盖与编译产物布局，匿名页/COW 查初始化时机与 Zygote 继承页写入，swap-in 查内存压力与 zRAM 配置；`madvise(MADV_WILLNEED)` 只是把等待前移的提示，不保证读入或保留页面。

**Q28: 从系统调用层重建 Binder 调用语义为什么这么难？`BINDER_WRITE_READ` 的 ioctl 耗时能当 Binder RPC 耗时吗？**

Binder 驱动只处理 transaction code、flags、目标 handle、数据缓冲区和对象 offsets，方法名与 Java/Kotlin 参数类型不在 Binder 内核 ABI 中——要还原"哪个方法被调用"需要四层证据逐级拼接：syscall 层（ioctl 参数与返回值）、Binder UAPI 层（`BINDER_WRITE_READ` 命令字、transaction code、flags、数据长度）、Parcel 层（interface token、字节序列、对象 offsets）、签名表层（descriptor + code 到方法与参数类型的映射）。签名表必须与 `Build.FINGERPRINT`、AIDL 接口版本和采集器版本绑定，同一个 transaction code 跨系统版本不保证对应同一方法；复杂 Parcelable、vendor 接口和动态注册接口都没有系统性覆盖。

ioctl 耗时不能当单次 RPC 耗时：一次 ioctl 的 write buffer 可以包含多条命令，也可能进入读取路径等待工作，oneway 事务不同步等待回复。端到端时延应分段计算：客户端应用 slice + `binder_transaction`/`binder_transaction_received` tracepoint（给出事务调试编号、目标进程/线程、reply 标记）+ 服务端 slice；tracepoint 是元数据，不含完整 Parcel 内容。研究方案（WOOTdroid 的 WDBind）在驱动 `copy_from_user()` 之前读用户地址，存在 TOCTOU、短读和 arm64 地址标签（TBI/MTE）风险，且 v1 不处理 reply——实验只在已 root 的 Android 16 Pixel 上做过，不能外推到量产 user build。权限边界：自定义 eBPF 不是应用公开 API，平台 BPF 程序随系统镜像由 loader 加载（加载链与普通应用的权限边界已在工具文档按 AAOS13 核对）；普通应用的系统侧证据走 Perfetto 与 `ProfilingManager`。

**Q29: Profilo 的 ATrace provider 到底捕到了什么？"它采集的 trace 与 Perfetto system trace 一样"错在哪？**

Profilo（Meta 开源，上游 2023-02 归档、README 声明 API 不稳定）在 API 27+ 的实现是：`dlsym()` 查找 libcutils 私有变量 `atrace_enabled_tags` 与 `atrace_marker_fd` 的地址，对 `libcutils.so` 的 `__write_chk` 安装 PLT hook，启用时把 tag mask 原子交换为全 1；之后命中 hook 的 ATrace 写入只解析 `B`/`E`（同线程同步 slice 开始/结束）转写进 Profilo 缓冲区并直接返回成功——异步事件 `S`/`F`/`G`/`H`、instant `I`/`N` 和 counter `C` 被静默丢弃，调用方无法从返回值发现丢失。AAOS13 源码核对：`trace-dev.cpp` 先打开 `/sys/kernel/tracing/trace_marker`（失败回退 debug 路径），`atrace_enabled_tags` 是普通 `uint64_t`——Profilo 把 `dlsym` 地址当 `std::atomic<uint64_t>*` 操作属于私有 ABI 假设。

"与 system trace 一样"错在两点：可见范围上它只改本进程的重定向槽，能看到的是当前进程内 framework/ART/HWUI 执行到的 ATrace 点，触不到 `system_server`、SurfaceFlinger，也没有 sched、Binder、块 I/O 等内核事件——它只是一份"当前进程同步 slice 的应用内副本"；完整性上，启用期间命中 hook 的写入不再进内核 trace_marker，与 Perfetto system trace 并发采集会缺本进程的 ATrace 事件，必须禁止重叠或把缺失写进采集协议。继续维护 fork 时应做能力协商（安装失败上报并跳过该 provider）、事件语义测试（嵌套、多线程、缓冲区回绕、启停后 tag mask 恢复）与目标构建的开销实测；其 Java 栈采样依赖的 ART 内部布局版本表只列到 Android 9，不能宣称 Android 17 支持。

**Q30: 新项目要做线上应用内 trace 或系统级追踪，公共选项有哪些？Profilo 的架构还有什么参考价值？**

按需求选公共入口：只需业务标记时，Java/Kotlin 用 `android.os.Trace` 或 AndroidX Tracing（材料口径 2026-08 稳定版 1.3.0），native 用 NDK ATrace——这些 API 只发标记，采集端启用对应类别后标记才出现在 Perfetto system trace 中；需要线上应用内采集时，评估 AndroidX Tracing `2.0.0-beta01`（可插拔 backend/sink、可把事件写成 Perfetto trace packet，仍是预发布版本）或 Perfetto Tracing SDK 的 in-process backend（C++17、不连系统 `traced`，只包含应用注册的数据源）；需要系统级因果分析时用 Perfetto system trace（Android 10+，同轴组合应用标记、sched、Binder、频率、内存与 I/O）；Android 15+ 还可用 `ProfilingManager` 请求受平台管理的 profile（限流、不保证执行、结果经脱敏）。

Profilo 仍有架构参考价值：provider 按需启停的组织方式、trigger 决定是否采集的控制流、固定容量 mmap 环形缓冲区（写满循环复用旧槽位，读线程落后时会覆盖未读数据）与待处理文件管理，都是线上短窗口 trace 的成熟设计。但直接依赖其上游 AAR 快速上线没有维护方保证：仓库已归档、trace schema 无版本承诺、实现依赖私有符号与 PLT relocation，Java unwinder 依赖旧 ART 布局。两种 in-process 方案都只含应用自己的数据源，不会自动加入调度器或系统进程事件；选择应用内采集后，抽样、大小与频率限制、脱敏、加密、上传与保留策略仍要自己实现——Perfetto 格式只解决数据模型与工具兼容，不替应用决定合规边界。

**Q31: JVMTI/ART TI 在 Android 上从哪个版本可用、谁能 attach agent？agent 的生命周期入口有哪些？**

ART TI（ART 对 JVMTI 的部分实现）从 Android 8.0/API 26 开始提供，公共的 `Debug.attachJvmtiAgent()` 从 Android 9/API 28 开始；运行中附加只允许 `android:debuggable="true"` 的应用——`profileable` 只向受支持的分析工具开放有限能力，不能让发布构建获得 JVMTI attach 权限，不可调试进程会收到 `SecurityException`。AAOS13 源码核对：`art/openjdkjvmti` 存在、`Debug.attachJvmtiAgent()` 已有；attach 由 ActivityManager 与 ART 权限检查把关，agent 经按需加载的 `libopenjdkjvmti` plugin 以 `jvmtiEnv` 调用、以回调接收事件。CTS 会检查可调试与不可调试应用的 attach 边界及 agent 二进制接口稳定性。

生命周期入口有三个（AAOS13 `agent.cc` 已核对符号名）：`Agent_OnLoad` 对应独立 ART 进程经启动参数 `-Xplugin` + `-agentpath` 加载（服务 ART 自测；应用进程由 Zygote 派生，用不上这条路径）；`Agent_OnAttach` 对应运行中的 debuggable 进程接受附加（应用调试最常见，`adb shell cmd activity attach-agent ...` 或应用自身调用 `attachJvmtiAgent()`）；`Agent_OnUnload` 只在 ART 运行时关闭时调用——没有与 attach 对称的运行中 detach，源码明确不执行 `dlclose()`（agent 可能假设库不会中途卸载），需要无 agent 的干净基线时重启进程。agent 与应用共享同一地址空间、没有进程隔离：越界访问、死锁、ABI 不匹配或回调阻塞都会直接影响目标进程；"标准接口"只约束 JVMTI 调用语义，隔离不了 agent 自身的 native 缺陷。

**Q32: 在 ART 上启用 JVMTI 事件和类重定义会改变什么？"任意 agent 都会让全进程永久解释执行"对吗？**

不对。AAOS13 源码核对（`openjdkjvmti/events.cc`）：事件启用所需去优化分四级——breakpoint、exception、method entry/exit 等是 `kLimited`（不请求全量去优化，但走 ART Instrumentation 的事件路径）；exception catch 是 `kFull`（所有方法与线程进入全量去优化）；field access/modification、single step 等指定线程时 `kThread`、未指定时 `kFull`；thread/class、GC、monitor 等事件是 `kNone`。`kNone` 只表示启用事件本身不进去优化流程，回调频率与数据采集仍有成本；去优化按请求计数，多个 agent 可同时持有，全量去优化可撤销但要等所有请求移除。最小 agent 的正确顺序是：`GetPotentialCapabilities()` 查询并 `AddCapabilities()` 申请、`SetEventCallbacks()` 登记回调、`SetEventNotificationMode()` 启用——GC 事件回调只报告 stop-the-world 暂停对，且发生在 VM 仍暂停期间，多数 JNI/JVMTI 调用不可用，回调里只做原子计数等轻量工作。

类重定义是另一个边界：标准 `RedefineClasses()` 只能替换方法体、拒绝改变 schema（增删方法/字段、改修饰符或继承关系会报错），正在栈上执行的旧方法成为 obsolete method、后续调用才用新定义；ART 扩展 `com.android.art.class.structurally_redefine_classes`（AAOS13 的 `ti_extension.cc` 已核对存在）只支持增量添加方法或字段、不允许删除成员，实现会暂停类加载与分配并使 JIT 代码失效——适合 IDE 受控操作，不能当线上热修复协议。method tracing 的路径还有版本差异：AAOS13 的 `Trace::Start()` 传 `needs_interpreter=!runtime->IsJavaDebuggable()`（非调试运行时走 stub 而非解释执行），Android 17 改为显式传 `false` 且枚举 `kInstrumentWithInstrumentationStubs` 更名 `kInstrumentWithEntryExitHooks`；AAOS13 的 arm64 汇编同时保留 `art_quick_instrumentation_entry` 与 `art_quick_method_entry_hook`，Android 17 已移除前者——按旧版本符号表适配新版本不可行，每个版本都要重核入口协议。

**Q33: XTrace 这类"线上动态方法追踪"方案的核心机制是什么？"Non-Invasive"应该怎么理解？**

核心机制是"只改少量目标方法的入口 + 尽量保留原编译执行路径"：把配置指定的方法组成 target set，只更新这些方法的入口（其余方法沿原入口执行，避免全局遍历与改写）；目标方法已有 JIT/AOT 编译代码时选择 ART 的 instrumentation stub、回调后继续执行原机器码，解释态方法走解释器入口（自适应入口）；事件代理注册到方法进入事件，经 JNI 调用 Java 层 interceptor 执行采集动作。论文实验把启动增量压到约 6.5 ms（Frida 对照约 130 ms）、CPU 增量低于 1%，消融显示目标注入主要改善启动与全局 CPU、自适应入口主要改善高频调用的事件成本；1.08 亿 DAU 的 A/B 按 Crash +0.5%、ANR +0.8% 非劣界通过。

"Non-Invasive"是论文中的相对概念：它不改写 DEX 方法体、不做 inline hook，但仍 hook ART 私有函数、定位 `ArtMethod` 并改变方法执行入口——公共 API、Play Integrity 结果、SELinux 策略和厂商 ROM 兼容性都没有随之获得保证。论文把 `UpdateMethodsCode`、`EnableMethodTracing` 称为 "public subset"，这只表示作者选用的 ART 符号子集；按 Android API 定义，这些 C++ 接口仍是平台内部实现（AAOS13 已核对 `InstrumentationListener` 位于 `art/runtime/instrumentation.h`，事件分发前有无监听器的快速检查）。证据边界也要分清：论文报告按 arXiv v1（无源码、无 SDK），兼容范围自报 Android 5.0–15+，性能数字来自单台 Android 15 设备；Android 17 的入口与 tracing 路径已变化，适配远多于替换符号名。普通线上应用没有等价公共 API：目标在 Framework、事件短到采样难以命中且必须记录每次调用时，这类方案才有独特价值，且属于运行时平台工程；其余场景用 `ProfilingManager` 栈采样、编译期插桩或短录制的 `Debug.startMethodTracing()`。
