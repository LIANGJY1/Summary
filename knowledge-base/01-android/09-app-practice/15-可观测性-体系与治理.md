**Q1: 指标、日志、追踪三类可观测性信号分别回答什么问题？为什么不能共用同一套存储、标签和采样规则？**

指标回答群体趋势（这个版本是否变差、影响哪些机型、是否达到告警阈值），日志还原单次现场（操作路径、错误码、降级原因），追踪解释耗时路径（一次启动、卡顿或请求慢在哪个阶段）。混用的代价是双向的：日志明细做长期高频聚合会让存储与查询成本失控，而只有指标看板时，Crash 率上升后既没有日志定位场景、也没有追踪解释 span。三者共享关联键（`event_id`、`session_id`、`trace_id`、`scene_id`、构建版本与设备维度），但存储、保留期与采样独立演进。

Android vitals 侧重 Play 分发侧的指标（用户感知崩溃率、用户感知 ANR 率等，按最近 28 天均值每日评估），不提供自定义业务场景与内部日志；Firebase Performance 更接近应用内部性能观测。自建体系把 vitals 当外部质量基线，再用日志与追踪补现场，而不是用其中一个替代全部。

**Q2: 可观测性事件为什么同时保存墙钟与单调时钟？最小事件信封应包含哪些字段？**

`System.currentTimeMillis()` 是可被用户或网络校准的墙钟，用于与发布、告警跨系统对时；`SystemClock.elapsedRealtimeNanos()` 是包含深度睡眠、单调递增的经过时间，用于本机会话内排序与耗时，设备重启后归零。一次读数不能同时满足两种用途，所以每条事件同时记录两者，并配 `session_id`（短期、可重置、用途受限，不用永久设备 ID）与场景内序号划定会话边界。

最小信封还包括：`event_type`、`event_id`（重试去重）、`trace_id`（关联日志与追踪）、`schema_version`（服务端兼容新旧格式，新增字段有缺省语义、废弃字段先双读验证再停发）、应用与系统版本、设备与网络维度，以及采样纳入概率与规则 ID。高基数字段（原始 URL、永久用户 ID、自由文本、堆栈全文）不进指标标签，否则索引与分组成本随取值数量增长。

**Q3: 高频性能事件的采样为什么用确定性分桶而不是逐事件随机？纳入概率为什么必须随事件上报？**

逐事件独立随机会把同一会话抽成不连续片段，排查时无法还原用户路径；确定性分桶用 `HMAC(sampling_key, 可重置标识)` 之类的稳定输入，让同一用户在配置时间窗内始终落入同一样本组，客户端不上传原始标识。只有抽样设计与纳入概率已知时，服务端才能按权重估计总体；异常补采、失败全量与成功抽样混在一起时必须分层计算，不能全体除以一个采样率——排查界面也要显示采样命中与丢弃原因，避免把"没有采到"误判成"没有发生"。

配套纪律：采样配置带版本、签名与过期时间，拉取失败沿用最近有效快照、过期后回退保守策略；提供紧急关闭开关（kill switch）但范围受限，不能远程关掉 Crash/ANR 等最低诊断能力。哈希不是匿名化：低熵内容（错误消息、URL、手机号）可被枚举反推，敏感字段应先移除再用受控密钥生成指纹；用户日志回捞、远程诊断等高敏感能力默认关闭，按目标、时间窗、单设备配额与自动过期开启。

**Q4: 监控 SDK 为什么必须"主线程只入队"？普通 App 能采到哪些系统层信号，哪些采不到？**

采集 API 常从主线程调用，若在调用栈内完成 JSON 序列化、文件扩容或同步写盘，存储抖动会直接进入页面耗时，`mmap` 写入也有缺页与回写长尾。所以入口只读必要原始值并尝试写入有界队列（队列满按事件等级丢弃并记丢弃数），聚合、压缩、脱敏与上传交给专用线程和受约束的持久任务；SDK 自身开销（入口 P95/P99、分配次数、丢弃率）要纳入发版门禁。进程生命周期也是硬约束：缓存进程可能被冻结，冻结期间无法自采，恢复后只能承认区间缺失并记录原因，不能用零填充。

平台能力分层：StatsD 的 `addConfig()`/`getReports()` 需要 `DUMP` + `PACKAGE_USAGE_STATS`，`setPullAtomCallback()` 需要 `REGISTER_STATS_PULL_ATOM`，都是特权路径（按 Android 17 材料口径；AAOS13 树未包含该模块源码），普通 App 只能用极少数公开入口；公开可用的是 AndroidX JankStats（帧级数据，回调会复用 `FrameData`、跨线程保存要先复制，`isJank` 是库内启发式）、`Debug.MemoryInfo` 与 `getProcessMemoryInfo()`（仅同 UID、调用限频，密集轮询可能返回旧值）。系统内存策略是另一层观察对象：PSS 曲线本身不能证明 compaction、freezer 或 MemoryLimiter 触发，要用 trace、dumpsys 或退出记录交叉验证。版本差异点：AAOS13 源码中 `CachedAppOptimizer` 默认 Freezer 开、Compaction 关，材料核对基准（Android 17 r1）中两者默认开——某一版的默认值不是平台承诺。

**Q5: Crash SDK 的"捕获、序列化、持久化、上报"四段各做什么？为什么上报要交给下次启动？**

崩溃发生时当前线程、堆、锁与文件描述符都不可信，现场只做最小记录：Java 路径在自定义 UncaughtExceptionHandler 里写摘要并保存、在 finally 中调用前一个处理器维持平台退出链；Native 路径只允许异步信号安全操作与预分配内存，寄存器与线程现场交给成熟 SDK 生成 minidump。网络请求、数据库事务和复杂序列化都不属于崩溃现场，进程退出后由下次启动或健康辅助进程补充设备与版本信息再上传。

序列化把摘要（`crash_id`、schema 版本、异常或信号、进程线程、构建标识、栈顶帧、采样策略版本）与附件（完整堆栈、minidump、受限日志片段）分开演进，附件记录类型、字节数与内容摘要。持久化按环境选择：健康窗口用"临时文件 → fsync → 原子重命名"，每进程独立目录、损坏文件进隔离区；SQLite 只用于进程恢复后的状态索引，崩溃线程可能正持有数据库锁，不能作为现场唯一写入路径。上报由下次启动执行：先传摘要、按服务端策略传附件、确认后回收本地文件；服务端以 `crash_id` 与附件摘要做幂等去重，客户端重试不计为多个事件。fatal 与 non-fatal 分开统计，不混用口径。

**Q6: 多进程应用的崩溃采集怎么归集？isolated 进程有什么限制？**

普通 `android:process` 子进程各自安装幂等的捕获模块、写以稳定进程角色命名的独立文件，但只让主进程或专用上传进程拉取配置并执行网络上传；配置由主进程写版本化只读快照供其他进程读取。进程 ID 只在一次生命周期内有效，事件 ID 用预生成 ID，或用"无法还原原始安装标识的派生值 + 单调时间 + 构建标识"组合并在服务端检测冲突。

isolated 进程（`android:isolatedProcess="true"`）没有应用权限、不能直接访问应用私有状态或发起网络上传，即使它来自同一个 APK：可行设计是由宿主经受控 IPC 平时收集有限诊断数据，进程退出后用 `ApplicationExitInfo` 按进程名、UID、时间与退出原因补齐记录；隔离进程崩溃后无法保证 Binder 继续执行，不能把收尾保存寄托在崩溃后的跨进程调用上。WebView 渲染进程由系统管理，不能安装普通采集器，宿主只能经 `onRenderProcessGone` 一类回调观察退出并决定是否销毁重建 WebView（API 边界见 APM 邻居文档）。动态特性模块跟随应用 `versionCode` 管理，崩溃记录记已安装 split 与实验配置，不虚构独立的模块版本。

**Q7: 用 ApplicationExitInfo 补偿崩溃采集时，为什么同一事件可能被 SDK 和系统历史各记一次？怎么去重？**

`getHistoricalProcessExitReasons()`（API 30 起，AAOS13 已具备）返回有界历史，记录会被更近的退出淘汰；`getTraceInputStream()` 来自独立的系统级环形缓冲区，可能被包括其他应用在内的后续记录覆盖而返回 `null`；API 31 起 `REASON_CRASH_NATIVE` 可返回 protobuf 编码的 tombstone 流。同一退出因此可能同时被 Crash SDK 与系统历史发现。

去重要综合应用构建、进程名、相近发生时间、退出原因、SDK 事件 ID，以及可用的致命信号、Build ID 或栈顶帧，不能只拼"PID + 时间戳"——PID 会被系统复用。读取时机是下次获得运行机会时尽早读、限量入库，收到服务端确认前保留记录；发现可读 trace 时立即在字节上限内复制到私有目录并关闭流，不把系统侧流当长期归档。非空 trace 不覆盖实际 `reason`：进程可能从 ANR 恢复后又因其他原因退出，旧的 ANR trace 附在后一条记录上，实际原因与附件类型分别保存。

**Q8: 发布构建的符号化产物为什么要与二进制绑定归档？缺 mapping 时门禁应该怎么做？**

混淆名与 Native 地址只在同一次构建内有意义：同一 `versionCode` 可能被重新构建，单靠它选不出正确的 R8 mapping；Native 侧要靠 ABI、`.so` 文件名、ELF Build ID 与 PC 相对地址匹配未剥离产物或符号包，重新链接会改变地址布局与 Build ID——即使源码提交与版本名相同，也不能拿另一份 ELF 还原线上地址。所以每个可发布构建把 APK/AAB 摘要、mapping 内容摘要、原生符号文件、Git 提交与构建变体归档为同一组不可变产物，CI 在发布时复制到只增不改的仓库。

门禁规则：启用 R8 却缺 mapping、包含 Native 库却缺对应 Build ID 的符号文件时直接阻断发布，否则上线后只能把栈标记为"无法反混淆"，Native 崩溃无法还原函数。问题签名要等符号化之后再生成（异常类型 + 还原后的稳定帧序列 + 规范化消息 + 构建范围；Native 用致命信号 + Build ID + 符号化函数 + 模块内偏移区间 + ABI），混淆名和绝对地址不能做跨版本问题组主键；服务端保留原始事件与问题组的映射，聚类算法更新后可重新归组而不改原始事件。

**Q9: ANR 监控为什么要分"端侧疑似、系统预警、系统确认"三层？**

因为三层的证据强度不同，混在一起会把长卡顿误判成系统 ANR：主线程哨兵与 Looper 监控只能证明"运行期出现过可疑长卡顿"；`ApplicationExitInfo` 的 `REASON_ANR`（API 30+）是系统确认记录，trace 可读但属历史接口；Android 17 的 `registerAnrWarningListener()`/`AnrWarningResult` 是接近超时的尽力预警，可能不投递、也可能来不及执行，且 API 37 才有（AAOS13 上不存在；`AnrInfo` 同为 API 37）。事件模型要带 `authority` 字段分别入库——系统退出、当前错误状态、预警、端侧疑似、Play 聚合、OEM 事件各自标记，不把缺失字段伪装成同一口径。

快照设计围绕"时间、线程、资源、场景"：主线程栈之外要补 Binder、持锁与线程池对端线程栈，否则只能停在"主线程在等锁"而不知道锁被谁持有；运行期可先写本地环形缓冲区，疑似 ANR 时按时间窗与字节上限截取。去重分三层：传输层按事件 ID 与附件摘要幂等；事故层用系统 `(anrType, anrId)` 或带时间约束的进程身份关联预警、哨兵与退出；问题层在符号化后按卡点聚类——同一次事故的预警、疑似卡顿和系统退出是三条记录而不是三次 ANR。告警用暴露量、置信区间与版本/设备分布校准，避免低暴露版本偶发误报；Play 的 0.47% 与 8% 是它的不良行为阈值，不是内部事故分级线。

**Q10: 线上排障的推进顺序是什么？"证据等级"为什么要区分 A–D？**

标准顺序：建立事件编号并记录现象、首报时间与影响面；先做安全处置（暂停扩大灰度、保留已知证据，避免重启或清缓存毁掉现场）；建立时间线，把客户端日志、traceId、Crash/ANR、配置变更与发布记录对齐（本机排序用单调时钟、跨设备对时用带时区墙钟）；列出证据缺口，再选择动态日志、受控 profiling、用户协助的 bug report 或受控复现，采集动作本身限时限量可撤销；修复后按相同分桶口径验证指标恢复。

证据分级防止把相关性写成根因：A 级是平台直接信号（公共 API、系统回调、退出记录），可按字段原义陈述但不能扩写 API 未提供的细节；B 级时间相关、C 级群组相关、D 级用户描述只用于提出和筛选假设，不能写成"该厂商会执行某策略"。缺失数据要有语义：进程退出、作业未获得运行机会、断网、队列满、用户强行停止（作业和闹钟在再次显式启动前不会恢复）都可能表现为"没有数据"，服务端要把"没收到事件"与"指标为零"分开，恢复后记录 `unsupported`、`frozen_gap` 等原因而不是补零。

**Q11: 远程日志与动态日志级别要控制哪三类成本？哪些字段永远不该进日志？**

三类成本：CPU 来自字符串构造、序列化与压缩；I/O 来自频繁写盘与同步落盘；流量来自批量上传。开关按日志标签或结构化事件类型生效、只覆盖明确的用户分组，以服务端到期时间和客户端累计预算双重终止；每次下发、命中、续期与撤销写审计记录，客户端无法验证签名、版本或有效期时维持安全默认级别。

隐私边界先于功能：密码、验证码、完整 token、支付凭据、输入文本与联系人内容不得进入日志；URL 默认只保留主机名、路径模板与错误码，丢弃 query、fragment 与凭据；字段在产生处分类、在写盘与上传两处校验——私有目录不是采集敏感数据的理由。普通 App 不能把远端字符串解释成系统属性（`log.tag.<TAG>`/`Log.isLoggable()` 更适合 adb 调试设备），也不能读取全设备 logcat（Android 官方把全设备日志限定给 OEM App）；bug report 需要用户在开发者选项里主动生成分享，是高成本后备手段而非每次反馈的默认要求。

**Q12: 诊断命令通道的安全设计要点是什么？为什么不能通过它下发可执行代码？**

诊断命令是远程控制面，安全级别应高于普通远程配置。命令信封至少包含：`command_id`、命令类型与参数 schema 版本、目标范围（包名/签名/渠道/版本/设备或匿名主体）、签发与过期时间、nonce 或单调序列、最大执行次数、网络与文件预算、结果字段 allowlist，以及审批 ID 与签名信息；端侧先验证签名、受众、期限与本地政策再写入持久执行记录，`command_id` 与 nonce 进防重放表，服务端用同一 ID 幂等接收结果，wall clock 不可信时用服务端时间锚点与短有效期缩小重放窗口。

动作集合必须是预编译白名单：拉取限定会话或时间窗的日志、对固定端点做 DNS/连接/TLS 探测、读白名单目录元数据（防目录穿越）、输出配置快照、请求 ProfilingManager 或写应用内 trace 标记。任意 shell、反射、任意文件读取或网络目标等于远程代码执行入口，不应出现在普通用户路径；熔断开关按命令类型、版本与签名密钥缩围，客户端离线时靠命令过期自行生效。不下发代码还因为 Android 官方将远程动态加载列为安全风险且可能违反 Play 政策——补日志靠预埋观察点与签名命令调整采集级别即可。回执记录 `issued → delivered → validated → started → result_created → uploaded` 各阶段：未送达不算执行失败，已生成文件未上传不算 profiling 失败。

**Q13: 非 Play 渠道与国内 ROM 场景，可观测性会缺什么？怎么补齐而不误判？**

Android Vitals 的数据来自选择共享使用与诊断信息、且通过 Play 安装并通过认证的设备，官方明确排除非 Play 安装的版本与未认证机型——同一个 APK 在其他市场产生的问题不会进入同一份 Vitals；厂商报表与应用市场数据的覆盖条件也不同，不能视为 Vitals 等价物。

补齐方式是平台公共 API + 应用自身事件 + 服务端统计的同口径路径。每条事件记录分发字段与应用内声明的渠道：`getInstallSourceInfo()` 自 API 30，`installingPackageName` 可被更改，`initiatingPackageName` 在来源不可用或包已卸载时为空，`originatingPackageName` 由发起方提供且未经框架验证（缺 `INSTALL_PACKAGES` 权限拿不到）；平台字段与自有渠道不一致时记录差异并标"待解释"。再采集能力快照（standby bucket、后台受限、省电、热状态、page size 等）并带采集时间——这些状态随时变化，读取失败记 `unknown` 不写 0。渠道通常与机型、地区、ABI、签名、用户群同时变化：实验室比较要同一源码等价构建、同设备交叉安装并记录编译状态；线上按版本、产物摘要、厂商与系统构建分层并报样本量与置信区间。"加入白名单"引导只在公共 API 显示后台受限且延迟影响可解释时触发，不作为首次启动必做步骤。

**Q14: 性能 A/B 实验的随机化单元和暴露口径怎么定？为什么"只分析成功激活的用户"会引入偏差？**

随机化单元要选与产品语义一致的稳定单元（账号、安装或设备），分析时保留分桶版本：按请求随机会让同一用户反复切换方案，更换哈希函数或盐值会重新分桶。随机化单元与统计单元必须一致——按用户分桶时，同一用户的多次启动、帧与会话是相关观测，应先在用户级聚合再比较，或使用按单元聚类的标准误/聚类 bootstrap；否则活跃用户贡献更多事件，置信区间会过窄。

暴露要拆成漏斗分别记录：分配（assignment）→ 配置拉取（fetch）→ 激活（activate）→ 实际使用 → 上报成功；主分析按预注册的分配口径。只分析激活者属于处理后选择偏差：变体自身导致启动失败或崩溃时，"成功用户"样本恰好抹掉了损伤。Firebase A/B 的官方边界同理：未触发激活事件的目标用户不进实验结果但仍可能收到实验值，且实验开始后不能修改变体权重。

**Q15: 用 P90/P99 做实验主指标时，判定协议与均值有什么不同？分群分位值能加权相加吗？**

不能。主效应应直接定义为两组分位差 `Qτ(variant) − Qτ(baseline)`，并直接为差值构造区间——分别看两组区间是否重叠不能替代差值区间。分位数是非线性秩统计量，不适用均值公式：按随机化单元做聚类 bootstrap（被抽中单元携带其全部合格事件，直接按帧或请求重采样会破坏单元内相关性），或把 SLO 转成用户/会话级违约率 `P(X > L)`；两种结果回答的问题不同，尾部报告除 P99 外还要预注册体验阈值 `L` 的违约率与超阈值时长。

总体分布是各群混合累积分布 `F(x) = Σ wg·Fg(x)`，总体分位值是混合 CDF 的逆函数，不等于各群分位值的加权和；人群构成变化与群内分布变化要分开归因，标准化时把两组重加权到同一参考构成再计算经验分布。区间同时包含可接受改善与不可接受退化时，结论就是证据不足，不能用单点方向替代。重复查看普通 p 值并随时停止会抬高假阳性率，要用固定终点、预分配错误预算的序贯方法或 anytime-valid 推断；低端机、热限频造成的真实慢样本属于用户体验，不能当异常值删除。

**Q16: SRM（样本比例失衡）检查为什么必须先于性能指标判断？常见原因有哪些？**

实际分配数与预设权重的差异超出随机波动可解释范围时，实验数据已不可用于决策——继续比较收益是在损坏的数据管道上读数。检查用卡方检验（大样本）或精确方法（小样本、稀疏分群），覆盖全量与预注册关键分群，阈值与查看频率预注册；并沿"分配 → 拉取 → 激活 → 指标产生 → 上传成功"逐层定位：分配已均衡而激活后失衡，说明问题发生在处理之后——某变体在激活或上报前崩溃，此时只过滤"成功用户"会隐藏 Crash/ANR 造成的损伤。

常见原因包括分桶哈希函数或盐值变更、安装 ID 重置、目标条件实现不一致、埋点丢失与变体提前崩溃。A/A 实验用于长期校准分桶与统计任务的假阳性率、置信区间覆盖率，但它不能证明平台永远无偏。实验平台自身也是事故源：一个错误配置可能让启动多拉接口、打开高频日志或调整线程池参数，因此平台要支持配置审计、灰度放量、紧急关闭和不可变的配置版本历史（紧急关闭生成新配置版本并保留旧快照，不覆盖历史值）。

**Q17: 把 Macrobenchmark 接进 CI 门禁，指标可用性与基线选择有哪些硬边界？**

环境边界：物理设备而非模拟器（模拟器受宿主机与虚拟化影响）；目标包接近生产——non-debuggable、profileable、与生产一致的 R8、资源压缩、签名后处理与 Baseline Profile，测试 APK 与目标 APK 分开构建；固定设备不等于环境恒定，要记录电量、温控、build fingerprint、`CompilationMode` 与数据准备方式。指标边界：`StartupTimingMetric.timeToInitialDisplayMs` 测首帧（TTID），`timeToFullDisplayMs` 依赖 `reportFullyDrawn()`（TTFD）且在 Android 10 / API 29 及更早可能不可用，没有完整绘制点的场景不能用 TTFD 卡门禁；`FrameTimingMetric.frameDurationCpuMs` 与 `frameOverrunMs`（API 31+ 才可用）语义不同、不能共享阈值；`TraceSectionMetric` 与 `PowerMetric` 仍是实验性 API（前者默认 `targetPackageOnly = true` 且 `Mode.Sum` 累计所有同名 section）。

基线边界：`baseline` 不能总指向上一轮——上一轮本身可能已退化，逐次比较放过累积变化；固定已知良好版本适合判断累计漂移，滚动稳定基线适合识别设备环境变化，更新固定基线是发布决策、不能由测试任务在结果变差后自动完成。CI 分三档：PR 快检只验证编译与可执行；主干定时任务在固定物理设备上多轮测量建趋势；发布候选在代表性设备档位跑核心路径。JSON 与每次迭代的 Perfetto trace 都要归档，聚合异常后能回到单次 trace 查原因；测试环境异常标"无效运行"，不伪装成业务豁免。

**Q18: 发版门禁应检查哪些域？产物身份为什么要先冻结？**

检查域至少覆盖：启动（按启动类型、入口与设备群比较 TTID，正确调用 `reportFullyDrawn()` 的场景才用 TTFD）；渲染（FrameTiming 分布与生产慢帧/冻帧，按刷新率与页面分组）；内存（Java/原生堆、PSS/RSS、OOM 与低内存退出）；稳定性（崩溃、ANR、原生崩溃与 `ApplicationExitInfo` 退出原因，按受影响用户数与事件数分别呈现）；功耗（固定场景能耗与异常唤醒）；数据健康度（实验分组、采样配置、上报与查询延迟）；包体与配置（AAB/动态特性大小、资源与远程参数快照）。任一域失败执行预设动作并记录审批人。

产物身份先冻结：`versionCode`、Git 提交、AAB/APK 文件摘要、签名证书摘要、`compileSdk`/`targetSdk`、R8 mapping、原生符号、Baseline Profile 版本与远程配置快照绑定同一构建 ID——实验室和生产引用同一份证据，数字变化才能转换成发布决定。阈值绑定指标版本、设备群、场景与发布阶段，来自本项目历史噪声、SLO 与最小可检测效应，不复制其他项目的毫秒数或百分比。升级目标版本时按"保留原 targetSdk 验证运行兼容"与"targetSdk 升级验证目标兼容"两轮推进（材料以 Android 17 为例），兼容开关只用于逐项定位，正式结论来自接近生产的候选包在完整行为组合下的验证。

**Q19: staged rollout 的 userFraction、暂停（halt）与"回滚"各是什么语义？灰度期间为什么不能只看崩溃率？**

`userFraction` 是有资格接收该分阶段版本的用户比例，不是安装完成率或在线占比；它只对 `inProgress`/`halted` 状态有效且严格在 0 与 1 之间。暂停把状态置为 `halted`：阻止更多用户取得该版本，已安装用户停留在该版本——Play 不能远程降级 APK，"回滚"实际是三种操作：暂停发布、回退服务端配置、发布更高 `versionCode` 的修复包；已全量版本也可暂停（前一个版本会重新提供给未安装用户，内部测试轨道除外），配置错误走配置回退，已安装用户靠服务端兼容与功能开关兜底。staged rollout 不满足严格 A/B 条件（无稳定旧版对照组，覆盖受国家、资格与自动更新影响），版本间差异可以触发处置但不能证明代码因果。

灰度决策要分快慢信号：自建 APM、崩溃/ANR 事件流与启动帧指标是快信号（前提是数据延迟与覆盖达标）；Android vitals 每天更新最近 28 天均值，适合长期质量判断，不能作为刚起步小流量的扩量依据；客服与评论到达慢且有选择偏差，"暂时没有投诉"不能抵消已观测的崩溃或数据管道异常。上报成功率、事件丢弃、配置命中率或上报延迟异常时，当前结论标"不可判定"，维持或暂停当前比例。

**Q20: App Performance Score 的静态分与动态分分别评估什么？分数怎么转换成工程任务？**

这是 Google 仍处 Preview 的评估框架（2026 年口径），0–100 分表示评估表中还有多少改进空间。静态分不运行应用、检查源码配置：最新 AGP、R8 full mode 且 keep 例外受控、Baseline Profile 覆盖至少一条用户路径、Startup Profile 优化 DEX 布局、最新稳定版 Compose、内容可用时调用 `FullyDrawnReporter`/`reportFullyDrawn()`；这些项成本低、信号清楚、适合接 CI。注意配置纪律：生成 profile 的 variant 应关闭 R8 混淆以保持方法签名可匹配，最终 release 才启用；只检查仓库里有 `baseline-prof.txt` 证明不了 release 产物包含并使用它。

动态分在物理设备上测启动到可交互（口径指向 TTFD）与滚动/动画中的 slow/frozen frames 占比，分数属于"该设备、该构建、该次观察条件"，不能跨应用排名，低端设备会放大问题。分数不能给根因、也不能替代线上 KPI——分数高但支付页等待久、搜索首屏空，用户仍觉得差。转换方式是四个队列：配置项（AGP/R8 → Profile → Compose/TTFD）、测试项（冷启动、通知启动、滚动、核心交易路径的 Macrobenchmark 用例）、trace 项（固定场景采 trace，归因线程/I/O/Binder/GPU）、平台项（采集 → 聚合 → 告警）；静态与动态都低时先修静态项（配置修正也可能改善动态表现），但阻断核心业务的动态问题不能等静态项完成。规则会随 Preview 迭代，报告保存评分日期与规则快照，不同规则生成的分数不画同一条趋势线。

**Q21: getHistoricalProcessExitReasons() 的三个参数怎么用？历史容量有多大？**

签名是 `(packageName, pid, maxNum)`：`packageName` 传 null 匹配调用者 UID 下的包（查其他 UID 需要系统级 `DUMP` 权限），传包名时通过 `BIND_EXTERNAL_SERVICE` 绑定的外部服务进程记录也可能纳入——主进程读到推送进程的 `REASON_LOW_MEMORY` 不能算主进程启动失败；`pid` 非 0 按进程过滤，但 PID 会被系统复用，不能单独做事件 ID；`maxNum = 0` 表示返回系统当前仍保留的全部匹配记录。结果按时间从新到旧排列。

容量是有界环形缓冲：AOSP 默认资源 `config_app_exit_info_history_list_size` 为每包 16 条（按 AAOS13 源码核对），设备厂商可覆盖，不属于 SDK 合约；公开 API 只承诺"近期记录"，同一 PID 可以保留多次退出记录。没有历史可能由缓冲淘汰、系统尚未记录、数据被清除或厂商实现差异造成，不能据此断定"进程未异常退出"。查询经 Binder 批量返回，放在应用可交互后的后台 executor 执行，不进首帧关键路径。

**Q22: ApplicationExitInfo 的 reason 与 status 怎么解释？哪些 reason 容易误判？**

`reason` 是系统分类主字段，`status` 的含义取决于 `reason`：进程自行 `exit()` 时保存退出码，因操作系统信号结束（`REASON_SIGNALED`）时保存信号编号。易误判点：`REASON_USER_REQUESTED` 覆盖"设置中强行停止"与"从最近任务移除"等多种入口，且 Android 14 / API 34 之前包更新也用它（API 34 才加入 `REASON_PACKAGE_UPDATED` 与 `REASON_PACKAGE_STATE_CHANGE`，跨版本报表必须按 API 级别解释）；`REASON_USER_STOPPED` 指多用户设备上的系统用户或工作资料被停止，与 Force stop 无关；低内存终止要先查 `isLowMemoryKillReportSupported()`，不支持的设备上表现为 `REASON_SIGNALED` + SIGKILL，即使支持，`REASON_LOW_MEMORY` 也只说明系统当时有内存压力、不能证明应用泄漏；`REASON_FREEZER` 自 API 33 公开（AAOS13 已具备），指 freezer 相关退出，不能用来命名某个厂商的后台管理功能；`REASON_UNKNOWN` 与一般 `REASON_SIGNALED` 信息不足，不能自动标"被安全中心杀死"。

细分原因 subreason 在平台源码中属隐藏信息，公开 API 没有读取入口；`description` 只是人工阅读文本且格式不保证稳定，服务端不能靠解析字符串恢复内部细分。AAOS13 源码中的公开常量集到 `REASON_FREEZER` 为止，`REASON_MEMORY_LIMITER` 与 `REASON_ANOMALY` 只以 API 10000 预览形式出现在在线参考中，覆盖 API 37 的数据协议不应提前引用。`pss`/`rss`（单位 kB）是系统最近一次采样，进程在采样前死亡时可能为 0——0 要标"不可用"，不插值，也不等于死亡时刻的精确内存。

**Q23: ApplicationExitInfo 的 trace 附件有哪些读取边界？**

四个边界决定消费方式。其一，trace 在独立的系统级环形缓冲区里，可能被包括其他应用在内的新记录覆盖，`getTraceInputStream()` 返回 `null` 属于允许结果。其二，常见内容是 ANR 线程转储文本，而 API 31 起 `REASON_CRASH_NATIVE` 可返回 protobuf 编码的 tombstone 流——两者格式不同，必须结合 `reason` 判断类型，不能把所有非空流当文本或都标成 ANR。其三，进程从 ANR 恢复后因其他原因退出时，先前的 ANR trace 会附在后一条记录上，实际 `reason` 与附件类型分别保存。其四，读取是 I/O 操作，应在后台按字节上限复制到私有临时文件、校验成功后再发布为待上传附件；超配额、解析失败与缺失都作为明确状态上报。

系统还可能稍后为已有记录补上 ANR trace：本地按来源指纹 upsert（存在则更新、不存在则插入），而不是"看过时间戳就永久跳过"，否则会漏掉后来出现的附件。隐私优先于字段完整度：ANR trace、tombstone 可能包含线程名、文件路径与内存片段，上传前限制字节数、验证格式、删除不需要的数据，无法可靠脱敏的附件不上传。

**Q24: ProfilingManager 与 ProfilingTrigger 的能力从哪个版本开始？AAOS13 上能用吗？结果为什么可能没有？**

`ProfilingManager` 自 Android 15 / API 35 提供四类请求（system trace、Java heap dump、heap profile、stack sampling），AAOS13（API 33）上不存在，低版本继续用自有指标、Perfetto、bugreport 等实验室路径。请求受系统级与进程级限流，且可能因已有 profiling 进行中、磁盘不足、参数无效或执行失败而没有结果——"请求已发出"与"结果已生成"是两个状态；必须成对提供 executor 与 listener（或提前注册全局监听器），两处都没有时请求被丢弃且无回调。只有 `error_code == ERROR_NONE` 才读 `getResultFilePath()`，路径来自回调、不能拼接固定目录；结果脱敏且只含请求进程的信息，其他进程 CPU 活动合并显示在 `OtherProcesses`。App 在结果投递前退出时，系统会在下次启动并注册全局监听器后尝试补投。

触发器按版本递增：Android 16 / API 36 加 `APP_FULLY_DRAWN`、`ANR`（结果只投递给 `registerForAllProfilingResults()` 的全局监听器，且依赖系统当时正在后台 trace）；SDK extension 36.1 加 `requestRunningSystemTrace()` 与用户终止类触发器（要用 `SDK_INT_FULL` 对比 `BAKLAVA_1` 判断，`SDK_INT == 36` 区分不了 36.0 和 36.1）；Android 17 / API 37 加 `OOM`（要求自定义 UncaughtExceptionHandler 继续调用默认处理器，否则系统无法使用）、`COLD_START`（新启动 trace + stack sampling，未调 `reportFullyDrawn()` 时默认 5 秒停止、用 discard buffer 保住启动早期内容）、`ANOMALY` 与过量 CPU 终止等。Android 17 部分设备的 MemoryLimiter 终止表现为 `REASON_OTHER` 且 `description` 含精确字符串 `"MemoryLimiter:AnonSwap"`——只有这个文档保证的完整标记可机器判断，不能匹配宽泛的 `"MemoryLimiter"` 或把所有 `REASON_OTHER` 归入内存限制。所有触发式采集都是尽力而为，"触发已登记""系统产生结果""结果已上传"要分开统计。

**Q25: ApplicationStartInfo 给启动样本补了什么？它和 TTID/TTFD、业务埋点是什么关系？**

它是 Android 15 / API 35 的系统侧启动记录（AAOS13 上不存在），提供进程身份（PID 与 package/real/defining 三类 UID）、启动 reason、冷/温/热类型、启动状态与单调时钟时间戳。价值是为每条启动样本补系统归因：冷启动从创建进程开始，温启动复用部分已保存状态，热启动把仍在运行的应用带回前台——同样首帧耗时，桌面图标冷启动、最近任务恢复与广播拉起的优化方向完全不同。

它不能定位慢代码，也不能替代平台 TTID/TTFD 或业务埋点：TTID 是系统收到启动 Intent 到首帧显示，TTFD 到应用调用 `reportFullyDrawn()`；业务首页可用、路由与异步数据完成仍要自己记录。公开 start reason 覆盖 launcher、broadcast、push、job 等；API 36 加 `getStartComponent()` 区分 Activity/Service/Broadcast/Provider，API 35 只能按 reason 粗分并接受较低分类精度。`getIntent()` 已移除 extras 且不应直接上传，上报只走白名单映射的 route 与 entry scene。

**Q26: 读 ApplicationStartInfo 时为什么先看 startupState 再看 startType？时间戳相减要满足什么条件？**

历史查询可能包含尚未完成的启动记录：`STARTUP_STATE_STARTED` 只保证身份/原因字段与 `START_TIMESTAMP_LAUNCH`；`STARTUP_STATE_FIRST_FRAME_DRAWN` 才额外保证 `BIND_APPLICATION`、`APPLICATION_ONCREATE` 与 `FIRST_FRAME`。`getStartType()` 只在首帧完成状态有保证，未完成记录可能返回 `START_TYPE_UNSET`，线上协议用 nullable 或 `unavailable` 表示，不能把未设置值当成热启动。`addApplicationStartInfoCompletionListener()` 在当前启动首帧完成时投递一次后自动移除，不等待 `reportFullyDrawn()`；需要 `FULLY_DRAWN` 时间戳要在调用 `reportFullyDrawn()` 后重新查询或重新注册监听器。

时间戳是纳秒单调时钟（同一次开机周期内可比较），只在同一条记录、两个 key 均存在时相减：`FIRST_FRAME − LAUNCH` 在 launch 可信时可保存为系统首帧区间；`APPLICATION_ONCREATE − BIND_APPLICATION` 包含框架在两点之间执行的工作，不能当 `onCreate()` 自身耗时；不能与 `System.currentTimeMillis()` 直接相减，要同刻保存两种时钟快照再在同一 boot session 内近似换算。开发者自定义 key 限定在 21–30 区间、重复写覆盖旧值、`reportFullyDrawn()` 之后写入被丢弃。版本注意：Service 启动的 `START_TIMESTAMP_LAUNCH` 在 Android 15/16 可能不正确，不要给 Service 启动设耗时门禁。

**Q27: 线上冷启动 SLA 应该统计哪些启动？ApplicationStartInfo 与 ApplicationExitInfo 怎么关联？**

SLA 只纳入完成记录中的 `START_TYPE_COLD` 且组件为 Activity 的用户显式启动（reason 为 `LAUNCHER` 或 `LAUNCHER_RECENTS`）；warm/hot 分桶统计、不与 cold 聚合，后台 Service/Broadcast/Provider 拉起属于后台拉起健康度，不进首页冷启动指标；`START_ACTIVITY` 的外部跳转由业务入口场景细分。

与前一次退出的关联要保留两份原始记录、再生成带置信度的关联边：exit 的 timestamp 是 epoch 毫秒、start 的时间戳是单调纳秒，两次的 PID 通常不同，改时间、重启与包更新都会影响匹配；候选匹配用包 UID、进程名、先后顺序、boot session 与业务 session，时间窗口由线上数据校准、不是平台保证。`wasForceStopped()` 是本次启动记录上的直接信号，优先于从模糊 exit reason 推断，用于决定是否重新注册被清理的 alarm/job；`REASON_CRASH` 后短时间 cold start 指向崩溃循环，`REASON_PACKAGE_UPDATED` 对应新版本首启，用户请求终止不计为 crash 恢复。CI 的 Macrobenchmark `StartupMode.COLD/WARM/HOT` 与系统的 `START_TYPE_*` 是两套枚举，不要按整数值对应——CI 管可重复回归，线上分位数管用户分布，Android 17 的 `COLD_START` 触发式 trace 只做低频抽样诊断。
