# 应用内存与分配

## 第一章 应用分配与内存抖动

**Q1: [learning] Java OOM 的崩溃栈为什么不能直接指出内存占用者？线上堆样本怎样取证？**

OutOfMemoryError 的栈标识失败的分配点，不能直接指出谁长期持有了堆。要找占用者，应在可承受的高水位时采集 Java heap dump，或使用目标平台支持的 OOM 触发采样能力，再分析引用链、支配对象和对象生命周期。OOM 已发生后再完整转储可能因内存和 I/O 压力失败，不能承诺每次都拿到样本。

样本分析按依赖顺序推进：

1. **确定样本范围：**记录进程、堆上限、触发条件、采样成功率与采集开销。对进程内存、上传体积和敏感内容设置预算。超预算时减少采样或在受控诊断环境复现。
2. **定位持有关系：**比较对象数量、Shallow Size、Retained Size 和通向 GC Root 的引用链。失败分配点与最大保留对象不一致时，按持有链追查 owner。
3. **还原代码位置：**混淆构建用同一构建产物的映射文件还原类与方法。裁剪字符串内容或 Bitmap 像素可降低敏感信息与体积，但必须验证裁剪后引用图仍可用于当前结论。
4. **修复并复测：**页面退出后仍被任务或监听器持有时，取消任务与解除注册。对象数量合理但单体过大时，控制缓存容量或单对象负载。相同操作循环后比较存活对象与内存基线。

不要把批量 Bitmap.recycle() 当通用修复。API 26 起 Bitmap 像素主要在原生内存，由对象生命周期与 NativeAllocationRegistry 关联管理，提前回收可能使仍在绘制的调用方访问已释放像素。Android 17 的 ProfilingTrigger.TRIGGER_TYPE_OOM 可申请 OOM 时的 Java heap dump。AAOS13 没有该 API。工具使用边界见 [Hprof 与 heap dump 工具边界](../04-工具/02-性能剖析/04-Java堆转储.md)。

**Q2: [learning] TLAB 让分配很快，为什么高频分配仍然会拖慢帧？**

TLAB（线程本地分配缓冲区）只优化分配动作本身：线程在私有缓冲区内推进指针、避免堆全局锁。之后仍有多种成本：

1. 缓冲区用尽时需要补充空间。
2. 每次分配都会增加标记、扫描与回收工作量。活对象越多，收集器要处理的引用越多。
3. 大对象或突发分配容易离开最轻的分配路径。
4. 回收线程消耗 CPU 与内存带宽，会与 UI 线程、RenderThread 竞争。
5. 可分配空间不足时，发起分配的线程要等待 GC 完成。这个等待往往比单次 GC 暂停更长。

从帧预算看：120 Hz 一帧约 8.33 ms，GC 暂停、分配等待或 CPU 竞争只要与已接近预算的帧重叠，就可能产生 missed frame。没有“某类 GC 固定耗时几毫秒”的跨设备常量，判定靠 trace 中分配、GC slice 与 FrameTimeline 的对齐，而不是暂停时长直方图。AAOS13 的收集器是并发复制 CC（支持分代），材料按 Android 17 核对的 CMC 及分代 CMC 在 AAOS13 源码中不存在，但这不改变“高频分配仍有后续成本”的结论。

跨层边界：ART 分配与 GC 机制见 [ART 分配与 GC 机制](../02-系统/02-进程启动与ART.md)。

**Q3: [learning] 常见的 Java 分配热点有哪些？各自怎么证实和修？**

证实热点一律使用 allocation profile 调用栈，不按代码外观猜。常见类别与处置方式如下：

1. **逐帧回调：**onDraw、动画或触摸回调创建 Paint、Path、Rect、临时集合时，把可复用状态移到 View 成员并在构造期创建，帧回调只更新字段。
2. **循环内临时对象：**循环创建集合、正则、格式化器或中间 DTO 时，把容器移出循环，用 clear() 复用并按已知规模设置初始容量。复用前确认引用不会被异步任务或返回值保存，否则会引入并发错误。
3. **字符串与日志：**把 `result += item` 改为 buildString。在调用点判断日志级别，或使用接收 lambda 的延迟日志 API，确保禁用时不构造文本。
4. **键装箱与容器选择：**只有热点经 profile 证实后，才评估将 `HashMap<Int, T>` 换成 `SparseArray`。`SparseArray` 以排序数组省去 key 装箱，但查询与插入特征不同，应由 benchmark 决定，不能按元素数量设统一切换点。
5. **密集数值容器：**密集数值计算若经 profile 证实对象分配或装箱是热点，可评估改用 `IntArray` 或 `LongArray`。比较时同时确认索引访问、容量和实际工作负载相符。
6. **value class 装箱边界：**Kotlin 的 `@JvmInline value class` 只在直接参数与局部变量路径避免包装。泛型、接口、可空场景仍会装箱，优化前需按实际调用路径检查分配 profile。
7. **大 buffer：**使用固定数量轮转或分块处理，限制同时存活的 buffer 数量，并按实际最大负载验证容量。
8. **图像对象：**按目标尺寸解码并遵守图像库的 buffer pool 所有权。API 26 起 Bitmap 像素在 native 堆。库管理的对象应归还库的池，不要在未知调用方仍可能使用时提前 `recycle()`。

**Q4: [learning] Compose 的内存抖动怎么治理？remember、strong skipping、derivedStateOf 各解决什么？**

Compose 结构本身占内存，但更常见的 churn 来自重组期重复执行的构造代码与不稳定的参数身份。不同机制解决不同问题：

1. **remember(keys)：**跨重组保存对象。key 要准确描述失效时机。key 变化过频会让缓存反复失效，缺 key 会让旧对象与新输入不匹配。remember 会延长对象在组合中的存活，不适合无限增长的数据。
2. **Strong skipping：**Kotlin 2.0.20 起默认启用。参数未变的 restartable composable 可跳过，编译器会记忆捕获不稳定对象的 lambda。不要为跳过重组随意加 @Stable。它是行为契约，标注错误会让 UI 漏掉更新，应先用编译器报告核对稳定性推断。
3. **derivedStateOf：**适合输入变化频率高、输出变化频率低的场景，例如滚动位置持续变化而按钮只关心是否在顶部。若输入每次变化都必须更新结果，直接计算更简单。
4. **原始类型状态 API：**计数器等状态可用 mutableIntStateOf、mutableLongStateOf 等 API 减少 JVM 路径上的装箱。

Compose 经 AndroidX 发布，不与 platform API 绑定。库版本边界不能推断为 Android 17 设备的专属运行时行为。

**Q5: [learning] 内存排查怎样先区分故障类型，再解读曲线形态？**

入口取决于故障种类，不能用 Java 堆余量解释所有内存问题：

1. **Java 堆 OOM：**记录 `OutOfMemoryError` 消息、堆上限、失败分配大小和调用栈。
2. **Native 分配失败：**查 tombstone、malloc 日志和 Native Heap。
3. **系统压力杀进程：**用 Android 11+ 的 `ApplicationExitInfo` 核对 lmkd 退出原因。应用内通常没有 Java OOM。
4. **文件描述符耗尽：**`EMFILE` 是句柄问题，不能并入堆 OOM。

用 `dumpsys meminfo` 判断增长来自 Java Heap、Native Heap、Graphics 还是 mmap。PSS 估算进程对系统的贡献，不是堆硬上限。多轮操作后基线持续抬升，查对象是否被 GC Root 意外持有。高频锯齿伴随停顿，查分配速率及 GC，尤其是 `onDraw()`、`onBindViewHolder()` 和重组热点。Heap Dump 中仍存活的对象须按预期生命周期判断，不能一概称泄漏。

## 第二章 进程内存归因

**Q6: [learning] 对象已经释放、堆占用不高，进程 PSS 为什么仍降不回冷启动值？**

PSS 统计进程的驻留页。对象释放后，分配器可能暂留空闲页供后续分配，播放所加载的共享库和窗口缓冲也可能在退出页面后继续计入 PSS。

某 Android 13 车机退出媒体页后，Java 堆接近冷启动基线，PSS 仍高约 14 MiB。分类对账表明增量主要来自四处。

1. 共享库代码页约 5.1 MiB。
2. System 共享页约 4.3 MiB。
3. Dalvik Other 约 1.4 MiB。
4. 其他私有页与栈合计约 4.6 MiB。

在同一进程重复相同操作，核对增量是否累积。堆活跃分配回落而 PSS 稳定时，先按分类检查驻留成本。持续上涨时，再使用采样或堆转储追踪占用者。

**Q7: [learning] 怎么判定 PSS 的高位平台是一次性高水位，还是持续泄漏？**

用棘轮实验判定：同一进程内重复完全相同的操作路线，在固定检查点采样；各轮收敛即一次性高水位，逐轮抬升才是泄漏嫌疑。单次高峰没有结论，趋势才有。实验步骤：

1. 强制停止应用后冷启动，取得基线。
2. 按固定路线遍历各页面，每步固定等待，并在固定检查点采样。
3. 返回起点后按 0/2/10/30 秒采样，观察回落速度与落点。
4. 不杀进程，重复同一路线至少 3 轮，对比各轮同一检查点的数值。

判读标准：同一检查点的各轮数据在设备基线的正常波动范围内收敛，支持一次性高水位的判断。逐轮抬升则是泄漏嫌疑，转入 heap dump 做对象级分析。两条辅证：销毁页面时 PSS 大幅回落说明释放机制活着，闲置后自然回落同样说明有界。实测：退出重进循环三轮的峰值 106.9 → 95.3 → 95.7 MB，有界；一次 125.3 MB 的峰值在同一进程 17 分钟后自然回落到 95.7 MB。

依据：Android 14 模拟器与某车机真机（Android 13）实测。

**Q8: [learning] 判断应用的 PSS 水位是否真的过高，为什么需要分场景基线和同机横向对比？**

在同一设备按场景建 PSS 基线，再分别看趋势和同类应用。

1. **按场景采样。** 冷启动、图文页、全屏视频分别在稳定后采样。原车机样本依次约为 48 MiB、53–58 MiB 和 111–130 MiB。
2. **检查趋势。** 同一场景保持页面状态一致并重复采样。八次样本在 111–130 MiB 内振荡，说明这段时间未出现持续上升。
3. **同机横向核对。** 选择功能和内容复杂度相近的应用，并记录机型与版本。横向结果用于建立参考范围。

实际占用超出场景预算，或相同操作使高位逐轮抬升时，用内存分类或对象引用继续定位。依据为 Android 13 车机与 Android 14 模拟器样本。

**Q9: [learning] dumpsys meminfo 里 Heap Size 与 Heap Alloc 的差值说明什么，为什么 native 堆占用在对象释放后不立即下降？**

Heap Size 是分配器向系统持有的内存总量，Heap Alloc 是当前活对象占用字节，两者之差是"已释放但未归还系统"的空闲竞技场，即碎片水位。native 分配器以竞技场为单位管理内存、整场清空才归还，所以高频分配潮过后 PSS 会长时间停在高位；Java 大对象空间相反，每个大对象独立 mmap、回收即 munmap 归还。

三个数字与差值的读法：

1. **Heap Size：**分配器从系统持有并尚未归还的内存，含空闲竞技场。
2. **Heap Alloc：**活对象占用字节，对应"仍被持有"的口径。
3. **差值（Size 减 Alloc）：**已释放未归还部分；碎片水位的长期监控指标是这个差值，不是 PSS 总量。

两类堆行为不同的机制：

1. **native 堆：**Android 11 起默认 native 分配器为 scudo，以竞技场为单位向系统取内存并管理（showmap 中为 `anon:scudo:primary` 与 `anon:scudo:secondary` 大块区）；释放的内存留在场内空闲列表等待复用，整场清空才归还系统。实测某进程 native Heap Size 115 MB 而 Alloc 仅 28 MB，showmap 单场最大 24.8 MB，即约 45 MB 空场未归还——这部分是历史 churn 的后遗症，不是当前业务占用。
2. **Java 大对象空间：**超过大对象阈值的对象进入独立的大对象空间（showmap 中为 `anon:dalvik-free list large object space`），每块独立 mmap；GC 回收后直接 munmap 归还系统，所以 Java 大对象占用在回收后立即下降，没有竞技场水位问题。

分析时的两个辅助判断：

1. **排除单个大缓冲：**看 scudo secondary 的大块分布；实测单块最大仅 1.6 MB，说明数十 MB 的 native 占用是大量中小块与空场的积累，不是某个 native 大缓冲。
2. **降水位的方向：**治理高频临时分配让竞技场清空；应用侧没有强制 native 分配器归还的接口，不要寻找这类开关。

依据：Android 14 模拟器与某车机真机（Android 13）实测。

**Q10: [learning] 同一字体资源为什么会在进程内存里出现多份字节相同的副本，怎么判定与修复？**

实测某车机应用三个字体字重各在 Java 堆出现 3 份字节相同的 6.5 MB 副本、共 59 MB：直接成因是多条互不共享的加载路径各自把资源整份读进自己的缓冲，加上并发首用在缓存填充前竞态出并列副本。它随页面退出一起释放，不是崩溃级缺陷，但是值得修复的工程缺陷（峰值占用与安装体积）。

字重（weight）是同一字族的粗细变体；本例涉及 Regular、Medium、Demibold 三个字重，对应 400、500、700。

证据链与判定：

1. **哈希相同：**同尺寸数组哈希全同，先排除流水线缓冲，确认是同一文件的重复读取。
2. **双属性声明：**字体族声明文件里每个字体项同时写系统命名空间与兼容库命名空间两套字体属性，等于启用两条加载路径：系统路径按 mmap 共享资源、不产生 Java 堆副本；兼容库的字体组件会把资源字体整份读入内存缓冲再交给 native（此机制为由堆形态与组件行为作出的推断，未逐行核对兼容库源码），产生堆中观察到的 byte[] 副本。
3. **并发首用：**字体族被主题与多个样式引用，首帧并发 inflate 多个带该样式的控件，异步加载在缓存填充前为同一资源各发一次读取任务，副本数等于并发首用数。
4. **同生同死：**每份副本被各自的字体实例与 native 注册表钉住，UI 销毁时一起释放；实测页面退出后全部一起释放，无硬泄漏。

修复清单按性价比排序：

1. **砍双路径：**声明文件只保留一套命名空间的字体属性。
2. **消竞态：**启动时对每个字重同步预加载一次并全局复用，并发首用不再各读一份。
3. **用零拷贝路径：**只留系统命名空间属性，系统路径 mmap 共享资源，Java 堆零副本。
4. **瘦安装体积：**删除未使用字重；实测打包 10 个字重只用 3 个，删除可省 40 MB 以上。
5. **长期子集化：**全 CJK 字库每字重约 6.5 MB，按 UI 实际用字子集化可降到 1 至 2 MB。

判定边界：多份同尺寸大数组共存时，先用哈希区分"重复加载"与"流水线缓冲"；再用是否随页面退出一起释放区分"缺陷"与"泄漏"。

依据：Android 14 模拟器与某车机真机（Android 13）实测。
