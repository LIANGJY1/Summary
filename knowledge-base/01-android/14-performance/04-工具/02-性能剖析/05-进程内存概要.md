# Debug Memory Info

本组收录该工具或 API 的采集、使用与结果解释题。

<!-- 来源：03-resource-domains/01-memory-performance.md · Q1 -->

**Q1: [learning] Debug.MemoryInfo 的 App Summary 口径是什么？为什么 getProcessMemoryInfo() 不能高频调用？**

App Summary 是 dumpsys meminfo 的应用摘要口径。常用值回答不同问题：

1. `getMemoryStats()`：返回 `summary.java-heap`、`summary.native-heap`、`summary.graphics` 等域摘要键（AAOS13 `Debug.java` 核对）。
2. `getTotalPss()`：按比例分摊共享页，并包含已换出页的 SwapPss。
3. `getTotalUss()`：各域 Private Clean 与 Private Dirty 的总和。
4. `getMemoryClass()`：返回 MB 为单位的 ART 托管堆近似预算；它与 PSS 不是同一口径，不能相除得到使用率。

getProcessMemoryInfo() 只面向调试或进程管理 UI：官方文档明确 Android Q 起普通应用只返回调用 UID 进程的信息（其余为 0），且采样被显著限频——调用快于限频会返回上一次的数据。AAOS13 AMS 实现为按 MEMORY_INFO_THROTTLE_TIME 节流加缓存。因此它适合放在实验步骤边界或低频诊断任务中，不能放进每帧回调、紧循环或高频定时器。更短的采样周期未必产生新数据。

**Q2: [learning] dumpsys meminfo 的 PSS、RSS、私有脏页与 SwapPss 应怎样解读？**

按问题选择口径。比较进程总体驻留量时先看 PSS，排查可疑增长时再看分类和私有页。

1. **PSS** 将私有驻留页全额计入，共享页按共享进程数分摊。
2. **RSS** 统计进程映射的全部驻留页，共享页会在多个进程中重复计入。同一设备快照里 PSS 为 87.5 MiB、RSS 为 172.5 MiB。
3. **Private Dirty / Private Clean** 分别统计已修改和未修改的独占页。检查脏页的增长来自 Java 堆、Native 堆还是匿名映射。
4. **SwapPss** 统计分摊到进程的换出页。后台驻留量下降时，同时核对 PSS 与 SwapPss。

先读汇总区的 TOTAL PSS，再看 Java Heap、Native Heap、Graphics 等分类，最后查详细映射和对象计数。Graphics 为 0 也可能是设备未提供有效统计。对象计数反复上涨是追查引用链的线索。

依据为 Android Developers 的 dumpsys 文档及 Android 14 模拟器、Android 13 车机样本。

**Q3: [learning] 从 dumpsys meminfo 输出提取总 PSS，直接搜 TOTAL 为什么会出错，怎么写才可靠？**

输出里有两类含 TOTAL 的行：汇总区尾部的 TOTAL PSS： 87537 是给人读的文本行，详细表尾的 TOTAL 87537 58184 ... 才是数据行，且数据行的列宽随数值位数变化，固定列位或简单匹配 TOTAL 都会拿错。可靠提取式：

```bash
awk '$1=="TOTAL" && $2 ~ /^[0-9]+$/ {print $2}'
```

第一个条件排除文本行（其第二字段是 PSS： 而非数字），正则再排除异常行。配套纪律：序列采样按固定间隔使用同一解析式；每个检查点把完整输出落盘，后续的分类对账与 Objects 区分析都要用原始文件，不能只存提取后的数字。

依据：Android 14 模拟器与某车机真机（Android 13）实测。

**Q4: [learning] 后台闲置进程的 PSS 回落，为什么不能全部当成释放？**

后台进程的 PSS 下降可能来自换出。启用压缩交换时，部分匿名页可进入 zram，而原有驻留页被释放。

1. 同时记录 PSS 和 SwapPss。前者反映驻留量，后者反映进程分摊的换出量。两者相加可辅助比较驻留与换出的逻辑规模。
2. 核对进程状态与各内存分类。某 Android 13 车机样本的 SwapPss 达 43.9 MiB，单看 PSS 会低估其保留的匿名页。zram 实际消耗还受压缩率与元数据影响。
