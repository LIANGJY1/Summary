# 内核模块构建与部署

> 学习资料（文章模式沉淀）。边界：本文回答"Kconfig/Kbuild 如何决定内建与模块、外部模块编译与工具链匹配、.ko 部署验证与迭代流程"；驱动运行时设计归 [../12-platform-native/02-driver-runtime.md](../12-platform-native/02-driver-runtime.md)。Q 序列即结构，供 atlas 同源直读。

**Q1: `obj-y`、`obj-m` 与 Kconfig 的 `bool`、`tristate` 如何决定驱动是内建还是模块？**

Kconfig 决定功能配置值及依赖，Kbuild 的 `obj-$(CONFIG_FOO)` 根据该值选择将目标编入内核、构建成 `.ko` 或不构建。配置类型与 Kbuild 目标必须匹配。

`bool` 配置通常只能取 `y/n`，适合控制内建或关闭；`tristate` 可取 `y/m/n`，分别对应内建、模块或关闭。Makefile 中 `obj-y += foo.o` 纳入内核映像，`obj-m += foo.o` 构建可加载模块；写成 `obj-$(CONFIG_FOO)` 时，符号值决定展开结果。

新增驱动时，需要在正确目录的 Kconfig 声明配置项、在 Kbuild Makefile 加入对象，再通过产品配置启用。配置符号未启用、依赖不满足或 Kconfig 类型不支持 `m` 时，源码不会按预期生成目标。

**Q2: 外部内核模块（out-of-tree module）如何利用内核 Kbuild 编译，为什么主机编译器路径不能照搬？**

外部模块应通过目标内核已配置/准备的构建树调用 Kbuild，并用 `M=<模块目录>` 指明模块源码目录；编译器、架构、配置和符号版本必须与目标内核匹配。

典型形式是 `make -C <kernel-build-tree> M=<module-source-dir> modules`。其中 `-C` 指向目标内核源码或其已准备的输出构建目录，`M` 指向外部模块。AAOS 目标通常要使用其内核构建系统要求的 LLVM/交叉工具链与参数；宿主机默认 GCC 仅因能编译 Linux 程序，并不意味着能生成设备可加载的 `.ko`。

必须同时匹配目标架构、内核配置、生成头文件、`Module.symvers`/符号版本等信息。Android 内核构建树如何准备随分支而异，应优先使用该分支提供的构建脚本，而不是硬编码个人目录或 clang 版本。

**Q3: `.ko` 构建成功后，为什么还不能断定它能在 AAOS 设备上加载？**

`.ko` 文件只是构建产物；设备是否接受它还取决于运行内核兼容性、签名/模块策略、权限、SELinux 与模块依赖。主机上编译成功不等于目标内核通过加载验证。

部署前确认模块为目标 ABI，且与设备当前运行的内核版本、配置和符号信息匹配。加载失败时检查内核日志中的 `vermagic`、未知符号、签名、格式或策略错误。量产系统可能禁用动态模块加载或要求受信任签名；userdebug 模拟器上的实验流程不能视为量产设备流程。

**Q4: 修改字符驱动后，如何组织重新构建、部署、验证和清理？**

迭代应围绕同一目标内核构建环境完成，依次更新源码、构建目标、部署匹配的 `.ko` 和测试程序、加载并验证，再卸载和检查清理结果。

1. 先确认改动属于内建驱动还是可加载模块；两者的重新构建和部署路径不同。
2. 使用匹配的内核构建树与工具链重新构建，并检查日志、模块架构及符号/版本信息。
3. 将产物部署到允许的位置；只有目标系统允许动态加载且具备所需权限/策略时，才通过 `insmod`/`rmmod` 测试模块。
4. 验证设备节点、返回数据、边界错误、内核日志和并发/卸载行为；退出前确认节点与模块按预期撤销。

模拟器的 `adb root`、`dmesg`、`emulator -show-kernel` 和临时目录可辅助实验，但 root 权限、日志可见性和 SELinux 行为由镜像配置决定。不要在未确认节点/内核策略时把实验命令照搬到真机或量产系统。
