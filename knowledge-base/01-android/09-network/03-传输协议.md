# Android 传输与车云协议实践

本册收录车云协议定界与版本兼容、车机链路选型、连接恢复、拥塞与弱网诊断。TCP 字节流、定界与套接字保活接口见 [套接字接口](../../02-os/03-进程与通信/03-套接字接口.md)，HTTP 流复用、流量控制与 QUIC 迁移见 [通用 HTTP](../../03-network/02-HTTP.md)。车云业务的多网络绑定和消息通道见 [多 APN 与虚拟网卡](05-多APN与虚拟网卡.md)。

**Q1: [learning] 车云二进制协议怎样把 TCP 字节流解析成业务帧？**

可用固定帧头加变长正文定义车云二进制协议。帧头包含魔数、版本、正文长度和校验信息。解析器保存尚未收到完整帧的字节，先读齐头部并检查长度上限，再按长度收集正文。Netty 的 LengthFieldBasedFrameDecoder 可按协议中的长度字段切帧。

1. **定界。** 一次读取可能只收到一部分帧，也可能收到多帧。解析器持续消费已收齐的帧，把剩余字节留到下一次读取。若直接根据分隔符切分二进制内容，要定义转义规则以处理正文中的同值字节。
2. **扩展。** 车联网遥测可以在帧内用 TLV（Type-Length-Value）组织可新增的信号。帧头长度标识整条业务帧，TLV 的长度标识单个字段。
3. **校验。** 在协议容许重同步时，魔数提供候选帧起点，仍须检查版本、长度和校验值。CRC（Cyclic Redundancy Check）用于检测传输或存储中的意外损坏。

**Q2: [learning] 车控指令偶尔“一顿一顿”延迟 40ms，跟 Nagle 算法有什么关系？**

Nagle 算法为减少小包，会攒住未满 MSS 的小包，直到收到前一个包的 ACK 才发下一个。对端 TCP 还有延迟确认（案例中的等待约 40 ms，具体时序取决于实现与连接状态）——两者叠加形成“发送方等 ACK、接收方等数据”的互等，交互式流量表现为固定节奏的卡顿（社区实测案例：未开 TCP_NODELAY 的音频流服务端收帧忽快忽慢）。对策：交互式/小包低延迟连接（车控指令、实时音频、RPC）设置 `TCP_NODELAY` 禁用 Nagle，让小包立即发出。吞吐型大流量传输保持默认即可。注意禁 Nagle 只影响发送节奏，不解决带宽与拥塞问题。带外确认：抓包看小包是否按发送节奏到达，是验证 NODELAY 生效的直接证据。

**Q3: [learning] Android 车云长连接出现假在线时，保活和业务心跳各做什么？**

车机仍显示 TCP 已建立时，对端可能已经重启，或者链路静默失联。连接闲置时内核不一定很快感知；主动发送后，故障也可能等到重传超时才暴露。内核探测和业务心跳用于发现不同故障。

1. **协议栈探测。** 已启用的 TCP keepalive 识别一部分对端或路径失联情况。Android 可按可用网络、接口权限及设备卸载能力评估 SocketKeepalive，把部分探测交给底层。系统默认空闲期与业务恢复期限不一定一致，需按目标设备和连接测量。
2. **业务健康与恢复。** 心跳设置明确的响应期限，才能判断对端应用是否仍能处理请求。超时后关闭旧连接、重新连接并恢复会话状态。车云 MQTT 可用 Keep Alive 检测连接失活，遗嘱消息通知订阅方。
3. **旧会话清理。** 链路恢复时服务器可能仍保有旧会话。服务端按会话令牌区分新旧连接，或明确允许新连接顶掉旧连接，避免同一个车端会话双活。

**Q4: [learning] “PC 浏览器 HTTPS 正常、车机/App 握手失败”——证书链不完整事故怎么定位？**

最常见根因是服务器只部署了域名证书、漏发中间证书链（阿里云小程序握手失败案例与 TopSSL 排查文章口径）：完整信任链需要“站点证书 → 中间 CA → 根 CA”，服务器必须把中间证书一并发送。桌面浏览器有中间证书缓存并能通过 AIA（Authority Information Access）在线补齐，多数移动客户端不具备补齐能力，直接握手失败——所以“电脑正常、车机不行”恰恰指向链不完整而不是网络问题。定位：SSL Labs/myssl.cn 检测工具报 "Chain issues: Incomplete"，或 `openssl s_client -connect host:443` 看返回链。修复是把 fullchain（站点+中间证书拼接）部署上服务器。车机交付检查单里应加入“全证书链检测”，避免新业务域名带着这条病上线。

**Q5: [learning] Linux/Android 的 TCP 拥塞控制是什么？应用层能利用什么结论？**

内核默认拥塞控制多为 cubic（丢包驱动），新内核支持 BBR（基于带宽与 RTT 估计，弱网长肥管道下更稳，通用 Linux 机制口径。切换算法需 sysctl 权限，应用不可调）。应用层可利用的结论三条：慢启动期吞吐爬坡——长连接复用比每次新建快，首包后不要立刻打满。丢包会被 cubic 解释为拥塞并塌缩窗口——弱网下应用层主动限速（04 册下载策略）比“能发多快发多快”总吞吐更高。QUIC 在应用层自带拥塞控制，绕开内核算法限制——这就是弱网优化选 QUIC 的底层原因之一。诊断勿把“限速导致丢包”误判为网络故障：应用自限速、运营商 QoS、拥塞丢包三者的抓包特征不同（重传模式与窗口轨迹）。

**Q6: [learning] 自定义二进制协议的字节序与版本兼容怎么设计？**

字节序统一用网络序（大端），编解码集中在协议层一处完成，业务层永不手写字节操作——大小端问题是跨厂商联调最高频的协议 bug 源。版本兼容纪律：帧头带版本号，新增字段只增不改不改语义（TLV 天然支持未知字段跳过——不认识的 Type 按 Length 跳过继续解析，这是 TLV 相对紧凑结构的最大工程优势）。删除字段先废弃后移除。枚举值只增不减。升级策略：版本协商在握手阶段完成（双方取交集），低版本对端不识别的新字段靠“跳过未知”消化。这些纪律与 02 册的通道设计（绑定、重连、幂等）组合，才是完整的车云协议设计。

**Q7: [learning] 车云通道怎么选型——MQTT、HTTP(S)、私有 TCP/QUIC 各适合什么？**

按业务特征选通道（综合本章节各册）：**MQTT**——双向指令与状态遥测，持久会话+遗嘱+QoS 解决弱网不丢指令，是 TSP 消息通道默认解。**HTTPS**——大文件（OTA 更新或地图数据）、低频配置拉取、生态兼容性要求高的接口，请求-响应模型简单、CDN/网关生态成熟。**私有 TCP/QUIC**——极致延迟或特殊传输语义（实时音视频流、高频信号流）才值得自建，代价是协议维护、断线恢复、安全全部自己做。常见反模式：用 HTTP 轮询模拟推送（延迟与耗电双输）。用 MQTT 传大文件（Broker 存储与重传成本失控）。多通道共存是常态：一条 MQTT 指令通道 + HTTPS 文件通道 + 可选实时流通道，按业务分流到对应 APN。

**Q8: [learning] 车机开热点后“部分网站打不开”，为什么可能是网段冲突？**

Android 热点默认网段是 192.168.43.0/24（工业设备案例中手机热点 192.168.43.x 同段冲突的定位方法可直接迁移）：当热点网段与车机侧其他内网（TBOX 专网、诊断网段、上游路由器 LAN）相同或重叠时，路由表出现同目的不同接口的歧义，流量被路由进错误链路形成黑洞——症状是“热点客户端能连上、部分目标不通”，且随上游环境变化时好时坏（工业案例口径：Ping 不通但独立通道正常）。设计期对策：车内各网段统一规划互不重叠（热点、veth、专网各占独立 /24），并对已知常见网段（192.168.0/43/1.x）避让。运行期检测：冲突时从热点客户端 traceroute，第一跳之后的路径走向即可暴露歧义。修改默认热点网段在 framework/tethering 配置层完成（OEM 可定制）。

**Q9: [learning] DNS 劫持有哪些形态？HTTPDNS 为什么能防，怎么防得彻底？**

运营商/链路 DNS 劫持的常见形态（社区攻防实践口径）：解析结果替换（域名指向广告页或错误 IP）、TTL 篡改（长期缓存错误结果）、对不存在域名返回广告 IP（NXDOMAIN 重定向）。HTTPDNS 的防御原理是绕过链路 DNS：应用经 HTTPS 直接向 HTTPDNS 服务查询解析结果，解析路径不走运营商递归，天然避开劫持点（腾讯云/阿里云实践口径）。防彻底还要补三件事：结果校验（对解析 IP 做服务侧校验或 HTTPS 域名校验兜底，防止 HTTPDNS 通道本身被污染）、降级路径（HTTPDNS 不可用时回退系统 DNS，但要保留劫持检测）、与证书校验联动（HTTPS 的域名校验使“连上假 IP”也无法完成握手，是最后一道防线）。车机注意：私网域名走私网 DNS，公网 HTTPDNS 不解析私网名——两套解析体系按域名域分流，不能混用。

**Q10: [learning] 业务拆成多条连接后，消息乱序怎么设计保序？**

车云常见形态是指令与遥测各走独立通道（甚至不同 APN），同一业务对象的事件会乱序到达——“状态变更回执”可能晚于下一条指令的回执到达。设计三件：**业务序列号**——按业务对象（车辆/会话）维护单调序号随消息下发，接收端按序号重组与去重，不依赖到达顺序。**连接亲和**——同一业务键的消息固定走同一连接/通道，天然串行（代价是通道故障时该业务全停，按业务重要性取舍）。**版本/时间裁决**——跨通道的最终状态以业务时间戳或版本号高者为准，到达顺序只影响延迟不影响正确性。反模式：按“谁先到谁生效”处理带因果的消息（如“解绑”先于“绑定”到达），业务状态机直接错乱——保序是协议设计职责，不能指望网络替你保序。

**Q11: [learning] 对端一直不 read 数据，本端的 send 会怎样？TCP 流量控制怎么工作？**

TCP 用滑动窗口做流量控制：接收方在每个 ACK 里通告自己的剩余接收缓冲（rwnd），发送方未确认在途数据不能超过该窗口——对端应用不 read，接收缓冲逐渐占满，rwnd 通告到 0，发送方 `send()` 就会阻塞（或非阻塞返回 EAGAIN），直到对端恢复读取、窗口重新打开（通用 TCP 机制口径）。两层推论：阻塞与假死——“发得慢”不是网络问题而是对端消费不动，诊断看两端缓冲与窗口（`ss -tm` 可见），修复在对端的消费速度而非本端重试。超时风险——窗口长期为 0 时 TCP 有探测机制（零窗口探针），但应用层的写超时（SO_SNDTIMEO/非阻塞+select）要自己设，否则业务线程可能无限期挂起。UDP 对照：接收缓冲满时新到的包直接丢弃、不阻塞发送方——这就是高频遥测选 UDP 的机制根源。

**Q12: [learning] 高频小信号上报选 UDP 还是 TCP/MQTT？UDP 的坑在哪？**

UDP 适合的判据：容忍偶发丢失（下一帧信号很快覆盖）、追求低延迟（无握手无重传排队）、发送频率高到 TCP 状态维护不划算——车机高频信号流是典型。UDP 无连接也无队头阻塞，一包丢失不拖累后续包（与 TCP 的排队阻塞形成对照）。必须自建的三件事：**序列号**用于去重与乱序排序。**丢包容忍策略**（信号类丢一帧无碍，累计类要用周期快照代替增量）。**MTU 约束**——UDP 超过路径 MTU 会触发 IP 分片，任一分片丢失则整包报废，等于把丢包率放大数倍，单包应控制在安全尺寸内（通用 UDP 工程口径）。反例：不可丢的指令、需要会话与安全的业务不要用裸 UDP——自建可靠层等于重写半个 TCP。这类需求回到 MQTT/TCP 通道。选型一句话：信号流用 UDP+序列号+快照，指令与事务用可靠通道，按报文语义分流而不是全局一刀切。

**Q13: [learning] 车机大量短连接后“新连接建不出来”——TIME_WAIT 累积是怎么回事？**

主动关闭连接的一方会进入 TIME_WAIT 状态并停留约 1–4 分钟（2MSL，通用 TCP 机制口径），期间占用本地四元组（源 IP+源端口+对端+端口）。车机上典型的触发形态：某些模块用“每条请求新建连接、用完即关”的模式高频访问服务器，短连接把临时端口与 TIME_WAIT 槽位消耗殆尽，症状是新建连接失败（EADDRNOTAVAIL）或大量连接堆在 TIME_WAIT。治理按优先级：**长连接复用**是根治（连接池或单一 MQTT 通道），短连接场景开启端口复用参数（`tcp_tw_reuse`，需系统层权限，且仅对出向连接有效）。同时检查是否真的需要逐条新建——HTTP 的 keep-alive 已是标配。定位：`ss -s` 与 `ss -tan state time-wait | wc -l` 看规模，按对端统计是谁在制造短连接。

**Q14: [learning] “网关 ping 不通但配好 IP 了”——二层（ARP）排查怎么做？**

IP 配置正确不代表二层可达：ARP 表里网关条目异常（STALE/FAILED/被别的设备冒用 IP）会让流量卡在“找不到网关 MAC”，表现与断网无异（通用 Linux 机制口径）。排查三板斧：`ip neigh` 看网关条目状态——FAILED 表示 ARP 请求无应答，REACHABLE 才是健康。`ip neigh flush` 清掉可疑条目后重新触发流量观察学习过程。抓 ARP 包（`tcpdump arp`）确认请求与应答是否成对、应答 MAC 是否正确。车机特有场景：网关切换/重复 IP（02 册网段冲突）都会让 ARP 学习到错误表项。热插拔上游设备后“旧网关 MAC 失效”也是同类。三层定位口诀：ARP 不通查二层（线、隔离、IP 冲突），ARP 通而 IP 不通查路由，路由通而业务不通查应用——这条口诀是 02 册五段定位法的二层前置段，车辆链路问题先过这一层再进入 IP 层取证。
