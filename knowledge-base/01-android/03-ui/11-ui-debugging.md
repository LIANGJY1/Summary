# UI 疑难排查与体验踩坑

> 学习资料（文章模式沉淀）。主线：UI 问题的分层归因、窗口不显示/白屏/黑屏的判定顺序、首帧阻塞定位、掉帧的阶段归因与帧度量字段、抓帧工具集、重绘范围过大的判定与治理、系统栏与圆角遮挡的正确解法、输入分发超时与 UI 阻塞的关系、渲染相关内存与纹理代价、SurfaceView 黑区、车机多显示与电源策略带来的特有故障、复盘与预防机制。AOSP 机制按本地 AAOS13 源码（Android 13）核对（WindowManagerShellCommand.java、ActivityManagerService.java 的 dump 归属、FrameMetrics.java、ViewRootImpl.java），命令与工具用法按官方文档口径（2026-09 检索）。系统侧机制见 [04-window-system.md](04-window-system.md)，绘制与失效机制见 [02-view.md](02-view.md)，流畅性度量方法见 [流畅性度量](../15-performance/05-smoothness.md)。Q 序列即结构，供 atlas 同源直读。

**Q1: 遇到白屏、黑屏或卡顿时，为什么应先分层归因再抓帧？**

先按进程、窗口、合成和硬件分层归因，再抓帧。抓帧只能说明某一帧的结果，不能单独解释界面为何没有出现。

1. **进程与线程**：确认进程、目标 Activity 和主线程是否正常。
2. **ViewRootImpl**：确认窗口根节点是否建立、是否请求重绘、是否跳过绘制。
3. **WindowManagerService**：确认窗口、frame、可见性与 insets。
4. **合成侧**：确认图层是否存在、尺寸是否为零、是否被裁剪或遮挡。
5. **硬件与驱动**：最后检查刷新率、合成耗时和面板。

先看高层能更快定位界面为何未建立。确定图层已提交后再抓帧，才能判断内容或呈现问题。buffer 会被覆盖，因此需要按现场及时取证。

**Q2: 应用页面完全没出来，怎样从窗口建立、frame 到图层逐步判定？**

三段判定，各段的判据不同：

1. **窗口是否建立**：`dumpsys window windows` 里查目标窗口。若不在列表，抓应用侧异常（BadTokenException 之类）与 relayout 返回码，问题在建立阶段结束。
2. **frame 是否正确**：在列表里就看 frame 与可见性相关字段。frame 为 0 或异常小，指向布局约束或测量问题。`isOnScreen` 为假时检查可见性、焦点和遮挡。
3. **是否被合进去**：`dumpsys window displays` 看该显示上的层级与 insets。`dumpsys SurfaceFlinger --list` 确认图层存在，再用 `dumpsys SurfaceFlinger` 看该图层尺寸与被谁遮挡。

顺序的价值是每一步都能排除一整类原因。反过来从合成层往上猜，通常会误判成"渲染问题"。

**Q3: 冷启动白屏数秒，如何把首帧前的初始化阶段拆开定位？**

判据是"首帧之前做了什么"：把时间轴对齐到进程创建，分别测量以下阶段：

1. Application 初始化。
2. ContentProvider 初始化。
3. Activity.onCreate 到 onResume。
4. 首次 measure/layout/draw 遍历。

优先检查主线程上的同步初始化、网络或磁盘等待，以及布局一次性创建大量对象。

还要排除两种假象：

1. 白屏持续很久但首帧很快，问题可能在合成或显示点亮时机。车机还要检查电源策略是否关闭显示。
2. 首帧很快但用户看到的只是骨架，这属于产品设计，不是首帧延迟。

**Q4: 透明主题页面看似黑屏，怎样区分窗口未创建与窗口有界但没有内容？**

透明主题窗口没有背景，而内容尚未绘制时，合成结果会显露下层窗口或背景，看起来像黑屏。要先确认窗口与内容是否提交，再归因于主题。

1. **常见来源**：启动过渡 Activity 使用透明主题且首帧未填充内容，普通页面误用了 Dialog/半透明主题，或内容树为空、异步加载期间没有子节点。
2. **窗口检查**：运行 `dumpsys window windows` 确认目标窗口存在且 frame 非零。若窗口不存在或 frame 异常，应先排查建窗与布局。
3. **视图检查**：打开开发者选项中的“显示布局边界”。能看到边界说明视图布局已建立，但不证明内容像素已提交。看不到边界则继续查内容树与窗口提交。
4. **修复顺序**：先提供非透明背景和可显示的首帧内容，再处理过渡效果与层级。

**Q5: 帧时间超预算或用户仍感觉掉帧，怎样区分 UI 线程、渲染线程和合成侧？**

按帧时间里的阶段字段分。应用侧可以拿到的帧度量里有三个关键量：总耗时（`TOTAL_DURATION`）、输入处理耗时（`INPUT_HANDLING_DURATION`）与本帧预算（`DEADLINE`，本地 FrameMetrics.java 核对：总耗时小于预算即视为命中本帧）。判定规则是：

1. **总耗时本身就超预算**：看输入处理耗时占比很高（首要是事件处理逻辑与同步 Binder），还是占比不高但绝对值大（布局或绘制过重）。
2. **总耗时没超预算但仍掉帧**：问题在应用之外——合成侧或显示侧，典型是刷新率切换、多图层合成、驱动侧等待。

这个判定必须用真实帧数据，不能靠体感：体感只能告诉你"这一帧晚了"，数据才能告诉你晚了哪一段。

**Q6: 需要判断是哪个窗口迟交帧，gfxinfo、SurfaceFlinger 与 Perfetto 各提供什么证据？**

1. **gfxinfo 查询**（含 framestats 变体）：例如 `dumpsys gfxinfo <包名>` 可查看应用级帧统计与阶段耗时。它属于 ActivityManagerService 的 dump 命令。`dumpsys window` 则由 WindowManagerShellCommand 提供。
2. `dumpsys SurfaceFlinger --latency <窗口名>` 与 `--latency-clear`：单窗口的呈现时间戳序列，回答"帧是准时到的还是迟到的"。适合确认掉帧是应用提交晚还是合成/呈现晚。
3. **SurfaceFlinger 图层查询**：使用 `dumpsys SurfaceFlinger` 或 `--list`。图层与缓冲状态。
4. **Perfetto trace（gfx、view、input、hal、sched、freq、binder_driver 等类别）**：能同时看到 UI 线程调用栈、渲染线程、合成与内核调度，回答"这一帧的时间花在哪"。工具与类别用法见 [Perfetto 采集与 SQL 分析](../15-performance/04-perfetto-analysis.md)。
5. **帧时间线 / 帧指标采集**：FrameMetrics 回调可把逐帧数据收进自有采集，用于线上分布统计。

选型原则：先确定要回答"应用内还是应用外"，再选工具。不要用一类工具的数据去解释另一类工具的现象。

**Q7: ViewRootImpl 没有执行绘制时，是否能从框架诊断字段找到跳过原因？**

AAOS 13 的 ViewRootImpl 会在遍历与 dump 信息中记录跳过绘制的原因，但这些是框架内部诊断细节，必须在目标系统版本核对。

1. **记录含义**：字段可指出屏幕关闭、根视图缺失、前置绘制回调取消等情况。它能把“没有重绘”的假设变成可检查原因。
2. **处置区别**：屏幕关闭时不应盲目重试。业务取消或 `cancelDraw` 则要追查触发取消的回调与状态。
3. **版本边界**：内部字段、dump 路径和具体原因可能随版本变化。本地 AAOS 13 源码与目标产品分支若不同，应以目标分支为准。

**Q8: 局部数据变化造成大范围重绘和掉帧，如何判断失效范围并缩小成本？**

先确认失效是否必要，再判断父子尺寸变化和动画是否扩大了重绘范围。缩小高频变化区域通常比一味简化整棵视图树更有效。

1. **调用路径**：检查属性 setter 是否调用 `invalidate()`，自定义 View 是否漏调或重复失效。
2. **脏区范围**：父容器尺寸变化可能使子 View 的局部失效扩大为整层重新录制。
3. **动画路径**：逐帧修改绘制属性可能不断触发重录，成本随动画时长累计。
4. **治理顺序**：将高频变化部分拆成独立小 View，再优先使用只改变合成位置的属性动画。若数据变化不影响视觉，去掉无效 `invalidate()`。最后再压平层级和减少绘制调用。

**Q9: 刘海、圆角或系统栏压住按钮，怎样按 Insets 调整内容与点击区域？**

用 `WindowInsets` 处理系统栏、显示切口和手势区的动态避让，不要写死屏幕边距。

1. **选择类型**：通过 `WindowInsets.Type` 指明需处理的状态栏、导航栏、显示切口或强制手势区域。
2. **响应变化**：在 insets 回调中更新对应容器的 padding。尺寸或位置因此变化时让布局重新计算。
3. **沉浸式场景**：内容可延伸到系统栏下方，同时把交互区域避开系统手势区。用 `WindowInsetsController` 控制系统栏显隐，不以硬改布局代替窗口栏策略。

**Q10: 用户点击后长期无响应并出现输入超时，主线程阻塞如何造成这两类现象？**

主线程长时间忙碌会让输入事件排队，既造成点击无响应，也可能使事件超过输入分发超时。

1. **卡顿证据**：界面短时迟滞但未超过输入超时，优先在主线程 trace 中定位同步工作。
2. **超时证据**：分发超时日志和 ANR 提示说明事件未及时交给目标窗口处理。还要检查应用主线程是否阻塞。
3. **共同治理**：把磁盘、网络、长计算和同步 Binder 工作移出主线程。出现输入超时需要优先处理，因为它已影响事件分发及时性。

**Q11: 页面渲染卡顿并伴随内存上涨，怎样区分分配、纹理与缓冲区问题？**

将帧表现与内存类别结合，才能区分绘制工作过重、分配压力和图形资源未释放。

1. **帧卡但内存稳定**：检查大位图每帧重传、大面积模糊或渐变造成的绘制与纹理上传成本。
2. **帧卡且内存上涨**：检查绘制路径对象分配、重复解码和大图峰值。
3. **内存缓慢增长且不回落**：检查纹理、硬件缓冲和 Surface 资源是否释放。
4. **验证手段**：结合内存分类统计与绘制 trace。图片优先按目标尺寸下采样，并为不同屏幕选择合适资源变体，避免解码原图后再缩放。

**Q12: SurfaceView 区域变黑或偏移，如何分别确认图层、位置和 buffer？**

按三段排除：

1. **检查图层**：确认 SurfaceFlinger 中图层存在且尺寸正确。
2. **检查位置与遮挡**：确认 SurfaceView 的位置、透明区域和父窗口中的其他图层没有冲突。
3. **检查内容提交**：确认视频解码或渲染仍在运行，并确实送出了 buffer。黑区常见的成因是"父视图变换与独立 surface 不兼容"——在目标 Android 版本不支持对应变换的情况下，对 SurfaceView 做旋转、圆角或缩放动画可能无法得到与普通 View 相同的裁剪和变换结果，因而出现错位或空区。

**Q13: 车机同一页面在主屏和副驾屏大小不同，怎样检查显示配置与窗口几何？**

跨显示尺寸不一致时，先检查 Activity 使用的显示上下文，再分别检查窗口几何和显示重新分配后的状态恢复。

1. **资源上下文**：Activity 的 Configuration 与显示关联。从默认显示或进程全局度量取值可能不对应当前窗口。
2. **窗口尺寸**：窗口实际几何以 relayout 结果为准，不能用 Configuration 替代窗口尺寸。
3. **重新分配**：显示移除、重新分配或 occupant zone 改变可能导致 Activity 重建或换绑。需要持久化的 UI 状态不应只保存在旧 View 实例中。

**Q14: 车机屏幕熄灭但应用进程仍运行，如何判断是否由电源策略控制？**

车机息屏时进程仍可运行，需先排除应用渲染和窗口状态，再确认显示电源策略。屏幕不可见不等于 Activity 已退出。

1. **应用侧**：确认进程仍运行、是否继续提交帧以及是否保有窗口。
2. **显示侧**：查看 `dumpsys display` 和车辆电源状态，确认是否由 power policy 关闭显示。
3. **恢复测试**：通过车辆信号触发电源状态变化，不以手动关屏替代真实休眠/唤醒。
4. **持续任务**：导航播报等逻辑需单独处理电源与可见性状态，不能把屏幕熄灭当成应用被切走。

**Q15: 同类 UI 缺陷反复回归，怎样把视觉与状态问题变成可重复验证的检查？**

把"靠人眼看"变成"可判定"，可以落实为四项检查：

1. **埋点**：逐帧指标与应用级状态快照线上采集，掉帧率与白屏时长按版本跟踪（[线上诊断](../15-performance/16-app-observability-governance.md)）。
2. **可视化对比**：关键界面在多分辨率、多密度、多字号、多语言、深浅色下的截图基线对比，差异纳入评审。车机上还要按不同 occupant zone 显示各采一份。
3. **状态驱动测试**：把夜间模式、字号缩放、语言切换、UX 限制变化、电源状态、显示热插拔做成可触发的用例，而不是靠人工记得去点。
4. **走查清单**：按窗口与内容分类列出必查项（首帧、透明与层级、insets 避让、多字号不破版、分心限制形态、返回栈、异常恢复），每项写清判定标准，避免"看起来没问题"式验收。

**Q16: Android Studio 预览 XML 资源时如何缩放画布？**

Android Studio 的预览缩放只改变编辑器画布，不会改变 XML 中的 `dp`/`sp` 尺寸或运行时布局。

1. **工具栏**：使用布局预览工具栏的缩放控件调整画布。
2. **快捷键**：预览素材中的 Ctrl +/− 取决于操作系统、Android Studio 版本和当前 Keymap，不能保证各环境相同。
3. **查询按键**：快捷键无效时先聚焦预览面板，再用 Find Action 搜索 Zoom In/Zoom Out，或在 Settings/Preferences 的 Keymap 中查询当前绑定。
