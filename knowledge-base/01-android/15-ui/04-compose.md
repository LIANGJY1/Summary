# Compose 运行期与 View 互操作

> 学习资料（文章模式沉淀）。主线：组合/布局/绘制三阶段与"读状态即订阅"、组合期写状态的无限重组、remember 与 rememberSaveable 的持有边界、derivedStateOf 与延迟读取、稳定性推断与 strong skipping、列表键与重组范围、LaunchedEffect/SideEffect/DisposableEffect 分工、ComposeView 嵌入与组合策略、AndroidView 的代价、自定义宿主与帧时钟、重组与掉帧的归因工具、View 迁移的高频坑。Compose 属 AndroidX、不在 AOSP 源码树内，本册结论按官方文档与 AndroidX 源码口径（2026-09 检索）；渲染侧的帧调度与掉帧度量见 [../02-rendering/01-渲染管线与VSync调度.md](../02-rendering/01-渲染管线与VSync调度.md)，View 侧绘制机制见 [02-view.md](./02-view.md)，应用实践见 [Compose 渲染实战](../09-app-practice/07-渲染实战-Compose进阶.md)。Q 序列即结构，供 atlas 同源直读。

**Q1: 滚动列表时任意状态变化都让整页重组，Compose 的组合、布局、绘制各阶段怎样响应？**

三个阶段依次是组合（把 composable 函数执行成一棵节点树）、布局（测量并定位）、绘制（发出绘制命令）。重组指的是状态变化后**重新执行 composable 函数**以更新组合结果，它只发生在组合阶段。

机制是快照与订阅：状态对象写入时记下全局快照，组合执行期间被读取的状态被记录为"本次组合的依赖"；写入发生后，运行时把依赖集合中包含该状态的组合范围标脏，排进下一次重组调度（官方文档口径）。这条设计的后果是——重组范围由"谁读了状态"决定，而不是由"谁调用了谁"决定，因此把状态读尽量推迟到后面的阶段能直接缩小重组面。

**Q2: 点击后 composable 持续重组甚至掉帧，为什么不能在组合函数体里直接写状态？**

因为写入会把本次组合标脏，而标脏的下一次重组又会执行同一段代码再次写入，于是永远排不到一个"不再需要重组"的稳定态，表现为持续掉帧（官方文档把这类写法列为常见陷阱）。

正确做法是分清两类写：事件响应里的写（点击回调里改状态）发生在组合之外，是正确的；组合期间需要"同步派生"的写应当移出组合，或改为在下一帧/副作用里执行。判断标准是问"这次写入是否是因为组合读了某个状态而被迫发生"，是则说明它是派生逻辑，应该改写成派生而非写入。

**Q3: 旋转屏幕后输入内容消失，remember 与 rememberSaveable 分别能保留什么？**

remember 把值存在组合里，只跨重组有效，**不跨配置变更与进程重建**：屏幕旋转后拿到的是全新组合，之前记住的值消失。rememberSaveable 会把值按可保存形式写入实例状态，因此能跨配置变更恢复。

选型规则是"这个值是纯派生/缓存，还是用户可感知的界面状态"：缓存、对象引用、监听器用 remember；滚动位置、展开状态、输入内容这类"用户操作痕迹"用 rememberSaveable。可保存类型有限（基本类型、Bundle 可装类型等）：没注册 Saver 的自定义类型用不了 rememberSaveable——要么注册自定义 Saver 换取跨重建，要么退回 remember 并接受重建丢失。

**Q4: 滚动偏移每帧变化却只关心是否到达顶部，derivedStateOf 如何减少无用更新？**

它适合依赖频繁变化、但界面只关心派生结果何时变化的场景。例如列表滚动时，界面只需知道首项是否越过阈值；直接读取每帧变化的滚动偏移会触发过多更新，derivedStateOf 可以按派生结果是否变化来通知（Android 官方文档口径）。

默认不传 SnapshotMutationPolicy 时，派生状态会在依赖变化时触发更新，即使计算结果相等。若要按结果相等性过滤更新，应传入 structuralEqualityPolicy() 等合适的策略；不要为不相关或低频状态增加 derivedStateOf，它也有计算和管理成本。

**Q5: 某个状态更新让大量 composable 重跑，不稳定参数会怎样影响跳过？**

编译器根据类型是否不可变、变化是否可观察来推断稳定性。基本类型与不可变数据类型通常稳定；带可变属性的类型和 Kotlin List、Set、Map 等集合默认不稳定，即使变量声明为 val 也不代表集合内容不可变（Android 官方文档口径）。默认跳过规则下，参数不稳定的 composable 通常不可跳过；父级重组时，即使参数实际没有变化，它仍可能重新执行。

先用 Layout Inspector 或编译器稳定性报告确认问题，再考虑把集合改为不可变集合、明确建模可观察状态，或启用强跳过；不要只为消除报告而标注 @Stable / @Immutable。

**Q6: 启用 strong skipping 后不稳定参数仍会重组吗？它改变了哪些跳过规则？**

它是 Compose 编译器的一个模式，改变两件事：不稳定参数的 composable 也变为可跳过；捕获了不稳定变量的 lambda 会被记忆化（官方文档与 AndroidX 设计文档口径）。它引入于 Compose 编译器 1.5.4，并在 Kotlin 2.0.20 起默认启用。比较规则也随之分岔：不稳定参数用实例相等（===）比较，稳定参数仍用 equals。

需要知道的边界：它放宽的是跳过条件，不是让不稳定的类型变稳定；编译器仍会把 restartable 函数标记为可跳过，non-restartable 函数不受影响；lambda 在强跳过下会被自动记忆，因此"每次重组都新建 lambda 导致重组"这类问题会自动缓解，但不能替代稳定性治理。

**Q7: 高频状态只影响位移却反复触发组合，怎样把状态读取推迟到布局或绘制阶段？**

做法是把读取包进只在布局/绘制阶段执行的 lambda 型 modifier 或 effect，使状态订阅发生在后段阶段。官方文档给出的收益是：这样状态变化时可以跳过组合阶段，直接从布局阶段开始；代价是可读性和调试难度上升（官方文档口径）。

判断是否值得的标准是看 trace：只有当重组本身占了显著耗时、且被读状态确实高频变化时才推迟读取；否则优先用 derivedStateOf 与稳定键解决，收益更直接。

**Q8: 列表插入一行后输入状态跑到别的行，Lazy 列表的 key 应如何选择？**

它给每个列表项一个稳定身份，让 Compose 在数据增删、顺序变化或复用位置时能对上号：没有稳定键时，运行时按位置匹配，插入或删除会让后续项的数据"错位"到别的位置（表现为状态跑到别的行、动画错乱），并且容易在重组时丢掉复用收益。官方性能建议是给懒布局提供稳定键（官方文档口径）。

实践要求是键必须唯一且稳定：拿数据库主键或业务唯一 id，不要拿数组下标——下标在删除时必然复用，等于没有键。

**Q9: 协程因界面重组反复启动或资源未释放，三个 Effect 的生命周期边界是什么？**

1. LaunchedEffect 在组合后启动协程，键变化时取消上一个并重启。
2. SideEffect 在每次成功重组后运行，用于把非 Compose 状态同步到外部世界。
3. DisposableEffect 在组合后建立资源并在离开组合时清理，用于注册/反注册。

常见误用可以按触发时机区分：

1. **点击事件**：直接在点击回调里处理，不要把用户事件建模成 LaunchedEffect。
2. **每帧变化的 Effect 键**：会反复取消并重启协程；键应表达协程需要跟随的输入。
3. **需要长期保留的资源**：不要绑定到会频繁离开组合的 DisposableEffect，应选择与资源真实生命周期一致的 owner。

**Q10: Fragment 页面销毁后 Compose 内容仍占内存，ComposeView 的组合策略该怎样选？**

ComposeView 持有一个组合，需要明确的销毁时机，否则组合会随宿主一起泄漏、或在宿主暂时不可见时保留过期的状态。这就是 ViewCompositionStrategy 存在的原因，官方提供多种策略：在视图从窗口移除时释放、在离开 ViewTree 生命周期所有者时释放、或在进入对象池时释放（官方文档口径）。

选型规则：宿主是普通 Activity/Fragment 里的一个 View，用随 ViewTree 生命周期释放的策略最贴近直觉；宿主是可复用容器（列表项、Tab 页面、ComposeView 复用池），要用"从窗口分离即释放"或"归还对象池即释放"，否则会出现切走再切回状态莫名重置或内存涨高。

**Q11: Compose 页面嵌入旧 View 控件后变卡，AndroidView 的 update 应避免做什么？**

AndroidView 保留了一棵 View 子树，并通过桥接参与 Compose 的布局与绘制。性能风险集中在两处：

1. **update 做重活**：状态变化时更新块可能重新执行，因此不要在其中重复创建控件或运行昂贵计算。
2. **高频跨栈同步**：View 与 Compose 之间频繁传递变化会增加桥接与布局成本。

优先让 View 承担它擅长的部分，例如成熟控件或复杂自绘，并把更新块限制为必要的属性同步。

**Q12: 自定义 Compose 宿主中的动画与界面更新不同步，Recomposer 为什么需要帧时钟？**

宿主需要显式提供 Recomposer 与帧时钟，两者要成对设置，否则要么不重组、要么在错误时机重组。官方做法是把帧时钟接到平台的帧回调上，使重组调度与 VSync 对齐（官方文档口径）。

这正是"自定义宿主里动画和重组不同步"问题的根因：重组没挂到帧时钟上就会在消息循环的随机时机执行，布局在下一帧才生效，于是看到"点了没反应、过一会儿才跳"的现象。跨栈宿主还要先定 Composition 的销毁时机（如随窗口分离释放）——时机不明确就会泄漏或保留过期状态。

**Q13: Compose 页面滚动掉帧，应先用哪些工具区分重组、布局和绘制瓶颈？**

先归因到"重组慢 / 布局慢 / 绘制慢"，再处理：

1. **工具**：用 Layout Inspector 查看重组次数与哪些 composable 在重组；用 trace 事件（AndroidX 提供的 trace 事件 API，官方在性能文档中给出用法）把自定义慢逻辑包起来看耗时；用帧时间线/帧指标判断是否真的超过帧预算（度量口径见[流畅性度量](../07-performance/01-流畅性.md)）。
2. **归因顺序**：重组次数异常高 → 查不稳定参数与延迟读取；单次重组耗时高 → 查组合期重活与昂贵的列表筛选排序；布局慢 → 查测量复杂度与深嵌套；绘制慢 → 查绘制期分配与大面积渐变模糊。
3. **不要先做的事**：不要一上来就加缓存层或换渲染后端，先确认瓶颈阶段，否则优化落不到点上。

**Q14: 把旧页面从 View 迁到 Compose 后出现主题、状态或返回键问题，迁移时要检查哪些边界？**

1. **主题与类型体系不同**：View 主题属性与 Material 主题不是一一对应，迁移后颜色、字号可能整体偏移，需要逐屏比对而不是逐控件替换。
2. **状态归属**：迁移前状态常挂在 View 上，迁移后若不放进状态对象（或用 rememberSaveable 进实例状态），切走再回来会丢——remember 只跨重组、挡不住配置变更与进程重建。
3. **生命周期不对称**：View 的回调（绘制、可见性）与 composable 的生命周期不是一一对应，依赖 OnDrawListener 之类的逻辑迁过去往往要重新设计。
4. **返回键与焦点**：View 体系里靠 onBackPressed 与焦点顺序处理的交互，迁到 Compose 需要显式的返回处理与焦点修饰符，缺了就表现为"返回没反应"或"键盘焦点乱跳"。
5. **嵌回 View 的位置**：AndroidView 内部不要再反向调 Compose 状态，容易形成双向更新环。

**Q15: 同一页面混用 View 和 Compose 后尺寸与状态互相打架，怎样确定约束和状态的唯一来源？**

布局侧只有一条纪律：两者都要参与同一套尺寸约束，不要一个用固定 dp、一个用自适应，否则任何一侧的尺寸错误都会被另一侧放大。状态侧的方向是单向的——选定一个状态持有方，View 侧通过 AndroidView 的 update 接收状态、Compose 侧通过回调接收事件，不要让两个体系各自持有一份真值。

还有一个版本相关的注意点：Compose 侧走的是 AndroidX 的渲染实现与管线，跨栈页面的帧预算受两套系统的录制与渲染影响，混用页面掉帧时要按阶段分别归因，不要默认"卡在 Compose"或"卡在 View"。
