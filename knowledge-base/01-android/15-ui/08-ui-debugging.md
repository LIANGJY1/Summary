# UI 疑难排查与体验踩坑

> 学习资料（文章模式沉淀）。主线：UI 问题的分层归因、窗口不显示/白屏/黑屏的判定顺序、首帧阻塞定位、掉帧的阶段归因与帧度量字段、抓帧工具集、重绘范围过大的判定与治理、系统栏与圆角遮挡的正确解法、输入分发超时与 UI 阻塞的关系、渲染相关内存与纹理代价、SurfaceView 黑区、车机多显示与电源策略带来的特有故障、复盘与预防机制。AOSP 机制按本地 AAOS13 源码（Android 13）核对（WindowManagerShellCommand.java、ActivityManagerService.java 的 dump 归属、FrameMetrics.java、ViewRootImpl.java），命令与工具用法按官方文档口径（2026-09 检索）。系统侧机制见 [05-window-system.md](./05-window-system.md)，绘制与失效机制见 [02-view.md](./02-view.md)，流畅性度量方法见[流畅性度量](../07-performance/01-流畅性.md)。Q 序列即结构，供 atlas 同源直读。

**Q1: 遇到白屏、黑屏或卡顿时，为什么应先分层归因再抓帧？**

按五层分，从下往上排除，前一层不成立就不进后一层：

1. **进程与线程**：进程是否存在、界面是否在可见栈里、主线程是否被阻塞。
2. **ViewRootImpl**：窗口是否建立、是否被请求重绘、是否被判定跳过绘制。
3. **WindowManagerService**：窗口是否存在、frame 是否正确、可见性状态、insets。
4. **合成侧**：对应图层是否存在、大小是否为 0、是否被裁剪或遮挡。
5. **硬件与驱动**：刷新率、合成耗时、面板。

先抓帧的问题是它只能回答"某一帧发生了什么"，回答不了"界面为什么没出现"。一个白屏问题在合成层看是"图层存在但内容为初始 buffer"，根因却在主线程首帧阻塞；而一个图层完全不存在的问题，抓再多帧也没有诊断价值。归因顺序还决定了取证成本——越靠上层的信息越容易过期（buffer 会被覆盖），越靠下层越稳定。

**Q2: 应用页面完全没出来，怎样从窗口建立、frame 到图层逐步判定？**

三段判定，各段的判据不同：

1. **窗口是否建立**：`dumpsys window windows` 里查目标窗口。若不在列表，抓应用侧异常（BadTokenException 之类）与 relayout 返回码，问题在建立阶段结束。
2. **frame 是否正确**：在列表里就看 frame 与可见性相关字段。frame 为 0 或异常小，指向布局约束或测量问题；isOnScreen 为假指向可见性、焦点或被遮挡。
3. **是否被合进去**：`dumpsys window displays` 看该显示上的层级与 insets；`dumpsys SurfaceFlinger --list` 确认图层存在，再用 `dumpsys SurfaceFlinger` 看该图层尺寸与被谁遮挡。

顺序的价值是每一步都能排除一整类原因；反过来从合成层往上猜，通常会误判成"渲染问题"。

**Q3: 冷启动白屏数秒，如何把首帧前的初始化阶段拆开定位？**

判据是"首帧之前做了什么"：把时间轴对齐到进程创建，分别测量以下阶段：

1. Application 初始化。
2. ContentProvider 初始化。
3. Activity.onCreate 到 onResume。
4. 首次 measure/layout/draw 遍历。

优先检查主线程上的同步初始化、网络或磁盘等待，以及布局一次性创建大量对象。

还要排除两种假象：

1. 白屏持续很久但首帧很快，问题可能在合成或显示点亮时机；车机还要检查电源策略是否关闭显示。
2. 首帧很快但用户看到的只是骨架，这属于产品设计，不是首帧延迟。

**Q4: 透明主题页面看似黑屏，怎样区分窗口未创建与窗口有界但没有内容？**

因为窗口本身不画背景，内容也还没画出来时合成出来就是屏保或下层内容，视觉上等同于"什么都没有"。叠加一个常见错误——在首帧之前就去读窗口尺寸，会进一步把布局推迟，形成"透明 + 空尺寸"的互相等待。

透明主题的三个常见来源逐一排除：过渡用的启动页 Activity 误用透明主题且首帧前未填充内容；普通页面误配 Dialog/半透明系主题导致无背景层；内容树为空或首帧前被清空（异步数据未到时布局已挂但无子节点）。取证顺序：先确认窗口存在且 frame 非 0（白屏判定的第一段：`dumpsys window windows` 看列表与 frame），再开开发者选项的"显示布局边界"——边界画得出来说明窗口与视图树都在、只是没有内容像素，边界也没有则窗口或内容未提交；最后才怀疑透明与层级。修复与之反向：先保证非透明背景与首帧内容，再打磨过渡与层级。

**Q5: 帧时间超预算或用户仍感觉掉帧，怎样区分 UI 线程、渲染线程和合成侧？**

按帧时间里的阶段字段分。应用侧可以拿到的帧度量里有三个关键量：总耗时（TOTAL_DURATION）、输入处理耗时（INPUT_HANDLING_DURATION）与本帧预算（DEADLINE，本地 FrameMetrics.java 核对：总耗时小于预算即视为命中本帧）。判定规则是：

1. **总耗时本身就超预算**：看输入处理耗时占比很高（首要是事件处理逻辑与同步 Binder），还是占比不高但绝对值大（布局或绘制过重）。
2. **总耗时没超预算但仍掉帧**：问题在应用之外——合成侧或显示侧，典型是刷新率切换、多图层合成、驱动侧等待。

这个判定必须用真实帧数据，不能靠体感：体感只能告诉你"这一帧晚了"，数据才能告诉你晚了哪一段。

**Q6: 需要判断是哪个窗口迟交帧，gfxinfo、SurfaceFlinger 与 Perfetto 各提供什么证据？**

1. **gfxinfo 查询**（含 framestats 变体）：例如 `dumpsys gfxinfo <包名>`。应用级帧统计与阶段耗时。它属于 ActivityManagerService 的 dump 命令，不是窗口服务的命令（ActivityManagerService.java 与 WindowManagerShellCommand.java 归属核对；后者提供 `dumpsys window`）。
2. **dumpsys SurfaceFlinger --latency <窗口名>** 与 --latency-clear：单窗口的呈现时间戳序列，回答"帧是准时到的还是迟到的"。适合确认掉帧是应用提交晚还是合成/呈现晚。
3. **SurfaceFlinger 图层查询**：使用 `dumpsys SurfaceFlinger` 或 `--list`。图层与缓冲状态。
4. **Perfetto trace（gfx、view、input、hal、sched、freq、binder_driver 等类别）**：能同时看到 UI 线程调用栈、渲染线程、合成与内核调度，回答"这一帧的时间花在哪"。工具与类别用法见 [Perfetto 采集与 SQL 分析](../10-tools/01-Perfetto-采集与SQL分析.md)。
5. **帧时间线 / 帧指标采集**：FrameMetrics 回调可把逐帧数据收进自有采集，用于线上分布统计。

选型原则：先确定要回答"应用内还是应用外"，再选工具；不要用一类工具的数据去解释另一类工具的现象。

**Q7: ViewRootImpl 没有执行绘制时，是否能从框架诊断字段找到跳过原因？**

本地 ViewRootImpl 维护了跳过绘制的记录字段，用于在遍历中标注"因为屏幕关闭、没有根视图、前置绘制回调取消等原因没有执行绘制"（本地 AAOS13 源码核对，dumpsys 路径会输出该原因）。它的价值是把"没重绘"从推测变成可读字段：屏幕关闭、preDraw 取消与 cancelDraw 各自对应完全不同的处置方向（前者不该重试，后者是业务取消）。

需要注意的是这类诊断字段属于框架内部实现，跨版本可能变化，依赖它时要在目标版本上确认（本地源码树为研读副本，与上游可能存在差异）。

**Q8: 局部数据变化造成大范围重绘和掉帧，如何判断失效范围并缩小成本？**

按三步判断失效范围：

1. **确认重绘是否必要**：检查属性 setter 是否已经调用 invalidate，以及自定义 View 是否漏调或重复调用。
2. **确认脏区是否被放大**：父容器尺寸变化时，子 View 的一次 invalidate 可能导致整层重新录制。
3. **确认是否叠加动画**：属性动画每帧修改属性并触发失效，重录成本会随动画持续时间累积。

治理按收益排序：把高频变化的部分拆成独立小 View 以隔离脏区；用属性动画走合成层位移而不是触发重录；对"数据变了但视觉不变"的路径去掉 invalidate；最后才是降复杂度（扁平层级、减少绘制调用）。

**Q9: 刘海、圆角或系统栏压住按钮，怎样按 Insets 调整内容与点击区域？**

用 insets 做避让，不要写死边距。做法是按 WindowInsets.Type 声明关心哪几类（状态栏、导航栏、显示切口、强制手势区），在 insets 变化时更新对应容器的 padding；需要"内容延伸到栏下但可点击区避开"的场景，用 WindowInsetsController 控制栏的显隐而不是改布局。

常见错误有三类：

1. 写死 paddingTop，把状态栏尺寸硬编码，换机型或车机主题后就会错位。
2. 只处理状态栏而忽略手势区，导致全面屏手势区域的底部内容被压住。
3. Insets 变化后只改 padding；如果尺寸或位置发生变化，还需要触发布局。

**Q10: 用户点击后长期无响应并出现输入超时，主线程阻塞如何造成这两类现象？**

输入分发的超时计时覆盖的是事件从进入系统到被目标窗口消费的过程；应用主线程忙时事件排队，耗时会显著变长。因此主线程上的长任务既造成界面无响应，也会推高输入超时概率，两者在症状上都会表现为"点了没反应"。

区分方法：输入超时往往伴随日志里的分发超时记录与"应用无响应"提示，而单纯 UI 卡顿没有分发超时记录（输入系统机制见[输入系统](../03-input/01-输入系统.md)）。治理手段相同——缩短主线程长任务——但优先级判断不同：涉及输入超时的必须立即处理，因为它已经在影响交互正确性。

**Q11: 页面渲染卡顿并伴随内存上涨，怎样区分分配、纹理与缓冲区问题？**

三类表现与三类原因对应：卡顿且内存平稳，常见于大位图每帧重传或大面积渐变模糊（每帧产生大量绘制指令或纹理上传）；卡顿并伴随内存上涨，常见于在绘制路径分配对象或解码大图；内存缓慢上涨且不回落，要查硬件层纹理与未释放的缓冲。

排查手段是内存分类统计加绘制侧验证（[内存实践](../09-app-practice/10-内存实践.md)）。一条实用纪律是"大图不进内存路径"：能用下采样尺寸解决的，不要解码原图；能在资源变体里给不同屏幕不同尺寸的，不要运行时缩放。

**Q12: SurfaceView 区域变黑或偏移，如何分别确认图层、位置和 buffer？**

按三段排除：

1. **检查图层**：确认 SurfaceFlinger 中图层存在且尺寸正确。
2. **检查位置与遮挡**：确认 SurfaceView 的位置、透明区域和父窗口中的其他图层没有冲突。
3. **检查内容提交**：确认视频解码或渲染仍在运行，并确实送出了 buffer。黑区常见的成因是"父视图变换与独立 surface 不兼容"——对 SurfaceView 做旋转、圆角、缩放动画时，独立 surface 不参与视图变换，结果就是位置错位或露出空区。

**Q13: 车机同一页面在主屏和副驾屏大小不同，怎样检查显示配置与窗口几何？**

先确认是否拿到正确的显示上下文：Activity 的 Configuration 是按显示绑定的，若代码从默认显示或全局度量取值，就会与实际窗口不一致。再确认窗口几何来源是否正确：窗口尺寸应来自 relayout 返回值而不是 Configuration。最后确认显示切换时的状态处理：显示被移除或重新分配时，Activity 可能被重建或换绑 occupant zone，界面状态若只存在 View 上就会丢失或错位。

**Q14: 车机屏幕熄灭但应用进程仍运行，如何判断是否由电源策略控制？**

判断顺序是排除应用侧（是否还在渲染、是否有窗口）与排除系统显示开关（`dumpsys display` 与电源状态），最后落到电源策略：车机屏幕由策略关闭而非普通显示开关驱动，应用侧应当以电源状态与策略变化为准，而不是依赖屏幕开关广播。

实践含义有两点：测试"息屏恢复"必须控制车辆信号而不是点屏幕开关；应用若依赖持续可见性做逻辑（如持续导航播报），要显式处理电源状态而非假设"看不见=被切走"。

**Q15: 同类 UI 缺陷反复回归，怎样把视觉与状态问题变成可重复验证的检查？**

把"靠人眼看"变成"可判定"，可以落实为四项检查：

1. **埋点**：逐帧指标与应用级状态快照线上采集，掉帧率与白屏时长按版本跟踪（[线上诊断](../09-app-practice/16-可观测性-线上诊断.md)）。
2. **可视化对比**：关键界面在多分辨率、多密度、多字号、多语言、深浅色下的截图基线对比，差异纳入评审；车机上还要按不同 occupant zone 显示各采一份。
3. **状态驱动测试**：把夜间模式、字号缩放、语言切换、UX 限制变化、电源状态、显示热插拔做成可触发的用例，而不是靠人工记得去点。
4. **走查清单**：按窗口与内容分类列出必查项（首帧、透明与层级、insets 避让、多字号不破版、分心限制形态、返回栈、异常恢复），每项写清判定标准，避免"看起来没问题"式验收。
