# 仪器化测试

> Android 应用测试机制学习资料。边界：本文回答“仪器化测试与本地单元测试的边界、androidTest 源集与 AndroidJUnitRunner 协作链路、Espresso 的主线程同步机制与 IdlingResource、权限与多用户测试”。测试的概念分层与策略归 [../../06-testing/01-测试基础.md](../../06-testing/01-测试基础.md)，协程与 Flow 的测试归 [../02-应用框架/13-异步与Flow测试.md](../02-应用框架/13-异步与Flow测试.md)。依据以 Android Developers 官方测试文档为准，命令与配置项按文档口径标注。Q 序列即结构，供 atlas 同源直读。

**Q1: [learning] 什么时候必须用仪器化测试？它和本地单元测试的边界由什么决定？**

边界由被测行为的依赖决定：结论不依赖真实 Android 运行时的逻辑留在 JVM 本地单元测试，依赖 Context、生命周期、Binder、真实 View 树或图形栈的行为必须上设备执行仪器化测试。把依赖运行时的测试硬塞进 JVM，要么靠 Robolectric 模拟（结论仍需真机复核），要么测不出真实缺陷。

按依赖选择测试位置：

1. **本地单元测试：**位于 `src/test/`，覆盖纯逻辑、状态转换、算法分支。外部协作者用 Fake 或 Mock 替换，运行在 JVM，速度快、定位准。
2. **仪器化测试：**位于 `src/androidTest/`，行为依赖真实运行时——组件生命周期推进、Intent 与 Bundle 的实际 Parcel 往返、SQLite 在设备上的行为、View 测量布局绘制、跨进程调用。它们运行在设备或模拟器上，由 instrumentation 机制驱动。
3. **边界判断**：Robolectric 等环境能模拟部分框架行为，适合加速反馈，但“模拟通过”不证明真机一致；涉及真实图形、跨进程或厂商定制的结论必须以仪器化测试为准。仪器化测试慢而真，因此通常只覆盖集成路径与关键 UI 流程，大量分支仍在本地层消化。

依据：Android Developers《Test your app on Android》对两类测试的定位与源集划分。

**Q2: [learning] androidTest 源集与 AndroidJUnitRunner 如何协作把测试跑上设备？**

仪器化测试写在 `src/androidTest/java/`，随测试变体编译成独立的测试 APK，经 `am instrument` 命令注入设备，由 runner 驱动 JUnit 4 测试生命周期。链路上每一步各有职责：

1. **构建**：`androidTestImplementation` 声明测试期依赖（AndroidX Test、Espresso 等），只进入测试 APK 不污染生产包。测试 APK 与被测 APK 是两个包，前者声明 `android:testOnly` 语义并以后者为 instrumentation target。
2. **Runner 配置**：`defaultConfig` 中 `testInstrumentationRunner "androidx.test.runner.AndroidJUnitRunner"` 指定 runner 类。AndroidJUnitRunner 负责加载测试 APK、创建 Instrumentation 环境并把 JUnit 4 的 `@Test` 类逐个执行；省略该配置时 Gradle 无法发起 connected 测试。
3. **执行**：`./gradlew connectedDebugAndroidTest` 构建两个 APK、安装到已连接设备并执行；底层等价于 `adb shell am instrument -w <测试包名>/<runner类名>`。可用 `-e class`、`-e package`、`-e annotation` 等参数过滤，只跑一个类或一组注解标记的用例。
4. **环境边界**：测试 APK 安装在目标设备上，受目标设备的用户、权限与系统版本约束——车载多用户设备上 `am instrument` 支持 `--user` 指定运行用户，跨用户组件的行为要在对应用户下测。

依据：Android Developers《Advanced test setup》《Build instrumented tests》与 AndroidJUnitRunner 文档的过滤参数说明。

**Q3: [learning] Espresso 为什么能在异步工作后自动校验 UI？IdlingResource 补上什么缺口？**

Espresso 的同步建立在“主线程与消息队列已空闲”的判断上：执行 onView 断言前，它先等主线程当前消息队列排空，再执行查找与校验，因此正常的点击→更新→断言序列不需要测试者手工 sleep。

机制与缺口：

1. **自动同步的覆盖面**：主线程消息（Handler 回调、invalidate 触发的遍历）与 Espresso 已知的异步资源完成时，队列进入 idle，断言才执行。这覆盖了框架自身的异步（布局、绘制）。
2. **覆盖不到的部分**：测试者自己启动的后台线程、协程、网络请求或自定义执行器不在主线程消息队列上，Espresso 无从得知它们何时结束，断言会提前执行——这是“测试偶尔过偶尔挂”的典型来源。
3. **IdlingResource 的补位**：把自定义异步工作注册为 IdlingResource，报告 busy/idle 状态；Espresso 在所有已注册资源 idle 前不执行断言。注册必须在测试结束前注销，泄漏的资源会让测试永久等待。
4. **Compose 的对应机制**：Compose 测试用 `createComposeRule`（或 `createAndroidComposeRule`）驱动，同步模型等价——awaitility 类的手工等待同样应让位于 Compose 的同步设施与 IdlingResource。

因此，遇到仪器化测试的偶发失败先查“异步工作是否绕过了同步机制”，而不是加延时——延时只把失败概率挪到更慢的设备上。

依据：Android Developers《Espresso》与《Testing in Compose》对同步与 IdlingResource 的说明。

**Q4: [learning] 仪器化测试里怎么处理运行时权限与多用户？**

权限与用户是仪器化测试和真实用户路径差异最大的两处：测试必须显式拿到与生产一致的授权状态，且要在目标用户下执行，否则结论对生产环境无效。

1. **权限授予**：用 AndroidX Test 的 `GrantPermissionRule.grant(权限名)` 在测试开始前授权，等价于自动化点掉授权对话框；不授权时，依赖危险权限的用例会在运行时拒绝路径上失败，那是另一类有效用例，不要混在同一个测试里。
2. **UI Automator 的跨应用场景**：被测流程要跨出应用（系统对话框、设置页）时，Espresso 的进程内同步不再适用，用 UI Automator 按系统界面元素操作，并接受更弱的同步保证。
3. **多用户设备**：instrumentation 默认在当前用户执行；车载多用户场景用 `adb shell am instrument --user <userId>` 在目标用户下跑，涉及 profile 可见性、跨用户 Intent 的用例必须在对应用户的会话中验证，user 0 的通过不证明工作资料下的行为。
4. **结果回收**：connected 任务的测试结果与设备上的 logcat、screenshot（失败时按 runner 配置保存）一起构成失败取证材料；只看 Gradle 的 PASS/FAIL 会丢掉设备侧的失败现场。

依据：Android Developers《UI Automator》《GrantPermissionRule》文档与 am instrument 命令行参数说明。
