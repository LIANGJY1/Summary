# Android 平台差异与系统诊断

跨版本、跨设备归因先固定系统交付变量，再按 Framework、Native 服务、HAL 与内核证据定位；采集工具操作见[工具索引](../../04-工具/README.md)，应用侧 ANR 采集边界见 [APM 架构](../../04-工具/README.md)。

**Q1: [learning] 同一个 APK 在两台设备上启动、掉帧或后台行为不同，怎样把差异归因到具体层而不是笼统的“ROM 优化”？**

OEM 性能分析要回答三个可验证的问题：当前设备相对 AOSP 基线改了什么、改动通过哪一层影响了目标进程、改善了哪个指标又把成本转移到哪里。启动、流畅性、内存、功耗、温控五类目标共享 CPU、GPU、内存带宽、存储带宽、电池功率与散热能力，局部收益经常伴随另一项成本，比如预热换启动快、峰值提频牺牲稳态帧率。

改动位置按层排查：内核层包括调度、schedutil、cgroup、PSI 与设备驱动，OEM 经内核补丁、Kconfig、设备树或 sysfs 运行参数改变行为，看到非标准节点要先确认它属于 GKI、vendor module 还是产品私有实现。native 层包括 SurfaceFlinger、HWC、AudioFlinger 等，显示路径差异常来自 HWC 能力与合成策略，Binder 延迟要分解为客户端等待、事务排队与服务端执行。framework 层包括 AMS/WMS、CachedAppOptimizer、JobScheduler 与产品 overlay、DeviceConfig、task profile。应用层则是 SDK 行为与厂商公开 SDK。

归因流程：固定实验条件（机型、内存档位、build fingerprint、温度、刷新率）→ 建立 AOSP 基线并记录默认值与可覆盖项 → 读取目标设备配置（Settings、DeviceConfig、overlay、task profiles，user build 读不到的记为未知）→ 用 trace 确认执行动作（启动链、掉帧链、后台链、功耗链）→ 逐项做单变量消融 → 给结论标注证据等级：L1 源码与运行证据一致、L2 官方文档或产品配置加运行证据、L3 仅有现象。品牌和地区不能替代设备证据，“某厂商一定杀后台”会把排障变成长期维护的例外集合。

**Q2: [learning] 一轮 AOSP 平台性能优化开始前，怎样判断问题属于平台而不是单个应用？结论需要哪三类证据共同约束？**

只有证据指向公共路径、或应用无法在公开接口与文档约定内避开问题时，才应优先修改平台：同机多个应用出现相同的合成、调度或驱动等待，比单应用的 View 遍历、图片解码更接近平台问题。判断不能只靠一次 trace，应找同版本同设备的对照应用，再比较不同版本、设备与兼容性开关（compat change），现象只有随平台变量稳定移动，才有依据继续检查 framework、ART、native 服务或内核。

结论由三类证据共同约束，且不能互相替代：

1. **公开约定**：release notes、behavior changes 与 SDK 文档决定兼容与迁移边界，但不说明目标设备实际启用了什么。
2. **固定 tag 源码**：回答实现、开关条件与默认值，源码中存在某函数或配置默认为 y，不能单独证明设备已启用。
3. **设备运行证据**：build fingerprint、ART/APEX 版本、内核版本加 trace 与实验，说明本次负载实际走到哪条路径。

证据到位后按以下顺序推进：

1. **确认分布：**用多轮样本比较 P50/P90 等分位数与离散程度，避免只凭单次 trace 定结论。
2. **解释慢样本：**用 Perfetto、simpleperf 或 dumpsys 追到实际执行路径。
3. **控制变量：**一次只改一个主要变量；无法隔离时降低结论强度。
4. **评估副作用与回退：**检查稳定性、资源、正确性、兼容性和安全；可配置优化要定义默认值、分批发布设备组，以及回滚后的清理动作。

版本归因时还要把系统版本、`targetSdkVersion`、Mainline/APEX（包括 ART）、内核版本与 vendor HAL 交付路径分开记录。target SDK 影响部分兼容变更，但新系统上的全局资源策略并不一定由 target 控制；同一大版本也可能因独立 ART/APEX 更新或不同 GKI 分支而走不同实现。固定 APK 与场景，记录 build fingerprint、模块/内核版本及产品配置；具体版本轴与示例见[应用侧版本记录题](../../01-应用/01-启动/01-启动与交付.md)。

**Q3: [learning] 跨应用、框架和设备服务的故障应怎样划分归因边界？**

表面症状不能确定责任层。崩溃、无响应、界面未更新或媒体无声，可能分别发生在应用状态管理、框架回调、服务协议、驱动或硬件资源路径。

按边界逐层取证：

1. **应用层：**确认请求、参数、状态迁移和结果处理是否符合契约。
2. **框架与服务层：**确认调用是否到达、回调是否按契约返回，以及服务是否报告失败或重启。
3. **设备与驱动层：**只有前两层证据指向资源、调度、HAL 或驱动时，再收集对应系统日志与状态。
4. **修复归属：**应用层补偿只能标注为规避或恢复措施；不能把它写成设备根因修复。

跨层结论应分别说明观察到的事实、推断与未验证路径。将应用仓库中的配套修改当成系统根因修复，会掩盖仍需设备侧验证的问题。

**Q4: [learning] Android 框架内部的 SQLite 诊断信息（OperationLog、语句缓存统计、慢查询开关）能搬进普通 App 吗？AAOS13 与 Android 17 有什么差异？**

不能——这些诊断都是框架私有或 `@hide`，普通 App 没有对应采集接口。AAOS13 源码核对：`SQLiteConnection.OperationLog` 保留 `MAX_RECENT_OPERATIONS = 20` 条最近操作，只服务于 framework 调试与 dump。材料核对的“严格超过 2 秒的操作记入长操作”（`LONG_OPERATION_THRESHOLD_MS = 2_000`）是 Android 17 的实现，AAOS13 树中不存在该常量，2 秒也不应复制成业务慢查询门槛。`SQLiteConnectionPool#getStatementCacheMissRate()` 在 Android 17 带 `@hide`（AAOS13 树中未见该方法）。

公开侧的边界：每连接 prepared statement cache 默认 25、`setMaxSqlCacheSize()` 公开上限 100（AAOS13 已核对 `SQLiteDatabaseConfiguration` 默认 25 与 `MAX_SQL_CACHE_SIZE = 100`），没有内存与命中率证据时不应把缓存调到上限。`setIdleConnectionTimeout()` 已废弃，文档警告重建连接会清除 per-connection PRAGMA 且系统没有恢复回调。`setLookasideConfig(0, 0)` 只是请求禁用 lookaside，系统可能按设备选择不同值。开发设备可用 `adb shell dumpsys meminfo <package>` 查看缓存命中统计，普通应用没有免权限的生产 API。`SQLiteDebug.shouldLogSlowQuery()` 读取带 UID 后缀的系统属性、受日志标签控制，是隐藏调试开关，不能当动态下发阈值方案。结论：线上用自己 driver 层或回调采集，framework 细节只用于理解平台行为。
