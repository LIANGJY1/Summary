# 图片格式与体积

**Q1: [learning] 图片像素尺寸和图片文件大小是什么关系？**

像素尺寸和编码后的文件字节数没有固定换算比例。两者的关系要分开判断：

1. **像素数：**宽、高各翻倍，像素数变为四倍。
2. **文件字节：**还受画面细节、格式、质量参数和元数据影响，不会随像素数按固定倍数变化。
3. **Android 交付：**缩小 ImageView 只改变绘制尺寸，不会减少源文件字节。网络图比较实际响应字节，应用资源比较构建产物。

依据为 Android Developers《Drawable resources》。

**Q2: [learning] 图片源尺寸过大时，先缩像素还是先降编码质量？**

先确定交付像素，再调编码质量，不能用降质量代替尺寸选择：

1. **定尺寸：**按实际显示大小与必要裁切设置输出像素，减少需要编码的样本数。
2. **调质量：**在该尺寸下比较质量参数，控制细节损失与文件字节。
3. **验收：**按目标显示尺寸检查清晰度。依据为 Android Developers《Reducing image download sizes》。

**Q3: [learning] JPEG、PNG、GIF 和 SVG 怎样按内容选型？**

按画面内容、透明度和动画需求选择：

1. **JPEG（Joint Photographic Experts Group）：**有损压缩适合能接受细节损失的照片，不保存透明背景。
2. **PNG（Portable Network Graphics）：**无损压缩适合文字、细线和需要精确透明边缘的图形。
3. **GIF（Graphics Interchange Format）：**调色板适合少色短动画，照片式动画易失真。
4. **SVG（Scalable Vector Graphics）：**矢量描述适合简单、需跨尺寸显示的图形，Android 使用时须核对导入与绘制支持。

**Q4: [learning] 相同分辨率的 PNG 为什么文件体积不同？**

PNG 保存像素的无损结果，相同宽高不保证相同字节数。差异来自：

1. **内容：**平色比复杂纹理更易压缩。
2. **表示：**颜色类型、位深和元数据改变待编码字节。
3. **编码：**扫描行先过滤，再由 DEFLATE（无损数据压缩算法）压缩。过滤与压缩设置不同，即使像素相同也可能得到不同体积，最终像素仍不变。

依据为 W3C《PNG Specification》。

**Q5: [learning] PNG 的 Adam7 交错编码能直接缩小文件吗？**

不能。Adam7 是 PNG 的交错编码方式，不会减少像素或文件体积：

1. **传输顺序：**把像素分成七轮，让支持渐进显示的读取端先得到粗略画面。
2. **最终图像：**所有轮次合并后像素不变。
3. **文件大小：**交错通常还会增加少量编码字节。Android 控件是否逐轮显示取决于加载方式。

依据为 W3C《PNG Specification》。

**Q6: [learning] PNG 的颜色类型与位深怎样影响体积和画质？**

颜色类型决定保存灰度、真彩色、索引色及透明信息，位深决定每个颜色样本的精度。按源图选择：

1. **少量离散颜色：**可试索引色或较低位深，比较体积并检查量化后的色带和边缘。
2. **渐变与透明过渡：**保留足够颜色与透明精度，不能为省字节直接压低位深。
3. **已有 8 位源图：**转成 16 位 PNG 不会增加原有细节，只会增加表示空间。

依据为 W3C《PNG Specification》。

**Q7: [learning] PNG 的透明信息怎样影响文件与 Bitmap？**

PNG 的文件透明表示与解码后的 Bitmap 配置是两件事：

1. **完整 alpha：**逐像素记录透明度，适合半透明边缘。全图不透明时可去掉无用 alpha，但须检查边缘，文件收益以实测为准。
2. **tRNS 透明度块：**为灰度或真彩色指定透明值，或为索引色调色板指定透明度。非 RGBA（Red、Green、Blue、Alpha）文件也可能有透明信息。
3. **Bitmap 内存：**即使文件不透明，若仍解为 ARGB_8888（Alpha、Red、Green、Blue 各 8 位），每像素基数仍为 4 字节。文件是否含 alpha 不能单独决定解码内存。

依据为 W3C《PNG Specification》和 Android《BitmapFactory.Options》。

**Q8: [learning] PNG 色彩辅助块为什么不能随意删除？**

这些 PNG 数据块提供颜色解释信息：

1. **iCCP：**嵌入 ICC（International Color Consortium）色彩配置文件。
2. **gAMA：**记录伽马信息。
3. **sRGB：**表明使用标准 RGB 色彩空间。

删除它们可能减少文件字节，也可能改变 Android 设备上的显示颜色。先确认数据块用途，再对照文件字节与目标设备画面。依据为 W3C《PNG Specification》。

**Q9: [learning] JPEG 质量参数降低，文件一定按比例变小吗？**

不一定。质量参数只控制编码器在细节和码量间的取舍，实际结果还取决于：

1. **画面内容：**纹理越复杂，通常越难压缩。
2. **编码实现与色度采样：**不同编码器对同一质量值的处理可能不同，也会改变细节表现。
3. **验收条件：**以代表性图片比较实际文件字节和目标尺寸下的画质，不能直接比较不同编码器的质量数字。

依据为 Google《Image formats: JPEG》。

**Q10: [learning] JPEG 为什么适合照片却可能损伤文字截图？**

JPEG 对照片与文字图的影响不同：

1. **照片：**有损编码通常能以较少字节保留可接受的观感，可比较 4:2:0 色度采样。
2. **文字和细线：**有损编码可能造成模糊或振铃。4:2:0 减少颜色采样，彩色细边更容易渗色。4:4:4 保留完整颜色采样，可与无损格式对照并按目标显示尺寸检查可读性。

依据为 Google《Image formats: JPEG》。

**Q11: [learning] 渐进式 JPEG 一定比基线 JPEG 更小吗？**

不一定。渐进式 JPEG 把画面编码为逐步细化的多次扫描，大图有机会缩小文件，但结果还受图片内容和编码器影响。用相同源图与视觉质量比较两种输出的字节数。依据为 Google《Image formats: JPEG》。

**Q12: [learning] JPEG 能直接保存透明背景吗？**

常规 JPEG 不保存 alpha。透明图转 JPEG 时必须先选背景颜色进行合成，否则透明区域会被替换，边缘还可能出现底色。需要保持半透明轮廓时，选支持 alpha 的 PNG 或合适的 WebP，并在深浅背景上检查边缘。

**Q13: [learning] 为什么不应反复从 JPEG 成品重新压缩？**

每次有损重编码都以已丢失细节的像素为输入，可能累积块状或边缘失真。应从原始素材生成不同尺寸与质量的版本，再分别验收。只调高第二次的质量参数也无法恢复第一次丢失的信息。依据为 Android Developers《Reducing image download sizes》。

**Q14: [learning] 清理 JPEG 元数据时，为什么要保留或处理方向信息？**

Exif（Exchangeable Image File Format）方向标签记录查看器应如何旋转原始像素。清理时按处理方式选择：

1. **删除标签：**先把像素按标签旋正并重编码，否则图片可能横置或倒置。
2. **保留标签：**确认交付链路会保留并正确读取方向信息。

依据为 AndroidX《ExifInterface》。

**Q15: [learning] GIF 适合哪类图片或动画？**

GIF 用调色板表示帧，适用性取决于内容：

1. **少色短动画：**可使用 GIF，并检查帧数和显示效果。
2. **颜色丰富或长动画：**量化易造成失真，可比较动态 WebP 的体积与播放成本。
3. **静态图片：**GIF 没有动画收益，应按内容比较索引色 PNG、JPEG 或 WebP，并检查透明边缘与设备兼容。

依据为 Android《Supported media formats》和 Android Developers《Create WebP images》。

**Q16: [learning] 动态 GIF 的帧数与变化区域怎样影响文件体积？**

GIF 体积主要随帧数和每帧更新的数据增加：

1. **帧数：**冗余帧会增加需保存的数据，可在不改变播放时长的前提下减少。
2. **变化区域：**帧可只覆盖逻辑画布的一部分，缩小更新区域可能减小数据量。
3. **画面语义：**优化后仍须保持帧时长、清除方式和最终画面。

依据为《GIF89a Specification》。

**Q17: [learning] SVG 为什么能缩放而不依赖一组固定像素尺寸？**

SVG 是用 XML（Extensible Markup Language）描述路径、形状和样式的矢量格式，显示时再按目标尺寸栅格化：

1. **缩放：**简单图形可用同一份矢量描述适配多种密度。
2. **绘制成本：**复杂路径和效果仍可能增加绘制工作。
3. **Android 解码：**SVG 不能由 ImageDecoder 直接当作普通位图解码。

**Q18: [learning] SVG 转为 VectorDrawable 后怎样判断是否值得用？**

VectorDrawable 是 Android 的矢量资源表示，不能完整承接所有 SVG 特性。导入后逐项核对：

1. **画面：**文字、滤镜、复杂遮罩与路径可能转换失败或失真。
2. **资源体积：**复杂插画的路径数据可能比位图大，旧系统兼容方案还可能生成多密度位图。
3. **绘制成本：**复杂路径、渐变与遮罩会增加绘制工作。应与位图在目标设备上比较。

依据为 Android Developers《Add multi-density vector graphics》和《Reduce your app size》。

**Q19: [learning] 为什么不能把 .9.png 直接批量改成 WebP？**

.9.png 包含 Android NinePatch 所需的拉伸区和内容内边距信息，不是普通 PNG 位图：

1. **直接改格式：**会丢失 NinePatch 的布局语义，Android Studio 的 WebP 转换器也会跳过它。
2. **转换前处理：**保留 NinePatch，或先换成能表达同等布局行为的资源。

依据为 Android Developers《Drawable resources》和《Create WebP images》。

**Q20: [learning] WebP 的有损和无损模式怎样选择？**

WebP 支持有损、无损、透明与动画，按素材比较：

1. **照片：**以相同视觉质量比较有损 WebP 与 JPEG 的字节数。
2. **透明图形：**以相同像素和元数据取舍比较无损 WebP 与 PNG，转换不保证更小。
3. **质量参数：**质量 100 不等于无损。cwebp 默认有损模式仍须显式切换为无损模式，Android Studio 转换器的行为另按其选项判断。

依据为 Google《WebP Compression Techniques》《cwebp》和 Android Developers《Create WebP images》。

**Q21: [learning] WebP 全透明区域的 RGB 值为何会影响体积？**

透明像素不可见，但隐藏的 RGB 值仍可能参与编码：

1. **默认处理：**cwebp 可改写全透明像素的 RGB 值以改善压缩。
2. **保留原值：**启用 exact。若后续流程会读取这些值，须保留并比较文件体积。

依据为 Google《cwebp》。

**Q22: [learning] WebP、HEIF 和 AVIF 在 Android 上怎样处理兼容？**

按实际编码特性、系统版本和设备能力选择主格式与回退：

1. **WebP：**有损解码自 Android 4.0 起支持，透明与无损解码自 Android 4.2.1 起支持。Android Studio 转换透明或无损 WebP 要求最低系统版本 minSdk 至少为 18（Android 4.3），工具门槛不能代替运行时判断。
2. **HEIF（High Efficiency Image File Format）：**是容器，Android 9 起的解码为设备可选。8 位应核对实际设备，10 位还依赖可选的 HEVC（High Efficiency Video Coding）Main10。
3. **AVIF（AV1 Image File Format）：**Android 12 起支持基线 8 位解码，10 位解码可选。Android 14 起的平台编码能力不等于 Bitmap.compress 支持 AVIF。
4. **交付验收：**在目标设备解码实际文件，为不支持的设备提供可解码回退。依据为 Android《Supported media formats》和《Create WebP images》。

**Q23: [learning] 图片扩展名为何不足以确认实际格式？**

扩展名只是文件名，不能证明内部编码。把 PNG 改名为 .jpg 后，文件头与编码仍是 PNG。应核对文件签名和容器特征，而非仅凭后缀判断格式。依据为 W3C《PNG Specification》与 Google《WebP Container Specification》。

**Q24: [learning] 比较图片格式时为什么要固定视觉质量并检查局部？**

只比较字节会奖励更严重的失真，不同编码器的相同质量数字也不代表同等画质。对照应固定：

1. **输入与显示：**同一源图、像素尺寸、裁切和实际显示尺寸。
2. **画质：**全图指标之外检查文字、肤色、透明边缘等易被平均值掩盖的区域。
3. **成本：**在相同设备和缓存状态下比较文件字节、解码耗时与首次可见时间。

局部画质不达标时，文件再小也不能作为替代版本。依据为 Android Developers《Reducing image download sizes》。

**Q25: [learning] Android 的 dp 怎样换算为图片需要的像素尺寸？**

dp（density-independent pixels，与密度无关的像素）是布局尺寸，图片目标像素约等于 dp × 设备密度倍率。例如 48 dp 在 3 倍密度上约占 144 × 144 屏幕像素。图片还须留出实际裁切或放大的余量，远超目标像素通常只增加交付和解码成本。依据为 Android Developers《Support different pixel densities》。

**Q26: [learning] drawable 密度变体怎样影响解码尺寸和画质？**

Android 按设备密度选择 drawable 变体，并可能把所选位图缩放到目标密度。缺少匹配变体时：

1. **选低密度图：**放大后的 Bitmap 像素可能增加，但细节不会增加，显示可能模糊。
2. **选高密度图：**缩小后仍可能交付较多文件字节。

3. **核对输出：**检查资源目录、源宽高、设备密度和返回 Bitmap，不能只从源文件推算输出。依据为 Android Developers《Support different pixel densities》和 Android《BitmapFactory.Options》。

**Q27: [learning] drawable-nodpi 适合哪些位图？**

drawable-nodpi 表示资源不参加密度自动缩放：

1. **适用：**由应用明确控制采样和显示尺寸的位图。
2. **限制：**它不会缩小高分辨率原图，也不替代目标尺寸计算。
3. **比较内存：**先确认普通 drawable 是否发生了密度缩放。依据为 Android Developers《Support different pixel densities》。

**Q28: [learning] 图片自带大块透明留白为何会增加成本？**

透明留白仍占像素宽高，可能放大文件、解码结果和纹理。

处理取决于留白用途：

1. **只是布局间距：**裁到内容边界，再由布局提供间距。
2. **承载对齐规则：**保留必要的视觉语义，避免裁切后位置变化。

依据为 Android Developers《Optimizing bitmap images》。

**Q29: [learning] 图片瘦身后怎样核对下载、包体与内存收益？**

三种口径应分别验收：

1. **交付字节：**网络图看实际响应。应用资源在 Android App Bundle（AAB）按设备分发时通常只下载所需密度变体。通用安装包可能包含多套。
2. **包体贡献：**构建会处理资源，APK 还有 ZIP 封装。用同一设备交付物及 APK Analyzer 的 Raw File Size、Download Size 比较，不能直接相减源文件字节。
3. **运行时内存：**核对返回 Bitmap 的宽高、配置与 allocationByteCount。编码文件变小但输出像素不变，不能据此宣称内存下降。

依据为 Android Developers《The Android App Bundle format》《Analyze your build with the APK Analyzer》和 Android《Bitmap API reference》。
