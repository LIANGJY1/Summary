# 图片格式与体积

**Q1: [done] 位图是什么？**

位图用二维像素网格表示图像，每个像素记录颜色及可选的透明度，适合照片和纹理丰富的图像，因为能逐像素保存细节；放大时可能出现明显像素化。位图是一种表示方式，不等同于某种压缩算法。





**Q2: [done] 矢量图形是什么？**

矢量图形用点、线、曲线和路径等几何对象及其填充、描边属性描述画面，适合图标、标志和简单线稿，因为可按目标尺寸绘制并保持边缘清晰。照片若用大量几何对象描述，通常不如位图合适。

依据为 W3C《SVG 1.1》和 Android Developers《Vector drawables overview》。

**Q3: [done] 栅格化是什么？**

栅格化（rasterization）是把路径、曲线等矢量图形描述映射为目标尺寸上的像素，用于显示或输出的过程。渲染器据图形覆盖范围确定像素颜色和透明度，抗锯齿可平滑边缘。SVG 或 VectorDrawable 可按新的目标尺寸重新栅格化；位图放大只能插值，不能恢复矢量细节。

依据为 W3C《SVG 1.1》与 Android Developers《Vector drawables overview》。



**Q4: [done] JPEG、PNG、GIF 和 SVG 有什么区别？**

JPEG、PNG、GIF 按像素表示画面；SVG 用路径和形状描述画面，显示时再转换为像素。它们的压缩方式和适用内容不同：

1. **JPEG（Joint Photographic Experts Group，联合图像专家组）：**有损位图格式，通过变换和量化舍弃细节以减小体积，不支持透明，适合照片。
2. **PNG（Portable Network Graphics，便携式网络图形）：**无损位图格式，支持透明，适合图标、文字和锐利边缘。它使用 DEFLATE 无损压缩算法；解码可还原编码前的像素。
3. **GIF（Graphics Interchange Format，图形交换格式）：**基于调色板的位图格式，每帧最多 256 色，使用 LZW（Lempel–Ziv–Welch）无损压缩并支持动画，适合少色动画，不适合照片。
4. **SVG（Scalable Vector Graphics，可缩放矢量图形）：**用 XML（Extensible Markup Language，可扩展标记语言）描述路径和形状，可按目标尺寸栅格化。复杂图形会增加绘制成本。





**Q5: [done] Android 应用图片资源有哪些类型，分别适合什么场景？**

按表示方式和用途，Android 图片资源分为位图、XML 绘图资源和动画资源：

1. **位图：**JPG、PNG、WebP 和 GIF 可放在 drawable 资源目录。照片常用 JPG 或 WebP；透明图标、文字和锐利边缘常用 PNG；GIF 主要用于兼容简单动画。
    1. **九宫格位图：**`.9.png` 用 1 像素边框标记可拉伸区和内容区，编译后作为 NinePatchDrawable，适合按钮、气泡等可变尺寸背景。
2. **XML 绘图资源：**VectorDrawable 用路径描述图形，适合简单图标；ShapeDrawable 用属性描述纯色、圆角、描边和渐变，可替代简单背景图。SVG 导入 VectorDrawable 时需检查复杂路径的绘制成本。
3. **动画资源：**AnimationDrawable 按帧播放；AnimatedVectorDrawable 适合简单图标动效，可避免准备多张位图。
4. **运行时输入：**BMP（Bitmap）、HEIF（High Efficiency Image File Format）和 AVIF（AV1 Image File Format）可作为解码输入，但不等同于通用 drawable 资源。HEIF 从 Android 9 起支持且依设备而异；AVIF 的 8 位解码从 Android 12 起支持。加载前需确认设备能力。

依据为 Android Developers《Drawable resources》《Create resizable bitmaps (9-patch files)》《Create WebP images》《Vector drawables overview》《Supported media formats》和 Camera2 API 文档。





**Q6: [done] 图片像素尺寸与文件大小有什么关系？**

像素尺寸用宽 × 高表示，口语中常称像素分辨率；它决定像素数量，但不能直接换算压缩文件大小。同尺寸图片的文件大小还取决于内容和编码方式：

1. **像素数量：**宽、高各翻倍，像素数变为四倍，未压缩像素数据量也随之增加。
2. **图像内容：**重复颜色多的图片更容易压缩；因此同尺寸纯色 PNG 通常比细节丰富的照片小。
3. **编码数据：**PNG 的透明通道和色彩元数据会增加字节；过滤与 DEFLATE 压缩结果也会影响文件大小，但不改变解码像素。

依据为 W3C《Portable Network Graphics (PNG) Specification, Third Edition》。




**Q7: [done] 降低 JPEG 质量会怎样影响文件大小、画质和内存？**

降低 JPEG 质量通常会减小文件并损失细节，但不会改变解码输出尺寸。相同宽高和像素配置下，Bitmap 像素内存基本相同：

1. **文件大小：**质量越低，编码舍弃的信息通常越多，输出文件通常越小；实际大小还取决于图像内容和编码器。
2. **画质：**JPEG 以 8 × 8 像素块处理图像并量化细节。压缩过强会模糊纹理、破坏边缘或产生块状伪影。
3. **Bitmap 内存：**由解码后的宽高、像素配置和分配容量决定，不能用 JPEG 文件字节数推算。

依据为美国国会图书馆《JPEG DCT Compression Encoding, Baseline》和 Android《Bitmap API reference》。





**Q8: [learning] 图片交付时为什么先确定尺寸，再选择格式和质量？**

先确定显示所需的像素尺寸，再选择格式和质量。尺寸会同时影响传输字节、解码内存和显示质量；降低编码质量通常只减少文件字节。

1. **按用途定尺寸：**100 dp 控件在 3 倍密度设备上约需 300 px。列表缩略图和可放大的详情图应使用不同尺寸。
2. **匹配裁切：**4000 × 3000 的照片填满 300 × 300 区域，需要保留至少 400 × 300 再裁切。服务端若已按相同主体裁好，可直接交付 300 × 300。
3. **设置尺寸档位：**按设备和控件分布选择少量档位。逐像素生成变体会分散缓存；所有场景都传最大图则浪费带宽。
4. **分清两端职责：**服务端缩图减少响应字节；客户端采样控制解码输出。客户端指定尺寸不会自动缩小远端文件。
5. **最后比较质量：**在相同显示尺寸下比较编码字节和可接受画质。不同编码器的相同质量参数不代表相同画质。

依据为 Android Developers《Reducing image download sizes》和《Loading Large Bitmaps Efficiently》。尺寸档位为根据两端成本归纳的工程策略。





**Q9: [learning] PNG 怎样减小体积并保留画质？**

先优化无损编码，再评估会改变颜色表示或画面范围的操作。PNG 文件变小不代表解码内存也变小：

1. **无损重编码：**调整过滤和 DEFLATE 压缩策略，可在像素不变时减少字节；收益取决于内容和编码器。
2. **减少颜色：**原图颜色较少时可改用索引色。照片或渐变量化成少色会损失颜色，即使输出仍是 PNG，也不是无损处理。
3. **裁掉透明留白：**可减少像素和解码内存，但要同步调整布局间距、点击区域和对齐位置。不透明图可移除无用 alpha 通道。
4. **保留色彩信息：**iCCP、gAMA 和 sRGB 信息会影响颜色解释，不能一概删除。透明边缘应在深、浅背景上检查。
5. **验收实际产物：**Android 构建可能重写 PNG；Adam7 交错主要影响逐步显示，不是稳定的瘦身方法。应比较构建包和实际响应数据。

依据为 W3C《Portable Network Graphics (PNG) Specification, Third Edition》和 Android Developers《Drawable resources》。





**Q10: [learning] JPEG 怎样压缩照片并控制画质损失？**

JPEG 适合照片，不适合透明图或需要精确保留文字边缘的图像。质量、色度采样和 Exif 元数据分别影响细节、彩色边缘和方向：

1. **质量：**从原始素材生成各版本，避免反复有损重编码。不同编码器的质量数值不能直接比较。
2. **色度采样：**4:2:0 通常适合照片，但红蓝细字可能渗色。文字截图应比较 PNG、无损 WebP 或 4:4:4 JPEG。
3. **透明度：**JPEG 不支持 alpha。转码前应合成指定背景；背景会变化时保留透明格式。
4. **方向：**Exif（Exchangeable Image File Format）方向标签描述旋转或镜像。移除标签前须把方向变换写入像素。
5. **渐进显示：**渐进式 JPEG 分多次扫描细化图像，但只有下载、解码和界面更新链路都支持时才会渐进展示。

依据为 JPEG 标准、AndroidX《ExifInterface》和 Android Developers《Reducing image download sizes》。





**Q11: [learning] WebP、HEIF 和 AVIF 怎样选择与回退？**

先确认目标设备能解码，再比较相近画质下的文件大小、解码耗时和显示时机：

1. **WebP：**Android 4.0 起支持有损解码；透明和无损 WebP 的资源支持要求 API 级别 18 及以上。静态支持不代表动画支持。
2. **HEIF：**Android 9 起的平台解码支持依设备而异。需检查具体编码配置和设备解码能力，不能假定所有 HEIC 都可读。
3. **AVIF：**Android 12 起支持基线 8 位解码；10 位解码需另行确认。平台解码支持不代表 Bitmap.compress 支持该格式编码。
4. **回退：**设备能力检查和实际解码都可能失败，应准备经过验证的兼容格式，并区分格式、尺寸和内容版本的缓存身份。
5. **验证收益：**用相同素材、相近画质和相同输出尺寸，在目标设备比较响应字节、解码耗时、首次显示和失败率。格式更先进不保证端到端更快。

依据为 Android《Supported media formats》《ImageDecoder.isMimeTypeSupported》和 Android Developers《Create WebP images》。旧系统库回退会增加包体和维护成本。





**Q12: [learning] 短动画和长动画分别适合什么格式？**

短小、少色动画可用 GIF 或动态 WebP；简单图标动效可用 AnimatedVectorDrawable；连续、长时间的照片式运动可评估视频：

1. **GIF（Graphics Interchange Format）：**适合兼容已有的少色动画。每帧最多 256 色，不适合照片；编辑时还需保留帧时长、处置和透明叠加语义。
2. **动态 WebP：**适合需要更多颜色或透明度的短动画。Android 9 起 ImageDecoder 可为受支持输入创建 AnimatedImageDrawable；旧设备需核验库支持。
3. **AnimatedVectorDrawable：**适合简单图标的路径和属性动画，不必保存多张像素帧。复杂路径仍有逐帧绘制成本。
4. **视频：**适合长时间的连续运动，可能利用硬件解码；透明背景、自动静音、循环和播放器资源需单独验证。
5. **控制播放：**限制画布、帧率、并发播放和离屏播放，并测量首帧等待、持续处理时间和峰值内存。

依据为 GIF89a、Android《AnimatedImageDrawable》《ImageDecoder》和《Supported media formats》。





**Q13: [learning] 何时用 VectorDrawable、ShapeDrawable 或 NinePatch 替代位图？**

简单图形用绘图资源，可变尺寸背景用 NinePatch；复杂照片和插画继续使用位图。替换时同时比较包体、首次绘制和持续绘制成本：

1. **ShapeDrawable：**用属性描述纯色、圆角、描边和渐变，可替代简单背景图。检查描边、阴影和内容间距是否一致。
2. **VectorDrawable：**适合可缩放的简单图标。复杂路径、渐变和遮罩可能增加解析或栅格化成本；SVG 导入还需检查转换结果。
3. **NinePatch：**`.9.png` 保存可拉伸区域和内容内边距。转成普通 WebP 会丢失该语义；能用 ShapeDrawable 表达时可改为形状资源。
4. **验证：**按实际控件尺寸比较产物字节和低端设备首次显示，不为追求矢量化引入复杂绘制或大量小 View。

依据为 Android Developers《Vector drawables overview》《Add multi-density vector graphics》《Drawable resources》和《Create WebP images》。





**Q14: [learning] Drawable 密度缩放怎样影响 Bitmap 尺寸和内存？**

资源密度会影响 Bitmap 解码尺寸；宽高缩放后，像素数和内存按面积变化：

1. **密度换算：**标为 mdpi 的 100 × 100 图片在 xxxhdpi 环境下可能缩放到 400 × 400，像素数增至 16 倍。以实际选中的资源和 Bitmap 输出尺寸为准。
2. **目录选择：**系统会按设备配置选择资源并进行必要的密度缩放。只在一个目录放超大图，不能保证各设备画质或内存合适。
3. **nodpi：**资源不参与密度缩放，但不会自动降采样；4000 × 3000 原图仍可能完整解码。
4. **解码检查：**BitmapFactory.Options.inScaled 默认启用；有效的 inDensity 和 inTargetDensity 会影响输出缩放。普通资源通常应保留密度适配，按原始像素处理时再考虑关闭。
5. **排查：**记录资源目录、源尺寸、目标密度、采样率和输出尺寸，先确认密度缩放再比较内存。

依据为 Android Developers《Support different pixel densities》和 Android《BitmapFactory.Options》。





**Q15: [learning] 宽色域、HDR 和增益图怎样影响图片优化？**

优化时不能只看清晰度，还要确认色彩解释和动态范围是否保留。HDR（High Dynamic Range，高动态范围）图像可能包含额外亮度信息：

1. **色彩空间与精度：**色彩空间定义像素值如何映射为颜色；像素配置定义数值精度。宽色域不一定要求 RGBA_F16，也不能只凭文件后缀推断 Bitmap 配置。
2. **增益图：**Android 14 起支持的 Ultra HDR JPEG 可用增益图扩展基础图像的动态范围。普通 JPEG 重编码或丢弃增益图可能使画面退化为标准动态范围。
3. **转换验证：**缩放、裁切、截图和导出时确认处理链是否保留色彩空间及增益图，并检查不支持 HDR 的设备回退效果。
4. **内存预算：**高精度像素、辅助图像和处理中间结果会增加内存或带宽。按实际 Bitmap 配置和处理链测量，不能一概按宽 × 高 × 4 估算。

依据为 Android Developers《Display Ultra HDR images》《Use wide color gamut content》和 Android《Bitmap.Config》《Gainmap》。





**Q16: [learning] 上传图片时怎样控制编码体积和运行时内存？**

先确定上传用途和输出尺寸，再选择格式与质量。编码减小产物字节，不会减少已解码原图占用的内存：

1. **确定输出：**头像和预览可先校正方向、裁切并采样；原图存档应保留源文件。
2. **选择编码：**Bitmap.compress 的 quality 范围为 0～100，但含义依格式而异。PNG 忽略该参数；Android 11 起的 WEBP_LOSSLESS 中，它表示压缩投入，不代表像素保真度。
3. **减少副本：**Bitmap、缩放结果、ByteArrayOutputStream 内部数组和 toByteArray 复制结果可能同时占内存。直接写入临时文件或目标流可避免大字节数组副本，但仍需 Bitmap 和编码工作区。
4. **满足字节上限：**quality 不能保证固定文件大小。超限时有限调整质量；仍超限则降低尺寸。每轮从同一像素源编码，避免反复解码有损结果。
5. **处理失败：**检查编码返回值和写入异常；取消时清理未完成文件，不能把空文件或半成品作为成功结果。
6. **验收：**检查方向、透明度、色彩和元数据。普通 Bitmap 重编码不保证保留所有源文件信息；要求保真的存档应保留原文件。

依据为 Android《Bitmap.compress》《Bitmap.CompressFormat》和 Java ByteArrayOutputStream 契约。





**Q17: [learning] 怎样验证图片格式优化的实际收益？**

分别测交付、解码、显示和画质，不能用源文件大小代替端到端收益：

1. **网络：**记录实际响应字节、缓存来源和格式协商结果；源文件大小不等于真实传输量。
2. **安装包：**在相同构建条件下比较 APK 资源字节和下载估算。Android App Bundle 会按设备拆分资源，不能把仓库所有图片总和当作单设备下载量。
3. **运行：**在输出尺寸相同的条件下比较解码耗时、实际像素配置、allocationByteCount 和首次显示时间。
4. **画质与兼容：**覆盖照片、文字、渐变、透明边缘、方向标签和格式回退，并记录设备及缓存条件。
5. **决策：**若文件变小但目标设备解码变慢，应按首屏与非首屏场景分别选型，并保留可复现的前后数据。

依据为 Android Developers《Analyze your build with the APK Analyzer》《The Android App Bundle format》和《Reducing image download sizes》。
