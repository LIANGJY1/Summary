# 图片显示与渲染

**Q1: [learning] 显示缩放为什么不能代替按目标尺寸解码？**

显示缩放只改变像素如何映射到控件，不会缩小已经分配的 Bitmap。源尺寸、解码尺寸和显示尺寸必须分别管理。

1. **内存差异：**4000 × 3000 的 ARGB_8888 Bitmap 即使缩在 100 × 75 的控件里，仍有约 45.8 MiB 像素。先解码到 400 × 300，则像素约 0.46 MiB，后续绘制才使用这份较小结果。
2. **保持比例：**CenterCrop 与 Compose ContentScale.Crop 填满并裁掉超出部分，FitCenter 与 ContentScale.Fit 保留整图但可能留白。FillBounds 分别缩放两轴，比例不同会变形。
3. **内容与边界：**Crop 决定原图怎样映射，clip 决定哪些绘制结果能越过组件边界，二者不能互相替代。对齐点还会决定主体被裁掉哪一侧。
4. **图像质量：**把小图放大时，过滤只影响插值与边缘平滑，无法恢复不存在的纹理。需要细节时提高来源分辨率，不能靠更高过滤质量弥补。
5. **验收：**用横图、竖图与主体偏移图核对尺寸、裁切和清晰度。要减少内存，修改的是解码输出或输入资源，不只是控件宽高。

依据为 Android《ImageView.ScaleType》、Android Developers《Customize an image》《Optimizing bitmap images》。

**Q2: [learning] 图片到达后怎样避免列表跳动和重复布局？**

在数据到达前确定图片区域的尺寸或宽高比，让占位、缩略图和主图共享稳定布局。仅替换绘制内容，通常比让布局随图片固有尺寸改变更可控。

1. **跳动原因：**wrap_content 或无约束 Image 可能先按占位尺寸布局，主图到达后重新测量，导致条目高度变化和可见位置移动。
2. **预留空间：**固定头像用固定尺寸，内容流可由服务端提供宽高比，未知比例时使用业务默认比例。目标布局一旦确定，也能给图片库提供合理采样尺寸。
3. **条目身份：**Compose Lazy 列表的稳定 key 让状态随条目移动，RecyclerView 的绑定也应对应稳定数据身份。key 解决身份，不会阻止图片区域自身高度变化。
4. **减少重启：**不要在每次重组或重复绑定时制造无意义的新模型版本、尺寸或变换，让图片请求反复失效。真正的内容变化仍必须更新身份。
5. **验证：**记录重测量次数、滚动位置和请求重启次数，分别模拟慢网、缓存命中、条目插入和方向切换。只在热缓存下看不到跳动不算通过。

依据为 Android Developers《Lazy lists and lazy grids》《Optimizing bitmap images》及 Glide 4《Targets》。

**Q3: [learning] Compose 怎样让图片按布局尺寸异步加载？**

给组件有限布局约束，并使用能够把约束传给解码器的加载方式。ContentScale 负责内容映射，不能独自补足缺失的请求尺寸。

1. **本地小资源：**painterResource 适合小图标，可能在主线程解析和解码，不会自动按 Image 的显示尺寸为任意大图采样。大位图资源同样应评估异步加载。
2. **Coil 3 AsyncImage：**根据布局约束和 ContentScale 推导请求尺寸，通常适合列表。尺寸或宽高比必须能收敛，无界滚动方向不能天然代表目标原像素。
3. **rememberAsyncImagePainter：**默认不检测屏幕显示尺寸，可能按原始尺寸加载。确需 Painter 接口时，用 rememberConstraintsSizeResolver，并把同一个解析器同时接到请求 size 和组件 Modifier，缺一端都不能正确传递约束。
4. **子组合成本：**SubcomposeAsyncImage 便于通过子组合表达状态，但在长列表中会增加组合开销。只有该状态布局确有需要时使用，并对照 AsyncImage 测滚动表现。
5. **状态与画面：**rememberAsyncImagePainter 首次组合可能报告 Empty，即使内存结果已可在首帧绘出。不要据此自动插入一帧空白，性能验收仍以实际画面为准。

依据为 Coil 3《Compose》与 Android Developers《Optimizing bitmap images》。

**Q4: [learning] 圆角、裁切和着色何时预生成，何时绘制时处理？**

固定且反复复用的复杂效果可预处理，随状态变化的简单效果优先评估绘制时完成。判断依据是重复计算、像素副本和每帧成本的总和。

1. **预生成：**在后台对合理尺寸图像做固定变换，缓存结果后重复展示较便宜。不同尺寸、圆角半径、主题色会生成不同变体，缓存数量和处理峰值可能增加。
2. **绘制裁切：**简单圆角或形状裁切可共用原图，避免多份结果。复杂 Path、遮罩或不支持的绘制操作仍可能引入额外图层，不能假定所有 clip 都免费。
3. **ColorFilter：**显示时着色不需要为每种主题生成完整 Bitmap，适合单色图标。它只影响绘制，不会改写导出的源像素。
4. **处理顺序：**需要实际导出或下游算法读取效果时，必须生成像素结果。预裁切与绘制裁切还应保持同一坐标和主体焦点，否则缓存正确也可能画面错误。
5. **选择实验：**在同一目标尺寸比较处理时间、变体数量、峰值与滚动慢帧。静态效果未必值得预生成，动态效果也未必可以无限叠加。

依据为 Glide 4《Transformations》、Android Developers《Customize an image》《Graphics modifiers》。

**Q5: [learning] 软件 Bitmap 解码完成后，首次绘制为什么还会卡？**

硬件加速绘制可能还要为软件像素建立并上传纹理，解码成功只是显示链路的一部分。大图集中在同一帧到达，会放大首次准备成本。

1. **定位证据：**资源回调已及时到达，而首次包含图片的帧在 RenderThread 或图形准备阶段变长，应检查纹理上传和图像尺寸。不能仅凭“第二次更快”断定是哪层缓存。
2. **减少像素：**控制解码尺寸比只降低文件压缩质量更直接。多个缩略图误解到原图尺寸，会同时增加像素驻留和首次上传工作。
3. **提前准备：**Bitmap.prepareToDraw 早已存在，Android 7.0 起可提前异步安排纹理上传。只对已经完成像素修改且明确归自己管理的 Bitmap 评估调用，图片库可能已执行该步骤。
4. **限制收益：**调用不保证纹理一直驻留，也不意味着显示帧必定无等待。之后修改像素可能重新触发准备，过早准备大量离屏图还会挤占图形资源。
5. **Hardware Bitmap：**可改变部分上传与驻留成本，但仍有解码、缓冲和绘制工作。最终以首次显示帧及进程内存比较，不以返回配置判断成功。

依据为 Android《Bitmap.prepareToDraw》与 Android Developers《Slow rendering》。

**Q6: [learning] drawWithCache 和 graphicsLayer 缓存了什么？**

drawWithCache 主要复用绘制所需对象，graphicsLayer 隔离绘制内容并支持图层属性变换，二者都不是图片加载缓存的替代品。

1. **对象缓存：**drawWithCache 可复用 Brush、Path 等创建成本高的对象，尺寸或构建缓存时读取的状态变化会重新执行构建。绘制回调仍会按需要运行，Bitmap 的加载与寿命仍由其他机制管理。
2. **图层属性：**graphicsLayer 可在内容不变时调整平移、旋转、缩放等属性，避免重复执行内容绘制逻辑。若内容本身持续变化，就不能期待相同复用收益。
3. **离屏含义：**图层不总等于独立像素缓冲，是否离屏栅格化受合成策略和效果影响。强制离屏会额外消耗与图层面积相关的图形内存。
4. **使用边界：**仅绘制一张已经缓存的静态图，没有昂贵对象构建时，额外加 drawWithCache 未必改善性能。为大列表所有条目长期保留离屏层可能扩大驻留。
5. **验证：**分别比较组合、布局、绘制和图形占用。某阶段执行次数下降并不保证总帧时间下降，可能只是把工作移到另一阶段。

依据为 Android Developers《Graphics modifiers》。

**Q7: [learning] 淡入、透明叠加与模糊为什么可能增加图形内存？**

这些效果可能让多张图片同时存活，并引入混合或离屏缓冲。成本由覆盖面积、叠加数量和实现决定，不由动画代码的行数决定。

1. **淡入共存：**占位或旧图与新图交叉过渡时，短时间内都需要保留。Glide 4 默认不启用过渡，其内置过渡也通常跳过内存缓存命中，自定义实现可能不同。
2. **透明语义：**新图含透明区域时，只淡入新图可能露出下方占位内容。必须验证透明边缘和过渡结束后的画面，不能为省绘制改变预期合成结果。
3. **整体 alpha：**Compose 默认合成策略在 alpha 小于 1 时可能使用离屏层。ModulateAlpha 可减少部分离屏需求，但对有重叠绘制的内容会改变混合结果，不能只凭省内存切换。
4. **模糊：**Compose Modifier.blur 依赖 Android 12 及以上能力，旧版本需要符合产品预期的回退。大面积动态模糊可能反复处理离屏结果，固定模糊可评估较小尺寸的预生成方案。
5. **优化顺序：**先减少不必要面积和同时动效数，再比较过渡时长或实现。使用真实透明图与低端设备同时验收画质、峰值和慢帧。

依据为 Glide 4《Transitions》、Android Developers《Customize an image》《Graphics modifiers》。

**Q8: [learning] 软件 Canvas 和图片变换怎样避免拖慢主线程？**

把与当前帧无关的大像素运算放到有界工作队列，主线程只交付最终结果。开启硬件加速也不会让任意软件 Bitmap 变换自动变成 GPU 运算。

1. **识别路径：**Canvas(Bitmap) 绘制到软件 Bitmap，与 View 的硬件加速 Canvas 不同。缩放、逐像素访问、模糊和压缩导出可能仍由 CPU（Central Processing Unit）完成。
2. **减少工作：**先按业务尺寸采样，再进行确需落到像素的变换，尽量组合裁切与旋转。逐像素 getPixel/setPixel 循环有大量调用开销，应评估批量访问或经过验证的原生实现。
3. **限制峰值：**批量 IntArray 也会占内存，改成批量访问不等于零成本。输出、数组和原 Bitmap 并存时，一起纳入预算。
4. **线程安全：**工作线程独占可变结果，完成后再交付。不能边修改同一 Bitmap 边让界面绘制，也不能在任务未结束时把存储归还对象池。
5. **取消与交付：**页面变化时取消尚未需要的工作，结果交付前检查当前请求身份。后台化只消除主线程直接执行，过度并发仍会争用计算与内存带宽。

依据为 Android《Canvas》《Bitmap》与 Android Developers《Slow rendering》。

**Q9: [learning] Bitmap 能解码成功，为什么仍可能无法绘制？**

解码内存限制、Canvas 绘制限制和图形后端纹理限制不是同一道门。分配成功不保证当前画布能接受该尺寸或存储类型。

1. **尺寸限制：**目标后端允许的最大纹理宽高可能小于源图。Canvas 提供最大 Bitmap 宽高查询，实际限制受设备与绘制路径影响，不能硬编码一个通用“最大像素数”。
2. **容量限制：**平台绘制路径也可能拒绝过大的 Bitmap。不要把某次异常中的字节阈值当作所有 Android 版本的 API 契约。
3. **类型限制：**Hardware Bitmap 不能绘制到软件 Canvas。某个 View 开启软件层，或截图路径使用 Canvas(Bitmap)，都可能暴露此前没有出现的兼容问题。
4. **生命周期：**已回收或交回图片库的 Bitmap 继续被自定义 View 使用，也可能失败。解决方法是修复所有权，不是把异常吞掉后继续绘制。
5. **处理策略：**普通显示减小输出，局部高清查看采用区域解码，软件消费提前请求软件 Bitmap。失败时提供合理占位并保留尺寸、配置和 Canvas 路径证据。

依据为 Android《Canvas.getMaximumBitmapWidth》《Canvas.getMaximumBitmapHeight》、Glide 4《Hardware Bitmaps》《Resource Reuse》。

**Q10: [learning] 怎样确认主图第一次进入了哪一帧？**

先定义测量终点，再关联资源身份、目标更新和帧。应用回调只能证明资源事件，不能直接证明面板已经显示对应像素。

1. **视觉终点：**区分占位首次出现、缩略图可辨认、主图首次出现和过渡结束。用缩略图时间冒充主图时间会掩盖最终画质等待。
2. **应用证据：**记录目标更新，并给首次绘制该资源的应用帧关联请求身份。onPreDraw 发生在绘制前，不能当成图片已显示的证明。
3. **系统证据：**Android 12 起可利用 FrameTimeline 在 Perfetto 中关联预期与实际帧时序，分析应用和合成链路的延迟。具体关联能力取决于表面和追踪数据，不能只凭一个独立日志时间戳匹配。
4. **内容证据：**帧时间线本身不知道业务像素是占位还是主图，需应用标记配合录屏或测试截图核对。录屏也可能有延迟和丢帧，不等于精确的面板扫描测量。
5. **报告边界：**只拿到资源回调就报告资源就绪，只拿到提交帧就报告已提交。缺少呈现证据时不声称测得用户肉眼看到的精确时刻。

依据为 Perfetto《FrameTimeline》及 Android Developers《Slow rendering》。

**Q11: [learning] 热缓存下滚动仍卡，怎样排查图片显示成本？**

先用证据确认取数与解码是否真的消失，再检查当前帧中的布局、绘制、上传和合成。热缓存只是减少部分工作，不代表图形资源也全部驻留。

1. **验证缓存：**记录实际来源与 Bitmap 身份。相同地址不同尺寸或变换可能仍在解码，缓存命中率的总体数字也可能掩盖当前慢条目。
2. **主线程：**检查条目重绑、尺寸变化、复杂占位、同步本地解码和重复布局。目标数量大时，即使每个交付很短，也可能集中占满一帧。
3. **渲染线程：**比较首次与再次使用同一 Bitmap 的帧，定位纹理准备、复杂裁切或离屏层。内存命中不保证纹理没有被驱逐。
4. **合成与带宽：**大面积透明叠加、多图渐变和模糊增加像素处理。移除某个效果做单变量对照，比一口气更换加载库更容易验证原因。
5. **预算：**60 Hz 一帧约 16.7 ms，120 Hz 约 8.3 ms。按设备实际刷新率及帧时间分布验收，不能在所有设备上套一个 16 ms 阈值。

依据为 Android Developers《Slow rendering》《Graphics modifiers》及 Glide 4《Debugging》。

**Q12: [learning] 面试中怎样完整分析图片列表慢、卡和内存高？**

先把症状拆成可测指标，再沿取数、解码、驻留和显示逐段提出假设。每个措施都应对应证据，并说明代价与验证方法。

1. **明确场景：**确认是首次等待长、快速滚动掉帧、内存持续增长，还是短时峰值导致 OOM（Out Of Memory）。固定设备、图片集、列表尺寸和缓存状态后建立基线。
2. **解释数量级：**例如 12 张误解为 4000 × 3000 的 ARGB_8888 图片，仅像素约 549.3 MiB，尚未计其他副本。若按 400 × 300 输出，12 张约 5.49 MiB。这个推导证明优先查输出尺寸合理，但不代表真实设备已测得该收益。
3. **按证据行动：**取数慢就评估服务端尺寸与缓存，解码峰值大就修采样和并发，旧页持有就修生命周期，资源早就绪而帧慢就查布局、上传与合成。
4. **说明取舍：**预取可能争用资源，缓存可能扩大驻留，RGB_565 可能伤画质，Hardware Bitmap 限制软件消费。没有适用于所有图片的单一开关。
5. **闭环：**同条件比较主图可见时间分布、慢帧、响应字节、峰值和失败率，并覆盖错图、透明度、方向及后台恢复。未实测时只报告假设和预期，不能把计算示例包装成项目成果。

依据为前述平台与加载库机制，流程是面向面试与实际排障的分析示例。
