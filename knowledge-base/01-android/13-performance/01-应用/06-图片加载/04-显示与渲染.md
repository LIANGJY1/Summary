# 图片显示与渲染

**Q1: [learning] 显示缩放能代替按目标尺寸解码吗？**

不能。绘制缩放改变显示方式，不会减少已经解码的像素。三种尺寸由不同环节决定：

1. **图片尺寸：**由源图像素决定。
2. **控件尺寸：**由父布局约束决定。
3. **Bitmap 输出尺寸：**由图片请求和解码策略决定。应让图库得到有界目标像素，再用绘制缩放决定裁切或留白。

依据为 Glide 4《Targets》和 Android Developers《Optimizing bitmap images》。

**Q2: [learning] View 与 Compose 的图片缩放怎样决定裁切、留白或变形？**

按是否保持比例与是否填满区域判断：

1. **CenterCrop / ContentScale.Crop：**保持比例并填满，超出的内容被裁掉。
2. **FitCenter / ContentScale.Fit：**保持整图可见，比例不同时留白。
3. **ContentScale.FillBounds：**宽高分别缩放，比例不同时可能拉变形。

4. **验收：**这些名称不能机械对应，对齐位置也会改变可见内容。迁移时用非正方形样图核对。依据为 Android《ImageView.ScaleType》和 Android Developers《Customize an image》。

**Q3: [learning] 放大小图时过滤质量能恢复细节吗？**

不能。目标像素超过源图可提供的细节时，缩放过滤只能改变邻近像素的插值与边缘平滑，不能生成真实纹理。更高过滤质量还可能增加绘制成本。按最大显示倍率检查照片、细线和像素画，再选合适源尺寸与过滤方式。依据为 Android Developers《Optimizing bitmap images》。

**Q4: [learning] ColorFilter 为什么通常不需要另存一张着色位图？**

ColorFilter 在绘制时改变颜色，适合显示效果无需生成新像素的场景：

1. **主题色切换：**可复用原图，避免为每种颜色保存完整位图副本。
2. **绘制成本：**复杂或重复叠加时仍可能拖慢目标帧，应实测。
3. **导出图片：**ColorFilter 不会改写源文件，需另行生成处理后的像素。

依据为 Android Developers《Customize an image》。

**Q5: [learning] 裁切图片时为什么要区分内容裁切与 View 边界裁切？**

两种裁切控制不同边界：

1. **内容裁切：**ContentScale.Crop 或 CenterCrop 决定原图哪些区域映射到目标。
2. **View 边界裁切：**clip 或 clipToBounds 限制绘制结果不能越过控件边界。

两者叠加时检查主体焦点是否被裁掉。依据为 Android Developers《Customize an image》。

**Q6: [learning] 图片到达后为什么会让列表位置跳动？**

图片到达后位置跳动，通常是图片区域尺寸随内容变化：

1. **原因：**占位图和主图比例不同，导致 View 重新布局或 Compose Lazy 列表重排。
2. **约束尺寸：**预留固定尺寸或宽高比，在区域内切换占位、缩略图和主图。
3. **验收：**检查布局次数与滚动位置。条目插入或移动时为列表项提供稳定 key。

依据为 Android Developers《Optimizing bitmap images》和《Lazy lists and lazy grids》。

**Q7: [learning] 圆角等图片效果何时预变换，何时绘制时处理？**

按样式是否稳定选择：

1. **固定效果：**可预变换并缓存，但不同尺寸或圆角半径会产生不同结果与缓存键。
2. **动态效果：**先比较绘制时裁切或滤镜，避免为每种状态留一份像素。

3. **Compose 裁切：**Modifier.clip 也有绘制成本，复杂轮廓须测慢帧。
4. **比较结果：**同时检查画质、像素峰值和帧耗时。依据为 Glide 4《Transformations》和 Android Developers《Customize an image》。

**Q8: [learning] 模糊效果为什么要核对 Android 版本？**

Compose 的 blur 效果有平台与绘制成本边界：

1. **平台支持：**常用 blur 效果依赖 Android 12 及以上，旧系统须提供回退。
2. **运行成本：**大面积动态模糊可能增加离屏缓冲和帧耗时，应在目标设备测量。

3. **效果边界：**不能假设同一 Modifier 在所有系统版本产生相同效果。依据为 Android Developers《Customize an image》。

**Q9: [learning] 软件 Canvas 反复绘制大图为何可能拖慢主线程？**

软件 Canvas 的主线程成本取决于待处理的像素工作：

1. **成本来源：**图片面积、绘制缩放和重复次数越大，CPU（Central Processing Unit）每帧工作通常越多。
2. **优化与验证：**先将输出控制在显示所需尺寸，再对比硬件加速和软件绘制的帧耗时。

3. **判断边界：**文件体积小不代表绘制便宜。依据为 Android Developers《Slow rendering》。

**Q10: [learning] Compose 图片怎样按布局目标尺寸加载？**

组件能否给出有界尺寸决定加载器能否按目标像素解码：

1. **painterResource：**大位图可能在组合路径同步解码，不会按 Image 的显示尺寸自动降采样，适合小图标。
2. **Coil 3 AsyncImage：**结合有限布局约束与 ContentScale 解析请求尺寸，仍应核对返回结果。
3. **rememberAsyncImagePainter：**裸 model 可能按原图加载，需要时配置 rememberConstraintsSizeResolver。
4. **无界容器：**先给出尺寸或宽高比，不能指望 ContentScale 推断目标像素。

5. **列表加载：**优先传图片 model，让请求根据当前布局确定尺寸。依据为 Coil 3《Compose》和 Android Developers《Graphics and rendering performance optimization》。

**Q11: [learning] Coil 3 的 Painter 初始 Empty 状态等于首帧看不到图片吗？**

不等于。rememberAsyncImagePainter 的状态在首次组合可为 Empty，即使内存缓存图片已能在首帧绘出。测试应以实际画面或帧为准，不把初始状态直接记成占位时长。依据为 Coil 3《Compose》。

**Q12: [learning] SubcomposeAsyncImage 为什么不宜默认用于长列表？**

SubcomposeAsyncImage 用子组合表达加载状态，布局灵活但会增加组合工作：

1. **常规长列表：**优先评估 Coil 3 AsyncImage。
2. **确需加载状态子组合：**再用 SubcomposeAsyncImage，并测量滚动帧。

依据为 Coil 3《SubcomposeAsyncImage》接口文档。

**Q13: [learning] Compose 列表项缺少稳定 key 为什么会让图片状态错位？**

稳定 key 应标识条目内容，而不是当前列表位置：

1. **缺少稳定 key：**插入或移动后，组合状态可能跟随位置，导致占位或过渡状态错配。
2. **提供唯一 key：**让状态随数据身份移动。
3. **更新图片请求：**确认图片 model 也对应当前条目内容。

依据为 Android Developers《Lazy lists and lazy grids》。

**Q14: [learning] drawWithCache 缓存的是整张图片像素吗？**

通常不是。drawWithCache 缓存绘制阶段创建的对象，不缓存图片像素：

1. **可复用对象：**例如昂贵的 Brush 或 Path，可在尺寸或相关状态不变时复用。
2. **绘制内容：**绘制回调仍会按需执行，Bitmap 仍由图片库等机制管理。

依据为 Android Developers《Graphics modifiers》。

**Q15: [learning] graphicsLayer 为什么有时能减少重复绘制工作？**

graphicsLayer 是否有收益取决于内容变化方式：

1. **属性变化：**只改平移、缩放等图层属性时，可复用已记录的绘制内容。
2. **内容变化或离屏栅格化：**可能增加重绘和图形内存。
3. **验收：**对比优化前后的慢帧与图形内存。

依据为 Android Developers《Graphics modifiers》。

**Q16: [learning] Compose 的图片 alpha 动画何时需要离屏层？**

alpha 小于 1 时，离屏策略取决于合成方式：

1. **默认策略：**可能先把整层画到离屏缓冲，再与背景混合。
2. **ModulateAlpha：**可减少部分离屏工作，但重叠绘制的混合结果可能改变。
3. **验收：**图片与装饰重叠时先核对画面，再比较图形内存和慢帧。

依据为 Android Developers《Graphics modifiers》和《CompositingStrategy》。

**Q17: [learning] Hardware Bitmap 能消除图片首次显示成本吗？**

不能。Hardware Bitmap 改变像素存放与绘制路径，不会免除加载和显示成本：

1. **可能省下：**部分软件 Bitmap 首绘时的纹理上传。
2. **仍需承担：**缓冲创建、解码、页面绘制和图形内存成本。
3. **使用限制：**不能直接绘制到需要 CPU 可访问像素的软件 Canvas。后续若需软件绘制，应在解码前请求软件 Bitmap。

依据为 Android《Bitmap.Config》和《Bitmap API reference》。

**Q18: [learning] 软件 Bitmap 解码完成后为什么首绘仍可能慢？**

软件 Bitmap 首次进入硬件加速绘制时，可能需要准备并上传为图形纹理，因此解码完成不代表首绘成本结束：

1. **提前准备：**Android 7.0 起，应用自己管理且像素已定稿的 Bitmap 可评估调用 prepareToDraw。
2. **内容变更：**准备后再改像素可能使结果失效并触发再次上传。
3. **图库管理的 Bitmap：**确认图片库是否已处理，避免重复准备。
4. **验收：**比较首次显示帧，不以调用本身推断收益。

依据为 Android《Bitmap API reference》和 Android Developers《Slow rendering》。

**Q19: [learning] 同一图片再次显示更快能说明什么？**

再次显示变快不能单独证明命中了网络或图片缓存。定位省掉的工作时，对照各阶段证据：

1. **图库阶段：**取数、解码或变换可能减少。核对 Glide 返回的数据来源类型（DataSource）。
2. **图形阶段：**纹理准备与上传可能减少。比较 Bitmap 身份和首次、再次显示帧。
3. **界面阶段：**布局或绘制路径可能变化。多张新图同帧出现时，上传、裁切和混合成本还会叠加。

依据为 Glide 4《Caching》和 Android Developers《Slow rendering》。

**Q20: [learning] 怎样确认占位、缩略图和主图分别在哪一帧可见？**

占位、缩略图和主图是不同的视觉状态，应分别确认首次可见帧：

1. **识别资源：**记录当前显示的是占位、缩略图还是主图，并确认内容版本。
2. **关联应用帧：**记录目标更新及首次包含该图的应用帧。
3. **确认显示：**应用提交后仍要经过系统合成与显示。只有应用内事件时只能报告“已提交”，不能当作面板可见时间。

依据为 Glide 4《Options》和 Android Developers《FrameTimeline》。

**Q21: [learning] 图片渐变过渡怎样影响可见时间和绘制成本？**

资源交付后，主图可能尚未达到最终 alpha。应区分首次出现与过渡结束，并核对：

1. **Glide 4 默认行为：**默认不启用过渡。内置过渡在内存缓存命中时也不运行，自定义过渡可改变规则。
2. **透明图片：**只让新图淡入时，透明像素可能露出下方占位图，须按背景和过渡方式验收。
3. **长列表：**大量图片同时渐变会增加混合与可能的离屏层工作，须比较慢帧。

依据为 Glide 4《Transitions》。

**Q22: [learning] 图片资源就绪但显示仍慢，应怎样排查并验证优化？**

固定设备、图片集、目标尺寸、布局、滚动路径和缓存状态，沿同一图片的时间线检查：

1. **目标未更新：**查请求是否交付到正确目标及主线程排队。
2. **主线程慢：**查重测量、列表重绑和绘制记录。
3. **RenderThread 慢：**查首次纹理上传、裁切与离屏层。
4. **应用帧已提交仍晚：**查系统合成与显示时序。

用以下指标比较优化前后，避免只凭回调时间宣布收益：

1. **可见时间：**主图首次进入显示帧的时间。
2. **绘制成本：**慢帧分布与图形内存。
3. **布局成本：**布局次数。依据为 Android Developers《Slow rendering》和《FrameTimeline》。
