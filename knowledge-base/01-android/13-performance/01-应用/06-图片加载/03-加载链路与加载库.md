# 加载链路与加载库

**Q1: [learning] 为什么同 URL 的图片请求可能有不同缓存和耗时？**

URL（Uniform Resource Locator）只标识来源，不足以标识处理结果。比较前对齐两类条件：

1. **请求结果：**内容版本、目标尺寸、变换、选项和结果类型可能改变缓存键。
2. **执行路径：**内存、磁盘或网络来源，以及设备负载，都可能改变耗时。

记录 Glide 实际返回的数据来源类型（DataSource），不能只按 URL 聚合。依据为 Glide 4《Caching》。

**Q2: [learning] Glide 怎样确定 ImageView 的请求尺寸？**

Glide 4 的 ImageViewTarget 通过 getSize 获取目标宽高，再据此决定降采样与变换。检查请求尺寸时按顺序确认：

1. **请求已绑定：**into 已调用并把请求交给 ImageView。
2. **目标已布局：**View 已完成布局并提供非零宽高。
3. **尺寸回调已到：**getSize 收到目标尺寸。明确知道目标像素时才指定 override。

依据为 Glide 4《Targets》和《Debugging》。

**Q3: [learning] Glide 的 override 怎样影响输出和缓存？**

Glide 4 的 override 指定输出宽高，会影响解码、变换和结果缓存键，但不会改变远端原文件字节：

1. **内存效果：**大源图解码到与小图相近的输出尺寸和配置时，Bitmap 才可能占用相近内存。
2. **失效条件：**目标尺寸无界、请求原始尺寸或自定义 Target 错报尺寸，都可能使自动降采样失效。
3. **核对方式：**检查返回 Bitmap 的宽高和配置。

依据为 Glide 4《Targets》和《Caching》。

**Q4: [learning] Glide 的各层缓存按什么顺序查找？**

Glide 4 按复用成本依次查找：

1. **活动资源：**仍被目标引用的结果。
2. **内存缓存：**最近释放、可直接复用的 Bitmap 结果。
3. **资源磁盘缓存：**处理后的文件，命中后仍可能需要解码。
4. **数据磁盘缓存：**原始编码字节，命中后须按目标解码与变换。
5. **原始来源：**前面未命中才访问本地文件或网络。

记录实际 DataSource，不能把所有命中都视为无需解码。依据为 Glide 4《Caching》。

**Q5: [learning] Glide 的磁盘缓存策略怎样按来源和复用方式选择？**

Glide 4 的磁盘策略按来源和复用目标选择：

1. **AUTOMATIC：**远端来源倾向缓存原始数据，本地来源倾向缓存处理结果，实际写入还受编码器和来源类型影响。
2. **DATA：**同源图要生成多种尺寸或变换时，缓存原始字节便于重新处理。
3. **RESOURCE：**同一处理结果会反复显示时，缓存结果以减少重复变换。

4. **验收：**两种策略都占磁盘，应按实际命中与复用情况调整。依据为 Glide 4《Caching》。

**Q6: [learning] 自定义 Transformation 为什么必须稳定参与缓存键？**

缓存键必须表达会改变变换结果的参数：

1. **参数一致：**自定义变换的 equals、hashCode 与 updateDiskCacheKey 应描述相同参数。
2. **键随结果变化：**参数改变输出像素时，缓存键也须变化，否则可能错误复用或持续失配。

依据为 Glide 4《Transformations》。

**Q7: [learning] 固定 URL 的图片缓存怎样区分版本和访问范围？**

固定 URL 可能在内容更新或账号切换后返回不同图片，缓存身份必须随这两类变化：

1. **内容版本：**使用带版本的 URL，或为 Glide 请求提供摘要、修订号等可靠 signature。
2. **访问范围：**按账号或权限分区，但不要把原始令牌写入缓存键。退出或权限变化时处理旧缓存。

3. **缓存清理：**只清一次缓存不能保证后续请求新鲜，也不能防止跨账号误复用。依据为 Glide 4《Caching》。

**Q8: [learning] 图片库磁盘缓存与 HTTP 缓存可以视为同一层吗？**

不能。两种缓存的身份与控制规则不同：

1. **HTTP（Hypertext Transfer Protocol）缓存：**由网络客户端按响应头管理。
2. **图片库磁盘缓存：**按图片请求身份和图库自身策略存储。
3. **Coil 3：**默认网络缓存策略不直接遵守 Cache-Control，须检查网络模块的配置。

先确认实际命中或写入的缓存层，再判断过期图。依据为 Coil 3《Network Images》。

**Q9: [learning] Glide 的缓存控制选项分别影响什么？**

三个选项作用于不同边界：

1. **onlyRetrieveFromCache：**只从缓存取，未命中就失败。
2. **skipMemoryCache：**不把结果留在内存缓存，展示中的 Bitmap 仍占内存，也可能增加后续解码。
3. **DiskCacheStrategy.NONE：**跳过 Glide 磁盘缓存，减少写盘与占用，也失去该层复用。其他网络缓存仍可能命中。

4. **选择依据：**按离线需求、数据敏感性和命中率选择，不能把它们当作统一的省内存开关。依据为 Glide 4《Caching》。

**Q10: [learning] 为什么 Coil 3 通常共享一个 ImageLoader？**

通常共享一个 ImageLoader，因为每个实例各自持有资源：

1. **共享实例：**页面间可复用内存缓存、磁盘缓存和网络客户端。
2. **多个实例：**会分割缓存并增加资源占用。
3. **拆分条件：**确需测试隔离或不同授权域时再创建独立实例。

依据为 Coil 3《Image Loaders》。

**Q11: [learning] Coil 3 网络图没有加载时为什么先查网络组件？**

Coil 3 核心库不一定包含网络取数能力，URL 模型本身也不保证能被读取。排查时按顺序检查：

1. **组件：**安装并注册网络模块。
2. **请求失败原因：**确认是否为网络组件缺失或配置错误。
3. **后续环节：**组件无误后再查缓存与解码。

依据为 Coil 3《Network Images》和《Getting Started》。

**Q12: [learning] 图片请求怎样随页面和列表目标清理？**

页面退出或目标复用后仍交付旧图会浪费资源并显示错内容。按目标所有权处理：

1. **页面：**让 Glide RequestManager 跟随 Activity 或 Fragment 生命周期，跨页面工作才考虑 application context。
2. **RecyclerView：**同一 ImageView 绑定新条目时发新请求或清旧请求，自定义回调再核对条目身份。
3. **自定义 Target：**保存实例并调用 clear，解除目标对资源的占用。图片库管理的 Bitmap 不能由业务直接 recycle。

依据为 Glide 4《Targets》和《Resource Reuse》。

**Q13: [learning] RecyclerView 图片预取怎样判断收益并控制开销？**

只有取数或解码常晚于条目进入视口，预取才可能缩短占位时间。执行时要控制：

1. **请求一致：**预取与正式绑定使用相同模型、尺寸和变换，否则结果缓存可能不命中。
2. **窗口范围：**从视口附近少量条目开始，避免离屏工作争用网络、线程和内存。
3. **方向变化：**反向滚动时取消已远离视口的请求，再按新方向预取。

4. **验收：**无用下载与峰值上升而主图可见时间未改善时，应缩小或停用预取。依据为 Glide 4《RecyclerView integration》和《Caching》。

**Q14: [learning] Glide 缩略图请求能改善什么，何时不会受益？**

缩略图主要缩短可辨认内容首次出现的等待，不保证主图更早完成：

1. **加载关系：**Glide 4 的 thumbnail 与主请求并行，已完成的主图不会被迟到的缩略图覆盖。
2. **可能的额外成本：**重复读取大源，或缩略图很少先于主图出现时，会增加工作。
3. **显示风险：**内容版本不一致可能短暂显示旧图。
4. **验收：**分别记录缩略图和主图的可见时间。

依据为 Glide 4《Options》和《Caching》。

**Q15: [learning] 首屏主图为什么应优先于离屏请求？**

首屏主图应先于离屏预取，因为额外请求会争用网络、CPU（Central Processing Unit）、磁盘与内存：

1. **先处理：**取消过期预取并限制预取窗口。
2. **再调度：**根据主图排队时间和资源占用调整并发。
3. **使用 priority：**它影响 Glide 库内调度，不保证系统严格按优先级完成。

依据为 Glide 4《Options》。

**Q16: [learning] 服务端缩图与客户端降采样怎样分工？**

两端分别控制不同成本：

1. **服务端：**按少量常用尺寸档位提供变体，减少传输字节并维持缓存复用。
2. **客户端：**按实际目标尺寸降采样，控制 Bitmap 像素。

3. **验收：**同时控制传输字节和输出像素时，服务端与客户端需协同。按设备分布、裁切和实际字节选择服务端尺寸档位。依据为 Android Developers《Reducing image download sizes》。

**Q17: [learning] Glide 的占位、缩略图与错误请求各在何时显示？**

三者对应不同阶段：

1. **占位图：**主请求进行时显示。
2. **缩略图：**可在主图完成前先显示，不等于主请求成功。
3. **error 请求：**主请求失败后才启动，即使缩略图已经出现。Glide 4.3 起支持 error RequestBuilder，它有自己的尺寸等选项。

4. **失败回退：**若要保留已显示的缩略图，须明确验证失败后的视觉表现。依据为 Glide 4《Options》。

**Q18: [learning] 为什么图片请求失败不宜无限自动重试？**

无限重试会占用带宽与调度槽，挤压可见图片。应先按错误类型决定是否重试：

1. **暂时性网络错误：**可在合适时机有限重试。
2. **格式、权限或资源缺失：**先修复原因，重复请求通常无效。
3. **重试后仍失败：**保留原请求尺寸和失败来源等证据，避免把重试当作根因修复。

依据为 Glide 4《Debugging》的失败归因流程。

**Q19: [learning] Glide 图片请求从创建到显示怎样划分并测量耗时？**

请求成功不等于图片已显示。要比较首屏耗时，应沿同一请求记录阶段并固定实验条件：

1. **创建并绑定：**Glide.with() 获取请求管理器，load() 设置来源，into() 绑定目标并启动请求。load() 本身不表示取数或解码已经开始。
2. **取得目标尺寸：**目标提供布局宽高，尚未布局时请求可能等待。
3. **查找并生成资源：**记录缓存来源。未命中时再跟踪取数、解码和变换。
4. **区分交付和显示：**资源交给目标后还要绘制并进入显示帧。请求回调不等于图片已可见。
5. **固定实验条件：**保持设备、网络、图片集、目标尺寸与进入路径一致，区分冷缓存、磁盘命中和内存命中。
6. **标识请求：**记录内容版本、目标身份和唯一请求标识，避免列表复用后混淆。

依据为 Glide 4《Configuration》《Targets》《Caching》《RequestListener》和 Android Developers《FrameTimeline》。

**Q20: [learning] 图片加载链路优化后怎样验证瓶颈已消失？**

只改变一个候选瓶颈，在相同请求条件下对齐取数、解码、目标更新和首次包含主图的帧：

1. **磁盘命中仍慢：**查读盘、缓存文件解码、变换和输出尺寸。
2. **资源就绪到目标更新慢：**查主线程排队、目标生命周期与布局。
3. **目标已更新但帧慢：**查绘制、纹理上传和显示链路。

4. **最终验收：**对比可见时间、慢帧、下载字节与内存峰值。若回调变快而可见时间不变，原瓶颈可能已转移。依据为 Glide 4《Debugging》和 Android Developers《FrameTimeline》。
