# 图片解码与内存

**Q1: [done] 压缩文件很小，为什么解码后仍可能占大量内存？**

压缩只减少文件字节，不决定解码后的像素内存。Bitmap 的像素内存主要由输出宽高和每像素字节数决定。

1. **像素内存：**ARGB_8888 每像素 4 字节。4000 × 3000 像素解码后约占 45.8 MiB，与压缩文件本身有多大无关。
2. **输出尺寸与配置：**同一张图采样到 2000 × 1500 后，ARGB_8888 像素约占 11.4 MiB；若解码器采用 RGB_565（每像素 2 字节），约占 5.7 MiB。复用较大的 Bitmap 时，底层容量可能不随当前像素量缩小，详见 Q4。
3. **解码峰值：**像素之外还会有临时工作缓冲。Android 11 的 BitmapFactory.decodeStream 未提供缓冲区时会另建 16 KiB 数组，通常远小于像素内存。

依据为 Android Developers《Loading Large Bitmaps Efficiently》、Android《Bitmap API reference》和 Android 11 BitmapFactory 实现。

**Q2: [done] Bitmap 解码临时缓冲区怎样优化内存占用？**

频繁串行调用 BitmapFactory.decodeStream 时，可复用 BitmapFactory.Options.inTempStorage 提供约 16 KiB 的临时数组，减少重复分配和垃圾回收；数组本身仍占内存，也不会减少 Bitmap 像素内存。

1. **复用范围：**每个解码工作线程复用自己的数组；并行解码不要同时共享同一数组。
2. **优化重点：**临时数组很小，降低峰值内存应优先按显示尺寸采样，并控制同时解码的图片数。

依据为 Android Developers《BitmapFactory.Options》和 Android 11 BitmapFactory.decodeStream 实现。

**Q3: [learning] getByteCount 与 getAllocationByteCount 为什么可能不同？**

两者衡量的对象不同：

1. **getByteCount：**按当前宽高和配置计算像素字节数。
2. **getAllocationByteCount：**返回底层已分配容量。较大的 Bitmap 被复用为较小输出时，原有容量可能仍保留。

3. **使用：**估算当前像素数据用 getByteCount，核对 Bitmap 实际分配容量用 getAllocationByteCount。依据为 Android《Bitmap API reference》。

**Q4: [done] Bitmap 复用为什么可能让实际占用高于当前像素量？**

Bitmap 复用不会让内存逐次增长；大 Bitmap 被复用为较小结果时，当前像素量会下降，但底层分配容量不会自动缩小。若该对象留在缓存或 BitmapPool 中，较大的容量仍计入内存占用。

1. **何时发生：**使用 inBitmap 或 BitmapPool，且较大容量被较小图片复用时会出现。是否常见取决于图片尺寸分布和池策略；不是每次复用都会发生。
2. **如何发现：**记录 Bitmap 的宽高、配置、getByteCount 和 getAllocationByteCount；两者差距较大时，用 Profiler 查找持有者，见下一题。
3. **如何优化：**按目标尺寸解码；对象池的容量限制与清理时机见 Q6。若大容量 Bitmap 仍被界面持有，先替换它，确认不再使用后再释放。

依据为 Android《Bitmap API reference》《BitmapFactory.Options》和 Android Developers《Managing Bitmap Memory》。

**Q5: [done] Android Studio Memory Profiler 怎样判断 Bitmap 由谁持有？**

抓取堆转储后，查看 Bitmap 实例的引用链，找出仍持有它的界面、缓存或对象池：

1. **抓取快照：**在目标页面显示时，以及离开页面或清理缓存后分别抓取 Heap Dump，便于对比哪些 Bitmap 仍存活。
2. **查看引用：**筛选 Bitmap 类并选择实例，在 References 中沿引用链回溯：ImageView/Drawable 通常指向界面图片；缓存容器指向缓存项；BitmapPool 实现指向待复用对象。
3. **判断归属：**同一 Bitmap 可能同时被多个对象引用。离开页面后仍由旧 View 持有，需查生命周期清理；由缓存或对象池持有则检查其容量和淘汰策略。Android 7.0 及以上还可查看实例的 Native Size。

依据为 Android Studio《Capture a heap dump》和 Android《Bitmap API reference》。

**Q6: [done] 如何限制或清理过大的 Bitmap 闲置对象？**

按字节数管理缓存和对象池，并在 UI 隐藏或系统提示后台内存压力时淘汰可重建的闲置 Bitmap：

1. **常态限制：**为缓存和对象池设容量上限；超限时优先移除过大、较少复用的闲置对象，并选择容量接近目标的 Bitmap。
2. **内存压力：**在 ComponentCallbacks2.onTrimMemory 收到 TRIM_MEMORY_UI_HIDDEN 时释放仅供 UI 使用的缓存；收到 TRIM_MEMORY_BACKGROUND 时进一步清理可快速重建的资源。
3. **安全释放：**库管理的 Bitmap 使用库提供的清理接口；自行管理的 Bitmap 先从 View、缓存和对象池解绑，确认不再使用后才可 recycle，避免释放仍在绘制的像素。

依据为 Android《ComponentCallbacks2》、Android《Bitmap API reference》和 Android Developers《Managing Bitmap Memory》。

**Q7: [done] Bitmap 像素数据为什么放在 Native Heap，而不是 Java Heap？**

Bitmap 的 Java 对象一直在 Java 堆；Android 8.0（API 26）起，普通软件 Bitmap 的大块像素缓冲由 Native Heap 管理。分开放置减轻 Java 堆压力，但不减少进程总内存，因此 Java 堆有空余也不能证明 Bitmap 内存充足。

1. **版本演变：**Android 2.3.3 及以下像素在原生内存，且释放时机不够可预测；Android 3.0 至 7.1 移入托管堆；Android 8.0 起普通软件 Bitmap 再由 Native Heap 管理。
2. **职责分层：**Java 层的 Bitmap 是轻量包装对象，保存尺寸、配置和 native 指针；像素是连续的大块原始数据，由原生图形代码解码、读写和绘制。让像素留在原生侧，可由实际使用它的原生实现直接处理，避免把大块像素当作 Java 数据管理。
3. **生命周期衔接：**Bitmap 通过 NativeAllocationRegistry 向 ART 登记原生分配大小和释放函数。包装对象不可达后，运行时可在回收过程中释放对应像素缓冲，并把原生分配纳入内存压力判断；释放不保证与对象变得不可达同时发生。
4. **收益与诊断：**像素缓冲不占 Java 堆配额，但仍占进程内存，Native Heap 过高同样可能导致 OOM。排查时结合 Bitmap 的 getAllocationByteCount、原生分配统计和进程内存；HARDWARE Bitmap 使用图形缓冲区，也不计入普通软件 Bitmap 的 Native Heap 像素缓冲。

依据为 Android Developers《Bitmaps and memory》及 Android 8 Bitmap 实现。具体设计动机是根据实现归纳；官方资料主要描述内存位置与管理方式。

**Q8: [learning] BitmapFactory 为什么先用 inJustDecodeBounds 读尺寸？**

它用于先读取尺寸而不分配像素：

1. **预读：**设置 inJustDecodeBounds 后，BitmapFactory 读取图片头并填充 outWidth、outHeight，不返回已解码的 Bitmap。
2. **计算：**根据源宽高和显示目标选择采样倍率。
3. **解码：**对同一内容进行正式解码，避免先完整解码再决定输出尺寸。

依据为 Android《BitmapFactory.Options》。

**Q9: [learning] inSampleSize 怎样改变 Bitmap 的输出尺寸？**

inSampleSize 控制 BitmapFactory 输出采样倍率：

1. **采样为 2：**宽、高大致各减半，像素数约为四分之一。
2. **非 2 的幂：**向下取最近的 2 的幂，例如设为 3 通常按 2 处理。
3. **最终尺寸：**格式取整与资源密度缩放可能改变宽高，应检查返回的 Bitmap。

依据为 Android《BitmapFactory.Options》。

**Q10: [learning] 怎样按目标尺寸选择采样与精确缩放？**

按目标显示方式决定采样和缩放：

1. **确定目标：**同时比较源图和目标的宽、高，并确认完整显示还是允许裁切。
2. **粗采样：**按两轴共同可满足的倍率减少解码像素。只看一轴可能使另一轴不足或过大。
3. **精确缩放：**再贴合控件目标尺寸，避免先完整解码大图再生成缩略图。

依据为 Android Developers《Loading Large Bitmaps Efficiently》和 Android《ImageDecoder》。

**Q11: [learning] 图片的 Exif 方向为什么会影响采样验收？**

Exif（Exchangeable Image File Format）方向标签说明显示时如何旋转像素，因此文件头宽高可能与最终视觉方向不同。采样验收应：

1. **先定方向：**把方向标签纳入目标宽高计算，避免横向文件头对应竖向显示时选错倍率。
2. **再验输出：**检查旋转后的可见宽高和清晰度。

依据为 AndroidX《ExifInterface》。

**Q12: [learning] drawable 密度缩放怎样影响 BitmapFactory 采样结果？**

资源解码包含采样与密度缩放两步：

1. **采样：**inSampleSize 先缩小源图。
2. **密度缩放：**inDensity 与 inTargetDensity 可能再改变输出尺寸，因此不能只用源宽高除以采样倍率推算结果。
3. **是否关闭：**应用按源像素控制输出时，可评估关闭 inScaled。普通密度适配资源通常保留默认缩放。

调整后检查资源目录、设备密度、返回宽高与画面大小。依据为 Android《BitmapFactory.Options》。

**Q13: [learning] inPreferredConfig 设为 RGB_565 就能省一半内存吗？**

不能保证。inPreferredConfig 只是请求的首选项，解码器可能返回其他配置。评估 RGB_565 时需同时检查：

1. **内存：**RGB_565（Red、Green、Blue）用 16 位表示不透明像素，理论像素字节约为 ARGB_8888 的一半。
2. **画质：**渐变和暗部可能出现色带，且不适合需要透明度的图像。
3. **结果：**核对返回配置和 allocationByteCount，不能只看请求值。

依据为 Android《BitmapFactory.Options》和《Bitmap.Config》。

**Q14: [learning] 图片只需要透明遮罩时，为什么不一定要保存完整颜色通道？**

只有业务确实只消费透明度时，单通道遮罩才可能减少颜色通道占用：

1. **配置：**Bitmap.Config.ALPHA_8 每像素 1 字节。
2. **限制：**普通图片解码是否返回 ALPHA_8，不能从源文件推定。
3. **验收：**显式处理遮罩后，检查实际输出配置与后续绘制效果。

依据为 Android《Bitmap.Config》。

**Q15: [learning] RGBA_F16 何时值得承担更高内存成本？**

RGBA_F16（Red、Green、Blue、Alpha 各 16 位浮点）每像素 8 字节，约为 ARGB_8888 的两倍。是否值得使用取决于：

1. **精度需求：**解码结果和屏幕确需保留高精度或宽色域时才考虑。
2. **内存预算：**1280 × 720 像素约需 7.03 MiB，ARGB_8888 约需 3.52 MiB。
3. **实际输出：**源文件支持宽色域不保证返回 RGBA_F16，应核对 config、colorSpace 与分配量。

依据为 Android《Bitmap.Config》和《ImageDecoder》。

**Q16: [learning] 预乘 alpha 对 Bitmap 处理有什么边界？**

预乘 alpha 会先把颜色通道乘以透明度，使 View/Canvas 混合时使用已关联的颜色值。处理像素时要区分：

1. **按预乘值绘制：**透明边缘可按预期参与混合。
2. **直接使用非预乘值：**若误当成预乘结果，边缘可能变色。
3. **需要原始通道值：**核对 BitmapFactory 的 inPremultiplied 设置和实际消费路径。该解码器默认返回预乘像素。

依据为 Android《BitmapFactory.Options》。

**Q17: [learning] 需要读写 Bitmap 像素时怎样选择分配方式？**

后续消费方决定解码结果：

1. **读取像素或画到软件 Canvas：**选择软件 Bitmap。硬件 Bitmap 不支持 getPixel，也不能直接画到软件 Canvas。
2. **修改像素：**除软件结果外还须请求可变 Bitmap，硬件分配器不能与 setMutableRequired(true) 同用。

3. **避免事后复制：**把硬件图复制为软件图会增加一份像素和复制成本。依据为 Android《ImageDecoder》和《Bitmap API reference》。

**Q18: [learning] Hardware Bitmap 等于 GPU 直接解压图片吗？**

不等于。Config.HARDWARE 描述像素最终存放在图形缓冲，不规定压缩数据由谁解码。应分开看这几项成本：

1. **解码：**CPU（Central Processing Unit）或其他实现处理压缩数据。硬件配置本身不证明由 GPU（Graphics Processing Unit）解码。
2. **准备：**建立图形缓冲并上传像素仍可能耗时。
3. **验收：**分别测量资源就绪和首次显示。

依据为 Android《Bitmap.Config》和 AAOS（Android Automotive OS）13 ImageDecoder 实现。

**Q19: [learning] ImageDecoder 的默认分配器保证硬件 Bitmap 吗？**

不保证。Android 9 起，ALLOCATOR_DEFAULT 由解码器选择，可能返回软件 Bitmap。按消费方式判断：

1. **只读显示：**可先使用默认分配器，再检查返回配置。
2. **CPU 访问像素或要求硬件结果：**明确选择合适分配器，并确认解码条件允许。

依据为 Android《ImageDecoder》。

**Q20: [learning] ImageDecoder 的共享内存分配器省掉了什么？**

ALLOCATOR_SHARED_MEMORY 让像素适于进程间共享，影响的是数据传递方式，不会免除像素内存：

1. **有跨进程消费方：**评估共享分配器能否减少复制与传递成本。
2. **单进程 ImageView：**通常没有共享需求，启用前应验证内存收益。

依据为 Android《ImageDecoder》。

**Q21: [learning] ImageDecoder 怎样设置最终输出尺寸？**

在 OnHeaderDecodedListener 中读取源尺寸，并在分配像素前选择一种目标尺寸设置：

1. **setTargetSize：**指定输出宽高。
2. **setTargetSampleSize：**指定输出采样倍率。
3. **调用顺序：**两者控制同一目标尺寸，后调用的设置覆盖前者，不会叠加。目标大于源图只增加像素，不会增加细节。

检查返回宽高，避免先完整解码再缩图。依据为 Android《ImageDecoder》。

**Q22: [learning] ImageDecoder 的 setCrop 何时不能替代区域解码？**

setCrop 裁剪的是解码输出，不保证只解码源文件的局部。按需求选择：

1. **只需改变最终画面边界：**使用 setCrop。
2. **超大源图只显示局部：**评估 BitmapRegionDecoder，按源图区域解码，避免保留整图像素。
3. **小图或仍需整图：**区域解码会增加实现复杂度，应比较峰值后再选。

依据为 Android《ImageDecoder》和《BitmapRegionDecoder》。

**Q23: [learning] ImageDecoder 的低内存策略会牺牲什么？**

MEMORY_POLICY_LOW_RAM 允许解码器在适合时选择更省内存的像素配置，可能降低颜色精度：

1. **它能做什么：**在解码器认为合适时减少像素配置成本。
2. **它不能保证什么：**不会固定减半，也不能代替缩小输出尺寸。
3. **怎样验收：**比较返回 config、分配量与目标屏幕画质。

依据为 Android《ImageDecoder》。

**Q24: [learning] 图片数据不完整时，ImageDecoder 应怎样处理？**

默认把截断或损坏视为解码失败。仅当业务接受不完整画面时才使用 OnPartialImageListener：

1. **可继续：**明确允许部分图像展示，并把结果标记为不完整。
2. **应失败：**网络数据尚未接收完整或文件永久损坏时，不把部分结果当作完整资源。

依据为 Android《ImageDecoder》。

**Q25: [learning] ImageDecoder 的后处理为何可能增加峰值成本？**

setPostProcessor 在解码和缩放后处理像素，可能增加 CPU 工作与临时资源：

1. **控制输出：**固定效果可在较小结果上完成时，先设合理目标尺寸。
2. **测量峰值：**观察解码和后处理期间的内存，不能只用最终 Bitmap 字节代表处理上限。

依据为 Android《ImageDecoder》。

**Q26: [learning] 区域解码的坐标为什么必须回到源图？**

BitmapRegionDecoder 接收的区域矩形使用源图像素坐标，View 坐标不能直接传入：

1. **换算：**把经过缩放和平移的屏幕可见范围反算到源图坐标。
2. **裁边：**将矩形限制在源图范围内。
3. **采样：**按显示倍率选择采样参数，避免解错区域或越界。

依据为 Android《BitmapRegionDecoder》。

**Q27: [learning] 多线程共用一个 BitmapRegionDecoder 能并行解码吗？**

不能直接假设。AAOS 13 的 BitmapRegionDecoder 实现用锁保护同一原生解码器，因此同一实例上的请求会串行：

1. **增加线程：**可能只增加等待，不能让同一实例并行解码。
2. **增加实例：**可能增加内存和输入读取成本。
3. **选并发数：**在目标 Android 版本测吞吐与峰值内存。

依据为 AAOS 13 BitmapRegionDecoder 实现。

**Q28: [learning] BitmapRegionDecoder 的格式支持为何要按平台版本核对？**

支持列表随平台演进，需区分参考文档和目标设备：

1. **AAOS 13 参考实现：**列出 JPEG、PNG、WebP 和 HEIF。
2. **当前 Android API（Application Programming Interface）参考：**还列出 AVIF，不能据此推断 Android 13 或所有厂商设备都支持。
3. **应用验收：**用目标设备解码实际文件，并准备失败回退。

依据为 Android《BitmapRegionDecoder》与 AAOS 13 参考资料。

**Q29: [learning] inBitmap 复用要满足什么条件，失败后怎样处理？**

候选 Bitmap 必须可变，且容量与平台版本的规则匹配：

1. **Android 4.4 起：**候选 allocationByteCount 足够即可跨尺寸复用。
2. **更早版本：**要求 JPEG 或 PNG、相同尺寸且 inSampleSize 为 1 等更严格条件。

采样与密度缩放后的输出决定所需容量。复用失败时按以下步骤回退：

1. **移除候选：**不合适的 Bitmap 可能导致 IllegalArgumentException。
2. **重新解码：**不再传入该候选，按正常路径解码。
3. **核对结果：**无论是否复用，都检查返回 Bitmap 的配置和分配量。

依据为 Android《BitmapFactory.Options》。

**Q30: [learning] 为什么不能回收仍被界面引用的 Bitmap？**

recycle 会使像素存储不可再安全使用。释放前应确认所有权和引用状态：

1. **业务自有 Bitmap：**确认所有消费者已结束后再释放。
2. **仍被 View 或图库引用：**不要回收，否则后续绘制可能失败。
3. **图片库管理资源：**通过目标生命周期归还，不由业务直接 recycle。

依据为 Android《Bitmap API reference》和 Glide 4《Resource Reuse》。

**Q31: [learning] 动态图片为什么不能按首帧 Bitmap 估算内存？**

Android 9 起，ImageDecoder 提供两类不同结果：

1. **decodeBitmap：**返回静态 Bitmap。
2. **decodeDrawable：**对受支持的 GIF（Graphics Interchange Format）或动态 WebP 返回 AnimatedImageDrawable。
3. **播放内存：**除当前帧外还可能有组合缓冲和待解码数据，取决于帧尺寸、变化区域和缓存策略，不能简单乘总帧数。

应分别测首帧、持续播放和多图同播峰值。依据为 Android《ImageDecoder》和《AnimatedImageDrawable》。

**Q32: [learning] 动态图片离开可见区为什么要停止播放？**

不可见动画仍可能触发帧调度、解码和绘制，占用 CPU 与像素缓冲：

1. **离开可见区或页面停止：**停止 AnimatedImageDrawable。
2. **重新可见：**按页面与列表状态恢复播放。
3. **生命周期注意：**只移走 View 不会自动取消播放。依据为 Android《AnimatedImageDrawable》。

**Q33: [learning] 同页多图的内存预算应包含哪些对象？**

按同时存活的对象计，不按可见图片数或 URL（Uniform Resource Locator）数计：

1. **活动结果：**可见图及仍被目标引用的 Bitmap，同一对象被多目标引用只计一次。
2. **缓存与池：**内存缓存保留可再次展示的结果，BitmapPool 保留可重写的空闲容量，两者都占内存。
3. **不同结果：**同源图按不同尺寸、配置或变换可能生成多份 Bitmap。
4. **在途工作：**并发解码、变换输入输出与临时缓冲。

5. **核对占用：**用各 Bitmap 的 allocationByteCount 核对像素容量，再用进程峰值观察其他原生和图形分配。依据为 Android Developers《Managing Bitmap Memory》和 Glide 4《Caching》。

**Q34: [learning] 怎样验证减少解码并发确实降低了峰值内存？**

按相同条件对照并发调整前后：

1. **固定条件：**使用相同图片集、目标尺寸、缓存状态和滚动路径。
2. **观察指标：**比较峰值内存和首图可见时间。
3. **判断限流：**峰值下降但关键图排队明显变长，说明并发限制过度。
4. **调整顺序：**先缩小输出并取消过期工作，再调并发上限。

依据为 Android Developers《Loading Large Bitmaps Efficiently》。

**Q35: [learning] 图片导致 OOM 时应先查哪类证据？**

OOM（Out Of Memory）排查应先找最大同时存活的像素，再核对相关分配：

1. **单图：**检查源尺寸、输出尺寸、像素配置和 allocationByteCount。
2. **并发与缓存：**统计活动、缓存和在途 Bitmap 数量。
3. **进程内存：**同时检查原生与图形分配。
4. **优先修复：**若压缩文件小而输出过大，先修目标尺寸和请求生命周期。

依据为 Android Developers《Managing Bitmap Memory》。
