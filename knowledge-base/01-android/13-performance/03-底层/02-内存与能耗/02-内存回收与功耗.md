# 内存回收与功耗硬件

应用与系统服务如何使用这些机制见 [进程、启动与 ART](../../02-系统/02-进程与运行时/02-进程启动与ART.md) 及 [系统调度、电源与温控服务](../../02-系统/03-调度与能效/03-调度电源与温控.md)。

**Q1: [learning] AppFlow 论文把 GB 级应用冷启动当成什么问题？为什么“只加文件预读”可能反而变慢？**

AppFlow（《AppFlow: Memory Scheduling for Cold Launch of Large Apps on Mobile and Vehicle Systems》，arXiv:2603.17259 预印本，已被 MobiCom 2026 接收；非 AOSP 主线）把大型应用冷启动拆成三类相互影响的成本：CPU 与调度、文件 I/O、内存分配与回收。论文提出三项协调机制：

1. **启动前预读：**按文件访问频次，在预算内选择预读集合；论文将每个应用的文件大小分界建模为 multiple-choice knapsack，并使用全局 100 MB 预算。
2. **启动中读取：**对大文件采用吞吐优先的读取策略。
3. **内存压力下的进程选择：**结合内存压力与进程上下文选择可终止的后台进程。

这些方案分别应对进程创建、类加载与初始化，APK/DEX/SO/资源不在 page cache 导致的 major fault，以及分配触发 kswapd、direct reclaim 与 swap 等成本；论文评测结果不等于 Android 平台承诺。

“只加预读”可能更慢的原因是预读与回收互相抵消：预读占用的 page cache 在低内存下会被回收，论文测得预读页被回收后启动 I/O 延迟增至 6.4 倍。其 ablation 也显示只开 Selective File Preloader 时 cold relaunch 数增加 30%。因此它修改了内核回收路径（按窗口进入 file-first、经 /proc 清单把预加载页标为 active 暂不逐出、每 10 秒刷新活跃度），并约束进程终止只能给系统原本允许终止的候选重新排序，导航、通话、音频等可感知进程不得因预测分数低而被杀。证据边界要守住：128KB 文件分界、100 MB 预算、最多 66.5% 冷启动下降等都来自论文设备与应用集合（Pixel 7/8 与 Raspberry Pi 4B 车载试验台、Android 15 基线），论文未公开完整 Framework/kernel patch，也未进入 Android 17 主线——材料核对的 android17-6.18 vmscan.c 没有预加载清单或启动窗口，这些只能当待验证假设。

**Q2: [learning] 低内存的性能损失为什么没有固定顺序？不同页面的回收成本差在哪？**

分配遇到压力后走哪条路径由页类型与设备配置决定：

1. **clean file page：**直接丢弃，再访问时 refault 需要重新读文件。
2. **dirty file page：**先回写，付出写入延迟与存储竞争。
3. **匿名页：**换入 ZRAM，付出压缩/解压 CPU 与 swap-in 延迟。
4. **高阶连续页：**可能触发 compaction 后重试。
5. **direct reclaim：**分配线程可能同步进入回收，直接损失执行时间。

判断时避免两种误判：

1. direct reclaim 不一定产生存储 I/O；clean 页可丢弃，匿名页在常见配置下进入 ZRAM，因此“回收等于读盘”不成立。
2. 主线程处于 D 状态不等于正在等待回收；要用 direct reclaim 事件或内核调用栈确认等待对象。

把 vmscan、block I/O、refault 与线程状态放在同一段 trace 里核对先后与因果。

**Q3: [learning] ZRAM、MGLRU 和回收事件观测有哪些设备与版本边界？**

ZRAM 评估应成对比较以下指标：

1. pswpin/pswpout、ZRAM 占用与压缩效率。
2. memory PSI、direct reclaim 与 kswapd 时间。
3. swap-in 后的启动与切换延迟。
4. 压缩线程 CPU 与功耗。
5. lmkd kill 与缓存进程存活。

只提高压缩比可能增加 CPU，只加容量可能挤占未压缩内存。page-cluster 控制一次换入预读的相邻页数；16 KB 页设备上同一值覆盖更大字节范围。配置节点是否可用取决于内核，评估指标（mm_stat 口径）见 [../../07-memory-storage/01-memory-management.md](../../../07-memory-storage/01-memory-management.md)。

MGLRU 用 generation 记录页面热度。是否启用要读 `/sys/kernel/mm/lru_gen/enabled` 并核对设备配置；评估关注 refault、scan/steal、direct reclaim、PSI 与冷启动回访。generation 的 bitmask 随内核版本变化，不当作常量。

回收事件观测有版本边界：材料按 Android 17 核对，lmkd 优先用 BPF 库 libmemevents 订阅回收事件，失败时回退 vmstat，并已删除旧版 Perfetto 的 mm_events 常驻 probe。AAOS13 树的 system/memory/libmeminfo 中没有 libmemevents，lmkd 通过轮询 vmstat 获取回收状态。具体设备以镜像为准，不把某一版的观测设施写成平台通用结论。

**Q4: [learning] minor fault 和 major fault 的计数边界在哪？为什么不能用 Δfaults × 4 KB 估算分配字节？**

minor fault 指内核成功完成、最终不带 `VM_FAULT_MAJOR` 且处理过程中没有 retry 的缺页，常见来源是匿名页按需分配、写时复制（COW）和“页缓存已有数据、只需建立 PTE”。major fault 指成功完成但带 `VM_FAULT_MAJOR` 或发生过 retry 的缺页，对应文件页读入与 zRAM/后备存储的 swap-in。计数时机有三处差异（材料按 Android 17 与 6.18 内核核对，本地 AAOS13 树无内核目录）：Simpleperf 的 `page-faults` 在 arm64 校验 VMA 之前计数，包含后来失败的访问。`min_flt`/`maj_flt` 在 `handle_mm_fault()` 成功返回后才记账，`VM_FAULT_ERROR`（最终 SIGSEGV/SIGBUS 的失败访问）不进入任何 fault 计数——所以 `page-faults` 与 minor+major 之和出现差值是有源码依据的，排查时同时检查失败访问、统计区间和工具权限。

换算陷阱有四个：Android 15 起存在 16 KB 页设备，页大小必须运行时查询（`Os.sysconf(OsConstants._SC_PAGE_SIZE)` 或原生 `getpagesize()`），4 KB 只是旧默认。minor fault 还包含 COW 与页缓存映射，同一虚拟区域被回收后再次访问会再 fault。分配器复用已驻留的堆页时，发生分配却没有新增 fault。readahead 和大 folio 让一次 major fault 与一页 I/O 失去一一对应。fault 计数是同步异常的次数，不等于阻塞时间。major 增长只有与关键线程等待存储在同一时间段出现，才支持“I/O 影响关键路径”的判断。改进手段按原因选：冷启动文件页查 Baseline Profile 覆盖与编译产物布局，匿名页/COW 查初始化时机与 Zygote 继承页写入，swap-in 查内存压力与 zRAM 配置。`madvise(MADV_WILLNEED)` 只是把等待前移的提示，不保证读入或保留页面。

**Q5: [learning] IPowerStats 能提供什么能耗读数，硬件轨道有哪些边界？**

Android 的 `IPowerStats`/PowerStats HAL 可暴露设备实现的 energy consumer 与 energy rail，读数是对应硬件部件在采样区间内累计的能量（常见单位 µWs）。轨道名称和覆盖范围由设备实现决定，并非所有 SoC 都提供 GPU、NPU、显示或内存 rail；量产设备缺少 rail 时应记为不可用，不能以估算值补齐。电池电流与电压是整机读数，会把屏幕、调制解调器和后台任务一并计入，且 USB 充电可能改变电量计数语义。

PowerStats HAL 的可用数据、权限和 App 可访问边界见[工具侧 PowerStats 说明](../../04-工具/README.md)。整机电流积分、基线扣除、随机化与 race-to-idle 能耗实验属于测量方法，不在本题展开。
