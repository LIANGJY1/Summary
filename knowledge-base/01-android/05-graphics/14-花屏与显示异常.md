# Android 花屏与显示异常诊断

> 范围：Android/AAOS 画面出现错块、条纹、撕裂、颜色异常或短暂错误帧时的分层诊断。图形链路与工具行为依据 AOSP《Graphics》《SurfaceFlinger and WindowManager》《Hardware Composer HAL》《Synchronization framework》《Color management》《Winscope》及 Android 多屏文档。设备侧显示链路须按目标硬件实现核对。

**Q1: [learning] 花屏图案像紫蓝色法线贴图时，怎样确认包内资源是不是运行时显示的那张图？**

![图片](../../_assets/%E8%8A%B1%E5%B1%8F%E5%9B%BE%E6%A1%88%E5%83%8F%E7%B4%AB%E8%93%9D%E8%89%B2%E6%B3%95%E7%BA%BF%E8%B4%B4%E5%9B%BE%E6%97%B6-%E6%80%8E%E6%A0%B7%E7%A1%AE%E8%AE%A4%E5%8C%85%E5%86%85%E8%B5%84%E6%BA%90%E6%98%AF%E4%B8%8D-e813164b642d70396f3960a43b31f29445e6e0ef5a7c6995c6d5c5f667ce9d32.png)

法线贴图是供材质着色器读取表面法线方向的纹理，常用 RGB 编码切线空间法线向量；接近朝外方向的编码常呈紫蓝色。屏幕上出现相似纹理只能说明它是候选资源，不能证明资源被运行时使用，更不能单独证明它导致花屏。

确认资源与画面的关系要逐步补齐证据：

1. **确认资源存在：**先用匹配版本的资源工具解析 Kanzi 包并查资源名、材质引用和贴图类型。工具不可用时，可用字符串和 PNG/JPEG 文件头扫描作线索，但这类扫描只覆盖可识别的嵌入图像，不能证明专有或压缩纹理都已提取。
2. **比较图像内容：**把异常区域校正透视、裁去屏幕边框，再比较纹理结构、关键局部和 UV 岛排列。颜色相似或都像毛发不算同图证据。渲染结果经过缩放、裁切、旋转、UV 映射和着色后，也不一定能与原图逐像素相等。
3. **确认运行时绑定：**从 Kanzi 页面、Prefab、材质到贴图追踪引用，并在异常发生时记录实际加载的资源、材质和 Surface。包里存在一张图片，不代表当前页面或当前设备配置会使用它。
4. **确认故障边界：**比较贴图采样前的源图、材质采样结果、应用提交 buffer 与系统/外部画面。若提交 buffer 已包含错误纹理，继续查资源绑定、UV 和 shader；若 buffer 正常而物理屏异常，调查下游合成与显示链路。

因此应分别回答“资源包里有没有”“运行时有没有引用”“异常帧是否由它生成”三个问题。前一个问题成立不能代替后两个问题。



**Q2: [learning] Android 用户说“花屏”时，为什么不能直接判断是 GPU 或屏幕硬件故障？**

“花屏”是对可见异常的描述，不是 Android 的错误码或单一故障类型。相同视觉结果可由错误像素、图层几何、同步时序、显示合成或物理输出造成。先把现象写成可观察条件，才能选择正确的证据入口。

1. **像素内容错误：**固定区域出现错色、错行、马赛克或上一帧残影。先判断该区域属于应用窗口、独立视频层还是整屏。
2. **几何与层级错误：**内容本身完整，但被错误裁剪、旋转、拉伸、错位或短暂盖住。优先检查窗口与 SurfaceFlinger layer 状态。
3. **时间异常：**横向断裂、闪一下旧帧或间歇黑帧。记录持续时间、是否只在动画和刷新率切换时出现，避免把掉帧、撕裂和坏像素混称一类。
4. **物理输出异常：**整个显示器持续彩线、噪点或重影，甚至 Android 尚未启动时也存在。应把显示控制器之后的链路纳入调查，而不是只查应用绘制。

单张照片只能描述某一时刻的外观。故障归因还需要同一时间窗的画面、图层状态和显示侧证据。



**Q3: [learning] 花屏复现记录至少需要哪些条件，为什么“偶发一次”不能直接交给某一层修复？**

最小记录要能回答异常发生在什么设备、哪块屏、哪段画面和哪个状态转换中。缺少这些条件，团队无法把同一故障与视觉相似的其他故障区分开，也无法验证修复。

1. **设备与构建：**记录机型、SoC、Android/AAOS 构建、显示驱动版本、应用版本及受影响物理屏。多屏设备不要只写动态分配的 displayId，补充稳定显示标识或物理端口。
2. **触发与范围：**记录冷启动、旋转、唤醒、切应用、播放视频、倒车画面或刷新率切换等触发点，以及是否只有一个区域、一种内容或一块屏异常。
3. **时序与频率：**保存出现前后的时间点、持续帧数或时间、可复现次数，以及热机、温度、电源和负载条件。偶发故障应保留失败样本及相同条件的正常样本。
4. **并行证据：**尽量同步录外部摄像机画面、系统截屏或录屏、应用日志、SurfaceFlinger/Winscope 状态与 Perfetto trace。每份证据标注采集时刻和它观察的链路边界。

先固定触发条件再做单变量对照。未经对照就改 GPU、HWC 或面板参数，会让症状变化与修复效果无法区分。



**Q4: [learning] 花屏排查如何按“像素从哪里产生到哪里显示”建立故障边界？**

对标准应用画面，可按“内容生产者 → 图形缓冲区及同步 → SurfaceFlinger 图层与合成 → Composer HAL/HWC → 显示控制器与物理链路 → 面板”追踪。每跨过一个边界，都要找到该边界前后的同一帧或同一状态，不能只凭进程名推断责任。

1. **生产者：**View/Compose 通常进入应用窗口缓冲，视频、相机、游戏也可能各自生产 Surface 缓冲。原始 buffer 已损坏时，下游正确显示仍会花屏。
2. **系统合成：**SurfaceFlinger 根据 layer 的 buffer、裁剪、变换、透明度和层级形成显示内容。像素完好但状态错误，也会看到错位或露底。
3. **设备合成：**HWC 逐帧决定哪些 layer 走 DEVICE、哪些走 CLIENT。格式、缩放、旋转和硬件 plane 能力会改变实际路径。
4. **物理输出：**合成提交之后仍有扫描输出、接口链路和面板处理。系统的 present fence 不等于面板每个像素已经正确发光。

这是定位模型，不表示所有设备都开放每个观测点。证据缺一层时，应把结论停在已观测的最后边界。



**Q5: [learning] 系统截屏正常而肉眼或外部录像可见花屏，能直接判定面板坏了吗？**

不能。截屏、录屏和物理屏观察的是不同路径。普通系统捕获可能重建或读取合成内容，受保护内容、硬件 overlay、厂商显示后处理和面板输出未必以同样方式进入捕获结果。

1. **系统截屏异常：**说明异常已进入该捕获路径，优先检查生产者 buffer、layer 状态和捕获合成。但截屏异常仍不能单凭一张图分清生产者与 SurfaceFlinger。
2. **系统截屏正常、外部录像异常：**把嫌疑范围扩大到捕获路径之外的 HWC、显示控制器、接口、面板，以及未进入捕获的受保护或设备侧 layer。还要核对两份证据是否确实取自同一帧、同一显示器。
3. **生产者自检图正常、系统截屏异常：**优先检查从 buffer 提交到图层合成之间的格式、同步和几何状态，但自检图是否读取了同一个实际 buffer 必须先确认。

Android 16 QPR2 引入可生产化的 DPU readback 能力，支持时可补充 HWC 输出附近的像素证据。它不是旧版本或所有设备都具备的通用截屏模式。受保护内容也不能为了排障而绕过安全限制。



**Q6: [learning] 为什么排查局部花屏前要先区分 View/Compose、TextureView 与 SurfaceView 的出图拓扑？**

三者的像素不一定经过同一个可见 SurfaceFlinger layer。找错 layer 会把“没有独立内容层”误判为“应用没有出帧”，也会把宿主窗口正常误判为视频内容正常。

1. **普通 View/Compose：**通常由宿主应用窗口生产最终 buffer。SurfaceFlinger 看到的是窗口层，不知道其中哪个具体控件画错。
2. **TextureView：**外部内容先进入应用进程的 SurfaceTexture，再由宿主渲染管线采样进窗口 buffer。通常没有与该 TextureView 对应的独立可见 SurfaceFlinger 内容层。
3. **SurfaceView：**有独立内容 Surface/layer，宿主 View 树主要管理其位置和可见性。内容 buffer 与几何 transaction 可能由不同节奏提交。

因此“只有视频区域花屏”应先确定承载方式。SurfaceView 查独立 layer、解码输出及 HWC 合成。TextureView 查外部 producer、SurfaceTexture 采样和宿主窗口绘制。普通控件查应用绘制与窗口 buffer。



**Q7: [learning] 应用窗口或游戏只有部分区域随机错块，怎样区分绘制错误、缓冲复用错误与合成错误？**

先锁定异常像素在实际提交的 buffer 中是否已经存在，再检查 buffer 生命周期和合成状态。视觉上的“随机”并不能证明 GPU 驱动错误，越界读取、未初始化内容、旧帧复用和错误裁剪也会呈现随机块。

1. **生产者侧验证：**在可调试场景记录同一帧的绘制输入、目标尺寸、裁剪、纹理/缓冲标识及提交时间。若生产者能安全读取同一实际 buffer，可比较提交前像素与异常捕获像素。
2. **生命周期验证：**核对缓冲是否在 GPU 或消费者仍读取时被改写、回收到池中或跨线程复用。重点检查 acquire/release fence 与资源所有者，不能只看 Java 对象是否还活着。
3. **合成侧验证：**同一帧比较 SurfaceFlinger 的 layer buffer、crop、transform、dataspace 和 HWC composition type。若内容正确而显示位置或颜色错误，转查图层与设备合成。

调试抓帧工具可能改变渲染后端或时序。异常只在量产构建出现时，应保留未注入工具的基线，并用同构建、同显示模式复测。



**Q8: [learning] 图像出现隔行错位、斜纹或绿紫色块时，怎样检查像素格式、stride 与 crop 契约？**

这类形态常提示“消费者按错误布局解释同一批字节”，但只是排查方向，不是症状到根因的唯一映射。要把生产者实际 buffer 的尺寸、格式、各 plane 布局、裁剪和消费者期待值逐项对齐。

1. **格式与位深：**确认实际是 RGB、RGBA、YUV 的哪种格式，位深及通道顺序是什么。不能仅凭一张绿色画面断言 U/V 反了。
2. **行与像素步长：**rowStride 可能大于可见宽度的字节数，YUV 各 plane 还可能有不同 pixelStride。按 width 直接连续拷贝每行会错行或把填充字节当像素。
3. **裁剪与旋转：**buffer 的物理宽高不必等于显示区域。检查 crop、变换矩阵、采样坐标和 chroma 对齐，区分源数据损坏与显示解释错误。
4. **跨组件传递：**相机、解码器、GPU、gralloc 和 HWC 可能支持的格式组合不同。只在某个分辨率或合成方式出现异常时，核对两端协商结果及设备能力。

Image.Plane 对 YUV_420_888 明确提供每个 plane 的 rowStride 与 pixelStride。不能假定所有 YUV_420_888 内存都按紧密 NV21 排列。



**Q9: [learning] 花屏伴随旧帧残影或画面撕裂时，acquire fence 与 release fence 分别该怎样检查？**

两类 fence 约束同一缓冲区的读写先后。acquire fence 告诉消费者生产者何时写完，release fence 告诉生产者消费者何时读完。忽略任一边界，都可能让一帧包含未完成或被过早覆盖的像素。

1. **提交到消费：**检查生产者是否把正确的 acquire fence 随 buffer 一起交出，SurfaceFlinger/HWC 是否在读取前等待它。queueBuffer 已发生只证明提交，不证明 GPU 写入已经完成。
2. **消费到复用：**检查旧 buffer 的 release fence 是否 signal 后才被重新写入。只看 buffer 回到可分配槽位，不足以证明所有设备读者都结束。
3. **时间关联：**把异常帧的 buffer id、frame number、fence signal 和 latch/present 时间对齐。fence 长时间未 signal 更像等待或卡帧，过早复用才支持内容破坏假设。

若没有同一 buffer 的标识与 fence 记录，只凭“像撕裂”不能认定是同步错误，也不能盲目加入全局等待作为修复。



**Q10: [learning] 短暂出现错误裁剪、重影或露底时，如何判断是 layer transaction 与 buffer 更新不同步？**

先在同一时间轴上看内容 buffer 与 layer 几何何时生效。应用可能提交了新位置、crop 或 z-order，却还没有供给匹配的新 buffer。反过来，新 buffer 也可能先于对应几何生效。两种情况会呈现不同的瞬时错画。

1. **识别层级：**在 Winscope 找到目标显示器、宿主层、SurfaceView 内容层及其父容器，确认异常区域实际由哪个 layer 覆盖。
2. **比较状态：**对照 requested 与 calculated 的 crop、transform、alpha、visible region 和 parent/leash：

    1. requested 已错时，追提交 transaction 的调用者。
    2. requested 正确而 calculated 错时，检查父链继承和遮挡。
3. **对齐内容：**记录异常帧附近的 buffer/frame number、transaction 与显示时间。若几何变化和内容交付分属两笔事务，检查是否需要在同一绘制边界协调提交。

静态 dumpsys 只给某一刻状态，无法证明一次闪屏的前后顺序。短暂异常应保留连续 layer/transaction trace 或录像。



**Q11: [learning] 只有特定图层组合花屏时，为什么要检查 HWC 的 DEVICE/CLIENT 合成选择？**

HWC 按当前帧的层数、格式、缩放、旋转、混合、受保护属性及硬件 plane 能力决定合成方式。某种组合只在 DEVICE 路径异常，可能把调查范围收窄到设备合成。只在 CLIENT 路径异常，则应检查 SurfaceFlinger 的 GPU 合成与 client target。但“切换后症状消失”本身仍不足以证明唯一根因。

1. **记录逐帧选择：**确认异常 layer 当时的 composition type、可见区域和输出显示器。不能拿正常时刻的 dumpsys 推断异常帧的路径。
2. **控制变量：**在可控测试环境只改变一个会影响合成选择的条件，如浮层、旋转或格式，同时记录 HWC 决策是否真的改变。改变 UI 也可能同时改变 buffer、时序和带宽。
3. **核对受保护内容：**受保护视频可能必须走受支持的安全硬件路径。它未进入普通截图或切换后变黑，不等于视频解码没有产生帧。

HWC 是设备相关实现。若 trace 只证明合成类型变化，后续仍需 vendor HWC、显示控制器或硬件读回证据确认具体失效点。



**Q12: [learning] 画面颜色异常但形状完整时，如何区分 YUV 转换、dataspace、HDR 与面板色彩问题？**

先找颜色第一次偏离已知测试图的位置。完整几何加系统性偏色通常提示颜色解释或变换不一致，但 YUV 范围、色彩矩阵、传递函数、色域、HDR 元数据和面板配置属于不同环节。

1. **源内容：**用可复现的灰阶、纯色和肤色样本，比对解码/相机输出的格式、YUV limited/full range 与矩阵。原始样本已偏色时，不应先改面板色温。
2. **图层元数据：**检查 buffer dataspace、像素格式、HDR 元数据和 SurfaceFlinger 选择的合成路径。内容按一种色域编码却被按另一种解释，会产生系统性偏色。
3. **显示输出：**检查当前 display color mode、HDR 能力、厂商色彩校准和是否经过设备侧处理。只有一块物理屏偏色时，不能忽略该屏的独立输出配置。
4. **对照实验：**比较 SDR 与 HDR、普通 UI 与视频、不同显示器及截屏与外部摄像机结果，每次只改一个条件并记录变化发生的边界。

调饱和度让肉眼“看起来正常”不等于修复契约。应让生产者标注与实际像素编码一致，并验证 HWC 与显示模式能正确解释。



**Q13: [learning] 视频或相机预览区域花屏而应用其他 UI 正常，排查入口为何不同于普通 View？**

视频与相机往往有独立的帧生产者、格式协商和 Surface 目标。其他 UI 正常只排除了部分宿主窗口问题，不能排除解码器、相机 HAL、缓冲转换或 HWC 对该内容层的处理。

1. **确定承载目标：**先确认 SurfaceView、TextureView、ImageReader 或应用自绘路径。SurfaceView 可独立合成，TextureView 会被宿主采样，ImageReader 可能还经过应用转换。
2. **确认源帧：**用同一 frame number 或时间戳比较解码/相机输出与送往 Surface 的内容：

    1. 源帧已坏时，优先查码流、解码或相机/ISP。
    2. 源帧正确时，继续查传递与显示。
3. **检查格式与寿命：**核对分辨率切换、YUV plane 步长、crop、颜色空间、Image/codec buffer 归还以及 fence。只在切分辨率时出现斜纹，优先检查新旧格式配置与缓冲尺寸是否配套。
4. **检查设备合成：**异常只在 overlay 或受保护播放出现时，记录 HWC composition type 与安全路径限制，再与普通内容对照。

MediaCodec 的 releaseOutputBuffer(render=true) 把帧交给输出 Surface，不等于该帧已经在面板上正确显示。



**Q14: [learning] 横向断裂与间歇卡一下怎样区分，FrameTimeline 能证明哪一种？**

画面撕裂是同一物理刷新中看见来自不同时间的画面部分。卡顿是预期帧没有按时呈现或上一帧被重复显示。两者可能同时发生，但单看 FPS 或 FrameTimeline 的 jank 标志不能证明物理撕裂。

1. **卡顿证据：**在 Android 12 及更高版本可用 FrameTimeline 对照预期与实际呈现时间，并结合应用、SurfaceFlinger 和 fence 时间找迟到环节。它主要解释帧时间与 jank 归属。
2. **撕裂证据：**需要外部高速录像、设备侧扫描输出/读回或其他能观察同一物理刷新内不同区域的手段。外部摄像机的滚动快门也可能制造横线假象，应通过不同拍摄设置和现场肉眼观察交叉验证。VSync 是降低中途更新风险的同步机制，但“存在 VSync 事件”不等于设备链路必无撕裂。
3. **共同原因排查：**刷新率切换、buffer 过早复用、显示控制器提交时序和高负载均可能改变两类现象。只有同一异常帧的时间与像素证据才能区分。

若录像只显示整帧停顿或重复，先按掉帧/卡顿处理，不要把“看起来断续”直接命名为撕裂。



**Q15: [learning] 花屏只在旋转、分辨率或刷新率切换时出现，应该核对哪些跨层状态？**

模式切换会同时改变显示配置、坐标变换、buffer 尺寸、合成选择和呈现节奏。故障若只在切换边界出现，应追踪旧配置何时失效、新配置何时生效，以及是否有一帧把两套状态混用。

1. **框架状态：**记录目标 display 的 active mode、逻辑尺寸、方向、窗口配置与 SurfaceFlinger 显示状态。不要只相信应用请求的帧率，实际模式由系统与设备决定。
2. **buffer 状态：**检查生产者是否按新尺寸、格式和 transform 重新配置，旧 buffer 是否仍被 latch 或用于新几何。
3. **HWC 与设备状态：**核对显示配置切换、client target 重新分配、HWC validate/present 结果和设备日志。外接屏 hotplug 还可能改变支持的显示模式。
4. **可视时间线：**外部录像与层级 trace 对齐切换点，判断是一帧过渡状态、持续错误配置还是物理链路重新训练期间的异常。

Android 13 起，系统在显示分辨率变化后会重新分配 client composition 的 framebuffer，但何时实际使用仍要结合该设备的 invalidate 与 HWC 路径验证，不能套用固定帧数。



**Q16: [learning] 系统截屏正常但整块物理屏持续彩线或噪点，如何把问题推进到显示控制器与面板链路？**

先证明上游交给显示设备的内容在相同时间窗内可复现地正确，再核对设备侧输出。持续彩线的候选包括显示控制器读 buffer、接口链路、面板时序、电源和面板本身，普通 Android trace 通常不能区分这些物理节点。

1. **跨状态观察：**比较开机 logo、Recovery 或其他不依赖目标应用的画面，以及不同亮度、刷新率、温度和电源状态。Android 启动前也异常会降低应用层故障的可能性。
2. **跨输出对照：**比较同一内容在另一块屏、外接显示或硬件读回上的结果。系统截图正常是线索，不是物理链路清白的充分证明。
3. **设备证据：**在具备权限与硬件支持的调试环境，检查 HWC/显示驱动日志、连接状态、错误计数器、显示控制器 CRC 或读回结果。具体节点名称和可用性由 SoC、内核与面板方案决定。
4. **定位边界：**若显示控制器读回正确而面板摄像画面异常，优先调查读回点之后的链路。若读回也异常，继续回溯 HWC 配置、输入 buffer 和显示控制器处理。

不要用重启暂时恢复就断定是软件问题。重启也会重新训练链路、重置面板和重新分配显示缓冲。



**Q17: [learning] AAOS 多屏或仪表出现花屏时，为什么必须先确定异常画面是否由 Android 渲染？**

车机主屏、副驾屏、仪表和倒车画面可能由不同进程、显示器、虚拟机或独立 ECU 生产。即使物理屏接在同一 SoC 上，也不能假定其全部像素都经过 Android 的应用窗口与 SurfaceFlinger。

1. **确认内容所有者：**区分 Android UI、独立相机/视频输入、安全域覆盖层和其他控制器送来的图像。可通过产品显示架构、目标显示的 layer 树和硬件输入拓扑验证。
2. **确认显示身份：**记录逻辑 displayId、稳定物理显示标识或端口、分辨率、刷新率与镜像关系。displayId 可能随热插拔和启动顺序变化，不能单独用它把故障绑定到某块物理屏。
3. **确认发生边界：**若 Android 截屏与 layer trace 都没有该画面，只能说明这些观察点没有覆盖它，不能断言画面不存在。应向对应渲染域或显示复用链路取证。
4. **确认影响范围：**仪表上的安全相关元素可能由与 Android 不同的高可用渲染路径负责。必须分别检查 Android 内容与安全元素，不把一者的正常当作另一者的证据。

AOSP AAOS 显示文档明确存在仪表由独立单元或非 Android 渲染的集成形式。具体量产车的责任边界以项目架构和实机证据为准。



**Q18: [learning] 花屏修复后怎样证明根因已消除，而不是只把画面暂时藏起来？**

修复要同时解释“原来哪一层违反了什么契约”和“修改后同一触发条件下为何不再违反”。只调大缓冲、强制 GPU 合成、延迟显示或重启组件可能缓解症状，也可能掩盖同步、格式或设备问题。

1. **保留前后证据：**用同一设备、构建、显示模式和触发脚本复现，对比异常像素、buffer/fence、layer transaction、HWC 路径及设备日志中与假设直接相关的指标。
2. **验证负面样本：**在原失败条件下重复运行到足够覆盖原故障概率，并测试临近边界，如旋转、分辨率、HDR、温度和多屏切换。零次复现只支持“当前条件未再观察到”，不能单独证明根因。
3. **确认副作用：**如果修复改变合成路径或增加等待，检查帧时间、输入延迟、功耗、受保护内容和其他显示器。画面正常但引入持续掉帧不算完整修复。
4. **归档可迁移结论：**记录失效契约、适用设备/版本、最小证据组合与不适用条件。具体项目的时间线、日志与硬件编号留在项目档案或问题复盘中。

最终结论应停在证据支持的层级。能证明“错误不在应用提交的 buffer”时，不要进一步无证据地写成“面板已坏”。



**Q19: [learning] 花屏只在完全下电冷启动出现，Launcher 重启不出现，而且复现概率不稳定，能据此判断什么？**

这组现象把调查重点指向冷启动独有的状态和时序，但还不能证明是 Kanzi Surface、GPU 驱动、静态资源或面板中的任何一项。完全下电再上电会重新经历系统和显示栈的启动，而只重启 Launcher 进程通常不会重置这些系统级服务与硬件状态；两种触发必须分开记录和对照。

先把两种触发做成可比较的实验：

1. **固定条件：**保持设备、软件构建、显示模式和外设一致，明确记录“完全断电再上电”与“仅重启 Launcher”的边界。记录每轮的 boot ID、系统 uptime、应用进程代际和 Kanzi Surface 创建/销毁序列。
2. **保留成对样本：**每次失败都保存异常前后的外部录像、可用的系统截图、完整 logcat 和 SurfaceFlinger/Winscope 状态；同样保存相同触发下未失败的样本。日志没有报错不能代替画面证据。
3. **逐个检验假设：**若应用或 Kanzi 初始化竞态成立，失败应与 Surface 创建、渲染启动、首帧或加载回调的相对顺序相关；若静态贴图本身错误，同一资源和场景更可能在多次运行中呈现相同缺陷；若系统截屏正常而外部画面异常，调查范围应向截屏未覆盖的 HWC、显示控制器和物理链路移动。
4. **量化复现率：**四次重启中三次失败仍只是小样本，既不能证明“必现”，也不足以证明第四次正常是修复。按冷启动和应用重启分别增加轮次，报告每种条件的失败次数、总次数和采集缺失情况。

一次只改变一个条件，例如等待 Surface 明确可用后再启动渲染，并观察失败率及对应时间线是否按假设变化。只要缺少异常帧或边界证据，结论就应停留在“冷启动相关、概率性故障”。



**Q20: [learning] 替换一张法线贴图后，异常页面图案也跟着变化，能证明什么？为什么 Kanzi 会把法线贴图显示出来？**

该对照强烈支持异常画面受这张贴图或其材质资源链路影响，排查重点应从“是不是相似图片”转到 Kanzi 场景、材质、shader 和实际纹理绑定。但单凭替换贴图仍不能断言它被直接当作屏幕颜色输出：贴图可能作为输入参与了材质计算，最终改变页面图案。

GPU 不知道一张纹理在美术语义上叫“法线贴图”。RGB 只是纹理数据；“把 RGB 当颜色显示”还是“解码成法线用于光照”，由材质属性、shader 代码及纹理槽绑定决定。若最终画面近似原始紫蓝贴图，优先验证：

1. **材质槽绑定错误：**法线纹理误连到了 Base Color/Albedo 或 Emissive 槽，或导入/运行时属性映射错位。预测：检查异常帧活动材质属性会看到该纹理进入颜色输出槽；仅更正绑定即可改变输出。
2. **shader 或变体不匹配：**材质使用了错误 shader、缺少法线贴图宏/变体，或 shader 参数布局与材质不一致，导致纹理采样结果未按法线解码，而作为颜色输出。预测：记录活动 shader/变体并对比正常冷启动；切换到已知正确的材质/变体后原触发下不再输出原始纹理。
3. **冷启动时资源/材质状态竞态：**首帧时纹理句柄、材质参数或 shader 资源未就绪/仍引用旧状态，后续初始化可能恢复。预测：失败样本与资源上传、材质绑定、shader 就绪及首帧的相对顺序相关；固定等待/同步边界后失败率应下降。
4. **调试或预览路径：**某个启动分支直接用纹理显示/预览节点绘制资源。预测：活动场景图中能找到采样该纹理并无光照输出的节点，且这种路径对应特定页面状态。

区分方法是在同一失败构建上一次只改一个变量：使用纯色或明显棋盘图替换该贴图；对照异常帧和正常帧的活动页面、材质属性、shader/变体、纹理槽/资源句柄及提交 buffer。若替换贴图只改变图案、页面布局和几何仍不变，说明该纹理影响了页面绘制；若输出像素近似纹理原始 RGB，才支持“按颜色直接输出”。当前项目还需拿到这些运行时状态，才能从上述机制中确认根因。
