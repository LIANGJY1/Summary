# 车控信号语义与状态闭环

> 本册讨论车辆信号从协议值到应用状态的转换，以及车控请求与反馈的边界。平台契约以 AOSP VHAL interface、property configuration 和 CarPropertyManager 文档为依据。项目例证来自 `Summary/project/yadi/git提交与缺陷分析/`，缺陷编号仅用于追溯该项目事实，不能当成通用协议定义。

**Q1: [learning] 车辆属性为什么不能只保存一个数值？**

车辆属性至少要同时处理值、状态、采样时间和区域。数值相同，不代表它在不同时间或区域仍是当前事实。AOSP VHAL 的 VehiclePropValue 包含 timestamp、areaId、status 和 value。当 status 不是 AVAILABLE 时，value 必须被忽略。

应用建立内部状态时要保留以下信息：

1. **值与单位：**先按信号矩阵或 VHAL 属性定义完成解码和量纲转换，再交给业务判断。
2. **状态：**区分 AVAILABLE、UNAVAILABLE、ERROR，以及应用额外定义的超时。不能让 0、全 1 位模式或任意合法数值兼任“无数据”。
3. **时间：**使用采样时间判断新鲜度，记录接收时间以诊断传输和排队延迟。回调到达时间不能替代采样时间。
4. **区域：**座椅、车窗、车门等区域属性要按 areaId 独立保存状态和超时，不可把某一区域的失效扩散到全部区域。

“最后一次有效值”可以另存为历史快照，但它不是当前值。项目中曾因超时或故障值覆盖该快照，恢复后继续向 3D 车模发送错误状态。保留快照时要同时记录其时间和失效原因。

**Q2: [learning] 信号超时后，界面何时保留旧值、显示占位符或显示故障？**

超时只证明当前观测失效，界面策略必须按信号的安全含义和用户可能作出的判断决定。将旧值画成当前值，或把超时画成合法的 0，都可能误导驾驶员。

决策按下列边界展开：

1. **允许短暂保留：**对低风险的历史或舒适功能，可保留最后值，但要明确标示数据已过期，并设定过期后清除或降级的条件。
2. **需要占位：**当前值不可确定、旧值会误导操作时，显示“--”或产品定义的未知态。例如未收到有效充电功率时，0 kW 会被误读为已确认没有充电。
3. **需要告警或禁用：**信号失效本身触发整车诊断或安全要求时，按已批准的故障策略显示并限制操作。不能由某个 UI 分支自行把所有超时定义为“车辆故障”。

控件的显示值与可操作性分开维护。置灰不应顺手重置用户设置，恢复可用也不等于旧值重新成为当前值。项目中的 SOC 清零、慢充滑条回默认值和充电状态误显示，都来自把这几种语义写在同一分支。

**Q3: [learning] 车控请求值与状态反馈值编码不同，应怎样避免混用？**

请求域和反馈域可能使用不同枚举、偏移和无动作码。业务层应先把两者分别转换成同一个语义状态，再做比较。不能用原始 int 跨方向直接相等判断。

转换边界包括：

1. **请求编码：**把语义操作转换为目标信号的命令值，并显式处理 NoAction、无效值和不支持的档位。
2. **反馈解码：**把状态信号的原始值转换为语义状态，遇到未知枚举要返回无效状态，不要默认选中某一档。
3. **协议改版：**检查发送映射、反馈解码、循环切换和显示映射是否都使用新版本的值域。只有代码同时适配两个方向，升级才算完成。

给整数常量加 `REQ_`、`STS_` 前缀有助于阅读，但两套常量仍同为 int，编译器不会阻止混用。若要在编译期隔离，需要不同类型或封装的转换接口。项目中的驾驶模式与座椅加热缺陷说明了方向和版本混用的后果，具体编码只对对应车型有效。

**Q4: [learning] UI 单位与车辆协议单位不同，收发两端怎样保证换算正确？**

每条边界只使用一种明确单位，并在接入层集中换算。先换算和验证原始数据，再钳制显示范围。先钳制会把量纲错误掩盖成看似合法的最大值。

收发路径分别核对：

1. **接收：**检查原始值的状态和无效码，按协议缩放系数转换为内部单位，验证目标值域，再交给 UI。不能把无效码钳成一个合法数字。
2. **发送：**把 UI 的语义目标转换为协议单位，检查舍入、溢出、步长和允许档位，再调用车控接口。协议入参名称或类型应显式表达单位。
3. **联调：**同一日志记录属性 ID、areaId、状态、采样时间、原始值及单位、归一化值及单位和请求关联标识。这样才能区分发送错误、回读错误与显示错误。

例如 UI 以 0.1 kW 为一档、协议以 W 为单位时，显示档位 33 对应 3300 W。项目中下发与回显曾分别遗漏换算，因此两个方向都要独立核对，不能因为一个方向正确就推断另一个方向正确。

**Q5: [learning] 超时标志与数据信号来自不同帧时，恢复阶段应立即读取缓存吗？**

不能一概立即读取，也不能一概等待下一个回调。两个帧有各自的采样周期和传输延迟，超时标志恢复只说明通信状态改变，不证明关联数据已经刷新。如果本地缓存曾被异常分支覆盖，单纯清除标志又可能一直保留错误状态。

恢复逻辑应按时间和来源裁决：

1. 标记超时状态已解除，但在收到新鲜的关联数据前继续把当前值视为待确认。
2. 比较关联数据的采样时间与恢复时间。只有数据时间满足接口定义的新鲜度条件，才发布为当前状态。
3. 若接口支持可靠的主动读取，可在后台读取权威源，并对返回值再次检查状态、时间和区域。若读取只会返回旧缓存，就等待该数据自己的下一次有效事件。
4. 设置有限等待超时。关联数据持续不到时维持未知态或进入产品定义的降级态，不能无限展示旧值。

项目中两个案例分别出现“过早读到旧缓存”和“恢复时未重取而持续显示旧状态”。它们对应不同的数据源条件，不能抽象成相反的两条通用指令。

**Q6: [learning] 车控 Set 返回成功后，应用需要怎样确认实际状态？**

先查接口对“成功”的定义。AOSP CarPropertyManager 的异步 Set 可选择是否等待属性更新。等待时，成功条件包含命令送达车辆总线及目标值被确认。不等待时，成功只表示送达总线。即使已看到属性更新，执行器是否完成动作仍取决于车辆接口契约。

按属性能力设计闭环：

1. **可读写状态：**订阅反馈并在进入页面时读取一次当前值，避免漏掉注册前的变化。关联本次请求、目标值、区域和超时，收到新状态后再清除 pending。
2. **只写命令或动作：**没有对应可读反馈时，不能强行要求每个 Set 都配套 Feed。按接口约定使用不等待属性更新的 Set 语义，并通过单独的结果事件、诊断状态或有限超时表达不确定性。
3. **其他入口修改：**车辆按键、另一屏幕或其他服务可能改同一状态。UI 的当前值应来自权威状态流，不能只在本页点击后更新。

项目中的充电上限遗漏 Feed 监听，使外部变更无法刷新 UI。这证明该属性需要反馈订阅，不构成“所有车控 Set 属性都必须有 Feed”的平台规则。

**Q7: [learning] 车控界面采用乐观更新时，怎样防止旧回调覆盖新请求？**

乐观更新只适合接口和安全策略允许先显示目标状态的场景。界面应区分目标值、待确认状态和权威反馈值，并用请求序号或会话代际识别每次操作，避免旧校验任务回写新请求。

一次操作按状态机处理：

1. 用户操作后记录请求 ID、目标值和截止时间，显示明确的 pending 状态。只有可乐观显示的控件才先展示目标值。
2. 反馈到达时先验证 area、采样时间和请求关联。确认对应本次请求后，按权威反馈更新状态并撤销该请求的延迟校验。
3. 反馈值与目标不同或超时后，按车辆实际有效状态与产品策略收敛。不能无条件回滚到点击前缓存，因为它也可能已经过期。
4. 新请求覆盖旧请求时，旧请求的定时任务和迟到回调不得修改当前 UI。服务断连后要清除 pending，并显式进入未知或失败态。

项目里曾出现重复点击事件与旧延迟任务共同改变把手加热档位。固定的 600 ms 时间窗只能处理当时量到的一类重复，可能吞掉合法连点。优先让事件携带按下/抬起、序号或会话身份。只能做时间去重时，应在目标设备上量化噪声和用户操作分布。

**Q8: [learning] 多个车辆信号合成一个 UI 状态时，谁负责仲裁？**

合成状态应由一个明确的 reducer 根据所有输入和时间条件计算。让每条信号回调直接写同一个渲染属性，会使最后到达者无条件覆盖其他输入，即使两个信号并不同步。

仲裁器至少处理：

1. **输入身份：**记录每个信号的状态、时间戳、区域及协议版本。未更新的输入不能被当成与新输入同时采样。
2. **业务不变量：**明确哪些组合合法、哪个输入更权威，以及冲突或缺失时如何降级。例如“充电结束”不等于“充电枪已拔出”。
3. **输出单点：**只有 reducer 计算并发布目标状态，所有输入回调只更新自己的输入快照。输出给 UI、Kanzi 或日志时使用同一结果。

项目中充电状态与充电枪连接状态曾相互覆写。修复重点是明确组合规则和单一输出入口，不能只在其中一个回调里增加临时条件。
