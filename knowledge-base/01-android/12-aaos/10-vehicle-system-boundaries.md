# 整车系统边界：通信、诊断、升级、安全与电源

> 本册解释座舱开发必须理解的整车系统边界。VHAL 与电源链路以 AOSP 官方文档为依据。诊断、安全与升级分别参考 ISO 14229、ISO 13400、ISO 26262、ISO 21448、ISO/SAE 21434、AUTOSAR SOME/IP 与 Uptane。标准规定与车型实现分开描述，具体接口仍以目标车型的网络拓扑、信号矩阵、诊断数据库和安全方案为准。

**Q1: [learning] 分布式 ECU、域控制器、区域控制器和中央计算分别解决什么问题？Android 座舱的边界在哪里？**

这些概念描述不同的职责聚合方式，不能当成所有车型都会依次经历的固定代际。判断一套 E/E 架构时，应分别看计算放在哪里、I/O 在哪里汇聚、软件由谁部署，以及故障由哪一层隔离。

1. **分布式 ECU：**每个功能由相对独立的控制器负责，接口和发布节奏清晰，但控制器、线束和跨 ECU 协调成本随功能增加而上升。
2. **域控制器：**按动力、底盘、车身、座舱或智驾等功能域集中计算，减少域内 ECU 数量，但域间网关、接口兼容和联合升级成为新约束。
3. **区域控制器：**按车辆物理位置汇聚传感器和执行器 I/O，缩短线束。功能软件可以运行在中央计算平台。区域控制器主要解决布线和 I/O 汇聚，不等于它拥有对应功能的业务决策权。
4. **中央计算：**把多个域的软件负载集中到高算力平台，通过虚拟化、进程隔离或安全分区共享硬件。它减少硬件碎片，却提高资源隔离、启动依赖、故障遏制和跨域升级的要求。

Android 座舱通常负责 HMI、媒体、导航、连接和部分车辆功能入口。即使 Android 运行在中央计算平台，也不能由此推断它直接承担制动、转向或动力控制。安全关键闭环由哪个分区或控制器执行，取决于系统安全架构。Android 常消费经网关、车辆服务或 VHAL 暴露的受控接口。

**Q2: [learning] CAN/LIN 的信号通信、以太网的服务通信与 AAOS VHAL 属性是什么关系？**

三者处在不同抽象层。CAN/LIN 信号描述报文中的位、周期和编码。SOME/IP 等服务通信描述方法、事件和服务实例。VHAL 属性是 AAOS 向 CarService 暴露车辆功能的统一契约。VHAL 不要求底层必须使用 CAN，也不是把 DBC 信号逐个改名后的镜像。

1. **信号层：**DBC 或同类网络描述定义报文 ID、起始位、长度、字节序、缩放、偏移、单位、发送周期和有效值。接收一个报文只证明链路收到了位模式，不证明信号新鲜、有效或来自期望车型配置。
2. **服务层：**服务接口按方法调用、事件发布和服务发现组织数据，适合表达较复杂的请求响应和版本化接口。服务可运行在以太网之上，但服务可用不等于业务状态已经同步。
3. **VHAL 层：**属性包含类型、访问方式、变化模式、区域和状态等元数据。OEM 负责把车辆网络中的信号或服务转换为这些属性。Android 13 起引入 AIDL VHAL，新的实现须采用 AIDL。既有 HIDL 实现仍可被 CarService 支持，具体后端以目标设备为准。

映射设计要明确方向、单位、区域、枚举、时间戳、无效值、权限和写入确认方式。多个底层信号可以合成一个属性，一个底层服务也可以映射为多个属性。遇到值错误时，应分段核对原始报文或服务事件、网关转换、VHAL 值、CarService 分发和应用显示，不能只查 Android 日志。

**Q3: [learning] 车控请求返回成功后，为什么不能立即认定执行器已经达到目标状态？**

一次车控至少包含“请求被本层接受、命令送达下游、控制器接受、执行器动作、状态被重新观测”五个阶段。同步 API 返回成功通常只能证明前面的一个或几个阶段，具体语义由接口契约决定。

1. **本层接受：**参数、权限和当前服务状态通过检查，请求进入队列。
2. **下游送达：**VHAL、网关或车辆网络已经接收命令，但目标 ECU 仍可能超时、拒绝或离线。
3. **控制器接受：**目标 ECU 接受请求，不代表机械动作已经完成。例如空调风门、电动尾门和座椅移动都需要时间，也可能被防夹或安全条件中断。
4. **执行器动作：**机构尝试移动或切换，可能因为保护条件、机械故障或中途取消而未达到目标。
5. **状态确认：**权威状态沿反向链路上报，应用才能确认实际结果。状态回报还要检查时间戳、有效性和是否对应本次请求。

界面可以在安全且可撤销的场景做乐观显示，但必须保留 pending 状态、超时、失败和权威值回写。请求 ID、目标值、发起时间和最后确认状态应能关联。迟到的旧回调不能覆盖更新请求。涉及门锁、尾门、动力或其他安全相关功能时，界面反馈策略还要遵守整车安全需求，不能为了即时感把“已发送”显示成“已完成”。

**Q4: [learning] UDS、DoIP、DTC 和 OBD 分别是什么？Android 诊断应用应处在哪个边界？**

UDS（Unified Diagnostic Services，统一诊断服务）定义诊断客户端如何访问 ECU 的诊断能力，ISO 14229 的服务与具体数据链路解耦。DoIP（Diagnostics over Internet Protocol）按 ISO 13400 在 IP 网络上承载车辆诊断通信。DTC（Diagnostic Trouble Code，诊断故障码）是 ECU 记录的故障结果及相关状态。OBD 是面向法规和排放诊断的一组接口要求，不能与 UDS 或物理诊断口画等号。

1. **会话与权限：**ECU 可区分默认、扩展、编程等诊断会话。某些服务还需要安全访问或更强认证。进入会话不等于获得所有操作权限。
2. **诊断能力：**常见能力包括读取标识与数据、读取或清除 DTC、执行例程、控制通信和下载软件。清除故障码会丢失证据，执行例程或刷写可能改变车辆状态，因此必须受权限、前置条件和审计约束。
3. **传输边界：**UDS 可以承载在 CAN、DoIP 等传输上。更换为 DoIP 改变寻址、路由和带宽条件，不改变诊断服务本身的业务含义。
4. **Android 边界：**量产 Android 应用通常通过 OEM 诊断服务、受控网关或远程诊断代理访问诊断能力，而不是直接向动力或底盘 ECU 任意发送服务。网关负责路由、车辆状态前置条件、授权、速率限制和日志审计。

排障时至少区分传输不可达、诊断路由失败、会话不满足、安全访问失败、服务被 ECU 拒绝和服务执行失败。只看到一个“诊断失败”提示，无法确定故障层次。

**Q5: [learning] 整车 OTA 为什么不是把 Android A/B 升级流程复制到所有 ECU？**

Android A/B 解决的是一个 Android 设备上系统分区的原子切换与启动回退。整车 OTA 还要协调多个硬件能力、升级协议和安全等级不同的 ECU。每个 ECU 是否支持双分区、是否能回滚、升级时能否断电都可能不同，因此整车需要独立的编排层。

1. **盘点与兼容：**先读取硬件号、当前软件版本、引导程序能力和依赖关系，确认目标包适用于这辆车。只比较版本号不能发现硬件或标定不兼容。
2. **安全元数据：**验证签名、目标身份、版本和过期信息，并防止重放或把合法旧包当成修复包降级。Uptane 将车辆更新中的角色、元数据和 ECU 验证责任分开，以降低密钥或仓库被攻破后的影响。
3. **前置条件：**检查电量、充电状态、挡位、车速、网络、存储、温度和诊断会话等条件。条件在下载后、安装前仍需重新确认。
4. **顺序与激活：**按依赖图决定先升级谁、哪些可以并行、何时重启或激活。网关接口先后不兼容时，即使每个单包都正确，车辆仍会进入不可用组合。
5. **验证与恢复：**升级后检查启动、通信、版本和关键功能健康状态。恢复策略可能是 A/B 回退、重新刷写、保持旧版本 ECU、进入降级模式或要求售后救援，不能统一假设所有 ECU 都能原地回滚。

安全防回滚与故障恢复也不能混为一谈：前者阻止降到存在已知安全风险的版本，后者要求升级失败后恢复可运行状态。方案需要预先定义允许回到哪个版本、由谁授权以及依赖 ECU 如何保持兼容。

**Q6: [learning] ISO 26262、SOTIF 和 ISO/SAE 21434 分别处理什么风险？它们怎样影响座舱软件？**

三者的问题来源不同。ISO 26262 处理安全相关 E/E 系统因故障行为造成的风险。SOTIF（Safety Of The Intended Functionality，预期功能安全，ISO 21448）处理功能没有故障却因能力不足或可合理预见的误用造成的风险。ISO/SAE 21434 处理车辆 E/E 系统生命周期中的网络安全风险。

1. **功能安全：**关注随机硬件故障、系统性软件错误和安全机制。ASIL 是危害分析与风险评估后得到的完整性等级，不是给某个 Android 模块凭经验贴的标签。
2. **SOTIF：**常见于依赖复杂传感器和算法的功能，例如感知在特定环境下能力不足。它不以组件损坏为前提，也不替代 ISO 26262。
3. **网络安全：**关注攻击者能力、攻击路径、资产影响和风险处置。身份认证、密钥保护、最小权限、更新安全和事件响应属于这一范围。

座舱不是天然的安全关键控制器，也不是天然与安全无关。仪表警告、驾驶员接管提示、倒车影像、紧急呼叫和某些车辆控制入口可能参与安全目标。架构上应把安全决策和最终执行放在满足相应安全要求的边界内，Android 负责受控显示与交互时还要处理超时、数据无效、失联、降级显示和可诊断性。是否需要安全认证、采用什么 ASIL 分解或独立监控，只能由整车安全分析决定。

**Q7: [learning] 车辆供电、点火状态、唤醒源与 AAOS 电源状态是什么关系？**

物理供电、车辆使用状态和 Android 软件状态是三套相关但不等价的概念。KL30、KL15、ACC 等名称在不同厂商和电气架构中的定义可能不同，不能仅凭信号名推导 SoC 当前是否执行代码。

1. **物理供电：**电池、PMIC 和不同电源域决定 SoC、内存、基带、TBOX、外设是否仍有电。某个域常供电不代表 Android 应用处理器也常供电。
2. **整车状态：**VMCU 或其他电源主控根据车门、钥匙、充电、远程命令等事件决定车辆和座舱应进入的状态，并通过 VHAL 与 AAOS 协调。
3. **AAOS 状态：**CarPowerManagementService 协调准备关机、Garage Mode、Suspend-to-RAM 或关机，并通过电源策略控制组件。最终 suspend 和 wake 仍由内核、驱动与硬件唤醒源完成。
4. **应用状态：**屏幕关闭、用户不交互、Activity 停止和系统 suspend 不是同一事件。应用只能依据公开的电源与生命周期回调管理资源，不能用屏幕状态推断整车已下电。

排查“车辆放置后亏电”时，应沿电源域、系统 suspend、内核 wakeup source、网络或外设唤醒、用户空间任务逐层取证。一次唤醒可能是正常维护任务，持续无法 suspend 或高频重复唤醒才指向异常。报告应同时给出车辆状态、Android 电源状态、唤醒原因、持续时间和电流测量条件。

**Q8: [learning] 座舱使用车速、轮速、方向盘转角和横摆角速度时，为什么不能只看一个数值？**

车辆信号必须连同语义和质量一起使用。相同数值在不同坐标系、单位、采样时刻或有效状态下可能表达完全不同的车辆运动。

1. **来源与定义：**仪表车速可能经过滤波和法规校准，轮速来自各车轮传感器，GNSS 速度可由多普勒观测或位置序列估计。它们的延迟、噪声和失效方式不同，不能相互当作无条件真值。
2. **单位与符号：**转角是方向盘角还是前轮转角，横摆角速度的正方向是什么，坐标系是车体坐标还是地图坐标，都必须由接口契约确定。
3. **时间：**比较多个信号时要使用采样时间或共同时间基准。回调到达时间混入网络、队列和线程调度延迟，不能替代测量时间。
4. **状态与新鲜度：**除数值外还要检查 AVAILABLE、ERROR 或 UNAVAILABLE 等状态、超时阈值和数据是否冻结。最后一次有效值只能作为明确标记的缓存，不能永久显示为当前状态。
5. **车辆条件：**挡位、制动、转向和速度之间存在物理约束，但短暂不一致可能来自采样错位、滤波或不同 ECU 周期。只有对齐时间和信号定义后，才能判断是真实异常还是观测误差。

座舱逻辑应消费经过整车接口定义和权限控制的信号，不应自行把原始轮速等输入组合成安全控制判断。需要派生显示值时，应记录算法、输入版本、无效处理和降级显示，使结果可复现、可诊断。
