# Android 与 Kanzi 渲染端的状态同步

> 本册讨论一个 Android 宿主向独立 Kanzi 渲染端发送状态和命令时的接口契约。Kanzi 的具体状态表、连接能力和动画回执由项目定义，不应推断为所有 AAOS 设备的通用机制。项目例证来自 `Summary/project/yadi/git提交与缺陷分析/`。

**Q1: [learning] 渲染端重新连接后，为什么要重新发送当前状态？**

如果渲染端只保存收到的属性而没有独立的权威数据源，断连期间的更新会丢失。重新连接时 Android 必须发送一份当前有效状态快照，再继续发送增量变化，避免渲染端继续显示旧状态或默认配置。

同步顺序应明确：

1. **建立会话：**确认双方协议版本、功能配置和可写属性，不把“连接对象存在”当成状态已经同步。
2. **发送快照：**从权威源读取仍有效的车辆和应用状态。未知或超时的输入按接口契约发送未知态，不能把旧缓存伪装为当前值。
3. **接续增量：**给快照和事件关联会话代际或序号。快照生成期间到达的新事件要重放或合并，防止旧快照覆盖新状态。
4. **确认完成：**若接口提供写入回执，确认关键配置与状态成功应用。没有回执时至少记录发送结果，并在连接恢复后重新检查可见状态。

项目中一次性功能配置早于 Kanzi 连接发送，因连接门禁而被跳过。恢复后补发是接口时序要求，而不是“初始化代码已经执行”的推论。

**Q2: [learning] 渲染状态由多个属性共同决定时，退出状态应怎样复位？**

进入和退出条件必须覆盖同一组组成字段。只复位主属性、遗漏从属属性，会留下协议允许写入但业务非法的组合，例如主档位已回 P，而渲染端仍持有 D 档桌面标志。

处理组合状态时应：

1. 把合法组合列为状态表，标出每个属性的所有写入来源。
2. 由单一映射函数从业务状态生成整组渲染值，避免多个回调分别修改同一组合。
3. 若协议不能原子提交整组值，约定安全的发送顺序或过渡态，并用序号防止新旧批次交错。
4. 在进入、退出、断连恢复和页面重建后用同一映射函数重发快照。

项目中的 Gear 与 D_Desktop 残留说明了“只清主字段”会锁住交互。具体先发送哪个属性，必须以渲染端状态机的协议说明为准。

**Q3: [learning] Android 向 Kanzi 写入值时，为什么要核对属性类型、枚举与配置版本？**

字符串、浮点数和整数在发送通道上可能都能被装箱，但渲染属性只接受协议规定的类型和值域。写入调用返回不报错，也不能证明渲染端已应用该值。

接口核对至少包含：

1. **类型与单位：**发送端类型、精度和单位必须与渲染端属性定义一致。把 float 转成字符串再写入 float 属性，可能被静默拒绝。
2. **枚举与默认值：**枚举、保留值、动作复位值和未知态由双方同一版本的状态表定义。越界值不能靠渲染端默认分支“猜对”。
3. **功能配置：**高低配车型的能力字与状态表分开校验。未发送配置不等于功能关闭，渲染端可能使用自己的默认配置。
4. **可观测性：**日志记录属性名、类型、原始值、转换后值、协议版本和写入结果。故障时再核对渲染端实际接收值与当前状态。

项目中曾因把充电里程写入字符串通道而持续显示 0.0。类型检查应位于共享协议适配层，避免每个调用点自行装箱。

**Q4: [learning] 渲染端重复上报点击事件时，怎样区分重复与合法连点？**

仅凭两次事件的时间差无法可靠区分重复和合法快速操作。若协议能提供事件序号、按下与抬起边沿或请求 ID，应优先用这些信息建立一次物理操作的身份。时间窗只能在协议缺少身份信息时作为受测量约束的降级办法。

判断时要核对：

1. 渲染端是否把同一按住动作按帧、按周期或按重连重发。
2. 业务动作是“设为目标值”还是“每收到一次就推进一档”。后者更容易被重复事件放大。
3. 同一来源的重复分布与用户合法连点的时间分布是否重叠。重叠时任何固定窗口都会误杀一类事件。
4. 重连和进程重启后序号如何归零，避免把新会话事件当作旧事件。

项目曾测到约 386 ms 的重复上报并设置 600 ms 去重窗。这个数值只描述当时设备的修复条件，不能作为其他控件或车型的默认值。

**Q5: [learning] Android 能显示的文本为什么可能在 Kanzi 中缺字或错排？**

文本能传输到渲染端，不代表渲染端字体、整形引擎和布局规则支持相同字符。Emoji、组合字符、变体选择符和连字序列尤其需要按实际字体与渲染能力验证，不能把 Java 字符串非空等同于可显示。

治理应覆盖：

1. **协议能力：**明确允许的文字范围、字体回退、最大长度和不支持字符的替代显示方式。
2. **输入与持久化：**在共享写入边界统一验证，防止某个页面绕过局部 InputFilter。历史数据读取时还要兼容旧值。
3. **Unicode 边界：**Java char 是 UTF-16 代码单元。code point 能避免拆开代理对，但一个可见 Emoji 仍可能由多个 code point 组成。需要保持或过滤完整可见字符时应按 grapheme cluster 或经过验证的序列规则处理。
4. **测试：**使用目标 Kanzi 字体、渲染版本和实际设备测试组合序列，不凭 Android 文本控件的显示结果推断车模行为。

不支持字形可能表现为空白方框、缺字或布局异常，不能未经渲染端取证就断言整串必然不显示。

**Q6: [learning] 渲染动画与 Android 页面切换怎样交接，避免动画被截断？**

动画结束的判断应来自渲染端完成事件或明确的协议状态。Android 只按固定延迟暂停或销毁渲染，设备负载、帧率和过渡路径变化后就可能截断动画。无限等待又会让页面卡住。

交接阶段依次处理：

1. 发出带会话或序号的动画请求，并进入等待完成态。
2. 收到对应完成事件后切换页面或暂停渲染，忽略旧动画的迟到完成事件。
3. 设置有界超时和取消路径。超时后根据产品策略跳过动画、恢复可操作界面或报告失败。
4. 页面销毁、用户切换和渲染端重连时清理等待状态，不能让旧回调作用于新页面。

若旧协议没有完成事件，实测的最短播放时间只能作为临时兼容参数，并要覆盖低帧率和高负载条件。

**Q7: [learning] 渲染协议里的动作复位值与初始化配置应在哪里维护？**

动作复位值、配置字和状态枚举属于双方接口契约，应集中定义并随协议版本验证。散落在业务回调里的数字 0 或“一次性发送”很难区分必要的协议步骤与历史残留代码。

适配层应分别管理：

1. **状态值：**长期表示当前事实，重连时应重发最新快照。
2. **动作命令：**触发一次行为。若协议要求发送复位值，必须说明复位时机、重复发送和丢失后的处理。不能假定所有 Action 都以 0 复位。
3. **能力配置：**连接后发送，并在协议升级或车型配置改变时重新协商。发送早于连接成功而被门禁跳过时必须排队或补发。

项目中某个 Action=0 用于动画收尾，某个配置字只在初始化发送。这两个约定应各有名字和版本说明，而不是被复制到其他渲染属性。

**Q8: [learning] 状态机的进入动作与派生 UI 状态应怎样组织？**

进入某状态必需的副作用应集中在状态机的进入动作中，而由状态计算出的显示字段应统一派生。若每条事件路径自行更新一部分字段，同一个状态会因进入路径不同而出现不同画面。

设计时依次确认：

1. 定义一个业务事实源和状态转移函数，输入包括车辆反馈、本地请求、连接状态及其时间。
2. 由新状态统一计算选中态、按钮可用性、渲染属性和必要的一次性通知。
3. 对每个进入路径检查同一状态产生相同派生输出。对离开路径检查临时属性和监听是否清理。
4. 对并发回调规定序号或时间裁决，避免旧事件在新状态之后再次触发进入动作。

这样能覆盖项目中“某条路径漏发进入通知”和“点击路径更新了选中态、信号回灌路径漏更新派生字段”的两类问题。
