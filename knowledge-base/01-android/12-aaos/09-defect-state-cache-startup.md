# 车机启动、状态与缓存边界

> 本册保留 AAOS 项目中可迁移的启动和状态管理机制。文件加密与特权权限以 AOSP 官方文档为依据，项目例证来自 `Summary/project/yadi/git提交与缺陷分析/`。具体缺陷的提交和单次修复过程仍应回看项目材料。

**Q1: [learning] 开机关键路径中的静态初始化为什么不能直接访问用户 CE 存储？**

Kotlin object 的 init 块和 Java 静态初始化在类首次使用时执行，引用点可能早于用户解锁。文件加密设备的 CE（Credential Encrypted）存储只在对应用户解锁后可用，DE（Device Encrypted）存储才可在 Direct Boot 阶段使用。因此，对 CE 文件的读取、建目录和写入都不能假定在早启动阶段成功。

设计时先按数据与启动时机选择：

1. **解锁前必须使用的数据：**放在 DE 存储，并确认组件支持 Direct Boot。DE 中的数据应限制在该阶段确有需要且适合提前暴露的范围。
2. **必须留在 CE 的数据：**等对应用户解锁后再读取或写入。多用户设备要检查目标 userId，不能用 user 0 的解锁状态推断驾驶员用户已解锁。
3. **初始化代码：**只建立轻量内存结构，不在类加载路径做磁盘、Binder 或网络等待。首次使用也需有可观察的失败状态和重试时机。
4. **未就绪写入：**若写入不能丢，保存待写请求并在解锁后持久化。若允许丢弃，返回明确失败，不能静默跳过后仍报告成功。

某车机项目曾在单例初始化时创建目录，首启存储准备窗口出现卡启动。这个案例说明应把 I/O 移出不可控的类加载时机，不能推出“读 CE 文件安全、只有写 CE 会阻塞”的通用规则。

**Q2: [learning] AAOS 系统应用新增特权权限后，为什么还要核对 allowlist？**

Manifest 声明权限只表示应用请求它。受 privileged 保护的权限还需按 Android 版本和应用安装分区写入相应的 privileged permission allowlist。同一分区的配置文件才能为该分区上的 privileged 应用授权或拒绝。签名权限是否授予则取决于签名等权限规则，不能把所有 `signature|privileged` 权限都说成“必须靠 allowlist 才能获得”。

排查顺序是：

1. 查权限的保护级别，以及声明方是否为 Android 核心平台或 CarService。
2. 查应用实际安装分区和是否位于 priv-app 路径，再检查同分区 `/etc/permissions/` 中该包的授权或拒绝项。
3. 核对 Manifest 请求、构建打包结果和设备上的实际授权状态。源码树里的 XML 存在，不代表它已进入当前镜像。
4. 查看 PackageManager 启动日志与权限拒绝信息，区分安装期 allowlist 校验、运行时权限拒绝和服务启动异常。

项目中 SystemUI 接入车载权限后只更新应用声明、遗漏镜像侧配置，暴露了这条构建边界。具体权限是否需要 allowlist，应逐项按保护级别和签名关系核对，不能批量照抄权限名。

**Q3: [learning] 状态处理函数的提前返回为什么容易漏掉资源清理？**

清理动作若只写在函数尾部，任何提前 return、异常或取消路径都会绕过它。监听、浮层、pending 请求和临时禁止操作状态都需要与创建它们的 owner 和终止条件配对。

审查时按资源生命周期列出：

1. 哪个事件创建资源，资源由哪个页面、服务或会话拥有。
2. 成功、失败、超时、用户取消、页面销毁和服务死亡分别怎样结束资源。
3. 哪些 return、异常和异步回调可能绕过正常收尾。能用 `finally` 或 owner 的统一关闭入口收敛时，应避免在每个分支复制清理代码。
4. 关闭是否幂等。重复回调或两个结束事件同时到来时，不应二次注销或重复弹窗。

项目中的互联浮窗曾因断开处理分支提前返回而残留。修复重点是把资源退出条件与状态机事件对齐，而非只在该分支再补一个零散的 `finish()`。

**Q4: [learning] 服务未连接时暂存监听注册，为什么不能按 callback 直接覆盖写入？**

同一个 callback 可能分批订阅多组属性。若暂存表以 callback 为 key，每次赋值都替换前一次列表，连接恢复后只会注册最后一组，前面的属性永远收不到事件。

暂存结构至少满足：

1. **追加或合并：**同一 callback 的属性集合应合并并去重，不能把后一次注册理解为“覆盖全部订阅”，除非 API 明确提供 replace 语义。
2. **注销：**服务尚未连接时取消订阅，需同时更新暂存表，避免重连后把已注销的 callback 再注册。
3. **代际：**重连时对当前会话一次性重放有效订阅，旧连接的迟到回调不得混入新会话。
4. **失败：**某组属性注册失败时记录失败项与原因，不因其余组成功就宣称整个 callback ready。

项目中相同 callback 的第二批属性覆盖第一批，导致仪表部分信号长期没有监听。检查暂存容器时应同时看 key、value、合并语义和重放时机。

**Q5: [learning] 多进程共用文件时，进程内缓存为什么会失效？**

进程内单例只保证本进程访问同一对象。另一进程改写文件后，本进程的内存副本不会自动更新。每次读前重新打开文件也不自动保证跨进程写入是原子的、两边不会同时覆盖。

根据一致性要求选择方案：

1. **偶尔读取的低频数据：**在读前验证文件版本或重新读取，并使用原子文件替换、锁或单写者保证写入完整。
2. **需要及时同步的共享状态：**由 ContentProvider、Binder 服务或数据库的单一 owner 管理，其他进程通过受控接口读写和订阅变化。
3. **允许缓存的客户端：**缓存只作加速层，必须有失效通知或版本校验。写入路径不能因为本地缓存未包含目标对象就静默放弃真实数据更新。

项目里座椅名称在不同进程的缓存出现分歧，说明“单例”不是跨进程事实源。决定是否采用中心服务，应看更新频率、故障恢复与一致性需求，而不是只看重读文件能否暂时消除旧值。

**Q6: [learning] 异步请求的旧回执为什么会污染新页面或新连接？**

回执晚到时，接收者可能已属于另一页面、另一设备或下一次请求。只凭“当前有一个弹窗”或“当前开关处于 pending”来处理，会把旧结果套到新事务上。

请求和结果至少要匹配：

1. **对象：**用户、设备、车辆属性及 areaId 必须对应。
2. **代际：**请求 ID 或会话序号必须对应当前连接。重连后旧连接的结果一律失效。
3. **生命周期：**结果接收者仍处于允许更新 UI 的状态，销毁后应解除监听或忽略结果。
4. **结果状态：**成功、失败、取消和超时分别清除 pending，并根据权威状态更新界面。超时不能无限保留覆盖层或禁用控件。

广播、LiveData 或其他可重放状态源可能再次交付最近结果。具体是否重放取决于该机制，不能把所有广播都叫“粘性广播”。对同一个业务结果，消费状态应由事务身份决定，而不是由回调次数推断。

**Q7: [learning] 同一入口被快速重复触发时，怎样避免重复页面或弹窗？**

先明确“只能有一个”的对象范围：是一个 Activity 任务、一个流程会话，还是跨多个宿主共享的同一弹窗。不同范围需要不同的 owner，单个 View 的点击防抖不一定覆盖其他入口。

实现时分别处理：

1. **请求入口：**使用业务会话状态或一次性导航事件，在发起请求时原子地标记进行中。请求被拒、成功、取消或宿主退出时都要释放该状态。
2. **任务语义：**按目标 Activity 的任务与 back stack 要求选择 Intent flags 和 launchMode。它们决定任务复用行为，但不自动阻止同一个业务流程被多个入口重复发起。
3. **多个宿主：**若设置页和控制中心都能打开同一弹窗，防重状态应放在共同 owner。只检查各自 FragmentManager 看不到另一宿主。
4. **恢复：**进程重建时恢复流程状态或从权威数据源重建，不能让“进行中”标志永远锁住入口。

固定时间锁可能吞掉合法的再次点击。“跳转锁 + launchMode”也不是所有页面都必须同时采用的规则，选择由业务唯一性与任务栈契约决定。

**Q8: [learning] 派生 UI 状态为什么应由一个状态源统一计算？**

按钮可用性、分组显隐、选中态与反馈文字往往由多个输入共同决定。若回调各自手工改一部分 View，遗漏一条更新路径就会出现“控件值正确，但标题、覆盖层或可用性仍是旧状态”。

统一计算的输入与输出应分开：

1. **输入：**权威设备状态、用户请求、服务连接、权限、驾驶限制和页面生命周期，各自保留自己的未知态。
2. **计算：**用同一个纯函数或 reducer 从输入生成完整 UI 状态，明确冲突时的优先级。不能让两个信号回调直接改对方负责的字段。
3. **输出：**一次渲染同时更新标题、内容、空态、按钮可用性和覆盖层。页面重新可见时从当前输入重新计算，而不是依赖上一次回调恰好执行。
4. **验证：**测试每种输入变化、失联、取消和重连后的输出，特别是提前返回、空值和错误结果。

这条结构保留了项目中多个 UI 缺陷的共同机制，单个“标题残留”“设备图标没清”或“回弹后联动区域没变”无需各自变成一条长期知识规则。
