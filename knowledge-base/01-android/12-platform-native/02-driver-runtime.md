# 内核驱动运行时

> 学习资料（文章模式沉淀）。边界：本文回答"字符设备/VFS 分发、file/inode/fops、设备号与 /dev 节点、copy_from_user、MMIO、ioctl/mmap、内核数据结构"；模块构建与部署归 [../13-build-system/06-kernel-modules.md](../13-build-system/06-kernel-modules.md)。材料中的固定物理地址与宿主机裸 gcc 命令不是生产做法。Q 序列即结构，供 atlas 同源直读。

**Q1: AAOS 中 Linux 内核驱动位于系统栈的什么位置，应用是否通常直接读写硬件？**

内核驱动位于 Linux 内核中，负责管理设备并向上层暴露受控接口；AAOS 的应用通常通过 Android Framework、HAL 或系统服务访问硬件，而不是直接访问寄存器或任意 `/dev` 节点。

典型路径是应用调用平台 API，Framework/系统服务经 HAL 与内核驱动交互，驱动再使用内核设备子系统和硬件总线接口。不同硬件可能通过字符/块设备、sysfs、网络接口、专用子系统或 HAL 通道暴露；“Linux 一切皆文件”是统一接口思想，不代表所有硬件都只通过一个 `/dev` 文件访问。设备权限、SELinux 策略和服务架构也决定了谁能访问接口。

**Q2: 用户态调用 `open`、`read` 或 `write` 后，VFS 如何把操作分发到设备驱动？**

系统调用进入内核后由 VFS 根据路径和对象类型选择实现；对字符设备节点，设备号关联字符设备驱动，文件操作最终可分发到驱动注册的 `file_operations` 回调。

用户态通过文件描述符操作已打开对象。内核中的 fd 表项引用 `struct file`；其 `f_op` 指向相应文件操作函数表。字符设备路径还涉及 inode 中的设备号及内核注册的字符设备范围/操作集。普通文件、socket 和字符设备虽然共享 `read`/`write` 等调用形式，底层分发目标不同。

实际调用会经过权限检查、VFS 与具体子系统代码，不宜把它简化成“`sys_write` 直接按 fd 找到驱动函数”。追踪某个具体设备时，应从设备节点、设备号、注册调用和回调实现逐层确认。

**Q3: `struct file`、文件描述符、`struct inode` 和 `file_operations` 各是什么关系？**

文件描述符是进程 fd 表中的整数索引，`struct file` 表示一次打开的内核文件对象，`struct inode` 描述文件对象及其类型/元数据，`file_operations` 则提供该对象可调用的操作实现。

对于字符设备，inode 可包含设备号；`struct file` 保存打开标志、当前位置等每次打开相关状态，并通过 `f_op` 连接到读写回调。驱动可以在 `.open` 中把设备实例或私有状态挂到 `file->private_data`，后续 `.read`、`.write`、`.unlocked_ioctl`、`.release` 再使用该状态。多个 fd 可以指向同一个打开对象，重复 `open` 通常会创建新的打开状态。

`f_pos` 是否有意义取决于设备语义；流式设备不一定像普通文件一样支持随机访问。具体结构字段随内核版本变化，不应照抄某个版本的完整结构体定义。

**Q4: 字符设备的主设备号、次设备号和 `/dev` 节点各负责标识什么？**

设备号是内核侧字符设备标识，由主设备号和次设备号组成；主设备号用于关联驱动操作集，次设备号通常用于区分同一驱动管理的设备实例。`/dev` 节点是用户空间访问该设备的文件系统入口。

驱动可动态申请设备号范围，也可在确有需要时使用固定范围；随后注册字符设备操作集，并建立设备对象/节点或由设备管理机制创建设备节点。节点的 major/minor 必须与驱动注册范围相符。仅有驱动代码或仅有 `/dev` 文件都不等于设备已正确可用。

Android/Linux 上设备节点的创建方式、权限、所有者和 SELinux 标签由设备模型、devtmpfs/init 规则及策略共同决定；不要假设调用 `device_create` 就解决了全部访问控制。

**Q5: 字符设备 `open` 到 `release` 的生命周期应如何设计？**

`open` 在一次打开时建立或引用设备状态，读写/ioctl 在打开期间执行操作，最后一次关闭对应的 `release` 释放该打开实例的资源。驱动需保证每个失败路径和并发路径都能正确清理。

字符设备驱动通常在初始化阶段申请设备号、初始化/注册 `cdev` 或等价设备对象，并按需要创建 class/device 节点；退出阶段撤销节点、注销设备并释放号码。`file_operations` 中按需实现 `.open`、`.read`、`.write`、`.unlocked_ioctl`、`.release` 等方法。`.owner = THIS_MODULE` 等模块引用管理细节用于避免模块仍在被使用时卸载。

回调应定义明确的缓冲区、偏移、并发、错误码和生命周期语义。没有实现的方法不应假设会自动操作硬件；用户接口需兼容 32/64 位 ioctl 等场景时还要考虑 compat 处理。

**Q6: 为什么驱动不能直接解引用用户传入的指针，`copy_from_user` 与 `copy_to_user` 如何使用？**

用户地址不能作为可信内核指针直接解引用；驱动应通过 `copy_from_user`/`copy_to_user` 在用户空间与内核缓冲区之间安全拷贝，并处理拷贝未完成的返回值。

写回调收到 `const char __user *buf` 时，先检查请求长度是否在允许范围内，再分配或选择有界内核缓冲区，执行 `copy_from_user`，最后按设备协议处理数据。读回调准备好内核数据后再 `copy_to_user`。这两个函数的非零返回表示仍有字节未成功拷贝，通常需转换为合适的错误或部分传输结果，不能无视失败并返回完整长度。

输入大小可能远大于固定缓冲区；材料示例中的 `char kbuf[1024]` 若不限制 `size` 就会越界。还需处理整数溢出、并发访问、阻塞语义与部分读写。驱动接口的长度与格式检查是内核安全边界。

**Q7: 驱动访问 MMIO 寄存器时，为什么不应把固定物理地址强转成指针后直接读写？**

固定物理地址直接解引用既不具备可移植性，也绕开了内核对 I/O 地址映射、访问顺序和体系结构差异的处理。驱动应使用资源管理及硬件子系统提供的映射/API，例如设备资源映射后使用 `readl`/`writel`，或使用 GPIO、I2C、SPI、regmap 等框架。

物理地址取决于具体 SoC/板级描述，寄存器访问还可能涉及字节序、访问宽度、屏障、时钟/电源状态和并发保护。`volatile` 不能替代 MMIO 映射、总线访问器或内存屏障。通过 GPIO/I2C/SPI 子系统访问时，框架负责相应资源与总线约定，驱动不必自行硬编码寄存器。

材料中的 `0xFE200000` LED 地址只是虚构式教学例子，不能用于真实设备或其他板卡。

**Q8: `ioctl` 和 `mmap` 什么时候适合用于设备接口，它们增加了哪些设计责任？**

`ioctl` 适用于不自然映射成字节流读写的设备控制命令；`mmap` 可用于把受控设备/缓冲区映射到用户空间以支持特定共享或高吞吐场景。二者都扩大了接口复杂度和安全审查范围。

`ioctl` 命令需定义稳定的命令号、结构布局、尺寸与兼容规则，并验证用户数据和调用权限。`mmap` 需严格限制可映射区域、长度、权限、缓存属性与生命周期，不能让用户映射任意物理内存。很多设备已有成熟内核子系统或 dma-buf 等机制，应优先复用而不是自创裸接口。

普通 `read`/`write` 可表达顺序数据通道时，优先保持简单的流式接口；只有控制语义或性能要求确实需要时才引入 ioctl/mmap。

**Q9: Linux 内核的 `list_head`、`hlist` 和红黑树分别适合什么数据组织？**

三者都是内核常用的侵入式数据结构，节点嵌入宿主对象；链表适合顺序组织，`hlist` 常用于哈希桶链，红黑树适合保持键有序并进行对数复杂度查找。选择取决于访问模式，而不是名称偏好。

1. `list_head` 是双向链表节点，常构成循环链表；`list_entry`/`container_of` 从嵌入成员定位宿主对象。
2. `hlist` 使用轻量桶头和节点，适合哈希表桶内链式冲突处理；哈希函数与负载分布由调用方设计。
3. 红黑树维护键序，查找、插入和删除在平衡条件下为 `O(log n)`；内核 rbtree 通常由调用方实现比较逻辑并调用链接/平衡接口。

这些容器本身不自动提供并发保护或对象生命周期管理。遍历时删除要使用适配的安全迭代宏；并发场景需选择锁/RCU 等同步策略；分配的节点必须在移除后按匹配方式释放。

**Q10: 为什么 `/dev/hello` 不一定会随着驱动注册自动出现，驱动卸载时又应如何处理？**

设备节点创建取决于驱动采用的设备模型和系统用户空间管理方式；注册字符设备操作集与创建 `/dev` 节点是相关但分离的步骤。动态主次设备号也需要被正确关联到节点。

驱动可使用 `cdev` 与设备模型接口注册设备，并按系统配置通过 devtmpfs/udev/init 等机制创建设备节点；Android 还需相应 init 规则、权限和 SELinux 标签。卸载时应先阻止新访问、撤销节点/设备对象，再注销字符设备和释放号码；存在打开引用或并发回调时，必须确保对象不会提前释放。

因此，`insmod` 成功但 `/dev/hello` 不存在，排查重点包括是否调用节点创建接口、目标是否启用 devtmpfs/规则、设备号是否正确以及 init/SELinux 配置是否缺失。

**Q11: 用用户态小程序验证字符驱动时，测试程序的 ABI 与驱动读写协议要核对什么？**

测试程序应为目标 Android ABI 构建，并按照驱动定义的读写协议传递长度和数据；用宿主机原生 `gcc -static` 生成的程序仍可能依赖宿主 ABI/运行时，静态链接不等于自动兼容 Bionic。

驱动与测试程序的最小闭环包括：打开设备节点、写入受支持数据、读取结果、检查返回字节数和错误码、关闭文件，并检查内核日志。测试数据长度必须覆盖边界情况，如零长度、超过最大缓冲区、部分读写和无效命令。程序应使用 Soong/NDK 等目标 Android 构建方式，或确认预编译二进制确实为目标架构和 Android runtime 构建。
