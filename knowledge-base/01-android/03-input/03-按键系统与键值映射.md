# 按键系统与键值映射：扫描码、键值定制与物理按键接入

> 学习资料（文章模式沉淀）。主线：KeyEvent 携带的字段与"扫描码 → 按键码 → 字符/行为"三层映射、`.kl`/`.kcm`/`.idc` 三类配置文件的分工、语法与查找链、新增物理按键的端到端定制流程、黑屏唤醒键的框架裁决、方向盘按键的两条接入路线取舍、uinput 虚拟设备、媒体键与 HOME 等系统键的特殊路由、方向键焦点导航、fallback 合成键与按键排查路径。机制按本地 AAOS13 源码（Android 13，`frameworks/native/libs/input/`、`frameworks/base/services/core/java/com/android/server/policy/`）核对；内核驱动侧（gpio-keys、rotary-encoder、adc-keys）为官方内核文档口径（2026-09 检索，本地树未含内核源码）。按键分发的 InputStage 顺序与 key repeat 合成机制见 [01-输入系统.md](./01-输入系统.md)；车机按键与旋钮的系统侧链路见 [06-AAOS车机输入.md](./06-AAOS车机输入.md)，CarService 层概览见 [../15-ui/06-aaos-ui.md](../15-ui/06-aaos-ui.md)。Q 序列即结构，供 atlas 同源直读。

**Q1: 一条 KeyEvent 里 downTime、eventTime、scanCode、keyCode、metaState、repeatCount 分别是什么？为什么说按键信息有三层？**

一条按键从硬件到应用经历了三次"翻译"，事件字段也对应三层：驱动上报的原始扫描码（`getScanCode()`）是第一层，描述"键盘矩阵上第几个键"；`.kl` 布局文件把它翻译成平台统一的按键码（`getKeyCode()`，如 `KEYCODE_VOLUME_UP`）是第二层；`.kcm` 字符映射再把它翻译成字符或行为（字母 `a`、组合 `Ctrl+C` 的含义）是第三层。三层分工使同一枚键在不同设备上可以映射出不同按键码，而应用永远只面向按键码编程。

时间与状态字段有四个：`downTime` 是本次按下动作发生的时间，同一次按键的所有事件（含 repeat）共享；`eventTime` 是当前这条事件自身的时间；`repeatCount` 从 0 开始，长按不放时由系统合成的事件依次递增；`metaState` 是修饰键状态位（`META_SHIFT_ON`、`META_CTRL_ON`、`META_ALT_ON` 等），让"按住 Shift 再按 A"在事件层就有语义。判断"这是不是长按后的连发"，看 `repeatCount > 0`；判断"长按语义已确认"，看 `FLAG_LONG_PRESS` 标志（由分发器在合成第一条 repeat 时携带）。

排查按键问题时先分清层：`getevent` 看到的是扫描码层，`dumpsys input` 的设备 dump 显示加载的是哪个布局文件，应用 `onKeyDown` 收到的是按键码层——三层任何一层配错，表现都是"按了没反应"或"按 A 出 B"。

**Q2: 扫描码到按键码的映射文件按什么顺序查找？目录优先级是怎样的？**

查找链分两步：先决定候选文件名，再按目录优先级逐个探测。文件名按设备身份从具体到通用：`.idc` 配置里 `keyboard.layout`/`keyboard.characterMap` 显式指定的名字最优先，且只有"布局与字符映射两份表同时到位"才直接采用；否则依次尝试 `Vendor_%04x_Product_%04x_Version_%04x`、`Vendor_%04x_Product_%04x`（用 `EVIOCGID` 读到的 vendor/product/version）、设备规范名，最后退到 `Generic`、再退到 `Virtual`。按 AAOS13 源码核对（`frameworks/native/libs/input/Keyboard.cpp` 的 `KeyMap::load` 与 `InputDevice.cpp` 的路径解析），厂商指定缺一份时其余半份仍会由后续降级策略补齐，避免改名拼错让设备整个不可用。

目录探测顺序（找到即返回）依次为：`/product/usr`、`/system_ext/usr`、`/odm/usr`、`/vendor/usr`、`/apex/com.android.input.config/etc/usr`（输入配置 APEX）、`/system/usr`（`ANDROID_ROOT` 下），最后是用户数据目录 `$ANDROID_DATA/system/devices/`。这意味着 `/odm/usr/keylayout/Vendor_1234_Product_5678.kl` 会遮蔽 `/system/usr/keylayout/` 下的同名文件——车机厂商定制优先放在 odm/vendor 分区，不改动 system。

排查"按键映射没生效"时，`dumpsys input` 里每个设备的 `KeyLayoutFile`/`KeyCharacterMapFile` 字段直接显示最终命中的绝对路径：显示的是 Generic.kl 说明按 VID/PID 和设备名都没找到专属文件，通常是文件名不符或放错了分区。

**Q3: `.kl` 按键布局文件的语法是什么？flags 列能写什么？**

基础语法共五个顶级声明（按 AAOS13 源码核对，`frameworks/native/libs/input/KeyLayoutMap.cpp` 的解析器关键词）：`key <扫描码> <KEYCODE> [flags...]` 把扫描码映射为按键码并可附加策略标志，另有 `key usage <HID 用法码>` 变体按 HID 用法映射（HID 设备查表时用法优先于扫描码）；`axis <扫描码> <AXIS>` 映射相对轴（支持 invert 反向、split 拆分双轴与 flat 死区）；`led <扫描码> <LED>` 关联指示灯；`sensor <绝对轴> <传感器类型> <轴>` 声明传感器类设备的轴；`requires_kernel_config <CONFIG>` 要求特定内核配置存在，不满足时整个文件不加载、自动改试同名 `_fallback` 布局。flags 列表逐个经标签表转成位标志，重复声明同一标志会报解析错误。

`.kl` 可写的标志共四个（按 AAOS13 源码核对，标签表只认这四个，对应 `frameworks/native/include/input/Input.h` 的 policy 标志定义）：`WAKE`（可唤醒）、`VIRTUAL`（电容虚拟键，参与静默期误触抑制）、`FUNCTION`（当作功能修饰键）、`GESTURE`（触摸固件识别的手势键，按下会取消同设备的触摸序列）；其余 policy 标志由系统内部使用，写进 `.kl` 无效。`WAKE` 是"黑屏时按键能否唤醒"的第一道输入，但不是唯一条件。

定制示例——把某面板厂商按键板的扫描码 116 映射为语音键并允许唤醒：

```text
key 116   KEYCODE_VOICE_ASSIST  WAKE
```

注意映射方向：一个 KEYCODE 可以被多个扫描码映射过来（复用语义），但反查扫描码时布局文件返回的是一组扫描码；车机上"同一个按键码来自不同按键板"的场景要在应用里用 `KeyEvent.getDeviceId()` 区分来源，而不是改映射。

**Q4: `.kcm` 字符映射文件与 `.kl` 怎么分工？type 声明影响什么？**

分工是"行为映射"与"字符映射"：`.kl` 决定扫描码变哪个按键码（只对键盘类设备必配），`.kcm` 决定按键码在各修饰键组合下产生什么字符或 fallback 行为。`.kcm` 的语法是 `type` 声明加 `key` 块：`key <KEYCODE> { label: ... base: ... <修饰列>: ... }`，修饰列按 `shift`、`lctrl`、`ralt` 等命名；`fallback` 属性声明"该键未被应用处理时合成的替代按键"。按 AAOS13 源码核对（`frameworks/native/libs/input/KeyCharacterMap.cpp` 解析器），`type` 与 `key`/`map` 是顶层关键词，`fallback` 是 key 块内的属性之一。

`type` 的取值有 `NUMERIC`（12 键数字板）、`PREDICTIVE`、`ALPHA`（带字母但非全键盘）、`FULL`（标准全键盘）、`OVERLAY` 和 `SPECIAL_FUNCTION`。type 影响框架对该设备的能力判断：FULL 键盘允许直接字母输入，非 FULL 的按键更多走 fallback。`SPECIAL_FUNCTION` 在新版本里已建议不写在 `.kcm` 而改用 `.idc` 的 `keyboard.specialFunction` 声明——按 AAOS13 源码核对，解析器读到 `type SPECIAL_FUNCTION` 会打警告提示迁移；该类型的意义是"设备全是功能键，不产生文本"，框架对它的按键不再尝试字符匹配。

改键场景的判断规则：想改"这个键是什么键"改 `.kl`；想改"这个键打出什么字、按住 Ctrl 是什么"改 `.kcm`；中文物理键盘输入法场景则两者都不动，由输入法消费按键码自行转换。

**Q5: `.idc` 输入设备配置文件是干什么的？哪些场景必须配？**

`.idc`（输入设备配置）是设备级属性文件，告诉 InputReader"这个设备是什么类型、该怎么处理"，很多行为没有它就无法正确工作。查找链与 `.kl` 相同（设备名/Vendor_Product 系列），同样按分区目录优先级探测。

必须配 `.idc` 的典型场景：

- **旋钮类设备**：能力位无法自证身份，`.idc` 里 `device.type = rotaryEncoder` 是唯一判定依据（按 AAOS13 源码核对，`EventHub.cpp` 对旋钮类只认这个配置），配套 `device.scalingFactor`、`device.res` 定标；
- **触摸屏绑定副屏**：`touch.displayId` 指定目标显示的 uniqueId，车机仪表屏/副驾屏触控绑定靠它；
- **面板贴装方向与显示不一致**：`touch.orientation = ORIENTATION_90/180/270` 声明设备自身朝向；
- **键盘指定专属布局**：`keyboard.layout`/`keyboard.characterMap` 点名映射文件；
- **特殊功能键盘**：`keyboard.specialFunction = 1`（替代旧的 `.kcm` type 声明）；
- **触控行为微调**：`touch.size.calibration`、`touch.wake` 等校准与策略属性族。

`.idc` 的定位是"驱动机 Intelligence 之外的设备画像"：能力位描述硬件能发什么事件，`.idc` 描述这些事件该怎么解释。新接入一个输入设备而行为异常时，第一步就是 `dumpsys input` 查它的设备类型判定是否符合预期——判定错了，后面的 mapper 全错。

**Q6: 新增一个车机物理硬键，从内核到应用响应要改哪些地方？**

按数据流向共四段，每段都有可核对的生产物：

1. **驱动层让按键产生事件**：GPIO 按键走 `gpio-keys` 驱动（设备树里声明 `linux,code` 指定扫描码、`wakeup-source` 可选）；多个键共用一个 ADC 分压引脚走 `adc-keys`（按电压区间判键）；若按键接在 MCU 上经 CAN 上报，则由 MCU 侧转成 HID 设备或直接进 VHAL。
2. **映射层让扫描码变按键码**：确认设备的 VID/PID（`getevent -i` 可读），在 `/odm/usr/keylayout/` 或 `/vendor/usr/keylayout/` 放 `Vendor_XXXX_Product_XXXX.kl`，写 `key <扫描码> <KEYCODE_XXX>`；扫描码选内核已定义的标准码，`.kl` 里不需要也不应该自造码值。
3. **框架层确认不拦截**：非系统键（音量、亮度、 Assist 等被 `PhoneWindowManager` 特殊处理的键）无需动作；若新键恰好撞上系统键码，要么换键码，要么在设备侧的 `interceptKeyBeforeQueueing` 定制中放行——选键码时应避开系统保留段。
4. **应用层消费**：Activity/View 的 `onKeyDown`/`onKeyUp` 按 `KEYCODE` 处理，检查 `repeatCount` 防长按连发；车机全局键（任何界面都要响应）用 `CarInputManager` 的捕获机制或系统服务注入路径，而不是每个 Activity 都写一遍。

验证按段推进：`getevent -lt` 确认扫描码与时间戳 → `dumpsys input` 确认加载了新 `.kl`（看 `KeyLayoutFile` 路径）→ `onKeyDown` 日志确认应用收到正确键码。哪段没过就修哪段，跨段猜是排查按键定制的最大时间黑洞。

**Q7: 为什么有的按键黑屏时能点亮屏幕？唤醒判定发生在哪一层？**

唤醒判定发生在 `InputDispatcher` 入队前的策略钩子 `interceptKeyBeforeQueueing()`（实现是 `PhoneWindowManager`），不在应用层。判定依据有两个来源：按键在 `.kl` 里带 `WAKE` 标志（转成 policy 标志），或事件本身是 `event.isWakeKey()`——后者是隐藏的按键码白名单（CAMERA、MENU、PAIRING、STEM_1/2/3、WAKEUP）；屏幕灭着且该键属于允许唤醒的键集时，调用 `wakeUpFromWakeKey()` 点亮屏幕。外接键盘还有一层自动补位：`ACTION_DOWN` 且设备为外部设备、未被 `.idc` 的 `keyboard.doNotWakeByDefault` 豁免、又不是媒体键时，InputReader 自动为它补上唤醒标志——需要逐键写 `WAKE` 的只有内置键盘（按 AAOS13 源码核对，`KeyboardInputMapper` 的补位逻辑与 `PhoneWindowManager.java` 的 `isWakeKeyWhenScreenOff()` 二次过滤：媒体键永不唤醒、音量键仅 dock 态唤醒，所以"配了 WAKE 就一定唤醒"不成立）。还有一个防穿透细节：唤醒用的按键，其抬起事件会被吞掉——策略层记下唤醒键（`mPendingWakeKey`），亮屏后同键的 UP 直接丢弃，应用不会收到缺 DOWN 的残缺序列。

同时要注意唤醒与放行是两个决定：灭屏时事件默认不放给应用（`ACTION_PASS_TO_USER` 不置位），唤醒键只负责把屏幕点亮、自身被消费。这解释了"黑屏按音量键只亮屏不调音量"的行为。双击唤醒类厂商特性在 AOSP 侧只留了传感器通道：框架挂起等待唤醒手势传感器（`TYPE_WAKE_GESTURE`）触发后走同一唤醒路径，手势识别本身在触摸固件或厂商传感器实现里。

工作场景对应：车机旋钮/硬键"熄屏按不动"时，先查 `.kl` 是否带 `WAKE`，再查 `isWakeKeyWhenScreenOff` 的键集覆盖，最后查电源策略（AAOS 的挂睡状态与 power policy 禁屏、灭屏是不同状态）——三层都可能让按键"无效"，表现相同而原因不同。

**Q8: 方向盘按键接 Android 有哪两条路线？各自适合什么情况？**

两条路线的本质区别是"按键数据走通用输入通道还是专用车机通道"：

- **HID/uinput 路线**：MCU 把 CAN 报文翻译成 USB HID 键盘报文，或 SoC 上的服务用 `/dev/uinput` 创建虚拟键盘注入事件。事件经标准 evdev → EventHub → 按键分发全链路，需要配 `.kl` 做扫描码映射。适合"按键就是普通按键"的场景：无特殊长按语义、无需按显示路由、改动最小；弱点是按键进入 Android 后没有车载上下文（不知道该投到主屏还是仪表）。
- **VHAL 路线**：MCU/车控服务把按键写进 `HW_KEY_INPUT` 属性，CarService 的 `InputHalService` 订阅并转成 `KeyEvent`，再由 `CarInputService` 按目标显示分发（按 AAOS13 源码核对，`InputHalService.java` 订阅三属性并在 `onHalEvents` 转换）。适合需要车载语义的场景：按键要区分主屏/仪表、要支持系统级长按（语音键长按、通话键接听）、要允许应用捕获独占。

选型判断：按键只驱动当前界面交互，HID 路线省事；按键有整车级含义（语音、接听、息屏），VHAL 路线才能拿到按显示路由、长按处理与捕获仲裁。两条路线并存也常见——音量/媒体键走 HID，语音/接听走 VHAL；此时要防止同一物理键被两边重复上报。

**Q9: uinput 是什么？怎么用它创建一个虚拟按键设备？**

uinput 是内核提供的虚拟输入设备接口：用户态程序打开 `/dev/uinput`，声明设备能力，内核就生成一个与其他真实设备无差别的 evdev 节点，之后 `write()` 事件即可注入。按 AAOS13 源码核对（`bionic/libc/kernel/uapi/linux/uinput.h`），主要 ioctl 包括 `UI_SET_EVBIT`/`UI_SET_KEYBIT`/`UI_SET_RELBIT`/`UI_SET_ABSBIT`（声明事件类型与各码位能力）、`UI_DEV_SETUP` + `UI_DEV_CREATE`（设备名/VID/PID 与创建）、`UI_DEV_DESTROY` 销毁。

典型流程：设 `UI_SET_EVBIT(EV_KEY)` → 逐个 `UI_SET_KEYBIT(所需扫描码)` → `UI_DEV_SETUP`（name、bus/vendor/product）→ `UI_DEV_CREATE` → 循环 `write(input_event)` 注入（`EV_KEY` 按下/释放 + `EV_SYN/SYN_REPORT` 收尾）。注入的设备走与真实硬件完全相同的 EventHub → InputReader 路径，对 Android 而言不可区分；这也意味着虚拟设备同样受 `.kl` 映射、权限与安全机制约束。

使用场景：模拟旋钮/按键做自动化测试（比 `adb shell input keyevent` 更接近真实设备，因为走的是设备层而非注入层）；把 MCU 经串口上来的协议翻成标准输入事件；调试 InputReader 的设备接入逻辑。注意与系统注入的区别——uinput 是"造设备"，`input` 命令是"发事件"，前者需要驱动权限（root 或特定 SELinux 域），后者只要 shell。

**Q10: 蓝牙耳机的播放/暂停键为什么前台应用经常收不到？媒体键的路由有什么特殊之处？**

媒体键（`KEYCODE_MEDIA_PLAY_PAUSE`、`KEYCODE_HEADSETHOOK` 等）在按键分发里被专门劫持：系统把它们路由给 MediaSessionService，由它决定"哪个媒体会话是当前的 media button 会话"，再派发给该会话注册的 `MediaButtonReceiver` 或回调。按 AAOS13 源码核对（`MediaSessionService.java`），系统会记住最近的 media button 接收者（含从 `Settings.Secure` 恢复的持久化记录），按键优先派给"最近活跃的媒体会话"而不是当前焦点窗口。

设计原因：媒体键的语义是控制"正在播放的媒体"，与屏幕焦点无关——用户在浏览设置时按蓝牙耳机暂停键，期望的是暂停音乐而不是触发设置页。应用要接媒体键，正确姿势是注册 `MediaSession` 并在播放活跃时保持会话置顶，而不是指望 `onKeyDown`。

排查口径：前台应用收到媒体键是例外而非常态；"我的播放器按耳机键没反应"先查 `MediaSession` 是否活跃、是否被其他会话抢占，`dumpsys media_session` 能列出各会话与当前 media button 会话归属。车机上音量键另有一层：CarAudioService 会按音区处理，与媒体键又是两套路由。

**Q11: HOME 键为什么应用层拦不到？哪些按键会被系统"吃掉"？**

因为系统键在进入应用之前就被策略钩子消费了。按键有两道系统闸门：`interceptKeyBeforeQueueing()`（入队前，电源策略层，决定唤醒/灭屏/是否放行）和 `interceptKeyBeforeDispatching()`（分发前，可延迟或直接消费事件）。HOME、电源、截屏、Assistant 等系统级键码在 `PhoneWindowManager` 里被识别并处理（返回桌面、弹电源菜单等），事件不再投递给应用；应用侧的 `onKeyDown` 只会收到被策略放行的键。

判断一个键能不能被应用处理，标准是查 `PhoneWindowManager.interceptKeyBeforeDispatching` 的键码清单：`KEYCODE_HOME` 被消费（这就是"HOME 键监听不到"的标准答案，且每块显示器有独立的 Home 处理器）；`KEYCODE_APP_SWITCH`（最近任务）同样被策略层消费——按下预加载、抬起切换，应用收不到；`KEYCODE_BACK`/`KEYCODE_MENU` 放行给应用（所以 BACK 可拦截，MENU 仅在与修饰键组合时被劫持做调试功能）；音量键默认放行但前台应用处理前后系统可能有音量条逻辑；`KEYCODE_POWER` 短按消费、长按走电源菜单。系统级快捷键（Meta 组合、亮度键等）也在这一层处理；Android 13 新增的 `KEYCODE_VIDEO_APP_*`/`FEATURED_APP_*`/`DEMO_APP_*` 系列被转给 SystemUI 后丢弃，普通应用同样收不到。

车机扩展：VHAL 路线的按键在进标准分发前还要过 `CarInputService` 一层（语音/通话键的特殊处理、按显示路由、捕获仲裁），所以车机"应用拦不到某硬键"的原因多一层可能——被 CarService 消费或被捕获方截走。排查顺序是先 `cmd car_service` 侧确认事件流出 CarService，再查 PhoneWindowManager 消费，最后才是应用层。

**Q12: 方向键在电视/车机这类无触摸设备上怎么移动焦点？应用要怎么配合？**

`KEYCODE_DPAD_UP/DOWN/LEFT/RIGHT`、`KEYCODE_TAB` 这类导航键不走触摸分发，而由 `ViewRootImpl` 转成焦点移动：按键未被普通按键逻辑消费时进入 `performFocusNavigation()`，把键码映射为 `FOCUS_UP/DOWN/LEFT/RIGHT/FORWARD/BACKWARD` 方向，调用焦点系统在 View 树上寻找下一个可聚焦 View 并请求焦点（按 AAOS13 源码核对，`ViewRootImpl.java`）。`KEYCODE_DPAD_CENTER`/`KEYCODE_ENTER`/空格在焦点所在 View 上转成"点击"。

应用配合要求集中在三件事：一是**可聚焦性**——控件 `focusable` 且在触摸模式下也可聚焦（车机旋钮界面常要求 `focusableInTouchMode`，否则触摸模式切换会丢焦点）；二是**焦点可见性**——`focusable` 的 View 要画焦点态（foreground/drawable selector），旋钮用户靠它知道在哪；三是**布局可达性**——焦点搜索基于几何邻近与方向，被遮挡、越界滚动、RecyclerView 子项未布局完成都会导致"焦点跳不到"，滚动容器的子项要能自动滚入可见区。

车机旋钮方案的分工：AOSP 的 RotaryController（无障碍服务）负责解析旋钮并驱动同样的焦点移动，应用侧只需要按焦点导航规范做好可聚焦性——这也是"适配旋钮 = 适配焦点导航"的原因。调试时 `adb shell input keyevent DPAD_LEFT` 可在无旋钮环境验证焦点链。

**Q13: `downTime` 和 `eventTime` 为什么分开？长按判定和 repeat 判定分别用哪个？**

`downTime` 记录本次按键序列中按下动作的时间，同一序列内的所有事件（含每条 repeat）都携带同一个 `downTime`；`eventTime` 是当前这条事件产生的时间。分开存才能只靠一条事件算出"已经按了多久"：框架决定何时合成 repeat、应用判断是否超时，看的都是 `eventTime - downTime` 是否越过各自的阈值，不需要谁在旁边记住按下时刻。

repeat 由分发器在入队空闲时合成：首条延迟取长按超时（Android 13 运行时默认 400 ms，随 `Settings.Secure.LONG_PRESS_TIMEOUT` 可调；native 侧兜底常量为 500 ms），后续间隔固定 50 ms，第一条 repeat 的 `repeatCount` 为 1 并带 `FLAG_LONG_PRESS`。因此应用侧的规范是：`onKeyDown` 里用 `event.getRepeatCount() == 0` 做"仅首次"的初始化，重复事件里做连续动作（如长按加速滚动），长按语义的显式标志看 `FLAG_LONG_PRESS` 而不是自己起计时器——自己计时会与系统 repeat 节奏叠加，表现为动作提前或翻倍。

`downTime` 还有一个边界用途：注入事件时 `downTime` 填错（如每次都填当前时间）会让框架的时长计算失效，长按类逻辑永远不触发。用 `adb shell input keyevent --longpress` 注入长按时，系统就是靠拉开 `downTime` 与 `eventTime` 来表达长按的。

**Q14: fallback 合成键是什么机制？为什么按键没人处理时会"变成"另一个键？**

fallback 是按键的第二轮分发：一条按键未被应用消费时，system_server 侧按设备 `.kcm` 里该按键码的 `fallback` 声明（运行时 API 是 `KeyCharacterMap.getFallbackAction()`）合成一条带 `FLAG_FALLBACK` 标志的新按键再分发一轮。按 AAOS13 源码核对（`PhoneWindowManager.dispatchUnhandledKey`，注释言明"仅在首个 DOWN 未被处理时调用"），合成与再分发都在 framework 策略层完成：先确认事件不是系统自己消费的，再查 fallback 声明生成新键，新键还要过一遍 `interceptFallback`（重走入队与分发两道拦截钩子）才派发；后续 UP 与 repeat 从缓存的 fallback 动作取，不再重复查询。标志 `FLAG_FALLBACK = 0x400` 定义于 `KeyEvent.java`；应用进程内也有携带该标志的合成事件（如摇杆轴换算成方向键），但那不是 `.kcm` fallback 机制本身。

价值在于让旧交互在新设备上存活：Generic.kcm 里就有现成例子——`ESCAPE` 的 alt 组合 fallback 成 HOME、`DEL` 的 ctrl+alt 组合 fallback 成 BACK、手柄 A 键 fallback 成 `DPAD_CENTER`、小键盘未开 NumLock 时数字键 fallback 成光标移动（按 AAOS13 源码核对，`Generic.kcm` 的 fallback 声明）；应用不需要认识每一种物理键，只需处理标准键码。分发两轮的代价是"一次按键、两次 onKeyDown"，应用若在第一轮返回 true 则不会触发 fallback，日志里看到带 `FLAG_FALLBACK` 的按键时要明白它是合成键而非硬件事件。

定制场景：给车机硬键在 `.kcm` 里声明 `fallback` 可以实现"应用不认这个键就当返回键用"的兜底语义；反向的坑是 fallback 键又被系统拦截（如 fallback 成 HOME），行为会随拦截策略变化，配置后要按真实设备验证两轮分发各自的结果。

**Q15: "按了某个物理键没反应"或"按 A 出 B"，排查路径怎么走？**

按键问题按三层映射与两道闸门定位，顺序如下：

1. **确认硬件事件到达**：`getevent -lt` 按对应 `/dev/input/eventX`（先 `-il` 找到设备），按物理键看扫描码（`MSC_SCAN` 行给出原始扫描码）与 `EV_KEY value`。没有输出是驱动/接线问题，映射层无从谈起；
2. **确认映射生效**：`dumpsys input` 里该设备的 `KeyLayoutFile` 显示实际加载的 `.kl` 绝对路径。显示 `Generic.kl` 说明专属映射没找到——核对文件名（Vendor_Product 规则）与分区路径（odm/vendor 优先）；按 A 出 B 多半是命中了错误的 Generic 映射或 `.kl` 里扫描码写错；
3. **确认按键码正确**：`adb shell getevent -l` 的标签即按键码层的结果；或用 `adb shell input keyevent <KEYCODE>` 反向注入，隔离"映射层对了、应用没处理"的情况；
4. **确认未被系统闸门消费**：对照系统键清单（HOME、电源等被 PhoneWindowManager 消费；车机硬键还要确认是否被 CarService 捕获/特殊处理），换一个应用（如打开设置）交叉验证"是全局被吃还是只有我的界面没处理"；
5. **确认应用层逻辑**：`onKeyDown` 日志检查键码、`repeatCount` 与返回值——返回 true 才算消费；长按连发没防会表现为"按一下执行多次"。

车机专属提示：VHAL 路线的按键不产生 `getevent` 输出（不走 evdev），排查从 `dumpsys car_service --services CarInputService` 与 VHAL 上报侧开始；两条路线的按键问题要分别用各自的工具链，混用会白查很久。

**Q16: 两个键同时按的组合逻辑（如截屏）在哪实现？要做"HOME+某键进工程模式"怎么定制？**

组合键由策略层的 `KeyCombinationManager` 统一管理：它在 `interceptKeyBeforeDispatching` 的入口查表，命中已注册的组合规则（音量下+电源截屏就是双键规则）就把两个键一起消费，事件不再进应用、也不再走各自的单击逻辑（按 AAOS13 源码核对，`PhoneWindowManager` 在分发钩子最前面做已消费短路）。单键的长按与连击（电源长按菜单、连按唤出）由 `SingleKeyGestureDetector` 提供模板：注册长按与连击回调，由它判定按压时长与单位时间内的次数，达到最大连击数立即触发。

自己定制的要点是"照抄框架模式而不是改应用"：在策略层注册组合规则，声明两个键码与触发动作；组合命中的键要保证不被单键逻辑提前消费（拦截顺序决定，框架入口的短路就是为此设计）；组合是否放行给应用由拦截结果独立控制。应用层监不到组合键是常态——组合裁决发生在按键离开策略层之前。

调试用 `adb shell input keycombination <键1> <键2>`（同时按下的语义）；两条间隔几十毫秒的独立 `keyevent` 注入可能进不了组合时间窗，组合逻辑没触发时先检查注入方式而不是先改代码。

**Q17: `ACTION_MULTIPLE` 是什么？现在还有哪些场景会遇到？**

`ACTION_MULTIPLE` 是 KeyEvent 除按下/抬起外的第三种动作，表示"一条事件携带多次按键或一串字符"：与输入法交互时框架可能投递，内容要么是"同一键码重复 N 次"，要么是一段要直接插入的字符序列（此时键码为 UNKNOWN、事件携带 characters）。按 AAOS13 源码核对（`KeyEvent` 类文档与分发逻辑），它是低带宽时代的压缩手段，现实意义是兼容：未被 `onKeyMultiple` 处理的"重复键码"形态会在分发时降级重放为多条按下/抬起，纯字符形态无法重放、直接按未处理返回。

应用侧的取舍：新代码不主动处理它，但不要假设它不存在——批量文本进入按键通道的场景（扫码枪、某些外接输入设备）仍可能以它出现；需要批量字符语义时重写 `onKeyMultiple`，其余情况让基类的降级重放兜底。前提一并记住：软键盘输入默认不走 KeyEvent（文本经 InputConnection 进入应用），`ACTION_MULTIPLE` 只在按键事件体系内出现，目标 API 较新的应用收到的软键盘按键事件本身就该按"没有"设计。
