# 焦点分发与多屏输入：窗口命中、每屏焦点与分发管线组件

> 学习资料（文章模式沉淀）。主线：按键焦点窗口的每屏计算与焦点请求语义、触摸目标的窗口命中测试（touchable region、遮挡校验、spy 窗口）、slippery 出界换窗、窗口级触摸拆分、监视窗口的三个真实用户、窗口级指针捕获、拖放会话、触摸模式、分发链上的旁路组件（误触抑制、事件分类、版本演进）、车机多屏的输入路由。"点不到/抢事件"的应用侧排查见 [02-app-event-dispatch.md](02-app-event-dispatch.md)。机制按本地 AAOS13 源码（Android 13，`frameworks/native/services/inputflinger/dispatcher/`、`frameworks/base/services/core/java/com/android/server/policy/`）核对；屏下指纹示例按 SystemUI 源码核对。队列与 ANR 机制见 [01-input-system.md](01-input-system.md)；多屏窗口架构见 [../03-ui/04-window-system.md](../03-ui/04-window-system.md)。Q 序列即结构，供 atlas 同源直读。

**Q1: 按键事件的目标窗口怎么确定？焦点的记账单位为什么是令牌而不是窗口句柄？**

按键按焦点分发：InputDispatcher 把按键发给"所在显示器的焦点窗口"。焦点记账在 `FocusResolver` 里按屏分桶、按令牌（window token）归属——一个令牌背后可以挂多个窗口句柄（分屏切出的片段、镜像副本），它们共用同一条输入通道，按句柄记账会让同一应用的两个片段各持一份焦点，所以焦点只能按令牌记（按 AAOS13 源码核对，`FocusResolver.h` 的策略注释与数据结构）。窗口可获焦的条件是：令牌下至少一个句柄可见、且所有句柄都可获焦。

焦点请求分两类、持久化语义不同（这是最容易读混的地方）：普通请求（`setFocusedWindow` 不带焦点令牌）会保存下来，窗口当前不可获焦时等它变得可获焦再授予；条件请求（带 focusedToken）不持久，条件不满足就撤销，窗口失焦后回到原焦点令牌。所有焦点变更从 `updateFocusedWindow` 一个出口流出，"没变"返回空、不发通知。

排查意义：按键没到预期窗口时，先 `dumpsys input` 看 `FocusedWindow`（按屏），再确认请求类型——普通请求的延迟授予与条件请求的即时期撤销，表现都是"焦点没过去"，但机制与修法不同。

**Q2: 窗口属性变化时焦点怎么重算？"焦点被别的窗口抢走"发生在什么条件下？**

每次窗口集合变化（增删、属性变化、可见性变化），WMS 把最新窗口信息推给 InputDispatcher（经 SurfaceFlinger 转推窗口信息，遗留接口为 `setInputWindows`），分发器重评估现有焦点"还能不能留"：焦点窗口变得不可见/不可获焦时焦点丢失；若之前有已保存的焦点请求且现在可获焦，则授予它。焦点丢失瞬间，未完成的按键事件会进待发队列，等新焦点出现时发出（按 AAOS13 源码核对，`FocusResolver` 头注释与 `InputDispatcher` 的焦点处理）。

会被"抢走"的典型场景：弹窗/新窗口落在焦点窗口之上且可获焦；焦点窗口退出；分屏边界调整导致句柄可见性变化。注意触摸不是焦点变更的条件——点一个不可获焦窗口不会改变按键焦点，按键焦点与触摸目标是两套独立状态（点谁不一定把按键焦点给谁）。

车机对应物：VHAL 路线的硬键在 CarService 侧就按目标显示注入，进到 InputDispatcher 后同样按"该屏焦点窗口"分发；乘员屏各自的焦点互不影响。

**Q3: 一条触摸事件怎么选中目标窗口？命中测试按什么顺序？**

按下时刻（`ACTION_DOWN`），InputDispatcher 从前到后遍历窗口做命中测试，选中第一个满足条件的窗口：坐标落在其 `touchableRegion` 内、窗口可触摸（未禁用、没有 `DROP_INPUT` 类输入配置）、未被上方不透明窗口完全遮挡（遮挡校验会计算遮挡链与透明度，被完全遮住的窗口不参与命中）。同时会收集路径上所有命中的 spy 窗口（监视窗口）一并接收事件副本。后续 `MOVE`/`UP` 延续按下时的目标，不在每个采样点重选。

`touchableRegion` 是窗口向系统声明的可触摸区域，可以小于窗口自身尺寸（如周围的非交互边框）；安全校验还包括 UID 与通道令牌的匹配。命中结果写入触摸状态（`TouchState`），记录每根指针归属的窗口，这是触摸拆分与出界换窗的基础。

排查"点到 A 却触发了 B"时，`dumpsys input` 的 `Windows:` 段列出每个窗口的 displayId、`touchableRegion` 与变换矩阵——把出问题的坐标代进去看落在谁的区域内，通常能直接看出是区域声明错误还是遮挡计算与视觉预期不一致。

**Q4: slippery 窗口是什么？"手指滑出窗口边界后事件跟出去"是怎么实现的？**

slippery（可滑出）窗口允许进行中的触摸在滑出自身边界后把后续事件移交给下方窗口：`MOVE` 阶段分发器检测到指针已离开 slippery 目标的区域且进入另一个可接收窗口，就对旧窗口做"滑出"（合成取消语义的事件边界处理）、对新窗口做"滑入"，之后事件流交给新窗口（按 AAOS13 源码核对，`InputDispatcher.cpp` 的 slippery exit/entrance 处理）。普通窗口不 slippery，滑出后事件继续发给原窗口直到抬起——这就是默认"点到谁就永远给谁"的实现层依据。

典型 slippery 用户是壁纸与桌面这类大面积、需要"滑动过渡到上层内容"的窗口。应用层对应的观感是：在支持的窗口上滑动时，"列表滚到头接着滑桌面"这类跨窗口手势不需要抬手重来。

注意与系统手势抢占区分：slippery 是按几何边界的自然移交，不产生对原目标的抢夺语义；而系统手势监视器接管（`pilferPointers`）会给原目标合成 `ACTION_CANCEL`。排查"滑到边缘行为突变"时，先确认相关窗口是否 slippery，再看是否发生了监视器接管——两者的日志特征不同。

**Q5: 多指按下落在两个窗口上，窗口级触摸拆分怎么工作？**

与 View 层拆分对应，窗口级也有拆分：按下后的每个新指针独立做命中测试，落在不同窗口就分属不同目标；分发时把原始多指事件按每个目标的指针集合拆成子事件，各自只看到自己的手指，动作类型按子集重算（第一个/最后一个指针的按下抬起会被映射成该窗口视角的 `DOWN`/`UP`）。窗口消失或不可触摸时，其名下指针的后续事件按取消语义处理（按 AAOS13 源码核对，`InputDispatcher.cpp` 的 `splitMotionEvent` 与触摸状态维护）。

这个机制的常见验证场景：双指分别按在分屏的两个应用上，各自拖动互不干扰；以及"一个手指按在对话框外、一个按在对话框内"时，两个窗口各自收到自己的指针流。

边界：拆分按指针集合进行，同一窗口的多个指针始终整组出现；某一指针滑入另一窗口不会自动换窗（除非 slippery）；监视窗口收到的始终是完整事件副本，不参与拆分。把"应用内多指错乱"与"窗口间拆分"分开看，才能定位问题在 View 层还是分发器层。

**Q6: 监视窗口（spy window / InputMonitor）有哪些真实用户？它与普通窗口接收事件有什么区别？**

监视窗口通过 `InputManagerService.monitorGestureInput()` 创建，需要 `MONITOR_INPUT` 权限（系统签名级），以"spy window"身份参与命中测试：与应用并行收到同一事件流的只读副本，不消费、不阻塞应用分发；要接管时另调 `pilferPointers()`。三个生产级用户：

- **SystemUI 的手势导航**：边缘返回手势的"先并行观察、成立再接管"；
- **屏下指纹**：SystemUI 的指纹 overlay 窗口经监视通道直接收取指纹区域的触摸，处理完送指纹 HAL，事件不进应用窗口分发（按 AAOS13 源码核对，`UdfpsController` 的触摸处理路径）——"指纹区域的触摸不触发下面的按钮"正是监视窗口在系统侧截流的体现；
- **无障碍/输入相关的全局监听**：`dumpsys input` 的 `Global monitors on display N` 段列出的就是各屏监视者。

区别的工程含义：监视窗口的回调不影响应用的事件流，适合"观察判断后可能抢夺"的系统交互；如果需求只是观察（统计、录制），监听副本即可；如果需求是拦截替代，要么走接管路径，要么用全局 `InputFilter`。应用没有创建监视窗口的入口，见到"我的窗口收不到某个区域的触摸"时应先查是否被系统监视者接管。

**Q7: 窗口级指针捕获（pointer capture）和应用级有什么关系？窗口失焦会怎样？**

`Window.requestPointerCapture()` 请求后，该窗口获得全部指针事件（鼠标移动不再驱动全局光标，触摸板手势被跳过），事件 source 转为相对语义。窗口级的关键约束是：捕获要求窗口持有焦点，窗口失焦或焦点显示器切换时捕获被系统强制释放，应用通过回调感知（版本边界：Android 14+ 引入相对/绝对双模式 API，AAOS13 只有相对模式）。

与监视窗口的关系容易混：捕获是"把指针独占给我"（点对点、排他），监视是"给我一份副本"（并存）。游戏鼠标视角用捕获，系统手势用监视。

车机意义有限但排查会遇到：带触摸板/鼠标的车机（如办公模式、开发调试接鼠标）上，捕获状态残留会表现为"光标消失、点击异常"，先查该窗口是否持有焦点、捕获是否被释放——`dumpsys input` 的窗口信息里有指针捕获状态字段。

**Q8: 拖放（drag and drop）在框架层是怎么实现的？谁在驱动事件？**

应用调用 `startDragAndDrop()` 后，WMS 建立拖放会话并把状态写入 InputDispatcher 的 `DragState`：拖动过程中的指针事件由分发器以拖放语义投递给拖拽发起窗口与悬停目标窗口，目标窗口收到 `ACTION_DRAG_ENTERED/LOCATION` 等拖放事件而非普通触摸（按 AAOS13 源码核对，`dispatcher/DragState.cpp` 与分发器的拖放事件路径）。会话结束（释放指针或超时）时清理状态并按结果通知双方。

对排查的启示：拖放进行中原窗口失焦、拖拽发起进程被杀、目标窗口销毁，都会让会话异常终止，表现是"拖着的卡片消失"且双方收不到结束回调。区分"拖放事件"与"触摸事件"的日志标志是 action 类别（`ACTION_DRAG_*` 走独立编号段），`dumpsys input` 里能看到活动拖放会话。

应用侧注意：拖放目标窗口必须声明可接受拖放的类型（`View.setOnDragListener` 在窗口层接受），否则悬停目标不变、事件不达——"拖到窗口上没反应"先查目标窗口的拖放监听注册，再查分发器层的会话状态。

**Q9: 每块屏幕的焦点是独立的吗？`setFocusedDisplay` 改变什么？**

独立。InputDispatcher 按显示器维护各自的焦点窗口与输入策略（Android 10 起的多屏输入支持），`setFocusedDisplay()` 切换"默认焦点屏"——影响的是没有携带 displayId 的事件（如某些注入与外设输入）去哪块屏，各屏已有焦点的窗口不受影响（按 AAOS13 源码核对，`InputDispatcher.h` 的 `mFocusedDisplayId` 与 `setFocusedDisplay` 接口）。窗口信息按屏推送，焦点请求也按屏保存；连 HOME 键的处理都按屏各有一份（策略层为每块显示器建独立的 Home 处理器），所以多屏设备上"哪块屏的 HOME"是按事件 displayId 决定的。

车机映射：主屏与仪表屏各有焦点窗口，VHAL 硬键经 CarService 标注目标显示后注入对应屏，各自独立分发；乘员屏（多 Zone 方案）同样按屏独立。折叠屏展开切换默认屏也是同一机制。

排查多屏按键问题时先问"这块屏的焦点窗口是谁"——`dumpsys input` 按屏列出焦点；按键"发到另一块屏"通常是注入时 displayId 缺省、落到了默认焦点屏，修法在注入端显式指定 displayId，而不是改焦点。

**Q10: 触摸模式（touch mode）是什么？为什么旋钮/按键界面要关心它？**

触摸模式是全局状态：设备一旦被触摸，系统进入触摸模式（焦点可不在任何可聚焦 View 上）；方向键/轨迹球/旋钮等非触摸输入会把设备切回非触摸模式，此时必须有焦点 View 存在（按键和导航事件才有落点）。应用侧 `View.isInTouchMode()` 可查，`ViewRootImpl` 收到系统的触摸模式变更消息后同步 View 树状态，`TOUCH_MODE` 变更经输入通道传递。

它解释几个经典现象：触摸列表后按方向键，第一次按键可能只是"把焦点放回列表"而不滚动（触摸模式切回非触摸模式时焦点重置）；按钮在触摸模式下点击不改变焦点，键盘导航时才看到焦点框。TV 与车机旋钮界面要求关键控件 `focusableInTouchMode`，就是为了在混合输入下保留焦点状态。

设计纪律：旋钮/按键为主的车机界面应在布局里声明初始焦点（`requestFocus` 或 FocusArea 的 defaultFocus），不要依赖"用户先按一下方向键"来建立焦点——首次进入界面时处于触摸模式或无焦点状态，按键会没有落点。

**Q11: 分发链上的误触抑制与事件分类组件是干什么的？没有分类硬件会怎样？**

InputReader 之后、InputDispatcher 之前有一段监听链（Android 13 为 `InputReader → UnwantedInteractionBlocker → InputClassifier → InputDispatcher`）。`UnwantedInteractionBlocker` 做无意触碰抑制（典型是手掌边缘误触的模型判断）；`InputClassifier` 做运动事件分类，输出 `MotionEvent.setClassification()` 可读的分类结果——`CLASSIFICATION_DEEP_PRESS`（重压，用于加速长按类交互）、`CLASSIFICATION_AMBIGUOUS_GESTURE`（歧义手势，会放大 slop 并延后长按）。分类能力来自 `android.hardware.input.classifier` HAL；设备没有该 HAL 时分类恒为 `CLASSIFICATION_NONE`，应用读到的永远是默认值（按 AAOS13 源码核对，分类器在无 HAL 设备上直通）。

版本边界：Android 14 起分类组件由 `InputProcessor` 承担，Android 15 链上增加 `PointerChoreographer`（统一指针呈现）；AAOS13 树上不存在这两个组件。做版本兼容的组件（如依赖深压分类的交互）必须处理"分类恒为 NONE"的回退路径，不能把重压交互建立在"一定有分类"的假设上。

排查应用侧线索：`MotionEvent.getClassification()` 返回值异常或恒为 NONE 时，先确认设备是否存在 classifier HAL（`dumpsys input` 可见监听链组件），再看是否是版本差异，最后才是交互代码问题。

**Q12: "这个点被谁接走了"——事件流向的窗口级排查怎么做？**

按分发器记录的字段逐层对照（`dumpsys input` 为入口）：

1. **窗口清单**：`Windows:` 段每个窗口的名字、displayId、`touchableRegion`、ownerPid/Uid、`dispatchingTimeout` 与变换矩阵——确认目标窗口在列、区域覆盖出问题的坐标、超时配置正常；
2. **监视者**：`Global monitors on display N` 段确认是否有系统监视者覆盖该区域（手势导航、指纹、无障碍）；
3. **触摸状态**：发生中的手势看连接段——`OutboundQueue`/`WaitQueue` 计数说明事件已选出目标但未完成（队列归属哪个窗口，目标就是谁）；
4. **注入对照**：`adb shell input tap x y` 注入同坐标，观察是否复现，排除"硬件报点偏移"（若注入行为正常而真机触摸异常，问题在触摸侧上游的设备绑定与坐标映射层）。

多屏设备务必带 `-d` 或按 displayId 过滤，先确认坐标在哪块屏——跨屏误判会让后续全部排查白做。这个四步法定位的是"窗口级"一层；若注入有效而真实触摸无效，问题在窗口之前的链路，要转去查设备接入与坐标映射。

**Q13: 副驾屏/仪表屏的触摸"完全没反应"，分发侧有哪些可能原因？**

分发侧按"可用性 → 遮挡 → 焦点"收敛（若注入有效而真实触摸无效，问题在设备侧上游的绑定与校准，不是本层）：

- **窗口可触摸性**：目标屏上的窗口是否带禁触摸的输入配置（`DROP_INPUT` 类、安全标志）；`Windows:` 段的 `touchableRegion` 是否为空或未覆盖——多屏 letterbox、不可交互层（如系统遮罩）会把区域裁掉；
- **遮挡**：目标屏上是否盖着全屏的不可交互窗口（车机电源策略下的黑屏遮罩、分心限制触控锁定遮罩）——遮挡校验判"被完全遮住"的窗口不参与命中，触摸被遮罩层接住或直接丢弃；
- **焦点与显示状态**：该屏是否处于熄屏/省电状态（分发器对非活动屏的事件处理受显示状态影响）；按键类还要确认该屏焦点窗口存在（无焦点窗口的按键不会自动换屏）；
- **监视者抢占**：目标屏上的全局监视者（该屏自己的手势导航、无障碍）是否接管了指针——`Global monitors` 按屏列出，逐屏确认。

区分口诀：触摸没反应且 `getevent` 正常、注入也无效 → 分发侧（上面四条）；注入有效而真实触摸无效 → 设备侧上游（绑定与校准）。车机上"某块屏时好时坏"优先怀疑电源策略与分心遮罩的时序，而不是输入配置。

**Q14: 焦点请求是持久化的——这个语义会带来什么反直觉行为？**

`setFocusedWindow` 的普通请求"存下来直到达成"：窗口发起请求时若不可获焦，请求不会作废，而是被保存，等它变得可获焦的那一轮窗口更新时补授予；授予瞬间当前焦点窗口失去焦点，未完成的按键事件进入待发队列等新焦点就绪。另一类带焦点令牌的条件请求则相反——不持久，条件不满足即撤销（按 AAOS13 源码核对，`FocusResolver` 的策略注释与数据结构）。

反直觉都来自持久化：其一，**延迟生效**——应用在启动早期（窗口尚不可获焦时）调用了 `requestFocus`，几秒后焦点"莫名"跳到它身上，其实是当年那笔请求终于达成；其二，**意外的焦点回归**——当前窗口失焦（被遮挡、退出、变不可获焦）后，焦点优先尝试满足此前保存的请求，于是"焦点跳到一个谁都没点的旧窗口"的案例，根因往往是某个 SDK 或无障碍服务曾代表它请求过焦点；其三，**重复请求幂等但不撤销**——请求没有被窗口主动取消的概念，靠的是窗口状态变化后的重新评估。

排查焦点漂移问题把这三条当检查表：先确认漂移目标窗口是否有过 `requestFocus` 调用（含框架内部调用，如 EditText 获得触摸焦点时的请求）；再对照失焦时序（谁先失焦、请求是否正好可获焦）；最后区分请求类型——条件请求的漂移一定是即时的，持久请求的漂移可以滞后任意久。`dumpsys input` 的焦点状态按屏列出当前结果，配合应用侧请求日志对时序。
