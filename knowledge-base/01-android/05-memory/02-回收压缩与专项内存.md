# 回收压缩与专项内存

> 学习资料（文章模式沉淀）。主线：终结引用与 Cleaner 的兜底清理边界、物理页规整与直接回收的性能归因、ZRAM 压缩交换与写回预取、ARM MTE 内存标签、跨进程共享内存与端侧推理内存预算。源文档：android-internals-wiki §4.6《ART FinalizerDaemon、Cleaner 与 ReferenceQueue》、§4.7《内存规整与直接回收性能边界》、§4.8《ZRAM 压缩交换与应用重启延迟》、§4.9《ARM MTE 内存标签扩展实战》、§4.10《跨进程内存共享与端侧推理预算》；机制按本地 AAOS13 源码（Android 13）核对，与材料 Android 17 语境的差异（FinalizerDaemon 的 Cleanable 分支、SystemCleaner 执行线程、MMD、NpuManager 与 App Functions）已标注；`Cleaner` 与 `SystemCleaner` 自 API 33 起公开、`ApplicationExitInfo.REASON_FREEZER` 自 API 33（Android 13）可用已按本地源码 API 清单核对。内存全景、ART GC、lmkd 与缓存进程冻结见 [01-内存管理与压力治理.md](./01-内存管理与压力治理.md)。Q 序列即结构，供 atlas 同源直读。

**Q1: 看到 FinalizerDaemon 忙或文件描述符上涨时，GC、ReferenceQueueDaemon、FinalizerDaemon 与应用代码各自负责什么？为什么不能用"GC 发生过"证明资源已释放？**

四个角色分工不同：ART 的引用处理判定可达性并生成待处理引用；ReferenceQueueDaemon 把待处理引用转移到目标队列；FinalizerDaemon 串行执行 `finalize()`；应用代码负责在明确的生命周期边界关闭资源。前三者是运行时机制，兜底执行的时间不确定，最末项才是资源所有权。

按 AAOS13 源码核对（`libcore/libart/src/main/java/java/lang/Daemons.java`），进程内常驻四个守护线程：HeapTaskDaemon、ReferenceQueueDaemon、FinalizerDaemon、FinalizerWatchdogDaemon。链路是：GC 判定不可达但需要后续处理的对象成为 pending 引用 → ReferenceQueueDaemon 从静态字段 `ReferenceQueue.unenqueued` 取链转移 → 终结引用落到 `FinalizerReference.queue` → FinalizerDaemon 逐个执行 `finalize()`。每一步只推进"引用"，不执行资源关闭。

因此，GC 是否发生只说明引用机制在运转：应用若把释放寄望于 `finalize()`，关闭时机由 GC 与调度决定，进程结束前来不及执行就直接丢失。主路径必须是显式关闭（Java 的 try-with-resources、Kotlin 的 `use`），终结与 Cleaner 只是兜底。

**Q2: 可终结对象的 FinalizerReference 为什么有"head 链表"与"queue"两套结构？`get()` 返回的 zombie 是什么含义？**

每个需要执行 `finalize()` 的对象注册时会生成一个 FinalizerReference 节点；"全部可终结对象链表"与"待终结队列"是两套独立结构。按 AAOS13 源码核对（`libcore/luni/src/main/java/java/lang/ref/FinalizerReference.java`）：静态字段 `queue` 是共享的 ReferenceQueue；`LIST_LOCK` 保护的 `head` 链表覆盖堆内所有可终结对象，此时对象可能仍然可达；只有 GC 判定对象不可达后，节点才进入 `queue`。

`FinalizerReference.get()` 返回的是 `zombie` 字段而不是普通的 referent：GC 判定对象需要终结时，把对象从 referent 移到 zombie，让它在 `finalize()` 执行前保持可访问。zombie 是源码字段名，只表示"等待终结期间被保留"，不表示资源已释放。

Java 允许终结方法把对象重新挂回可达对象图，称为对象复活。复活不会让终结机制变成可靠的复用协议，只会显著增加生命周期推理难度，工程代码应禁止这种做法。

**Q3: 待处理引用如何从 GC 转移到 FinalizerDaemon？为什么进度计数器不能当队列长度读？**

GC 产生的 pending 链表挂在静态字段 `ReferenceQueue.unenqueued` 上；ReferenceQueueDaemon 在 `ReferenceQueue.class` 上等待，取到链后先置空全局字段，再调用 `ReferenceQueue.enqueuePending(list, progressCounter)` 把引用转移到各自目标队列，终结引用的目标就是 `FinalizerReference.queue`，随后由 FinalizerDaemon 串行消费。以上转移与批处理逻辑按 AAOS13 源码核对（`libcore/ojluni/src/main/java/java/lang/ref/ReferenceQueue.java`）。

`enqueuePending()` 按"相邻同队列"合并加锁区间：连续指向同一队列的引用在一次 synchronized 区间内处理，批内以 `MAX_ITERS = 100` 限制规模，结束后 `notifyAll()` 唤醒消费者。进度计数器按批递增（旧式 `sun.misc.Cleaner` 每处理一个递增一次），FinalizerDaemon 另有自己的计数器，两者互不共用。

这个计数器只是看门狗判断守护线程是否仍在推进的内部活性信号，不是公开的队列长度，也不是性能指标；排查积压时应回到资源计数、线程栈与日志。

**Q4: FinalizerWatchdogDaemon 判定超时的条件是什么？Android 13 与 Android 17 的判定方式有何差异？**

看门狗同时监控 FinalizerDaemon 与 ReferenceQueueDaemon 是否长时间无进展，超时值来自 `VMRuntime.getFinalizerTimeoutMs()`，受厂商配置与版本影响，不应写成固定秒数。确认超时且调试器未连接时，它先给本进程发送 SIGQUIT 保留原生线程栈，再把超时异常交给未捕获异常处理，由 Zygote 派生的进程通常随之崩溃终止。

按 AAOS13 源码核对（`Daemons.java` 的 `waitForProgress()`）：一次观察先睡满整个超时窗口；若 FinalizerDaemon 的进度计数器未变且仍处于被监控状态，再补睡 500 ms 复查一次，仍未推进才构造 `TimeoutException`，并带上正在执行的 `finalize()` 调用栈。ReferenceQueueDaemon 则按容忍计数处理：`TOLERATED_REFERENCE_QUEUE_TIMEOUTS = 5`，同一段未完成处理期间第 6 次被观察超时才判定失败——容忍存在的原因是该线程只在批次边界推进计数器。

版本边界：材料按 Android 17 核对的"超时窗口分 5 次唤醒、每次比较计数"是 A17 的调度方式；Android 13 是整窗口单次睡眠加 500 ms 复查。"容忍 5 次"的行为两者一致。另外 Android 13 的 FinalizerDaemon 只处理终结引用；材料描述的"FinalizerDaemon 同时执行 SystemCleaner 的 Cleanable 并用 `reachabilityFence()` 收尾"在 AAOS13 的 `Daemons.java` 中不存在，属于 Android 14 之后的演进。

**Q5: `sun.misc.Cleaner`、`java.lang.ref.Cleaner` 与 `SystemCleaner` 三种 Cleaner 路径的执行线程与异常边界有何不同？**

三条路径的线程归属和故障隔离不同，混写会直接导致线程归因错误。按 AAOS13 源码核对：`sun.misc.Cleaner` 是平台内部实现，`ReferenceQueue.enqueuePending()` 识别到它的占位队列后不入普通队列，直接在 ReferenceQueueDaemon 线程调用 `clean()`——它的慢动作会卡住全进程的待处理引用转移；`java.lang.ref.Cleaner.create()` 每次 创建一个由 CleanerImpl 管理的守护线程，清理动作抛出的 Throwable 被该线程捕获忽略（按 `jdk/internal/ref/CleanerImpl.java` 核对），一个动作阻塞只影响同一 Cleaner 上后续注册的动作。

SystemCleaner 提供进程共享实例，但执行线程有版本差异：Android 13 的 `SystemCleaner.cleaner()` 经 `CleanerFactory` 返回共享 Cleaner，运行在自己的 "Common-Cleaner" 守护线程上（按 `android/system/SystemCleaner.java` 与 `jdk/internal/ref/CleanerFactory.java` 核对）；材料按 Android 17 核对的行为是经隐藏入口把队列接到 `FinalizerReference.queue`，与 `finalize()` 共用 FinalizerDaemon 并受看门狗监控，未捕获异常通常导致进程崩溃。分析线程栈时按目标版本归因。

三条路径都只保证清理动作至多执行一次，不保证 GC 触发时间，也不保证动作一定在进程退出前执行。应用不应通过反射或隐藏 API 依赖 `sun.misc.Cleaner`。

**Q6: 资源包装类怎样才能让 Cleaner 兜底真正生效？为什么清理动作不能捕获所有者？**

Cleaner 只在所有者进入虚可达状态（强、软、弱引用都不可达）后才自动执行；如果清理动作直接或间接引用了所有者，所有者恒为强可达，自动清理永远不会发生。所以主路径必须是显式关闭，Cleaner 只处理遗漏：所有者明确、`close()` 幂等、正常/异常/取消路径都关闭，兜底动作保持快速且不执行 I/O、IPC 或网络（SystemCleaner 是全进程共享的，慢动作会挡住后续共享清理）。

最小写法是把句柄放进静态嵌套的 State 对象，用 `AtomicLong.getAndSet(0)` 保证只释放一次：

```java
final class NativeSession implements AutoCloseable {
    private static final Cleaner CLEANER = SystemCleaner.cleaner();

    private static final class State implements Runnable {
        private final AtomicLong handle;
        State(long handle) { this.handle = new AtomicLong(handle); }
        @Override public void run() {
            long value = handle.getAndSet(0L);
            if (value != 0L) { nativeRelease(value); }
        }
    }

    private final State state;
    private final Cleaner.Cleanable cleanable;

    NativeSession(long handle) {
        state = new State(handle);
        cleanable = CLEANER.register(this, state);
    }

    @Override public void close() { cleanable.clean(); }

    private static native void nativeRelease(long handle);
}
```

`State` 不持有 `NativeSession`：显式 `close()` 在调用线程立即释放；遗忘关闭时才由 Cleaner 延迟兜底。若释放本身可能等待 Binder、磁盘或不可控锁，就不适合放进共享 Cleaner，应设计成可显式等待的业务操作。版本边界：`java.lang.ref.Cleaner` 与 `SystemCleaner` 自 API 33（Android 13）公开；更低版本不能假设存在公共 Cleaner，也不应把隐藏的 `sun.misc.Cleaner` 当兼容方案。

**Q7: CloseGuard 和 StrictMode 在资源泄漏排查中各自回答什么问题？**

CloseGuard 回答"资源在哪里获取却没有关闭"，StrictMode 负责在开发和持续集成阶段更早暴露这类错误；两者都只报告，不释放资源，也不保证告警何时出现。

`android.util.CloseGuard` 自 API 30 起公开，典型顺序是：获取资源后 `open("close")` 记录获取位置、显式关闭时调用 `close()`、兜底检查阶段调用 `warnIfOpen()`。StrictMode 的 `VmPolicy.detectLeakedClosableObjects()` 自 API 11 起提供，用于发现 `Closeable` 未显式关闭就走到终结处理，配置后输出进入日志。

设置 VM policy 会整体替换当前进程策略，多个模块各自调用会互相覆盖，应在统一的调试初始化入口合并检测项。只记录告警而不修复所有权，fd 与原生内存仍会继续增长；生产环境是否启用、采用日志还是更强的 penalty，要结合噪声、性能与隐私要求评估。

**Q8: 终结队列堆积为什么会表现为"Java 堆不大、原生内存与文件描述符持续上涨"？**

对象进入终结处理后，`FinalizerReference.zombie` 会在 `finalize()` 开始前保留它；Java 包装对象可能很小，但它代表的资源可能很大——文件与套接字的 fd、SQLite 游标与 CursorWindow、原生解码缓冲区、GraphicBuffer/ImageReader/Surface、JNI 全局引用及其保活的对象图。浅层大小只统计对象本身的 Java 堆占用，按它排序会漏掉间接持有的原生与图形资源。

FinalizerDaemon 是单线程串行执行，队首的慢任务会推迟同一队列后面的所有工作。慢清理一般不直接运行在主线程，却仍会与主线程争抢 CPU、持有主线程需要的锁、发起 Binder 或文件系统操作、推迟 fd 与图形缓冲区归还，被看门狗判定超时还会导致进程崩溃。

判断积压要看生成速度是否长期高于消费速度（例如每轮固定操作后 fd 净增不回落），不能用固定公式预测线上延迟，因为 GC 触发、线程调度和清理耗时都在变化。

**Q9: 定位终结积压时，线程栈、Perfetto、simpleperf 与堆转储各自能证明什么？**

按"先证明增长、再定位执行点"推进：固定一轮业务操作反复采样 fd、原生堆与图形内存，确认净增趋势后再用工具收窄。`/proc/<pid>/fd` 在量产设备上可能被权限和 SELinux 拦截——"命令被拒绝"不能写成"文件描述符没有增长"，此时用可调试构建或应用自建计数。

线程栈回答"谁在执行"：FinalizerDaemon 停在某类 `finalize()` 说明该类兜底代码正在追赶；停在某次共享清理动作说明该动作偏慢。修复点仍是显式生命周期，而不是让守护线程跑得更快。Perfetto 回答守护线程何时获得 CPU、运行区间是否与掉帧重叠；simpleperf 适合在 CPU 异常时找热点，但阻塞型问题可能没有明显热点；两者都不提供引用队列长度，Perfetto 也没有公开的 `FinalizerReference.queue` 深度计数器。堆转储适合比较资源包装对象的实例数、查所有者的保留关系，但生成 HPROF 本身会触发暂停，也不能直接证明"这些对象都不可达、只是在等待终结"——结论要与 fd 计数、日志和线程栈互相印证。

**Q10: order 描述什么？为什么"回收出了很多页"仍可能救不了高阶分配？**

order 是伙伴系统中"连续物理页数量 = 2^order"的指数，order-0 就是一个基础页。回收（reclaim）解决"可用页数量"，规整（compaction）通过迁移可移动页把分散空闲页合并成连续块，解决"连续性"；两者目标不同，回收得到的多个 order-0 页物理位置未必相邻，高阶分配仍可能失败。

需要高阶连续物理页的主要是内核对象、透明大页或大型 folio、CMA 和特定驱动路径，而不是普通应用的大对象：大块 `malloc()` 或 Java 大数组申请的是连续虚拟地址，缺页时通常逐页获得 order-0 物理页。图形与多媒体缓冲区是否要求物理连续，还取决于 IOMMU 是否支持地址重映射、使用的 DMA heap 和驱动实现。

诊断时要先确认事件属于哪一层：物理页规整、页面回收、ZRAM 压缩、Android 缓存应用页面回收（`CachedAppOptimizer` 的 `madvise`）是四种不同操作，Perfetto 中的 `Compaction` 字样既可能来自 Framework 的 ATrace，也可能来自内核 `mm_compaction_*` 跟踪点。

**Q11: 直接回收与直接规整都会拖慢分配线程，两者的顺序和 PSI 计入方式是什么？**

材料按 Android 17 内核（android17-6.18）核对：部分高阶分配在进入直接回收之前会先尝试直接规整，常规重试则先执行 `__alloc_pages_direct_reclaim()`、仍失败再 `__alloc_pages_direct_compact()`；两类同步操作都在发起分配的线程上下文执行，直接延长该请求的墙钟时间。order-0 的普通缺页可以触发直接回收，但不进入直接规整入口，所以主线程缺页卡顿应优先检查直接回收的证据。

两类操作的停顿时间都经 `psi_memstall_enter()`/`psi_memstall_leave()` 计入内存 PSI。PSI 的 some/full 只说明任务因内存短缺停顿，不区分回收、规整还是 swap I/O，归因必须叠加内核跟踪点（`mm_vmscan_*`、`mm_compaction_*`）与 `/proc/vmstat` 的区间增量；`compact_success` 增长只说明规整后取得了目标页面，不代表没有延迟。版本边界：本地 AAOS13 树不含内核源码，以上分支顺序以材料核对的 Linux 6.18 语境为准，具体分支受内核版本影响；lmkd 作为独立用户态进程不在这条内核慢路径上。

**Q12: `vm.compaction_proactiveness` 等规整参数怎么理解？调参实验要遵守什么纪律？**

`kcompactd` 是每个内存节点的后台规整线程，`vm.compaction_proactiveness`（0–100，通用内核默认 20，按材料核对的 Android 17 内核文档）控制主动规整的积极程度：0 只关闭主动规整，不关闭分配请求驱动的直接规整；写入非零值本身会立即触发一次规整。主动规整用相对大页 order 的外部碎片分数判断，kswapd 正在运行时会跳过，避免两类后台内存工作争用。

配合参数还有 `vm.extfrag_threshold`（0–1000，默认 500，只参与高成本阶数的规整适用性判断，与主动规整的 0–100 分数不是同一个量）和 `vm.compact_memory`（写 1 手工规整全部节点，只适合受控实验）。读取 `extfrag_index` 需要 debugfs 与权限，量产设备通常拿不到——采集失败不能换算成碎片程度。

调参必须是可回滚的单变量实验：用业务指标定义目标，固定设备、构建、温度与工作负载并先采基线；每轮只改一个参数、记录原值并在测试后恢复，写入瞬间不能当稳态样本；同时比较前台延迟分位数、kcompactd CPU 时间与能耗，恢复默认后复测排除假收益。`drop_caches` 不执行规整还会制造额外缓存未命中，不适合用来重置实验。

**Q13: 分析"应用重新打开变慢"时，为什么必须先确认原进程还在？用什么证据区分换入恢复与冷启动？**

两种场景的成本结构完全不同：进程存活、部分匿名页在 ZRAM 中，是换入恢复，成本是缺页、解压和可能的后备设备读取，ZRAM 与本次恢复直接相关；进程已被 lmkd 或其他机制终止，则是冷启动，要付出创建进程、初始化运行时、加载代码资源、重建组件的全部代价，旧进程的 ZRAM 页面随交换槽位清理，不再构成新进程的恢复路径。

证据链按序取：记录恢复前后 PID 是否变化；确认 Activity 启动类型；Android 11（API 30）起用 `ApplicationExitInfo.getHistoricalProcessExitReasons()` 读退出原因，其中 `REASON_FREEZER` 对应冻结器相关退出（自 API 33 可用，AAOS13 源码中取值 14）；部分设备无法可靠报告低内存终止原因，可用 `ActivityManager.isLowMemoryKillReportSupported()` 判断后再结合日志与 `dumpsys activity`。用户"感觉像冷启动"只是体验描述，不能证明进程发生过重建。

**Q14: 匿名页为什么要换出到 ZRAM？页面在 ZRAM、后备设备与交换缓存三种位置时恢复成本差在哪？**

匿名页没有可直接重读的文件后备，Java 堆、原生堆和匿名 `mmap()` 的数据都属于这一类；要在释放物理页的同时保留进程状态，只能把页写入交换空间。Android 通常把 ZRAM 块设备作为交换设备：回收器选中页 → 分配交换条目 → ZRAM 按页接收并压缩 → 压缩对象存入 zsmalloc → 页表保留条目、原物理页释放。整个过程用 CPU 时间换容量，ZRAM 自身还消耗内存（分配器碎片与元数据），不能把 `SwapTotal - SwapFree` 直接当节省的物理内存。

恢复成本按页面当前位置分级：仍在 ZRAM 内存中，缺页付出调度、查找、分配目标页与解压，瓶颈是 CPU 与内存带宽；已写回后备设备（/data），还要叠加块 I/O，瓶颈是存储延迟与队列竞争；命中交换缓存则可能复用内存中的页，只剩页表更新。所以 `VmSwap` 相同的两个进程恢复耗时也可能不同，还要结合页面是否已写回、首帧前访问集中度以及设备当时的 CPU 与存储负载。

**Q15: Android 13 的 ZRAM 写回与 Android 17 引入的 mmd 有什么机制差异？写回会给进程带来什么保护？**

Android 13 没有 mmd：ZRAM 写回由系统服务 `ZramWriteback`（`frameworks/base/services/core/java/com/android/server/ZramWriteback.java`，按本地源码核对）承担，它是一个 JobService，用两个 JobScheduler 周期任务工作——`MARK_IDLE_JOB_ID = 811` 标记空闲页、`WRITEBACK_IDLE_JOB_ID = 812` 执行写回，参数走系统属性。Android 17 引入内存管理守护进程 mmd（`system/memory/mmd`，AAOS13 树中不存在），把 ZRAM 配置、重压缩、写回与按进程预取统一交给原生守护进程，由 system_server 经接口调度；启用后旧资源覆盖项与 `ro.zram.*` 写回属性被忽略。

mmd 时代的进程级协作（按材料核对）：缓存进程冻结并完成页面回收后，system_server 以 pidfd 标识目标进程请求按进程写回；写回成功后 ActivityManager 标记该进程，下一轮 OOM 调整用 `min(adj, zramWritebackAdj)`（AOSP 默认 249）计算只发给 lmkd 的优先级分值，进程在已写回状态下获得更强保护，解冻时标记清除；进程因 Activity 激活解冻时再请求预取已写回条目。pidfd 用于避免整数 PID 复用误伤。排障先确认设备用哪套方案，不能只查旧属性。

**Q16: 为什么"换出总量"预测不了 ZRAM 恢复延迟？预取能解决多少？**

恢复不会一次读回全部换出页：只有 CPU 执行到某条指令、访问尚未驻留的虚拟页时才发生缺页。长尾取决于首帧前触碰了哪些热页——Activity 与 View 状态、首屏 Bitmap 与图形资源相关匿名数据、分配器热点元数据、数据库连接与业务索引、Binder 恢复后立刻消费的数据。同样是 100 MiB SwapPss，首帧前访问 5 MiB 热页与 40 MiB 热页的体验完全不同，所以 `SwapPss` 描述当前归属，不足以预测恢复成本。

此外，ZRAM 解压消耗 CPU，写回与预取要访问 /data 后备设备，可能与主线程、RenderThread、APK/DEX 读取争用；即使单次缺页很短，数百次分散缺页仍会形成明显长尾。MMD 的按进程预取（存在该机制的设备上）在 Activity 解冻时异步读回相关条目，只能减少后续同步缺页等待，不保证全部页面在应用访问前就绪。对比不同页大小的设备时按字节归一化统计，不直接比较交换槽位数量——16 KiB 页设备一个槽位对应 16 KiB 未压缩内容。

**Q17: ARM MTE 检测内存错误的原理是什么？为什么说它是概率性检测？**

MTE 为每 16 字节的标签粒度保存一个 4 位分配标签，并把指针虚拟地址的 bits[59:56] 作为逻辑标签；CPU 访问标签内存时比较两者，不匹配则按当前线程的检查模式报告。它能发现的空间错误是越过 16 字节粒度边界访问相邻数据，时间错误是内存释放重分配后换了标签、旧指针继续访问。

概率性来自两点：4 位标签只有 16 种取值，错误访问可能猜中标签——偏重释放后使用的独立随机标签策略给出的均匀检出概率约为 15/16（约 93%）；越界访问仍落在同一 16 字节粒度内时，没有标签边界可以触发检查。因此 MTE 是原生内存错误的检测与缓解手段，不能证明程序不存在内存错误。

MTE 只检查使用标签内存的访问：Java/Kotlin 对象由 ART 管理，32 位进程、未启用 `PROT_MTE` 的映射、没有正确设置标签的自定义分配器都不在保护范围内。判断设备能力应直接查询（如 `adb shell grep -w mte /proc/cpuinfo`），不能由 SoC 宣传名称或 Android 版本反推；部分设备还需要开发者选项重启到支持 MTE 的配置。

**Q18: MTE 的 SYNC、ASYNC 与 ASYMM 三种模式在报告行为和适用场景上有什么差别？**

SYNC 在发生不匹配的那条指令上同步报告：SIGSEGV 加 `SEGV_MTESERR`，si_addr 为故障地址，该次访问不完成；tombstone 可以给出出错 PC 与地址，Android 还会让 Scudo 记录内存分配与释放调用栈补充上下文，适合开发测试和需要准确归因的高价值进程。ASYNC 允许 CPU 继续执行，在之后的时刻报告：`SEGV_MTEAERR` 且 si_addr 通常为 0，故障地址与触发指令一般无法准确恢复，适合开销较低的生产检测——发现问题后应回到 SYNC 复现。ASYMM 对读同步、对写异步，性能接近 ASYNC 且能定位读错误。

应用 manifest 只接受 `off`、`default`、`sync`、`async`，没有 `asymm` 值：Bionic 在请求 ASYNC 时把 `PR_MTE_TCF_ASYNC | PR_MTE_TCF_SYNC` 两个模式位一并交给内核，内核可结合 CPU 首选模式（sysfs 的 `mte_tcf_preferred`）选择实际执行模式。开销没有通用百分比——硬件检查、Scudo 标签管理和 SYNC 调用栈记录的成本随 CPU 与负载变化，评估时对同一发布构建分别跑 OFF、ASYNC 与 SYNC，比较帧长尾、CPU 时间、指令数与 RSS。

**Q19: Android 如何把 manifest 的 memtagMode 决策传给 Bionic 与 Scudo？运行时能改吗？**

应用进程由 Zygote 派生，堆标签级别按优先级取值后经 mallopt 交给分配器。按 AAOS13 源码核对（`Zygote.java`、`com_android_internal_os_Zygote.cpp`）：决策顺序为 `<process android:memtagMode>` → `<application android:memtagMode>` → 兼容性变更开关 `NATIVE_MEMTAG_SYNC` → `NATIVE_MEMTAG_ASYNC` → 应用显式关闭 TBI（`allowNativeHeapPointerTagging` 为 false 则 NONE）→ `persist.arm64.memtag.app_default`；进程派生时 `SpecializeCommon()` 调用 `mallopt(M_BIONIC_SET_HEAP_TAGGING_LEVEL, level)`（选项编号 -204，按 `malloc.h` 核对）。`ApplicationInfo` 的内部常量 `MEMTAG_DEFAULT=-1/OFF=0/ASYNC=1/SYNC=2` 属于隐藏实现，应用只应使用 manifest 字符串。

运行时 ASYNC 与 SYNC 可以反复切换，用于复现问题；从 NONE 重新开启不被支持，TBI 与 ASYNC/SYNC 之间也不能互换——按 AAOS13 的 `heap_tagging.cpp` 核对，重新启用会因现有指针与内存块无法安全恢复统一带标签状态而失败。策略应在进程启动时定好。

两个实现细节：Bionic 初始化把 `PR_MTE_TAG_SET_NONZERO`（非零标签掩码，按 `bionic_prctl.h` 核对为 0xfffe）交给 prctl，标签 0 留给 Scudo 分配块头，帮助捕获对分配器元数据的线性越界——这是 Scudo 的约定而非架构规则。版本边界：材料按 Android 17 核对的链首项 `persist.arm64.memtag.app.<package>`（按包名覆盖）在 Android 13 中不存在，A13 链从进程属性开始。

**Q20: 只设置 memtagMode 覆盖不了哪些内存？栈与全局变量 MTE 如何启用、怎么验证？**

`android:memtagMode` 只覆盖普通系统分配器管理的原生堆。栈 MTE 需要编译器为栈对象插桩，并在 ELF 中声明 `DT_AARCH64_MEMTAG_STACK`，由链接器与 libc 在启动或 `dlopen()` 时把线程栈重映射为 `PROT_MTE`；全局变量 MTE 需要编译器与 LLD 链接器生成 `DT_AARCH64_MEMTAG_GLOBALS/GLOBALSSZ` 描述符，链接器为可写数据段写入分配标签，文件映射不支持时复制到私有匿名映射（会失去文件页共享）。NDK 侧的编译链接选项是 `-fsanitize=memtag`、`-march=armv8-a+memtag` 与 `-fsanitize-memtag-mode=sync`，官方将这类插桩构建定位为调试用途。

验证顺序：确认设备 `/proc/cpuinfo` 有 mte；确认进程重启后处于预期模式——manifest 为 default 或未指定的应用可用 `adb shell am compat enable NATIVE_MEMTAG_SYNC com.example.app` 临时启用（ASYNC 对应 `NATIVE_MEMTAG_ASYNC`），下次启动生效；用 SYNC 复现 ASYNC 上报的场景；对照 tombstone 中 `SEGV_MTESERR` 的故障地址与分配/释放调用栈；保留 MTE 与 ASan/HWASan 的互补测试。

版本边界：Android 12 起 AOSP 平台与分配器系统性支持 MTE，AAOS13 已含决策链与 mallopt 通路（本地源码核对）；栈标签自 Android 14 QPR3 起面向应用，全局变量链接器支持与 Android 17 的 MTE ifunc 细节按材料核对，不能按本地树确认。

**Q21: 端侧推理的四种部署方式在内存归属与隔离强度上有什么差别？为什么推理进程不会自动获得优先级保护？**

四种部署的隔离依次增强：应用主进程内推理，内存计入主进程，无额外隔离；`android:process=":inference"` 独立进程，隔离地址空间与故障但通常仍是应用 UID——它适合把原生引擎崩溃限制在单独 PID，不能充当不可信模型代码的保密沙箱；`isolatedProcess="true"` 服务，使用系统分配的隔离 UID，权限与数据访问明显收窄，所需数据要通过受约束的 Binder 只传本次请求所需的 fd 与只读共享区；系统或厂商推理服务，用自己的 UID，边界由系统映像、SELinux 与服务协议决定。

不存在"正在执行 AI"的通用进程标签。AMS 按组件状态、绑定关系持续计算 `oom_score_adj`，推理内存变大不会直接调高或调低它——内存大小只影响终止后能释放多少，可能影响同一档位内的选择；系统托管服务（如设备上的 AICore，包名 `com.google.android.aicore` 不属于 AOSP）的生命周期与优先级由设备实现决定。拆分进程后要分别观察两个 PID 的状态与内存，`dumpsys activity processes` 与 `/proc/<pid>/oom_score_adj` 是直接证据。

**Q22: 用 Binder 传推理输入为什么容易失败？1 MiB、64 KiB 各是什么边界？**

Binder 的接收端映射由 libbinder 的 `BINDER_VM_SIZE` 决定：按 AAOS13 源码核对（`frameworks/native/libs/binder/ProcessState.cpp`）为 `(1 * 1024 * 1024) - sysconf(_SC_PAGE_SIZE) * 2`，约 1016 KiB，由该进程所有 Binder 线程的并发事务共享——请求、返回值、对象偏移表和并发事务都占用这块空间，不能理解成"每线程 1 MiB"。

平台建议的单事务安全大小是 64 KiB：AAOS13 中已是公开常量 `IBinder.MAX_IPC_SIZE = 64 * 1024`，方法 `getSuggestedMaxIpcSizeBytes()` 自 API 34 起公开（本地树中为隐藏静态方法）。超限事务抛出的 `TransactionTooLargeException` 是启发式异常：调用方无法可靠判断请求是否未送达，也可能是服务端已处理、返回值发送失败，所以接口要按"操作可能已部分完成"设计幂等。

按内容分工通道：命令、令牌与小结构走 AIDL/Parcelable；一次性大块字节用 `SharedMemory` 加 Binder 传 fd；图像、视频帧等硬件可导入数据用 `HardwareBuffer`；持久内容用 `ContentProvider` 加 URI。"通过 Binder 传 fd"仍会发送一个小 Parcel，共享的是 fd 指向的对象。

**Q23: SharedMemory 的 setProtect、close 与"零拷贝"各有什么语义边界？**

`android.os.SharedMemory` 实现 Parcelable 可经 Binder 传递，区域经原生 `ashmem_create_region()` 创建（按 AAOS13 的 JNI 实现核对）。`setProtect()` 只能移除权限、不能添加，返回 false 表示请求比现有保护更宽，且不改变已经建立的映射——所以"只读快照"的正确顺序是：`mapReadWrite()` 写入后 `unmap()` 解除本方可写映射，再 `setProtect(PROT_READ)`，最后发送；发送方若保留旧的可写映射，这块区域就不能称为不可变。fd 代表访问能力，拿到 fd 就能在保护范围内映射，发送前仍要校验 Binder 调用者身份、数据用途、长度与版本。

`close()` 只关闭当前对象持有的 fd，已经建立的映射继续有效；只有全部 fd 关闭且映射解除后，相关物理页才具备释放条件。最小示例：

```java
SharedMemory region = SharedMemory.create("inference-context", capacity);
ByteBuffer writable = region.mapReadWrite();
try { writable.put(payload); } finally { SharedMemory.unmap(writable); }
if (!region.setProtect(OsConstants.PROT_READ)) { region.close(); throw new IllegalStateException(); }
try { remote.consume(region, payload.length); } finally { region.close(); }
```

"零拷贝"要说明观察范围：发送方把源数组写入共享区、接收方再 `ByteBuffer.get(byte[])`、推理运行时把数据重排到自己的内存区、驱动导入失败后建私有暂存缓冲、可写私有映射触发 COW，都会产生复制或额外物理页。更准确的说法是"两个进程共享同一组页面"，用 PSS、缺页与驱动统计验证从输入到推理后端的完整路径。

**Q24: 图像帧、模型权重、结构化数据分别该走什么通道？CursorWindow 的默认大小是多少？**

按内容形态选择：图像帧已位于 gralloc 缓冲区且推理服务接受同一格式的 `HardwareBuffer` 时优先走硬件缓冲——前提是双方支持相同格式、尺寸与用途标志，HAL 或驱动能导入，并正确处理缓存一致性与同步栅栏；不要把它统称为"GPU 显存"。模型权重与文本上下文没有硬件导入协议，用 `SharedMemory` 或只读文件映射。需要数据所有权、权限与审计时用 `ContentProvider`：Cursor 只返回 id、类型、长度与内容 URI，二进制大对象用 `openFileDescriptor()` 流式读取，配合 URI 授权限定接收方与有效期。

CursorWindow 的实现按 AAOS13 源码核对：原生层（`frameworks/base/libs/androidfw/CursorWindow.cpp`）先使用至多 16 KiB 的进程内区域（`kInlineSize = 16384`），写入空间不足时才扩展为 ashmem 共享区域；构造参数 `windowSizeBytes` 是扩展后的上限，无参构造使用资源 `config_cursorWindowSize`（AOSP 默认 2048，即 2 MiB），因此"默认永远是 2 MiB"不能作为接口约束。

Android 16 起才提供的 App Functions（受控函数调用、响应内 URI 授权）在 AAOS13 中不存在，此处只作版本边界标注：Android 13 上的跨应用受控动作仍走 ContentProvider 或自定义 AIDL 接口。

**Q25: 一次端侧生成式推理的内存由哪些部分组成？权重和 KV cache 怎么估算？**

进程可见内存大致由六部分组成，任何一项都可能落在 Java 堆、原生堆、文件映射、共享内存或 dma-buf：权重与常量、KV cache 或循环状态、计算工作区、runtime 与业务对象、输入输出缓冲、allocator 与驱动保留。只写"模型占 1.4 GB"无法说明压力来源。

权重下限是 `P × q / 8`：2B 参数、4 位权重的纯权重约 0.93 GiB。但文件与运行时还包含量化 scale 与 zero point、张量元数据、词表、对齐填充和重排后的权重副本，不能按"INT4 就是 1.0 GiB"断言文件或 RSS；运行时对同一只读模型文件用 `MAP_PRIVATE` 时，未修改的文件页可通过页缓存共享，前提是没有解压、反量化、重排到私有缓冲，驱动也没有为每个会话复制设备侧权重。

KV cache 按 `2 × layers × kv_heads × head_dim × tokens × batch × bytes_per_element` 估算（因子 2 代表 K 和 V）：26 层、4 个 KV 头、每头 256 维、FP16、batch 为 1 时，1024 token 约 104 MiB，4096 token 约 416 MiB。MHA、GQA、MQA 对 KV 头的共享方式不同，分页 KV、滑动窗口、量化 KV 与多会话并发都会改变结果，参数应取自模型配置与运行时分配日志。

会话结束后 RSS 不立即下降有几种互斥解释：对象仍被引用、分配器留存已释放块、干净文件页仍驻留、驱动仍持有缓冲区——分别用堆转储、heapprofd、`dumpsys meminfo` 与驱动统计区分；重复执行"创建—运行—释放—施压"周期观察是否无上限增长，才能判断泄漏，进程 RSS 未回到初始值本身不是泄漏证据。
