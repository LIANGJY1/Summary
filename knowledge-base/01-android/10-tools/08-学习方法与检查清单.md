**Q1: Android 性能学习路线为什么围绕"记录现象、采集证据、解释机制、验证修改"四个动作组织，而不是按目录通读？**

因为这条路线的完成标准是复现能力而不是阅读量：章节阅读服务于当前实验，不以通读目录作为完成条件。每次练习都要保留原始数据、采集配置、设备状态、分析过程和复测结果——只有结论、没有可复查证据的记录，无法判断结论来自机制分析还是偶然波动。每个阶段有对应的验收方式：定义问题阶段随机抽排查卡片，要求说明某项数据如何支持或排除候选原因；Perfetto 阶段用一份未见过的 trace 写报告；优化阶段要求另一位工程师按文档复现实验并得到方向一致的结果；跨层案例要求标注 AOSP/ACK tag 与目标设备的差异。

两个基础区分要先行建立：trace 是按时间排列的事件记录，dump 是某一时刻的状态快照，两者提供的时间信息不同、不能互相替代；源码可以解释已经观察到的路径，却不能单独证明目标设备当时走过该路径，证据不足时应调整采集项后重测，而不是继续在代码里找解释。

**Q2: 分析 Android 性能时，源码版本坐标为什么要"平台 tag + 内核 tag"双锚点？读带版本烙印的旧文章时怎么处理？**

平台机制和路径以 AOSP tag 为准（如 `android-17.0.0_r1`），进入调度、Binder、内存回收或文件系统问题后切换到 ACK（Android Common Kernel）tag——两份代码分属不同仓库、演进节奏不同，单锚点会让内核结论落在错误版本上。tag 不可变，固定 tag 才能让不同时间的练习落在同一份代码上；分析旧记录时要先比较新旧 tag 的差异，再决定能否沿用源码结论。

AOSP 是参照系而不是设备事实：厂商可以修改 Framework、HAL、内核配置和性能策略，分析商用设备时要同时记录 build fingerprint、API level、内核版本、SoC、刷新率、电源模式和温控状态；AOSP 路径用于定位公共机制，不能代替目标设备上的 trace、配置与符号。读旧文章（如 2015 年的内存系列、2019 年的启动优化文章）用同一条纪律：把长期有效的系统机制与当时的操作步骤、阈值和工具界面分开理解，复现时以待测设备的 Android 版本、内核和厂商实现为准，复用观测思路而不照搬旧版本的策略或阈值。

**Q3: 开始一次性能排查前，"先固定测试条件"要记录哪些项？为什么必须留正常对照样本、把信号与原因分开记录？**

测试条件决定结论的可比性，至少记录四组：应用版本、构建类型、设备型号、Android 版本、API 级别、CPU ABI 和厂商系统版本；刷新率、电源模式、电量、充电状态与温控状态（性能模式和温度不同的两组结果不可直接比较）；复现步骤、复现概率、起止时间与用户可见现象，并为日志与 trace 保留同一时间基准；至少一组正常样本和一组异常样本，两组的机型、账号数据、网络与操作步骤尽量一致。

留正常对照的目的：异常样本只能说明"当时发生了什么"，与正常样本的差值才指向"哪里不同"；没有对照，单条异常证据既能支持也能反驳多个假设。把"观测到的信号"和"据此提出的原因"分开记录，是防止把假设写成事实：例如"主线程等待 Binder 回复 800 ms"是信号，"远端服务持锁"仍需远端线程或调度证据确认，混写会让后续排查沿着未经验证的原因走偏。

**Q4: 卡顿排查为什么要先确认渲染路径、再进 Perfetto 时间线？method tracing 为什么要先做无插桩对照？**

因为不同现象对应的采集范围不同：列表掉帧、动画停顿、点击无响应、画面撕裂各自要查的链路段不一样。排查顺序是：先确认页面使用标准 View、Compose、SurfaceView、TextureView 还是 OpenGL/Vulkan 直接上屏，是否有悬浮窗、Dialog、多窗口或画中画改变缓冲区数量与合成成本；再区分"应用没有按时产出画面"还是"已产出的画面迟迟没有显示"——前者优先查应用线程，后者要检查 SurfaceFlinger、GPU 与显示合成。进入时间线后，在 FrameTimeline 中定位用户看到的慢帧、确认 Actual 与 Expected Timeline，而不是先去搜一个耗时较长的函数；帧预算随刷新率取值（60/90/120 Hz 每帧约 16.7/11.1/8.3 ms），16 ms 不是所有设备的固定阈值。

method tracing 记录方法进入与退出，能提供调用级耗时，但开销可观、可能制造原本不存在的卡顿——启用后要先做一次无插桩对照，确认卡顿不是插桩引入的；定位策略是先用系统跟踪锁定区段，再对较小范围做方法级分析。

**Q5: 启动排查时，多套测量口径为什么要先对齐？只看到 base.odex 文件为什么不能证明 Baseline Profile 已被采用？**

因为同一轮排查里通常并存多套测量：`am start -W` 的 TotalTime、Logcat 的 Displayed、Macrobenchmark 结果和业务埋点，各自的起点与终点定义不同。不对齐口径，A 工具的"改善"和 B 工具的"回退"可能只是量的不是同一段；先明确冷、温、热启动类型，再让每个测量声明自己的起点终点，TTID（首帧显示）与 TTFD（关键内容可交互）回答的问题不同，混用会把内容加载时间错误地记进系统启动。

编译状态的检查同样要区分"文件存在"与"规则被采用"：`speed-profile` 表示正在使用按配置文件编译的代码；只看到 `/data/app/.../oat/.../base.odex` 文件存在，不能证明目标 Baseline Profile 规则已安装或被 ART 采用——用 ProfileVerifier 或 `dumpsys package dexopt` 检查编译状态。启动期创建的线程还要检查是否与主线程竞争 CPU：减少线程数之后应同时比较首帧时间和完整可用时间，避免只是把任务移到更晚的阶段。

**Q6: 内存问题为什么要先区分故障类型再定位？"锯齿曲线"和"基线抬升"分别指向什么？**

因为四类故障的证据和入口完全不同，混在一起排查会浪费采集资源：Java 堆 OOM 要记录 `OutOfMemoryError` 的异常消息、堆上限、失败分配大小和调用栈；原生分配失败要看 tombstone、malloc 日志与 Native Heap，不能用 Java 堆余量排除原生内存问题；进程被 LMKD 因系统内存压力终止时，应用内通常不会抛出 Java OOM，要用 `ApplicationExitInfo`（Android 11+）核对退出原因；文件描述符耗尽报 `EMFILE`（Too many open files），与堆 OOM 是两类问题。

先看整体再定位：`dumpsys meminfo` 里确认是 Java Heap、Native Heap、Graphics 还是 mmap 映射随复现步骤增长，PSS 便于估算进程对系统的贡献但不是某个堆的硬上限。曲线形态是分岔判断：多轮操作后基线持续升高，转向查泄漏——检查已关闭的 Activity/Fragment 是否仍可从 GC Root 到达、单例或监听器是否持有短生命周期对象；高频锯齿则查分配速率与 GC 暂停——确认 `onDraw()`、`onBindViewHolder()` 或重组热点里是否每次都创建临时对象。Heap Dump 中仍存活的对象不都是泄漏，要结合预期生命周期判断。

**Q7: 功耗问题为什么先按现象分类复现场景？哪些后台行为最容易成为"待机耗电"的来源？**

发热、前台续航缩短、后台静默掉电、待机无法休眠是四类不同的问题，需要不同的复现场景与对照条件；测量时固定亮度、刷新率、网络、信号、位置、音量、电量区间和温度，并保留正常对照。温度只能说明热量累积，不能单独指出耗电模块——发热要与持续 CPU/GPU 负载、蜂窝弱信号或充电时段对齐才能归因。

待机耗电的高频来源按链条检查：设备能否进入 Deep Sleep，不能时是哪个唤醒源、定时器、中断或唤醒锁覆盖了待机区间；`PARTIAL_WAKE_LOCK` 是否在异常、取消和超时路径都能成对释放；`AlarmManager` 是否高频唤醒——可延迟且退出应用后仍要执行的持久任务适合 WorkManager，日历提醒等精确的面向用户事件才需要 AlarmManager；周期性网络同步能否合并请求、增加退避并使用充电或网络约束。前台与硬件侧的常见项：静止或不可见时仍在提交帧、高精度位置未随场景停止、传感器/扫描未按生命周期注销、蜂窝小包高频上传。版本敏感边界：对 Android 15 及以上且 target API 35+ 的应用，`dataSync` 与 `mediaProcessing` 类型的前台服务在任意 24 小时内累计上限 6 小时（同类型多服务共享时限，回到前台重置，超时触发 `Service.onTimeout(int, int)`）。

**Q8: 一份可复查的性能案例报告要包含什么？为什么"工具截图里的一条长条"不能判定责任组件？**

报告按固定结构写，让没有参与排查的人能复查和复现：问题定义（用户场景、指标、阈值、发生比例）；实验条件（设备、软件版本、构建、数据、网络、温控和操作脚本）；证据时间轴（问题窗口、线程状态、系统资源与跨进程关系）；源码解释（对应 tag 下的路径、事件记录点和版本差异）；候选与反证（哪些原因被数据支持、哪些已排除、哪些待补采）；修改内容（单变量改动和预期影响）；复测数据（原始样本、统计分布、trace 对照和功能回归）；适用边界（设备差异、副作用、回退条件与后续监控）。任何一项关键结论都应能指向 trace、dump、benchmark 输出、构建产物或源码位置。

截图里的长条只能提供"某个区间很长"的观测事实，不能判定阻塞对象、调度原因或责任组件：区间长可能来自线程在等待锁、Binder、I/O 或 CPU，需要用线程状态分解、调用栈和对照实验收窄。完成标准由复现能力定义：另一位工程师应能依据记录还原环境、运行实验、找到同一证据区间，并判断修改是否改善目标指标；结果方向不一致时，报告要解释噪声来源或缩小结论范围。
