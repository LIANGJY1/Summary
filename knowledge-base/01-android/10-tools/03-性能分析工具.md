**Q1: Android Studio Profiler 的 System Trace、Callstack Sample 与 Record Java/Kotlin Methods 三种 CPU 任务分别回答什么问题，为什么它们的时间读数不能互换使用？**

三种任务的证据类型不同：System Trace 记录带时间戳的系统事件与线程状态（Android 10 及以上为 Perfetto 格式，含调度、CPU 核心、渲染与部分系统进程数据），Callstack Sample 周期性截取调用栈给出 CPU 时间分布，Record Java/Kotlin Methods 用 ART 运行时插桩在方法进入和退出时写时间戳、呈现调用层级。稳妥的选择顺序：先用 System Trace 判断问题属于执行、等待、调度还是渲染并圈定时间窗；时间主要消耗在 Running 状态且缺少方法级标记时，用 Callstack Sample 找高占比调用路径；只有调用顺序仍不清楚时，把场景缩短后录制 Java/Kotlin Methods。System Trace 没有 tracepoint（显式写入的事件点）的普通方法不会自动展开；方法插桩会改变被测程序时序，官方建议把录制控制在 5 秒以内，其绝对耗时只适合在同一录制条件下辅助排序，性能结论要回到无插桩 trace 或基准测试复核。另外 Android 7.1 及以下设备的采集量受 File size limit 约束，Android 8.0（API 26）及以上会忽略该上限，但仍不适合长时间录制。

**Q2: Callstack Sample 报告里某函数占比 30% 能说明什么、不能说明什么？主线程大部分时间在等 Binder 时为什么 CPU 样本反而很少？**

占比描述的是所选窗口内的采样命中分布，近似 CPU 时间分布，不是某一次调用的持续时间，也不能推出调用次数接近。Callstack Sample 要求设备至少为 Android 8.0（API 26）；它按固定间隔采样，短于采样间隔的调用可能完全缺席，同一方法的多次调用也已聚合，这称为采样偏差。主线程等待 Binder、锁或 I/O 时处于非运行状态，不会产生 CPU 样本，因此样本少不能证明该路径很快——等待时间要用 System Trace 的线程状态（Running、Runnable、Sleeping、Uninterruptible Sleep）和唤醒链解释。分析 Java/Kotlin 程序时栈中还会出现 JNI、ART、`/apex/`、`/system/` 和 `[kernel.kallsyms]` 帧，隐藏这些帧只改变展示；App 的原生代码采样由 Simpleperf 作为后端支持。

**Q3: Android Studio Memory Profiler 顶部的内存分类是什么口径？看到曲线上升就宣布泄漏为什么不可靠？**

分类统计来自系统报告的 App 私有已提交内存页，不包含与系统或其他 App 共享的页面，因此不等于 RSS 或 PSS；Graphics 包含图形缓冲区队列、GL surface 和 GL texture 等 CPU/GPU 共享内存，不是独立的 GPU 显存。曲线上升只是候选时段：缓存扩容、延迟 GC、原生分配器保留空闲页、Bitmap 或图形缓冲区的生命周期，以及测试路径没有回到同一状态，都能产生相似曲线；进程 RSS 没有立即下降也不等价于 Java 对象仍存活。泄漏结论需要可重复路径、明确的生命周期预期、多轮 GC 后对象数仍单调增长，以及从 GC Root 追到的引用链。配套任务上，Java/Kotlin allocation 默认 Full 记录全部分配、可切 Sampled（结果为估计值），Android 7.1 及以下最多保存 65,535 条分配记录而 Android 8.0 及以上没有这项限制（材料口径）；Native allocation 任务按累计分配字节数触发采样（材料标注当前默认 2,048 字节），其 Native Remaining Size 只描述窗口内分配减释放的净变化，不能直接证明窗口结束后仍有泄漏。

**Q4: `<profileable>` 与 `debuggable` 两种构建在 Profiler 能力上差在哪？接近发布的性能问题为什么要先用 profileable 构建采集？**

能力边界由 manifest 属性决定：`<profileable>`（Android 10 / API 29 加入）只开放受控的低扰动采集，System Trace、Callstack Sample、Native allocations 等任务可用；Java/Kotlin allocations、heap dump 和 Interaction timeline 需要 `debuggable` 构建。Studio 菜单中的 `Profile 'app' with low overhead` 对应 profileable 路径，`Profile 'app' with complete data` 对应 debuggable 路径；官方推荐环境是 API 29 及以上、带 Google Play 的测试设备并使用 AGP 7.3 及以上（材料口径）。debug 构建自身的开销会改变 Java、JNI 和编译优化行为，所以只在接近发布的构建中出现的问题应先用 profileable release variant 采集，确认范围后再制作尽量小的 debuggable variant 复现 Java 堆问题。若问题只出现在真实用户设备上，Android 15（API 35）起的 ProfilingManager 提供另一套受系统限流和脱敏约束的生产采集入口。

**Q5: simpleperf 的 `stat`、`record`、`report` 各产出什么证据？报告里的 Overhead 为什么不能一律当墙钟时间读？**

`stat` 汇总事件计数，回答"消耗了多少"；`record` 以指定事件触发周期采样，把程序计数器、线程、映射与可选调用栈写入 `perf.data`，回答"消耗发生在哪"；`report` 读取同一 `perf.data`，默认按 `comm,pid,tid,dso,symbol`（进程/线程名、PID、TID、动态共享库、函数符号）聚合样本，回答"样本如何归属"。Overhead 是条目占所选事件总权重的比例，而不同事件衡量的量不同：`task-clock` 是线程在 CPU 上运行的时间，`cpu-cycles` 受 CPU 频率、微架构和迁核影响，`instructions` 是已退休指令数，所以 Overhead 不能一律解释为现实中经过的时间。`record` 产生的是离散样本，占比接近只表示所选事件的权重接近，不证明调用次数接近。`-f 1000` 表示线程处于运行态时每秒约采样 1000 次——线程一秒只运行 200 ms 时样本量约 200 个；`-c 100000` 则按事件累计值采样，每累计十万个所选事件产生一个样本。事件加 `:u` 后缀只统计用户态，适合分析应用代码并减少无符号内核帧干扰。

```bash
simpleperf record -e task-clock:u -f 1000 -p "$APP_PID" --duration 10 -g -o perf.data
simpleperf report -i perf.data -g --sort comm,pid,tid,dso,symbol
```

**Q6: 非 root 设备上用 simpleperf 分析应用有哪些授权路径？Android 16 前后设备内置与侧载二进制的权限差别是怎么回事？**

授权分三种场景：`profileable` 发布应用允许 shell 通过预装工具采样（manifest 声明 `<profileable android:shell="true">`，它不把应用改成 debuggable，也不授予读取进程内存的权限）；`debuggable` 应用可走 run-as 流程，但 debug 构建会改变 Java、JNI 和编译优化行为，材料按 Android 17 核对时 `app_profiler.py` 默认拒绝这类构建，接受偏差需显式传入 `--unrepresentative_profile_debug_app`；root 或 userdebug/eng 构建可分析普通发布应用、原生系统进程或全系统目标。版本差异来自权限模型：Android 16 起（材料引 `environment.cpp` 的实现注释）侧载的 simpleperf 二进制不再拥有获取内核样本所需的权限，应用采样优先由 `simpleperf_app_runner` 启动设备内置 Simpleperf；此前版本（包括 Android 13）优先走 run-as 路径。simpleperf 源码不在本地 AAOS13 树，以上按材料转写。动手前先用 `run_simpleperf_on_device.py list --show-features` 与 `list` 探测设备能力和事件清单：采集时返回 `permission denied`、`not supported`、`event not found` 分别指向权限、内核/硬件支持、事件名称三类不同问题。

**Q7: simpleperf 的 `-g` 默认怎么还原调用栈？帧指针模式什么时候更快、什么时候反而断栈？丢样了按什么顺序排查？**

`-g` 默认选择 DWARF 调用栈：内核为样本保存寄存器和用户栈数据，simpleperf 用 `libunwindstack` 离线展开，依赖 ELF 中的 `.eh_frame`、`.debug_frame`、`.ARM.exidx` 或 `.gnu_debugdata`；材料按 Android 17 核对的单样本栈数据上限是 65,528 字节，深栈仍可能在到达线程入口前截断。`--call-graph fp` 让内核沿帧指针取调用链，在保留帧指针的 ARM64 原生代码上开销较低；但 ART 不保证为 Java 代码保留合适的帧指针，32 位 ARM/Thumb 混合代码也容易断栈，所以 FP 报告更短可能只是代码没有保留帧指针，与调用深度无关。比较两种模式应看 `[unknown]` 比例、栈深、热点归属和业务指标扰动。出现丢样时按顺序定位：先降低 `-f` 确认丢样是否随采样率下降；只有内核丢样时逐步增大 `-m`（每 CPU 的内核缓冲页数，必须是 2 的幂）；用户态缓冲不足或栈被截断时增大 `--user-buffer-size`；再缩短时长、减少目标线程或改用 FP。每次只改一个变量，并记录工具结束时的 `Samples recorded`、`Samples lost` 和 `truncated stacks` 统计。

**Q8: 线程因锁或 I/O 离开 CPU 的时间，普通 CPU 采样为什么采不到？`--trace-offcpu` 怎么补齐，边界是什么？**

普通 CPU 采样只在线程运行（on-CPU）时产生样本；线程因抢占、锁、I/O 或其他等待而未在 CPU 上执行时处于 off-CPU，这段时间不在任何样本里。`--trace-offcpu` 额外记录 `sched:sched_switch` 调度切换样本和上下文切换记录，用相邻时间戳估算线程离开 CPU 后停留在哪条调用路径，报告端用 `report_html.py --trace-offcpu on-off-cpu` 把 on-CPU 与 off-CPU 两类权重分开显示。约束有三条：整次记录只能选择 `cpu-clock` 或 `task-clock` 中的一个事件；离开 CPU 的权重来自调度时间戳，丢失样本或切换记录都会降低精度；使用前应先用 `list --show-features` 探测内核支持。若问题涉及可运行队列等待、线程唤醒者、Binder 对端或 CPU 频率，Perfetto System Trace 能提供更完整的时间上下文，两者按证据需要选择或并行采集。

**Q9: ARM Topdown 把流水线 slot 分成哪四类？为什么"分类名称相同"不能把 Intel 的公式直接搬到 Arm CPU 上？SPE 能补什么、不能补什么？**

Topdown（自顶向下微架构分析）把超标量处理器的执行机会按 slot 归入四类：Retiring（公式认定的已退休 slot）、Bad Speculation（错误推测与恢复开销）、Frontend Bound（前端未及时供给后端的损失）、Backend Bound（后端资源约束导致的损失）。它回答"执行机会消耗在了哪里"，是诊断方向而非优化处方；函数热点、调用栈和数据地址仍要交给采样工具定位。公式属于具体 CPU 而不属于指令集：slot 宽度（如 Neoverse V1 定义中的 8 slots/cycle）、事件和系数都由该 CPU 的 telemetry specification 定义，不能从 Armv8、Armv9 或 Android API 级别推导；把 Intel TMAM 公式换成 Arm 事件名没有物理含义。材料按 Android 17 核对：simpleperf 可以采集 `raw-stall-slot-backend` 这类原始事件（`simpleperf list raw` 查看），但不计算四类指标；异构 SoC 上大/小核公式不同、计数不要跨簇相加，事件数超过 PMU 计数器时的分时复用会让比例不可信。SPE（Statistical Profiling Extension，Android 17 simpleperf 新增采集与解码）能按采样指令地址、数据地址和事件位（L1、TLB、分支、LLC 等）定位热点指令，但该版本解码器不输出操作类型、`PERF_SAMPLE_DATA_SRC`、延迟权重、物理地址和可用于逐样本对齐的时间戳，`--spe-cache-miss` 不是 Android 17 的有效命令。

**Q10: LeakCanary 判定一个对象"泄漏"的流程是什么？为什么"等待期和 GC 后仍被保留"不等于"永远无法释放"？**

流程四步（按 LeakCanary 2.14 材料口径）：生命周期观察器把应结束生命周期的对象交给 `ObjectWatcher`（只保留弱引用）；默认等待五秒并触发 GC，弱引用仍未清除则对象进入保留集合；保留对象数量达到阈值（应用可见时默认累计 5 个才转储，不可见时等待一个 `retainedDelayMillis`）后调用 Android 堆转储接口；Shark 堆分析器解析 HPROF，从 GC Root 搜索到保留对象的引用路径并按泄漏签名聚类。它判断的是"对象在等待期和 GC 后仍被保留"，不是"已被证明永远无法释放"——异步任务、动画、消息队列和测试操作尚未结束时对象都可能暂时存活。默认只跟踪已销毁的 Activity、Fragment、Fragment View、Service 和已执行 `onCleared()` 的 ViewModel，业务对象要在生命周期结束处显式调用 `AppWatcher.objectWatcher.expectWeaklyReachable(instance, reason)`。修复依据是引用链上第一条生命周期不合理的强引用，而不是路径中出现过的熟悉类名；基础依赖应使用 `debugImplementation`，避免把堆转储与分析代码带进 release APK。

**Q11: `adb shell am dumpheap` 从 shell 到 ART 经过哪些层？为什么 user 构建上对普通发布应用执行会失败？**

链路分四层（AAOS13 源码核对）：`ActivityManagerShellCommand.runDumpHeap()` 解析参数并创建输出文件描述符，输出路径省略时落到 `/data/local/tmp/heapdump-<时间>.prof`；`ActivityManagerService.dumpHeap()` 检查调用方持有 `android.permission.SET_ACTIVITY_WATCHER`，调用 `enforceDebuggable()` 检查目标进程，并临时调用 `enableFreezer(false)` 关闭缓存应用冻结器；请求经 Binder 到达应用进程的 `ActivityThread.handleDumpHeap()`，在 `-g` 时执行 `System.gc()`、`System.runFinalization()`、`System.gc()` 序列后按分支选择托管堆、native heap 或 malloc info；最后由 ART 停止托管线程并写文件。user 构建上失败的原因是 `enforceDebuggable()` 的实现（AAOS13 核对）：`!Build.IS_DEBUGGABLE && !proc.isDebuggable()` 即抛 SecurityException——user 构建只能转储 debuggable 应用，`profileable` 声明不开放 HPROF；userdebug/eng 构建才允许转储其他目标。Android 13 的选项是 `--user`、`-n`（native heap dump）、`-g`、`-m`（malloc info）；Android 17 材料口径另有 `-b <png|jpg|webp>` 把 Bitmap 像素写进托管堆转储，属版本差异。`-n` 和 `-m` 的产物不是 HPROF，不能交给 HPROF 分析器；应用在自己进程内调用 `Debug.dumpHprofData()` 不经过 AMS 这组跨进程检查。Freezer 临时关闭的目的是防止目标进程被冻结后无法处理 Binder 请求，托管线程的暂停由 ART 负责，两者是两件事。

**Q12: ART 生成 HPROF 时为什么整个采集期间都处于停顿？"app/zygote/image"堆空间归类对裁剪文件有什么约束？**

`art/runtime/hprof/hprof.cc` 的 `DumpHeap()` 先进入与 GC 互斥的 `ScopedGCCriticalSection`，再创建 `ScopedSuspendAll(..., true /* long suspend */)` 停止其他托管线程，使对象和引用在遍历期间保持一致；`Hprof::Dump()` 在这个暂停范围内执行两遍——第一遍用计数输出器计算整体大小和最大 record 大小，第二遍写正式数据，停顿覆盖计数遍历、正式遍历和文件输出（AAOS13 源码核对）。所以代价远不止"扫一遍对象"，耗时随对象数、字段与数组数据量、存储速度和 Bitmap 内容变化，没有一组"每 100 MB 几秒"的数字能跨设备成立。文件头 magic 是 `JAVA PROFILE 1.0.3`，对象 ID 宽度为 4 字节（AAOS13 源码核对，注释明确 hprof-conv 按 4 硬编码）。`HEAP_DUMP_INFO` record 把对象归入 `HPROF_HEAP_APP`（含 app image）、`HPROF_HEAP_ZYGOTE`、`HPROF_HEAP_IMAGE` 三个空间；zygote 和 boot image 对象通常不是应用泄漏的分配主体，但会出现在 GC Root 路径中、其类与字符串 record 也可能被其他对象引用，直接删除这些二进制区段会得到引用断裂、无法解析的文件——KOOM 一类工具用配套的裁剪器和补全器维护引用关系，手工裁剪前必须理解这一点。

**Q13: Perfetto 的 `android.java_hprof` 与完整 ART HPROF 差在哪？它的 fork 管线为什么停顿更短但仍不是零成本？**

两者都来自 ART 托管堆，但产物和停顿边界不同：完整 HPROF（`am dumpheap`、`Debug.dumpHprofData()`）保存类、对象、字段、数组、字符串与 GC Root，能回答"某个字段保存了什么"；`android.java_hprof`（Android 11+ 数据源）只记录类型、对象大小、GC Root 与引用关系，直接写成 protobuf `HeapGraph` 包，不保存实例基本类型字段值、字符串内容、基本类型数组字节和 Bitmap 像素，因此文件更小、隐私面也更小，且能与同一 trace 里的 GC、调度事件做时间对齐。管线（AAOS13 源码核对关键点）：Perfetto 的 `JavaHprofProducer` 找到目标并授权后发送 `__SIGRTMIN + 6` 信号（`art/perfetto_hprof/perfetto_hprof.cc` 中 `kJavaHeapprofdSignal`），ART 插件的信号处理器只向 pipe 写通知，专用监听线程再进入 GC 临界区、执行 fork——父进程随后尽快恢复托管线程，派生出的子进程遍历 fork 时刻的堆副本并输出 `HeapGraph`。fork 采用写时复制：采集仍有 fork、页表、页面复制、子进程内存与序列化开销，不能描述成零成本。数据里的 `native_size` 只覆盖 `NativeAllocationRegistry` 为部分 Java 对象登记的原生内存，不能替代 heapprofd 的 native 分配采样；能否采集由 Perfetto 侧的 `CanProfile()` 按 build type、UID 与 manifest 属性判定，与 `am dumpheap` 的权限模型不是同一套。

**Q14: 排查 native 内存安全错误时，malloc debug、HWASan 与 MTE 应该怎么选？各自的前提是什么？**

按检出目标与运行前提选择：malloc debug（API 24+）在分配器前加入 shim，用 `guard`/`front_guard`/`rear_guard` 检测越界写、`free_track` 提高 use-after-free 检出机会、`backtrace` 记录分配栈，适合错误在分配器检查点才显现的场景，但它会改变被测进程的时序与内存行为，不能开在生产或性能基准里。HWASan 由编译器插桩并用影子内存保存地址标记，要求 ARM64、重编译目标 native 代码，且使用 libc++ 时必须选 `c++_shared`；版本边界要注意——Android 10 至 Android 13 上应用运行依赖 HWASan 系统镜像，Android 14 起普通系统才能用 `wrap.sh`（`LD_HWASAN=1`）启动 debuggable 应用（材料口径，AAOS13 属于前一档）。MTE 由 Arm CPU 比较指针标记与内存标记，需要 SoC、内核与系统支持，应用通过 `android:memtagMode`（API 31+）请求，`sync` 在出错指令处触发信号、精度高，`async` 精度低。三者都是测试变体工具；只是想找"哪些调用栈在持续分配"，默认选择仍是 heapprofd 而不是它们。

**Q15: `dumpsys` 输出的是哪种证据？为什么 `dumpsys cpuinfo` 的结果不能叫"瞬时 CPU"？**

`dumpsys` 通过 ServiceManager 找到目标 Binder 服务并调用它的 dump 接口，拿到的是该服务在采集时刻愿意公开的内部状态——或是即时快照，或是某段累计统计窗口，不是时间线；事件先后要靠 Perfetto、Winscope 或日志补足。AAOS13 的 `dumpsys.cpp` 核对：无参数全量模式按服务名排序逐项 dump，单个服务默认等待 10 秒；`-t` 单位秒、`-T` 单位毫秒（默认 10 秒），是全局参数应写在服务名之前；`-l` 列出注册且可见的服务；`--pid` 只打印服务所在进程 PID；`--priority` 按 CRITICAL 等优先级筛选；`--proto` 筛选声明 `DUMP_FLAG_PROTO` 的服务。cpuinfo 正是"累计窗口"的例子：它输出 ActivityManager 后台 `ProcessCpuTracker` 最近两个采样点之间的增量（来自 `/proc/stat` 与 `/proc/<pid>/stat`，AAOS13 存在该类），调用命令的时刻不一定触发新的测量窗口，"瞬时 CPU"的说法高估了时间精度；进程行的 `user`/`kernel` 分列自该进程的两种态 CPU 时间，`iowait`、`irq`、`softirq` 只在 TOTAL 行传入，多线程进程能并行占用多个 CPU、百分比可能超过 100%。

**Q16: `dumpsys activity oom` 里的 cur、set、curRaw、setRaw 和 adjType 各代表什么？OOM adjustment 数值高就代表进程会被杀吗？**

OOM adjustment 是系统交给 lmkd 的进程保护分数，数值越大在内存压力下通常越早进入回收候选，但它不表示进程已经发生 OOM。基准值在 AAOS13 的 `ProcessList.java` 核对：`FOREGROUND_APP_ADJ = 0`、`VISIBLE_APP_ADJ = 100`、`PERCEPTIBLE_APP_ADJ = 200`、cached 区间从 900 开始（材料按 Android 17 引用的 `psc/Constants.java` 是新版本文件名，数值一致）。字段要分开读：`curRaw` 是本轮计算中尚未施加部分修正的 raw adj，`setRaw` 是上次写入记录的 raw adj，`cur` 是本轮计算后的目标值，`set` 是已提交给进程/lmkd 路径的值；`adjType`、`adjSource`、`adjTarget` 说明哪个组件关系（绑定服务、ContentProvider、前台服务、显示器可见性等）抬升或降低了保护级别。发现 `set` 与界面状态不符时，应连同这些归因字段一起核对，不能只用一个数字判定 OOM 计算错误；LMK 的最终归因还要对照 lmkd 日志、PSI 与 `exit-info` 退出原因。可见进程还可能受 laddering 影响、被分配到 100–199 之间的细分值（材料口径，具体行为受设备配置控制）。

**Q17: `dumpsys gfxinfo` 的 `reset`、`framestats` 与聚合统计各承担什么？"Number Slow bitmap uploads" 高就是图片解码慢吗？**

`reset` 清空进程内保存的 HWUI 帧数据以划出可重复的测试窗口；无参数输出 since-reset 的聚合统计；`framestats` 输出环形缓冲区里的逐帧列，解析时读取 `---PROFILEDATA---` 之后的 header 按列名建索引——不同版本会增加字段，按固定列号解析会把后续时间戳整体错位，未填充字段可能用 0、负值或哨兵值，计算差值前要过滤。AAOS13 的 HWUI 源码核对：`JankTracker` 使用固定 120 项的环形缓冲（写满覆盖最早记录），`ProfileData` 同时输出 deadline-aware 与 legacy 两组统计（`Janky frames` 与 `Janky frames (legacy)`）及 90/95/99 分位，deadline 口径按 `GpuCompleted` 是否越过 `FrameDeadline` 判定，`FrameInfo.h` 中存在 `FrameDeadline`、`SyncStart`、`IssueDrawCommandsStart`、`GpuCompleted` 等字段。分类名是 trace 入口不是根因：`Slow bitmap uploads` 是保留的历史输出名（对应 `SyncStart → IssueDrawCommandsStart` 超阈值），不能凭名称认定发生了图片解码；`Slow issue draw commands` 也不区分 CPU、GPU、队列或 fence 等待。方法级归因回到 Perfetto 的 FrameTimeline、UI Thread、RenderThread 与 GPU 证据。

**Q18: 排查图层缺失或晚呈现时，Android 13 上 `dumpsys SurfaceFlinger` 的 `--list` 与 `--latency` 怎么用？`--frontend` 为什么是无效参数？**

Android 13 的 dumper 注册了 `--list`（输出 Layer 精确名称）、`--latency` 与 `--latency-clear`（单 Layer 的历史帧统计）、`--displays`、`--frametimeline`、`--static-screen` 等入口（AAOS13 `SurfaceFlinger.cpp` 核对）；`--frontend`、`--hwclayers`、`--scheduler` 是 Android 15 之后 FrontEnd 架构引入的视角（材料按 Android 17 核对），在 Android 13 设备上不可用——这是本文最容易被旧资料误导的版本差异。`--latency` 的用法：先用 `--list` 复制精确 layer name，输出首行是采集时刻的刷新周期信息，其后每行是一帧的三个纳秒级时间戳——期望呈现时间、实际呈现时间、帧就绪时间（三元组语义按材料口径，各版本字段含义略有差异）；`actual − desired` 只能标记晚呈现，不能独立归因，晚呈现可能来自生产者、acquire fence、调度、client composition、HWC 或 present fence。解析要过滤 0、负值和未完成哨兵，三列都有效才计算差值。dump 中 CLIENT（GPU/RenderEngine 合成）与 DEVICE（HWC 硬件路径）的合成方式只代表该次采集附近的状态，跨帧结论应使用 Perfetto、Winscope 或稳定复现实验。

**Q19: "WLAN rail 在 20 秒窗口增加 4.2 J"与"目标 UID 被 BatteryStats 归因 0.3 mAh"为什么不能放进同一列比较？**

因为它们是两种证据：前者是 ODPM（设备端电源轨监控）或 Power Stats HAL 的系统级硬件计量，rail 是给某类硬件供电的电源轨，能量单位 `uWs` 数值上等于微焦耳，测量的是整个设备子系统；后者是 BatteryStats 用功耗模型按 UID、组件和进程状态归因的估算结论，精度依赖 `power_profile.xml` 与活动时长统计。两类数据的单位、时间范围和系统消耗的分配规则都不同，报告必须写明用的是哪种。ODPM 是设备级测量，前台 App、后台进程、系统服务和硬件自身活动都可能贡献读数，不能自动归因给目标应用；Android Studio Hedgehog 起的 Power Profiler 展示 ODPM 数据，官方高精度 rail 范围是 Pixel 6 及后续 Pixel 设备（材料口径），没有 ODPM 的设备可能只有电池容量、电荷或电流读数。整机供电端的高精度结论则要靠外部电源分析仪，它同样不提供线程级归因。

**Q20: Battery Historian 时间线里的色块、top_app 和电池百分比分别代表什么？哪些解读是错的？**

Battery Historian 把 bugreport 中的 BatteryStats 历史渲染成时间线，色块只表示事件或状态正在活动（CPU running、userspace wakelock、JobScheduler、Mobile radio/Wi-Fi、GPS/sensor 等），无法读出该组件消耗了多少电量。常见误读有三类：把某一行持续变色当成耗电来源——能量结论还要结合归因统计、rail、线程活动或外部测量；把 `top_app` 当成"耗电最多的应用"——它只表示当时处于前台，提供场景上下文；在短窗口读电池百分比——百分比来自 fuel gauge（电量计量芯片及估算算法）并取整，短测试里可能长时间不变或一次跳变，短时优化应比较 rail 能量或可重复的系统级指标，长时待机测试再把百分比斜率作辅助证据。时间重叠只能建立相关性：WLAN 活动与一次图片下载重叠只说明该操作值得进一步测量，不能排除同时刻其他进程也在使用 WLAN。WakeLock 行的判断边界是：bugreport 生成时仍被持有的锁值得检查，但录音、导航等任务可能合法持锁，要按持锁原因、生命周期和时长是否与用户可见任务一致判断。

**Q21: 采集一份可比较的 bugreport 给 Battery Historian，命令顺序和状态开关怎么安排？Historian 现在还能用吗？**

顺序是有状态的，按此执行（AAOS13 `BatteryStatsService` 核对选项存在）：`dumpsys batterystats --reset` 清空当前统计与 history（确认不需要保留现场后执行）；`--enable full-wake-history` 临时打开完整 userspace wakelock 时间线（占用历史缓冲区，只覆盖目标窗口）；断开 USB 让 BatteryStats 进入 on-battery 统计口径，执行固定测试场景；重新连接后 `adb bugreport bugreport.zip` 生成报告；最后 `--disable full-wake-history` 恢复。直接读文本时，`--charged`、`--history`、`--usage` 与 `-c`/`--checkin` 输出粒度不同，且 `--checkin` 在材料按 Android 17 核对时还带"输出并清除旧统计"的语义，自动化脚本不能把 `-c` 与 `--checkin` 当作等价。Android 7.0 及以上使用 zip 格式 bugreport，包含账号、网络、日志等敏感信息，不应上传到不受信任的在线 Historian 服务。维护状态：Google 的 battery-historian 仓库已于 2022 年 12 月归档转为只读（材料口径），官方文档仍给出 `stable:3.1` 容器命令但旧镜像可能拉取失败；打不开时直接用 `dumpsys batterystats` 文本、Perfetto `android.power` 或 Power Profiler。Historian 适合回看较长窗口的 wakelock、job、alarm、定位与网络活动，不适合短时函数级测量，也不能从时间线算出某段代码的毫瓦数。

**Q22: Macrobenchmark 与 Microbenchmark 的进程边界和编译控制有什么不同？"Microbenchmark 数字更稳定"能替代 Macrobenchmark 吗？**

不能互相替代，差别在进程边界与测量对象：Macrobenchmark 的测试 APK 运行在目标应用进程之外，驱动启动、滚动、动画等完整用户场景，要求独立的 `com.android.test` 模块、目标 APK 使用接近 release 的非 debuggable 构建并在 manifest 声明 `<profileable>`；Microbenchmark 在基准测试进程内循环调用被测代码，循环会形成预热缓存与稳定代码路径，结果接近热点代码的最佳情况。分工是：启动、进程创建、系统服务与完整渲染必须由 Macrobenchmark 加系统 trace 判断；JSON 解析、布局 inflate、列表 item 绑定等可隔离热点用 Microbenchmark，并用 `BlackHole.consume()` 防止编译器把没有外部用途的计算整段删除（材料口径：Benchmark 1.3.0-beta01+ 配合 AGP 8.4.0+ 默认对 Microbenchmark APK 做全量 AOT）。典型证据路径是：Macrobenchmark 发现回归并保留 trace，Perfetto 定位到可隔离函数，Microbenchmark 比较候选实现，再回到 Macrobenchmark 确认端到端改善。迭代次数没有统一的"10"：先在固定设备上观察分布与热状态，再选择能稳定区分目标回归幅度的数值。

**Q23: StartupTimingMetric 的 TTID 与 TTFD 分别计到哪里？CompilationMode 的 DEFAULT、None、Partial、Full、Ignore 各用于什么？**

`timeToInitialDisplayMs`（TTID）从系统收到启动 Intent 计到目标 Activity 首帧；`timeToFullDisplayMs`（TTFD）计到应用调用 `reportFullyDrawn()` 之后的首个完整帧——应用不调用该 API 就没有可解释的 TTFD，API 29 及以下还可能无法提供该字段（材料口径）。报告比较以 median 为主，同时保留 min、max 和单次 trace；`StartupMode.COLD` 会在 setup 与 measure 之间终止目标进程，三种启动模式不能混在一条趋势曲线里。CompilationMode 按研究目标选择：`DEFAULT` 在 API 24+ 尝试安装 APK 内的 Baseline Profile（API 23 按系统默认行为全量编译）；`None()` 清除已编译代码与 profile，观察无预编译状态；`Partial()` 安装 Baseline Profile，观察 profile 覆盖后的状态；`Full()` 对目标 APK 全量 AOT，研究编译上限；`Ignore()` 保留设备当前编译状态不重置（实验 API），适合由外部脚本精确控制 ART 编译的场景。Android 14 起重置编译状态可保留应用数据，更低版本常需要重装 APK。Baseline Profile 的收益必须由同一 APK、同一设备、同一启动模式下的 `None()` 与 `Partial()` 实测得出，跨项目引用"提升约 30%"没有意义。

**Q24: 为什么 Espresso 不能用来驱动 Macrobenchmark 的测量区间？UI Automator、Monkey 与 Android CLI 在性能链路里各承担什么？**

Macrobenchmark 的测试 APK 运行在目标应用进程之外，而 Espresso 是白盒工具——它面向目标应用的 instrumentation 环境，`onView()` 前会等待消息队列与 `IdlingResource` 空闲，把它的 matcher 和同步放进 `measureBlock` 会把框架同步、断言与测试代码的开销计入测量。完整性能场景的驱动是 UI Automator：它在测试进程中通过系统级 UiAutomation 连接读取 accessibility node、注入手势，不要求目标应用链接测试代码，因此能驱动保留 release 优化的 APK 并处理权限弹窗；页面准备放进 `setupBlock`，`measureBlock` 只留固定输入。Espresso 保留在提交验证阶段做功能断言。Monkey 是另一类：生成伪随机事件做稳定性压测（`-p` 限包、`-s` 固定 seed 可重放事件序列、`--throttle` 限速、`--monitor-native-crashes` 监视 native 崩溃），它不控制编译和设备状态，不能用于启动耗时或帧时间回归判定。Android CLI（材料口径：2026 年 5 月发布 1.0）是运行在开发机/CI 上的主机编排工具：`android run` 只安装并启动 APK、不执行构建，`layout`/`screen` 返回 UI 树与截图，`studio` 子命令做符号与静态检查查询——它不生成帧级测量数据，性能结论仍来自 Macrobenchmark、Perfetto 等采集端；Journey 用自然语言执行路径、存在执行差异，不适合控制计时区间。

**Q25: 性能 CI 的五个阶段各固定什么？为什么模拟器跑出的基准数字不能进物理设备基线？**

五个阶段各有固定物：构建阶段生成接近 release 的 `benchmark` 变体（关闭 debuggable、保留 R8 与资源压缩、只换 CI 签名）；设备准备阶段固定型号、build fingerprint、电量、充电方式、亮度、刷新率与账号后台；执行阶段分层——PR 冒烟用 `dryRunMode` 或少量场景验证脚本，夜间趋势固定物理设备跑完整迭代，发布候选再增加机型；产物收集阶段保存指标 JSON 与每个测量 iteration 一份系统 trace，并把 Git commit、APK 哈希、设备指纹写入同一次运行记录；回归判定阶段只在同名测试、同名指标、同一启动/编译模式和同类设备之间比较，阈值从该设备历史方差与业务预算推导。AndroidX Benchmark 会把模拟器判为配置错误：即使通过 `suppressErrors` 继续运行，产物也只能用于诊断，不能与物理设备比较或写入基线。统计上还要注意：同一 invocation 内的多个 iteration 共享温度、缓存和后台状态，彼此相关，重复抽样不产生独立样本；设备刷机、Benchmark 库升级或 Baseline Profile 更新属于环境迁移，应建立新基线，避免把环境变化显示成代码回归。

**Q26: ProfilingManager 解决什么问题？它是什么时候引入的，Android 13 上能用吗？**

ProfilingManager 补足量产设备上"问题发生时没有开启分析工具"的取证空档：应用可以在运行中请求 system trace、Java heap dump、heap profile 和 stack sampling，采集完成后通过回调拿到结果文件路径，不需要连接开发机。版本边界必须点明：平台类 `android.os.ProfilingManager` 自 Android 15（API 35）引入，AndroidX Core 1.15.0 起提供 `androidx.core.os.Profiling` 与各 request builder 封装，系统触发（trigger）能力再分 API 36、36.1、API 37 三档（材料口径）；Android 13 上不存在该 API——本地 AAOS13 树的 frameworks/base 与 packages/modules 下均无 ProfilingManager 对应类（本地源码核对），Android 13 及更早的替代是连接开发机对 debuggable/profileable 构建采集，或降级使用 Android vitals、FrameMetrics/JankStats、`ApplicationExitInfo` 等指标与记录。它属于 Mainline 模块、可经 Google Play 系统更新独立更新，因此设备实际行为可能与固定 AOSP tag 的源码有差异。

**Q27: 发起一次 ProfilingManager 显式请求要注意什么？"提交成功"等于"采集成功"吗？**

不等于。请求经 Binder 进入系统服务后还要依次通过并发状态、限流与参数检查，任一阶段失败都映射到错误码，只有 `errorCode` 为 `ERROR_NONE` 且 `getResultFilePath()` 非 null 才有文件；限流按 profiling 类型的资源成本在小时/天/周窗口以及应用 UID 与整机预算上分别检查，不是固定"每小时几次"，返回 `ERROR_FAILED_RATE_LIMIT_*` 时应退避而不是循环重试。显式请求的要素：按问题选 builder——SystemTraceRequestBuilder 看线程时间线与调度交叠、JavaHeapDumpRequestBuilder 看对象存活与 GC Root 引用链、HeapProfileRequestBuilder 看持续分配调用栈、StackSamplingRequestBuilder 要低开销热点线索；`executor` 与 request-specific listener 必须成对传入，两者都为 null 仅在已注册全局 listener 时有意义，没有任何 listener 的请求会被丢弃；`tag` 只取前 20 个字母、数字和连字符并转小写进入文件名，不能承载用户数据；heap dump 是某一时刻的快照、没有时长参数；`BufferFillPolicy` 只属于 system trace 请求，`RING_BUFFER` 保留停止点前的时间窗、`DISCARD` 保留采集开头的早期证据（材料口径）。结果文件只能通过返回的 `resultFilePath` 访问，成功结果用它去重；`ProfilingResult` 没有唯一结果 ID，失败时路径为 null。

**Q28: system-triggered profiling 为什么"注册了 ANR trigger 却常常拿不到文件"？APP_FULLY_DRAWN 与 COLD_START 两个 trigger 的窗口差在哪？**

注册 trigger 只是允许系统在条件满足时采样，不保证每次事件都有产物：系统会周期性、带随机性地启动后台 trace 并用 ring buffer 保存最近数据，事件发生时只有后台 trace 正在运行且配额充足，才会生成当前 trace 的快照——后台 trace 未运行、限流命中都会导致"事件发生了但没有文件"。两个启动 trigger 的窗口完全不同（材料按 API 36/37 口径）：`APP_FULLY_DRAWN` 保存触发点之前 ring buffer 里已在运行的后台 trace，适合看启动尾段与触发前的系统活动；`COLD_START` 为这次冷启动新开一份 system trace 并同时做 stack sampling，使用 DISCARD 保留采集开头，在应用调用 `reportFullyDrawn()` 时停止、未调用时默认约 5 秒停止。两者的起点、停止点和产物都不同，样本必须按 trigger type 分组统计，不能混进同一个分位数。trigger 结果只送到全局 listener，进程重启后可再次投递；版本上 API 36 提供 APP_FULLY_DRAWN 与 ANR，36.1 增加用户强停、最近任务移除等 kill 类 trigger 与 `requestRunningSystemTrace()`（判断用 `SDK_INT_FULL`），API 37 增加 OOM、COLD_START 等——其中 `TRIGGER_TYPE_OOM` 只覆盖 Java OOM，不含 lmkd 或 native OOM，应用自定义 `UncaughtExceptionHandler` 时必须续调默认 handler。实验设备可用 `profiling_testing` 的 DeviceConfig 开关关闭限流或指定测试包，测试后必须恢复。

**Q29: statsd 在系统观测里处在什么位置？pushed atom 与 pulled atom 有什么区别？**

statsd 是平台侧的指标守护进程：接收 atom（用 protobuf schema 描述的结构化事件或状态记录），按 `StatsdConfig` 配置聚合成 metric 报告。它不录制逐线程、逐调度事件的时序——"某类事件是否发生、发生多少次、按 UID 或包名切分后的分布"归 statsd，"这段时间内事件按什么顺序发生"归 Perfetto。Statsd 模块自 Android 11 起以 `com.android.os.statsd` APEX 分发，Android 12 起源码迁移到 `packages/modules/StatsD`（材料口径；本地 AAOS13 树不含该模块源码，仅 `system/core/libstats` 有日志 socket 接入层，属部分核对）。atom 分两类：pushed atom 由系统服务在事件发生时经 `libstatssocket` 写入（如 `ANROccurred`、`LmkKillOccurred`、`AppStartOccurred`、`WakelockStateChanged`、`ScheduledJobStateChanged`）；pulled atom 由 statsd 按配置或命令向系统数据源拉取当前状态（如 `KernelWakelock`、`CpuTimePerUid`、`ProcessMemoryState`），pulled 区间的 field number（同时是 atom ID）从 10000 开始（材料口径，本地无 `atoms.proto` 无法直接核对）。statsd 过载时发送端可能收到 `EAGAIN`、写入丢失但不阻塞并维护 drop 计数——所以报告缺条目也不能单独证明事件未发生。

**Q30: statsd 配置里的 AtomMatcher、Predicate 与各类 metric 各管什么？报告里缺条目按什么顺序排查？**

配置层不关心事件怎么产生，只关心"哪些 atom 算命中、怎么聚合"：`AtomMatcher` 按 atom ID 和字段条件匹配事件；`Predicate` 用 start/stop atom 表示条件区间（如只统计前台期间）；metric 决定聚合方式——`EventMetric` 保留命中事件明细，`CountMetric` 按时间 bucket 计数，`DurationMetric` 统计状态持续时长（`SUM` 累加区间、`MAX_SPARSE` 保留已结束区间的最大值），`GaugeMetric` 对 pulled atom 或触发事件做周期采样，`ValueMetric`/`KllMetric` 聚合数值字段（KLL 用分位数摘要估计分布）。报告缺条目时按数据流顺序排查：`allowed_log_source` 是否放行了写入来源；matcher/predicate 是否真的命中；metric activation 是否已启用；当前未结束的 bucket 是否被包含；报告是否已被导出并清除；pull 是否超时；socket 或队列是否发生丢失。atom 与 metric 要分开看：报告里有条目只证明对应 atom 到达 statsd、命中配置并进入报告，它不能替代 ANR trace、tombstone、Perfetto trace 或 dumpsys 现场。

**Q31: 本地用 `cmd stats` 验证一份 statsd 配置的流程是什么？为什么这套命令不能进量产自动化？**

最小流程四步（材料按 Android 17 源码口径转写，本地树无 statsd 模块源码）：用与目标版本匹配的 `statsd_config.proto` 把 textproto 编成二进制（`protoc --encode=android.os.statsd.StatsdConfig`）；`adb shell cmd stats config update 123456 < config.pb` 下发——配置必须从 stdin 传入 wire-encoded protobuf，配置 ID 是 int64，省略 UID 时使用调用方 UID，跨 UID 操作只对 eng/userdebug 开放；触发场景后 `adb shell cmd stats dump-report 123456 --keep_data --include_current_bucket --proto` 拉取报告——`dump-report` 默认导出即清除，调试时要加 `--keep_data`；结束后 `cmd stats config remove 123456` 清理，省略 UID 与 NAME 会删除全部配置。辅助命令：`print-uid-map` 查 UID 到包名映射，`pull-source <id>` 验证某个 puller 是否工作（它不创建 metric、不证明周期采集成功），`print-stats` 打印 statsd 自身统计，`print-logs` 需要 root。不能进量产的原因在权限模型：`cmd stats` 的 shell 入口只允许 root/shell UID；`StatsManager` 是 `@SystemApi`，`addConfig()`/`getReports()` 要求 `DUMP` + `PACKAGE_USAGE_STATS` 特权，量产环境的配置与上报由系统镜像、GMS 或厂商机制控制，普通 App 无法下发平台级配置。

**Q32: 一次 ANR 排查里，statsd、Perfetto、logcat、dumpsys 各能提供什么？为什么缺一类证据结论就会偏窄？**

四类证据回答不同问题：statsd 的 `ANROccurred` 报告回答哪个 UID/进程发生 ANR、reason 字段是什么、处理各阶段耗时是否异常；Perfetto 还原 ANR 前主线程处于 runnable、blocked 还是 Binder 等待、谁持有锁；logcat 还原 ActivityManager 的 ANR 判定路径；`dumpsys activity exit-info`（`ApplicationExitInfo`，Android 11+）区分 ANR、Java/native crash、low-memory kill、用户请求等退出原因，`lastanr` 保存最近一次 ANR 状态。缺任何一类结论都会偏窄：statsd 只有聚合事实没有时序，Perfetto 不知道平台统计口径，dumpsys 快照只证明当前状态，ANR trace 的线程栈要靠系统保存。LMK 同理——`LmkKillOccurred` 只记录哪个进程被杀，内存压力为什么升高要查 lmkd 日志、PSI、PSS/zRAM 与前后台状态。工程上的分工原则：线上 APM 负责应用内会话与业务维度，statsd 负责系统侧平台事件维度，后端按时间、版本、设备关联两者；只有系统侧才知道、App 无权限拿到的事件才值得引入 statsd，APM 能稳定采到的不必重复采集。

**Q33: StrictMode 的 ThreadPolicy 与 VmPolicy 各管什么范围？在 Application.onCreate() 里 setThreadPolicy() 之后，线程池里的磁盘操作为什么检测不到？**

`ThreadPolicy` 只作用于调用 `StrictMode.setThreadPolicy()` 的那条 OS 线程——它不是"主线程策略"，常见写法覆盖主线程只是因为 `onCreate()` 恰好运行在主线程；线程池、Binder 线程和手工创建的线程不会自动继承这份 Java 线程策略，需要各自安装。`VmPolicy` 由 `setVmPolicy()` 安装到进程级静态状态，进程内各线程触发对应检查点时都受约束。两条机制细节（AAOS13 `StrictMode.java` 核对）：每次 `setThreadPolicy()`/`setVmPolicy()` 都会整体替换现有策略；Builder 启用了 detector 却未显式配置 penalty 时，`build()` 自动补上 `penaltyLog()`；`setThreadPolicyMask()` 会同时更新 libcore `BlockGuard` 的 Java policy 与 Binder native 层保存的策略 mask。多进程方面，`android:process` 创建的进程会重新运行 `Application.onCreate()`，策略与违规限流状态各进程独立。

**Q34: StrictMode 的磁盘与网络检测点在哪里？为什么 SharedPreferences 后台加载 XML 时主线程卡住、却不报 DiskReadViolation？**

检测点不是拦截每个系统调用，而是 framework 与 libcore 预埋的检查点：`detectDiskReads()`/`detectDiskWrites()` 通过当前线程的 `BlockGuard.Policy` 接收 `onReadFromDisk()`/`onWriteToDisk()` 回调，`detectNetwork()` 走 `onNetwork()`，`detectUnbufferedIo()` 走 `onUnbufferedIO()`（AAOS13 libcore 源码核对），资源只有接入 `CloseGuard` 并调用 `open()`/`close()`/`warnIfOpen()` 才参与泄漏检测。`SharedPreferences` 是典型盲区：`SharedPreferencesImpl` 在后台线程加载 XML，主线程 getter 只是等待加载完成——磁盘 syscall 不在主线程，主线程 StrictMode 不会产生 `DiskReadViolation`，但界面仍因等待而卡住，此时要看 Perfetto 的线程状态与工作线程 I/O。同类边界还有：直接从 native 代码发起、未经过检查点的 syscall 可能绕过检测；主线程用 `Future.get()` 等待后台 I/O 时检查点在工作线程；检测到磁盘访问不代表该访问一定慢。`detectExplicitGc()`（显式 `System.gc()` 检查）在 Android 13 是 `@hide`/`@TestApi`（AAOS13 源码与 API 表核对），材料按 Android 17 口径为 API 34 起对 SDK 公开——在 Android 13 上不能直接调用；`noteSlowCall(name)` 只标记调用点、没有耗时阈值，要知道耗时用 trace section 加 Perfetto。

**Q35: StrictMode 的 penalty 各是什么语义？用 penaltyListener 记录违规时为什么要用独立 Executor？**

penalty 决定违规被检出后的处理：`penaltyLog()` 通过 logger 输出违规，相同调用栈指纹会限流；`penaltyDeath()` 在 ThreadPolicy 是处理末尾抛 `RuntimeException`，在 VmPolicy 是调用 `killProcess()` 退出；`penaltyDeathOnNetwork()` 特殊——启用 `detectNetwork()` 后它在其他 penalty 之前直接抛 `NetworkOnMainThreadException`，只想记录就不要同时启用；`penaltyListener(executor, listener)` 把原始 `Violation` 交给指定 Executor（Executor 参数必填，AAOS13 公开 API 核对）；`penaltyDropBox()` 经 ActivityManager 写入系统诊断存储；`penaltyDialog()`/`penaltyFlashScreen()` 面向交互式调试。listener 机制里，回调执行期间 StrictMode 会临时放开回调线程的 ThreadPolicy，避免 listener 内部的日志、入队等操作再次触发自身形成递归，但队列消费与 Executor 生命周期仍由应用负责——回调里不要同步上传网络或做重型符号化，堆栈与明文数据也可能含敏感信息。另一个读数边界：带 Looper 的线程上记录的 `durationMillis` 是从违规时刻到 Looper 完成本轮工作之间的时间，可能包含违规操作后的其他同步代码，不是磁盘 syscall 的精确耗时；同一 Looper 循环的记录数量有上限，日志条数不能当成违规发生次数。

**Q36: 应用堆栈里出现"发生在 system_server 的 DiskReadViolation"是怎么回事？用 `allowThreadDiskReads()` 临时放行时要注意什么？**

这是 ThreadPolicy mask 随同步 Binder 调用传播的结果：`setThreadPolicyMask()` 同时更新 BlockGuard 的 Java policy 与 Binder native 层的 mask，发起同步 Binder 调用时 mask 随事务到达服务端 Binder 线程；服务端触发违规后 `PENALTY_GATHER` 把 `ViolationInfo` 放进 `gatheredViolations` 这个 ThreadLocal，`Parcel.writeNoException()` 把收集到的违规写入 reply——AAOS13 源码核对为最多写前 3 条、每条栈约截断到 20 kB——调用方 `Parcel.readException()` 再经 `readAndHandleBinderCallViolations()` 补上本地调用栈并交给调用方当前策略处理。所以 IPC 间接执行的 I/O 会出现在应用堆栈里；这套传播只覆盖 ThreadPolicy，远端进程的 VmPolicy 不传播，回传信息也不包含 Binder 调用本身的耗时。临时放行方面：`allowThreadDiskReads()` 只清除 disk-read 检测位，`allowThreadDiskWrites()` 同时清除 disk-write 与 disk-read 位（AAOS13 的 `allowThreadDiskWritesMask()` 实现核对，因为写文件通常伴随读取元数据）；返回值是放行前的完整策略，必须在 `finally` 中恢复，异常、提前返回和嵌套调用都不能让线程永久处于宽松状态。放行不会让操作更快，注释应写明数据量上限、调用阶段和无法异步化的原因。自动化测试安装策略时，`@Before` 运行在测试线程、直接调用只改变测试线程，要用 `runOnMainSync` 切到应用主线程；依赖 GC 与 finalization 时序的 VmPolicy 违规不适合直接做确定性断言，适合先收集证据。
