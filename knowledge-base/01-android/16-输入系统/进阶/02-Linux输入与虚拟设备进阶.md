# Linux输入与虚拟设备：进阶

> 对应主课程中的详细机制、配置、源码和排查。题目按来源版本说明适用范围。

**Q1: [learning] 触摸采样率 240 Hz 与屏幕刷新率 120 Hz 是什么关系？高采样率的价值由什么决定？**

两者是彼此独立的频率：采样率是触控硬件每秒检测位置的次数，决定坐标的时间密度。刷新率是屏幕每秒更新画面的次数，限定显示更新机会。240 Hz 触控配 120 Hz 显示，理想情况下每个显示周期约有两个触控样本。相位也未必对齐，且控制器可能动态调整报告率，样本数只是频率比而非保证。

高采样率的价值取决于下游怎么消费：多出的样本常被合并进同一个 `MotionEvent` 的历史记录，列表滚动只读当前坐标时收益有限。笔迹拟合、速度估计、轨迹预测和高帧率场景更能利用密集样本。显示帧数仍受渲染能力与刷新率限制，提高采样率不能直接推导端到端延迟缩短——事件能否进入最近一帧，取决于到达时刻与整条处理路径。验证设备实际采样节奏应从驱动事件时间或结构化输入跟踪统计相邻样本间隔，而不是只看规格表。

**Q2: [learning] 一个触摸/按键事件从硬件到 InputReader 经过内核哪些环节？**

路径是：触控 IC/按键控制器驱动 → 内核 input core → evdev handler → `/dev/input/eventX` 字符设备 → 用户态读取。驱动用 `input_allocate_device()`/`input_register_device()` 注册一个 input 设备并上报事件。input core 负责设备与 handler 的匹配连接。evdev 为每个打开的文件句柄维护独立的环形事件缓冲（量级为数十个事件包），用户态消费不过来时溢出，内核以 `SYN_DROPPED` 标记重同步。Android 侧的读取者是 InputFlinger 进程内的 EventHub 线程，它把裸事件包装成 `RawEvent` 交给 InputReader。

`input_event` 结构是四字段的定长记录：`time`（时间戳）、`type`、`code`、`value`，按本地 UAPI 头核对（`bionic/libc/kernel/uapi/linux/input.h`），64 位平台上该结构 24 字节（时间被拆成秒/微秒两个字段），这决定了用 `hexdump` 直接解析 `/dev/input/eventX` 时的字节布局。

理解这条链的排查意义在于分段：`getevent` 有输出说明驱动与内核段通了。InputReader 没消费通常是设备分类或配置问题。而“事件有了但坐标乱”则进入校准与绑定环节——每一层有各自独立的失效方式。

**Q3: [learning] input_event 的 type/code/value 各自什么语义？一帧触摸由哪些事件组成？**

`type` 是事件大类：`EV_SYN`（同步，0x00）、`EV_KEY`（按键/触点状态，0x01）、`EV_REL`（相对位移，0x02）、`EV_ABS`（绝对坐标，0x03）、`EV_SW`（开关，0x05）、`EV_LED`、`EV_FF`（力反馈）等（码值按本地 `input-event-codes.h` 核对）。`code` 是大类内的具体项，`value` 的语义随 type 变化：`EV_KEY` 的 value 0/1/2 表示释放/按下/自动重复。`EV_REL` 是增量。`EV_ABS` 是当前绝对值（轴的 min/max/fuzz/flat/resolution 由 `input_absinfo` 描述）。`EV_SW` 是开关状态。

一次触摸“帧”以 `EV_SYN/SYN_REPORT` 收尾：驱动先发若干坐标与状态事件（`ABS_MT_POSITION_X/Y`、`BTN_TOUCH` 等），最后一条 `SYN_REPORT` 表示“此刻的快照完整”。多点协议里还有 `SYN_MT_REPORT` 作为单触点的分隔符（Type A 专用）。接收端看到 `SYN_REPORT` 才处理积累的事件，之前的事件只是“草稿”。

`getevent -l` 输出里的每个三元组就是一条 `input_event`：例如 `0003 0035 000003d4` 是 `EV_ABS`、`ABS_MT_POSITION_X(0x35)`、值 980。读懂三元组是触摸驱动联调的基本功——上游固件改报点协议时，第一验证点就是这层输出变了什么。

**Q4: [learning] 多点触控协议 Type A 与 Type B 有什么区别？Android 怎么判断驱动用的是哪种？**

Type A 无硬件追踪能力，每帧重发全部触点，触点间用 `SYN_MT_REPORT` 分隔、帧尾 `SYN_REPORT` 收尾，接收端只能按“位置相似”猜测哪些样本属于同一根手指。Type B 硬件维护触点身份，用 `ABS_MT_SLOT` 选择槽位、增量更新，触点抬起时把该槽的 `ABS_MT_TRACKING_ID` 置 -1，接收端按槽位稳定跟踪。按 kernel.org 官方文档结论，Type A 已废弃、内核驱动已全部迁移到 Type B。两者的触点身份标识也不同：Type A 的 `BLOB_ID` 仅用于分组，不能当追踪 ID 用。

Android 13 的 `MultiTouchInputMapper` 要求 tracking ID 和 slot 轴都有效，且 slot 的最小值为 0、最大值大于 0，才按 Protocol B 处理；否则走 Protocol A 分支。槽位上限为 32，驱动声明更多会被裁剪（按 AAOS13 源码核对）。Protocol B 的累加器还有一个启动细节：configure 时先向驱动查询当前槽号作为初始槽，否则 evdev 缓冲里残留的旧事件会被并进错误的槽、两根手指的数据串在一起——源码注释明确说宁可首帧跳一下也不要卡住一根手指。

驱动联调含义：Type B 驱动必须正确维护 tracking id 的分配与 -1 释放，漏发释放会导致 Android 认为手指一直按着（“幽灵触点”）。报点数超过声明槽数会触发裁剪丢点。

**Q5: [learning] SYN_DROPPED 是什么？出现时系统会怎样、该查什么？**

SYN_DROPPED 表示该读取者的输入事件流失去连续性。缓冲溢出是常见原因，但不是唯一原因。

1. **产生条件：**Linux 5.15 中，客户端缓冲溢出会丢弃事件并插入该标记；切换事件时钟时，如果该客户端队列非空，也会清空队列并插入标记。部分状态查询失败补偿路径也可能产生该标记。
2. **Android 处理：**Android 13 的 InputDevice 收到标记后重置设备状态，忽略其后的事件直到下一个 SYN_REPORT，再恢复处理。丢失的历史事件不会自动重建。
3. **读取者隔离：**getevent 与 EventHub 的缓冲独立，一个读取者未见标记不能证明另一个读取者没有丢失事件。
4. **排查方向：**结合缓冲、读取速度、InputReader 调度、时钟切换和设备日志确认实际原因。需要同步当前状态时，根据设备能力与读取接口核实，不能仅凭标记认定某个应用导致溢出。

与它症状相似的还有驱动槽位或 tracking ID 管理错误，例如漏发触点释放；应结合原始事件判断，不能仅凭有无 SYN_DROPPED 就排除其他原因。依据：Linux 5.15 evdev.c 与 Android 13 InputDevice.cpp。

**Q6: [learning] 充电或特定充电器插入时触摸乱跳（鬼触摸），原因与对策链是什么？**

典型成因是电气噪声：充电器的共模噪声经 Y 电容耦合进触控面板的电容检测回路，信噪比骤降后 IC 把噪声判为触点。劣质充电器纹波更大、非隔离 DC-DC 更明显。其他来源包括显示屏（尤其高刷新率模组）与 TP 之间的耦合、地弹、ESD、结构压应力（边框挤压使静态电容漂移）。这些是触控行业的通用结论（厂商应用笔记口径，本地树无内核驱动源码，证据等级为二手）。

对策按层递进：IC 侧开启跳频（在多个发射频率间自动避开干扰频点）、充电检测联动（插入充电器时切高阈值/低灵敏度档）、噪声阈值自适应。硬件侧改进屏蔽与接地、TP 与显示间加屏蔽层。部分厂商驱动会暴露 sysfs/proc 节点动态切换这些模式。

排查口径有规律可循：只在充电时乱跳优先查充电器与跳频配置（换原装充电器复测是第一步）。固定区域乱触怀疑结构压应力。完全随机乱点怀疑 ESD 或地。复现路径要固定（同一充电器、同一亮度、同一界面），否则驱动参数调了也验证不了。

**Q7: [learning] 边缘滑动断触、干手指没反应，是同一类问题吗？怎么分？**

不是同一类，信号幅值与算法抑制是两个不同环节。边缘断触的典型原因是触控面板边缘电场畸变（ITO 走线区信号弱），IC 的边缘抑制算法把这些区域的低质量触点滤掉——表现为手势滑到屏幕边缘丢失。对策是调整边缘补偿参数或放宽边缘区的判定阈值（厂商驱动参数，行业通用结论）。干手指（或手套模式未开）则是触点电容变化量低于阈值，IC 判为未接触。对策是开启手套/高灵敏模式或降低阈值，代价是鬼触摸风险上升。

区分方法看报点流的形态：边缘断触的 `getevent` 序列里坐标沿边缘推进然后整帧消失（触点被算法丢弃）。干触是按压瞬间就没有触点产生（阈值未达）。前者调边缘参数，后者调阈值或模式，改错了方向参数怎么调都无效。

车机场景加两条：贴膜（尤其厚钢化膜）会系统性降低信号幅值，量产前要用目标膜材测。低温环境电容特性变化，低温手套场景要在高低温箱里验证阈值余量，常温调好的参数冬天可能不够。

**Q8: [learning] 触控 IC 与驱动联调有哪些标准入口？**

以主流方案为例（厂商驱动资料口径，本地树未含驱动源码）：读版本与身份——Goodix 部分 GT9xx 型号上电后从对应寄存器读 product id，FocalTech FT 系列有对应的固件版本寄存器，驱动 probe 日志（dmesg 里的 probe 成功/失败、product id、fw version）是第一证据。改配置——该项目所用 GT9xx 型号的配置是一段 186 字节的寄存器数组（灵敏度、跳频、噪声阈值等都在其中），一个常见坑是配置尾部的版本号必须大于 IC 内已存版本否则新配置不生效（“改了参数没效果”先查版本号递增）。调试节点——vendor 驱动普遍暴露 sysfs/proc 节点（fw_version、glove、charger、gesture 等模式开关），量产前这些节点要按安全要求收敛。

通用流程性入口与厂商无关：dmesg 的 input core 注册行（`input: xxx as /devices/.../input/inputN`）确认驱动注册成功。`/proc/bus/input/devices` 的位图与 `getevent -p` 等价。I2C 通信失败（probe 阶段 NACK）先查上电时序与从地址（GT9xx 的中断脚电平还兼从地址选择）。

车机特有的收敛点：触控固件升级走厂商定义的时序握手进 bootloader，失败态要有恢复路径。调试节点与固件升级接口在量产版本要按安全基线关闭或加权限。

**Q9: [learning] 想看到触控 IC 的原始电容数据（热力图），有什么现成管道？**

部分触控 IC 会额外暴露一个带 `V4L2_CAP_TOUCH` 能力的视频节点，输出原始电容矩阵帧。AOSP InputReader 里有配套的 `TouchVideoDevice`：以非阻塞方式打开该节点、`VIDIOC_QUERYCAP` 校验能力、mmap 多缓冲采集热力图帧，帧数据（宽高与原始值）以 `TouchVideoFrame` 结构保存（按 AAOS13 源码核对，`reader/TouchVideoDevice.cpp`）。这是研究 IC 原始感知（触点形状、噪声分布、水膜与压应力特征）的现成管道，不需要在驱动里加自定义接口。

用途定位是研究与疑难分析：驱动工程师定位“IC 看到了什么”（区分是感知问题还是算法问题），算法侧采集数据训练防误触模型。常规功能排查用不到它——`getevent` 的报点流已覆盖绝大多数场景。而且热力图数据量大，开启采集对性能有影响，只在受控调试环境使用。

配套关系要清楚：热力图是驱动的原始感知层，报点流是 IC 算法处理后的结果层。两者对照可以回答“IC 没报点是因为没感知到，还是感知到了但被算法抑制”——这正是鬼触摸/断触定性（硬件问题还是参数问题）的分水岭。

**Q10: [learning] 输入链路中的 input core、evdev 和 /dev/input/eventX 分别是什么？**

它们分别是内核中的输入事件处理层、向用户态提供事件的接口，以及访问该接口的设备节点。事件经过的路径是：

输入设备或虚拟输入设备 → 输入驱动 → input core → evdev → `/dev/input/eventX` → EventHub → InputReader。

1. **输入驱动和 input core**：驱动将按键、坐标等变化报告给 input core。input core 是 Linux 输入子系统的公共处理层，负责将事件交给对应的事件处理器。
2. **evdev**：内核中的通用输入事件处理器，接收 input core 转交的事件，供用户态程序读取。每次独立打开设备节点都会建立自己的事件缓冲区。
3. **设备节点**：`/dev/input/event0`、`/dev/input/event1` 等是字符设备节点，是程序访问内核输入设备的入口，不是保存事件日志的普通文件。物理输入设备和虚拟输入设备都可能对应这类节点。
4. **两种写法**：`/dev/input/eventX` 中的 `X` 是编号占位符，例如实际节点可以是 `event0`。`/dev/input/event*` 中的 `*` 是通配符，表示匹配多个节点，常用于命令行或泛指这类节点。`open()` 不会自行展开 `*`。编号可能随设备发现顺序变化，`event0` 不一定是触摸屏。
5. **读取接口**：程序用 `open()` 打开实际节点，获得文件描述符；可通过 `epoll` 等待可读，再用 `read()` 读取 `input_event` 结构，包含时间、类型、编码和值。还可用 `ioctl()` 查询设备支持的按键、坐标轴等能力。
6. **Android 侧**：EventHub 扫描 `/dev/input`，打开实际设备节点并读取事件，再交给 InputReader 解析为 Android 输入事件。

依据：Linux 内核 `Documentation/input/input.rst` 和 Android 13 `EventHub.cpp`。

**Q11: [learning] uinput 是什么？怎么用它创建一个虚拟按键设备？**

uinput 是内核提供的虚拟输入设备接口：用户态程序打开 `/dev/uinput`，声明设备能力，内核就生成一个与其他真实设备无差别的 evdev 节点，之后 `write()` 事件即可注入。按 AAOS13 源码核对（`bionic/libc/kernel/uapi/linux/uinput.h`），主要 ioctl 包括 `UI_SET_EVBIT`/`UI_SET_KEYBIT`/`UI_SET_RELBIT`/`UI_SET_ABSBIT`（声明事件类型与各码位能力）、`UI_DEV_SETUP` + `UI_DEV_CREATE`（设备名/VID/PID 与创建）、`UI_DEV_DESTROY` 销毁。

典型流程：设 `UI_SET_EVBIT(EV_KEY)` → 逐个 `UI_SET_KEYBIT(所需扫描码)` → `UI_DEV_SETUP`（name、bus/vendor/product）→ `UI_DEV_CREATE` → 循环 `write(input_event)` 注入（`EV_KEY` 按下/释放 + `EV_SYN/SYN_REPORT` 收尾）。注入的设备走与真实硬件完全相同的 EventHub → InputReader 路径，对 Android 而言不可区分。这也意味着虚拟设备同样受 `.kl` 映射、权限与安全机制约束。

使用场景：模拟旋钮/按键做自动化测试（比 `adb shell input keyevent` 更接近真实设备，因为走的是设备层而非注入层）。把 MCU 经串口上来的协议翻成标准输入事件。调试 InputReader 的设备接入逻辑。注意与系统注入的区别——uinput 是“造设备”，`input` 命令是“发事件”，前者需要驱动权限（root 或特定 SELinux 域），后者只要 shell。

**Q12: [learning] getevent 有哪些参数？测触控上报率用哪个组合？**

Android 13 的 toolbox `getevent` 常用参数如下：

1. `-t`：为事件打印时间戳。
2. `-l`：把事件类型和代码显示为助记符。与 `-t` 组合的 `-lt` 便于按时间阅读事件流。
3. `-i`：打印设备身份信息，例如 bus、vendor、product、version 和 name。
4. `-p`：打印设备能力位。
5. `-c N`：读取 N 条事件后退出，适合脚本化采集。
6. `-r`：统计同步事件速率，可用于观察触控设备的 `SYN_REPORT` 频率。
7. `-s <bit>` 和 `-S`：查询开关状态。
8. `-v`：增加输出详细程度。
9. `-d`：打印 HID 描述符信息。

测触控上报率时，`-r` 统计每秒 `SYN_REPORT` 次数。按住屏幕移动可观察当前设备的报告频率，但该频率不等于显示刷新率，也不能单独证明每个报告都对应有效坐标变化。`-c` 配合 `-lt` 可限制采集量，例如 `getevent -lt -c 200 /dev/input/event2` 在读取 200 条事件后退出。

`-il` 可同时列出设备信息及加载的 key layout、key character map 和 input device configuration 路径，便于确认映射文件命中情况。读取 `/dev/input` 需要相应权限。若 shell 无法访问节点，应结合构建类型、节点权限和 SELinux 拒绝日志判断，不能据此认定设备不存在。

**Q13: [learning] 没有第三方工具时，/proc/bus/input/devices 和 sysfs 能回答什么问题？**

`/proc/bus/input/devices` 每个设备一组字段：`I:` 总线/厂商/产品/版本、`P:` 物理拓扑路径、`S:` sysfs 路径、`U:` 唯一标识（蓝牙设备常见 MAC）、`H:` handlers（对应哪个 eventX 节点）、`B:` 各类事件能力位图。它回答“系统里有哪些输入设备、各自在哪个节点、是什么身份”——`getevent -il` 需要逐设备打，这份文件一次看全，还能与 `dumpsys input` 交叉验证“内核暴露的”与“Android 识别的”设备清单是否一致。

sysfs 侧的常用入口：`/sys/class/input/inputN/name`、`/sys/class/input/inputN/capabilities/`（能力位，与 `B:` 行同源）、触控厂商驱动挂的自有节点（固件版本、模式开关，节点名随厂商各异）。虚拟按键定义在 `/sys/board_properties/virtualkeys.<设备名>`（行格式 `0x01:扫描码:中心X:中心Y:宽:高`）。

排查定位：新设备没被识别时，先看这份文件确认内核层是否存在——不存在查驱动/probe 日志（dmesg），存在而 `dumpsys input` 没有，查 EventHub 打开失败的原因（权限、SELinux、配置加载失败）。

**Q14: [learning] 整机触摸“完全没反应”，通用 Android 设备上的分层决策树是什么？**

按“事件存在性”从底层向上五层收敛，每层给出判定命令：

1. **驱动层**：`getevent -lt` 按住屏幕——无输出查 TP 驱动（dmesg probe、中断、固件）。有输出记录时间戳与坐标供后续比对。
2. **识别层**：`dumpsys input` 设备清单是否有该设备、分类是否正确（触摸屏被识别成别的类则事件形态全错）。加载的 `.idc` 是否正确（视口/绑定错则坐标错屏）。
3. **分发层**：`Windows:` 段确认有可触摸窗口且 `touchableRegion` 覆盖屏幕。全局监视者是否接管。安全模式/无障碍的触摸探索开启时行为改变（每次单触被转译为探索手势）。
4. **注入对照**：`input tap` 有效而真机无效 → 问题在 1–2 层（设备与坐标）。注入也无效 → 3 层以下（窗口与策略）。
5. **环境矩阵**：安全模式（排除第三方应用与无障碍）、新建用户（排除用户级配置）、恢复出厂前最后确认——环境类复现矩阵能快速切掉“软件环境”变量。

车机硬键的排查另有专用分层法（第一分岔同样是区分 VHAL 链与设备链）。“部分区域无反应”不走本决策树，先查该区域的遮挡与虚拟按键定义，再查触控边缘抑制。

**Q15: [learning] “屏幕乱跳/自动乱点”（鬼触摸类）现场怎么取证才能定位到硬件还是软件？**

取证目标是用可复现的证据把问题切到“感知层/算法层/应用层”。固定动作：

1. **建复现矩阵**：充电器（原装/第三方/无线）、电源（充电/电池）、温度（常温/低温）、贴膜（有无）、握持位置、界面（固定界面与随机界面）逐维记录——只在充电时出现指向噪声，只在固定区域指向结构/压应力。
2. **抓原始报点**：`getevent -lt -c` 录下乱跳时段的完整事件流——固定坐标的幽灵点（同一位置反复出现）多为结构或传感通道问题。随机散点伴随 `SYN_DROPPED` 为缓冲溢出或强噪声。坐标形态与手指动作相关（画圈变乱跳）考虑固件滤波参数。
3. **排除软件侧**：同一段事件流回放给无 UI 的界面（或检查应用日志确认没有手势识别误触发）——报点异常而应用行为正常说明问题止于感知层。报点正常而应用乱响应查应用手势逻辑。
4. **交叉验证**：换充电器/断电复测、摘膜复测、温度恢复后复测，固定变量逐个排除。

产出的结论要带矩阵与报点样本，“偶尔乱跳”没有矩阵支撑就无法回归验证整改效果。IC 参数类整改（跳频、阈值）的验证也要用同一矩阵复测。

**Q16: [learning] 触控采样率与刷新率分别能缩短哪段输入反馈延迟？**

两者改变的是不同环节，不能把标称参数直接换算成触摸到屏幕发光的总时长：

1. **1000 Hz 触控采样：**理想采样间隔约 1 ms。驱动批处理、事件预测、游戏逻辑、GPU 队列和显示扫描仍增加延迟。
2. **高刷新率：**60 Hz 与 120 Hz 的刷新间隔约为 16.67 ms 与 8.33 ms。应用和 GPU 能按时出帧时，显示侧等待可缩短。应用已经积压时，提高刷新率不能让 MotionEvent 更早送达。窗口请求的模式还受 SurfaceFlinger 图层投票与设备能力约束，Game Mode 的 FPS throttling 只能限速。

`requestDisallowInterceptTouchEvent(true)` 只影响 ViewGroup 的应用内拦截，改变不了 InputDispatcher 的目标选择。测量时按 Perfetto 输入事件的 read、dispatch、handling、ack 和关联帧 present 分段，记录帧关联覆盖率与输入源。量产 user 构建可结合 FrameTimeline 与自定义标记，详细 `android.input.inputevent` 数据源仅供 userdebug/eng。报告 P50/P90/P95/P99 和样本量，自动化注入样本单独分组。

**Q17: [learning] virtio-input 事件包含什么，怎样从虚拟设备到达客体输入系统？**

virtio-input 是 virtio 输入设备，事件是设备与驱动间传递的一条输入记录。按 Virtio 1.2，记录包含 type（类型）、code（该类型下的代码）和 value（值），以小端格式传输。记录本身没有时间戳字段。

假设设备支持多点触摸，且已选中处于接触状态的槽位，下面是一组示意更新：

1. `EV_ABS / ABS_MT_POSITION_X / 500`：报告 X 坐标为 500。
2. `EV_ABS / ABS_MT_POSITION_Y / 300`：报告 Y 坐标为 300。
3. `EV_SYN / SYN_REPORT / 0`：结束这一组状态更新。

事件的传递步骤如下：

1. **接收缓冲区：**guest 驱动向 eventq 提供设备可写的缓冲区。设备将输入记录写入缓冲区并发布完成状态。
2. **客体处理：**驱动取回记录并重新提供缓冲区。Linux virtio_input 驱动将 type、code、value 交给 input core，evdev 再向用户态提供输入事件。
3. **Android 分发：**EventHub 和 InputReader 读取并处理输入，后续分发阶段才将对应事件交给应用。一个输入更新通常包含多条记录，不能将单条记录、一次队列通知与一个 MotionEvent 等同。
4. **反向状态和丢失：**statusq 可用于从驱动向设备反馈键盘指示灯等状态。若 eventq 缺少可用缓冲区，规范允许设备丢弃输入。是否发生丢失需结合实现和观测数据判断。

不能仅凭该记录得到 host 产生输入的时间。Linux 具体输入路径可在后续环节提供或换算时间戳，取时位置与时钟须按对应内核实现核实。依据：OASIS《Virtual I/O Device 1.2》§5.8、Linux virtio_input 驱动。

**Q18: [learning] 触摸屏和触控板的设备类型如何配置与排查？**

Android 可根据驱动报告的能力自动识别，也可通过设备匹配的 idc 文件明确触摸设备类型。`touch.deviceType` 的可用值和行为应按目标版本核验。

1. **touchScreen：**作为关联显示的触摸屏。
2. **touchPad：**作为不直接关联显示的触控板。
3. **pointer：**作为间接指针操作设备。
4. **default 或未指定：**由系统依据设备能力自动判断。

排查时先用 `adb shell getevent -li` 核对设备能力，再用 `adb shell dumpsys input` 检查识别类型及关联。配置文件是否被选中取决于设备标识与查找规则；不要只因文件存在就认定已生效。依据：AOSP《Touch devices》和 Android 13 TouchInputMapper。

**Q19: [learning] 触控笔的压力和悬停异常怎样分层检查？**

触控笔能否报告压力、悬停和工具类型取决于设备及驱动，应用不能假定这些能力总是存在。

1. **设备和内核：**检查设备声明的按键与坐标轴，确认接触、悬停或压力变化是否产生事件。
2. **Android 识别：**检查输入设备能力和显示关联，区分笔和手指的工具类型。
3. **应用处理：**检查 MotionEvent 的工具类型、动作和相应轴值，并正确处理取消。
4. **源码：**Android 13 的 TouchInputMapper 与 ExternalStylusInputMapper 可用于追踪目标设备的转换路径。

能力、校准和厂商笔协议因设备而异。驱动未报告的压力不能由应用可靠推断。
