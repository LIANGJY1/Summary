# 输入链路总览：进阶

> 对应主课程中的详细机制、配置、源码和排查。题目按来源版本说明适用范围。

**Q1: [learning] 一次点击“没有反应”，输入事件从硬件到 View 树要经过哪些阶段，排查时按什么顺序分段定位？**

事件主链路是：内核 input core/evdev（`/dev/input/eventX`）→ `EventHub`（epoll + inotify）→ `InputReader`（mapper 生成 `NotifyArgs`）→ 监听链 → `InputDispatcher`（目标选择与队列）→ `InputChannel`（AF_UNIX SOCK_SEQPACKET 套接字）→ 应用 `NativeInputEventReceiver` → `ViewRootImpl` 的 `InputStage` → View/ViewGroup。“没有反应”可能停在链路上任何一段，且帧率正常不能证明输入及时到达。

排查按“事件是否存在”逐级缩小，顺序为：

1. `getevent -lt`：确认 evdev 节点是否产生事件及时间戳，排除触控固件与驱动。
2. `dumpsys input`：确认设备启用、视口、焦点窗口与连接状态。
3. 输入系统跟踪：确认 `RawEvent`、`NotifyMotionArgs`/`NotifyKeyArgs` 是否出现。
4. `InputDispatcher` 丢弃与超时日志：确认是否因过期、策略、安全校验或无目标被丢。
5. 应用侧 `deliverInputEvent` 与主线程状态：确认事件已到达但消费被阻塞。

`InputReader` 与 `InputDispatcher` 是 `system_server` 中的原生线程（`libinputflinger` 库，不是独立进程）。`adb shell input tap` 走系统注入路径，可以绕过真实硬件与 evdev，注入成功只能说明注入点之后的链路可用。按 AAOS13 源码（`frameworks/native/services/inputflinger/InputManager.cpp`）核对，Android 13 的监听链是 `InputReader → UnwantedInteractionBlocker → InputClassifier → InputDispatcher`。Android 14 起分类组件改为 `InputProcessor`，Android 17 链上还增加了 `PointerChoreographer`、Rust 桥接的 `InputFilter` 等阶段，分析具体设备时按对应标签确认。

**Q2: [learning] 点击无响应时，WMS、InputFlinger 和应用各自可能的责任段是什么？**

输入事件先由 native InputFlinger 处理：InputReader 读取并规范化设备事件，InputDispatcher 按输入窗口快照选择目标并投递。WMS 不遍历触摸事件，而是经 DisplayContent 的 InputMonitor 把每个窗口的 input token/channel、touchable region、transform、focusable 与当前焦点窗口写进 `SurfaceControl.Transaction.setInputWindowInfo()`，与 layer 状态同一批提交（AAOS13 源码核对 InputMonitor）。输入延迟因此拆成三段：快照过期（窗口移动或转场后 input info 未更新，查 WMS/InputMonitor 的提交与快照发布时序）、队列等待（目标正确但 dispatcher 或线程调度延迟）、应用处理慢（事件已到但主线程被锁、I/O 或重计算占用）。InputDispatcher 判定无焦点或窗口无响应时，经 InputManagerCallback 回到 WMS，由 AnrController 通知 ActivityManager 产生 ANR。ANR 超时受目标窗口与应用状态影响，不应硬编码成单一的“5 秒”结论。

**Q3: [learning] 车机物理按键从按下到应用响应的完整链路是什么？**

标准链路（VHAL 路线）是：物理按键 → MCU/CAN → VHAL 实现写入 `HW_KEY_INPUT` 属性 → CarService 的 `InputHalService` 收到属性变化并转成标准 `KeyEvent` → `CarInputService` 做车载级分发（特殊键处理、显示路由、捕获仲裁）→ 无人拦截时经 `injectInputEvent` 注入系统 → `InputDispatcher` 按目标屏焦点窗口分发 → 应用 `onKeyDown`。每段都有独立观测点，任何一段断链或被截走，表现都是“按键没反应”。

这条链的关键设计是：按键在 CarService 层以**标准 KeyEvent** 的形态注入，后续与真实输入设备的事件走完全相同的系统分发——应用不需要为车机硬键写特殊通道。而按键进入 Android 之前的车载语义（投到哪块屏、长按含义、是否给仪表）全部在 CarService 层裁决，这是它与普通 Android 设备的本质区别。

对应地，旋钮（`HW_ROTARY_INPUT`）与 OEM 自定义键（`HW_CUSTOM_INPUT`）各有专属属性，在 `InputHalService` 里与按键并行转换。排查硬键问题的第一分岔就是确认按键走的是这条 VHAL 链还是 HID/uinput 设备链——前者 `getevent` 无输出，后者有。

**Q4: [learning] 复现一个输入问题，一次到位的采集清单是什么？**

按“一次复现、五路证据”组织，避免反复复现引入变量：

1. **事件流**：`getevent -lt -c N <对应节点>`（或全节点）覆盖复现窗口——原始报点与时间戳的基线。
2. **系统日志**：`logcat` 全量（分发器、ANR、窗口相关标签都在里面），复现结束后立刻停。
3. **状态快照**：复现前后各一次 `dumpsys input`（必要时加 `dumpsys window`、车机加 `dumpsys car_service --services CarInputService`），对比差异而非只看单次。
4. **性能轨迹**：Perfetto 短窗口采集（含输入计数轨道与应用进程），用于时序对齐与帧分析。
5. **现场上下文**：设备状态记录——电源/充电、温度、亮灭屏、当前前台与焦点窗口、复现步骤的精确时间点（对照 getevent 时间戳）。

纪律：采集顺序先被动（1–4 并行启动）后主动（注入对照、参数试探）。每改变一个变量重新采集而不是混在一份记录里。上报问题时附上“哪条证据排除了哪一层”——比“现象+日志一大包”的处置速度快一个量级。

**Q5: [learning] 点击与拖动的输入到反馈延迟怎样定义起止点？**

交互延迟必须从对应动作的输入样本起算，到用户所需的反馈帧呈现结束。按压反馈、点击结果和连续拖动的起点不同，混用会让相同实现得到不同数字：

1. **按压反馈：**普通 View 通常在 ACTION_DOWN 后显示按下态，从 `ACTION_DOWN.eventTime` 到包含该状态的帧呈现。
2. **点击结果：**普通点击在抬手后确认，从 `ACTION_UP.eventTime` 到包含操作结果的帧呈现。
3. **拖动反馈：**逐个输入样本计算 event-to-photon 延迟并比较整段手势的分布。只量“开始移动到列表首次滚动”会漏掉中段波动。

`MotionEvent.getEventTimeNanos()` 接近系统输入样本时刻，不是手指接触玻璃的物理时刻。present 信号也不是面板像素完成发光。因此 Perfetto 适合量软件路径，实验室级 touch-to-photon 还需高速相机或光电传感器。报告要同时写明动作起点、完成标志与帧呈现口径，不能把回调结束当成可见反馈。

**Q6: [learning] 触摸 ACK 很快，为什么画面仍可能迟迟没有反馈？**

ACK 只表示应用完成输入事件处理，反馈还须等帧调度、渲染、合成与呈现。AAOS13 的输入链可按先后拆开：

1. **读取和选目标：**驱动经 Linux input 子系统产生事件。system_server 内的 InputReader 通过 EventHub 读取并转换坐标，InputDispatcher 选择目标窗口。
2. **交给应用：**InputPublisher 经 InputChannel 写入 Unix domain socket。Binder 用于建立窗口和通道，不承载每条 MotionEvent。应用的 NativeInputEventReceiver 收到后交给 ViewRootImpl 和 `dispatchTouchEvent()`。
3. **确认已处理：**应用调用 `finishInputEvent()` 回送 ACK。Perfetto `android.input` 标准库的 `total_latency_dur` 到系统收到 ACK 为止。
4. **产生可见反馈：**Choreographer 调度帧，应用渲染并提交 buffer，SurfaceFlinger 合成和 present。`end_to_end_latency_dur` 延伸到关联帧呈现。缺少可信帧关联时为 NULL。

两列相差大时检查 ACK 之后的 VSync 相位、渲染、buffer 和合成，不能直接认定输入分发慢。AAOS13 的 `InputManager::start()` 在 system_server 内启动 InputReader 和 InputDispatcher 两条 native 线程，不存在独立的 InputFlinger 进程。

**Q7: [learning] 分析输入延迟时，怎样把事件时间、通知、分发和应用处理分段？**

先选定同一事件和一致的时间口径，再用可观测端点分段；每段只说明两个端点之间的时间，不自动代表其中某个函数的执行耗时。

1. **设备记录到读取：**比较事件时间与读取时间，确认时间域及上游盲区。
2. **读取到系统分发：**检查 Reader 监听链、过滤或回注，以及 Dispatcher 处理。
3. **分发到应用：**检查目标连接、通道、应用调度与事件消费。
4. **应用到呈现：**需要额外的帧关联与显示证据，不能用输入回执代替。

例如在一份 AAOS13 采集中，事件时间到应用回调约 43.597 ms，分段包含读取、过滤回注及分发；该值是单次观察，不能外推为设备固定延迟。依据：《全链路解剖》15 篇 §2—§3。

**Q8: [learning] 看到主线程 Sleeping 或 Runnable 很久，能直接断定输入卡在应用执行吗？**

不能。线程状态反映该时间窗内的调度状态，不直接给出具体等待条件或哪个函数耗时。

1. **Sleeping：**线程处于等待状态，还需其他证据确认等待对象。
2. **Runnable：**线程可以运行但尚未获得 CPU，不属于该线程执行代码的耗时。
3. **Running：**线程正在 CPU 上执行，仍需结合 trace 片段判断具体工作。

一次 AAOS13 采集中，应用主线程约 50.928 ms 处于 Sleeping，结束时由输入分发线程唤醒；这本身不足以证明睡眠期间唯一等待对象或完整根因。依据：《全链路解剖》14、15 篇。

**Q9: [learning] 一次输入通知到分发相差约 35 ms，为什么不能直接归因于 Dispatcher 排队？**

因为这两个观察点之间可能还存在过滤、跨线程转交和回注，事件并不一定在整个区间内都位于 Dispatcher 入站队列。

在《全链路解剖》的一次 AAOS13 采集中，同一事件从 notifyMotion 到 prepareDispatchCycleLocked 约 34.738 ms。证据支持该事件经过 InputFilter 转交和回注，而不能把整个间隔等同于入站队列排队。过滤器内部具体执行情况及调度竞争的单一根因仍未证实。

分析时应核对过滤状态、入队时刻、队列计数和线程状态；该案例是一次采集结果，不代表所有设备的固定行为。依据：该系列 06、15、16 篇。
