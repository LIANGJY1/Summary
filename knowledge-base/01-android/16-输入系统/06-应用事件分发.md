# 应用事件分发

> 以 Android 13 为主要参考。基础流程和职责在本册，详细配置、源码及排查见 [应用事件分发进阶](进阶/06-应用事件分发进阶.md)。

**Q1: [learning] 系统发给窗口的触摸事件怎样到达 View？**

应用通过窗口的输入通道收到事件，ViewRootImpl 将事件送入界面处理流程，随后经过 Activity、Window、ViewGroup 和目标 View 的分发。具体路径受窗口和事件类型影响。

Android 13 可从 `ViewRootImpl.java`、`ViewGroup.java` 和 `View.java` 查看应用侧处理。

**Q2: [learning] View 消费触摸事件意味着什么？**

事件处理方法的返回值会影响当前事件是否被视为处理，以及后续手势事件的分发。通常一个目标未接受 ACTION_DOWN，就不能依赖它继续收到同一手势后续事件。

父容器拦截、窗口变化或取消也会改变后续去向，应结合实际分发层次判断。

**Q3: [learning] MotionEvent 中的坐标与指针标识如何理解？**

MotionEvent 可以包含一个或多个指针及其坐标。pointer id 用于在一次手势中识别指针，pointer index 是当前事件中访问该指针的位置，可能随手指增减变化。

局部坐标和屏幕坐标的参考系不同，使用前应确认目标 View、窗口和显示的变换关系。

**Q4: [learning] 应用处理输入慢与画面反馈慢怎样区分？**

分别观察事件到达、应用完成处理和反馈帧呈现。事件已完成处理并不代表画面已呈现，主线程阻塞也可能同时推迟输入和绘制。

事件时间、处理完成时间与帧呈现时间属于不同观察点，测量时应写明起点和终点。

**Q5: [learning] 输入处理完成为什么不代表画面已经显示？**

应用确认输入只表示本次事件处理已完成。可见反馈还需要帧调度、应用渲染、合成和呈现，因此输入正常也可能因后续帧延迟而感觉卡顿。

排查时分别观察设备上报、事件分发、应用处理和反馈呈现，不能把某一段耗时当成完整的用户感知延迟。

**Q6: [learning] 不同输入设备在应用侧都产生触摸事件吗？**

不一定。按键通常通过 KeyEvent 表达；触摸、鼠标、触控笔和摇杆等可通过不同来源与动作的 MotionEvent 表达；输入法提交文本则使用文本输入接口。

应用应根据事件类型、source 和设备能力选择处理方式，不应把所有 MotionEvent 都当作手指触屏。
