# Linux输入与虚拟设备

> 以 Android 13 为主要参考。基础流程和职责在本册，详细配置、源码及排查见 [Linux输入与虚拟设备进阶](进阶/02-Linux输入与虚拟设备进阶.md)。

**Q1: [done] Linux 输入子系统的事件从设备到用户态经过哪些环节？**

Linux 输入子系统将不同设备的状态变化转换为统一事件，供用户态读取，无需分别解析各设备的硬件协议。以 Android 触摸输入为例：

触摸设备 → 输入驱动 → input core → evdev → `/dev/input/eventX` → EventHub → InputReader

1. **输入设备和驱动：**设备产生触摸坐标等状态变化，驱动将其转换为 Linux 输入事件并上报。虚拟设备也可通过对应的虚拟驱动上报。
2. **input core：**这是内核输入子系统的公共层。它检查设备能力、维护输入状态，并在收到 `SYN_REPORT` 等同步标记时，将积累的变化交给已连接的处理器。
3. **evdev 和设备节点：**evdev 是输入事件处理器，将事件写入读取者的缓冲区。用户态程序通过 `/dev/input/eventX` 设备节点读取事件。
4. **Android 读取和转换：**EventHub 打开节点并读取事件。InputReader 根据设备类型和配置，将原始事件转换为 Android 输入事件，再交给后续分发。

设备接入时，驱动先注册输入设备并声明能力，evdev 再与匹配的设备建立连接。输入事件中的一组状态更新不等同于一次 Android 事件或一帧画面。

依据：Linux 5.15 输入子系统，以及《全链路解剖》02—04 篇。

**Q2: [done] evdev 和输入设备节点是什么，为什么有多个节点？**

evdev 是 Linux 内核中向用户态提供输入事件的处理器。`/dev/input/eventX` 是访问某个输入设备事件接口的字符设备节点，例如 `event0`。

1. **为什么有多个节点：**系统可能同时接入触摸屏、键盘等多个输入设备。不同节点让程序分别识别设备、查询能力和读取事件。例如 `event0` 可能对应触摸屏，`event1` 可能对应键盘。编号不是固定的。
2. **evdev 怎么工作：**设备驱动上报变化后，input core 将事件交给 evdev。evdev 把事件写入读取者的缓冲区，供用户态通过设备节点读取。
3. **EventHub 怎么读取：**EventHub 扫描 `/dev/input` 目录，打开可用的输入事件节点，查询设备能力，再等待并读取事件。随后 InputReader 根据设备类型处理这些事件。
4. **节点和设备的关系：**节点对应的是内核注册的输入设备，不一定与物理设备一一对应。同一个物理设备可能提供多个输入接口，虚拟输入设备也可以有自己的节点。
5. **两种路径写法：**`eventX` 中的 `X` 是编号占位符。`/dev/input/event*` 中的 `*` 是通配符，用于匹配多个节点，不是实际节点名称，`open()` 也不会自行展开它。

依据：Linux 5.15 `evdev.c`、Android 13 `EventHub.cpp`。

**Q3: [done] Linux input_event 用于哪些组件通信，包含哪些信息？**

input_event 是 Linux 内核与用户态程序之间传递输入事件的数据结构。在读取方向上，内核的 evdev 将事件提供给 EventHub、getevent 等程序，程序通过 `/dev/input/eventX` 的 `read()` 读取。

例如，触摸事件的传递路径是：输入驱动 → input core → evdev → input_event → EventHub。

input_event 包含以下字段：

1. **时间：**事件记录携带的时间，时钟和取时位置取决于配置与输入路径。
2. **type：**事件类型，例如 EV_KEY 表示按键状态，EV_ABS 表示绝对坐标。
3. **code：**类型下的具体项目，例如 ABS_MT_POSITION_X 表示触点 X 坐标。
4. **value：**该项目的值，例如 X 坐标为 500。

一条 input_event 只表达一项事件，一次触摸更新通常包含多条记录。

**Q4: [done] Linux 输入状态、输入事件和同步包分别是什么？**

输入状态描述设备当前的情况，例如按键是否按下、触点是否存在以及触点坐标。输入事件报告一次状态变化；同步包把属于一组更新的事件组织在一起。

以单指触摸为例，假设设备已选定并建立触点，一次上报可能包含：

1. `EV_KEY / BTN_TOUCH / 1`：触摸接触状态变为按下。
2. `EV_ABS / ABS_MT_POSITION_X / 500`：报告触点的 X 坐标为 500。
3. `EV_ABS / ABS_MT_POSITION_Y / 300`：报告触点的 Y 坐标为 300。
4. `EV_SYN / SYN_REPORT / 0`：这组状态更新结束。

X、Y 是独立事件，可同组上报或只上报变化的坐标，同组不代表硬件同时采样。

设备类型和协议会影响实际上报的字段与顺序，多点触摸还需区分触点。

从上报到读取的过程是：

1. **驱动上报：**驱动把事件交给 input core。input core 检查能力、维护状态，并收集需要交付的变化。
2. **同步交付：**常规路径收到 SYN_REPORT 后，input core 将这一组事件交给 evdev。evdev 写入读取者的缓冲，并在完整输入包可读时通知等待者。
3. **用户态读取：**EventHub 等待读取就绪，再通过 `read()` 读取事件。非阻塞读取在当前无数据时可能返回 `EAGAIN`。
4. **恢复状态：**读取者按事件和同步边界更新自己看到的状态。如果收到 `SYN_DROPPED`，说明事件流失去连续性，不能继续假定旧状态完整。

一次 `read()` 可以取到多个完整包，也可能只取走一个已完成包的一部分。一次读取、一次唤醒、一组输入更新和一帧画面不能直接等同。

依据：Linux 5.15 输入子系统，以及《全链路解剖》02、03 篇。

**Q5: [done] virtio-input 的 wire 事件是什么？**

wire 指通信双方约定的数据传输格式。virtio-input 的 wire 事件，就是虚拟输入设备与 guest 驱动之间按照该格式传递的一条输入记录。

1. **包含什么：**记录包含 `type`（类型）、`code`（代码）和 `value`（值）。例如，一条记录可以表示触摸点的 X 坐标为 500。
2. **怎样传递：**guest 驱动准备缓冲区，虚拟设备通过 virtqueue 将事件写入缓冲区。guest 驱动取出记录后，将字段交给 Linux 输入子系统。
3. **时间从哪里来：**这条记录没有时间戳字段，不能直接用它得知 host 产生事件或手指接触屏幕的时刻。后续 Linux 输入事件可以获得时间戳，但取时位置取决于具体输入路径。

这里的 wire 是“传输格式”的意思，不要求数据经过物理网线。依据：Linux 5.15 `virtio_input.h` 和 `virtio_input.c`。

**Q6: [learning] virtio-input 如何接入客体系统？**

virtio-input 是虚拟机中的虚拟输入设备。宿主侧提供输入，虚拟设备通过 virtio 队列向客体驱动传递事件，客体驱动再将事件报告给 Linux 输入子系统。

如果客体运行 Android，后续可经 evdev、EventHub 和 InputReader 进入 Android 输入链。virtio-input 记录本身不携带时间戳，不能仅凭它推断宿主产生输入的时刻。

**Q7: [done] Android 的 getevent 是什么，怎样读取和解析输入事件？**

getevent 是 Android 的输入设备调试工具。它读取 Linux 输入设备上报的原始事件，并把事件字段打印出来。

1. **发现设备：**执行 `adb shell getevent -lp`，查看设备节点、名称和支持的事件类型。`-l` 显示可读名称，`-p` 显示设备能力。
2. **读取事件：**执行 `adb shell getevent -l` 时，工具扫描 `/dev/input`，尝试打开设备节点，并持续读取可用节点上报的事件。需要查看单个设备时，可指定节点，例如 `adb shell getevent -l /dev/input/event0`。
3. **解析字段：**例如 `EV_ABS ABS_MT_POSITION_X 000001f4` 表示一个绝对坐标事件，报告 X 坐标值为十六进制 `1f4`，即十进制 500。`EV_SYN SYN_REPORT` 表示一组状态更新结束。
4. **理解边界：**getevent 根据 Linux 输入事件代码显示名称，不判断用户是在点击还是滑动。它只读取成功打开的节点在监听期间提供的事件，不代表所有车机 VHAL 或软件注入事件都会经过这些节点。节点访问还受权限与设备配置影响。
5. **与 EventHub 的关系：**两者都可读取输入设备。getevent 用于调试并打印事件，EventHub 将事件交给 InputReader 继续处理；独立打开同一节点时，通常各有自己的事件缓冲。

**Q8: [learning] getevent 和 EventHub 同时读取设备，为什么通常不会互相抢走事件？**

evdev 为每次独立打开设备节点的读取者维护独立缓冲。getevent 和 EventHub 通常分别读取各自缓冲中的事件副本。

1. 两个读取者的读取速度和缓冲溢出状态分别判断。
2. getevent 能及时读取，不代表 EventHub 同期也已读取。
3. 设备被独占抓取等特殊配置会影响其他读取者，不能无条件认为所有打开者都能收到事件。

依据：Linux 5.15 evdev 与《全链路解剖》03 篇。

**Q9: [learning] 输入设备已经可读，为什么读取线程仍可能没有运行？**

设备就绪只表示已有数据可读取，等待该设备的线程还需要被调度到 CPU 才能执行。

1. 内核准备好数据并通知等待者。
2. 线程进入可运行状态后，仍可能等待 CPU。
3. 线程获得 CPU 后，EventHub 才能执行读取。

因此，就绪通知时间、开始运行时间和读取完成时间是不同的观察点。

**Q10: [learning] 为什么不能直接比较 getevent 和 Perfetto 中的时间？**

比较前必须确认两个工具使用的时钟域及其映射。时间单位相同，并不代表起点和计时规则相同。

1. CLOCK_MONOTONIC 和 CLOCK_BOOTTIME 对系统挂起时间的处理不同。
2. evdev 读取者可配置事件时钟；getevent 与 EventHub 的实际设置要分别核实，不能只看默认值。
3. trace 若使用不同时间域，需要核对时钟转换；单个时间点吻合不能证明整个采集期间已经完成逐点校验。

依据：Linux 5.15 evdev、Android 13 EventHub 和《全链路解剖》03 篇。

**Q11: [learning] 输入无响应时，怎样区分设备未上报和 Android 未处理？**

先确认内核是否提供设备和事件，再检查 Android 是否识别和分发：

1. **设备与节点：**查看输入设备及其事件节点。节点不存在时检查设备接入和驱动注册；节点存在但打不开时检查访问权限和 SELinux。
2. **事件上报：**在有权限的前提下操作设备并观察事件。节点存在不代表设备一定上报了预期事件。
3. **Android 处理：**确认 EventHub 是否发现设备，再检查设备分类、关联显示和窗口分发。

单凭应用没有响应，不能直接认定驱动故障。
