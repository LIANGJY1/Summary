**Q1: [learning] API 30 的 ApplicationExitInfo 能回答什么、不能回答什么？读取时有哪些边界？**

`ApplicationExitInfo` 是进程退出后留在系统里的历史记录，能补上异常处理器来不及写完的证据，解释 LMK、信号退出、用户强停等非 Crash 退出。它不是实时崩溃回调，只能在后续进程读取，记录与 trace 都可能缺失。

使用边界：

1. **历史性与容量**：通过 `ActivityManager.getHistoricalProcessExitReasons()` 查询近期记录。AAOS13 的 `AppExitInfoTracker` 以 30 分钟间隔把内存状态落盘，`config_app_exit_info_history_list_size` 默认每包 16 条——两者是系统实现细节而非公开契约，写盘前重启可能丢记录，应用仍要保留自己的启动标记与最小崩溃记录。
2. **trace 可能为空**：`getTraceInputStream()` 的数据在全局环形缓冲中，可能被其他应用的新记录覆盖而返回 `null`。Android 12（API 31）起 `REASON_CRASH_NATIVE` 可能返回 tombstone protobuf。进程 ANR 后恢复、后来因别的原因退出时，该记录仍可能附带早先的 ANR trace，原因码与 trace 内容要分别判断。
3. **采样值**：`getPss()` 是按比例分摊共享内存后的驻留量、`getRss()` 是全部驻留物理内存，都是系统最近一次采样，可能为 0，不是死亡瞬间快照。

版本边界：REASON 常量随版本变化，AAOS13（API 33）定义 15 个 `REASON_*`（0–14），Android 14 起新增 `REASON_PACKAGE_UPDATED` 与 `REASON_PACKAGE_STATE_CHANGE`，材料按 Android 17 核对为 17 个（0–16），持久化协议不要写死常量数值。重启后消费记录要按 `processName`、`timestamp`、`reason`、`status` 去重，避免每次启动重复上报同一条历史记录。

**Q2: [learning] ApplicationExitInfo 的 reason 与 status 怎么解释？哪些 reason 容易误判？**

`reason` 是系统分类主字段，`status` 的含义取决于 `reason`：进程自行 `exit()` 时保存退出码，因操作系统信号结束（`REASON_SIGNALED`）时保存信号编号。易误判点：`REASON_USER_REQUESTED` 覆盖“设置中强行停止”与“从最近任务移除”等多种入口，且 Android 14 / API 34 之前包更新也用它（API 34 才加入 `REASON_PACKAGE_UPDATED` 与 `REASON_PACKAGE_STATE_CHANGE`，跨版本报表必须按 API 级别解释）。`REASON_USER_STOPPED` 指多用户设备上的系统用户或工作资料被停止，与 Force stop 无关。低内存终止要先查 `isLowMemoryKillReportSupported()`，不支持的设备上表现为 `REASON_SIGNALED` + SIGKILL，即使支持，`REASON_LOW_MEMORY` 也只说明系统当时有内存压力、不能证明应用泄漏。`REASON_FREEZER` 自 API 33 公开（AAOS13 已具备），指 freezer 相关退出，不能用来命名某个厂商的后台管理功能。`REASON_UNKNOWN` 与一般 `REASON_SIGNALED` 信息不足，不能自动标“被安全中心杀死”。

细分原因 subreason 在平台源码中属隐藏信息，公开 API 没有读取入口。`description` 只是人工阅读文本且格式不保证稳定，服务端不能靠解析字符串恢复内部细分。AAOS13 源码中的公开常量集到 `REASON_FREEZER` 为止，`REASON_MEMORY_LIMITER` 与 `REASON_ANOMALY` 只以 API 10000 预览形式出现在在线参考中，覆盖 API 37 的数据协议不应提前引用。`pss`/`rss`（单位 kB）是系统最近一次采样，进程在采样前死亡时可能为 0——0 要标“不可用”，不插值，也不等于死亡时刻的精确内存。

**Q3: [learning] ApplicationExitInfo 的 trace 附件有哪些读取边界？**

四个边界决定消费方式。其一，trace 在独立的系统级环形缓冲区里，可能被包括其他应用在内的新记录覆盖，`getTraceInputStream()` 返回 `null` 属于允许结果。其二，常见内容是 ANR 线程转储文本，而 API 31 起 `REASON_CRASH_NATIVE` 可返回 protobuf 编码的 tombstone 流——两者格式不同，必须结合 `reason` 判断类型，不能把所有非空流当文本或都标成 ANR。其三，进程从 ANR 恢复后因其他原因退出时，先前的 ANR trace 会附在后一条记录上，实际 `reason` 与附件类型分别保存。其四，读取是 I/O 操作，应在后台按字节上限复制到私有临时文件、校验成功后再发布为待上传附件。超配额、解析失败与缺失都作为明确状态上报。

系统还可能稍后为已有记录补上 ANR trace：本地按来源指纹 upsert（存在则更新、不存在则插入），而不是“看过时间戳就永久跳过”，否则会漏掉后来出现的附件。隐私优先于字段完整度：ANR trace、tombstone 可能包含线程名、文件路径与内存片段，上传前限制字节数、验证格式、删除不需要的数据，无法可靠脱敏的附件不上传。

**Q4: [learning] 用 ApplicationExitInfo 补采集崩溃与 ANR 证据时有哪些字段语义陷阱？Android 13 与 Android 17 的能力差在哪里？**

API 30 起可以通过 `ActivityManager.getHistoricalProcessExitReasons()` 读取当前 UID/包的历史退出记录（AAOS13 已核对存在），它是下次启动后的补充证据，不能替代进程内 crash handler。读取时的语义陷阱：

- `REASON_ANR` 的 trace 通常是系统 ANR 文本流，且流可能为空。
- API 31 起 `REASON_CRASH_NATIVE` 返回按 `tombstone.proto` 编码的 protobuf（AAOS13 源码已核对），不能按 UTF-8 文本解析。
- trace 位于全局环形存储，容量用完后覆盖较旧记录，其他应用的新记录也会占用这份容量。
- 进程发生 ANR 后恢复、再因其他原因退出时，退出记录仍可能带 ANR trace——trace 存在不等于 `reason == REASON_ANR`。
- PSS/RSS 是系统最近采样值，0 也可能表示来不及采样。
- `description` 是面向人阅读的说明，格式不保证跨设备版本稳定，不能当协议切片解析。
- 不支持 LMK report 的设备把低内存 kill 记为 `REASON_SIGNALED` 加 `SIGKILL`，这个组合只能标“可能 LMK”——`SIGKILL` 也可能来自 force-stop、shell 或其他系统策略。

版本差异：API 37 新增 `getAnrInfo()`（ANR 类型、超时时长等结构化信息），AAOS13 源码中不存在该方法，Android 13 只能用 reason 字段加 trace 文本。更早的 Android 8–10（API 26–29）连 `ApplicationExitInfo` 都没有，系统 ANR 与 LMK 对普通应用没有本地查询 API，只能用 watchdog 标疑似事件、用 heartbeat 与正常退出标记识别“非正常消失”并保留 unknown，系统级证据依赖 Vitals、bugreport 或厂商渠道。

**Q5: [learning] 用 ApplicationExitInfo 补偿崩溃采集时，为什么同一事件可能被 SDK 和系统历史各记一次？怎么去重？**

getHistoricalProcessExitReasons()（API 30 起，AAOS13 已具备）返回有界历史，记录会被更近的退出淘汰。`getTraceInputStream()` 来自独立的系统级环形缓冲区，可能被包括其他应用在内的后续记录覆盖而返回 `null`。API 31 起 `REASON_CRASH_NATIVE` 可返回 protobuf 编码的 tombstone 流。同一退出因此可能同时被 Crash SDK 与系统历史发现。

去重要综合应用构建、进程名、相近发生时间、退出原因、SDK 事件 ID，以及可用的致命信号、Build ID 或栈顶帧，不能只拼“PID + 时间戳”——PID 会被系统复用。读取时机是下次获得运行机会时尽早读、限量入库，收到服务端确认前保留记录。发现可读 trace 时立即在字节上限内复制到私有目录并关闭流，不把系统侧流当长期归档。非空 trace 不覆盖实际 `reason`：进程可能从 ANR 恢复后又因其他原因退出，旧的 ANR trace 附在后一条记录上，实际原因与附件类型分别保存。

**Q6: [learning] getHistoricalProcessExitReasons() 的三个参数怎么用？历史容量有多大？**

`ActivityManager.getHistoricalProcessExitReasons(packageName, pid, maxNum)` 的三个参数分别限定包、进程和返回数量：

1. **`packageName`：**传 `null` 时匹配调用者 UID 下各包的记录；查询其他 UID 需要系统级 `DUMP` 权限。传具体包名时，通过 `BIND_EXTERNAL_SERVICE` 绑定的外部服务进程记录也可能被纳入。因此，主进程读到推送进程的 `REASON_LOW_MEMORY`，不代表主进程启动失败。
2. **`pid`：**传非 0 值时按进程 PID 过滤。PID 会被系统复用，不能单独作为事件 ID。
3. **`maxNum`：**限制返回记录数；传 0 表示返回系统当前仍保留的全部匹配记录。

返回结果按时间从新到旧排列。历史记录使用有界环形缓冲：AAOS 13 的 AOSP 资源 `config_app_exit_info_history_list_size` 默认每包保留 16 条，设备厂商可以覆盖；这是平台实现默认值，不是 SDK 对所有设备的保证。同一 PID 可能对应多条退出记录。查不到记录可能是缓冲淘汰、系统尚未记录、数据已清除或厂商实现差异，不能据此断定进程没有异常退出。

该查询通过 Binder 批量返回。应在应用可交互后交给后台 `Executor` 执行，避免把历史读取放到首帧关键路径。
