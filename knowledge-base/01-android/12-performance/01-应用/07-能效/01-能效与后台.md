# 应用能效与后台任务

## 功耗归因与结论口径

**Q1: [learning] 用户反馈“应用掉电快”，第一步要把感受转换成什么？三类功耗证据各能回答什么？**

先把感受转换成可重复场景——设备、系统构建、前后台状态、网络、温度、测试区间与业务动作全部固定，否则电量百分比、某条电源轨峰值或某个 UID 的 CPU 时间都不能单独定责。证据分三层：设备能量层（外部电源分析仪、ODPM 电源轨、电池电荷计）回答测试区间内整机或某条供电链路耗了多少能量，不能回答归谁。系统归因层（`dumpsys batterystats`、`BatteryUsageStats`、Android vitals）回答系统把 CPU、网络、WakeLock、传感器活动记给了哪个 UID，数值是模型与硬件数据混合的归因结果。执行行为层（Perfetto、应用日志、方法追踪）回答哪个线程、请求或回调在什么时刻运行。可靠结论至少两层互相印证，并用同机基线对照或逐模块消融复核。报告要保存每次重复的原始结果而不只是均值。

**Q2: [learning] WakeLock 的 tag 为什么必须稳定且不能包含用户信息？用 WorkSource 把锁记到别的 UID 名下可行吗？**

tag 是 BatteryStats 与 Android vitals 聚合的键：稳定 tag（硬编码的包名、类名或操作名）让同一持锁点可聚合、可定位。把请求 ID、时间戳、递增序号或用户 ID 放进 tag 会造成高基数——同一持锁点分散成大量统计项，线上数据无法聚合。系统发现 tag 可能包含个人信息时，诊断工具只显示 `_UNKNOWN`。业务请求 ID 应留在应用日志中，通过时间戳与锁统计关联。

WorkSource 表示“这份工作替哪个 UID 执行”，常见于系统服务或中间层。材料按 Android 17 核对，`PowerManagerService.BinderService.acquireWakeLock()` 会在非空 WorkSource 上校验 `UPDATE_DEVICE_STATS` 权限——普通应用不能借此改写自身归因，也不应把成本转给其他 UID。归因还要注意：某个系统组件持有锁不代表成本一定计在它名下，排查时要结合 WorkSource、UID 与 tag 三条线索。

**Q3: [learning] 客户端 isHeld() 返回 true 的 WakeLock，为什么在系统侧可能根本不生效？WakeLockStateListener 观察到的又是什么？**

`isHeld()` 只说明客户端尚未 release。服务端是否“尊重”这把锁由 PowerManagerService 决定。AAOS13 源码核对（`setWakeLockDisabledStateLocked()`），对应用 UID 的 PARTIAL_WAKE_LOCK 满足任一条件即被禁用：owner UID 处于 cached 状态（`NO_CACHED_WAKE_LOCKS` 开启时按进程状态判断）、设备处于 Doze 且 UID 不在静态或临时豁免名单、Low Power Standby 生效且 UID 不在 LPS allowlist、force-suspend 激活。材料按 Android 17 核对的版本还检查 owner 进程 frozen 状态与 power group 强制禁用——A13 该方法没有 frozen 检查，属版本差异。

`WakeLockStateListener`（API 33 引入，AAOS13 `PowerManager.java` 已含 `setStateListener()`）回调的 `enabled=false` 表示 Framework 服务因上述电源策略暂时忽略这把锁。策略重新允许后，仍处于 held 状态的锁可能再次生效。因此监听状态不能替代 release：客户端仍要保证成功、失败、取消、超时和组件销毁都进入同一条释放路径，引用计数锁还要由单一 owner 管理 acquire/release 配对。

**Q4: [learning] 应用没有调用过 newWakeLock()，Android vitals 里为什么仍会出现归因到它的锁？excessive partial wake lock 指标怎么算、超了会怎样？**

JobScheduler、WorkManager、AlarmManager、FCM、Location 与音频栈都在各自的执行窗口内代持 WakeLock 并归因到发起应用：Job 执行期由调度框架代持、Alarm 投递到 `onReceive()` 完成期间持锁、位置栈在采集与投递期持锁、FCM 在消息投递期间短时持有。所以排查陌生锁名时不能只搜项目里的 `newWakeLock()`，要按锁名与时间回查是哪条 API 链路。WorkManager 管理锁的生命周期也不代表 Worker 可以无限执行——Job 的 stop reason 仍要记录。

excessive partial wake lock 口径（按材料与官方文档转写）：所有非豁免 partial wake lock 在应用后台或运行 FGS 期间的持有时间合计，24 小时内达到或超过 2 小时的应用会话被计入。audio、location 与 JobScheduler user-initiated API 创建的锁豁免。若 28 天内超过 5% 的会话命中，可能影响 Google Play 的可见性（材料记录 2026 年 3 月起逐步执行）。

边界：2 小时与 5% 是质量指标口径，不是系统 API 配额，也不是“每用户可持锁 5% 的时间”。修复要回到 Play Console 的锁名、affected sessions 与 P90/P99 时长定位具体业务，再看持锁区间内的 CPU、网络、定位活动与 suspend 成功次数，不能只看持锁总时长。

**Q5: [learning] 为什么“深色模式省电 X%”与“省电模式提升续航 Y%”不能直接写进产品文案？这两类结论各依赖什么条件？**

因为两者的收益都由设备与内容条件决定。深色模式：收益只对像素自发光的 OLED/AMOLED 且界面颜色占比大的页面明显——图片、视频、地图等媒体像素不随主题变化。LCD 的背光持续工作，页面配色难以形成同等级收益。用户在深色界面上提高亮度还会抵消像素收益。材料引用的单机实验（同一 AMOLED 设备上 Instagram -2.4%、全部场景汇总 -1.4%）只说明该设备该脚本下的方向。文案应写成“在部分 OLED 设备和深色内容页面上可能降低显示功耗”，并把视觉舒适与低光使用作为独立收益。

省电模式：它是策略输入而非固定参数包——AAOS13 源码核对，`PowerManagerService` 发布 low-power 状态，`BatterySaverController` 与 `BatterySaverPolicy` 计算各服务策略。它会限制后台、位置、网络、动画、刷新率或处理器策略，但具体 CPU 上限与刷新率上限不属于统一的应用层保证，OEM 还能叠加策略。材料引用的实验（该设备汇总 -9.1%、YouTube -14%、WhatsApp 无同方向）同样是设备与脚本共同的结果。应用应读 `PowerManager.isPowerSaveMode()`、监听 `ACTION_POWER_SAVE_MODE_CHANGED` 并降低自身工作量。测试报告记录它带来的可观察变化（刷新率范围、任务推迟、网络与频率变化），不要假设固定幅度，也不要直接读写 `Settings.Global.LOW_POWER_MODE` 当控制方案。

## 待机、省电与任务接口

**Q6: [learning] Doze、App Standby Bucket 与用户“后台受限”分别约束什么？待机桶有哪些档位？**

三类后台状态作用对象不同，可以叠加：

1. **Doze：**看设备整体状态（灭屏、静止、未充电），延后网络、Job、Sync 与普通 Alarm，并忽略普通应用的 WakeLock。
2. **App Standby Bucket：**看单个应用的活跃度，控制 job、alarm 与网络预算。
3. **用户“后台受限”：**由用户明确禁止该应用后台活动，不等于系统预测出的待机桶。

一次 Job 延迟可能同时受到 Doze、桶位、配额与网络条件约束。

Doze 有 Light 与 Deep 两套状态机：

1. **Deep Doze：**要求屏幕关闭、未充电且设备持续静止，完整实现依赖 significant motion detector；设备移动、亮屏或接充电器会使其退出。
2. **Light Doze：**Android 7.0 引入，只要求屏幕关闭、未充电，不要求设备静止，因此移动中的设备也可能更早受限。

`dumpsys deviceidle` 的 `mState` 与 `mLightState` 要分开读。DeviceIdleController 属 jobscheduler 模块，源码不在本地 AAOS13 树，状态机按材料核对。

维护窗口外的 Doze 限制主要包括：

1. 普通网络访问暂停，后台 Wi-Fi 扫描停止。
2. 普通 Alarm、Job 与 Sync 延后。
3. 非豁免应用的 WakeLock 被忽略；FGS 提高进程重要性，但不获得设备级 Doze 豁免。
4. 维护窗口短暂恢复网络并批量处理积压工作；窗口间隔由平台版本、overlay、DeviceConfig 与设备实现决定，不是应用可依赖的定时器。

高优先级 FCM 与 allow-while-idle Alarm 只提供受控执行窗口，带有频率边界，不能当持续占用 CPU 的通道。电池优化豁免只覆盖部分限制，不能推导为所有 Alarm 与后台约束都解除。

App Standby Bucket 档位按 AAOS13 `UsageStatsManager.java` 核对：

1. **ACTIVE：**常量值 10。
2. **WORKING_SET：**常量值 20。
3. **FREQUENT：**常量值 30。
4. **RARE：**常量值 40。
5. **RESTRICTED：**常量值 45。
6. **NEVER：**内部桶，值为 50，表示安装后未启动。

桶是资源控制器的共同输入而非执行器：JobScheduler 的 QuotaController、AlarmManager、NetworkPolicyManagerService 各自消费这份状态。官方 power-details 页给的基线适用于电池供电且无豁免的情形，例如 Rare 桶 job 每 24 小时最多 10 分钟、Restricted 桶 job 每天一次最多 10 分钟，充电时基本不按桶限制。分桶阈值属系统实现且厂商可调，不能把某个天数当稳定规则。

观测入口：`adb shell am get-standby-bucket <package>`、`dumpsys deviceidle`、`dumpsys jobscheduler <package>`。最后一条命令在无 jobscheduler 源码的 AAOS13 树上仍可用，只是源码不在本地树。

**Q7: [learning] Battery Saver、Data Saver 与 Low Power Standby 分别限制什么？**

这三种开关属于不同控制面，排查时要分别取证：

1. **Battery Saver：**全局低电量策略。AAOS13 源码中 `PowerManagerService` 发布 low-power 状态，由 `BatterySaverController` 与 `BatterySaverPolicy`（`services/core/java/com/android/server/power/batterysaver/`）计算各服务策略，可影响位置、后台任务、显示与性能；它不会简单地把所有 App 改成 Rare bucket。
2. **Data Saver：**计费网络策略，只处理后台网络访问，不代表设备进入 Doze 或待机桶变化。
3. **Low Power Standby：**Android 13 / API 33 起公开，AAOS13 树中有 `LowPowerStandbyController.java`。设备非交互且不在维护窗口时，可禁用非豁免应用网络并忽略其 WakeLock，运行 FGS 的应用也在范围内。

排查“FGS 活着却断网”时，先确认 `isLowPowerStandbyEnabled()` 并监听 `ACTION_LOW_POWER_STANDBY_ENABLED_CHANGED`，再分别核对 `dumpsys deviceidle`、Data Saver、VPN 与网络验证。AAOS13 的 `PowerManagerService.setWakeLockDisabledStateLocked()` 在 `mLowPowerStandbyActive` 时会对不在 `mLowPowerStandbyAllowlist` 的 UID 禁锁。FGS 通知存在不等于 WakeLock 与网络可用；系统角色、进行中的通话、临时 allowlist 或设备策略可能获得例外。

应用可通过 `PowerManager.isPowerSaveMode()` 判断 Battery Saver、通过 `ACTION_POWER_SAVE_MODE_CHANGED` 监听变化，并用 `getLocationPowerSaveMode()` 获取定位节电策略（如熄屏停 GNSS、只给前台或降频）。具体功能影响要在目标 build 上读取状态并测量，不能用 `low_power=1` 推导固定性能幅度。

**Q8: [learning] JobScheduler 从 schedule() 到 onStartJob() 经过什么？JobService 回调有哪些必须遵守的生命周期约定？**

JobScheduler 面向带条件的可延期工作：应用声明“做什么、需要哪些条件、最晚可以延后多久”，系统结合设备状态与所有应用的请求选择执行窗口，`RESULT_SUCCESS` 只表示系统接受任务，不表示已启动。执行链（材料按 Android 17 的 APEX 源码核对，AAOS13 树未检出 jobscheduler 模块源码，机制自 Android 5.0 起稳定）：`JobSchedulerService.scheduleAsPackage()` → 各 StateController 跟踪约束 → 约束、配额与优先级筛出就绪任务 → `JobConcurrencyManager` 分配执行上下文 → `JobServiceContext` 绑定应用服务 → `onStartJob()` 回调。

生命周期约定：`onStartJob()` 与 `onStopJob()` 都在主线程回调，不能在里面做耗时工作。`onStartJob()` 返回 true 表示工作会继续，完成时必须调用 `jobFinished()`（收到 `onStopJob()` 后不再调用）。返回 true 且不调用 `jobFinished()` 会让系统持续认为任务在运行。`JobServiceContext` 会代为持有 `PARTIAL_WAKE_LOCK` 并在清理时释放，所以 JobService 通常无须自持锁，但这不豁免业务里的长循环与重复网络请求。持久化任务写 `/data/system/job/jobs.xml`，重启后恢复。系统代持的锁也意味着任务时长要自控，否则计入执行窗口与功耗。

跨层边界：JobScheduler 调度与回调边界见 [JobScheduler 调度与回调边界](../../02-系统/03-调度电源与温控.md)。

**Q9: [learning] WorkManager、JobScheduler、UIDT、expedited、FGS 与 exact alarm 怎么选？各有什么 API 版本边界？**

选型先问三个问题：任务是否要跨进程生命周期保留、是否由用户刚刚明确发起、允许延后多久。按序判断：页面存活期的短异步用协程/执行器。可延期、需重试、跨重启用 WorkManager（API 23+ 走 JobScheduler 承载，约束、桶位与配额仍生效）。用户刚触发的重要短任务评估 expedited（API 31 引入，专用配额、允许约束更少、配额不足需定义降级或丢弃策略）。用户发起的长网络传输用 UIDT（API 34 引入 `setUserInitiated(true)`，需权限、网络约束与进度通知）。持续可感知工作用符合类型要求的 FGS。闹钟提醒等精确时刻用 exact alarm（API 31 起需 special access 授权，未授权抛 SecurityException）。

版本边界：pending reason 查询分三档——API 34 单原因、API 36 多原因与 history、API 37 累计统计，Android 13 上没有公开的等待原因查询，只能用 `dumpsys jobscheduler` 与桶位推断。TARE（资源经济实验）存在于 Android 13–14 的 AOSP 源码但为隐藏、默认关闭，Android 15 起删除，Android 13 设备上不应把它当可依赖机制。

跨层边界：后台执行 API 与系统配额见 [后台执行 API 与系统配额](../../02-系统/03-调度电源与温控.md)。

**Q10: [learning] App Hibernation 与待机桶、应用归档有什么区别？应用进入休眠后发生了什么、怎么恢复？**

三者相邻但不相同：待机桶按活跃度控制后台资源配额。App Hibernation 面向长期未使用应用，把包置于类似 Force stop 的状态并回收存储。应用归档（API 35 起）移除 APK 保留数据。按 AAOS13 源码核对，休眠状态由 `AppHibernationService`（`system_server`）维护，分为用户级（`setHibernatingForUser`：Force stop + 删除该用户缓存）与全局级（所有用户都超阈值时设置，资源配置开启时删除 dexopt/OAT 产物）两层。“多久未使用、谁该豁免”的策略在可独立更新的 PermissionController 模块（AAOS13 树未检出其源码，材料按 Android 17 核对默认未使用阈值 90 天、检查周期 15 天，可被 DeviceConfig 覆盖）。调试用 `adb shell cmd app_hibernation get-state/set-state`（该命令在 A13 只实现这两个子命令）。

休眠后：后台入口失效（Job、Alarm、推送包括高优先级 FCM 都无法唤醒进程）。权限自动重置是独立步骤——PermissionController 按权限组筛选已授予的用户敏感运行时权限并撤销，退出休眠不会自动恢复，用户要在功能入口重新授权。cache 与可选的 dexopt 产物被删，filesDir/数据库/凭据保留。恢复靠直接或间接用户操作解除 stopped 状态，`PackageManagerService` 随之清除休眠标记并定向发送 `LOCKED_BOOT_COMPLETED`/`BOOT_COMPLETED`（需 `RECEIVE_BOOT_COMPLETED` 声明）。应用应在启动与该广播中共用幂等重建入口，恢复首启可能同时承担冷启动、缓存重建与代码重新优化的成本，不能给出固定延迟。

## 端侧推理性能与能效

**Q11: [learning] Android 上有哪几条端侧推理路径？为什么混用会误判成本？**

四条路径的接口与责任方不同：

1. **应用内 LiteRT：**应用打包 runtime 与模型，通过 `Interpreter` / delegate 或 `CompiledModel` 执行，CPU / GPU / NPU 由 delegate 决定。
2. **Play services LiteRT：**运行时由 Play services 更新，生命周期与模型交付不完全由应用包控制。
3. **AICore / ML Kit GenAI：**系统服务管理 Gemini Nano 与模型分发；AICore 包名不属于 AOSP。
4. **NNAPI：**由 NDK API、系统运行时与厂商驱动组成。层次混用会误判初始化成本、内存归属与失败处理——例如 `CompiledModel` 仍是应用内执行路径，不是 AICore 客户端。AICore 的可用性受设备、模型下载与配额影响，与 LiteRT delegate 的失败模式完全不同。

版本边界：NNAPI 自 Android 8.1 引入、API 35（Android 15）起官方标记弃用——Android 13 上 NNAPI 未弃用且是主线模块，“弃用”表示新项目不应再以它为长期入口，不表示既有应用失效。Android 17 的 `FEATURE_NEURAL_PROCESSING_UNIT` 与 NpuManager 调度控制面在 AAOS13 中不存在。无论哪条路径，推理都不应在主线程执行，但仍要防止工作线程挤占主线程与 RenderThread。

**Q12: [learning] 为什么“实验室里最快的推理后端”放进真实页面未必改善体验？**

用户感知的是从输入到 UI 更新的端到端延迟，运行时报告的 kernel 时间只覆盖一段。一次推理包含输入采集、解码缩放归一化、模型与运行时初始化、delegate 分区或编译、输入传输、加速器执行、输出读取与后处理、UI 更新。常见成本有首次准备（打开模型、分配张量、编译子图）、稳态执行、并发干扰、内存压力、热衰减与队列延迟。

两个典型反例：GPU 推理与渲染、相机管线共享资源，GPU 耗时下降不代表页面更流畅。推理线程占满高性能核后，单测模型耗时下降，页面帧时间与整机功耗却可能恶化——线程数要实测而非默认拉满。优化目标应写成可测预算（如“相机预览期间 P95 端到端延迟低于一帧、连续运行十分钟后温度等级可接受”），基准测试至少设 CPU 基线、目标 delegate 无缓存首次创建、缓存命中预热后、与真实 UI/相机并发四组对照，并记录 P50/P95/P99 与温度。

**Q13: [learning] 端侧推理的内存由哪些部分组成？“模型文件 100 MB 所以最多占 100 MB”错在哪？**

推理内存由多个所有者和生命周期不同的部分组成：

1. **模型映射：**FlatBuffer 与权重文件页，驻留量会随访问增长。
2. **权重转换：**delegate 打包、重排、量化展开或编译缓存，首次 prepare 后可能持续驻留。
3. **Tensor：**输入、输出、中间激活与 KV cache，随 shape 和 batch 变化。
4. **Workspace：**CPU scratch 或 GPU / NPU 临时缓冲，可能位于 native heap、驱动或 dma-buf。
5. **输入输出管线：**Bitmap、YUV / RGB 转换结果与纹理。
6. **服务进程：**AICore 等跨进程 runtime 的内存不在应用自身堆内。

“文件 100 MB”只描述压缩后的模型文件：映射驻留按页增长、delegate 可能生成编译产物或权重副本、运行时预分配 tensor arena 与工作区、多会话并发叠加，峰值可达数倍文件大小。观测要分阶段打点：模型打开前、runtime 创建后、首次执行后、稳定运行后、释放后与内存压力时。应用侧只记录到调用端分配，系统托管路径（AICore）的模型权重与服务侧工作不计入调用方 PSS——判断整机压力要同时看相关系统进程、dma-buf 与 `MemAvailable`。释放后 RSS 不立即下降，要先区分分配器留存、文件页缓存与仍被引用的 tensor，重复“创建—运行—释放—施压”周期确认是否有无上限增长。

**Q14: [learning] 端侧 LLM 推理的 TTFT 和 TPOT 应该怎么定义与测量，为什么平均 TPOT 不足以描述生成体验？**

TTFT 等于首个 token 到达时间减请求进入时间，覆盖分词、排队和冷启动，对应用户实际等待。TPOT 等于最后一个 token 与首个 token 的时间差除以输出 token 数减 1，只在输出多于 1 个 token 时有定义。TPOT 是整段 decode 的平均值，会掩盖个别 token 的停顿，工程报告还应给出相邻 token 延迟的 P50、P95、最大值与随时间变化的曲线。

测量口径的关键边界：要分析执行后端时应单独报告 prefill 区间，并把模型文件读取、权重映射、后端初始化、计算图编译与首轮 kernel 预热分开统计，不能把预热后的时间称为冷启动 TTFT。采用推测解码或一次提交多 token 的运行时，输出回调与硬件 kernel 不再一一对应，此时 token 到达间隔仍可描述用户体验，但不能据此推断每个 token 的硬件执行周期。能耗同理要定分母：`prefill_energy/input_token` 反映长输入处理成本，`decode_energy/output_token` 适合比较连续生成，`request_energy/output_token` 包含加载与应用开销，`joules/successful_request` 还能反映取消与失败造成的浪费。不同口径可以同时报告，不能把其中一个简称“模型能效”后横向比较。

**Q15: [learning] LLM decode 阶段 CPU 与 GPU 利用率都不高，TPOT 却很差，可能有哪些原因？**

decode 呈“CPU 短暂工作—提交—等待加速器—读取结果—采样”的交替过程，任一环节的等待都会拉长 token 间隔，而两侧的平均利用率都不高，所以单张利用率截图无法证明升频策略有问题。常见原因：

1. **串行依赖**：CPU 必须等加速器结果才能采样并发起下一轮，任一侧空闲可能表示在等待前一阶段。
2. **短时突发**：短 kernel 的利用率在采样窗口内被平均，频率尚未稳定升高工作已结束。
3. **跨设备交接**：CPU 提交慢让 GPU 暂时没工作，GPU 执行慢又让 CPU 休眠。
4. **带宽瓶颈**：计算单元升频后权重或 KV cache 受带宽限制，延迟改善很小。
5. **热与功率上限**：观测到的低频来自 thermal clamp 或功率预算，不是 governor 低估。
6. **后台竞争**：相机、显示、网络与系统服务共同消耗 CPU、带宽与热余量。

诊断应从 token 时间线开始，再关联 CPU 放置、频率、调度、内存与温度的同一时间轴。

**Q16: [learning] 普通应用在端侧 LLM 能效上能做什么、不能做什么？**

普通应用能改变工作负载并向系统描述时间目标：选择模型、量化格式、上下文长度、采样参数，选择运行时公开的 CPU/GPU/NPU 后端，调整线程数与请求队列，并在 API 支持时创建 ADPF hint session、查询 thermal status。不能指定硬件频率、修改 governor 或 thermal 配置，也不应直接调用 AIDL Power HAL——`IPower` 是系统与厂商实现之间的接口，Framework API 负责身份、权限与版本兼容。

这条边界决定了优化的优先级：频率策略只能在既定工作量上取舍，减少每个请求必须完成的计算与数据传输通常更稳定。量化收益要确认后端是否原生支持该位宽、不支持的算子是否回退 CPU。KV cache 容量随上下文增长，应记录运行时真实分配而非只按模型配置推算。内存允许时应复用模型映射、已编译图与长期 session，避免每次对话重复加载编译。root 实验机上的固频实验（如 FUSE 论文在 root Pixel 7 上把最低/最高频率设为同一值）会绕过平台功耗与温控约束，其结论不能写成 SDK 能力。

**Q17: [learning] 应用如何用 PerformanceHintManager 为 LLM decode 建立性能提示，Android 13 与 Android 17 的 API 差异是什么？**

通过 `getSystemService(PerformanceHintManager.class)` 为一组长期 worker 线程创建 hint session，表达“这些线程周期性完成一轮工作并希望在目标时间内结束”：每个周期调用 `reportActualWorkDuration()` 报告实际时长，目标变化时用 `updateTargetWorkDuration()` 更新。`createHintSession()` 可能返回 `null`，应用必须保留没有 session 时仍可正确执行的路径。

```java
PerformanceHintManager manager =
        context.getSystemService(PerformanceHintManager.class);
PerformanceHintManager.Session session =
        manager.createHintSession(workerTids, targetNanos);
if (session != null) {
    session.reportActualWorkDuration(actualDecodeNanos);
}
```

版本差异已按本地 AAOS13 源码（`frameworks/base/core/java/android/os/PerformanceHintManager.java`）核对：Android 13 提供 `createHintSession(tids, initialTargetWorkDurationNanos)`、`updateTargetWorkDuration(long)` 与 `reportActualWorkDuration(long)`，没有 `setThreads()` 与 `setPreferPowerEfficiency()` 等更新 API（Android 17 语境下可用于更新线程集合、表达能效偏好与按 CPU/GPU 分项上报）。target 线程 ID 必须来自真实执行线程，不能用 UI 线程代替。用法条件：session 覆盖长期 worker，不能每生成一个 token 就创建销毁。target 取产品可接受的 token 周期，不能长期填达不到的极小值。actual 的统计边界要固定，不能这轮只量 GPU、下一轮把采样与 UI 回调计入。prefill 若没有稳定分块周期，可为边界明确的 chunk 用独立 session，或只为 decode 建 session 并用 trace 单独评估 TTFT。

## 传感器与蓝牙

**Q18: [learning] 传感器批处理（batching）到底省了哪部分电，为什么它不能减少采样？**

batching 省的是“缓冲与搬运 + AP 唤醒”两段成本：事件暂存在 sensor hub 的硬件 FIFO 中合并交付，减少应用处理器（AP）的唤醒次数。它不改变采样频率，传感器本体（MEMS、ADC、融合算法）的功耗仍在，所以“采样频率越低越省电”只覆盖传感器本体一部分成本。

传感器耗电来自三个位置：**采样与计算**（频率、传感器类型、融合复杂度，发生在 MEMS/hub/融合算法）。**缓冲与搬运**（FIFO 深度、事件大小、共享方式，发生在 hub SRAM、硬件 FIFO、HAL FMQ 与 SensorService 队列）。**AP 唤醒与处理**（wake-up 属性、批量窗口、回调工作量，发生在 SoC resume、SensorService 与应用线程）。关键边界：`batch()` 只是提交配置，真正的省电来自 hub/FIFO 在 AP 之外暂存事件。没有硬件 FIFO 或低功耗 hub 时，即使 `batch()` 返回成功，也可能无法减少 AP 唤醒。

**Q19: [learning] registerListener 的 samplingPeriodUs 与 maxReportLatencyUs 分别控制什么，请求 50 Hz 加 5 秒延迟会不会变成 0.2 Hz？**

`samplingPeriodUs` 控制采样频率（单位是微秒，20,000 µs 约为 50 Hz，只有增大它才降低频率）。`maxReportLatencyUs` 控制事件允许在 FIFO 暂存的最长交付延迟，正数表示允许批量交付，0 表示尽快上报。所以四参数重载请求"20,000 µs + 5,000,000 µs"仍以约 50 Hz 采样，只是允许每批最多等 5 秒交付，不会变成 0.2 Hz。应用回调可能一次收到多个事件，其 timestamp 早于回调时刻。

两个参数都有边界。采样周期是提示值：硬件只有离散的输出数据率（ODR）档位，HAL 会就近映射，应用不能假定回调严格等间隔。而且不同 reporting mode 下含义不同——continuous 是期望采样周期，on-change 是最快事件间隔，one-shot 直接忽略（应使用 `requestTriggerSensor()` 而非 `registerListener()`）。`maxReportLatencyUs` 不降低采样频率，也不保证事件等到窗口结束：FIFO 已满、其他 sensor 到期、应用调用 `flush()` 或 AP 因其他原因醒来都会提前交付。理论批量时长上限可用“可用 FIFO 事件数除以采样频率”估算，`getFifoMaxEventCount() == 0` 表示不支持硬件 batching，共享 FIFO 的实际容量介于 `getFifoReservedEventCount()` 与 max 之间——50 Hz sensor 若只有 100 个槽位，请求 5 秒延迟也可能在约 2 秒后提前上报。

**Q20: [learning] BLE 扫描的能耗由哪些参数决定？ScanFilter 与 setReportDelay() 分别省的是什么，SCAN_MODE_LOW_LATENCY 能长期开着吗？**

一次扫描的能耗分三段：

1. **Controller：**扫描窗口占用接收机；active scan 还要发送 scan request 并等待 response。
2. **Bluetooth 进程：**执行过滤、组装结果与统计。
3. **应用进程：**处理 Binder 回调与业务逻辑。scan mode 控制接收占空比——材料按 Android 17 源码转写的 AOSP 默认参数：`LOW_POWER` 约 10%、`BALANCED` 约 25%、`LOW_LATENCY` 100%（100 ms 窗口/100 ms 间隔）。这些毫秒数不是 SDK 公开保证，`Settings.Global`、DeviceConfig 与 OEM 都可能改变运行参数，应用只应依赖 mode 的语义。`LOW_LATENCY` 的 100% 占空比只适合用户正在等待配对的短窗口，长期开启等于让接收机持续工作。

`ScanFilter` 的收益主要在结果侧：匹配在 controller 支持硬件 offload 时下沉，减少无关结果上送、Binder 回调与应用进程工作。它不会自动缩短 controller 的扫描窗口——想降低射频接收时间要缩短时长或换更低 duty cycle 的 mode。`setReportDelay()` 批量上送主要减少 host 与应用唤醒，硬件批量存储能力取决于设备。Android 14 新增 `CALLBACK_TYPE_ALL_MATCHES_AUTO_BATCH`（熄屏批量投递、亮屏恢复逐条，最小 10 分钟），适合容忍延迟的观察任务。蓝牙模块源码（le_scan 包）不在本地 AAOS13 树，以上参数按材料 Android 17 语境转写。

**Q21: [learning] 进程可能被回收时仍要发现 BLE 设备，应该用什么方案？周期用 Job/Alarm 启动扫描、连续 start/stop 为什么都被系统限制？**

后台 presence 的正确入口是 `PendingIntent` 扫描（系统代应用投递结果。Intent 用 mutable flag 供系统填充 extras、用显式 Receiver 限制投递目标）或 Companion Device Manager 的 presence API。两者都不给应用无限后台执行权，Android 12+ 的后台 FGS 启动限制仍然生效。用 Job/Alarm 周期启动扫描模拟“设备出现”是反模式：外围设备不在附近时每个周期仍唤醒进程，还会撞上注册频率限制——材料按 Android 17 核对，AOSP 默认保留最近 5 次已结束扫描，最早一次仍在 30 秒窗口内时，后续非特权注册收到 `SCAN_FAILED_SCANNING_TOO_FREQUENTLY`（默认值可由 DeviceConfig 调整，非公开保证）。注册失败后应停止循环，等待业务事件或退避计时器。

系统还有两层被动保护（按材料 Android 17 核对）：熄屏且无过滤、或位置关闭且未声明不用于位置的扫描会被暂停（`requiresScreenOn()`/`requiresLocationOn()`，位置检查与 `BLUETOOTH_SCAN` 运行时授权是两层独立检查），亮屏或位置恢复后继续。长时扫描默认 10 分钟降级（无 filter 转 opportunistic、有 filter 压到不高于 `LOW_POWER`），Android 17 另有按 UID 的扫描额度限速（默认每 1 小时补充 6 分钟额度）。这些保护不能反向利用——业务离开扫描场景仍要显式 stop。权限侧注意：`BLUETOOTH_SCAN` 的 `neverForLocation` 是数据用途声明，不改变扫描占空比，不是省电参数。

**Q22: [learning] GATT 连接已经建立，为什么蓝牙功耗仍然很高？连接优先级、MTU、notification 与轮询应该怎么组合？**

“已连接”不等于低功耗：连接间隔很短、notification 很密、链路质量差导致重传、应用高频轮询 characteristic 或持续发小包，都会让 controller 频繁进入 active。控制要点按业务阶段切换：批量传输窗口用 `requestConnectionPriority(HIGH)`，传输完成恢复 `BALANCED`——返回 true 只表示请求已提交，最终参数由 controller 与外围设备决定。周期状态更新启用 characteristic notification，由外围设备在数据变化时推送，优于主机固定周期 `readCharacteristic()`。MTU 减少分片（材料按 Android 14 核对，首个 MTU 请求固定请求 517。API 37 的 `setAutomaticMtuEnabled(true)` 自动协商），最终结果仍要在 `onMtuChanged()` 里确认并按协商值分片。通知频率由配件固件控制——配件每几十毫秒发送一次无变化数据时，手机侧无法单独消除这部分成本。

生命周期与重连：不再使用的 `BluetoothGatt` 要 `disconnect()` 加 `close()`。重连要有带 jitter 的指数退避、重试上限与取消条件（蓝牙关闭、权限撤销、用户解绑、业务完成），避免多台设备同时重连形成风暴。`autoConnect=true` 适合已知设备的长期在场检测，但不保证进程存活。API 37 新增 `BluetoothGattConnectionSettings` 统一 transport、autoConnect、opportunistic 等参数（AAOS13 无此 API，按材料版本标注），其中 opportunistic client 不维持底层连接、只适合复用现有连接的观察者。

## 后台任务治理与前台服务

**Q23: [learning] BACKGROUND_RESTRICTED 能由系统自动打上吗？“耗电豁免”是什么性质的东西？**

`BACKGROUND_RESTRICTED` 不能仅凭 tracker 自动进入，源码要求用户同意该级别。多个 policy 提出候选等级时控制器取数值更大的等级并保留来源 tracker，但这是汇总规则而非完整决策——之前还要处理休眠、force-stop、系统豁免与当前待机分组（`AppRestrictionController` 的 tracker 汇总逻辑，Android 13 已有）。`AppBatteryExemptionTracker` 记录的是耗电扣除区间：按 UID 维护状态位，同 UID 的第一个包进入可豁免状态时记开始事件、全部离开才记结束事件（避免共享 UID 的两个包重复计时），`AppBatteryTracker` 再从后台总耗电中扣除这些区间——这是归因层面的“这段耗电不算它的”，不是给固定时长的后台执行许可，源码也没有“16 ms 生效延迟”或统一豁免窗口的契约。`EXEMPTED` 等级同样不是 CPU、网络与前台服务规则的通行证，各子系统仍按各自的 allowlist 判断。

**Q24: [learning] 应用侧怎么降低厂商后台差异带来的不可预期性？**

目标是“在 AOSP 允许的执行窗口内完成尽量少的工作、任何中断可恢复、诊断日志说明停在哪一层”。做法：可延迟且需持久化的工作交给 WorkManager，每次执行设计为幂等、可重入。持续向用户提供能力时使用合法类型的前台服务，并处理后台启动失败与运行时限。推送只当“有新工作”的提示，业务状态保存在服务端，不假定每条消息同时到达。重要本地状态在产生时持久化，不依赖进程退出回调。对外部副作用使用幂等键与检查点，进程被停止后从已确认位置继续。只有核心功能确受影响时才向用户解释具体系统设置——不默认引导所有用户关闭电池优化，也不跳转未经文档保证的厂商私有设置页。私有保活策略既不能消除差异，也无法用公开证据验证，不应依赖。

**Q25: [learning] 评审一个后台任务应该连续回答哪些问题？Doze、待机分组与任务接口为什么不能互相替代？**

后台执行 API 的选择从任务语义开始：页面关闭可取消的工作留在进程内；可延期且需跨进程重试的工作交给 WorkManager；平台约束调度用 JobScheduler；用户指定时刻的提醒用 AlarmManager；持续可感知的工作才用前台服务；消息送达优先用推送通道。API 选择仍须继续回答以下六个问题：任务是否用户刚刚发起并正在等待结果。结果允许延迟到什么时刻。网络、充电、空闲、电量哪些是业务要求。重复触发时保留、替换还是追加旧工作。页面关闭、退出账号、权限撤销、数据删除时谁负责取消。被系统停止后哪些进度可安全恢复、哪些步骤必须幂等。三组条件不可互替：Doze 描述整台设备是否空闲（未充电、静止、熄屏一段时间，暂停网络、忽略普通 WakeLock、延后 Job 与 Alarm 到维护窗口）。App Standby 待机分组描述单个应用的近期使用频率（active/working set/frequent/rare/restricted，`restricted` 是限制最严的分组但 Android 13 起每天仍保留一次十分钟批处理时段，OEM 可调算法，应用不应诱导分组）。任务接口与权限决定具体执行资格（WorkManager/JobScheduler 的约束与配额、FGS 类型与启动资格）。进程存活也不等于任务可持续：组件生命周期、后台启动资格、Job 配额与资源权限是不同条件，任务开始时间不是承诺时间。

**Q26: [learning] 从 startForegroundService() 到真正以前台服务运行，要过哪三道互相独立的检查？**

FGS 生命周期有三道相互独立的检查，失败发生在不同阶段：

1. **允许启动：**`startForegroundService()` 进入 AMS 时检查调用方状态。后台无豁免会抛 `ForegroundServiceStartNotAllowedException`。高优先级 FCM 只可能提供临时启动窗口，来源和时效由产生例外的系统组件决定，没有固定“10 秒”契约；应用应检查 `RemoteMessage.getPriority()`，不能假定推送必然获准。
2. **允许晋升：**调用 `startForeground()` 时，运行时类型必须是 Manifest 类型位集合的子集，否则抛 `IllegalArgumentException`；类型专用权限或前提不满足会抛 `SecurityException`，没有有效类型会抛 `MissingForegroundServiceTypeException`。多个类型可按位组合，但 `shortService` 与其他类型组合时会被系统忽略。
3. **允许访问资源并继续运行：**camera、microphone、location、health 受 while-in-use 能力约束。后台应用的 `checkSelfPermission()` 仍可能返回已授权，只表示用户授予了“使用期间可用”权限；限时类型还受运行时限与子系统检查约束。

三道检查分别记录失败原因，因为修复位置各不相同。

**Q27: [learning] startForegroundService() 之后迟迟不调 startForeground() 会发生什么？怎么避免晋升超时？**

系统会启动晋升计时器，到期后停止仍在等待的服务并进入 ANR 流程。Service 在等待期间被提前销毁时，应用会收到 `ForegroundServiceDidNotStartInTimeException`。计时器默认值 AAOS13 源码核对为 30 秒（`ActivityManagerConstants.DEFAULT_SERVICE_START_FOREGROUND_TIMEOUT_MS = 30 * 1000`），超时后另有约 10 秒的 ANR 处理延迟，两个值都可由 DeviceConfig 改写——Android 17 材料口径与 Android 13 一致。诊断标志是错误文本 `Context.startForegroundService() did not then call Service.startForeground()`，说明故障点在晋升阶段而不是业务执行。避免方式：预先创建通知渠道。Service 进入回调后立即构造轻量通知并调用 `startForeground()`。业务工作交给可取消的异步任务。完成、失败或取消时统一 `stopSelf()`。常见错误是在 `onCreate()` 里同步建库、恢复大对象或等网络返回后再晋升，这会把全部冷启动成本叠加到计时器上。也不要把 30 秒当业务预算——进程启动、主线程排队和依赖初始化都在挤占它。

**Q28: [learning] 前台服务到底“买到”了什么？FGS 与后台启动 Activity（BAL）是什么关系？**

FGS 提供用户可感知的持续执行形态：持续通知，以及更高的内存回收优先级——普通非 short FGS 的进程档位基准 `PERCEPTIBLE_APP_ADJ = 200`（AAOS13 源码核对 `ProcessList`。Android 17 材料口径 short FGS 为 `PERCEPTIBLE_MEDIUM_APP_ADJ + 1`，Android 13 无 shortService 类型）。它不提供：更高 CPU 频率或调度优先级、任何 WakeLock 或资源、Doze/待机分组/JobScheduler 配额豁免、免受 LMKD 回收的保证、后台 Activity 启动权、超出类型额度的运行权。FGS 与 BAL 无隐式继承：运行 FGS 时直接 `startActivity()` 仍要过 `BackgroundActivityStartController` 检查，合法路径来自用户点击通知的 `PendingIntent`、可见窗口、系统角色或权限等。Android 14 起发送方、Android 15 起创建方都要显式设置 `PendingIntent` 的 BAL 授权模式，Android 17 把规则扩展到 `IntentSender.sendIntent()` 并建议仅在发送方可见时贡献权限（`MODE_BACKGROUND_ACTIVITY_START_ALLOW_IF_VISIBLE`）。BAL 被拦截通常没有异常，logcat 记录 `Background activity launch blocked!`（Android 16+ 可用 StrictMode 检测提前发现）。另外 Android 16 起与 FGS 并行运行的 Job 仍消耗各自调度配额，FGS 不能替 Job 解除配额或待机限制。

**Q29: [learning] WakeLock 和 Alarm 分别解决什么问题？为什么说它们都不是保活接口？**

WakeLock 表达“工作已经开始，设备暂时不能进入会中断它的休眠”。Alarm 表达“工作尚未开始，系统到达约定时刻后通知应用”。都不是保活接口：WakeLock 不保证进程存活、不提供后台启动资格，应用 Partial WakeLock 还会被电源策略禁用（Doze、Low Power Standby、cached 状态等，机制与禁用条件见 [../../04-工具/17-battery-historian/01-功耗报告.md](../../04-工具/17-battery-historian/01-功耗报告.md)）。Alarm 的回调只应做短小分发——AlarmManager 投递广播期间持有的 `*alarm*` WakeLock 只覆盖 `BroadcastReceiver.onReceive()`，方法返回后系统即可释放，接收器里启动异步工作应把输入持久化并交给 WorkManager，不能依赖系统锁继续保护后续工作。配置错误的代价：持锁范围过大会阻止系统进入低功耗状态，唤醒型 Alarm 过密增加设备唤醒次数，无资格的精确 Alarm 调用时抛 `SecurityException`。持锁的所有权、超时与释放规范（稳定标签、`try/finally`、引用计数语义）已在 [../../04-工具/17-battery-historian/01-功耗报告.md](../../04-工具/17-battery-historian/01-功耗报告.md) 覆盖，此处不重复。

**Q30: [learning] AlarmManager 的各 API 怎么选？时间基准与 PendingIntent 身份有哪些坑？**

按时效与偏差容忍选择 API：

1. **非精确单次：**`set()` / `setWindow()` 允许系统合并唤醒；target 31+ 的应用请求小于十分钟窗口时，系统可能扩展到十分钟。
2. **重复或空闲期投递：**`setInexactRepeating()` 用于粗略重复，普通周期工作仍优先 WorkManager；`setAndAllowWhileIdle()` 用于空闲期也需投递的非精确事件。
3. **精确投递：**`setExact()` / `setExactAndAllowWhileIdle()` 受精确 Alarm 权限与频率约束。
4. **用户可见闹钟：**`setAlarmClock()` 面向闹钟等明确用户功能，系统可为投递离开低功耗模式。

时间基准也要与用途匹配：

1. **墙上时钟：**`RTC` 使用墙上时间，适合当地时间提醒；要处理校时、时区和夏令时变化。
2. **开机后时长：**`ELAPSED_REALTIME` 使用开机后单调时间，适合同一次开机内的延迟。
3. **是否唤醒：**带 `WAKEUP` 的类型才会唤醒设备；业务允许等待时优先选择不唤醒类型。

PendingIntent 的 extras 不参与等价判断，只改 extra 可能覆盖已有 Alarm。用唯一 `data` URI，或 action、组件和 requestCode 的组合区分提醒，取消时重建等价身份。设备关机会清除 Alarm，跨重启的提醒先持久化并在 `BOOT_COMPLETED` 后重建。当地时间重复提醒宜按下一次日历时间安排单次 Alarm，而非用固定毫秒间隔。

补充边界：

Android 12（API 31）引入 "Alarms & reminders" special app access。Android 13 起可按场景选择两种权限（AlarmManager 属 jobscheduler 模块、源码不在本地 AAOS13 树，按材料转写）：`SCHEDULE_EXACT_ALARM` 由用户授予、也可被用户或系统撤销，使用面较宽，调用前检查 `canScheduleExactAlarms()`。`USE_EXACT_ALARM` 安装时自动授予且用户不可撤销，只允许闹钟、计时器、日历等受限核心场景，并受应用商店政策约束。材料按 Android 14 核对：target 33+ 的多数新安装应用不再预授予 `SCHEDULE_EXACT_ALARM`，备份恢复到 Android 14 设备也按拒绝处理——这些是 A13 之后的行为。

`setExactAndAllowWhileIdle()` 能在 Doze 期间交付，但受每个 App 约九分钟一次的频率边界（官方文档口径，系统还可拉长间隔）——这是防滥用边界，不是轮询周期建议。它适合用户明确感知的关键事件（闹钟、日历提醒）。回调里只安排短操作，联网或持久工作交给 JobScheduler/WorkManager。`setAlarmClock()` 面向用户可见闹钟，系统会为交付离开低功耗模式。`setAndAllowWhileIdle()` 允许空闲期交付不精确闹钟。

`OnAlarmListener` 形式的 `setExact()`（API 24 起）不要求精确闹钟权限，但它是进程内监听器：进程退出后不再投递，系统还可在进程没有任何组件时取消（材料按 Android 17 核对的新增 listener 版 `setExactAndAllowWhileIdle()` 同样如此，A13 无该重载）。这个例外不能用来构造后台保活。需要跨进程生命周期的可靠提醒应使用 `PendingIntent` 并遵守精确闹钟权限与政策。

**Q31: [learning] Android 17 的 Listener 版 setExactAndAllowWhileIdle() 适合什么场景、边界在哪？**

新重载接受 `OnAlarmListener` 与 `Executor`，不要求 `SCHEDULE_EXACT_ALARM` 权限，适合“组件仍在运行、不希望持续持锁等待下一次时机”的进程内调度（如长连接维护）：回调经进程内 Binder 交付，系统在投递前获取共享 WakeLock、`onAlarm()` 返回后释放，因此回调应同步快速完成、不要再自持应用 WakeLock——把工作另起异步线程后立即返回会失去这段保护。边界：不跨进程生命周期——进程没有任何活动组件、进入 cached 或冻结状态、或组件结束时，系统可以移除该 Alarm，组件结束也应主动 `alarmManager.cancel(listener)`。它仍受允许空闲分发的频率限制（Android 17 为 Listener 型维护独立配额，AOSP 默认值不是业务承诺），不适合循环安排高频回调。进程死亡后仍需触发的提醒应使用 `PendingIntent` 版本并遵守精确 Alarm 权限。版本边界：该重载为 API 37 新增，Android 13 上不存在（AlarmManagerService 源码不在本地树，按材料锚点转写）。A13 的进程内等价选择是 `OnAlarmListener` 版 `setExact()`（同样不跨进程存活）。

**Q32: [learning] WorkManager 的唯一工作、任务链与 Data 传参各有哪些边界？**

WorkManager 的机制按职责区分：

1. **唯一工作：**`enqueueUniqueWork()` 的 `KEEP` / `REPLACE` / `APPEND` / `APPEND_OR_REPLACE` 解决重复入队，不解决业务去重。唯一名称应包含业务作用域，如 `account-sync:<id>`；所有账户共用 `sync` 会误合并请求，随机名称则失去去重意义。周期任务的 `UPDATE` 保留入队时间，并让后续轮次采用新约束。
2. **任务链：**`beginWith(...).then(...).enqueue()` 才把整张 DAG 写入 WorkManager。上游失败或取消时，下游直接进入失败或取消，不会执行。可接受的降级结果作为 `success(Data)` 传出；不可接受的失败在链外观察终态后，再明确入队另一条链。
3. **输入合并：**多个前置任务汇聚时，默认 `OverwritingInputMerger` 对同名键只保留一个值，覆盖顺序不可依赖；收集并行结果使用 `ArrayCreatingInputMerger`。
4. **Data：**只支持基本类型、字符串及其数组，序列化后不超过 10 KiB。大对象放数据库或文件，仅传主键或摘要；跨重启传 URI 时确认权限仍有效。
5. **任务身份：**WorkRequest 的 UUID 是 WorkManager 内部标识，不要与平台 Job ID 混用。

补充边界：

约束表达的是业务条件，只添加必要约束：`setRequiresCharging(true)` 加 `NetworkType.UNMETERED` 表示“充电且不计费网络”才执行。业务只需联网时用 `CONNECTED`。UNMETERED 的语义是 `ConnectivityManager` 报告当前网络不计费，不等同于 Wi-Fi——某些 Wi-Fi 会被标记计费，某些蜂窝环境也可能被标记不计费。多余约束会推迟任务，并让积压工作在条件满足时集中执行。

`PeriodicWorkRequest` 的 15 分钟最小间隔是请求下限，系统可以因约束、Doze、配额或 standby bucket 延后某一轮，也不承诺固定相位。`Result.retry()` 只用于可恢复错误，鉴权失败、参数错误等永久失败继续重试只会重复唤醒设备与服务器。重复触发用 `enqueueUniqueWork(..., ExistingWorkPolicy.KEEP, ...)` 消除同一时刻的等价任务。但 KEEP 不解决可靠性——Worker 仍要靠服务端游标或幂等键处理漏发与重复投递。跨模块合并同约束工作时，可让多个 `JobWorkItem` 共享一个稳定 `JobInfo`（Android 14 起支持随 persisted Job 持久化，按材料核对），合并后仍受 Job 数量上限、调度入口节流与配额约束。

版本边界：材料按 Android 16 核对，top-started 与和 FGS 并发执行的 Job（含 WorkManager 路径）受 runtime quota 约束，A13 无此规则。Job 执行期系统代持 CPU WakeLock（机制自 JobScheduler 引入起稳定），业务无须自持锁。

**Q33: [learning] Job 一直不执行，怎么按“WorkManager 层 → 系统层 → Worker 层”取证？Pending reasons 怎么读？**

三层取证：WorkManager 层看 WorkSpec 状态、约束、依赖与入队时间（`getWorkInfoByIdFlow` 观察 `state`/`progress`/`stopReason`——停止后仍可能重新调度，一次停止不能显示为永久失败）。系统层看 `dumpsys jobscheduler` 中对应 `SystemJobService` Job 的等待原因、约束与配额。Worker 层确认是否进入 `doWork()`、返回了什么结果、是否收到停止信号。Pending reasons：`getPendingJobReason(jobId)`（API 34）返回主要等待原因，`getPendingJobReasons`/`getPendingJobReasonsHistory`（API 36）给出当前原因集合与变化历史，`getPendingJobReasonStats`（API 37）给出每种原因的累计等待时长（官方功能页称之为 JobDebugInfo，公开 SDK 无同名类，入口都在 `JobScheduler`）。原因常量只给方向：`CONSTRAINT_*` 指向显式约束，`QUOTA` 指向待机分组或运行额度，`BACKGROUND_RESTRICTION`/`APP_STANDBY` 指向应用状态，`DEVICE_STATE` 含 Doze、热状态、内存压力等。边界：这些 API 均为 34+，Android 13 无（材料锚点）。历史不跨重启、Job 完成或取消后清空，查询与完成竞态可能抛 `IllegalArgumentException`。多个原因同时计时，累计之和可能大于实际等待。发布门禁要区分“合理等待”（低优先级同步等充电或非计费网络）与设计错误（用户发起任务长期等 `QUOTA`、反复入队不完成）。

**Q34: [learning] setExpedited() 与长时 Worker（setForeground()）的使用边界是什么？**

加急：`setExpedited()` 用于短小、对用户重要、需要尽快开始的一次性工作——不能用于周期任务，也不等于立即执行。Android 12+ 申请加急 Job，配额与待机分组、进程重要性相关且没有固定可查询的分钟数，`OutOfQuotaPolicy.RUN_AS_NON_EXPEDITED_WORK_REQUEST` 让配额不足时退化为普通任务而不是被放弃。兼容 API 23–30 时系统可能以前台服务承载加急工作，Worker 需要实现 `getForegroundInfo()`。普通 Worker 一次执行约十分钟上限。超过就转长时 Worker：`setForeground()` 后由 WorkManager 管理前台服务与通知，目标 34+ 必须在 `ForegroundInfo` 传入与工作内容相符的前台服务类型并声明对应权限（如 dataSync 需要 `FOREGROUND_SERVICE_DATA_SYNC`，并覆盖清单中 WorkManager 的 `SystemForegroundService` 类型）。配额纪律：普通、加急、长时不要混用同一语义。Android 15+ 的 dataSync/mediaProcessing 六小时额度与 Android 16–17 的 JobScheduler 运行配额都继续适用于长时 Worker——`setForeground()` 只声明业务类别，不取消配额检查。用户主动发起的大文件传输更适合 user-initiated data transfer job 或直接前台服务。

## 定位、媒体与混合页面

**Q35: [learning] FusedLocationProvider 的请求参数哪些是承诺、哪些只是请求条件？批量交付要注意什么？**

全部是请求条件不是承诺：优先级表达期望精度档（`PRIORITY_HIGH_ACCURACY`/`PRIORITY_BALANCED_POWER_ACCURACY`/`PRIORITY_PASSIVE`），`minUpdateIntervalMillis` 是允许的最快回调间隔而非固定周期，`setMinUpdateDistanceMeters()` 减少无足够位移时的回调，`setMaxUpdateDelayMillis()` 允许批量交付（只有最大延迟至少是请求间隔两倍时才被视为允许批处理，硬件仍可逐点交付），`setDurationMillis()`/`setMaxUpdates()` 限制请求寿命。`GRANULARITY_PERMISSION_LEVEL` 让请求遵守当前授权精度（Android 12 起用户可只授大致位置，降档还会导致进程重启）。批量交付的坑：一次回调可能带多条位置、批次之间可能出现时间逆序——按 `Location.elapsedRealtimeNanos` 排序去重，把事件发生时间与回调到达时间分别记录。`Location.time` 只适合展示、不适合单机轨迹的单调排序。连续请求要有两层停止条件：正常路径由页面或会话用同一个回调实例调用 `removeLocationUpdates()`，异常路径靠 duration/maxUpdates 兜底。主线程回调只做轻量处理，轨迹压缩、写库与上报移到受控执行器。

补充边界：

两个直接问题：参数没有从产品场景推导——1 秒间隔加 0 米最小位移让 GNSS 无法休眠。注册后没有对应的 `removeLocationUpdates()`，会话结束后请求仍然有效。按场景修正：页面只要一次位置用 `getCurrentLocation()`（API 30 起，取消信号跟随页面生命周期）。连续导航用 `LocationRequest`，间隔、最小位移与批量延迟由可接受延迟、路径误差和运动速度推导，导航停止即移除。`setMaxUpdateDelayMillis()` 允许批量交付、减少应用被唤醒次数，但实时导航不能接受过长批量延迟（LocationManager 源码不在本地 AAOS13 树，API 行为按材料与版本标注转写）。

“进入或离开区域时通知”类需求用 Geofencing：系统可以合并多个客户端的请求，应用无需短周期轮询维持判断。边界：Android 8.0 起后台交付围栏事件的响应可能放宽到几分钟量级，不适合秒级轨迹或严格到达时间。硬件是否参与围栏判断属于设备实现，不能把“存在 GNSS geofencing 能力”写成“当前业务已由硬件独立处理”。

后台定位的权限链（按材料核对的跨版本累积行为）：Android 8.0 起后台 App 每小时只有少量位置更新，且与 targetSdk 无关。Android 10 起持续后台定位需要 `ACCESS_BACKGROUND_LOCATION`，只有 while-in-use 权限时退到后台不能继续假设完整定位。Android 11 起在后台启动 `location` 类型 FGS 且无后台定位权限就拿不到位置。Android 14 对 target 34+ 在创建该 FGS 时即校验类型权限与 while-in-use 条件，不满足可能抛 `SecurityException`。另外 Battery Saver 的位置模式与 Thermal 是两条通道：产品允许温度升高时降频定位，应监听热状态自行调整请求，平台不会把热状态自动换算成某个 location power-save mode。

**Q36: [learning] 一次性定位、地理围栏还是被动定位，怎么按业务选并守住退出条件？**

按新鲜度与触发语义选：页面只需要一次较新位置用 `getCurrentLocation()`（带取消信号，不为一次查询注册长期回调）。`getLastLocation()` 不主动计算、可能为空或过时，判断新鲜度用 `elapsedRealtimeNanos` 与当前单调时间比较而不是墙上时钟。进入或离开区域用 Geofencing（位置服务统一维护围栏，应用不必周期轮询当前位置）。复用其他客户端已产生的位置用 `PRIORITY_PASSIVE`（不为自己计算位置，可能长期无结果，不能承载时限承诺）。Geofencing 的参数纪律：每应用、每设备用户最多同时 100 个围栏，大量门店先维护城市或商圈级再按用户区域替换。官方建议典型围栏 100–150 米半径以容纳 Wi-Fi 定位误差、`setNotificationResponsiveness()` 取 5 分钟或更大更省电（经验建议，按业务误触成本调整，不写成通用常量）。`DWELL` 事件过滤短暂穿越。围栏经 `PendingIntent` 投递，接收器核对错误码与 transition 类型，功能关闭、账号退出或区域集合改变时按 request ID 或原 `PendingIntent` 移除。边界：Android 8.0 起后台围栏按几分钟量级处理、低响应值不构成及时送达保证。被动定位与围栏仍受后台定位权限约束（权限链见 [../../04-工具/17-battery-historian/01-功耗报告.md](../../04-工具/17-battery-historian/01-功耗报告.md)）。

**Q37: [learning] 传感器采集会话的注册、交付与注销有哪些必须守住的纪律？（批处理机制之外）**

批处理如何省电见 [../../04-工具/17-battery-historian/01-功耗报告.md](../../04-工具/17-battery-historian/01-功耗报告.md)。会话纪律有四条。其一，选对传感器实例与模式：one-shot（触发一次后停用）传感器用 `requestTriggerSensor()` 而不是 `registerListener()`。同类型可有 wake-up 与 non-wake-up 两个独立实例，用 `Sensor.isWakeUpSensor()` 判断——业务只需要最新或累计状态时选 non-wake-up 或更大报告延迟，减少处理器唤醒。其二，注销前 flush：需要尾部数据时先 `SensorManager.flush(listener)` 并等 `onFlushCompleted()` 再注销（异步操作，要准备超时退出。返回 false 表示监听器未注册或请求失败）。其三，后台停止交付：Android 9 起不向后台应用交付 continuous、on-change、one-shot 传感器事件，长时间采集需要用户可见的 `health` 类型前台服务（Android 14+ 声明 `FOREGROUND_SERVICE_HEALTH` 与对应运行时条件。身体传感器权限 API 36 起改用 `READ_HEART_RATE` 等细分权限）并在服务停止时解除注册——保留监听器不会让后台进程继续收数据。其四，注册结果要检查（`registerListener()` 可能返回 false），并用实际事件时间戳验证最终采样率而不是相信请求值。

**Q38: [learning] Wi-Fi RTT 与 BLE 测距会话怎么治理功耗与失败？**

两者都是测量 API、不替代普通定位，也没有跨设备固定的精度或功耗。Wi-Fi RTT：请求必须由扫描得到的真实 `ScanResult` 构建。目标 33+ 使用 `NEARBY_WIFI_DEVICES` 权限。回调按 MAC 地址关联。`RangingResult.STATUS_BUSY_TRY_LATER` 表示对端忙，应等 `getRetryAfterDurationMillis()` 给出的时间再重试，不能循环请求。BLE：RSSI 受人体遮挡、姿态、天线与多径影响，只适合区域判定或排序、不应直接承诺米级距离。后台运行不会自动把扫描改成低功耗，无过滤的 `ScanCallback` 扫描在熄屏时暂停，进程结束后仍需接收匹配结果要用带过滤条件的 `PendingIntent` 扫描。所有扫描显式用原 callback 调用 `stopScan()` 结束。共同纪律：每个测量会话记录能力检查、权限、开始/停止、样本数、失败与重试。先用地理围栏缩小候选区域，再在用户进入相关功能或满足后台条件时启动有界会话，定位结束后扫描与测距不得残留。

**Q39: [learning] Android 17 的后台音频硬化分哪两级？失败为什么是静默的？怎么取证？**

两级条件：第一级对所有应用——后台播放、申请音频焦点或修改音量时，必须有可见 Activity（画中画也算可见）或一个类型不是 `shortService` 的前台服务，与 targetSdk 无关。第二级只对 target 37——FGS 还要具有 while-in-use 能力（在应用可见时启动服务，或由通知点击、桌面小组件、媒体按键等明确用户操作触发）。已获准精确闹钟且音频用途为 `USAGE_ALARM` 的场景可免第二级、免不了第一级，普通媒体内容不能借用 alarm 用途规避。失败刻意静默：播放被静音但播放器可能仍报告“正在播放”，`requestAudioFocus()` 返回 `AUDIOFOCUS_REQUEST_FAILED`，音量修改被忽略——`AudioTrack.write()` 成功只说明数据已提交，不证明声音送到输出设备。取证看 `AudioHardening` 日志：`level: partial` 表示没有合格前台服务（第一级），`full` 表示有 FGS 但缺 WIU（第二级）。焦点请求被硬化拒绝时不会进入常规焦点竞争，与“被其他应用抢走焦点”是两种原因。版本边界：AAOS13 源码核对 `Tracks.cpp` 与 `services/audio` 下无任何 hardening 逻辑、无 `HardeningEnforcer`，该机制为 Android 17 新增。调试子命令存在 `set-hardening`（r1 源码）与 `set-enable-hardening`（官方文档）两种命名，用 `cmd audio help` 确认当前镜像。

**Q40: [learning] 声音已经停了，但网络、解码、WakeLock 还在跑——“僵尸播放”怎么治理？**

先纠正状态来源：Media3 的 `playWhenReady`、`playbackState` 表达播放器状态机，不表达平台授权状态。每次播放会话应记录焦点结果、FGS 类型与状态、Activity 可见性、音频 usage 与 `AudioHardening` 命中，把“用户想听却没有声音”与“用户不再听但资源仍运行”分开统计。生命周期上让播放入口、MediaSession、`mediaPlayback` FGS 与资源表达同一份用户意图：用户开始播放时启动 `mediaPlayback` 类型 FGS（配合 Media3 `MediaSessionService`）。短暂缓冲、瞬时网络故障或不足 10 分钟的暂时性失败保留服务便于恢复（官方建议窗口）。播放完成、收到永久 `AUDIOFOCUS_LOSS`、用户明确暂停不再继续或发生不可恢复错误时，停止播放器、结束 MediaSession、停止 FGS，并确认网络请求、解码线程、WakeLock 与预取随停止原因一起释放。播放静默失败时不能只重试播放——先判断是硬化限制还是业务错误，硬化限制下重试只会继续空耗网络、解码与电量。

**Q41: [learning] Hybrid 页面的功耗都花在哪？为什么不能按“一个页面一个进程”估内存？**

一次用户操作会经过应用进程、WebView provider 包、一个或多个 Chromium renderer、JavaScript 与 JSBridge：CPU 消耗在脚本、DOM/CSS 计算、图片解码、滚动合成与桥调用两端的编码还原，桥调用过密还会增加主线程或业务线程的调度等待。内存上多个 WebView 可能共享同一个 renderer（共享只发生在同一应用进程内），不能按页面数估进程数——AAOS13 本地源码核对：WebView 加载器 `loader.cpp` 用 `mmap(PROT_NONE)` 预留 `libwebviewchromium.so` 的虚拟地址空间，这段 reservation 只占虚拟地址范围、不等于 PSS/RSS 或实际物理页，32 位进程还要关注地址空间碎片。网络与存储上重定向、第三方脚本、字体与多层缓存（HTTP 缓存、DOM storage、Service Worker、应用离线包）叠加，清理其中一层不代表其他层已清空。生命周期上页面离屏后 renderer、音视频与定时器可能仍活跃，容器要把可见性映射到 `onPause()`/`onResume()`，不复用时从 View 树移除并 `destroy()`。

**Q42: [learning] “原生比 Web 省电”的论文结论能直接推出某个 Hybrid 页面必须原生化吗？**

不能。arXiv:2308.16734 比较的是 10 个内容平台的 Android 原生应用与 Chrome Web 版本——不是应用内 WebView。单台 Android 10 设备、固定脚本每对象重复 25 次，能耗由 Batterystats 按硬件活动与功耗模型估算。结论是原生能耗更低、CPU 与内存用量更大（统计显著且效应量大）、网络差异效应量小、帧时间数据不足以支持孰优结论。外推限制：未测 WebView 容器。Web 与原生不是控制成同一功能的代码。静态脚本覆盖不了结账、发帖等交互。实验期间 Web 内容可能变化。“统计显著”只说明当前样本下差异不太可能是随机波动，效应量描述幅度，都不保证在其他设备、页面与浏览器上复现。它提示的是 CPU、内存与网络的风险方向。原生化决策要靠本业务同场景测量——原生页、应用内 WebView、外部浏览器三组对照（浏览器组帮助判断问题来自 Web 内容还是应用容器），冷/热进程与有无缓存分别组合，`netstats` 按 UID 取前后差值而不是比较两个完整文件的总字节。

**Q43: [learning] WebView 的生命周期与 renderer 异常应该怎么接？**

可见性映射：页面不可见调 `WebView.onPause()`（暂停布局、解析与 JS 定时器），恢复用 `onResume()`。`pauseTimers()`/`resumeTimers()` 是进程级全局开关、影响当前进程所有 WebView，只在整应用退后台等场景使用，不能当单页面开关。不复用的 WebView 从 View 树移除并 `destroy()`，`clearCache()` 不是页面退出的清理接口。renderer 异常：API 26+ 实现 `WebViewClient.onRenderProcessGone()`，用 `RenderProcessGoneDetail.didCrash()` 区分异常终止与系统回收，失去 renderer 的 WebView 必须移除并销毁、不能复用。API 29+ 可再加 `WebViewRenderProcessClient.onRenderProcessUnresponsive()`/`onRenderProcessResponsive()`，无响应回调可能以不短于 5 秒的间隔重复、告警要去重，主动终止 renderer 时必须能处理共享它的所有 WebView。API 26–28 没有无响应回调，加载或交互超时只是体验信号、不能断言 renderer 失联。观测按页面记录 provider 包与版本（`getCurrentWebViewPackage()` 可能返回 null）、驻留时长、CPU、PSS、网络与退出原因。Android 公共 API 不提供可线上记录的 renderer PID，本地诊断用 Perfetto 或 `ps` 按 renderer 进程关联。

**Q44: [learning] 原生化与保留 WebView 的取舍怎么落地成可执行规则？**

两个问题定取舍：页面高频操作是否产生了可测量的额外 CPU、内存或网络成本。局部原生化能否消除主要成本。按业务形态的倾向：视频流/直播原生播放器优先（长驻留、高带宽、解码渲染成本高）。信息流原生列表加局部 Hybrid（高频滚动、大图、广告脚本多）。电商与内容详情 Hybrid 可用（页面变化快但交互深度中等，配资源预加载、模板缓存、JSBridge 允许列表、图片尺寸约束）。活动/营销页 WebView 可用（低频、生命周期短、需快速回退版本，限制第三方脚本）。登录/支付/风控原生优先（安全、稳定与可观测性要求高，必要 Web 页用独立容器与审计日志）。富交互工具页局部原生化（原生负责输入与高频渲染区域，Web 负责配置面板，密集桥调用合并批量）。保留 WebView 的页面要按测量结果处理缓存命中、图片尺寸、请求合并与不可见释放，并为 CPU 时间、PSS、网络字节、卡顿率、退出率与 Android Vitals 设量化阈值，越线停止放量。TWA 与 PWA 的成本归属不同（TWA 页面运行在浏览器、宿主拿不到页面内容与 Cookie，不能注入 JSBridge），功耗测试不要与普通 WebView 混成一组。

## 前台服务、冻结与后台网络

**Q45: [learning] 应用退后台一段时间后 WebSocket 心跳超时被服务端断开、解冻后定时任务瞬间连发，甚至后台“无故”死亡——缓存进程冻结（Freezer）下发生了什么？怎么治理长连接？**

冻结是 Android 11+ 对缓存进程的默认治理：cgroup freezer 把整个进程暂停——没有 CPU、没有定时器、socket 不收包——进程还在，但一切主动行为停摆。冻结流程与资格判断的机制细节见 memory 册，冻结中的 Binder 事务语义见架构册 Binder 深化篇。

1. **三类现象**：心跳停导致服务端按超时断连。解冻瞬间积压的 Handler 消息与定时任务连发（用 `elapsedRealtime` 差值确认积压）。冻结中收到同步 Binder 事务的进程会被直接终止（`ApplicationExitInfo` 的 `REASON_FREEZER`）。
2. **确认**：`dumpsys activity processes` 看 frozen/pending 状态。`getApplicationExitInfo()` 看 reason。先区分“被冻结”与“被厂商后台限制”——两者取证入口不同。
3. **长连接治理**：需要持续连接的场景用前台服务（豁免冻结，遵守本篇关于前台服务类型和启动限制的约束）。或退后台主动断连、解冻后重连。推送走 FCM 高优先级消息，不依赖冻结期心跳。
4. **边界**：冻结不是功耗问题的万能解释——先排除 `BACKGROUND_RESTRICTED` 与厂商限制（对应本篇“进程可能被回收时发现 BLE 设备”题中的后台限制排查），再查冻结状态。

跨层边界：Cached Apps Freezer 系统行为见 [Cached Apps Freezer 系统行为](../../02-系统/02-进程启动与ART.md)。

**Q46: [learning] Android 14 强制的 foregroundServiceType 有哪些？从 BOOT_COMPLETED 能拉起哪几种前台服务？**

Android 14（targetSdk 34）起前台服务必须在 manifest 声明 `android:foregroundServiceType`，官方类型共 13 种（camera、connectedDevice、dataSync、health、location、mediaPlayback、mediaProjection、microphone、phoneCall、remoteMessaging、shortService、specialUse、systemExempted），每种还需对应的 `FOREGROUND_SERVICE_*` 权限（API 34 新增，normal 级）加用例本身的运行时权限。缺声明直接抛 `MissingForegroundServiceTypeException`。

1. **超时语义**（ANR 超时契约见 [ANR 检测与证据诊断](../../02-系统/04-ANR与故障诊断.md)）：shortService 约 3 分钟且不可重入。Android 15 起 targetSdk 35+ 的 dataSync/mediaProcessing 在 24 小时窗口内累计 6 小时，`onTimeout()` 后数秒内必须 stop，否则抛 `ForegroundServiceDidNotStopInTimeException`——常见误传是“Android 14 六小时”，6 小时是 Android 15 行为。
2. **BOOT_COMPLETED 豁免清单**：Android 14 仅豁免 mediaPlayback、phoneCall、shortService、systemExempted 四类。Android 15（targetSdk 35）移除了 mediaPlayback——“开机后台起音乐服务”从此不可靠，迁移路径是 WorkManager expedited work 或等用户交互。
3. **while-in-use**：camera/microphone/location 类型只有应用处于前台（或经通知点击等明确用户操作触发）才能访问对应硬件。
4. **排查入口**：后台启动被拒抛 `ForegroundServiceStartNotAllowedException`——先对照豁免类型与启动时机，再查 OEM 限制（对应本篇关于 OEM 后台限制和前台服务豁免的分析）。

补充边界：

限时规则从 Android 14 起逐版本引入（AAOS13 源码核对：`ServiceInfo` 只有 `FOREGROUND_SERVICE_TYPE_DATA_SYNC`、`MEDIA_PLAYBACK` 等类型常量，没有 shortService）：`shortService`（Android 14）约三分钟，超时回调 `Service.onTimeout(int)`，仍不停止会走 ANR 流程。`dataSync` 与 `mediaProcessing`（Android 15、target 35+）在应用处于后台时每 24 小时累计 6 小时，回调为 `Service.onTimeout(int, int)`，数秒内不停止会抛内部远程服务异常并终止进程。六小时按类型分别计时，同一 App 的多个同类型服务共享额度，回前台会重置。额度耗尽后再启动同类型服务收到 `ForegroundServiceStartNotAllowedException`。

实现路径（材料按 Android 17 的 `ActiveServices` 核对）：`getTimeLimitedFgsType()` 把 dataSync 与 mediaProcessing 纳入限时路径，宽限期结束后 `onFgsCrashTimeout()` 以 `ForegroundServiceDidNotStopInTimeException` 终止宿主进程。shortService 使用独立的 ANR timer，两条超时路径不能混为同一种故障。超时回调里只应保存进度、释放资源并停止服务。数据同步可改用 WorkManager 或 user-initiated data transfer job（各自接受对应配额规则）。

配套的前台服务启动边界（Android 14、target 34+）：类型声明、类型权限与运行时前置条件必须同时成立——缺 `foregroundServiceType` 可能触发 `MissingForegroundServiceTypeException`，缺 `FOREGROUND_SERVICE_*` 权限或 location/camera/microphone 的 while-in-use 条件不满足触发 `SecurityException`，后台启动无豁免触发 `ForegroundServiceStartNotAllowedException`。日志判读要区分三者，修复位置各不相同。

**Q47: [learning] 蜂窝网络请求为什么要批量处理？哪些请求不能延迟？**

蜂窝数据传输的成本不只来自字节数，还包括 DNS、建连、TLS 和请求完成后的 modem tail time。应用能控制请求是否过碎、重复握手以及可否合并，但无法从 Android 公共 API 得知跨设备稳定的 RRC、DRX 或 inactivity timer 状态。

风险是反复把蜂窝 modem 拉进活跃状态：DNS、建连、TLS 握手与传输本身消耗能量，请求结束后基带还会保持一段 tail time（高功耗驻留）。应用层可以确认并控制“请求是否过碎、是否重复握手、能否合并”：日志、埋点、缓存媒体等可延迟内容先写入本地持久化 outbox，再由一个唯一 Worker 批量上传，收到服务端确认后按事务删除，并配低频恢复同步兜底。复用 HTTP 连接、增量接口、ETag 与断点续传减少重复字节。交互请求、支付确认等用户正在等待的发送操作保留独立及时路径，不能为批量而延后。

不能跨设备引用的是 modem 行为：RRC 连接态、DRX 周期、inactivity timer 与发射功率由基带、制式、运营商参数与信号共同决定，公开 Android API 没有跨设备可靠的 RRC 状态，`setRadioPower()` 属系统 telephony 控制路径、普通应用不能用它节能。tail 时长与能量必须在目标设备和网络上测量。把 3G/LTE/5G 的状态放进同一张固定电流表会产生错误结论。

诊断注意：`TrafficStats` 的字节数不能换算成 mAh——相同字节在 Wi-Fi、5G 弱信号与漫游下的能量差别很大。UID 网络字节下降也不等于蜂窝功耗按比例下降，还要看信号、制式、modem rail 与请求时间线。

**Q48: [learning] 后台消息为什么优先用推送，而不是常驻轮询？FCM 优先级有哪些边界？**

轮询会把消息送达变成应用侧定时探测：即使没有新消息，也要付出定时器唤醒、网络握手与维持进程的成本。持续通知只表达用户可见，不会降低这些成本，也不带来 Doze、配额或 Low Power Standby 豁免。

轮询把“消息送达”变成应用侧定时探测：没有新消息也要付出定时器唤醒、网络握手与维持进程的成本，`START_STICKY` 还可能在进程被杀后拉起服务继续轮询。持续通知只表达用户可见，不降低这些成本，也换不来 Doze、配额或 Low Power Standby 的豁免。按业务时效选择：用户可见的实时消息用共享推送通道。后台内容刷新用普通优先级推送触发一次同步，再加低频兜底同步。可延迟同步交给 WorkManager/JobScheduler 并声明约束。

FCM 优先级边界：normal priority 适合普通同步，在 Doze 中可能延迟到维护窗口。high priority 只用于时间敏感、会产生用户可见通知的消息，系统会给接收方短暂的网络与 partial WakeLock 机会，处理完成后设备继续空闲。长期发送 high priority 却没有用户可见结果，FCM 可能降低后续消息优先级或改为代理通知。

推送不能替代数据一致性设计：消息可能重复、延迟或丢失，客户端仍要用版本号或游标拉取缺失数据。测试 Doze 场景时要在未充电状态下用 `dumpsys deviceidle force-idle` 验证推送送达与普通同步的恢复延迟，并在结束后 `unforce`。

## 功耗数据读取

**Q49: [learning] 普通 App 在 Android 13/17 上还能从系统读到哪些功耗相关数据？哪些路径走不通？**

公开可用的有两层。本 UID 层：API 24 起 `SystemHealthManager.takeMyUidSnapshot()` 返回本 UID 的 `HealthStats`（用户态/内核态 CPU 时间、Wi-Fi 与移动网络字节、WakeLock、Job、Sync、传感器、前后台状态等键），它是资源代理指标而不是能量测量。读取前必须用对应的 `has…()` 检查键是否存在，共享 UID 会把多个包的统计记到同一身份，系统代持的 WakeLock 和库内部调度也会影响解释。电池状态层：`BatteryManager` 公开电量、充电状态、瞬时/平均电流、charge counter（微安时）和 energy counter（纳瓦时）等属性，描述整块电池或燃料计状态、不提供 App 归因。设备可以不支持某个属性——`getIntProperty()` 对 targetSdkVersion 为 Android 9 及以上的应用返回 `Integer.MIN_VALUE`（更旧目标返回 0），`getLongProperty()` 返回 `Long.MIN_VALUE`，API 35 新增的 `getStringProperty()` 返回 `null`。

走不通的路径：`BatteryStatsManager#getBatteryUsageStats()`、`BatteryUsageStatsQuery` 和按 UID 获取 `BatteryConsumer` 的路径都带 `@hide`，且受 `BATTERY_STATS` 权限保护（Android 17 清单声明为 `signature|privileged|development`，AAOS13 同样不是普通应用可得）。`SystemHealthManager` 也没有 `getBatteryUsageStats()`、`registerBatteryStateCallback()` 或 `getCurrentPowerStats()`。普通 App 不能复制系统设置或 system_server 的调用代码获取全设备 `BatteryUsageStats`——这类信息应通过 adb、bugreport、平台测试组件或 OEM 授权的系统应用获取。
