# 应用启动与交付

**Q1: [learning] 冷启动、温启动、热启动的判定依据是什么，为什么不能凭生命周期日志下结论？**

三种类型描述启动前的进程与 Activity 状态：

1. **冷启动：**进程不存在，需创建进程、绑定 Application、创建 Activity、生成首帧。
2. **温启动：**常见口径是进程存活、Activity 需要重建。
3. **热启动：**进程与目标 Activity 都在，只需带回前台并恢复。

生命周期日志只能辅助判断，出现 `onCreate()` 或 `onResume()` 不足以推断类型——按 Home、按返回、从 Recents 恢复、点通知产生不同任务栈状态。

可靠证据是 `am start -W` 输出、Macrobenchmark 的 `StartupMode`、Perfetto Android App Startups 区间，以及 API 35+（Android 15，AAOS13 无）`ApplicationStartInfo.getStartType()`。

冷启动时序按 AAOS13 源码核对为：Launcher 发起 → ATMS 解析并可先显示 starting window → `Process.start` 经 Zygote fork 并 specialize → 应用 `attachApplication` → `handleBindApplication()`（其中先 `makeApplicationInner()` 创建 Application，再 `installContentProviders()`，最后 `callApplicationOnCreate()`，所以 Provider 的 `onCreate()` 早于 `Application.onCreate()`）→ `ClientTransaction` 驱动 Activity 生命周期与 UI → 首帧 buffer 提交。

TTID 的平台计量边界是 `ActivityRecord.onWindowsDrawn()` 调用 `ActivityMetricsLogger.notifyWindowsDrawn()`（AAOS13 核对），它晚于生命周期回调返回、早于面板像素发光。

**Q2: [learning] TTID 与 TTFD 各自的语义与阈值是什么，reportFullyDrawn() 报早或报晚会发生什么？**

TTID 统计从系统收到启动请求到目标 Activity 首帧，Logcat 的 `Displayed` 行与 vitals 启动告警以此为口径：冷启动达 5 秒、温启动 2 秒、热启动 1.5 秒归为 excessive startup（官方告警边界，官方度量指南另给出冷 500 ms/温 200 ms/热 150 ms 的建议目标，均为转写口径）。TTFD 用相同起点，终点是应用调用 `reportFullyDrawn()` 报告主内容可用，二者描述不同阶段，首帧可能只是骨架或空列表。

框架侧保护：过早调用时 `ActivityMetricsLogger.notifyFullyDrawn()` 会检查窗口是否已 drawn 并推迟报告，保证 TTFD 不早于 TTID，但它无法判断业务是否真可用，就绪条件定义错误仍会失真——与首屏无关的预取、埋点不应延后 TTFD，错误状态应设计成可交互以免 TTFD 永远无法上报。测量工具分层：`am start -W -S` 适合冒烟检查（`-S` 会改变现场；`ThisTime`、`TotalTime`、`WaitTime` 覆盖范围不同）。Logcat 定位样本但缺少线程与渲染细节。

Macrobenchmark 固定启动类型、`CompilationMode` 与迭代并自动保存 trace，是可复现对照的标准工具。Perfetto 的 `android.startup` 标准库可查启动类型、TTID 与 TTFD（应用未上报时 TTFD 为空）。API 35+ 的 `ApplicationStartInfo` 提供结构化的阶段时间戳（读取前先检查 startup state，`FULLY_DRAWN` 依赖应用上报）。

**Q3: [learning] 启动监控为什么不能只上报 Application.onCreate() 的出入口耗时，为更早拿到时间点新增自动初始化 Provider 错在哪？**

只埋 `Application.onCreate()` 会漏掉系统收到启动请求、进程创建、`bindApplication`、Provider 安装与首帧渲染这几段，也无法表达首屏核心内容何时可用。而为了“更早”新增自动初始化 Provider，等于把监控 SDK 自己的类加载与初始化放进每一次冷启动的关键路径——Provider 在 `Application.onCreate()` 之前安装（该时序已按 AAOS13 的 `ActivityThread.handleBindApplication()` 核对）。

正确做法是固定一份测量契约并分层埋点：已有最早轻量入口或 `Application.attachBaseContext()` 记 `process_observed`（只说明 App 代码能看到进程，不含 fork 精确时间）。`onCreate()` 出入口只解释 Application 阶段。首屏状态机记 `content_ready`。`reportFullyDrawn()` 调用处记 `fully_drawn_reported`。已有 Provider 即使承担最早入口，也应只保存一个时间戳与必要身份，序列化、压缩、网络发送与扩展设备信息延后到首帧后。

采集器本身不能在首帧前建大线程池、扫描完整设备信息或同步写日志。边界：`onResume`、`OnPreDrawListener` 与 `Choreographer.FrameCallback` 都只是自定义近似点，事件名要写成 `pre_draw`、`frame_callback`，不能冒充平台 TTID，因为它们都不能证明 SurfaceFlinger 已完成显示。

跨层边界：Provider 初始化的系统边界见 [Provider 初始化的系统边界](../../02-系统/02-进程启动与ART.md)。

**Q4: [learning] 启动任务应按什么完成边界分级？**

初始化框架只能改变任务组织，不能让不必要的工作变便宜。先逐项回答当前进程与入口是否需要、首帧或关键内容前是否必须完成、失败能否降级，再按完成边界分级：

1. **PRE_APP：**Application.onCreate() 前由 Provider 生命周期强制执行；不应为追求“更早”把额外工作放进这里。
2. **PRE_FIRST_FRAME：**TTID 前必须就绪，否则首屏不能正确渲染的同步状态。
3. **PRE_FULLY_DRAWN：**TTFD 前首要操作所需的数据和能力。
4. **DEFERRED：**页面可用后才需要的二级功能、预取与非必要 SDK。

“移到后台”仍会消耗 CPU、I/O 与内存，“首帧后执行”只改变开始时间，“首次使用”把成本转移到用户第一次进入功能。长期轮询和周期任务属于运行期调度，启动图只负责配置到约定状态，不能让启动任务永久未完成。

**Q5: [learning] 启动任务图的节点为什么必须把“异步完成”建模成一等状态，“SDK init 已提交”与“SDK 已就绪”差在哪？**

后继任务只能在前驱产生最终结果后就绪，所以节点必须声明 id、进程、phase、依赖、执行上下文、任务逻辑与完成信号，且完成要带结果——`Success`、`Degraded`（含备用值）、`Failed` 三态，“已提交异步工作”不是完成。用 `suspend` 函数表达逻辑完成点：函数挂起时不占住调用线程，只有结果产生才算结束。SDK 的 `startAsync()` 返回只说明请求已提交，依赖它的后继不能据此运行。App Startup 的 `create()` 必须同步返回可用实例，内部若只提交异步任务，依赖顺序对逻辑就绪没有保证。框架也可以用 Guava `ListenableFuture`、Java `CompletionStage` 或带完成回调的接口实现同一契约。边界：等待异步结果时应在生产者与消费者两端记录可关联的 async trace（并控制关联 ID 数量），否则 trace 里“切片结束”只代表提交，无法定位真正的初始化完成时刻。

**Q6: [learning] 构建启动任务图时必须拒绝哪些无效输入，DFS 与 Kahn 检测环各怎么做？**

任何任务执行前，构图校验器应拒绝：

- 重复 ID 与不存在的依赖；
- 自依赖与环；
- 被禁用但仍被硬依赖的节点；
- Main 任务阻塞等待后台 worker，而该 worker 又要回 Main 才能完成；
- 当前进程不允许的节点；
- 阶段倒挂（如首帧任务硬依赖 `DEFERRED` 任务）；
- 多个节点写同一非线程安全状态却没有顺序约束。

环检测两条等价路径：DFS 把当前递归路径中的节点标为 `GRAY`，再次遇到 `GRAY` 节点即存在环，并可直接输出环路径。Kahn 拓扑排序反复移除入度为 0 的节点，处理结束后仍有剩余节点即存在环。错误信息必须输出完整环路径（如 `A → B → C → A`），方便配置与模块负责人定位。边界：任务图可以有多个互不依赖的根节点，不要求整张图只有一个连通分量。条件任务应在构图时移除节点并重新检查所有后继，而不是留到执行阶段才跳过。

**Q7: [learning] 启动任务的超时与失败语义怎么定义，“A 超时就当作完成”会破坏什么？**

超时通常只让等待方停止等待，底层网络、Binder、文件 I/O 或供应商线程可能继续运行。`Future.cancel(true)` 与线程 interrupt 只是协作取消信号，任务代码需要主动检查取消状态或调用底层取消 API。把硬依赖的超时映射成“完成”会破坏语义——正确做法是映射成 `Degraded` 或 `Failed`，再由后继的契约决定能否继续。失败策略至少四种：

1. **`FAIL_GRAPH`：**终止依赖该结果的关键路径并展示可恢复错误。
2. **`USE_FALLBACK`：**产出类型一致的本地或默认备用结果。
3. **`SKIP_DEPENDENTS`：**跳过所有无法满足硬依赖的后继。
4. **`CONTINUE_SOFT`：**仅软依赖继续并记录能力缺失。

框架要保存原始异常、任务 ID、进程、线程与已运行时长。捕获 `Throwable` 后无条件继续会掩盖 `OutOfMemoryError` 等进程级风险，也会让后继在半初始化状态运行。反例：为每个任务新建线程再用 `CountDownLatch.await(timeout)` 包住，只会让 executor 工作线程空等另一线程、无法停止被包裹任务，还放大线程数与栈内存。

**Q8: [learning] Jetpack App Startup 解决什么问题、边界在哪，第三方 ContentProvider 的自动初始化如何处置？**

App Startup 用一个 `InitializationProvider` 统一接管 manifest metadata 注册的 `Initializer`，`dependencies()` 声明顺序，`AppInitializer#doInitialize()` 先递归完成依赖再 `create()`。它减少独立 Provider 的组件与发现开销、统一依赖顺序，但有三个边界：

1. Initializer 不会被自动并行执行。
2. `create()` 耗时仍计入启动。
3. 自动初始化只适合耗时短、所有相关进程都需要且必须很早可用的组件。

时序上 Provider 安装发生在 `handleBindApplication()` 内、早于 `Application.onCreate()`（AAOS13 源码核对），所以任何通过 Provider 的 SDK 自动初始化都直接进入冷启动路径。处置流程：

1. 从目标 variant 的合并 Manifest 找出全部 Provider 与 metadata 并追溯来源依赖。
2. 查文档是否支持关闭自动初始化。

App Startup 的单个注册项可用 `<meta-data>` 加 `tools:node="remove"` 移除、保留公共 `InitializationProvider`，再在业务触发点手动 `initializeComponent()`（手动初始化仍会递归依赖树）。第三方自定义 Provider 只有文档明确支持才能 remove，否则可能破坏启动、备份或后台任务。多进程应用要逐进程计算成本：带 `android:process` 的组件所在进程也会安装可见 Provider 并创建 Application，初始化器应识别当前进程与入口需求。

跨层边界：ContentProvider 初始化与进程启动见 [ContentProvider 初始化与进程启动](../../02-系统/02-进程启动与ART.md)。

**Q9: [learning] Jetpack App Startup 1.2.0 的执行模型是什么，动态特性模块与多进程场景各有哪些坑？**

App Startup 1.2.0 用一个 `InitializationProvider` 发现 Manifest `<meta-data>`（value 为 `androidx.startup`）声明的 `Initializer`：反射按类名加载、深度优先初始化 `dependencies()`、用 `initializing` 集合检测环、调用 `create()` 并缓存结果、为发现与初始化加 Trace。全部发生在 Provider 安装阶段的主线程，不支持优先级、超时、取消与异步结果。

三个关键边界：其一，动态特性模块——metadata 指向尚未安装模块中的类时 `Class.forName()` 抛异常并被包装成 `StartupException`，进程可能在 `Application.onCreate()` 之前终止，可选模块的桥接 initializer 应留在基础模块或等模块安装后手动初始化。其二，多进程——`AppInitializer` 是进程内单例，Provider 归属由最终 Manifest 的 `android:process` 决定，默认 Provider 不会因为应用有多个子进程就各执行一次，跨进程完成关系要用 Binder、Provider 或持久状态显式传递。

其三，手动初始化——在最终合并 Manifest 中对对应 `<meta-data>` 用 `tools:node="remove"`（Merger 按 `android:name` 匹配，只从自己源码删一行不能证明已移除），需要时调 `AppInitializer.initializeComponent()`，注意关闭一个组件的自动初始化也会关闭由它带入的依赖。metadata 与集合遍历顺序不是契约，有先后要求必须写进 `dependencies()`。

**Q10: [learning] MessageQueue.IdleHandler 的 queueIdle() 在什么条件下被调用，为什么不能当“设备空闲”信号？**

`IdleHandler` 在所属 Looper 没有可立即分发的消息、准备进入等待时收到 `queueIdle()`——即使队列里仍有未来时间点才到期的消息也可能被调用。返回 `true` 表示以后每次进入 idle 仍可调用，`false` 表示用后移除。它只说明主线程消息队列暂时无事可做，不代表 CPU 或 GPU 利用率低、下一次输入或 VSync 很远、系统给了固定执行预算，也不说明设备适合预解压或构建大对象。正确用法是只做有界检查或向调度器发一次信号（返回 `false` 避免重复触发），由调度器再核对首帧状态、页面可见性、任务 deadline 与资源冲突。

禁止在 `queueIdle()` 里读数据库或文件、解析大 JSON、创建大量对象、返回 `true` 轮询业务状态，也不要让每个 SDK 各自注册。版本边界：Android 17 引入并发消息队列 DeliQueue，`targetSdkVersion >= 37` 默认启用，IdleHandler 的外部语义与 legacy 保持一致。AAOS13 仍是经典单 monitor 锁的 `MessageQueue` 实现（本地核对无 `CombinedDeliMessageQueue`），两条路径下“队列将要等待”的语义相同。

**Q11: [learning] “首帧已提交”为什么不能靠 view.post() 或 onResume 判断，registerFrameCommitCallback() 有哪些边界？**

`view.post()` 只表示 Runnable 进入了主线程消息队列，执行位置受队列已有消息、同步屏障与 traversal 调度影响。`onResume` 不等于首帧，`OnPreDrawListener` 发生在即将绘制之前，`Choreographer.FrameCallback` 只是帧调度回调，三者都不能证明该帧已提交或显示。API 29+ 的硬件渲染窗口可用 `ViewTreeObserver.registerFrameCommitCallback()` 观察“当前渲染内容已提交到 swap chain（等待显示的图形缓冲队列）”，用它打开调度门、不在回调里执行初始化。

边界：回调只针对注册后参与提交的帧，注册太晚只能观察后续帧。提交到 swap chain 不等于像素已经显示。软件渲染时不会回调，允许软件渲染的应用要提供独立的保守触发或把任务改成首次使用执行，且该信号只用于性能调度、不作为业务正确性的唯一条件。首帧后队列要限流：控制同时运行的 CPU 任务数、I/O 是否访问同一文件或数据库、主线程回调分散到多个帧，jank、thermal 或低电量时暂停非必要预热。从 TTID 前移走的任务可能延长 TTFD，只有 TTFD 必需项才进入完成条件。需要跨进程存活的预热交给 WorkManager，它的调度时机不是精确的“首帧后 500 ms”。

**Q12: [learning] 启动线程池为什么“按核数创建 + 无界队列”常常无效，CallerRunsPolicy 会把什么搬回主线程？**

`ThreadPoolExecutor` 在核心线程都忙时先调用 `workQueue.offer()` 入队，只有入队失败才创建非核心线程，最后才执行拒绝策略——所以配无界 `LinkedBlockingQueue` 时线程数停在核心线程数，`maximumPoolSize` 不参与扩容且积压无上界，调大它没有效果。有界队列的拒绝策略必须绑定任务契约：`CallerRunsPolicy` 让提交线程直接执行被拒任务，提交者是 Main 时后台重活直接回到启动关键路径，主线程提交禁止使用。关键任务被拒应记录并走明确降级，遥测类任务可丢弃但要记录丢弃原因。

并发度也不该固化成 `availableProcessors()`：它不表达大小核、调频、温度与 RenderThread 竞争，首帧期间占满所有核心可能让 Main 与 RenderThread 更慢。阻塞线程不占 CPU 但占栈与调度结构，I/O 并发应按数据库、连接池、Binder 与服务端配额设上限，同池同步等待子任务会造成永久饥饿。

优先级方面 `Process.setThreadPriority()` 对应 Linux nice 值（AAOS13 核对：`THREAD_PRIORITY_BACKGROUND = 10`、`FOREGROUND = -2`、`DEFAULT = 0`，数值越小权重越高），由 `java.lang.Thread` 创建的子线程不继承它，线程工厂应显式命名并让每个 worker 在自己入口设置。不要把业务线程硬绑大核。

反例参考：`AsyncTask` 的 `THREAD_POOL_EXECUTOR`（AAOS13 核对：core 1、max 20、`SynchronousQueue`、拒绝后转 5 线程串行兜底）是遗留实现，不是应用线程池模板。

**Q13: [learning] 多进程应用为什么必须逐进程建初始化清单，在 Application.onCreate() 里按进程名分支漏掉了什么？**

Provider 归属由最终 Manifest 的 `android:process` 决定：默认 Provider 只随默认进程安装，声明 `:worker` 的 Provider 只在对应进程创建。每个进程有独立的堆、静态字段、ClassLoader 与 App Startup 单例，一个进程不能依赖另一个进程的静态 `initialized` 布尔值。在 `Application.onCreate()` 里按 `Application.getProcessName()`（API 28+）分支只能约束分支之后的工作——分配给该进程的自动初始化 Provider 已在此前执行，无法撤销。

类第一次加载触发的静态初始化同样拦不住，所以进程选择应在 Manifest 或构图阶段完成，而不是在 initializer 里先加载全量模块再 `if` 跳过。进程启动没有“只创建进程、暂不运行组件”的通用接口：启动 Activity、`startService()`、`bindService()`、访问远程 Provider、接收广播都可能触发进程创建。

拉起时机按用户路径分档：

1. **首屏前：**缩小协议与初始化集，使用异步协议、deadline 与降级。
2. **首帧后：**低端机上仍会与主进程竞争 CPU/存储/内存，预热实验要同时比较命中率、TTID/TTFD、全应用 PSS 与失败率。
3. **临近入口：**由明确产品信号触发，并支持过期取消。
4. **系统调度：**使用 WorkManager/JobScheduler。

普通私有远程进程沿用应用 UID 与权限，`isolatedProcess` 用隔离 UID、没有自身权限，两者的权限假设要分别验证。

**Q14: [learning] 首帧前同步访问远程 Provider 或同步等待 Binder 会发生什么，MODE_MULTI_PROCESS 和 Application.onTerminate() 为什么不可依赖？**

主进程通过 `ContentResolver` 同步访问远端 authority 时，`ActivityThread` 会向 system_server 请求 Provider 并等待承载进程完成发布，等待方若是主线程，进程创建、Provider 安装、`Application.onCreate()` 的全部时间都进入 UI 关键路径。`bindService()` 后又同步等待连接结果同理——远端进程并不会让同步访问自动变快。

跨进程能力应建模为状态机（Disconnected/Connecting/Ready/Failed，处理 `onServiceDisconnected`/`onBindingDied`/`onNullBinding`/`binderDied` 的不同语义），业务协程异步等待 ready，主线程禁止 `CountDownLatch`、自旋或无限期同步调用。超时边界：`withTimeout` 只让调用方协程停止等待，不能中断已进入内核的同步 Binder 事务，需要硬时限的耗时协议要改成异步请求 + 请求 ID + 显式 `cancel` + 服务端可重试。

两个历史 API 不可依赖：`Context.MODE_MULTI_PROCESS` 自 API 23 废弃，不能可靠协调跨进程 `SharedPreferences`（各进程独立缓存、无冲突合并规则），跨进程状态要有唯一写入者与一致性协议。`Application.onTerminate()` 在量产设备结束进程时不会被调用，恢复要靠 Binder 死亡监听、持久化状态与幂等请求。

另外 `android:multiprocess="true"` 允许系统在调用方同 UID 进程本地创建 Provider 实例（AAOS13 核对：`ContentProviderRecord.canRunHere()` 同时检查 multiprocess 与 UID），省部分 Binder 但复制对象/缓存/连接，不是通用启动优化。

跨层边界：Binder 与远程 Provider 的系统路径见 [Binder 与远程 Provider 的系统路径](../../02-系统/02-进程启动与ART.md)。

**Q15: [learning] SDK Runtime 退场后广告 SDK 的启动治理应该怎么做，“异步 init”返回后能假设什么？**

广告 SDK 回到宿主进程 AAR 形态后，治理从最终 merged manifest 入手：SDK 的 Provider/App Startup initializer 属于哪个进程、能否按供应方支持方式关闭自动初始化（Provider 在 `Application.onCreate()` 之前执行，进程分支和延迟开关来不及阻止它）、authority 是否冲突、升级后的 Manifest diff 是否新增组件。`Application.onCreate()` 只注册轻量网关并读取本地功能开关，不等待 SDK ready。

页面并发 init 由网关状态机（Idle/Initializing/Ready/Failed）合并成一次会话任务，失败保存为调用方可读取的结果，重试按错误类型与退避间隔由网关控制，不能多个页面各自循环触发。阶段拆分：Provider 只留 SDK 强制且无法关闭的最小工作。首帧前只做“页面是否保留广告容器”的本地决策。初始化与首请求放到首帧后或临近广告入口，低端设备上“首帧后”仍可能与首屏动画争 CPU，要用实验确认首个广告可用率与启动体验的取舍。

两个边界：SDK 文档说“异步初始化”也要在 trace 中验证——异步 API 可能在返回前同步执行类加载、读取 Preferences、创建线程，完成回调也可能回主线程。init 超时只是调用方停止等待，后台初始化未必取消，失败后的备用路径不能比正常路径更重（如回主线程同步初始化旧 SDK），否则少量错误样本会集中到 P99 与 ANR。首屏广告要产品先定默认行为：跳过、固定占位、短 deadline 或独立可取消加载页，并把广告等待计入 TTFD/业务 ready。

**Q16: [learning] @HiltAndroidApp 的 component 什么时候创建，ContentProvider 与 ViewModel 场景的注入时机差在哪？**

`@HiltAndroidApp` 生成的应用基类在 `onCreate()` 中先执行 `hiltInternalInject()`（创建 `SingletonComponent` 并给 Application 做成员注入），用户 Application 覆盖 `onCreate()` 时必须先调用 `super.onCreate()`，注入字段只能在 `super` 返回后使用。`SingletonComponent` 按第一次访问创建（生成代码用 volatile 双检锁），标准 Hilt 应用的这次访问就发生在 `super.onCreate()` 的注入阶段。

component 构造只建立 provider、module 与 scope 关系，不把图中所有业务对象创建一遍。两个入口的时机差：Android `ContentProvider` 安装在 `Application.onCreate()` 之前（AAOS13 核对），Hilt 不支持给 `ContentProvider` 加 `@AndroidEntryPoint`，若必须访问 binding 要声明显式 `@EntryPoint`——它只解决访问方式，且会把 component 创建提前到 Provider 阶段，所以非必要 Provider 应移除或延迟，必须保留的只读轻量 binding。

`@HiltViewModel` 不会随进程无条件创建，首次 `ViewModelProvider`/`hiltViewModel()` 请求时才建立 `ViewModelComponent` 并解析构造参数，它是否属于启动成本取决于首屏何时请求——把重工作从 Activity 字段移进 ViewModel 构造函数只是换位置。Hilt Gradle 插件默认启用 `fastInit`（减少 component 初始化需加载的类），但不会让重对象自动延迟。

**Q17: [learning] @Singleton、直接注入、Lazy<T>、Provider<T> 的构造时机差在哪，“图里有 2000 个 binding”等于启动创建了 2000 个对象吗？**

不等。`@Singleton` 只规定同一 `SingletonComponent` 内共享一个实例（Dagger 用 `DoubleCheck` 包装：第一次 `get()` 计算并缓存），component 创建时没被请求就不会提前构造——它不是 eager。时机差异：`@Inject lateinit var` 与构造参数注入在宿主被注入/构造时就拉起递归依赖，`@Inject lateinit var` 不具备“第一次业务使用时再注入”的语义。`dagger.Lazy<T>` 第一次 `get()` 时创建并由该 wrapper 缓存（分别注入的两个 `Lazy` 各自独立）。

`Provider<T>` 每次 `get()` 请求（unscoped binding 每次新建，scoped 返回缓存）。因此判断启动成本要看 Application 直接注入字段、Provider 阶段访问的 binding、首屏 ViewModel 及其递归依赖，而不是图的总大小。边界：若启动路径仍在首帧前调用 `Lazy.get()`，延迟形同虚设。`@Provides` 方法体是重活常见藏身处（网络栈构建、证书读取、数据库打开、native 库加载、线程池创建），适合 `@Binds` 的接口映射不要写成 `@Provides`。`@Reusable` 允许复用但不保证对象身份相同。

**Q18: [learning] Koin 的启动成本分哪两段，createdAtStart、lazyModules 与 KSP 迁移各要注意什么？**

Koin 经典 DSL 的启动成本分两段：`startKoin { modules(...) }` 创建 `KoinApplication`、注册 `GlobalContext` 并载入 module definitions（运行时注册表，按类型/qualifier/scope 查找，不是每次都走 Java 反射）。第一次 `get()` 解析 definition 并执行构造 lambda，是否缓存由 `single`/`factory`/scope 决定。

要点：`createdAtStart = true` 标记 eager singleton，标准 `startKoin` 在注册完后自动 `createEagerInstances()` 统一创建——优化先删没有业务必要的 `createdAtStart`。

`lazyModules()` 用协程后台载入 module（Koin 4.2 起多个 module 各用一个协程并行，默认 `Dispatchers.Default`），`waitAllStartJobs()` 会阻塞等待、主线程调用会把成本放回启动路径（应使用挂起的 `awaitAllStartJobs()`），且同步 module 依赖尚未载入的 lazy module 时 Koin 目前不自动校验，只适合延迟依赖边界清晰、首屏不访问的 feature。release 不要显式启用 DEBUG/INFO 级 `AndroidLogger`（默认 `EmptyLogger`）。

KSP/kapt 属于构建期优化：KSP 直接分析 Kotlin symbol，收益体现在 clean/incremental 构建时间（官方口径“最高约两倍”描述 symbol processing），在 DI 图、编译选项与发布产物等价前不能换算成冷启动收益。每个 module 移除全部 kapt processor 后再比较构建时间，并用 release Macrobenchmark 验收。框架名称不决定结果：小型手写 `ServiceLocator` 也可能在静态初始化中 eager 创建全部服务。

**Q19: [learning] 哪些“GC 抑制”手段不可用于生产应用，启动期分配治理的正确顺序是什么？**

三类方案不可用：hook `libart.so`（替换 `ConcurrentGCTask` 的 vtable 条目或 inline hook）直接改系统运行时内部 ABI，受只读映射、RELRO、CFI 等加固保护，ART 可经 Mainline 独立更新，在 `Run()` 中 sleep 还会连 trim、transition 一起延迟，失败后果是随机崩溃、堆破坏或 OOM。

反射调用 `VMRuntime` 的 `requestConcurrentGC()`、`setTargetHeapUtilization()`、`notifyStartupCompleted()`——它们是 hidden 或 module-only API 且受 non-SDK 接口限制，而 `registerSensitiveThread()` 只是给线程设 JIT sensitive 标记（AAOS13 核对：`handleBindApplication()` 第一行即为 UI 线程调用它），没有“优先分配”或“减少 GC”的语义。

无证据地在首帧后主动 `System.gc()`——显式请求可能引入暂停与带宽竞争，只有 trace 与对照实验证明无交互窗口的请求能改善后续关键路径才可评估。正确顺序：先用 Perfetto 证明 GC 与启动关键路径重叠并确认 cause 与 collector。再用 Allocation Recording（要求 debuggable 构建，采集期间耗时不作基准）按分配字节与次数定位调用栈，区分短命对象、存活对象（live set）与大对象。然后治理——把与首帧无关的对象图延后并错峰、降低瞬时分配率（重复解析、大集合 map/filter 链、字符串与日志、未预估容量扩容）、给启动期缓存设容量与逐出边界。

边界：把工作移到后台线程不降低 GC 压力，进程内 heap 由线程共享。对象池只适合已测出高频构造且重置可控的对象，随意池化反而扩大 live set。

跨层边界：ART 与 GC 机制见 [ART 与 GC 机制](../../02-系统/02-进程启动与ART.md)。

**Q20: [learning] 启动首帧的可选布局应怎样选择 ViewStub 与 AsyncLayoutInflater？**

`ViewStub` 适合首帧大概率不出现的可选子树：不绘制、measure 为零，`inflate()` 或设为 VISIBLE 时被目标布局替换（目标布局不能以 `<merge>` 为根，替换后原 stub 已移除）。每次启动都立即 inflate 的场景它只改变时机。

`AsyncLayoutInflater` 的构造与 `inflate()` 在 UI 线程、View 在后台线程创建，要求父容器 `generateLayoutParams()` 与所有 View 构造可在后台线程安全执行（不能在构造里建 Handler 或依赖当前 Looper），不支持含 Fragment 的布局，失败会回 UI 线程重试。如果首帧必须等它完成，工作仍在关键路径上，TTID 未必缩短。

**Q21: [learning] 用户点击图标后看到的“启动画面”有哪些可能的实现，热启动会显示 Splash 吗？**

启动期间用户先看到的通常是系统创建的 starting surface，不一定是带品牌图标的 Splash。system_server 的 `ActivityRecord` 检查显示状态、主窗口是否已绘制、有无可用且兼容的 TaskSnapshot、任务与进程状态和主题，决定是否创建与类型，再交 WM Shell 绘制。可选类型包括 Splash Screen、纯色 Splash、legacy Splash（沿用旧主题行为）、TaskSnapshot（任务上次可见界面的快照）、windowless（直接挂到任务表面的实现）与 none。

AAOS13 已有 `STARTING_WINDOW_TYPE_SPLASH_SCREEN`/`SOLID_COLOR_SPLASH_SCREEN`/`LEGACY_SPLASH_SCREEN`/`SNAPSHOT`/`NONE` 常量（本地核对），windowless 为后续版本新增。选择依据启动条件：TaskSnapshot 常用于已有任务切回且快照兼容，Splash 常见于冷启动、新任务与 warm start。hot start（进程与目标 Activity 都在、只需带回前台）不会重复显示 Splash。

两个边界：Splash 由系统在 App 首帧前创建，App 不需要自己 inflate 一张启动页。App 主题只是输入之一，最终类型受任务、进程、snapshot 与系统策略影响，所以“点击后看见一张图”不能推断走了哪条路径，解释 Perfetto 前先确认启动类型与 starting window 类型。

跨层边界：SplashScreen 系统窗口行为见 [SplashScreen 系统窗口行为](../../02-系统/02-进程启动与ART.md)。

**Q22: [learning] AndroidX core-splashscreen 在不同系统版本上的能力边界是什么，starting theme 各属性控制什么？**

AndroidX core-splashscreen 的表现取决于设备 API 与所用库版本。按 AndroidX 官方 SplashScreen API 参考和 Android Developers 迁移指南核对，兼容范围分三档：

1. **API 21～22：**兼容主题可工作，但应用真正启动前不会显示兼容图标，只有背景。
2. **API 23～30：**模拟 Android 12 的静态 Splash 图标；不能期待 AVD 图标动画。
3. **API 31+：**委托平台 SplashScreen API，可使用系统 Splash 与平台退出交接。测试至少覆盖上述三个边界及产品目标 API。

starting theme 中只显式设置产品确实需要的属性，省略行为须按所用库与父主题确认：

1. **`windowSplashScreenBackground`：**控制单色背景。品牌色需要一致时显式指定不透明色并提供夜间资源；省略时 AndroidX 从父主题的背景属性取得颜色，平台默认 Splash 也可能使用单色 `windowBackground`，不能假定是期望的品牌色。
2. **`windowSplashScreenAnimatedIcon`：**控制中心图标。需要品牌图标时显式指定 drawable 并按 adaptive icon 安全区域留白；省略时 AndroidX 默认使用 launcher icon，API 21～22 在启动早期仍不显示图标。
3. **`windowSplashScreenAnimationDuration`：**只描述图标动画时长，不控制 Splash 停留。静态图标不必显式设置；动画图标在 Android 12 的迁移方案中需要声明时长，Android 13 起平台可从 AVD 推断。具体省略行为取决于图标类型和 API，不能把它当延长启动页的开关。
4. **`postSplashScreenTheme`：**指定 `installSplashScreen()` 后 Activity 使用的正常主题。迁移指南将其列为必填；省略时不能保证完成预期的主题切换，不能未经验证地假定会继承应用主题。若用它负责切换，就不要再用手动 `setTheme()` 做第二套切换。

底部品牌图不受官方设计规范推荐。库的稳定版本会变化，本文不以某个“当前最新版”推断设备行为，集成时固定依赖版本。

所有可能直接成为起始 Activity 的外部入口（launcher、deep link、通知冷启动）都要配 starting theme 并在 `super.onCreate()` 前调用 `installSplashScreen()`，只验证桌面图标会漏掉其余路径。

跨层边界：系统版本上的 SplashScreen 实现见 [系统版本上的 SplashScreen 实现](../../02-系统/02-进程启动与ART.md)。

**Q23: [learning] 自定义 Splash 退出动画必须做什么收尾，旧 windowBackground 与专用 SplashActivity 在 Android 12+ 的问题是什么？**

系统 Splash 是应用窗口绘制前的 starting surface，只改善过渡，不会减少应用初始化工作；单独创建 Splash Activity 还会多一次 Activity 生命周期、窗口创建与转场。注册 `setOnExitAnimationListener` 后回调在 UI 线程执行，动画结束的所有路径——正常结束、取消、Activity 销毁、系统动画缩放关闭导致立即结束——都必须调用 `provider.remove()`，否则 Splash View 持续覆盖应用。参数是 `SplashScreenViewProvider`，与 `ContentProvider` 无关。退出动画只改变画面交接：内容首帧必须已在 Splash 下方稳定，动画结束不等于内容可用，主线程仍有长任务时动画结束后照样掉帧。时长用设备实测决定，低端机、动画缩放关闭与“减少动态效果”的无障碍偏好下要有合理行为。

迁移两个旧方案：Android 11 及更早放在启动主题 `windowBackground` 里的 layer-list，在 Android 12+ 冷/温启动会被系统 Splash 替换、外观不再等同，应把颜色与图标转成 `Theme.SplashScreen` 属性、设置 `postSplashScreenTheme` 并删除两套启动视觉。

专用 SplashActivity 在 Android 12+ 会出现“系统 Splash + 自身页面”两段画面，还多一轮生命周期与跳转，路由应放进单 Activity 或直接启动目标 Activity（迁移期允许“保持 Splash、立即跳转并结束自己”，但路由必须同步、快速、无网络等待）。交接内容时优先显示有边界的本地缓存再异步刷新，骨架屏要贴近最终结构避免 layout shift。starting surface 首见时间、TTID、TTFD 是三个不同时点，Splash 显示得早不会自动缩短 TTID。



**Q24: [learning] Compose 的 setContent 到首帧经过哪些阶段，初始组合会执行哪些 composable？**

`ComponentActivity.setContent` 创建 `ComposeView` 作为公开宿主（内部组合创建时才创建/复用 `AndroidComposeView`），View 尚未 attach 时只保存 content，初始组合在 attach 或显式 `createComposition()` 时创建。窗口级 `Recomposer` 受 Lifecycle 驱动（STARTED 后 frame clock 提供帧、`ON_STOP` 暂停、`ON_DESTROY` 取消）。

初始组合执行“本轮会进入”的内容：没有上一轮结果可复用，进入的 group 都要执行，已进入 group 里的 `remember { ... }` calculation 也执行一次。条件分支未选中的内容不执行。Lazy layout 尚未被请求的 item 不会因为数据集合存在就全部执行——所以首帧成本没有“层数 × 数量”公式，它等于被进入的 composable 工作量、创建的布局/modifier/semantics 节点、业务计算，再加上应用变更、测量、布局与绘制的总和。

组合完成后 `AndroidComposeView` 仍是 `ViewRootImpl` 管理的 View 子树，还要经过 `onMeasure`/`onLayout`/draw、HWUI 与 RenderThread、SurfaceFlinger 合成才上屏——组合只是首帧中的一段，trace 显示组合很短而 I/O、文本测量或渲染很长时，删 composable 层级不解决问题。首屏 ready 用 `ReportDrawnWhen` 注册到 `FullyDrawnReporter`，合法空态也要能进入 Ready，否则 TTFD 永久缺失。

**Q25: [learning] Compose 自带的 Baseline Profile 覆盖什么，为什么 Class.forName() 预热不是替代品？**

Compose 随应用发布、不在 platform boot image 中，其发布物附带的 Baseline Profile 只覆盖 Compose 库代码，应用合并这些 library profile 后 ART 可提前编译库的规则路径，但不会自动覆盖应用自己的 composable、ViewModel、导航与数据准备路径。`androidx.compose:compose-bom` 只是版本清单，不含实现代码也不是 profile 载体。

所以应用仍要用 `BaselineProfileRule` 采集桌面启动、通知、deep link 等主要入口并让测试走到首屏可交互，Startup Profile 反映相同入口且只能由应用自己的启动测试贡献（库不能替宿主贡献）。`Class.forName()` 预热 Compose 类是反模式：它把类加载移到更早的主线程路径、扩大每次启动的必做集合，既不能替代 AOT 编译，也不能保证启动代码在 DEX 中相邻存放。Profile 只改变编译状态与布局，数据库查询、网络等待与图片解码照旧存在。收益必须用目标产物与设备测量，不要写“提升 10%～30%”这类固定承诺。

**Q26: [learning] Column、Lazy layout 与 SubcomposeLayout 怎么选，什么模式会让“首帧后立刻再来一帧”？**

选择依据内容规模：固定且数量少的内容用 `Column`/`Row`。数量大或未知时用 Lazy layout，避免一次组合并布局所有 item。Lazy 首屏注意：item 在异步内容到达前不要是 0 像素，否则一次 measure 会误判 viewport 能容纳大量 item、造成无效组合。为可重排数据提供稳定 `key`。异构列表提供合适 `contentType` 帮助复用组合结果。不要把大量元素塞进同一个 `item { ... }`（它们仍会作为一个单元一起组合和测量）。小型固定按钮组不应只为“懒加载”换成 `LazyRow`。

`SubcomposeLayout` 只用于子内容依赖父布局约束的场景（`LazyColumn`、`BoxWithConstraints` 是官方例举），普通 `Box` 即使用 `Modifier.align` 走的仍是常规 `Layout`。默认选它会把一部分组合移进布局阶段，常增加当前帧总成本。

“首帧后立刻再来一帧”来自阶段反馈：`onSizeChanged()`/`onGloballyPositioned()` 得到尺寸写入 `MutableState`，又在同一布局关系中把它读成 `padding`、`height` 或子节点位置——能在同一次测量中求解的父子关系应使用现有布局组件或自定义 `Layout`，自适应页面从当前 constraints 派生结构。边界：重组优化（稳定类型、Strong Skipping、延后状态读取）主要减少后续重复工作，不能免除首屏第一次必须进入的内容。`remember` 只缓存后续复用，它的 calculation 在初始组合中仍要执行。

**Q27: [learning] 体积治理要先固定哪四种口径？为什么“下载少 1 MB，安装空间未必同步少 1 MB”？**

四种口径分别回答不同问题：

1. **上传制品：**APK / AAB 本身的文件大小。
2. **设备交付集合：**固定 ABI、语言、密度与模块后，设备实际拿到哪些 split。
3. **安装占用：**已装 APK、提取的原生库、ART 编译产物与应用数据占用。
4. **运行时映射：**DEX、SO 与资源的文件页、私有脏页和共享页如何进入进程。下载减少不等于安装同步减少：未压缩条目让 APK 文件变大，却可能免去安装期提取并支持直接映射。`.vdex`/`.odex`/`.art` 是安装与运行期产物，占设备存储但不计入商店下载字节。磁盘文件大小也推不出 PSS。

APK 结构上要防误读：`classes*.dex` 保存字节码。`resources.arsc` 与 `res/` 是编译资源，`assets/` 按原始文件接口读取，静态缩减器不能仅凭代码判断 asset 是否仍被使用。`lib/<abi>/` 保存各 ABI 的 ELF。`META-INF/` 有 V1 签名产物不代表只用了 V1——V2/V3 签名位于 APK Signing Block。对比基线必须用同一发布变体、构建工具、签名流程和设备规格，每次只改一类变量，用 APK Analyzer 先按增长目录（DEX、资源还是 lib/）选择后续路径。

**Q28: [learning] “64K 限制”到底限制什么？Defined Methods 与 Referenced Methods 差在哪？**

限制的是单个 DEX 的 `method_ids` 引用表（65,536 项，`field_ids` 同级有 16 位上限）。计数包含应用代码、依赖和该 DEX 引用的 Android/Java 平台方法，不等于源码中声明的方法数。APK Analyzer 里 Defined Methods 只统计本 DEX 定义的方法，Referenced Methods 统计该 DEX 的方法 ID 表——定义在其他 DEX 或平台中的方法仍占当前 DEX 的引用条目，所以决定是否触发上限的是 Referenced。

65,536 解释了为什么需要 multidex，却不能充当体积预算：两个版本的引用数相同，方法体、字符串与调试信息差异仍可能让字节数相差很大。反之引用数下降也可能伴随 DEX 变大。索引区的增长常由依赖、生成代码和宽泛 keep 规则推动——即使方法体很短，一个方法仍会增加 method、type、proto、string 多处数据。

**Q29: [learning] R8 的 keep 规则为什么容易膨胀？怎么找到“是谁保留了这段代码”并安全放宽？**

R8 的三类收益（裁剪不可达代码、优化改写、缩短名称）都受 keep 配置约束：一条裸 `-keep` 同时阻止 shrinking、obfuscation 和 optimization。AGP 8.0 起 R8 Full Mode 已是默认，旧项目里的 `android.enableR8.fullMode=false` 兼容开关要删除才恢复全模式。规则膨胀的典型来源是包级 `-keep class com.example.** { *; }` 止崩后长期保留、`@Keep` 整类标记，以及依赖 AAR 携带的 consumer rules——“应用自己的 proguard-rules.pro 很干净”不能证明 keep 配置健康。

治理方法：规则只保护运行时协议真正需要的部分，先回答反射、JNI、序列化或 WebView bridge 访问的是类、成员、名称、签名还是注解。WebView bridge 已由静态代码创建时用 `-keepclassmembers,allowoptimization` 只保带注解的方法、允许优化方法体，而不是保留整个包。定位工具：`-printconfiguration` 输出合并配置，`-whyareyoukeeping` 追踪意外存活类（只用于本地诊断分支），配合产物中的 configuration.txt、seeds.txt、usage.txt 与 mapping.txt 归因。AGP 9.3 起的 R8 Configuration Analyzer（外部工具链口径）把最终配置量化成 Shrinking/Optimization/Obfuscation 三个分数并给出 Blast Radius 表，可先于完整构建定位宽规则。放宽前必须补动态入口测试、分批发布与线上崩溃监控。mapping.txt 随发布归档，否则线上混淆栈无法还原。

**Q30: [learning] minSdk ≥ 21 的应用还需要 multidex 兼容处理吗？DEX 个数多会拖慢启动吗？**

Android 5.0 / API 21 起 ART 原生加载 APK 内的 `classes2.dex` 等多个 DEX，minSdk ≥ 21 不需要 `androidx.multidex` 安装器，也不需要为类可见性维护旧版主 DEX 类清单——那是 Dalvik 时代为安装器在加载次级 DEX 前保证类可见的方案（minSdk ≤ 20 才需要，且 `MultiDex.install()` 完成前只能可靠访问主 DEX）。这个历史边界不应套到现代应用。

DEX 个数不是启动耗时公式：多 DEX 有文件头、索引与对齐等结构成本，但启动开销取决于启动路径触达的类与方法、它们的布局局部性、Baseline/Startup Profile 是否匹配当前二进制、有无可用 VDEX/OAT/App Image 以及存储速度与缺页。把 `classes3.dex` 合回 `classes2.dex` 不保证启动变快，为减少文件数而加 keep 或打乱布局可能更差。安装后的 `.vdex`/`.odex`/`.art` 占设备存储、不计入商店下载。Startup Profile 由 R8 调整 DEX 布局让启动类集中到首个 DEX（机制与 AGP 版本边界见 cpu-power 邻居文档），验证目标是启动类是否进入 `classes.dex` 与 TTID/TTFD，而不是某个单文件的大小。

**Q31: [learning] Native SO 的 strip 与节区分析怎么做？哪些字节删了会出问题？**

AGP 默认对发布库执行 strip：完整符号表与 DWARF 调试信息（`.debug_*`）移入独立符号制品（`SYMBOL_TABLE` 可还原函数名，`FULL` 还原到源文件与行号），strip 后的 `.so` 进包，两者必须来自同一次链接（重新链接会改变地址布局与 Build ID）。节区语义决定删什么安全：`.text`/`.rodata` 占文件字节且只读映射。`.data` 同时占文件与进程私有脏页。`.bss` 是 `SHT_NOBITS`，占运行内存但不占同量文件字节，`llvm-size` 的大 BSS 值不能当 APK 增长。`.dynsym`/`.dynstr` 与必要重定位是可运行 ELF 的一部分，`--strip-all` 也不能删。`.eh_frame`/`.ARM.exidx` 等栈展开元数据删除前必须用受控 Native 崩溃验证 tombstone、C++ 异常与 profiler 回溯仍工作。

比 strip 更有收益的是让不可达代码消失和缩小导出面：`-ffunction-sections`/`-fdata-sections` 加链接期 `--gc-sections` 删除不可达节区（这是链接期 GC，不是运行时内存回收）。`-fvisibility=hidden` 与 version script 控制符号可见性，JNI 库从 `JNI_OnLoad()` 调 `RegisterNatives()` 后常见公开入口只剩 `JNI_OnLoad`。LTO/ThinLTO 与 ICF 要保存 linker map、节区增量与性能数据评估，ICF 激进模式可能合并地址相同的函数，影响依赖函数地址唯一性的逻辑。多 AAR 同名同路径 `.so` 冲突时 `packaging.jniLibs.pickFirsts` 只选构建系统遇到的第一份——不比较 SHA-256、build ID 与 SONAME，只有在证明候选可互换后才能用。

**Q32: [learning] 安装期系统怎么为一个包选择 ABI？**

按 AAOS13 源码核对，`PackageAbiHelperImpl.derivePackageAbi()` 按包是否 multi-arch、设备支持的 ABI 顺序与是否提取原生库选择分支。需要提取时调用 `NativeLibraryHelper.copyNativeBinariesForSupportedAbi()`，其内部 `findSupportedAbi()` 选择设备 ABI 列表中排名最靠前的匹配项。`extractNativeLibs=false` 时仍选择并校验 ABI 但不复制 `.so`——未压缩且满足对齐的库可直接从 APK 映射，代价是 APK 可能因不压缩而变大，报告要同时记录下载量与安装占用。

**Q33: [learning] Android 15 的 16 KB 页设备上，Native 库要满足哪两层对齐？**

16 KB 是两层独立对齐：ELF 内每个 `PT_LOAD` 的 `p_align` 要支持 16 KB，且未压缩 `.so` 在 APK ZIP 中的起始偏移按 16 KB 对齐。NDK r28+ 默认生成对齐 ELF，r27 及以下要显式传 `-Wl,-z,max-page-size=16384` 与 `-Wl,-z,common-page-size=16384`，AGP 8.5.1+ 处理未压缩库的 ZIP 对齐。Google Play 要求面向 Android 15/API 35 及更高版本的 64 位应用支持 16 KB，2027-02-01 起不满足的应用更新无法发布（已与官方文档核对）。对齐可能增大文件（段间空隙与 ZIP 填充），增量由布局决定、没有固定百分比。

跨层边界：16 KB 页面设备的底层对齐要求见 [16 KB 页面设备的底层对齐要求](../../03-底层/02-内存回收与功耗.md)。

**Q34: [learning] Android 17 的 Safer Native DCL 对动态加载 .so 增加了什么要求？**

版本边界：Android 17 的 Safer Native DCL 要求目标 API 37 应用用 `System.load()` 加载前把文件设为只读、否则抛 `UnsatisfiedLinkError`（AAOS13 无此要求）。Android 17 还提供 fatal 兼容测试属性让不兼容立即中止，兼容路径只用于迁移、不能替代 Play 要求。

**Q35: [learning] 资源体积优化中，“删”与“换”分别要守住哪些边界？**

删的边界在引用图与限定符回退。资源缩减依赖代码缩减（只有被删除代码引用的资源才会被删）：safe mode 会从字符串常量推测动态引用而保守保留，strict mode 只信显式引用与 `tools:keep`，迁移要先记录 safe mode 额外保留的原因再逐个消除。`Resources.getIdentifier()`、拼接资源名、通知、App Widget、清单元数据与反射 R 字段都在静态引用图之外，`tools:discard` 强删运行时仍会访问的资源会导致 `Resources.NotFoundException`。限定符是运行时选择规则不是冗余：语言、密度、夜间、最小宽度与版本限定符删除某候选后系统会回退并可能产生缩放、布局或语言错误，裁剪要在对应配置设备上验证。语言过滤用 AGP 8.8 起的 `androidResources.localeFilters`（旧 `resourceConfigurations` 已弃用），它过滤依赖翻译但不会生成缺失译文，关闭语言拆分会增加首装下载、换来离线切换可靠。

换的边界在格式版本与解码成本：WebP 各模式 Android 8 / API 26 起支持。AVIF 自 Android 12 / API 31，minSdk 26 应用要保留 WebP/PNG 回退资源（如 `drawable-v31` 目录），且回退会增加 AAB 上传总量。VectorDrawable 适合图标与路径图形，不适合照片（pathData 膨胀与 inflate 成本）。JPEG/WebP/AVIF/MP3 等已压缩格式再套通用压缩收益有限，`noCompress` 换取随机访问与直接映射但下载字节增加。硬规则：已签名 APK 不能再重压或用第三方资源混淆工具改写条目，任何转换必须放在签名前的受支持构建阶段。9-patch 的拉伸区元数据不做普通格式替换。

**Q36: [learning] on-demand 动态特性模块的工程边界有哪些？为什么 base 不能引用 feature 的实现类？**

交付方式按行为分：install-time（默认、随安装、不减首装）、conditional（按设备特性、国家或最低 API 条件交付）、on-demand（运行时触发下载）、deferred install（后台尽力预取、无法跟踪进度）与 deferred uninstall（请求返回不代表文件已消失）。on-demand 流程经 `SplitInstallManager`：`startInstall()` 成功回调只返回会话 ID，必须等监听器报 `INSTALLED` 才能进入功能。`REQUIRES_USER_CONFIRMATION` 要走确认对话框。`FAILED`/`CANCELED` 保留基础功能并提供重试。监听器按页面或进程生命周期注销，进程重建后用 `installedModules` 与会话状态恢复，不能只依赖内存变量。

依赖方向是硬边界：feature 可以访问 base 的公共 API，base 在编译期不能引用 feature 实现，共享接口、错误类型与路由协议放 base 或独立 API 模块。feature 不重复声明签名、`versionCode` 与 `minifyEnabled`，附加 keep 规则构建时全量合并。`dist:title` 字符串放 base（模块下载前系统也要读取）。`dist:fusing=true` 决定模块能否进入需要融合的 universal APK。刚装完的一段时间内，平台可能无法应用 feature 新增的 manifest 组件、通知等系统界面也可能访问不到 feature 资源，通知图标与故障页应放 base。已安装 feature 随应用更新由 Play 管理，不要自建独立版本协议。

**Q37: [learning] 非 Play 渠道怎么替代 AAB 能力？为什么“运行时下载 DEX/SO”不能当体积方案？**

按渠道能力逐项降级：支持 AAB 的渠道按其文档上传验证，不能假设分包、签名或动态交付与 Google Play 相同。只收单 APK 的渠道构建 universal APK 或 per-ABI APK——`bundletool --mode=universal` 只融合 manifest 中 `dist:fusing=true` 的模块，多 APK 的 `versionCode`、签名与升级兼容要自管。受控安装器必须一次提交匹配设备的 base 与全部必需 split 并处理失败回滚。平台侧校验是硬约束：安装会话要求每个 split name 唯一、包名/版本/签名一致，缺必需 split 返回 `INSTALL_FAILED_MISSING_SPLIT`（机制按 AAOS13 的 `PackageInstallerSession` 口径核对），缺 split 的侧载在 Android 10 及以上设备会失败。

大资源走自建下载或 PAD：资源清单含版本、长度、哈希、签名与最低应用版本，先验证再原子发布。PAD 的 asset pack 不允许包含可执行代码，fast-follow/on-demand 以归档展开、路径可能跨会话移动、内容视为只读（补丁依赖完整性）。Google Play 的 Device and Network Abuse 政策禁止从 Play 之外下载可执行代码（WebView 或解释器中运行、仅间接访问 API 的 JS 除外），所以动态 DEX/JAR/`.so` 下载不是合规的体积方案——减少首次下载的正确路径是按需模块、按 ABI 拆分或删除代码。

**Q38: [learning] debuggable=false 的 release 包会自动删除 Log.d() 吗？R8 按级别删除日志怎么配置？**

不会自动删除。`debuggable=false` 只让 liblog 按 tag 属性和默认优先级决定是否写入，调用点、参数求值和 JNI 入口仍然发生。要构建期删除，当前 R8 文档提供 `-maximumremovedandroidloglevel`，按级别删除 `Log.*` 与 `Log.isLoggable()` 调用：

```proguard
# INFO 对应数值 4；删除 INFO 及以下级别。
-maximumremovedandroidloglevel 4
```

级别映射为 VERBOSE=2、DEBUG=3、INFO=4、WARNING=5、ERROR=6、ASSERT=7。可选的类规范可以把规则限定到特定类。多条规则命中同一方法时 R8 取最小级别。

边界与做法：该规则近年才进入正式文档，使用前确认项目 R8/AGP 版本支持，规则只进 release 变体，并用反编译或 mapping 输出验证结果。`-assumenosideeffects` 属于强制优化假设，参数带可观察副作用时不保证连带删除，构建期删除应配合调用前的条件判断。隐私上，`READ_LOGS` 自 Android 4.1 起是特权权限，但预装特权组件与 bugreport 仍可能读到日志——令牌、密码、会话密钥应完全不入日志（掩码只适合允许展示部分信息的字段），异常对象也要审查，服务端响应和 URI 查询参数可能经异常文本进入日志。

**Q39: [learning] 线上冷启动 SLA 应该统计哪些启动？ApplicationStartInfo 与 ApplicationExitInfo 怎么关联？**

SLA 只纳入完成记录中的 `START_TYPE_COLD` 且组件为 Activity 的用户显式启动（reason 为 `LAUNCHER` 或 `LAUNCHER_RECENTS`）。warm/hot 分桶统计、不与 cold 聚合，后台 Service/Broadcast/Provider 拉起属于后台拉起健康度，不进首页冷启动指标。`START_ACTIVITY` 的外部跳转由业务入口场景细分。

与前一次退出的关联要保留两份原始记录、再生成带置信度的关联边：exit 的 timestamp 是 epoch 毫秒、start 的时间戳是单调纳秒，两次的 PID 通常不同，改时间、重启与包更新都会影响匹配。候选匹配用包 UID、进程名、先后顺序、boot session 与业务 session，时间窗口由线上数据校准、不是平台保证。`wasForceStopped()` 是本次启动记录上的直接信号，优先于从模糊 exit reason 推断，用于决定是否重新注册被清理的 alarm/job。`REASON_CRASH` 后短时间 cold start 指向崩溃循环，`REASON_PACKAGE_UPDATED` 对应新版本首启，用户请求终止不计为 crash 恢复。CI 的 Macrobenchmark `StartupMode.COLD/WARM/HOT` 与系统的 `START_TYPE_*` 是两套枚举，不要按整数值对应——CI 管可重复回归，线上分位数管用户分布，Android 17 的 `COLD_START` 触发式 trace 只做低频抽样诊断。

跨层边界：ApplicationStartInfo 工具/API 细节见 [ApplicationStartInfo 工具/API 细节](../../04-工具/29-application-start-info/01-启动历史.md)。

**Q40: [learning] 启动各阶段耗时为什么要用单调时钟相减，uptimeNanos、elapsedRealtimeNanos、nanoTime、currentTimeMillis 各适合什么？**

启动耗时要靠“终点减起点”，时钟必须只向前推进、不受用户改时、网络校时和时区影响。`System.currentTimeMillis()` 这类墙钟只适合记录事件发生的对齐时间（发布、灰度），相减得到的“耗时”可能被校时污染。各时钟的分工：

1. **`SystemClock.uptimeNanos()`：**不计深度休眠，适合进程内 CPU/主线程工作区间。平台启动记录（Android 15+）的各节点也用它，因此自定义点经 `addStartInfoTimestamp()` 写入时必须用同一时基。
2. **`SystemClock.elapsedRealtimeNanos()`：**计入深度休眠、以开机为基准，适合同一台设备本次启动会话内的阶段耗时。
3. **`System.nanoTime()`：**只保证用于计算同一运行环境内的时间差，不能依赖其绝对起点。

边界：不要把自有 `elapsedRealtimeNanos` 与平台记录里的 `uptimeNanos` 节点相减。一个事件可同时存墙钟（对齐发布）与单调耗时（阶段计算），服务端不跨设备相减单调时钟。

**Q41: [learning] 线上启动分位数应该怎么聚合，“TTFD 变好但完成率下降”说明什么？**

启动耗时呈右偏长尾，均值会被极慢样本拉高、也会被大量热启动稀释。分位数必须从同一 cohort（冷/温/热、入口、安装状态、版本、设备档位一致的样本组）的原始数据或可合并分布摘要计算，不能先算每台设备或每天的分位数再平均——平均分位数不是全量分位数。样本至少按冷/温/热、首屏路由与入口、首装/升级/普通启动、版本与实验组、Android 版本与设备档位、主/远程进程分组，Profile 编译状态可靠可得时单独分组。

“TTFD 数值变好但完成率下降”是幸存者偏差：启动期间退出、崩溃、ANR、进程被杀或长期 loading 的会话没有 TTFD，排除后曲线“变好”，慢到无法完成的会话恰恰被隐藏，所以每个窗口要同时展示请求会话数、TTID/TTFD 有效样本数与完成率、超时数、首屏前崩溃与退出。回归门禁应同时满足：同 cohort 样本量达标、P90 绝对增量超产品预算、相对增量超历史噪声带、置信区间不跨“无影响”边界、连续两个窗口成立。慢样本高采样的诊断数据不能与告警数据直接混算分位数，合并须按采样概率加权。

Play Vitals 的 excessive 启动阈值（冷 5 秒、温 2 秒、热 1.5 秒，官方口径转写）是外部告警边界，内部预算应按入口与设备档位设得更严格。线下对照用 Macrobenchmark 固定 `CompilationMode` 与启动模式，同时记录每轮的启动类型、编译状态与原始样本。

**Q42: [learning] 冷启动同步 Binder 等待怎样拆分到服务端与客户端？**

只对已经配对的同步事务分段，四段都是墙钟口径而非 CPU 时间：

1. **客户端总等待：**`client_dur`，从调用到收到 reply。
2. **请求派发：**`server_ts - client_ts`，包含驱动传递、服务端队列和线程重新获 CPU，不能直接命名为“线程池排队”。
3. **服务端处理：**`server_dur`，从收到事务到发出 reply；其中可能含锁、I/O、嵌套 Binder 与调度等待。
4. **回复残差：**从 `client_dur` 扣除请求派发和服务端处理，包含 reply 传递及客户端恢复执行。

嵌套事务的区间可能互相包含，直接求和会重复计时。AAOS13 的 SystemServer 通过 `BinderInternal.setMaxThreads(31)` 设置 Binder 线程上限 31，普通 libbinder 进程默认上限 15；上限不是实时可用 worker 数。确认拥塞须看到多客户端长派发间隔、服务端 worker 集中阻塞和负载变化后的对应恢复。Binder 优先级继承可缓解调度反转，不能解决长锁、I/O 或服务端容量不足；材料 r6 内核语境可用 `binder_set_priority` tracepoint 验证该路径。

**Q43: [learning] 启动优化为什么要先删任务，再考虑并发？**

启动耗时由到达 TTID 或 TTFD 终点的最长依赖链决定，不是所有初始化耗时之和。按同一测量协议推进：

1. 固定启动类型、TTID/TTFD 口径、构建、设备与编译状态，保存基线。
2. 画出关键路径，删除无效工作，推迟当前入口不需要的工作。
3. 缩短仍在关键路径上的任务，只把相互独立且值得并发的任务交给有界执行器。
4. 用相同条件复测，并检查完整可用时间、功能与功耗等副作用。

主线程提交后台任务后立刻 await、join 或等锁，依赖链没有缩短，还增加同步开销。后台线程占满性能核、触发缺页或持有主线程需要的锁也会使 TTID 变差。每项初始化应有 owner、trigger、deadline、依赖、线程亲和、失败策略与幂等契约；并发上限从目标设备 Perfetto 的调度、频率和 I/O 证据确定，不能直接按核心数创建无界线程池。

**Q44: [learning] ContentProvider 自动初始化的成本从哪里来，“Provider 数量少”能直接换算成启动快吗？**

Provider 的成本不只是 `onCreate()`。

AAOS13 的链路（已按源码核对）：`handleBindApplication()` 先创建 Application，再 `installContentProviders()` 对每个 Provider 经 `AppComponentFactory.instantiateProvider()` 实例化、`ContentProvider.attachInfo()` 读取权限/authorities/exported 并落到字段、在主线程调用 `onCreate()`，最后把本批 holder 汇总后一次调用 `publishContentProviders()` 发布给 system_server——是批量一次发布，不是每个 Provider 单独一次 Binder 调用。

成本分四层看：组件固定成本（类加载、构造、`attachInfo`、authority 注册）、`onCreate()` 负载（文件、数据库、反射、SDK 初始化、native 库加载）、资源竞争（它创建的后台线程与首帧争 CPU/I/O/锁）、进程成本（远端 Provider 触发承载进程启动与发布）。常见误判：`onCreate()` 很快不代表它创建的后台线程不会与首帧争资源。删除一个 Provider 后 TTID 下降，也可能是其业务初始化一起被删。看到 Provider 类不代表全部成本归属框架。Provider 数量只能作审计入口，不能换算毫秒。

测量要用自有 Provider 的稳定 trace 切片、第三方 Provider 的合并 Manifest + Perfetto 组合证据，以及唯一差异为是否保留自动入口的 release A/B。

**Q45: [learning] android:initOrder 和 Manifest 书写顺序能表达依赖吗，边界在哪？**

`android:initOrder` 只能在同一进程内声明 Provider 的相对实例化顺序（数值高的先初始化），Manifest 中元素的书写顺序不是依赖契约。它只能表达静态先后，不能让 `onCreate()` 异步、不能表达完成结果/失败/降级、不能解决跨进程依赖、也不能缩短各 Provider 自身的工作——所以它适合“谁先装配”这类弱约束，需要完整任务依赖时应改用 App Startup 的同步依赖图或显式任务框架。改动顺序前先核对合并结果：源码 Manifest 不是安装包里的最终结果，依赖库、build type、product flavor 与 placeholder 都可能改变组件，AGP 的合并决策报告在模块 `build/outputs/logs/manifest-merger-<variant>-report.txt`，要按准备发布的每个构建变体检查，不能只看 debug。

**Q46: [learning] SDK Runtime 退场后，为什么不能把它当作广告 SDK 的启动隔离方案？**

新项目不能再以 SDK Runtime 为启动隔离前提。Google 的 Privacy Sandbox 状态公告已将 SDK Runtime 列为退场技术；Android 17（API 37）的公开 API 文档也将 `SdkSandboxManager` 等类型标为 deprecated。Android 13 虽有管理类和状态查询，但还没有平台 `loadSdk()`，因此不能仅凭 API 符号存在就设计隔离进程中的广告初始化。

启动治理应以目标构建的实际 SDK 交付形态为准：确认最终合并 Manifest 中的 Provider、App Startup initializer 与所属进程，再测量其在首帧前执行的工作。历史 Android 14–16 产品若仍使用 SDK Runtime，应按设备的 Ad Services 扩展与服务能力维护降级路径；不能把该历史能力推断为新项目的可用方案。AAOS13 本地树不含对应模块源码，版本状态依据是 Google Privacy Sandbox 状态公告与 Android 17 SDK API 文档，而非本地源码。

**Q47: [learning] Baseline Profile、Startup Profile、Cloud Profile 与本地运行时 profile 各由谁生产、被谁消费？**

四类 profile 的生产者、消费方与验证方法不同：

1. **Baseline Profile：**应用或库作者在 CI 生成，随 APK/AAB 交付，供 Android 7（API 24）及以上的 ART 做预先编译；核对安装与实际编译状态。
2. **Startup Profile：**由应用启动场景贡献，构建期交给 D8/R8 调整 DEX 布局，不产生独立的设备端 ART 编译状态；核对构建产物的启动类布局。
3. **Cloud Profile：**Google Play 聚合真实用户数据后分发（API 28+，需足够样本和聚合时间），补充未覆盖的热路径；核对安装来源与设备端实际编译状态。
4. **本地运行时 profile：**设备上的 ART/JIT 随使用积累，指导该设备后续的 `speed-profile` 编译；核对目标设备的实际 filter。

库可随 AAR 贡献 Baseline Profile，构建时合并并按 release 混淆结果重写，但不能替宿主贡献 Startup Profile。两类规则可来自同一生成脚本：启动场景设 `includeInStartupProfile = true`，非启动场景保持 `false`，避免扩大启动 DEX 布局范围。

Startup Profile 的 DEX layout optimization 从 AGP 8.1 起可用；AGP 8.1–8.2 需在 Baseline Profile 配置中显式启用，AGP 8.3 起默认启用。功能可用与默认开启是两个版本门槛。release 构建还需启用 R8、minification 与完整优化，启动场景通过 `includeInStartupProfile = true` 纳入 profile。固定并记录 AGP、Macrobenchmark 与 ProfileInstaller 版本，升级工具链后重新生成和测量。

**Q48: [learning] 竞品包体积对比前为什么要先选定“包”的对象？哪些数字不能混用？**

“包有多大”至少对应四种对象：

1. AAB（上传商店的发布包）；
2. 单个 APK；
3. 某设备实际收到的 base + split APK 集合；
4. 压缩下载估算。

只拿竞品的 `base.apk` 与自家 universal APK 比较没有意义。横向对比要先收集目标设备完整 split 集合，按相同 ABI、density、language 和动态模块计算，取不到完整集合时写明缺少的 split。

两种大小口径不能混用：raw file size（文件本身大小）与 download size（传输压缩后的估算），`apkanalyzer apk file-size` 与 `apk download-size` 分别读取，后者是估算值、不等于 Play Console 的交付统计。分类检查按维度进行：DEX 大小受功能量、依赖、编译器与 R8 配置影响，不能从 DEX 较大断言代码质量差。native 库按 ABI 和压缩状态拆分（AAB 通常只向设备发送匹配 ABI，universal APK 可能含多套 .so），并检查符号剥离、页对齐与重复库。资源与 `resources.arsc` 分开看密度和语言变体。assets 里的离线数据、模型和预置媒体，若走 Play Asset Delivery 或运行时下载，要另记“首装下载”与“首次使用追加下载”。位图改矢量图可能减小文件也可能增加运行时栅格化成本，要结合场景判断。

**Q49: [learning] 为什么“Android 17 上发生”不足以描述性能问题？版本、交付路径与 target SDK 要怎样拆开记录？**

同一个 APK 在两个系统版本上可能走进不同的调度、进程管理与运行时路径，性能记录至少要包含四条独立变量：

1. 设备系统版本；
2. `targetSdkVersion`；
3. Mainline 模块版本；
4. 内核版本。

target SDK 决定一部分兼容开关的启用。运行在新系统上的所有应用变更则与 target 无关，例如 Android 14 的缓存进程资源管理与 Android 17 部分设备的应用内存限制（命中时 ApplicationExitInfo 的 description 含 MemoryLimiter:AnonSwap）。

大版本也不是唯一版本轴，交付路径决定覆盖与回滚：framework 走整机 OTA。Mainline 模块走 APEX 独立更新，ART 可单独升级，同大版本不保证 ART 构建相同。内核走 boot/vendor_boot，Android 17 官方兼容矩阵包含多条 GKI 分支（材料注明 android13-5.10 从 QPR1 起不再受支持），看到 Android 17 不能反推内核是 6.18。vendor HAL 走厂商分区。应用编译输入走 APK/DM/Profile。

做法：跨版本实验把 OS、target、Mainline、kernel 与产品配置作为独立变量记录，固定 APK、数据集、温度与电源条件。能用 compat change 或 feature flag 在同一设备做 A/B 时优先成对比较。报告 P50/P95 与样本数，不把官方公开的内部百分比（如 DeliQueue 的 missed frames 下降 4%）当作业务目标。
