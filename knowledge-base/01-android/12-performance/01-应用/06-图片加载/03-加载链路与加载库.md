# 加载链路与加载库

> 学习资料。收应用侧图片加载链路的性能题目：请求发起与可见性验收、取图（内存/磁盘/网络缓存）、列表与大图长图场景的加载治理和测量。机制按 AAOS13（Android 13）本地源码核对并逐题标注，不在本地树的组件按源材料（Android 17 锚点）转写并标注版本差异。边界：渲染合成与帧显示链路归 [界面渲染与交互响应](../02-渲染/01-渲染与响应.md) 与 [04-graphics](../../../04-graphics/)。Q 序列即结构，供 atlas 同源直读。

**Q1: [learning] 一张网络图片从发起到上屏要经过哪些阶段，为什么“图片库加载成功”的回调不能当作图片已可见的验收结论？**

回调成功只说明结果已经交给显示目标（ImageView 或 Composable），从交付到用户看见还隔着 View 树更新、RenderThread 采样与系统合成。完整阶段是：获取压缩数据（网络或磁盘）→ 查找各级缓存 → 解码（尺寸决策、采样、缩放、变换）→ 结果交给显示目标 → 宿主 View 更新 DisplayList（记录待执行绘制命令的显示列表）→ RenderThread 通过 HWUI 采样 Bitmap 并提交窗口缓冲区 → SurfaceFlinger 与 HWC 合成上屏。

首图慢要按现象分四类归因：解码时间片很长，查工作线程的 I/O 与编解码器。UI 回调或 View 树遍历很长，查设置 Drawable 引起的布局变化与主线程变换。UI 按时但 RenderThread 首次绘制变长，查软件 Bitmap 上传与图形分配。应用帧已提交但上屏仍晚，查 FrameTimeline、BLAST 与 SurfaceFlinger 侧。四类要按同一请求身份、同一 FrameTimeline 关联，单看图片库事件无法判断图片何时可见。

**Q2: [learning] 为什么 2560×1440 的图在 1280×720 的控件里用 Glide 加载，解码内存和原生 1280×720 的图一样大？**

因为 Glide 默认不按源图原始分辨率解码，而是按显示它的 View 尺寸采样解码：2560×1440 的源图要放进 1280×720 的全屏控件，Glide 自动选择 inSampleSize 为 2，直接解出一张 1280×720 的 Bitmap——内存从 14.7MB 变为 3.6MB，恰好等于一张原生 1280×720 的图。不是先解出 14.7MB 再缩小，而是从一开始就只分配目标大小的内存。

1. **三步决策：**

    1. 取目标 ImageView 的实测布局尺寸（像素）。
    2. 按“解码结果不小于 View 尺寸且越贴近越好、步长取 2 的整数次幂”选采样倍数（2560 除以 1280 正好为 2）。
    3. 把采样参数交给底层解码器，产出的 Bitmap 本身就是 1280×720。

2. **为什么没有画质代价：**2560×1440 缩到 1280×720 与 GPU 把全尺寸位图画到屏上做的是同一运算。屏幕只有 1280×720 个点要喂，两条路结果一致。设计预留的两倍图，其高分辨率价值保留在文件里，将来换高分屏可直接受益。
3. **什么时候这个机制会失灵：**以下情况会按原图或近似尺寸解码：

    1. 显式 override 指定 Target.SIZE_ORIGINAL：按 2560×1440 全量解码。
    2. 绕过 Glide 直接用 BitmapFactory 解码：无人告知目标尺寸，全量进内存。
    3. 源图与 View 尺寸不是 2 的整数次幂：取不小于目标的最近采样，结果略大于 View 尺寸（面积上限约 2 倍）。
4. **剩余代价在哪：**内存被按尺寸采样保住后，两倍图剩下的代价是 APK 里多背的文件体积与首次解码多读多算的 I/O 和 CPU。优化方向是换有损 WebP 或让设计出 1 倍图，而不是继续压内存。
