# 图片格式与体积

> 学习资料。收应用侧图片加载链路的性能题目：图片格式、分辨率与文件体积。机制按 AAOS13（Android 13）本地源码核对并逐题标注，不在本地树的组件按源材料（Android 17 锚点）转写并标注版本差异。Q 序列即结构，供 atlas 同源直读。

**Q1: [learning] 图片大小与分辨率是什么关系，一定同增同减吗？**

不一定。图片像素尺寸、文件体积、屏幕显示尺寸是三个独立变量，Android 的 dp、密度桶、缩放与按需采样体系本质上就是把它们解耦。只有“无损格式 + 显示尺寸固定 + 密度升高”三者同时成立时才同增同减。

1. **三个变量各由什么决定：**

    1. 图片像素尺寸（分辨率）：编码时写死，存在文件里。
    2. 文件体积：像素尺寸乘上由内容决定的压缩率。
    3. 屏幕显示尺寸：由 View 的布局参数（ImageView 宽高加 ScaleType）决定，与图片自身无关。

2. **显示尺寸与分辨率脱钩：**48dp 的 ImageView 里放 4000×3000 的照片，显示仍是 48dp，但解码内存按原图算。反过来，32×32 的图标也能拉伸铺满全屏，只是变糊。分辨率只决定清晰度上限，不决定显示大小。
3. **车机实例：**1024×720 的屏配 2048×1440 的图（像素恰为两倍），不同贴法结果不同：

    1. 全屏显示：图的像素是屏幕点的 4 倍，多出的像素在这块屏上没有对应点可显示，只能被压掉，但解码内存仍按 2048×1440 计。
    2. ImageView 缩小到 200×200：显示变小，解码内存一分不少——除非用 Glide、Coil 这类库按控件尺寸提前采样。
    3. 换 1024×720 的图：1:1 显示，不浪费。
    4. 换 512×360 的图：全屏显示会糊，屏幕点找不到自己的颜色，只能取邻近色猜测。

4. **唯一会同增同减的因果链：**显示尺寸固定、清晰度要求不变、格式无损时，屏幕像素翻倍必须让图片像素跟着翻倍，体积随之上涨，这就是设计按两倍屏预留切图的由来。换成有损 WebP 或 Vector 后这条链也会断。
5. **判断规则：**显示多大由布局说了算，清不清楚看图片像素够不够屏幕的点用，占多少内存按图片自身的像素算——三本账分开记。

**Q2: [learning] 同样分辨率的 PNG，为什么文件大小会差几倍？**

因为 PNG 无损只保证解压后逐位还原、一个像素不丢，不保证文件一样大。压缩前的原始数据量由分辨率与像素格式唯一决定（宽 × 高 × 每像素字节数），文件大小等于原始数据量除以压缩率，而压缩率由图片内容决定。“同一张图缩放时体积约正比于面积”只在缩放这一种场景成立。

1. **压缩前的账是固定的：**同一分辨率的 RGBA PNG，压缩前数据完全一致：1280×720 × 4 字节 = 3600KB，每张都相同。
2. **压缩率由内容决定：**某车机项目的 drawable 资源目录实测，两张同为 1280×720 的图，一张大面积接近纯黑的背景压到 391KB，一张满幅照片压到 1583KB，相差 4 倍。另测一个 36×36 的纯色图标，可压到 0.2KB，每像素摊 0.2 字节，而照片每像素摊 1.76 字节。
3. **PNG 压缩做的事（DEFLATE）：**DEFLATE 是 1991 年定义、ZIP 的核心，gzip、zlib 与 PNG 共用的通用无损压缩算法，分两步。第一步 LZ77 扫描重复字节串，把再次出现的串替换成回指引用，大片纯色因此几乎不占空间。第二步 Huffman 编码按出现频率分配码长，高频符号用短码。无损的含义是解压后与原始数据逐位相同，而照片像素近乎随机、找不到重复串，所以 PNG 压不动照片。
4. **选型结论：**纯色图标与大面积平色底适合 PNG。照片、噪点纹理应换 JPEG 或有损 WebP（后者还支持透明），单张可缩小数倍到近十倍。分辨率只决定压缩前的账，压缩后的差异来自内容重复度。

**Q3: [learning] 怎样判断一张图是不是 RGBA？为什么文件里不是 RGBA 也不代表解码后省内存？**

判断看文件头的颜色类型即可，但“文件里存了几个通道”与“解码后占多少内存”是两回事：BitmapFactory 默认无视源文件实际通道，一律解成 ARGB_8888（4 字节每像素），不透明的 RGB 图也照样占 4 字节每像素，除非显式指定更省的解码格式。

1. **命令行判别：**file 命令的输出直接给出颜色类型，如 `8-bit/color RGBA` 表示每通道 8 位、四通道。其他常见值包括 RGB（无透明）、grayscale（灰度）与 colormap 或 palette（索引色）。
2. **原理：**PNG 文件头 IHDR 块明文记录这些信息，宽高在第 16 至 24 字节，第 25 字节是颜色类型（6 为 RGBA、2 为 RGB、3 为索引色）。用 Pillow 时 Image.open 后的 mode 属性返回 RGBA、RGB、P 等。
3. **Android 的坑：**解码内存按解码配置算而不是按文件格式：默认 ARGB_8888 下 RGB、灰度、索引色源文件都被解成 4 字节每像素。要省内存必须显式设置解码格式（如 RGB_565）或改走其他途径，不能靠“文件本身不带透明”推断。

**Q4: [learning] JPG、PNG、GIF、SVG 分别是什么，有什么区别？**

JPG、PNG、GIF 是位图格式，把像素阵列按各自的算法压进文件。SVG 是矢量格式，用文本描述图形，不含像素。选型先看三点：能不能接受有损压缩、要不要透明与动画、要不要缩放不失真。

1. **JPG（JPEG，Joint Photographic Experts Group）：**有损压缩位图。编码时把画面分块做频域变换，丢弃人眼不敏感的高频细节来换体积，照片可以压得比 PNG 小很多。不支持透明与动画，反复保存会累积画质损失，文字、线条与纯色边缘尤其容易出现压缩噪点。
2. **PNG（Portable Network Graphics）：**无损压缩位图，压缩算法是 DEFLATE（ZIP、gzip 也用这个算法），解压后逐位还原、一个像素不丢，支持完整的 alpha 透明。适合图标、UI 元素、截图与带透明的图。照片在 PNG 下体积通常远大于 JPG，平色图形则能压得很小。
3. **GIF（Graphics Interchange Format）：**索引色位图，每帧最多 256 色，用 LZW（Lempel-Ziv-Welch）做无损压缩，支持逐帧动画与 1 位透明（像素要么全透明要么不透明）。颜色多的照片量化到 256 色时会严重失色，因此只适合颜色少的简单动图。
4. **SVG（Scalable Vector Graphics）：**矢量格式，用 XML（Extensible Markup Language）文本描述路径、形状与填充，按目标尺寸栅格化后绘制，缩放不失真，同设计下文件通常远小于位图。Android 平台不直接解码 SVG（AAOS13 的 ImageDecoder 支持列表里没有它），工程上要先把 SVG 转成 VectorDrawable，后者只覆盖一部分 SVG 能力。

5. **选型：**

    1. **照片与复杂渐变**：JPG。
    2. **图标、UI 元素、截图与带透明的图**：PNG。
    3. **颜色少的简单动图**：GIF。
    4. **需要任意缩放不失真的图形**：SVG。
