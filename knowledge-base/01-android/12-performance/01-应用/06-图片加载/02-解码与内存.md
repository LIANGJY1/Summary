# 图片解码与内存

> 学习资料。收应用侧图片加载链路的性能题目：解码与降采样（inSampleSize、区域解码）、Bitmap 内存与复用。机制按 AAOS13（Android 13）本地源码核对并逐题标注，不在本地树的组件按源材料（Android 17 锚点）转写并标注版本差异。边界：Bitmap 与图形内存的通用机制归 [06-memory-storage](../../../06-memory-storage/)。Q 序列即结构，供 atlas 同源直读。

**Q1: [learning] 4000 × 3000 的 ARGB_8888 图片解码后占多少像素内存？为什么压缩文件体积不能代表解码后内存，Bitmap 像素数据在各版本存在哪里？**

按像素算 4000 × 3000 × 4 = 48,000,000 bytes ≈ 45.8 MiB。显示目标 1000 × 750 时同配置约 2.86 MiB，像素数量相差 16 倍。压缩文件体积只影响下载与磁盘占用，解码后内存由输出像素尺寸和每像素字节数决定，所以“文件小”不等于“内存小”。

`width × height × 4` 只是下限：行跨度（row stride，相邻两行像素起始位置的字节差）的对齐、色彩配置、增益图与编解码中间缓冲都会增加运行时占用。存储位置按版本演进（官方文档口径，转写）：Android 2.3.3 及以下在原生内存，3.0 至 7.1 计入 Dalvik/ART 托管堆，8.0 / API 26 起回到原生堆——AAOS13 源码核对 `Bitmap` Java 对象经 `NativeAllocationRegistry` 登记原生分配，`getAllocationByteCount()` 返回当前底层分配空间，被复用过的 Bitmap 可能出现它大于 `getByteCount()`。`Config.HARDWARE` 的像素在图形内存而非原生堆。

**Q2: [learning] 用 BitmapFactory 把大文件解码到目标显示尺寸时，为什么要先 inJustDecodeBounds 读边界再按 2 的幂设置 inSampleSize？inSampleSize 传 3 会发生什么？**

直接解码会按原图尺寸分配像素内存。两阶段做法把"只读文件头拿到 `outWidth`/`outHeight`（不分配像素）“与”真正解码"分开，中间选出不超过目标尺寸的最大 2 的幂作为采样值。AAOS13 源码（`BitmapFactory.java`）核对：`inSampleSize <= 1` 按 1 处理，非 2 的幂向下取整到最近的 2 的幂——传 3 等效于 2，所以循环里只翻倍即可。

```kotlin
val bounds = BitmapFactory.Options().apply { inJustDecodeBounds = true }
BitmapFactory.decodeFile(path, bounds)   // 只解析头信息
var sampleSize = 1
while (bounds.outWidth / (sampleSize * 2) >= targetWidth &&
       bounds.outHeight / (sampleSize * 2) >= targetHeight) {
    sampleSize *= 2
}
```

`inSampleSize` 只做粗粒度采样，结果与显示目标仍是近似尺寸，图片库还会做精确缩放。解码资源文件时还要考虑 `inDensity`/`inTargetDensity`。若走像素复用（`inBitmap`），AAOS13 源码核对候选必须可变、未回收，且 `Config.HARDWARE` 被直接拒绝。API 19 起复用条件放宽为"新结果字节数不超过候选 `getAllocationByteCount()`"，普通业务应交给图片库的资源池而不是手写池。

**Q3: [learning] ImageDecoder 的 ALLOCATOR_DEFAULT、SOFTWARE、SHARED_MEMORY、HARDWARE 四种分配器怎么选？为什么“默认一定返回 HARDWARE”是错的？**

选择依据是结果怎么被消费：`ALLOCATOR_DEFAULT` 通常尝试 Hardware Bitmap（像素在图形内存、只可上屏），小图或与硬件分配不兼容时可回退软件结果。`ALLOCATOR_SOFTWARE` 给需要 `getPixel()`、软件 Canvas 或业务后处理的场景。`ALLOCATOR_SHARED_MEMORY` 用于跨进程共享像素。`ALLOCATOR_HARDWARE` 强制 HARDWARE，与 `setMutableRequired(true)` 冲突时抛异常。AAOS13 源码核对四个常量与该语义均存在，所以业务必须读返回值的 `config`，不能把默认策略当固定契约。

`ImageDecoder.decodeBitmap()` 是同步调用且标注 `@WorkerThread`，`OnHeaderDecodedListener` 在调用线程、方法返回之前执行，可以配置 `setTargetSize()`/`setTargetSampleSize()`，但它不是异步通知，不会把解码移出调用线程。AAOS13 javadoc 同时明确：`setCrop()` 只是裁剪解码缩放后的输出，不替代 `BitmapRegionDecoder.decodeRegion()`。`ImageDecoder` 也没有把现有 Bitmap 设为解码目标的公开入口（无 `inBitmap` 等价物），从 BitmapFactory 迁移时原有的“解码目标复用”收益要重新评估。

**Q4: [learning] Hardware Bitmap 是“由 GPU 直接解码”吗？它的成本结构是什么，对它调用 getPixel() 会发生什么？**

不是。静态图的实际顺序（材料按 Android 17 `ImageDecoder_nDecodeBitmap` 说明，AAOS13 的 `Bitmap`/`ImageDecoder` 行为一致）：先建立 CPU 可写的 SkBitmap 由编解码器写入像素，PostProcessor 若存在也先在这块软件像素上执行，最后才调用 `Bitmap::allocateHardwareBitmap()` 创建图形缓冲并上传。所以 Hardware Bitmap 没有消除 CPU 解码与像素传输，它把图形缓冲准备提前到解码完成时，避免首次绘制时 HWUI 再建立纹理副本——成本发生的时间与存储形态变了，不是“GPU 解码”。

访问限制按 AAOS13 源码核对：`getPixel()`、`getPixels()`、`copyPixelsToBuffer()` 等直接访问在 `Config.HARDWARE` 上抛 `IllegalStateException`，软件 Canvas 也不能绘制它。把 Hardware Bitmap 显式复制成软件 Bitmap 可能触发 GPU 回读（把图形内存读回 CPU 可访问内存），需要单独测量。它不会因为自身存在就成为 SurfaceFlinger 图层，仍由宿主窗口提交。

**Q5: [learning] 长图、地图类需求为什么必须走 BitmapRegionDecoder 分块，而不是解码整图后裁切？AAOS13 上它的格式与并发边界是什么？**

一次解码完整图片再裁切仍会占用完整图片的像素内存。分块模型按缩放层级计算可见源坐标，只解码当前视口与有限预取区，离开视口的分块进入有上限的缓存。并发边界按 AAOS13 源码核对：`BitmapRegionDecoder` 用内部锁（`mNativeLock`）保护原生解码器，同一实例一次只能执行一个 `decodeRegion()`，给同一解码器配多个工作线程只会增加等待，预取队列应支持取消并优先当前视口。

格式边界是版本敏感点：AAOS13 源码 javadoc 声明区域解码仅支持 JPEG、PNG、WebP、HEIF——材料标注的 AVIF 是 Android 17 才加入平台声明（AVIF 平台解码本身从 Android 12 / API 31 开始），所以向 Android 10/11 下发需平移缩放的超大图时要准备兼容格式。带 `isShareable` 的 `newInstance()` 重载已弃用。`recycle()` 后所有读取与解码都会失败。

**Q6: [learning] 解码后的内存由什么决定？为什么换成 JPEG/WebP 省不了运行时内存？**

解码后的内存只由“分辨率 × 解码像素格式”决定，与文件格式、文件体积无关。一张 1280×720 的图，无论它是 391KB 的 PNG、200KB 的 JPEG 还是更小的有损 WebP，默认解码后都是 3600KB（1280 × 720 × 4 字节）。压缩格式只是像素的另一种写法：解码就是把压缩数据还原成完整像素阵列，有损压缩扔掉的是信息，不是格子数。

1. **固定公式：**原始数据量等于宽 × 高 × 每像素字节数。1280×720 乘 4 字节正好 3600KB。它只随两个因素变：分辨率（2560×1440 为 14400KB）与每像素字节数（无透明 RGB 为 3 字节、RGB_565 为 2 字节、灰度 1 字节）。默认 ARGB_8888 下这个原始数据量恰好等于解码后的内存占用。
2. **与文件格式无关：**PNG 用无损记法、JPEG 与 WebP 用丢弃人眼不敏感细节的记法，但还原出来都是 1280×720 个点、每点 4 字节，一分不少。
3. **省内存只有三条路：**按 View 尺寸降分辨率采样（inSampleSize）、降每像素字节数（RGB_565）、不栅格化（VectorDrawable 按需绘制）。
4. **两本账分开记：**换 JPEG/WebP 省的是 APK 体积与磁盘，省不了运行时内存。内存要靠按尺寸采样与合适的像素格式。

**Q7: [learning] RGB_565 是什么，能省多少解码内存，代价是什么？**

RGB_565 是 16 位色像素格式：每像素 2 字节，位分配 5+6+5（红 5 位、绿 6 位、蓝 5 位，绿色多分一位因为人眼对绿色最敏感），没有透明度通道。相对默认的 ARGB_8888（4 字节每像素、1677 万色加 256 级透明），它用“无透明 + 6.5 万色”换一半内存：1280×720 的图从 3600KB 降到 1800KB。

1. **代价一，丢透明：**表达不了任何透明与半透明，图标、圆角、阴影、渐隐遮罩这类需要 alpha 的图不能用。
2. **代价二，色带：**每通道档位减少，渐变从平滑过渡变成台阶式色带。深色背景上的暗部渐变最容易看出来，照片因自带噪点掩护通常不易察觉。
3. **同族格式对照：**

    1. ARGB_8888：4 字节每像素带透明，是默认。
    2. RGB_565：2 字节无透明，适合不透明照片与全屏背景。
    3. ALPHA_8：1 字节只存 alpha，用于纯遮罩。
    4. RGBA_F16：8 字节带透明，用于 HDR 广色域。
    5. HARDWARE：像素只存图形内存、不占 Java 堆，但显存开销照旧。
4. **用法与验证：**BitmapFactory 手动解码时设置 inPreferredConfig 为 RGB_565。该选项是“尽量满足”的偏好而不是命令，带透明的图在某些路径会回退成 ARGB_8888，解码后要读取 Bitmap 的 config 验证实际结果。Glide 用 asBitmap 加 format 指定 DecodeFormat.PREFER_RGB_565 更稳：检测到图不透明才真用 565，有 alpha 自动回退。
5. **与压缩格式的关系：**文件格式省磁盘体积、解码格式省运行时内存，是两个正交的旋钮，可以同时拧：文件换有损 WebP，解码用 565 加按尺寸采样。
