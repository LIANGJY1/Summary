# 性能分析与测量

**Q1: [learning] 性能问题开始分析前，怎样把用户反馈变成可测量的问题？**

先把反馈描述成一段关键用户旅程，写清触发条件、起点、终点和成功状态，再选择能代表这段旅程的指标。例如“打开首页慢”需要明确从点击图标还是进程启动开始、首帧还是内容可交互作为结束；“页面卡顿”需要固定页面、手势和帧预算。症状名称本身不是指标，也不能直接说明根因。

按具体问题学习对应机制：[应用启动与交付](../01-应用/startup/startup.md)、[渲染与响应](../01-应用/rendering/rendering.md)、[内存](../01-应用/memory/memory.md)和[网络](../01-应用/network/network.md)。

**Q2: [learning] 一次性能测量需要固定哪些条件，结果才可以比较？**

测量合同至少固定工作负载、设备状态和统计协议。工作负载包括入口、数据、操作步骤和终止条件；设备状态包括型号、系统与应用版本、构建和编译状态、刷新率、温度、电量及网络；统计协议包括预热、重复次数、排除规则、分组维度和聚合方法。任一条件改变，都应标记为不同实验条件，避免把环境差异误当作代码收益。

**Q3: [learning] 为什么性能结果应看分布，而不能只看一个数字？**

缓存、调度、垃圾回收、I/O、温控和网络波动会让同一工作负载产生不同结果。均值可以描述可加总成本，但交互延迟、启动耗时和帧耗时通常还要观察分位数、超阈值比例、样本量与原始样本。只有来自相同指标定义和相同人群分组的数据才可比较；不同设备档位、刷新率、启动类型或版本不能随意混在一起。

**Q4: [learning] 怎样区分性能容量不足与偶发延迟？**

容量不足表现为持续工作量超过目标时限，通常要减少关键路径工作或增加有效资源；偶发延迟则来自调度、锁、Binder、I/O 等等待，重点是找出阻塞链。单看平均耗时或工具标签不能区分二者。帧预算随刷新率变化，具体帧分析应结合目标设备的帧时间线和渲染机制。

**Q5: [learning] 一次可复查的性能调查应按什么顺序推进？**

按“定义问题 → 建立基线 → 采集区分假设的证据 → 提出可证伪假设 → 单变量干预 → 同协议复测并检查副作用”推进。采集内容由待验证假设决定；一次打开所有数据源会增加扰动并降低分析效率。复测除目标指标外，还要检查稳定性、内存、功耗和功能正确性。

**Q6: [learning] 性能报告可以把结论写到什么程度？**

结论强度应与证据一致：时间上同时出现只能说明观测到关联；调用、等待或资源路径能解释影响方向时，才形成机制假设；改变该机制并观察预期中间量变化后，才能报告干预结果；在独立轮次或设备上复现后，结论才适用于已覆盖范围。报告至少保留：

1. **问题与条件：**用户场景、指标口径、出现频率，以及设备、系统和应用版本、构建、数据与环境。
2. **原始证据：**正常与异常样本、目标时间窗及 trace、dump、基准数据等原始材料。
3. **推理过程：**机制假设、证据与反证、未排除原因、源码或版本坐标。
4. **干预与复测：**单变量改动、预期中间量、复测分布、副作用和回退条件。

**Q7: [learning] 为什么“App 问题”或“系统问题”还不能作为根因结论？**

这类标签只指出责任边界，不说明发生了什么机制。应继续明确目标进程或组件、资源状态、调用和等待关系，以及最终造成的用户影响。例如主线程可能在执行计算，也可能等待 Binder、锁或 I/O；三者的优化方向不同。按实际对象进入[应用](../01-应用/README.md)、[系统](../02-系统/README.md)或[底层](../03-底层/README.md)主题继续归因。

**Q8: [learning] 怎样安排性能优化优先级并避免收益回退？**

优先考虑受影响用户范围、发生频率、体验损失、证据把握和修复成本；严重但低频的 ANR、崩溃或数据损坏不能被平均分掩盖。把验证过的指标定义、设备与构建条件、基线、回归门禁、灰度观察和回滚条件纳入版本流程，并持续检查目标指标之外的副作用。

**Q9: [learning] 性能实验最常见的偏差来自哪里？**

重复次数不能修复系统性偏差。比较前要控制或记录会改变执行路径的条件：构建与插桩状态、JIT/AOT/Profile 编译状态、温度与频率、刷新率、进程与缓存状态、网络与数据集，以及采集本身的开销。每次只改变主要实验变量；需要比较不同环境时，分组报告，不能混成一个结果。具体的启动、帧、内存与功耗协议分别见[应用主题](../01-应用/README.md)和[工具目录](../04-工具/README.md)。

**Q10: [learning] 实验室数据与线上数据各自适合回答什么问题？**

线上数据适合发现影响范围、设备分布和长尾趋势；受控实验适合复现现象、定位机制和验证改动。推荐顺序是先用线上信号确定场景与人群，再在实验室固定条件复现，最后用同一测量合同复测并观察灰度。trace 中出现 GC、Binder 或 I/O 只说明采集到了相关活动；只有它落在目标时间窗、解释了延迟，并能通过对照实验验证，才支持根因结论。

**Q11: [learning] 一个长期性能指标的定义需要固定什么？**

指标合同要固定测量对象与起止事件、观测单位、计算分子和分母、排除条件、统计窗口、样本分组、采样概率、聚合方法，以及系统、应用和采集配置版本。指标含义改变时应升级定义版本，不能把新旧口径直接拼接成趋势。用户体验结果、线上健康、发布门禁和诊断解释属于不同用途，即使名称相似，也不应共用未说明口径的数值。

**Q12: [learning] 线上分位数和异常样本应该怎样统计？**

分位数不可跨组求平均；合并分布应基于原始样本或可合并的直方图/分布摘要，并保持场景、版本、设备档位与刷新率等口径一致。长期趋势使用稳定抽样且记录入选概率的基线样本；异常触发样本适合回查现场和聚类，不能直接估计总体发生率或分位数，因为它的入选概率取决于结果。告警同时检查绝对阈值、对照回归、最小样本量和数据覆盖健康，避免把采集故障误判为性能改善。
