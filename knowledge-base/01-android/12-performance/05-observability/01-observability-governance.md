# Android 性能可观测性治理

**Q1: [learning] 指标、日志、追踪三类可观测性信号分别回答什么问题？为什么不能共用同一套存储、标签和采样规则？**

三类信号分别回答不同问题：

1. **指标：**查看群体趋势，例如版本是否变差、影响哪些机型、是否达到告警阈值。
2. **日志：**还原单次现场，例如操作路径、错误码与降级原因。
3. **追踪：**解释耗时路径，例如一次启动、卡顿或请求慢在哪个阶段。混用的代价是双向的：日志明细做长期高频聚合会让存储与查询成本失控，而只有指标看板时，Crash 率上升后既没有日志定位场景、也没有追踪解释 span。三者共享关联键（`event_id`、`session_id`、`trace_id`、`scene_id`、构建版本与设备维度），但存储、保留期与采样独立演进。

Android vitals 侧重 Play 分发侧的指标（用户感知崩溃率、用户感知 ANR 率等，按最近 28 天均值每日评估），不提供自定义业务场景与内部日志。Firebase Performance 更接近应用内部性能观测。自建体系把 vitals 当外部质量基线，再用日志与追踪补现场，而不是用其中一个替代全部。

**Q2: [learning] 可观测性事件为什么同时保存墙钟与单调时钟？最小事件信封应包含哪些字段？**

`System.currentTimeMillis()` 是可被用户或网络校准的墙钟，用于与发布、告警跨系统对时。`SystemClock.elapsedRealtimeNanos()` 是包含深度睡眠、单调递增的经过时间，用于本机会话内排序与耗时，设备重启后归零。一次读数不能同时满足两种用途，所以每条事件同时记录两者，并配 `session_id`（短期、可重置、用途受限，不用永久设备 ID）与场景内序号划定会话边界。

最小事件信封还应逐项包含：

1. **事件身份：**`event_type` 与 `event_id`，后者用于重试去重。
2. **关联与兼容：**`trace_id` 关联日志与追踪；`schema_version` 管理新旧格式兼容。新增字段定义缺省语义，废弃字段先双读验证再停发。
3. **环境维度：**应用与系统版本、设备与网络维度。
4. **采样信息：**采样纳入概率与规则 ID。高基数字段（原始 URL、永久用户 ID、自由文本、堆栈全文）不进指标标签，否则索引与分组成本随取值数量增长。

**Q3: [learning] 高频性能事件的采样为什么用确定性分桶而不是逐事件随机？纳入概率为什么必须随事件上报？**

逐事件独立随机会把同一会话抽成不连续片段，排查时无法还原用户路径。确定性分桶用 `HMAC(sampling_key, 可重置标识)` 之类的稳定输入，让同一用户在配置时间窗内始终落入同一样本组，客户端不上传原始标识。只有抽样设计与纳入概率已知时，服务端才能按权重估计总体。异常补采、失败全量与成功抽样混在一起时必须分层计算，不能全体除以一个采样率——排查界面也要显示采样命中与丢弃原因，避免把“没有采到”误判成“没有发生”。

配套纪律：采样配置带版本、签名与过期时间，拉取失败沿用最近有效快照、过期后回退保守策略。提供紧急关闭开关（kill switch）但范围受限，不能远程关掉 Crash/ANR 等最低诊断能力。哈希不是匿名化：低熵内容（错误消息、URL、手机号）可被枚举反推，敏感字段应先移除再用受控密钥生成指纹。用户日志回捞、远程诊断等高敏感能力默认关闭，按目标、时间窗、单设备配额与自动过期开启。

**Q4: [learning] 监控 SDK 为什么必须“主线程只入队”？普通 App 能采到哪些系统层信号，哪些采不到？**

采集 API 常从主线程调用，若在调用栈内完成 JSON 序列化、文件扩容或同步写盘，存储抖动会直接进入页面耗时，`mmap` 写入也有缺页与回写长尾。所以入口只读必要原始值并尝试写入有界队列（队列满按事件等级丢弃并记丢弃数），聚合、压缩、脱敏与上传交给专用线程和受约束的持久任务。SDK 自身开销（入口 P95/P99、分配次数、丢弃率）要纳入发版门禁。进程生命周期也是硬约束：缓存进程可能被冻结，冻结期间无法自采，恢复后只能承认区间缺失并记录原因，不能用零填充。

平台能力分层：StatsD 的 `addConfig()`/`getReports()` 需要 `DUMP` + `PACKAGE_USAGE_STATS`，`setPullAtomCallback()` 需要 `REGISTER_STATS_PULL_ATOM`，都是特权路径（按 Android 17 材料口径。AAOS13 树未包含该模块源码），普通 App 只能用极少数公开入口。公开可用的是 AndroidX JankStats（帧级数据，回调会复用 `FrameData`、跨线程保存要先复制，`isJank` 是库内启发式）、`Debug.MemoryInfo` 与 `getProcessMemoryInfo()`（仅同 UID、调用限频，密集轮询可能返回旧值）。系统内存策略是另一层观察对象：PSS 曲线本身不能证明 compaction、freezer 或 MemoryLimiter 触发，要用 trace、dumpsys 或退出记录交叉验证。版本差异点：AAOS13 源码中 `CachedAppOptimizer` 默认 Freezer 开、Compaction 关，材料核对基准（Android 17 r1）中两者默认开——某一版的默认值不是平台承诺。

**Q5: [learning] 发布构建的符号化产物为什么要与二进制绑定归档？缺 mapping 时门禁应该怎么做？**

混淆名与 Native 地址只在同一次构建内有意义：同一 `versionCode` 可能被重新构建，单靠它选不出正确的 R8 mapping。Native 侧要靠 ABI、`.so` 文件名、ELF Build ID 与 PC 相对地址匹配未剥离产物或符号包，重新链接会改变地址布局与 Build ID——即使源码提交与版本名相同，也不能拿另一份 ELF 还原线上地址。所以每个可发布构建把 APK/AAB 摘要、mapping 内容摘要、原生符号文件、Git 提交与构建变体归档为同一组不可变产物，CI 在发布时复制到只增不改的仓库。

门禁规则：启用 R8 却缺 mapping、包含 Native 库却缺对应 Build ID 的符号文件时直接阻断发布，否则上线后只能把栈标记为“无法反混淆”，Native 崩溃无法还原函数。问题签名要等符号化之后再生成（异常类型 + 还原后的稳定帧序列 + 规范化消息 + 构建范围。Native 用致命信号 + Build ID + 符号化函数 + 模块内偏移区间 + ABI），混淆名和绝对地址不能做跨版本问题组主键。服务端保留原始事件与问题组的映射，聚类算法更新后可重新归组而不改原始事件。

**Q6: [learning] ANR 监控为什么要分“端侧疑似、系统预警、系统确认”三层？**

因为三层的证据强度不同，混在一起会把长卡顿误判成系统 ANR：主线程哨兵与 Looper 监控只能证明“运行期出现过可疑长卡顿”。`ApplicationExitInfo` 的 `REASON_ANR`（API 30+）是系统确认记录，trace 可读但属历史接口。Android 17 的 `registerAnrWarningListener()`/`AnrWarningResult` 是接近超时的尽力预警，可能不投递、也可能来不及执行，且 API 37 才有（AAOS13 上不存在。`AnrInfo` 同为 API 37）。事件模型要带 `authority` 字段分别入库——系统退出、当前错误状态、预警、端侧疑似、Play 聚合、OEM 事件各自标记，不把缺失字段伪装成同一口径。

快照设计围绕“时间、线程、资源、场景”：主线程栈之外要补 Binder、持锁与线程池对端线程栈，否则只能停在“主线程在等锁”而不知道锁被谁持有。运行期可先写本地环形缓冲区，疑似 ANR 时按时间窗与字节上限截取。去重分三层：传输层按事件 ID 与附件摘要幂等。事故层用系统 `(anrType, anrId)` 或带时间约束的进程身份关联预警、哨兵与退出。问题层在符号化后按卡点聚类——同一次事故的预警、疑似卡顿和系统退出是三条记录而不是三次 ANR。告警用暴露量、置信区间与版本/设备分布校准，避免低暴露版本偶发误报。Play 的 0.47% 与 8% 是它的不良行为阈值，不是内部事故分级线。

**Q7: [learning] 线上排障的推进顺序是什么？“证据等级”为什么要区分 A–D？**

排障按以下顺序推进：

1. 建立事件编号，记录现象、首报时间与影响面。
2. 先做安全处置：暂停扩大灰度、保留已知证据，避免重启或清缓存毁掉现场。
3. 建立时间线，对齐客户端日志、traceId、Crash/ANR、配置变更与发布记录；本机排序用单调时钟，跨设备对时用带时区墙钟。
4. 列出证据缺口，再选择动态日志、受控 profiling、用户协助的 bug report 或受控复现；采集动作本身限时、限量且可撤销。
5. 修复后按相同分桶口径验证指标恢复。

证据等级用于避免把相关性写成根因：

1. **A 级：**平台直接信号，例如公共 API、系统回调与退出记录；只按字段原义陈述，不扩写 API 未提供的细节。
2. **B 级：**时间相关，仅用于提出和筛选假设。
3. **C 级：**群组相关，仅用于提出和筛选假设。
4. **D 级：**用户描述，仅用于提出和筛选假设。

B–D 级证据不能单独写成“该厂商会执行某策略”。缺失数据要有语义：进程退出、作业未获得运行机会、断网、队列满、用户强行停止（作业和闹钟在再次显式启动前不会恢复）都可能表现为“没有数据”，服务端要把“没收到事件”与“指标为零”分开，恢复后记录 `unsupported`、`frozen_gap` 等原因而不是补零。

**Q8: [learning] 远程日志与动态日志级别要控制哪三类成本？哪些字段永远不该进日志？**

三类成本：CPU 来自字符串构造、序列化与压缩。I/O 来自频繁写盘与同步落盘。流量来自批量上传。开关按日志标签或结构化事件类型生效、只覆盖明确的用户分组，以服务端到期时间和客户端累计预算双重终止。每次下发、命中、续期与撤销写审计记录，客户端无法验证签名、版本或有效期时维持安全默认级别。

隐私边界先于功能：密码、验证码、完整 token、支付凭据、输入文本与联系人内容不得进入日志。URL 默认只保留主机名、路径模板与错误码，丢弃 query、fragment 与凭据。字段在产生处分类、在写盘与上传两处校验——私有目录不是采集敏感数据的理由。普通 App 不能把远端字符串解释成系统属性（`log.tag.<TAG>`/`Log.isLoggable()` 更适合 adb 调试设备），也不能读取全设备 logcat（Android 官方把全设备日志限定给 OEM App）。bug report 需要用户在开发者选项里主动生成分享，是高成本后备手段而非每次反馈的默认要求。

**Q9: [learning] 诊断命令通道的安全设计要点是什么？为什么不能通过它下发可执行代码？**

诊断命令是远程控制面，安全级别应高于普通远程配置。命令信封至少包含：`command_id`、命令类型与参数 schema 版本、目标范围（包名/签名/渠道/版本/设备或匿名主体）、签发与过期时间、nonce 或单调序列、最大执行次数、网络与文件预算、结果字段 allowlist，以及审批 ID 与签名信息。端侧先验证签名、受众、期限与本地政策再写入持久执行记录，`command_id` 与 nonce 进防重放表，服务端用同一 ID 幂等接收结果，wall clock 不可信时用服务端时间锚点与短有效期缩小重放窗口。

动作集合必须是预编译白名单：拉取限定会话或时间窗的日志、对固定端点做 DNS/连接/TLS 探测、读白名单目录元数据（防目录穿越）、输出配置快照、请求 ProfilingManager 或写应用内 trace 标记。任意 shell、反射、任意文件读取或网络目标等于远程代码执行入口，不应出现在普通用户路径。熔断开关按命令类型、版本与签名密钥缩围，客户端离线时靠命令过期自行生效。不下发代码还因为 Android 官方将远程动态加载列为安全风险且可能违反 Play 政策——补日志靠预埋观察点与签名命令调整采集级别即可。回执记录 `issued → delivered → validated → started → result_created → uploaded` 各阶段：未送达不算执行失败，已生成文件未上传不算 profiling 失败。

**Q10: [learning] 非 Play 渠道与国内 ROM 场景，可观测性会缺什么？怎么补齐而不误判？**

Android Vitals 的数据来自选择共享使用与诊断信息、且通过 Play 安装并通过认证的设备，官方明确排除非 Play 安装的版本与未认证机型——同一个 APK 在其他市场产生的问题不会进入同一份 Vitals。厂商报表与应用市场数据的覆盖条件也不同，不能视为 Vitals 等价物。

补齐方式是平台公共 API + 应用自身事件 + 服务端统计的同口径路径。每条事件记录分发字段与应用内声明的渠道：`getInstallSourceInfo()` 自 API 30，`installingPackageName` 可被更改，`initiatingPackageName` 在来源不可用或包已卸载时为空，`originatingPackageName` 由发起方提供且未经框架验证（缺 `INSTALL_PACKAGES` 权限拿不到）。平台字段与自有渠道不一致时记录差异并标“待解释”。再采集能力快照（standby bucket、后台受限、省电、热状态、page size 等）并带采集时间——这些状态随时变化，读取失败记 `unknown` 不写 0。渠道通常与机型、地区、ABI、签名、用户群同时变化：实验室比较要同一源码等价构建、同设备交叉安装并记录编译状态。线上按版本、产物摘要、厂商与系统构建分层并报样本量与置信区间。“加入白名单”引导只在公共 API 显示后台受限且延迟影响可解释时触发，不作为首次启动必做步骤。

**Q11: [learning] 性能 A/B 实验的随机化单元和暴露口径怎么定？为什么“只分析成功激活的用户”会引入偏差？**

随机化单元要选与产品语义一致的稳定单元（账号、安装或设备），分析时保留分桶版本：按请求随机会让同一用户反复切换方案，更换哈希函数或盐值会重新分桶。随机化单元与统计单元必须一致——按用户分桶时，同一用户的多次启动、帧与会话是相关观测，应先在用户级聚合再比较，或使用按单元聚类的标准误/聚类 bootstrap。否则活跃用户贡献更多事件，置信区间会过窄。

暴露要拆成漏斗分别记录：分配（assignment）→ 配置拉取（fetch）→ 激活（activate）→ 实际使用 → 上报成功。主分析按预注册的分配口径。只分析激活者属于处理后选择偏差：变体自身导致启动失败或崩溃时，“成功用户”样本恰好抹掉了损伤。Firebase A/B 的官方边界同理：未触发激活事件的目标用户不进实验结果但仍可能收到实验值，且实验开始后不能修改变体权重。

**Q12: [learning] 用 P90/P99 做实验主指标时，判定协议与均值有什么不同？分群分位值能加权相加吗？**

不能。主效应应直接定义为两组分位差 `Qτ(variant) − Qτ(baseline)`，并直接为差值构造区间——分别看两组区间是否重叠不能替代差值区间。分位数是非线性秩统计量，不适用均值公式：按随机化单元做聚类 bootstrap（被抽中单元携带其全部合格事件，直接按帧或请求重采样会破坏单元内相关性），或把 SLO 转成用户/会话级违约率 `P(X > L)`。两种结果回答的问题不同，尾部报告除 P99 外还要预注册体验阈值 `L` 的违约率与超阈值时长。

总体分布是各群混合累积分布 `F(x) = Σ wg·Fg(x)`，总体分位值是混合 CDF 的逆函数，不等于各群分位值的加权和。人群构成变化与群内分布变化要分开归因，标准化时把两组重加权到同一参考构成再计算经验分布。区间同时包含可接受改善与不可接受退化时，结论就是证据不足，不能用单点方向替代。重复查看普通 p 值并随时停止会抬高假阳性率，要用固定终点、预分配错误预算的序贯方法或 anytime-valid 推断。低端机、热限频造成的真实慢样本属于用户体验，不能当异常值删除。

**Q13: [learning] SRM（样本比例失衡）检查为什么必须先于性能指标判断？常见原因有哪些？**

实际分配数与预设权重的差异超出随机波动可解释范围时，实验数据已不可用于决策——继续比较收益是在损坏的数据管道上读数。检查用卡方检验（大样本）或精确方法（小样本、稀疏分群），覆盖全量与预注册关键分群，阈值与查看频率预注册。并沿“分配 → 拉取 → 激活 → 指标产生 → 上传成功”逐层定位：分配已均衡而激活后失衡，说明问题发生在处理之后——某变体在激活或上报前崩溃，此时只过滤“成功用户”会隐藏 Crash/ANR 造成的损伤。

常见原因包括分桶哈希函数或盐值变更、安装 ID 重置、目标条件实现不一致、埋点丢失与变体提前崩溃。A/A 实验用于长期校准分桶与统计任务的假阳性率、置信区间覆盖率，但它不能证明平台永远无偏。实验平台自身也是事故源：一个错误配置可能让启动多拉接口、打开高频日志或调整线程池参数，因此平台要支持配置审计、灰度放量、紧急关闭和不可变的配置版本历史（紧急关闭生成新配置版本并保留旧快照，不覆盖历史值）。

**Q14: [learning] 把 Macrobenchmark 接进 CI 门禁，指标可用性与基线选择有哪些硬边界？**

环境边界：物理设备而非模拟器（模拟器受宿主机与虚拟化影响）。目标包接近生产——non-debuggable、profileable、与生产一致的 R8、资源压缩、签名后处理与 Baseline Profile，测试 APK 与目标 APK 分开构建。固定设备不等于环境恒定，要记录电量、温控、build fingerprint、`CompilationMode` 与数据准备方式。指标边界：`StartupTimingMetric.timeToInitialDisplayMs` 测首帧（TTID），`timeToFullDisplayMs` 依赖 `reportFullyDrawn()`（TTFD）且在 Android 10 / API 29 及更早可能不可用，没有完整绘制点的场景不能用 TTFD 卡门禁。`FrameTimingMetric.frameDurationCpuMs` 与 `frameOverrunMs`（API 31+ 才可用）语义不同、不能共享阈值。`TraceSectionMetric` 与 `PowerMetric` 仍是实验性 API（前者默认 `targetPackageOnly = true` 且 `Mode.Sum` 累计所有同名 section）。

基线边界：`baseline` 不能总指向上一轮——上一轮本身可能已退化，逐次比较放过累积变化。固定已知良好版本适合判断累计漂移，滚动稳定基线适合识别设备环境变化，更新固定基线是发布决策、不能由测试任务在结果变差后自动完成。CI 分三档：PR 快检只验证编译与可执行。主干定时任务在固定物理设备上多轮测量建趋势。发布候选在代表性设备档位跑核心路径。JSON 与每次迭代的 Perfetto trace 都要归档，聚合异常后能回到单次 trace 查原因。测试环境异常标“无效运行”，不伪装成业务豁免。

**Q15: [learning] 发版门禁应检查哪些域？产物身份为什么要先冻结？**

发版门禁至少覆盖以下域：

1. **启动：**按启动类型、入口与设备群比较 TTID；仅对正确调用 `reportFullyDrawn()` 的场景使用 TTFD。
2. **渲染：**按刷新率与页面分组检查 FrameTiming 分布、生产慢帧与冻帧。
3. **内存：**检查 Java / 原生堆、PSS / RSS、OOM 与低内存退出。
4. **稳定性：**检查崩溃、ANR、原生崩溃与 `ApplicationExitInfo` 原因，分别呈现受影响用户数与事件数。
5. **功耗：**检查固定场景能耗与异常唤醒。
6. **数据健康度：**检查实验分组、采样配置、上报与查询延迟。
7. **包体与配置：**检查 AAB / 动态特性大小、资源与远程参数快照。

任一域失败都执行预设动作并记录审批人。

产物身份先冻结：`versionCode`、Git 提交、AAB/APK 文件摘要、签名证书摘要、`compileSdk`/`targetSdk`、R8 mapping、原生符号、Baseline Profile 版本与远程配置快照绑定同一构建 ID——实验室和生产引用同一份证据，数字变化才能转换成发布决定。阈值绑定指标版本、设备群、场景与发布阶段，来自本项目历史噪声、SLO 与最小可检测效应，不复制其他项目的毫秒数或百分比。升级目标版本时按“保留原 targetSdk 验证运行兼容”与“targetSdk 升级验证目标兼容”两轮推进（材料以 Android 17 为例），兼容开关只用于逐项定位，正式结论来自接近生产的候选包在完整行为组合下的验证。

**Q16: [learning] staged rollout 的 userFraction、暂停（halt）与“回滚”各是什么语义？灰度期间为什么不能只看崩溃率？**

`userFraction` 是有资格接收该分阶段版本的用户比例，不是安装完成率或在线占比。它只对 `inProgress`/`halted` 状态有效且严格在 0 与 1 之间。暂停把状态置为 `halted`：阻止更多用户取得该版本，已安装用户停留在该版本——Play 不能远程降级 APK，“回滚”实际是三种操作：暂停发布、回退服务端配置、发布更高 `versionCode` 的修复包。已全量版本也可暂停（前一个版本会重新提供给未安装用户，内部测试轨道除外），配置错误走配置回退，已安装用户靠服务端兼容与功能开关兜底。staged rollout 不满足严格 A/B 条件（无稳定旧版对照组，覆盖受国家、资格与自动更新影响），版本间差异可以触发处置但不能证明代码因果。

灰度决策要分快慢信号：自建 APM、崩溃/ANR 事件流与启动帧指标是快信号（前提是数据延迟与覆盖达标）。Android vitals 每天更新最近 28 天均值，适合长期质量判断，不能作为刚起步小流量的扩量依据。客服与评论到达慢且有选择偏差，“暂时没有投诉”不能抵消已观测的崩溃或数据管道异常。上报成功率、事件丢弃、配置命中率或上报延迟异常时，当前结论标“不可判定”，维持或暂停当前比例。

**Q17: [learning] App Performance Score 的静态分与动态分分别评估什么？分数怎么转换成工程任务？**

这是 Google 仍处 Preview 的评估框架（2026 年口径），0–100 分表示评估表中还有多少改进空间。静态分不运行应用、检查源码配置：最新 AGP、R8 full mode 且 keep 例外受控、Baseline Profile 覆盖至少一条用户路径、Startup Profile 优化 DEX 布局、最新稳定版 Compose、内容可用时调用 `FullyDrawnReporter`/`reportFullyDrawn()`。这些项成本低、信号清楚、适合接 CI。注意配置纪律：生成 profile 的 variant 应关闭 R8 混淆以保持方法签名可匹配，最终 release 才启用。只检查仓库里有 `baseline-prof.txt` 证明不了 release 产物包含并使用它。

动态分在物理设备上测启动到可交互（口径指向 TTFD）与滚动/动画中的 slow/frozen frames 占比，分数属于“该设备、该构建、该次观察条件”，不能跨应用排名，低端设备会放大问题。分数不能给根因、也不能替代线上 KPI——分数高但支付页等待久、搜索首屏空，用户仍觉得差。转换方式是四个队列：配置项（AGP/R8 → Profile → Compose/TTFD）、测试项（冷启动、通知启动、滚动、核心交易路径的 Macrobenchmark 用例）、trace 项（固定场景采 trace，归因线程/I/O/Binder/GPU）、平台项（采集 → 聚合 → 告警）。静态与动态都低时先修静态项（配置修正也可能改善动态表现），但阻断核心业务的动态问题不能等静态项完成。规则会随 Preview 迭代，报告保存评分日期与规则快照，不同规则生成的分数不画同一条趋势线。
