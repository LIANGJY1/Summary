# Android 四大组件：职责、启动方式与生命周期

> 面试复习范围：四类组件各自解决什么问题、怎样被系统调度、生命周期和线程模型有什么区别。本文按 Android 应用框架的一般行为描述；后台启动、广播投递等策略会随系统版本和 target SDK 变化。Activity 页面导航与窗口细节另见 [Activity 启动与窗口生命周期](../15-ui/01-activity.md)。

**Q1: Android 四大组件分别承担什么职责？**

四大组件是 Android 应用向系统声明的四种交互入口：Activity 承载用户界面，Service 承载无界面的持续工作或服务接口，BroadcastReceiver 响应事件通知，ContentProvider 封装并共享结构化数据。它们由系统按各自契约创建和调度，不应把它们理解成四种普通的应用内对象。

1. **Activity：界面与用户交互入口**。系统通过 Intent 启动 Activity，并把它放入任务（Task）的返回栈（Back Stack）；生命周期反映界面可见、交互和销毁状态。
2. **Service：后台组件与服务接口**。它可以由 start 方式运行，也可以由客户端 bind 后提供接口；Service 本身不创建工作线程。
3. **BroadcastReceiver：事件接收入口**。系统或应用发送广播后，系统把匹配的 Intent 交给接收器；接收器适合快速处理事件并移交后续工作。
4. **ContentProvider：数据访问与共享接口**。调用方通常经 ContentResolver，以 content URI 访问提供方；提供方可通过权限控制跨应用数据访问。

四者都可作为系统进入应用的入口，但生命周期语义不同：Activity 跟随界面与任务状态，Service 跟随 started/bound 状态，Receiver 的回调很短暂，Provider 由系统在提供方进程启动时初始化并承载数据访问。

**Q2: Activity 从 startActivity 到显示界面，启动链路和生命周期怎样串起来？**

调用 startActivity 会把 Intent 启动请求交给系统；系统解析目标组件并决定任务栈、进程和窗口启动，应用主线程随后创建 Activity 并驱动生命周期。典型首次启动按以下顺序理解即可，具体内部类和调用路径会随 Android 版本演进。

1. **发起请求**：调用方构造显式或隐式 Intent，调用 startActivity；若从非 Activity 的 Context 启动，通常要补 `FLAG_ACTIVITY_NEW_TASK`。
2. **系统解析与调度**：系统检查目标组件、权限和启动条件，结合任务栈、launchMode 与 Intent flags 决定复用现有实例、创建实例或切换任务。Android 10 起，后台 Activity 启动受到额外限制。
3. **准备应用进程**：目标进程不存在时，系统请求 Zygote 创建应用进程，并让应用主线程完成 Application 初始化；进程已存在时则复用它。
4. **创建 Activity**：系统通过应用进程主线程的调度消息触发 Activity 实例化与回调；首次创建常见顺序是 `onCreate()` → `onStart()` → `onResume()`，随后窗口获得显示机会并绘制首帧。
5. **切换旧界面**：新 Activity 启动时，旧 Activity 至少会进入 `onPause()`；新界面取得焦点后，若旧界面不再可见，旧 Activity 再进入 `onStop()`。

Launcher 点击图标是根 Activity 启动的一个特例：Launcher 准备 Intent 与启动参数，再把请求交给系统 Activity 管理服务。Android 14 的具体源码阶段不能直接当成所有 Activity 启动路径或所有 Android 版本的源码流程。

启动模式与 flags 共同影响实例复用和任务栈操作：`standard` 通常为每次启动创建实例；`singleTop` 仅在目标实例已位于栈顶时复用，并通过 `onNewIntent()` 交付新 Intent；`singleTask` 按任务与栈规则复用实例，可能清除其上方的 Activity。`FLAG_ACTIVITY_NEW_TASK` 参与选择或复用任务，**不表示每次启动都必定新建任务**。

Activity 生命周期回答的是**实例状态变化**，不等于进程生命周期。系统内存紧张时通常杀掉承载进程，而不是单独“杀 Activity”；进程被杀后，回到应用可能会重建 Activity，因此重要界面状态要通过保存状态与持久化机制恢复。配置变化也可能导致 Activity 销毁并重建。

面试常用区分是：`onPause()` 表示 Activity 失去前台交互机会，应快速返回；`onStop()` 表示 Activity 已不可见；`onDestroy()` 不保证在进程被系统直接杀死前执行。返回键结束当前 Activity 与 Home 键让任务退到后台也不是同一种状态转换。

**Q3: Service 的 started 和 bound 两种启动方式有什么区别？Service 为什么不等于子线程？**

started 描述“要求 Service 持续执行工作”，bound 描述“客户端连接并调用 Service 接口”；同一个 Service 可以同时处于 started 和 bound 状态。Service 默认运行在宿主进程的主线程，因此耗时 I/O 或计算必须移到工作线程、线程池或协程执行。

1. **Started Service**：客户端调用 `startService()`（满足平台限制时）或 `startForegroundService()`；首次创建先回调 `onCreate()`，之后调用 `onStartCommand()`。它不会因启动它的 Activity 销毁而自动停止，工作完成后必须调用 `stopSelf()` 或由其他组件调用 `stopService()`。
2. **Bound Service**：客户端调用 `bindService()`；首次创建时先回调 `onCreate()`，再调用 `onBind()` 返回 IBinder 接口。客户端通过 `ServiceConnection` 收到连接并使用接口；所有客户端解绑后，若 Service 没有 started 状态，系统会销毁它。同进程 Binder 调用通常在客户端调用线程执行，跨进程 AIDL 调用会在服务端 Binder 线程池处理，因此不能假设所有 Service 方法都运行在主线程。
3. **两种方式并用**：若 Service 既被 start 又被 bind，所有客户端解绑不会停止 started 生命周期；还需显式 stop。销毁时调用 `onDestroy()` 做资源清理。
4. **进程与线程**：Service 是组件和生命周期入口，不是执行器，也不天然运行在独立进程。声明 `android:process` 可以改变进程归属，但不会自动把回调切到工作线程。
5. **现代后台限制**：Android 8.0 起，应用处于后台时启动普通后台 Service 受到限制；需要可延迟、可重试的持久后台任务时优先考虑 WorkManager/JobScheduler。用户可感知且符合条件的持续工作才使用前台 Service，并遵守其通知、类型和启动限制。

启动模式 `START_STICKY`、`START_NOT_STICKY` 和 `START_REDELIVER_INTENT` 是系统在 Service 进程被回收后的重建策略，不是线程模型，也不保证 Service 永不被杀。选择时要围绕任务是否需要恢复、是否需要原 Intent 重新投递来回答。

**Q4: BroadcastReceiver 怎样接收广播？为什么 onReceive() 里不应做耗时工作？**

Receiver 可以在 Manifest 静态声明，也可以由进程运行时动态注册；收到匹配广播时，系统调用 `onReceive()`。该回调通常运行在应用主线程，而且回调结束后 Receiver 生命周期即告结束，因此它只应做快速处理或安排可靠的后续任务。

1. **静态注册**：在 Manifest 声明 `<receiver>` 和 Intent Filter，系统可在应用进程尚未运行时按条件拉起进程并分发符合规则的广播；Android 8.0 起，大量隐式广播不能再通过 Manifest 注册接收，具体例外以平台文档为准。
2. **动态注册**：用 `registerReceiver()` 在进程运行期间注册，合适时调用 `unregisterReceiver()`。Android 13 起，面向较新 target SDK 的动态 Receiver 通常需要明确指定导出状态，按是否接收其他应用发送的广播选择 `RECEIVER_EXPORTED` 或 `RECEIVER_NOT_EXPORTED`。
3. **短时回调**：`onReceive()` 返回后，系统可以认为这次接收处理完成；不要在其中启动裸线程后就返回并期待进程继续存活。耗时或需要保证执行的工作应交给 WorkManager、JobScheduler 等受系统管理的调度机制。
4. **线程与异步**：默认注册方式下回调在主线程执行；动态注册可指定 Handler，但这不改变 Receiver 的短生命周期。`goAsync()` 可延长一次广播处理窗口以完成短时异步工作，仍须尽快调用 `PendingResult.finish()`，不能把它当作长期任务方案。

广播是事件通知与松耦合分发机制，不提供严格的低延迟或恰好一次执行保证。多个应用都需要快速的双向请求/响应时，应评估 bound Service 等 IPC 机制，而不是把广播当作通用 RPC。

**Q5: ContentProvider 如何完成跨进程数据访问？它与直接访问数据库有什么区别？**

ContentProvider 把数据操作封装成统一的 URI 访问契约：调用方使用 ContentResolver 发起查询或修改，系统按 authority 找到 Provider，并在需要时启动提供方进程；跨进程调用由 Binder 承载。它的关键价值是稳定的数据接口和访问控制，不是某一种数据库实现。

1. **标识数据**：Provider 在 Manifest 中声明 authority；调用方以 `content://authority/path/...` 表示数据位置。路径约定及 MIME 类型共同构成访问契约。
2. **发起访问**：调用方通过 ContentResolver 调用 query、insert、update、delete 或 getType；通常不直接实例化另一个应用的 Provider。
3. **路由与执行**：框架根据 authority 找到 Provider；如果提供方进程尚未运行，系统先创建进程并初始化 Provider，然后把操作分发给对应方法。
4. **返回结果**：query 返回 Cursor；写操作返回受 API 契约约束的 URI 或影响行数。调用方负责及时关闭 Cursor，并按约定观察数据变化。
5. **控制权限**：通过 `android:exported`、读写权限和临时 URI 授权决定谁可访问哪些数据。对外暴露时，必须把 URI 路径、调用权限和实际数据范围一起纳入安全边界。

Provider 的 `onCreate()` 用于快速初始化，避免在其中做耗时数据库创建或数据加载；除 `onCreate()` 外，Provider 的数据操作方法可能并发调用，必须保证线程安全。Provider 提供跨应用数据接口，但不是每个应用内数据库都必须经由 Provider 暴露。

**Q6: 面试中怎样概括四大组件的生命周期与执行边界？**

回答时先讲各组件的调度契约，再讲共同边界：系统创建组件不代表自动创建工作线程，也不代表应用进程永久存活。适合用下面的顺序收束。

1. **Activity**：围绕界面前后台状态回答生命周期；任务栈决定导航返回关系，进程被杀后要考虑状态恢复。
2. **Service**：围绕 started 与 bound 回答存活条件；后台工作、前台服务和受调度任务按可见性、时效性与系统限制选择。
3. **BroadcastReceiver**：围绕一次事件回调回答；快速完成或转交系统调度的后台工作，不依赖回调结束后的进程存活。
4. **ContentProvider**：围绕 URI 数据契约、跨进程路由、并发访问和权限回答；耗时初始化和线程安全是实现重点。

因此，“组件负责被系统识别和调度，线程负责执行并发工作，进程负责承载组件实例”是面试中的关键边界；不要把 Service 说成线程、把 Receiver 说成长期任务容器，或把 Activity 销毁等同于进程立即结束。
