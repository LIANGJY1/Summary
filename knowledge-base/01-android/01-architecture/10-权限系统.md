# Android 权限系统

> 学习资料（文章模式沉淀）。主线：应用权限的声明与授权、Framework 检查、AppOps、Linux UID/GID 和 SELinux 的协作边界。应用沙箱机制见 `09-应用沙箱.md`，SELinux 策略细节见 `11-SELinux.md`。应用侧 API 使用与排障按具体服务主题归档。

**Q1: [learning] Android 的 android.permission.* 是什么机制，权限检查发生在哪一层？**

Android 权限是由系统框架管理的访问控制契约：应用在 manifest 请求权限，系统按 protection level 和用户/系统授权状态决定是否授予，受保护的 API 或服务再依据调用者身份检查是否允许操作。它主要由 Android Framework 与系统服务实现，但不能简化为“纯 Java 检查”或“内核完全不参与”。

1. **声明与授予**：`uses-permission` 表达应用的请求，不代表请求已获授权。PackageManager/PermissionManager 根据权限类型、安装状态、用户选择、系统签名或预装策略记录授权状态。普通权限通常自动授予，危险权限等还受运行时授权流程约束。
2. **调用检查**：Framework API 或服务端在执行受保护操作前检查调用 UID、包名、权限状态，并可能进一步检查 AppOps、角色、前台状态或用户限制。具体检查点取决于 API，不能假定所有权限都只在安装时检查。
3. **底层约束**：部分权限状态会映射为进程 supplementary GID 或其他系统状态。Linux DAC、内核网络检查和 SELinux 可在各自边界执行相应限制。大多数相机、位置等 API 则由框架服务做调用者授权与数据访问控制，不能仅凭权限名推断为直接访问设备节点。

因此，定位一次权限拒绝应从具体 API 的检查路径开始，再确认系统记录的授权状态、AppOps 结果和实际进程的 UID/GID、SELinux 域。manifest 中出现权限名只证明应用提出了请求。

**Q2: [learning] Android 应用权限与 SELinux、Linux UID/GID 分别控制什么？它们怎样互补？**

三者处于不同的执行边界：应用权限表达应用能否使用某项受保护能力，UID/GID 与文件权限控制进程对内核资源的自主访问，SELinux 按安全域和对象标签实施强制访问控制。任何一层都不能替代另外两层。

1. **Framework 权限与 AppOps**：系统服务可按调用 UID/包名及用户授权决定是否允许访问相机、定位、联系人等 API。AppOps 还能表达某些操作的运行状态或用户限制，实际关系按 API 与版本而变。
2. **Linux DAC 与补充组**：进程 UID/GID 参与文件、设备节点和部分内核接口的访问判断。某些 Android 权限会映射到补充组，例如 `INTERNET` 与 `inet` 组有关联，内核网络路径可以据此限制创建 IP socket 的资格。
3. **SELinux**：内核根据进程安全上下文、对象标签和策略决定访问是否允许。即使 Framework 权限检查通过，SELinux 仍可拒绝服务或进程访问某个文件、设备或 Binder 端点。反过来，SELinux 允许进程访问某对象也不代表应用获得了对应 Framework API 权限。

以相机为例，应用需要通过相机 API 和系统服务完成访问，Framework 检查调用者权限。CameraService 等可信组件再按自身 UID/GID 与 SELinux 域访问设备资源。`camera` 组用于设备侧权限配置，不应推导为第三方应用获授 `CAMERA` 权限后就直接获得该组。

**Q3: [learning] Android 为什么需要 Framework 权限？部分权限怎样通过 UID/GID 影响内核访问？**

Framework 权限让系统能够按应用身份和用户授权管理高层能力，并把需要内核参与的少数访问限制映射到进程凭据。它不是把每项用户授权都翻译成一个 GID。每个权限的实现方式必须查对应平台配置与调用链。

1. **用户同意与最小授权**：危险权限等可通过系统界面让用户按应用作出授权决定。内核的文件模式位或 SELinux 策略本身不能代替这套面向应用的声明、解释和授权状态管理。
2. **权限到 GID 的映射**：平台配置可为某些权限定义补充组。AOSP 的 `android.permission.INTERNET` 与 `inet`（GID 3003）存在这种关联，使内核网络访问规则能够约束没有相应资格的进程。应检查目标分支的 `platform.xml` 和 PermissionManager 实现，不能把一项权限的映射推广到所有权限。
3. **进程凭据生效**：系统根据应用 UID 和已授予权限计算进程所需的 GID，进程创建或凭据更新路径再把它们应用到进程。实际生效时机和权限撤销后的处理应以目标 Android 版本源码为准。
4. **相机权限的边界**：`CAMERA` 的普通应用授权由 Framework/相机服务检查。AOSP 历史上曾将该权限映射到 `camera` 组，后来删除了这项映射。当前不能用它作为“应用权限必然映射成设备节点 GID”的例子。设备节点所属的 `camera` 组仍可供可信相机服务使用。

资料来源：AOSP `frameworks/base/data/etc/platform.xml` 的权限到 GID 映射、`PermissionManagerService` 的授权与 GID 计算实现，以及 `system/core/include/private/android_filesystem_config.h` 的 Android UID/GID 定义。具体映射随平台版本和产品配置变化。

**Q4: [learning] protectionLevel 的基础级别与标志位如何组合决定一个权限怎样被授予？**

protectionLevel 由一个基础级别与零个或多个标志位组合而成。基础级别决定默认授予方式：normal 安装时自动授予，dangerous 由用户在运行时决定，signature 按签名匹配在安装时授予，internal 不按签名、只按标志位授予。标志位扩展额外的授予途径或限制，例如 privileged、appop、development、role 与 knownSigner。读一个权限的授予规则必须同时看两部分。

Android 13 的基础级别有五个：

1. **normal（0）：**安装时自动授予，用户不可撤销。
2. **dangerous（1）：**运行时权限。targetSdk 23 及以上的应用由用户在授权对话框或设置中决定，低于 23 的应用安装时授予但用户可在设置中关闭。
3. **signature（2）：**请求方与定义方签名一致时安装时授予。系统权限的定义方是平台，因此只有平台签名应用能靠这一级获得。
4. **signatureOrSystem（3）：**已废弃，等价于 signature 加 privileged 标志。
5. **internal（4）：**Android 12 新增。不走签名匹配，完全由标志位决定授予途径，用于明确“不允许普通签名匹配”的内部权限。

常见标志位及其扩展的授予途径如下：

1. **privileged（0x10）：**位于 priv-app 目录的特权应用可获授，还需在 privapp-permissions 允许清单中列出。
2. **development（0x20）：**可用 adb shell pm grant 在开发期授予。
3. **appop（0x40）：**授予状态由 AppOps 跟踪，检查时必须经 AppOpsManager 或其封装，不能只看 checkSelfPermission。
4. **pre23：**targetSdk 低于 23 的应用安装时自动获授。
5. **runtimeOnly（0x2000）：**只能作为运行时权限授予，不能靠安装时途径获得。
6. **role：**持有对应角色的应用可获授。
7. **knownSigner：**Android 13 新增。请求方签名在权限声明的已知签名者列表中即可获授，用于跨厂商的受信协作。

以 SYSTEM_ALERT_WINDOW 为例，它的 protectionLevel 是 signature|setup|appop|installer|pre23|development：普通应用无法靠签名获得，但可经 appop 路径由用户在“显示在其他应用上层”设置中开启，targetSdk 低于 23 的应用安装时自动获授，开发期可用 pm grant。

依据：Android 13 的 PermissionInfo 常量定义与 core/res/AndroidManifest.xml 中的权限声明。

**Q5: [learning] 运行时权限的授权状态存储在哪里？授予与撤销分别何时写盘？**

运行时权限的授予状态与标志按用户存放在 /data/system/users/<userId>/runtime-permissions.xml，安装时权限记录在全局的 /data/system/packages.xml。PermissionManagerService 修改状态后通过 PackageManager 的 writeSettings 落盘：授予走异步调度写入，撤销走同步写入，因为撤销之后紧接着要杀进程，状态必须先持久化。

按存储与写盘环节，规则有四条：

1. **分文件原因：**运行时权限按用户隔离，多用户各有自己的授权记录。packages.xml 是全局包状态，不随用户变化。
2. **内存结构：**UidPermissionState 按 appId 与用户记录每个权限的 granted 状态与 flags。常见标志有 USER_SET、USER_FIXED、POLICY_FIXED、SYSTEM_FIXED、GRANTED_BY_DEFAULT、ONE_TIME 与 AUTO_REVOKED，它们决定设置页能否修改以及系统能否自动回收。
3. **写盘时机：**默认回调 onPermissionGranted 调用 writeSettings(true) 异步调度。onPermissionRevoked 调用 writeSettings(false) 立即同步写入。异步写入由 Settings 合并调度，默认延迟 300 ms，最长不超过 2 s。
4. **查看方法：**adb shell dumpsys package <包名> 的 runtime permissions 段落列出每个权限的 granted 与 flags。userdebug 构建可直接读取该 xml 文件。

依据：Android 13 的 PermissionManagerServiceImpl 默认 PermissionCallback、PackageManagerService.writeSettings 与 Settings 的 RuntimePermissionPersistence。

**Q6: [learning] 撤销运行时权限后应用进程为什么会被杀死？哪些情况例外？**

PermissionManagerService 撤销运行时权限的默认回调会在 handler 上调用 ActivityManager.killUidForPermissionChange，杀掉该 appId 在该用户下的全部进程，原因码为 KILL_APP_REASON_PERMISSIONS_REVOKED。权限对应的补充 GID 发生变化时也会以 KILL_APP_REASON_GIDS_CHANGED 杀进程。目的是让进程不再持有已不被允许的能力，例如已打开的相机会话或已持有的 GID。

按触发路径，规则有四条：

1. **撤销路径：**onPermissionRevoked 先通知权限变化监听器，再同步写盘，最后 post 杀进程。调用方传入 overrideKill 为 true 时跳过杀进程。
2. **GID 路径：**权限映射到补充组时，进程凭据只在进程创建时设置，撤销后必须重启进程才能移除 GID，因此 onGidsChanged 直接杀进程。
3. **例外：**撤销 POST_NOTIFICATIONS 且该应用持有 BACKUP 权限并处于设备初始设置阶段时不杀，避免打断备份恢复。授予权限不杀进程，除非授予改变了补充 GID。
4. **应用侧影响：**用户在设置中关闭权限后回到应用，看到的是进程重建后的新实例。开发者应把权限检查放在使用点，不缓存启动时的检查结果。

依据：Android 13 的 PermissionManagerServiceImpl 中 mDefaultPermissionCallback 的 onPermissionRevoked 与 onGidsChanged，以及 killUid 实现。

**Q7: [learning] AppOps 与权限的分工是什么？MODE_FOREGROUND 等五种模式各表示什么？**

权限回答“应用是否被允许拥有某项能力”，AppOps 在此之上记录和裁决“每次具体操作是否放行”，并能表达权限表达不了的状态：前台限定、用户在设置中关闭的 appop 类权限、没有对应权限的操作，以及操作次数与最近使用记录。检查时 AppOpsManager 返回五种模式之一，调用方据此决定放行、静默忽略或抛错。

五种模式的含义如下：

1. **MODE_ALLOWED（0）：**放行。
2. **MODE_IGNORED（1）：**不放行但不抛异常，调用方应静默失败，例如返回空数据。
3. **MODE_ERRORED（2）：**不放行且应抛 SecurityException。
4. **MODE_DEFAULT（3）：**该操作未被单独设置，回落到权限检查结果。
5. **MODE_FOREGROUND（4）：**仅应用处于前台时放行。Android 9 引入，用于位置等权限的“仅在使用时允许”。

AppOps 与权限的分工按操作类型分三种：

1. **appop 类权限：**protectionLevel 含 appop 的权限（如 SYSTEM_ALERT_WINDOW、WRITE_SETTINGS）的授予状态由 AppOps 跟踪。checkSelfPermission 反映不出用户开关，必须用 AppOpsManager 或 Settings.canDrawOverlays 这类封装检查。
2. **运行时权限的运行态：**位置、相机、麦克风等在权限已授予的前提下还受 AppOps 模式影响。系统服务执行受保护操作前通常调用 noteOp 或 startOp 记录一笔，前台限定、隐私指示器和使用记录都基于此。
3. **无权限的操作：**部分操作没有对应权限只有 op，例如 OP_RUN_IN_BACKGROUND，完全由 AppOps 控制。

依据：Android 13 的 AppOpsManager 模式常量与 op 定义。

**Q8: [learning] SYSTEM_ALERT_WINDOW 这类 appop 权限的授予与检查路径是什么？为什么不弹运行时对话框？**

SYSTEM_ALERT_WINDOW 的 protectionLevel 是 signature|setup|appop|installer|pre23|development，不含 dangerous，所以不会出现运行时授权对话框。普通应用要通过 Settings.ACTION_MANAGE_OVERLAY_PERMISSION 引导用户在“显示在其他应用上层”页面开启，系统把结果记录为 AppOps 的 OP_SYSTEM_ALERT_WINDOW 模式。检查用 Settings.canDrawOverlays(context)，它内部走 AppOps 检查而不是 checkSelfPermission。

按声明、授予、检查三个环节，路径如下：

1. **声明：**manifest 仍需 uses-permission，否则设置页不会列出该应用。
2. **授予：**targetSdk 低于 23 的应用安装时自动获授。targetSdk 23 及以上由用户在设置页开启，对应 op 置为 MODE_ALLOWED。development 标志允许开发期用 adb shell appops set <包名> SYSTEM_ALERT_WINDOW allow 或 pm grant 授予。
3. **检查：**canDrawOverlays 调用 isCallingPackageAllowedToDrawOverlays，对 OP_SYSTEM_ALERT_WINDOW 做 AppOps 检查，再回落到权限检查。持有平台签名权限 SYSTEM_APPLICATION_OVERLAY 的应用直接通过。

用 AppOps 而不用运行时对话框的原因是这类能力危害面广且不适合在使用瞬间决定，系统要求用户在独立设置页慎重开启。AppOps 模式能表达“已声明但被用户关闭”，而安装时权限的 granted 位做不到。WRITE_SETTINGS 同理：protectionLevel 为 signature|preinstalled|appop|pre23|role，引导入口是 Settings.ACTION_MANAGE_WRITE_SETTINGS，检查用 Settings.System.canWrite(context)。

依据：Android 13 的 core/res/AndroidManifest.xml 权限声明、Settings.canDrawOverlays 与 Settings.isCallingPackageAllowedToDrawOverlays。

**Q9: [learning] 系统默认应用为什么无需用户同意就拥有运行时权限？DefaultPermissionGrantPolicy 如何授予？**

系统首次启动、升级与新用户创建时，PackageManagerService 调用 DefaultPermissionGrantPolicy.grantDefaultPermissions，按功能类别（拨号、短信、浏览器、相机、输入法等）与厂商配置文件，对预装的默认应用直接授予对应运行时权限，并打上 FLAG_PERMISSION_GRANTED_BY_DEFAULT 标志。用户之后仍可在设置中撤销，除非同时标记了 SYSTEM_FIXED。

按授予对象与标志，规则有四条：

1. **对象：**按包名或 Intent 解析出的默认处理应用，以及各分区 etc/default-permissions/*.xml 中厂商声明的包与权限。
2. **GRANTED_BY_DEFAULT：**表示非用户授予。默认应用变更时系统可撤销该权限并清除此标志，用户手动修改过的权限不受影响。
3. **SYSTEM_FIXED：**表示系统固定，用户不能在设置中撤销。撤销默认授予时不清除该位。
4. **边界：**本策略只对预装系统应用生效。第三方应用通过角色（Role）成为默认应用后获得的权限，由角色机制在用户切换默认应用时处理，不在本策略内。

依据：Android 13 的 DefaultPermissionGrantPolicy 与 PackageManagerService 对 grantDefaultPermissions 的调用。

**Q10: [learning] checkPermission、checkCallingPermission 与 checkCallingOrSelfPermission 有什么区别？为什么 checkCallingOrSelfPermission 可能泄漏权限？**

三者都返回 PERMISSION_GRANTED 或 PERMISSION_DENIED，区别在于“检查谁”：checkPermission(permission, pid, uid) 检查指定进程，checkCallingPermission 只检查当前 Binder 调用的远端调用者，不在 IPC（Inter-Process Communication）处理中时恒返回拒绝，checkCallingOrSelfPermission 在 IPC 中检查调用者、不在 IPC 中检查自己。后者的危险在于，自己的组件被外部触发后再执行受保护操作时，自己拥有的权限会让没有权限的外部调用方间接获得能力。

按使用场景，四条规则如下：

1. **checkCallingPermission：**不在处理 IPC 时恒失败，这是为了防止意外把自身权限泄漏给调用者。适合 Service 或 ContentProvider 的 Binder 方法内部检查。
2. **checkCallingOrSelfPermission：**官方注释标注 Use with care。Activity 与 BroadcastReceiver 由 system_server 调起，此时它检查的是应用自己而不是启动方，不能用于校验谁发起了启动或广播。
3. **enforce 系列：**enforceCallingPermission 等在拒绝时直接抛 SecurityException，适合必须阻断的路径。
4. **Binder 身份：**Binder.getCallingUid 与 getCallingPid 只在 Binder 线程处理事务期间有效。调用 clearCallingIdentity 之后再检查，检查到的是自己。

依据：Android 13 的 Context.checkCallingPermission 与 Context.checkCallingOrSelfPermission 注释，以及 ContextImpl 实现。
