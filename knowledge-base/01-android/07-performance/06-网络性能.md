# Android 网络性能：请求分段、TLS 与 DNS 诊断

> 学习资料（文章模式沉淀）。主线：把一次请求的等待时间拆到排队、DNS、建连、TLS、传输各段，按复用、协议、弱网策略优化，再用 netd 与 DnsResolver 的系统链路定位解析故障。源文档：android-internals-wiki 第 12 章《网络性能》§12.1–§12.2；机制按本地 AAOS13 源码（Android 13）核对，与材料 Android 17 语境的差异（Android 17 的 ECH/CT 默认值、`DnsResolver(Context, Looper)`、HTTPS 资源记录组合查询、`ACCESS_LOCAL_NETWORK`，以及 netd 与 DnsResolver、Conscrypt 模块源码不在本地树）已标注；OkHttp 5.3.0 与 Cronet 18.0.1 属第三方库，按材料口径转写。蜂窝 radio tail 与推送调度的功耗视角见 [05-功耗.md](./05-功耗.md)。Q 序列即结构，供 atlas 同源直读。

**Q1: 一次 HTTPS 请求应该按哪些分段计时？TTFB 为什么不能单独证明服务端慢？**

非双工请求按顺序观察：调用入队（Dispatcher 排队）→ 代理选择与 DNS → 路由尝试 → TCP 加 TLS 或 QUIC 加 TLS → 请求头与请求体 → 响应头 → 响应体 → 反序列化与界面更新。各段用事件边界度量：Dispatcher 排队用 `dispatcherQueueStart`/`dispatcherQueueEnd`，DNS 用 `dnsStart`/`dnsEnd`，建连与 TLS 分别用 `connectStart` 到 `secureConnectStart` 和 `secureConnectStart`/`secureConnectEnd`，响应头等待从请求发送结束到 `responseHeadersStart`。缓存命中或连接复用会让 DNS 与 connect 事件缺席，重定向、路由回退与重试会让某些段出现多次——监控要按 attempt 保存事件序列，不能假定每种事件只出现一次。

TTFB 的起点在不同平台口径不同：从 `callStart` 起算包含排队、DNS、建连、握手与上传；从请求发送结束起算才接近"网络往返加服务端"。TTFB 高可能来自客户端排队、边缘节点排队、CDN cache miss 或源站处理，必须结合服务端 trace、`Server-Timing`、CDN 缓存状态与客户端分段计时才能归因。`responseHeadersStart` 表示开始读响应头，不等于业务已拿到可展示数据；OkHttp 的 `callStart` 在 `enqueue()`/`execute()` 后即触发，网络完成到业务可用之间还有解析与 UI 提交。

**Q2: 主线程发起网络会抛 `NetworkOnMainThreadException`，但"主线程等待后台网络结果"为什么同样危险？BlockGuard 覆盖哪些入口？**

危险在于结果相同——主线程被网络往返阻塞，造成卡顿甚至 ANR。`Future.get()`、`CountDownLatch.await()`、`runBlocking` 等同步等待不会触发任何异常，因为它们不是网络调用，而是阻塞在锁或队列上；Perfetto 里主线程出现 `nativePollOnce` 通常只说明 Looper 在等消息，只有调用栈、线程状态与网络 slice 时间重叠共同指向等待点时，才能判断 UI 在等网络。

直接发起网络的检测由 BlockGuard 提供。AAOS13 源码核对（`libcore/ojluni/src/main/java/java/net/Inet6AddressImpl.java`）：`lookupHostByName()` 在读 DNS 缓存之前就调用 `BlockGuard.getThreadPolicy().onNetwork()`，所以主线程即使命中缓存也会抛异常；缺 `INTERNET` 权限时 `getaddrinfo` 返回 EACCES/EPERM，被转成带提示的 `SecurityException`。`BlockGuardOs`（`libcore/luni/src/main/java/libcore/io/BlockGuardOs.java`）在 connect、阻塞 poll、recvmsg 等入口都有 onNetwork 守卫，但 JNI 直接 I/O 可能绕过部分检测——检测机制不是安全边界。

**Q3: HTTP/2 与 HTTP/3 在同连接并发与丢包处理上的本质区别是什么？"上了 HTTP/3 就一定更快"错在哪？**

HTTP/2 用 HPACK 压缩头部、把多个 stream 复用进一条 TCP 连接，减少了 HTTP/1.1 时代为并发而开多条连接的开销；但 TCP 按字节顺序交付，任一 stream 的数据丢失会让同连接上所有 stream 等待重传（队头阻塞）。HTTP/3 把 HTTP 映射到 QUIC stream（基于 UDP），某个 stream 丢失的数据只阻塞它自己，头部压缩换成 QPACK，且协议带 Connection ID 与路径验证能力，IP 或端口变化后有机会迁移连接。

"一定更快"不成立：HTTP/3 的共享拥塞控制窗口、设备 CPU、服务器调度与 UDP 路径仍是整条连接的共享资源，有丢包时不保证快于 HTTP/2；连接迁移能否成功还取决于 provider 配置、服务器支持、NAT、VPN 与中间网络，Wi-Fi 与蜂窝切换时请求仍可能失败。发布 HTTP/3 要按协商后的协议（不是"已启用"配置值）、首次连接与会话恢复、网络与地区分组观察 P95/P99、失败率与回退率，服务端要正确发布能力并允许 UDP 路径，客户端保留 HTTP/2 回退。

**Q4: TLS 1.3 的 0-RTT early data 为什么只能承载能容忍重放的操作？QUIC 连接迁移是无条件的吗？**

0-RTT 让客户端在恢复连接的握手中提前发送 early data，省一次往返；代价是这份数据可能被攻击者截获后原样重发（重放攻击），安全属性弱于新握手后的数据。RFC 8446 要求应用协议自行评估重复执行的后果，业务条件应写成"该请求被重复执行也不会产生不可接受后果"——不能简化成 GET/HEAD 白名单：GET 也可能消费一次性令牌或触发计数，带幂等键的 POST 反而可以容忍。支付、发帖、创建订单等操作要等握手完成或依赖服务端幂等键与去重记录。0-RTT 还需要会话状态、客户端允许与服务端接受同时成立，服务端可以拒绝，正确性不能依赖它一定成功。

连接迁移同样有条件：QUIC Connection ID 允许 IP/端口变化后经新路径继续，但迁移能否成功取决于 provider 配置、服务器支持、路径验证与中间网络，切网时仍会失败。业务层要保留取消、重试与幂等处理，不能把迁移理解成无感知切换。平台边界：Android 10 起平台 TLS 1.3 默认启用，但基于 socket 的平台 TLS API 不支持 0-RTT（按官方文档口径）；OkHttp 5.3.0 的稳定配置没有 HTTP/3 与 early data 开关，Cronet 用 `QuicOptions.Builder.enableTlsZeroRtt()` 与 `addAllowedQuicHost()` 控制（按材料转写）。

**Q5: 为什么整个进程要共享一个 OkHttpClient？连接池默认的"5 和 5 分钟"是什么口径，一次连接复用要满足什么条件？**

每个 OkHttpClient 拥有独立的连接池与线程资源：每次请求新建 client 会丢失连接复用机会并留下空闲资源。不同超时或拦截器需求用 `newBuilder()` 从共享 client 派生——派生 client 共享连接池和线程；只有代理、信任管理器、证书固定或 DNS 相互冲突时才需要真正独立的 client。

"5 和 5 分钟"是 OkHttp 5.3.0 默认最多保留 5 条空闲连接、每条空闲连接 keep-alive 5 分钟——它是空闲连接上限，不是连接总数、域名数或并发上限；正在承载 HTTP/2 stream 的连接不算空闲。调参前先统计新建连接率、空闲回收与服务端 keep-alive 策略，不要凭经验数字扩大连接池。

一次复用要满足完整 `Address` 条件：scheme、端口、代理、DNS 结果、socket/TLS 配置、hostname verifier 与 certificate pinner 全部一致；HTTP/2 跨主机 connection coalescing 还要求现有连接指向同一 IP/端口、证书覆盖新主机且校验与 pin 兼容——两个域名不保证共享连接。OkHttp 5 默认启用 fast fallback 并行尝试多路由以降低 IPv6/IPv4 等待，一次 Call 会出现多组 connect 事件，监控按 attempt 分别保存。"预热"是一笔真实成本：发送 HEAD 或空 GET 产生 DNS、建连、TLS、流量与电量开销，后续请求还可能因网络切换、authority 不同或空闲回收而无法复用；DNS 预解析只省 resolver 段，完不成 TCP/TLS 握手。

**Q6: OkHttp 的 `callTimeout`、`connectTimeout`、`readTimeout`、`writeTimeout` 分别约束哪一段？弱网下把超时一律调大或调小各有什么问题？**

四者是不同层级的期限（OkHttp 5.3.0 默认 connect/read/write 各 10 秒，默认没有覆盖整个 Call 的总期限）：`callTimeout` 覆盖整个调用，包括 DNS、建连、写入、服务端处理、读取、重定向与内部恢复；`connectTimeout` 只约束新 TCP socket 的连接阶段，不约束 DNS 与整体；`readTimeout` 约束 socket 上单次读取操作之间的间隔，不等于整个响应体的期限；`writeTimeout` 约束单次写入操作，不等于上传业务的完整截止时间。交互接口需要明确的总期限；大文件上传适合分片加断点续传；长连接与流媒体按心跳或 segment 设计；后台同步用 WorkManager 的网络约束与重试调度。

一律调大超时会延长用户等待并占用并发资源（Dispatcher 与连接被慢请求占满）；一律调小会在尾部网络上放大失败与重试。正确做法是按接口 SLO、用户等待预算、请求体大小与可恢复方式分别设定，并记录每次超时发生在哪一段，再调整对应边界。

**Q7: 判断"失败后能不能自动重试"的依据是什么？"请求体已发出后连接中断"为什么最危险？**

依据是失败位置决定了服务端是否可能已经执行业务：DNS 失败或尚未发出请求的连接失败，服务端大多没收到业务请求，可以让网络库尝试其他地址或路由（受总期限约束）；TLS 证书、主机名或协议校验失败属于安全配置或中间网络异常，应停止盲目重试并保留错误分类；请求体发送后连接中断时，客户端不知道服务端是否已执行，最危险——必须查询业务状态或依赖幂等键去重，不能直接重发；HTTP 408、429、503 表示服务端可能允许稍后尝试，按接口契约和 `Retry-After` 决定；响应体中途失败时已收到部分数据，支持 Range/ETag 的下载可续传。HTTP 方法名只是线索：声明为 PUT/DELETE 的接口仍可能有审计或通知副作用，写操作的安全要靠服务端幂等键。

重试的节律也要受控：指数退避加随机抖动，受尝试次数、总期限、前后台状态与用户取消约束；网络恢复时不要让所有挂起请求同时重发。OkHttp 的 `retryOnConnectionFailure` 默认开启，处理路由与连接层恢复，重定向和认证也会在一个 Call 内产生 follow-up——应用层重试叠加上去时要把网络库 attempt 与业务 attempt 分开记录，避免重试次数相乘；Interceptor 内阻塞等待退避会占用执行资源，重试编排更适合放在上层或 WorkManager。

**Q8: HTTP 连接复用、TLS 会话恢复与 TLS 1.3 0-RTT 三者有什么区别？客户端持有 session ticket 就一定能恢复吗？**

三者的传输层与握手行为不同：HTTP 连接复用不新建传输层连接、也不重新握手，原连接仍可用时直接发新请求；TLS 会话恢复要新建连接并重新握手，但用 PSK 或缓存的 session state 缩短协商；0-RTT 是恢复握手中提前发送 early data，还要叠加网络栈、服务端与业务语义允许（重放边界见上一问）。复用命中时，DNS、TCP、TLS 四段全部跳过——这通常比微调加密算法更值得检查。

会话恢复不保证发生：服务端重启、保护 ticket 的密钥轮换、负载均衡把请求转到其他节点、ticket 过期，都会让这次连接退回完整握手；只看客户端的 `secureConnectStart`/`secureConnectEnd` 无法可靠判断是否恢复，要结合 TLS 库日志或服务端的完整/恢复握手指标。TLS 1.3 完整握手让客户端在首个 ClientHello 携带 key share，一个往返后即可发应用数据（TLS 1.2 通常按两个往返理解）——这是消息路径比较，不能换算成固定毫秒数。

**Q9: targetSdk 决定的明文流量默认值是什么？Network Security Config 还能管什么，证书固定为什么不是默认推荐？**

Android 9（API 28）起 targetSdk 28 及以上的应用默认 `cleartextTrafficPermitted=false`，targetSdk 27 及以下默认 true；Network Security Configuration 自 Android 7 起可按域名配置明文、信任锚、调试证书与证书固定。注意这是 targetSdk 默认值：第三方库或 native 网络实现是否查询 `NetworkSecurityPolicy` 要核对对应代码，不能假定所有网络路径都遵守。从 HTTP 迁移应直接配置 HTTPS URL——先 HTTP 再跟随 301/302 会多一次明文请求并在重定向前暴露请求元数据；WebView 的 mixed content 是另一组配置。

证书固定（certificate pinning）官方不建议作为一般应用的默认方案：服务端证书或 CA 轮换处理不当会让应用失联。威胁模型确需 pinning 时，要准备备用 pin、失效时间、轮换演练与远端恢复方案。删除证书校验、信任所有证书或放宽主机名校验都不属于性能优化。HPKE 的版本层次：Android 15 加 `HpkeSpi`（provider 实现 SPI），Android 17 才有应用层 `Hpke`/`Sender`/`Recipient` API 且只支持 base mode（不认证发送方）——两条路径在 Android 13 上都不存在，按材料转写。

**Q10: Android 17 的 Encrypted Client Hello 解决什么问题？一次连接真正发出 ECH 要同时满足哪些条件，"失败会静默降级"可靠吗？**

普通 TLS ClientHello 明文暴露 SNI（目标主机名）等元数据；ECH（RFC 9849）把敏感内容放进加密的 inner ClientHello，外层保留路由与兼容协商所需信息——ECH 不等于隐藏全部访问行为，观察者仍可依据 IP、流量形态和 DNS 看到部分元数据。生效需要四个条件同时成立（按材料核对 Android 17 行为，Android 13 无 ECH）：网络库已接入平台 ECH 能力；DNS 或网络库拿到服务端可用的 ECHConfig（含公钥与算法参数，常由 DNS HTTPS 资源记录分发）；终止 TLS 的 CDN、代理或服务节点支持对应配置；连接路径没有绕过平台网络安全策略。`<domainEncryption>` 提供 enabled/disabled 模式，enabled 在有 ECHConfig 时要求使用 ECH、没有时发送 ECH GREASE 占位扩展；disabled 则两者都不做。

"静默降级"不可靠：材料按 AOSP `android-17.0.0_r1` 核对，Conscrypt 的 `SSLParametersImpl.getEchOptions()` 依据网络安全策略生成选项，`Platform` 把配置不匹配包装为 `EchConfigMismatchException`（可携带服务端返回的重试配置）——网络库可能按重试配置重连，也可能把失败交给调用者，应用不应假定平台总会回退普通 TLS。性能评估分两段：HTTPS 资源记录查询是否增加等待取决于缓存与解析器实现（不能统一写成"多一次 DNS RTT"）；ClientHello 的 HPKE 加密只在新握手中执行。

**Q11: Android 17 的 Certificate Transparency 什么条件下默认开启？为什么"至少两个 SCT"不是完整策略？**

CT 通过公开日志与 SCT（签名证书时间戳）留下可审计的签发记录，用于发现误签或恶意签发；CA 签名本身只能证明证书追溯到受信根。默认值由运行系统与 targetSdk 共同决定（按材料核对）：Android 16 允许应用选择启用（opt-in）；应用运行在 Android 17 且 targetSdk 37 及以上时平台默认启用。运行在旧系统上的同一 APK 拿不到 Android 17 的平台 CT 验证，targetSdk 低于 37 也不能凭"设备是 Android 17"推断已开启——Android 13 上两者都不适用。

Network Security Config 有一个容易遗漏的分支：当前域显式启用 CT 才执行；当前域使用用户证书或应用配置了自定义信任锚时默认不执行 CT；其余继承上层。私有 PKI 与抓包调试环境常落入第二种情况——同一应用的公网站点执行 CT、企业根证书的内网站点不执行。完整策略按 SCT 交付方式、证书有效期、日志状态与运营者判断：嵌入证书在有效期不超过 180 天时需要 2 个不同合格日志的 SCT、超过 180 天需要 3 个，且覆盖至少 2 个日志运营者；OCSP stapling 或 TLS 扩展方式需要至少 2 个合格日志的 SCT——日志清单会变化，不要把数字固化成永久服务端规则。CT 检查在本地验证握手携带的证书、OCSP 响应或扩展，不应按"额外一次网络请求"估算；迁移期更常见的影响是握手直接失败（SCT 缺失、日志状态不满足、证书链发送错误）。

**Q12: 用 OkHttp `EventListener` 做网络监控要注意什么？`NetworkCallback` 的 `VALIDATED` 能证明业务域名可达吗？**

EventListener 的使用约束：每个 `Call` 要由 `EventListener.Factory` 创建独立 listener 实例（事件携带并发状态）；回调必须快速返回，不能做磁盘或网络 I/O，也不能重新进入同一个 client——事件先写无阻塞队列，由后台消费者批量处理。DNS、connect、请求与响应事件可能因重定向、fast fallback 和重试重复出现，要追加到 attempt 列表；连接复用时 DNS 与 connect 缺席是正常结果。指标要限制基数并保护隐私：记录白名单映射的接口模板、协议、状态码与错误类别，完整 URL、query、header、请求体与 token 不进性能日志。计时用单调时钟；Perfetto 不会自动展开 OkHttp Call，需要用 AndroidX Tracing 异步 slice 标记逻辑调用并用唯一 cookie 区分并发请求。

`VALIDATED` 不能证明业务可达：`INTERNET` 是能力声明，`VALIDATED` 是系统对公网探测点的结论，业务请求成功还取决于目标域名、路由、证书、CDN 与服务端。`NetworkCapabilities.getLinkDownstreamBandwidthKbps()` 返回的是设备到所接网络的第一跳带宽估计，不是到目标服务的吞吐；`SubscriptionInfo` 的流媒体速率上限（Android 17 新增，按材料核对）返回 `BITRATE_UNKNOWN` 时也不是测速值。这些平台状态只作为请求策略输入；后台任务关心"有网或非计费网"时优先用 WorkManager/JobScheduler 约束，网络切换后不要统一清空连接池或立即重放全部失败请求。

**Q13: HTTP cache 与业务离线数据各管什么？`onlyIfCached()` 在缓存缺失时返回什么？**

OkHttp cache 遵守 HTTP 缓存语义：客户端只保存符合 `Cache-Control`、`ETag`、`Last-Modified`、`Vary` 规则的响应，服务端负责正确返回这些头。它不能替代 Room、SQLite 或文件层的业务离线数据——后者承载业务状态与查询能力，前者只缓存 HTTP 响应。

离线时若产品允许使用过期但可接受的 stale 响应，可显式构造只读缓存请求：`CacheControl.Builder().onlyIfCached().maxStale(...)`。cache miss 时该请求得到 504 `Unsatisfiable Request`，不会自动访问网络——UI 要区分"没有缓存""缓存过旧""请求失败"与"已展示旧数据并刷新中"四种状态。弱网降级（已有缓存、低分辨率、小分页、暂停自动播放）的输入应结合用户设置、metered、漫游、系统估计与近期请求观测，并用滞回（升降级不同阈值）避免画质频繁切换；同一 Wi-Fi 可能拥塞、蜂窝也可能吞吐良好，transport 标签不能直接当质量判据。

**Q14: "netd 负责 Android 的 DNS"错在哪？DNS resolver 从 netd 到独立模块经历了怎样的迁移？**

错在混淆了两个服务。Android 17 的 resolver 源码位于 `packages/modules/DnsResolver`，native netd 位于 `system/netd`（两个目录都不在本地 AAOS13 树，源码结论按材料 Android 17 语境转写）：netd 负责创建网络、路由、接口、权限与转发规则；DNS Resolver 模块按 `netId` 保存解析配置与缓存、执行查询和 Private DNS。`ConnectivityService` 在同一网络生命周期里分别调用两者——创建时 `mNetd.networkCreate()` 加 `mDnsResolver.createNetworkCache(netId)`，销毁时对应 destroy。

迁移路径（按材料核对）：Android 9 及更早，resolver 代码分布在 Bionic 与 netd，Java 查询可经本地代理 `dnsproxyd`；Android 9 引入用户侧 Private DNS 设置（基于 DoT）；Android 10 resolver 迁入 `system/netd/resolv` 并以 `com.android.resolv` APEX 交付，直接服务 `/dev/socket/dnsproxyd`，resolver 配置的 Binder 入口也从 netd 移入模块；Android 17 当前实现位于 `packages/modules/DnsResolver`，接口仍是 `IDnsResolver`。模块化允许通过 Mainline 更新解析器而无需完整 OTA，但普通应用没有获得全局 DNS 控制权——不能清空所有网络的 resolver 缓存、不能改别的网络的 DNS server、不能操纵 Private DNS 校验状态。

**Q15: `DnsResolver` 的 Looper、Executor 与 CancellationSignal 分别控制什么？`query()` 与 `rawQuery()` 的错误信息差别为什么重要？**

三者控制不同的纬度：Looper（Android 17 新增 `DnsResolver(Context, Looper)` 构造引入，`getInstance()` 同版本废弃，按材料核对）用来监视 resolver 文件描述符的可读事件；查询方法中的 Executor 决定结果回调在哪个执行环境运行——两个线程参数不能互相替代；`CancellationSignal` 让调用方取消异步查询，页面退出、请求取消或网络会话失效后继续等旧查询只增加无效工作。解析入口还有 `InetAddress.getAllByName()`/`Network.getAllByName()`（传入明确 `Network` 时用该网络的 resolver 配置，未指定则跟随默认网络）与 native 的 `android_getaddrinfofornetwork()`。

错误信息差别影响诊断：`query()` 返回整理后的 `InetAddress` 列表，`DnsResolver.Callback` 能区分成功与 `DnsException`；`rawQuery()` 还提供 DNS rcode 与原始应答报文。而 `InetAddress` 与 OkHttp 常规路径把多种失败折叠成 `UnknownHostException`——不能从这一个异常反推 NXDOMAIN、SERVFAIL、超时还是本地策略拒绝。`FLAG_NO_CACHE_LOOKUP`、`FLAG_NO_CACHE_STORE`、`FLAG_NO_RETRY` 是诊断或特定协议用途：旁路缓存会增加延迟、流量与 resolver 压力，不适合为"更实时"长期全量开启。

**Q16: 切网后"域名已解析到新地址、请求却还在走旧链路"是怎么回事？系统怎么组织 DNS 缓存与配置？**

配置与缓存都按网络隔离。`LinkProperties` 更新后，`ConnectivityService.updateDnses()` 把变化交给 `DnsManager.noteDnsServersForNetwork()`，后者生成 `ResolverParamsParcel` 经 `IDnsResolver.setResolverConfiguration()` 写入对应 `netId`（参数含 DNS server、搜索域、采样与超时配置、Private DNS 信息；这条链路在 Android 17 源码核对、目录不在本地树）；resolver 模块为每个 `netId` 维护独立缓存，Wi-Fi 与蜂窝不会共用解析状态。Java 侧同样如此——AAOS13 源码核对，libcore 的 `Inet6AddressImpl` 地址缓存以 (host, netId) 为 key，`DnsManager` 还会发受权限保护的 `ACTION_CLEAR_DNS_CACHE` 让各进程丢弃 VM 缓存旧结果。

旧链路问题的根源通常不是 DNS 而是连接复用：清理 resolver 或 VM 缓存不会关闭 OkHttp 连接池里已建立的 socket，域名解析到新地址后，复用的旧连接仍发往旧网络。排查时回看 connect 事件、目标地址与 socket 绑定的 `Network`，而不是怀疑 DNS 污染。应用自定义缓存要遵循同一边界：只以 hostname 作 key 会让旧网络的地址在新网络继续使用，VPN 分流与企业域名尤其受影响。

**Q17: Private DNS 与应用自带 DoH 各保护哪一段？接入应用 DoH 要处理哪些边界？**

Private DNS（Android 9 引入的用户设置）保护的是本机 resolver 到上游 DNS provider 之间的 DNS 流量；它不替代 HTTPS，也不隐藏 TLS ClientHello 里的 SNI（那是 ECH 的职责，见前文）。材料按 Android 17 核对：resolver 内部同时存在 DoT 与 DoH 的配置、验证与统计代码（含 `packages/modules/DnsResolver/rust/src/doh/`），但应用从 `InetAddress`、OkHttp `Dns` 或普通 `query()` 回调无法可靠判断某次查询走 DoT 还是 DoH——可观测的公开状态是 `LinkProperties` 中 Private DNS 是否生效、provider name 与已验证服务器，报告写"Private DNS 状态"即可，不要在没有平台证据时写死传输协议。

应用自带 DoH 是另一套解析策略：自行选择服务端、缓存、bootstrap 与 fallback，可能绕开系统 Private DNS、VPN DNS、企业 split DNS 与 captive portal 的预期路径。接入边界：公网固定域名可按业务策略用应用 resolver，企业内网与 VPN 域名优先遵循系统策略；fallback 是否允许从加密解析切回系统 DNS 由安全与隐私策略定义；DoH 服务自身域名的解析不能再次调用同一个业务客户端，否则形成无法完成的递归依赖，要用独立、最小化的 bootstrap 路径。

**Q18: DNS 故障诊断应收集哪些系统证据？resolver 的 querylog 与 server 统计能回答什么、不能回答什么？**

先确认请求是否真的停在 DNS：按顺序记录 DNS 开始/结束/失败、connect 开始与目标地址、TLS 握手、HTTP 首字节、取消与切网事件——复用已有连接时没有 DNS 事件属正常；DNS 快而 connect 超时应查路由与地址族，TLS 慢回 TLS 专项。系统侧三组证据：`dumpsys connectivity` 核对当前网络、`LinkProperties`、能力标志与 Private DNS 状态；`dumpsys dnsresolver` 列出各网络的缓存、DNS server 统计、搜索域与参数；`dumpsys dnsresolver querylog` 输出查询记录（Android 17 的 `DnsQueryLog` 会遮蔽 hostname 与地址，仍属受限诊断数据）。resolver dump 需要 `DUMP` 权限，普通第三方应用不能在生产设备自行执行。

`ResolverController::dump()` 的 server 统计（查询总数、成功、错误、超时、平均 RTT、server 状态）能回答"设备当前 resolver 是否集中失败"，不能替代应用侧分段计时——应用可能命中自己的缓存、等待线程调度或复用既有连接。`NetworkDiagnostics`（材料按 Android 17 核对）把探测 socket 绑定到指定 `Network`，对网关、DNS server 与测试地址做 ICMP、UDP DNS 与 DoT 探测，能缩小系统网络故障范围，但不能证明业务域名、CDN 或应用 HTTPDNS 正常。现象分流举例：`UnknownHostException` 增长先查解析入口与 resolver/HTTPDNS 结果，不推 NXDOMAIN；`.local` 失败先核对 targetSdk 37 的 `ACCESS_LOCAL_NETWORK` 权限与目标网络（Android 17 起 .local 解析受本地网络权限限制，A13 无此权限），再判断 resolver 故障；VPN 下公网正常内网失败，查 VPN DNS、split DNS 与绑定的 `Network`。指标按解析来源、缓存状态、传输类型、查询类型与 rcode 分组聚合，分位数服务于 SLO——低流量域名的 p99 波动大，固定套用制造噪声；`netId` 会被系统复用，长期聚合用进程内递增的网络会话号，无盐哈希 hostname 在候选域名很少时可被离线枚举，不算匿名化。

**Q19: 用 OkHttp 自定义 `Dns` 接 HTTPDNS 时，缓存 key、TTL 与 bootstrap 有什么约束？为什么 URL 不能改成裸 IP？**

`Dns.lookup(hostname)` 是同步接口且可能被多请求并发调用，实现边界：优先读线程安全的内存缓存；缓存 key 至少包含 hostname 与网络会话（必要时加地址族与用户网络策略），避免旧网络地址跨网络复用；TTL 使用 DNS/HTTPDNS 服务返回的有效期，对负缓存（域名不存在或失败结果）单独设策略；缓存缺失时同步访问 HTTPDNS 的耗时会进入建连前的 DNS 阶段；异步预取由明确业务触发、过期结果不无限续用；持久化地址只适用于能正确保存 TTL、网络分区与数据版本的设计，默认用内存；系统 fallback 是否允许由可用性、隐私与企业网络策略共同决定。HTTPDNS 客户端要独立、最小化 bootstrap，不能递归调用同一个自定义 `Dns`。

连接仍要保留 hostname：URL 改成裸 IP 会破坏 HTTP Host、TLS SNI 与证书主机名校验的一致性——把 URL 换成 IP 再关闭主机名校验属于安全缺陷。正确做法是连接层用解析出的 IP、URL 与校验层保持域名。连接池还会改变 DNS 统计：请求复用现有连接时不调用 `lookup()`；同一域名多 IP 时连接策略决定尝试顺序与回退。

**Q20: 网络性能日志应该记录什么、不应该记录什么？OkHttp、Cronet 与平台 `HttpEngine` 的选型边界是什么？**

日志记录低基数分组字段：白名单映射的接口模板、协议、状态码、错误类别、时间分段、metered/roaming、缓存命中；完整 URL、query、header、请求体、响应体、Cookie、Authorization 与 token 不进入性能日志。CDN 观测也走白名单：记录协议与 IP family、POP/cache 状态响应头白名单字段、各分段耗时——客户端很难仅凭 TTFB 区分边缘排队、cache miss 与源站处理，需要 CDN 日志与服务端 trace ID（白名单传递）配合。

选型边界（按材料核对）：OkHttp 自管连接池、TCP 经 `java.net.Socket`、TLS 经平台 JSSE/Conscrypt，5.3.0 的稳定协议栈是 HTTP/1.1 与 HTTP/2；Cronet 使用 Chromium native 网络栈，需要 HTTP/3 时评估 Play services 依赖（`CronetProviderInstaller.installProvider()` 处理缺失与更新，fallback 实现能力较弱不能预设同等表现；一个进程通常只建一个 `CronetEngine`，多个 engine 不能共用 storage directory）；API 34 起的 `HttpEngine` 使用设备提供的实现。主线程禁网与等待、EventListener 口径对三者一致适用；第三方依赖的版本与 provider 可用性要在运行时观测，协议协商结果以线上分组为准。
