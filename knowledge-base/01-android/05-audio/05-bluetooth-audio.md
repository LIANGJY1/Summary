# 蓝牙音频

> 本文按延迟测量、LE Audio 传输模式、编解码卸载、应用控制、助听器配置、经典蓝牙通话切换和音量同步整理蓝牙音频问题。Q1 从 `03-ui/04-window-system.md` 的音频部分迁入，Q2–Q6 由 `12-performance/21-energy-efficiency.md` 的 LE Audio 内容整理；原始问题与补充说明均在本册保留并重新划分边界。本文的 Android 接口说明以公开 API 契约为准，AOSP 实现细节需结合目标分支和厂商实现核对。

**Q1: [learning] 用 LDAC 或 aptX 时，为什么不能按编解码器名称套固定延迟？必须经蓝牙出声的产品该怎样验证？**

编解码器名称不能推出端到端延迟，因为总延迟还受手机与耳机缓冲、无线调度、链路质量和耳机后处理影响。产品应在目标手机、耳机、协商配置和使用场景下测声学端到端延迟，并分别报告典型值、尾部值和断续情况。

1. **区分延迟来源：**编码器帧长只是预算中的一项。分包与发送调度、接收抖动缓冲、解码、耳机 DSP 和声学输出都会增加时延。即使编解码器相同，耳机固件、音质或低延迟模式、缓冲策略和射频环境不同，结果也可能不同。因此，“LDAC 固定 30–50 ms”或“aptX 固定 50–80 ms”不是 Android 平台或某条具体链路的保证。
2. **固定测量条件：**记录手机型号与系统版本、耳机型号与固件、实际协商的编解码器和模式、连接状态以及无线环境。不能仅依据开发者选项中手工选中的值推断最终协商结果。
3. **测量声学端到端结果：**使用高速摄像、外部采集设备或声学回环，测量应用发出可识别信号到耳机实际出声的间隔。报告中位数、P95/P99 等尾部延迟和丢音/断续率，避免只给单次最好成绩。
4. **按交互场景选路径：**节奏游戏、虚拟乐器等对反馈时序敏感的场景，内置扬声器或有线/USB 音频通常更容易获得可控结果。必须支持蓝牙时，应按目标设备实测后校准或补偿，并允许用户切换输出路径。

手机侧启用 FastMixer 或 MMAP 不能消除蓝牙无线传输和耳机端缓冲，它们改善的是本机音频路径的一部分，不是整条蓝牙链路的时延保证。

**Q2: [learning] LE Audio 使用 7.5 ms LC3 帧时，为什么不能据此推出端到端延迟是 20–40 ms？**

LC3 帧时长描述编码帧覆盖的音频时间，不等于编解码算法延迟，更不等于手机到耳机的声学端到端延迟。稳态单向延迟要把发送端、ISO 传输和接收端预算一起计算，并用外部测量确认。

1. **发送端缓冲：**应用或 AudioTrack、AudioFlinger 和音频 HAL 可能各自积累数据。实际深度由流类型、缓冲配置和厂商实现决定，不能只用应用缓冲估算。
2. **编码与组帧：**编码器必须收集一帧所需的采样再产生编码数据。7.5 ms 或 10 ms 是常见 LC3 帧时长，但采样率与帧内采样数也影响对应的实际时长。例如 44.1 kHz 下，按 BAP 配置使用的帧样本数换算后，时长可能与名义值略有差异。
3. **ISO 发送与同步：**CIS 或 BIS 的发送间隔、控制器调度、允许的重传和 QoS 配置都会影响数据何时到达。Presentation Delay 是同步播放时间安排的一部分，接收端会按协商值保留数据以便同步，不是可以从 LC3 帧长直接推出来的常数。
4. **接收端渲染：**耳机还要接收缓冲、解码、执行本地后处理并驱动扬声器。目标耳机可能为稳定播放或多耳同步增加额外缓冲。
5. **先确定测量口径：**冷启动延迟、已连接后的启动延迟、稳态单向延迟、双向往返延迟、路由切换间隙和抖动不是同一指标。报告结果时必须说明起点、终点及连接状态。
6. **测量完整链路：**对稳态单向延迟，可发送脉冲或 MLS 等已知波形，用外部声卡对输入与耳机声学输出做互相关，并报告中位数与 P95/P99。logcat 中的“stream started”是软件控制面的状态，不包含其后的传输等待、耳机缓冲和声学渲染。

LC3 帧时长可用于解释预算的粒度，不能代替对目标手机、耳机和链路的实测。

**Q3: [learning] LE Audio 单播 CIS/CIG 与广播 BIS/BIG 在可靠性和扩展性上有什么区别？**

单播 CIS 面向特定接收设备，控制器可以依据该链路的 QoS 和重传配置安排链路层重传。广播 BIS 面向多个接收者，没有针对单个接收者的确认反馈。广播因此便于一对多分发，但发送端不能获知某一接收者的丢包情况并为它单独补发。

1. **单播 CIS/CIG：**CIG 组织一个或多个 CIS。接收端和发送端使用点对点的等时链路，控制器可在允许的等时事件与重传预算内重发未成功的数据。增加设备、流或方向可能需要更多 CIS 和控制器时隙，是否能容纳取决于控制器资源、PHY、QoS 和设备支持，不能简单按设备数线性估算。
2. **广播 BIS/BIG：**BIG 组织一个或多个面向广播的 BIS。广播没有每个接收者单独返回的链路层确认，但发送端可按配置重复发送数据以提高接收概率。重复发送能提升总体鲁棒性，却不能根据某个听众的接收情况做定向重传。接收设备仍要扫描并完成周期广播与 BIG 同步，因此加入广播也有耗时和功耗成本。
3. **评估可靠性：**丢失单个包不一定形成可闻断音，听感还受 LC3 丢包隐藏、接收缓冲和连续丢包长度影响。连续丢包或超出接收端恢复能力时才更容易出现可闻缺口。
4. **评估扩展与功耗：**广播适合向多个接收者分发相同内容，发送计划不必为每个听众建立一条独立的点对点确认链路。单播适合需要针对设备协商配置、双向控制或按连接管理的场景。不能据此推断广播在所有设备上都更省电，必须实测发送端和接收端的功耗。

ACL 控制连接与 ISO 数据流承担不同职责，不能把“ACL 断开”简单等同为所有 CIS 立即以同一种方式终止。需按目标 Bluetooth Core 版本、连接状态和实现检查控制面与等时流的实际状态。

**Q4: [learning] 手机有音频 DSP，LE Audio 编码就一定由硬件 offload 吗？怎样判断它对功耗的影响？**

有音频 DSP 不代表当前 LE Audio 流已 offload。必须同时满足平台配置、Bluetooth Audio HAL 能力、控制器数据路径支持和当前流配置匹配等条件。功耗收益也要在目标设备的实际活动状态下测量。

1. **识别数据路径：**AOSP Bluetooth Audio AIDL 的 SessionType 区分 LE Audio 单播软件编码/解码、单播硬件 offload 编码/解码、广播软件编码和广播硬件 offload 编码。硬件 offload session 表示编码或解码数据路径由硬件承担，Bluetooth 栈仍负责控制与会话管理。
2. **核对启用条件：**AOSP Bluetooth 模块的 codec manager 会检查 `ro.bluetooth.leaudio_offload.supported`、`persist.bluetooth.leaudio_offload.disabled`、HAL 验证结果和控制器 `CONFIGURE_DATA_PATH` 能力。当前主线源码中，前者缺省为 `false`，后者缺省为 `true`，所以未显式启用或未满足能力检查时不能假设 offload 生效。具体分支和厂商属性仍须查目标设备源码与属性值。
3. **核对本次流配置：**即使平台启用了 offload，当前编解码器、采样率、帧时长、声道分配和方向还必须落在 HAL/ADSP 报告的能力范围内。属性表示平台允许尝试，不等于每一条流都由 DSP 处理。
4. **从运行时证据确认：**检查 Bluetooth 栈的 codec location、会话类型、HAL 日志和数据路径状态。仅看芯片规格、产品属性或系统设置中的编解码器名称，不能证明本次会话使用了硬件路径。
5. **谨慎解释功耗：**offload 可能减少 AP 执行编解码和周期性处理的工作，使其更容易进入较深 idle，但仍有控制、数据搬运、射频和缓冲成本。AP 唤醒频率取决于实现和缓冲，不可把 10 ms 帧时长直接换算成 AP 固定每秒唤醒 100 次。
6. **验证收益：**对比同一设备、相同链路和相同播放条件下的 CPU 调度、wakeup source、AudioFlinger 活动与电源轨数据。分别确认 offload 是否生效以及系统总功耗是否下降，避免把相关性当作因果。

数据路径类型可在 Android 硬件接口仓库的 `bluetooth/audio/aidl/android/hardware/bluetooth/audio/SessionType.aidl` 查看。能力与运行时选择逻辑可在目标 Android 分支的 `packages/modules/Bluetooth/system/bta/le_audio/codec_manager.cc` 核对。

**Q5: [learning] 普通 Android 应用能控制 LE Audio 的哪些部分，哪些能力不能当作公开应用接口？**

普通应用可以播放媒体、申请通信路由并查询平台是否支持 LE Audio，但不能仅凭硬件支持状态强制某个耳机、编解码器或 Profile 成为当前路由。能力查询、端点可用性、系统策略和实际协商是不同层次。

1. **媒体播放：**音乐或视频应用继续通过 AudioTrack、Media3 等媒体 API 提交音频，由 Android 音频策略选择可用输出设备。应用通常不应通过隐藏 Bluetooth 接口直接控制媒体编解码器协商。
2. **通信路由：**API 31 起，通信应用可先用 `AudioManager.getAvailableCommunicationDevices()` 查询通信场景可选的输出端点，再将选中的 sink 传给 `setCommunicationDevice()`。系统会自动选择匹配的输入端点。通话结束或设备断开时应清除选择。API 33 的 Android BLE Audio 文档要求应用为兼容 BLE Audio 从旧的 `startBluetoothSco()` 迁移到该接口。
3. **硬件能力查询：**API 33 起，`BluetoothAdapter.isLeAudioSupported()` 和 `isLeAudioBroadcastSourceSupported()` 返回状态码而不是布尔值。`FEATURE_SUPPORTED` 表示相应硬件功能受支持，`FEATURE_NOT_SUPPORTED` 表示不支持，蓝牙未开启等情况还可能返回错误码。查询成功只说明设备侧能力，不保证已连接端点支持目标配置。
4. **确认本次可用端点：**检查系统当前提供的通信设备、耳机连接状态和音频路由变化。手机支持 LE Audio 不代表当前耳机、双方 Profile、系统版本、区域配置和产品策略都允许目标场景。
5. **区分应用与系统权限：**Bluetooth Profile proxy 适合读取 SDK 明确公开的连接信息，不代表普通应用可任意调用连接/断开、选择 codec 或更改系统 Profile 优先级。若方法标记为隐藏、系统 API 或受 `BLUETOOTH_PRIVILEGED` 等权限限制，就不能作为普通第三方应用的兼容性契约。

因此，应用应围绕公开的媒体与通信路由 API 设计降级路径，并监听设备可用性和路由结果。系统支持状态不能替代对实际端点和当前路由的确认。

**Q6: [learning] 助听设备使用 ASHA 或 HAP 时，为什么不能把 HAP 描述成“用 BLE 替代 Classic ASHA”？**

ASHA 本身就使用 Bluetooth Low Energy，而 HAP 是构建在 LE Audio 等时通道之上的标准助听设备配置。两者的链路、控制协议和能力模型不同，不能概括成从 Classic 蓝牙迁移到 BLE。

1. **ASHA 的链路：**Android 的 ASHA 实现通过 BLE 的 GATT 控制和面向连接的 L2CAP CoC 传输音频。CoC 可使用多个音频包的弹性缓冲抵御部分丢包，代价是增加端到端延迟。ASHA 没有规定从助听器向手机返回语音的音频上行链路，因此使用手机麦克风不能被描述成 ASHA 设备的统一双向通话能力。
2. **HAP 的链路与角色：**HAP 定义助听器生态中使用 LE Audio 等时通道的互操作要求，依赖 CAP、BAP、VCP、MICP、CSIP 和 GATT 等配置。HAP 规范还定义了可选的 CCP 角色，因此符合 HAP 不等于每个设备都必须实现同一种通话上行能力。实际麦克风来源和通话链路要看双方声明的角色与配置。
3. **Android 支持边界：**Android 13（API 33）加入平台级 LE Audio 支持，但单个产品是否支持 HAP、广播接收或特定双向音频配置，还取决于硬件、系统构建、耳机能力和产品策略。不能从“Android 13 支持 LE Audio”推出“所有 Android 13 手机和助听器都支持完整 HAP 功能”。
4. **产品验证重点：**助听场景应在目标手机和助听器上验证时延、左右同步、丢包恢复、通话麦克风路径与续航。协议名称本身不能保证某个固定延迟或省电比例。

ASHA 的 Android 平台机制见 AOSP 文档 `source.android.com/docs/core/connect/bluetooth/asha`。HAP 的角色和依赖关系以 Bluetooth SIG Hearing Access Profile 规范为准。

**Q7: [learning] 经典蓝牙耳机播放 A2DP 音乐时来电切到 HFP/SCO，为什么会短暂无声或仍从扬声器出声？**

A2DP 媒体与 HFP/SCO 通信使用不同的 Profile、链路和音频策略。来电期间，系统需要建立或切换通话链路并将通信流路由到目标设备。切换失败、尚未完成或应用继续请求旧路由时，就可能出现短暂无声、提示音漏播或声音走错端点。

1. **把切换看成异步过程：**经典 HFP 通话路由可能涉及媒体路径挂起、SCO/eSCO 音频链路准备和通信设备选择。旧版 `startBluetoothSco()` 文档明确指出建立连接可能需要数秒，调用返回不代表链路已就绪。应用应监听设备与通信路由变化，不要在发起请求后立即假定声音已到耳机。
2. **使用与系统版本匹配的路由 API：**API 31 起，VoIP 应用可从 `getAvailableCommunicationDevices()` 选择输出端点，再调用 `setCommunicationDevice()`，并确认当前通信设备确实切换成功。API 33 起为 BLE Audio 兼容应采用此路径。`startBluetoothSco()` 和 `stopBluetoothSco()` 从 API 34 起弃用，`setBluetoothScoOn()` 从 API 37 起弃用且对普通应用早已是 no-op。结束通话后调用 `clearCommunicationDevice()`，避免遗留路由请求影响其他应用。
3. **解释通话音质变化：**HFP 语音常使用 CVSD 窄带或 mSBC 宽带语音编码，其采样规格通常分别是 8 kHz 与 16 kHz。实际模式由设备协商决定。A2DP 音乐切入 HFP 后音质下降是不同 Profile 的带宽与语音编码选择造成的，不能按 A2DP 音质标准调优。
4. **保护切换期间的关键声音：**媒体挂起和通信路由建立之间可能存在空窗。短提示音如果恰在窗口内播放，可能被静音策略抑制或落到旧路由。对必须送达的提示，应等待通信端点确认后播放，或采用产品明确支持的独立提示路径。
5. **按现象定位：**“耳机已连但扬声器出声”优先核对 `getCommunicationDevice()`、可用通信端点和请求是否被接受。“有路由但短暂无声”优先检查 SCO 状态、切换时序和音频策略。“只有通话音质变差”先确认协商的 HFP 编码模式。

这些 API 处理的是通信场景的设备选择，不保证每个厂商设备都以同一时序完成 Profile 切换，仍要在目标 Android 版本和耳机上验证。

**Q8: [learning] 蓝牙耳机与手机的音量不同步时，怎样判断是 AVRCP 绝对音量映射还是本地音量控制问题？**

先确认当前媒体链路是否使用经典蓝牙 A2DP 的 AVRCP 绝对音量，再观察手机与耳机对同一次音量变化的响应。绝对音量启用时，两端需要同步音量状态和量程映射。关闭或不支持时，手机与耳机可能分别控制系统数字增益和耳机本地增益。

1. **限定适用范围：**AVRCP 绝对音量属于经典蓝牙媒体控制路径，不能拿它解释所有 Bluetooth Profile 或直接代表 LE Audio 的音量机制。先确认故障发生在 A2DP 媒体播放中，而不是 HFP 通话、系统提示音或其他输出设备。
2. **检查状态但不依赖私有字段：**可查看目标系统版本的 Bluetooth/audio dump 和日志中是否协商或启用了 absolute volume。旧版本或特定分支可能出现 `mAvrcpAbsVolSupported` 一类字段，但这不是稳定 SDK 契约，字段缺失或名称变化都不能作为功能不支持的证据。
3. **核对两端映射：**在固定媒体音量下，逐级调整手机音量并观察耳机按键、耳机实际响度和手机滑条是否同步。若滑条变化但耳机响度跳变、范围不一致或反向变化，问题更可能在音量量程映射或耳机固件的同步处理。
4. **做单变量 A/B：**可在开发者选项中暂时关闭“绝对音量”，断开并重新连接后重复测试。关闭后恢复正常，说明问题与绝对音量协商或两端状态同步相关。这只是定位手段，不是推荐用户永久关闭的修复方案。
5. **检查重连状态：**比较首次连接、断开重连和耳机重启后的初始音量。如果只有重连后不同步，检查手机和耳机是否各自持久化最后音量、重连时谁先上报状态以及状态更新是否被覆盖。

只有确认音量控制和 AVRCP 同步正常后，才需要继续检查音频增益或输出路径。编解码器与传输延迟通常不会直接造成音量状态不同步。
