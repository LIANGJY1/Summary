# 内核模块构建与部署

> 学习资料（文章模式沉淀）。边界：本文回答 Kconfig/Kbuild 如何选择内建、模块或关闭，外部模块如何匹配目标内核构建，`.ko` 的设备加载条件，以及驱动修改后的验证与清理流程。驱动运行时设计归 [../09-platform-native/02-driver-runtime.md](../09-platform-native/02-driver-runtime.md)。内核分支、GKI 与产品配置会改变工具链及模块策略，应以目标分支构建脚本为准。Q 序列即结构，供 atlas 同源直读。

**Q1: [learning] Kconfig 的 `bool`/`tristate` 和 Kbuild 的 `obj-y`/`obj-m` 怎样共同决定驱动是否进入内核或生成 `.ko`？**

Kconfig 声明功能开关、可选值与依赖，Kbuild 根据最终配置值选择目标。`bool` 通常只能取 `y` 或 `n`，`tristate` 可以取 `y`、`m` 或 `n`，分别表示内建、模块和不构建。

1. **配置声明：**在 Kconfig 中定义 `CONFIG_FOO` 及其类型和依赖。若依赖不满足，配置系统会限制或关闭该项，Makefile 即使引用它也不会生成预期目标。
2. **Kbuild 目标：**`obj-y += foo.o` 将 `foo.o` 纳入内核映像，`obj-m += foo.o` 将它构建为可加载模块。常用写法 `obj-$(CONFIG_FOO) += foo.o` 会按配置展开：值为 `y` 时加入内核，值为 `m` 时生成 `.ko`，值为 `n` 时没有目标。
3. **类型匹配：**`bool` 不能选择 `m`，适合只允许内建或关闭的功能。需要支持可加载形式时，配置项必须是 `tristate`，并且 Kbuild 规则与模块依赖也要支持该形式。
4. **工程接入：**新增驱动要同时把 Kconfig 文件接入上级配置树、把 Kbuild Makefile 接入上级构建树，再由产品 defconfig 或配置片段选择启用。只增加源文件不会自动把它纳入内核构建。

**Q2: [learning] 外部内核模块怎样通过 Kbuild 编译？为什么宿主机默认编译器和工具链不能直接用于设备模块？**

外部模块应调用与目标设备内核相匹配的 Kbuild，并提供已配置、已准备的内核构建树和模块源码目录。典型形式为 `make -C <kernel-build-tree> M=<module-source-dir> modules`，但实际架构与工具链参数必须沿用目标 Android 内核分支提供的构建脚本。

1. **`-C <kernel-build-tree>`：**让 make 先切换到目标内核源码或其输出构建目录，再由其中的 Kbuild 规则编译。该目录必须包含本次构建所需的内核配置和生成头文件。
2. **`M=<module-source-dir>`：**告诉 Kbuild 外部模块源码位于何处。它不同于内核树本身，也不会替模块补齐内核配置、导出符号信息或目标工具链。
3. **`modules`：**请求 Kbuild 执行外部模块构建目标，产物通常为 `.ko`。是否还需准备 Module.symvers、配置额外变量或运行 Android kernel build 脚本，取决于目标分支的构建流程。
4. **目标工具链：**`ARCH=arm64` 一类值选择目标内核架构，不能按执行构建的主机架构默认推断。`LLVM=1` 让 Kbuild 使用 LLVM 工具链。使用 GNU 交叉工具时，`CROSS_COMPILE` 提供 GNU 工具前缀。纯 LLVM 交叉编译通常不需要它，除非还要调用非 LLVM assembler 或工具。
5. **为何不能用主机默认值：**宿主机 GCC 可能产生错误架构或不兼容的对象文件。模块还必须匹配目标内核版本、配置、生成头文件、符号 CRC 与 ABI。Android kernel manifest 和产品构建脚本通常固定了可兼容的 Clang 版本与参数，应使用该路径，不要硬编码个人主机工具链。

**Q3: [learning] 外部模块 `.ko` 已经构建成功，为什么 Android 设备仍可能拒绝加载？**

主机生成 `.ko` 只证明模块通过了该次编译，不能证明设备正在运行的内核可以接受它。加载还取决于架构、内核配置和 ABI、符号依赖、模块装载策略、权限、SELinux 与部署位置。

1. **内核兼容：**核对模块的目标 ABI、`vermagic`、内核配置和 `Module.symvers`。启用 `CONFIG_MODVERSIONS` 时，内核会比较导出符号的 CRC，发现不匹配就可能拒绝模块。模块通常应由目标内核的同一构建或受支持的兼容构建产出。
2. **GKI 与 KMI：**使用 GKI 的 vendor module 只能依赖对应内核分支公开维护的 KMI 符号集合。一个分支的符号列表不代表另一个 Android Common Kernel 分支也提供相同 ABI，模块依赖非白名单符号可能无法链接或加载。
3. **Android 装载策略：**模块需要存在于允许的只读分区或 ramdisk，并满足该设备的 init/modprobe 配置和 SELinux 策略。GKI vendor module 不使用单个模块签名作为通用装载前提，Android 对 Verified Boot 设备的真实性保护依赖模块所在分区的验证机制。其他内核或产品策略可能不同，不能概括成“所有模块必须签名”或“所有模块都可动态加载”。
4. **定位失败原因：**检查内核日志与 `dmesg` 中的 `vermagic` 不匹配、未知符号、符号 CRC、格式、权限或 SELinux 拒绝信息。主机编译退出码为成功不能替代设备侧加载验证。

**Q4: [learning] 修改字符驱动后，如何安排重构建、部署、验证和清理？**

先确定驱动是内建代码还是可加载模块，再用目标内核构建环境生成产物，按设备策略部署并验证设备行为，最后确认模块和设备节点都按预期清理。模拟器和 userdebug 的调试能力不能代表量产镜像权限。

1. **确认目标：**检查配置值是 `y`、`m` 还是 `n`，确定改动需要重建内核映像还是 `.ko`。记录目标内核版本、架构和产品构建类型。
2. **重构建：**调用目标分支的构建脚本或已准备的 Kbuild 输出目录，并检查编译结果、模块架构、`vermagic` 和符号依赖。不要把旧构建目录中残留的 `.ko` 当成本次产物。
3. **部署与加载：**量产集成时按 Android 构建要求将模块放入 vendor、odm、system_dlkm 或相应 ramdisk，并生成依赖和加载顺序文件。临时 `insmod`/`rmmod` 只适用于设备策略允许、权限足够且依赖已满足的调试环境。
4. **验证功能：**检查模块加载日志、设备节点、正常数据、边界输入错误和并发行为。卸载时确认设备文件关闭、内核资源释放、依赖顺序正确，并观察是否出现 use-after-free 或卸载后访问。
5. **实验工具边界：**`adb root` 用于可 root 的调试镜像，量产 user build 通常不开放该能力。设备端 `dmesg` 可能受权限限制。`emulator -show-kernel` 用于启动模拟器时显示内核日志，适合实验观察，不会增加真机或量产系统的调试权限。
