**Q1: [done] 某车机项目 85 天开发窗口的提交流呈现什么缺陷画像，哪些数据支持“功能开发在前、提测放量在后”的判断？**

画像由三个指标构成：

1. **提交构成**：非 merge 提交 1010 条，其中缺陷修复 761 条（75.3%）、功能开发 241 条（23.9%）、其他 8 条。
2. **缺陷规模**：修复共涉及 543 个去重缺陷单。
3. **月度修复量**：从 6 月的 34 条爬升到 9 月上半月的 319 条，7 月为 189 条，8 月为 219 条。

功能提交从 6 月底开始入库，修复量随后逐月上升，并在 9 月上半月达到峰值。这一先后关系支持“功能开发在前、提测放量在后”的解释，但不能单靠提交曲线证明缺陷流入固定滞后一个月。修复占非 merge 提交的 75.3%，说明这段窗口的提交以缺陷修复为主。

这段时间的时间顺序与修复量变化支持“功能先合入、后集中提测”这一解释，但提交曲线本身不能证明缺陷流入必然滞后一个月。判断项目是否进入密集修复期时，可检查两个指标：

1. 月度修复量是否持续爬升。
2. 修复是否占非 merge 提交的大多数。该项目的 75.3% 可作为本项目对照值，七成只能作为便于观察的经验阈值，不是跨项目标准。

两项同时成立时，可以把修复处理能力与回归矩阵列为近期重点，再结合需求变更量、未关闭缺陷时长和发布计划校准投入。这里的“处理能力”不是单看提交比例，而要由周期内新增量、关闭量和未关闭时长共同判断。

**Q2: [done] 某车机项目被修复缺陷中必现占 79.2%、已闭环占 89.5%，这两个比例分别能说明什么、不能说明什么？**

口径为某车机项目 85 天窗口内的 543 个被修复缺陷单：

1. **复现频次**：必现（80%~100%）430 个，占 79.2%。偶现（低于 10%）23 个，占 4.2%。原报告据此认为多数问题可由常规冒烟发现，但复现率不等于冒烟覆盖率。还要核对用例是否覆盖对应前置条件与复现步骤。
2. **闭环比例**：闭环 486 个，占 89.5%。这只说明样本中近九成缺陷单已达到闭环状态，不能单独证明修复吞吐跟得上缺陷流入或流程整体健康。评估吞吐还要按时间比较新增、关闭数量及未关闭时长。

复现频次影响问题能否稳定重现，闭环比例描述样本的处理状态，两者都不能直接代表产品质量。未闭环缺陷仍需按严重度和影响范围排序。偶现缺陷虽然只占 4.2%，但 11 个 A 级中有 5 个属于偶现或低概率，因此还要针对并发与时序做机制分析。

判断规则：稳定可复现的问题应纳入明确的回归场景。偶现问题还要补充并发、时序或状态机分析。矩阵回归与机制分析互补，不能把任一项当成另一项的替代。

**Q3: [learning] 某车机项目中 UI 还原与主题适配占修复记录的 34.7%，这一分布能支持哪些改进决策？**

761 条修复中，264 条（34.7%）归类为 UI 还原与主题适配，是第二名“信号与协议”（88 条）的三倍。主要子形态有：

1. 颜色、字号、字重、间距与设计稿不符。
2. 深色资源缺失或使用错误。
3. 设计稿版本混淆。
4. 动态资源名绕过深色资源限定符。
5. 多模块同名资源遮蔽。

这个分类结果表明，在该项目的修复记录中，UI 还原与主题适配是数量最多的类别。子形态集中在视觉规格、资源配置与设计版本，因此日夜和分辨率矩阵、资源审查清单是可直接针对这些记录的预防措施。分类数据本身不能进一步证明这是所有车机项目的普遍规律。

投入时落实两项措施：

1. UI 提测必须跑“日夜×分辨率”矩阵。
2. 评审固定检查新增颜色是否配置深色值、动态资源名是否改为静态引用。

判断规则：把资源与主题覆盖检查列为改进候选，再用后续同口径数据检验它是否降低了 UI 类缺陷。

**Q4: [learning] 某车机项目中信号与协议、状态缓存、蓝牙、异步时序四类缺陷占比如何转成评审重点？**

口径为某车机项目 761 条修复的互斥归类：信号与协议 88 条、状态管理与缓存 77 条、蓝牙机制 73 条、异步时序与竞态 57 条，四类合计 295 条（38.8%）。加上 UI 还原的 264 条后，前五类共 559 条（73.5%）。这组占比可用于确定复核优先级，但反映的是该项目观察窗口内的修复分布，不是所有项目的通用缺陷概率。

按权重排序的评审抓手如下：

1. **信号与协议（11.6%）**：常见风险是静默失效。评审值域换算、超时语义，以及状态域与命令域的区分。
2. **状态管理与缓存（10.1%）**：常见现象是状态残留与缓存滞后。评审重置路径是否成对清理，以及缓存是否以事实源为准。
3. **蓝牙机制（9.6%）**：风险集中在连接状态机与跨进程协作。评审互斥状态转换和跨进程状态同步。
4. **异步时序与竞态（7.5%）**：缺陷可能只在特定时序暴露。评审回调生命周期、延迟任务取消性与主线程阻塞。

反向加权一条：占比 7.5% 的异步时序却是偶现 A 级的主要来源，评审权重不能只按占比线性分配——低频高害类别要额外加权。这四类的技术细节由 Android 对应的主线程与蓝牙主题册承载，此处只取权重与抓手。

**Q5: [learning] 某车机项目根因统计中“其他（描述过短）”占 10.1%，阅读其余类别占比时要注意什么？**

某车机项目口径下，77 条修复（10.1%）因提交消息与缺陷库描述都过短而无法可靠归类，被单列为“其他”。这个类别给分布数字带来两项约束：

1. **限制分类结论**：各类别占比的分母是全部 761 条修复。77 条无法归类的记录仍在分母中，但没有被分配给具体根因。若其中许多实际属于 UI，UI 占全部修复的比例就会被低估。
2. **暴露流程问题**：“描述过短”与“提交自带完整 why/how 仅 27.9%”是同一问题的两面。信息在源头没有记录，统计自然无法归类。

使用这类分布时按两个步骤判断：

1. 先看“无法归类”桶的大小，再读各类占比。决策时关注类别排序与相对差距，不把未知记录当成已知类别。
2. 治理重点放在提高描述质量、缩小“其他”桶，而不是修正统计方法。

**Q6: [learning] 某车机项目中四类次要根因合计 125 条、约 16.4%，为什么评审投入不能只按类别占比分配？**

因为占比反映发生数量，不直接代表缺陷的严重度、发现难度或治理成本。需求变更这一类占 7.2%，其余三类各低于 4%。外部条件变化、边缘路径遗漏或依赖升级仍可能造成高影响缺陷。

某车机项目 761 条修复的互斥归类中，这四类的口径与含义如下：

1. **需求变更与理解偏差（55 条，7.2%）**：需求中途变更后，布局、代码、联动调用没有成对清理，缺陷在变更时就已埋下，只是延迟到下一次走查才暴露。治理动作是把 UI 变更纳入流程，必须带单流转，不能按旧稿顺手修改。
2. **逻辑遗漏与边缘场景（25 条，3.3%）**：主体分支正确，遗漏的是相等边界、闭包捕获旧值、循环外变量沿用上一轮残留等非主流路径。治理动作是加强评审，逐项检查边界值与临时变量作用域。
3. **崩溃与异常防护（24 条，3.2%）**：包括并发修改异常、`Fragment` 销毁后的迟到回调、回调重复注册和生命周期守卫缺失。占比不高，但这类问题直接构成“偶现 A 级”的一种形态，排查成本远高于修复成本。
4. **第三方 SDK 与 AAR（21 条，2.8%）**：约四成条目是“升级 3D 车模 aar”本身。渲染端 SDK 升级既直接交付修复（把手加热、座椅加热恢复响应，中低配车模不再出现座椅调节入口，充电枪状态渲染修正），也带来新的映射要求。Android 侧的信号值域映射表与配置字清单必须随每次 aar 升级重新评审。

分配评审注意力时区分两类处理方式：

1. **前三类**：评审权重应高于占比，因为它们由“条件变化”而非“写错”暴露，只能靠流程与清单兜底。
2. **第三方 SDK 与 AAR**：把外部依赖升级当作接口变更评审，而不是例行 bump。

因此，前五类决定主要投入方向，后四类决定评审清单要覆盖的非代码失效路径。

**Q7: [learning] 11 个 A 级缺陷全部落在哪两条规律线上？这条规律如何用于排查与排期？**

口径：某车机项目 85 天窗口内的 543 个缺陷单中，A 级有 11 个（2.0%）。复盘发现它们全部符合两种形态，其中 5 个偶现或低概率、6 个必现：

1. **偶现或低概率，关联并发与状态机**：案例包括通话状态切换的并发修改异常、多实例重复注册回调、主线程同步 Binder 阻塞、`Fragment` 销毁后回调继续刷新、界面退出未重置坐标。这些都是并发路径与状态残留缺陷，靠堆测试用例几乎抓不住。
2. **必现，关联多系统联调与启动时序**：案例包括系统级音频通路阻塞（dsp/HAL 层）、流程弹窗缺少关闭路径并叠加状态机提前 `return` 的盲区、组合状态覆盖写丢失属性组、单例初始化早于存储就绪导致卡开机。这些问题在对应场景下可稳定复现，但定位仍需要跨系统。回归矩阵只有覆盖了相关启动与联调场景，才能把它们作为冒烟检查项。

两种形态对应不同的排查与排期动作：

1. **偶现 A 级**：从并发路径与状态机审查切入，不从“加日志等复现”切入。
2. **必现 A 级**：把启动时序与跨系统状态恢复列为独立验收项，不等联调暴露后再处理。

判断规则：A 级虽只占金字塔尖的 2%，却都可能卡死或卡开机。两条规律线划定了高代价缺陷的检索范围。

**Q8: [learning] 追溯性损耗有哪些形态？它们如何把"提交↔缺陷"的自动关联压到 75.4%？**

口径：某车机项目 85 天窗口内的 761 条修复提交中，只有 574 条（75.4%）能精确关联到缺陷库。追溯性损耗有六种形态：

1. **无单号与占位**：85 条完全没有可关联单号，其中大量是 `SIR-XXXX` 式占位。aar 更新、分支同步、日志调试类提交也在其中。
2. **库外单号**：102 条引用的单号不在缺陷库导出内，其中旧工单系统单号约 60 个、跨域单号约 30 个，另有个别笔误。
3. **类型错标**：feature 与 bugfix 互相标错 40 多例。
4. **重复提交对**：同一 diff 以两个单号先后入库，且单号交叉错标。
5. **Change-Id 串号**：一个 Change-Id 挂多个单号。
6. **搭车修改**：提交内容与单号声明的范围不符，例如日志提交夹带真实修复。

这些损耗都会让“从缺陷单反查代码”或“从提交反查缺陷”至少断一个方向：

1. 游离提交无人认领。
2. 重复提交让修复计数虚高。
3. 错标把修复归给错误的问题。

判断规则：自动关联的覆盖率受提交纪律、单号映射和缺陷库数据范围共同限制。工具只能匹配已有信息，补不出未记录的信息。

**Q9: [learning] "缺陷库根因填充率 98.7%、提交自带完整 why/how 仅 27.9%"这组对照说明了什么，复盘应如何据此取数？**

口径与含义如下：

1. **缺陷库根因填充率**：某车机项目 543 个被引用缺陷单中，536 个填有根因分析，占 98.7%。
2. **提交消息完整率**：761 条修复提交中，仅 212 条消息自带完整 `[why]` 与 `[how]`，占 27.9%。

这组对照只说明两个来源的字段填充情况不同：缺陷单的根因字段填得较完整，提交消息只有约四分之一同时包含 why 与 how。字段已填写不等于根因判断准确，仍要核对缺陷描述、代码改动和实际修复是否相符。

据此取数时，让单号连接两种来源，并按字段分工：

1. **缺陷库**：提供缺陷现象、等级、频次和库方根因。
2. **Git diff**：提供实际代码改动的主要证据。根因要结合现象和改动推导，来源冲突时不能把提交标题当成代码事实。
3. **提交消息**：只作为检索键和补充说明。

某项目曾出现 A 级单的主提交只含日志、真实修复在邻提交的情况。若信提交消息，会把日志当作修复经验沉淀。

98.7% 的字段填充率有助于开展根因字段统计，但它不是自动关联的必要条件，也不保证根因判断准确。应把“能否关联记录”与“根因内容是否可靠”作为两项独立检查。评估项目的可复盘性时分别检查：

1. **缺陷库根因填充率**：决定有多少记录具备可供复核的根因字段，不代表根因内容已经验证。
2. 提交 `[why]` 完整率：决定提交侧可信度。

**Q10: [learning] "提交↔缺陷库自动关联 + 逐 commit 精读"这套复盘方法是怎么运转的？**

方法包含两个支柱：

1. **自动关联**：解析提交消息中的单号前缀（智能化域 `SIR-`、整车域 `VIR-`、旧工单 `YD-`），与缺陷库导出精确匹配，批量获取每笔修复对应的等级、频次、状态与库方根因。某车机项目覆盖 574/761（75.4%），其余属于追溯性损耗。
2. **逐 commit 精读**：逐条阅读全部非 merge 提交的 diff，每条产出固定五段：问题、根因分析（双源互证）、关键代码摘录、为什么能修复、复盘经验。该项目 85 天窗口产出 1010 篇，覆盖 1010/1010。

运转要点有三项：

1. **特殊提交标注类型后不套模板**：aar 更新、分支同步、纯资源、建库类不强行套“问题→根因”模板。
2. **描述与 diff 不符处逐条注明“以 diff 为准”。**
3. **功能提交与修复提交分开统计**，分别产出附录。

产出分为三层：

1. **画像统计**：分类计数与占比。
2. **模式归纳**：跨案例提炼系统性规律，例如“内部哨兵不得落入协议值域”。
3. **深案例库**：逐条记录可检索的问题与修法。

判断规则：这套方法的成本在精读环节，产出的是组织资产。后续遇到同类问题可直接检索案例，不必重新踩坑。

**Q11: [learning] 逐 commit 精读为什么必须读 diff，而不能只汇总提交消息和缺陷库描述？**

因为提交消息与实际改动的失真是常态而非例外，只信消息会把错误经验写进知识库。某车机项目 85 天窗口内出现过三类实证：

1. **主单提交名不副实**：一笔 A 级必现单挂名的主单提交只含日志调整与死代码清理，真实机制修复在 17 分钟前的邻提交里。
2. **一次修复被计成两次**：同一 diff 以两个单号先后入库且单号交叉错标，只看标题会重复计数。
3. **标题与 diff 完全串单**：标题写 UI 适配，diff 却是另一套改动。

所以精读的单位是 diff，单号只是检索键。处理规则：现象与复现信息取缺陷库（测试的描述通常更完整），根因与修法从 diff 推导，冲突时以 diff 为准并在产物中显式注明冲突点，不静默择一。

判断规则：任何"按提交消息统计"的复盘都应预留 patch 抽查——提交消息可以随手复制，diff 不能，这就是以 diff 为准的底层原因。

**Q12: [learning] 复盘统计时，重复提交对、类型错标与不适用模板的特殊提交应如何处理，才能不污染结论？**

处理原则按三类分别确定：先定性、再纳入统计，不让元数据直接决定归类。

1. **重复提交对**：直接比对去掉提交信息后的 patch 来确认内容是否一致。`git patch-id` 可用于全量查找疑似重复，它忽略行号与空白差异，适合候选筛查，不等同于字节级 patch 比较。确认是同一修复后只计一次，单号归属按实际改动判断。
2. **类型错标**：不能只按标题前缀筛选样本，否则标错的提交会被直接漏掉。先保留完整候选集，再结合缺陷单性质、提交消息和 diff 复核实际类型。feature 前缀但 diff 实为修复的，计入修复并标注错标，需求提交则从缺陷样本中分离。
3. **特殊提交**：aar 更新、分支同步、纯资源、建库类不强行套用“问题→根因”模板。标注类型后排除出缺陷样本。某项目口径为 1010 条 = 761 修复 + 241 功能 + 8 其他，功能与其他另出附录。

判断规则：口径要显式写进报告（互斥归类、供量级参考），让读者知道每个数字怎么来的——口径不透明的统计比没有统计更危险。

**Q13: [learning] 同一单号被多笔提交引用时，怎样区分口袋单、真实返工与需求迭代？**

某车机项目口径下，引用次数较多的单号及其性质如下：

1. **需求/联调单 SIR-3401**：被 6 个提交引用，时间跨度半个多月，涉及锁屏信号联调与主交互状态机两个模块。多数是功能提交，少数是联调修复。这说明它属于需求/联调性质，“引用次数”不等于“缺陷返工次数”。
2. **缺陷单 SIR-2463、VIR-36**：分别对应副蓝牙无声、重连后通话无姓名，各被引用 4 次。
3. **缺陷单 SIR-7808、SIR-2858、SIR-3307、SIR-7464、SIR-7647**：分别对应预约充电时间设置、导航中拨蓝牙电话、主交互状态连携、蓝牙开关二次确认与辅助驾驶滚动条、热点关闭态与蓝牙确认式样，各被引用 3 次。

解读时按三种情况分别处理：

1. **需求或联调单多次被引用**：单号颗粒度大于提交颗粒度。统计缺陷前先看单据性质，不能把引用次数当作返工次数。SIR-3401 的 6 次引用横跨五个互不相关的子需求，是“口袋单”的典型。
2. **真实缺陷单多次修复**：多次提交是复核信号，不足以单独证明前次修复错误。要看同一现象是否再次出现、改动是否逐步收敛，以及提交是在分步实施还是反复试探。SIR-2463 的 4 次修复横跨应用层与 dsp/HAL 两层，应结合每次 diff 判断是跨层分步处理还是根因定位反复。
3. **单号性质不明**：需求单与缺陷单共用同一前缀时，前缀不足以判定性质，必须回到单据内容。

判断规则：引用次数只能触发核查，不能直接等同返工次数。先按单据内容定性，再核对每笔 diff 与现象的关系。

**Q14: [learning] 修复的模块分布（车控设置应用 259 条居首）对新人上手与回归测试排布有什么指导意义？**

分布口径：某车机项目 85 天窗口内的 761 条修复中，前六个模块合计约 92%，具体分布如下：

1. 车控车设应用：259 条。
2. SystemUI：128 条。
3. 蓝牙电话：112 条。
4. 能量中心：82 条。
5. Launcher：77 条。
6. 蓝牙音乐：45 条。

车控车设应用的修复数最高，说明它在该窗口承担了最多已记录修复工作。这里统计的是绝对修复数，没有按代码规模、功能改动量或测试覆盖量归一化，因此不能据此断言它的缺陷密度最高。可先将其作为回归资源的候选重点，再结合改动量和严重度校准。

模块分布有三种用法：

1. **新人上手**：先读跨模块的模式归纳建立复杂度地图，再按目标模块查深案例库。高频模块的许多功能点都有前人踩坑记录。
2. **回归排布**：按模块修复量和缺陷严重度分配测试资源，优先检查车控车设等高修复量模块的日夜与信号矩阵。
3. **风险预估**：改动落在历史修复量高的模块时，可提高评审与回归优先级，并按改动规模和风险校准强度。

判断规则：模块修复数适合作为资源初分配的线索，不是缺陷概率。还要结合改动量、严重度和测试覆盖验证风险。

**Q15: [learning] 把"自动关联+逐 commit 精读"的复盘方法迁移到其他项目，哪些前提必须满足？**

迁移这套方法需要满足四个前提：

1. **单号体系可解析**：提交消息带稳定前缀的单号，缺陷库可导出且根因字段填充率足够。填充率不足时，根因分布会退化为提交消息文本分类，结论质量骤降。
2. **提交消息有最低结构**：至少提供单号与类型标签两个解析锚点。某车机项目 `[what][why][how]` 模板执行率虽仅 27.9%，但单号锚点支撑了 75.4% 的关联率。
3. **精读预算充足**：逐 commit 阅读 diff 是人力密集步骤，可按“先 bugfix 后 feature、先 A/B 级后 C/D 级”分批，或只精读高频模块。
4. **统计口径透明**：明确互斥归类规则、特殊提交处理方式，以及冲突时以 diff 为准的原则。

落地路径：先跑小样本（一个模块一至两周的提交）校准归类口径与产出模板质量，再放量到全量。判断规则：这套方法的本质是把个人经验转成组织可检索资产，前提齐备时，一个季度就能沉淀上千条带代码证据的案例。

**Q16: [learning] 同一 diff 以两个缺陷单号先后入库且单号交叉错标，这种"交叉串单"是怎么形成的？对修复计数和归因各有什么影响？**

交叉串单通常由两类操作造成：

1. 全量 `git add -A` 把多个工单的改动带进同一提交。
2. 本地分支 cherry-pick 或合并后未去重，同一份 patch 被挂上不同单号重复入库。

它会造成两种统计错误：

1. **修复计数虚高**：一次修复被统计两次。
2. **归因错位**：挂着 A 单标签的提交，实际包含 B 单的修复。

某车机项目实例中，同一天同模块的 4 个 UI 提交两两成对重复并交叉错标：

1. **A 单（字体遮挡）**：真实修复正确入库一次，之后又有一笔 B 单（按钮文案与底色）的修复被错误挂到 A 单。
2. **B 单（按钮文案与底色）**：同样一正一错，各自都挂着一笔内容不属于该单的提交。

应通过排除提交信息后的 patch 内容比对来判定：

```bash
diff <(git show 5b443500 --format=) <(git show b6771acc --format=)   # 输出为空即同一 patch
```

两笔提交去掉提交信息后的 patch 完全一致，可判定为重复对。统计修复时按重复 patch 去重，单号归属按实际改动而不是提交标题判断。若重复 patch 已经应用在目标分支上，之后再次 cherry-pick 可能变成空改动。但不同分支或提交链仍可能保留重复记录，不能据此假定代码或历史天然会去重。

patch 比对有三项边界：

1. 必须排除提交信息（`--format=` 置空），否则两笔提交会因标题不同而被误判为不同 patch。
2. 含二进制文件（图片、aar）的提交 patch-id 不稳定，需辅以改动文件清单比对。
3. 重复提交不一定相邻。cherry-pick 到其他分支的重复要在全量提交范围内查重。

**Q17: [learning] 要在提交流水线上预防单号占位、类型错标与重复提交对，有哪些可落地的卡点？分别拦截什么损耗形态？**

三层卡点分别覆盖入库前、入库时和合并前三个拦截点：

1. **pre-commit**：校验提交消息格式，包括类型枚举、真实单号和模块白名单。
2. **CI**：用 patch-id 对全量历史查重。
3. **MR 评审**：核对单号与 diff 范围是否 1:1 对应。

某车机项目 85 天窗口的损耗形态可逐条映射到卡点：

1. `SIR-XXXX` 占位：85 条无单号提交中大量是占位，单号格式校验直接拒绝。
2. **feature/bugfix 互标**：40 多例，类型枚举校验兜住。
3. **同一 diff 两个单号入库**：CI patch-id 查重兜住。
4. **日志提交夹带真修复**：靠 MR 评审核对“单号声明的范围与实际改动文件”兜住。

配套的个人操作规则有两条：

1. 一个提交只 stage 一个工单的改动。
2. 多工单并行时用 `git add -p` 按工单拆分，不用全量 `git add -A`。

这些卡点有两项边界：

1. 它们只能拦截格式可校验的损耗。描述空洞（why/how 缺失）、库外旧单号等语义问题，仍需评审与描述质量指标（如 [why] 完整率）兜底。
2. pre-commit 钩子可被 `--no-verify` 绕过，关键校验还须在服务端执行。

**Q18: [learning] 缺陷单挂名的主提交 diff 与缺陷描述明显不符时，如何找回真实的功能修复提交？**

1. 作者相同。
2. 模块相同。
3. 时间邻近。
4. 提交消息描述相似。
