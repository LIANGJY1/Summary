## 1. 定位：CAN 在整车网络里的位置

CAN（Controller Area Network，ISO 11898）诞生于 1980 年代 Bosch，解决"几十个 ECU 互相说话"的问题：多主总线、差分两线、抗干扰、硬件级优先级仲裁。整车网络的现代分工是：**动力/底盘等实时控制域用 CAN/CAN-FD**（确定性、成熟、成本低），**高带宽域（摄像头、座舱、智驾）用车载以太网**，**低成本简单外设（车窗、后视镜）用 LIN**，骨干互联用以太网交换机（SOME/IP 与 TSN 运行其上，见 SOME/IP 详解）。一个常见误解是"CAN 会被人联网攻击"——CAN 网段本身无 IP 栈、不出车，攻击面在"能向 CAN 注入报文的入口"（诊断口、被攻陷的联网 ECU），这也是网关隔离与报文校验（AUTOSAR SecOC）存在的原因。

## 2. CAN 基础机制

### 2.1 差分信号与显性/隐性

CAN 用双绞线差分传输（CAN_H/CAN_L）：两线电压差存在为**显性位（0）**，无差为**隐性位（1）**。显性可以覆盖隐性——多个节点同时发送时，总线上呈现的是所有发送位的"按位与"，这是硬件仲裁的物理基础；位流中间的显性沿同时充当同步时钟。

### 2.2 四种帧类型

数据帧（携带数据，最常用）、遥控帧（请求某 ID 的节点发送对应数据帧）、错误帧（检测到错误时任何节点可发，破坏当前帧迫使重发）、过载帧（接收方来不及处理时的流控提示）。

### 2.3 数据帧字段逐段

帧起始（SOF，显性）→ 仲裁场（11 位标准 ID 或 29 位扩展 ID + RTR 位，区分数据帧/遥控帧）→ 控制场（IDE、DLC 数据长度码）→ 数据场（经典 CAN 0–8 字节）→ CRC 场（15 位校验）→ ACK 场（其他节点应答）→ 帧结束（7 位隐性）。ID 同时承担两个职责：**寻址内容**（"这是什么信号"而不是"发给谁"，CAN 是广播制，谁需要谁取用）与**仲裁优先级**。

### 2.4 非破坏性逐位仲裁

多节点同时发送时逐位比较：发送隐性（1）而总线上读到显性（0）的节点立即退出仲裁、转为接收，ID 数值越小（显性位越多）优先级越高。关键是"非破坏性"：胜出的帧全程不受干扰、无需重发，仲裁损耗只在输家侧。工程含义：ID 即优先级——刹车信号规划小 ID，娱乐大块数据规划大 ID；把大块数据配成高优先级会饿死整条总线。

### 2.5 错误处理：五类错误与 Bus-Off

检测到五类错误（位错误、填充错误、CRC 错误、格式错误、ACK 错误）的节点立即发错误帧销毁当前帧。每个节点维护 TEC/REC 两个计数器，状态机为：**错误主动**（Error Active，正常发错误帧）→ **错误被动**（Error Passive，只能发被动错误帧且需暂停）→ **Bus-Off**（TEC 超 255，节点与总线物理隔离；需检测到 128 次 11 位连续隐性位后才允许恢复）。设计含义：一个持续发错的节点会被总线自动"隔离"，坏的是它自己而不是整条总线；Bus-Off 恢复策略（快恢复/慢恢复、恢复次数上限）是软件要显式设计的点。

### 2.6 位填充

连续 5 个同值位后自动插入一个反位，保证信号沿密度供同步使用——这意味着实际位流长度与"逻辑位数"不同，示波器量波特率与分析帧长时都要按填充后的物理位计算。

## 3. CAN-FD 的关键差异

CAN-FD（Flexible Data-rate）在向下兼容经典 CAN 的前提下解决带宽与载荷两个瓶颈：**双速率**——仲裁段保持慢速率（保证仲裁可靠），数据段切换到高速率（可达 5/8 Mbps）；**大载荷**——数据场扩到最大 64 字节（经典 8 字节），单帧效率大幅提升；CRC 增强为 17/21 位适配更长帧。迁移成本：需要全网收发控制器/收发器支持 FD，且经典 CAN 节点混挂时 FD 帧会被当作错误帧——FD 升级通常按网段整体切换。选型口径：信号类低带宽业务留在经典 CAN，大 payload（域控间数据、刷写）走 CAN-FD 或直接上以太网。

## 4. ID 规划与实时性

ID 规划是 CAN 设计的核心工作：按"报文重要性 + 周期"分配 ID 段与发送周期，保证最高优先级报文的最坏仲裁延迟可计算（所有更高优先级报文的最大阻塞之和）。上层标准再约定 ID 语义：乘用车诊断/常用功能遵循各厂 DBC 定义，商用车 J1939 用 29 位扩展 ID 划分参数组（PGN）与源地址，OBD-II 法定诊断占用固定 ID 段（7E0–7E8 物理寻址/7DF 功能寻址）。改动 ID 规划是跨供应商的协议变更，成本极高——这也是"早期 ID 规划质量决定整车总线健康度"的原因。

## 5. LIN：低成本从属总线

LIN（Local Interconnect Network，ISO 17987）定位是 CAN 的低成本补充：单主多从、单线、最高约 20 kbps、从机节点无需精确晶振（从报文头同步）。通信完全由主节点驱动的**调度表**（Schedule Table）决定——主节点按表依次发送报文头，指定的从机补全数据；没有仲裁也没有随机接入，时序完全确定。适用：车窗、雨刷、后视镜这类"简单、便宜、对带宽无要求"的执行器；设计要点是调度表容量与时序预算（所有周期报文加起来不能超表长）。

## 6. 与车载以太网 / SOME/IP 的关系

现代整车上两套世界并存：CAN/LIN 承载传统 ECU 的信号类通信，车载以太网承载域间大带宽与服务化通信。两者经**网关 ECU** 互转：信号→服务（把 CAN 报文解析成信号后封装为 SOME/IP Event 提供给座舱/智驾）与服务→信号（座舱下发控制指令映射回 CAN 报文）是网关的标准职责，映射关系即 SOA 接口设计的一部分（SOME/IP 详解文档的通信模式一节）。对 Android 座舱开发者的含义：你几乎永远不直接碰 CAN 帧——你消费的是网关转换后的 SOME/IP 服务或 VHAL 属性；但"这个信号在 CAN 上的周期与优先级"决定了上游数据的时效上限，联调时要有这个意识。

## 7. 诊断协议：OBD、UDS 与 DoIP

### 7.1 OBD-II 与 UDS（ISO 14229）

OBD-II 是法规要求的排放诊断接口（固定 ID、有限服务）；真正的整车诊断标准是 UDS（Unified Diagnostic Services，ISO 14229），定义 26 种服务、六大功能单元。常用服务速览：`0x10` 诊断会话控制（默认/扩展/编程三会话，扩展会话才开放写操作）、`0x27` 安全访问（Seed-Key 握手解锁敏感服务）、`0x22`/`0x2E` 按 DID 读/写数据、`0x19` 读 DTC 故障码、`0x14` 清故障码、`0x31` 例程控制（自检触发）、`0x34/0x36/0x37` 请求下载/传数据/退出（刷写三件套）。协议细节：请求-响应模型，否定响应固定为 `7F + SID + NRC`（错误码，如 0x33 安全未解锁、0x78 响应挂起）；会话层超时参数（P2/P2*）控制响应时限。

### 7.2 DoIP（ISO 13400）：诊断跑上以太网

DoIP 把 UDS 的承载从 CAN 换成以太网：ISO 14229-2 使 UDS 会话层与传输方式解耦，同一个 `0x22` 读数据服务既可走 CAN（DoCAN）也可走 DoIP。DoIP 增加了以太网特有的环节：车辆发现（Vehicle Identification 报文）、路由激活（Diagnostic routing activation，建立诊断套接字）、以及大 payload 刷写带宽（以太网刷写远快于 CAN）。排查意义：高带宽 ECU（座舱、智驾）刷写与诊断走 DoIP/以太网，传统 ECU 走 CAN——诊断"通不通"要按 ECU 所在总线分别验证。

## 8. Android 座舱视角

座舱 Android 不直接挂 CAN：车辆信号经网关/车身域控转换后，以 **CarService VHAL 属性**（06-system 电源/属性册）或 SOME/IP 服务（本文互链文档）的形态进入座舱。开发者的接触面是：VHAL 属性的取值与频率（上游 CAN 报文周期决定的时效上限）、信号到属性的映射正确性（网关映射表）、以及诊断/刷写链路里座舱作为 DoIP 目标的角色。涉及跨域联调时，先用 14-network/05 册的分层框架确认"这条信号走的是哪个域的哪条总线、谁转换的"，再定位。

## 9. 排查工具与方法

三层排查法（社区实践口径）：**物理层**——示波器看差分波形（显隐性电平、位时间、CAN-FD 双速率切换、上升沿质量）；**链路层**——CAN 分析仪/candump 抓帧看仲裁结果、错误帧类型与计数器状态（`candump any`、`cansend` 是 Linux SocketCAN 标准工具，Android 侧需带 CAN 控制器的内核与驱动）；**应用层**——按 DBC 解析信号值比对预期，UDS 用诊断仪或脚本发服务请求验证。总线级异常速查：整条总线瘫痪查终端电阻（两端 120Ω）与总线短路；单节点失效查其 Bus-Off 状态；偶发错误帧查位定时配置与干扰源。
