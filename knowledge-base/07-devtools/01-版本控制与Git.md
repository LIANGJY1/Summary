# 版本控制与 Git

> 通用开发工具学习资料（学习资料目录 `07-devtools/` 首册）。边界：本文回答“Git 合并、cherry-pick、rebase、冲突解决、reset 回退、reflog 恢复、pull 协作与 Gerrit 评审推送的操作语义与场景选择”；提交纪律与仓库治理等非技术规则归 [../08-项目经验/](../08-项目经验)。Q 序列即结构，供 atlas 同源直读。

**Q1: [learning] Git 的整体工作原理是什么？**

Git 本质是内容寻址的快照存储系统：每次提交记录的是当时整个项目目录树的快照而非文件差异，快照按内容的 SHA-1 哈希寻址存储，提交之间经父指针串成历史。工作模型可分三层理解：

1. **对象库**：blob（文件内容）、tree（目录结构）、commit（提交，指向 tree 与父提交）、tag 四类对象构成不可变历史图。哈希相同即内容相同，相同内容天然去重。
2. **三个工作区**：工作目录、暂存区与 HEAD 所指的分支历史。git add 把改动写入暂存区，git commit 把暂存区打包成新的 commit 对象。
3. **分支与引用**：分支只是指向某个 commit 的可移动指针，切换分支就是把 HEAD 指向另一条提交链并重建工作目录。远端跟踪引用（如 origin/main）记录上次同步位置，pull/push 在本地与远端对象库之间搬运对象并移动引用。

由此可推出 Git 的多数行为：

1. **提交不可变**：回退与改写安全，误删可从 reflog 找回。
2. **分支创建成本极低**：鼓励按特性多分支。
3. **合并的本质**：把两条提交链汇合成一个提交。

**Q2: [learning] 特性分支合回主干时，git merge 什么时候只做快进（fast-forward），什么时候产生真正的合并提交？**

快进指合并时 Git 不创建合并提交、只把当前分支指针直接前移到目标提交的情形。发生条件是当前分支自分叉后没有任何独有提交——此时目标分支的提交就是当前分支头的直接延续，移动指针即完成“合并”，历史保持一条直线。

例如 main 分叉后没有新提交而 feature 有三个提交，在 main 上执行 git merge feature 得到的就是快进：main 指针直接移到 feature 的头提交，不产生新对象。与之相对，两条分支都有独有提交时无法快进，Git 只能创建一个有两个父提交的合并提交把两条线汇合。

因此快进与否由“当前分支有没有独有提交”决定，与特性分支有多少提交无关。合并前用 git log --graph 或 git merge-base 查看分叉点即可预判结果。

**Q3: [learning] 明明可以快进，为什么还要用 git merge --no-ff 强制创建合并提交？代价是什么？**

--no-ff 强制生成一个合并提交（有两个父提交），把特性分支的存在和它的提交集合显式留在历史图里。收益主要有两点：

1. **合并点可追溯**：从历史图能直接看出“某段改动作为一个整体在何时合入”。要整体回退一个特性时，revert 这个合并提交即可，不需要逐个辨认其中的普通提交。
2. **分支边界清晰**：快进会让特性分支的提交混入主干线性历史，事后无法区分“哪些提交属于同一个特性”。

代价是历史图出现汇合节点、线性度下降。取舍规则：单人仓库或一次性的小改动，快进更干净。多人共享的主干，保留合并节点通常更可追溯，这也是团队协作中常见推荐 --no-ff 的原因。

**Q4: [learning] git merge --squash 与普通 merge、--no-ff 的结果差在哪里？什么场景适合用它，用它后要注意什么？**

--squash 把特性分支上的全部改动压缩成一个放在当前分支上的新提交：这个提交只有当前分支头一个父提交，历史图上没有合并关系，特性分支内部的多次提交历史也不会进入主干。这与普通 merge（两条分支都有提交时产生双父合并提交）和 --no-ff（强制产生双父合并提交）在“是否保留分支历史与合并关系”上有本质差别。

它适合短生命周期的特性分支：主干只想要一个干净、完整描述这次改动的提交，不关心开发过程的中间状态。用完要注意：因为 Git 不记录“该分支已被合并”，之后对同一分支再执行普通 merge 会把已应用的改动当作新改动引入，所以 squash 合入后应直接删除该特性分支，不要再合并它。

**Q5: [learning] git cherry-pick 的执行语义是什么？它与 merge、rebase 各自的适用边界在哪？**

cherry-pick 取出指定提交的改动内容，把它应用到当前分支头并生成一个新提交：新提交有全新的哈希，与原提交没有对象层面的关联，本质是“把那笔提交的 diff 重放一次”。适用边界按要搬移的内容范围选择：

1. **只搬个别提交**：跨分支搬运单点修复、把某个改动摘到发布分支，用 cherry-pick。
2. **搬整条分支且保留合并关系**：用 merge。
3. **搬整条提交序列并改写基点**：用 rebase。

搬运后两个提交内容相同但哈希不同，追溯时要靠提交消息或 -x 选项（在提交消息中记录 cherry picked from 的来源哈希）建立关联。

**Q6: [learning] cherry-pick 遇到冲突时的继续与取消操作是什么？一次搬多个提交怎么写？**

冲突时的完整流程：

1. 手工解决冲突文件。
2. 用 git add 将解决结果标记完成。
3. 执行 git cherry-pick --continue 应用下一个提交；若想整体放弃，执行 git cherry-pick --abort，回到 cherry-pick 开始前的状态。

多个提交按顺序列出即可：git cherry-pick `<哈希1>` `<哈希2>`，或用 `<起点>^..<终点>` 表示区间。提交按参数顺序逐个应用，中途任何一笔冲突都会停下来等待处理。

**Q7: [learning] git rebase 把提交搬到新基点时发生了什么？为什么不能对已推送到共享分支的提交执行？**

rebase 读取当前分支相对目标基点的独有提交，在新基点上逐个重放，生成内容等价但哈希全新的提交序列。它因此属于改写历史的操作，只适合尚未共享给他人、或确认无人基于其工作的提交。

执行过程依次是：

1. **分离独有提交**：找到当前分支与目标基点的共同祖先，确定需要搬运的提交序列。
2. **切换基底**：把当前分支头指向目标基点。
3. **逐个重放**：按原顺序重放每个独有提交并创建新提交。遇到冲突时暂停，解决后用 git rebase --continue 继续，用 git rebase --abort 放弃整个操作并回到 rebase 开始前的状态。

rebase 与 merge 的本质差异在这里：merge 保留旧提交并新增一个合并提交，历史不发生改写。rebase 则丢弃旧提交链、创建新提交链，旧提交在重放完成后不再被分支引用。

不能对已推送的共享提交执行 rebase，因为哈希改写会产生连锁反应：

1. **远端出现两套历史**：远端仍指向旧提交链，本地改写后的推送会被拒绝，只能强制覆盖。
2. **协作者历史分叉**：基于旧提交工作的协作者 pull 时，会把旧提交链与新提交链当作两条有效历史合并，产生大量重复提交与冲突。
3. **清理代价高**：逐个辨认、剔除重复提交远比重新同步费时。

这正是 Git 官方文档的警告：“不要 rebase 仓库之外、别人可能基于其工作的提交。”个人特性分支确需改写已推送历史时，推送必须用 --force-with-lease 覆盖远端：它在远端引用被他人更新过时拒绝推送，比裸 --force 更能避免误伤他人新提交。

**Q8: [learning] 解决 merge 冲突时，冲突标记中的 ours 与 theirs 各指哪边？为什么在 rebase 中含义相反？**

冲突标记中 ours 指当前检出的那一侧，theirs 指正在合入的那一侧。merge 时检出的是你的分支，ours 就是你自己的改动。rebase 时检出的是新基点，theirs 才是你自己的提交。方向搞反会静默丢掉一侧改动，是冲突解决中最典型的误操作。

一次冲突在文件中呈现为三个标记围出的两段内容：

```text
<<<<<<< HEAD
当前检出侧的内容
=======
正在合入侧的内容
>>>>>>> 来源名
```

1. **ours**：`<<<<<<<` 与 `=======` 之间的内容，即当前 HEAD 检出状态的版本。
2. **theirs**：`=======` 与 `>>>>>>>` 之间的内容，即正在应用进来的版本。

两个词在 merge 与 rebase 中方向相反，根源是两者的检出对象不同：

1. **merge**：你在目标分支上执行合并，Git 始终检出你的分支，因此 ours 是你的改动，theirs 是对方分支的改动。
2. **rebase**：Git 先检出目标基点，再把你独有的提交逐个重放上来，检出侧是基点一侧，因此 ours 是基点或已完成重放部分的版本，theirs 反而是你自己的提交。

git checkout --ours -- <文件> 与 git checkout --theirs -- <文件> 遵循同一套映射：rebase 冲突中执行 --ours 会保留基点版本而不是你的修改。Git 2.23 起的 git restore --ours -- <文件>、git restore --theirs -- <文件> 语义相同，同样遵循该映射。

实际解决冲突时不必背诵方向：`>>>>>>>` 标记行显示该段内容的来源，merge 中是对方分支名，rebase 中是被重放提交的说明文字，逐段确认来源再取舍即可。cherry-pick 的方向与 merge 一致：ours 是当前分支，theirs 是被摘取的提交。

**Q9: [learning] 本地工作区有未提交修改时，怎样安全地执行 git pull 拉取远端更新？**

未提交修改与 pull 带入的更新可能冲突，直接 pull 会被拒绝或触发合并。安全的暂存流程：

1. git stash：把工作区与暂存区的本地修改暂存起来，工作区回到干净状态。
2. git pull：拉取并合并远端更新。
3. git stash pop：把暂存的修改放回工作区；若与刚拉入的更新冲突，按冲突解决后正常提交。

更规范的做法是先把本地修改提交成一笔 commit，再执行 git pull --rebase，让本地提交重放到远端更新之上——历史更线性，冲突也在提交粒度上处理。两种方式的选择标准：

1. 临时的半成品改动用 stash。
2. 已有明确意图的改动先提交再 rebase。

**Q10: [learning] git reset 的 --soft、--mixed、--hard 分别回退什么？已推送的提交为什么应该用 git revert 撤销？**

reset 把当前分支指针退回目标提交，三种模式决定暂存区与工作区是否跟着回退；revert 则不改写历史，而是追加一笔内容相反的新提交。未推送的提交按需要保留的内容选 reset 模式，已推送的共享提交用 revert。

三种模式的回退范围依次扩大：

1. **--soft**：只把分支指针退回目标提交，暂存区与工作区保持不变，改动保留为已暂存状态。
2. **--mixed**：默认模式，省略参数时即此行为。退回指针并重置暂存区，工作区文件保持不变，改动保留为未暂存状态。
3. **--hard**：指针、暂存区、工作区全部重置到目标提交，未提交的改动被直接丢弃。

撤销已推送的共享提交时选 revert 而不是 reset，取决于两者对历史的影响：

1. **revert 不改写历史**：它计算目标提交的逆补丁并追加一笔新提交，旧提交原样保留在历史中，协作者正常 pull 即可同步，不会产生分叉。
2. **reset 改写历史**：它把分支指针移回旧位置，目标提交从分支历史中消失，推送后远端与协作者本地历史分叉，只能强制覆盖，触发与 rebase 共享提交相同的协作灾难。

两个操作都不立即删除提交对象：reset 移出的提交短期内仍可通过 reflog 定位找回；revert 甚至不产生不可达对象。因此“会不会丢数据”不是两者的选择依据，“历史是否允许被改写”才是。

**Q11: [learning] git reset --hard 或误删分支后提交“消失”了，怎样用 reflog 找回？哪些改动救不回来？**

reflog 记录 HEAD 在本地的每一次移动——提交、合并、reset、切换分支各留下一条；被移出分支的提交凭条目中的哈希仍在对象库里，执行 git reset --hard <哈希> 或 git branch <名字> <哈希> 即可找回。从未写入对象库的改动救不回来。

找回流程：

1. **定位条目**：执行 git reflog，每行显示一次 HEAD 移动后的位置（如 HEAD@{2}）、提交哈希与操作说明，从中找到目标提交。
2. **恢复引用**：用 git branch <新分支名> <哈希> 把提交固定到分支，或用 git reset --hard <哈希> 把当前分支指回去；后者再次改写当前分支位置，先确认工作区没有需要保留的未提交改动。

提交“消失”只是引用层面的：reflog 条目让对象保持可达，git gc 不会回收它们。保留期由配置决定，gc.reflogExpire 默认 90 天，对已不可达的对象更激进，gc.reflogExpireUnreachable 默认 30 天，到期后条目与对象都可能被 gc 清理，找回要趁早。

救不回来的改动按是否进入过对象库区分：

1. **从未 git add 的工作区修改**：内容从未写入对象库，被 reset --hard 覆盖后无法找回。
2. **已 git add 但未提交的改动**：内容已作为 blob 对象写入，可用 git fsck --lost-found 列出悬空 blob 逐个辨认恢复，但没有文件名与目录结构信息，恢复成本高。

另外 reflog 是纯本地记录，clone 得到的仓库不携带它；换一台机器或新建 clone 无法用 reflog 恢复别处丢失的历史。

**Q12: [learning] 为什么 checkout 某个提交或标签会进入 detached HEAD？此时产生的提交怎么保住？**

detached HEAD 指 HEAD 直接指向某个提交而不是分支名，此时提交照常写入对象库，但不属于任何分支；切回分支后它们失去引用，只能在 reflog 保留期内找回。正确做法是在离开 detached 状态前，把提交固定到新建分支。

进入 detached HEAD 的常见入口：

1. git checkout <提交哈希>：HEAD 直接指向该提交。
2. git checkout <标签>：标签不像分支那样随提交前移，检出标签时 HEAD 落在它指向的提交上，同样脱离分支。
3. rebase 等改写历史的操作内部也工作在 detached 状态，这是它们“检出基底再重放”的实现基础。

风险来自引用缺失：Git 靠“分支 → 提交”的引用链保证对象可达，detached 状态下产生的新提交没有分支指向，切走后成为不可达对象，仅由 reflog 条目维持可达约 90 天，gc 清理后物理删除。

保住提交的方法按所处时机选择：

1. **仍在 detached 状态**：执行 git switch -c <新分支名>（Git 2.23 起可用，旧版本用 git checkout -b 等效），从当前位置创建分支并停留在其上，之后的提交都归该分支。
2. **已经切回其他分支**：先通过 git reflog 找到当时的提交哈希，再执行 git branch <新分支名> <哈希> 固定。

预防比找回便宜：checkout 旧提交只用于查看历史时不产生新提交，就没有丢失风险；确认要基于旧提交改代码时，先建分支再动手。

**Q13: [learning] 在 Gerrit 评审流程下，把特性分支的提交合入主干并送审的完整操作是什么？push 到 refs/for/ 与普通 push 的区别在哪？**

Gerrit 不是“推送即合入”：推送到 refs/for/<目标分支> 不会修改任何分支，而是用这些提交创建待评审的 change，评审通过后由 Gerrit 完成真正的合入。普通 push 到分支名则是直接改写远端分支。完整操作顺序：

1. 同步两条分支：分别在其本地分支上 git pull，保证起点最新。
2. 切到主干分支：git checkout <主干>。
3. 以保留合并节点的方式合入：git merge --no-ff <特性分支>，填写合并提交消息。
4. 送审推送：git push origin <主干>:refs/for/<主干>。

送审要求提交消息携带 Change-Id（由 commit-msg 钩子自动生成），同一笔修改被评审驳回后修改并重新推送时保持 Change-Id 不变，Gerrit 才能把新补丁集挂到同一个 change 下。
