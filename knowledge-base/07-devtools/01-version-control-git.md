# 版本控制与 Git

> 通用开发工具学习资料（学习资料目录 `07-devtools/` 首册）。边界：本文回答"Git 合并、cherry-pick、pull 协作与 Gerrit 评审推送的操作语义与场景选择"；提交纪律与仓库治理等非技术规则归 [../08-exp/](../08-exp/)。Q 序列即结构，供 atlas 同源直读。

**Q1: [learning] git 的整体原理简述？**

Git 本质是内容寻址的快照存储系统：每次提交记录的是当时整个项目目录树的快照而非文件差异，快照按内容的 SHA-1 哈希寻址存储，提交之间经父指针串成历史。工作模型可分三层理解：

1. **对象库**：blob（文件内容）、tree（目录结构）、commit（提交，指向 tree 与父提交）、tag 四类对象构成不可变历史图；哈希相同即内容相同，相同内容天然去重。
2. **三个工作区**：工作目录、暂存区与 HEAD 所指的分支历史；git add 把改动写入暂存区，git commit 把暂存区打包成新的 commit 对象。
3. **分支与引用**：分支只是指向某个 commit 的可移动指针，切换分支就是把 HEAD 指向另一条提交链并重建工作目录；远端跟踪引用（如 origin/main）记录上次同步位置，pull/push 在本地与远端对象库之间搬运对象并移动引用。

由此可推出 Git 的多数行为：提交不可变，所以回退与改写安全（误删可从 reflog 找回）；分支创建成本极低，所以鼓励按特性多分支；合并的本质就是把两条提交链汇合成一个提交。

**Q2: [learning] git 中的 fast-forward 指的是什么？**

快进指合并时 Git 不创建合并提交、只把当前分支指针直接前移到目标提交的情形。发生条件是当前分支自分叉后没有任何独有提交——此时目标分支的提交就是当前分支头的直接延续，移动指针即完成“合并”，历史保持一条直线。

例如 main 分叉后没有新提交而 feature 有三个提交，在 main 上执行 git merge feature 得到的就是快进：main 指针直接移到 feature 的头提交，不产生新对象。与之相对，两条分支都有独有提交时无法快进，Git 只能创建一个有两个父提交的合并提交把两条线汇合。是否可快进可用 git merge-base 判断：分叉点恰为当前分支头即可快进。

**Q3: [learning] 特性分支合回主干时，git merge 什么时候只做快进（fast-forward），什么时候产生真正的合并提交？**

快进只发生在当前分支自分叉点之后没有任何新提交时：当前分支头是特性分支头的祖先，Git 直接把当前分支指针移到特性分支头，不创建提交，历史保持线性。一旦两条分支各自有新提交，快进不可能，Git 会创建一个拥有两个父提交的合并提交，把两条演进线汇合。因此快进与否由"当前分支有没有独有提交"决定，与特性分支有多少提交无关；合并前用 git log --graph 或 git merge-base 查看分叉点即可预判结果。





**Q4: [learning] 明明可以快进，为什么还要用 git merge --no-ff 强制创建合并提交？代价是什么？**

--no-ff 强制生成一个合并提交（有两个父提交），把特性分支的存在和它的提交集合显式留在历史图里。收益主要有两点：

1. **合并点可追溯**：从历史图能直接看出"某段改动作为一个整体在何时合入"；要整体回退一个特性时，revert 这个合并提交即可，不需要逐个辨认其中的普通提交。
2. **分支边界清晰**：快进会让特性分支的提交混入主干线性历史，事后无法区分"哪些提交属于同一个特性"。

代价是历史图出现汇合节点、线性度下降。取舍规则：单人仓库或一次性的小改动，快进更干净；多人共享的主干，保留合并节点通常更可追溯，这也是团队协作中常见推荐 --no-ff 的原因。





**Q5: [learning] git merge --squash 与普通 merge、--no-ff 的结果差在哪里？什么场景适合用它，用它后要注意什么？**

--squash 把特性分支上的全部改动压缩成一个放在当前分支上的新提交：这个提交只有当前分支头一个父提交，历史图上没有合并关系，特性分支内部的多次提交历史也不会进入主干。这与普通 merge（两条分支都有提交时产生双父合并提交）和 --no-ff（强制产生双父合并提交）在"是否保留分支历史与合并关系"上有本质差别。

它适合短生命周期的特性分支：主干只想要一个干净、完整描述这次改动的提交，不关心开发过程的中间状态。用完要注意：因为 Git 不记录"该分支已被合并"，之后对同一分支再执行普通 merge 会把已应用的改动当作新改动引入，所以 squash 合入后应直接删除该特性分支，不要再合并它。





**Q6: [learning] git cherry-pick 的执行语义是什么？它与 merge、rebase 各自的适用边界在哪？**

cherry-pick 取出指定提交的改动内容，把它应用到当前分支头并生成一个新提交：新提交有全新的哈希，与原提交没有对象层面的关联，本质是"把那笔提交的 diff 重放一次"。适用边界按要搬移的内容范围选择：

1. **只搬个别提交**：跨分支搬运单点修复、把某个改动摘到发布分支，用 cherry-pick。
2. **搬整条分支且保留合并关系**：用 merge。
3. **搬整条提交序列并改写基点**：用 rebase。

搬运后两个提交内容相同但哈希不同，追溯时要靠提交消息或 -x 选项（在提交消息中记录 cherry picked from 的来源哈希）建立关联。





**Q7: [learning] cherry-pick 遇到冲突时的继续与取消操作是什么？一次搬多个提交怎么写？**

冲突时的完整流程：

1. 手工解决冲突文件。
2. 用 git add 将解决结果标记完成。
3. 执行 git cherry-pick --continue 应用下一个提交；若想整体放弃，执行 git cherry-pick --abort，回到 cherry-pick 开始前的状态。

多个提交按顺序列出即可：git cherry-pick <哈希1> <哈希2>，或用 <起点>^..<终点> 表示区间。提交按参数顺序逐个应用，中途任何一笔冲突都会停下来等待处理。





**Q8: [learning] 本地工作区有未提交修改时，怎样安全地执行 git pull 拉取远端更新？**

未提交修改与 pull 带入的更新可能冲突，直接 pull 会被拒绝或触发合并。安全的暂存流程：

1. git stash：把工作区与暂存区的本地修改暂存起来，工作区回到干净状态。
2. git pull：拉取并合并远端更新。
3. git stash pop：把暂存的修改放回工作区；若与刚拉入的更新冲突，按冲突解决后正常提交。

更规范的做法是先把本地修改提交成一笔 commit，再执行 git pull --rebase，让本地提交重放到远端更新之上——历史更线性，冲突也在提交粒度上处理。两种方式的选择标准：临时的半成品改动用 stash，已有明确意图的改动先提交再 rebase。





**Q9: [learning] 在 Gerrit 评审流程下，把特性分支的提交合入主干并送审的完整操作是什么？push 到 refs/for/ 与普通 push 的区别在哪？**

Gerrit 不是"推送即合入"：推送到 refs/for/<目标分支> 不会修改任何分支，而是用这些提交创建待评审的 change，评审通过后由 Gerrit 完成真正的合入；普通 push 到分支名则是直接改写远端分支。完整操作顺序：

1. 同步两条分支：分别在其本地分支上 git pull，保证起点最新。
2. 切到主干分支：git checkout <主干>。
3. 以保留合并节点的方式合入：git merge --no-ff <特性分支>，填写合并提交消息。
4. 送审推送：git push origin <主干>:refs/for/<主干>。

送审要求提交消息携带 Change-Id（由 commit-msg 钩子自动生成），同一笔修改被评审驳回后修改并重新推送时保持 Change-Id 不变，Gerrit 才能把新补丁集挂到同一个 change 下。
